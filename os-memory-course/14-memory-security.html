메모리 보안: 하드웨어·OS의 메모리 보호 메커니즘

앞 장들에서 페이지 테이블은 주소 변환 장치였습니다. 같은 엔트리가 "누가, 무엇을 할 수 있는가"도 함께 결정합니다. 이 장에서는 페이지 권한 비트에서 시작해 스택 카나리, 주소 무작위화, 커널/유저 경계 보호, 페이지 테이블 분리, 제어 흐름 무결성 하드웨어, 메모리 태깅, capability까지 차례로 살펴봅니다. 관점은 하나입니다. OS와 하드웨어가 메모리를 어떻게 보호하도록 설계되었고, 그 설계가 메모리 관리 코드에 어떤 비용과 제약을 남겼는가입니다.

학습 목표

  • x86-64 PTE의 R/W·U/S·XD 비트와 ARM64의 대응 비트를 설명하고, 영역별 권한과 W^X 원칙을 판단한다.
  • 스택 카나리가 프레임 어디에 놓이고 에필로그에서 어떻게 검증되는지 명령어 수준으로 따라간다.
  • ASLR·PIE·KASLR이 무작위화하는 대상과 엔트로피를 계산하고, RELRO가 GOT를 어떻게 보호하는지 설명한다.
  • SMEP/SMAP, KPTI, PCID가 커널/유저 경계를 어떻게 지키고 TLB 비용을 어떻게 줄이는지 설명한다.
  • 섀도 스택, PAC/BTI, MTE, CHERI가 각각 무엇을 보호하는지 구분하고, 메모리 안전 언어와의 관계를 정리한다.

1. 페이지 권한 비트와 W^X 원칙

5장에서 본 x86-64 PTE에는 주소 말고도 권한 비트가 있습니다. 보호와 직접 관련된 비트는 네 개입니다.

  • P(bit 0, Present): 0이면 어떤 접근이든 페이지 폴트가 납니다. Linux는 PROT_NONE 매핑을 "Present를 끄고 소프트웨어 비트로 표시"하는 방식으로 구현합니다.
  • R/W(bit 1): 0이면 읽기 전용입니다. 커널 모드 쓰기도 막으려면 CR0.WP=1이어야 하며, Linux는 항상 켭니다.
  • U/S(bit 2): 1이면 유저 모드(CPL 3)가 접근할 수 있습니다. 0이면 커널 전용입니다.
  • XD(bit 63, Execute Disable, AMD 용어로 NX): EFER.NXE=1일 때 1이면 이 페이지에서 명령어를 인출할 수 없습니다.

여기서 눈여겨볼 점이 두 가지입니다. 첫째, x86-64에는 읽기 금지 비트가 없습니다. Present이면 읽을 수 있습니다. 그래서 "쓰기 전용"이나 "실행 전용(execute-only)"은 PTE만으로 표현할 수 없습니다. Linux는 CPU가 보호 키(PKU)를 지원하면 실행 전용 매핑을 보호 키로 흉내 냅니다. 둘째, 권한은 모든 레벨의 엔트리를 합성해 결정됩니다. PML4·PDPT·PD·PT 중 하나라도 R/W=0이면 읽기 전용, 하나라도 U/S=0이면 커널 전용, 하나라도 XD=1이면 실행 불가입니다. 상위 레벨 한 비트로 512GiB 범위를 한꺼번에 막을 수 있다는 뜻이고, 5절의 KPTI가 이 성질을 이용합니다.

유저 공간에서는 mmap·mprotect의 PROT_READ/WRITE/EXEC가 이 비트로 번역되고, 결과는 /proc/PID/maps의 rwxp 열에 그대로 보입니다. 정상적인 프로세스에서 각 영역이 어떤 권한을 갖는지가 곧 OS 보호 설계의 기본형입니다.

W^X: 쓰기와 실행은 동시에 허용하지 않는다

W^X(Write XOR Execute)는 "어떤 페이지도 쓰기 가능하면서 동시에 실행 가능해서는 안 된다"는 원칙입니다. 배경은 단순합니다. 과거에는 스택이나 힙에 쓰인 데이터가 그대로 명령어로 실행될 수 있었고, 데이터 쓰기 버그 하나가 곧 임의 코드 실행으로 번졌습니다. NX 비트와 W^X는 "데이터는 데이터로만, 코드는 코드로만" 쓰이도록 경계를 하드웨어로 강제합니다.

  • ELF 로더: 링커가 세그먼트별 권한(PT_LOAD의 p_flags)을 정하고, 커널의 load_elf_binary()가 그대로 매핑합니다. 스택의 실행 여부는 PT_GNU_STACK 헤더로 결정되며, readelf -lW a.out | grep GNU_STACK에서 RW이면 실행 불가 스택입니다.
  • 커널 자신: CONFIG_STRICT_KERNEL_RWX와 CONFIG_STRICT_MODULE_RWX가 커널·모듈의 text를 읽기 전용+실행, 데이터를 실행 불가로 만듭니다. 커널 text를 고쳐야 하는 ftrace나 static key는 별도의 임시 매핑을 통해 씁니다.
  • 유저 공간 강제: Linux는 기본적으로 RWX 매핑을 허용합니다(JIT 호환성). 강제하려면 SELinux의 execmem 정책, systemd의 MemoryDenyWriteExecute=, 또는 Linux 6.3에 추가된 prctl(PR_SET_MDWE, PR_MDWE_REFUSE_EXEC_GAIN, …)를 씁니다.
JIT는 W^X를 어떻게 지키나

JIT 컴파일러는 코드를 "쓰고" 나서 "실행"해야 합니다. 대표적인 방법은 세 가지입니다. (1) 권한 토글: 쓸 때 rw-, 실행할 때 mprotect로 r-x. 단순하지만 mprotect마다 TLB shootdown 비용이 듭니다. (2) 이중 매핑: 같은 물리 페이지(예: memfd)를 두 가상 주소에 rw-와 r-x로 따로 매핑합니다. 페이지 하나를 두 VMA가 공유한다는, 11장에서 본 구조의 응용입니다. (3) 스레드별 토글: Apple Silicon의 MAP_JIT+pthread_jit_write_protect_np(), x86 PKU의 pkey_mprotect+WRPKRU처럼 페이지 테이블을 고치지 않고 레지스터 하나로 현재 스레드의 권한만 바꿉니다. TLB를 건드리지 않으므로 빠릅니다.

페이지 권한 매트릭스와 W^X 판정
영역을 고르면 일반적인 Linux x86-64 프로세스에서의 권한과 그 이유가 표시됩니다. R/W/X를 바꿔 W^X 위반, 기능 실패(필요한 권한 부족), 최소 권한 위반(불필요한 권한)을 판정해 보세요.

2. 스택 보호: 카나리와 가드 페이지

스택에는 지역 배열과 함께 반환 주소와 저장된 프레임 포인터가 섞여 있습니다. 배열 경계를 넘는 쓰기 버그(예: 길이 검사 없는 strcpy)는 그 위의 제어 데이터를 덮을 수 있고, 함수가 반환하는 순간 엉뚱한 주소로 점프합니다. NX는 "스택의 데이터가 실행되는 것"을 막지만, 제어 데이터가 손상되는 것 자체는 막지 못합니다. 스택 카나리는 이 손상을 반환 직전에 탐지하는 컴파일러+런타임 장치입니다.

카나리의 위치와 출처

컴파일러(GCC/Clang의 -fstack-protector-strong, 많은 배포판의 기본값)는 보호 대상 함수의 프롤로그에서 비밀 값 하나를 지역 변수와 저장된 rbp 사이에 넣고, 에필로그에서 그 값이 그대로인지 확인합니다. 아래로 자라는 스택에서 배열 끝을 넘는 쓰기는 높은 주소로 진행하므로, 반환 주소에 닿기 전에 반드시 카나리를 먼저 덮습니다.

  • 값의 출처: 커널이 execve 때 보조 벡터의 AT_RANDOM으로 16바이트 난수를 전달하고, glibc가 이를 바탕으로 카나리를 만들어 TLS(x86-64에서는 %fs:0x28)에 둡니다. 프로세스마다 다르고, 같은 프로세스 안에서는 모든 함수가 공유합니다.
  • 최하위 바이트 0: glibc 카나리의 첫 바이트는 0입니다. C 문자열 함수가 카나리 값을 그대로 이어 출력하거나 복사하지 못하게 하려는 설계입니다.
  • 변수 재배치: 컴파일러는 배열을 카나리 바로 아래에 두고 스칼라 지역 변수와 포인터는 그보다 아래에 둡니다. 배열 오버플로가 다른 지역 변수를 먼저 오염시키지 않게 하려는 것입니다.
  • 실패 처리: 불일치하면 __stack_chk_fail()이 호출되어 *** stack smashing detected ***: terminated를 출력하고 abort()(SIGABRT)로 끝냅니다. 손상된 프레임으로 반환하지 않는 것이 핵심입니다.
함수 호출과 반환: 카나리 저장과 검증
함수 f()가 호출되어 프레임을 만들고, 카나리를 저장하고, 반환 직전에 비교하는 과정을 단계별로 봅니다. "버그 시나리오"를 켜면 16바이트 버퍼에 24바이트를 복사하는 버그가 생기고, 에필로그에서 이를 탐지합니다.

스택의 다른 보호 장치

  • 가드 페이지와 stack_guard_gap: 커널은 자라는 스택 VMA 아래에 접근 불가 간격을 두어 스택이 다른 매핑과 맞닿지 않게 합니다. 2017년 이후 기본 간격은 256페이지(4KiB 페이지에서 1MiB)이며 부팅 파라미터 stack_guard_gap=로 조정합니다. 컴파일러의 -fstack-clash-protection은 큰 스택 할당을 페이지 단위로 나눠 건드려서, 이 간격을 한 번에 건너뛰지 못하게 합니다.
  • 커널 스택의 가드: CONFIG_VMAP_STACK은 커널 스레드 스택을 vmalloc 영역에 두어 양옆에 매핑되지 않은 가드 페이지를 둡니다. 커널 스택 오버플로가 조용한 메모리 손상 대신 즉시 폴트로 드러납니다(9장의 vmalloc 참고).
  • 섀도 콜 스택: 반환 주소를 일반 스택과 분리된 두 번째 스택에 따로 저장하는 방식입니다. 소프트웨어 구현(Clang의 ShadowCallStack, arm64 커널의 CONFIG_SHADOW_CALL_STACK)과 하드웨어 구현(6절의 Intel CET)이 있습니다.
카나리의 한계

카나리는 "연속된 오버플로가 반환 직전까지 이어진 경우"만 잡습니다. 카나리를 건너뛰는 인덱스 쓰기, 함수 포인터 같은 다른 지역 변수의 손상, 힙 손상은 보지 못하며, 검사는 반환 시점에만 일어납니다. 그래서 카나리는 단독 방어가 아니라 NX·ASLR·CFI와 겹쳐 쓰는 한 층으로 설계되었습니다.

3. 주소 무작위화: ASLR, PIE, KASLR, RELRO

NX로 "주입한 코드 실행"을 막아도, 이미 메모리에 있는 코드와 데이터의 주소를 알고 있다면 버그를 악용할 여지가 남습니다. ASLR(Address Space Layout Randomization)은 실행할 때마다 주요 영역의 시작 주소를 무작위로 바꿔 그 전제를 깨뜨립니다. 보호의 강도는 "추측해야 하는 비트 수", 즉 엔트로피로 표현합니다.

Linux의 ASLR 수준

/proc/sys/kernel/randomize_va_space(sysctl kernel.randomize_va_space)가 전체 수준을 정합니다.

값무작위화 대상
0없음. 모든 영역이 고정 주소. 디버깅 외에는 쓰지 않습니다(프로세스 단위로는 setarch -R로 끌 수 있고, gdb도 기본으로 이렇게 실행합니다).
1스택, mmap 베이스(공유 라이브러리, 익명 mmap), vDSO, PIE 실행 파일의 로드 주소
2 (기본)1의 모든 것 + brk 힙 시작 주소

x86-64 기본값 기준으로 mmap 베이스와 PIE 로드 주소는 페이지 단위 28비트(vm.mmap_rnd_bits, 28~32 사이로 조정 가능, 32비트 호환 프로세스는 vm.mmap_rnd_compat_bits 기본 8), 스택 꼭대기는 페이지 단위 22비트에 페이지 내 오프셋까지 무작위화됩니다.

PIE: 실행 파일 자신도 움직이게

ASLR이 켜져 있어도 실행 파일이 고정 주소(x86-64 non-PIE는 관례적으로 0x400000)에 링크되어 있으면 그 text와 데이터는 움직일 수 없습니다. PIE(Position Independent Executable, -fPIE -pie)로 빌드하면 실행 파일이 ELF 타입 ET_DYN이 되고, 커널이 공유 라이브러리처럼 무작위 주소에 로드합니다. 현재 주요 배포판의 GCC는 PIE를 기본으로 켭니다. x86-64는 RIP 상대 주소 지정이 있어 PIE의 성능 비용이 작습니다. 범용 레지스터 하나를 GOT 포인터로 묶어야 했던 i386과는 다릅니다. file a.out이 pie executable이라고 표시하면 PIE입니다.

ASLR 시뮬레이터: 실행할 때마다 바뀌는 주소 공간
"다시 실행"을 누를 때마다 새 프로세스의 레이아웃이 만들어집니다. 직전 실행과 달라진 주소는 주황색으로 표시됩니다. 값은 x86-64 Linux 기본값(mmap·PIE 28비트, 스택 22비트)을 따르며, brk 무작위 범위는 커널 버전에 따라 다르므로 여기서는 32MiB(13비트)로 가정했습니다.

레이아웃은 execve에서 정해집니다. fork한 자식은 부모의 주소 공간을 그대로 복제하므로(11장의 COW) 같은 레이아웃을 공유합니다. 워커를 fork만으로 다시 띄우는 서버는 모든 워커가 같은 배치를 갖습니다. Android의 zygote처럼 fork 기반으로 앱을 띄우는 구조가 ASLR 관점에서 꾸준히 논의되는 이유이고, 보안상 중요한 프로세스는 exec로 재시작해 새 레이아웃을 받게 설계합니다.

KASLR: 커널도 움직인다

커널 이미지도 고정 주소에 있으면 같은 문제가 생깁니다. KASLR(CONFIG_RANDOMIZE_BASE)은 부팅할 때마다 커널 이미지의 물리 주소와 가상 주소를 무작위로 정합니다. x86-64에서는 커널 text가 1GiB 범위 안에 2MiB 정렬로 놓이므로 위치의 수는 많아야 512개(9비트)이고 실제로는 커널 크기만큼 더 적습니다. 유저 ASLR보다 엔트로피가 훨씬 작습니다. 그래서 KASLR은 주소 정보 노출을 막는 장치와 짝을 이뤄야 의미가 있습니다. kernel.kptr_restrict(/proc/kallsyms 등에서 커널 포인터 숨김), kernel.dmesg_restrict가 그 역할을 합니다. x86-64의 CONFIG_RANDOMIZE_MEMORY는 direct map, vmalloc, vmemmap 영역의 베이스도 무작위화합니다. 끄려면 커널 커맨드라인에 nokaslr을 줍니다.

RELRO: 재배치가 끝난 데이터는 읽기 전용으로

동적 링크된 프로그램은 GOT(Global Offset Table)에 외부 함수·변수의 주소를 담습니다. 동적 링커가 실행 중에 이 표를 채워야 하므로 GOT는 원래 쓰기 가능한 데이터입니다. 쓰기 가능한 함수 포인터 표는 메모리 손상 버그가 제어 흐름으로 번지는 통로가 되기 쉽습니다. RELRO(RELocation Read-Only)는 재배치가 끝난 영역을 mprotect로 읽기 전용으로 바꿉니다.

  • Partial RELRO(-Wl,-z,relro): .got, .dynamic, .init_array 등 PT_GNU_RELRO 세그먼트를 재배치 직후 읽기 전용으로 만듭니다. 지연 바인딩(lazy binding)에 쓰이는 .got.plt는 쓰기 가능하게 남습니다.
  • Full RELRO(-Wl,-z,relro,-z,now): 시작할 때 모든 심볼을 즉시 바인딩(BIND_NOW)하므로 .got.plt까지 읽기 전용이 됩니다. 대가는 시작 시간 증가입니다. 심볼이 많은 대형 프로그램에서 눈에 띌 수 있습니다.

확인은 readelf -lW a.out | grep GNU_RELRO(세그먼트 존재)와 readelf -d a.out | grep -E 'BIND_NOW|FLAGS'(즉시 바인딩)로 합니다. 메모리 관리 관점에서 RELRO는 "VMA 하나를 쪼개 일부 페이지만 권한을 바꾸는" mprotect의 전형적인 사용 예입니다. /proc/PID/maps에서 라이브러리 하나가 r--p, r-xp, r--p(RELRO), rw-p 여러 줄로 보이는 이유입니다.

4. 커널/유저 경계 1: SMEP와 SMAP

Linux는 커널과 유저가 하나의 가상 주소 공간을 나눠 씁니다(유저는 하위 절반, 커널은 상위 절반). U/S 비트가 유저의 커널 접근을 막지만, 반대 방향, 즉 커널이 유저 페이지를 건드리는 것은 원래 막지 않았습니다. 커널은 특권이 더 높으니 어디든 접근할 수 있었던 것입니다. 이 때문에 커널의 함수 포인터 하나가 오염되면 커널이 유저가 마음대로 채운 페이지의 코드를 실행하거나, 유저 페이지에 놓인 가짜 구조체를 믿고 읽는 문제가 생겼습니다. 두 개의 CR4 비트가 이 방향을 막습니다.

  • SMEP(Supervisor Mode Execution Prevention, CR4 bit 20): 커널 모드(CPL 0~2)에서 U/S=1인 페이지의 명령어를 인출하면 페이지 폴트가 납니다. "커널은 유저 메모리를 실행하지 않는다"를 하드웨어가 강제합니다.
  • SMAP(Supervisor Mode Access Prevention, CR4 bit 21): 커널 모드에서 U/S=1인 페이지를 읽거나 쓰면 페이지 폴트가 납니다. 단, RFLAGS.AC(bit 18)가 1인 동안은 허용합니다.

커널은 시스템 콜 인자를 유저 버퍼에서 읽어야 하므로 SMAP을 영구히 켜 둘 수는 없습니다. 그래서 stac(Set AC)와 clac(Clear AC) 명령어로 정해진 짧은 구간에서만 유저 접근을 엽니다. Linux에서는 copy_from_user(), copy_to_user(), get_user(), put_user(), 그리고 user_access_begin()/user_access_end() 쌍이 그 구간입니다. 커널 코드가 __user 포인터를 직접 역참조하면 SMAP 폴트(oops)가 나므로, 이 규칙을 지키지 않은 코드가 바로 드러납니다. objtool은 AC가 켜진 구간에서 임의 함수를 호출하는 코드를 빌드 시점에 경고합니다.

CPU 지원은 grep -o -w 'smep\|smap' /proc/cpuinfo | sort -u로 확인합니다. 커널 커맨드라인 nosmep, nosmap으로 끌 수 있지만, 이는 문제 진단용입니다. 비용은 매우 작습니다. SMEP는 공짜에 가깝고, SMAP은 유저 복사 구간마다 stac/clac 두 명령어가 추가될 뿐입니다.

5. 커널/유저 경계 2: KPTI와 PCID

2018년 초에 공개된 Meltdown과 Spectre는 CPU의 투기 실행(speculative execution)이 권한 검사보다 먼저 데이터를 캐시에 남길 수 있다는 문제였습니다. 특히 Meltdown은 영향받는 CPU에서 유저 모드 코드가 "매핑은 되어 있지만 U/S=0이라 접근 불가"인 커널 메모리의 내용을 캐시 부채널로 추론할 수 있게 했습니다. U/S 비트만으로는 경계가 충분하지 않다는 뜻이었고, OS 쪽 대응이 유저 모드에서는 커널 메모리를 아예 매핑하지 않는 것이었습니다. Spectre 계열은 페이지 테이블이 아니라 분기 예측을 다루는 다른 대책(retpoline, IBRS 등)이 필요하며 이 장의 범위 밖입니다.

페이지 테이블 두 벌

KPTI(Kernel Page-Table Isolation, Linux 4.15. 개발 당시 이름은 KAISER)는 프로세스마다 최상위 테이블(PGD)을 두 벌 둡니다.

  • 커널용 PGD: 유저 매핑 + 커널 전체. 커널 모드에서 씁니다. 이 사본에서는 유저 영역 엔트리에 NX를 걸어, SMEP가 없는 CPU에서도 커널이 유저 코드를 실행하지 못하게 합니다.
  • 유저용 PGD: 유저 매핑 + 커널 진입·탈출에 꼭 필요한 최소 부분(진입 트램펄린, cpu_entry_area의 IDT·GDT·TSS·진입 스택 등)만. 유저 모드에서 씁니다.

두 PGD는 8KiB로 정렬된 연속 두 페이지에 붙어 있어서 CR3의 bit 12 하나만 뒤집으면 전환됩니다. 시스템 콜·인터럽트·예외로 커널에 들어올 때마다 진입 코드의 SWITCH_TO_KERNEL_CR3가 CR3를 커널용으로, 나갈 때 SWITCH_TO_USER_CR3가 유저용으로 바꿉니다. 하위 레벨 테이블(PUD 이하)은 두 PGD가 공유하므로 메모리 비용은 프로세스당 4KiB 정도입니다.

비용과 PCID

문제는 TLB입니다. CR3에 쓰면 기본적으로 global이 아닌 TLB 엔트리가 모두 무효화됩니다. KPTI에서는 커널 매핑을 대부분 global로 둘 수 없으므로, 시스템 콜 한 번마다 두 번의 플러시와 그 뒤의 페이지 워크가 생깁니다. 시스템 콜이 잦은 워크로드(작은 I/O, 네트워크 서버, 데이터베이스)에서 눈에 띄는 성능 저하가 보고된 이유입니다.

PCID(Process-Context IDentifier, CR3 하위 12비트)가 이 비용을 줄입니다. TLB 엔트리에 PCID 태그를 붙여, CR3를 바꿔도 다른 PCID의 엔트리를 버리지 않을 수 있습니다. CR3에 쓸 때 bit 63(NOFLUSH)을 1로 주면 새 PCID의 기존 엔트리도 유지됩니다. Linux는 커널용과 유저용 PCID를 bit 11 하나로 구분합니다(유저 PCID = 커널 PCID | 0x800). 4장의 ASID와 같은 발상입니다.

KPTI 시스템 콜 왕복: CR3 전환과 TLB
유저 모드에서 시스템 콜 하나를 처리하고 돌아오는 과정입니다. PCID를 끄고 켜며 TLB에 남는 엔트리를 비교해 보세요. CR3 값은 커널 PGD가 물리 주소 0x12340a000, PCID가 1인 예입니다.

상태 확인과 제어는 다음으로 합니다.

# 현재 CPU의 취약성과 적용된 대책
cat /sys/devices/system/cpu/vulnerabilities/meltdown
#   Mitigation: PTI      ← KPTI 사용 중
#   Not affected         ← 하드웨어가 영향받지 않음 (KPTI 불필요)
dmesg | grep -i 'page tables isolation'
grep -o -w 'pcid\|invpcid' /proc/cpuinfo | sort -u

# 커널 커맨드라인 (x86): pti=on | pti=off | pti=auto, nopti
# arm64: kpti=  (커널을 EL0에서 매핑 해제하는 같은 개념)
현업에서의 판단

KPTI는 영향받는 CPU에서만 켜집니다(pti=auto가 기본). AMD CPU와 하드웨어 수정이 들어간 최근 Intel CPU는 "Not affected"로 표시되고 KPTI 비용이 없습니다. 오래된 하드웨어에서 성능 회귀를 분석할 때는 먼저 이 파일을 확인하고, PCID 지원 여부를 보세요. PCID가 없는 CPU에서 KPTI 비용이 가장 큽니다.

6. 제어 흐름 무결성 하드웨어: CET, PAC, BTI

카나리는 반환 직전에 "아마도 손상됐다"를 추정하고, ASLR은 주소를 숨깁니다. 둘 다 확률적 방어입니다. 제어 흐름 무결성(CFI) 하드웨어는 더 직접적인 질문을 합니다. "이 반환은 정말 대응하는 호출로 돌아가는가?", "이 간접 분기의 목적지는 분기해도 되는 곳인가?"

Intel CET 섀도 스택

CET(Control-flow Enforcement Technology)의 섀도 스택(SHSTK)은 반환 주소만 담는 두 번째 스택입니다. call은 반환 주소를 일반 스택과 섀도 스택(SSP 레지스터가 가리킴)에 모두 넣고, ret는 두 값을 꺼내 비교합니다. 다르면 #CP(Control Protection, 벡터 21) 예외가 발생하고, Linux는 유저 프로세스에 SIGSEGV를 보냅니다.

메모리 관리 관점에서 흥미로운 점은 섀도 스택 페이지의 표현입니다. 일반 mov로 섀도 스택을 쓸 수 있으면 의미가 없으므로, 섀도 스택은 PTE의 R/W=0이면서 Dirty=1인 특수 조합으로 표시됩니다. 이 페이지에는 call, ret와 전용 명령어만 쓸 수 있고 일반 쓰기는 폴트가 납니다. 그런데 기존 Linux는 COW 대상 페이지를 "읽기 전용인데 dirty"로 만들 수 있었습니다. 그래서 커널은 이 조합이 섀도 스택으로 오인되지 않도록, 일반 페이지를 쓰기 금지할 때 Dirty 비트를 소프트웨어 비트(SavedDirty)로 옮기는 작업을 해야 했습니다. 새 보호 기능이 PTE 비트 해석을 바꾸면 메모리 관리 코드 전체가 영향을 받는다는 좋은 예입니다.

  • 유저 공간 섀도 스택은 Linux 6.6부터 지원됩니다. 커널이 스레드마다 섀도 스택을 할당하고(map_shadow_stack 시스템 콜로 추가 할당 가능), 양옆에 가드 간격을 둡니다.
  • 바이너리는 -fcf-protection=full로 빌드해 ELF의 .note.gnu.property에 SHSTK/IBT 지원을 표시하고, 로더와 런타임이 모든 모듈이 지원할 때만 켭니다.
  • 하드웨어: Intel은 11세대(Tiger Lake)부터, AMD는 Zen 3부터 섀도 스택을 지원합니다.
섀도 스택: call/ret에서 두 스택 비교
main → f → g 호출과 반환을 따라갑니다. "버그 시나리오"를 켜면 f의 본문에서 버그가 일반 스택의 반환 주소를 덮어쓰고, f가 반환할 때 섀도 스택과 비교해 #CP가 발생합니다.

간접 분기 추적: IBT와 BTI

반환이 아닌 간접 call/jmp(함수 포인터, 가상 함수, switch 점프 테이블)는 섀도 스택이 보지 못합니다. Intel CET의 IBT(Indirect Branch Tracking)는 간접 분기의 목적지가 endbr64 명령어로 시작하지 않으면 #CP를 냅니다. 컴파일러는 주소가 취해지는 함수의 입구에만 endbr64를 넣으므로, 함수 중간으로 뛰어드는 간접 분기가 막힙니다. Linux 커널은 5.18부터 커널 자체에 IBT를 적용합니다(CONFIG_X86_KERNEL_IBT).

ARM의 BTI(Branch Target Identification, ARMv8.5-A)도 같은 발상입니다. 간접 분기의 목적지는 bti c(call 목적지), bti j(jump 목적지) 같은 랜딩 패드여야 합니다. 차이는 페이지 단위로 켠다는 점입니다. stage 1 PTE의 GP(Guarded Page) 비트가 1인 페이지에서만 검사하며, Linux는 BTI를 지원하는 ELF의 코드 세그먼트를 PROT_BTI로 매핑해 이 비트를 켭니다. BTI를 모르는 오래된 라이브러리는 GP=0으로 매핑되어 그대로 동작하므로, 점진적 도입이 가능합니다.

ARM PAC: 포인터에 서명하기

ARMv8.3-A의 PAC(Pointer Authentication Code)는 별도 스택 없이 포인터 자체를 보호합니다. 64비트 포인터 중 가상 주소로 쓰이지 않는 상위 비트에 암호학적 서명(PAC)을 넣습니다.

  • 프롤로그의 paciasp가 반환 주소 레지스터(LR)에 서명합니다. 키는 커널이 관리하는 128비트 비밀 키(APIAKey 등, 프로세스마다 다름), 수정자(modifier)는 현재 SP입니다.
  • 에필로그의 autiasp(또는 retaa)가 서명을 검증하고 PAC 비트를 걷어 냅니다. 실패하면 포인터가 무효 주소로 바뀌어 사용 시 폴트가 나고, FEAT_FPAC가 있는 CPU에서는 검증 즉시 예외가 납니다.
  • PAC에 쓸 수 있는 비트 수는 가상 주소 크기와 TBI(Top Byte Ignore) 설정에 따라 달라집니다. 48비트 VA라면 대략 7~15비트입니다.
  • 빌드: -mbranch-protection=standard(PAC-RET + BTI). 커널: CONFIG_ARM64_PTR_AUTH, CONFIG_ARM64_BTI. Apple의 arm64e ABI는 반환 주소 외의 코드·데이터 포인터에도 PAC를 넓게 적용합니다.
섀도 스택 vs PAC: 설계 선택의 차이

섀도 스택은 반환 주소의 사본을 메모리에 두고 페이지 권한으로 보호합니다. 결정적이지만 스택이 하나 더 필요하고, 페이지 테이블 비트 해석이 바뀝니다. PAC는 레지스터의 비밀 키로 서명하므로 추가 메모리가 없고 반환 주소 외의 포인터에도 쓸 수 있지만, 서명 비트 수만큼의 확률적 보호입니다. 두 방식 모두 "제어 데이터를 일반 데이터와 다르게 다룬다"는 같은 원칙에서 나왔습니다.

7. 메모리 태깅: ARM MTE

지금까지의 기법은 주로 제어 데이터(반환 주소, 함수 포인터)를 지켰습니다. 하지만 메모리 안전 버그의 뿌리는 "포인터가 자기 객체 밖을 가리키거나(공간적 오류), 이미 해제된 객체를 가리키는 것(시간적 오류)"입니다. MTE(Memory Tagging Extension, ARMv8.5-A)는 이 뿌리를 하드웨어로 검사합니다.

  • 할당 태그(allocation tag): 물리 메모리 16바이트 granule마다 4비트 태그를 별도의 태그 저장소에 둡니다. 메모리 오버헤드는 4/128 = 1/32(약 3.1%)입니다.
  • 주소 태그(logical tag): 포인터의 bit 59:56에 4비트 태그를 넣습니다. TBI(Top Byte Ignore) 덕분에 상위 바이트는 주소 변환에서 무시되므로, 태그가 붙은 포인터도 정상 주소로 동작합니다.
  • 검사: 태그 검사가 켜진 페이지에 load/store를 하면 하드웨어가 포인터 태그와 해당 granule의 할당 태그를 비교합니다. 다르면 태그 검사 폴트입니다.
  • 할당자의 역할: malloc은 IRG로 무작위 태그를 고르고 STG/ST2G/STZG로 객체 영역의 granule에 태그를 씁니다. 이웃 객체와 다른 태그를 골라 경계 넘침을 확실히 잡고, free 시 재태깅해서 해제 후 사용(use-after-free)을 잡습니다.

검사 모드: 동기, 비동기, 비대칭

  • 동기(sync): 불일치한 명령어에서 즉시 정밀한 예외가 납니다. 접근은 실행되지 않습니다. Linux는 SIGSEGV(si_code = SEGV_MTESERR)와 정확한 폴트 주소를 줍니다. 디버깅에 적합하지만 비용이 가장 큽니다.
  • 비동기(async): 불일치를 레지스터(TFSR)에 기록만 하고 접근은 진행됩니다. 커널은 다음 커널 진입(시스템 콜, 문맥 전환 등) 때 이를 확인해 SIGSEGV(SEGV_MTEAERR)를 보내며, 주소 정보는 없습니다. 비용이 작아 프로덕션에 적합합니다.
  • 비대칭(asymm, ARMv8.7): 읽기는 동기, 쓰기는 비동기로 검사합니다.

Linux에서 유저 프로세스는 prctl(PR_SET_TAGGED_ADDR_CTRL, PR_TAGGED_ADDR_ENABLE | PR_MTE_TCF_SYNC | (마스크 << PR_MTE_TAG_SHIFT), 0, 0, 0)로 모드를 고르고, 태그 검사할 메모리를 mmap/mprotect의 PROT_MTE로 표시합니다. 커널 자신은 CONFIG_KASAN_HW_TAGS(하드웨어 태그 기반 KASAN)로 slab·page 할당에 MTE를 씁니다. Android의 Scudo 할당자가 MTE를 지원하며, Pixel 8이 일반 소비자 기기 중 처음으로 MTE를 사용할 수 있게 했습니다.

MTE 실습: 할당, 해제, 접근과 태그 검사
256바이트(16 granule) 힙 영역입니다. 각 칸의 큰 글자가 할당 태그(16진수), 점선 칸이 해제된 영역입니다. 할당하면 이웃·이전 태그와 다른 무작위 태그(1~F)가 붙은 포인터가 생깁니다. 포인터와 오프셋을 골라 읽기/쓰기를 해 보고, 해제한 포인터로 다시 접근해 보세요. 비동기 모드에서는 폴트가 "커널 진입" 때 보고됩니다.

검사 단위가 16바이트이므로, 20바이트 객체(실제로는 32바이트 = 2 granule 차지)의 오프셋 20~31 접근은 같은 태그라 통과합니다. 태그가 4비트라 무관한 메모리에 우연히 같은 태그가 있을 확률도 1/16 근처입니다. 그래서 MTE는 "모든 버그를 확정적으로 막는 장치"가 아니라, 대부분의 메모리 안전 버그를 낮은 비용으로 높은 확률로 탐지하는 장치로 이해해야 합니다.

8. CHERI capability와 메모리 안전 언어

CHERI: 포인터를 capability로 바꾸기

MTE가 "포인터와 메모리에 확률적 태그를 붙이는" 접근이라면, CHERI(Capability Hardware Enhanced RISC Instructions)는 포인터 자체를 권한 증명서(capability)로 바꿉니다. 64비트 주소 체계에서 capability는 128비트이고, 메모리에는 128비트마다 별도의 1비트 유효성 태그가 붙습니다.

OS 관점에서는 페이지 테이블·스왑·fork 모두가 capability 태그를 보존해야 합니다. 스왑 아웃할 때 태그 비트를 따로 저장하는 것처럼 메모리 관리 코드 곳곳에 손이 갑니다. 연구용 OS인 CheriBSD가 이를 구현했고, Arm의 Morello 시제품 보드(2022)에서 돌아갑니다. 상용 CPU에 널리 들어간 단계는 아니지만, 공간적 메모리 안전을 하드웨어로 결정적으로 보장하는 가장 구체적인 설계입니다.

메모리 안전 언어와 OS 대책의 관계

Microsoft와 Chromium 프로젝트는 각각 자기 제품의 심각한 보안 버그 중 약 70%가 메모리 안전 문제라고 발표했습니다. 근본 대책은 처음부터 그런 버그가 생기지 않는 언어를 쓰는 것입니다. Rust는 소유권과 빌림 검사로 safe 코드에서 use-after-free, 이중 해제, 데이터 경쟁을 컴파일 시점에 막고, 슬라이스 접근은 런타임 경계 검사로 막습니다. Linux 커널은 6.1부터 Rust로 드라이버 등을 작성할 수 있는 기반을 넣었습니다.

그렇다고 이 장의 OS·하드웨어 대책이 쓸모없어지지는 않습니다.

  • unsafe와 FFI: Rust 프로그램도 C 라이브러리(libc, OpenSSL 등)를 부르고, 저수준 코드는 unsafe 블록에서 작성합니다. 그 경계 밖은 여전히 C의 규칙을 따릅니다.
  • 언어가 보지 못하는 층: JIT이 만든 코드, 하드웨어 투기 실행(5절), 물리 메모리 비트 플립(9절)은 언어의 타입 시스템 밖입니다.
  • 기존 코드: 수십억 줄의 C/C++ 코드가 계속 돌아갑니다. NX, ASLR, CET, MTE는 재작성 없이 그 위험을 줄입니다.

정리하면 메모리 안전 언어는 "버그가 생기지 않게", OS·하드웨어 대책은 "생긴 버그가 피해로 이어지지 않게" 합니다. 둘은 대체 관계가 아니라 서로 다른 층의 방어입니다.

9. 물리 메모리 수준: Rowhammer와 ECC/TRR

지금까지의 보호는 모두 "메모리에 저장된 비트는 쓴 그대로 남는다"를 전제로 했습니다. Rowhammer(2014년 학계 보고)는 이 전제가 깨질 수 있음을 보였습니다. DRAM의 한 행(row)을 짧은 시간에 매우 많이 활성화하면, 셀이 조밀한 최신 DRAM에서는 이웃 행의 전하가 누설되어 접근 권한이 없는 인접 행의 비트가 뒤집힐 수 있습니다. 페이지 테이블의 권한 검사는 가상 주소 수준에서 일어나므로, 물리적 간섭을 막지 못합니다.

대응은 주로 메모리 하드웨어 쪽에 있습니다.

  • ECC: 서버용 ECC DIMM은 64비트당 8비트 검사 비트로 1비트 오류를 정정하고 2비트 오류를 탐지합니다(SECDED). 여러 비트가 한꺼번에 뒤집히면 정정하지 못할 수 있지만, 탐지만 해도 조용한 손상을 막습니다. Linux EDAC가 오류를 집계하며 /sys/devices/system/edac/mc/mc*/ce_count(정정됨), ue_count(정정 불가)로 확인합니다.
  • TRR(Target Row Refresh): DDR4 세대의 DRAM·메모리 컨트롤러가 자주 활성화되는 행을 추적해 이웃 행을 미리 리프레시합니다. 구현이 제조사마다 다르고 완전하지 않다는 연구가 있어, DDR5는 RFM(Refresh Management)과 on-die ECC 같은 장치를 더했습니다.
  • 리프레시 주기 단축: 리프레시를 더 자주 하면 누설 시간이 줄어듭니다. 전력과 대역폭을 대가로 치릅니다.

메모리 관리와의 접점은 이렇습니다. 커널의 메모리 오류 처리(memory_failure(), hwpoison)는 정정 불가 오류가 난 물리 페이지를 격리하고, 그 페이지를 매핑한 프로세스에 SIGBUS를 보냅니다. 물리 계층의 문제도 결국 페이지 단위로 수습됩니다.

각 기법은 버그가 피해로 번지는 경로의 서로 다른 지점을 끊습니다. 메모리 안전 언어와 MTE·CHERI는 버그 자체를 막거나 잡고, 카나리·섀도 스택·PAC·CFI는 제어 흐름 탈취를 막고, NX·W^X·RELRO는 쓸 수 있는 곳과 실행할 수 있는 곳을 분리하고, ASLR·KASLR은 필요한 정보를 숨기고, SMEP·SMAP·KPTI는 권한 경계를 지킵니다. 하나가 뚫려도 다음 층이 남도록 겹쳐 두는 것이 설계 목표입니다.

핵심 요약

  • x86-64 PTE의 R/W·U/S·XD 비트가 페이지 권한을 정하고, 유효 권한은 4단계 엔트리의 합성입니다. 읽기 금지 비트는 없어서 실행 전용은 PKU 같은 별도 장치가 필요합니다.
  • W^X는 쓰기와 실행을 동시에 허용하지 않는 원칙입니다. 커널은 STRICT_KERNEL_RWX로 강제하고, JIT은 권한 토글·이중 매핑·스레드별 토글로 지킵니다.
  • 스택 카나리는 지역 배열과 저장된 rbp 사이에 놓이고, 에필로그에서 TLS 원본(%fs:0x28)과 비교해 다르면 __stack_chk_fail로 중단합니다.
  • ASLR(randomize_va_space 0/1/2)은 스택·mmap·PIE·brk의 베이스를 무작위화합니다. 추측 확률은 1/2ⁿ이고, x86-64 mmap은 28비트, KASLR은 9비트 이하입니다. RELRO는 재배치가 끝난 GOT를 읽기 전용으로 만듭니다.
  • SMEP/SMAP은 커널이 유저 페이지를 실행·접근하지 못하게 하고, stac/clac로 연 짧은 구간에서만 유저 메모리를 복사합니다.
  • KPTI는 유저 모드에서 커널을 매핑하지 않도록 PGD를 두 벌 두고, 커널 진입·탈출마다 CR3를 바꿉니다. PCID와 NOFLUSH 비트가 TLB 플러시 비용을 줄입니다.
  • CET 섀도 스택은 반환 주소를 W=0·D=1 특수 페이지에 따로 두고 ret에서 비교합니다(#CP). IBT·BTI는 간접 분기 목적지를 랜딩 패드로 제한하고, PAC는 포인터 상위 비트에 서명합니다.
  • MTE는 16바이트 granule마다 4비트 태그를 두고 포인터 태그와 비교합니다. 할당 시 이웃과 다른 태그, 해제 시 재태깅으로 오버플로와 UAF를 높은 확률로 잡습니다. 동기 모드는 정밀, 비동기 모드는 저비용입니다.
  • CHERI는 경계·권한이 든 capability로 공간적 안전을 결정적으로 보장합니다. 메모리 안전 언어와 OS·하드웨어 대책은 서로를 대체하지 않고 다른 층을 지킵니다.
  • Rowhammer처럼 물리 계층의 비트 플립은 페이지 권한으로 막을 수 없고, ECC·TRR·리프레시 같은 메모리 하드웨어와 커널의 hwpoison 처리가 대응합니다.

프롤로그가 TLS의 원본을 [rbp-8]에 복사하고, 에필로그가 ret 전에 두 값을 비교합니다. 다르면 __stack_chk_fail()이 호출되어 손상된 반환 주소를 쓰기 전에 프로세스를 중단합니다. 검사 시점이 반환 직전뿐이라는 것이 카나리의 한계이기도 합니다.
kernel.randomize_va_space를 2에서 1로 바꾸면 무엇이 달라지나요?
1은 스택, mmap 베이스, vDSO, PIE 로드 주소를 무작위화하고, 2는 여기에 brk 힙 시작 주소를 더합니다. 0이면 모두 고정입니다.
SMAP이 켜진 커널의 read() 시스템 콜 경로가 유저 버퍼에 데이터를 써야 합니다. 올바른 동작은?
SMAP은 RFLAGS.AC=1인 동안만 커널의 유저 페이지 접근을 허용합니다. stac/clac는 한 명령어씩이라 비용이 작고, 허용 구간을 사용자 복사 함수 안으로 좁힙니다. CR4를 바꾸는 것은 비싸고 모든 코드에 창을 여는 셈이며, SMAP은 읽기와 쓰기를 모두 막습니다.
KPTI가 켜진 시스템에서 PCID가 성능에 도움이 되는 이유는?
PCID 없이 CR3에 쓰면 global이 아닌 TLB 엔트리가 모두 사라져, 시스템 콜마다 커널과 유저 양쪽에서 페이지 워크가 반복됩니다. PCID는 엔트리에 주소 공간 태그를 붙여 공존하게 합니다. Linux는 커널 PCID와 유저 PCID를 bit 11로 구분합니다. CR3 전환 자체는 여전히 일어납니다.
MTE가 켜진 힙에서 p = malloc(20)을 받았습니다. 이웃 객체와 태그가 다르다고 할 때, p[28]을 읽으면?
태그는 16바이트 granule 단위로 붙습니다. 20바이트는 올림해서 2 granule(오프셋 0~31)을 차지하고 둘 다 같은 태그이므로 28은 통과합니다. 오프셋 32 이상은 다음 객체의 granule이라 태그가 달라 폴트가 납니다. MTE의 검사 단위가 granule이라는 한계를 보여 줍니다.
Intel CET 섀도 스택 페이지는 페이지 테이블에서 어떻게 표시되나요?
"쓰기 금지인데 dirty"라는, 원래 하드웨어가 만들지 않는 조합을 섀도 스택 표시로 재정의했습니다. 일반 store는 막히고 call/ret와 전용 명령어만 쓸 수 있습니다. 이 때문에 Linux는 COW 등으로 쓰기 금지된 일반 페이지의 Dirty 비트를 소프트웨어 비트로 옮겨, 섀도 스택으로 오인되지 않게 해야 했습니다.
