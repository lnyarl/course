가상화와 메모리: EPT, Ballooning, KSM

가상 머신 안의 "물리 메모리"는 사실 호스트 프로세스의 가상 메모리다. 주소 변환이 한 단계 더 늘어나면서 생기는 비용, 그 비용을 하드웨어로 줄이는 방법, 그리고 VM 수십 대가 실제 RAM보다 많은 메모리를 "약속"받는 오버커밋 기법을 차례로 해부한다.

학습 목표

  • GVA → GPA → HPA 세 주소 공간과 각 변환을 누가 관리하는지 설명할 수 있다.
  • 섀도 페이지 테이블과 EPT/NPT의 동작과 비용 구조를 비교하고, 2D page walk가 최대 24회 메모리 참조가 되는 이유를 직접 셀 수 있다.
  • VPID/ASID 태깅, EPT violation 처리 경로(KVM)를 이해한다.
  • Ballooning, KSM, 호스트 스왑, free page reporting, 메모리 핫플러그의 원리와 함정을 안다.
  • 컨테이너와 VM의 메모리 격리 차이, 기밀 컴퓨팅(SEV-SNP, TDX)이 메모리 관리에 주는 제약을 설명할 수 있다.

1. 주소가 세 단계가 된다: GVA → GPA → HPA

게스트 OS는 자기가 물리 메모리 전체를 소유한다고 믿고 페이지 테이블을 만든다. 하지만 하이퍼바이저 입장에서 그 "물리 메모리"는 여러 VM이 나눠 쓰는 진짜 DRAM의 일부일 뿐이다. 그래서 주소 공간이 셋으로 나뉜다.

주소의미변환 주체KVM에서의 실체
GVA (Guest Virtual)게스트 프로세스가 보는 가상 주소게스트 OS의 페이지 테이블 (게스트 CR3)게스트 리눅스의 mm_struct
GPA (Guest Physical)게스트가 "물리"라고 믿는 주소하이퍼바이저 (섀도 PT 또는 EPT/NPT)memslot: GPA 범위 → QEMU 프로세스의 HVA
HPA (Host Physical)실제 DRAM 주소—호스트 커널이 QEMU의 HVA에 붙여 준 물리 프레임

KVM에서 핵심은 GPA → HPA가 두 단계로 다시 쪼개진다는 점이다. QEMU(VMM)는 mmap()으로 게스트 RAM 크기만큼 익명(또는 hugetlbfs·memfd) 메모리를 잡고, KVM_SET_USER_MEMORY_REGION ioctl로 "GPA 0x0~ 는 내 HVA 0x7f.. 이다"라는 memslot을 등록한다. 그러면 GPA→HVA는 memslot의 단순 오프셋 계산, HVA→HPA는 평범한 호스트 프로세스의 페이지 테이블이다.

왜 이 설계가 강력한가 게스트 RAM이 "QEMU 프로세스의 평범한 가상 메모리"이므로, 호스트 커널이 프로세스에 적용하는 모든 메커니즘 — 요구 페이징, THP, 스왑, KSM, NUMA 밸런싱, cgroup 메모리 제한, 페이지 마이그레이션 — 이 VM 메모리에 그대로 적용된다. 하이퍼바이저가 메모리 관리자를 따로 만들 필요가 없다. 반대로 말하면, 앞 장에서 배운 호스트 쪽 함정(스왑 스톰, THP 컴팩션 지연, NUMA 원격 접근)도 그대로 VM 성능 문제로 나타난다.

2. 소프트웨어 해법: 섀도 페이지 테이블

2008년 이전의 x86 CPU에는 두 번째 변환 단계를 하드웨어로 해 주는 기능이 없었다. MMU는 CR3가 가리키는 페이지 테이블 하나만 걸을 수 있다. 그래서 하이퍼바이저는 게스트 PT(GVA→GPA)와 자신의 매핑(GPA→HPA)을 합성한 GVA→HPA 테이블을 따로 만들어 실제 CR3에 넣었다. 이것이 섀도 페이지 테이블(sPT)이다.

문제는 동기화다. 게스트가 자기 PT를 고치면 섀도도 고쳐야 하는데, 하이퍼바이저는 그 사실을 모른다. 그래서:

  • 게스트 PT 페이지를 쓰기 금지(write-protect)한다. 게스트가 PTE를 쓰면 폴트 → VM exit → 하이퍼바이저가 쓰기를 에뮬레이트하고 섀도 PTE를 갱신한다.
  • 게스트의 CR3 쓰기(컨텍스트 스위치), INVLPG도 가로챈다(trap). 프로세스마다 섀도 테이블 집합을 캐시해야 한다.
  • 게스트가 본 적 없는 섀도 엔트리는 비워 두고, 실제 접근 시 #PF를 가로채 게스트 PT를 소프트웨어로 걸어 채운다(“hidden page fault”).
  • Accessed/Dirty 비트도 게스트 PT에 역으로 반영해야 한다.

KVM은 지금도 섀도 MMU 코드를 유지한다. EPT를 끈 경우(kvm_intel.ept=0)뿐 아니라, 중첩 가상화(L1 하이퍼바이저가 만든 EPT를 L0가 다시 섀도링: "shadow EPT")에서도 쓰이기 때문이다.

3. 하드웨어 해법: Intel EPT / AMD NPT

Intel은 Nehalem(2008)에서 EPT(Extended Page Tables)를, AMD는 Barcelona(2007)에서 NPT(Nested Page Tables, RVI)를 도입했다. 하이퍼바이저는 GPA→HPA 테이블을 만들어 VMCS의 EPTP 필드(AMD는 VMCB의 nCR3)에 넣고, 게스트는 자기 CR3를 마음대로 바꾼다. 하드웨어 page walker가 둘을 엮어 걷는다.

EPTP 자체에는 비트 2:0 = 페이징 구조 메모리 타입, 비트 5:3 = page-walk length − 1 (4단계면 3, 5단계면 4), 비트 6 = A/D 활성화가 들어간다. 게스트 PTE에는 없던 "실행 전용(X만 1)" 권한이 가능하다는 점도 특징이다(하이퍼바이저 기반 보안 도구들이 이를 활용).

X 권한이 분리된 이유 게스트 커널이 손상돼도 하이퍼바이저가 "이 GPA는 실행 불가"를 강제할 수 있다. Windows의 HVCI(VBS) 같은 하이퍼바이저 기반 코드 무결성은 EPT의 X·MBEC를 이용한다. 게스트 페이지 테이블은 게스트 커널이 조작할 수 있지만 EPT는 게스트 커널 손이 닿지 않는 곳에 있기 때문이다.

4. 2D page walk: 왜 최대 24회인가

TLB 미스가 나면 하드웨어는 게스트 페이지 테이블을 걸어야 한다. 그런데 게스트 CR3와 게스트 PTE 안의 주소는 모두 GPA다. 게스트 테이블 한 칸을 읽으려면 먼저 그 테이블의 GPA를 EPT로 HPA로 바꿔야 한다. 즉 게스트 walk의 매 단계마다 EPT walk가 하나씩 끼어든다.

  • 게스트 레벨 수 n, EPT 레벨 수 m일 때, 게스트 테이블 n개 + 최종 데이터 GPA 1개 = n+1개의 GPA를 변환해야 한다. 각각 m회 참조 → m(n+1).
  • 여기에 게스트 엔트리 자체를 읽는 n회가 더해진다.
  • 총합 m(n+1) + n = nm + n + m = (n+1)(m+1) − 1. n=m=4이면 24, 5단계 페이징끼리면 35.
2D page walk 격자 애니메이션

현실에서는 왜 24배 느리지 않은가

  • TLB가 최종 GVA→HPA를 캐시한다. 24회 walk는 TLB 미스 때만 일어난다.
  • Paging-structure cache(PML4/PDPT/PDE 캐시)와 nested TLB(GPA→HPA 변환 캐시)가 대부분의 중간 참조를 건너뛰게 한다. 상위 레벨 엔트리는 재사용률이 매우 높다.
  • walk의 참조는 대부분 L1/L2 캐시에서 해결된다. 하지만 working set이 큰 워크로드(DB, 인메모리 캐시, JVM 대형 힙)는 TLB 미스율이 높아 2D walk 비용이 수~수십 % 오버헤드로 드러난다.
현업 처방: 양쪽 다 huge page 게스트만 2MiB를 쓰면 게스트 레벨이 3으로, 호스트만 쓰면 EPT 레벨이 3으로 준다(위 위젯에서 24→19). 둘 다 2MiB면 15, 호스트 1GiB면 더 줄어든다. 그래서 대형 VM은 호스트에서 hugetlbfs(QEMU -mem-path 또는 memory-backend-memfd,hugetlb=on)로 게스트 RAM을 잡는다. 단, EPT가 2MiB 리프를 쓰려면 호스트 쪽에서 해당 GPA 범위가 물리적으로 연속된 2MiB 프레임에 매핑돼 있어야 한다. 호스트 THP가 쪼개지면(split) EPT 리프도 4KiB로 쪼개진다.

5. 섀도 vs EPT: 어떤 워크로드에서 누가 이기나

EPT가 항상 이기는 것은 아니다. 섀도 PT는 TLB 미스 비용이 네이티브와 같지만 PT 수정·CR3 전환마다 VM exit 비용을 낸다. EPT는 반대다. 아래 계산기는 이 트레이드오프를 교육용 단순 모델로 보여 준다(실제 비용은 CPU 세대·캐시 상태에 따라 크게 달라진다).

6. TLB 태깅: VPID와 ASID

VM 두 개가 같은 GVA 0x400000을 쓰더라도 HPA는 다르다. TLB 엔트리가 "어느 VM 것인지" 모르면 VM 전환(그리고 VM exit/entry) 때마다 TLB를 통째로 비워야 한다. VM exit는 I/O, 인터럽트, 타이머마다 초당 수천~수만 번 일어나므로 이것은 치명적이다.

  • Intel VPID(Virtual Processor ID): 16비트 태그. VMCS에 VPID를 넣으면 TLB 엔트리가 VPID로 구분된다. VPID 0은 호스트(VMX root)용. 무효화는 INVVPID, EPT 기반 캐시 무효화는 INVEPT.
  • AMD ASID: VMCB의 ASID 필드. ASID 0은 호스트. 무효화는 VMCB의 TLB_CONTROL 또는 INVLPGA.
  • 게스트 내부에서는 다시 PCID(게스트 프로세스 구분)가 함께 쓰인다. 즉 TLB 엔트리는 사실상 (VPID, PCID, GVA) 조합으로 식별된다.

7. EPT violation과 KVM의 지연 할당

게스트가 접근한 GPA에 대해 EPT 엔트리가 없거나 권한이 부족하면 EPT violation VM exit(Intel exit reason 48)가 난다. AMD에서는 #NPF(VMEXIT_NPF, exit code 0x400). VMCS에는 문제의 GPA(GUEST_PHYSICAL_ADDRESS)와 exit qualification(읽기/쓰기/실행 중 무엇이었는지, GVA가 유효한지 등)이 담긴다. 엔트리 형식 자체가 잘못된 경우는 별도의 EPT misconfiguration(exit reason 49)이며, KVM은 이를 일부러 이용해 MMIO 접근을 빠르게 식별한다(MMIO GPA에 예약 비트 패턴을 넣어 둠).

KVM 처리 경로 (x86, TDP MMU)

  1. handle_ept_violation() → kvm_mmu_page_fault()
  2. GPA로 memslot을 찾아 HVA 계산
  3. HVA → 호스트 PFN: hva_to_pfn() 계열 함수(커널 버전마다 이름이 조금씩 바뀌어 왔다). 이 단계가 사실상 QEMU 프로세스에서의 평범한 페이지 폴트다. 처음 접근이면 호스트가 0으로 채운 페이지를 할당하고, 스왑아웃된 페이지면 스왑인(느림 → async page fault로 게스트에게 다른 일을 시킬 수 있음)
  4. EPT 엔트리(SPTE)를 설치. 호스트 매핑이 THP/hugetlb면 2MiB/1GiB 리프로 설치 가능
  5. VM entry로 게스트 명령 재실행

즉 게스트가 "16GiB RAM 부팅"해도 실제로 건드린 페이지만 호스트 RAM을 소비한다. 이것이 메모리 오버커밋의 출발점이다. 반대로, 호스트가 페이지를 회수하면 MMU notifier가 KVM에 알려 해당 EPT 엔트리를 지우고 TLB를 flush한다. 호스트 MM과 "2차 MMU(EPT)"를 일관되게 유지하는 장치다.

라이브 마이그레이션과 dirty 추적 라이브 마이그레이션은 메모리를 복사하는 동안 게스트가 다시 더럽힌 페이지를 계속 재전송한다. 더럽혀진 페이지를 알아내는 방법은 (1) EPT를 쓰기 금지로 바꿔 쓰기마다 violation을 받거나, (2) EPT D 비트 + Intel PML(Page Modification Logging: 하드웨어가 더럽혀진 GPA를 512엔트리 버퍼에 기록하고, 가득 차면 VM exit)을 쓰는 것이다. KVM은 이 정보를 dirty bitmap 또는 dirty ring(5.11+)으로 QEMU에 넘긴다. 쓰기가 아주 많은 VM은 dirty rate가 전송 대역폭을 넘어 마이그레이션이 끝나지 않는데, 이때 auto-converge(vCPU 스로틀링)나 post-copy를 쓴다.

8. 오버커밋 ①: Ballooning

호스트 RAM 256GiB에 32GiB VM을 12대 올리면(합 384GiB) 오버커밋이다. 평소엔 게스트들이 메모리를 다 쓰지 않아 괜찮지만, 게스트가 한번 만진 페이지는 게스트가 해제해도 호스트는 알 수 없다. 게스트 OS의 free list에 있는 페이지는 호스트 관점에서는 여전히 "사용 중"이다. 이 의미적 간극(semantic gap)을 메우는 첫 번째 방법이 ballooning이다.

게스트 안에 balloon 드라이버(리눅스 drivers/virtio/virtio_balloon.c)가 있다. 호스트가 목표치(num_pages, 4KiB 단위)를 설정하면, 드라이버는 게스트 커널에게서 평범하게 페이지를 할당받아 움켜쥐고 그 PFN(GPA) 목록을 inflate virtqueue로 호스트에 알린다. 호스트(QEMU)는 해당 범위를 madvise(MADV_DONTNEED)로 버려 실제 프레임을 회수한다. 게스트 커널이 메모리를 내주는 과정은 일반 할당과 똑같으므로, 게스트 내부 free가 부족하면 게스트 자신의 회수 로직(페이지 캐시 축출, 스왑)이 돈다. 하이퍼바이저가 게스트 내부 사정을 몰라도, 무엇을 버릴지는 게스트가 가장 잘 고른다는 것이 핵심 아이디어다.

Ballooning의 함정

  • 게스트 협조가 필수: 드라이버가 없거나 게스트가 멈춰 있으면 회수 불가. 악의적 게스트는 무시할 수 있다(그래서 호스트 스왑이 최후 수단으로 남는다).
  • 느리다: 페이지 단위 할당 → virtqueue 통지 → 호스트 madvise. 수 GiB 회수에 수 초 이상 걸릴 수 있어 갑작스런 압박엔 부적합.
  • 과하게 부풀리면 게스트 OOM: 기본적으로 풍선 페이지는 게스트 MemTotal에서 빠진다. VIRTIO_BALLOON_F_DEFLATE_ON_OOM 기능이 협상되면 게스트가 OOM 직전 스스로 풍선을 줄인다(대신 MemTotal을 줄이지 않음).
  • huge page 단편화: 풍선이 4KiB 페이지를 흩어서 가져가면 호스트 쪽 2MiB 매핑이 쪼개져 EPT도 4KiB가 된다(→ 2D walk 비용 증가). 리눅스는 balloon 페이지를 compaction 시 옮길 수 있게 만들어(balloon compaction) 게스트 쪽 단편화를 완화한다.
  • 장치 패스스루(VFIO)로 게스트 메모리가 pin된 VM은 ballooning·KSM·호스트 스왑이 사실상 불가능하다. DMA가 언제든 그 HPA를 쓸 수 있기 때문이다.

9. 오버커밋 ②: KSM (Kernel Samepage Merging)

같은 OS 이미지로 부팅한 VM 50대는 커널 코드, 공유 라이브러리, 0으로 채운 페이지 등 내용이 바이트 단위로 같은 페이지를 엄청나게 많이 갖는다. KSM은 커널 스레드 ksmd가 주기적으로 페이지를 훑어 같은 내용을 찾아 하나의 쓰기 금지 프레임으로 병합하고, 누군가 쓰면 CoW로 다시 분리한다.

  • 대상: madvise(MADV_MERGEABLE)로 표시된 익명 영역(QEMU는 게스트 RAM에 이를 건다). 리눅스 6.4+는 prctl(PR_SET_MEMORY_MERGE)로 프로세스 전체를 대상으로 할 수 있다.
  • 제어: /sys/kernel/mm/ksm/run(1=동작), pages_to_scan, sleep_millisecs. 통계: pages_shared(병합된 KSM 페이지 수), pages_sharing(그것을 추가로 공유하는 매핑 수 = 절약량), pages_unshared, pages_volatile, full_scans.
  • 자료구조: 병합 완료 페이지의 stable tree와 후보 페이지의 unstable tree. 둘 다 페이지 내용 자체를 키로 하는 red-black tree(비교는 memcmp)다. 체크섬은 "직전 스캔 이후 내용이 바뀌었나(volatile)"를 거르는 용도로만 쓴다. 바뀌는 페이지를 트리에 넣으면 트리 순서가 깨지기 때문에, unstable tree는 매 전체 스캔마다 비우고 다시 짓는다.

KSM의 비용과 보안 문제

  • CPU 비용: ksmd가 페이지를 비교하는 데 CPU를 쓴다. pages_to_scan을 키우면 병합은 빨라지지만 코어 하나를 상당 부분 태울 수 있다.
  • 쓰기 지연: 병합된 페이지에 쓰면 CoW 폴트 + 복사 + EPT 갱신이 일어나 평소 쓰기보다 훨씬 느리다. 메모리를 아끼던 호스트가 "역병합 폭풍"으로 갑자기 메모리 부족에 빠질 수도 있다.
  • 사이드채널: 바로 그 쓰기 지연이 정보 누출 통로다. 공격자 VM이 "피해자에게 있을 법한 내용"의 페이지를 만들어 두고 병합 주기를 기다린 뒤 써 본다. 쓰기가 느리면 병합됐다는 뜻 → 다른 VM에 같은 내용이 존재함을 알게 된다(설치된 소프트웨어·버전 탐지, 일부 ASLR 우회 연구 사례). 더 나아가 병합된 페이지를 Rowhammer로 뒤집어 다른 VM의 페이지를 오염시키는 공격(Flip Feng Shui, 2016)도 시연됐다.
그래서 퍼블릭 클라우드는 VM 간 KSM을 끈다 서로 신뢰하지 않는 테넌트 사이의 메모리 중복 제거는 사이드채널 위험이 너무 크다. KSM은 같은 조직의 VDI·테스트 환경처럼 신뢰 경계 안에서 밀도를 높일 때 주로 쓴다. 기밀 VM(12절)은 메모리가 VM별 키로 암호화돼 내용이 같아도 암호문이 달라지므로 KSM이 원천적으로 효과가 없다.

10. 오버커밋 ③: 호스트 스왑, free page reporting, 메모리 핫플러그

호스트 스왑: 최후의 수단

게스트 RAM은 QEMU의 익명 메모리이므로 호스트가 그냥 스왑아웃할 수 있다. 게스트 협조가 필요 없다는 장점이 있지만 무엇을 내보낼지 호스트는 잘 모른다. 대표적 문제가 이중 페이징(double paging)이다: 호스트가 이미 스왑아웃한 페이지를 게스트도 "오래 안 쓴 페이지"로 골라 자기 스왑에 쓰려 한다 → 그 페이지를 읽는 순간 호스트 스왑인 → 게스트는 디스크에 쓰고 해제 → 디스크 I/O 두 번, 이득 없음. 또한 게스트 커널 코드나 스핀락이 들어 있는 페이지가 스왑아웃되면 vCPU 전체가 멈춰 게스트 쪽에서 soft lockup 경고가 뜨기도 한다. 그래서 호스트 스왑은 ballooning이 따라가지 못하는 갑작스러운 압박을 흡수하는 안전망으로 쓰고, zswap 같은 압축 계층과 함께 쓰는 경우가 많다.

Free page reporting (리눅스 5.7+)

ballooning은 "목표치만큼 빼앗는" 방식이라 게스트가 손해를 본다. free page reporting(VIRTIO_BALLOON_F_REPORTING, mm/page_reporting.c)은 게스트 버디 할당자의 free list 중 큰 덩어리(기본 pageblock_order, x86-64에서 2MiB 이상)를 주기적으로 호스트에 알려 호스트가 백킹 프레임을 버리게 한다. 페이지는 여전히 게스트 free list에 남아 있고, 게스트가 다시 할당해 접근하면 EPT violation → 호스트가 새로 0 페이지를 붙여 준다. 목표치 관리가 필요 없고 게스트 MemTotal도 줄지 않는다.

reporting이 회수하지 못하는 것: 게스트 페이지 캐시 리눅스 게스트는 남는 메모리를 페이지 캐시로 다 채운다. free가 아니므로 reporting 대상이 아니다. 그래서 오래 돈 VM은 실제로 쓰지 않는 캐시로 호스트 메모리를 점유한다. 대책으로 게스트에서 주기적 proactive reclaim(cgroup v2 memory.reclaim, DAMON 기반 회수)을 돌리거나, 호스트 측에서 free page reporting과 결합한다.

비슷한 이름의 free page hinting(VIRTIO_BALLOON_F_FREE_PAGE_HINT)은 라이브 마이그레이션 시 "이 페이지는 free니 전송하지 않아도 된다"고 알려 주는 별도 기능이다.

메모리 핫플러그

  • ACPI DIMM 핫플러그(QEMU pc-dimm): 가상 DIMM을 꽂으면 게스트가 메모리 블록을 인식한다. 리눅스는 메모리를 memory block 단위(x86-64에서 보통 128MiB 이상, /sys/devices/system/memory/block_size_bytes)로 관리하고, /sys/devices/system/memory/memoryN/state에 online/offline을 쓰거나 memhp_default_state/auto_online_blocks 정책으로 자동 온라인한다.
  • 핫언플러그는 어렵다: 블록 안의 모든 페이지를 다른 곳으로 옮겨야 하는데, 커널 객체(slab, 페이지 테이블)는 옮길 수 없다. 그래서 언플러그할 메모리는 ZONE_MOVABLE로 온라인해야 한다(online_movable). 대신 ZONE_MOVABLE 비중이 너무 크면 커널 할당이 가능한 영역이 부족해지는 트레이드오프가 있다.
  • virtio-mem(리눅스 5.8+): 게스트 협조형으로 서브블록(예: 2MiB) 단위 plug/unplug. DIMM 단위보다 세밀하고, 언플러그 실패 시 다른 서브블록을 시도할 수 있다. ballooning의 "부풀린 페이지"와 달리 진짜로 게스트 메모리 크기를 바꾸는 방식이라 NUMA 노드 단위 관리에도 적합하다.

12. 기밀 컴퓨팅: SEV-SNP와 TDX

지금까지의 모든 기법은 하이퍼바이저가 게스트 메모리를 읽고 바꿀 수 있다는 전제 위에 있었다. 기밀 컴퓨팅은 그 전제를 뒤집는다. 클라우드 운영자(하이퍼바이저·호스트 커널·관리자)도 게스트 메모리를 볼 수 없게 하는 것이 목표다.

AMD SEV → SEV-ES → SEV-SNPIntel TDX
암호화메모리 컨트롤러의 AES 엔진, VM별 키(ASID로 선택). 게스트 PTE의 C-bit로 페이지별 암호화 여부 지정 (위치는 CPUID 0x8000001F EBX[5:0])MKTME 기반, 물리 주소 상위 비트의 HKID(키 ID)로 키 선택. GPA의 shared 비트로 private/shared 구분

메모리 관리에 주는 제약

  • I/O는 shared 페이지로: 장치(가상 NIC 등)는 암호문을 해석할 수 없으므로 게스트는 bounce buffer(SWIOTLB)를 shared로 표시해 거기서 데이터를 주고받는다. I/O 처리량이 떨어지는 이유다.
  • 페이지 수락(acceptance): 게스트는 쓰기 전에 페이지를 검증·수락해야 한다. 부팅 시 전체를 수락하면 대형 VM 부팅이 매우 느려지므로 리눅스는 6.5부터 unaccepted memory를 지원해 처음 할당될 때 지연 수락한다.
  • 오버커밋 기법 대부분이 무력화: KSM은 효과 없음(키가 달라 암호문이 다름), 호스트 스왑·마이그레이션은 별도 펌웨어 지원이 필요, 많은 구현에서 게스트 private 메모리를 pin한다. 리눅스 6.8의 guest_memfd(KVM_CREATE_GUEST_MEMFD)는 private 메모리를 호스트 유저 공간 매핑 없이 관리하는 기반이다. ballooning은 게스트 협조 방식이라 개념적으로 가능하다.
  • RMP/Secure EPT 검사 비용: 하이퍼바이저 쪽 메모리 접근과 페이지 상태 변경에 추가 검사가 붙는다. 상태 변경(private↔shared 전환)이 잦은 워크로드는 성능 영향이 크다.

핵심 요약

  • 가상화된 메모리는 GVA → GPA → HPA 3단계다. KVM에서 GPA는 QEMU 프로세스의 HVA이므로 호스트 MM 기능이 VM 메모리에 그대로 적용된다.
  • 섀도 PT는 TLB 미스가 싸지만 게스트 PT 수정마다 VM exit. EPT/NPT는 그 반대이며, 2D walk는 최대 nm+n+m회(4×4 → 24회) 참조한다.
  • 2D walk 비용은 TLB·paging-structure cache·nested TLB와 양쪽 huge page로 줄인다. EPT 2MiB 리프는 호스트 백킹이 연속 2MiB일 때만 가능하다.
  • VPID/ASID는 TLB 엔트리에 VM 태그를 붙여 VM exit/전환 시 flush를 없앤다. EPT 변경 시에는 여전히 INVEPT와 원격 flush가 필요하다.
  • EPT violation은 KVM에서 사실상 "QEMU 프로세스의 페이지 폴트"로 이어진다. 지연 할당이 오버커밋을 가능하게 하고, MMU notifier가 호스트 회수와 EPT를 동기화한다.
  • 오버커밋: ballooning(게스트가 페이지를 골라 반납), free page reporting(free 덩어리 자동 보고), KSM(동일 페이지 병합, 사이드채널 주의), 호스트 스왑(최후 수단, 이중 페이징), virtio-mem/DIMM 핫플러그.
  • 컨테이너는 같은 커널 위의 회계·한도, VM은 하드웨어 주소 공간 분리. 기밀 VM(SEV-SNP/TDX)은 VM별 키 암호화와 소유권 테이블로 하이퍼바이저조차 메모리를 못 보게 하며, 그 대가로 대부분의 오버커밋 기법을 잃는다.

확인 문제

게스트 4단계 페이징 + 호스트 EPT 4단계(모두 4KiB)에서 TLB와 모든 페이지 워크 캐시가 비어 있을 때, 데이터 접근 직전까지 필요한 최대 메모리 참조 횟수는?
n·m + n + m = 16 + 4 + 4 = 24. 5개의 GPA(게스트 테이블 4개 + 데이터)를 각각 EPT 4회로 변환(20회)하고 게스트 엔트리 4개를 읽는다(4회). 데이터 접근 자체를 포함하면 25회다.
VPID(또는 AMD ASID)가 주로 해결하는 문제는?
TLB 엔트리에 VM 태그를 붙여 서로 다른 VM(그리고 호스트)의 변환이 공존할 수 있게 한다. 따라서 전환 때 flush가 필요 없다. 2D walk 비용 자체는 줄이지 않는다.
KSM이 서로 신뢰하지 않는 VM 사이에서 보안 위험이 되는 핵심 이유는?
병합 페이지는 쓰기 금지 상태라 쓰기 시 CoW 분리가 일어나고 지연이 크다. 이 타이밍 차이가 "같은 내용의 페이지가 다른 VM에 있다"는 정보를 누출한다. 직접 읽는 것은 불가능하다.
Free page reporting과 ballooning의 차이로 옳은 것은?
reporting은 virtio-balloon 드라이버를 통해 동작하며(게스트 협조), pageblock_order 이상 덩어리만 보고한다. 페이지 캐시는 free가 아니므로 대상이 아니다.
fork/exec가 초당 수만 번 일어나는 빌드 서버 VM에서 섀도 페이지 테이블이 특히 불리한 이유는?
섀도 방식은 게스트 PT 페이지를 쓰기 금지해 동기화하므로, 주소 공간을 자주 만들고 바꾸는 워크로드에서 VM exit가 폭증한다. 2D walk는 EPT 쪽 비용이다.
AMD SEV-SNP의 RMP(Reverse Map Table)가 하는 일은?
암호화만으로는 하이퍼바이저가 암호문 페이지를 다른 GPA에 매핑하거나 옛 내용을 되돌려 놓는 공격을 막을 수 없다. RMP가 페이지 소유권과 검증 상태를 강제해 이를 막는다.
