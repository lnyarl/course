Linux 메모리 회수, swap, OOM, cgroup

Linux는 남는 메모리를 놀리지 않고 캐시로 채웁니다. 그래서 진짜 질문은 "메모리가 얼마나 남았나"가 아니라 "필요할 때 얼마나 빨리, 싸게 되찾을 수 있나"입니다. 이 장은 그 회수 장치들, 즉 워터마크, kswapd, LRU, swap, OOM killer, cgroup을 하나의 그림으로 묶고, 운영에서 보는 숫자를 읽는 법까지 다룹니다.

학습 목표

  • 존 워터마크(min/low/high)와 kswapd 백그라운드 회수, direct reclaim, OOM으로 이어지는 단계를 설명할 수 있다.
  • 익명 페이지와 파일 페이지의 회수 비용 차이, LRU 리스트(active/inactive × anon/file)의 이동 규칙, MGLRU의 아이디어를 안다.
  • swappiness의 정확한 의미와 swap, swap cache, zswap/zram의 역할을 구분한다.
  • OOM killer의 점수 계산(oom_badness, oom_score, oom_score_adj)으로 희생자를 예측할 수 있다.
  • cgroup v2 메모리 컨트롤(memory.min/low/high/max, memory.events)과 컨테이너 OOMKilled, 쿠버네티스 requests/limits의 연결을 이해한다.
  • free, /proc/meminfo, vmstat를 해석하고 drop_caches를 언제 쓰면 안 되는지 안다.

1. 회수의 전체 그림

"free 메모리가 200 MB밖에 없어요!"라는 경보는 Linux에서 대개 오경보입니다. 커널은 빈 메모리를 페이지 캐시로 적극 채우고, 메모리가 필요해지면 그 캐시를 되찾아(회수, reclaim) 씁니다. 회수할 수 있는 것은 다음과 같습니다.

  • clean 파일 페이지: 디스크에 원본이 있으므로 그냥 버리면 된다. 가장 싸다.
  • dirty 파일 페이지: 먼저 writeback한 뒤 버린다.
  • 익명 페이지(힙, 스택, shmem/tmpfs): 원본이 없으므로 swap 영역에 써야만 버릴 수 있다. swap이 없으면 회수할 수 없다.
  • 커널 캐시: dentry·inode 캐시 같은 slab 객체는 각 서브시스템의 shrinker가 줄인다(SReclaimable).

회수는 압박 정도에 따라 단계적으로 강해집니다.

  1. kswapd(백그라운드): 여유 메모리가 low 워터마크 아래로 내려가면 깨어나 high까지 회수한다. 할당하는 쪽은 기다리지 않는다.
  2. direct reclaim(동기): 여유가 min 아래로 떨어지면 메모리를 요청한 스레드가 직접 회수한다. 이 동안 애플리케이션이 멈추므로 지연 스파이크가 생긴다. 고차(연속 페이지) 할당이면 compaction도 함께 시도한다.
  3. OOM killer: 회수를 반복해도 진전이 없으면 프로세스 하나를 골라 죽인다. cgroup 한도에 걸린 경우에는 그 cgroup 안에서만 고른다.

2. 워터마크와 kswapd, direct reclaim

각 메모리 존(Normal, DMA32 등)에는 세 개의 워터마크가 있습니다. 모두 "여유 페이지 수"에 대한 기준선입니다.

워터마크는 두 sysctl로 정해집니다.

  • vm.min_free_kbytes: 모든 존의 min 워터마크 합. 기본값은 커널이 저메모리 크기로 계산하며(대략 4·√(lowmem KiB)), THP가 켜져 있으면 khugepaged가 더 크게 올리기도 합니다.
  • vm.watermark_scale_factor(기본 10, 단위 0.01%): 간격 d = max(min/4, 존 크기 × factor / 10000)로 정해지고 low = min + d, high = min + 2d입니다. 이 값을 키우면 kswapd가 더 일찍 깨어 더 많이 회수하므로 direct reclaim을 줄일 수 있습니다. 메모리가 크고 할당 폭주가 잦은 서버에서 쓰는 튜닝입니다.

현재 값은 /proc/zoneinfo에서 존별로 min, low, high(페이지 단위)로 볼 수 있습니다.

시뮬레이션: 워터마크를 넘을 때 일어나는 일
4 GiB 존 하나를 단순화한 모델입니다. 파일 읽기는 여유 메모리를 페이지 캐시로 바꾸고(회수 가능), 익명 할당은 swap이 없으면 회수할 수 없는 메모리를 늘립니다. 파일 읽기만 늘려서는 OOM이 나지 않는다는 점, 그리고 익명 할당을 계속하면 결국 어떻게 되는지 확인해 보세요.

현업에서 direct reclaim이 보이는 모습 평소엔 빠르던 서비스가 메모리 사용이 높을 때 p99 지연이 튀고, CPU 프로파일에 shrink_node, try_to_free_pages 같은 회수 함수가 보입니다. /proc/vmstat의 allocstall_*(direct reclaim 진입 횟수)와 pgscan_direct/pgsteal_direct가 늘고 있다면 확실합니다. 대응은 다음과 같습니다. 3. 익명 페이지 vs 파일 페이지

회수 정책의 핵심은 "어떤 페이지를 내보내는 게 가장 싼가"입니다. 두 종류의 비용은 비대칭입니다.

"swap을 끄면 안전하다"는 착각 swap이 없으면 익명 페이지는 고정된 것과 같아서, 메모리 압박이 오면 커널은 파일 페이지만 계속 쥐어짭니다. 그중에는 지금 실행 중인 프로그램의 코드 페이지도 있습니다. 결과는 OOM이 아니라, 코드 페이지를 버렸다 다시 읽기를 반복하는 스래싱입니다. 시스템이 수 분간 응답하지 않다가 한참 뒤에야 OOM killer가 동작하기도 합니다(8장). 작은 swap(또는 zram)이 있으면 오래 쓰이지 않은 익명 페이지를 내보낼 수 있어서 오히려 활성 파일 캐시를 지킬 수 있습니다. 응답 불능 상태를 빨리 끊으려면 PSI 기반의 사용자 공간 OOM 도구(systemd-oomd 등)를 함께 쓰는 것이 현대적인 해법입니다.

4. LRU 리스트와 workingset

7장의 교과서 LRU는 모든 접근마다 리스트를 갱신해야 해서 커널에 그대로 쓸 수 없습니다. Linux의 전통적 회수(MGLRU 이전)는 두 단계 리스트로 근사합니다. 메모리 cgroup과 NUMA 노드마다 다음 리스트가 있습니다.

  • inactive_anon, active_anon, inactive_file, active_file
  • unevictable: mlock된 페이지, ramfs, SHM_LOCK 세그먼트 등 회수 대상이 아닌 페이지

아이디어는 이렇습니다. 새 페이지는 inactive에서 시작하고, 거기 있는 동안 한 번 더 접근되면 active로 승격됩니다. 회수는 inactive의 꼬리에서만 일어나고, active가 너무 커지면 active 꼬리를 inactive로 강등해 다시 한 번 기회를 줍니다. 한 번 읽고 마는 스트리밍 데이터는 inactive를 거쳐 빠져나가므로 active의 작업 집합을 밀어내지 못합니다(스캔 저항성).

몇 가지 실제 구현 디테일이 있습니다.

  • 접근 감지: read()로 접근한 페이지 캐시는 커널이 직접 표시합니다(PG_referenced, folio_mark_accessed). 매핑된 페이지는 CPU가 PTE의 Accessed 비트를 세우고, 회수 스캔이 rmap(11장)으로 그 비트를 모아 봅니다.
  • 익명 페이지의 시작 위치: 과거엔 새 익명 페이지가 active에서 시작했지만, 5.9 이후 커널은 익명 페이지에도 workingset 감지를 적용하면서 inactive에서 시작시킵니다.
  • workingset refault 감지: 파일 페이지가 회수될 때 XArray의 그 자리에 "언제 쫓겨났는지"를 담은 shadow entry를 남깁니다. 다시 읽히면(refault) 그 사이 회수된 양(refault distance)을 계산하고, active 리스트 크기 안쪽이었다면 "작업 집합인데 공간이 부족해 밀려났다"고 판단해 곧바로 active로 넣습니다. /proc/vmstat의 workingset_refault_*, workingset_activate_*가 이 카운터입니다. refault가 많다면 메모리가 작업 집합보다 작다는 신호입니다.
LRU 상태 전이 위젯
페이지 버튼을 누르면 그 페이지에 접근합니다. 왼쪽이 리스트 머리(최근), 오른쪽이 꼬리입니다. R은 참조(referenced) 표시입니다. 회수된 페이지를 누르면 refault가 일어납니다. 학습용으로 단순화한 second-chance 모델입니다(실제 커널은 매핑 수, 실행 코드 여부, 리스트 비율 등을 더 따집니다).

5. MGLRU (multi-gen LRU)

두 단계 LRU는 "active냐 inactive냐"라는 1비트짜리 나이 정보만 가집니다. 또 매핑된 페이지의 접근 여부를 알려면 rmap으로 페이지마다 PTE를 찾아가야 해서, 메모리가 크고 매핑이 많을수록 CPU를 많이 씁니다. Google이 주도해 Linux 6.1에 들어간 MGLRU는 이 두 문제를 다른 방식으로 풉니다.

  • 세대(generation): 페이지를 여러 세대(최소 2, 최대 4)로 나눕니다. 최근 접근된 페이지는 가장 젊은 세대로, 회수는 가장 늙은 세대에서 합니다. 나이 정보가 1비트보다 풍부해집니다.
  • aging은 페이지 테이블 워크로: 페이지마다 rmap을 타는 대신 프로세스의 페이지 테이블을 순서대로 훑어 Accessed 비트를 한꺼번에 모읍니다. 접근된 PTE가 몰려 있는 영역은 효율이 좋습니다.
  • tier: fd로 여러 번 접근된 파일 페이지를 구분하고, refault 비율을 피드백 삼아 어느 쪽을 보호할지 조정합니다.
  • thrashing 방지: /sys/kernel/mm/lru_gen/min_ttl_ms로 "이 시간 안에 만들어진 세대는 쫓아내지 않는다"를 지정할 수 있습니다. 그래도 회수할 수 없으면 OOM으로 빨리 넘어가 장시간 무응답을 피합니다.

사용 여부는 cat /sys/kernel/mm/lru_gen/enabled로 확인합니다(0이 아니면 켜짐). 기본 활성화 여부는 커널 빌드 설정(CONFIG_LRU_GEN_ENABLED)과 배포판에 따라 다릅니다. 켜져 있으면 /proc/meminfo의 Active/Inactive 구분은 세대에서 근사한 값이 됩니다.

6. swappiness의 진짜 의미

vm.swappiness(기본 60, 범위 0~200)는 흔히 "swap을 얼마나 자주 쓸지"로 오해되지만, 커널 문서의 정의는 익명 페이지 회수(swap I/O)와 파일 페이지 회수(파일 I/O)의 상대적 비용입니다.

  • 100: 두 I/O의 비용이 같다고 보고 양쪽을 대등하게 압박한다.
  • 100보다 작음: swap I/O가 더 비싸다고 보고 파일 페이지를 우선 회수한다. 기본값 60은 회전 디스크 시절 기준이다.
  • 100보다 큼: swap이 더 싸다(예: zram처럼 메모리 내 압축 swap)고 보고 익명 페이지를 우선 회수한다.
  • 0: 익명 페이지 스캔을 최대한 피하지만, 파일 페이지가 바닥나는 극한 상황에서는 여전히 swap할 수 있다. 0은 "swap 금지"가 아니다. 확실히 막으려면 swap을 끄거나 mlock을 쓴다.

내부적으로 anon 쪽 우선순위는 swappiness, file 쪽은 200 − swappiness로 놓고, 여기에 각 리스트의 최근 refault 비용을 곱해 스캔 비율을 정합니다. 위 LRU 위젯은 그중 첫 번째 요소만 반영해 4페이지 중 anon 몫을 정합니다. 참고로 cgroup v1에는 cgroup별 memory.swappiness가 있었지만 cgroup v2에는 같은 파일이 없습니다.

7. swap, swap cache, zswap/zram

swap 영역

swap은 전용 파티션이나 swap 파일입니다(mkswap → swapon, 확인은 swapon --show 또는 /proc/swaps). 영역마다 우선순위(swapon -p)가 있어 높은 쪽부터 쓰고, 같은 우선순위끼리는 번갈아 씁니다. 익명 페이지가 swap out되면 PTE에는 물리 주소 대신 swap 엔트리(영역 번호 + 슬롯 오프셋)가 들어가고 present 비트가 꺼집니다. 다시 접근하면 페이지 폴트가 나고 swap-in이 일어납니다.

swap cache

swap cache는 swap 공간을 위한 페이지 캐시입니다. 다음 두 문제를 해결합니다.

  • 공유된 익명 페이지(fork 후 COW 공유 중): 여러 PTE가 같은 swap 엔트리를 가리킵니다. 첫 swap-in이 페이지를 swap cache에 올려 두면, 다른 프로세스의 폴트는 I/O 없이 같은 페이지를 찾습니다.
  • 불필요한 재기록 방지: swap-in된 페이지가 수정되지 않았다면 swap 슬롯의 사본이 아직 유효합니다. 다시 회수할 때 쓰기 없이 버릴 수 있습니다. /proc/meminfo의 SwapCached가 이렇게 메모리와 swap 양쪽에 있는 페이지의 양입니다.

압축 swap은 "swap = 느린 디스크"라는 등식을 깹니다. 압축·해제에 CPU를 쓰는 대신 I/O를 없애므로 swappiness를 100 이상으로 올리는 근거가 됩니다.

8. OOM killer

회수를 여러 번 시도해도 진전이 없으면 커널은 out_of_memory()를 호출해 희생자를 고릅니다. 그 전에 알아 둘 배경이 하나 있습니다. Linux는 기본적으로 메모리를 오버커밋합니다. malloc이나 mmap은 가상 주소만 예약하고 물리 메모리는 첫 쓰기 때 줍니다. 그래서 "할당은 성공했는데 나중에 메모리가 없는" 상황이 생길 수 있고, OOM killer는 그 상황의 안전장치입니다.

vm.overcommit_memory동작
0 (기본)휴리스틱. 명백히 불가능한 요청만 거부
1항상 허용 (Redis 권장값 등)
2엄격. 커밋 총량(Committed_AS)이 CommitLimit = swap + RAM × overcommit_ratio/100(기본 50)을 넘으면 할당 실패(ENOMEM)

희생자 선택: oom_badness

현재 커널의 점수 계산은 단순합니다. 오래전 커널에는 실행 시간, nice 값, root 여부 같은 복잡한 휴리스틱이 있었지만 대부분 제거되었습니다.

points = RSS 페이지 수 + swap으로 나간 페이지 수 + 페이지 테이블 페이지 수
adj    = oom_score_adj × (totalpages / 1000)      // totalpages = RAM + swap (cgroup OOM이면 cgroup 한도)
badness = points + adj                            // oom_score_adj == -1000 이면 아예 제외
→ badness가 가장 큰 프로세스를 죽인다 (그 mm을 공유하는 프로세스도 함께)
  • /proc/PID/oom_score_adj: −1000~1000. −1000이면 OOM killer 대상에서 제외됩니다. +1000이면 메모리 전체에 해당하는 가산점이 붙어 사실상 가장 먼저 죽습니다. 값을 낮추려면 CAP_SYS_RESOURCE가 필요합니다. systemd에서는 OOMScoreAdjust=로 지정합니다.
  • /proc/PID/oom_score: 현재 점수를 사람이 보기 좋게 바꾼 값입니다. 현재 커널은 (1000 + badness × 1000 / totalpages) × 2/3로 계산해 0~2000 범위로 보여 줍니다. adj가 0인 작은 프로세스는 666 근처로 보입니다.
  • init(PID 1)과 커널 스레드는 대상이 아닙니다. 이미 죽어 가는 프로세스가 있으면 새 희생자를 고르지 않고 기다립니다. oom_reaper 커널 스레드는 희생자의 익명 메모리를 비동기로 먼저 해제해, 희생자가 커널 안에서 막혀 있어도 메모리가 돌아오게 합니다.
  • 관련 sysctl: vm.panic_on_oom(기본 0, 1이면 OOM 시 커널 패닉), vm.oom_kill_allocating_task(기본 0, 1이면 점수 계산 없이 할당을 시도한 태스크를 죽임).
OOM 점수 계산기: 누가 죽나
각 프로세스의 RSS, swap 사용량, oom_score_adj를 바꿔 보세요. 페이지 테이블은 RSS/512 페이지로 근사했습니다(4 KiB 페이지, PTE 8바이트 기준). 계산은 커널의 정수 연산을 따릅니다.
프로세스RSS (MiB)swap (MiB)oom_score_adjbadness (페이지)oom_score

OOM이 일어나면 커널 로그(dmesg, journalctl -k)에 메모리 상태 덤프와 함께 Out of memory: Killed process 1234 (java) total-vm:..., anon-rss:..., file-rss:..., shmem-rss:..., oom_score_adj:0 같은 줄이 남습니다. cgroup 한도 때문이면 앞에 Memory cgroup out of memory가 붙습니다. 어느 쪽인지가 원인 분석의 첫 갈림길입니다. 노드 전체 메모리가 부족했는지, 한 컨테이너가 자기 한도를 넘었는지가 여기서 갈립니다.

9. cgroup v2 메모리 컨트롤과 쿠버네티스

cgroup v2의 메모리 컨트롤러는 프로세스 묶음 단위로 메모리를 계량하고 제한·보호합니다. 계량에는 익명 메모리뿐 아니라 그 cgroup이 처음 읽어 들인 페이지 캐시, tmpfs/shmem, 커널 메모리(slab, 소켓 버퍼 등)가 포함됩니다. "컨테이너 메모리 사용량에 캐시가 들어가 있다"는 점이 수많은 오해의 출발점입니다.

파일의미
memory.current현재 사용량 (캐시 포함)
memory.min하드 보호. 이 양 이하로는 어떤 상황에서도 회수되지 않음(보호량을 지킬 수 없으면 다른 곳에서 OOM)
memory.low최선 노력 보호. 보호받지 않는 메모리를 먼저 회수하고, 그래도 부족할 때만 건드림
memory.high스로틀 한도. 넘으면 해당 cgroup의 할당자가 직접 회수하고 지연(sleep)됨. OOM killer는 부르지 않음. 주된 사용량 조절 수단
memory.max하드 한도. 넘을 수 없음. 회수로도 못 맞추면 cgroup 안에서 OOM kill
memory.swap.max / memory.swap.currentswap 사용 한도 / 사용량
memory.events누적 카운터: low, high, max, oom, oom_kill (최근 커널은 oom_group_kill도). 하위 cgroup 포함. 자기 것만 보려면 memory.events.local
memory.statanon, file, shmem, active_file, inactive_file, pgfault, workingset_refault_* 등 상세 분해
memory.oom.group1이면 OOM 시 cgroup 안의 프로세스를 하나만이 아니라 전부 함께 죽임(부분적으로만 죽은 서비스 방지)
memory.pressure이 cgroup의 PSI (메모리 때문에 멈춘 시간 비율)
컨테이너 메모리 한도 시뮬레이터
한 cgroup 안의 워크로드가 익명 메모리와 페이지 캐시를 이만큼 원한다고 할 때, 한도 설정에 따라 결과가 어떻게 달라지는지 봅니다. 회수는 싼 것(캐시)부터, 그다음 swap 순으로 한다고 단순화했습니다.
익명(RAM)페이지 캐시swap한도 초과(OOM)

drop_caches 주의점

    
sync; echo 3 > /proc/sys/vm/drop_caches(1 = 페이지 캐시, 2 = dentry·inode 등 회수 가능 slab, 3 = 둘 다)는 다음 성질을 가집니다.

    
    
      
  • clean이고 사용 중이 아닌 캐시만 버립니다. dirty 페이지는 남으므로 먼저 sync합니다. 매핑된 페이지와 Shmem은 버려지지 않습니다.
    • 
      
  • 메모리를 "확보"해 주지 않습니다. 그 캐시는 원래 필요할 때 커널이 알아서 회수할 수 있었으므로 MemAvailable은 거의 변하지 않고 MemFree만 커집니다.
    • 
      
  • 대신 이후 모든 파일 접근이 디스크로 가서 일시적으로 성능이 떨어지고, 운영 중인 DB라면 지연이 폭증합니다. 커널 로그에 실행 기록(drop_caches: 3)이 남습니다.
    • 
      
  • 정당한 용도는 콜드 캐시 벤치마크와 디버깅 정도입니다. cron으로 주기 실행하는 "메모리 최적화"는 안티패턴입니다.
    • 
    

  


  
핵심 요약
    
    
  • 여유 메모리가 low 아래면 kswapd가 깨어 high까지 비동기 회수하고, min 아래면 할당 스레드가 direct reclaim으로 멈춘다. 그래도 진전이 없으면 OOM killer가 동작한다.
    • 
    
  • watermark 간격은 max(min/4, 존 크기 × watermark_scale_factor/10000)이며, 키우면 kswapd가 일찍 일해 direct reclaim이 준다.
    • 
    
  • clean 파일 페이지는 버리기만 하면 되고, 익명 페이지는 swap이 있어야 회수된다. swap이 없으면 압박이 파일 페이지(실행 코드 포함)에 몰려 스래싱이 생긴다.
    • 
    
  • 2단계 LRU: 새 페이지는 inactive에서 시작, 다시 접근되면 active로, 회수는 inactive 꼬리에서. shadow entry 기반 refault 감지가 작업 집합을 보호한다. MGLRU(6.1+)는 여러 세대와 페이지 테이블 워크로 이를 개선한다.
    • 
    
  • swappiness(0~200, 기본 60)는 swap I/O와 파일 I/O의 상대 비용이다. 0도 swap 금지가 아니다.
    • 
    
  • OOM badness = RSS + swap + 페이지 테이블 + oom_score_adj × totalpages/1000. adj −1000은 제외, +1000은 사실상 1순위다.
    • 
    
  • cgroup v2: min(절대 보호) < low(최선 보호) < high(스로틀) < max(하드 한도, OOM). 페이지 캐시도 cgroup에 계량되지만 한도에서 먼저 회수된다. 쿠버네티스 limits = memory.max, OOMKilled = exit 137.
    • 
    
  • free의 buff/cache는 전부 회수 가능한 것이 아니다(Shmem 포함). 판단 기준은 MemAvailable과 PSI·vmstat의 si, allocstall이다. drop_caches는 메모리 문제의 해결책이 아니다.
    • 
  


  
확인 문제

  

    
존의 여유 페이지가 low와 min 사이에 있을 때 일반적인(GFP_KERNEL) 할당 요청은 어떻게 처리되나?

    
    
    
    
    
fast path는 low 워터마크를 기준으로 하고, 실패하면 slow path에서 kswapd를 깨운 뒤 min 워터마크 기준으로 다시 시도합니다. min 위라면 성공하므로 요청자는 멈추지 않습니다. direct reclaim은 min 아래로 떨어질 때 시작됩니다.

  

  

    
swap이 전혀 없는 서버에서 메모리 압박이 심해질 때 가장 먼저 나타나기 쉬운 증상은?

    
    
    
    
    
swap이 없으면 익명 페이지는 회수 불가라서, 커널은 남은 파일 페이지를 쥐어짭니다. 실행 중인 프로그램의 코드 페이지까지 버렸다 다시 읽는 스래싱이 일어나고, 회수가 "약간씩 진전"하는 동안에는 OOM이 늦게 옵니다. PSI 기반 사용자 공간 OOM 도구가 필요한 이유입니다.

  

  

    
RAM 16 GiB, swap 0인 노드에서 RSS 6 GiB, adj 0인 java와 RSS 300 MiB, adj 1000인 BestEffort 파드 프로세스가 있다. 노드 전체 OOM 시 희생자는?

    
    
    
    
    
adj는 totalpages/1000 단위로 환산됩니다. adj 1000이면 RAM+swap 전체에 해당하는 약 16 GiB 상당의 점수가 붙으므로 RSS 300 MiB여도 java(6 GiB)보다 큽니다. panic_on_oom 기본값은 0입니다. 위 계산기로 직접 확인해 보세요.

  

  

    
limits.memory가 1 GiB인 컨테이너가 로그 파일을 대량으로 읽고 쓰면서 memory.current가 1 GiB 근처에 계속 붙어 있다. 익명 메모리는 300 MiB다. 가장 가능성 높은 결과는?

    
    
    
    
    
페이지 캐시도 cgroup에 계량되므로 memory.current는 한도 근처까지 찹니다. 하지만 캐시는 한도에서 먼저 회수되므로 익명 메모리가 한도를 넘지 않는 한 OOM은 나지 않습니다. 다만 회수가 잦으면 I/O가 늘어 느려질 수 있으니 memory.pressure를 확인하세요.

  

  

    
vm.swappiness에 대한 설명으로 옳은 것은?

    
    
    
    
    
커널 문서의 정의대로 0~200 범위에서 두 I/O의 상대 비용입니다. 0은 익명 스캔을 최대한 피하는 것일 뿐, 극한 상황에서는 여전히 swap할 수 있습니다. "사용률 임계" 해석은 흔한 오해입니다.

  

  

    
free -m에서 buff/cache가 9 GiB, available이 6 GiB로 나왔다. 둘의 차이를 설명할 수 있는 가장 그럴듯한 원인은?

    
    
    
    
    
Cached에는 Shmem이 포함되고, 모든 캐시를 공짜로 버릴 수는 없습니다(워터마크 예비분, 활성 작업 집합 등). MemAvailable은 이를 감안한 추정치입니다. drop_caches는 MemFree만 바꿀 뿐 available은 거의 그대로입니다.
