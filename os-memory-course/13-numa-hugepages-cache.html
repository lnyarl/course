NUMA, Huge Page, 캐시와 메모리 모델

페이지 테이블 아래에는 하드웨어 층이 하나 더 있습니다. 메모리는 64바이트 라인 단위로 오가고, 코어들은 일관성 프로토콜로 라인 소유권을 주고받습니다. 메모리 컨트롤러까지의 거리는 소켓마다 다르고, TLB는 생각보다 적은 범위만 덮습니다. 원인 모를 성능 저하나 특정 아키텍처에서만 터지는 동시성 버그는 대개 이 층에서 시작됩니다.

학습 목표

  • 주소를 tag | index | offset으로 나눠 어느 set에 들어갈지 계산하고, 충돌 미스가 생기는 접근 패턴을 알아본다.
  • MESI 상태 전이와 버스 트랜잭션을 추적하고, false sharing이 왜 비싼지 트랜잭션 수로 설명한다.
  • x86-TSO와 ARMv8의 메모리 순서 차이를 litmus test로 설명하고, 알맞은 배리어나 acquire/release를 고른다.
  • NUMA first-touch 정책의 결과를 예측하고 numactl, numastat, 자동 NUMA 밸런싱으로 진단하고 조정한다.
  • TLB reach를 계산해 huge page가 필요한 시점을 판단하고, THP의 지연 스파이크와 메모리 블로트를 설명한다.

1. 캐시 구조: 라인, set, tag | index | offset

CPU 캐시는 바이트 단위로 데이터를 가져오지 않습니다. 전송과 저장의 단위는 캐시 라인이고, x86-64와 대부분의 ARM64 코어에서 64바이트입니다. 1바이트를 읽어도 그 바이트가 속한 64바이트 정렬 블록 전체가 올라옵니다. 순차 접근이 빠른 것(공간 지역성), 구조체 필드 배치가 성능에 영향을 주는 것, false sharing이 생기는 것 모두 이 사실에서 나옵니다. Apple M 계열처럼 128바이트 라인을 보고하는 CPU도 있으므로 하드코딩하기 전에 확인하세요.

# Linux: 캐시 기하 정보 확인
getconf LEVEL1_DCACHE_LINESIZE
lscpu --caches
cat /sys/devices/system/cpu/cpu0/cache/index0/{level,type,size,ways_of_associativity,number_of_sets,coherency_line_size}
# macOS
sysctl hw.cachelinesize hw.l1dcachesize

연관도(associativity)와 주소 분할

어떤 라인을 캐시의 어디에 둘지 정하는 방식은 세 가지입니다. 직접 사상(1-way)은 위치가 한 곳뿐이라 하드웨어가 단순하지만 충돌이 잦습니다. 완전 연관은 어디든 둘 수 있지만 모든 엔트리의 태그를 동시에 비교해야 해서 크게 만들 수 없습니다(그래서 소형 TLB에 주로 씁니다). 실제 데이터 캐시는 그 중간인 N-way set-associative입니다. 캐시를 S개의 set으로 나누고, 각 set에 라인을 N개(way)까지 담습니다.

  • offset = 하위 log₂(라인 크기) 비트. 라인 안의 바이트 위치입니다. 64B라면 6비트입니다.
  • index = 그다음 log₂(S) 비트. 어느 set인지 고릅니다. S = 캐시 크기 ÷ (라인 크기 × way 수).
  • tag = 나머지 상위 비트. set 안의 N개 way에 저장된 tag와 동시에 비교해 히트를 판정합니다.

예를 들어 32KiB, 8-way, 64B 라인이면 S = 32768 ÷ (64×8) = 64 set이므로 offset 6비트, index 6비트이고 나머지가 tag입니다.

왜 L1은 "set을 늘리지 않고 way를 늘리는가"

L1 데이터 캐시는 주소 변환(TLB 조회)과 병렬로 시작해야 빠릅니다. 그래서 대부분 VIPT(Virtually Indexed, Physically Tagged)로 만듭니다. 가상 주소로 set을 고르면서 동시에 TLB로 물리 주소를 얻고, 물리 tag로 비교합니다. index+offset 비트가 페이지 오프셋(4KiB면 12비트) 안에 들어오면 가상 주소와 물리 주소의 해당 비트가 같으므로 별칭(aliasing) 문제가 생기지 않습니다. 64 set × 64B = 4KiB가 상한이므로 용량을 늘리려면 way를 늘려야 합니다. 많은 x86 코어가 오랫동안 32KiB 8-way였다가 최근 코어 일부가 48KiB 12-way로 간 이유가 이것입니다(48K ÷ 12 = 4K).

미스의 분류 (3C + 1)

  • 강제(compulsory) 미스: 처음 접근하는 라인입니다. 프리페처가 줄여 줍니다.
  • 용량(capacity) 미스: 작업 집합이 캐시보다 큽니다. 블로킹(타일링)으로 줄입니다.
  • 충돌(conflict) 미스: 캐시 전체에는 여유가 있지만 특정 set에 라인이 몰립니다. 2의 거듭제곱 stride 접근이 전형적인 원인입니다. 32KiB 8-way에서는 4KiB 간격 주소가 모두 같은 set으로 가므로 9번째 라인부터 서로를 밀어냅니다. 행렬의 행 길이를 4096바이트 대신 4096+64바이트로 패딩하는 관행이 이것을 피하려는 것입니다.
  • 일관성(coherence) 미스: 다른 코어의 쓰기로 내 사본이 무효화된 경우입니다. 2절과 3절에서 다룹니다.

2. 캐시 일관성과 MESI 프로토콜

코어마다 L1/L2가 따로 있으므로 같은 라인의 사본이 여러 캐시에 생깁니다. 한 코어가 쓴 값을 다른 코어가 영원히 못 보면 공유 메모리 프로그래밍이 성립하지 않습니다. 캐시 일관성(coherence)은 한 주소에 대해 두 가지 불변식을 지킵니다.

  • SWMR(Single-Writer, Multiple-Reader): 어느 시점이든 한 라인은 쓰기 가능한 사본 하나만 있거나, 읽기 전용 사본만 여러 개 있다.
  • 데이터 값 불변식: 읽기는 그 라인에 마지막으로 쓰인 값을 본다.

일관성은 한 주소의 문제이고, 여러 주소 사이의 순서는 메모리 일관성 모델(4절)이 다룹니다. 두 개념을 섞으면 "캐시가 일관되니 순서도 보장된다"는 흔한 오해에 빠집니다.

교과서 MESI와 실제 칩의 차이
  • 버스 대신 디렉터리/스눕 필터: 코어가 수십 개면 모든 요청을 브로드캐스트할 수 없습니다. L3 슬라이스나 홈 에이전트가 "누가 이 라인을 가졌는가"를 추적해 필요한 코어에만 메시지를 보냅니다. 상태 기계의 의미는 같습니다.
  • MOESI(AMD 등): O(Owned) 상태가 있어 M인 라인을 다른 코어가 읽을 때 메모리에 쓰지 않고 dirty인 채로 공유합니다. 위 시뮬레이터의 "Flush 후 S"가 만드는 메모리 쓰기를 줄입니다.
  • MESIF(Intel): F(Forward) 상태의 사본 하나만 읽기 요청에 응답해 중복 응답을 막습니다.
  • 성능 카운터에서 쓰기 미스는 흔히 RFO(Read For Ownership)로 표시됩니다. 다른 코어가 수정한 라인을 가져오는 경우는 HITM(Hit Modified)으로 보이며 가장 비싼 축에 속합니다.

3. False sharing: 공유하지 않는데 공유되는 라인

스레드 A는 a만, 스레드 B는 b만 씁니다. 논리적으로 공유하는 데이터가 없는데도 두 변수가 같은 64바이트 라인에 있으면 일관성 프로토콜은 라인 단위로 동작하므로 쓰기마다 라인 소유권이 코어 사이를 오갑니다(ping-pong). 각 쓰기가 L1 히트(수 사이클)에서 코어 간 라인 이전(수십~수백 사이클)으로 바뀝니다. 코드에 버그가 없고 프로파일러에서는 "그냥 느린 store"로만 보이기 때문에 찾기 어렵습니다.

False sharing 시뮬레이터: 같은 라인 vs alignas(64)

해결: 라인을 분리하거나, 공유를 없애거나

// C++17: 스레드별 카운터를 각각 다른 캐시 라인에
struct alignas(64) PaddedCounter {          // 또는 alignas(std::hardware_destructive_interference_size)
    std::atomic<long> value{0};
};                                          // sizeof == 64, 배열 원소마다 라인 하나
PaddedCounter per_thread[NTHREADS];

// C: GCC/Clang 속성
struct counter { long v; } __attribute__((aligned(64)));

// Linux 커널: 자주 쓰는 필드를 라인 경계로
struct foo { spinlock_t lock; /* ... */ } ____cacheline_aligned_in_smp;
  • 정렬 + 크기: alignas(64)는 시작 주소만 맞춥니다. 구조체 크기도 64의 배수여야 배열의 다음 원소가 같은 라인을 침범하지 않습니다. C++에서는 alignas가 sizeof를 정렬 단위로 올려 주지만, 수동 패딩(char pad[56])을 할 때는 직접 계산해야 합니다.
  • 64가 아니라 128을 쓰는 라이브러리: Intel 코어의 인접 라인 프리페처는 128바이트 쌍 단위로 라인을 가져옵니다. 그래서 Rust crossbeam의 CachePadded, Folly 등은 x86-64에서 128바이트로 패딩합니다. Apple M 계열은 라인 자체가 128바이트입니다.
  • 가장 좋은 해결은 공유 자체를 없애기: 스레드 로컬에 누적하고 마지막에 합치기(sharding), 커널의 per-CPU 변수가 이 방식입니다. 패딩은 메모리를 낭비하고 캐시 밀도를 떨어뜨립니다. 작은 객체 수백만 개를 전부 패딩하면 오히려 느려집니다.
  • 언어별 도구: Java @Contended(JDK 내부 어노테이션, 사용자 코드에서는 -XX:-RestrictContended 필요), Go golang.org/x/sys/cpu.CacheLinePad.
현업 진단: perf c2c

perf c2c record -- ./app 다음 perf c2c report를 실행하면 HITM이 많이 일어난 캐시 라인과 그 라인 안에서 접근된 오프셋, 접근한 코드 위치를 보여 줍니다. 한 라인에서 서로 다른 오프셋을 서로 다른 스레드가 쓰고 있다면 false sharing입니다. 같은 오프셋이라면 true sharing이므로 설계(락 분할, 배치 처리)를 바꿔야 합니다.

4. 메모리 순서와 메모리 모델: x86-TSO vs ARM

캐시가 완벽하게 일관되어도 한 스레드가 프로그램 순서대로 실행한 메모리 연산이 다른 스레드에게 다른 순서로 보일 수 있습니다. 재배열은 세 곳에서 생깁니다.

  1. 컴파일러: 의존성이 없는 load/store를 옮기거나, 레지스터에 캐싱하거나, 아예 없애기도 합니다. 일반 변수에 대한 데이터 레이스는 C/C++에서 미정의 동작입니다.
  2. 스토어 버퍼: 코어는 store를 일단 자기 스토어 버퍼에 넣고 다음 명령으로 넘어갑니다. 버퍼가 캐시에 반영(drain)되기 전까지 다른 코어는 그 값을 볼 수 없습니다. 자기 자신은 버퍼에서 값을 바로 읽습니다(store-to-load forwarding).
  3. 비순차 실행과 무효화 큐: 약한 모델의 코어는 독립적인 load끼리, load와 store 사이도 순서를 바꿔 완료할 수 있습니다.

스텝 애니메이션: 스토어 버퍼가 만드는 Store→Load 재배열 (SB 테스트)
초기값 x = y = 0. 코어 0은 x = 1; r1 = y;, 코어 1은 y = 1; r2 = x;를 실행합니다. 어떤 인터리빙으로도 SC에서는 r1 = r2 = 0이 불가능하지만 x86에서는 실제로 관측됩니다. mfence를 넣고 다시 재생해 보세요.
Litmus test 탐색기: 모델별로 가능한 결과 전부 나열
작은 병렬 프로그램에서 나올 수 있는 모든 최종 레지스터 값을 열거합니다. SC는 모든 인터리빙을, TSO는 스레드별 FIFO 스토어 버퍼 모델을, ARM은 배리어·acquire/release·같은 주소 제약을 지키는 범위에서 각 스레드 연산을 재배열한 뒤 인터리빙을 열거합니다. 주황 테두리는 문제의 "놀라운 결과"입니다.

언어 수준 메모리 모델로 사고하기

하드웨어 모델을 직접 다루는 대신 C/C++11, Rust, Java의 메모리 모델로 의도를 표현하면 컴파일러가 아키텍처별로 맞는 명령을 고릅니다.

std::atomic<int> flag{0}; int data = 0;
// 생산자
data = 42;
flag.store(1, std::memory_order_release);   // x86: mov, ARM64: stlr
// 소비자
while (flag.load(std::memory_order_acquire) == 0) {}   // x86: mov, ARM64: ldar
assert(data == 42);                         // release-acquire 쌍이 보장

// seq_cst store는 x86에서 xchg(또는 mov+mfence)로 컴파일된다. SB 패턴을 막으려면 seq_cst가 필요하다.

Linux 커널은 자체 메모리 모델(LKMM, tools/memory-model/)과 READ_ONCE()/WRITE_ONCE(), smp_mb(), smp_rmb()/smp_wmb(), smp_load_acquire()/smp_store_release()를 씁니다. x86에서는 smp_rmb()와 smp_wmb()가 컴파일러 배리어로만 컴파일됩니다. TSO가 이미 그 순서를 보장하기 때문입니다.

"x86에서는 잘 되던 코드"가 ARM에서 터지는 이유

메시지 전달(MP) 패턴을 일반 변수나 relaxed 원자 연산으로 짜면 x86에서는 TSO 덕분에 우연히 동작합니다. 같은 코드를 AWS Graviton이나 Apple Silicon으로 옮기면 소비자가 flag == 1을 보고도 오래된 data를 읽을 수 있습니다. 아키텍처 이전 시 데이터 레이스 검사(ThreadSanitizer)와 메모리 순서 검토를 함께 하는 이유입니다. 거꾸로, x86에서도 컴파일러 재배열은 일어나므로 "x86이니 배리어가 필요 없다"는 결론은 틀렸습니다.

5. NUMA: 거리가 있는 메모리

메모리 컨트롤러가 CPU 패키지 안으로 들어오면서(AMD Opteron, Intel Nehalem 이후) 멀티 소켓 서버의 각 소켓은 자기 DRAM을 직접 가집니다. 다른 소켓의 메모리는 소켓 간 링크(Intel UPI, AMD Infinity Fabric)를 거쳐야 하므로 느립니다. 이것이 NUMA(Non-Uniform Memory Access)입니다. 소켓 하나 안에서도 AMD EPYC의 NPS 설정이나 Intel의 SNC(Sub-NUMA Clustering)를 켜면 여러 NUMA 노드로 나뉩니다. CXL로 붙인 메모리는 CPU가 없는 별도 노드로 보입니다.

$ numactl --hardware
available: 2 nodes (0-1)
node 0 cpus: 0 1 2 3 ...
node 0 size: 257579 MB
node 1 cpus: 4 5 6 7 ...
node distances:
node   0   1
  0:  10  21
  1:  21  10

node distances는 펌웨어(ACPI SLIT)가 알려 주는 상대값입니다. 로컬을 10으로 놓고 21이면 "대략 2.1배"를 뜻하지만 실측과 꼭 맞지는 않습니다. 실제 지연과 대역폭은 Intel MLC(Memory Latency Checker) 같은 도구로 측정합니다. 대략적인 감각으로는 로컬 DRAM 접근이 수십~100ns 남짓이고, 원격은 그보다 1.3~2배 느립니다. 원격 노드로의 대역폭이 부족해지는 경우가 지연 증가보다 더 큰 문제가 되기도 합니다.

first-touch: 페이지는 처음 건드린 CPU의 노드에 놓인다

Linux의 기본 정책(MPOL_DEFAULT, 로컬 할당)에서 malloc이나 mmap은 가상 주소만 예약합니다. 물리 페이지는 처음 접근해서 페이지 폴트가 난 순간, 그 폴트를 처리하는 CPU가 속한 노드에서 할당됩니다. 그래서 할당한 스레드가 아니라 처음 쓴 스레드가 위치를 정합니다. 흔한 실수는 메인 스레드가 큰 배열을 memset이나 초기화 루프로 0으로 채운 뒤 워커 스레드 수십 개에 나눠 주는 것입니다. 모든 페이지가 노드 0에 몰려 절반의 워커가 원격 접근을 하고, 노드 0 메모리 컨트롤러에 대역폭이 몰립니다.

numa_miss와 numa_foreign이 계속 늘면 한 노드의 메모리가 부족해 할당이 넘치고 있다는 뜻입니다. 이 카운터는 할당 위치만 셉니다. 원격 접근 횟수는 perf의 메모리 이벤트(예: perf mem, 오프코어 응답 이벤트)로 봐야 합니다.

자동 NUMA 밸런싱

/proc/sys/kernel/numa_balancing(sysctl kernel.numa_balancing)을 켜면 커널이 접근 패턴을 보고 페이지나 태스크를 옮깁니다.

  1. 스케줄러 틱마다 태스크 주소 공간의 일부 범위를 골라 PTE를 일부러 접근 불가(PROT_NONE 성격)로 바꿉니다(task_numa_work() → change_prot_numa()).
  2. 다음 접근에서 NUMA hinting fault가 나면 어느 노드의 CPU가 어느 노드의 페이지를 만졌는지 기록하고 PTE를 복구합니다.
  3. 통계가 쌓이면 페이지를 접근 노드로 마이그레이션하거나, 태스크를 메모리가 많은 노드로 옮깁니다.

대가로 추가 폴트, TLB 플러시, 페이지 복사 비용이 생깁니다. /proc/vmstat의 numa_hint_faults, numa_hint_faults_local, numa_pages_migrated, numa_pte_updates로 그 양을 볼 수 있습니다. CPU와 메모리를 이미 numactl이나 cgroup cpuset으로 고정한 지연 민감 워크로드에서는 끄는 경우가 많습니다.

현업 사례: MySQL "swap insanity"와 zone_reclaim_mode

대형 InnoDB 버퍼 풀을 쓰는 서버에서 메모리가 넉넉한데도 swap이 일어나는 현상이 보고됐습니다. 버퍼 풀이 first-touch로 노드 하나에 몰리고, 그 노드가 꽉 차자 커널이 원격 노드에서 할당하는 대신 로컬 노드에서 회수(swap 포함)를 택했기 때문입니다. 당시 일부 시스템에서 기본으로 켜지던 vm.zone_reclaim_mode가 이 동작을 부추겼습니다. 대응은 numactl --interleave=all로 기동하는 것이었고, 이후 MySQL에 innodb_numa_interleave 옵션이 생겼습니다. 오늘날 zone_reclaim_mode는 기본 0이며, DB와 파일 서버에서는 0을 권장합니다.

7. Huge page와 TLB reach

4장에서 TLB 미스 한 번이 페이지 워크(x86-64 4단계면 메모리 참조 최대 4번)를 부른다는 것을 봤습니다. TLB reach는 TLB가 미스 없이 덮을 수 있는 메모리 양입니다.

TLB reach = 엔트리 수 × 페이지 크기

엔트리가 1,536개인 2단계 TLB(STLB)라면 4KiB 페이지로는 6MiB밖에 덮지 못합니다. 수십 GiB를 무작위로 다루는 DB, JVM 힙, 인메모리 캐시, 그래프 처리에서는 거의 모든 접근이 TLB 미스이고 페이지 워크가 L1/L2를 오염시킵니다. 같은 엔트리 수로 2MiB 페이지를 쓰면 reach는 3GiB가 되어 512배 늘어납니다.

TLB reach 계산기
TLB 엔트리 수와 작업 집합 크기(WSS)를 넣으면 페이지 크기별 reach, WSS 대비 커버율, WSS를 매핑하는 데 필요한 리프 엔트리 수와 그 페이지 테이블 메모리를 계산합니다. 실제 CPU는 크기별로 엔트리 수가 다르고(1GiB 전용 엔트리는 보통 매우 적음) 레벨도 여러 개이므로, 프리셋 값은 예시입니다.

huge page의 비용

  • 물리적으로 연속된 2MiB(정렬 포함)가 필요합니다. 오래 돈 시스템은 단편화되어 있어 compaction(페이지 이동으로 빈 공간 모으기) 없이는 확보하기 어렵습니다.
  • 관리 단위가 커집니다. COW, swap, NUMA 마이그레이션, 부분 munmap/mprotect를 2MiB 단위로 처리하거나 매핑을 4KiB로 쪼개야(split) 합니다.
  • 내부 단편화: 조금만 쓰는 영역에 2MiB를 통째로 주면 RSS가 부풉니다(8절 위젯).

THP 모드

  • enabled=always: 정렬된 2MiB 범위가 들어가는 익명 매핑이면 폴트 시 huge page를 시도합니다.
  • enabled=madvise: madvise(addr, len, MADV_HUGEPAGE)로 표시한 영역에서만 씁니다. 원하는 프로그램만 혜택을 받습니다.
  • enabled=never: THP를 쓰지 않습니다.
  • defrag는 폴트 시점에 2MiB를 못 구할 때의 행동입니다. always는 폴트 경로에서 직접 compaction/회수까지 하므로 지연이 튑니다. defer는 kcompactd를 깨우고 일단 4KiB로 진행합니다. madvise(흔한 기본값)는 madvise한 영역만 직접 compaction합니다.

khugepaged

커널 스레드 khugepaged가 주기적으로 주소 공간을 훑어 4KiB 페이지들로 채워진 2MiB 정렬 범위를 하나의 huge page로 합칩니다(collapse). 튜닝 값은 /sys/kernel/mm/transparent_hugepage/khugepaged/ 아래 pages_to_scan, scan_sleep_millisecs, alloc_sleep_millisecs, max_ptes_none에 있습니다. max_ptes_none은 범위 안에서 비어 있어도 되는 PTE 수의 상한이고 기본값은 511입니다. 512칸 중 하나만 채워져 있어도 합칠 수 있다는 뜻이며, 이것이 블로트의 원인이 됩니다.

THP 메모리 블로트 계산기
64MiB 익명 영역(2MiB × 32칸)에서 4KiB 페이지 K개를 무작위로 건드립니다. 4KiB 매핑이면 건드린 페이지만 RSS가 되고, THP(always, 또는 max_ptes_none=511로 collapse된 경우)면 한 번이라도 건드린 2MiB 칸 전체가 RSS가 됩니다.

초록 막대 = 그 2MiB 칸 안에서 실제로 건드린 4KiB 페이지 비율, 주황 칸 = THP라면 통째로 상주하는 칸.

THP의 함정과 DB들이 "끄라"고 권하는 이유

  1. 지연 스파이크: defrag=always이거나 madvise된 영역에서 폴트가 나면, 2MiB를 구하려고 그 자리에서 compaction이나 회수를 합니다. 평균 처리량은 좋아져도 p99 지연에 수~수십 ms 스파이크가 섞입니다. 지연 민감 서비스에서 THP를 의심해야 하는 대표 증상입니다(/proc/vmstat의 compact_stall, thp_fault_fallback 확인).
  2. 메모리 블로트: 위 위젯처럼 듬성듬성 쓰는 힙에서 RSS가 크게 부풉니다. 할당자가 MADV_DONTNEED로 4KiB 단위 반환을 해도 huge page를 쪼개야(split) 해서 반환 효과가 늦거나 줄어듭니다.
  3. fork와 COW: Redis는 스냅샷(BGSAVE)을 위해 fork합니다. THP가 켜져 있으면 부모가 쓸 때 생기는 COW 비용과 메모리 증가가 커질 수 있어서, Redis는 기동 시 THP 경고를 출력하고 never를 권합니다.
  4. 예측 불가능성: 같은 프로그램이라도 그날의 메모리 단편화 상태에 따라 huge page를 받을 수도, 못 받을 수도 있습니다. 성능 재현성이 떨어집니다.
권장의 변화도 함께 기억할 것

Oracle은 THP를 끄고 hugetlbfs(HugePages)를 쓰라고 권하고, PostgreSQL도 공유 버퍼에 huge_pages 설정으로 hugetlbfs를 씁니다. 반면 MongoDB는 오래 "THP를 끄라"고 권하다가 8.0에서 새 TCMalloc과 함께 켜라는 쪽으로 바꿨습니다. 정답은 고정되어 있지 않습니다. 무난한 출발점은 enabled=madvise, defrag=defer+madvise이고, 이를 기준으로 워크로드에서 p99 지연과 RSS를 측정해 결정하세요.

9. folio: 커널이 페이지를 묶어 다루는 방식

Linux는 물리 프레임마다 struct page(대개 64바이트, RAM의 약 1.6%)를 둡니다. huge page나 order>0 할당은 compound page로 표현했습니다. 첫 struct page가 head, 나머지가 tail입니다. 문제는 struct page *를 받은 함수가 그게 head인지 tail인지 알 수 없다는 점입니다. 그래서 곳곳에서 compound_head()를 반복 호출했고, tail을 head처럼 다루는 버그도 생겼습니다.

struct folio(Linux 5.16에 도입)는 "절대 tail이 아닌 페이지", 즉 2n개의 연속 페이지 묶음 전체를 가리키는 타입입니다. 타입 시스템으로 head와 tail의 혼동을 막고, 페이지 캐시·LRU·회수 코드가 "페이지 하나"가 아니라 "folio 하나" 단위로 일하게 바꿨습니다.

  • 대형 folio 페이지 캐시: 파일시스템이 지원하면 페이지 캐시가 4KiB보다 큰 folio를 쓸 수 있습니다. LRU 항목 수, 참조 카운트 연산, radix/xarray 엔트리가 줄어듭니다.
  • mTHP(multi-size THP, 익명 메모리는 6.8부터): 2MiB만이 아니라 16KiB, 64KiB 같은 중간 크기 folio를 씁니다. /sys/kernel/mm/transparent_hugepage/hugepages-64kB/enabled처럼 크기별로 켭니다. ARM64의 contiguous PTE 비트(연속된 16개 4KiB 엔트리를 TLB 엔트리 하나로)와 결합하면 2MiB 연속 메모리를 구하지 못해도 TLB 이득을 얻고, 블로트도 작습니다.

정리하면 huge page 논쟁이 "4KiB냐 2MiB냐"에서 "그 사이의 적절한 크기를 상황에 맞게"로 옮겨 가고 있고, folio가 그 기반입니다.

핵심 요약

  • 캐시는 64B 라인 단위로 동작하고, 주소는 tag | index | offset으로 나뉩니다. set 수 = 크기 ÷ (라인 × way). 2의 거듭제곱 stride는 한 set에 몰려 충돌 미스를 냅니다.
  • VIPT L1은 index+offset을 페이지 오프셋 안에 두려고 용량을 way로 늘립니다(32K/8-way, 48K/12-way).
  • MESI는 SWMR을 지킵니다. E는 "읽고 쓰기"를 버스 없이 하게 하고, S→M은 무효화, I→M은 RFO가 필요합니다. 실제 칩은 디렉터리, MOESI, MESIF를 씁니다.
  • False sharing은 라인 단위 일관성의 부작용입니다. alignas(64)(x86에서는 종종 128)로 분리하거나 스레드별 누적으로 공유 자체를 없앱니다. 진단은 perf c2c로 합니다.
  • 일관성(한 주소)과 메모리 모델(여러 주소의 순서)은 다릅니다. x86-TSO는 Store→Load 재배열만 허용하고, ARMv8은 독립 연산의 재배열을 거의 다 허용합니다. 언어의 acquire/release/seq_cst로 의도를 표현하세요.
  • NUMA에서 페이지는 처음 건드린 CPU의 노드에 놓입니다(first-touch). 병렬 초기화, --interleave, --membind, 자동 NUMA 밸런싱으로 조정하고 numastat, numa_maps로 확인합니다.
  • TLB reach = 엔트리 × 페이지 크기. 2MiB 페이지는 reach를 512배로 늘리고 워크를 한 단계 줄입니다. hugetlbfs는 예측 가능하지만 미리 예약해야 하고, THP는 자동이지만 지연 스파이크와 블로트라는 대가가 있습니다.
  • folio는 head/tail 혼동을 타입으로 없앤 묶음 단위이며, 대형 folio 페이지 캐시와 mTHP의 기반입니다.

확인 문제

48KiB, 12-way, 64B 라인 L1D 캐시의 index 비트 수는?
set 수 = 49152 ÷ (64 × 12) = 64 = 2⁶이므로 index는 6비트, offset도 6비트입니다. index+offset = 12비트로 4KiB 페이지 오프셋 안에 들어가므로 VIPT로 만들어도 별칭 문제가 없습니다. 32KiB에서 48KiB로 갈 때 set 대신 way를 늘린 이유입니다.
MESI에서 코어 0이 라인 X를 E 상태로 갖고 있고 다른 코어는 모두 I입니다. 코어 0이 X에 쓰면 버스에는 무엇이 나가나요?
E는 "깨끗하고 유일한 사본"이므로 무효화할 대상이 없습니다. 버스 없이 M으로 바뀝니다. E 상태가 존재하는 이유가 바로 이 경우를 싸게 만들기 위해서입니다.
두 스레드가 struct { long a; long b; } s;의 a와 b를 각각 쉬지 않고 증가시켜 느립니다. 다음 중 false sharing을 해결하지 못하는 것은?
atomic은 각 변수의 연산을 원자적으로 만들 뿐 라인 배치를 바꾸지 않습니다. 두 atomic이 같은 라인에 있으면 ping-pong은 그대로이고, lock 접두 명령이 더해져 오히려 더 느려질 수 있습니다.
SB 테스트(x=1; r1=y ∥ y=1; r2=x, 초기값 0)에서 x86-64가 r1=r2=0을 허용하는 직접적인 원인과 해결책은?
각 코어의 store가 스토어 버퍼에 머무는 동안 뒤의 load가 메모리(캐시)의 옛 값을 읽습니다. 일관성은 위반되지 않았고, 순서(모델)의 문제입니다. 뒤의 load가 앞의 store를 기다리게 하려면 전체 배리어(mfence, lock 명령, xchg)가 필요하며, C++에서는 seq_cst가 이를 생성합니다. volatile은 하드웨어 재배열을 막지 못합니다.
2소켓 서버에서 메인 스레드가 40GiB 배열을 memset으로 0 초기화한 뒤 워커 64개(양 소켓에 반씩)에게 구간을 나눠 줬습니다. 예상되는 현상은?
first-touch 정책 때문에 memset을 실행한 CPU의 노드에 물리 페이지가 할당됩니다(그 노드가 꽉 차면 넘칩니다). 해결책은 워커가 자기 구간을 직접 초기화하는 병렬 first-touch, 공유 데이터라면 interleave입니다. 자동 NUMA 밸런싱이 나중에 일부를 옮겨 줄 수는 있지만 비용이 따릅니다.
STLB 1,536엔트리 × 2MiB = 3GiB의 TLB reach를 노리고 huge page 도입을 검토 중입니다. 다음 설명 중 틀린 것은?
1536 × 2MiB = 3GiB입니다. THP는 huge page를 못 구하면 조용히 4KiB로 폴백합니다(thp_fault_fallback 카운터 증가). 실패가 드러나는 것은 hugetlbfs 쪽입니다. 풀이 비면 mmap이 실패하거나 폴트 시 SIGBUS가 납니다.
