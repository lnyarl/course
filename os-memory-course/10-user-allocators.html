유저 공간 할당자: malloc의 내부

커널은 프로세스에게 페이지 단위의 거친 메모리(brk, mmap)만 준다. 그 안에서 malloc(37) 같은 바이트 단위 요청을 수백만 번 처리하고, 해제된 조각을 재활용하며, 멀티스레드 경합을 견디는 것은 전적으로 라이브러리 할당자의 몫이다. 이 장은 glibc의 ptmalloc2를 해부하면서 청크·bin·아레나의 구조, 단편화와 RSS 문제, 그리고 use-after-free 같은 힙 버그가 왜 생기고 어떻게 잡는지를 코드 수준에서 본다.

학습 목표

  • 힙 확장 수단인 brk/sbrk와 mmap의 차이, M_MMAP_THRESHOLD의 동적 조정을 설명할 수 있다.
  • malloc 청크의 헤더(size, prev_size, P/M/A 비트)와 경계 태그 병합 원리를 그릴 수 있다.
  • ptmalloc2의 bin 종류(tcache, fastbins, unsorted, small, large)와 할당/해제 경로를 추적할 수 있다.
  • 단편화로 RSS가 줄지 않는 이유와 malloc_trim·아레나 수 튜닝을 설명할 수 있다.
  • use-after-free, double free, overflow가 힙에서 어떻게 나타나는지와 ASan/Valgrind의 탐지 원리를 안다.
  • jemalloc/tcmalloc/mimalloc의 설계 선택(size class, thread cache, 반환 정책)을 비교할 수 있다.

이 장의 모델은 교육용 단순화다 아래 시뮬레이터와 설명은 glibc ptmalloc2의 핵심 구조를 정확히 재현하되, 실제 구현의 모든 세부(정확한 정렬 규칙, 큰 bin의 skip list, tcache 카운트 한계, 최근 버전의 보안 강화 등)를 담지는 않는다. 숫자(예: tcache 16바이트 간격 64개 bin, fastbin 상한 등)는 x86-64 glibc 2.3x 기준이며 버전·튜닝에 따라 달라진다. 목표는 "할당자가 왜 이렇게 행동하는가"의 직관을 만드는 것이다.

1. 왜 라이브러리 할당자가 필요한가

커널의 mmap은 페이지(4 KiB) 단위로만 메모리를 주고, 시스템 콜이라 수백 나노초가 든다. 프로그램이 malloc(24)를 초당 수백만 번 부른다면 매번 시스템 콜로 페이지를 받는 것은 두 가지 이유로 불가능하다.

  • 속도: 시스템 콜 + 페이지 폴트 비용이 24바이트 할당 하나에 수천 배다. 좋은 할당자의 fast path는 수~수십 나노초, 함수 호출 몇 번 수준이어야 한다.
  • 낭비: 24바이트에 4 KiB 페이지를 통째로 쓰면 170배 낭비다.

그래서 할당자는 커널에서 큰 메모리 덩어리를 한 번에 받아(brk로 힙을 넓히거나 mmap으로 블록을 받아) 사용자에게는 그것을 잘게 쪼개 나눠 준다. 핵심 책무는 세 가지다.

  1. 분할: 큰 영역을 요청 크기에 맞는 청크로 자른다.
  2. 재활용: free된 청크를 자료구조(bin)에 모아 두었다가 다음 요청에 재사용한다. 같은 크기라면 시스템 콜 없이 즉시 돌려준다.
  3. 병합: 인접한 free 청크를 합쳐 더 큰 요청에 쓸 수 있게 하고, 단편화를 억제한다.

Linux의 기본은 glibc에 내장된 ptmalloc2(Wolfram Gloger가 Doug Lea의 dlmalloc을 멀티스레드로 확장한 것)다. 그 설계를 축으로 보되, 11절에서 다른 철학의 할당자와 비교한다.

2. 힙을 넓히는 두 가지: brk와 mmap

할당자가 커널에서 메모리를 얻는 길은 둘이다.

brk / sbrk (메인 힙)mmap (익명 매핑)
구조데이터 세그먼트 끝(program break)을 위로/아래로 옮겨 하나의 연속 영역을 키우거나 줄인다주소 공간 아무 곳에나 독립된 매핑을 만든다
단위포인터 하나(break) 이동. 할당자가 그 안을 청크로 관리매핑 하나 = 요청 하나 (페이지 정렬)
해제break를 되돌려야 커널에 반납 → 꼭대기가 free여야만 축소 가능munmap으로 즉시 완전 반납 (RSS 즉시 감소)
적합작고 수명이 짧은 수많은 할당크고 수명이 길거나 독립적인 할당

ptmalloc2는 요청 크기가 M_MMAP_THRESHOLD(기본 128 KiB) 이상이면 메인 힙을 거치지 않고 전용 mmap 매핑을 만든다. 이렇게 하면 그 청크를 free할 때 바로 munmap으로 커널에 반납되어 RSS가 즉시 준다(8절의 "RSS가 안 줄어드는 문제"를 큰 할당에 한해 피한다).

임계값은 고정이 아니라 학습한다 임계값을 128 KiB에 고정하면, 100 KiB짜리를 반복 할당·해제하는 프로그램은 매번 brk 힙에 남겨 단편화를 키운다. 반대로 임계값이 너무 낮으면 중간 크기 할당마다 mmap/munmap 시스템 콜과 페이지 폴트를 유발한다. 그래서 glibc는 동적 조정(dynamic mmap threshold)을 쓴다. mmap으로 받았던 블록이 free될 때, 그 크기를 보고 임계값을 그 크기까지 올린다(상한 DEFAULT_MMAP_THRESHOLD_MAX, 64비트에서 32 MiB). "방금 해제된 이 크기는 brk 힙에서 재활용하는 편이 낫다"고 학습하는 것이다. mallopt(M_MMAP_THRESHOLD, ...)로 임계값을 직접 고정하면 이 학습이 꺼진다.
brk vs mmap 결정 · 동적 임계값 시뮬레이터
같은 크기를 반복 할당·해제하며 glibc의 동적 임계값이 어떻게 움직이는지 본다. 할당 크기가 현재 임계값 이상이면 mmap, 아니면 brk 힙으로 간다.

3. 청크: 헤더와 경계 태그

ptmalloc2는 힙을 청크(chunk)들의 연속으로 본다. 사용자가 받는 포인터(mem) 바로 앞에 메타데이터가 있다. 핵심 트릭은 경계 태그(boundary tag)다. 각 청크는 자기 크기를 헤더에 담고, 하위 3비트를 플래그로 재활용한다. 크기는 항상 8/16바이트 정렬이라 하위 비트가 어차피 0이기 때문이다.

  • prev_size 겹침: 앞 청크가 사용 중이면 그 청크는 자기 payload를 꽉 채워 쓰므로, 뒤 청크의 prev_size 자리를 앞 청크가 데이터로 빌려 쓴다. 그래서 16바이트 요청이 실제로는 더 적은 오버헤드로 들어간다(usable size ≥ 요청). 앞 청크가 free가 되는 순간에만 prev_size가 진짜 의미를 갖는다.
  • P 비트로 앞을 본다: 내 size의 P 비트가 0이면 "앞 청크가 free". 그러면 내 prev_size로 앞 청크의 시작 주소(this − prev_size)를 구해 병합한다.
  • size로 뒤를 본다: this + size가 다음 청크. 그 다음다음 청크의 P 비트를 보면 "뒤 청크가 free"인지 안다.
  • 최소 청크: x86-64에서 32바이트(헤더 + 최소 fd/bk 공간). malloc(1)도 최소 청크를 받는다. 정렬은 16바이트.
청크 크기 계산기
요청 바이트를 넣으면 실제 청크 크기, 플래그가 들어갈 size 워드, 내부 단편화를 보여 준다. (x86-64, 포인터 8바이트, 정렬 16바이트)

4. ptmalloc2의 bin들

free된 청크는 크기와 상황에 따라 서로 다른 자료구조에 들어간다. 이 분류가 ptmalloc2 성능의 핵심이다. 할당 요청이 오면 빠른 것부터 차례로 뒤진다.

bin크기대 (x86-64)구조병합목적
tcache청크 32~1040 B (요청 ≤1032 B), 64개 bin스레드별, 단일 연결 LIFO, bin당 최대 7개안 함스레드 로컬·락 없는 최속 경로 (glibc 2.26+)
fastbins청크 32~128 B (요청 ≤120 B, M_MXFAST로 조정)아레나별, 단일 연결 LIFO즉시 안 함 (지연)작은 청크의 빠른 재사용
unsorted bin모든 크기이중 연결, 단일 리스트이미 됨free/분할 청크의 임시 대기열 (한 번의 기회)
small bins청크 < 1024 B, 16 B 간격 62개 bin크기별 이중 연결, 정확히 한 크기함작은 청크의 크기별 정렬 보관
large bins≥ 1024 B크기 범위별 이중 연결, 크기 내림차순 정렬함큰 청크, best-fit 탐색
top chunk-힙 꼭대기의 미분할 영역-어느 bin도 못 주면 여기서 잘라 냄, 모자라면 brk 확장

할당 경로 (malloc)

  1. 크기가 tcache 범위면 해당 tcache bin 확인 → 있으면 즉시 반환(락 없음).
  2. fastbin 범위면 해당 fastbin 확인 → 있으면 반환 (+ 같은 tcache bin을 채워 둠).
  3. small bin 범위면 정확한 크기 bin 확인.
  4. 그 외에는 unsorted bin을 훑으며 각 청크를 제 크기의 small/large bin으로 정리(sort)한다. 지나가다 딱 맞는 게 있으면 바로 준다. large는 best-fit.
  5. 여전히 없으면 top chunk에서 잘라 내고, top도 모자라면 brk/mmap으로 확장한다.

해제 경로 (free)

  1. mmap 청크(M 비트)면 munmap으로 즉시 반납.
  2. tcache 범위이고 해당 bin에 자리(<7)가 있으면 tcache에 넣고 끝(병합 안 함).
  3. fastbin 범위면 fastbin에 넣고 끝(병합 지연).
  4. 그 외에는 앞·뒤 청크와 병합한 뒤 unsorted bin에 넣는다. top과 인접하면 top에 흡수된다.
왜 fastbin/tcache는 병합을 미루나 작은 할당은 "잠깐 쓰고 바로 다시 할당"되는 패턴이 많다. 그때마다 병합했다 다시 쪼개면 손해다. 그래서 작은 청크는 "같은 크기 그대로" 리스트에 꽂아 두고 즉시 재사용한다(캐시 지역성도 좋다). 대신 병합이 미뤄져 단편화에 취약해지고, 보안상 공격 표면이 된다. 주기적으로 malloc_consolidate()가 fastbin들을 모아 병합한다(큰 할당이 top을 필요로 할 때 등). 이 "성능 위해 병합을 미루는 로컬 캐시"는 9장 커널의 PCP·SLUB freelist와 정확히 같은 트레이드오프다.

5. 할당 시뮬레이터

실제 ptmalloc2의 동작을 단순화한 모델로 재현한다. malloc/free 시퀀스를 실행하며 힙 레이아웃, bin 상태, tcache가 어떻게 변하는지 추적한다.

ptmalloc2 힙 시뮬레이터 (tcache · fastbin · bins · 병합)
버튼으로 할당/해제하거나, 힙의 사용 중 청크(파란색)를 클릭하면 free된다. tcache는 bin당 7개, fastbin은 ≤128 B, mmap은 ≥128 KiB. 초록 free 청크끼리 인접하면 병합된다(tcache/fastbin에 있는 동안은 예외).

6. 병합과 단편화

해제 시 병합(coalescing)은 경계 태그로 양 옆을 본다. 의사코드로:

void _int_free(chunk *p) {
    size_t size = chunksize(p);
    // 1) 다음 청크가 free면 병합 (내 뒤)
    chunk *next = (char*)p + size;
    if (!inuse(next)) { unlink(next); size += chunksize(next); }
    // 2) 앞 청크가 free면 병합 (P 비트가 0)
    if (!prev_inuse(p)) {
        chunk *prev = (char*)p - p->prev_size;
        unlink(prev); size += chunksize(prev); p = prev;
    }
    // 3) top과 인접하면 top에 흡수, 아니면 unsorted bin에
    if ((char*)p + size == top) { top = p; top_size += size; }
    else { p->size = size; insert_unsorted(p); set_prev_size(next_of(p)); }
}

병합으로도 못 막는 것이 외부 단편화다. "free 공간의 합은 충분한데, 연속된 조각이 없어 큰 요청이 실패(또는 힙 확장)하는" 상황이다. 전형적인 시나리오: 작은 청크 A·B·C·D·E를 할당한 뒤 A·C·E만 해제하면, free 공간이 B·D 사이에 끼어 흩어진다.

단편화 스텝 애니메이션
10개의 64 B 청크를 할당한 뒤 짝수 번째만 해제한다. free 바이트는 많지만 연속 공간은 64 B뿐이라 320 B 요청은 top을 넓혀야 한다.
best-fit가 항상 좋지 않다 "가장 꼭 맞는 free 청크"를 고르면 남는 조각이 작아져 단편화가 심해질 수 있다(쓸모없는 파편 양산). ptmalloc2는 small bin은 정확한 크기, large bin은 best-fit, 그리고 "최근에 쓴 메모리 근처를 재사용"하는 지역성 휴리스틱을 섞는다. 할당자 설계에서 "단편화 최소화"와 "속도·지역성"은 늘 충돌하며, 정답은 워크로드마다 다르다. 이것이 jemalloc·tcmalloc 같은 대안이 존재하는 이유다.

7. 아레나와 멀티스레드 경합

초창기 dlmalloc은 전역 락 하나로 힙을 보호했다. 스레드가 많아지면 이 락이 심각한 병목이 된다. ptmalloc2의 답은 아레나(arena), 즉 독립된 힙과 bin 집합을 여러 개 두는 것이다.

  • 메인 아레나는 brk 힙을 쓴다. 보조 아레나는 mmap으로 큰 영역(기본 64 MiB 단위, "heap")을 받아 쓴다.
  • 스레드가 malloc할 때 자기에게 연결된 아레나의 락을 trylock한다. 경합하면 다른 아레나를 시도하고, 전부 바쁘면 새 아레나를 만든다. 성공한 아레나를 그 스레드에 붙여 둔다.
  • 아레나 최대 수는 MALLOC_ARENA_MAX로 정하며, 기본은 코어 수 × 8(64비트)이다. 설정하지 않으면 코어가 많은 머신에서 아레나가 폭증한다.
  • tcache(2.26+)가 스레드 로컬 캐시를 담당하면서, 작은 할당은 아레나 락을 아예 건드리지 않게 되어 경합이 크게 줄었다.
현업 사례: 아레나로 인한 "가상 메모리 폭발" 코어 64개 서버에서 멀티스레드 Java/JNI나 C++ 서비스가 top의 VIRT(또는 VSZ)가 수십 GiB로 치솟는데 실제 RSS는 작은 현상을 자주 겪는다. 원인은 아레나 수 = 64×8 = 512개, 각 아레나가 64 MiB씩 mmap 예약 → 32 GiB 주소 공간 예약이다(실제로 쓴 페이지만 RSS에 잡히므로 VIRT만 큰 것). 더 나쁜 경우, 각 아레나에 조금씩 남은 단편화가 합쳐져 RSS도 부푼다. 해법: export MALLOC_ARENA_MAX=2(또는 4). 컨테이너에서 특히 중요한데, cgroup이 코어 수를 제대로 안 보여 주면 glibc가 호스트 코어 수로 아레나를 잡기 때문이다. 메모리 안정성을 위해 약간의 멀티스레드 할당 처리량을 포기하는 트레이드오프다.

8. 단편화로 RSS가 안 줄어드는 문제

"메모리를 다 free했는데 왜 프로세스 RSS가 그대로인가?" 이것은 버그가 아니라 brk 힙의 구조적 성질이다.

  1. free는 청크를 bin에 넣을 뿐, 커널에 페이지를 반납하지 않는다(그래야 다음 할당이 빠르다).
  2. brk 힙은 꼭대기(top)부터만 줄일 수 있다. 힙 맨 위에 살아 있는 청크가 하나라도 있으면, 그 아래가 전부 free여도 break를 내릴 수 없다. free가 자동으로 하는 trim도 이 꼭대기 축소뿐이다.
  3. 그래서 "오래 사는 작은 객체 하나"가 힙 꼭대기에 있으면 그 아래 수백 MiB가 자동으로는 반납되지 않는다. 명시적 malloc_trim(0)은 중간의 빈 페이지를 madvise로 돌려줄 수 있지만, 살아 있는 객체가 페이지마다 흩어져 있으면 그것도 소용없다.
malloc_trim · RSS 반환 시뮬레이터
64 KiB 청크 8개로 힙을 채운 뒤 일부를 해제하고 비교한다. 자동 trim(free 시)은 꼭대기 연속 free만 sbrk로 줄이고, malloc_trim(0)은 중간 구멍의 빈 페이지까지 MADV_DONTNEED로 반납한다.
  • malloc_trim(pad): 꼭대기 연속 free 영역은 sbrk 음수로 반납하고, glibc 2.8부터는 모든 아레나의 중간 free 청크에 걸친 통째로 빈 페이지도 madvise(MADV_DONTNEED)로 반납한다(주소 공간은 유지, RSS만 감소). 단 페이지 일부라도 사용 중이면 그 페이지는 못 돌려준다.
  • M_TRIM_THRESHOLD(기본 128 KiB): top의 free가 이 값을 넘으면 free가 자동으로 trim한다. 이 자동 trim은 꼭대기만 줄인다. 중간 구멍까지 반납하려면 명시적 malloc_trim(0)을 불러야 한다.
  • tcache/fastbin에 들어간 청크는 할당자 입장에서 "사용 중"이라 trim 대상이 아니다. 작은 객체가 페이지마다 하나씩 살아 있는 패턴(희소 단편화)은 어떤 trim으로도 회수되지 않는다.
  • 이것이 장수 서버에서 jemalloc/tcmalloc을 쓰는 큰 이유다. 이들은 메모리를 가상 영역(run/span) 단위로 관리하고 사용하지 않는 페이지를 madvise(MADV_FREE/DONTNEED)로 적극 반환해, 중간이 비어도 OS에 돌려줄 수 있다.

9. 힙 메모리 버그

할당자의 메타데이터와 사용자 데이터가 같은 힙에 섞여 있다는 사실이 C/C++ 메모리 버그를 위험하게 만든다. 셋을 본다.

use-after-free (UAF)

char *p = malloc(64);
free(p);              // p는 tcache bin에 들어감
                      // ... 어딘가 strcpy(p, attacker);
char *q = malloc(64); // 같은 청크 재사용 → q == p
q[0] = 'X';           // p로 쓴 데이터를 덮음 / 반대도

double free

free(p);
free(p);   // 같은 청크를 두 번 → bin 리스트에 p가 두 번
char *a = malloc(64);  // a == p
char *b = malloc(64);  // b == p (!!) → a와 b가 같은 메모리

heap buffer overflow

char *p = malloc(16);
memcpy(p, src, 32);   // 다음 청크의 헤더(size 등)를 덮어씀
free(p);              // 할당자가 오염된 메타데이터를 보고 abort하거나, 나중에 엉뚱한 곳이 깨짐

이 버그들이 위험한 이유는 증상이 원인과 멀리 떨어진 곳에서 나타나기 때문이다. 메타데이터나 남의 데이터가 조용히 깨지고, 한참 뒤 전혀 무관한 malloc/free에서 abort하거나 데이터가 오염된다. 또한 할당자 메타데이터 오염은 보안 취약점으로 이어질 수 있어 CVE의 큰 비중을 차지한다. glibc는 흔한 오염을 조기에 감지해 즉시 중단하도록 여러 무결성 검사를 넣었다:

  • tcache key(2.29+): tcache 청크에 아레나별 키를 심어, double free 시 같은 키가 이미 있으면 abort.
  • safe-linking(2.32+): 단일 연결 리스트(tcache/fastbin)의 포인터를 주소 기반 값과 섞어 저장해, 오염된 포인터를 쉽게 감지·무력화.
  • free 시 다음 청크 size의 타당성, 리스트에서 뺄 때 양방향 링크의 일관성 검사 → 실패 시 free(): invalid next size, corrupted double-linked list 등의 메시지로 abort.
UAF / double free / overflow 시각화
시나리오를 골라 단계별로 넘기면, 포인터와 힙 바이트가 어떻게 어긋나는지 본다. 빨간 빗금은 ASan의 레드존(독성 바이트)이다.

10. ASan과 Valgrind

두 도구는 같은 버그를 전혀 다른 원리로 잡는다.

AddressSanitizer (ASan)Valgrind (Memcheck)

valgrind --leak-check=full --track-origins=yes ./app
섀도 메모리의 핵심 아이디어 ASan은 가상 주소를 shadow = (addr >> 3) + offset으로 매핑한다. 접근할 때마다 이 섀도 바이트를 읽어, 해당 8바이트가 전부 접근 가능하면 0, 일부만/레드존이면 음수나 부분값이다. 할당 시 레드존을 "독성"으로, free 시 청크 전체를 "독성"으로 칠하고 격리에 넣으면, 해제된 메모리에 접근하는 순간 섀도 검사가 걸린다. 이 "메타데이터를 데이터와 분리해 별도 영역에 둔다"는 발상은 9장 커널의 slub_debug red zone·poisoning과 같은 계보다.

ptmalloc2는 범용·호환성 위주다. 처리량·단편화·메모리 반환에서 더 나은 선택이 상황별로 존재한다. 모두 LD_PRELOAD나 링크로 교체할 수 있다.

반환 정책 비교: decay 시뮬레이터
워크로드가 피크 후 메모리를 해제했을 때, "즉시 반환 / 지연 반환(decay) / 반환 안 함" 세 정책의 RSS 궤적을 비교한다. 지연 반환은 재할당 시 페이지 폴트를 아껴 처리량과 RSS를 절충한다.

12. GC 언어와의 관계, 실무 튜닝

GC 언어와의 관계 (간략)

Java/Go/C#/JS 같은 관리 언어도 결국 OS에서 큰 메모리 덩어리를 받아(대개 mmap) 그 안을 자체 할당자로 관리한다. 차이는 해제를 누가 하느냐다.

  • C/C++ malloc: 프로그래머가 free 시점을 정한다. 즉시 재사용 가능, 하지만 UAF/leak은 사람 책임.
  • GC: 런타임이 도달 불가능한 객체를 찾아 회수한다. UAF가 원천 봉쇄되지만, GC가 압축(compaction)하며 객체를 옮길 수 있어(이동형 GC) 단편화를 능동적으로 없앤다. 이는 malloc이 못 하는 일이다(C 포인터는 고정되어야 하므로).
  • 그래서 관리 언어 힙은 malloc 힙보다 단편화에 강하지만, bump-pointer 할당 + 주기적 멈춤(또는 동시 GC의 복잡성)이라는 다른 비용을 진다. CLR/JVM GC는 별도 장(또는 과정)에서 깊게 다룬다.

핵심 요약

  • 라이브러리 할당자는 커널에서 큰 덩어리(brk/mmap)를 받아 바이트 단위 요청으로 분할·재활용·병합한다. M_MMAP_THRESHOLD(기본 128 KiB)는 큰 할당을 mmap으로 직행시키고, 해제된 크기를 학습해 동적으로 올라간다.
  • 청크는 size 하위 3비트에 A(non-main-arena)/M(mmapped)/P(prev-inuse)를 담고, 다음 청크의 prev_size를 경계 태그로 복제해 양 옆 청크의 free 여부를 O(1)에 판정·병합한다. free 청크는 payload 자리에 fd/bk 링크를 둔다.
  • ptmalloc2 bin: tcache(스레드 로컬·락 없음) → fastbin(병합 지연) → unsorted → small/large(병합·정렬). 작은 캐시는 성능을 위해 병합을 미루고, 그 대가로 단편화·보안 표면이 생긴다(커널 PCP/SLUB과 같은 트레이드오프).
  • brk 힙은 꼭대기부터만 줄어서, 맨 위의 장수 객체 하나가 그 아래 전부의 RSS 반환을 막는다. malloc_trim·tcmalloc/jemalloc의 madvise 반환이 대책이다.
  • 아레나는 멀티스레드 락 경합을 줄이지만, 코어 수 × 8개까지 늘어나 VIRT/RSS를 부풀린다. MALLOC_ARENA_MAX=2~4가 컨테이너의 단골 처방이다.
  • UAF·double free·overflow는 할당자 메타데이터를 오염시켜 임의 쓰기로 번진다. ASan(섀도 메모리 + 레드존 + 격리, 컴파일 계측)과 Valgrind(DBT + V/A비트, 초기화 안 된 읽기까지)가 원리를 달리해 잡는다.
  • 현대 할당자의 공통 원칙: 스레드 로컬 캐시로 락 회피, 소수 size class로 반올림, 큰 가상 영역을 자체 관리하며 안 쓰는 페이지를 적극 반환. GC 언어는 이동형 압축으로 단편화를 능동 제거하지만 다른 비용을 진다.

확인 문제

청크 size 워드의 하위 비트 중 P(PREV_INUSE)가 하는 일은?
P는 앞 청크의 사용 여부다. 내 size의 P가 0이면 앞 청크가 free이고, 그때 내 prev_size가 유효해져 this − prev_size로 앞 청크를 찾아 병합한다. 자신의 사용 여부는 "다음 청크의 P 비트"에 적힌다. M은 mmap, A는 non-main-arena로 각각 다른 비트다.
glibc 기본 설정에서 malloc(200000)(약 195 KiB)을 한 뒤 free하면?
195 KiB ≥ 128 KiB이므로 mmap 직행이고, free 시 munmap으로 커널에 바로 반납된다. fastbin(≤128 B)·tcache(≤1032 B)는 크기가 전혀 맞지 않는다. 단, 이 크기를 반복 할당·해제하면 동적 임계값이 올라가 brk 힙 재활용으로 바뀔 수 있다.
64코어 서버의 멀티스레드 C++ 서비스가 RSS는 2 GiB인데 VIRT가 40 GiB다. 가장 먼저 시도할 것은?
VIRT만 크고 RSS는 작은 것은 아레나가 코어 수×8 = 512개까지 생겨 각 64 MiB 영역을 mmap 예약한 전형적 증상이다. 실제 쓴 페이지만 RSS에 잡히므로 VIRT만 부푼다. MALLOC_ARENA_MAX를 낮추는 것이 표준 처방이다. RAM 증설은 문제를 안 고친다.
ASan과 Valgrind(Memcheck)에 대해 옳은 것은?
ASan은 -fsanitize=address 재컴파일 + 섀도 메모리로 약 2배 느림. Valgrind는 재컴파일 없이 동적 이진 번역으로 10~50배 느리지만 V비트로 초기화 안 된 값 읽기까지 잡는다. 둘 다 overflow·UAF를 잡는다(레드존·격리 vs 접근불가 유지).
tcache와 fastbin이 free 시 병합을 하지 않는 주된 이유는?
같은 크기 그대로 LIFO 리스트에 꽂아 두면 다음 같은 크기 할당을 즉시(그리고 cache-hot 상태로) 돌려줄 수 있다. 병합은 단편화를 줄이지만 작은 할당의 흔한 "할당→해제→재할당" 패턴에서는 손해다. 대신 단편화·보안 표면이 늘어 주기적 malloc_consolidate로 정리한다. 커널의 PCP/SLUB freelist와 동일한 선택이다.
모든 메모리를 free했는데도 프로세스 RSS가 거의 안 줄었다. malloc_info의 fordblks가 매우 크다. 맞는 해석은?
fordblks는 "free 되었으나 아직 OS에 반납되지 않은" 바이트다. 이것이 크면 누수가 아니라 단편화·미반납이다(누수라면 uordblks가 크다). 자동 trim은 꼭대기만 줄이므로 malloc_trim(0)을 시도하고, 살아 있는 객체가 페이지마다 흩어진 경우라면 MALLOC_ARENA_MAX↓나 jemalloc/tcmalloc 교체를 검토한다.
