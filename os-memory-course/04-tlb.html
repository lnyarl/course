TLB와 유효 접근 시간

페이징은 모든 메모리 접근을 두 번 이상의 접근으로 바꿔 놓는다. TLB는 이 비용을 거의 0으로 되돌리는 작은 캐시다. 이 장에서는 TLB의 구조, 성능 모델, 그리고 멀티코어 운영체제가 TLB 일관성을 지키기 위해 치르는 비용을 다룬다.

학습 목표

  • TLB가 없으면 왜 메모리 접근이 2배(다단계라면 그 이상)가 되는지 설명하고, 유효 접근 시간(EAT)을 계산한다.
  • 완전 연관/집합 연관 TLB의 조회 방식과 실제 CPU의 L1 dTLB·iTLB·STLB 계층을 이해한다.
  • 접근 패턴과 교체 정책에 따라 TLB 히트율이 어떻게 달라지는지 시뮬레이션으로 확인한다.
  • TLB reach 개념으로 huge page가 왜 효과적인지 정량적으로 설명한다.
  • 문맥 교환 시 TLB flush, ASID/PCID, 멀티코어 TLB shootdown의 동작과 비용을 설명한다.
  • perf로 dTLB 미스를 측정하고 해석한다.

1. 왜 TLB가 필요한가

3장에서 본 페이징의 주소 변환을 다시 떠올려 보자. CPU가 가상 주소 VA에 접근하면 MMU는 VA를 VPN(가상 페이지 번호)과 오프셋으로 나누고, 메모리에 있는 페이지 테이블에서 VPN에 해당하는 PTE를 읽어 PFN(물리 프레임 번호)을 얻는다. 그 다음에야 실제 데이터를 읽는다. 즉 프로그램이 한 번 메모리에 접근할 때마다 하드웨어는 메모리에 두 번 접근한다.

  • 단일 레벨 페이지 테이블: PTE 1회 + 데이터 1회 = 2회
  • x86-64 4단계 페이지 테이블: PML4E, PDPTE, PDE, PTE 4회 + 데이터 1회 = 최대 5회 (5장에서 자세히)
  • 5단계(LA57): 최대 6회. 가상 머신 안에서 2차원(nested) 페이지 워크까지 하면 최악 24회 이상이 된다 (15장).

명령어 인출도 메모리 접근이므로, 이 비용을 그대로 치르면 CPU는 사실상 절반 이하 속도로 돈다. 해결책은 늘 그렇듯 캐시다. 최근에 사용한 VPN → PFN 변환 결과(와 권한 비트)를 CPU 안의 작은 연관 메모리에 저장해 두는 것, 이것이 TLB(Translation Lookaside Buffer)다.

TLB가 잘 동작하는 이유는 캐시와 같다: 지역성(locality). 4KB 페이지 하나에는 64바이트 캐시 라인이 64개 들어 있으므로, 순차 접근이라면 캐시 미스 64번에 TLB 미스는 1번뿐이다. 실제 프로그램의 TLB 히트율은 보통 99% 이상이다. 하지만 "보통"에서 벗어나는 워크로드(대형 해시 테이블, 그래프 순회, 인메모리 DB, JVM 대형 힙)에서는 TLB 미스가 실행 시간의 수십 %를 차지하기도 한다. 이 장의 후반부가 바로 그 이야기다.

왜 "Lookaside"인가 TLB는 변환 경로 "옆에서(lookaside)" 먼저 들여다보는 버퍼라는 뜻이다. 현대 CPU에서는 L1 데이터 캐시가 VIPT(가상 인덱스, 물리 태그) 구조여서, 캐시 세트 인덱싱(페이지 오프셋 비트만 사용)과 TLB 조회가 병렬로 진행된다. 그래서 L1 캐시 히트 지연(4~5 사이클)에 TLB 조회 시간이 숨는다. 32KB 8-way L1D가 흔한 이유도 여기 있다: 32KB / 8-way = 4KB = 페이지 크기, 즉 인덱스 비트가 페이지 오프셋 안에 들어간다.

2.2 완전 연관 vs 집합 연관

TLB도 캐시이므로 캐시와 똑같은 설계 공간을 가진다.

  • 완전 연관(fully associative): 어떤 VPN이든 어느 엔트리에나 들어갈 수 있다. 조회 시 모든 엔트리의 태그를 동시에 비교(CAM)해야 하므로 엔트리 수가 늘면 면적·전력·지연이 급증한다. 그래서 작은 L1 TLB(수십 엔트리)에 쓰인다.
  • 집합 연관(N-way set associative): VPN의 하위 비트로 세트를 고르고, 그 세트 안의 N개만 비교한다. 엔트리 수를 1,000~3,000개로 키울 수 있지만 충돌 미스(conflict miss)가 생긴다. 특정 간격(stride)으로 접근하면 같은 세트로만 몰려 TLB가 텅 비어 있어도 미스가 난다.

2.3 실제 CPU의 TLB 계층 (대략적인 수치)

현대 CPU는 캐시처럼 TLB도 계층화한다. 파이프라인 단계와 함께 조회돼야 하는 L1 TLB는 명령어용(iTLB)과 데이터용(dTLB)으로 나뉘고 작고 빠르다. 그 뒤에 명령어/데이터 공용의 큰 L2 TLB(Intel은 STLB, Second-level TLB라고 부른다)가 있다. 아래는 공개 문서에 나온 대표 수치이며 세대마다 바뀐다.

숫자를 외울 필요는 없다. 기억할 것은 규모 감각이다: L1 TLB는 수십 엔트리, L2 TLB는 1~3천 엔트리. 4KB 페이지 기준으로 L2 TLB 전체가 덮는 메모리는 고작 수 MB에 불과하다. L3 캐시(수십 MB)보다도 작다. 이것이 5절의 TLB reach 문제다.

확인하는 방법 Linux에서 cpuid -1 | grep -i tlb(cpuid 패키지) 또는 x86info -c로 TLB 구성을 볼 수 있다. ARM에서는 TRM(Technical Reference Manual)을 참고한다. 최근 Intel CPU는 CPUID leaf 0x18로 TLB 정보를 보고한다.

3. TLB 시뮬레이터: 접근 패턴과 교체 정책

TLB가 가득 찼을 때 새 변환을 넣으려면 기존 엔트리 하나를 쫓아내야 한다. 실제 하드웨어는 진짜 LRU 대신 의사 LRU(tree-PLRU 등)나 랜덤에 가까운 정책을 쓴다. 진짜 LRU는 way 수가 늘면 상태 비트와 갱신 논리가 비싸기 때문이다. 아래 시뮬레이터로 접근 패턴 × TLB 크기 × 연관도 × 교체 정책의 상호작용을 직접 확인해 보자. 페이지는 4KB로 가정한다.

4. 유효 접근 시간(EAT)

TLB 히트율을 α, TLB 조회 시간을 ε, 메모리 접근 1회 시간을 m, 페이지 테이블 레벨 수를 L이라 하자. 히트면 TLB 조회 후 데이터 접근 1회, 미스면 TLB 조회 후 레벨마다 1회씩 페이지 테이블을 읽고 데이터에 접근한다.

EAT = α·(ε + m) + (1 − α)·(ε + (L + 1)·m)

교과서의 단일 레벨(L = 1)에서는 EAT = α(ε+m) + (1−α)(ε+2m)이다. 예: α = 80%, ε = 20ns, m = 100ns라면 0.8×120 + 0.2×220 = 140ns. 즉 40% 느려진다. 히트율이 98%면 122ns로 줄어든다.

5. TLB reach와 huge page

TLB reach = (TLB 엔트리 수) × (페이지 크기). TLB 미스 없이 접근할 수 있는 메모리의 최대 크기다. 작업 집합이 reach보다 크고 접근이 흩어져 있으면 미스율은 구조적으로 높을 수밖에 없다.

  • 1536 엔트리 × 4KB = 6MB — 현대 서버의 수백 GB 메모리에 비하면 극히 작다.
  • 1536 엔트리 × 2MB = 3GB — 같은 엔트리로 512배를 덮는다.
  • 1GB 페이지 16 엔트리 = 16GB.

지난 수십 년간 메모리 용량은 수천 배 늘었지만 TLB 엔트리 수는 수십 배밖에 늘지 않았다. 엔트리를 늘리면 조회 지연과 전력이 늘기 때문이다. 그래서 reach를 늘리는 현실적인 방법은 페이지를 키우는 것, 즉 huge page다. huge page는 5장에서 볼 것처럼 페이지 테이블 워크를 중간 레벨(PD 또는 PDPT)에서 끝내므로 미스 비용도 한 단계 이상 줄인다.

6. 문맥 교환과 TLB flush, ASID/PCID

TLB 엔트리 VPN 0x400 → PFN 0x1A2는 특정 프로세스의 페이지 테이블에서만 참이다. 프로세스 B로 전환한 뒤에도 이 엔트리가 남아 있으면 B가 A의 메모리를 읽게 된다. 가장 단순한 해법은 문맥 교환 때 TLB를 전부 비우는 것(flush)이다. 실제로 x86에서 PCID를 쓰지 않으면 CR3에 새 페이지 테이블 주소를 쓰는 순간 G 비트가 없는 모든 엔트리가 무효화된다.

문제는 비용이다. flush 자체는 빠르지만 그 뒤 TLB가 다시 채워질 때까지 연속된 미스가 난다. 스레드 전환이 잦은 서버, 시스템 콜·인터럽트가 잦은 워크로드에서 이 손실이 누적된다.

6.1 첫 번째 완화책: Global 페이지

커널 매핑은 모든 프로세스에서 같다. 그래서 x86은 PTE에 G(Global) 비트(bit 8, CR4.PGE가 켜져 있을 때 유효)를 두어 CR3를 바꿔도 이 엔트리는 남게 한다. 2018년 Meltdown 대응으로 도입된 KPTI(Kernel Page-Table Isolation)는 유저 모드용 페이지 테이블에서 커널 매핑 대부분을 없앴고, 커널 진입·복귀마다 CR3를 바꾼다. 이 때문에 시스템 콜마다 TLB가 날아갈 뻔했고, 이를 막아 준 것이 다음의 PCID다.

6.2 근본 해법: TLB 엔트리에 주소 공간 ID를 태그

엔트리마다 "어느 주소 공간의 변환인지"를 나타내는 ID를 붙이면, 조회 시 (현재 ID, VPN)이 모두 맞아야 히트로 처리된다. 그러면 문맥 교환 때 flush하지 않아도 된다. 다른 프로세스의 엔트리는 그대로 남아 있다가 돌아왔을 때 다시 히트한다.

심화: Linux는 4096개 PCID를 어떻게 쓰는가

PCID가 4096개라고 해서 프로세스마다 고정 PCID를 주지는 않는다. 그러려면 프로세스가 4096개를 넘을 때 재활용 문제가 생기고, PCID를 다른 프로세스에 재배정할 때 모든 CPU에서 해당 PCID 엔트리를 지워야 하기 때문이다. Linux x86(arch/x86/mm/tlb.c)은 대신 CPU별로 최근 사용한 소수의 mm에만 동적으로 ASID를 배정한다(TLB_NR_DYN_ASIDS, 현재 6). CPU마다 "어느 슬롯에 어느 mm이 있었고, 그 mm의 TLB 세대(tlb_gen)가 몇이었는지"를 기억해 두고, 다시 그 mm으로 전환할 때 세대가 같으면 flush 없이 CR3만 바꾼다.

KPTI가 켜져 있으면 mm 하나에 커널용/유저용 PCID 쌍이 붙어서 시스템 콜 진입·복귀 시 CR3 전환이 flush 없이 이뤄진다. PCID가 없는 오래된 CPU에서 KPTI 성능 저하가 유독 컸던 이유다.

ARM64 Linux(arch/arm64/mm/context.c)는 ASID 공간 전체를 전역 비트맵으로 관리하며, 다 소진되면 세대(generation)를 올리고 모든 CPU의 TLB를 한 번에 비운 뒤 재배정하는 롤오버 방식을 쓴다.

7. TLB shootdown

TLB는 코어마다 따로 있고, 데이터 캐시와 달리 하드웨어가 자동으로 일관성을 맞춰 주지 않는다(x86 기준). 같은 프로세스의 스레드가 코어 0, 1, 2에서 돌고 있을 때 코어 0이 munmap()으로 페이지를 해제하면, 코어 1과 2의 TLB에는 이미 사라진 매핑이 남아 있다. 이 상태에서 그 물리 프레임이 다른 용도로 재사용되면 코어 1은 남의 데이터를 읽거나 덮어쓴다. 보안 사고이자 메모리 오염이다.

그래서 운영체제는 페이지 테이블에서 매핑을 없애거나 권한을 줄일 때(munmap, mprotect, madvise(MADV_DONTNEED), 페이지 회수·마이그레이션, COW 해제 등) 다른 코어들의 TLB까지 무효화해야 한다. 이 과정을 TLB shootdown이라고 한다. x86에서는 IPI(Inter-Processor Interrupt)로 이뤄진다.

TLB shootdown 단계별 애니메이션 (x86, 4코어)
CPU 0~2는 같은 프로세스(mm A)의 스레드를 실행 중이고, CPU 3은 다른 프로세스(mm B)를 실행 중이다. CPU 0의 스레드가 페이지 X를 munmap 한다.

7.1 왜 비싼가, 그리고 현업에서 어떻게 보이나

  • 동기적이다: 시작한 코어는 모든 대상 코어의 응답을 기다린다. 대상 코어 수가 늘수록, 그리고 대상 코어가 인터럽트를 막고 있는 구간에 있으면 지연이 늘어난다. 대략 수 μs 단위다.
  • 대상 코어도 방해받는다: 하던 일을 멈추고 인터럽트 핸들러를 실행하며, 무효화 후에는 TLB 미스가 따라온다.
  • 증상: 스레드가 많은 프로세스에서 munmap/madvise가 잦으면 /proc/interrupts의 TLB(TLB shootdowns) 카운터가 급증하고 시스템 시간(sys%)이 오른다. 메모리를 OS에 자주 반환하는 할당자 설정(예: jemalloc/tcmalloc의 공격적 purge)에서 흔하다.

Linux의 완화책: (1) 배치 — mmu_gather로 여러 페이지 해제를 모아 한 번에 flush, (2) 범위 vs 전체 — 페이지가 많으면 INVLPG 반복 대신 전체 flush(tlb_single_page_flush_ceiling, 기본 33), (3) lazy TLB — 커널 스레드를 실행 중인 코어는 이전 mm을 빌려 쓰므로 IPI 대신 나중에 확인, (4) mm_cpumask로 그 mm을 실제로 실행한 적 있는 코어에만 IPI. 관련 함수는 flush_tlb_mm_range()와 native_flush_tlb_multi()(구 버전 native_flush_tlb_others())다.

ARM64는 다르다: 하드웨어 브로드캐스트 ARMv8은 TLBI VAE1IS처럼 접미사 IS(Inner Shareable)가 붙은 TLB 무효화 명령을 제공한다. 이 명령은 인터커넥트를 통해 같은 공유 도메인의 모든 코어에 무효화를 브로드캐스트하고, 뒤따르는 DSB ISH가 완료를 보장한다. IPI도 인터럽트 핸들러도 필요 없다. 대신 브로드캐스트는 관계없는 코어에도 전달되므로 코어가 아주 많은 서버에서는 인터커넥트 부하가 이슈가 된다. 최근 x86에도 비슷한 기능이 들어오고 있다(AMD의 INVLPGB/TLBSYNC).

8. 소프트웨어 관리 TLB vs 하드웨어 페이지 워커

TLB 미스가 났을 때 누가 페이지 테이블을 걷는가? 두 가지 설계가 있다.

8.1 하드웨어 관리 (x86, ARM64, RISC-V 대부분)

MMU 안의 페이지 워커(page miss handler)가 CR3/TTBR에서 시작해 페이지 테이블을 직접 읽는다. 따라서 페이지 테이블 형식은 아키텍처가 정한다. OS는 그 형식에 맞춰 테이블을 만들어 둘 뿐이다. 장점은 빠르다는 것이다. 예외가 없으니 파이프라인을 비우지 않고, 비순차 실행 중에 워크를 진행하며, 최근 코어는 여러 워크를 동시에 처리하고 다음 페이지를 미리 워크하기도 한다. x86 워커는 PTE의 Accessed/Dirty 비트도 하드웨어로 세팅한다(ARM64는 ARMv8.1의 선택 기능 TCR_EL1.HA/HD).

8.2 소프트웨어 관리 (MIPS, 초기 SPARC, Alpha의 PALcode 등)

MIPS의 TLB 미스는 예외다. 하드웨어는 미스난 가상 주소를 BadVAddr와 Context/EntryHi에 넣고 TLB Refill 예외 벡터로 점프한다. OS의 핸들러(수십 명령)가 자기 마음대로 정한 페이지 테이블을 조회해 EntryLo0/EntryLo1에 값을 넣고 tlbwr(Random 레지스터가 가리키는 슬롯에 쓰기)를 실행한 뒤 eret로 복귀한다. MIPS TLB 엔트리는 짝수/홀수 인접한 두 페이지를 한 번에 매핑한다(VPN2). Linux MIPS는 이 refill 핸들러를 부팅 시 CPU 특성에 맞춰 즉석에서 기계어로 생성한다(arch/mips/mm/tlbex.c).

역사는 하드웨어 워커가 이겼다. 핸들러 실행 비용이 메모리 지연에 비해 상대적으로 커졌고, 가상화가 보편화되면서 "TLB 미스마다 소프트웨어 개입"이 감당하기 어려워졌기 때문이다. 다만 소프트웨어 관리 TLB의 아이디어(OS가 변환 구조를 선택한다)는 연구와 일부 특수 프로세서에 남아 있다.

9. 실무: perf로 TLB 미스 측정하기

아래 프로그램은 256MB 배열을 stride 바이트 간격으로 순환하며 읽는다. stride가 64면 한 페이지에서 64번 연속 읽으므로 TLB 미스는 64번에 한 번이다. stride가 4096이면 매 접근이 새 페이지이고, 65,536개 페이지(256MB/4KB)는 STLB reach(수 MB)를 훨씬 넘는다.

// tlbtest.c — gcc -O2 tlbtest.c -o tlbtest
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
int main(int argc, char **argv) {
    size_t size = 256UL << 20, stride = strtoul(argv[1], 0, 10);
    char *a = aligned_alloc(1 << 21, size);
    memset(a, 1, size);                       /* 미리 폴트 처리 (6장) */
    size_t idx = 0; long sum = 0;
    for (long i = 0; i < 100000000; i++) {   /* 1억 번 로드 */
        sum += a[idx];
        idx = (idx + stride) & (size - 1);
    }
    printf("%ld\n", sum);
}
$ perf stat -e dTLB-loads,dTLB-load-misses ./tlbtest 64
     1xx,xxx,xxx      dTLB-loads
       1,6xx,xxx      dTLB-load-misses   #    ~1.5% of all dTLB cache accesses

$ perf stat -e dTLB-loads,dTLB-load-misses ./tlbtest 4096
     1xx,xxx,xxx      dTLB-loads
     1xx,xxx,xxx      dTLB-load-misses   #   ~100% of all dTLB cache accesses

위 출력은 형태를 보여 주기 위한 예시이며 실제 숫자는 CPU, 커널, 컴파일러에 따라 다르다. 해석할 때 주의할 점:

  • 범용 이벤트의 의미는 CPU마다 다르다. dTLB-load-misses가 L1 dTLB 미스인지, STLB 미스(=페이지 워크 발생)인지는 perf가 마이크로아키텍처 이벤트로 매핑하는 방식에 달렸다. 정밀하게 보려면 perf list | grep -i tlb로 원시 이벤트를 찾는다. Intel이라면 dtlb_load_misses.walk_completed(워크 완료 수)와 dtlb_load_misses.walk_active(워크 진행 중인 사이클 수) 같은 이벤트가 있다. walk_active / cycles가 "TLB 미스로 날린 시간 비율"에 가장 가까운 지표다.
  • TLB 미스와 캐시 미스는 같이 온다. stride 4096은 캐시 미스도 매번 일으키므로, 실행 시간 차이를 전부 TLB 탓으로 돌리면 안 된다. huge page를 켜고 같은 실험을 반복해 차이를 분리하라.
  • huge page 효과 확인: 위 코드에서 memset 앞에 madvise(a, size, MADV_HUGEPAGE)를 넣고(<sys/mman.h>), grep AnonHugePages /proc/meminfo로 THP 적용 여부를 확인한 뒤 다시 측정한다. stride 4096에서 dTLB 미스가 급감한다(256MB = 2MB 페이지 128개).
  • iTLB도 있다: 코드가 수백 MB인 대형 바이너리(브라우저, DB, 대형 C++ 서버)에서는 iTLB-load-misses가 문제가 된다. 코드 영역을 huge page로 올리는 기법(예: 링커로 핫 코드를 모으고 2MB 정렬, 런타임에 재매핑)이 실제 프로덕션에서 쓰인다.
TLB 관점의 성능 체크리스트
  1. 작업 집합이 STLB reach(4KB 기준 수 MB)를 넘는가? 넘는다면 접근이 랜덤한가?
  2. THP 상태(always/madvise/never)와 AnonHugePages 확인.
  3. 데이터 구조의 메모리 밀도: 포인터 추적 구조(연결 리스트, 트리)는 노드가 페이지 전역에 흩어지기 쉽다. 아레나 할당으로 모으면 TLB와 캐시 모두 이득.
  4. 스레드 많은 프로세스에서 /proc/interrupts의 TLB shootdown 증가율.
  5. 가상 머신이라면 미스 비용이 2차원 워크로 몇 배 커진다(15장). 게스트와 호스트 모두 huge page를 쓰는 것이 효과적이다.

핵심 요약

  • 페이징은 메모리 접근 1회를 (레벨 수 + 1)회로 늘린다. TLB는 VPN → PFN 변환을 캐시해 이 비용을 히트 시 거의 0으로 만든다.
  • L1 TLB는 작고(수십 엔트리) 완전 연관 또는 고연관, L2 TLB(STLB)는 1~3천 엔트리의 집합 연관이 일반적이다. 집합 연관에서는 특정 stride가 충돌 미스를 만든다.
  • EAT = α(ε+m) + (1−α)(ε+(L+1)m). 이 식은 상한이며, 실제 워크는 데이터 캐시와 페이지 워크 캐시 덕분에 더 싸다.
  • LRU는 TLB 크기보다 한 페이지 큰 순환 접근에서 히트율 0%가 된다. 작업 집합이 TLB에 들어가느냐가 성능 절벽을 만든다.
  • TLB reach = 엔트리 수 × 페이지 크기. 4KB 기준 수 MB에 불과하며, huge page(2MB/1GB)가 reach를 512배·26만 배로 늘리는 가장 현실적인 수단이다.
  • 문맥 교환 시 TLB flush를 피하기 위해 x86은 PCID(12비트), ARM64·MIPS·RISC-V는 ASID를 쓴다. 커널 매핑은 Global 비트로 보존한다(KPTI 이전).
  • 매핑 제거·권한 축소 시 다른 코어의 TLB를 비우는 shootdown이 필요하다. x86은 IPI 기반이라 비싸고, ARM64는 TLBI…IS 브로드캐스트로 하드웨어가 처리한다.
  • MIPS 같은 소프트웨어 관리 TLB는 OS가 페이지 테이블 형식을 자유롭게 정하지만 미스 비용이 크다. 현대 주류는 하드웨어 페이지 워커다.
  • 측정은 perf stat -e dTLB-loads,dTLB-load-misses로 시작하고, 정밀 분석은 워크 사이클 이벤트(Intel의 dtlb_load_misses.walk_active 등)로 한다.

확인 문제

단일 레벨 페이지 테이블, TLB 히트율 80%, TLB 조회 20ns, 메모리 접근 100ns일 때 유효 접근 시간은?
0.8 × (20 + 100) + 0.2 × (20 + 100 + 100) = 96 + 44 = 140ns. 미스일 때는 TLB 조회 후 PTE 읽기 1회와 데이터 읽기 1회가 필요하다.
16엔트리 완전 연관 TLB(LRU)에서 17개 페이지를 0,1,…,16,0,1,…처럼 순환하며 계속 접근한다. 장기적인 TLB 히트율은?
페이지 16을 넣을 때 LRU는 가장 오래전에 쓴 페이지 0을 쫓아낸다. 그런데 다음 접근이 바로 0이다. 0을 넣으면서 1을 쫓아내고, 다음이 1이다. 이렇게 매번 미스가 난다. 이런 상황에서는 Random 정책이나 OPT가 낫다. 시뮬레이터에서 직접 확인해 보라.
STLB가 1536 엔트리일 때, 4KB 페이지와 2MB 페이지의 TLB reach는 각각 얼마인가?
1536 × 4KB = 6144KB = 6MB, 1536 × 2MB = 3072MB = 3GB. 같은 엔트리 수로 512배를 덮는다.
x86-64에서 PCID를 사용하는 주된 목적은?
PCID는 TLB 엔트리에 주소 공간 태그를 붙여 문맥 교환·KPTI의 CR3 전환 시 flush를 피하게 한다. 다른 코어 무효화(shootdown)는 여전히 OS가 IPI로 해야 한다.
스레드 32개가 여러 코어에서 실행되는 프로세스에서 madvise(MADV_DONTNEED) 호출이 아주 잦을 때, 가장 먼저 의심할 오버헤드는?
매핑을 제거하면 해당 mm을 실행 중인(했던) 모든 코어의 TLB를 무효화해야 하므로 IPI가 날아가고, 시작한 코어는 응답을 기다린다. /proc/interrupts의 TLB 카운터와 sys 시간으로 확인한다.
MIPS 같은 소프트웨어 관리 TLB에서 TLB 미스가 발생하면?
소프트웨어 관리 TLB에서 TLB 미스는 곧 예외다. 핸들러는 OS가 정한 형식의 페이지 테이블을 읽어 EntryLo 레지스터를 채우고 TLB 쓰기 명령을 실행한다. 페이지 자체가 메모리에 없으면 그때 일반 페이지 폴트 경로로 넘어간다.
16엔트리 TLB를 4-way(4세트)로 구성하고 세트 = VPN mod 4라 하자. VPN 0, 4, 8, 12, 16을 순환 접근하면?
TLB 전체에는 자리가 남아 있어도 세트 하나의 용량(4)을 넘으면 충돌 미스가 난다. 2의 거듭제곱 stride로 접근하는 코드(큰 행렬의 열 방향 순회 등)에서 실제로 나타나는 현상이다.
