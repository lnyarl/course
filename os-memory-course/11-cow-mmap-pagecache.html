1. fork()와 Copy-on-Write

Unix의 프로세스 생성은 fork()로 자신을 복제한 뒤, 자식이 대개 곧바로 execve()로 다른 프로그램을 올리는 패턴입니다. 부모의 메모리를 fork 시점에 전부 복사하면 어떻게 될까요? 8 GiB짜리 JVM이 셸 명령 하나를 실행하려고 8 GiB를 복사하고, 자식은 몇 마이크로초 뒤 exec로 그 복사본을 통째로 버립니다. 시간과 메모리를 모두 낭비하는 셈입니다.

Copy-on-Write(COW)는 복사를 "정말 필요해질 때까지" 미룹니다. fork는 데이터 페이지를 복사하지 않고 페이지 테이블 항목(PTE)만 복사합니다. 부모와 자식은 같은 물리 프레임을 가리키게 되고, 커널은 양쪽 PTE를 읽기 전용으로 바꿉니다. 둘 중 하나가 쓰려고 하면 MMU가 보호 폴트를 일으키고, 그때 커널이 그 페이지 하나만 복사합니다.

커널은 "진짜 보호 위반"과 "COW 폴트"를 어떻게 구분하나

핵심은 VMA 권한과 PTE 권한의 불일치입니다. fork 후 VMA(vm_area_struct)에는 여전히 VM_WRITE가 있습니다. 쓰기를 막는 쪽은 PTE의 R/W 비트뿐입니다. 쓰기 폴트가 나면 커널은 이렇게 판단합니다.

  • VMA에도 쓰기 권한이 없다 → 진짜 위반 → SIGSEGV.
  • VMA는 쓰기 가능한 private 매핑인데 PTE만 읽기 전용이다 → COW 폴트 → do_wp_page() 처리.

do_wp_page()는 바로 복사하지 않고 먼저 이 페이지를 나 혼자 쓰고 있는지 확인합니다. 다른 프로세스가 이미 자기 사본을 만들어 떠났거나 자식이 exit해서 내가 마지막 사용자라면, 복사 없이 PTE에 쓰기 권한만 다시 줍니다(재사용, reuse). 공유자가 남아 있을 때만 wp_page_copy()가 새 프레임을 할당하고 4 KiB를 복사한 뒤 내 PTE를 새 프레임으로 돌립니다. 이 판정은 페이지의 참조 카운트와 "익명 페이지 독점" 플래그(PageAnonExclusive)로 이루어집니다. 세부 조건은 커널 버전마다 여러 번 바뀌었지만, "마지막 사용자는 복사하지 않는다"는 원칙은 같습니다.

fork 자체의 비용: 페이지 테이블 복사

COW가 데이터 복사를 없앴어도 fork는 공짜가 아닙니다. 커널(copy_page_range())은 부모의 PTE를 자식 쪽으로 복사하고, 부모 PTE를 쓰기 금지로 바꾸고, 각 페이지의 참조 카운트를 올립니다. RSS가 100 GiB인 프로세스라면 4 KiB 페이지 약 2,600만 개, PTE만 약 200 MiB입니다. 그래서 fork 한 번에 수십~수백 밀리초가 걸리고, 그동안 부모 스레드가 멈춥니다. 이미 쓰기 금지된 PTE를 부모가 다시 쓰면 그때마다 COW 폴트도 납니다. 커널은 파일 기반 공유 매핑처럼 나중에 폴트로 다시 채울 수 있는 VMA의 PTE는 복사를 생략해 이 비용을 줄입니다.

현업 사례: Redis BGSAVE와 메모리 2배 문제 Redis는 스냅샷(RDB)이나 AOF rewrite를 위해 fork하고, 자식이 메모리를 직렬화하는 동안 부모는 요청을 계속 처리합니다. 부모가 쓰는 페이지마다 COW 복사가 일어나므로 쓰기가 많은 워크로드에서는 스냅샷 중 메모리 사용량이 최대 2배까지 늘 수 있습니다. 운영 시 확인할 점:
  • fork 지연: Redis INFO의 latest_fork_usec. 페이지 테이블 크기에 비례합니다.
  • Transparent Huge Page: COW가 큰 페이지 단위로 일어나면 지연과 복사량이 커질 수 있어 Redis는 THP 비활성화를 권장합니다(13장).
  • overcommit: vm.overcommit_memory=2(엄격)이면 대형 프로세스의 fork가 커밋 한도에 걸려 ENOMEM으로 실패할 수 있습니다. 실제 복사가 거의 없더라도 COW로 쓸 수 있는 메모리 전체가 커밋으로 계산되기 때문입니다. Redis가 vm.overcommit_memory=1을 권하는 이유입니다(12장).
더 깊이: fork와 관련된 madvise 플래그와 멀티스레드 함정
  • MADV_DONTFORK: 해당 범위를 자식에 아예 매핑하지 않습니다. RDMA·DMA 버퍼처럼 물리 주소가 고정돼야 하는 영역에 씁니다. COW로 부모 쪽 페이지가 다른 프레임으로 바뀌면 장치는 옛 프레임에 계속 DMA하게 되기 때문입니다.
  • MADV_WIPEONFORK(Linux 4.14+): 자식 쪽에서는 해당 범위가 0으로 채워진 상태로 보입니다. 난수 생성기 상태나 비밀 키가 자식에게 복제되는 것을 막습니다.
  • 멀티스레드 프로세스의 fork: 자식에는 fork를 호출한 스레드 하나만 복제됩니다. 다른 스레드가 잡고 있던 malloc 잠금 같은 락은 자식에서 영원히 풀리지 않을 수 있습니다. 그래서 POSIX는 멀티스레드 프로그램에서 fork 후 exec 전까지 async-signal-safe 함수만 호출하라고 요구합니다.

2. vfork, posix_spawn, clone

COW 덕분에 fork+exec는 싸졌지만, 앞에서 본 것처럼 페이지 테이블 복사 비용은 남습니다. 거대한 프로세스가 짧은 자식을 자주 띄우는 경우(빌드 도구, JVM이 외부 명령 실행 등)에는 이 비용이 눈에 띕니다. 결국 exec로 버릴 주소 공간이라면 처음부터 복제하지 않는 편이 낫습니다.

방식주소 공간부모의 상태주의점
fork()COW로 복제(PTE 복사)계속 실행대형 프로세스에서 fork 지연, overcommit 계산
vfork()부모 것을 그대로 빌려 씀(복제 없음)자식이 execve 또는 _exit할 때까지 정지자식이 변수를 바꾸거나 함수에서 return하면 부모 스택·데이터가 깨짐. exec/_exit 외에는 하지 말 것
posix_spawn()구현에 따라 다름. glibc(2.24+)는 Linux에서 clone(CLONE_VM|CLONE_VFORK)과 별도 스택 사용exec 성공/실패가 정해질 때까지 대기vfork의 속도를 안전한 API로 제공. 파일 디스크립터·시그널 설정은 attr/file_actions로 지정
clone()/clone3()플래그로 공유 범위를 직접 선택 (CLONE_VM이면 공유 = 스레드)플래그에 따름pthread_create도 내부적으로 clone. fork·vfork·스레드는 모두 이 위의 특수한 경우
설계 관점 fork가 "복제 후 수정" 모델이라면 posix_spawn은 "무엇을 실행할지 한 번에 기술" 모델입니다. fork 모델은 유연하지만 주소 공간 복제 비용과 멀티스레드 함정을 안고 있어서, 프로세스를 많이 띄우는 런타임은 대부분 posix_spawn이나 CLONE_VM|CLONE_VFORK 경로로 옮겨 갔습니다. 대용량 서비스에서 system()이나 popen()을 자주 부른다면 어느 경로로 자식을 만드는지 확인해 볼 가치가 있습니다.

3. mmap의 네 가지 조합

mmap(addr, len, prot, flags, fd, off)은 두 질문에 대한 답으로 성격이 정해집니다.

  1. 무엇으로 채우나? 파일(fd)인가, 0으로 채운 익명 메모리(MAP_ANONYMOUS)인가.
  2. 쓰기를 누구와 공유하나? 나만 보는가(MAP_PRIVATE, COW), 같은 대상을 매핑한 모두가 보는가(MAP_SHARED).

mmap은 호출 시점에 아무것도 읽거나 할당하지 않습니다. VMA 하나만 만들고, 실제 페이지는 첫 접근 때 폴트로 채웁니다(6장의 demand paging). 미리 채우려면 MAP_POPULATE나 madvise(MADV_WILLNEED)를 씁니다.

인터랙티브 매트릭스: file/anonymous × private/shared
셀을 눌러 동작, 쓰기 시 일어나는 일, fork 후 동작, 예시 코드, 실제 용도, /proc/meminfo에 잡히는 항목을 확인하세요.
파일 매핑의 함정: SIGBUS 파일 매핑에서 파일 크기를 넘어선 페이지를 건드리거나, 다른 프로세스가 파일을 truncate해서 매핑 범위 뒤쪽이 사라지면 SIGBUS가 납니다. 디스크 I/O 오류도 read()처럼 에러 코드로 돌아오지 않고 시그널로 옵니다. mmap 기반 저장소(LMDB 등)나 로그 파일을 매핑하는 코드에서 자주 만나는 크래시 원인입니다.

4. 페이지 캐시: address_space와 XArray

Linux에서 일반 파일 I/O는 거의 모두 페이지 캐시를 거칩니다. 페이지 캐시는 "파일의 어느 오프셋이 어느 물리 페이지에 들어 있는지"를 기록한 커널 자료구조이고, 다음과 같이 구성됩니다.

  • 각 inode는 struct address_space(inode->i_mapping)를 하나 가집니다. 이름과 달리 주소 공간이 아니라 "이 파일의 캐시된 페이지 집합"입니다.
  • address_space->i_pages가 실제 인덱스입니다. 키는 파일 내 페이지 번호(오프셋 / 페이지 크기), 값은 페이지(최근 커널에서는 folio)입니다. 오래전에는 radix tree였고 Linux 4.17부터 같은 개념을 더 다루기 쉬운 API로 감싼 XArray로 바뀌었습니다. 각 항목에는 dirty·writeback 같은 태그가 붙어 있어, writeback할 때 "dirty 태그가 붙은 항목만" 빠르게 순회할 수 있습니다.
  • address_space->i_mmap은 이 파일을 매핑한 모든 VMA를 담은 구간 트리(interval tree)입니다. 페이지 하나가 어느 프로세스의 어느 가상 주소에 매핑돼 있는지 역으로 찾을 때 씁니다(9절 rmap).
  • folio(5.16 무렵 도입)는 "하나 이상의 연속 페이지 묶음"을 나타내는 타입입니다. 큰 folio를 쓰면 페이지 캐시 항목 수와 LRU 관리 비용이 줄어듭니다. 이 장에서는 편의상 "페이지"라고 부릅니다.

파일 매핑과 페이지 캐시의 관계

파일을 MAP_SHARED로 매핑하면 PTE가 페이지 캐시 페이지 자체를 가리킵니다. 그래서 다음이 모두 같은 물리 페이지를 봅니다.

  • 같은 파일을 mmap한 다른 프로세스들
  • 그 파일을 read()하는 프로세스 (read는 페이지 캐시에서 복사해 감)
  • MAP_PRIVATE로 매핑한 프로세스 중 아직 그 페이지에 쓰지 않은 프로세스

MAP_PRIVATE 매핑에 쓰면 그 순간 COW가 일어나, 그 프로세스만의 익명 페이지가 생깁니다. 이후 파일이 바뀌어도 그 페이지에는 반영되지 않습니다. 반대로 아직 쓰지 않은 페이지에서 파일 변경이 보일지는 POSIX상 정의되지 않았고, Linux에서는 보통 보입니다(같은 캐시 페이지를 보고 있으므로). 이식성 있는 코드는 이 동작에 기대면 안 됩니다.

실전: 페이지 캐시에 무엇이 올라와 있나 fincore(util-linux)나 vmtouch는 파일별로 페이지 캐시에 상주하는 페이지 수를 보여 줍니다. 내부적으로 mmap 후 mincore(2)로 상주 여부를 묻는 방식입니다. "DB 재시작 직후 느린 이유"(캐시 콜드)를 확인할 때 유용합니다. 시스템 전체 합계는 /proc/meminfo의 Cached, 그중 누군가 매핑하고 있는 양은 Mapped입니다.

5. read() vs mmap: 데이터 경로

같은 파일을 읽어도 데이터가 사용자 코드에 닿는 경로는 다릅니다. read()는 페이지 캐시에서 사용자 버퍼로 CPU 복사를 한 번 하고, mmap은 PTE가 페이지 캐시를 직접 가리키게 만듭니다.

왜 데이터베이스는 mmap을 피하기도 하나 mmap에 기대면 어느 페이지를 언제 내보낼지를 커널 LRU가 정합니다. DB는 트랜잭션 의미에 맞춰 "이 페이지는 WAL이 기록된 뒤에만 디스크로 가야 한다" 같은 순서를 지켜야 하는데, MAP_SHARED 페이지는 커널이 아무 때나 writeback할 수 있어 이 순서를 직접 통제하기 어렵습니다. 그래서 많은 DB가 자체 버퍼 풀 + pread/pwrite(또는 O_DIRECT) 구조를 택합니다. 반대로 LMDB처럼 읽기 전용 매핑과 copy-on-write B-tree로 이 문제를 비켜 가는 설계도 있습니다.

6. Dirty 페이지 writeback과 쓰기 스로틀링

write()는 보통 디스크에 쓰지 않습니다. 페이지 캐시의 해당 페이지를 수정하고 dirty 표시만 한 뒤 바로 반환합니다. 실제 디스크 기록(writeback)은 나중에 커널의 flusher 작업자(ps에서 kworker/…+flush-8:0처럼 보이는 per-device writeback 워커)가 합니다. 쓰기 지연 덕분에 같은 블록에 대한 여러 번의 쓰기가 합쳐지고 I/O가 정렬·병합됩니다. 대신 두 가지 위험이 생깁니다.

  • 전원이 나가면 dirty 데이터가 사라진다 → 앱이 필요하면 fsync (7절).
  • 앱이 디스크보다 빨리 쓰면 dirty 페이지가 끝없이 쌓여 메모리를 잡아먹고, 결국 한꺼번에 플러시하느라 긴 지연이 생긴다 → 임계값과 스로틀링.

스로틀링의 실제 모양

Linux 3.2 이후의 "IO-less dirty throttling"은 쓰는 프로세스가 직접 writeback I/O를 하지 않습니다. 대신 dirty 양에 따라 잠깐씩 잠들게(pause) 해서 쓰기 속도를 디스크 쓰기 대역폭 쪽으로 맞춥니다. 대략 이렇게 동작합니다.

  • dirty ≤ (background 임계 + 한도) / 2 (freerun 구간): 제한 없음.
  • 그 위: dirty가 setpoint(freerun과 한도의 중간쯤) 근처에 머물도록 쓰기 속도를 점점 줄임. setpoint에서 쓰기 속도 ≈ 디스크 대역폭.
  • 한도에 닿으면 강하게 차단.

7. fsync/msync, O_DIRECT, readahead

내구성: fsync 계열

fsyncgate (2018): fsync 실패 후 다시 fsync하면 성공한다? writeback 중 I/O 오류가 나면 해당 페이지는 dirty 표시가 지워질 수 있고, 오류는 한 번만 보고됩니다. PostgreSQL은 fsync가 실패하면 재시도하던 구조였는데, 재시도한 fsync가 "성공"을 돌려줘도 데이터는 이미 유실된 상태일 수 있다는 사실이 2018년에 드러났습니다. 이후 커널은 errseq_t(4.13+)로 오류를 파일 디스크립터별로 더 신뢰성 있게 전달하게 됐고, PostgreSQL은 fsync 실패 시 PANIC 후 WAL 복구로 정책을 바꿨습니다. 교훈은 이렇습니다. fsync 실패는 재시도할 오류가 아니라 "그 데이터는 잃었을 수 있다"는 신호다.

새 파일을 만들었다면 파일 fsync에 더해 디렉토리 fsync도 해야 디렉토리 엔트리가 영속화됩니다. "임시 파일에 쓰기 → fsync → rename → 디렉토리 fsync"는 원자적 교체의 표준 패턴입니다.

O_DIRECT: 페이지 캐시 우회

open(..., O_DIRECT)는 페이지 캐시를 거치지 않고 사용자 버퍼와 장치 사이에서 바로 DMA합니다.

  • 쓰는 이유: 자체 버퍼 풀을 가진 DB(예: InnoDB의 innodb_flush_method=O_DIRECT)는 캐시가 두 겹(DB 버퍼 풀 + 페이지 캐시)이 되는 낭비를 피하고, 캐싱 정책을 직접 통제합니다.
  • 제약: 버퍼 주소·파일 오프셋·길이를 장치 논리 블록 크기(보통 512 B 또는 4 KiB) 단위로 정렬해야 합니다. 맞지 않으면 EINVAL. 최근 커널은 statx()의 STATX_DIOALIGN으로 요구 정렬을 알려 줍니다.
  • O_DIRECT ≠ 내구성: 페이지 캐시는 건너뛰지만 장치의 휘발성 쓰기 캐시나 파일시스템 메타데이터는 남아 있으므로, 내구성이 필요하면 여전히 fsync/fdatasync(또는 O_DSYNC)가 필요합니다.
  • 같은 파일에 버퍼드 I/O와 O_DIRECT를 섞으면 캐시 일관성 비용과 미묘한 경쟁이 생깁니다.

readahead: 순차 읽기 예측

커널은 파일별로 접근 패턴을 추적하다가 순차 읽기가 감지되면 요청보다 앞쪽 페이지를 미리 비동기로 읽습니다. 윈도우는 순차성이 이어질수록 커지며, 기본 최대치는 장치의 /sys/block/<dev>/queue/read_ahead_kb(흔히 128 KiB, blockdev --getra는 512 B 섹터 단위로 표시)로 정해집니다. 프로그램이 힌트를 줄 수도 있습니다.

  • posix_fadvise(fd, off, len, POSIX_FADV_SEQUENTIAL / RANDOM / WILLNEED / DONTNEED): DONTNEED는 clean 캐시 페이지를 버리도록 요청합니다. 백업 도구가 캐시를 오염시키지 않으려고 씁니다.
  • madvise(addr, len, MADV_SEQUENTIAL / MADV_RANDOM / MADV_WILLNEED): mmap 영역용입니다.
  • readahead(2): 지정 범위를 페이지 캐시로 미리 읽습니다.
랜덤 접근 워크로드의 함정 랜덤 읽기 위주의 큰 mmap(예: 키-값 저장소 인덱스)에서 readahead가 켜져 있으면, 4 KiB를 원했는데 주변 수십 KiB를 같이 읽어 I/O 대역폭과 캐시를 낭비합니다. MADV_RANDOM으로 끄면 처리량이 크게 오르는 경우가 많습니다.

8. 공유 메모리와 tmpfs

프로세스 간에 같은 물리 페이지를 공유하는 방법은 여러 가지지만, Linux에서는 대부분 같은 기반을 씁니다. shmem(tmpfs의 내부 구현)입니다. shmem 페이지는 "파일처럼 address_space에 들어 있지만 뒤에 디스크가 없는" 페이지라서 회수하려면 swap으로 내보내야 합니다(12장).

tmpfs

tmpfs는 shmem 위의 메모리 파일시스템입니다. /dev/shm, /run, 많은 배포판의 /tmp가 tmpfs입니다. 기본 크기 한도는 RAM의 절반이고(mount -o size=로 변경), 한도는 상한일 뿐 실제로 쓴 만큼만 메모리를 씁니다. 파일을 지우기 전까지 그 메모리는 회수되지 않습니다(swap이 있으면 swap으로만 나감).

현업에서 자주 보는 증상
  • "buff/cache가 큰데 메모리가 안 풀린다": tmpfs와 공유 메모리는 /proc/meminfo의 Shmem으로 집계되면서 Cached에도 포함됩니다. 겉보기엔 캐시지만 drop_caches로도 비워지지 않습니다(12장).
  • 컨테이너의 "Bus error": Docker는 기본 /dev/shm을 64 MB로 잡습니다. 공유 메모리로 데이터를 주고받는 프로그램(예: PyTorch DataLoader의 멀티 워커)이 이 한도를 넘으면 매핑된 페이지를 채우지 못해 SIGBUS로 죽습니다. --shm-size나 쿠버네티스의 emptyDir: {medium: Memory}로 키웁니다. 이 메모리는 컨테이너 cgroup에 과금된다는 점도 기억해 두세요.

9. 역매핑(rmap)

페이지 테이블은 "가상 주소 → 물리 페이지" 방향만 알려 줍니다. 그런데 커널은 반대 방향 질문을 자주 해야 합니다. "이 물리 페이지를 매핑하고 있는 PTE는 어디 어디인가?"

  • 회수(12장): 페이지를 내보내려면 그 페이지를 가리키는 모든 PTE를 지워야 합니다(try_to_unmap). 최근 접근 여부도 모든 PTE의 Accessed 비트를 모아 봐야 압니다(folio_referenced).
  • 페이지 이동: NUMA 밸런싱, 메모리 compaction, 메모리 핫플러그는 페이지를 옮긴 뒤 모든 PTE를 새 위치로 고쳐야 합니다.
  • KSM: 같은 내용의 페이지를 합칠 때도 매핑을 바꿔야 합니다(15장에서 다룸).

모든 PTE마다 역방향 포인터를 두면 메모리가 너무 많이 듭니다(2.6 초기의 pte_chain 방식이 그랬습니다). 현재 Linux는 객체 기반 rmap을 씁니다. 페이지에는 "어느 객체에 속하는지"와 그 객체 안의 오프셋만 기록하고, 객체에서 매핑 후보 VMA들을 찾아 가상 주소를 계산한 뒤 페이지 테이블을 걸어 PTE에 도달합니다.

여기서 트레이드오프가 보입니다. 역매핑 탐색은 "후보 VMA를 모두 훑는" 작업이라, 같은 파일을 수천 프로세스가 매핑하거나(예: 공유 라이브러리) fork 계보가 깊어 anon_vma 체인이 길어지면 회수 한 번에 드는 비용이 커집니다. 예전에 fork를 반복하는 서버에서 anon_vma 체인이 비정상적으로 길어져 회수가 느려지는 문제가 보고되었고, 커널은 anon_vma 재사용 같은 최적화로 이를 완화해 왔습니다. 페이지당 메모리 오버헤드를 줄인 대가로 탐색 비용을 받아들인 설계입니다.

다음 장과의 연결 이 장에서 본 페이지 캐시·익명 페이지·shmem·dirty 상태는 12장의 회수에서 "무엇을 얼마나 싸게 내보낼 수 있나"를 결정합니다. 같은 내용의 익명 페이지를 합쳐 메모리를 아끼는 KSM(Kernel Samepage Merging)은 COW를 역으로 쓰는 기법으로, 가상화 맥락에서 15장에서 다룹니다.

핵심 요약

  • fork는 데이터가 아니라 PTE를 복사하고 양쪽을 읽기 전용으로 만든다. VMA는 쓰기 가능한데 PTE만 읽기 전용이라는 불일치가 COW 폴트의 표식이다.
  • COW 폴트에서 공유자가 남아 있으면 새 프레임에 복사하고, 마지막 사용자면 복사 없이 쓰기 권한만 되돌린다(재사용).
  • COW가 있어도 fork는 페이지 테이블 복사 비용과 overcommit 계산을 안고 간다. 대형 프로세스의 자식 생성은 posix_spawn(CLONE_VM | CLONE_VFORK 경로)이 유리하다.
  • mmap: file+private = 읽기는 캐시 공유, 쓰기는 COW 사본 / file+shared = 페이지 캐시에 직접 쓰고 writeback / anon+private = 0으로 채운 사유 메모리 / anon+shared = shmem 기반 공유.
  • 페이지 캐시는 inode별 address_space의 XArray(i_pages)로 관리되고, read()는 거기서 복사해 가며 mmap은 그 페이지를 직접 매핑한다.
  • dirty 데이터는 dirty_background_ratio(기본 10)에서 백그라운드 writeback, dirty_ratio(기본 20) 근처에서 쓰는 프로세스를 스로틀링한다. 30초가 지난 dirty는 임계와 무관하게 기록 대상이다.
  • 내구성은 fsync/fdatasync(파일) + 디렉토리 fsync로만 보장된다. fsync 실패는 재시도로 해결되지 않는다. O_DIRECT는 캐시를 우회할 뿐 내구성을 보장하지 않는다.
  • tmpfs·POSIX/SysV shm·memfd·공유 익명 매핑은 모두 shmem 기반이며 swap 없이는 회수되지 않는다(Shmem은 Cached에 포함됨).
  • rmap은 "페이지 → 매핑한 PTE들"을 찾는 역방향 경로로, 회수·이동·KSM에 필수다.

확인 문제

fork 직후 부모가 페이지 P에 쓰기를 해서 COW 복사가 일어났다. 이어서 자식이 같은 페이지 P에 쓰면 어떻게 되나?
자식 PTE는 fork 때 읽기 전용이 되었으므로 쓰기 폴트는 납니다. 하지만 부모가 사본으로 떠난 뒤 원래 프레임의 사용자는 자식 하나뿐이라 do_wp_page()는 복사 없이 재사용합니다. 복사는 "공유자가 남아 있을 때만" 일어납니다.
커널이 쓰기 보호 폴트를 COW로 처리할지, SIGSEGV를 보낼지 결정하는 근거는?
VMA는 "원래 허용된 권한", PTE는 "현재 하드웨어에 걸린 권한"입니다. VMA가 쓰기를 허용하는 private 매핑인데 PTE만 막혀 있다면 COW로 의도된 상태이고, VMA부터 쓰기를 허용하지 않으면 진짜 위반입니다.
다음 중 MAP_SHARED|MAP_ANONYMOUS 매핑에 대한 설명으로 옳은 것은?
공유 익명 매핑은 커널 내부의 shmem 객체가 뒷받침합니다. fork 후에도 같은 페이지를 공유하므로 쓰기가 서로 보입니다. 백킹 파일이 디스크에 없어서 회수하려면 swap으로 내보내야 하고, 집계는 Shmem(Cached에 포함)으로 잡힙니다.
dirty_background_ratio=10, dirty_ratio=20인 시스템에서 앱이 디스크 대역폭보다 훨씬 빠르게 버퍼드 write를 계속한다. 가장 정확한 설명은?
백그라운드 임계는 flusher를 깨우기만 하고 앱을 막지 않습니다. dirty가 더 늘면(대략 두 임계의 중간 이후) 쓰는 프로세스가 짧게 잠드는 방식으로 스로틀링됩니다. 비율의 기준은 전체 RAM이 아니라 dirty가 될 수 있는 메모리입니다.
O_DIRECT에 대한 설명으로 틀린 것은?
O_DIRECT는 페이지 캐시만 우회합니다. 장치 내부의 휘발성 쓰기 캐시, 파일시스템 메타데이터(블록 할당, 파일 크기)는 여전히 영속화가 필요하므로 fsync/fdatasync나 O_DSYNC를 함께 써야 합니다.
메모리 120 GiB를 쓰는 Redis가 BGSAVE를 할 때마다 수백 ms 동안 응답이 멈춘다. 가장 직접적인 원인은?
COW 덕분에 데이터 복사는 fork 시점에 일어나지 않지만, 페이지 테이블(4 KiB 페이지 기준 수천만 개 PTE)의 복사·쓰기 보호는 fork 안에서 동기적으로 일어납니다. 그 뒤로는 부모의 쓰기마다 COW 폴트가 추가 비용으로 따라옵니다.
