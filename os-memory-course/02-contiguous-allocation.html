주소 바인딩과 연속 메모리 할당

페이징이 나오기 전, 운영체제는 프로세스 하나를 물리 메모리의 연속된 한 덩어리에 넣었다. 이 단순한 방식이 어떤 문제에 부딪혔는지(재배치, 보호, 단편화) 이해하면, 페이징이 왜 그런 모양인지 저절로 납득된다. 그리고 그 문제들은 사라지지 않았다. 커널의 연속 물리 메모리 할당, malloc 힙, GPU 메모리, JVM 힙에서 지금도 같은 모습으로 나타난다.

학습 목표

  • 컴파일·로드·실행 시점 바인딩을 구분하고, ELF 재배치와 PIE가 그중 어디에 해당하는지 설명한다.
  • base/limit(재배치) 레지스터로 보호와 동적 재배치를 동시에 얻는 하드웨어를 설명한다.
  • first/best/worst/next fit을 직접 돌려 보고, 외부 단편화와 50% 규칙을 수치로 확인한다.
  • 내부/외부 단편화와 압축의 비용을 설명하고, 현대 시스템(Linux compaction, GC)에서 같은 문제가 어떻게 나타나는지 연결한다.
  • 세그멘테이션의 변환 과정을 설명하고, x86 세그멘테이션의 역사와 지금도 남아 있는 FS/GS의 쓰임을 안다.

1. 주소 바인딩: 주소는 언제 정해지나

소스 코드의 변수 count는 이름(심볼)일 뿐이다. 이 이름이 최종적으로 DRAM의 어느 바이트를 가리키게 되는지, 곧 주소 바인딩(address binding)은 여러 단계를 거쳐 정해진다. 핵심 질문은 "실제 물리 위치가 언제 고정되는가"다.

시점방식예대가
컴파일(링크) 시점프로그램이 놓일 물리 위치를 미리 알고 절대 주소 코드를 만든다.MMU 없는 마이크로컨트롤러 펌웨어(링커 스크립트로 주소 고정), MS-DOS .COM(세그먼트 안 오프셋 0x100에 적재된다고 가정)시작 위치가 바뀌면 다시 빌드해야 한다.
로드 시점컴파일러는 재배치 가능한(relocatable) 코드를 만든다. 로더가 적재 위치를 정하고 주소를 고쳐 쓴다.Windows DLL rebasing(선호 주소가 차 있으면 .reloc 정보로 패치), PIE의 R_X86_64_RELATIVE 재배치적재 후에는 옮길 수 없다. 패치할 페이지가 많으면 시작이 느리고 공유도 깨진다.
실행 시점CPU가 내는 주소를 매 접근마다 하드웨어(MMU)가 변환한다.base 레지스터, 세그멘테이션, 페이징(현대의 모든 범용 OS)변환 하드웨어가 필요하다. 대신 실행 중에도 옮길 수 있다(압축, 스왑, 페이지 이동).

아래 애니메이션은 C 코드 int count; void inc(void) { count++; }의 count가 x86-64 Linux에서 PIE로 빌드될 때 단계마다 어떻게 표현되는지 따라간다.

관찰: PIE의 코드는 로드할 때 고칠 것이 없다
      count(%rip)처럼 PC 상대 주소를 쓰면 코드와 데이터 사이 거리(0x2EDD)는 링크 시점에 고정된다. 실행 파일 전체가 어디에 놓이든 이 거리는 변하지 않으므로, 로더는 코드 페이지를 건드릴 필요가 없다. 그래서 코드 페이지를 여러 프로세스가 그대로 공유할 수 있다. 반면 데이터 안의 절대 포인터(함수 포인터 테이블 등)는 로드 주소에 따라 값이 달라지므로 ld.so가 R_X86_64_RELATIVE 재배치로 고친다. 이 페이지들은 COW로 프로세스마다 사본이 생긴다. 결국 현대 PIE는 로드 시점 바인딩(일부 데이터)과 실행 시점 바인딩(MMU)을 함께 쓴다.

  


  
  

    
2. 링킹, 로딩, 재배치

    
여러 .o 파일과 라이브러리를 하나의 실행 가능한 이미지로 묶는 과정은 두 가지 일로 나뉜다.

    
    
      
  1. 심볼 해석(symbol resolution): printf나 count 같은 이름이 어느 파일의 어느 정의를 가리키는지 결정한다. 정의가 없으면 "undefined reference", 둘이면 "multiple definition" 링크 에러가 난다.
    2. 
      
  2. 재배치(relocation): 섹션들을 합쳐 최종 배치를 정한 뒤, 컴파일러가 0으로 비워 둔 자리를 실제 값으로 채운다. 어느 자리를 어떤 공식으로 채울지는 .rela.text 같은 재배치 섹션에 적혀 있다(readelf -r inc.o로 확인).
    3. 
    

    

      
x86-64 재배치 타입채우는 값용도

      
R_X86_64_64S + A (64비트 절대 주소)데이터 안의 포인터

      
R_X86_64_PC32S + A − P (32비트 PC 상대)RIP 상대 데이터 접근

      
R_X86_64_PLT32L + A − P함수 호출(call). 외부 함수면 PLT 엔트리 L로 간다

      
R_X86_64_GOTPCREL(X)GOT 엔트리까지의 PC 상대 거리다른 모듈에 정의될 수 있는 전역 변수 접근

      
R_X86_64_RELATIVEB + A (로드 베이스 + 오프셋)동적 재배치. ld.so가 로드 시 적용

      
R_X86_64_JUMP_SLOT / GLOB_DAT심볼의 최종 주소동적 재배치. PLT용 GOT 슬롯 / 데이터용 GOT 슬롯

    

    
S=심볼 주소, A=addend, P=재배치 대상 위치, L=PLT 엔트리 주소, B=공유 객체 로드 베이스.


    
정적 링킹 vs 동적 링킹

    
정적 링킹은 라이브러리 코드를 실행 파일에 복사해 넣는다. 배포가 단순하고 시작이 빠르지만, 실행 파일마다 libc 사본을 갖게 되어 디스크와 메모리를 낭비한다. 보안 패치도 모든 바이너리를 다시 빌드해야 적용된다. 동적 링킹은 실행 시 ld-linux-x86-64.so.2가 공유 라이브러리를 mmap하고 심볼을 연결한다. 공유 라이브러리의 코드 페이지는 물리 메모리에 한 벌만 올라와 모든 프로세스가 공유한다(01·03장).

    
공유가 가능하려면 라이브러리 코드가 어느 주소에 매핑되든 코드 자체를 고치지 않아야 한다. 이것이 PIC(Position-Independent Code)다. 다른 모듈의 심볼은 GOT(Global Offset Table)라는 데이터 테이블을 거쳐 간접 접근하고, 외부 함수 호출은 PLT(Procedure Linkage Table) 스텁을 거친다. 고쳐야 할 것은 데이터 페이지인 GOT뿐이다.

    
심화: lazy binding, RELRO, 그리고 시작 시간

      
전통적으로 PLT는 lazy binding을 한다. 처음 호출할 때 ld.so의 resolver로 들어가 심볼을 찾고 GOT 슬롯을 갱신한다. 이후 호출은 바로 간다. 시작은 빠르지만 GOT가 실행 내내 쓰기 가능해야 한다는 약점이 있다. 그래서 공격자가 GOT를 덮어쓰면 제어 흐름을 빼앗을 수 있다.

      
최근 배포판은 -z now(BIND_NOW)와 -z relro를 함께 쓰는 Full RELRO를 기본으로 하는 경우가 많다. 시작할 때 모든 심볼을 해석하고, GOT를 mprotect로 읽기 전용으로 바꾼다. 01장 maps에서 본 r--p 줄이 이것이다. 대가는 시작 시간이다. 수천 개 심볼을 가진 거대 C++ 애플리케이션은 동적 재배치·심볼 해석만으로 수백 ms를 쓰기도 한다. LD_DEBUG=statistics ./app으로 재배치에 쓴 시간을 볼 수 있다. prelink, 심볼 가시성 제한(-fvisibility=hidden), DT_RELR(압축된 RELATIVE 재배치) 같은 최적화가 나온 배경이다.

    

    
현업에서: 재배치가 만드는 메모리 비용
      로드 시점에 고쳐 쓴 페이지는 COW로 프로세스 전용 사본(private dirty)이 된다. 비PIC 코드로 만든 공유 라이브러리(TEXTREL)는 코드 페이지까지 고쳐야 해서 공유 이점이 사라지고 보안상 W^X도 깨진다. 최신 툴체인이 TEXTREL에 경고를 내는 이유다. 자바·파이썬처럼 프로세스를 여러 개 띄우는 서비스에서 "프로세스당 private dirty가 왜 이렇게 크지?"라는 질문의 답이 재배치된 데이터 페이지인 경우가 많다.

  


  
  

    
3. base/limit 레지스터와 보호

    
여러 프로세스를 동시에 메모리에 올리려면(멀티프로그래밍) 두 가지가 필요하다. 한 프로세스가 남의 영역을 건드리지 못하게 하는 보호, 그리고 프로세스를 아무 위치에나 놓을 수 있게 하는 재배치다. 가장 단순한 하드웨어는 레지스터 두 개로 둘 다 해결한다.

    
    
      
  • 재배치(relocation/base) 레지스터: 프로세스가 놓인 물리 시작 주소.
    • 
      
  • 한계(limit) 레지스터: 프로세스 영역의 크기.
    • 
    

    
CPU가 낸 논리 주소 a에 대해 하드웨어는 매 접근마다 a < limit인지 확인한다. 위반이면 트랩(주소 오류 예외)을 일으켜 OS로 넘어간다. 통과하면 물리 주소 = base + a다. 프로그램은 자기가 0번지부터 시작한다고 믿고, 실제 위치는 base만 바꾸면 옮겨진다. 두 레지스터는 특권 명령으로만 바꿀 수 있고, OS는 문맥 교환 때 다음 프로세스의 값을 로드한다.

    
교과서에 따라 다른 변형도 나온다. CPU가 이미 물리 주소를 만들고(로드 시점 바인딩) 하드웨어는 base ≤ addr < base + limit인지만 검사하는 방식이다. 보호는 되지만 재배치는 하드웨어가 해 주지 않는다. 아래 위젯에서 두 방식을 비교해 보라.

4. 동적 재배치와 스와핑

    
실행 시점 바인딩이 있으면 OS는 프로세스를 실행 도중에 다른 위치로 옮길 수 있다. 내용을 복사하고 base만 바꾸면 끝이다. 같은 원리로 프로세스를 통째로 디스크(백킹 스토어)에 내보냈다가 나중에 다른 위치로 다시 들여올 수도 있다. 이것이 고전적 스와핑(swapping)이다. 실행 중인 프로세스 메모리의 합이 물리 메모리보다 커도 되므로 멀티프로그래밍 정도를 높일 수 있다.

    
문제는 비용이다. 100 MB 프로세스를 50 MB/s HDD로 내보내고 다른 프로세스를 들여오면 왕복 4초가 걸린다. 2 GB/s NVMe라도 0.1초다. 스케줄러의 타임 슬라이스는 수 ms이므로, 프로세스를 통째로 옮기는 스와핑은 문맥 교환 수단으로 쓸 수 없다. 그래서 현대 OS는 페이지 단위로 필요한 부분만 내보내고 들여온다(06·07장). Linux에서 "swap"이라는 말은 이 페이지 단위 스왑을 뜻한다.

    
옮길 수 없는 메모리: I/O와 pinning
      장치가 DMA로 어떤 프로세스의 버퍼에 쓰는 중이라면 그 메모리는 옮기거나 내보낼 수 없다. 장치는 물리 주소로 쓰기 때문에, 옮기면 다른 프로세스의 메모리를 덮어쓴다. 고전적 해법은 두 가지다. ① 그 프로세스는 스왑하지 않거나, ② 장치는 항상 커널 버퍼에만 쓰게 하고 커널이 복사한다(이중 버퍼링). 이 문제는 지금도 그대로다. RDMA의 메모리 등록, GPU용 pinned host memory, Linux의 pin_user_pages(), mlock()은 모두 "이 물리 페이지는 움직이지 마라"는 약속이다. 고정된 페이지가 많아지면 압축(7절)과 회수(12장)가 막혀 시스템 전체에 문제가 생긴다.

    
모바일 OS는 전통적으로 디스크 스왑을 쓰지 않았다. 플래시 수명과 지연 때문이다. 대신 메모리가 부족하면 백그라운드 앱을 종료하고(Android의 lmkd, iOS의 jetsam), 메모리를 압축해 RAM 안에 보관한다(Android zram, iOS·macOS 메모리 압축). "프로세스 전체를 내보낸다"는 고전 스와핑의 발상은, 앱 하나를 통째로 정리하는 형태로 살아 있는 셈이다.

  


  
  

    
5. 가변 분할 할당과 배치 전략

    
초기 멀티프로그래밍 시스템(IBM OS/360의 MFT)은 메모리를 고정 크기 분할로 미리 나눴다. 분할 하나에 프로세스 하나를 넣으니 단순하지만, 동시에 실행할 수 있는 프로세스 수가 분할 수로 묶이고 분할보다 작은 프로세스는 남는 공간을 낭비한다. 후속 MVT는 가변 분할을 썼다. 요청 크기만큼 잘라 주고, 비어 있는 구간(hole)들을 목록으로 관리한다. 새 요청이 오면 어느 hole을 고를지가 배치 전략이다.

    

      
전략규칙특징

      
First fit낮은 주소부터 훑어 처음 맞는 hole빠르다. 앞쪽에 작은 조각이 쌓인다.

      
Next fit지난번 할당이 끝난 위치부터 훑는다(순환)앞쪽 조각을 반복해서 훑지 않는다. 대신 큰 hole을 고르게 깎아 먹어 오히려 나빠지기도 한다.

      
Best fit맞는 것 중 가장 작은 hole큰 hole을 보존한다. 대신 쓸모없는 아주 작은 찌꺼기를 많이 남긴다. 전체를 훑어야 한다(크기순 정렬 구조가 없으면).

      
Worst fit가장 큰 hole남는 조각을 크게 남기려는 발상이다. 실제로는 큰 hole이 빨리 사라져 대체로 가장 나쁘다.

6. 내부 단편화 vs 외부 단편화

    
    

      
내부 단편화외부 단편화

      
원인요청보다 큰 고정 단위로 반올림가변 크기 블록의 할당·해제가 반복되며 생긴 흩어진 hole

      
어디서페이징(마지막 페이지), slab 크기 클래스, buddy(2의 거듭제곱 반올림), 구조체 패딩연속 할당, 세그멘테이션, malloc 힙, 물리 연속 메모리(huge page, DMA)

      
낭비량예측 가능. 평균 단위 크기의 절반 정도(요청당)워크로드에 따라 크게 달라지며 예측이 어렵다

      
해결책단위를 작게(대신 관리 비용 증가)압축, 비연속 할당 허용(페이징), 크기 클래스

    

    
메모리 관리 설계의 상당 부분은 외부 단편화를 내부 단편화로 바꾸는 거래다. 페이징은 모든 할당을 4 KB 단위로 만들어 외부 단편화를 없애고, 대신 프로세스당 평균 반 페이지 정도의 내부 단편화를 받아들인다. 예측할 수 있고 상한이 있는 낭비가 예측할 수 없는 실패보다 낫기 때문이다.

  


  
  

    
7. 압축(compaction)

    
외부 단편화의 직접적인 해결책은 할당된 블록들을 한쪽으로 밀어 hole들을 하나로 모으는 압축이다. 단, 프로세스를 옮겨도 프로그램이 계속 동작하려면 실행 시점 바인딩이 필요하다. base 레지스터만 바꾸면 되니까. 로드 시점에 절대 주소를 박아 넣은 프로그램은 옮기는 순간 모든 포인터가 틀어진다.

현대의 압축: Linux memory compaction과 GC
      
페이징 시스템에서도 물리적으로 연속된 큰 블록(2 MB huge page 등)이 필요하면 외부 단편화 문제가 돌아온다. Linux는 이동 가능한(movable) 페이지를 옮겨 연속 공간을 만드는 memory compaction을 한다. 페이지 테이블 항목만 고치면 되니 프로세스는 눈치채지 못한다. 페이징이 곧 실행 시점 바인딩이기 때문이다. 백그라운드 스레드 kcompactd가 돌고, 할당 경로에서 직접 압축하면 /proc/vmstat의 compact_stall이 증가한다. 수동으로는 echo 1 > /proc/sys/vm/compact_memory로 실행한다. 반면 커널 객체(slab)처럼 옮길 수 없는 페이지가 곳곳에 박혀 있으면 압축이 실패한다. 그래서 Linux는 페이지를 이동 가능성별(migrate type)로 모아 두려 한다(09장).

      
언어 런타임의 compacting GC(JVM G1/ZGC의 evacuation, .NET GC의 compact 단계)도 같은 일을 한다. 살아 있는 객체를 옮기고 모든 참조를 고친다. 런타임이 모든 포인터의 위치를 아는 덕분에 가능하다. C/C++ 힙은 포인터가 어디 있는지 알 수 없어 압축할 수 없다.

  


  
  

    
8. 50% 규칙

    
Knuth는 first fit을 분석해 다음 경험 법칙을 제시했다. 할당과 해제가 반복되어 평형에 이른 시스템에서 할당된 블록이 N개라면 hole은 평균 약 0.5N개다. 이것이 50% 규칙이다.

    
직관은 이렇다. 할당된 블록의 이웃은 대개 다른 블록이거나 hole이다. 블록이 해제되면 이웃 hole과 합쳐져 hole 수가 줄고, 할당이 hole을 정확히 채우는 일은 드물어서 hole 수가 거의 줄지 않는다. 이 흐름이 평형을 이룰 때 블록 둘에 hole 하나 꼴이 된다. hole의 평균 크기가 블록의 평균 크기와 비슷하다고 가정하면, 메모리의 1/3(=0.5N / 1.5N)이 hole로 존재한다. 교과서가 "메모리의 1/3이 쓸모없어질 수 있다"고 하는 근거다.


    

      
50% 규칙 실험

      
100,000 KB 메모리에 100~2000 KB 무작위 요청을 20,000번 보낸다. 할당이 실패할 때마다 살아 있는 블록 하나를 무작위로 해제해 "메모리가 늘 가득 찬" 평형 상태를 만든다. 후반 절반 동안의 평균을 잰다.

      

        
        
        
      

      

    

    
실험해 보면 hole/블록 비율은 전략과 관계없이 0.5 근처로 놀랍도록 안정적이다. 그러나 빈 공간 비율은 1/3보다 훨씬 작고 전략마다 다르다. hole의 평균 크기가 블록보다 작기 때문이다. 큰 hole은 다음 요청에 금방 쪼개져 소비된다. 즉 50% 규칙의 "개수" 부분은 견고하지만 "1/3 낭비"는 크기 분포에 대한 가정이 붙은 상한에 가깝다. 수치를 인용할 때는 이 차이를 구분해야 한다. worst fit의 빈 공간 비율이 가장 높게 나오는 것도 확인해 보라.

  


  
  

    
9. 세그멘테이션과 x86의 유산

    
base/limit 쌍을 프로세스당 하나가 아니라 논리적 단위마다 하나씩 두면 어떨까. 프로그래머가 보는 프로그램은 원래 코드, 전역 데이터, 힙, 스택처럼 크기와 성격이 다른 덩어리의 모음이다. 세그멘테이션은 주소를 <세그먼트 번호, 오프셋>으로 표현하고, 세그먼트마다 base, limit, 권한을 세그먼트 테이블에 둔다.

    
    
장점은 분명하다. 세그먼트마다 권한을 달리할 수 있다(코드 R-X, 데이터 RW-). 공유도 세그먼트 단위로 자연스럽다. 그러나 각 세그먼트는 여전히 가변 크기의 연속 블록이므로 외부 단편화가 그대로 남는다. 이 한계 때문에 현대 범용 OS는 보호와 공유를 페이징으로 해결하고 세그멘테이션은 사실상 꺼 두었다.


    

      
세그먼트 테이블 변환기

      
테이블 값은 편집할 수 있다(16진수). 주소를 넣는 방법은 두 가지다. 세그먼트 번호와 오프셋을 따로 넣거나, 16비트 가상 주소 하나를 넣는다(상위 2비트 = 세그먼트, 하위 14비트 = 오프셋). 접근 종류도 고를 수 있다.

    8086 실모드: 물리 주소 = 세그먼트 × 16 + 오프셋
    
      
    
        
        
        
        
        
      
    
      
    
    
    

    
    x86 세그멘테이션의 역사
    
    
    
      
    CPU세그멘테이션의미
    
      
    8086 (1978)실모드. 물리 = 세그먼트×16 + 오프셋 (20비트, 1 MB). CS/DS/SS/ES16비트 레지스터로 1 MB를 주소하려는 장치. 보호 없음. 세그먼트끼리 겹치며, 같은 물리 주소를 여러 seg:off로 표현할 수 있다.
    
      
    80286 (1982)보호 모드. 세그먼트 레지스터에는 셀렉터가 들어가고, 셀렉터로 GDT/LDT의 디스크립터(base, limit, 권한)를 찾는다교과서적 세그멘테이션. 세그먼트 최대 64 KB, 특권 링 도입.
    
      
    80386 (1985)32비트 세그먼트 + 페이징. FS/GS 추가. 논리 →(세그먼트)→ 선형 →(페이징)→ 물리OS들은 모든 세그먼트를 base 0, limit 4 GB로 설정한 flat 모델을 택했다. 세그멘테이션을 사실상 끄고 페이징만 쓴 것이다.
    
      
    x86-64 (2003~)long mode에서 CS/DS/ES/SS의 base는 0으로 취급하고 limit 검사도 하지 않는다. FS와 GS의 base만 살아 있다하드웨어 차원에서 flat 모델이 공식화되었다. FS/GS base는 MSR(IA32_FS_BASE, IA32_GS_BASE)로 설정한다.
    
    
    
    
    살아남은 FS/GS는 세그멘테이션의 본래 목적이 아니라 "레지스터 하나로 가리키는 스레드별·CPU별 데이터" 용도로 쓰인다.
    
    
      
      
    • Linux x86-64 유저 공간 TLS: glibc는 스레드마다 FS base를 그 스레드의 TCB(struct pthread)로 설정한다. __thread 변수는 %fs:오프셋으로 접근한다. 스택 보호(-fstack-protector)의 카나리 값은 %fs:0x28에 있다. 그래서 거의 모든 함수 프롤로그에 mov %fs:0x28,%rax가 보인다.
      • 
      
    • Linux 커널의 per-CPU 데이터: 커널은 GS base로 현재 CPU의 per-CPU 영역을 가리킨다. 유저↔커널 전환 시 swapgs 명령으로 유저 GS base와 커널 GS base(IA32_KERNEL_GS_BASE)를 맞바꾼다. 이 명령의 투기적 실행 문제가 2019년 SWAPGS 취약점이었다.
      • 
      
    • Windows x64: 유저 모드에서 GS가 TEB(Thread Environment Block)를, 커널 모드에서 KPCR을 가리킨다.
      • 
      
    • 설정 방법: 전통적으로 arch_prctl(ARCH_SET_FS, addr) 시스템 콜을 쓴다. Linux 5.9부터는 CPU가 지원하면 유저 공간에서 wrfsbase/rdfsbase(FSGSBASE 명령)를 직접 쓸 수 있다. 문맥 교환 때 커널이 스레드별 FS/GS base를 저장·복원한다.
      • 
      
    • ARM64는 세그먼트 레지스터 없이 전용 시스템 레지스터를 쓴다. 유저 TLS는 TPIDR_EL0, 커널 per-CPU 오프셋은 TPIDR_EL1(또는 EL2)다. 용도가 같으니 설계도 결국 같아진 셈이다.
      • 
    
    
    
    왜 세그멘테이션은 졌나
      ① 가변 크기라 외부 단편화가 생긴다. ② 포인터가 (세그먼트, 오프셋) 쌍이 되어 C 같은 언어의 단일 포인터 모델과 맞지 않는다(16비트 시절의 near/far 포인터 지옥). ③ 이식성: 다른 아키텍처(MIPS, ARM, PowerPC)는 페이징만 제공했다. 그래서 이식 가능한 OS는 페이징만 가정하고 설계했다. 보호 단위를 논리적 의미에 맞추겠다는 세그멘테이션의 아이디어는 VMA(영역별 권한)로 살아남았다. 다만 이제는 페이지 묶음으로 구현된다.
    
  
    

  
    핵심 요약
      
    
    • 주소 바인딩은 컴파일·로드·실행 시점에 일어날 수 있다. 실행 시점 바인딩(MMU)이 있어야 실행 중 이동(압축·스왑)이 가능하다. PIE는 PC 상대 주소로 코드 수정을 피하고 데이터 포인터만 로드 시 재배치한다.
      • 
    
    • 링커는 심볼 해석과 재배치를 하고, 동적 링커는 GOT/PLT를 채운다. Full RELRO는 그 뒤 GOT를 읽기 전용으로 만든다.
      • 
    
    • base/limit(재배치) 레지스터는 비교기와 덧셈기만으로 보호와 동적 재배치를 동시에 제공한다. 대신 프로세스 전체가 연속이어야 한다.
      • 
    
    • 가변 분할은 외부 단편화를 낳는다. first/best fit이 비슷하고 worst fit이 대체로 나쁘다. 하지만 모든 경우에 이기는 전략은 없다.
      • 
    
    • 50% 규칙: 평형 상태의 hole 수는 블록 수의 약 절반이다. "1/3 낭비"는 hole과 블록의 평균 크기가 같다는 가정이 붙은 수치다.
      • 
    
    • 압축은 실행 시점 바인딩이 있어야 가능하고 비싸다. Linux memory compaction과 compacting GC가 현대판이다. 고정된(pinned) 페이지가 이를 방해한다.
      • 
    
    • 세그멘테이션은 논리 단위별 base/limit/권한을 주지만 외부 단편화가 남는다. x86-64는 flat 모델로 사실상 비활성화했고, FS/GS base만 TLS와 per-CPU 데이터용으로 남았다.
      • 
  
    

  
    확인 문제
    
  
    
    
    재배치 레지스터 방식에서 relocation = 0x14000, limit = 0x4000이다. 논리 주소 0x4000에 접근하면?
    
    
    
    
    
    
    유효한 논리 주소는 0 ~ limit−1(0x3FFF)이다. 0x3FFF는 물리 0x17FFF로 변환되지만 0x4000은 경계를 벗어나 트랩이다. off-by-one을 조심하라. limit는 "크기"이므로 비교는 <다.
    
  
    
  
    
    
    hole이 1300 KB와 1200 KB 두 개 있다. 1000, 1100, 250 KB를 차례로 요청할 때 마지막 요청이 실패하는 전략은?
    
    
    
    
    
    
    Best fit은 1000→1200(200 남음), 1100→1300(200 남음)을 고르고, 250은 200짜리 두 개 중 어디에도 들어가지 못한다. First fit(그리고 이 경우의 worst fit)은 1000→1300(300 남음), 1100→1200(100 남음)으로 300 hole에 250을 넣는다. Knuth의 예로, best fit이 항상 최선은 아님을 보여 준다.
    
  
    
  
    
    
    로드 시점 바인딩만 지원하는 시스템에서 압축을 할 수 없는 이유는?
    
    
    
    
    
    
    압축은 실행 중인 프로세스의 위치를 바꾼다. 실행 시점 바인딩이면 base 레지스터(혹은 페이지 테이블)만 고치면 된다. 로드 시점 바인딩이면 메모리 안의 모든 주소 값을 찾아 고쳐야 하는데, 레지스터나 스택에 있는 포인터까지 찾아내는 것은 사실상 불가능하다.
    
  
    
  
    
    
    first fit을 쓰는 평형 상태 시스템에서 할당된 블록이 1000개라면, 50% 규칙에 따른 hole 개수와 "1/3 규칙"의 전제는?
    
    
    
    
    
    
    hole ≈ 0.5N이다. 크기가 같다고 보면 전체 1.5N 단위 중 0.5N이 hole이므로 1/3이다. 위 실험처럼 실제 hole은 대개 더 작아서 낭비 비율은 이보다 낮게 나오는 경우가 많다.
    
  
    
  
    
    
    x86-64 Linux에서 컴파일한 거의 모든 함수 앞에 mov %fs:0x28, %rax가 보이는 이유는?
    
    
    
    
    
    
    long mode에서 FS는 base만 의미가 있고, glibc는 이를 스레드의 TCB로 설정한다. 오프셋 0x28에는 스택 카나리가 있고, 함수 에필로그에서 이 값과 비교해 스택 버퍼 오버플로를 탐지한다. 커널 per-CPU 데이터는 GS를 쓴다.
    
  
    
  
    
    
    8086 실모드에서 1234:0010이 가리키는 물리 주소는?
    
    
    
    
    
    
    0x1234 × 16 = 0x12340, 여기에 0x10을 더하면 0x12350이다. 1235:0000도 같은 물리 주소다. 세그먼트가 16바이트 간격으로 겹치기 때문이다.
    
  
    
  
    
    
    4 KB 페이지를 쓰는 시스템에서 프로세스가 정확히 10,000바이트의 메모리를 필요로 한다. 단편화에 대한 설명으로 맞는 것은?
    
    
    
    
    
    
    ⌈10000/4096⌉ = 3페이지 = 12,288바이트이고, 12,288 − 10,000 = 2,288바이트가 마지막 페이지 안에서 버려진다. 고정 단위 안쪽의 낭비이므로 내부 단편화다. 페이징은 외부 단편화를 없애는 대신 이것을 받아들인다.
