메모리 장애를 증거로 좁히는 캡스톤

선수 장 · 실전 진단 도구와 종합 문제

16장의 도구 목록을 하나의 조사 절차로 묶습니다. free가 적고 응답이 느리다는 보고에서 출발해 사용량·회수 대기·소유 범위를 각각 확인합니다.

같은 시간과 같은 범위의 증거 묶음

서비스 PID, cgroup 경로, 요청률, 데이터 크기를 먼저 기록합니다. free -m, vmstat 1 3, /proc/pressure/memory와 해당 프로세스의 smaps_rollup을 같은 관측 구간에 모읍니다. 시스템 전체 PSI와 서비스 한정 cgroup 수치를 혼합하지 말고 누적 카운터는 두 시점 차이로 계산합니다.

RSS 증가만으로 누수를 확정할 수 없습니다. 살아 있는 애플리케이션 객체가 늘었는지, 할당자 arena가 빈 공간을 보유하는지, 파일 매핑이나 공유 페이지가 늘었는지 분해합니다. cgroup에서는 memory.current의 anon·file·shmem·kernel 구성과 memory.events를 함께 읽어 호스트 여유가 있는데 서비스만 한도에 부딪힌 경우를 구분합니다.

가설마다 실패할 수 있는 예측을 적기

누수 가설은 동일한 완료 작업량을 반복했을 때 살아 있는 객체나 회수되지 않는 소유 상태가 계속 증가할 것이라고 예측합니다. 단편화 가설은 live 객체가 줄어도 예약된 arena/RSS가 남는 차이를 예측합니다. 캐시 가설은 파일 작업과 file 비중이 함께 움직이고 압박이 없을 수 있다고 예측합니다. 각 예측의 근거가 없는 상태에서는 가능성으로 남깁니다.

개선 시험은 별도 개발 환경에서 작업량 또는 동시성 한 가지만 줄여 비교합니다. p99가 내려갔어도 완료 처리량이 절반으로 줄면 동일 조건 개선이 아닙니다. drop_caches, 운영 메모리 한도 변경, OOM 유발은 기본 진단 절차에 포함하지 않습니다. 원시 지표와 가설, 수행한 시험, 아직 하지 않은 검증을 분리해 보고서를 마칩니다.

실습과 예상 관찰

자신이 실행한 서비스나 개발 프로세스만 관찰합니다. 3초 간격으로 memory.current·memory.stat·memory.events를 두 번 읽고, 호스트 PSI와 같은 시각으로 표를 만드세요. 접근할 수 없는 파일은 0으로 채우지 말고 미관측으로 표시합니다. 아래 두 데이터 묶음은 교육용 예상 사례입니다.

MemAvailable 충분·PSI 낮음·file 비중 높음

예상 우선순위: 캐시 사용 자체를 장애로 보지 말고 실제 요청 지연의 다른 경로를 찾습니다. 실측 프로세스가 이 사례와 같은지 수집한 지표로 확인합니다.

호스트 여유·서비스 memory.events 증가·anon 비중 큼

예상 우선순위: 해당 cgroup의 제한과 작업 집합을 조사합니다. 증가한 이벤트가 어떤 종류인지 확인하기 전에는 OOM kill이 실제 발생했다고 단정하지 않습니다.

실습의 경계와 다음 장

이 캡스톤은 원인을 자동 판정하지 않으며 제공 사례는 운영 로그가 아닙니다. 모은 증거를 가지고 12장 회수·cgroup 계약으로 돌아가 가능한 경로와 관측된 경로를 대조하세요.
