실전 · Chapter 16

실전 진단 도구와 종합 문제

"메모리가 부족해요"라는 신고는 대부분 정확하지 않다. 무엇이, 어디에, 왜 쓰이고 있는지를 숫자로 확인하는 순서와 도구를 익히고, 실제 장애 사례로 추론 과정을 연습한다. 마지막으로 코스 전체를 종합 문제 20개로 점검한다.

학습 목표

  • 시스템 → cgroup → 프로세스 → 매핑 → 할당 지점 순으로 범위를 좁히는 진단 순서를 따를 수 있다.
  • free, vmstat, /proc/meminfo, smaps_rollup, pmap, top 컬럼의 정확한 의미를 알고 RSS/PSS/USS를 계산할 수 있다.
  • perf, bpftrace/BCC, massif, heaptrack, numastat, slabtop, PSI를 상황에 맞게 고를 수 있다.
  • OOMKilled, 힙 외 메모리 증가, THP 지연, 페이지 캐시 오해, 슬랩 폭증을 데이터로 구별할 수 있다.
목차
  1. 진단의 원칙: 범위를 좁히는 순서
  2. 시스템 전체: free, vmstat, /proc/meminfo, PSI
  3. 프로세스: top/htop, status, smaps, pmap
  4. 커널·NUMA: slabtop, numastat
  5. 이벤트와 할당 추적: perf, bpftrace/BCC, massif, heaptrack
  6. 증상 → 원인 진단 트리
  7. 케이스 스터디
  8. 더 공부할 자료
  9. 코스 종합 문제 20

1. 진단의 원칙: 범위를 좁히는 순서

메모리 문제를 잘 푸는 사람은 도구를 많이 아는 사람이 아니라 어떤 순서로 범위를 좁히는지 아는 사람이다. 한 번에 하나의 질문에만 답하는 도구를 순서대로 쓴다.

  1. 정말 부족한가? — MemAvailable, PSI(/proc/pressure/memory), major fault, 스왑 I/O. 숫자 하나("used 98%")로 판단하지 않는다.
  2. 어느 범위인가? — 시스템 전체인가, 특정 cgroup(컨테이너)인가. cgroup이면 memory.current, memory.stat, memory.events.
  3. 무엇의 메모리인가? — 유저 익명(anon), 파일 캐시(file), 공유 메모리(shmem/tmpfs), 커널(slab, page table, kernel stack), hugetlb 예약.
  4. 누구의 것인가? — 프로세스별 PSS, 그 안에서 매핑별(smaps, pmap).
  5. 어디서 할당했나? — 할당 스택(heaptrack, memleak, massif, 런타임 프로파일러).

PSI: 압박을 직접 재는 지표

$ cat /proc/pressure/memory
some avg10=3.21 avg60=1.05 avg300=0.40 total=58273611
full avg10=0.87 avg60=0.22 avg300=0.08 total=14202155

PSI(Pressure Stall Information, 4.20+)는 "메모리 때문에 태스크가 멈춰 있던 시간 비율"이다. some은 하나 이상의 태스크가 메모리(회수, 스왑인, 스래싱 리폴트)를 기다린 시간 비율, full은 모든 non-idle 태스크가 동시에 막힌 시간 비율이다. avg10/60/300은 각각 10초/60초/300초 이동평균(%), total은 누적 µs. cgroup v2에서는 memory.pressure로 컨테이너별로 볼 수 있고, systemd-oomd와 Android lmkd 같은 유저 공간 OOM 데몬이 이 값으로 판단한다. "메모리 사용률"보다 훨씬 좋은 경보 지표다.

/proc/PID/smaps와 smaps_rollup

smaps는 매핑(VMA)마다, smaps_rollup(4.14+)은 프로세스 전체 합계를 준다. 대형 프로세스에서 smaps 전체를 읽는 것은 커널이 모든 페이지 테이블을 걸어야 해서 비싸므로(수백 ms, mmap_lock 경합) 모니터링에는 rollup을 쓴다.

Pss_Shmem:         16000 kB

  • USS(Unique Set Size) = Private_Clean + Private_Dirty. 이 프로세스만 매핑한 페이지.
  • PSS(Proportional Set Size) = 전용 페이지 + Σ(공유 페이지 ÷ 그 페이지를 매핑한 프로세스 수). 모든 프로세스의 PSS 합 ≈ 실제 사용한 물리 메모리.
  • "Shared"는 지금 실제로 둘 이상이 매핑한 페이지다(top의 SHR과 다르다). smem 도구가 PSS/USS를 표로 보여 준다.

slabtop(/proc/slabinfo 기반)은 커널 객체 캐시별 사용량을 보여 준다. -o는 한 번만 출력, -s c는 캐시 크기순 정렬. SUnreclaim이 클 때는 어떤 캐시가 범인인지 여기서 찾는다. 리눅스는 같은 크기·속성의 캐시를 병합(slab merging)하므로 이름이 kmalloc-256처럼 뭉뚱그려 보이면 부팅 옵션 slab_nomerge로 분리해 추적한다.

5. 이벤트와 할당 추적: perf, bpftrace/BCC, massif, heaptrack

perf

$ perf stat -e page-faults,minor-faults,major-faults,dTLB-loads,dTLB-load-misses -p 1234 -- sleep 10
       1,203,551      page-faults
       1,203,402      minor-faults
             149      major-faults
  18,331,229,104      dTLB-loads
     402,113,880      dTLB-load-misses   #  2.19% of all dTLB cache accesses

$ perf record -e page-faults -g -p 1234 -- sleep 10    # 폴트를 일으킨 콜스택
$ perf report --stdio
  • minor fault: 디스크 I/O 없이 해결(첫 접근 0 페이지, CoW, 캐시에 있는 파일 페이지). 대량이면 메모리를 새로 만지는 패턴(대형 할당·해제 반복, THP 분할)을 의심.
  • major fault: 디스크(파일 또는 스왑)에서 읽음. 지연 원인의 1순위.
  • dTLB-load-misses 비율이 높으면 huge page 효과가 큰 워크로드다(13장). 이벤트 이름과 지원 여부는 CPU마다 다르므로 perf list로 확인한다.

bpftrace / BCC

# 프로세스별 페이지 폴트 수
$ bpftrace -e 'software:page-faults:1 { @[comm] = count(); }'

# direct reclaim에 걸린 시간 분포 (할당 경로에서 회수하느라 멈춘 시간)
$ bpftrace -e 'tracepoint:vmscan:mm_vmscan_direct_reclaim_begin { @s[tid] = nsecs; }
  tracepoint:vmscan:mm_vmscan_direct_reclaim_end /@s[tid]/ {
    @us[comm] = hist((nsecs - @s[tid]) / 1000); delete(@s[tid]); }'

# OOM 희생자 기록
$ bpftrace -e 'tracepoint:oom:mark_victim { printf("OOM victim pid=%d\n", args->pid); }'

# BCC 도구 (배포판에 따라 memleak-bpfcc 같은 이름)
$ memleak -p $(pidof app) 30     # 30초마다 아직 해제되지 않은 할당의 상위 스택
$ oomkill                        # OOM kill 발생 시 트리거 프로세스·희생자·페이지 수
$ drsnoop                        # direct reclaim 이벤트와 지연
$ slabratetop                    # 캐시별 kmem_cache_alloc 빈도
$ cachestat 1                    # 페이지 캐시 히트/미스
memleak의 오버헤드 유저 공간 memleak은 malloc/free마다 uprobe를 건다. 할당이 초당 수백만 번인 서비스는 수 배 느려질 수 있다. 운영 환경에서는 짧게, 또는 샘플링(-s 옵션)으로 쓴다. 할당자 자체의 프로파일러(jemalloc prof, tcmalloc heap profiler, Go pprof, JVM NMT)가 있다면 그쪽이 훨씬 싸다.

핵심 요약

  • 진단은 압박 여부 → 범위(cgroup/시스템) → 메모리 종류 → 소유 프로세스 → 할당 지점 순으로 좁힌다.
  • 판단 기준은 MemFree가 아니라 MemAvailable과 PSI, 그리고 스왑 I/O·major fault다. buff/cache가 큰 것은 정상이다.
  • RSS는 공유 페이지를 중복 계산한다. 전체 합산은 PSS, "죽이면 돌아오는 양"은 USS. top의 SHR은 "공유 가능한" 페이지다.
  • 컨테이너 OOM은 memory.events와 memory.stat(anon/file/shmem/kernel)로 분해한다. tmpfs(shmem)는 스왑 없이는 회수되지 않는다.
  • RSS만 늘고 힙 live가 일정하면 단편화·아레나·네이티브 할당을 의심하고, pmap의 크기 패턴(64MiB 아레나 등)으로 할당자를 추정한다.
  • 지연 스파이크는 compact_stall(THP), direct reclaim, major fault, NUMA 원격 접근 중 무엇과 상관있는지 카운터 차이로 확인한다.
  • 도구 선택: 전체(free/vmstat/meminfo/PSI) → 프로세스(smaps_rollup/pmap) → 커널(slabtop/numastat) → 이벤트(perf/bpftrace) → 할당(heaptrack/memleak/massif).

코스 종합 문제 20

개론·심화·실전을 고루 섞었다. 계산 문제는 종이에 직접 풀어 본 뒤 고르자. 점수는 각 문제의 첫 번째 선택으로만 집계된다.

점수 0 / 20 응답 0/20
개론·계산32비트 가상 주소, 4KiB 페이지, 단일 레벨 페이징. 가상 주소 0x00403A7C의 페이지 번호(VPN)와 오프셋은?
4KiB = 212이므로 하위 12비트(16진 3자리)가 오프셋: 0xA7C. 나머지 상위 20비트가 VPN: 0x00403A7C >> 12 = 0x00403.
개론·계산32비트 주소, 4KiB 페이지, PTE 4바이트인 단일 레벨 페이지 테이블의 프로세스당 크기는?
엔트리 수 = 232 / 212 = 220개, × 4B = 4MiB. 프로세스마다 이만큼 연속으로 필요하다는 점이 다단계 페이지 테이블의 동기다.
개론·계산x86-64 4단계 페이징(48비트, 4KiB). 가상 주소 0x00007F1234567000의 (PML4, PDPT, PD, PT) 인덱스는?
각 인덱스는 9비트: PML4 = (VA>>39)&511 = 254, PDPT = (VA>>30)&511 = 72, PD = (VA>>21)&511 = 418, PT = (VA>>12)&511 = 359, 오프셋 = 0.
개론·계산57비트 가상 주소, 4KiB 페이지, 8바이트 PTE에서 각 테이블이 정확히 한 페이지를 차지하도록 하면 몇 단계가 필요한가?
한 페이지에 4096/8 = 512 = 29개 엔트리 → 레벨당 9비트. (57 − 12) / 9 = 5. x86-64의 LA57(5단계 페이징)이 바로 이 구성이다.
개론·계산메모리 접근 100ns, TLB 조회 시간은 무시, TLB 히트율 99%, TLB 미스 시 4단계 페이지 워크(캐시 없음). 유효 접근 시간(EAT)은?
EAT = 0.99 × 100 + 0.01 × (4 × 100 + 100) = 99 + 5 = 104ns. 미스 시 페이지 테이블 4회 + 데이터 1회.
개론·계산메모리 접근 200ns, 페이지 폴트 처리 8ms, 폴트율 p = 0.001일 때 EAT는 대략?
EAT = 0.999 × 200 + 0.001 × 8,000,000 = 199.8 + 8,000 = 8,199.8ns ≈ 8.2µs. 1000번에 한 번의 폴트로도 40배 이상 느려진다 — 폴트율은 백만분의 일 수준이어야 한다.
개론·계산참조열 7 0 1 2 0 3 0 4 2 3 0 3 2 1 2 0 1 7 0 1, 프레임 3개(처음엔 비어 있음). FIFO의 페이지 폴트 수는?
FIFO는 15회. 같은 참조열에서 LRU는 12회, OPT는 9회다(첫 3회 강제 미스 포함).
개론·계산같은 참조열(7 0 1 2 0 3 0 4 2 3 0 3 2 1 2 0 1 7 0 1), 프레임 3개에서 LRU의 페이지 폴트 수는?
LRU는 12회. 최근 사용 순서를 추적하면 3 0 4 2 구간 등에서 FIFO보다 3회를 덜 교체한다.
개론·계산같은 참조열, 프레임 3개에서 OPT(Belady 최적)의 페이지 폴트 수는?
OPT는 9회. 미래에 가장 늦게 쓰일 페이지를 내보낸다. 실제로는 구현 불가능하지만 다른 알고리즘의 하한 기준이 된다.
개론·계산참조열 1 2 3 4 1 2 5 1 2 3 4 5에 FIFO를 적용할 때 프레임 3개와 4개의 폴트 수는?
프레임을 늘렸는데 폴트가 9→10으로 늘었다: Belady의 이상 현상. FIFO는 스택 알고리즘이 아니라서 생긴다(LRU/OPT에는 없다).
심화·계산1MiB 버디 할당자(시작 주소 0, 같은 크기면 낮은 주소 블록 우선)에 70KiB, 35KiB, 80KiB를 순서대로 요청했다. 남은 free 블록 구성과 내부 단편화 총량은?
70→128K(@0), 35→64K(@128K, 128K 블록 분할), 80→128K(@256K, 256K 블록 분할). 남는 블록: 64K@192K, 128K@384K, 512K@512K. 내부 단편화 = (128−70) + (64−35) + (128−80) = 58 + 29 + 48 = 135KiB.
개론·계산64엔트리 데이터 TLB의 TLB reach(커버 가능한 메모리)는 4KiB 페이지와 2MiB 페이지에서 각각?
64 × 4KiB = 256KiB, 64 × 2MiB = 128MiB. 같은 엔트리 수로 512배를 덮는다. 큰 working set에서 huge page가 효과적인 이유다.
심화·계산게스트는 4단계 4KiB 페이징, 호스트 EPT는 게스트 RAM을 2MiB 페이지로 매핑(EPT walk 3회)한다. 캐시가 모두 빈 상태에서 2D page walk의 최대 메모리 참조 수는?
n·m + n + m = 4×3 + 4 + 3 = 19. 호스트 쪽 huge page만으로도 24에서 19로 줄고, 게스트도 2MiB면 3×3+3+3 = 15.
실전·계산프로세스 P는 3개 프로세스가 공유하는 3MiB 라이브러리와 2MiB 전용 힙을 매핑하고 있다. P의 (RSS, PSS, USS)는?
RSS = 3 + 2 = 5, PSS = 3/3 + 2 = 3, USS = 전용 2. 세 프로세스의 RSS를 더하면 라이브러리가 세 번 계산되지만 PSS 합에는 한 번만 들어간다.
개론리눅스에서 fork() 직후 자식이 전역 변수 하나에 쓰면 일어나는 일로 옳은 것은?
fork는 페이지 테이블만 복사하고 양쪽 PTE를 쓰기 금지로 바꾼다. 첫 쓰기 시 CoW 폴트로 그 페이지만 복사한다. fork 후 대량 쓰기(Redis BGSAVE 등)가 메모리를 두 배 가까이 쓰게 하는 이유이기도 하다.
심화스래싱의 근본 원인과 가장 근본적인 해결책의 짝은?
워킹셋 합이 메모리를 넘으면 페이지가 계속 서로를 밀어낸다. CPU 이용률이 떨어졌다고 프로세스를 더 넣으면 악화된다(고전적 실수). 스왑을 키워도 해결되지 않는다.
심화커널이 버디 할당자 위에 slab/SLUB 계층을 두는 주된 이유는?
버디는 2n 페이지 단위라 수십~수백 바이트 객체에 낭비가 크다. slab은 같은 타입 객체를 페이지에 촘촘히 담고, CPU별 freelist로 락 없이 빠르게 할당한다. slab 객체는 일반적으로 스왑되지 않는다.
심화cgroup v2의 memory.high와 memory.max에 대한 설명으로 옳은 것은?
memory.high는 "여기서부터 느려져라"라는 소프트 한도로, 할당하는 태스크에 직접 회수와 지연을 부과한다. memory.max를 넘을 수 없고 회수로도 못 맞추면 cgroup 내 OOM kill이 일어난다.
심화KPTI(Meltdown 완화)가 시스템 콜 성능을 떨어뜨리는 이유와 이를 줄이는 하드웨어 기능은?
KPTI는 유저 모드용 페이지 테이블에서 커널 매핑 대부분을 제거하므로 진입/복귀마다 CR3를 전환한다. PCID가 없으면 매번 TLB가 비워진다. PCID가 있으면 두 주소 공간의 엔트리가 공존할 수 있다.
실전64GiB 서버에서 MemFree 0.8GiB, buff/cache 46GiB, MemAvailable 46GiB, PSI some avg60 = 0.00, si/so = 0이다. 올바른 판단은?
available이 크고 PSI·스왑 I/O가 0이면 압박이 없다. drop_caches는 뜨거운 캐시를 버려 오히려 디스크 I/O와 지연을 유발한다.
