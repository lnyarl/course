개론 · Chapter 06

가상 메모리와 페이지 폴트

malloc(1 GiB)는 왜 즉시 성공하고 RSS는 그대로일까? 페이지 폴트는 에러가 아니라 가상 메모리의 정상 동작 경로다. CPU 예외에서 커널 핸들러, 디스크 I/O, 명령 재시작까지 한 번의 폴트를 끝까지 따라가 본다.

학습 목표

  • 가상 메모리가 해결하는 문제와 요구 페이징(demand paging)의 원리를 설명할 수 있다.
  • x86-64 #PF 예외(CR2, 에러 코드)부터 Linux exc_page_fault → do_user_addr_fault → handle_mm_fault까지의 경로를 단계별로 말할 수 있다.
  • minor / major fault와 SIGSEGV(SEGV_MAPERR / SEGV_ACCERR)를 구분하고, 각각의 비용을 정량적으로 추정할 수 있다.
  • mm_struct와 vm_area_struct(VMA)의 역할, /proc/PID/maps 읽는 법을 안다.
  • 지연 할당·zero page·오버커밋이 VSZ/RSS와 OOM에 미치는 영향을 이해하고, prefault 도구(MAP_POPULATE, mlock)를 적절히 고를 수 있다.
  • /usr/bin/time -v, perf stat로 페이지 폴트를 측정하고 해석할 수 있다.

1. 가상 메모리는 무엇을 위해 존재하나

3장에서 페이징은 "가상 주소를 페이지 단위로 물리 프레임에 매핑하는 방법"이었다. 가상 메모리(virtual memory)는 여기서 한 걸음 더 나아간다. 매핑이 항상 존재할 필요가 없다는 것이다. 페이지 테이블 엔트리(PTE)가 "아직 없음"이어도 되고, 내용이 디스크(파일, 스왑)에 있어도 된다. 접근하는 순간 하드웨어가 커널을 불러 빈 곳을 채우게 하면 된다. 이 "부르는" 메커니즘이 페이지 폴트다.

이 한 가지 장치로 운영체제는 다음을 동시에 얻는다.

목적어떻게 달성하나현업에서 보이는 모습
물리 메모리보다 큰 주소 공간필요한 페이지만 RAM에, 나머지는 디스크나 "미할당" 상태로VSZ가 수십 GiB인 JVM, 수백 GiB 파일을 통째로 mmap하는 DB
격리와 보호프로세스마다 별도 페이지 테이블, PTE 권한 비트(R/W, U/S, NX)버그 난 프로세스가 다른 프로세스를 망가뜨리지 못하고 SIGSEGV로 죽음
공유여러 프로세스의 PTE가 같은 프레임을 가리킴libc 코드는 시스템 전체에 한 벌, 페이지 캐시 공유
단순한 프로그래밍 모델모든 프로세스가 0부터 시작하는 연속된 주소를 봄링커·로더가 물리 배치를 신경 쓰지 않음
지연(lazy) 처리할당·로드·복사를 실제 접근 시점까지 미룸빠른 프로세스 시작, fork의 COW(11장), malloc이 즉시 반환
파일 I/O와 메모리의 통합파일 페이지를 페이지 캐시에 두고 그대로 매핑mmap(), 실행 파일 로딩
흔한 오해: "가상 메모리 = 스왑" Windows의 "가상 메모리 설정" 화면 때문에 생긴 오해다. 스왑이 0이어도 가상 메모리는 늘 동작한다. 지연 할당, 파일 매핑, 공유, 보호는 모두 스왑 없이 이루어진다. 스왑은 "익명 페이지를 내보낼 곳"일 뿐이다.

2. 요구 페이징: 필요할 때만 올린다

요구 페이징(demand paging)은 페이지를 실제로 접근할 때만 메모리에 올리는 방식이다. 극단적인 형태인 순수 요구 페이징은 프로세스를 페이지 하나 없이 시작한다. 첫 명령어 페치부터 폴트가 나고, 폴트가 날 때마다 필요한 페이지가 하나씩 들어온다.

Linux의 execve()가 실제로 이렇게 동작한다. ELF 로더(binfmt_elf)는 헤더를 읽고 각 세그먼트를 mmap으로 매핑만 한다. 코드 페이지는 CPU가 그 주소를 실행하려는 순간 폴트로 들어온다. 그래서 100 MiB짜리 바이너리도 실행에 필요한 일부만 읽힌다.

왜 이게 통하나: 지역성

프로그램은 짧은 시간 동안 주소 공간의 작은 부분만 집중적으로 쓴다(시간·공간 지역성). 폴트 한 번으로 4 KiB를 가져오면 그 안의 수백~수천 번 접근이 폴트 없이 처리된다. 지역성이 깨지면(무작위 접근 + 메모리 부족) 폴트가 폭증하는데, 이것이 8장의 스래싱이다.

설계 트레이드오프

  • 장점: 시작이 빠르고, 쓰지 않는 코드·데이터는 메모리를 먹지 않는다. 같은 RAM에 더 많은 프로세스가 들어간다.
  • 단점: 첫 접근 비용이 예측 불가능한 시점에 나타난다. 지연 시간에 민감한 서비스에서는 "첫 요청만 느리다", "가끔 수 ms 튄다" 같은 증상이 된다. 그래서 9절의 prefault 도구가 존재한다.
파일 페이지에는 "주변도 같이" 최적화가 있다 파일 매핑의 읽기 폴트에서 Linux는 폴트 주소 주변 페이지 중 이미 페이지 캐시에 있는 것을 한꺼번에 매핑한다(fault-around, filemap_map_pages(), 기본 범위 64 KiB). 캐시에 없는 페이지는 readahead로 디스크에서 미리 읽어 온다. 둘 다 순수 요구 페이징의 폴트 횟수를 줄이는 장치다. 익명 메모리에는 fault-around가 없다.

3. 페이지 폴트 처리 전 과정

x86-64에서 페이지 폴트는 #PF, 예외 벡터 14다. 주소 변환 중 PTE의 P 비트가 0이거나 권한을 위반하면 MMU는 변환을 멈추고 CPU에 예외를 올린다. CPU는 두 가지 정보를 커널에 넘긴다.

  • CR2 레지스터: 폴트를 일으킨 가상 주소.
  • 에러 코드(스택에 push): 왜 폴트가 났는지를 나타내는 비트들.
비트이름0일 때1일 때
0P페이지 없음(not-present)있는데 보호 위반(protection violation)
1W/R읽기 접근쓰기 접근
2U/S커널 모드에서 발생사용자 모드에서 발생
3RSVD예약 비트가 1인 페이징 엔트리를 만남 (커널 버그·하드웨어 문제의 신호)
4I/D명령어 페치 중 발생 (NX 활성화 시 의미 있음)
5PK보호 키(PKU) 위반
6SS섀도 스택(CET) 접근
15SGXSGX 관련 위반

자주 보게 될 값은 0x4(사용자 읽기, 페이지 없음), 0x6(사용자 쓰기, 페이지 없음), 0x7(사용자 쓰기, 보호 위반), 0x14(사용자 명령어 페치, 페이지 없음)이다. 커널 로그의 segfault at ... error 6에 나오는 숫자가 바로 이 에러 코드다.

폴트는 "재시작 가능한" 예외다

x86 예외는 trap(명령 다음으로 복귀)과 fault(명령 자체로 복귀)로 나뉜다. #PF는 fault이므로 CPU가 저장하는 RIP는 폴트를 일으킨 명령의 주소다. 커널이 PTE를 채우고 복귀하면 같은 명령이 처음부터 다시 실행된다. 명령이 부분적으로 실행된 상태로 남지 않도록 CPU가 보장해야 하기 때문에, 요구 페이징은 하드웨어 지원 없이는 불가능하다. rep movsb처럼 긴 명령은 RCX/RSI/RDI에 진행 상황이 남아 이어서 실행된다.

페이지 폴트 처리 흐름 스텝 애니메이션
시나리오를 고르고 ▶로 진행하라. 하드웨어(윗줄)와 커널(아랫줄) 사이를 오가는 경로, 그리고 정상 폴트와 SIGSEGV가 어디서 갈리는지에 주목.
심화: 커널 모드에서 난 폴트는 어떻게 되나

커널도 폴트를 낸다. 대표적으로 read() 시스템 콜이 사용자 버퍼에 복사하는 copy_to_user() 중, 그 버퍼 페이지가 아직 할당되지 않은 경우다. 이것은 정상이고 사용자 폴트와 똑같이 handle_mm_fault()로 처리된다.

사용자가 넘긴 포인터가 아예 잘못된 경우, 커널은 예외 테이블(exception table)을 본다. copy_to_user 같은 "사용자 메모리에 접근하는 명령"은 미리 fixup 주소가 등록돼 있어, 폴트가 나면 그 위치로 점프해 -EFAULT를 반환한다. 등록되지 않은 커널 코드에서 잘못된 주소를 건드리면 oops(커널 패닉으로 이어질 수 있음)가 된다.

4. minor, major, 그리고 SIGSEGV

"페이지 폴트"라는 하나의 이름 아래에 비용이 수천 배 차이 나는 사건들이 섞여 있다. 커널은 해결에 디스크 I/O가 필요했는지로 나눠 센다.

분류대표 원인대략적 비용카운터
Minor (soft)익명 페이지 첫 접근(0 채움), 이미 페이지 캐시에 있는 파일 페이지 매핑, COW 복사, 스왑 캐시에 남아 있는 페이지보통 1 µs 안팎 (0 채움·복사 포함)min_flt, perf minor-faults
Major (hard)페이지 캐시에 없는 파일 페이지, 스왑 아웃된 익명 페이지NVMe 수십 µs ~ HDD 수 msmaj_flt, perf major-faults
Invalid어떤 VMA에도 속하지 않는 주소, VMA 권한 위반프로세스 종료(시그널)폴트로는 세지 않음. 시그널로 나타남

표의 비용은 하드웨어와 커널 버전에 따라 크게 달라지는 대략적인 크기(order of magnitude)다. 중요한 것은 minor와 major 사이에 10~1000배 이상 차이가 난다는 점이다.

SIGSEGV는 "PTE가 없다"가 아니라 "VMA가 없다"

초보자가 자주 헷갈리는 지점이다. 하드웨어 입장에서는 정상 폴트와 잘못된 접근이 똑같은 #PF다. 둘 다 PTE가 비어 있다. 차이는 커널의 VMA(가상 메모리 영역) 목록에 있다. VMA는 "이 주소 범위는 이 프로세스가 합법적으로 쓸 수 있고, 권한은 이렇다"는 커널 쪽 장부다.

  • VMA 안 + 권한 OK: 아직 채우지 않았을 뿐. 커널이 채우고 재실행한다.
  • VMA 밖: SIGSEGV, si_code = SEGV_MAPERR (NULL 역참조, 해제된 mmap 영역 접근, 스택 오버플로).
  • VMA 안 + 권한 위반: SIGSEGV, si_code = SEGV_ACCERR (문자열 리터럴에 쓰기, NX 영역 실행).
  • 파일 매핑에서 파일 끝을 넘는 페이지: VMA는 있지만 데이터가 없다. SIGBUS. 다른 프로세스가 매핑된 파일을 truncate하면 자주 발생한다.
VMA에는 쓰기 권한이 있는데 PTE는 읽기 전용인 경우 fork 직후의 COW 페이지, zero page 매핑이 그렇다. 쓰기 시 보호 위반 폴트(P=1, W=1)가 나지만 VMA가 쓰기를 허용하므로 정당하다. 커널은 do_wp_page()에서 페이지를 복사하고 쓰기 가능한 PTE로 바꾼다. 이것도 minor fault다. "PTE 권한"과 "VMA 권한"을 구분해 두는 이유가 바로 이런 지연 처리를 위해서다.
$ ./a.out
Segmentation fault (core dumped)
$ dmesg | tail -1
a.out[41233]: segfault at 10 ip 000055d0c1a0113d sp 00007ffc6b1e0c40 error 4 in a.out[55d0c1a01000+1000]

segfault at 10은 CR2 값(NULL 포인터 + 구조체 오프셋 0x10), error 4는 에러 코드(사용자 모드 읽기, 페이지 없음)다. ip에서 a.out 매핑 시작 주소를 빼면 바이너리 내 오프셋이 나오므로 addr2line으로 소스 위치를 찾을 수 있다. (이 로그는 debug.exception-trace sysctl이 1일 때 출력되며, 대부분 배포판의 기본값이다.)

5. 폴트율과 유효 접근 시간

4장의 TLB EAT와 같은 방식으로, 메모리 접근 한 번의 기대 시간을 폴트 확률 p로 쓸 수 있다.

EAT = (1 − p) × (메모리 접근 시간) + p × (페이지 폴트 처리 시간)

교과서 예시: 메모리 접근 200 ns, 디스크 폴트 처리 8 ms. 1,000번에 한 번만 폴트가 나도 EAT = 0.999×200 + 0.001×8,000,000 ≈ 8,200 ns, 즉 약 41배 느려진다. 성능 저하를 10% 이내로 묶으려면 220 > 200 + 7,999,800·p, 즉 p < 1/400,000 수준이어야 한다. 메모리 접근 40만 번에 한 번만 major fault를 허용한다는 뜻이다.

폴트율 기반 유효 접근 시간(EAT) 계산기
폴트 처리 시간을 바꿔 가며, 폴트율이 얼마일 때 체감 성능이 무너지는지 확인하라. 그래프는 로그-로그 축이다.

교훈: major fault는 "비율"이 아니라 "거의 0"이어야 한다 NVMe라도 폴트 하나가 메모리 접근 수백 번 값이다. 그래서 지연 시간 SLO가 있는 서비스는 major fault를 사건으로 다룬다. 반면 minor fault는 1 µs 수준이라 초당 수만 번도 흔하다. 다만 수백만 번이 몰리면(대용량 버퍼 초기화) 그 자체로 수백 ms가 된다.

6. Linux 구현: mm_struct, VMA, 폴트 핸들러

mm_struct: 주소 공간 하나

프로세스의 주소 공간 전체는 struct mm_struct 하나로 표현된다. task_struct->mm이 이를 가리키며, 같은 프로세스의 스레드들은 같은 mm_struct를 공유한다. 스레드가 메모리를 공유한다는 말의 실체가 이것이다. 커널 스레드는 mm이 NULL이다.

vm_area_struct(VMA): 연속된 가상 주소 구간 하나

VMA는 [vm_start, vm_end) 범위와 권한·성격이 같은 구간이다. mmap() 한 번, 힙, 스택, 실행 파일 각 세그먼트가 각각 VMA가 된다. 주요 필드는 다음과 같다.

  • vm_start, vm_end: 범위 (vm_end는 포함하지 않음)
  • vm_flags: VM_READ, VM_WRITE, VM_EXEC, VM_SHARED, VM_GROWSDOWN(스택), VM_LOCKED(mlock) 등
  • vm_page_prot: 이 VMA의 PTE를 만들 때 쓸 하드웨어 보호 비트
  • vm_file, vm_pgoff: 파일 매핑이면 파일과 시작 오프셋(페이지 단위). 익명이면 vm_file == NULL
  • anon_vma: 익명 페이지의 역매핑(rmap) 정보 (12장 회수에서 중요)
  • vm_ops: 파일·드라이버별 콜백. ->fault가 폴트 시 페이지를 구해 온다(일반 파일은 filemap_fault)

VMA 탐색은 폴트마다 일어나므로 빨라야 한다. Linux는 오랫동안 레드-블랙 트리와 연결 리스트를 함께 썼고, 6.1부터 maple tree(mm->mm_mt)로 바꿨다. VMA 수는 vm.max_map_count(기본 65530)로 제한된다. mmap을 아주 많이 하는 Elasticsearch 같은 프로그램이 이 값을 올리라고 요구하는 이유다.

  • 예전 커널(약 5.7 이전)에서는 진입 함수가 do_page_fault() → __do_page_fault()였다. 오래된 문서와 블로그에는 이 이름이 많이 나온다. ARM64는 지금도 do_page_fault()라는 이름을 쓴다(do_mem_abort()에서 호출).
  • mmap_sem은 5.8에서 mmap_lock으로 이름이 바뀌었다. 폴트는 이 락을 읽기로, mmap/munmap은 쓰기로 잡는다. 그래서 스레드가 많은 프로세스에서 한 스레드가 mmap/munmap을 반복하면 다른 스레드들의 폴트가 막히는 경합이 생겼고, 이를 줄이려고 6.4에서 per-VMA 잠금이 들어왔다.
  • major fault처럼 I/O를 기다려야 할 때 커널은 잠금을 풀고 VM_FAULT_RETRY를 반환한 뒤 I/O가 끝나면 폴트를 다시 처리한다. 디스크를 기다리는 동안 락을 붙잡고 있지 않기 위해서다.
  • 폴트 처리 결과에 VM_FAULT_MAJOR가 있으면 maj_flt를, 없으면 min_flt를 올린다(mm_account_fault()).

7. 지연 할당과 zero page

이제 서두의 질문에 답할 수 있다. glibc malloc은 큰 요청(기본 임계값 M_MMAP_THRESHOLD 128 KiB, 동적으로 조정됨)을 mmap(MAP_PRIVATE|MAP_ANONYMOUS)으로 처리한다. 커널의 mmap은 VMA만 만들고 PTE도 프레임도 만들지 않는다. 그래서:

  • VSZ(가상 크기, VmSize)는 즉시 늘어난다. VMA 크기의 합이기 때문이다.
  • RSS(상주 크기, VmRSS)는 그대로다. 실제 프레임이 매핑된 페이지 수이기 때문이다.
  • 각 페이지를 처음 쓰는 순간 minor fault가 나고, 그때 0으로 채운 프레임이 할당된다.

zero page: 읽기만 하면 메모리를 안 쓴다

익명 페이지를 쓰기 전에 읽기부터 하면 어떻게 될까? 내용은 어차피 전부 0이다. 그래서 do_anonymous_page()는 읽기 폴트일 때 새 프레임을 할당하지 않고, 시스템에 하나뿐인 공유 zero page(x86에서는 empty_zero_page)를 읽기 전용으로 매핑한다. 이 매핑은 RSS에 포함되지 않는다. 나중에 쓰기를 하면 보호 위반 폴트가 한 번 더 나고, do_wp_page()가 새 프레임을 할당해 교체한다. 즉 "읽고 나서 쓰기"는 페이지당 폴트가 2번이다.

지연 할당 시뮬레이터: malloc / touch와 VSZ·RSS
4 KiB 페이지 단위로 정확히 계산한다. 격자는 가장 최근 할당 영역을 64칸으로 나눈 것이다(한 칸 = 영역의 1/64). 가정: THP 꺼짐, 기본 프로세스 VSZ 6 MiB·RSS 1.5 MiB.

직접 확인하는 C 코드:

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

static void show(const char *tag) {
    char cmd[80];
    snprintf(cmd, sizeof cmd, "grep -E 'VmSize|VmRSS' /proc/%d/status", getpid());
    printf("== %s\n", tag); fflush(stdout);
    system(cmd);
}

int main(void) {
    size_t sz = 1UL << 30;                 /* 1 GiB */
    show("start");
    char *p = malloc(sz);                  /* mmap: VMA만 생성 */
    show("after malloc");                  /* VmSize +1 GiB, VmRSS 그대로 */
    volatile char s = 0;
    for (size_t i = 0; i < sz; i += 4096) s += p[i];   /* 읽기: zero page */
    show("after read");                    /* VmRSS 여전히 그대로 */
    memset(p, 1, sz);                      /* 쓰기: 페이지마다 프레임 할당 */
    show("after memset");                  /* VmRSS +1 GiB */
    free(p);                               /* munmap: 둘 다 감소 */
    show("after free");
    return 0;
}
결과가 시뮬레이터와 다를 수 있는 이유
  • THP(Transparent Huge Page)가 always면 2 MiB 정렬된 구간은 폴트 한 번에 2 MiB 페이지 하나가 통째로 할당된다. 폴트 수는 1/512로 줄고 RSS는 2 MiB 단위로 뛴다. 읽기 폴트는 huge zero page를 쓸 수 있다(13장).
  • calloc은 mmap으로 받은 메모리가 이미 0임을 알아서 memset을 생략한다. 그래서 calloc도 RSS를 즉시 늘리지 않는다.
  • malloc 헤더 때문에 실제 mmap 크기는 요청보다 조금 크다.
심화: 왜 커널은 페이지를 반드시 0으로 채우나

새로 할당한 프레임에는 직전 사용자(다른 프로세스, 커널)의 데이터가 남아 있다. 이를 그대로 넘기면 비밀번호·키가 유출된다. 그래서 익명 페이지는 반드시 0으로 채운 뒤 사용자에게 준다. 이 비용(4 KiB memset)이 minor fault 비용의 상당 부분을 차지한다. 대용량 할당에서 페이지 폴트 처리 시간이 메모리 대역폭에 묶이는 이유이기도 하다.

8. 오버커밋: 약속과 실제 사이

지연 할당 덕분에 커널은 실제로 줄 수 있는 것보다 많은 메모리를 약속할 수 있다. 이를 오버커밋(overcommit)이라 한다. 대부분의 프로그램은 할당받은 메모리를 다 쓰지 않으므로(스레드 스택 8 MiB 중 수십 KiB, fork 후 곧바로 exec) 이는 대체로 이득이다. 대가는 약속을 못 지키는 순간이 할당 시점이 아니라 접근 시점에 온다는 점이다. 그때는 malloc이 NULL을 돌려줄 기회가 이미 지났으므로 커널은 OOM killer로 누군가를 죽인다.

vm.overcommit_memory

값이름동작
0 (기본)Heuristic명백히 불가능한 요청만 거부. 현재 커널은 단일 요청이 RAM 전체 + 스왑 전체보다 크면 거부한다. 그 외에는 허용.
1Always검사하지 않고 항상 허용. 희소 배열을 거대하게 잡는 과학 계산, Redis(fork 기반 스냅숏) 권장값.
2Never (strict)총 약속량 Committed_AS가 CommitLimit을 넘으면 mmap/brk가 ENOMEM으로 실패. malloc이 NULL을 반환한다.
CommitLimit = (전체 RAM − hugetlb 예약) × vm.overcommit_ratio / 100 + 스왑 크기
              (vm.overcommit_ratio 기본 50. 대신 vm.overcommit_kbytes로 절대값 지정 가능)

$ grep -E 'CommitLimit|Committed_AS' /proc/meminfo
CommitLimit:    16346544 kB
Committed_AS:    9876532 kB

CommitLimit은 모드와 무관하게 항상 표시되지만 모드 2에서만 강제된다. Committed_AS에 들어가는 것은 쓰기 가능한 private 매핑(익명 메모리, private 파일 매핑의 쓰기 가능 부분)과 공유 메모리 등이다. 파일 공유 매핑이나 읽기 전용 private 매핑은 디스크에 원본이 있으므로 세지 않는다. MAP_NORESERVE는 모드 0/1에서 계산을 생략하게 하지만 모드 2에서는 무시된다.

오버커밋 판정 시뮬레이터
새 할당(쓰기 가능 private 매핑)이 각 모드에서 성공하는지 판정한다. 모드 2의 루트 예약(admin_reserve_kbytes)과 사용자 예약(user_reserve_kbytes)은 단순화를 위해 생략했다.
어느 모드를 써야 하나: 현업의 선택
  • 범용 서버: 0이 무난하다. 대신 OOM killer가 동작할 수 있음을 전제로 oom_score_adj와 cgroup 메모리 제한을 설계한다(12장).
  • Redis: 공식 문서가 1을 권장한다. 백그라운드 저장은 fork를 쓰는데, 부모 메모리가 크면 모드 0의 휴리스틱이나 모드 2의 계산에서 fork가 실패할 수 있기 때문이다. 실제로는 COW로 일부만 복사된다.
  • PostgreSQL: 공식 문서가 2를 권장한다. OOM killer가 postmaster를 죽이면 서비스 전체가 멈추므로, 차라리 할당 실패를 받아 해당 쿼리만 에러로 끝내는 편을 택한다. 단, 모드 2에서는 쓰지도 않을 스레드 스택·예약 영역도 약속량에 잡혀 다른 프로그램이 일찍 실패할 수 있다.

9. 미리 채우기: prefault, MAP_POPULATE, mlock

지연 할당은 처리량 면에서 유리하지만, 첫 접근의 지연이 문제가 되는 곳이 있다. 저지연 트레이딩, 실시간 오디오, 데이터베이스 버퍼 풀, 벤치마크가 그렇다. 이럴 때는 폴트를 미리, 예측 가능한 시점에 몰아서 처리한다.

도구효과주의
mmap(..., MAP_POPULATE)mmap 시점에 페이지 테이블을 채운다. 쓰기 가능 private 매핑이면 실제 프레임까지 할당한다(쓰기 폴트로 채워 COW를 미리 깨기 때문). 파일 매핑이면 readahead도 한다.mmap 호출이 그만큼 오래 걸린다. 이후 회수(reclaim)로 다시 빠질 수 있다.
madvise(MADV_POPULATE_READ / _WRITE)이미 만든 매핑의 일부 구간을 나중에 채운다 (Linux 5.14+). 실패 시 에러를 돌려준다.MAP_POPULATE와 달리 원하는 시점·범위를 고를 수 있다.
madvise(MADV_WILLNEED)파일 매핑의 비동기 readahead 힌트PTE를 채운다는 보장은 없다.
mlock(), mlockall(MCL_CURRENT|MCL_FUTURE), MAP_LOCKED페이지를 채우고(VM_LOCKED) 회수 대상에서 제외한다. 이후 major fault가 생기지 않는다.RLIMIT_MEMLOCK(ulimit -l) 제한. 잠근 만큼 다른 프로세스가 쓸 RAM이 줄어든다.
직접 터치 (pre-touch)시작 시 버퍼를 페이지마다 한 번씩 쓴다. JVM의 -XX:+AlwaysPreTouch가 대표적.시작 시간이 늘어난다. 읽기만 하면 zero page가 매핑되므로 반드시 쓰기로 터치해야 한다.
설계 질문: 지연과 선행 중 무엇을 고르나 총 작업량은 같거나, 쓰지 않을 페이지까지 채우면 오히려 늘어난다. prefault가 바꾸는 것은 비용이 나타나는 시점과 분산이다. "p99 지연이 중요한가, 평균 처리량과 메모리 효율이 중요한가?"로 판단한다.

10. 페이지 폴트 측정과 현업 사례

프로세스 단위: /usr/bin/time -v

셸 내장 time이 아니라 GNU time(/usr/bin/time)을 써야 한다. (macOS의 /usr/bin/time은 BSD판이라 -l 옵션을 쓴다.)

$ /usr/bin/time -v ./alloc_1g      # 1 GiB를 memset하는 프로그램 (출력 일부, 값은 예시)
	Maximum resident set size (kbytes): 1050880
	Major (requiring I/O) page faults: 0
	Minor (reclaiming a frame) page faults: 262271
	Voluntary context switches: 1
	...

1 GiB ÷ 4 KiB = 262,144. 나머지 백여 번은 프로그램 로딩·libc 초기화 몫이다. 숫자가 맞아떨어지면 THP가 쓰이지 않았다는 증거이기도 하다. 같은 실험을 THP always에서 하면 minor fault가 수백 번 수준으로 줄어든다.

perf stat

$ perf stat -e page-faults,minor-faults,major-faults ./alloc_1g
 Performance counter stats for './alloc_1g':
           262,271      page-faults
           262,271      minor-faults
                 0      major-faults
       0.38 seconds time elapsed            (값은 예시)

$ perf record -e page-faults -g ./app && perf report     # 폴트가 어느 코드에서 나는지

이들은 하드웨어 PMU가 아니라 커널이 세는 소프트웨어 이벤트라서 VM 안에서도 동작한다. page-faults(별칭 faults)는 minor와 major의 합이다.

실행 중인 프로세스와 시스템 전체

$ ps -o pid,vsz,rss,min_flt,maj_flt,cmd -p 1234      # 누적값 (vsz/rss는 KiB)
$ awk '{print "minflt="$10, "majflt="$12}' /proc/1234/stat
$ grep -E 'pgfault|pgmajfault' /proc/vmstat           # 부팅 후 시스템 전체 누적
$ sar -B 1                                             # 초당 fault/s, majflt/s (sysstat)

실습: 콜드 스타트의 major fault 만들기

$ sync; echo 3 | sudo tee /proc/sys/vm/drop_caches   # 페이지 캐시 비우기 (테스트 장비에서만!)
$ /usr/bin/time -v python3 -c 'pass' 2>&1 | grep -i 'page faults'
	Major (requiring I/O) page faults: 수백
$ /usr/bin/time -v python3 -c 'pass' 2>&1 | grep -i 'page faults'
	Major (requiring I/O) page faults: 0       ← 두 번째는 페이지 캐시에 있으므로 minor로 바뀐다

같은 프로그램, 같은 페이지인데도 페이지 캐시 상태에 따라 major/minor가 갈린다. "minor fault = 파일이 이미 메모리 어딘가에 있다"는 의미를 체감할 수 있는 실험이다.

현업에서 페이지 폴트로 나타나는 문제들

  • 배포 직후 첫 요청이 느림: 코드·데이터 페이지가 아직 페이지 캐시에 없어 major fault가 몰린다. 워밍업 트래픽이나 pre-touch로 완화한다.
  • 메모리 압박 후 간헐적 수 ms 지연: 회수가 오래 안 쓰인 실행 코드 페이지까지 내보내면, 그 코드 경로가 다시 실행될 때 major fault가 난다. 스왑이 0이어도 파일 페이지는 내보낼 수 있으므로 생기는 현상이다. sar -B의 majflt/s와 지연 그래프를 겹쳐 보라.
  • 대용량 버퍼 초기화가 수백 ms: 수 GiB를 처음 memset하면 수십만~수백만 번의 minor fault와 0 채움이 일어난다. THP나 MAP_POPULATE를 검토한다.
  • "RSS는 작은데 OOM": 오버커밋으로 VSZ는 크게 약속됐다가 여러 프로세스가 동시에 실제로 쓰기 시작하면 한꺼번에 RSS가 늘어난다. 모니터링은 VSZ가 아니라 RSS/PSS와 Committed_AS 추이를 봐야 한다.
  • 멀티스레드 서버의 폴트 경합: 한 스레드의 잦은 mmap/munmap(할당자가 큰 블록을 반복 반환)이 mmap_lock 쓰기 잠금을 잡아 다른 스레드들의 폴트를 막는다. 할당자 튜닝(10장)이나 최신 커널의 per-VMA 잠금이 해법이다.

핵심 요약

  • 가상 메모리는 "매핑이 항상 있을 필요는 없다"는 아이디어다. 비어 있거나 디스크에 있는 페이지는 접근 시 페이지 폴트로 채운다. 스왑과는 별개 개념이다.
  • x86-64 #PF(벡터 14)는 CR2(주소)와 에러 코드(P/W/U/I…)를 남기는 fault라서, 저장된 RIP로 복귀해 같은 명령을 재실행한다.
  • Linux 경로: exc_page_fault → do_user_addr_fault(VMA 탐색·권한 검사) → handle_mm_fault → handle_pte_fault(익명/파일/스왑/COW 분기). 예전 이름은 do_page_fault.
  • VMA 밖이면 SEGV_MAPERR, 권한 위반이면 SEGV_ACCERR. 하드웨어 폴트는 같고 판단은 커널의 VMA 장부가 한다.
  • minor(I/O 없음, ~µs)와 major(I/O 필요, 수십 µs~ms)는 비용이 수백~수천 배 다르다. 디스크 폴트율이 1/1000이면 수십 배 느려지므로 major fault는 사실상 0이어야 한다.
  • malloc은 VSZ만 늘린다. RSS는 첫 쓰기에서 늘고, 읽기만 하면 공유 zero page가 매핑되어 RSS가 늘지 않는다.
  • 오버커밋 모드 0/1/2는 "할당 시 실패(ENOMEM)"와 "접근 시 OOM kill" 사이의 선택이다. 모드 2는 Committed_AS < CommitLimit을 강제한다.
  • MAP_POPULATE, MADV_POPULATE_WRITE, mlock, pre-touch는 폴트 비용을 예측 가능한 시점으로 옮긴다. 측정은 /usr/bin/time -v, perf stat -e page-faults,minor-faults,major-faults, /proc/PID/stat으로 한다.

확인 문제

64비트 Linux(기본 설정, THP 꺼짐)에서 p = malloc(1 GiB) 직후, 아무 접근도 하지 않았을 때 가장 정확한 설명은?
큰 malloc은 mmap으로 VMA만 만든다. VSZ는 VMA 크기 합이므로 즉시 늘고, 프레임은 첫 쓰기 폴트 때 페이지 단위로 할당되므로 RSS는 그대로다. 0 채움도 폴트 시점에 페이지별로 일어난다.
프로세스 A가 /usr/bin/python3를 실행 중이다. 프로세스 B가 같은 바이너리를 새로 실행할 때, B가 처음 코드 페이지를 실행하며 나는 폴트는 주로 무엇인가?
B의 PTE는 비어 있으므로 폴트는 난다. 하지만 A 때문에 해당 파일 페이지가 이미 페이지 캐시에 있으므로 I/O 없이 매핑만 하면 된다. 이것이 minor fault다. 페이지 테이블은 프로세스마다 따로 있다(프레임만 공유).
NULL 포인터 구조체의 필드(p->x, 오프셋 0x10)를 읽었다. 커널 안에서 실제로 일어나는 일은?
낮은 주소에는 VMA가 없다(vm.mmap_min_addr로 매핑 자체도 금지된다). do_user_addr_fault()가 VMA 탐색에 실패해 bad_area 경로로 가고 SEGV_MAPERR로 시그널을 보낸다. dmesg에는 segfault at 10 ... error 4로 남는다.
메모리 접근 100 ns, 폴트 처리 10 ms, 폴트율 p = 10⁻⁵일 때 EAT는 대략 메모리 접근 시간의 몇 배인가?
EAT ≈ 100 + 10⁻⁵ × 10,000,000 ns = 100 + 100 = 200 ns. 10만 번에 한 번 폴트만으로도 2배가 된다. 계산기에서 직접 확인해 보라.
RAM 16 GiB, 스왑 0, vm.overcommit_memory=2, overcommit_ratio=50, 현재 Committed_AS 2 GiB다. malloc(10 GiB)는?
CommitLimit = 16 × 50% + 0 = 8 GiB. 2 + 10 = 12 GiB > 8 GiB이므로 mmap이 ENOMEM으로 실패하고 malloc은 NULL을 반환한다. 모드 2의 장점(할당 시점 실패)이자 단점(RAM이 남는데도 실패)이 동시에 드러나는 예다.
익명 mmap 영역 256 MiB를 할당하고, 모든 페이지를 한 번씩 읽기만 했다(THP 꺼짐). 그 결과로 옳은 것은?
256 MiB ÷ 4 KiB = 65,536페이지. 페이지마다 읽기 폴트가 나지만 커널은 공유 zero page를 읽기 전용으로 매핑하므로 새 프레임을 쓰지 않는다. 이후 같은 페이지에 쓰면 COW 폴트가 한 번 더 나며 그때 RSS가 늘어난다.
페이지 폴트 처리 후 CPU가 "같은 명령"을 다시 실행할 수 있는 근본 이유는?
fault는 명령 실행 전 상태로 되돌린 뒤 보고되는 예외다. 복귀 주소가 폴트 명령 자체이므로 PTE만 고쳐 주면 투명하게 재실행된다. 이 하드웨어 보장이 요구 페이징의 전제 조건이다.
