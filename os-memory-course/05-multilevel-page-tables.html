다단계 페이지 테이블과 x86-64

64비트 주소 공간은 거의 텅 비어 있다. 다단계 페이지 테이블은 "쓰지 않는 영역에는 테이블조차 만들지 않는다"는 아이디어로 이 희소성을 활용한다. 대가는 TLB 미스마다 테이블을 여러 번 읽어야 한다는 점이고, 하드웨어와 커널은 이 비용을 줄이려고 여러 장치를 겹겹이 둔다.

학습 목표

  • 단일 레벨 페이지 테이블의 메모리 비용을 직접 계산하고, 다단계 구조가 왜 필요한지 설명할 수 있다.
  • 32비트 x86(10|10|12), x86-64 4단계(9|9|9|9|12), 5단계(LA57)로 가상 주소를 분해하고 CR3부터 페이지 워크를 손으로 따라갈 수 있다.
  • canonical 주소, PS 비트에 의한 2MB/1GB 대형 페이지, paging-structure cache의 역할을 이해한다.
  • ARM64의 granule(4KB/16KB/64KB)과 TTBR0/TTBR1 분할을 x86-64와 비교할 수 있다.
  • Linux의 pgd/p4d/pud/pmd/pte 추상화와 "레벨 접기(folding)"를 코드 수준에서 이해한다.

1. 단일 레벨 페이지 테이블은 왜 안 되는가

3장에서 본 단일 레벨(선형) 페이지 테이블은 가상 페이지 번호(VPN)를 그대로 배열 인덱스로 쓴다. 조회는 빠르지만 주소 공간 전체에 대한 엔트리를 미리 연속으로 잡아 두어야 한다. 프로세스가 실제로 쓰는 메모리 양과 무관하게 테이블 크기가 결정된다는 것이 핵심 문제다.

환경VPN 비트엔트리 수PTE 크기프로세스당 테이블 크기
32비트, 4KB 페이지32 − 12 = 20220 ≈ 100만4B4 MiB
48비트(x86-64 4단계), 4KB 페이지48 − 12 = 36236 ≈ 687억8B512 GiB
57비트(LA57), 4KB 페이지57 − 12 = 452458B256 TiB

32비트에서도 프로세스 1,000개면 페이지 테이블만 4GB다. 그런데 실제 프로세스는 주소 공간의 극히 일부만 쓴다. 전형적인 리눅스 프로세스의 주소 공간은 아래쪽의 코드·데이터·힙, 위쪽의 공유 라이브러리와 스택, 그 사이의 거대한 빈 공간으로 이루어진다. 엔트리 대부분이 P=0(not present)인 배열에 메모리를 쓰는 것은 낭비다.

핵심 아이디어 페이지 테이블 자체를 다시 페이지 단위로 쪼개고, 그 조각들을 가리키는 상위 테이블을 둔다. 하위 조각이 전부 비어 있으면 상위 엔트리에 P=0만 적고 조각은 아예 할당하지 않는다. 결국 "페이지 테이블에 대한 페이지 테이블"이고, 이것을 반복하면 트리(정확히는 기수 트리, radix tree)가 된다.

이 설계에는 두 가지 부수 효과가 있다. 첫째, 각 테이블 조각을 정확히 한 페이지(4KB) 크기로 맞추면 페이지 테이블도 일반 물리 페이지 할당자로 관리할 수 있다. 연속된 큰 물리 메모리를 찾을 필요가 없다. 둘째, 대가로 주소 변환 한 번에 메모리를 레벨 수만큼 읽어야 한다. 이 비용은 TLB(4장)와 뒤에서 볼 paging-structure cache가 숨긴다.

2. 2단계 페이지 테이블: 32비트 x86 (10|10|12)

i386의 기본 페이징(PAE 아님)은 32비트 가상 주소를 다음처럼 나눈다.

  • 비트 31:22 (10비트): 페이지 디렉터리(Page Directory) 인덱스, PDE 1024개 중 하나
  • 비트 21:12 (10비트): 페이지 테이블(Page Table) 인덱스, PTE 1024개 중 하나
  • 비트 11:0 (12비트): 4KB 페이지 내 오프셋

엔트리가 4바이트이므로 1024 × 4B = 4KB, 즉 디렉터리와 각 페이지 테이블이 정확히 한 페이지다. 10비트라는 숫자는 여기서 나온다. CR3(PDBR)에는 현재 프로세스 페이지 디렉터리의 물리 주소가 들어 있다. 문맥 교환 때 CR3를 바꾸면 주소 공간 전체가 바뀐다.

얼마나 아끼는가

코드 1MB, 힙 2MB, 스택 64KB를 쓰는 작은 프로세스를 생각해 보자. 코드와 힙이 같은 4MB 구간에, 스택이 맨 위 4MB 구간에 있다면 필요한 것은 디렉터리 1개 + PT 2개 = 12KB다. 단일 레벨의 4MB와 비교하면 약 340분의 1이다. 대신 주소 공간을 빽빽하게 다 쓰는 극단적인 경우에는 디렉터리 4KB만큼 오히려 손해다. 다단계 테이블은 희소성에 거는 내기이고, 실제 프로그램에서 이 내기는 거의 항상 이긴다.

4MB 페이지 (PSE) CR4.PSE가 켜져 있으면 PDE의 PS 비트(비트 7)를 1로 설정해 PDE 하나가 4MB 페이지를 직접 가리키게 할 수 있다. 이 경우 PT 단계가 사라지고 하위 22비트가 전부 오프셋이 된다. "중간 레벨에서 워크를 끝낸다"는 대형 페이지의 원형이며, 7절의 2MB/1GB 페이지와 같은 원리다.
심화: PAE (2|9|9|12)는 왜 생겼나

32비트 주소 공간에서 4GB 넘는 물리 메모리를 쓰기 위해 Pentium Pro가 PAE를 도입했다. 물리 주소가 36비트(이후 최대 52비트)로 커지자 프레임 번호가 4바이트 엔트리에 들어가지 않게 되었다. 그래서 엔트리를 8바이트로 키웠고, 한 페이지(4KB)에 들어가는 엔트리는 512개, 즉 인덱스 9비트가 되었다. 32비트 주소에서 9+9+12 = 30비트를 빼면 2비트가 남고, 이 2비트가 4개짜리 PDPT(Page Directory Pointer Table)를 고른다.

PAE의 8바이트 엔트리와 512개 구성은 그대로 x86-64로 이어졌다. NX(XD) 비트(비트 63)도 8바이트 엔트리가 있어서 넣을 수 있었다. x86-64의 "9비트씩"은 PAE에서 물려받은 것이다.

3. x86-64 4단계 페이징과 canonical 주소

x86-64는 PAE 형식(8바이트 엔트리, 테이블당 512개)을 유지하면서 레벨을 4개로 늘렸다. 9비트 × 4 + 12비트 = 48비트 가상 주소이고, 표현 가능한 공간은 248 = 256 TiB다.

CR3에는 PML4 테이블의 물리 주소가 들어간다(하위 12비트는 PCID가 켜져 있으면 PCID, 아니면 PWT/PCD 플래그). 각 엔트리의 물리 주소 필드는 비트 51:12(CPU가 지원하는 MAXPHYADDR까지)이며, 하위 비트는 P/RW/US/A/D 등 플래그, 비트 63은 XD(NX)다.

canonical 주소: 위쪽 16비트는 왜 비어 있나

포인터는 64비트지만 변환에 쓰이는 것은 하위 48비트다. AMD는 남는 비트 63:48을 비트 47과 같은 값으로 채우도록(부호 확장) 강제했다. 이 규칙을 만족하는 주소를 canonical 주소라고 한다. 결과적으로 주소 공간은 아래쪽 128 TiB(0x0000_0000_0000_0000 ~ 0x0000_7FFF_FFFF_FFFF)와 위쪽 128 TiB(0xFFFF_8000_0000_0000 ~ 0xFFFF_FFFF_FFFF_FFFF)로 갈라지고, 그 사이는 쓸 수 없는 거대한 구멍이 된다. Linux는 아래쪽을 사용자 공간, 위쪽을 커널 공간으로 쓴다.

왜 굳이 canonical 규칙을 강제했나 위쪽 비트를 "무시"하도록 했다면 프로그램들이 포인터 상위 16비트에 태그를 숨겼을 것이고, 나중에 주소 공간을 넓힐 때 그 프로그램들이 전부 깨진다. 실제로 68000에서 24비트 주소 시절 상위 8비트를 쓰던 Mac 소프트웨어가 32비트 전환 때 대거 망가진 전례가 있다. 그래서 AMD는 "지금은 안 쓰지만 쓰면 예외"로 막아 두었고, 덕분에 5단계(57비트) 확장이 기존 바이너리를 깨지 않았다. 현재의 포인터 태깅은 Intel LAM, AMD UAI, ARM TBI처럼 하드웨어가 명시적으로 허용하는 방식으로만 한다.

non-canonical 주소에 접근하면 페이지 워크까지 가지도 않고 #GP(일반 보호 예외)가 난다(스택 세그먼트 참조라면 #SS). Linux에서는 둘 다 SIGSEGV로 끝나지만, 커널 oops 로그에서 "general protection fault ... probably for non-canonical address"가 보이면 쓰레기 포인터(초기화 안 된 값, use-after-free 후 덮어쓴 값, 0xdead000000000100 같은 poison 값)를 의심해야 한다. 페이지 폴트("unable to handle page request")와 구분해서 읽는 것이 디버깅의 첫걸음이다.

4. 5단계 페이징 (LA57)

256 TiB 가상 공간은 수 TB 메모리를 가진 서버, 비휘발성 메모리(persistent memory) 매핑, 대규모 데이터베이스에서 부족해지기 시작했다. Linux의 direct map은 물리 메모리 전체를 커널 가상 공간에 매핑하는데, 4단계에서는 이 영역이 64 TiB로 제한된다. 그래서 Intel은 5단계 페이징을 정의했다.

  • CR4.LA57(비트 12)을 켜면 PML5 레벨이 추가되어 9×5 + 12 = 57비트 가상 주소, 128 PiB 공간이 된다. canonical 규칙은 "비트 63:57 = 비트 56"으로 바뀐다.
  • CR3는 PML5 테이블을 가리키고, PML5 엔트리 하나가 256 TiB(4단계 주소 공간 전체)를 담당한다.
  • CPU 지원 여부는 /proc/cpuinfo의 la57 플래그로 확인한다. Intel은 Ice Lake 세대부터, AMD는 Zen 4부터 지원한다.
  • LA57은 64비트 모드에서 페이징을 켠 채로 바꿀 수 없다. 그래서 부팅 초기에 결정되며, Linux는 CPU가 지원하면 5단계로 부팅하고 no5lvl 커널 파라미터로 끌 수 있다.
Linux의 호환성 장치: 기본은 47비트 5단계로 부팅해도 Linux는 사용자 프로세스의 mmap을 기본적으로 47비트(128 TiB) 아래에만 배치한다. 포인터 상위 비트에 태그를 숨기는 JIT, 가비지 컬렉터, NaN-boxing 런타임이 깨지지 않게 하기 위해서다. 47비트 위 공간(최대 56비트, 64 PiB)이 필요한 프로그램은 mmap()의 주소 힌트로 그보다 높은 주소를 명시적으로 요청해야 한다. "능력은 넓히되 기본 동작은 바꾸지 않는다"는 전형적인 커널 호환성 설계다.

대가는 분명하다. TLB 미스 하나에 메모리 참조가 최대 4번에서 5번으로 늘어난다. 실제로는 상위 레벨 엔트리가 거의 항상 paging-structure cache에 적중하기 때문에(8절) 체감 비용은 작지만, 가상화 환경의 2차원 워크에서는 레벨 증가 비용이 곱으로 커진다.

5. 페이지 워크 따라가기

아래 위젯은 작은 가상 프로세스의 실제 페이지 테이블 트리를 만든다. 매핑은 PIE 코드(0x5555_5555_4000, 4페이지), 힙(33페이지), libc 일부(8페이지), 2MB THP 하나, 스택(33페이지), 그리고 커널 direct map의 1GB 페이지 하나다. 각 테이블은 512칸짜리 세로 막대로 그렸고, 가로 눈금은 P=1인 엔트리다. 대부분의 칸이 비어 있고, 빈 칸 아래에는 하위 테이블이 존재하지 않는다는 점을 눈여겨보자.

가상 주소 분해 + CR3부터 페이지 워크
주소를 입력하거나 프리셋을 고른 뒤 ▶ 재생 또는 다음 ▶으로 한 단계씩 따라간다. 4단계/5단계를 바꾸면 같은 매핑으로 트리를 다시 만든다.

위젯에서 확인할 것들:

  • "힙 끝 너머"는 PT까지 내려가서 마지막 칸이 비어 #PF가 난다. "중간 레벨 빈칸"은 PD 엔트리가 비어서 PT 단계까지 가지도 못한다. 하드웨어 입장에서는 둘 다 같은 #PF이고, 커널이 VMA를 확인해서 정상적인 요구 페이징인지 잘못된 접근인지 판단한다(6장).
  • 0x0000_8000_0000_0000은 4단계에서는 non-canonical이라 #GP지만, 5단계에서는 정상 주소라 PML4 칸이 비어서 #PF가 난다. 같은 숫자가 모드에 따라 다른 예외를 만든다.
  • 5단계에서는 테이블이 하나 더 늘어날 뿐 하위 구조는 같다. 이 프로세스는 PML5[0](사용자)과 PML5[511](커널)만 쓴다.

6. 페이지 테이블은 메모리를 얼마나 먹는가

다단계 테이블의 메모리 사용량은 "매핑된 바이트 수"가 아니라 매핑이 몇 개의 서로 다른 구간에 퍼져 있는가로 결정된다. 레벨 k의 테이블 수는 매핑된 주소들을 그 테이블이 담당하는 크기(PT는 2MB, PD는 1GB, PDPT는 512GB)로 나눴을 때 나오는 서로 다른 몫의 개수다.

  • 빽빽한 매핑: 1GB를 연속으로 4KB 페이지로 매핑하면 PT 512개(2MB) + PD 1개 + PDPT 1개 + PML4 1개 ≈ 2.01MB, 즉 데이터의 약 0.2%(8B/4KB)다. 단일 레벨이라도 이 부분은 똑같이 필요하므로, 차이는 상위 레벨 몇 장뿐이다.
  • 흩어진 매핑: 4KB 페이지 하나씩을 서로 1GB 넘게 떨어뜨려 놓으면 페이지마다 PT, PD, 경우에 따라 PDPT까지 새로 필요하다. 최악에는 4KB 데이터에 테이블 12~16KB가 붙는다.
페이지 테이블 메모리 사용량 계산기
N개의 영역을 주소 공간에 배치했을 때 단일 레벨과 다단계 테이블이 실제로 차지하는 메모리를 비교한다. 레벨별 테이블 수는 매핑 구간에서 직접 센 값이다.

계산기로 확인할 만한 실험:

  • 4단계, 4KB × 512개, 분산: 영역마다 PT·PD·PDPT가 따로 생겨 테이블이 매핑 데이터보다 커진다. 같은 512개를 "연속"으로 바꾸면 테이블 몇 장으로 줄어든다. 주소 공간 레이아웃이 페이지 테이블 비용을 결정한다.
  • 256MiB × 16개에 2MB 대형 페이지를 켜면 PT 레벨이 통째로 사라져 테이블 메모리가 수백 분의 1로 준다.
  • 32비트로 바꾸면 단일 레벨도 4MiB라 차이가 덜 극적이다. 64비트에서 다단계가 "선택"이 아니라 "필수"인 이유가 여기 있다.
현업: 공유 메모리 × 프로세스 수 = PageTables 폭증

PostgreSQL처럼 프로세스 기반 서버가 큰 공유 메모리(shared_buffers)를 쓰면, 같은 물리 페이지를 매핑하더라도 페이지 테이블은 프로세스마다 따로 존재한다. 공유 메모리 64GB를 4KB 페이지로 매핑하면 프로세스 하나당 PTE만 64GB/4KB × 8B = 128MB이고, 백엔드 500개가 전부 건드리면 이론상 64GB가 페이지 테이블로 사라진다. /proc/meminfo의 PageTables가 수십 GB로 치솟는 장애가 실제로 자주 보고된다.

대응은 대형 페이지다. 2MB 페이지면 PT 레벨이 사라져 테이블 크기가 1/512로 준다. 또 Linux는 hugetlbfs 공유 매핑이 1GB(PUD) 경계에 정렬돼 있으면 x86-64 등에서 PMD 페이지 자체를 프로세스 간에 공유(huge_pmd_share)해 이 비용을 더 줄인다. 프로세스별 사용량은 /proc/<pid>/status의 VmPTE로 확인한다.

$ grep PageTables /proc/meminfo
PageTables:        48212 kB
$ grep VmPTE /proc/$(pgrep -o postgres)/status
VmPTE:      1036 kB

7. 대형 페이지: 워크가 중간에서 끝나는 방법

x86-64에서 PD 엔트리와 PDPT 엔트리의 비트 7은 PS(Page Size)다. PS=0이면 엔트리는 다음 레벨 테이블을 가리키고, PS=1이면 엔트리 자체가 큰 페이지의 리프가 된다. 워크는 거기서 끝나고, 남은 하위 비트는 전부 오프셋이 된다.

4KB2MB1GB

PS 비트 위치의 미묘함 비트 7은 PDE/PDPTE에서는 PS지만 4KB PTE에서는 PAT 비트다. PTE 단계에서는 더 내려갈 곳이 없으니 PS가 필요 없고, 그 자리를 캐시 속성 선택에 재사용한다. 대신 대형 페이지 엔트리에서 PAT는 비트 12로 옮겨진다(대형 페이지는 정렬 때문에 물리 주소 하위 비트가 어차피 0이다). "같은 비트가 레벨마다 다른 의미"라는 점은 커널 코드에서 pmd_leaf(), pud_leaf() 같은 함수가 따로 있는 이유이기도 하다.

대형 페이지의 본래 목적은 페이지 테이블 절약보다 TLB reach 확대다(4장). 2MB 페이지 하나가 4KB TLB 엔트리 512개 몫을 하므로, 수십 GB 작업 집합을 다루는 DB·JVM·ML 워크로드에서 TLB 미스와 워크 비용이 크게 준다. 대가는 내부 단편화, 2MB 연속 물리 메모리 확보의 어려움(compaction 비용), 메모리 회수의 거친 단위다. 이 트레이드오프는 13장에서 다시 다룬다.

8. 워크 비용과 paging-structure cache

TLB 미스가 나면 하드웨어 페이지 워커가 CR3부터 엔트리를 순서대로 읽는다. 각 읽기는 앞의 결과에 의존하므로(포인터 추적) 병렬화할 수 없다. 다행히 페이지 테이블 엔트리도 일반 데이터처럼 L1/L2/LLC 캐시에 올라가므로, 매번 DRAM까지 가지는 않는다. 그래도 4번의 의존적 캐시 접근은 수십 사이클이다.

그래서 CPU는 TLB와 별도로 상위 레벨 엔트리를 캐시한다. Intel SDM은 이것을 paging-structure cache라고 부르고, 학계와 AMD 계열 자료에서는 흔히 page walk cache(PWC)라고 한다. 핵심은 "가상 주소의 상위 비트만 같으면 상위 레벨 엔트리도 같다"는 사실이다.

  • 프로세스가 512GB 안에서만 일한다면 PML4E는 사실상 항상 적중한다. 그래서 4→5단계 전환의 실제 비용은 생각보다 작다.
  • 최악은 수십 GB 이상의 넓은 영역을 무작위로 건드리는 경우(그래프 처리, 해시 조인, 큰 해시 테이블)다. PDE 캐시조차 미스가 나서 워크가 DRAM까지 내려간다. 이때 대형 페이지가 TLB와 PWC 양쪽에서 효과를 낸다.
  • 가상화에서는 게스트 페이지 테이블의 각 엔트리 주소가 다시 EPT/NPT를 거쳐야 하므로 4단계 × 4단계 2차원 워크에서 최대 (4+1)×(4+1) − 1 = 24번 메모리 참조가 필요하다(15장). PWC와 대형 페이지가 가상화 성능에 결정적인 이유다.
커널이 지켜야 할 규칙: 테이블을 해제할 때도 무효화해야 한다 paging-structure cache는 상위 엔트리의 사본을 들고 있다. 커널이 빈 PT 페이지를 해제하고 PDE를 지운 뒤 그 페이지를 다른 용도로 재사용했는데, 어떤 CPU의 PDE 캐시에 옛 PT 주소가 남아 있다면 하드웨어 워커가 엉뚱한 데이터를 PTE로 해석할 수 있다. 그래서 Intel SDM은 INVLPG가 해당 주소의 TLB 엔트리뿐 아니라 현재 PCID의 paging-structure cache 엔트리 전부를 무효화한다고 규정한다. Linux는 mmu_gather(tlb_gather_mmu() … tlb_finish_mmu())로 페이지와 페이지 테이블 해제를 모아 두었다가 TLB flush가 끝난 다음에 실제로 해제한다. 락 없이 페이지 테이블을 읽는 소프트웨어 워커(fast GUP)를 위해 RCU로 해제를 늦추는 설정(MMU_GATHER_RCU_TABLE_FREE)도 있다.

9. ARM64 변환 테이블과 비교

ARMv8-A(AArch64)도 기수 트리 구조지만 두 가지 면에서 x86-64와 다르다.

(1) granule: 페이지 크기를 고를 수 있다

변환 granule은 4KB, 16KB, 64KB 중 하나다. 테이블 한 장 = granule 크기, 디스크립터 = 8바이트이므로 레벨당 인덱스 비트는 log2(granule) − 3이다.

granule오프셋레벨당 비트 (엔트리)48비트 VA 구성블록(대형) 매핑대표 사용처
4KB129 (512)L0~L3, 4단계 (9|9|9|9|12)L1 1GB, L2 2MB대부분의 Linux 배포판, Android
16KB1411 (2048)L0(1비트, 2개)~L3, 4단계L2 32MBApple Silicon(macOS, iOS)
64KB1613 (8192)L1(6비트, 64개)~L3, 3단계L2 512MB일부 서버용 커널(대용량 메모리, HPC)

granule이 크면 레벨 수가 줄고 TLB reach가 커지지만 내부 단편화와 페이지 캐시 낭비가 커진다. 64KB 커널에서는 4KB 파일 수천 개를 열면 페이지 캐시가 16배로 부푼다. ARM64는 이 밖에 contiguous 비트로 연속된 엔트리 묶음(4KB granule이면 PTE 16개 = 64KB, PMD 16개 = 32MB)을 TLB 엔트리 하나로 합치게 할 수 있다. Linux arm64가 hugetlb 크기로 64KB, 2MB, 32MB, 1GB를 제공하는 이유다.

(2) TTBR0/TTBR1: 주소 공간을 레지스터 두 개로 나눈다

  • VA 상위 비트가 전부 0이면 TTBR0_EL1, 전부 1이면 TTBR1_EL1의 테이블로 변환한다. 두 범위의 크기는 TCR_EL1의 T0SZ/T1SZ(VA 크기 = 64 − TxSZ)로, granule은 TG0/TG1로 따로 정한다. 그 사이 주소는 변환 폴트다(x86의 non-canonical에 해당).
  • x86-64 커널은 새 프로세스의 PML4를 만들 때 커널 절반 엔트리를 복사한다(pgd_alloc()). 커널 상위 엔트리가 나중에 바뀌면 모든 프로세스의 PGD에 반영해야 하므로, x86-64 Linux는 vmalloc 영역 등의 상위 테이블을 부팅 때 미리 할당해 두고(preallocate_vmalloc_pages()) 이후에는 하위 레벨만 바꾼다. ARM64는 TTBR1이 별도라서 이런 복사 자체가 없다.
  • ARM64 디스크립터는 레벨에 따라 table / block / page 세 가지다. x86의 PS 비트 대신 디스크립터 하위 2비트의 타입 필드로 구분한다(L0~L2: 0b11 = table, 0b01 = block / L3: 0b11 = page).
ARM64 granule별 주소 분해기
granule과 VA 크기(Linux CONFIG_ARM64_VA_BITS로 고를 수 있는 조합)를 고르면 레벨 구성과 인덱스를 보여준다. TTBR 선택은 TBI(Top Byte Ignore)를 끈 상태 기준이다.

10. Linux의 pgd/p4d/pud/pmd/pte 추상화

Linux는 수십 개 아키텍처를 하나의 메모리 관리 코드로 지원한다. 그래서 하드웨어 레벨 이름 대신 5단계 일반 모델을 쓴다.

Linux뜻x86-64 5단계x86-64 4단계ARM64 4KB/48비트
pgd_tPage Global DirectoryPML5PML4L0
p4d_tPage 4th-level DirectoryPML4(접힘)(접힘)
pud_tPage Upper DirectoryPDPTPDPTL1
pmd_tPage Middle DirectoryPDPDL2
pte_tPage Table EntryPTPTL3

하드웨어 레벨이 5개보다 적으면 남는 레벨을 접는다(fold). 접힌 레벨은 엔트리 1개짜리 가상의 테이블로 취급되고, p4d_offset(pgd, addr)는 단순히 (p4d_t *)pgd를 돌려준다. 컴파일러가 이 호출을 전부 지워 버리므로 런타임 비용은 0이다. 공통 정의는 include/asm-generic/pgtable-nop4d.h, pgtable-nopud.h, pgtable-nopmd.h에 있고, 아키텍처는 CONFIG_PGTABLE_LEVELS에 맞춰 이 헤더를 포함한다. x86-64는 한 커널 이미지로 4단계와 5단계를 모두 지원해야 하므로 p4d를 런타임에 접는다(pgtable_l5_enabled()). p4d는 2017년(Linux 4.11) 5단계 지원을 준비하면서 pgd와 pud 사이에 새로 끼워 넣은 레벨이고, 실제 5단계 지원은 4.14에 들어왔다.

/* 커널에서 사용자 주소 addr의 PTE를 찾는 전형적인 워크 (개념 코드) */
pgd_t *pgd = pgd_offset(mm, addr);          /* mm->pgd + pgd_index(addr) */
if (pgd_none(*pgd) || pgd_bad(*pgd)) return NULL;
p4d_t *p4d = p4d_offset(pgd, addr);         /* 4단계면 사실상 no-op */
if (p4d_none(*p4d) || p4d_bad(*p4d)) return NULL;
pud_t *pud = pud_offset(p4d, addr);
if (pud_none(*pud)) return NULL;
if (pud_leaf(*pud)) return /* 1GB 페이지 */;
pmd_t *pmd = pmd_offset(pud, addr);
if (pmd_none(*pmd)) return NULL;
if (pmd_leaf(*pmd)) return /* 2MB THP / hugetlb */;
pte_t *pte = pte_offset_map(pmd, addr);     /* 사용 후 pte_unmap(pte) */

상수도 같은 체계다. x86-64 4단계에서 PAGE_SHIFT=12, PMD_SHIFT=21, PUD_SHIFT=30, PGDIR_SHIFT=39이고, 5단계에서는 P4D_SHIFT=39, PGDIR_SHIFT=48이다. PTRS_PER_PTE 등은 모두 512다. 실제 커널 코드에서는 이 워크를 직접 쓰기보다 walk_page_range()(mm/pagewalk.c)처럼 레벨별 콜백을 받는 범용 워커나, 폴트 경로의 handle_mm_fault() → __handle_mm_fault()처럼 필요한 테이블을 할당하면서 내려가는 코드(p4d_alloc(), pud_alloc(), pmd_alloc())를 쓴다. 다단계 테이블의 "필요할 때만 만든다"는 성질이 이 alloc 함수들에서 구현된다.

아키텍처별 레벨 접기 보기
구성을 고르면 Linux의 다섯 레벨이 어느 하드웨어 레벨에 대응하는지, 어느 레벨이 접히는지, 각 레벨의 SHIFT 값을 보여준다. 위의 워크 코드는 모든 구성에서 그대로 컴파일된다.

11. 다른 설계: 역 페이지 테이블과 해시 페이지 테이블

기수 트리만 답은 아니다. 64비트 주소 공간이 희소하다는 같은 문제를 다른 방식으로 푼 설계도 있다.

  • 역 페이지 테이블(inverted page table): 물리 프레임마다 엔트리 하나를 둔다(크기가 물리 메모리에 비례). 가상 주소로 찾으려면 해시로 검색한다. 프로세스가 많아도 테이블은 하나지만, 공유 메모리(한 프레임에 여러 가상 주소)를 표현하기 어렵다.
  • 해시 페이지 테이블: PowerPC의 HPT(Hashed Page Table)가 대표적이다. VPN을 해시해 고정 크기 테이블의 그룹(PTEG)을 찾는다. 워크가 1~2번의 메모리 접근으로 끝나는 장점이 있지만 해시 충돌 처리와 테이블 크기 결정이 까다롭고, 캐시 지역성이 나쁘다. IBM은 POWER9부터 기수 트리 MMU(radix)도 지원하고 있다.
왜 기수 트리가 이겼나 기수 트리는 (1) 인접한 가상 페이지의 엔트리가 같은 캐시 라인에 모여 지역성이 좋고, (2) 상위 레벨 캐시(PWC)로 워크를 단축하기 쉬우며, (3) 대형 페이지를 "중간에서 끝내기"로 자연스럽게 표현하고, (4) fork/COW나 범위 단위 해제에서 하위 트리를 통째로 다룰 수 있다. 하드웨어 워커가 단순하다는 점도 크다.

핵심 요약

  • 단일 레벨 테이블은 주소 공간 크기에 비례한다(32비트 4MiB, 48비트 512GiB). 다단계 테이블은 매핑이 퍼진 구간 수에 비례하므로 희소한 주소 공간에서 수천~수백만 배 작다.
  • 테이블 한 장 = 한 페이지가 되도록 인덱스 폭을 정한다. 32비트(4B 엔트리)는 10|10|12, PAE·x86-64(8B 엔트리)는 레벨당 9비트다.
  • x86-64 4단계는 9|9|9|9|12 = 48비트이고 비트 63:48은 비트 47의 부호 확장(canonical)이어야 한다. 위반 시 #GP다. LA57은 PML5를 추가해 57비트(128 PiB)를 만든다.
  • PDE/PDPTE의 PS=1은 워크를 중간에서 끝내 2MB/1GB 페이지를 만든다. 오프셋이 21/30비트가 되고 TLB reach가 커진다.
  • 워크는 의존적 메모리 접근의 연쇄다. TLB, paging-structure cache(PWC), 데이터 캐시가 비용을 숨기고, 가상화의 2D 워크(최대 24회)에서는 대형 페이지가 결정적이다.
  • ARM64는 granule(4/16/64KB)로 레벨 구조가 바뀌고, TTBR0/TTBR1로 사용자·커널 테이블을 분리한다.
  • Linux는 pgd→p4d→pud→pmd→pte 5단계 모델을 쓰고, 하드웨어에 없는 레벨은 접어서 런타임 비용 없이 같은 코드를 쓴다. 페이지 테이블 메모리는 PageTables(meminfo), VmPTE(status)로 확인한다.

확인 문제

x86-64 4단계 페이징에서 프로세스가 VA 0x0000_0000_0000_0000의 한 페이지와 VA 0x0000_7FFF_FFFF_F000의 한 페이지만 매핑했다. 필요한 페이지 테이블 페이지(4KB) 수는?
두 주소의 인덱스는 (0,0,0,0)과 (255,511,511,511)이다. PML4는 1장을 공유하지만 PML4 인덱스부터 다르므로 PDPT·PD·PT가 각각 2장씩 필요하다. 1 + 2 + 2 + 2 = 7장(28KB)이다. 단일 레벨이었다면 512GiB가 필요하다.
VA 0x0000_7F12_3456_7ABC를 4단계로 분해하면 (PML4, PDPT, PD, PT, offset)은?
각 인덱스는 9비트라 16진수 자릿수(4비트)와 경계가 맞지 않는다. (VA>>39)&0x1FF = 0x0FE, (VA>>30)&0x1FF = 0x048, (VA>>21)&0x1FF = 0x1A2, (VA>>12)&0x1FF = 0x167, VA&0xFFF = 0xABC다. 16진수 자릿수대로 끊는 실수(첫 번째 보기)가 가장 흔하다. 위의 워크 위젯에 넣어 확인해 보자.
4단계 x86-64에서 사용자 프로그램이 0x0000_8000_0000_0000을 역참조했다. 어떤 일이 일어나는가?
비트 47이 1인데 비트 63:48이 0이므로 canonical 규칙 위반이다. 페이지 워크 전에 #GP가 발생한다. 5단계(LA57)에서는 같은 주소가 canonical이라 정상적으로 워크를 시작한다.
워크 중 PD 엔트리의 비트 7(PS)이 1이었다. 옳은 설명은?
PDE의 PS=1은 2MB 페이지다. 워크는 여기서 끝나고 VA[20:0]이 오프셋이다. 1GB는 PDPTE의 PS=1이다. 비트 7이 PAT인 것은 4KB PTE에서다.
ARM64에서 16KB granule, 48비트 VA를 쓰면 최상위 레벨(L0) 테이블의 엔트리 수는?
오프셋 14비트, 레벨당 11비트다. 48 − 14 = 34비트를 11비트씩 나누면 11 × 3 = 33, 남는 1비트가 L0이므로 2개다. 그래서 47비트 VA로 줄이면 L0가 사라져 3단계가 된다.
5단계를 지원하지 않는 CPU에서 x86-64 Linux가 4단계로 동작할 때, Linux의 다섯 레벨 중 접히는(fold) 것은?
pgd = PML4, pud = PDPT, pmd = PD, pte = PT가 되고, 2017년 5단계 지원 때 끼워 넣은 p4d가 접힌다. x86-64는 이 판단을 pgtable_l5_enabled()로 런타임에 한다. 32비트 non-PAE x86(2단계)이라면 p4d, pud, pmd가 모두 접힌다.
PostgreSQL 서버에서 /proc/meminfo의 PageTables가 30GB까지 커졌다. 원인과 대응으로 가장 적절한 것은?
페이지 테이블은 물리 페이지를 공유해도 프로세스마다 따로 있다. 공유 메모리 크기 × 프로세스 수 × (8B/4KB)만큼 늘어난다. 2MB huge page로 PT 레벨을 없애거나(1/512), 프로세스 수를 줄이는 것이 정석이다. 5단계로 늘어나는 것은 상위 테이블 몇 장뿐이라 원인이 아니다.
