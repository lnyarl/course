메모리 계층과 프로세스 주소 공간

CPU는 1나노초에 수 개의 명령을 끝내지만, DRAM은 한 번 읽는 데 100나노초 가까이 걸린다. 메모리 관리의 거의 모든 설계는 이 속도 격차를 숨기고, 수많은 프로세스가 같은 물리 메모리를 안전하게 나눠 쓰게 만드는 문제에서 나온다. 이 장은 코스 전체의 지도를 그린다.

학습 목표

  • 레지스터부터 SSD까지 각 계층의 지연 시간·용량을 자릿수 단위로 기억하고, 그 격차가 설계에 주는 의미를 설명한다.
  • 시간·공간 지역성을 캐시 라인 단위로 설명하고, 배열 순회 순서가 성능을 수십 배 바꾸는 이유를 보인다.
  • 물리 주소와 가상 주소를 구분하고, 같은 가상 주소가 프로세스마다 다른 물리 위치를 가리키는 원리를 이해한다.
  • x86-64 Linux 프로세스의 주소 공간 배치(text/data/bss/heap/mmap/stack/kernel)와 canonical 주소 구멍을 설명하고 /proc/self/maps를 읽는다.
  • 커널/유저 분리와 MMU의 역할을 개괄하고, 이후 장(페이징·TLB·페이지 폴트)과 연결한다.

1. 메모리 관리가 푸는 네 가지 문제

운영체제의 메모리 관리는 서로 얽힌 네 가지 요구를 동시에 만족시켜야 한다. 이후 모든 장은 이 네 가지 중 하나 이상을 더 잘 풀려는 시도다.

요구내용대표 메커니즘 (등장하는 장)
속도느린 대용량 메모리를 빠른 소용량 메모리처럼 보이게 한다.캐시 계층, TLB(04), 페이지 캐시(11), Huge Page(13)
격리·보호한 프로세스가 다른 프로세스나 커널의 메모리를 읽거나 망가뜨리지 못하게 한다.base/limit(02), 페이지 테이블 권한 비트(03), NX·SMAP·KPTI(14)
추상화각 프로세스에게 0번지부터 시작하는, 크고 연속된, 자기만의 주소 공간을 준다.가상 주소, 페이징(03·05), 요구 페이징(06)

이 요구들은 자주 충돌한다. 격리를 강화하면(예: KPTI) 시스템 콜마다 페이지 테이블을 바꿔야 해서 느려진다. 효율을 위해 overcommit하면 결국 OOM killer가 프로세스를 죽여야 하는 순간이 온다. 전문가는 각 메커니즘이 무엇을 사고 무엇을 지불하는지를 말할 수 있어야 한다.

2. 메모리 계층: 수치로 보기

빠른 메모리는 비싸고 작으며, 크고 싼 메모리는 느리다. SRAM 셀은 트랜지스터 6개로 1비트를 저장하지만 DRAM 셀은 트랜지스터 1개와 커패시터 1개로 충분하다. 그 대신 DRAM은 주기적으로 리프레시해야 하고, 행(row)을 열고 감지 증폭하는 데 수십 ns가 걸린다. 그래서 컴퓨터는 서로 다른 기술을 층층이 쌓는다.

아래 표는 2020년대 x86-64 데스크톱/서버 CPU의 대략적인 수치다. 세대·제품마다 다르므로 정확한 값보다 자릿수를 기억하는 것이 중요하다.

선형 스케일로 바꾸면 SSD와 HDD를 제외한 모든 막대가 사실상 0이 된다. 이것이 핵심이다. DRAM 접근은 L1의 약 100배, SSD 접근은 DRAM의 약 500~1000배다. 그래서 다음 두 가지 결론이 나온다.

  1. 캐시 미스는 수백 사이클을 버린다. 현대 CPU는 비순차 실행(out-of-order)으로 일부를 가리지만, 포인터를 따라가는 코드(링크드 리스트, 트리)는 다음 주소를 알 수 없으므로 미스 지연을 그대로 맞는다.
  2. 디스크로 가는 페이지 폴트(major fault)는 수십만 사이클이다. 이 시간이면 CPU는 다른 프로세스를 실행하는 편이 낫다. 그래서 페이지 폴트 처리 중 프로세스는 잠들고 스케줄러가 개입한다(06장). 스래싱(08장)이 시스템 전체를 멈춘 듯 보이게 하는 이유도 이것이다.
현업에서: "메모리는 충분한데 왜 느리지?" CPU 사용률 100%가 곧 "계산 중"이라는 뜻은 아니다. perf stat -e cycles,instructions,cache-misses로 IPC(instructions per cycle)를 보면, 메모리에 묶인 코드는 IPC가 0.2~0.5 수준까지 떨어진다. CPU가 대부분의 사이클을 DRAM을 기다리며 보낸다는 뜻이다. "CPU 바운드처럼 보이는 메모리 바운드" 문제는 아주 흔하다.

3. 지역성과 캐시 라인

계층 구조가 동작하는 이유는 프로그램이 지역성(locality)을 갖기 때문이다.

  • 시간 지역성(temporal): 방금 접근한 데이터는 곧 다시 접근할 가능성이 크다. 루프 변수, 스택 꼭대기, 자주 호출되는 함수 코드가 그렇다.
  • 공간 지역성(spatial): 방금 접근한 주소 근처를 곧 접근할 가능성이 크다. 배열 순차 순회, 명령어 순차 실행이 그렇다.

하드웨어는 공간 지역성을 이용하려고 바이트 하나가 아니라 캐시 라인(x86-64와 대부분의 ARM64 코어에서 64바이트) 단위로 데이터를 가져온다. int 하나를 읽으면 옆의 15개 int가 함께 딸려 온다. 이 원리는 계층마다 반복된다. OS는 디스크에서 바이트가 아니라 페이지(보통 4 KB) 단위로 읽고, 파일을 순차로 읽으면 미리 읽기(readahead)까지 한다.

행 우선 vs 열 우선 순회

C/C++는 2차원 배열을 행 우선(row-major)으로 저장한다. a[i][j]와 a[i][j+1]은 메모리에서 이웃이지만, a[i][j]와 a[i+1][j]는 한 행 크기만큼 떨어져 있다. Fortran, MATLAB, Julia, 그리고 NumPy의 order='F' 배열은 열 우선이다.

// 빠름: 메모리 순서대로 접근 (stride = 4B)
for (i = 0; i < N; i++)
  for (j = 0; j < N; j++)  sum += a[i][j];

// 느림: 매 접근이 한 행(N*4B)씩 점프
for (j = 0; j < N; j++)
  for (i = 0; i < N; i++)  sum += a[i][j];
배열 순회와 캐시 라인 시뮬레이터
8×16 배열을 순회한다. 같은 색 띠(청록 테두리로 시작)가 하나의 64 B 캐시 라인이다. 캐시는 완전 연관·LRU로 단순화했다. 초록=히트, 빨강=미스. 캐시 용량을 배열이 차지하는 라인 수보다 작게 하고 열 우선으로 돌려 보라.

int 배열, 캐시 4라인일 때 행 우선은 128번 중 8번만 미스(히트율 93.75%)다. 열 우선은 128번 모두 미스다. 열 하나를 내려가는 동안 8개 행 = 8개 라인을 건드리는데 캐시에는 4개만 들어가므로, 다음 열로 돌아왔을 때 필요한 라인은 이미 쫓겨나 있다. 캐시 용량을 8라인으로 늘리면 열 우선도 8번만 미스가 난다. 작업 집합(working set)이 캐시에 들어가느냐가 성능의 경계선이다. 이 개념은 08장에서 페이지 단위로 그대로 다시 나온다.

실제 시스템에서는 더 나쁘다 int a[4096][4096]를 열 우선으로 돌면 매 접근이 16 KB씩 점프한다. 캐시 라인뿐 아니라 매번 다른 4 KB 페이지를 건드리므로 TLB 미스(04장)도 함께 터진다. 하드웨어 프리페처는 일정한 stride를 감지하지만 대체로 4 KB 페이지 경계를 넘어서는 프리페치하지 않는다. 또 실제 캐시는 완전 연관이 아니라 집합 연관(set-associative)이라, 2의 거듭제곱 stride는 같은 집합으로만 몰려 충돌 미스까지 일으킨다(13장). 행렬 곱 최적화에서 루프 순서 교환(loop interchange)과 타일링(blocking)이 기본인 이유다.

4. 물리 주소와 가상 주소

물리 주소(physical address)는 메모리 버스에 실제로 실리는 주소, 곧 DRAM 칩의 특정 셀을 가리키는 번호다. 논리 주소(logical address)는 CPU가 실행하는 명령이 만들어 내는 주소다. 가상 메모리를 쓰는 시스템에서는 논리 주소를 흔히 가상 주소(virtual address)라 부른다. (x86 문서는 세그먼트 변환 전을 logical, 후를 linear address로 구분하지만, 세그멘테이션을 사실상 쓰지 않는 64비트 모드에서는 셋이 거의 같다. 02장 참고.)

프로그램의 mov rax, [0x601040]에서 0x601040은 가상 주소다. CPU의 MMU(Memory Management Unit)가 이를 물리 주소로 바꾼다. 변환 규칙은 OS가 만든 페이지 테이블에 들어 있고, 프로세스마다 다른 테이블을 쓴다. 그래서 두 프로세스가 똑같은 가상 주소를 써도 서로 다른 물리 메모리에 닿는다.

가상 주소라는 간접 계층 하나로 얻는 것이 많다.

  • 격리: 페이지 테이블에 없는 물리 메모리는 표현할 방법 자체가 없다. 남의 메모리를 가리키는 주소를 만들 수 없다.
  • 재배치: 프로그램은 자기가 물리 메모리 어디에 놓일지 몰라도 된다. OS는 아무 빈 프레임에나 페이지를 둘 수 있다(외부 단편화 해결, 02·03장).
  • 크기 추상화: 가상 공간은 물리 메모리보다 클 수 있다. 실제로 쓰는 페이지만 물리 프레임을 차지하고 나머지는 디스크에 있거나 아직 존재하지 않는다(06장).
  • 공유: 여러 페이지 테이블이 같은 프레임을 가리키게 하면 공유 라이브러리, 공유 메모리, COW(11장)가 공짜로 생긴다.
심화: 커널은 물리 주소를 어떻게 다루나

커널 코드도 가상 주소로 실행된다. 페이징이 켜진 뒤에는 CPU가 내는 모든 메모리 접근이 변환을 거치므로 커널도 예외가 아니다. Linux x86-64는 물리 메모리 전체를 커널 가상 공간의 한 구간(direct map, 시작 주소는 page_offset_base, KASLR로 무작위화)에 선형으로 매핑해 둔다. 그래서 물리 주소 p를 __va(p) = p + PAGE_OFFSET으로 바로 접근할 수 있다. 반대 방향은 __pa()다.

장치는 또 다르다. DMA를 하는 장치는 CPU의 MMU를 거치지 않는다. 그래서 IOMMU(Intel VT-d, AMD-Vi, ARM SMMU)라는 장치용 MMU가 따로 있고, 장치가 보는 주소는 "버스 주소/IOVA"라 부른다.

5. 프로세스 주소 공간 레이아웃

x86-64 Linux에서 4단계 페이징을 쓸 때 가상 주소는 64비트 레지스터에 담기지만 실제로 의미 있는 비트는 하위 48비트다. 그중 아래 절반(128 TiB)은 유저 공간, 위 절반(128 TiB)은 커널 공간이고, 그 사이 거대한 영역은 쓸 수 없는 non-canonical 구멍이다. 그림의 각 영역을 눌러 보라 (크기 비율은 무시했다).

왜 이런 배치인가

  • 스택은 위에서 아래로, 힙은 아래에서 위로: 두 가변 영역이 가운데 빈 공간을 함께 나눠 쓰게 하려는 고전적 설계다. 64비트에서는 공간이 넉넉해서 의미가 줄었지만 관례로 남았다.
  • 0번지 근처는 비워 둔다: NULL 역참조를 즉시 잡기 위해서다. Linux는 vm.mmap_min_addr(기본 65536) 아래는 일반 프로세스가 매핑하지 못하게 막는다. 커널의 NULL 역참조 버그를 유저가 0번지에 코드를 깔아 악용하던 공격을 막는 목적도 있다.
  • 모든 시작 주소는 무작위: ASLR이 스택, mmap 기준점, 힙 시작, PIE 실행 파일의 로드 주소를 실행할 때마다 바꾼다(14장). cat /proc/sys/kernel/randomize_va_space가 2면 전부 켜진 상태다.

canonical 주소와 47비트 구멍

4단계 페이징에서 x86-64는 가상 주소의 비트 63~47이 모두 같아야(비트 47의 부호 확장) 유효한 canonical 주소로 인정한다. 그래서 유효한 주소는 0x0000000000000000~0x00007fffffffffff와 0xffff800000000000~0xffffffffffffffff 두 덩어리뿐이다. 그 사이 주소에 접근하면 페이지 폴트가 아니라 일반 보호 예외(#GP)가 난다. Linux에서는 둘 다 결국 SIGSEGV지만, 커널 로그와 원인 분석 방법이 다르다.

왜 구멍을 남겼을까? 하드웨어가 모든 64비트를 변환하려면 페이지 테이블 단계가 더 필요하고 TLB 태그도 길어진다. 256 TiB면 당분간 충분하니 48비트만 쓰되, 나머지 비트를 "아무 값이나 허용"하지 않고 반드시 부호 확장하게 강제했다. 상위 비트에 몰래 태그를 넣는 소프트웨어가 퍼지면 나중에 주소 공간을 넓힐 수 없기 때문이다. 실제로 Intel은 이후 5단계 페이징(LA57, 57비트)을 추가했고, 포인터 태깅은 별도 기능(Intel LAM, ARM TBI/MTE)으로 공식 지원한다.

canonical 주소 판정기
64비트 주소(16진수)를 입력하라. 4단계(48비트) 또는 5단계(57비트) 페이징 기준으로 부호 확장 규칙을 검사한다.
예시:
디버깅 팁 크래시 덤프에서 0xdead000000000100, 0x6b6b6b6b6b6b6b6b 같은 값을 역참조하다 #GP가 났다면, 해제된 객체를 다시 쓴(use-after-free) 흔적일 가능성이 크다. Linux 커널은 LIST_POISON1(0xdead000000000100), SLUB 디버그의 해제 표시 바이트(0x6b) 같은 값을 일부러 non-canonical이 되게 골라 둔다. 그래야 잘못 쓰면 바로 터진다.

7. 커널/유저 분리

커널 공간은 모든 프로세스의 주소 공간 위쪽에 똑같이 매핑되어 있다. 시스템 콜이나 인터럽트로 커널에 들어갈 때 페이지 테이블(CR3)을 바꾸지 않고 바로 커널 코드와 데이터를 쓰기 위해서다. 커널 주소에 접근할 수 있는지는 CPU의 현재 특권 수준과 페이지 테이블 엔트리의 U/S 비트가 결정한다.

  • x86-64: 특권 수준(CPL)은 ring 0(커널)과 ring 3(유저)만 쓴다. 커널 페이지는 U/S=0(supervisor)이다. ring 3에서 접근하면 페이지 폴트가 나고, 커널은 이를 SIGSEGV로 바꿔 보낸다.
  • ARM64: 특권 수준은 EL0(유저)과 EL1(커널)이다. 페이지 테이블 기준 레지스터가 둘(TTBR0_EL1=하위 유저 공간, TTBR1_EL1=상위 커널 공간)이라 분리가 하드웨어 구조에 녹아 있다.
  • 유저→커널 진입은 정해진 문으로만 가능하다. x86-64의 syscall 명령은 진입 주소를 MSR(IA32_LSTAR)에서 읽는다. 그래서 유저가 커널 안의 임의 위치로 점프할 수 없다.

커널이 반대로 유저 메모리를 실수로 실행하거나 접근하는 것도 위험하다. 공격자가 유저 공간에 깔아 둔 코드·데이터로 커널을 속일 수 있기 때문이다. 그래서 x86에는 SMEP(커널 모드에서 유저 페이지 실행 금지)와 SMAP(커널 모드에서 유저 페이지 접근 금지, copy_from_user() 같은 함수 안에서만 stac/clac로 잠시 허용)가 있다. ARM64의 대응 기능은 PXN과 PAN이다.

Meltdown과 KPTI 2018년 Meltdown 취약점은 U/S=0인 커널 페이지라도 투기적 실행 중에는 내용을 읽어 캐시에 흔적을 남길 수 있음을 보였다. 대응책 KPTI(Kernel Page-Table Isolation)는 유저 모드용 페이지 테이블에서 커널 매핑을 거의 다 빼 버린다. 대가로 시스템 콜마다 CR3를 바꾼다. PCID가 없으면 그때마다 TLB가 비워져 시스템 콜이 많은 워크로드가 눈에 띄게 느려졌다. "모든 프로세스에 커널을 매핑한다"는 오래된 설계 결정이 보안 때문에 흔들린 사례다(14장).

32비트 x86 Linux는 4 GB 공간을 기본 3 GB 유저 / 1 GB 커널로 나눴다. 커널이 물리 메모리를 1 GB 창(그중 direct map은 약 896 MB)으로만 볼 수 있어 "highmem"이라는 복잡한 우회책이 필요했다. 64비트에서는 공간이 넉넉해 이런 문제가 사라졌다. 이것이 서버가 일찍 64비트로 옮겨 간 실질적인 이유 중 하나다.

8. MMU의 역할 개괄

MMU는 CPU 안에서 모든 메모리 접근마다 가상→물리 변환과 권한 검사를 수행하는 하드웨어다. 이 코스의 개론 파트는 사실상 이 그림을 한 칸씩 확대해 가는 과정이다.

역할 분담을 정리하면 이렇다.

  1. 빠른 경로(하드웨어만): TLB에 변환이 있으면 1사이클 안팎으로 끝난다. 대부분의 접근이 여기서 처리된다.
  2. 느린 경로(하드웨어 page walker): TLB 미스면 MMU가 CR3에서 시작해 메모리의 페이지 테이블을 따라 내려간다. x86-64와 ARM64는 이 탐색을 하드웨어가 한다. MIPS 같은 일부 아키텍처는 TLB 미스를 소프트웨어(OS 핸들러)가 처리했다.
  3. 예외 경로(OS): 엔트리가 없거나(present=0) 권한을 위반하면 페이지 폴트 예외를 일으킨다. 커널은 폴트 주소(x86에서는 CR2 레지스터)와 에러 코드를 보고 정당한 요청이면 페이지를 채워 넣는다(요구 페이징, COW). 부당한 요청이면 SIGSEGV를 보낸다.
설계 원칙: 메커니즘은 하드웨어, 정책은 소프트웨어 MMU는 "이 주소를 이 규칙대로 변환하고, 안 되면 알린다"만 한다. 어떤 페이지를 메모리에 둘지, 누구와 공유할지, 무엇을 쫓아낼지는 전부 OS가 정한다. 이 분리 덕분에 같은 하드웨어 위에서 Linux, Windows, 하이퍼바이저가 서로 전혀 다른 메모리 정책을 쓸 수 있다.

핵심 요약

  • 계층별 지연은 자릿수로 기억한다. L1 ~1 ns, DRAM ~100 ns, NVMe ~수십 µs, HDD ~ms. DRAM 미스는 수백 사이클, 디스크 폴트는 수십만 사이클을 쓴다.
  • 캐시는 64 B 라인 단위로 공간 지역성을 이용한다. 순회 순서와 작업 집합 크기가 캐시 용량을 넘는지가 성능을 수십 배 가른다.
  • CPU가 만드는 주소는 가상 주소이고, MMU가 프로세스별 페이지 테이블로 물리 주소로 바꾼다. 이 간접 계층에서 격리, 재배치, 크기 추상화, 공유가 나온다.
  • x86-64 Linux(4단계)는 하위 128 TiB를 유저, 상위 128 TiB를 커널로 쓴다. 그 사이 non-canonical 구멍에 접근하면 #GP가 난다. 유저 공간은 아래부터 NULL 보호 구간, text, data, bss, heap(↑), mmap(↓), stack(↓) 순이다.
  • /proc/PID/maps는 VMA 목록이고 p/s는 private(COW)/shared를 뜻한다. 실제 사용량은 maps 크기가 아니라 smaps의 RSS/PSS로 본다.
  • 커널은 모든 주소 공간에 공유 매핑되고 U/S 비트로 보호된다. Meltdown 이후에는 KPTI로 이 설계를 일부 되돌렸다.
  • MMU는 변환과 검사(메커니즘)를, OS는 테이블 작성과 폴트 처리(정책)를 맡는다.

확인 문제

1 ns를 1초로 늘리면 DRAM 접근 1회(~100 ns)는 사람 기준으로 어느 정도인가?
100 ns × 10⁹ = 100초 ≈ 1분 40초다. 같은 배율로 NVMe 읽기(~50 µs)는 약 14시간, HDD(~5 ms)는 약 2달이다. L1 히트(1초)와 비교하면 DRAM 미스가 얼마나 비싼지 체감된다.
int a[2048][2048]을 for j { for i { sum += a[i][j]; } }로 순회하면 느린 가장 직접적인 이유는?
한 행은 2048×4 B = 8 KB다. 열 방향 접근은 매번 새 64 B 라인을 가져오지만 그중 4 B만 쓴다. 열 하나는 2048개 라인(128 KB)을 건드려 L1(32~48 KB)을 넘으므로, 다음 열에서 필요한 이웃 원소는 이미 쫓겨나 있다. 8 KB stride라 매 접근이 새 4 KB 페이지이기도 해서 TLB 미스도 겹친다.
4단계 페이징 x86-64에서 유저 프로그램이 주소 0x0000800000000000을 읽으면?
비트 47이 1인데 비트 63~48이 0이라 부호 확장 규칙을 어긴다. 이런 주소는 변환 대상조차 아니어서 #GP가 발생한다. 유저 공간의 끝은 0x00007fffffffffff, 커널 공간의 시작은 0xffff800000000000이다.
static char buf[64 * 1024 * 1024];(초기화 없음)를 선언한 프로그램에 대해 맞는 설명은?
0으로 초기화되는 전역/static은 .bss에 들어간다. ELF 파일에는 크기만 적히고, 로더는 익명(0으로 채워진) 매핑을 만든다. 요구 페이징 덕분에 처음 건드린 페이지만 물리 프레임을 받는다(06장). 그래서 VSZ는 64 MB 늘지만 RSS는 거의 그대로다.
/proc/PID/maps에서 7f..-7f.. r--p 00215000 08:01 1838302 /usr/lib/x86_64-linux-gnu/libc.so.6 줄의 p가 뜻하는 것은?
p는 MAP_PRIVATE, s는 MAP_SHARED다. 이 줄은 원래 쓰기 가능했다가 재배치가 끝난 뒤 mprotect로 읽기 전용이 된 RELRO 구간이다. 물리 메모리에 올라와 있는지는 maps가 아니라 smaps의 Rss나 /proc/PID/pagemap으로 봐야 한다.
두 프로세스가 같은 가상 주소 0x601040에 서로 다른 값을 저장하고 있을 수 있는 이유로 가장 정확한 것은?
가상→물리 변환 규칙은 프로세스별 페이지 테이블에 있다. 스케줄러가 다른 프로세스로 전환할 때 CR3(ARM64는 TTBR0_EL1)를 그 프로세스의 테이블 루트로 바꾼다. 그래서 같은 가상 주소가 다른 물리 프레임으로 간다.
