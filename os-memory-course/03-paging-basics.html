개론 · Chapter 03

페이징과 주소 변환

02장의 모든 문제(외부 단편화, 압축, 연속 할당)는 "프로세스가 물리적으로 연속이어야 한다"는 가정에서 나왔다. 페이징은 이 가정을 버린다. 주소 공간을 같은 크기의 조각으로 자르고, 조각마다 물리 위치를 따로 기록한다. 이 장에서는 그 기록, 곧 페이지 테이블 하나가 어떻게 생겼고 어떤 비용을 치르는지 비트 단위로 해부한다.

학습 목표

  • 페이지·프레임·페이지 테이블의 관계를 설명하고, 주소를 VPN과 오프셋으로 나누는 비트 연산을 손으로 할 수 있다.
  • 단일 레벨 페이지 테이블로 가상 주소를 물리 주소로 변환하고, 무효 페이지·권한 위반에서 어떤 페이지 폴트(에러 코드)가 나는지 판정한다.
  • x86-64 PTE의 실제 비트 배치(P, R/W, U/S, PWT, PCD, A, D, PAT, G, PFN, PK, XD)와 각 비트를 누가 왜 쓰는지 안다.
  • 페이지 테이블 크기를 계산해 단일 레벨 구조가 64비트에서 불가능한 이유를 보이고, 페이지 크기 트레이드오프를 설명한다.
  • 공유 라이브러리 페이지 공유의 원리와, 역 페이지 테이블·해시 페이지 테이블의 장단점을 안다.

1. 페이지와 프레임

가상 주소 공간을 고정 크기 페이지(page)로, 물리 메모리를 같은 크기의 프레임(frame, page frame)으로 자른다. 프로세스의 각 페이지는 아무 빈 프레임에나 들어갈 수 있다. 어느 페이지가 어느 프레임에 있는지는 프로세스별 페이지 테이블에 적는다.

이 구조에서 얻는 것을 02장과 비교해 보자.

  • 외부 단편화 없음: 모든 빈 프레임은 똑같이 쓸모 있다. 빈 프레임 n개면 n페이지짜리 요청을 반드시 채울 수 있다. 압축이 필요 없다.
  • 부분 적재: 페이지마다 "메모리에 있음/없음"을 표시할 수 있다. 프로세스 전체가 아니라 필요한 페이지만 올리면 된다(요구 페이징, 06장).
  • 페이지 단위 보호·공유: 페이지마다 권한을 따로 둘 수 있고, 두 테이블이 같은 프레임을 가리키게 하면 공유된다(8절).
  • 대가: 모든 메모리 접근에 변환이 필요하다(성능 → TLB, 04장). 테이블 자체가 메모리를 먹는다(크기 → 다단계, 05장). 마지막 페이지에 내부 단편화가 생긴다(7절).

2. 주소를 VPN | offset으로 자르기

페이지 크기가 2k바이트면 가상 주소의 하위 k비트는 페이지 안의 위치(오프셋)다. 나머지 상위 비트가 가상 페이지 번호(VPN)다. 페이지 크기를 2의 거듭제곱으로 정하는 이유가 여기에 있다. 나눗셈과 나머지가 비트 자르기로 바뀌어 하드웨어가 사실상 공짜로 계산한다.

VPN    = VA >> k                 // VA / 2^k
offset = VA & ((1 << k) - 1)     // VA % 2^k
PA     = (PFN << k) | offset     // 오프셋은 변환 없이 그대로 복사

변환되는 것은 VPN뿐이다. 오프셋은 가상 주소에서 물리 주소로 그대로 복사된다. 4 KB 페이지라면 주소의 하위 12비트(16진수 마지막 세 자리)는 가상이든 물리든 같다. 디버깅할 때 아주 유용한 사실이다.

3. 단일 레벨 페이지 테이블 변환

가장 단순한 페이지 테이블은 VPN으로 인덱싱하는 배열 하나다. 테이블의 물리 시작 주소는 PTBR(page-table base register)에 있다. x86에서는 CR3, ARM64에서는 TTBR0_EL1/TTBR1_EL1이 이 역할을 한다(실제로는 다단계 테이블의 루트를 가리킨다, 05장). 문맥 교환 때 OS는 PTBR만 바꾸면 주소 공간 전체가 바뀐다.

아래 애니메이션은 16비트 주소, 4 KB 페이지(VPN 4비트 + 오프셋 12비트), 4바이트 PTE, 20비트 물리 주소를 쓰는 작은 시스템이다.

CPU가 load [0x3A7C]를 실행할 때 하드웨어가 하는 일. 메모리 접근이 몇 번 일어나는지 세어 보라.
메모리 접근이 두 배가 된다 변환에 PTE를 읽는 메모리 접근(①)이 하나 더 필요하다. 데이터 접근(②)까지 합치면 모든 load/store가 두 번의 메모리 접근이 된다. 명령어 인출도 마찬가지다. 그대로라면 프로그램이 절반 속도로 돈다. 해결책은 최근 변환을 캐싱하는 TLB(04장)다. 다단계 테이블(05장)에서는 접근 ①이 4~5번으로 늘어나므로 TLB 없이는 아예 쓸 수 없다.

4. 직접 변환해 보기: 유효/무효와 페이지 폴트

PTE에는 프레임 번호만이 아니라 "이 매핑이 지금 유효한가(P, present)"와 "어떤 접근을 허용하는가(R/W, U/S, NX)"가 함께 들어 있다. MMU는 변환과 동시에 이 비트들을 검사한다. 조건이 맞지 않으면 페이지 폴트(#PF) 예외를 일으킨다. 이때 x86은 원인을 담은 에러 코드를 스택에 넣고, 폴트를 일으킨 가상 주소를 CR2에 넣는다.

0P페이지는 있었으나 권한 위반 (0이면 not-present)
1W/R쓰기 접근이었다
2U/S유저 모드에서 일어났다

    변환을 눌러라.

    "페이지 폴트 = 오류"가 아니라는 점이 중요하다. not-present 폴트의 대부분은 정상적인 사건이다. 아직 할당하지 않은 페이지(요구 페이징), 스왑된 페이지, COW 페이지를 커널이 처리한 뒤 명령을 다시 실행한다. 커널은 VMA 목록(01장의 maps)을 보고 정당한 접근인지 판단한다. 해당 주소에 VMA가 없거나 VMA 권한에 맞지 않을 때만 SIGSEGV를 보낸다. 그래서 위 변환기의 "스왑된 페이지" 폴트는 실제 시스템에서는 디스크에서 읽어 오는 major fault로 처리되고, 프로그램은 눈치채지 못한다(06장).

    현업 디버깅: 커널 로그 읽기 유저 프로세스가 죽으면 커널 로그에 segfault at 10 ip 000055d... sp 00007ffc... error 4 in app[55d...+1000] 같은 줄이 남는다. at 10은 CR2(폴트 주소, NULL+0x10이니 구조체 필드 접근), error 4는 0b100이다. 유저 모드(U=1)의 읽기(W=0)이고 not-present(P=0)다. error 6(유저 쓰기, not-present), error 7(유저 쓰기, 권한 위반: 읽기 전용 페이지에 쓰기), error 15도 외워 둘 만하다. 로그의 값은 16진수라서 0x15 = 0b10101, 곧 유저 명령 인출의 권한 위반(NX 페이지 실행)이다.

    5. PTE의 구조: x86-64 실제 비트

    x86-64의 PTE는 8바이트(64비트)다. 4 KB 페이지를 가리키는 마지막 단계 PTE의 배치는 Intel SDM Vol.3 4장 "4-level paging" 표에 정의되어 있다. 비트를 눌러 설명을 보고, 값을 바꿔(클릭하면 토글) 해석을 확인하라.

    x86-64 PTE 비트 다이어그램 (4 KB 페이지)
    비트를 누르면 0/1이 바뀌고 해당 필드 설명이 나온다. 16진수 값을 직접 넣거나 예시를 고를 수도 있다. MAXPHYADDR(물리 주소 폭)는 52로 가정했다. 실제 CPU는 39~52비트이고, 그 위 비트 ~51은 예약(0이어야 함)이다.

    0P (Present)OS0이면 나머지 비트는 하드웨어가 무시한다. 그래서 OS는 P=0인 PTE의 나머지 63비트에 스왑 위치(swap type + offset)를 적어 둔다(06장).
    1R/WOS0이면 읽기 전용. COW는 공유 페이지를 R/W=0으로 만들어 두고 쓰기 폴트를 잡는 트릭이다(11장).
    2U/SOS1이면 유저 접근 허용. 커널 매핑은 0이다.
    3, 4, 7PWT, PCD, PATOS세 비트가 PAT MSR의 항목을 골라 메모리 타입(WB, WC, UC 등)을 정한다. 장치 메모리(MMIO)는 캐시하면 안 되므로 UC, 프레임버퍼는 WC를 쓴다.
    5A (Accessed)하드웨어가 1로, OS가 0으로접근이 일어나면 MMU가 세운다. OS는 주기적으로 지우고 다시 섰는지 보며 "최근 사용"을 추정한다. 페이지 교체(Clock, LRU 근사)의 재료다(07장).
    6D (Dirty)하드웨어가 1로, OS가 0으로쓰기가 일어나면 세운다. 교체할 때 D=0이면 디스크 사본과 같으므로 그냥 버린다. D=1이면 먼저 써야 한다(write-back).
    8G (Global)OSCR3를 바꿔도 TLB에서 지우지 않는다. 모든 주소 공간에 공통인 커널 매핑에 쓴다(04장).
    9–11, 52–58IgnoredOS하드웨어가 무시하므로 OS가 자유롭게 쓴다. Linux는 soft-dirty, userfaultfd 쓰기 보호 표시 등에 쓴다.
    12–51PFNOS물리 프레임 번호. 물리 주소 = PFN × 4096 + offset. 최대 52비트 물리 주소(4 PiB)까지 표현한다.
    59–62PKOSCR4.PKE=1이면 유저 페이지의 protection key(0~15). 권한은 PKRU 레지스터로 유저가 시스템 콜 없이 바꾼다(pkey_mprotect, 14장).
    63XD / NXOSIA32_EFER.NXE=1이면 1일 때 명령어 인출 금지. 스택·힙에 주입한 코드의 실행을 막는다(W^X, 14장).
    A/D 비트를 하드웨어가 세운다는 것의 의미 MMU는 TLB에 변환을 채울 때 A를, 처음 쓸 때 D를 메모리의 PTE에 원자적으로 기록한다. 그래서 OS가 A/D를 지울 때는 그 변환이 TLB에 남아 있지 않게 TLB를 무효화해야 한다. TLB에 "이미 A=1"로 캐시되어 있으면 하드웨어가 다시 세우지 않기 때문이다. 이 비용 때문에 Linux는 A 비트를 지울 때 TLB flush를 생략하기도 한다(정확도를 조금 포기). ARM64는 원래 A/D를 소프트웨어로 관리했다(Access Flag 폴트). ARMv8.1의 하드웨어 관리(HAFDBS)가 나온 뒤에야 x86처럼 하드웨어가 갱신한다.

    6. 페이지 테이블은 얼마나 큰가

    단일 레벨 테이블은 주소 공간의 모든 가상 페이지에 대해 엔트리를 가져야 한다. 대부분이 쓰이지 않아도 마찬가지다. VPN으로 바로 인덱싱하는 배열이니 중간을 비울 수 없다. 크기 = 2(주소 비트 − 오프셋 비트) × PTE 크기다.

    페이지 테이블 크기 계산기
    단일 레벨 테이블이 프로세스마다 얼마를 차지하는지, 실제로 쓰는 메모리에 필요한 PTE만 따지면 얼마인지 비교한다.
    PTE 개수
    프로세스당 테이블
    전체 프로세스
    실사용분 PTE만

    32비트·4 KB·4 B PTE면 프로세스당 4 MiB다. 1990년대 기준으로도 부담스럽지만 불가능하지는 않다. 48비트·8 B PTE면 프로세스당 512 GiB다. 물리 메모리보다 큰 테이블을 연속으로 둘 수는 없다. 반면 실제로 쓰는 300 MiB를 매핑하는 데 필요한 PTE는 600 KiB 남짓이다. 주소 공간은 희소(sparse)하다. 아래에 코드·데이터·힙, 위에 스택·라이브러리가 있고 가운데 수십 TiB는 비어 있다(01장).

    해결 방향은 세 가지다.

    1. 다단계(계층) 페이지 테이블: 테이블 자체를 페이징해서, 빈 구간에 해당하는 하위 테이블은 아예 만들지 않는다. x86-64, ARM64, RISC-V가 모두 이 방식이다(05장).
    2. 해시 페이지 테이블: 쓰는 VPN만 해시 테이블에 넣는다(9절).
    3. 역 페이지 테이블: 가상 페이지가 아니라 물리 프레임마다 엔트리 하나를 둔다. 크기가 물리 메모리에 비례한다(9절).

    7. 페이지 크기 트레이드오프와 내부 단편화

    페이징에는 외부 단편화가 없지만 내부 단편화는 있다. 영역 크기가 페이지 크기의 배수가 아니면 마지막 페이지의 남는 부분이 낭비된다. 영역당 평균 낭비는 페이지 크기의 절반이다. 그럼 페이지는 작을수록 좋을까?

    폴트 1회 비용, I/O 단위작다크다(2 MB를 0으로 채우거나 읽어야 함)
    보호·공유·COW 단위세밀하다거칠다(1바이트를 써도 2 MB를 복사)
    물리 연속성 요구없다페이지 크기만큼 연속 프레임이 필요하다(02장 단편화 문제가 돌아옴)
    페이지 크기별 낭비와 TLB 도달 범위
    프로세스의 영역 크기 목록(바이트, KB/MB 접미사 허용)을 넣으면 페이지 크기별로 필요한 페이지 수, 내부 단편화, 64엔트리 TLB가 덮는 범위를 계산한다.

    결과를 보면 4 KB에서 내부 단편화는 1%도 안 된다. 2 MB 페이지를 모든 영역에 쓰면 낭비가 실사용량의 몇 배로 커진다. 반대로 64엔트리 TLB는 4 KB 페이지로 256 KB만 덮지만 2 MB 페이지로는 128 MB를 덮는다. 그래서 현대 시스템은 여러 페이지 크기를 섞는다. 기본은 4 KB로 두고, 크고 촘촘하게 쓰는 영역(DB 버퍼 풀, JVM 힙, VM 게스트 메모리)에만 huge page를 쓴다(Linux THP·hugetlbfs, 13장).

    아키텍처별 실제 페이지 크기
    • x86-64: 4 KB 기본, 2 MB와 1 GB huge page.
    • ARM64: 변환 granule로 4 KB, 16 KB, 64 KB 중 하나를 커널 빌드 시 고른다. Apple Silicon은 16 KB를 쓴다(그래서 Asahi Linux는 16 KB 커널이다). RHEL의 ARM64 커널은 한때 64 KB를 썼다.
    • Android: Android 15부터 16 KB 페이지 커널을 지원한다. 4 KB 정렬을 가정한 네이티브 라이브러리(ELF 세그먼트 정렬 4 KB)는 16 KB 커널에서 로드되지 않는다. 그래서 앱 개발자에게 -Wl,-z,max-page-size=16384로 다시 빌드하라는 요구가 생겼다. 페이지 크기는 ABI의 일부다.
    • 코드에서 페이지 크기를 4096으로 하드코딩하지 말고 sysconf(_SC_PAGESIZE)(셸에서는 getconf PAGESIZE)로 얻어야 하는 이유다.

    8. 보호와 공유

    페이징은 보호와 공유를 페이지 단위로 제공한다. 보호는 PTE의 권한 비트가 매 접근마다 검사되는 것으로 충분하다. 공유는 서로 다른 프로세스의 PTE가 같은 PFN을 가리키게 하면 된다.

    • 공유하려면 코드가 재진입 가능(reentrant)해야 한다. 실행 중에 자기 자신을 수정하지 않아야 하고, 그래서 R/W=0으로 매핑한다. 쓰기가 필요한 상태는 프로세스별 데이터 페이지에 둔다.
    • 공유 페이지가 프로세스마다 다른 가상 주소에 있어도 되려면 코드가 위치 독립적(PIC)이어야 한다(02장).
    • 메모리 사용량을 셀 때 공유 페이지를 어떻게 나눌지가 문제가 된다. RSS는 공유 페이지를 프로세스마다 통째로 세서 합하면 실제보다 커진다. PSS는 공유자 수로 나눠 세므로 합이 실제 사용량과 맞는다. 컨테이너나 다중 프로세스 서버(PostgreSQL, Chrome)의 메모리를 분석할 때 RSS 합계만 보면 크게 과대평가하게 된다.
    • 같은 원리로 공유 메모리(shm_open+mmap(MAP_SHARED))는 프로세스 간 통신이 되고, 커널의 제로 페이지는 아직 쓰지 않은 모든 익명 페이지의 읽기를 물리 프레임 하나로 처리한다.

    9. 역 페이지 테이블과 해시 페이지 테이블

    해시 페이지 테이블

    VPN을 해시해서 버킷을 찾고, 버킷의 체인에서 (VPN, PFN, next) 엔트리를 찾는다. 실제로 쓰는 페이지만 엔트리를 가지므로 희소한 64비트 주소 공간에 맞는다. 단점도 있다. 체인을 따라가는 메모리 접근이 예측 불가능하고, 해시 충돌이 성능을 흔들며, 인접 페이지끼리 캐시 지역성이 없다. 엔트리 하나가 연속된 여러 페이지(예: 16개)를 담당하게 하는 클러스터드 페이지 테이블은 지역성을 일부 되찾는 변형이다.

    역 페이지 테이블 (Inverted Page Table)

    시스템 전체에 테이블 하나를 두고, 물리 프레임마다 엔트리 하나를 둔다. 엔트리에는 "이 프레임을 어떤 프로세스의 어떤 가상 페이지가 쓰는가", 곧 (PID, VPN)를 적는다. 테이블 크기가 가상 주소 공간이 아니라 물리 메모리에 비례하므로 주소 공간이 아무리 커도 문제없다.

    장점단점
    역 페이지 테이블크기가 물리 메모리에 비례하고 시스템에 하나뿐이다. 64비트 공간에서도 작다.VPN으로 바로 인덱싱할 수 없어 검색(해시)이 필요하다. 프레임 하나에 (PID, VPN) 하나뿐이라 공유가 어렵다. 같은 프레임을 두 프로세스가 매핑하는 것을 직접 표현할 수 없다. 스왑된 페이지의 위치 등 "메모리에 없는 페이지" 정보는 별도 구조가 필요하다.
    실제로 쓴 시스템 PowerPC(IBM POWER)는 하드웨어 해시 페이지 테이블(HPT)을 쓴다. 이 테이블은 물리 메모리 크기에 비례해 잡히는 전역 테이블이라 역 페이지 테이블의 성격을 함께 갖는다. 공유 문제는 세그먼트로 푼다. 실효 주소를 먼저 세그먼트(SLB)로 전역 가상 주소(VSID 기반)로 바꾸므로, 두 프로세스가 같은 VSID를 쓰면 같은 HPT 엔트리를 공유한다. IA-64(Itanium)의 VHPT, UltraSPARC의 TSB도 해시 구조를 썼다. Linux는 아키텍처 독립 코드에서 항상 다단계 테이블 모델(pgd→p4d→pud→pmd→pte)을 쓰고, POWER에서는 이를 HPT에 반영하는 계층을 둔다. 최신 POWER9 이후는 다단계 형식의 Radix MMU도 지원해 Linux가 기본으로 쓴다. 역사적으로는 계층형이 이겼다. 하드웨어 page walker와 캐시 친화성, 공유의 단순함 덕분이다.

    핵심 요약

    • 페이징은 가상 페이지를 임의의 물리 프레임에 놓아 외부 단편화를 없앤다. 대가는 변환 비용, 테이블 메모리, 내부 단편화(평균 반 페이지)다.
    • 페이지 크기 2k이면 VA의 하위 k비트가 오프셋이고 상위가 VPN이다. 오프셋은 변환되지 않고 물리 주소로 그대로 간다.
    • 단일 레벨 변환: PTE 주소 = PTBR + VPN × PTE 크기, PA = PFN ≪ k | offset. TLB가 없으면 모든 접근이 두 번의 메모리 접근이 된다.
    • P=0이면 not-present 폴트, 권한(R/W, U/S, NX, SMEP/SMAP) 위반이면 protection 폴트다. x86은 원인을 에러 코드(P/W/U/RSVD/I/PK)로, 주소를 CR2로 알린다. not-present 폴트의 대부분은 정상 처리 대상이다.
    • x86-64 PTE: 0 P, 1 R/W, 2 U/S, 3 PWT, 4 PCD, 5 A, 6 D, 7 PAT, 8 G, 9–11 무시, 12–51 PFN, 52–58 무시, 59–62 PK, 63 XD. A/D는 하드웨어가 세우고 OS가 지운다.
    • 48비트·4 KB·8 B PTE의 단일 레벨 테이블은 프로세스당 512 GiB라 불가능하다. 희소한 주소 공간에는 다단계·해시·역 페이지 테이블이 필요하다.
    • 작은 페이지는 단편화와 보호 단위에, 큰 페이지는 테이블 크기와 TLB 도달 범위에 유리하다. 실제 시스템은 섞어 쓰고, 페이지 크기는 ABI의 일부다(16 KB Android/Apple).
    • 공유는 여러 PTE가 같은 PFN을 가리키는 것이다. 메모리 계산에는 RSS가 아니라 PSS를 써야 한다. 역 페이지 테이블은 작지만 공유와 검색이 어렵다.

    확인 문제

    32비트 가상 주소, 4 KB 페이지에서 VPN과 오프셋의 비트 수는?
    4 KB = 212이므로 오프셋 12비트, 나머지 32−12 = 20비트가 VPN이다. 가상 페이지는 220 = 약 100만 개다.
    4 KB 페이지, PTE[2]의 PFN이 0x7이다. 가상 주소 0x2ABC의 물리 주소는?
    VPN = 0x2ABC ≫ 12 = 2, offset = 0xABC. PA = (0x7 ≪ 12) | 0xABC = 0x7ABC. 오프셋(하위 세 자리)은 그대로다.
    x86-64 Linux에서 유저 프로그램이 읽기 전용(R/W=0)이지만 메모리에 있는(P=1) 페이지에 쓰다 죽었다. 커널 로그의 error 값은?
    P=1(권한 위반) + W=1(쓰기) + U=1(유저) = 0b111 = 7. 4는 유저 읽기·not-present, 6은 유저 쓰기·not-present, 커널 로그는 16진수로 찍으므로 error 15(0x15)는 유저 명령 인출·권한 위반(NX)이다. 단, 이 페이지가 COW 대상이면 커널이 사본을 만들어 정상 처리하므로 프로세스는 죽지 않는다.
    OS가 교체할 페이지를 고를 때 PTE의 D(dirty) 비트를 보는 이유는?
    D는 쓰기가 있었음을 뜻한다. 깨끗한(clean) 페이지는 버리기만 하면 되지만, 더러운(dirty) 페이지는 먼저 저장 장치에 써야 하므로 회수 비용이 크다. "최근 사용" 정보는 A(accessed) 비트가 준다.
    48비트 가상 주소, 4 KB 페이지, 8 B PTE의 단일 레벨 페이지 테이블 크기는?
    VPN = 48−12 = 36비트 → 236개 × 8 B = 239 B = 512 GiB. 프로세스마다 이만큼 필요하므로 불가능하다. 그래서 다단계 테이블을 쓴다(05장).
    역 페이지 테이블의 가장 큰 구조적 약점은?
    역 테이블은 프레임 → (PID, VPN) 방향이라 VPN → 프레임 조회에 해시 검색이 필요하다. 한 프레임에 매핑 하나만 기록되므로 공유 라이브러리 같은 다중 매핑이 어렵다. PowerPC는 세그먼트(VSID)로 이를 우회한다. 크기는 오히려 물리 메모리에 비례해 작다.
    ARM64에서 4 KB 대신 16 KB 페이지를 쓸 때 맞는 설명은?
    페이지가 4배 크면 TLB 엔트리 하나가 4배 범위를 덮고 테이블 단계도 줄일 수 있다. 대신 영역당 평균 낭비가 8 KB로 늘어난다. ELF 세그먼트가 4 KB로만 정렬된 라이브러리는 16 KB 커널에서 매핑할 수 없어, Android 15의 16 KB 전환에서 재빌드가 필요했다.
