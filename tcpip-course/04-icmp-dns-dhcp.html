4.1ICMP: IP의 오류 보고와 진단

ICMP(Internet Control Message Protocol, RFC 792)는 IP 위에 실리지만(Protocol=1) IP의 일부로 취급됩니다. 라우터나 호스트가 "패킷을 전달할 수 없었다"거나 "TTL이 만료됐다"를 출발지에 알리고, ping 같은 진단 도구의 바탕이 됩니다. 오류 메시지에는 원인 패킷의 IP 헤더 + 첫 8바이트(=TCP/UDP 포트 포함)가 실려, 수신 측이 어느 소켓의 문제인지 알 수 있습니다.

📌 ICMP 오류 메시지의 규칙

ICMP 오류에 대해 ICMP 오류를 보내지 않고(무한 루프 방지), 브로드캐스트/멀티캐스트 목적지나 첫 조각이 아닌 조각에 대해서도 보내지 않습니다. 또한 대부분의 OS는 ICMP 발신을 초당 수십 개로 rate-limit합니다 — traceroute에서 * * *가 간헐적으로 보이는 이유 중 하나입니다.

ping (애니메이션)

ping은 ICMP Echo Request(Type 8)에 식별자(프로세스 구분)와 시퀀스 번호, 그리고 보통 송신 타임스탬프를 데이터에 담아 보냅니다. 대상은 데이터를 그대로 복사해 Echo Reply(Type 0)로 돌려주고, 송신 측은 응답 수신 시각에서 데이터 안의 타임스탬프를 빼 RTT를 구합니다. 그래서 ping은 커널 시계 외에 별도 상태가 거의 필요 없습니다.

traceroute (애니메이션)

traceroute는 ICMP를 진단용으로 "악용"한 도구입니다. TTL을 1부터 하나씩 늘려 보내면, n번째 라우터에서 TTL이 0이 되어 그 라우터가 Time Exceeded를 돌려줍니다. 그 메시지의 출발지 IP가 곧 n번째 홉의 주소입니다. 목적지에 도달하면 다른 종류의 응답이 와서 끝을 알 수 있습니다.

$ traceroute -n 203.0.113.10
구현 차이

Linux/macOS traceroute: UDP를 33434부터 증가하는 포트로 보냄 → 목적지는 Port Unreachable(3/3)로 응답. Windows tracert와 traceroute -I: ICMP Echo 사용 → 목적지는 Echo Reply. -T(TCP SYN)는 방화벽 통과에 유리.

읽을 때 주의

① 각 홉은 독립적인 패킷으로 측정되므로 경로가 중간에 바뀔 수 있다(ECMP). ② 라우터가 ICMP 생성을 rate-limit하면 *가 나오지만 그 홉이 트래픽을 버리는 건 아니다. ③ 홉의 RTT가 다음 홉보다 클 수 있다 — 라우터의 제어 평면(CPU)이 느린 것뿐이다. ④ MPLS 구간은 TTL을 전파하지 않으면 홉이 숨는다.

4.2DNS: 이름을 주소로

DNS(Domain Name System, RFC 1034/1035)는 www.example.com 같은 이름을 IP 주소(및 다른 정보)로 바꾸는 분산 계층형 데이터베이스입니다. 이름은 오른쪽부터 읽습니다: 루트(.) → TLD(com) → 2단계(example) → 호스트(www). 각 단계는 다른 조직이 관리하며(위임, delegation), 이것이 DNS가 전 세계 규모로 확장되는 비결입니다.

이름 공간의 계층. 각 화살표는 NS 레코드에 의한 "위임"이다. 루트 서버는 13개 이름(a~m.root-servers.net)이지만 애니캐스트로 전 세계 1,900개 이상 인스턴스가 있다.

이름 해석 과정 (애니메이션)

클라이언트의 스텁 리졸버(OS 라이브러리)는 재귀 리졸버에게 "답을 끝까지 찾아서 줘"라고 재귀 질의를 보냅니다. 재귀 리졸버(ISP, 8.8.8.8, 1.1.1.1, 사내 DNS)는 루트부터 차례로 반복 질의를 하며 답을 찾고, 결과를 TTL 동안 캐시합니다.

💡 두 번째 질의가 빠른 이유

같은 리졸버에 mail.example.com을 물으면, 루트와 .com 질의는 건너뛰고(NS 레코드가 캐시에 있음) 권한 서버로 바로 갑니다. www.example.com을 다시 물으면 리졸버 캐시에서 즉시 답합니다. 캐시의 TTL은 권한 서버가 레코드마다 정하며(초 단위), TTL이 짧으면 변경이 빨리 퍼지지만 질의가 늘어납니다. 전환 작업 전에 TTL을 미리 줄여 두는 것이 운영의 기본 수칙입니다.

DNS 메시지 포맷

질의와 응답은 같은 형식을 씁니다. 12바이트 헤더 뒤에 Question / Answer / Authority / Additional 네 섹션이 옵니다. 보통 UDP 53번 포트를 쓰고, 응답이 크면 TCP로 전환합니다.

🔬 깊이 보기: UDP 512바이트 한계, EDNS(0), TCP 폴백

RFC 1035는 UDP DNS 메시지를 512바이트로 제한했습니다(당시 모든 호스트가 재조립을 보장하는 최소 IP 데이터그램 576바이트에서 유래). 응답이 더 크면 서버가 TC(Truncated) 비트를 세우고, 클라이언트는 TCP 53으로 다시 묻습니다. DNSSEC 서명이나 많은 A 레코드는 512를 쉽게 넘으므로, EDNS(0)(RFC 6891)가 OPT 의사 레코드로 "나는 4096바이트까지 받을 수 있다"를 광고하게 했습니다. 그러나 큰 UDP 응답은 IP 단편화를 유발하고(3장), 조각을 버리는 방화벽 때문에 응답이 사라지는 사고가 잦아, 2020년 "DNS Flag Day"에서 권장 EDNS 버퍼 크기를 1232바이트로 낮췄습니다(IPv6 최소 MTU 1280 − 헤더). "DNS는 UDP만 쓴다"고 하여 방화벽에서 TCP 53을 막는 것은 전형적인 운영 실수입니다.

🔬 깊이 보기: 캐시 포이즈닝과 소스 포트 무작위화

리졸버는 응답을 받으면 "내가 보낸 질의에 대한 답인가"를 16비트 트랜잭션 ID, 출발지/목적지 주소와 포트로 확인합니다. 2008년 Kaminsky 공격은 리졸버가 질의 중인 틈에 위조 응답을 수만 개 쏟아부어 ID를 맞히는 방식으로, 성공하면 리졸버 캐시에 가짜 NS/A가 들어가 그 도메인 전체가 납치됩니다. 대응은 ① 소스 포트 무작위화(16비트 ID × 16비트 포트 = 32비트 엔트로피), ② 0x20 대소문자 무작위화, ③ 근본적으로는 응답에 서명하는 DNSSEC. 위 애니메이션에서 질의마다 포트가 달라지는 것을 보세요.

4.3DHCP: 주소 자동 설정 (애니메이션)

막 부팅한 호스트는 IP 주소도, 게이트웨이도, DNS 서버도 모릅니다. DHCP(Dynamic Host Configuration Protocol, RFC 2131)는 이 "아무것도 모르는 상태"에서 설정을 받아오는 프로토콜이며, 그래서 브로드캐스트와 0.0.0.0 출발지 주소에 의존합니다. UDP 68(클라이언트) ↔ 67(서버). 네 단계의 머리글자를 따 DORA라 부릅니다.

📌 왜 Request도 브로드캐스트인가

Offer를 여러 서버가 보냈을 수 있습니다. 클라이언트는 하나를 골라 Request에 server identifier 옵션으로 명시하고 브로드캐스트합니다. 선택받지 못한 서버들도 이를 듣고 자기 Offer를 취소합니다. 그리고 아직 IP가 확정되지 않았으므로 유니캐스트를 쓸 수도 없습니다.

💡 임대(lease)와 갱신

주소는 영구가 아니라 임대입니다. 임대 시간의 50%(T1)에 클라이언트는 서버에 유니캐스트 Request로 갱신하고, 87.5%(T2)까지 실패하면 브로드캐스트로 아무 서버에게나 갱신을 시도하며, 만료되면 주소를 버리고 DORA를 다시 시작합니다. DHCP 옵션(RFC 2132)으로 서브넷 마스크(1), 라우터(3), DNS(6), 도메인(15), 임대 시간(51), PXE 부트 서버 등을 함께 받습니다.

🔬 깊이 보기: 서브넷을 넘는 DHCP — Relay Agent

브로드캐스트는 라우터를 못 넘으므로, 원칙적으로 서브넷마다 DHCP 서버가 필요합니다. 실제로는 라우터에 DHCP relay(ip helper-address)를 설정해, 라우터가 Discover를 받아 giaddr(gateway IP address) 필드에 자기 인터페이스 주소를 넣고 중앙 서버로 유니캐스트 전달합니다. 서버는 giaddr로 어느 서브넷의 풀에서 줄지 결정하고 릴레이에게 응답을 돌려줍니다. 이 구조 덕분에 수백 개 VLAN을 서버 한두 대로 처리합니다. 보안 측면에서는 가짜 DHCP 서버(rogue DHCP)가 잘못된 게이트웨이/DNS를 나눠줄 수 있어, 스위치의 DHCP snooping으로 신뢰 포트에서 온 Offer만 통과시킵니다. 이 snooping 테이블이 2장의 Dynamic ARP Inspection의 근거 자료가 됩니다.

🔬 깊이 보기: ICMP를 막으면 생기는 일 — PMTUD 블랙홀

"보안을 위해 ICMP 전부 차단"은 흔하지만 위험한 설정입니다. 3장에서 본 PMTUD는 ICMP Type 3 Code 4에 의존합니다. 방화벽이 이를 막으면, 송신 측은 DF=1로 1500바이트 세그먼트를 계속 보내고 MTU 1400 구간의 라우터는 계속 버리며, 아무 신호도 돌아오지 않습니다. 증상은 특이합니다: SYN/ACK(작음)은 성공해 연결은 맺히는데, 큰 응답(HTML, 이미지)이 오면 멈춤. "ping은 되는데 사이트가 안 열려요", "작은 파일은 되고 큰 파일은 안 돼요"의 상당수가 이것입니다. 처방은 ICMP 3/4와 11을 허용하거나, 라우터에서 TCP MSS 클램핑(--clamp-mss-to-pmtu), 또는 PLPMTUD(RFC 4821). ICMP를 선별적으로 허용하는 것이 전문가의 방화벽 정책입니다.

4.4실습: dig, ping, traceroute

# 기본 질의 (시스템 리졸버 사용). ANSWER SECTION의 숫자가 남은 TTL
dig www.example.com A
# 특정 리졸버에게 직접
dig @1.1.1.1 www.example.com AAAA
# 짧게
dig +short example.com MX
# 역방향
dig -x 93.184.216.34
# 권한 서버에게 직접 물어 캐시 없는 원본 TTL 확인
dig @a.iana-servers.net www.example.com +norecurse
# TCP로 강제 (방화벽이 TCP 53을 막는지 확인)
dig +tcp www.example.com
# EDNS 버퍼 크기 지정, DNSSEC 레코드 요청
dig +bufsize=1232 +dnssec example.com
dig +trace www.example.com

+trace는 dig 자신이 재귀 리졸버 역할을 흉내 내어 루트부터 반복 질의한다. 애니메이션의 3~5단계를 실제로 보는 것.

ping -c 4 1.1.1.1                 # RTT, 손실률
ping -c 4 -s 1472 -M do 1.1.1.1   # DF 설정 (3장)

traceroute -n 1.1.1.1             # UDP 방식 (-n: 이름 해석 생략)
traceroute -I 1.1.1.1             # ICMP Echo 방식
sudo traceroute -T -p 443 1.1.1.1 # TCP SYN 방식 (방화벽 통과)

mtr -n 1.1.1.1                    # traceroute + ping 반복. 홉별 손실/지터 통계
# 관찰 포인트: 특정 홉의 손실이 "그 이후 홉에도" 이어지면 진짜 손실,
#              그 홉만 손실이면 라우터의 ICMP rate-limit
# 터미널 1: DHCP 패킷 캡처 (포트 67/68)
sudo tcpdump -n -i eth0 -v 'udp port 67 or udp port 68'
# 터미널 2: 임대 해제 후 재요청
sudo dhclient -r eth0 && sudo dhclient -v eth0     # Linux
sudo ipconfig set en0 DHCP                          # macOS
# 캡처 예:
# IP 0.0.0.0.68 > 255.255.255.255.67: BOOTP/DHCP, Request from aa:aa:aa:00:00:05
#     DHCP-Message Option 53: Discover
# IP 10.0.0.1.67 > 10.0.0.23.68: BOOTP/DHCP, Reply
#     DHCP-Message Option 53: Offer, Lease-Time 86400, Router 10.0.0.1, DNS 10.0.0.2
✅ 확인 질문

① dig를 같은 이름으로 두 번 실행하면 TTL이 어떻게 변하는가? ② traceroute에서 마지막 홉의 응답 ICMP Type/Code는 무엇인가(UDP 방식 기준)? ③ DHCP Offer의 목적지 IP가 브로드캐스트가 아니라 10.0.0.23처럼 보이는 경우가 있다. 어떤 조건에서 그런가? (힌트: BOOTP 플래그의 Broadcast 비트)

4.5이해도 점검

요약

  • ICMP는 IP의 오류 보고·진단 채널. 핵심 타입: 8/0 Echo, 3/4 Frag Needed(PMTUD), 11/0 TTL Exceeded(traceroute), 3/3 Port Unreachable.
  • traceroute는 TTL을 1씩 늘려 각 홉의 Time Exceeded 출발지를 수집한다. 홉별 측정은 독립적이며 *가 곧 장애는 아니다.
  • DNS: 스텁 → 재귀 리졸버(재귀 질의) → 루트/TLD/권한(반복 질의). 결과는 TTL 동안 캐시. UDP 53 기본, TC 비트면 TCP 폴백, EDNS 버퍼 1232 권장.
  • DHCP DORA: Discover(0.0.0.0→255.255.255.255) / Offer / Request(브로드캐스트, 서버 지정) / Ack. 릴레이로 서브넷을 넘고, 임대는 T1/T2에 갱신.
  • ICMP 전면 차단은 PMTUD 블랙홀을, DNS TCP 차단은 큰 응답 실패를 만든다.
