12.1NAT의 등장과 종류

1990년대 초 IPv4 고갈이 가시화되자 두 가지 임시 처방이 나왔습니다. CIDR(3장)과 NAT(Network Address Translation, RFC 1631 → RFC 3022)입니다. NAT는 사설 주소(RFC 1918: 10/8, 172.16/12, 192.168/16)를 쓰는 내부 호스트가 바깥과 통신할 때, 경계 라우터가 IP 헤더(필요하면 TCP/UDP 헤더까지)를 고쳐 써서 소수의 공인 주소를 공유하게 합니다. "임시"였던 이 처방은 30년이 지난 지금도 거의 모든 가정·기업·이동통신망의 기본 구조입니다.

종류변환 내용용도
정적 NAT (1:1)내부 IP ↔ 공인 IP 고정 매핑. 포트는 그대로.내부 서버를 바깥에 노출. 양방향 시작 가능.
동적 NAT (N:M)공인 IP 풀에서 하나를 빌려 매핑. 포트 그대로.풀이 소진되면 새 연결 불가. 요즘은 드묾.
NAPT / PAT (N:1, "IP 마스커레이딩")IP 와 포트를 함께 바꿔 공인 IP 하나를 수만 연결이 공유.가정용 공유기, 클라우드 NAT 게이트웨이. "NAT"라고 하면 보통 이것.
CGNAT (RFC 6888)ISP 레벨 NAPT. 가입자 → ISP 사설(100.64/10, RFC 6598) → 공인. 이중 NAT.이동통신·일부 유선 ISP. 포트 블록을 가입자별로 할당.

12.2NAPT 변환 테이블 시뮬레이터 (애니메이션)

내부 호스트 두 대가 같은 출발지 포트(51000)로 외부 서버에 접속합니다. NAT 라우터(공인 IP 203.0.113.5)가 어떻게 충돌을 피해 테이블을 만들고, 돌아오는 응답을 어떻게 역변환하는지 보세요.

—
내부 src (IP:port)→ 외부 src (IP:port)목적지프로토콜타임아웃
📌 체크섬도 다시 쓴다

IP 헤더 체크섬은 IP가 바뀌었으니 당연히 재계산합니다. 그런데 TCP/UDP 체크섬도 재계산해야 합니다. 전송 계층 체크섬은 의사 헤더(pseudo-header)에 src/dst IP를 포함하기 때문입니다(5장). 이것이 NAT가 "L3 장비"가 아니라 L4까지 손대는 장비인 이유이고, 암호화된 ESP(IPsec)처럼 체크섬을 고칠 수 없는 패킷이 NAT를 통과하지 못하는 이유입니다.

12.3NAT 동작 유형과 홀 펀칭 (RFC 3489 · RFC 4787)

NAPT는 "내부에서 나간 연결의 응답"만 들여보내는 것이 기본입니다. 그런데 어떤 외부 패킷까지 들여보내느냐는 구현마다 다르고, 이것이 P2P·VoIP·게임의 성패를 가릅니다. STUN 규격(RFC 3489)의 고전적 4분류입니다. (RFC 4787은 이를 "매핑 동작"과 "필터링 동작"으로 더 정밀하게 나눕니다.)

내부 호스트 A가 S1:p1로 보내 매핑 NAT:40001이 생긴 상황에서, 각 유형이 누구의 인바운드 패킷을 허용하는지가 다릅니다. Symmetric NAT는 목적지마다 매핑 포트를 바꾸므로, 제3자가 알려준 포트로는 연결할 수 없습니다.

도구역할
STUN (RFC 8489)외부 서버가 "너의 패킷이 나에게 어떤 src IP:port로 보였다"를 알려줘 자신의 공인 매핑을 알게 한다. NAT 유형 추정에도 사용.
TURN (RFC 8656)홀 펀칭이 불가능할 때(Symmetric 등) 양쪽이 모두 접속하는 릴레이 서버. 비용이 들어 최후 수단.
ICE (RFC 8445)후보 주소(로컬, STUN 반사, TURN 릴레이)를 모두 모아 쌍을 이루며 연결성 검사 → 되는 것 중 최선 선택. WebRTC의 표준 절차.
🔬 깊이 보기: NAT 뒤에서 P2P가 되는 원리 — UDP 홀 펀칭 (애니메이션)

두 호스트가 모두 NAT 뒤에 있으면 어느 쪽도 먼저 "들어갈" 수 없습니다. 홀 펀칭(RFC 5128)은 양쪽이 동시에 서로를 향해 패킷을 쏴서 각자의 NAT에 "이 상대와 통신 중"이라는 상태를 만드는 기법입니다. 랑데부 서버는 주소만 소개하고 데이터는 중계하지 않습니다.

포트 포워딩, 헤어핀, 그리고 NAT가 깨뜨리는 것들

포트 포워딩(DNAT): 관리자가 정적 매핑 "203.0.113.5:8080 → 192.168.1.20:80"을 미리 넣어 외부에서 시작하는 연결을 허용. UPnP IGD / NAT-PMP / PCP(RFC 6887)는 내부 앱이 이것을 자동으로 요청하는 프로토콜(보안상 논란).
헤어핀(NAT loopback): 내부 호스트가 자기 네트워크의 공인 IP로 접속할 때, NAT가 패킷을 되돌려(헤어핀) 내부 서버로 보내야 한다. RFC 4787 요구 사항이지만 저가 공유기는 종종 지원하지 않아 "밖에서는 되는데 안에서는 안 되는" 현상이 생긴다.
  • 종단 간 원칙 위반: 호스트는 자기 공인 주소를 모르고, 외부에서 먼저 연결할 수 없다. IP 주소를 식별자로 쓰는 프로토콜이 모두 흔들린다.
  • 페이로드 안의 주소: FTP 능동 모드(PORT 명령), SIP/SDP(미디어 주소), 일부 게임은 데이터 안에 IP:port를 적는다. NAT는 이것을 몰라 깨지며, 그래서 프로토콜별로 페이로드를 고쳐 쓰는 ALG(Application Layer Gateway)가 생겼다 — 그리고 ALG 자체가 또 다른 버그·보안 문제의 원천이다.
  • IPsec AH는 IP 헤더를 무결성 검사에 포함하므로 NAT를 통과할 수 없다. ESP는 UDP 4500 캡슐화(NAT-T, RFC 3948)로 우회한다.
  • 상태 유지 부담: 모든 연결이 NAT 테이블에 남아야 한다. 테이블 고갈·타임아웃(UDP는 보통 30초~수 분)이 "오래 조용한 연결이 끊기는" 현상의 원인이고, 그래서 keepalive(9장)가 필요하다.
  • CGNAT의 추적성: 한 공인 IP를 수백 가입자가 공유하므로 IP만으로는 사용자를 특정할 수 없다. 남용 차단(IP 밴)이 무고한 가입자를 함께 막는다.

12.4방화벽: 패킷 필터에서 연결 추적까지

무상태 패킷 필터 (stateless)

패킷 하나만 보고 src/dst IP·포트·플래그로 허용/거부. 빠르고 단순하지만 "응답 패킷"을 구분할 수 없어 역방향 규칙을 열어 둬야 한다. 예: 라우터 ACL. 고전적 우회: ACK 플래그만 세운 패킷은 "기존 연결의 응답"으로 보여 통과(ACK 스캔).

vs

상태 기반 (stateful)

연결 추적 테이블(conntrack)에 흐름 단위 상태(NEW, ESTABLISHED, RELATED)를 기록. 내부에서 시작한 연결의 응답만 자동 허용. TCP는 핸드셰이크·종료를 따라가고, UDP/ICMP는 타임아웃 기반 "유사 연결"로 추적. NAT도 이 테이블 위에 구현된다.

연결 추적 테이블

# conntrack -L (리눅스 netfilter) 출력 예 tcp 6 431999 ESTABLISHED src=192.168.1.10 dst=93.184.216.34 sport=51000 dport=443 \ src=93.184.216.34 dst=203.0.113.5 sport=443 dport=40001 [ASSURED] mark=0 use=1 udp 17 29 src=192.168.1.11 dst=1.1.1.1 sport=53012 dport=53 \ src=1.1.1.1 dst=203.0.113.5 sport=53 dport=53012 mark=0 use=1 tcp 6 118 SYN_SENT src=192.168.1.12 dst=198.51.100.7 sport=40022 dport=22 \ [UNREPLIED] src=198.51.100.7 dst=203.0.113.5 sport=22 dport=40022 mark=0 use=1 # 각 항목 = 원방향 튜플 + 응답방향 튜플. 두 번째 튜플이 NAT 후 모습(dst=공인 IP, dport=변환 포트). # 숫자(431999, 29, 118)는 남은 타임아웃(초). ESTABLISHED TCP 5일, UDP 30초, SYN_SENT 2분.

netfilter 체인 흐름과 규칙 예

패킷은 PREROUTING(DNAT) → 라우팅 결정 → 로컬 행이면 INPUT, 통과면 FORWARD → POSTROUTING(SNAT/MASQUERADE) 순으로 흐른다. 로컬 프로세스가 보낸 패킷은 OUTPUT → POSTROUTING. 주소 변환은 연결의 첫 패킷에서만 결정되고 이후 패킷은 conntrack 항목을 따른다.
# 기본 정책: 들어오는 것 거부, 나가는 것 허용
iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT ACCEPT
# 루프백과 기존 연결의 응답 허용 (상태 기반의 핵심 한 줄)
iptables -A INPUT -i lo -j ACCEPT
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
# 새 연결은 SSH, HTTPS만
iptables -A INPUT -p tcp --dport 22  -m conntrack --ctstate NEW -j ACCEPT
iptables -A INPUT -p tcp --dport 443 -m conntrack --ctstate NEW -j ACCEPT
# ICMP는 PMTUD 때문에 막으면 안 된다 (4장) — 최소한 type 3/11 허용
iptables -A INPUT -p icmp -j ACCEPT

# NAT: 내부(eth1) → 외부(eth0) 마스커레이딩, 포트 포워딩
iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
iptables -t nat -A PREROUTING -i eth0 -p tcp --dport 8080 -j DNAT --to-destination 192.168.1.20:80
iptables -A FORWARD -i eth1 -o eth0 -j ACCEPT
iptables -A FORWARD -i eth0 -o eth1 -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A FORWARD -p tcp -d 192.168.1.20 --dport 80 -m conntrack --ctstate NEW -j ACCEPT
table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;
    iif lo accept
    ct state established,related accept
    ct state invalid drop
    tcp dport { 22, 443 } ct state new accept
    icmp type { destination-unreachable, time-exceeded, echo-request } accept
    icmpv6 type { nd-neighbor-solicit, nd-neighbor-advert, nd-router-advert, packet-too-big } accept
  }
  chain forward {
    type filter hook forward priority 0; policy drop;
    iifname "eth1" oifname "eth0" accept
    ct state established,related accept
  }
}
table ip nat {
  chain prerouting  { type nat hook prerouting  priority -100; tcp dport 8080 dnat to 192.168.1.20:80 }
  chain postrouting { type nat hook postrouting priority 100;  oifname "eth0" masquerade }
}

nftables는 iptables/ip6tables/arptables/ebtables를 하나로 통합했고(inet 패밀리로 v4/v6 동시 처리), 집합·맵을 지원해 규칙 수가 줄어든다. 커널 내부에서는 둘 다 같은 netfilter 훅을 쓴다.

⚠️ "포트가 닫혔다"의 세 가지 모습

방화벽이 패킷을 DROP하면 클라이언트는 타임아웃까지 기다린다(스캐너에게 "filtered"). REJECT하면 TCP RST 또는 ICMP Port Unreachable을 돌려줘 즉시 실패한다("closed"). 서비스가 없는 포트에 OS가 직접 RST를 보내는 것도 "closed". 외부 노출 면에서는 DROP이 정보를 덜 주지만, 내부 네트워크에서는 REJECT가 디버깅과 사용자 경험에 낫다.

12.5TLS 1.3 핸드셰이크 (RFC 8446) (애니메이션)

TLS는 TCP 연결 위에서 키 합의 → 인증 → 암호화 채널을 만드는 응용 계층(세션/표현 계층으로 보기도 함) 프로토콜입니다. TLS 1.3은 1.2 대비 핸드셰이크를 2-RTT에서 1-RTT로 줄이고, 취약한 알고리즘(RSA 키 교환, CBC, RC4, SHA-1, 압축, 재협상)을 모두 제거했습니다.

TLS 1.2(RSA 키 교환): 클라이언트는 서버 인증서를 받은 뒤에야 프리마스터 시크릿을 서버 공개키로 암호화해 보낼 수 있어 2-RTT가 필요하다. TLS 1.3은 ClientHello에 (EC)DHE 공개값을 미리 실어(key_share) 1-RTT에 끝낸다.

이전 세션에서 받은 PSK(NewSessionTicket)가 있으면 클라이언트는 첫 비행(ClientHello)에 바로 애플리케이션 데이터를 암호화해 실을 수 있습니다 — 0-RTT. 단 조건이 붙습니다.

  • 0-RTT 데이터는 재생(replay) 공격에 취약합니다. 공격자가 그 패킷을 복사해 다시 보내면 서버는 같은 요청을 두 번 처리합니다. 그래서 멱등한 요청(GET)에만 쓰고, HTTP는 Early-Data 헤더와 425 Too Early 응답(RFC 8470)으로 통제합니다.
  • 0-RTT 데이터는 PSK로만 보호되므로 전방 비밀성이 없습니다. 핸드셰이크가 끝난 뒤의 데이터부터 ECDHE로 보호됩니다.
  • QUIC(13장)은 TLS 1.3을 내장해 전송 핸드셰이크와 TLS 핸드셰이크를 합쳐 0-RTT/1-RTT 연결을 만듭니다.
  • 인증서 체인: 서버는 자기 인증서 + 중간 CA 인증서를 보낸다. 클라이언트는 서명을 따라 올라가 OS/브라우저에 내장된 루트 CA에 닿는지, 유효기간·폐기(OCSP/CRL)·이름(SAN에 호스트명 포함)을 검사한다. "체인 불완전" 오류 대부분은 서버가 중간 인증서를 빠뜨린 것.
  • SNI(Server Name Indication): ClientHello에 접속할 호스트명을 평문으로 실어, 한 IP에서 여러 도메인의 인증서를 고를 수 있게 한다. 평문이라 검열·감시에 쓰이며, ECH(Encrypted Client Hello)가 이를 암호화하는 후속 규격.
  • ALPN(RFC 7301): 핸드셰이크 안에서 "h2 / http/1.1 / h3" 등 상위 프로토콜을 협상. HTTP/2는 사실상 ALPN을 요구한다.
  • HSTS · 인증서 투명성(CT): 다운그레이드 방지와 잘못 발급된 인증서의 공개 로그. 2018년 이후 공개 CA 인증서는 CT 로그 제출이 필수.

TLS 1.2의 RSA 키 교환에서는 세션 키의 재료(프리마스터 시크릿)를 서버의 장기 RSA 공개키로 암호화해 보냈습니다. 문제는 누군가 암호화된 트래픽을 몇 년치 저장해 두었다가 나중에 서버 개인키를 입수하면(유출, 압수, 수학적 돌파) 과거 세션을 전부 복호화할 수 있다는 점입니다. 반면 (EC)DHE는 세션마다 새 임시 키 쌍을 만들고 교환 후 버리므로, 서버 개인키는 서명(인증)에만 쓰이고 세션 키 유도에는 관여하지 않습니다. 개인키가 나중에 털려도 과거 세션은 안전 — 이것이 전방 비밀성(forward secrecy)입니다. 2013년 대규모 감시 폭로 이후 이 성질이 필수로 여겨졌고, TLS 1.3은 아예 선택지를 없앴습니다. 부작용: 서버 개인키로 트래픽을 복호화하던 기업용 패시브 모니터링 장비가 동작하지 않게 되어, 이들은 TLS 종료 프록시(MITM)로 옮겨 가야 했습니다.

12.6TCP/IP를 노리는 공격과 방어

TCP/IP는 서로를 신뢰하는 연구 기관들 사이에서 설계되었습니다. 출발지 주소를 믿고, 상태를 먼저 만들고, 응답을 요청자에게 돌려줍니다. 아래 공격들은 모두 그 "선의의 가정"을 뒤집습니다.

SYN flood와 SYN cookies (RFC 4987) (애니메이션)

서버는 SYN을 받으면 SYN+ACK를 보내고 반열림(half-open) 연결 상태를 SYN 큐에 저장합니다(6장 백로그). 공격자가 출발지를 위조한 SYN을 쏟아부으면 응답은 허공으로 가고 큐만 차서, 정상 클라이언트의 SYN이 버려집니다.

SYN cookies(D. J. Bernstein, 1996)의 발상: 큐가 꽉 차면 상태를 저장하지 않는다. 대신 SYN+ACK의 ISN을 다음처럼 계산해 보낸다.

ISN = hash(src IP, src port, dst IP, dst port, secret, t)   // 상위 비트: 시각 카운터 t (5비트, 64초 단위)
                                                           // 중간: MSS 인덱스 (3비트)
                                                           // 하위 24비트: 해시
// 정상 클라이언트의 ACK가 오면 ack−1 을 같은 식으로 검증 → 맞으면 그때 연결 생성
🔬 깊이 보기: SYN cookies가 포기하는 것

ISN 32비트에 모든 정보를 욱여넣어야 하므로, SYN에 실렸던 TCP 옵션(Window Scale, SACK-permitted, Timestamps)을 기억할 자리가 없습니다. 그래서 쿠키 모드로 맺어진 연결은 윈도우 스케일링이 없어(64 KB 상한) 긴 굵은 파이프(9장)에서 느려지고, SACK도 꺼집니다. 리눅스는 클라이언트가 Timestamps를 쓰면 TS 값의 하위 비트에 옵션을 숨겨 이를 완화합니다(tcp_syncookies=1: 큐가 찼을 때만 사용, 기본값). 또 하나의 한계: 쿠키는 ACK가 왔을 때 "SYN이 있었다"는 사실만 검증하지 SYN+ACK의 재전송은 못 하므로, SYN+ACK가 손실되면 클라이언트가 알아서 SYN을 다시 보내야 합니다. 그래서 SYN cookies는 평시 기본 동작이 아니라 공격 시 생존 모드이며, 근본 완화는 업스트림에서의 유량 제한과 애니캐스트 스크러빙입니다.

IP 스푸핑과 BCP 38 (RFC 2827)

IP는 출발지 주소를 검증하지 않습니다. 공격자는 아무 주소나 적어 보낼 수 있고, 그 결과 ① 응답이 제3자(피해자)에게 가는 반사 공격, ② 출발지 기반 접근 제어 우회, ③ 추적 불능이 생깁니다. BCP 38(인그레스 필터링)은 "ISP는 고객에게 할당한 프리픽스가 아닌 출발지 주소의 패킷을 고객 쪽에서 받지 말라"는 운영 권고입니다. 20년 넘게 권고되었지만 전 세계 네트워크의 상당수가 아직 미적용(MANRS 프로젝트가 추적)이며, 그래서 아래 증폭 DDoS가 가능합니다. 라우터 구현은 uRPF(unicast Reverse Path Forwarding): "이 src IP로 가는 경로가 이 패킷이 들어온 인터페이스를 향하는가"를 FIB로 검사합니다.

증폭 DDoS

UDP 서비스에 피해자 주소로 위조한 작은 요청을 보내면, 서버가 피해자에게 훨씬 큰 응답을 보냅니다. 요청 크기 대비 응답 크기가 증폭률(BAF, Bandwidth Amplification Factor).

TCP RST 주입과 시퀀스 번호 추측

경로상의 공격자(또는 경로 밖이라도 운이 좋으면)가 올바른 4-tuple과 수신 윈도우 안의 시퀀스 번호로 RST를 보내면 연결이 끊깁니다. 1985년 Morris가 지적했듯 ISN이 예측 가능하면 경로 밖(off-path)에서도 연결 하이재킹이 가능합니다. 대응: ① ISN 랜덤화(RFC 6528: 비밀 키 해시 + 시간 기반), ② RST는 시퀀스가 정확히 RCV.NXT일 때만 수락하고 윈도우 안이면 "챌린지 ACK"를 보내는 RFC 5961, ③ BGP처럼 장기 세션은 TCP-AO(RFC 5925)/MD5 서명(RFC 2385), ④ 윈도우 축소로 추측 공간 축소. 역설적으로 RFC 5961의 챌린지 ACK 카운터가 부채널이 되어 2016년 리눅스 off-path 공격(CVE-2016-5696)이 나왔고, 이후 카운터가 무작위화되었습니다. 국가 단위 검열 장비(GFW 등)는 이 RST 주입을 합법적(?) 도구로 씁니다.

링크·이름 계층 스푸핑

ARP 스푸핑(2장): 같은 LAN에서 "게이트웨이 IP는 내 MAC"이라고 위조 ARP를 뿌리면 트래픽이 공격자를 거친다(MITM). 방어: 스위치의 DHCP Snooping + Dynamic ARP Inspection(DAI)(DHCP로 배운 IP-MAC 바인딩과 다른 ARP를 차단), 정적 ARP, 802.1X. IPv6에서는 RA Guard / ND Inspection이 대응물.
DNS 스푸핑/캐시 포이즈닝(4장): 리졸버의 질의에 공격자가 먼저 위조 응답을 보내 캐시를 오염. Kaminsky(2008)는 랜덤 서브도메인으로 시도 횟수를 무한히 늘렸다. 방어: 소스 포트·TXID 무작위화(32비트 엔트로피), 0x20 대소문자 랜덤화, 근본적으로 DNSSEC(서명 검증), 전송 암호화 DoT/DoH(경로상 변조 방지).

12.7IPsec과 VPN

TLS가 응용(소켓) 단위로 보호한다면, IPsec(RFC 4301)은 IP 계층에서 모든 상위 트래픽을 보호합니다. 두 프로토콜, 두 모드가 있습니다.

AH (프로토콜 51) — 인증만

IP 헤더AHTCP데이터

IP 헤더까지 포함해 무결성 보장(ICV). 암호화 없음. IP가 바뀌면 검증 실패 → NAT 불가. 실무에서 거의 안 씀.

ESP (프로토콜 50) — 암호화 + 인증

IP 헤더ESP 헤더TCP데이터ESP 트레일러ICV

점선 부분이 암호화. IP 헤더는 보호 범위 밖이라 NAT-T(UDP 4500)로 NAT 통과 가능. 사실상 IPsec = ESP.

전송 모드 (host-to-host)

원래 IP 헤더ESPTCP데이터

원래 IP 헤더를 그대로 두고 페이로드만 보호. 종단 호스트 간.

터널 모드 (gateway-to-gateway)

새 IP 헤더ESP원래 IP 헤더TCP데이터

원래 패킷 전체를 암호화하고 게이트웨이 주소의 새 IP 헤더를 씌움. 사이트 간 VPN. 내부 토폴로지가 숨겨진다.

키 합의는 IKEv2(RFC 7296, UDP 500/4500)가 담당하며, 보안 연관(SA)과 SPI로 어떤 키로 복호화할지 식별합니다.

VPN계층 · 전송암호특징
IPsec/IKEv2L3, ESP 또는 UDP 4500협상(AES-GCM 등)OS 내장, 모바일 로밍(MOBIKE), 사이트 간 표준
WireGuardL3, UDP고정: ChaCha20-Poly1305, Curve25519, Noise 프레임워크코드 4천 줄, 커널 내장(5.6+), 협상 없음(설정으로 고정), 1-RTT 핸드셰이크, 로밍 자연 지원
OpenVPNL2/L3, TCP 또는 UDPTLS 기반사용자 공간, 유연·이식성, 상대적으로 느림. TCP 위 TCP는 "TCP 멜트다운"(재전송 중첩) 주의

12.9이해도 점검

요약

  • NAPT는 IP와 포트를 함께 바꿔 공인 IP 하나를 공유하며, 첫 패킷에서 변환 테이블 항목을 만들고 응답을 역변환한다. 전송 계층 체크섬까지 재계산한다.
  • NAT 유형(Full cone ~ Symmetric)에 따라 인바운드 허용 범위가 다르고, STUN/TURN/ICE와 홀 펀칭이 P2P를 가능하게 한다. NAT는 종단 간 원칙·페이로드 내 주소·IPsec AH를 깨뜨린다.
  • 상태 기반 방화벽은 conntrack으로 흐름을 추적해 응답만 허용한다. netfilter: PREROUTING → INPUT/FORWARD → POSTROUTING.
  • TLS 1.3은 key_share를 ClientHello에 실어 1-RTT로 끝내고, ECDHE만 허용해 전방 비밀성을 보장한다. 0-RTT는 재생 공격에 취약하다.
  • SYN flood ↔ SYN cookies(상태 없는 핸드셰이크, 옵션 손실), 스푸핑 ↔ BCP 38/uRPF, 증폭 DDoS ↔ UDP 서비스 봉쇄, RST 주입 ↔ ISN 랜덤화·RFC 5961, ARP/DNS 스푸핑 ↔ DAI/DNSSEC.
  • IPsec ESP(터널 모드)는 사이트 간 VPN의 표준이고, WireGuard는 단순함으로 현대 VPN의 기본이 되었다.
