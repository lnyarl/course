라우팅 심화: OSPF · BGP

3장에서 라우터가 "테이블을 보고 다음 홉을 고른다"는 것을 배웠습니다. 이 장은 그 테이블이 어떻게 만들어지는가에 답합니다. 조직 내부를 묶는 링크 상태 프로토콜(OSPF)과, 7만 개가 넘는 자율 시스템을 하나의 인터넷으로 잇는 경로 벡터 프로토콜(BGP)을 알고리즘부터 정책까지 따라갑니다.

⏱ 약 90분인터넷 계층전송(BGP는 TCP 179)RFC 2328 · 4271 · 5340 · 6811

학습 목표

  • 라우팅과 포워딩을 구분하고, 라우팅 테이블 항목의 구성 요소(prefix, next-hop, metric, AD)를 설명할 수 있다.
  • 거리 벡터(Bellman-Ford)와 링크 상태(Dijkstra)의 동작을 단계별로 손으로 따라갈 수 있고, 각각의 수렴 특성과 한계를 설명할 수 있다.
  • OSPF의 인접 형성 → LSA 플러딩 → LSDB → SPF 흐름과 영역 구조를 설명할 수 있다.
  • BGP 경로 속성과 경로 선택 순서를 적용해 최적 경로를 고를 수 있고, AS_PATH가 루프를 막는 원리를 설명할 수 있다.
  • 피어링/트랜짓 관계, 경로 누출·하이재킹 사례와 RPKI의 역할을 설명할 수 있다.

11.1라우팅 vs 포워딩, 그리고 테이블 한 줄의 의미

두 단어는 자주 섞여 쓰이지만 전문가는 구분합니다.

포워딩 (Forwarding) — 데이터 평면

패킷 하나하나에 대해 목적지 주소로 테이블을 조회해 출력 인터페이스로 넘기는 일. 나노초 단위, 하드웨어(ASIC/TCAM)가 수행. 조회 규칙은 3장에서 본 Longest Prefix Match.

vs

라우팅 (Routing) — 제어 평면

그 테이블을 만드는 일. 이웃 라우터와 정보를 교환하고(라우팅 프로토콜), 알고리즘으로 최적 경로를 계산해 테이블을 채운다. 초~분 단위, 소프트웨어(CPU)가 수행.

라우터 내부에는 보통 두 테이블이 있습니다. 제어 평면이 관리하는 RIB(Routing Information Base, 모든 후보 경로)와 그중 최선만 골라 하드웨어로 내린 FIB(Forwarding Information Base). ip route가 보여주는 것은 FIB에 가깝고, show ip bgp가 보여주는 것은 RIB입니다.

라우팅 테이블 항목의 구성 요소

구성 요소의미예

📌 metric과 AD는 비교 대상이 다르다

OSPF cost 20과 RIP 홉 수 3은 비교할 수 없는 단위입니다. 그래서 라우터는 먼저 AD로 프로토콜을 고르고, 그 프로토콜 안에서 metric으로 경로를 고릅니다. 이 두 단계 중 어느 쪽도 Longest Prefix Match보다 먼저가 아닙니다. 순서는 항상 ① 가장 긴 프리픽스 → ② 가장 낮은 AD → ③ 가장 낮은 metric입니다.

정적 vs 동적 라우팅

정적 (static)

관리자가 손으로 입력. 예측 가능하고 CPU·대역폭을 쓰지 않지만, 링크가 죽어도 스스로 바뀌지 않는다. 용도: 단일 출구(stub) 네트워크의 디폴트 경로, 보안상 광고하면 안 되는 경로, 소규모 랩.

ip route add 10.9.0.0/16 via 10.0.0.2 dev eth0
ip route add default via 203.0.113.1

동적 (dynamic)

라우터끼리 프로토콜로 정보를 교환해 테이블을 자동 갱신. 장애 시 우회 경로로 수렴(convergence). 두 가족으로 나뉜다.

  • IGP(Interior Gateway Protocol): 한 조직(AS) 내부. RIP(거리 벡터), OSPF/IS-IS(링크 상태), EIGRP(고급 거리 벡터).
  • EGP(Exterior Gateway Protocol): AS 사이. 현재 유일하게 BGP-4(RFC 4271).

11.2자율 시스템(AS)과 IGP/EGP

인터넷은 하나의 네트워크가 아니라 약 7만 5천 개의 자율 시스템(Autonomous System)이 서로 연결된 집합입니다. AS는 "하나의 관리 주체가 하나의 라우팅 정책으로 운영하는 라우터들의 집합"이며, 16비트(현재는 32비트, RFC 6793) AS 번호(ASN)로 식별됩니다. 예: AS15169(Google), AS4766(KT), AS3786(LG U+), AS9318(SK브로드밴드). 문서·예제용으로는 64496–64511, 65536–65551이 예약되어 있습니다(RFC 5398).

AS 내부는 IGP(OSPF)가 "가장 빠른 길"을 계산하고, AS 사이는 BGP가 "정책적으로 허용된 길"을 교환한다. BGP 세션은 TCP 179번 포트 위에서 유지된다.
🔬 깊이 보기: 왜 내부는 링크 상태, 외부는 경로 벡터인가

AS 내부는 한 주체가 모든 라우터를 신뢰하고, 목표는 단순히 "가장 빠른 길"입니다. 전체 토폴로지를 모두에게 복제해 각자 Dijkstra를 돌리는 링크 상태 방식이 빠르고 루프가 없어 적합합니다. 반면 AS 사이에는 ① 토폴로지(내부 구조)를 공개하고 싶지 않고, ② "빠른 길"보다 "돈을 내는 고객 방향", "경쟁사 경유 금지" 같은 정책이 우선이며, ③ 수십만 프리픽스 × 수만 AS의 전체 그래프를 모두가 계산하는 것은 비현실적입니다. 경로 벡터는 "이 프리픽스로 가려면 이 AS 목록을 지난다"만 알려주므로 내부를 숨기면서도 루프 검출(자기 ASN이 있으면 거부)과 정책 적용(AS_PATH 필터)이 가능합니다. 즉, 링크 상태는 최적화 도구, 경로 벡터는 정책 도구입니다.

11.3거리 벡터: Bellman-Ford (애니메이션)

거리 벡터(Distance Vector) 라우팅의 아이디어는 단순합니다. 각 라우터는 "내가 아는 모든 목적지까지의 거리 목록(벡터)"을 이웃에게만 주기적으로 보내고, 이웃이 보낸 벡터에 링크 비용을 더해 더 짧으면 갱신합니다. 분산 Bellman-Ford 방정식: D_x(y) = min_v { c(x,v) + D_v(y) }. 전체 지도를 모르는 "소문 기반" 방식이며, RIP(RFC 2453)이 대표입니다.

무한 계수(count-to-infinity) 문제와 Split Horizon

소문 기반의 약점은 나쁜 소식이 느리게 퍼진다는 것입니다. 링크가 끊겼을 때, 이웃이 "나는 거기 갈 수 있어(사실은 너를 거쳐서)"라고 알려주면 서로를 믿고 거리를 1씩 올리며 루프에 빠집니다. 아래에서 Split Horizon with Poison Reverse를 켜고 끄며 비교해 보세요.

토글 후 ↺ 처음 을 누르세요
Split Horizon: 어떤 목적지를 이웃 N을 통해 가고 있다면, 그 목적지 정보를 N에게는 보내지 않는다. "너한테서 배운 걸 너한테 되팔지 않는다."
Poison Reverse: 보내지 않는 대신 명시적으로 "거리 ∞"라고 보낸다. 상대가 혹시 갖고 있을 잘못된 경로를 즉시 지워 준다. RIP는 16을 ∞로 쓴다(그래서 최대 15홉).
⚠️ Split Horizon의 한계

두 노드 사이 루프는 막지만 세 노드 이상의 루프(A→B→C→A)는 막지 못합니다. 그래서 RIP은 홀드다운 타이머, 트리거드 업데이트를 더하지만 근본 해결은 아닙니다. 오늘날 RIP는 소규모 랩 외에는 거의 쓰이지 않으며, 거리 벡터 계열 중 EIGRP만 DUAL 알고리즘(실현 가능한 후계자 조건)으로 루프를 수학적으로 막아 실무에 남아 있습니다.

11.4링크 상태: Dijkstra (인터랙티브)

링크 상태(Link State) 라우팅은 반대 접근입니다. 각 라우터가 "내 링크들과 비용"을 모든 라우터에게 플러딩하여 전원이 동일한 지도(LSDB)를 갖게 한 뒤, 각자 자기를 뿌리로 하는 최단 경로 트리를 Dijkstra 알고리즘으로 계산합니다. 소문이 아니라 지도를 보므로 루프가 없고 수렴이 빠릅니다. OSPF와 IS-IS가 이 방식입니다.

시작 노드를 고르고 단계별로 진행하세요. 주황 = 지금 확정하는 노드, 초록 = 확정됨(visited), 파랑 점선 = 이번 단계에서 완화(relax)한 간선.

임시 거리(tentative) — 아직 확정되지 않은 최단 거리 추정치
결과 라우팅 테이블 — 뿌리 라우터 관점의 next-hop

미방문 노드 중 임시 거리가 가장 작은 노드 u를 고르면, u까지의 거리는 더 이상 줄어들 수 없습니다. 다른 어떤 경로도 반드시 미방문 노드 하나를 먼저 지나야 하고, 그 노드의 거리는 이미 u보다 크거나 같기 때문입니다(간선 비용이 음수가 아닐 때). 이 성질 덕에 노드를 한 번씩만 확정하면 끝나며, 라우터 N개·링크 E개에 대해 O(E log N)입니다. 수천 라우터의 영역도 수십 ms에 계산되므로, OSPF의 병목은 계산이 아니라 LSA 플러딩과 SPF 재계산 빈도입니다. 그래서 SPF 지연 타이머(spf-delay, 지수 백오프)가 존재합니다.

11.5OSPF 동작 원리 (RFC 2328 / RFC 5340)

OSPF(Open Shortest Path First)는 IP 프로토콜 번호 89 위에서 직접 동작하며(TCP/UDP 아님), 다음 단계로 라우팅 테이블을 만듭니다.

  1. Hello: 각 인터페이스에서 멀티캐스트 224.0.0.5(AllSPFRouters)로 10초(브로드캐스트 링크 기본)마다 Hello를 보내 이웃을 발견한다. 영역 ID, Hello/Dead 간격, 인증, 네트워크 마스크가 모두 일치해야 이웃이 된다 — 불일치는 OSPF 장애 원인 1순위.
  2. 인접(adjacency) 형성: DBD(Database Description) 교환으로 서로의 LSDB 요약을 비교하고, 없는 LSA는 LSR/LSU로 요청·수신한다. 상태 머신: Down → Init → 2-Way → ExStart → Exchange → Loading → Full.
  3. LSA 플러딩: 각 라우터가 자신의 링크 정보를 LSA(Link State Advertisement)로 만들어 영역 전체에 신뢰성 있게 전파(ACK 기반). 시퀀스 번호로 최신성 판단, 30분마다 리프레시, MaxAge 60분.
  4. LSDB 동기화: 영역 안 모든 라우터가 동일한 Link State Database를 갖는다. 이것이 "지도".
  5. SPF 계산: 각 라우터가 자신을 뿌리로 Dijkstra를 실행, 최단 경로 트리에서 라우팅 테이블을 뽑는다. 비용 = 참조 대역폭(기본 100 Mbps) / 링크 대역폭 → 10G 링크에서 1 미만이 되므로 auto-cost reference-bandwidth를 반드시 올려야 한다.

영역(Area)과 라우터 역할

LSDB와 SPF 비용은 영역 크기에 비례합니다. 그래서 OSPF는 네트워크를 영역으로 나누고, 영역 사이에는 토폴로지 대신 요약 경로만 전달합니다. 모든 영역은 Area 0(백본)에 붙어야 하며, 영역 간 트래픽은 반드시 백본을 경유합니다(두 단계 계층).

ABR(Area Border Router)은 두 영역의 LSDB를 모두 갖고 Summary LSA(Type 3)를 만든다. ASBR(AS Boundary Router)은 외부 경로(BGP, 정적)를 External LSA(Type 5)로 주입한다.

DR/BDR: 브로드캐스트 링크의 인접 폭발 막기

한 이더넷 세그먼트에 라우터 n대가 있으면 전부 서로 인접을 맺을 때 n(n−1)/2개의 인접과 그만큼의 LSA 중복 플러딩이 생깁니다. OSPF는 세그먼트마다 DR(Designated Router)과 BDR을 뽑아, 모든 라우터가 DR/BDR과만 Full 인접을 맺게 합니다(나머지는 2-Way에 머묾). DR은 우선순위(priority, 0이면 후보 제외) → Router ID 순으로 선출되며, 선점(preempt)하지 않습니다 — 더 좋은 라우터가 나중에 켜져도 현 DR이 유지됩니다.

왼쪽: 5대 전부 인접(10개). 오른쪽: DR/BDR 선출 후 인접은 7개로, 라우터 수에 비례(2n−3)하게 줄어든다. DR은 224.0.0.6(AllDRouters)으로 LSU를 받는다.

11.6BGP: 인터넷을 잇는 경로 벡터 (RFC 4271)

BGP-4는 1994년 이후 인터넷의 유일한 AS 간 라우팅 프로토콜입니다. 특징을 한 줄로 요약하면 "TCP 위에서, 전체 경로(AS 목록)를 담아, 정책에 따라 선택적으로 광고하는 프로토콜"입니다.

전송: TCP 179. 이웃을 자동 발견하지 않고 수동 설정한 피어와 세션을 맺는다. 신뢰성·순서는 TCP가 책임지므로 BGP는 증분 업데이트만 보낸다(주기적 재광고 없음). 메시지: OPEN, UPDATE, KEEPALIVE(기본 60초), NOTIFICATION.
eBGP vs iBGP: 다른 AS와 맺으면 eBGP(보통 직접 연결, TTL 1), 같은 AS 내부끼리 맺으면 iBGP. iBGP는 배운 경로를 다른 iBGP 피어에게 재광고하지 않으므로(루프 방지) 풀 메시 또는 루트 리플렉터(RFC 4456)가 필요하다.

AS_PATH로 루프를 막는 원리 (애니메이션)

BGP UPDATE는 프리픽스와 함께 AS_PATH 속성(그 프리픽스까지 지나온 AS 번호 목록)을 실어 보냅니다. eBGP 피어에게 광고할 때 자신의 ASN을 앞에 붙이고(prepend), 받은 경로의 AS_PATH에 자기 ASN이 있으면 버립니다.

NEXT_HOPwell-known mandatory이 경로의 다음 홉 IP. eBGP에서는 광고한 피어 주소, iBGP로 전달될 때는 바뀌지 않아 내부 IGP로 도달 가능해야 한다(또는 next-hop-self).

    11.7BGP 정책: 피어링, 트랜짓, 그리고 사고들

    BGP가 "정책 프로토콜"이라는 말의 실체는 돈입니다. AS 사이의 관계는 크게 둘입니다.

    트랜짓 (Transit) — 고객 ↔ 공급자

    고객이 공급자에게 돈을 내고 인터넷 전체로의 도달성을 산다. 공급자는 고객 프리픽스를 모든 이웃에게 광고하고, 고객에게는 풀 테이블(또는 디폴트)을 준다.

    피어링 (Peering) — 대등

    두 AS가 (보통 무료로) 서로의 고객 트래픽만 교환한다. 피어에게서 배운 경로를 다른 피어나 공급자에게 넘기지 않는다. IX(인터넷 익스체인지, 예: KINX, DE-CIX)에서 흔히 맺는다.

    이 관계는 Gao-Rexford 규칙(valley-free)으로 요약됩니다: "고객에게서 배운 경로는 모두에게, 피어·공급자에게서 배운 경로는 고객에게만 광고한다." LOCAL_PREF로 고객 > 피어 > 공급자 순으로 선호를 두는 것도 이 규칙의 구현입니다.

    경로 누출과 하이재킹

    사고무슨 일이 있었나원인 유형
    2008 Pakistan Telecom – YouTube정부의 YouTube 차단 지시로 AS17557이 YouTube의 /22보다 더 구체적인 /24를 광고 → 상위 ISP가 필터 없이 전 세계로 전파 → YouTube 전 세계 접속 불가 2시간.하이재킹(더 긴 프리픽스)
    2017 Google – JapanGoogle이 실수로 NTT 등의 수만 프리픽스를 트랜짓하듯 광고(경로 누출). 일본 ISP 트래픽이 Google로 쏠려 대규모 장애.경로 누출(valley-free 위반)
    2018 Amazon Route 53공격자가 AS10297로 Route 53의 /24를 하이재킹 → DNS 응답 위조 → MyEtherWallet 사용자를 가짜 사이트로 유도, 암호화폐 탈취.악의적 하이재킹

    RPKI: 광고할 자격이 있는가 (RFC 6480 · 6811)

    BGP 자체에는 "AS 64500이 정말 203.0.113.0/24를 가졌는가"를 검증할 수단이 없습니다. RPKI(Resource Public Key Infrastructure)는 주소 소유자가 "이 프리픽스는 이 ASN이 최대 이 길이까지 원천(origin)으로 광고할 수 있다"는 ROA(Route Origin Authorization)에 서명해 공개하고, 라우터는 수신 경로의 origin AS를 ROA와 대조해 Valid / Invalid / NotFound로 판정합니다(ROV, Route Origin Validation). Invalid를 버리면 위 YouTube·Route 53형 사고는 막을 수 있지만, AS_PATH 중간 위조나 경로 누출은 막지 못합니다. 이를 위한 BGPsec(RFC 8205)과 ASPA는 아직 보급 초기입니다.

    🔬 깊이 보기: BGP 수렴이 느린 이유

    OSPF는 수백 ms에 수렴하지만 BGP는 경로 하나가 사라질 때 수 분이 걸리기도 합니다. 이유는 ① MRAI(MinRouteAdvertisementInterval, eBGP 기본 30초) — 플래핑 억제를 위해 같은 프리픽스의 업데이트를 묶어 보내므로 홉마다 최대 30초 지연, ② 경로 탐색(path hunting) — 경로가 철회되면 각 AS가 차선·차차선 경로를 순서대로 시도하며 광고·철회를 반복(Labovitz 2000, 최악 O(n!)), ③ 라우트 댐핑(RFC 2439) — 자주 흔들리는 경로에 페널티를 주어 일정 시간 무시. 안정성을 위한 장치들이 모두 수렴 지연으로 작동합니다. 그래서 실무에서는 BFD(RFC 5880)로 링크 장애를 수십 ms에 감지하고, 중요한 서비스는 애니캐스트와 여러 트랜짓으로 "수렴을 기다리지 않는" 구조를 만듭니다.

    11.8Longest Prefix Match 다시 보기 (인터랙티브)

    3장의 LPM을 실제 라우터에 가까운 테이블로 연습합니다. 디폴트 경로, 집계 경로, 구체적 경로, 호스트 경로, 블랙홀이 섞여 있습니다. 목적지를 입력하면 각 행의 프리픽스 비트와 비교해 매칭 여부와 선택 결과를 보여줍니다.

    경로 집계(aggregation)와 ECMP

    10.1.0.0/24 ~ 10.1.3.0/24 네 개의 연속 프리픽스는 앞 22비트가 같으므로 10.1.0.0/22 하나로 상위에 광고할 수 있다. CIDR(RFC 4632)의 핵심 효과: 글로벌 테이블 크기 억제. 단, 집계된 쪽에서는 내부 한 서브넷이 죽어도 바깥은 모르므로(블랙홀), 집계 라우터는 보통 집계 프리픽스를 Null0로 가리키는 항목을 함께 둔다.

    ECMP(Equal-Cost Multi-Path): 같은 프리픽스에 같은 비용의 next-hop이 여러 개면 라우터는 둘 다 FIB에 넣고 흐름(5-tuple 해시) 단위로 분산합니다. 패킷 단위로 분산하면 같은 TCP 연결의 패킷이 순서가 뒤집혀 가짜 dup ACK·성능 저하를 일으키기 때문입니다. OSPF·BGP(maximum-paths) 모두 지원하며, 데이터센터의 Clos(leaf-spine) 토폴로지가 ECMP 위에 세워져 있습니다.

    🔬 깊이 보기: "풀 테이블 100만 경로"의 의미

    2024년 기준 글로벌 IPv4 BGP 테이블은 약 95만~100만 프리픽스, IPv6는 약 20만입니다. 이 숫자가 중요한 이유는 ① 하드웨어 FIB(TCAM) 용량 — 2014년 8월 12일, 많은 구형 라우터의 기본 TCAM 할당 512K를 넘기면서 전 세계적으로 장애가 났습니다("512K day"). ② 수렴 시간 — 피어 세션이 리셋되면 100만 경로를 다시 받고 최선 경로를 재계산하는 데 수 분. ③ 메모리 — RIB는 피어 수 × 경로 수이므로 수십 피어면 수천만 항목. 그래서 대형 네트워크는 디폴트 + 부분 테이블, 루트 리플렉터 계층화, 플랫폼별 FIB 프로파일 조정 같은 운영 기법을 씁니다. 또 테이블이 느는 주 원인이 트래픽 엔지니어링용 /24 분할(deaggregation)이라는 점도 알아 두세요.

    요약

    • 포워딩은 패킷마다 FIB를 LPM으로 조회하는 데이터 평면, 라우팅은 그 테이블을 만드는 제어 평면이다. 선택 순서: 가장 긴 프리픽스 → 낮은 AD → 낮은 metric.
    • 거리 벡터(Bellman-Ford)는 이웃의 소문으로 수렴하며 무한 계수 문제가 있다. Split horizon/poison reverse는 2노드 루프만 막는다.
    • 링크 상태(Dijkstra)는 모두가 같은 지도(LSDB)를 갖고 각자 최단 경로 트리를 계산한다. OSPF: Hello → 인접 → LSA 플러딩 → SPF, 영역으로 규모를 제어하고 DR/BDR로 인접 수를 줄인다.
    • BGP는 TCP 179 위의 경로 벡터 프로토콜. AS_PATH로 루프를 막고, LOCAL_PREF → AS_PATH 길이 → ORIGIN → MED → eBGP → IGP metric → Router ID 순으로 경로를 고른다.
    • AS 관계(트랜짓/피어링)가 정책을 결정하고(valley-free), 경로 누출·하이재킹 사고를 RPKI/ROV가 부분적으로 막는다. BGP 수렴은 설계상 느리다.
