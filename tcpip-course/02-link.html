링크 계층: Ethernet · ARP · 스위치

IP 패킷은 결국 "같은 선에 꽂힌 이웃"에게 프레임으로 건네져야 합니다. 이 장은 그 이웃을 어떻게 지목하고(MAC), 스위치가 어떻게 길을 익히며(MAC 학습), IP 주소를 MAC 주소로 어떻게 바꾸는지(ARP)를 시뮬레이터로 봅니다.

⏱ 약 60분링크RFC 826 · IEEE 802.3 · 802.1Q

학습 목표

  • Ethernet II 프레임의 각 필드와 길이, 802.1Q 태그 위치를 그릴 수 있다.
  • MAC 주소의 OUI, I/G 비트, U/L 비트를 해석할 수 있다.
  • 스위치가 MAC 테이블을 학습하고 플러딩·포워딩·필터링을 결정하는 과정을 설명할 수 있다.
  • ARP 요청/응답의 흐름과 ARP 캐시의 역할, 그리고 ARP가 왜 스푸핑에 취약한지 설명할 수 있다.
  • MTU, 점보 프레임, CSMA/CD와 전이중의 관계를 이해한다.

2.1링크 계층이 하는 일

링크 계층은 하나의 물리적 링크(또는 스위치로 연결된 하나의 브로드캐스트 도메인) 안에서 프레임을 전달합니다. 1장에서 본 것처럼 IP는 "다음 홉이 누구인지"까지만 정하고, 실제로 그 홉에게 비트를 건네는 일은 링크 계층의 몫입니다. 핵심 기능은 네 가지입니다.

프레이밍(Framing)

비트 스트림에서 프레임의 시작과 끝을 구분한다. Ethernet은 Preamble/SFD와 프레임 간 간격(IFG)으로 해결.

주소 지정(Addressing)

48비트 MAC 주소로 링크 안의 NIC를 식별. 유니캐스트·멀티캐스트·브로드캐스트.

오류 검출(Error Detection)

FCS(CRC‑32)로 전송 중 손상된 프레임을 폐기. 재전송은 하지 않는다(TCP의 몫).

매체 접근 제어(MAC, Media Access Control)

공유 매체에서 누가 언제 보낼지 결정. 과거 CSMA/CD, 오늘날 전이중 스위칭으로 사실상 불필요.

📌 용어 주의

"MAC"은 두 가지 뜻으로 쓰입니다. ① Media Access Control(IEEE 802의 하위 계층 이름) ② 그 계층에서 쓰는 MAC 주소. 그 위에 LLC(Logical Link Control, 802.2)가 있지만, 인터넷 트래픽의 대부분은 LLC 없이 Ethernet II 프레임을 씁니다.

2.2Ethernet II 프레임 구조 (필드를 클릭하세요)

오늘날 IP 트래픽을 나르는 프레임은 거의 전부 Ethernet II(DIX) 형식입니다. 아래 도식은 전송 순서대로 필드를 배치했습니다. 물리 계층이 앞에 붙이는 Preamble(7바이트, 10101010…)과 SFD(1바이트, 10101011)는 수신 NIC의 클럭 동기화용이며, 소프트웨어(tcpdump 등)에서는 보이지 않습니다.

최소/최대 길이

헤더(14) + 페이로드(46~1500) + FCS(4) = 64~1518바이트. 46바이트 미만의 페이로드는 0으로 패딩됩니다. 64바이트 최소 길이는 CSMA/CD 충돌 검출을 위한 역사적 제약입니다(2.7절).

EtherType 주요 값

0x0800 IPv4 · 0x0806 ARP · 0x86DD IPv6 · 0x8100 802.1Q VLAN · 0x88CC LLDP · 0x8847 MPLS

값이 1536(0x0600) 이상이면 EtherType, 1500 이하이면 802.3 길이 필드로 해석합니다 — 두 형식을 한 필드로 구분하는 트릭입니다.

802.1Q VLAN 태그

스위치 포트를 논리적으로 나누는 VLAN은 Src MAC과 EtherType 사이에 4바이트 태그를 끼워 넣습니다. TPID 0x8100이 "다음은 VLAN 태그"라는 표시이고, 원래의 EtherType은 태그 뒤로 밀립니다. 그래서 태그된 프레임의 최대 길이는 1522바이트입니다.

2.3MAC 주소 해부 (인터랙티브)

MAC 주소는 48비트, 보통 xx:xx:xx:xx:xx:xx 16진수로 씁니다. 앞 24비트는 IEEE가 제조사에 배정한 OUI(Organizationally Unique Identifier), 뒤 24비트는 제조사가 부여한 일련번호입니다. 첫 바이트의 최하위 두 비트가 특별합니다.

  • I/G 비트(bit 0): 0 = 개별(Individual, 유니캐스트), 1 = 그룹(Group, 멀티캐스트). ff:ff:ff:ff:ff:ff는 전 비트 1인 브로드캐스트.
  • U/L 비트(bit 1): 0 = 전 세계 유일(Universally administered, 제조사 배정), 1 = 로컬 관리(Locally administered, VM·컨테이너·Wi‑Fi 무작위 주소 등 소프트웨어가 만든 주소).
첫 바이트는 전송 시 최하위 비트부터(LSB first) 나가므로, I/G 비트가 선로에서 가장 먼저 보이는 비트입니다. 수신 NIC는 첫 비트만 보고도 "내가 받을 그룹 주소인가"를 판별할 수 있습니다.
🔬 깊이 보기: IP 멀티캐스트 주소는 어떻게 MAC으로 바뀌나

IPv4 멀티캐스트 224.0.0.0/4는 OUI 01:00:5e 뒤에 IP 주소의 하위 23비트를 붙여 MAC을 만듭니다(RFC 1112). IP 멀티캐스트 주소는 28비트 가변이므로 5비트가 손실되어 32개의 IP 그룹이 하나의 MAC을 공유합니다 — 그래서 NIC 필터를 통과한 뒤 IP 계층이 한 번 더 걸러야 합니다. IPv6는 33:33 뒤에 하위 32비트를 붙입니다. 위 입력창에서 01:00:5e:7f:00:01을 넣으면 239.255.0.1, 239.127.0.1 등이 모두 같은 MAC이 됨을 떠올려 보세요.

2.4스위치는 어떻게 길을 배우는가 (시뮬레이터)

스위치는 설정 없이 꽂기만 해도 동작합니다. 비결은 투명 브리징(transparent bridging, IEEE 802.1D)의 세 동작입니다.

  1. 학습(Learning): 프레임이 들어오면 출발지 MAC과 들어온 포트를 MAC 테이블(CAM 테이블)에 기록한다. 기본 에이징 타임 300초.
  2. 포워딩/필터링(Forwarding/Filtering): 목적지 MAC을 테이블에서 찾아 해당 포트로만 내보낸다. 목적지가 들어온 포트와 같으면 버린다(필터링).
  3. 플러딩(Flooding): 목적지를 모르거나(unknown unicast) 브로드캐스트/멀티캐스트이면 들어온 포트를 제외한 모든 포트로 내보낸다.

⚠️ 스위치의 한계

플러딩 때문에 스위치로 묶인 네트워크는 하나의 브로드캐스트 도메인입니다. 호스트가 수천 대면 ARP·DHCP 브로드캐스트만으로도 부담이 커지고, 루프가 있으면 브로드캐스트 폭풍이 납니다(STP가 루프를 끊는 이유). 그래서 VLAN으로 도메인을 나누고, 도메인 사이는 라우터(L3)가 잇습니다. 또한 MAC 테이블을 가짜 주소로 가득 채우는 MAC flooding 공격을 받으면 스위치는 허브처럼 모든 프레임을 플러딩하게 됩니다.

2.5ARP: IP 주소 → MAC 주소 (애니메이션)

호스트가 "10.0.0.1에게 보내라"는 IP 패킷을 만들었어도, 프레임의 목적지 MAC을 모르면 보낼 수 없습니다. ARP(Address Resolution Protocol, RFC 826)는 같은 링크 안에서 "이 IP 가진 사람 MAC 알려줘"라고 브로드캐스트로 묻고, 당사자만 유니캐스트로 답하는 단순한 프로토콜입니다. ARP는 IP 위가 아니라 Ethernet 바로 위(EtherType 0x0806)에 실립니다.

💡 ARP 캐시

해석 결과는 캐시에 보관됩니다(Linux 기본 reachable 시간 약 30초 + 상태 머신, macOS 약 20분). 캐시가 없으면 패킷마다 브로드캐스트가 나가므로, 캐시는 ARP 트래픽을 수백 배 줄입니다. 요청을 받은 쪽(C)도 요청자의 주소를 학습한다는 점에 주목하세요 — 어차피 답장을 보내야 하기 때문입니다.

📌 Proxy ARP와 게이트웨이

목적지가 다른 네트워크이면 호스트는 서버가 아니라 게이트웨이 IP에 대해 ARP를 보냅니다. 일부 환경에서는 라우터가 남의 IP에 대해 대신 답하는 Proxy ARP(RFC 1027)를 쓰기도 합니다.

🔬 깊이 보기: ARP는 왜 스푸핑에 취약한가

ARP에는 인증이 없고, 상태도 없습니다. 대부분의 구현은 "요청한 적 없는 응답"이나 "다른 호스트가 보낸 요청의 sender 필드"까지 캐시에 반영합니다(성능을 위해). 공격자가 "10.0.0.1은 내 MAC이다"라는 ARP 응답을 계속 뿌리면, 피해자는 게이트웨이로 보내는 모든 프레임을 공격자에게 보냅니다 — ARP spoofing / 중간자 공격. 방어: 스위치의 Dynamic ARP Inspection(DHCP 스누핑 테이블과 대조), 정적 ARP 항목, 802.1X, 그리고 무엇보다 상위 계층 암호화(TLS)입니다. 링크 계층을 믿지 말라는 종단 간 원칙의 실례입니다.

🔬 깊이 보기: Gratuitous ARP

자기 자신의 IP를 묻는(또는 알리는) ARP를 Gratuitous ARP라 합니다. 쓰임새는 세 가지: ① 부팅 시 IP 충돌 감지(누군가 답하면 충돌), ② 다른 호스트들의 캐시 갱신(NIC 교체, VM 라이브 마이그레이션 후), ③ VRRP/HSRP 장애 조치 — 새 마스터 라우터가 가상 IP의 MAC을 자기 것으로 알려 트래픽을 즉시 끌어옵니다. 모두 "요청하지 않은 정보를 캐시에 반영"하는 성질을 선의로 쓰는 경우입니다.

2.6MTU와 점보 프레임

MTU(Maximum Transmission Unit)는 링크 계층이 한 프레임에 실을 수 있는 페이로드(IP 패킷)의 최대 크기입니다. Ethernet 표준 MTU는 1500바이트이며, 이 값은 1980년대 메모리 비용과 지연 사이의 타협의 산물입니다.

MTU가 크면 패킷당 헤더 오버헤드와 CPU 인터럽트가 줄어 처리량이 늘지만, 한 프레임이 선로를 점유하는 시간이 길어지고 한 비트 오류로 잃는 데이터가 커집니다. MTU가 경로 중간에서 줄어들 때 생기는 단편화 문제는 3장(IP 단편화·PMTUD)에서 다룹니다.

2.7CSMA/CD에서 전이중 스위칭으로

초기 Ethernet(10BASE5, 10BASE2, 허브)은 하나의 동축 케이블을 모든 호스트가 공유했습니다. 두 호스트가 동시에 보내면 신호가 겹쳐 깨지므로(충돌), CSMA/CD(Carrier Sense Multiple Access with Collision Detection)로 조율했습니다.

CSMA/CD 동작. 최소 프레임 64바이트는 "전송이 끝나기 전에 충돌을 감지"하기 위해 필요한 길이(10 Mbps, 최대 2.5 km 왕복 전파 시간)에서 나왔다.

스위치는 각 포트가 독립된 충돌 도메인이 되게 하고, 한 포트에 한 장치만 연결되면 전이중(full duplex)으로 동시에 송수신할 수 있습니다. 전이중에서는 충돌이 원천적으로 없으므로 CSMA/CD는 꺼집니다. 기가비트 이상의 Ethernet 규격은 전이중만 정의하며, 64바이트 최소 길이는 호환성을 위해 남았습니다. 흐름 제어가 필요하면 802.3x PAUSE 프레임(또는 데이터센터의 PFC)을 씁니다.

📌 Wi‑Fi는 다르다

무선(802.11)은 여전히 공유 매체입니다. 전파는 송신 중 충돌을 감지할 수 없어(자기 신호가 수신 신호를 덮음) CSMA/CA(충돌 회피: 짧은 대기 + RTS/CTS + ACK)를 씁니다. 그래서 Wi‑Fi에는 링크 계층 ACK와 재전송이 있고, 혼잡 시 지연 변동이 큽니다. TCP 성능 분석에서 "무선 구간은 다르다"고 말하는 이유입니다.

2.8실습: ARP 캐시와 프레임 헤더 관찰

# Linux — 상태(REACHABLE/STALE/DELAY)까지 보인다
ip neigh show
# 10.0.0.1 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE

# macOS
arp -a
# ? (10.0.0.1) at 0:11:22:33:44:55 on en0 ifscope [ethernet]

# 캐시 항목 삭제 → 다음 통신 때 ARP가 다시 나간다
sudo ip neigh del 10.0.0.1 dev eth0      # Linux
sudo arp -d 10.0.0.1                      # macOS
# -e : Ethernet 헤더(MAC, EtherType) 출력, -n : 이름 해석 생략
sudo tcpdump -e -n -i eth0 arp
# 00:11:22:aa:aa:aa > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42:
#     Request who-has 10.0.0.1 tell 10.0.0.5, length 28
# 00:11:22:33:44:55 > 00:11:22:aa:aa:aa, ethertype ARP (0x0806), length 42:
#     Reply 10.0.0.1 is-at 00:11:22:33:44:55, length 28

# VLAN 태그 보기 (트렁크 포트에서)
sudo tcpdump -e -n -i eth0 vlan

length 42 = Ethernet 헤더 14 + ARP 28. 최소 60바이트(FCS 제외)에 못 미치므로 실제 선로에서는 18바이트가 패딩되지만, tcpdump는 송신 측에서 패딩 전 길이를 보여줍니다.

# 터미널 1: ARP 캡처 대기
sudo tcpdump -e -n -i eth0 arp
# 터미널 2: 캐시 지우고 게이트웨이에 ping → Request/Reply 한 쌍이 보인다
sudo ip neigh del 10.0.0.1 dev eth0 && ping -c1 10.0.0.1

# Gratuitous ARP 직접 보내기 (Linux, iproute2)
sudo arping -U -I eth0 10.0.0.5

2.9이해도 점검

요약

  • Ethernet II 프레임: Dst MAC(6) · Src MAC(6) · EtherType(2) · 페이로드(46~1500) · FCS(4). 802.1Q 태그 4바이트는 Src MAC 뒤에 삽입.
  • MAC 주소 = OUI(24) + 일련번호(24). 첫 바이트의 I/G 비트가 멀티캐스트, U/L 비트가 로컬 관리 여부.
  • 스위치는 출발지 MAC으로 학습하고, 목적지 MAC으로 포워딩/필터링하며, 모르면 플러딩한다. 스위치 네트워크 = 하나의 브로드캐스트 도메인.
  • ARP는 브로드캐스트 요청·유니캐스트 응답으로 IP→MAC을 해석하고 캐시한다. 인증이 없어 스푸핑에 취약하다.
  • MTU 1500은 타협의 산물. 전이중 스위칭이 CSMA/CD를 대체했지만 64바이트 최소 길이는 남았다.
