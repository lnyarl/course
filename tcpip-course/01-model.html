PART 1 · 개론 — CHAPTER 01

네트워크와 TCP/IP 모델

인터넷의 모든 통신은 "계층"이라는 약속 위에서 이뤄집니다. 이 장에서는 TCP/IP가 왜 계층으로 설계되었는지, 데이터가 각 계층을 지나며 어떻게 포장(캡슐화)되는지, 그리고 한 패킷이 두 호스트 사이를 어떻게 여행하는지를 애니메이션으로 봅니다.

⏱ 약 50분응용전송인터넷링크

학습 목표

  • OSI 7계층과 TCP/IP 4계층의 대응 관계를 설명하고, 각 계층의 PDU(프로토콜 데이터 단위) 이름을 말할 수 있다.
  • 캡슐화·역캡슐화 과정을 헤더 단위로 그릴 수 있다.
  • 스위치·라우터·호스트가 각각 어느 계층까지 패킷을 들여다보는지 설명할 수 있다.
  • MAC 주소·IP 주소·포트 번호의 역할 차이를 설명할 수 있다.
  • 종단 간 원칙(end-to-end principle)과 최선형(best-effort) 전달의 의미를 이해한다.

1.1인터넷과 TCP/IP의 탄생

TCP/IP는 특정 회사의 제품이 아니라 공개 표준(RFC)으로 자라난 프로토콜 군(suite)입니다. 처음부터 "서로 다른 네트워크를 연결(inter-network)"하는 것이 목적이었고, 그 설계 철학이 지금도 인터넷을 지탱합니다.

1969
ARPANET 첫 노드 연결(UCLA–SRI). 패킷 교환(packet switching) 개념의 실증.
1974
Vint Cerf · Bob Kahn, "A Protocol for Packet Network Intercommunication" 발표. TCP의 원형. 이후 신뢰성(TCP)과 전달(IP)을 분리하는 설계로 발전.
1981
RFC 791(IP), RFC 793(TCP) 발행. 오늘날 쓰는 헤더 형식이 사실상 확정됨.
1983. 1. 1
"Flag Day": ARPANET이 NCP에서 TCP/IP로 전면 전환. 같은 해 DNS(RFC 882/883) 제안.
1989–91
BGP(RFC 1105), HTTP/WWW 등장. 상용 인터넷의 시작.
1993
CIDR(RFC 1519)로 클래스 기반 주소 체계 폐기. 주소 고갈 완화.
1998 / 2017
IPv6 규격 RFC 2460 → RFC 8200(표준). 2011년 IANA IPv4 풀 고갈.
2021–22
QUIC(RFC 9000), HTTP/3(RFC 9114). TCP 규격 통합본 RFC 9293 발행.
💡 전문가의 관점

TCP/IP의 성공 비결은 성능이 아니라 "느슨한 결합"입니다. IP는 아무것도 보장하지 않고(best effort), 신뢰성은 종단(TCP)이 책임집니다. 덕분에 중간 네트워크는 단순해졌고, 어떤 물리 매체(전화선, 이더넷, Wi‑Fi, 위성)도 그 아래에 끼워 넣을 수 있었습니다.

1.2왜 계층(layer)인가

통신에는 해결해야 할 문제가 너무 많습니다. 비트를 전기 신호로 바꾸기, 같은 선에 연결된 이웃을 구분하기, 전 세계 어디로든 길 찾기, 잃어버린 데이터 다시 보내기, 웹 페이지 형식 정하기… 이것을 하나의 거대한 프로그램으로 만들면 아무도 유지보수할 수 없습니다.

계층화는 이 문제를 관심사별로 분리하고, 각 층이 바로 아래 층의 서비스만 사용하도록 제한합니다. 핵심 규칙은 세 가지입니다.

  1. 각 층은 아래 층의 서비스를 이용하고, 위 층에 서비스를 제공한다. (TCP는 IP를 이용하고, HTTP에 서비스를 제공)
  2. 같은 층끼리 대화한다. 내 TCP는 상대방 TCP와 대화한다고 "느낀다"(peer-to-peer). 실제 데이터는 아래로 내려갔다가 올라온다.
  3. 층의 구현을 바꿔도 다른 층에 영향이 없다. Wi‑Fi를 Ethernet으로 바꿔도 HTTP 코드는 그대로다.

1.3OSI 7계층 vs TCP/IP 4계층 (인터랙티브)

OSI 모델은 ISO가 만든 "교과서적" 참조 모델이고, TCP/IP 모델은 실제 구현에서 나온 모델입니다. 현업에서는 OSI의 용어(L2 스위치, L3 라우터, L4 로드밸런서, L7 방화벽)를 쓰고, 프로토콜은 TCP/IP를 씁니다. 아래에서 각 층을 클릭해 보세요.

층을 클릭하세요

역할, 대표 프로토콜, PDU 이름, 주소 체계, 대표 장비를 보여줍니다.

📌 용어 정리: PDU

각 층이 다루는 데이터 덩어리의 이름이 다릅니다. 응용 = 메시지(message), 전송 = 세그먼트(TCP) / 데이터그램(UDP), 인터넷 = 패킷(packet, 정확히는 IP 데이터그램), 링크 = 프레임(frame), 물리 = 비트. 대화할 때 "패킷"을 두루뭉술하게 쓰긴 하지만, 전문가는 어느 층의 단위인지 구분해서 말합니다.

1.4캡슐화와 역캡슐화 (애니메이션)

송신 측에서 데이터는 위에서 아래로 내려가며 각 층의 헤더가 앞에 붙습니다(링크 계층은 뒤에 트레일러도 붙임). 수신 측에서는 아래에서 위로 올라가며 헤더가 하나씩 벗겨집니다. 각 헤더는 "내 바로 위 층에 이 데이터를 누구에게 줄지"를 담고 있습니다.

🔬 깊이 보기: 왜 헤더는 "앞"에 붙는가

헤더가 앞에 있으면 수신 장비가 패킷 전체를 받기 전에 처리 방향을 결정할 수 있습니다(스위치의 cut-through 포워딩). 반대로 오류 검출용 FCS(Frame Check Sequence)는 끝에 두어, 송신 측이 데이터를 내보내면서 동시에 CRC를 계산할 수 있게 합니다. 헤더 배치 하나에도 하드웨어 파이프라인 관점이 들어 있습니다.

1.5패킷의 여행: 호스트 → 스위치 → 라우터 → 호스트 (애니메이션)

이제 한 패킷이 네트워크를 가로지르는 모습을 보겠습니다. 핵심은 장비마다 들여다보는 깊이가 다르다는 것입니다. 스위치는 프레임(L2)만, 라우터는 패킷(L3)까지, 종단 호스트는 응용(L7)까지 열어봅니다. 그리고 IP 주소는 끝까지 유지되지만 MAC 주소는 홉(hop)마다 바뀝니다.

🔁 홉마다 바뀌는 것

Ethernet 헤더(src/dst MAC)는 라우터를 지날 때마다 완전히 새로 만들어집니다. TTL은 1씩 줄고, 그에 따라 IP 헤더 체크섬도 다시 계산됩니다.

🔒 끝까지 유지되는 것

src/dst IP 주소(NAT가 없다면), TCP 헤더, 응용 데이터는 중간 장비가 건드리지 않습니다. 이것이 "IP는 종단 간 주소, MAC은 다음 홉 주소"라는 말의 의미입니다.

1.6세 가지 주소: MAC · IP · 포트

캡슐화 애니메이션에서 본 것처럼, 각 계층은 자기만의 주소를 갖습니다. 세 주소의 범위(scope)가 다르다는 점이 핵심입니다.

주소계층길이·표기범위누가 정하나비유
MAC 주소링크(L2)48 bit, 00:1a:2b:3c:4d:5e같은 링크(LAN) 안에서만 의미제조사(OUI) + 장치 고유번호사람의 주민번호 — 전 세계 유일하지만 길 찾기엔 못 씀
IP 주소인터넷(L3)32 bit(v4) 192.0.2.10 / 128 bit(v6)전 세계(라우팅 가능)네트워크 관리자/ISP/DHCP, 위치에 따라 바뀜집 주소 — 이사하면 바뀌지만 우체부가 길을 찾는 기준
포트 번호전송(L4)16 bit, 0–65535한 호스트 안의 프로세스 구분서버는 잘 알려진 포트(80, 443…), 클라이언트는 임시 포트아파트 호수 — 같은 주소 안에서 받는 사람 구분
⚠️ 흔한 오해

"MAC 주소는 바뀌지 않으니 그걸로 라우팅하면 되지 않나?" — MAC은 계층 구조가 없습니다. 전 세계 수십억 장치의 MAC을 라우터가 모두 외워야 하죠. IP 주소는 앞부분(네트워크 프리픽스)으로 묶을 수 있어서, 라우터는 "203.0.113.0/24는 저쪽" 식으로 집계(aggregation)할 수 있습니다. 3장에서 자세히 다룹니다.

1.7TCP/IP를 떠받치는 설계 원칙

종단 간 원칙 (End-to-End Principle)

신뢰성·순서·보안 같은 기능은 통신의 양 끝(호스트)에서 구현해야 완전해진다. 네트워크 중간에서 아무리 노력해도 종단이 다시 검증해야 하므로, 중간은 단순하게 두고 끝에 지능을 둔다. (Saltzer, Reed, Clark 1984)

최선형 전달 (Best-Effort)

IP는 패킷을 잃어버리거나, 순서를 바꾸거나, 중복시킬 수 있다. 어떤 보장도 하지 않는 대신 어디서든 동작한다. 보장이 필요하면 위 층(TCP)이 책임진다.

견고성 원칙 (Postel's Law)

"보낼 때는 보수적으로, 받을 때는 관대하게." (RFC 761) 상호운용성의 바탕이 되었지만, 오늘날에는 모호한 입력을 관대하게 받아들이면 보안 취약점이 된다는 반성도 있다(RFC 9413).

모래시계 모델 (Hourglass)

위로는 수많은 응용, 아래로는 수많은 링크 기술, 허리에는 오직 IP 하나. 모든 것이 IP 위에서 돌아가므로 "IP 위에 올리기만 하면" 인터넷에 참여할 수 있다. 이 좁은 허리가 IPv6 전환을 어렵게 만든 이유이기도 하다.

모래시계: 모든 응용과 모든 링크 기술이 IP라는 하나의 허리를 통과한다.

1.8실습: 내 컴퓨터에서 세 주소 확인하기

터미널에서 아래 명령을 실행해 MAC·IP·포트를 직접 찾아보세요.

# 인터페이스별 MAC(ether)와 IP(inet)
ifconfig en0
# 기본 게이트웨이(라우터) — 패킷이 LAN을 벗어날 때 가는 첫 홉
netstat -rn | grep default
# 현재 열린 TCP 연결과 포트
netstat -an -p tcp | head
# 게이트웨이의 MAC 주소 (ARP 캐시)
arp -a
ip -br link        # MAC 주소
ip -br addr        # IP 주소
ip route           # 라우팅 테이블 (default via … 가 게이트웨이)
ss -tn             # 열린 TCP 연결 (로컬/원격 포트)
ip neigh           # ARP 캐시
ipconfig /all      # 물리적 주소(MAC), IPv4 주소, 기본 게이트웨이
route print        # 라우팅 테이블
netstat -an        # 연결과 포트
arp -a             # ARP 캐시
✅ 확인 질문

① 내 기본 게이트웨이의 IP와 MAC은 무엇인가? ② 브라우저로 아무 사이트나 연 뒤 ss -tn/netstat에서 원격 포트가 443인 연결을 찾아보라. 로컬 포트는 몇 번인가? (임시 포트 범위에 속하는지 확인)

1.9이해도 점검

요약

  • TCP/IP는 서로 다른 네트워크를 잇기 위해 계층으로 설계되었고, 각 층은 아래 층의 서비스만 이용한다.
  • OSI 7계층은 용어, TCP/IP 4계층은 실제 구현. PDU: 메시지 → 세그먼트/데이터그램 → 패킷 → 프레임 → 비트.
  • 송신은 헤더를 붙이며 내려가고(캡슐화), 수신은 벗기며 올라간다(역캡슐화).
  • 스위치는 L2, 라우터는 L3, 호스트는 L7까지 본다. MAC은 홉마다 바뀌고 IP는 종단 간 유지된다.
  • 종단 간 원칙 · 최선형 전달 · 모래시계 모델이 인터넷의 확장성을 만들었다.
