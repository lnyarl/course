IPv6

IPv6는 "주소가 길어진 IPv4"가 아닙니다. 헤더를 고정 길이로 단순화하고, 단편화를 종단으로 밀어내고, ARP·DHCP·ICMP의 역할을 ICMPv6 하나로 재편했으며, 호스트가 스스로 주소를 만들어 쓰도록 설계했습니다. 이 장은 그 설계 결정의 이유를 중심으로 IPv6를 익힙니다.

⏱ 약 80분인터넷링크RFC 8200 · 4291 · 5952 · 4861 · 4862 · 8981 · 6146 · 8305

학습 목표

  • IPv6 주소를 RFC 5952 규칙대로 축약·전개하고, 주소 유형을 프리픽스만 보고 판별할 수 있다.
  • IPv4와 IPv6 헤더를 필드 단위로 비교하고, 사라진 필드의 이유를 설명할 수 있다.
  • NDP(이웃 탐색)가 ARP와 DHCP의 역할을 어떻게 대체하는지 패킷 흐름으로 설명할 수 있다.
  • SLAAC로 호스트가 주소를 얻는 전 과정(링크로컬 → DAD → RA → GUA)을 그릴 수 있다.
  • Dual Stack · 터널링 · NAT64/DNS64의 동작과 적용 상황을 구분할 수 있다.

10.1왜 IPv6인가: 2³²의 한계

IPv4 주소는 약 43억 개입니다. 1990년대 초 이미 클래스 B 고갈이 예측되었고, CIDR(1993)과 NAT(1994)로 수명을 20년 이상 연장했지만 2011년 2월 IANA의 중앙 풀이, 2019년 11월 RIPE NCC의 마지막 /22가 소진되었습니다. 오늘날 IPv4 주소는 거래 시장에서 개당 수십 달러에 팔립니다.

IETF는 1990년대 중반 IPng 작업에서 "주소만 늘리자"가 아니라 20년간 드러난 IPv4의 설계 부채를 함께 정리하기로 했습니다(RFC 1752 → RFC 2460 → RFC 8200). 결과는 다음 네 가지로 요약됩니다.

주소 공간 128비트

3.4 × 10³⁸개. 지구 표면 1 m²당 6.7 × 10²³개. 목적은 "모자라지 않게"가 아니라 계층적 집계와 자동 구성을 위한 여유다. 서브넷 하나가 /64 = 1.8 × 10¹⁹개.

헤더 단순화

필드 13개 → 8개. 길이 가변(20–60) → 고정 40바이트. 라우터가 체크섬 재계산·단편화를 하지 않는다. 옵션은 확장 헤더 체인으로.

자동 구성 내장

DHCP 서버 없이 라우터 광고(RA)만으로 호스트가 주소를 만든다(SLAAC). 링크로컬 주소는 라우터조차 없어도 생긴다.

종단 간 복원

NAT가 필요 없으므로 모든 호스트가 전역 주소를 가진다. P2P·IoT·IPsec이 NAT 통과 없이 동작한다. (방화벽은 여전히 필요하다 — 주소 도달성과 접근 허용은 별개.)

10.2주소 표기와 축약 (인터랙티브)

128비트를 16비트씩 8그룹으로 나눠 16진수로 쓰고 콜론으로 구분합니다. RFC 5952는 사람마다 다르게 쓰던 표기를 하나의 정규형으로 통일했습니다.

  1. 각 그룹의 선행 0은 생략한다. 0db8 → db8, 0000 → 0.
  2. 연속된 0 그룹은 ::로 한 번만 줄인다. 가장 긴 연속 구간을 택하고, 길이가 같으면 앞쪽을 택한다. 0 그룹 하나는 ::로 줄이지 않는다.
  3. 16진수는 소문자.
  4. URL에서는 포트와 구분하기 위해 대괄호: http://[2001:db8::1]:8080/.

10.3주소 유형: 프리픽스로 읽는다

IPv6에는 브로드캐스트가 없습니다. "모두에게"는 멀티캐스트 ff02::1(링크의 모든 노드)로 대신하고, 그 밖의 모든 일대다 통신도 멀티캐스트로 합니다. 또 하나의 특징은 인터페이스가 여러 주소를 동시에 갖는 것이 정상이라는 점입니다(링크로컬 1개 + GUA 1개 이상 + 임시 주소들).

프리픽스유형범위설명
2000::/3Global Unicast (GUA)전역인터넷 라우팅 가능. 2000:–3fff:로 시작. ISP/RIR에서 할당 (보통 /48 조직, /56 가정, /64 서브넷).
fc00::/7Unique Local (ULA)사이트IPv4 사설 주소의 대응물. 실제로는 fd00::/8(L 비트=1)만 사용, 40비트 Global ID를 무작위 생성해 조직 합병 시 충돌을 피한다(RFC 4193).

📌 Anycast

IPv6는 유니캐스트 주소를 여러 인터페이스에 할당하는 anycast를 공식 지원합니다(별도 주소 공간 없음). 가장 가까운 인스턴스로 라우팅되므로 DNS 루트 서버(13개 주소, 1,900개 이상 인스턴스), CDN, DDoS 흡수에 쓰입니다. IPv4에서도 BGP로 같은 효과를 내지만, IPv6는 서브넷-라우터 anycast(프리픽스::0)를 규격에 넣었습니다.

10.4주소 구조와 인터페이스 식별자 (인터랙티브)

GUA는 세 부분으로 나뉩니다. 핵심은 인터페이스 ID가 64비트로 고정되어 있어 하위 64비트를 호스트가 스스로 만들 수 있다는 점입니다. 이것이 SLAAC의 전제입니다.

/48을 받은 조직은 서브넷 ID 16비트로 65,536개의 /64를 만들 수 있습니다. IPv4처럼 "호스트 수에 맞춰 서브넷을 쪼개는" 계산은 하지 않습니다. 모든 서브넷은 /64입니다(점대점 링크에 /127을 쓰는 예외 RFC 6164 제외).

인터페이스 ID 만들기: Modified EUI-64

초기 방식(RFC 4291 부록 A)은 48비트 MAC을 64비트로 늘립니다. 가운데에 ff:fe를 끼우고, 첫 바이트의 U/L 비트(0x02)를 반전합니다. 반전하는 이유: 관리자가 손으로 ::1, ::2처럼 짧은 주소를 쓸 때 "로컬 관리"를 뜻하는 0을 자연스럽게 쓰도록, 제조사 MAC에서 온 주소는 1이 되게 한 것입니다.

🔬 깊이 보기: Privacy Extensions(RFC 8981)와 안정적 비밀 주소(RFC 7217)

EUI-64 주소는 MAC을 그대로 드러냅니다. 노트북이 집·카페·회사를 옮겨 다녀도 하위 64비트가 같으므로 어떤 사이트든 사용자를 추적할 수 있습니다. RFC 4941(→ 8981)은 하위 64비트를 무작위로 만든 임시 주소를 주기적으로(기본 1일) 바꿔 가며 나가는 연결에 쓰도록 합니다. 들어오는 연결용 안정 주소도 MAC 대신 (프리픽스, 인터페이스, 비밀키)의 해시로 만드는 RFC 7217이 권장됩니다. 리눅스 net.ipv6.conf.*.use_tempaddr=2, addr_gen_mode=3(stable-privacy)이 그 설정입니다. 현대 OS는 모두 기본으로 켜져 있어, 실제 ip -6 addr 출력에서 EUI-64 주소를 보기는 오히려 어렵습니다.

10.5IPv4 vs IPv6 헤더 (인터랙티브)

두 헤더를 나란히 놓고 비교합니다. 필드를 클릭해 보세요. IPv6에서 사라진 필드(IHL, Identification, Flags, Fragment Offset, Header Checksum, Options)와 이름이 바뀐 필드(TTL → Hop Limit, Protocol → Next Header, Total Length → Payload Length), 그리고 새로 생긴 Flow Label을 주목하세요.

🔬 깊이 보기: 왜 IPv6에는 헤더 체크섬이 없나

IPv4 체크섬은 TTL이 1 줄 때마다 라우터가 다시 계산해야 합니다(증분 갱신 RFC 1624로 비용은 작지만 0은 아님). 그런데 이 체크섬이 잡아내는 오류는 거의 모두 링크 계층 CRC-32가 먼저 잡고, 잡지 못한 오류는 TCP/UDP 체크섬이 다시 잡습니다. 즉 삼중 보호 중 가장 약한 16비트 1의 보수 합을 빼도 안전성이 거의 줄지 않습니다. 대신 IPv4에서 선택이었던 UDP 체크섬을 IPv6에서는 필수로 만들어(RFC 8200 §8.1) 주소 오류가 상위 계층에서 반드시 잡히게 했습니다. 전송 계층 의사 헤더에 128비트 주소가 들어가므로 IP 헤더가 깨져 엉뚱한 호스트에 도착해도 체크섬이 실패합니다. 터널 캡슐화 등으로 UDP 체크섬 0이 꼭 필요한 경우를 위한 예외가 RFC 6935/6936입니다.

10.6확장 헤더 체인

IPv6 헤더의 Next Header는 "다음에 오는 것"의 번호입니다. 확장 헤더가 있으면 그 번호, 없으면 바로 전송 프로토콜(TCP 6, UDP 17, ICMPv6 58)입니다. 각 확장 헤더도 자기 Next Header를 가지므로 연결 리스트처럼 이어집니다. 권장 순서(RFC 8200 §4.1)가 있으며, Hop-by-Hop은 반드시 첫 번째여야 합니다 — 경로상의 모든 라우터가 봐야 하기 때문입니다.

⚠️ 확장 헤더의 현실

라우터·방화벽은 전송 헤더를 찾기 위해 체인을 끝까지 따라가야 합니다. 체인이 길거나 Fragment 헤더 뒤에 전송 헤더가 숨어 있으면 하드웨어 파서가 포기하고 패킷을 버리는 장비가 많습니다(RFC 7872 측정: 인터넷 경로의 수십 %에서 드롭). Routing Header Type 0은 증폭 공격에 악용되어 폐기되었습니다(RFC 5095). 실무에서 확장 헤더는 Fragment, ESP/AH, 그리고 세그먼트 라우팅(SRv6, Routing Type 4) 정도만 쓰입니다.

10.8SLAAC: 서버 없는 주소 자동 구성 (애니메이션)

호스트는 전원이 켜지면 아무 도움 없이 링크로컬 주소를 만들고, 라우터에게 프리픽스를 물어 전역 주소를 완성합니다(RFC 4862). DHCPv6(RFC 8415)는 선택 사항이며, RA의 두 플래그가 어느 쪽을 쓸지 알려 줍니다.

10.9전환 기술: 두 세계를 잇는 세 가지 방법

① Dual Stack

호스트와 네트워크가 IPv4·IPv6를 동시에 운용. 가장 단순하고 성능 손실 없음. 단점: IPv4 주소가 여전히 필요하므로 고갈 문제 자체는 해결 못 함. 오늘날 대부분의 ISP·클라우드 방식.

② 터널링

IPv6 패킷을 IPv4 패킷 안에 캡슐화해 IPv4 전용 구간을 통과. 6in4(프로토콜 41, 수동), 6to4(2002::/16, 폐기 RFC 7526), Teredo(UDP, NAT 통과, 폐기 수순), 6rd(ISP용, RFC 5969). 반대 방향(IPv4 in IPv6)은 DS-Lite(RFC 6333), MAP-E/T.

③ 변환 (NAT64/DNS64)

IPv6 전용 호스트가 IPv4 전용 서버와 통신하도록 헤더를 번역. 모바일 통신사(T-Mobile US 등)와 애플의 IPv6-only 네트워크 요구 사항의 핵심. 464XLAT(RFC 6877)는 IPv4 전용 앱까지 지원.

NAT64 + DNS64 동작 (애니메이션)

🔬 깊이 보기: 단편화를 종단에만 맡긴 이유와 최소 MTU 1280

IPv4 라우터는 MTU가 작은 링크를 만나면 패킷을 쪼갭니다. 이 작업은 라우터 CPU를 쓰고, 조각 하나만 잃어도 전체를 재전송해야 하며, 조각 재조립은 방화벽 우회(RFC 1858 tiny fragment)와 DoS의 온상이었습니다. IPv6는 라우터의 단편화를 금지하고(DF가 항상 켜진 셈), 송신자가 PMTUD(RFC 8201)로 경로 MTU를 알아내 필요하면 Fragment 확장 헤더로 직접 쪼개게 했습니다. 그리고 "모든 IPv6 링크는 최소 1280바이트를 단편화 없이 전달해야 한다"고 못 박았습니다(RFC 8200 §5). 1280은 IPv4 최소 576보다 크면서도 터널 오버헤드(IPv6 40 + 각종 캡슐화)를 감안해 1500에서 여유를 둔 값입니다. 따라서 "1280으로 보내면 어디든 통한다"가 보장되며, PMTUD 블랙홀이 의심되면 MTU를 1280으로 내리는 것이 표준 대응입니다. 반대로 ICMPv6 Packet Too Big(Type 2)을 방화벽이 막으면 IPv6는 IPv4보다 더 심하게 깨집니다 — 라우터가 대신 쪼개 주는 안전망이 없기 때문입니다.

10.10Happy Eyeballs: 느린 IPv6를 숨기는 법

Dual stack 호스트가 IPv6 연결을 먼저 시도했는데 경로가 깨져 있으면, 타임아웃(수십 초) 뒤에야 IPv4로 넘어가 사용자는 "IPv6를 켜니 느려졌다"고 느낍니다. Happy Eyeballs v2(RFC 8305)는 이를 해결합니다.

  1. AAAA와 A 질의를 동시에 보낸다. AAAA가 먼저 오면 바로 진행, A가 먼저 오면 AAAA를 50 ms만 더 기다린다.
  2. 주소 목록을 정렬(RFC 6724)하되 IPv6 우선. 첫 주소로 TCP connect()를 시작한다.
  3. 250 ms(Connection Attempt Delay) 안에 연결되지 않으면 다음 주소(보통 IPv4)로 병렬로 시도한다. 먼저 성공한 쪽을 쓰고 나머지는 닫는다.
  4. 결과를 캐시해 다음에는 성공했던 패밀리를 먼저 시도한다.

브라우저(Chrome, Firefox, Safari)와 macOS/iOS 소켓 API(connectx), curl(--happy-eyeballs-timeout-ms)이 구현합니다. 효과: 인터넷의 IPv6 경로 중 일부가 깨져 있어도 사용자는 알아채지 못합니다. 부작용: 그 덕분에 깨진 IPv6가 방치되기도 합니다.

10.11실습

# 인터페이스의 IPv6 주소들 — 링크로컬(fe80), GUA, 임시 주소(temporary), 유효 기간(valid_lft/preferred_lft)
ip -6 addr show
# 라우팅 테이블: default via fe80::... 인 것이 정상
ip -6 route
# 이웃 캐시 (ARP 캐시의 대응물) — 상태 REACHABLE/STALE/DELAY/PROBE 확인
ip -6 neigh
# 링크로컬로 핑: zone ID(%인터페이스) 필수. ff02::1 은 링크의 모든 노드
ping -6 fe80::1%eth0
ping -6 ff02::1%eth0
# 전역 연결 확인과 PMTUD 테스트
ping -6 -M do -s 1400 2001:4860:4860::8888
traceroute -6 ipv6.google.com
# DNS
dig AAAA www.google.com +short
dig AAAA ipv4only.arpa     # NAT64 환경이면 64:ff9b::... 가 합성되어 나온다 (RFC 7050)
# RA 받아 보기 / NDP 패킷 캡처
sudo rdisc6 eth0
sudo tcpdump -i eth0 -vv 'icmp6 and (ip6[40] == 133 or ip6[40] == 134 or ip6[40] == 135 or ip6[40] == 136)'
# 주요 sysctl
sysctl net.ipv6.conf.all.forwarding          # 1이면 라우터 모드 → RA를 무시한다!
sysctl net.ipv6.conf.eth0.accept_ra          # 0 끔, 1 호스트, 2 forwarding이어도 수락
sysctl net.ipv6.conf.eth0.use_tempaddr       # 2 = 임시 주소 생성 + 우선 사용
sysctl net.ipv6.conf.eth0.addr_gen_mode      # 0 EUI-64, 2 stable-privacy(secret 필요), 3 stable-privacy 자동
✅ 확인 질문

① 내 인터페이스의 링크로컬 주소가 EUI-64 방식인가, 무작위인가? (ff:fe가 가운데 있는지 보라.) ② ip -6 neigh에서 라우터 항목의 MAC과 ip -6 route의 default via 주소를 대조해 보라. ③ dig AAAA ipv4only.arpa의 결과로 현재 네트워크에 NAT64가 있는지 판단해 보라.

10.12이해도 점검

요약

  • 128비트 주소, 16진수 8그룹. RFC 5952: 선행 0 제거, 가장 긴 0 구간 하나만 ::(동률이면 앞), 소문자.
  • GUA 2000::/3, ULA fd00::/8, 링크로컬 fe80::/10, 멀티캐스트 ff00::/8. 브로드캐스트 없음. 서브넷은 항상 /64.
  • 헤더 40바이트 고정. 체크섬·라우터 단편화·IHL 삭제, 옵션은 확장 헤더 체인(Hop-by-Hop이 첫 번째), Flow Label 신설.
  • NDP(ICMPv6 133–137)가 ARP·라우터 발견·리다이렉트·DAD·NUD를 통합. NS는 solicited-node 멀티캐스트 ff02::1:ffXX:XXXX로.
  • SLAAC: 링크로컬 생성 → DAD → RS → RA(프리픽스, M/O 플래그) → GUA. 기본 라우터는 RA 송신자의 링크로컬 주소.
  • 전환: Dual Stack(주류), 터널링(6in4, 6rd, DS-Lite), 변환(NAT64/DNS64, 464XLAT). Happy Eyeballs가 깨진 IPv6를 가려 준다.
