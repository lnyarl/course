응용 계층과 소켓

드디어 사람이 쓰는 층입니다. 이 장에서는 HTTP를 해부하고, 브라우저에 URL을 입력한 순간부터 화면이 그려질 때까지 몇 번의 왕복(RTT)이 필요한지 세어 봅니다. 그리고 프로그램이 TCP를 다루는 창구인 소켓 API가 TCP 상태 머신과 어떻게 맞물리는지 봅니다.

⏱ 약 60분응용전송RFC 9110 · 9112 · 9113

학습 목표

  • HTTP/1.1 요청·응답 메시지의 각 줄이 무엇을 뜻하는지 설명할 수 있다.
  • 웹 페이지 한 번 로드에 필요한 RTT 수를 단계별로 계산할 수 있다.
  • socket/bind/listen/accept/connect가 TCP 상태 머신의 어떤 전이에 대응하는지 안다.
  • SYN 큐·accept 큐(backlog)의 역할과, 넘쳤을 때의 증상을 설명할 수 있다.
  • HTTP/1.1, HTTP/2, HTTP/3의 연결 모델 차이와 HOL blocking을 설명할 수 있다.

6.1통신 구조: 클라이언트-서버와 P2P

응용 계층 프로토콜은 "누가 먼저 말을 거는가"로 두 구조로 나뉩니다. 전송 계층 관점에서 서버 = listen()하는 쪽, 클라이언트 = connect()하는 쪽입니다. 역할은 고정된 기계가 아니라 연결마다 정해집니다.

📌 NAT 뒤의 피어

P2P의 가장 큰 현실적 장애물은 NAT입니다. 집 안의 두 피어는 서로 listen()해도 외부에서 connect()할 수 없습니다. 그래서 STUN/TURN/ICE 같은 "구멍 뚫기" 기법이 필요하고, 5장에서 본 동시 열기(simultaneous open)가 실제로 쓰입니다. 12장에서 다룹니다.

6.3연결 관리의 진화: Keep-Alive → 파이프라이닝 → 멀티플렉싱

HTML 하나에 이미지·CSS·JS가 수십 개 딸려옵니다. 리소스마다 TCP 연결을 새로 맺으면 handshake 비용(1 RTT + slow start)을 매번 치릅니다. HTTP 버전이 올라가며 연결 하나를 얼마나 알뜰하게 쓰는지가 달라졌습니다.

🔬 깊이 보기: HOL blocking은 왜 HTTP/2에서 남고 HTTP/3에서 사라지는가

HTTP/2는 하나의 TCP 연결 위에 여러 스트림을 프레임으로 섞어 보냅니다. 그런데 TCP는 하나의 바이트 스트림이라 세그먼트 하나가 유실되면, 뒤에 도착한 세그먼트들(다른 스트림 소속이라도)은 그 구멍이 메워질 때까지 응용에 전달되지 않습니다. 커널은 "어느 바이트가 어느 스트림인지" 모르기 때문입니다. QUIC은 스트림을 전송 계층 자체의 개념으로 끌어내렸습니다. 손실 복구가 스트림 단위로 일어나므로 스트림 A의 패킷이 유실되어도 스트림 B는 그대로 응용에 올라갑니다. 대가는 혼잡 제어·재전송을 UDP 위 사용자 공간에서 전부 다시 구현해야 한다는 것, 그리고 CPU 비용입니다(13장).

6.4URL 입력부터 화면까지: RTT를 세어 보자 (애니메이션)

네트워크 성능의 단위는 바이트/초가 아니라 왕복 횟수(RTT)인 경우가 많습니다. 한국↔미국 서부 RTT가 약 130ms라면, 5 RTT = 650ms. 아래 애니메이션은 캐시가 전혀 없는 첫 접속(cold start)을 가정합니다. RTT를 바꿔 총 소요 시간을 확인하세요.

최소 코드: Python

서버

import socket
srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("0.0.0.0", 8080))   # IP:port 고정
srv.listen(128)               # LISTEN 상태, backlog=128
while True:
    conn, addr = srv.accept()  # 완료된 연결 하나 꺼냄 (블록)
    data = conn.recv(4096)     # 바이트 스트림 일부
    conn.sendall(b"HTTP/1.1 200 OK\r\nContent-Length: 2\r\n\r\nok")
    conn.close()               # FIN 전송

클라이언트

import socket
c = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
c.connect(("127.0.0.1", 8080))   # 3-way handshake (블록)
c.sendall(b"GET / HTTP/1.1\r\nHost: localhost\r\n\r\n")
buf = b""
while True:
    chunk = c.recv(4096)          # 0바이트 = 상대 FIN(EOF)
    if not chunk:
        break
    buf += chunk
print(buf.decode())
c.close()
⚠️ 바이트 스트림에는 경계가 없다

sendall() 한 번이 recv() 한 번으로 오리라는 보장은 없습니다. 작은 메시지 여러 개가 합쳐져 오기도 하고(Nagle, 9장), 큰 메시지가 쪼개져 오기도 합니다. 그래서 모든 TCP 응용 프로토콜은 프레이밍을 정의합니다: HTTP는 Content-Length 또는 chunked 인코딩, 많은 바이너리 프로토콜은 길이 접두사(length-prefix), 텍스트 프로토콜은 줄바꿈. "recv가 반 토막 메시지를 돌려줬다"는 버그 리포트는 프로토콜 설계가 아니라 구현자의 오해입니다.

6.6블로킹, 논블로킹, 그리고 다중화 I/O

6.7백로그: SYN 큐와 accept 큐

listen(fd, backlog)의 backlog는 무엇일까요? 리눅스 커널은 LISTEN 소켓마다 두 개의 큐를 둡니다. handshake 중인 연결(SYN_RCVD)은 SYN 큐에, handshake가 끝났지만 응용이 아직 accept()하지 않은 연결(ESTABLISHED)은 accept 큐에 있습니다.

🔬 깊이 보기: accept 큐가 넘치면 무슨 일이 생기나

응용이 느려서(GC 정지, 스레드 풀 고갈) accept()를 못 하면 accept 큐가 꽉 찹니다. 리눅스 기본(tcp_abort_on_overflow=0)에서는 handshake의 3번째 ACK를 조용히 버립니다. 클라이언트는 이미 ESTABLISHED라고 믿고 요청을 보내는데, 서버 커널은 SYN_RCVD 상태라 데이터를 받지 않고 SYN+ACK를 재전송합니다. 클라이언트 입장의 증상은 "연결은 됐는데 응답이 1초, 3초, 7초… 늦게 온다"(지수 백오프)입니다. 간헐적 지연 장애의 단골 원인이며, nstat | grep ListenOverflows 또는 netstat -s | grep "listen queue"로 확인합니다. 대응: backlog와 net.core.somaxconn(리눅스 5.4+ 기본 4096) 상향, 그리고 근본적으로 응용의 accept 지연 해결.

6.10이해도 점검

요약

  • HTTP/1.1은 시작 줄·헤더·빈 줄·본문으로 된 텍스트 프로토콜이다. 빈 줄이 헤더의 끝이고, 본문 길이는 Content-Length 또는 chunked로 프레이밍한다.
  • 첫 접속은 DNS 1 + TCP 1 + TLS 1 + HTTP 1 = 약 4 RTT. 성능 최적화의 대부분은 왕복 수나 왕복 거리를 줄이는 것이다.
  • listen()=LISTEN, connect()=SYN 전송, accept()=accept 큐에서 완성된 연결 꺼내기, close()=FIN. 소켓 API는 상태 머신의 손잡이다.
  • accept 큐가 넘치면 3번째 ACK가 버려져 "연결은 됐는데 느린" 간헐 장애가 난다.
  • HTTP/2는 HTTP 층 HOL을, HTTP/3(QUIC)는 TCP 층 HOL까지 해결한다.
