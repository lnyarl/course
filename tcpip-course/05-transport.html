전송 계층 기초: UDP와 TCP

IP는 패킷을 "호스트"까지만 데려다 줍니다. 그 호스트 안의 어떤 프로그램에게 줄지, 잃어버리면 어떻게 할지, 순서가 섞이면 어떻게 할지는 전송 계층의 몫입니다. 이 장에서는 UDP의 단순함과 TCP의 연결 수립·종료 절차, 그리고 TCP 상태 머신 전체를 다룹니다.

⏱ 약 70분전송RFC 768 · RFC 9293

학습 목표

  • 포트 번호와 4-tuple로 소켓이 어떻게 식별되는지(다중화/역다중화) 설명할 수 있다.
  • UDP·TCP 헤더의 모든 필드와 TCP 플래그의 의미를 말할 수 있다.
  • 3-way handshake와 4-way close에서 시퀀스/ACK 번호와 양측 상태 변화를 손으로 그릴 수 있다.
  • RFC 9293의 TCP 상태 머신 11개 상태와 전이 조건을 이해한다.
  • 어떤 응용에 UDP를, 어떤 응용에 TCP를 써야 하는지 근거를 들어 판단할 수 있다.

5.1전송 계층의 첫 번째 일: 다중화와 역다중화

한 호스트에서는 브라우저 탭 여러 개, SSH, 메일 클라이언트가 동시에 통신합니다. IP 계층은 이 모든 패킷을 "같은 IP 주소"로 받습니다. 전송 계층은 포트 번호로 패킷을 올바른 소켓에 배달합니다(역다중화, demultiplexing). 보낼 때는 반대로 여러 소켓의 데이터를 하나의 IP 흐름으로 합칩니다(다중화).

여러 소켓이 포트 번호로 구분되어 하나의 IP 흐름으로 합쳐진다. 역방향으로 받을 때는 4-tuple로 소켓을 찾는다.
📌 4-tuple이 "연결"의 정체

TCP 연결은 (출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트) 네 값으로 유일하게 식별됩니다. 그래서 탭 1과 탭 2는 같은 서버의 같은 포트 443에 접속해도 출발지 포트가 달라 다른 연결이 됩니다. 서버 입장에서는 포트 443 하나로 수만 개 연결을 동시에 유지할 수 있는 이유이기도 합니다. "포트 하나에 연결 하나"라는 오해는 여기서 풀립니다.

5.3UDP: 최소한의 전송 계층 (RFC 768)

UDP 헤더는 8바이트가 전부입니다. 연결도, 순서도, 재전송도 없습니다. 하는 일은 딱 두 가지, 포트로 역다중화하고 체크섬으로 손상 검출하는 것뿐입니다. 필드를 클릭해 보세요.

의사 헤더(pseudo header)와 체크섬

UDP·TCP 체크섬은 자기 헤더와 데이터뿐 아니라 IP 헤더에서 가져온 의사 헤더(src IP, dst IP, 프로토콜 번호, UDP 길이)까지 포함해 계산합니다. 계층 위반처럼 보이지만, 이렇게 해야 "IP 주소가 깨져 엉뚱한 호스트에 배달된 데이터그램"을 전송 계층이 걸러낼 수 있습니다. IPv4에서 UDP 체크섬은 선택(0이면 미계산)이지만 IPv6에서는 필수입니다(RFC 8200 §8.1).

UDP가 "나쁜" 것이 아니다

UDP는 기능이 없는 것이 아니라 정책을 응용에 위임하는 것입니다. 실시간 음성(VoIP)에서는 늦게 온 재전송 패킷이 쓸모없고, DNS 질의는 한 번의 왕복으로 끝나야 하며, QUIC은 TCP를 커널 밖에서 다시 구현하기 위해 UDP를 운반체로 씁니다. 모두 "TCP의 정책이 맞지 않아서" UDP를 고른 사례입니다.

5.5연결 수립: 3-way handshake (애니메이션)

TCP는 데이터를 보내기 전에 양쪽이 초기 시퀀스 번호(ISN)를 교환하고 서로 받을 준비가 됐음을 확인합니다. 왜 2번이 아니라 3번일까요? 양방향 각각에 대해 "내 ISN을 상대가 받았다"는 확인이 필요하기 때문입니다. 2번째 메시지가 서버의 SYN과 클라이언트 SYN에 대한 ACK를 겸하므로 4번이 아니라 3번이 됩니다.

🔬 깊이 보기: SYN은 왜 시퀀스 번호 1바이트를 "소비"하는가

SYN 세그먼트에는 데이터가 없는데도 상대는 ack = ISN + 1로 응답합니다. SYN과 FIN은 "시퀀스 공간에서 1바이트를 차지하는 제어 비트"로 정의되어 있기 때문입니다(RFC 9293 §3.4). 이렇게 해야 SYN 자체가 신뢰성 있게 전달되었는지를 일반 데이터와 똑같은 ACK 메커니즘으로 확인할 수 있습니다. 즉 SYN의 ACK 번호 = "당신의 SYN 1바이트를 받았으니 다음은 ISN+1부터 보내라"는 뜻입니다.

🔬 깊이 보기: ISN은 왜 0이 아니라 무작위인가

ISN이 항상 0이면 ① 이전 연결의 지연된 세그먼트(같은 4-tuple)가 새 연결의 데이터로 오인될 수 있고, ② 공격자가 시퀀스 번호를 추측해 연결에 데이터를 주입(blind injection)하거나 RST로 끊을 수 있습니다. RFC 6528은 ISN = M + F(src IP, src port, dst IP, dst port, 비밀키) 형태(M은 4µs마다 증가하는 시계, F는 해시)를 권고합니다. 리눅스도 이 방식을 씁니다.

5.6데이터 전송: seq와 ack 계산 (계산기)

TCP는 바이트 단위로 번호를 붙입니다. 세그먼트의 seq는 "이 세그먼트의 첫 바이트 번호", ack는 "내가 다음에 받기를 기대하는 바이트 번호"(= 지금까지 연속으로 받은 마지막 바이트 + 1)입니다. 값을 바꿔가며 확인해 보세요.

ACK만 있는 세그먼트(데이터 0바이트)는 시퀀스 번호를 소비하지 않는다. SYN·FIN은 1바이트를 소비한다.

5.7연결 종료: 4-way close와 TIME_WAIT (애니메이션)

종료는 방향별로 따로 이뤄집니다. "나는 더 보낼 게 없다"(FIN)를 각 방향에서 한 번씩 보내고 각각 ACK를 받으니 총 4번입니다. 먼저 FIN을 보낸 쪽(능동 종료)은 마지막 ACK를 보낸 뒤 TIME_WAIT 상태에서 2MSL(리눅스 60초) 동안 기다립니다.

🔬 깊이 보기: TIME_WAIT는 왜 능동 종료 쪽에만, 왜 2MSL인가

두 가지 이유입니다. ① 마지막 ACK가 유실되면 상대(LAST_ACK)는 FIN을 재전송합니다. 그때 응답해 줄 누군가가 남아 있어야 하므로 ACK를 보낸 쪽이 기다립니다. 수동 종료 쪽은 ACK를 받으면 바로 CLOSED가 되어도 안전합니다. ② 같은 4-tuple의 새 연결이 즉시 생기면, 네트워크에 떠돌던 이전 연결의 지연 세그먼트가 새 연결에 섞일 수 있습니다. 세그먼트의 최대 생존 시간(MSL, Maximum Segment Lifetime)의 2배를 기다리면 "내가 보낸 ACK가 갔다가, 그에 대한 재전송 FIN이 오는" 왕복 동안 떠돌 수 있는 세그먼트가 모두 사라집니다. 서버가 능동 종료를 자주 하면 서버에 TIME_WAIT가 쌓이는 이유가 여기 있습니다(9장).

5.8TCP 상태 머신 (RFC 9293 §3.3.2 · 인터랙티브)

동시 열기 · 반쪽 닫기

동시 열기 (simultaneous open)

양쪽이 동시에 SYN을 보내면 둘 다 SYN_SENT → (SYN 수신) → SYN_RCVD → ESTABLISHED로 갑니다. 4번의 세그먼트가 오가며, 서버 없이도 연결이 됩니다. NAT 홀 펀칭(P2P)에서 실제로 쓰입니다.

반쪽 닫기 (half-close)

FIN은 "내 쪽 송신만 끝"이라는 뜻입니다. FIN_WAIT_2 상태에서는 상대가 보내는 데이터를 계속 받을 수 있습니다. shutdown(fd, SHUT_WR)이 바로 이것으로, "요청을 다 보냈으니 응답을 끝까지 달라"는 패턴(예: ssh host cmd < file)에 쓰입니다. close()는 양방향을 모두 닫습니다.

🔬 깊이 보기: RST는 언제, 왜 나오는가

RST(reset)는 "이 연결은 존재하지 않거나 유효하지 않다"는 즉시 중단 신호입니다. 대표적 발생 조건: ① LISTEN 중인 소켓이 없는 포트로 SYN이 오면 → RST (포트 스캐너가 "closed"로 판정하는 근거). ② 상대가 모르는 연결(4-tuple)로 세그먼트가 오면 → RST(서버 재부팅 후 옛 연결의 데이터가 올 때). ③ 수신 버퍼에 읽지 않은 데이터가 남은 채 close()하면 FIN 대신 RST. ④ 방화벽·로드밸런서가 세션을 끊을 때(Connection reset by peer). RST는 ACK를 요구하지 않고 재전송되지도 않습니다. 또한 RST는 수신 윈도우 안의 시퀀스 번호를 가져야 받아들여지는데(RFC 5961), 이것이 blind RST 공격을 어렵게 만듭니다.

DNS가 UDP인 이유

질의 1개 = 패킷 1개. handshake 1 RTT가 아까움. 응답이 512B(EDNS 시 4096B)를 넘거나 존 전송(AXFR)이면 TCP로 폴백.

VoIP가 UDP인 이유

20ms 음성 프레임이 손실되면 재전송해 받아봐야 이미 늦음. 손실 은닉(PLC)이 낫다. 타이밍은 RTP가 처리.

QUIC이 UDP인 이유

TCP는 커널·미들박스에 굳어 바꾸기 어렵다. UDP 위에 스트림·혼잡 제어·암호화를 사용자 공간에서 다시 만들어 HOL blocking을 없애고 0-RTT 연결을 구현.

5.11이해도 점검

요약

  • 전송 계층은 포트로 프로세스를 구분한다. TCP 연결은 4-tuple로 식별되며, 서버 포트 하나로 수많은 연결을 동시에 유지할 수 있다.
  • UDP는 8바이트 헤더로 역다중화와 체크섬만 제공한다. 정책을 응용에 위임하는 것이 장점이다.
  • TCP 헤더의 seq/ack는 바이트 단위이며, SYN·FIN은 시퀀스 1바이트를 소비한다.
  • 3-way handshake로 ISN을 교환하고, 4-way close로 방향별로 종료한다. 능동 종료 쪽은 2MSL TIME_WAIT를 거친다.
  • RFC 9293 상태 머신 11개 상태는 ss/netstat 출력의 상태 칼럼 그 자체다. 이상한 상태가 쌓이면 어느 전이가 막혔는지 추적한다.
