IP 계층: 주소 · 서브넷 · 라우팅 기초

IP는 인터넷의 허리입니다. 32비트 숫자 하나에 "어느 네트워크의 어느 호스트인가"를 담고, 라우터는 그 앞부분만 보고 수십억 대의 호스트 중 길을 찾습니다. 이 장에서는 IPv4 헤더, CIDR 계산, 최장 프리픽스 매칭, 단편화를 직접 계산하고 조작해 봅니다.

⏱ 약 90분인터넷RFC 791 · 1918 · 4632 · 1191

학습 목표

  • IPv4 헤더의 모든 필드를 이름·길이·역할과 함께 그릴 수 있다.
  • 임의의 IP/프리픽스에서 네트워크 주소, 브로드캐스트, 호스트 범위를 암산할 수 있다.
  • 라우팅 테이블에서 최장 프리픽스 매칭(LPM)으로 경로를 고를 수 있다.
  • IP 단편화의 Offset/MF 계산을 할 수 있고, 단편화를 피해야 하는 이유(PMTUD)를 설명할 수 있다.
  • TTL, 헤더 체크섬, DF 비트가 각각 어떤 문제를 해결하는지 안다.

3.1IP가 제공하는 것과 제공하지 않는 것

제공한다

  • 전역 주소 지정: 모든 호스트를 32비트(IPv6: 128비트) 주소로 식별
  • 라우팅: 네트워크를 넘어 목적지까지 홉 단위 전달
  • 단편화/재조립: 링크 MTU보다 큰 데이터그램 처리
  • 상위 프로토콜 다중화: Protocol 필드(6=TCP, 17=UDP, 1=ICMP)
  • 루프 방지: TTL
vs

제공하지 않는다

  • 전달 보장 (손실될 수 있음)
  • 순서 보장 (경로가 달라 뒤바뀔 수 있음)
  • 중복 방지
  • 흐름/혼잡 제어
  • 데이터 무결성 (헤더 체크섬만 있고 페이로드 검사는 없음)

이 "비연결(connectionless)·최선형(best-effort)" 설계 덕분에 라우터는 연결 상태를 기억할 필요가 없고, 패킷 하나하나를 독립적으로 처리합니다(datagram 모델). 신뢰성은 5·7장에서 다루는 TCP가 종단에서 책임집니다.

3.2IPv4 헤더 (필드를 클릭하세요)

기본 20바이트, 옵션이 있으면 최대 60바이트. 각 행이 32비트(4바이트)입니다. RFC 791(1981)의 형식이 지금까지 거의 그대로 쓰이며, ToS 바이트만 DSCP/ECN으로 재정의되었습니다(RFC 2474, 3168).

📌 전문가가 외우는 숫자

헤더 20바이트 · IHL 단위 4바이트(최소 5) · Total Length 최대 65535 · TTL 기본값: Linux 64, Windows 128, 네트워크 장비 255 · Protocol 1=ICMP, 6=TCP, 17=UDP, 41=IPv6-in-IPv4, 47=GRE, 50=ESP, 89=OSPF.

3.3IP 주소와 서브넷 마스크

IP 주소 32비트는 네트워크 부분(앞)과 호스트 부분(뒤)으로 나뉩니다. 어디서 나뉘는지를 알려주는 것이 서브넷 마스크(또는 프리픽스 길이 /n)입니다. 마스크는 앞에서부터 n개의 1과 나머지 0으로 구성되며, 주소 AND 마스크 = 네트워크 주소입니다.

서브넷 계산기 (인터랙티브)

💡 암산 요령

마스크가 옥텟 경계에 있지 않을 때(예: /26), "관심 옥텟"의 블록 크기 = 256 − 마스크 옥텟값입니다. /26 → 마스크 255.255.255.192 → 블록 64 → 네트워크는 .0, .64, .128, .192 중 하나. 142는 128~191 블록이므로 네트워크 .128, 브로드캐스트 .191. 2의 거듭제곱(128, 64, 32, 16, 8, 4, 2, 1 ↔ /25~/32)을 외워 두세요.

클래스풀에서 CIDR로

3.4라우팅 테이블과 최장 프리픽스 매칭 (인터랙티브)

라우터(그리고 모든 호스트)는 목적지 IP를 라우팅 테이블의 각 항목과 비교합니다. 규칙은 하나: 목적지 AND 마스크 == 네트워크인 항목 중 프리픽스가 가장 긴 것을 고른다(Longest Prefix Match). 기본 경로 0.0.0.0/0은 모든 주소와 매칭되지만 길이가 0이라 "다른 게 없을 때"만 선택됩니다.

#목적지 네트워크다음 홉 (게이트웨이)인터페이스매칭

라우팅 테이블 항목은 세 가지 출처에서 옵니다: ① 직접 연결(인터페이스에 IP를 설정하면 자동), ② 정적(관리자가 입력), ③ 동적(OSPF·BGP 등 라우팅 프로토콜이 교환, 11장). 다음 홉이 "직접 연결"이면 ARP로 목적지 호스트의 MAC을, 게이트웨이가 있으면 게이트웨이의 MAC을 찾습니다.

🔬 깊이 보기: 하드웨어 LPM과 테이블 크기

인터넷 코어 라우터의 전체 라우팅 테이블(DFZ)은 IPv4 약 95만 개 프리픽스(2024년 기준)입니다. 패킷마다 95만 개를 순회할 수는 없으므로 trie(Patricia/LC-trie, Linux의 fib_trie) 또는 TCAM(Ternary CAM) 하드웨어로 한 번에 찾습니다. TCAM은 비싸고 전력을 많이 쓰므로 수용 가능한 프리픽스 수에 한계가 있고, 2014년 "512K 사태"(테이블이 512K를 넘자 구형 장비가 멈춤)가 실제로 일어났습니다. CIDR 집계가 단순히 "깔끔함"이 아니라 인터넷 생존 조건인 이유입니다.

3.5IP 단편화 (애니메이션)

4000바이트 IP 데이터그램이 MTU 1500인 링크를 만나면 라우터(IPv4)는 이를 조각냅니다. 각 조각은 완전한 IP 패킷이며(헤더 복사), 세 필드로 재조립 정보를 담습니다.

  • Identification: 같은 원본에서 나온 조각은 같은 ID.
  • MF(More Fragments): 뒤에 조각이 더 있으면 1, 마지막 조각은 0.
  • Fragment Offset: 이 조각의 데이터가 원본 데이터의 어디서 시작하는지, 8바이트 단위(13비트로 65535를 표현하기 위해). 따라서 마지막을 제외한 조각의 데이터 길이는 8의 배수여야 한다.
원본 데이터그램 — Total Length 4000 = 헤더 20 + 데이터 3980, ID=0x1a2b, DF=0

재조립은 최종 목적지 호스트에서만 합니다. 중간 라우터는 조각을 더 쪼갤 수는 있어도 합치지 않습니다(경로가 다를 수 있고 상태를 유지해야 하므로). 수신 호스트는 모든 조각이 도착할 때까지 버퍼에 보관하고, 타이머(보통 30초) 안에 다 오지 않으면 전부 버립니다.

🔬 깊이 보기: 단편화는 왜 해로운가 → DF 비트와 PMTUD

① 조각 하나만 잃어도 원본 전체를 재전송해야 한다(TCP는 조각을 모른다). ② 첫 조각에만 TCP/UDP 헤더가 있어 방화벽·NAT·로드밸런서가 나머지 조각을 분류할 수 없다. ③ 재조립 버퍼는 DoS 표적이 된다(Teardrop, 겹치는 조각). ④ 라우터 CPU 부담.
그래서 현대 TCP는 DF(Don't Fragment)=1로 보내고, MTU가 작은 링크의 라우터가 ICMP "Fragmentation Needed"(Type 3 Code 4)로 그 링크의 MTU를 알려주면 송신 측이 패킷 크기를 줄입니다 — Path MTU Discovery(RFC 1191). IPv6는 아예 라우터 단편화를 금지하고 PMTUD를 필수로 합니다. 이 ICMP가 방화벽에 막히면 "작은 패킷은 되는데 큰 패킷은 안 되는" PMTUD 블랙홀이 생깁니다(4장). 대안으로 ICMP에 의존하지 않는 PLPMTUD(RFC 4821)와, TCP MSS 클램핑이 널리 쓰입니다.

3.6TTL과 헤더 체크섬

TTL (Time To Live)

원래 "초" 단위였지만 실제로는 홉 수입니다. 라우터는 전달 전에 1을 빼고, 0이 되면 패킷을 버리고 ICMP Time Exceeded(Type 11)를 출발지로 보냅니다. 목적은 라우팅 루프(설정 오류나 수렴 중에 생김)에 빠진 패킷이 영원히 돌지 않게 하는 것. traceroute(4장)는 이 동작을 역이용합니다. OS 기본값(64/128/255)으로 상대 OS를 짐작하는 수동 핑거프린팅도 가능합니다.

헤더 체크섬

헤더(만)를 16비트 단위로 더한 1의 보수 합의 1의 보수. 라우터는 TTL을 바꾸므로 홉마다 재계산(실제로는 RFC 1624의 증분 갱신)합니다. 페이로드는 검사하지 않으며, TCP/UDP가 자기 체크섬으로 보호합니다. IPv6는 링크 계층 CRC와 전송 계층 체크섬이 충분하다고 보고 헤더 체크섬을 없앴습니다.

🔬 깊이 보기: 1의 보수 체크섬 직접 계산

헤더 4500 003c 1c46 4000 4006 0000 ac10 0a63 ac10 0a0c에서 체크섬 자리를 0으로 두고 16비트 단어 9개를 더합니다. 합 = 0x4500+0x003c+0x1c46+0x4000+0x4006+0xac10+0x0a63+0xac10+0x0a0c = 0x2 B2D7. 32비트 합의 상위 캐리(0x2)를 하위에 더해 접습니다(end-around carry): 0xB2D7 + 0x2 = 0xB2D9. 1의 보수 → 0x4D26. 수신 측은 체크섬 포함 전부를 더해 0xFFFF가 나오면 정상. 1의 보수 덧셈은 바이트 순서·정렬에 무관하고 증분 갱신이 쉬워 1980년대 하드웨어에 적합했습니다. 단, 16비트 단어 교환이나 상쇄되는 오류는 못 잡습니다 — CRC보다 약합니다.

3.7실습: 라우팅 테이블과 PMTU 확인

# Linux
ip -4 addr show            # 인터페이스별 주소/프리픽스
ip route show              # 테이블. "default via 10.0.0.1 dev eth0" 가 /0
ip route get 8.8.8.8       # 이 목적지에 LPM 적용 결과 (nexthop, src 주소까지)
# 8.8.8.8 via 10.0.0.1 dev eth0 src 10.0.0.5 uid 1000

# macOS
netstat -rn -f inet
route -n get 8.8.8.8
# -M do : DF 비트 설정(단편화 금지), -s : ICMP 데이터 크기
# 1472 + 8(ICMP) + 20(IP) = 1500 → 성공, 1473은 실패해야 정상
ping -M do -s 1472 -c 2 1.1.1.1
ping -M do -s 1473 -c 2 1.1.1.1
# ping: local error: message too long, mtu=1500
#   (또는 중간 라우터의 "Frag needed and DF set (mtu = 1400)")

# macOS: -D 가 DF
ping -D -s 1472 -c 2 1.1.1.1

# 커널이 학습한 경로 MTU 캐시
ip route get 1.1.1.1 | grep -o 'mtu [0-9]*'
ip route show cache   # 구형 커널
# DF 없이 큰 패킷을 보내 단편화 유도
ping -s 4000 -c 1 10.0.0.1
# 다른 터미널에서 조각 관찰 (ip[6:2] & 0x1fff != 0 → offset이 0이 아닌 조각)
sudo tcpdump -n -i eth0 'ip[6:2] & 0x3fff != 0'
# IP (flags [+], id 0x1a2b, offset 0,    length 1500) 10.0.0.5 > 10.0.0.1: ICMP echo request
# IP (flags [+], id 0x1a2b, offset 1480, length 1500) 10.0.0.5 > 10.0.0.1: ip-proto-1
# IP (flags [none], id 0x1a2b, offset 2960, length 1068) 10.0.0.5 > 10.0.0.1: ip-proto-1

두 번째 조각부터 "ip-proto-1"로만 보이는 이유: ICMP 헤더는 첫 조각에만 있기 때문. 방화벽이 조각을 다루기 어려운 이유가 바로 이것.

3.8이해도 점검

요약

  • IP는 전역 주소·라우팅·단편화·상위 프로토콜 다중화를 제공하고, 신뢰성·순서·흐름 제어는 제공하지 않는다.
  • IPv4 헤더 20바이트: Version/IHL/DSCP·ECN/Total Length/ID/Flags/Offset/TTL/Protocol/Checksum/Src/Dst.
  • 주소 AND 마스크 = 네트워크. 호스트 비트 전부 0 = 네트워크 주소, 전부 1 = 브로드캐스트, 사용 가능 호스트 = 2ⁿ−2.
  • CIDR: 프리픽스 길이가 전부. 라우터는 최장 프리픽스 매칭으로 경로를 고르고, 집계로 테이블을 줄인다.
  • 단편화는 ID/MF/Offset(8바이트 단위)으로 재조립하지만 해로우므로, DF=1 + PMTUD로 피한다.
  • TTL은 홉 카운터(루프 방지), 헤더 체크섬은 1의 보수 합(홉마다 갱신).
