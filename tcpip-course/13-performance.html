13.1지연의 분해: 네 가지 성분 (계산기)

패킷 하나가 한 링크를 지나는 데 걸리는 시간은 네 성분의 합입니다. 각각 원인이 다르고, 해결책도 다릅니다.

성분공식무엇에 의존줄이는 방법
전파 지연 dprop거리 / 전파 속도 (광섬유 ≈ 2×108 m/s, 빛의 약 2/3)물리적 거리더 가까이(CDN, 엣지). 물리 법칙이라 다른 방법 없음
전송 지연 dtrans패킷 길이(bit) / 링크 대역폭(bit/s)패킷 크기, 링크 속도더 빠른 링크, 더 작은 패킷(헤더 오버헤드 트레이드오프)
처리 지연 dproc헤더 검사·라우팅 조회·체크섬 (µs 단위)장비 성능, 홉 수하드웨어 포워딩(ASIC), 홉 줄이기
큐잉 지연 dqueue큐 대기 시간 — 이용률 ρ가 1에 가까워지면 급증 (≈ ρ/(1−ρ) × dtrans)트래픽 부하, 버퍼 크기혼잡 제어·AQM·과도한 버퍼 제거(8장 bufferbloat)

서울↔미국 서부 ≈ 9,000 km. 처리 지연은 홉당 20 µs로 가정. 큐잉은 M/M/1 근사(홉마다 같은 ρ).

전파전송처리큐잉
🔬 깊이 보기: 대역폭을 늘려도 작은 파일은 빨라지지 않는다

위 계산기에서 대역폭을 100 Mbps → 10 Gbps로 올려 보세요. 전송 지연은 120 µs → 1.2 µs로 줄지만, 9,000 km의 전파 지연 45 ms는 그대로입니다. 웹 페이지 로드는 "DNS 1 RTT + TCP 1 RTT + TLS 1 RTT + 요청 1 RTT + Slow Start 몇 라운드"처럼 RTT의 배수로 결정됩니다. 100 KB 파일은 1 Gbps에서 전송에 0.8 ms밖에 안 걸리지만 Slow Start로 4라운드(IW10: 14.6K → 29K → 58K → 117K)가 필요하므로 RTT 90 ms라면 360 ms가 걸립니다. 이것이 "지연이 대역폭을 지배한다(latency dominates bandwidth)"는 명제이며, CDN·커넥션 재사용·0-RTT·IW 증가가 모두 RTT 횟수를 줄이려는 기법입니다.

13.2대역폭 · 처리량 · Goodput

대역폭 (bandwidth)

링크의 최대 비트 전송률. 물리적 용량. 1 Gbps 이더넷.

처리량 (throughput)

실제로 단위 시간에 전달된 비트. 경로의 병목 링크, 손실, 윈도우, 혼잡 제어에 의해 대역폭보다 낮다.

Goodput

응용이 실제로 받은 유용한 데이터율. 헤더(Ethernet 18 + IP 20 + TCP 32 ≈ 1500 중 4.7%)·재전송·TLS 레코드 오버헤드를 뺀 값.

1500바이트 프레임 기준 TCP goodput 상한은 대략 대역폭의 94–95 %입니다. 1 Gbps 링크에서 iperf3가 ~940 Mbps를 보고하면 정상이고, 그 이하라면 다른 제한 요인을 찾아야 합니다. 처리량을 제한하는 요인은 보통 다음 네 가지 중 하나입니다.

제한 요인상한 공식증상확인
수신/송신 윈도우rwnd / RTTRTT가 길수록 처리량 감소, 손실 없음ss -ti의 rcv_space, wscale; Wireshark "Window Full"
패킷 손실 + 혼잡 제어Mathis: (MSS/RTT)·(C/√p)cwnd 톱니, 재전송ss -ti retrans, nstat TcpRetransSegs
병목 대역폭min(linki)큐잉 지연 증가, 평평한 처리량iperf3, 인터페이스 카운터
응용/CPU—송신 버퍼가 비어 있음 (app-limited)ss -ti app_limited, top/perf

13.3웹 요청 워터폴 (인터랙티브)

브라우저 개발자 도구의 워터폴을 직접 만들어 봅니다. RTT·대역폭·리소스 수를 조절하고 프로토콜을 바꿔 보세요. 각 바는 RTT 단위의 핸드셰이크 비용과 대역폭 단위의 전송 비용으로 나뉩니다.

DNSTCP 연결TLS/QUIC 핸드셰이크요청 → 첫 바이트(TTFB)콘텐츠 다운로드

📌 모델의 가정

DNS 1 RTT, TCP 1 RTT, TLS 1.3 1 RTT, 요청/TTFB 1 RTT + 서버 처리 20 ms. 다운로드는 Slow Start(IW10, 1460 B MSS)로 필요한 라운드 수 × RTT에 전송 시간(크기/대역폭)을 더한 근사. HTTP/1.1은 연결 6개가 각각 핸드셰이크를 치르고, 리소스를 6개씩 묶어 순차 처리합니다. HTTP/2·3은 연결 하나에서 모든 리소스가 동시에 흐르며 대역폭을 나눕니다. 실제 브라우저는 우선순위·preconnect·캐시로 더 복잡하지만, 핸드셰이크 RTT가 얼마나 지배적인지를 보기엔 충분합니다.

13.4손실이 처리량을 깎는 방식: Mathis 공식 (계산기)

Mathis 등(1997)은 Reno 계열 AIMD에서 무작위 손실률 p일 때 평균 처리량의 상한을 유도했습니다.

Throughput ≤ (MSS / RTT) × (C / √p) , C ≈ 1.22 (지연 ACK 없을 때)

직관: cwnd가 W에서 손실로 W/2가 되고 다시 W까지 RTT마다 1 MSS씩 회복하는 톱니 한 주기에 약 (3/8)W² 개의 세그먼트가 흐르고, 그 사이 손실이 1개 → p = 8/(3W²) → W = √(8/3p). 평균 윈도우 (3/4)W를 RTT로 나누면 위 식이 나옵니다.

x: 손실률(log), y: 처리량(log). 세 곡선은 RTT 10/50/200 ms. 점은 현재 값.

⚠️ 해석 주의

이 공식은 Reno 계열·무작위 손실·충분히 큰 윈도우를 가정합니다. CUBIC은 지수가 다르고(≈ p−0.75, 큰 BDP에서 더 공격적), BBR은 손실에 거의 반응하지 않으므로 적용되지 않습니다. 그래도 "손실률이 100배 늘면 처리량은 10배 준다", "RTT가 10배면 처리량은 1/10"이라는 크기 감각을 주는 데는 여전히 가장 쓸모 있는 식입니다. 0.1 % 손실이 "작은 손실"이 아닌 이유가 여기 있습니다.

13.6Wireshark 핵심 기능

캡처 필터 vs 디스플레이 필터

캡처 필터는 BPF 문법(tcpdump와 같음)으로 커널에서 걸러 저장 자체를 줄임. 디스플레이 필터는 Wireshark 고유 문법(ip.addr==10.0.0.5 && tcp.port==443)으로 이미 캡처한 것을 보여줄지 결정. 분석할 때는 넓게 캡처하고 디스플레이 필터로 좁히는 편이 안전.

Follow TCP Stream

패킷 우클릭 → Follow → TCP Stream. 한 연결(4-tuple, tcp.stream == N)의 양방향 페이로드를 대화처럼 재조립. HTTP/1.1 평문 디버깅에 필수. TLS는 SSLKEYLOGFILE로 키를 기록하면 복호화 가능.

Expert Info

Analyze → Expert Information. 재전송·순서 뒤바뀜·제로 윈도우·체크섬 오류 같은 이상을 심각도별로 모아 보여줌. 캡처 열면 가장 먼저 볼 곳.

Statistics

Conversations(누가 누구와 얼마나), I/O Graph(시간별 처리량, 필터별 겹쳐 그리기), TCP Stream Graphs → Time-Sequence(Stevens)와 Window Scaling 그래프로 cwnd/rwnd 병목을 눈으로 확인.

tcp.analysis.* 디스플레이 필터

13.8커널 네트워크 스택 경로와 NIC 오프로드

패킷은 NIC에서 응용까지 여러 큐와 계층을 지납니다. 각 지점마다 드롭 카운터와 관측 도구가 따로 있으므로, "어디서 떨어졌는가"를 찾으려면 경로를 알아야 합니다.

수신(RX) 경로. 송신(TX)은 역순이며 qdisc(tc)가 TX 쪽에 있다. 노란 박스는 해당 지점을 관측하는 명령.

NIC 오프로드

기능동작효과·주의
TSO (TCP Segmentation Offload)커널이 64 KB짜리 "거대 세그먼트"를 NIC에 넘기면 NIC가 MSS 크기로 쪼개 전송CPU 절감. tcpdump로 보면 MTU보다 큰 세그먼트가 보임(캡처가 NIC 이전이므로)
GSO (Generic SO)TSO의 소프트웨어 버전. 스택을 큰 단위로 통과한 뒤 드라이버 직전에 분할NIC 지원 없이도 스택 오버헤드 감소
LRO / GRO수신 시 연속 세그먼트를 하나로 합쳐 스택에 전달 (LRO는 NIC, GRO는 커널)수신 CPU 절감. LRO는 헤더 정보를 잃어 라우터/브리지에서는 꺼야 함; GRO가 표준
Checksum offloadIP/TCP/UDP 체크섬을 NIC가 계산·검증송신 캡처에서 "incorrect checksum"이 보이는 원인 — 캡처 시점에 아직 계산 전(14장)
RSS (Receive Side Scaling)4-tuple 해시로 흐름을 여러 RX 큐·CPU에 분산멀티코어 확장. ethtool -l, /proc/interrupts로 분포 확인
RPS / RFSRSS의 소프트웨어 버전 / 응용이 돌고 있는 CPU로 흐름을 보냄캐시 지역성 향상

분산 스토리지나 MapReduce에서 한 클라이언트가 100개 서버에 동시에 요청하면, 100개 응답이 같은 순간 같은 ToR 스위치 포트로 몰립니다. 스위치 버퍼(수백 KB)가 순식간에 넘쳐 다수 흐름이 동시에 손실을 겪고, 각각 RTO(최소 200 ms — 데이터센터 RTT 100 µs의 2,000배)를 기다립니다. 처리량은 링크 용량의 몇 %로 추락합니다. 대응: RTO 최소값 축소(µs 단위, ip route … rto_min), DCTCP/ECN으로 손실 전에 신호, 응답을 작은 단위로 쪼개거나 지터를 넣어 동시성 완화, 깊은 버퍼 스위치. 이 문제는 "손실 기반 혼잡 제어 + 큰 RTO 최소값 + 얕은 버퍼"의 조합이 만든 구조적 결과입니다.

13.10QUIC / HTTP/3 vs TCP + TLS (애니메이션)

QUIC(RFC 9000)은 UDP 위에서 TCP의 신뢰성·혼잡 제어와 TLS 1.3을 하나로 합친 전송 프로토콜입니다. 설계 동기는 TCP의 세 가지 한계였습니다: 핸드셰이크 RTT, 스트림 간 HOL blocking, 그리고 커널·중간 장비에 묶여 진화가 느리다는 점(ossification).

항목TCP + TLS 1.3QUIC (HTTP/3)
첫 연결 핸드셰이크TCP 1 RTT + TLS 1 RTT = 2 RTT 후 요청전송+암호 통합 1 RTT
재연결TLS 세션 재개 + 0-RTT 데이터 가능하나 TCP 1 RTT는 남음 (TFO로 제거 가능하지만 보급 낮음)0 RTT: 첫 패킷에 요청 포함 (재생 공격 주의, 멱등 요청만)
HOL blocking한 연결의 한 세그먼트 손실이 모든 HTTP/2 스트림을 막음스트림별 독립 전달. 손실은 해당 스트림만 지연
연결 식별4-tuple. IP 바뀌면(Wi‑Fi→LTE) 연결 끊김Connection ID. 연결 마이그레이션으로 주소가 바뀌어도 유지
암호화 범위페이로드만. 헤더(seq, flags)는 평문 → 중간 장비가 간섭헤더 대부분 암호화. 중간 장비가 볼 수 있는 건 거의 없음 (ossification 방지)
구현 위치커널. 변경에 OS 업데이트 필요사용자 공간 라이브러리(quiche, msquic…). 앱 배포로 갱신. CPU 비용 높음(암호화·UDP 경로)
혼잡 제어CUBIC/BBR(커널)동일 알고리즘을 라이브러리에서. ACK에 손실·지연 정보 풍부(ACK ranges, ack delay)
네트워크 호환어디서나UDP 443 차단 환경에서는 TCP 폴백 필요(Alt-Svc)
🔬 깊이 보기: 지연 ACK와 Nagle이 벤치마크를 망치는 사례

요청-응답형 RPC를 작성해 "왜 호출당 40 ms나 걸리지?"라고 묻는 질문은 20년째 반복됩니다. 원인: 클라이언트가 헤더(write 1)와 본문(write 2)을 따로 쓰면 Nagle이 두 번째 작은 쓰기를 첫 쓰기의 ACK가 올 때까지 보류하고, 서버의 지연 ACK는 데이터가 더 오거나 40 ms(Linux 최소)가 지나야 ACK를 보냅니다. 둘이 서로를 기다리는 교착이 40 ms마다 풀립니다. 처리량 벤치마크에서는 안 보이고 작은 요청의 지연 벤치마크에서만 나타나는 것이 특징입니다. 해결은 TCP_NODELAY(사실상 모든 RPC 라이브러리 기본) 또는 writev/단일 write로 합치기. 반대로 대량 전송에서 TCP_NODELAY를 켜고 1바이트씩 쓰면 패킷 수가 폭증하므로, 선택이 아니라 쓰기 패턴에 맞게 결정해야 합니다(9장).

13.11성능 문제 진단 플로차트

증상을 고르면 확인 순서와 각 단계에서 의심할 원인을 보여줍니다. 핵심은 "네트워크냐 호스트냐"를 먼저 가르는 것입니다.

    13.12실습

    1. 핸드셰이크 캡처 후 Wireshark로 열기 
      sudo tcpdump -i any -nn -s 128 'tcp port 443' -w /tmp/https.pcap &
curl -s -o /dev/null https://example.com
sudo kill %1
# Wireshark에서: tcp.flags.syn==1 로 핸드셰이크만, Statistics → Conversations
    2. tshark로 통계 뽑기 (GUI 없이) 
      tshark -r /tmp/https.pcap -q -z conv,tcp            # 대화 목록·바이트 수
tshark -r /tmp/https.pcap -q -z io,stat,0.1           # 0.1초 단위 처리량
tshark -r /tmp/https.pcap -Y 'tcp.analysis.retransmission' | wc -l
tshark -r /tmp/https.pcap -T fields -e frame.time_delta_displayed -e tcp.flags.str -e tcp.len
    3. ss -ti 해석
      $ ss -ti dst 93.184.216.34 ESTAB 0 0 10.0.0.5:51234 93.184.216.34:443 cubic wscale:7,7 rto:204 rtt:3.2/1.1 ato:40 mss:1448 pmtu:1500 rcvmss:1448 advmss:1448 cwnd:10 bytes_sent:1234 bytes_acked:1234 segs_out:12 segs_in:11 data_segs_out:3 send 36.2Mbps lastsnd:120 lastrcv:118 lastack:118 pacing_rate 72.4Mbps delivery_rate 29.0Mbps app_limited busy:9ms rcv_space:14600 rcv_ssthresh:64076 minrtt:2.9

      rto:204 = RTO 204 ms(최소 200 + ...). rtt:3.2/1.1 = SRTT 3.2 ms / RTTVAR 1.1 ms. cwnd:10 세그먼트(아직 slow start 직후). send 36.2Mbps = cwnd×mss/rtt로 계산한 현재 가능 송신률. app_limited = 응용이 보낼 게 없어 네트워크가 병목이 아님. retrans:0/5가 보이면 현재 미복구/누적 재전송 수. wscale:7,7 = 양쪽 윈도우 스케일.

    4. iperf3 양방향 + 손실 주입 
      # 서버: iperf3 -s
iperf3 -c SERVER -t 20 -P 4            # 정방향 4 스트림
iperf3 -c SERVER -t 20 -R              # 역방향(서버→클라)
iperf3 -c SERVER -t 20 --bidir         # 동시 양방향
# 실험: 클라이언트에 1% 손실·50 ms 지연 주입 후 처리량이 Mathis 예측과 비슷한지 비교
sudo tc qdisc add dev eth0 root netem delay 50ms loss 1%
iperf3 -c SERVER -t 20 ; sudo tc qdisc del dev eth0 root
    5. 워터폴 실측: curl -w '@-' -o /dev/null -s https://example.com <<< 'dns %{time_namelookup} tcp %{time_connect} tls %{time_appconnect} ttfb %{time_starttransfer} total %{time_total}\n' 로 13.3의 모델과 비교.

    13.13이해도 점검

    요약

    • 지연 = 전파 + 전송 + 처리 + 큐잉. 장거리에서는 전파(RTT)가, 혼잡에서는 큐잉이 지배한다.
    • 작은 파일·웹 요청은 RTT 횟수가 결정한다. 대역폭 증가보다 핸드셰이크·Slow Start 라운드 줄이기가 효과적.
    • Mathis: 처리량 ∝ MSS/(RTT·√p). 손실 0.1 %는 작지 않다.
    • tcpdump는 -nn으로, 상대 seq를 기억하고, 시간 차로 RTT·지연 ACK·서버 처리를 읽는다.
    • Wireshark Expert Info와 tcp.analysis.*로 재전송·dup ACK·zero window를 먼저 걸러낸다.
    • 리눅스: ss -ti, nstat, ethtool -S, softnet_stat로 경로상 각 지점의 드롭을 찾는다. sysctl은 측정 후 해당 항목만.
    • QUIC은 1-RTT/0-RTT 핸드셰이크, 스트림 독립성, 연결 마이그레이션, 헤더 암호화로 TCP의 구조적 한계를 우회한다.
