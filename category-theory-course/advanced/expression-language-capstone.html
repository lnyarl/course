선수 장 · 기존 24장 · F-대수와 fold

덧셈·곱셈 표현식을 계산하고 출력하는 작은 언어를 만듭니다. 같은 트리를 다른 대수로 해석하면 계산기와 pretty printer를 분리할 수 있습니다. 이어 0 곱셈 최적화를 넣어, 수학적 값이 같다는 법칙이 오류나 로그가 있는 실행에서도 그대로 성립하는지 시험합니다.

자료형·한 층의 해석·전체 재귀를 분리하기

Expr를 Const(BigInteger), Add(Expr,Expr), Mul(Expr,Expr), Var(string)의 닫힌 합으로 정합니다. 한 층의 자식 자리만 A로 바꾼 ExprF<A>에 Map을 정의하면 자식 해석과 현재 노드 계산을 분리할 수 있습니다. fold는 자식들을 먼저 해석하고 Const/Add/Mul/Var에 해당하는 대수를 적용합니다. C# record를 썼다는 사실만으로 이 법칙이나 깊은 불변성이 증명되지는 않습니다.

Add(Const(2),Mul(Const(3),Const(4)))를 숫자 대수로 해석하면 14, 문자열 대수로 해석하면 (2+(3*4))를 얻습니다. 같은 구조를 재사용하지만 carrier 타입이 다릅니다. 문자열 모양의 동일성과 수치 결과의 동일성을 혼동하지 말고, pretty printer의 괄호·우선순위 정책도 명세해야 합니다. BigInteger를 쓰는 것은 이 산술 모형에서 고정 폭 정수 오버플로를 제외하기 위해서입니다.

최적화는 관찰 범위가 고정되어야 정당화된다

순수하고 전부 정의된 정수 계산에서는 x*0을 0으로 바꾸어 값 의미를 보존할 수 있습니다. 그러나 Var(missing)을 엄격하게 평가하면 오류가 나는 언어에서 Mul(Const(0),Var(missing))을 Const(0)으로 바꾸면 오류가 사라집니다. 수치 항등식만으로 오류 관찰을 보존했다고 결론 낼 수 없는 반례입니다.

캡스톤 검사는 작은 트리 생성기로 원본과 최적화된 식의 Result<BigInteger>를 비교합니다. 값을 비교할지, 오류 종류·평가 순서·로그 trace까지 비교할지 먼저 정합니다. 순수 총함수 하위 언어와 실패 가능한 경계를 나누면 허용할 rewrite도 선명해집니다. 두 해석기의 계산 수가 다르더라도 성능 주장은 실제 입력 크기와 측정 환경을 정한 별도 실험으로 다뤄야 합니다.

실습과 예상 관찰

기본 식의 값과 괄호 문자열을 먼저 적고 아래 조건을 선택하세요. 다음으로 C# 작은 트리를 깊이 3까지 만들어 원본/최적화의 결과를 비교하는 연습을 합니다. 외부 코드 실행 대신 자기 Expr 타입의 해석만 사용하고, missing 변수 반례를 반드시 포함하세요.

순수 기본 식 2+(3*4)

숫자 결과는 14, 완전 괄호 문자열은 (2+(3*4))입니다. 서로 다른 carrier를 가진 두 대수가 같은 트리를 해석합니다.

총함수 정수 식 x*0에서 x=7

원본과 Const(0)의 값은 모두 0입니다. 이 제한된 관찰에서는 rewrite가 값을 보존합니다.

엄격 평가의 0*Var(missing)을 0으로 축약

원본은 MissingVariable 오류, 축약식은 성공 0입니다. 오류도 관찰하는 언어에서는 이 rewrite가 안전하지 않습니다.
