1. 전역 로그를 반환 데이터로 옮기기

함수가 실행될 때마다 전역 문자열에 메시지를 붙인다고 합시다. 반환값이 늘 같아도 함수 호출을 생략하면 로그가 사라집니다. 2장의 메모이제이션 실험처럼, 반환값만 보면 놓치는 부작용이 있습니다. 공유 로그에 여러 호출이 동시에 접근하면 갱신 순서도 별도의 문제가 됩니다.

// 설명용 조각: 관찰 가능한 전역 변경을 가진 함수
static string globalLog = "";
static bool Negate(bool input)
{
    globalLog += "negate>";
    return !input;
}

첫 해결책은 이전 로그를 인수로 받고 다음 로그를 반환하는 것입니다. 그러면 숨은 상태를 드러낼 수 있지만 함수가 전체 로그 이력을 매번 받게 됩니다. 업무 값의 계산과 로그 이력 관리를 함께 떠안는 인터페이스입니다.

// 설명용 조각: 상태는 드러났지만 전체 이력을 인수로 받는다.
static (bool Value, string Log) Negate(bool input, string oldLog)
    => (!input, oldLog + "negate>");

원문은 한 단계를 더 나아갑니다. 함수는 이번 실행의 값과 이번 실행에서 생긴 로그 조각만 반환하고, 조각들을 합치는 일은 함수 바깥에서 맡깁니다. 이때 로그는 콘솔이나 파일에 기록된 것이 아니라 평범한 반환 데이터입니다. 나중에 그 데이터를 실제 콘솔에 출력하는 경계에서는 별도로 부작용이 일어납니다.

Writer는 로그 출력기가 아닙니다Writer<bool>(false, "negate>")라는 값을 만드는 것은 Console.WriteLine 호출과 다릅니다. 함수가 생성한 메시지를 데이터로 보존하므로 로그를 버릴지·저장할지·출력할지는 호출자가 정할 수 있습니다.

2. Writer와 일반 합성의 타입 불일치

이 장의 Writer는 값과 문자열 로그의 쌍입니다. C#에서는 불변인 문자열과 readonly record struct로 표현합니다. 제네릭 값 T가 자동으로 깊은 불변이 되는 것은 아니므로 예제에서는 BigInteger, bool, null이 아닌 문자열 같은 값으로 한정합니다.

// 설명용 선언. 6절의 전체 프로그램에 포함되어 있습니다.
readonly record struct Writer<T>(T Value, string Log);

f : A → Writer<B>는 A를 받아 B 값과 로그를 돌려줍니다. g : B → Writer<C>가 있다면 g(f(x))로 직접 연결할 수 없습니다. f가 반환한 것은 B가 아니라 Writer<B>이고 g가 원하는 것은 그 안의 B 값이기 때문입니다.

우선 손으로 연결해 봅시다. f를 실행하고, f의 Value를 g에 넣고, 마지막 Value와 두 로그를 묶습니다. 로그는 먼저 실행한 함수의 조각 다음 나중에 실행한 함수의 조각 순서로 이어 붙입니다.

// 설명용 조각: 반복되는 값 전달과 로그 조립
var first = f(input);
var second = g(first.Value);
var result = new Writer<C>(
    second.Value, first.Log + second.Log);

이 코드를 매 연결 지점에서 반복하면 값을 잘못 꺼내거나 로그 한쪽을 빠뜨리기 쉽습니다. 반복을 없애려면 이번에는 업무 함수를 추상화하는 것이 아니라 함수를 합성하는 방법을 추상화해야 합니다.

3. 값을 전달하고 로그를 모으는 합성

새 합성은 함수 f와 g를 받아 A → Writer<C> 함수를 만듭니다. 1장의 API 순서를 유지해 Compose(g, f)라고 부르며, 실행 순서는 f 다음 g입니다. 일반 함수 합성과 구별할 때는 수식에 작은 K를 붙여 g ∘K f라고 적겠습니다.

f(x) = (y, s_f), g(y) = (z, s_g)일 때
(g ∘K f)(x) = (z, s_f + s_g)
f : A → Writer<B>, g : B → Writer<C>

값 경로는 f의 출력 B를 g에 전달합니다. 로그 경로는 f가 만든 s_f와 g가 만든 s_g를 모읍니다. 같은 반환 쌍 안에 들어 있지만 두 경로의 책임이 다릅니다. f와 g는 서로의 로그를 읽지 않고 자신의 로그 조각만 만듭니다.

실험 1 · 값과 로그를 두 경로로 따라가기

f(x)=x+1, g(x)=2x, h(x)=x²입니다. 입력과 각 로그 조각을 바꾸고 재생하세요. 함수 실행·값 전달·로그 병합을 나누어 표시합니다. 이는 순수한 함수 합성의 설명용 단계를 나눈 것이며 실제 C# 명령의 시간 측정은 아닙니다.

원문 Haskell의 물고기 연산자 f >=> g는 같은 연결을 실행 순서로 적습니다. 여기의 C# API와 대응하면 Compose(g, f)입니다. Haskell 문법을 몰라도 “첫 값을 꺼내 다음 함수에 넣고 로그를 합친다”는 알고리즘으로 이해할 수 있습니다.

3장의 문자열 사상 합성과 순서가 다른가요?3장에서는 문자열 원소 자체를 한 객체의 사상으로 두고 g ∘ f := g ⋆ f로 정의했습니다. 여기서는 f와 g가 값을 계산하는 함수이며 로그는 그 함수의 반환 데이터입니다. 새 합성의 정의가 먼저 만든 로그 s_f 뒤에 s_g를 붙이도록 정합니다. 서로 다른 범주 구성의 정의를 기호만 보고 같은 것으로 바꾸면 안 됩니다.

4. 결합법칙은 로그의 모노이드 법칙에 기대어 선다

세 함수를 연결하면 어느 쪽으로 묶든 값은 h(g(f(x).Value).Value).Value로 흐릅니다. 로그는 한쪽에서 (s_f+s_g)+s_h, 다른 쪽에서 s_f+(s_g+s_h)가 됩니다. 따라서 값의 함수 합성이 결합적이고 문자열 연결도 결합적이므로 새 합성 역시 결합적입니다.

h ∘K (g ∘K f) = (h ∘K g) ∘K f
값: 두 쪽 모두 f → g → h
로그: (s_f ⋆ s_g) ⋆ s_h = s_f ⋆ (s_g ⋆ s_h)

문자열 대신 어떤 모노이드 M의 원소를 로그로 써도 같은 구성이 가능합니다. 로그를 합칠 때 그 모노이드의 연산 ⋆를 사용하고 항등 로그는 항등원 e로 정합니다. 즉 Writer가 필요로 하는 최소 조건은 문자열 자체가 아니라 로그 집합의 모노이드 구조입니다.

실험 2 · 로그 병합 정책을 바꾸면 어떤 법칙이 깨질까

세 로그 조각을 직접 편집합니다. 값 계산 f→g→h는 유지하고 로그 결합만 바꿉니다. 역순 연결도 결합적이며, 로그 의미가 달라진다는 점을 구별하세요.

역순 연산 a ⋆ b=b+a는 빈 문자열을 항등원으로 가지며 여전히 모노이드입니다. 따라서 그 로그 연산으로도 Writer 범주를 만들 수 있습니다. 다만 실행 순서대로 기록하겠다는 의도와 달라집니다. 반대로 뒤 로그만 남기는 연산은 결합적이지만 빈 문자열이 양쪽 항등원이 되지 못합니다. 괄호를 추가하는 연산은 결합법칙 자체가 깨집니다.

표본에서 두 결과가 같은 것과 일반 법칙이 성립하는 것은 구별해야 합니다. 위젯은 반례를 살펴보는 도구이며, 결합법칙의 일반 근거는 해당 로그 연산의 정의입니다. 반환 로그를 실제 전역 변수에 쓰는 부작용으로 바꾸면 이 순수한 쌍 모델의 등호를 그대로 적용할 수 없습니다.

5. 새 합성에 맞는 항등사상

일반 항등함수 x ↦ x는 A → A입니다. 하지만 지금 필요한 사상은 구현상 A → Writer<A>여야 합니다. 값은 그대로 두고 로그는 새 정보를 더하지 않는 항등원으로 반환해야 합니다.

idK_A(x) = (x, "")
f ∘K idK_A = f = idK_B ∘K f

항등사상이 “id 실행”이라는 로그를 새로 만들면 값이 같아도 원래의 Writer 결과와는 다릅니다. 앞쪽에 붙이면 id 로그가 먼저, 뒤쪽에 붙이면 id 로그가 나중에 붙습니다. 이 장의 함수 동등성은 반환 쌍의 값과 로그가 모두 같은지를 비교합니다.

실험 3 · 타입 연결과 항등사상 후보 검사

두 업무 함수를 고른 뒤 합성 가능한지 확인합니다. 항등사상 후보가 값을 바꾸거나 로그를 남기면 f의 앞·뒤에 붙인 결과가 어떻게 달라지는지도 비교하세요.

특정 입력에서 우연히 같아질 수 있습니다입력 기본값을 반환하는 잘못된 항등사상도 입력이 이미 기본값이면 표본을 통과할 수 있습니다. 모든 입력에서 값을 그대로 보존하고 항등 로그를 반환한다는 정의가 일반적인 항등법칙을 보장합니다.

6. 전체 C# 구현

C# 12 / .NET 8 BCL만 사용하는 전체 Program.cs입니다. 계산 함수는 콘솔을 쓰지 않고 Writer 값을 반환합니다. Main이 마지막 결과를 출력하는 부분에서만 실제 콘솔 부작용이 발생합니다. 기본값 default(Writer<T>)의 Log는 null일 수 있으므로 예제에서는 생성자로 null이 아닌 로그를 제공한 Writer만 사용합니다.

using System;
using System.Numerics;

readonly record struct Writer<T>(T Value, string Log);

internal static class Program
{
    static Writer<T> Identity<T>(T value) => new(value, "");

    // g 다음 f가 아니라 f 다음 g이다: Compose(g, f).
    static Func<A, Writer<C>> Compose<A, B, C>(
        Func<B, Writer<C>> g, Func<A, Writer<B>> f)
        => input =>
        {
            var first = f(input);
            var second = g(first.Value);
            return new Writer<C>(second.Value, first.Log + second.Log);
        };

    static void Main()
    {
        Func<BigInteger, Writer<BigInteger>> f = x => new(x + 1, "f>");
        Func<BigInteger, Writer<BigInteger>> g = x => new(x * 2, "g>");
        Func<BigInteger, Writer<BigInteger>> h = x => new(x * x, "h>");
        var composed = Compose(h, Compose(g, f))(2);
        var first = f(2);
        var second = g(first.Value);
        var third = h(second.Value);
        var manual = new Writer<BigInteger>(
            third.Value, first.Log + second.Log + third.Log);
        Console.WriteLine($"value = {composed.Value}");
        Console.WriteLine($"log = {composed.Log}");
        Console.WriteLine($"manual equals composed = {manual == composed}");

        var otherGrouping = Compose(Compose(h, g), f)(2);
        Console.WriteLine($"associativity value = {composed.Value == otherGrouping.Value}");
        Console.WriteLine($"associativity log = {composed.Log == otherGrouping.Log}");
        Func<BigInteger, Writer<BigInteger>> id = Identity<BigInteger>;
        Console.WriteLine($"identity before = {Compose(f, id)(2) == f(2)}");
        Console.WriteLine($"identity after = {Compose(id, f)(2) == f(2)}");

        Func<int, Writer<bool>> isEven = n => new(n % 2 == 0, "isEven>");
        Func<bool, Writer<bool>> negate = b => new(!b, "negate>");
        var isOdd = Compose<int, bool, bool>(negate, isEven)(3);
        Console.WriteLine($"isOdd(3) = {isOdd.Value}");
        Console.WriteLine($"isOdd log = {isOdd.Log}");
    }
}

examples/Ch04에서 dotnet run으로 실행합니다. 기대 출력:

value = 36
log = f>g>h>
manual equals composed = True
associativity value = True
associativity log = True
identity before = True
identity after = True
isOdd(3) = True
isOdd log = isEven>negate>

BigInteger는 이 예제의 덧셈·곱셈에서 고정 폭 오버플로를 피하기 위한 선택입니다. 메모리 한계와 실행 비용을 제거하지는 않습니다. record의 ==는 여기의 BigInteger·bool·string 필드를 적절히 값 비교하지만 임의의 T가 언제나 원하는 의미로 비교된다는 보장은 아닙니다. 이 프로그램은 샘플 결과를 검사하며 일반 법칙은 앞의 식 전개로 설명합니다.

7. 무엇을 클레이슬리 범주라고 부르는가

이 장에서 만든 Writer 범주는 클레이슬리 범주의 한 사례입니다. 객체는 여전히 A, B 같은 타입입니다. 이 새 범주의 사상 A → B를 원래 함수의 언어로 구현하면 A → Writer<B>가 됩니다. 도착 객체를 매번 Writer<B>라고 바꾸었다고 읽으면 사상의 합성 조건을 헷갈리게 됩니다.

아무 반환 타입에 장식을 붙였다고 자동으로 클레이슬리 범주가 생기는 것은 아닙니다. 해당 장식에 맞는 합성과 항등사상이 존재하고 법칙을 만족해야 합니다. 일반 이론에서는 이를 모나드 구조로 설명합니다. 원문도 이 장에서는 Writer라는 구체적인 사례를 먼저 다루고 모나드의 정의는 뒤로 미룹니다. 지금은 “객체뿐 아니라 사상의 표현과 합성 규칙도 바꿀 수 있다”는 점을 이해하면 됩니다.

원문 마지막 도전 문제는 로그 대신 실패 가능성을 반환 타입으로 표현합니다. Optional<B>를 돌려주는 함수에서 f가 실패하면 g를 호출하지 않고 실패를 이어 보내는 합성과, 모든 값을 성공으로 감싸는 항등사상을 직접 만들게 됩니다. 다음 실습 B에서 구현합니다.

8. 확인 문제

f : A → Writer<B>, g : B → Writer<C>를 일반 합성 g(f(x))로 연결할 수 없는 이유는?
f(x).Value를 g에 전달하고 f와 g의 로그를 따로 모아야 합니다. 이 반복을 새 합성으로 추상화합니다.
Writer 합성에서 올바른 항등사상은?
값과 로그가 모두 원래 결과를 보존해야 합니다. 새로운 로그를 남기면 항등사상이 아닙니다.
로그 연산 a ⋆ b = b + a를 사용하면?
역순 연결은 반대 모노이드의 연산입니다. 범주 법칙의 성립과 원하는 로그 순서라는 요구를 구분해야 합니다.
Writer 클레이슬리 범주에서 사상 A → B의 객체와 구현은?
클레이슬리 범주에서의 화살표와 기반 함수의 시그니처는 서로 다른 층위입니다.
값과 로그를 반환하는 순수 함수를 메모이제이션하면?
Writer의 로그는 데이터입니다. 콘솔 출력과 다릅니다. 같은 반환 쌍을 재사용하는 것과 외부 기록 동작을 다시 하는 것은 별개의 문제입니다.

9. 직접 구현하는 실습

실습 A · 누락된 로그를 잡는 회귀 검사

6절의 합성 함수를 고쳐서 두 번째 로그만 남기도록 만들면 어떤 결과가 달라지는지 예측하세요. 정상 합성과 누락 합성을 f→g→h에 각각 적용하고, 값을 비교하는 검사와 로그를 비교하는 검사를 따로 작성하세요.

기대 결과: 둘 다 값은 36입니다. 정상 로그는 f>g>h>, 누락 로그는 h>입니다. 값 동등성은 true지만 로그 동등성은 false입니다. 뒤 로그만 남기는 연산은 결합적일 수 있어도 항등법칙이 실패한다는 점도 설명하세요.

힌트

마지막 반환에서 first.Log + second.Log 대신 second.Log를 사용합니다. 원래 Compose를 덮어쓰지 말고 별도 함수 이름을 사용하세요.

해답 · Program 클래스에 추가할 메서드와 Main 조각
static Func<A, Writer<C>> DropFirstLog<A, B, C>(
    Func<B, Writer<C>> g, Func<A, Writer<B>> f)
    => x =>
    {
        var first = f(x);
        var second = g(first.Value);
        return new Writer<C>(second.Value, second.Log);
    };

// Main의 f,g,h 정의 뒤에서 실행
var good = Compose(h, Compose(g, f))(2);
var bad = DropFirstLog(h, DropFirstLog(g, f))(2);
Console.WriteLine($"same value = {good.Value == bad.Value}"); // True
Console.WriteLine($"same log = {good.Log == bad.Log}");       // False
Console.WriteLine($"bad log = {bad.Log}");                  // h>

항등사상을 뒤에 붙이면 마지막의 빈 로그만 남아서 f의 로그가 사라집니다. 따라서 범주를 얻으려면 결합법칙만 확인해서는 안 됩니다.

실습 B · Optional 역수 → 제곱근 연결하기

원문 4.4의 도전 문제입니다. 성공 여부와 값을 담은 Optional<T>를 만들고, 실패하면 다음 함수를 호출하지 않는 합성과 모든 값을 성공으로 감싸는 항등사상을 정의하세요. 역수 다음 제곱근으로 √(1/x)를 계산합니다.

기대 결과: x=4는 성공 0.5, x=0과 x=−4는 실패입니다. NaN·Infinity도 실패로 처리하세요. 여기의 성공 값은 유한 double 근삿값입니다. 0이 아닌 아주 작은 값의 역수가 무한대로 넘치는 경우도 실패로 정합니다. 이 구현을 모든 실수의 정확한 유리수·제곱근 연산이라고 부르면 안 됩니다.

힌트

Optional이 실패 상태면 Value를 읽거나 다음 함수를 호출하지 않습니다. 항등사상은 입력을 성공으로 감쌉니다. 실패는 None으로 전달하며 실제 부작용이나 비종료를 자동으로 고치는 것은 아닙니다.

해답 · 선언·메서드·Main 조각
// Program 클래스 바깥에 추가
readonly record struct Optional<T>(bool HasValue, T Value);

// Program 클래스 안에 추가
static Optional<T> Some<T>(T value) => new(true, value);
static Optional<T> None<T>() => default;
static Func<A, Optional<C>> ComposeOptional<A, B, C>(
    Func<B, Optional<C>> g, Func<A, Optional<B>> f)
    => x =>
    {
        var first = f(x);
        return first.HasValue ? g(first.Value) : None<C>();
    };
static Optional<double> SafeReciprocal(double x)
{
    if (!double.IsFinite(x) || x == 0) return None<double>();
    double result = 1.0 / x;
    return double.IsFinite(result) ? Some(result) : None<double>();
}
static Optional<double> SafeRoot(double x)
    => double.IsFinite(x) && x >= 0
        ? Some(Math.Sqrt(x)) : None<double>();

// Main에 추가
Func<double, Optional<double>> identity = Some<double>;
var rootReciprocal = ComposeOptional<double, double, double>(
    SafeRoot, SafeReciprocal);
foreach (double x in new[] { 4.0, 0.0, -4.0, double.NaN,
    double.PositiveInfinity, double.Epsilon })
{
    var result = rootReciprocal(x);
    Console.WriteLine(result.HasValue ? $"Some({result.Value})" : "None");
}
// Some(0.5), None, None, None, None, None (각 줄)
// identity는 임의의 double을 감쌀 수 있다.
// SafeRoot·SafeReciprocal의 입력 검증과 항등사상 정의는 별개다.

Optional의 실패 상태에서는 Value가 default(T)여도 의미상 읽지 않습니다. 모든 기본값이 실패라는 뜻도 아닙니다. 예를 들어 Some(0.0)은 정상적인 성공입니다. 이 작은 표현의 유효한 생성 규칙과 HasValue 검사를 지켜야 합니다.

핵심 요약

  • Writer<A>는 값 A와 이번 호출의 로그를 함께 반환합니다. 실제 로그 출력은 별도 부작용입니다.
  • 합성은 첫 Value를 다음 함수에 넘기고 첫 Log 뒤에 다음 Log를 붙입니다.
  • 합성의 결합법칙은 값의 함수 합성과 로그 모노이드의 결합법칙에 기대어 성립합니다.
  • 항등사상은 값을 유지하고 항등 로그를 반환합니다.
  • 클레이슬리 사상 A → B는 기반 함수 A → Writer<B>로 구현됩니다.
  • 모든 장식 타입이 자동으로 범주를 만드는 것은 아닙니다. 합성·항등·법칙이 필요합니다.
  • Optional에서는 실패 시 다음 함수를 호출하지 않는 합성과 성공으로 감싸는 항등사상을 만들 수 있습니다.
