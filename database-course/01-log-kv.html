저장 엔진 · Chapter 01

로그 구조 키-값 저장소

데이터베이스가 하는 일을 한 문장으로 줄이면 "값을 받아 파일에 넣어 두었다가, 나중에 그 값을 돌려준다"입니다. 전원이 꺼졌다 켜져도요. 이 장에서는 그 문장을 가장 단순하고도 실제로 쓰이는 방식으로 구현합니다. 모든 쓰기를 파일 끝에 덧붙이고(append-only), 메모리에는 "이 키의 최신 값은 파일의 몇 번째 바이트에 있다"는 색인만 둡니다. Riak의 저장 엔진 Bitcask가 이 구조이고, 7장에서 만들 WAL도 같은 뿌리입니다. 그 과정에서 바이너리 레코드 형식, crc 체크섬, 쓰다 만 레코드의 복구, 쓰레기를 치우는 compaction을 다룹니다.

학습 목표

  • 길이 접두사와 crc를 가진 바이너리 레코드 형식을 설계하고, 실제 파일의 hexdump를 읽을 수 있다.
  • 덧붙이기 전용 로그와 메모리 색인(keydir)으로 O(1) 읽기와 순차 쓰기를 구현할 수 있다.
  • 삭제를 tombstone 레코드로 표현하는 이유를 설명할 수 있다.
  • 시작할 때 로그를 재생하고, 끝이 잘리거나 손상된 레코드를 crc로 걸러 낼 수 있다.
  • compaction으로 공간을 회수하고, 임시 파일 + rename으로 이를 원자적으로 만들 수 있다.
  • mydb REPL을 구현해 완료 기준 17개를 통과시킨다.

1. 데이터베이스는 결국 파일이다

PostgreSQL에 INSERT를 보내면 SQL 해석, 실행 계획, 테이블과 인덱스, 페이지 캐시, 로그를 거쳐 결국 디스크의 파일 어딘가에 바이트 몇 개가 놓입니다. 이 코스는 그 계층을 아래에서부터 한 층씩 쌓습니다.

이 장이 끝나면 이렇게 동작해야 합니다(macOS에서 실제로 실행한 결과).

$ cargo run -- data.log
mydb> set greet hello world
OK
mydb> get greet
hello world
mydb> del greet
1
mydb> .exit
$ cargo run -- data.log           # 다시 켜도 삭제까지 기억한다
mydb> get greet
(nil)

이 코스는 운영체제 기능에 기대지 않으므로 macOS에서 그대로 할 수 있습니다. Linux도 같습니다. 차이가 나는 곳(7장의 fsync)은 그때 짚습니다.

cargo new mydb && cd mydb

3. 가장 단순한 데이터베이스

마틴 클레프만의 『데이터 중심 애플리케이션 설계』는 세상에서 가장 단순한 데이터베이스를 셸 함수 두 개로 보여 줍니다.

db_set() { echo "$1,$2" >> database; }
db_get() { grep "^$1," database | sed -e "s/^$1,//" | tail -n 1; }

놀랍게도 핵심은 이미 다 들어 있습니다. 쓰기는 파일 끝에 덧붙이기만 하고(빠르고, 기존 데이터를 망가뜨리지 않음), 같은 키를 여러 번 쓰면 마지막 줄이 최신 값입니다. 하지만 세 가지가 문제입니다.

4. 레코드 형식

값에 무엇이 들어 있든 경계를 알 수 있도록, 레코드 앞에 길이를 적습니다. 그리고 레코드가 온전한지 확인할 수 있도록 체크섬을 붙입니다.

  • 왜 길이를 앞에: 읽는 쪽은 머리 12바이트만 읽으면 레코드 전체 길이를 압니다. 값에 줄바꿈이나 0바이트가 있어도 상관없습니다.
  • 왜 리틀 엔디언: x86과 ARM 모두 리틀 엔디언이라 변환 비용이 없습니다. 중요한 것은 정해 두는 것입니다. 파일 형식은 기계를 넘어 옮겨지므로 "이 기계의 바이트 순서"에 맡기면 안 됩니다. Rust의 to_le_bytes/from_le_bytes가 이를 명시합니다.
  • 왜 crc가 길이까지 덮나: 길이 필드가 깨지면 그 뒤 모든 레코드의 경계가 어긋납니다. 길이를 믿기 전에 검증해야 합니다.
레코드 인코더
키와 값을 바꾸면 mydb가 파일에 쓸 바이트를 보여 줍니다. crc는 브라우저에서 실제로 계산합니다(crc32fast와 같은 CRC-32). "1비트 뒤집기"로 디스크 오류를 흉내 내 보세요.

실제로 set a 1, set greet hello world, del a를 실행한 파일의 hexdump입니다. 위젯에 같은 키와 값을 넣으면 같은 바이트가 나옵니다.

$ xxd data.log
00000000: 318a 2cea 0100 0000 0100 0000 6131 0426  1.,.........a1.&
00000010: d149 0500 0000 0b00 0000 6772 6565 7468  .I........greeth
00000020: 656c 6c6f 2077 6f72 6c64 c159 1af2 0100  ello world.Y....
00000030: 0000 ffff ffff 61                        ......a

레코드 셋의 크기는 14 + 28 + 13 = 55바이트입니다. 마지막 레코드의 ffff ffff가 삭제 표시입니다.

5. 색인: 키는 메모리에, 값은 파일에

읽기를 빠르게 하려면 "키 → 그 키의 최신 레코드가 시작하는 위치(바이트 오프셋)"를 메모리 해시맵에 둡니다. Bitcask는 이것을 keydir라고 부릅니다. 쓰기는 파일 끝에 덧붙이고 색인의 그 키를 새 오프셋으로 바꾸면 끝입니다. 읽기는 색인에서 오프셋을 찾고 그 위치에서 레코드 하나를 읽습니다. 디스크 탐색은 많아야 한 번입니다.

로그와 색인 시뮬레이터
명령을 입력하세요(set KEY VALUE, get KEY, del KEY, compact). 오프셋과 크기는 mydb의 실제 레코드 형식으로 계산합니다. 흐린 레코드는 아무도 가리키지 않는 쓰레기입니다.

쓰기와 재생을 한 단계씩 따라가기
set → 다른 키 쓰기 → 같은 키 덮어쓰기 → 삭제 → 재시작을 추적합니다. 파일에 기록하는 순간과 색인을 바꾸는 순간을 나눴습니다. 키를 바꾸면 실제 UTF-8 길이에 따라 오프셋도 바뀝니다.

화살표가 있는 레코드만 현재 색인이 가리킵니다. 점선 레코드도 파일에서 지워진 것은 아닙니다. 초기화·이전으로 돌아가 같은 중간 상태를 확인하세요. 도식은 좌우로 스크롤할 수 있습니다.

6. 삭제는 지우지 않는다

덧붙이기 전용 파일에서는 이미 쓴 레코드를 지울 수 없습니다. 그래서 "이 키는 지워졌다"는 레코드를 하나 더 씁니다. 이것이 tombstone(묘비)입니다. mydb는 val_len 자리에 0xFFFFFFFF를 써서 표시합니다. 값의 길이가 0인 것(빈 문자열)과 구분해야 하기 때문입니다.

  • 색인에서는 바로 지웁니다. 그래서 get은 즉시 (nil)이 됩니다.
  • tombstone이 없다면? 다시 켤 때 로그를 재생하면 예전의 set이 되살아납니다. "지웠는데 재시작하니 돌아왔다"는 버그입니다. 완료 기준의 "del은 재시작 후에도" 항목이 이것을 확인합니다.
  • tombstone 자체도 쓰레기를 만듭니다. compaction 때는 지워진 키를 아예 쓰지 않으므로 tombstone도 사라집니다.
분산 데이터베이스의 tombstone Cassandra 같은 시스템에서는 tombstone을 바로 버리면 안 됩니다. 삭제 소식을 아직 못 받은 복제본이 예전 값을 되살려 보낼 수 있기 때문입니다. 그래서 일정 기간(gc_grace_seconds) tombstone을 남겨 두고, 그 사이 tombstone이 많이 쌓이면 읽기가 느려지는 문제가 생깁니다. 단순해 보이는 "삭제 표시"가 운영 문제로 이어지는 예입니다.

7. 다시 켤 때: 재생과 찢어진 쓰기

색인은 메모리에만 있으니 프로그램을 다시 켜면 사라집니다. 그래서 시작할 때 로그를 처음부터 끝까지 재생(replay)해 색인을 다시 만듭니다. set이면 그 키의 오프셋을 기록하고, tombstone이면 그 키를 지웁니다. 마지막에 남은 것이 최신 상태입니다.

문제는 마지막 레코드입니다. 레코드를 쓰는 도중 전원이 꺼지면, 파일에는 앞부분만 남은 찢어진 레코드(torn write)가 생길 수 있습니다. 재생할 때 다음 중 하나라도 해당하면 그 레코드는 믿을 수 없습니다.

  1. 남은 바이트가 머리(12바이트)보다 적다
  2. 머리가 말하는 길이만큼 바이트가 없다
  3. 바이트는 다 있지만 crc가 맞지 않는다 (일부 블록만 디스크에 닿았거나, 디스크 오류)

mydb는 그 지점에서 재생을 멈추고 뒤를 잘라 냅니다(set_len). 잘라 내지 않으면 다음 쓰기가 쓰레기 뒤에 붙어, 그 뒤의 정상 레코드까지 영영 읽을 수 없게 됩니다.

정전 시뮬레이터
세 레코드가 정상적으로 쓰인 뒤, 네 번째 레코드 set torn value(21바이트)를 쓰는 도중 전원이 꺼집니다. 몇 바이트까지 디스크에 닿았는지 고르고, 다시 켰을 때 재생 결과를 보세요.

완료 기준은 실제로 파일을 망가뜨려 이것을 확인합니다. 마지막 레코드의 끝 1바이트를 잘라 낸 경우와, 마지막 레코드의 값 1바이트를 바꾼 경우입니다.

$ head -c $(( $(wc -c < test.log) - 1 )) test.log > cut && mv cut test.log
$ printf 'get torn\nget greet\n' | ./target/debug/mydb test.log
mydb: 깨진 꼬리 20바이트를 잘라 냅니다 (위치 69)       ← stderr
(nil)
hello world
write가 돌아왔다고 디스크에 있는 것은 아니다 write는 데이터를 운영체제의 페이지 캐시에 넣으면 돌아옵니다. 실제 디스크에 쓰는 것은 나중의 일입니다. 프로그램이 죽어도 운영체제가 살아 있으면 캐시의 데이터는 결국 디스크에 갑니다. 하지만 전원이 꺼지면 캐시에 있던 것은 사라집니다. 이를 막는 것이 fsync이고, 매 쓰기마다 부르면 매우 느려집니다. 1장의 mydb는 쓰기마다 fsync하지 않습니다. 이 trade-off와 macOS(F_FULLFSYNC)·Linux의 차이는 7장(WAL)의 주제입니다. compaction만은 바꿔 끼우기 전에 새 파일을 sync_all합니다(8절).
손상 바이트를 고르고 복구 경계 예측하기
set a 1, set b 2, set a 3의 14바이트 레코드 세 개를 실제 CRC-32로 인코딩했습니다. 1비트 손상 위치 또는 파일에 남길 길이를 바꾸고, 어디까지 보존할지 먼저 예측하세요.

빨간 테두리는 바뀐 바이트, 취소선은 잘린 바이트, 강조 테두리는 검증한 범위입니다. 첫 오류 뒤의 온전해 보이는 레코드도 재생하지 않습니다. 이는 이 장 예제의 복구 정책이며 실제 파일을 수정하지 않습니다.

8. 쓰레기와 compaction

덮어쓴 값과 지운 값은 파일에 그대로 남습니다. 같은 키를 계속 바꾸는 작업이라면 파일은 끝없이 커집니다. 실제로 재 본 결과입니다(macOS, release 빌드).

$ seq 1 100000 | awk '{print "set key"($1%100)" v"$1}' | ./target/release/mydb ow.log    # 키 100개를 10만 번 덮어쓰기
$ printf 'count\ncompact\n' | ./target/release/mydb ow.log
100
2278895 → 2291 바이트                ← 99.9%가 쓰레기였다

compaction은 살아 있는 키만 새 파일에 다시 쓰고 그 파일로 바꿔 끼웁니다. 중요한 것은 바꿔 끼우는 순서입니다.

  1. 살아 있는 레코드를 data.compact(임시 파일)에 쓴다
  2. 임시 파일을 sync_all로 디스크에 확정한다
  3. rename(data.compact, data.log)로 바꿔 끼운다

rename은 원자적입니다. 어느 순간에 전원이 꺼져도, 다시 켰을 때 data.log는 "옛 파일 전체" 아니면 "새 파일 전체"입니다. 반쯤 쓴 새 파일이 data.log가 되는 일은 없습니다. 2번을 빼면 그런 일이 생길 수 있습니다. rename이 디스크에 반영됐는데 새 파일의 내용은 아직 캐시에만 있다가 사라지는 경우입니다. (엄밀히는 rename 자체를 확정하려면 디렉터리도 fsync해야 합니다. 7장에서 다룹니다.)

9. 얼마나 빠른가, 무엇을 못 하는가

macOS(Apple Silicon)에서 release 빌드로 잰 값입니다.

작업결과왜
서로 다른 키 10만 개 set0.53초, 파일 2,977,790바이트모두 파일 끝에 덧붙이는 순차 쓰기이고, fsync를 하지 않아 페이지 캐시에서 끝난다
그 파일을 열어 색인 재생0.02초3 MB를 한 번에 읽어 메모리에서 파싱. 방금 쓴 파일이라 페이지 캐시에 있다

단순하고 빠르지만, 이 구조로는 할 수 없는 것이 분명합니다.

  • 키가 메모리에 다 들어가야 한다: 색인은 모든 키를 메모리에 둡니다. 키가 10억 개라면?
  • 범위 질의를 못 한다: "a로 시작하는 키 전부", "가격이 1만~2만인 상품"은 해시맵으로 할 수 없습니다. 키가 정렬되어 있지 않기 때문입니다.
  • 시작이 점점 느려진다: 재생 시간은 로그 크기에 비례합니다. 몇 GB가 되면 켜는 데만 한참 걸립니다(Bitcask는 hint 파일로 이것을 줄입니다).
  • 값을 고치려면 항상 새로 쓴다: 1바이트를 바꿔도 레코드 전체를 다시 씁니다.

2장에서는 반대 방향으로 갑니다. 파일을 4 KB 페이지로 나누고, 같은 자리를 고쳐 쓰며, 필요한 페이지만 메모리에 올리는 버퍼 풀을 만듭니다. 그 위에 3장의 B+트리가 올라가 정렬과 범위 질의, 메모리보다 큰 데이터를 해결합니다. 그리고 이 장의 로그는 7장에서 "페이지를 고치기 전에 먼저 적어 두는 기록", 즉 WAL로 돌아옵니다.

단계 A. 레코드 인코딩과 디코딩

입력은 키 바이트와 선택적 값입니다. encode는 길이와 CRC를 포함한 레코드를 반환하고, decode는 정상 레코드의 값과 소비한 바이트 수를 반환합니다. 불완전하거나 CRC가 다르면 None이므로 재생은 그 위치에서 멈춥니다.

fn encode(key: &[u8], value: Option<&[u8]>) -> Vec<u8> {
    let vlen = value.map_or(TOMBSTONE, |v| v.len() as u32);
    let mut body = Vec::with_capacity(8 + key.len() + value.map_or(0, <[u8]>::len));
    body.extend_from_slice(&(key.len() as u32).to_le_bytes());

fn decode(buf: &[u8]) -> Option<(Vec<u8>, Option<Vec<u8>>, usize)> {
    if buf.len() < HEADER {
        return None;
    }
    let u32_at = |i: usize| u32::from_le_bytes(buf[i..i + 4].try_into().unwrap());
    let (crc, klen, vlen) = (u32_at(0), u32_at(4) as usize, u32_at(8));
    let value_len = if vlen == TOMBSTONE { 0 } else { vlen as usize };
    let total = HEADER + klen + value_len;
    if buf.len() < total || crc32fast::hash(&buf[4..total]) != crc {
        return None;
    }
    let key = buf[HEADER..HEADER + klen].to_vec();
    let value = (vlen != TOMBSTONE).then(|| buf[HEADER + klen..total].to_vec());
    Some((key, value, total))
}
코드 해설 A

u32::from_le_bytes(buf[i..i + 4].try_into().unwrap())로 4바이트를 정수로 읽습니다. 삭제 표시일 때 값의 길이는 0으로 계산해야 전체 길이가 맞습니다. (vlen != TOMBSTONE).then(|| ...)로 Option을 만들 수 있습니다.

Db::open은 레코드를 앞에서부터 읽어 최신 오프셋 색인을 복원합니다. 삭제 표시는 색인에서 제거하고, 정상적으로 읽은 경계 end 뒤의 손상 꼬리만 잘라 냅니다.

    fn open(path: &Path) -> Result<Db> {
        let file = OpenOptions::new()
            .read(true)
            .append(true)
            .create(true)
            .open(path)
            .with_context(|| format!("{} 열기", path.display()))?;
        let data = fs::read(path)?;
        let mut index = HashMap::new();
        let mut pos = 0;
        while let Some((key, value, len)) = decode(&data[pos..]) {
            match value {
                Some(_) => index.insert(key, pos as u64),
                None => index.remove(&key),
            };
            pos += len;
        }
        if pos < data.len() {
            // 마지막 쓰기가 끝나지 못하고 꺼진 흔적. 그 뒤로는 믿을 수 없으니 잘라 낸다
            eprintln!("mydb: 깨진 꼬리 {}바이트를 잘라 냅니다 (위치 {pos})", data.len() - pos);
            file.set_len(pos as u64)?;
        }
        Ok(Db { path: path.to_path_buf(), file, index, end: pos as u64 })
    }
코드 해설 B: append 모드와 잘라 내기

단계 C. set, get, del

set은 인코딩한 레코드를 append하고 최신 오프셋을 색인에 기록합니다. get은 그 위치에서 레코드를 읽으며, del은 삭제 레코드를 추가한 다음 색인에서 키를 지웁니다.

    fn set(&mut self, key: &[u8], value: &[u8]) -> Result<()> {
        let at = self.append(&encode(key, Some(value)))?;
        self.index.insert(key.to_vec(), at);

    fn get(&self, key: &[u8]) -> Result<Option<Vec<u8>>> {
        let Some(&at) = self.index.get(key) else { return Ok(None) };

        let (_, value, _) = decode(&record).with_context(|| format!("위치 {at}의 레코드가 깨졌습니다"))?;
        Ok(value)
    }

    fn del(&mut self, key: &[u8]) -> Result<bool> {
        if !self.index.contains_key(key) {

        self.index.remove(key);
        Ok(true)

단계 D. compact

Db::compact는 살아 있는 키를 새 파일로 옮기고 동기화한 뒤 교체합니다. 반환한 이전/이후 크기로 공간 회수를 확인합니다. 파일 교체가 성공한 뒤에만 열린 파일과 색인을 바꿉니다.

    fn compact(&mut self) -> Result<(u64, u64)> {
        let tmp = self.path.with_extension("compact");
        let mut out = BufWriter::new(File::create(&tmp)?);
        let mut keys: Vec<Vec<u8>> = self.index.keys().cloned().collect();
        keys.sort(); // 키 순서로 쓰면 결과 파일이 결정적이다
        let mut index = HashMap::new();
        let mut pos = 0u64;
        for key in keys {
            let value = self.get(&key)?.context("색인에 있는 키의 값이 없습니다")?;
            let record = encode(&key, Some(&value));
            out.write_all(&record)?;
            index.insert(key, pos);
            pos += record.len() as u64;
        }
        // 새 파일이 디스크에 닿은 뒤에야 바꿔 끼운다. rename은 원자적이다
        out.into_inner()?.sync_all()?;
        fs::rename(&tmp, &self.path)?;
        self.file = OpenOptions::new().read(true).append(true).open(&self.path)?;
        let before = self.end;
        self.index = index;
        self.end = pos;
        Ok((before, pos))
    }

//! mydb 1장: 로그 구조 키-값 저장소 (Bitcask 방식)
//!
//! 레코드 = crc32(4) | key_len(4) | val_len(4) | key | value   (정수는 리틀 엔디언)
//! 쓰기는 항상 파일 끝에 덧붙이고, 메모리의 색인에는 키마다 최신 레코드의 위치만 둔다.

use std::collections::HashMap;
use std::fs::{self, File, OpenOptions};
use std::io::{self, BufWriter, IsTerminal, Write};
use std::os::unix::fs::FileExt;
use std::path::{Path, PathBuf};

use anyhow::{Context, Result, bail};

/// 레코드 머리: crc32 + key_len + val_len
const HEADER: usize = 12;
/// val_len 자리에 이 값이 오면 삭제 표시(tombstone)
const TOMBSTONE: u32 = u32::MAX;

struct Db {
    path: PathBuf,
    file: File,
    /// 키 → 그 키의 최신 레코드가 시작하는 위치 (Bitcask의 keydir)
    index: HashMap<Vec<u8>, u64>,
    /// 파일 끝 = 다음 레코드를 쓸 위치
    end: u64,
}

/// 레코드 하나를 바이트로. value가 None이면 삭제 표시
fn encode(key: &[u8], value: Option<&[u8]>) -> Vec<u8> {
    let vlen = value.map_or(TOMBSTONE, |v| v.len() as u32);
    let mut body = Vec::with_capacity(8 + key.len() + value.map_or(0, <[u8]>::len));
    body.extend_from_slice(&(key.len() as u32).to_le_bytes());
    body.extend_from_slice(&vlen.to_le_bytes());
    body.extend_from_slice(key);
    if let Some(v) = value {
        body.extend_from_slice(v);
    }
    // crc는 머리의 길이 필드부터 값 끝까지를 덮는다
    let mut record = crc32fast::hash(&body).to_le_bytes().to_vec();
    record.extend_from_slice(&body);
    record
}

/// 버퍼 맨 앞의 레코드 하나: (키, 값 또는 삭제 표시, 레코드 전체 길이).
/// 덜 쓰였거나 crc가 맞지 않으면 None
fn decode(buf: &[u8]) -> Option<(Vec<u8>, Option<Vec<u8>>, usize)> {
    if buf.len() < HEADER {
        return None;
    }
    let u32_at = |i: usize| u32::from_le_bytes(buf[i..i + 4].try_into().unwrap());
    let (crc, klen, vlen) = (u32_at(0), u32_at(4) as usize, u32_at(8));
    let value_len = if vlen == TOMBSTONE { 0 } else { vlen as usize };
    let total = HEADER + klen + value_len;
    if buf.len() < total || crc32fast::hash(&buf[4..total]) != crc {
        return None;
    }
    let key = buf[HEADER..HEADER + klen].to_vec();
    let value = (vlen != TOMBSTONE).then(|| buf[HEADER + klen..total].to_vec());
    Some((key, value, total))
}

impl Db {
    /// 로그를 처음부터 다시 읽어(replay) 색인을 만든다
    fn open(path: &Path) -> Result<Db> {
        let file = OpenOptions::new()
            .read(true)
            .append(true)
            .create(true)
            .open(path)
            .with_context(|| format!("{} 열기", path.display()))?;
        let data = fs::read(path)?;
        let mut index = HashMap::new();
        let mut pos = 0;
        while let Some((key, value, len)) = decode(&data[pos..]) {
            match value {
                Some(_) => index.insert(key, pos as u64),
                None => index.remove(&key),
            };
            pos += len;
        }
        if pos < data.len() {
            // 마지막 쓰기가 끝나지 못하고 꺼진 흔적. 그 뒤로는 믿을 수 없으니 잘라 낸다
            eprintln!("mydb: 깨진 꼬리 {}바이트를 잘라 냅니다 (위치 {pos})", data.len() - pos);
            file.set_len(pos as u64)?;
        }
        Ok(Db { path: path.to_path_buf(), file, index, end: pos as u64 })
    }

    fn append(&mut self, record: &[u8]) -> Result<u64> {
        let at = self.end;
        self.file.write_all(record)?;
        self.end += record.len() as u64;
        Ok(at)
    }

    fn set(&mut self, key: &[u8], value: &[u8]) -> Result<()> {
        let at = self.append(&encode(key, Some(value)))?;
        self.index.insert(key.to_vec(), at);
        Ok(())
    }

    fn get(&self, key: &[u8]) -> Result<Option<Vec<u8>>> {
        let Some(&at) = self.index.get(key) else { return Ok(None) };
        // 머리를 먼저 읽어 길이를 알고, 레코드 전체를 읽어 crc까지 확인한다
        let mut head = [0u8; HEADER];
        self.file.read_exact_at(&mut head, at)?;
        let klen = u32::from_le_bytes(head[4..8].try_into().unwrap()) as usize;
        let vlen = u32::from_le_bytes(head[8..12].try_into().unwrap()) as usize;
        let mut record = vec![0u8; HEADER + klen + vlen];
        self.file.read_exact_at(&mut record, at)?;
        let (_, value, _) = decode(&record).with_context(|| format!("위치 {at}의 레코드가 깨졌습니다"))?;
        Ok(value)
    }

    /// 지웠으면 true, 없던 키면 false
    fn del(&mut self, key: &[u8]) -> Result<bool> {
        if !self.index.contains_key(key) {
            return Ok(false);
        }
        self.append(&encode(key, None))?;
        self.index.remove(key);
        Ok(true)
    }

    /// 살아 있는 키만 새 파일에 다시 써서 바꿔 끼운다. (이전 크기, 새 크기)
    fn compact(&mut self) -> Result<(u64, u64)> {
        let tmp = self.path.with_extension("compact");
        let mut out = BufWriter::new(File::create(&tmp)?);
        let mut keys: Vec<Vec<u8>> = self.index.keys().cloned().collect();
        keys.sort(); // 키 순서로 쓰면 결과 파일이 결정적이다
        let mut index = HashMap::new();
        let mut pos = 0u64;
        for key in keys {
            let value = self.get(&key)?.context("색인에 있는 키의 값이 없습니다")?;
            let record = encode(&key, Some(&value));
            out.write_all(&record)?;
            index.insert(key, pos);
            pos += record.len() as u64;
        }
        // 새 파일이 디스크에 닿은 뒤에야 바꿔 끼운다. rename은 원자적이다
        out.into_inner()?.sync_all()?;
        fs::rename(&tmp, &self.path)?;
        self.file = OpenOptions::new().read(true).append(true).open(&self.path)?;
        let before = self.end;
        self.index = index;
        self.end = pos;
        Ok((before, pos))
    }
}

/// 명령 한 줄을 실행해 응답을 돌려준다. None이면 종료
fn execute(db: &mut Db, line: &str) -> Result<Option<String>> {
    let mut parts = line.trim_start().splitn(3, ' ');
    let reply = match (parts.next().unwrap_or(""), parts.next(), parts.next()) {
        ("", None, None) => String::new(),
        ("set", Some(key), Some(value)) => {
            db.set(key.as_bytes(), value.as_bytes())?;
            "OK".to_string()
        }
        ("get", Some(key), None) => match db.get(key.as_bytes())? {
            Some(v) => String::from_utf8_lossy(&v).into_owned(),
            None => "(nil)".to_string(),
        },
        ("del", Some(key), None) => (if db.del(key.as_bytes())? { "1" } else { "0" }).to_string(),
        ("count", None, None) => db.index.len().to_string(),
        ("compact", None, None) => {
            let (before, after) = db.compact()?;
            format!("{before} → {after} 바이트")
        }
        (".exit", None, None) => return Ok(None),
        _ => bail!("알 수 없는 명령 (set KEY VALUE | get KEY | del KEY | count | compact | .exit)"),
    };
    Ok(Some(reply))
}

fn main() -> Result<()> {
    let path = std::env::args().nth(1).unwrap_or_else(|| "mydb.log".to_string());
    let mut db = Db::open(Path::new(&path))?;
    let stdin = io::stdin();
    let interactive = stdin.is_terminal();
    let mut out = io::stdout().lock();
    let mut line = String::new();
    loop {
        if interactive {
            write!(out, "mydb> ")?;
            out.flush()?;
        }
        line.clear();
        if stdin.read_line(&mut line)? == 0 {
            break; // 입력 끝 (Ctrl+D)
        }
        match execute(&mut db, line.trim_end_matches(['\n', '\r'])) {
            Ok(Some(reply)) if reply.is_empty() => {}
            Ok(Some(reply)) => writeln!(out, "{reply}")?,
            Ok(None) => break,
            Err(e) => writeln!(out, "에러: {e:#}")?,
        }
    }
    Ok(())
}

핵심 요약

  • 레코드는 crc32 | key_len | val_len | key | value. 길이 접두사로 경계를 정하고, crc는 길이 필드부터 값 끝까지 덮어 레코드가 온전한지 확인합니다. 바이트 순서는 리틀 엔디언으로 정해 둡니다.
  • 쓰기는 파일 끝에 덧붙이기만 하고, 메모리 색인(keydir)이 키마다 최신 레코드의 위치를 가리킵니다. 읽기는 디스크 탐색 한 번입니다.
  • 삭제는 tombstone 레코드를 덧붙여 표현합니다. 없으면 재시작할 때 지운 값이 되살아납니다.
  • 시작할 때 로그를 재생해 색인을 만들고, 찢어지거나 crc가 틀린 꼬리는 잘라 냅니다.
  • 쓰레기는 compaction으로 치웁니다. 새 파일을 쓰고 → sync_all → rename해야 어느 순간에 꺼져도 안전합니다.
  • 한계: 모든 키가 메모리에, 범위 질의 불가, 재생 시간이 로그 크기에 비례. 2장의 페이지와 3장의 B+트리가 이를 풉니다.

확인 문제

레코드 형식에서 crc가 길이 필드까지 덮어야 하는 이유는?
길이 필드는 "다음 레코드가 어디서 시작하는가"를 정합니다. 이 숫자가 틀리면 재생 전체가 엉뚱한 바이트를 레코드로 읽게 됩니다.
tombstone 없이 색인에서만 키를 지우면 어떤 일이 생기나?
색인은 메모리에만 있습니다. 파일에 "지웠다"는 기록이 없으면, 재생은 그 키의 마지막 set을 최신 상태로 판단합니다.
재생 중 레코드 하나의 crc가 맞지 않았다. mydb가 그 지점에서 멈추고 뒤를 잘라 내는 이유는?
깨진 레코드의 길이를 믿고 건너뛸 수는 없습니다. 덧붙이기 전용 로그에서 손상은 대개 "마지막 쓰기가 끝나지 못한" 꼬리에 생기므로, 그 지점 이후를 버리는 것이 안전합니다.
compaction에서 임시 파일을 sync_all하지 않고 바로 rename하면 어떤 위험이 있나?
rename의 원자성은 "이름이 어느 파일을 가리키는가"에 대한 것입니다. 새 파일의 내용이 디스크에 있다는 보장은 fsync(sync_all)가 해 줍니다.
mydb 1장 구조로 효율적으로 할 수 없는 질의는?
해시맵 색인은 키를 정렬하지 않습니다. 범위 질의는 모든 키를 훑어야 합니다. 정렬된 색인(B+트리, 3장)이 필요합니다.
값의 길이가 0인 레코드(빈 문자열)와 tombstone을 어떻게 구분하나?
set k (빈 값)는 val_len 0, del k는 val_len 0xFFFFFFFF입니다. 4바이트 길이로 4 GB에 가까운 값은 어차피 못 쓰므로 최댓값 하나를 표시로 빌려 씁니다.
