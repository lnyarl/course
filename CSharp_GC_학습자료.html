.NET CLR · Garbage Collector

C# 가비지 컬렉터 해부

C#에서는 new만 하고 delete는 하지 않습니다. 그 뒤처리를 맡는 CLR의 GC가 언제, 무엇을, 어떻게 치우는지 직접 조작하면서 익히고, 실무에서 마주치는 설정·진단까지 이어서 다룹니다.

도달성 기반 추적형(tracing)·정확(precise) GC세대 Gen0 · Gen1 · Gen2LOH 기준 85,000 bytes압축 있음기준 런타임 .NET 8~10 (64비트)
PART 1 · 기초

01관리 힙과 할당

CLR은 관리 힙에서 다음 할당 위치를 포인터 하나로 기억합니다. new는 이 포인터를 객체 크기만큼 앞으로 미는 것이 거의 전부라서, C의 malloc처럼 맞는 빈 블록을 찾아다니지 않습니다. 대신 Gen0 예산을 다 쓰면 GC가 돌아 쓰레기를 치우고 공간을 다시 만듭니다.

직접 할당해 보기

힙의 블록을 클릭하면 지역 변수나 필드가 계속 참조하는 객체(주황)로 바뀝니다. 클릭하지 않은 객체는 잠깐 쓰고 버린 임시 객체입니다. GC가 돌면 참조가 남아 있는 객체만 살아남습니다.

alloc_ptr
Gen0 사용 0 / 24 칸GC 횟수 0Gen1으로 승격 0

실제로는 이렇게 동작합니다

  • 할당 컨텍스트: 스레드마다 GC에게서 받은 작은 메모리 조각(allocation quantum, 대략 8KB)을 갖고, 그 안에서 락 없이 포인터만 밉니다. 조각이 바닥나면 느린 경로로 GC에 새 조각을 요청하고, 이때 Gen0 예산이 소진됐으면 GC가 시작됩니다.
  • 0으로 초기화: 조각은 미리 0으로 채워져 나오기 때문에 필드 기본값이 보장됩니다. 큰 배열에서 이 비용을 피하려면 GC.AllocateUninitializedArray<T>()를 쓸 수 있습니다(내용을 반드시 직접 채울 때만).
  • 객체 레이아웃(64비트): 참조는 메서드 테이블 포인터를 가리키고, 그 앞 8바이트에 객체 헤더(동기화 블록 인덱스, 해시 코드 등)가 있습니다. 필드가 없는 객체도 최소 24바이트입니다.

02GC는 언제 도는가

GC는 타이머로 돌지 않습니다. 대부분 할당이 예산을 넘는 순간 할당을 시도한 스레드에서 시작됩니다. 할당을 줄이면 GC 횟수도 줄어드는 이유입니다.

트리거설명ETW/트레이스의 GC Reason
Gen0 예산 초과가장 흔한 경우. 새 할당 조각을 받으려는데 Gen0 예산을 다 씀AllocSmall
LOH·POH 예산 초과큰 객체 할당이 누적되어 예산을 넘음. Gen2 GC로 이어짐AllocLarge
명시적 호출GC.Collect(), 메모리 압박 알림 등 코드가 유도Induced
시스템 메모리 부족OS의 저메모리 알림, 또는 힙 하드 리밋(13장)에 근접LowMemory 등
  • 예산은 고정값이 아닙니다. Gen0 예산은 시작할 때 CPU 캐시(L3) 크기 등을 바탕으로 정하고, 이후 GC마다 각 세대의 생존율을 보고 다시 계산합니다. 생존율이 높으면 GC를 해도 얻는 게 적으므로 예산을 키워 GC 빈도를 낮춥니다.
  • 어느 세대를 수거할지도 GC가 정합니다. 기본은 예산을 넘은 가장 높은 세대이고, 단편화나 메모리 부족 같은 요인이 있으면 더 높은 세대로 올라갑니다.
  • GC.CollectionCount(0)은 Gen1·Gen2 GC도 함께 셉니다. 높은 세대 GC는 낮은 세대도 수거하기 때문입니다.

다음 GC는 몇 세대일까 (단순화한 모델)

Gen0 예산은 방금 다 썼다고 가정합니다. 다른 세대의 예산 사용률을 바꿔 보세요.

03Mark · Sweep · Compact

GC는 참조 카운트를 세지 않습니다. 루트(스택의 지역 변수, CPU 레지스터, static 필드, GC 핸들, F-Reachable 큐)에서 출발해 참조를 따라가며 닿는 객체에 표시(mark)하고, 닿지 않은 객체는 모두 쓰레기로 봅니다. 그래서 서로를 가리키는 순환 참조도 루트와 끊기면 회수됩니다.

힙 객체도달 가능(marked)빈 공간
  • Compact: 살아남은 객체를 앞으로 당기고, 그 객체를 가리키던 모든 참조의 주소를 고칩니다. 단편화가 사라지고 포인터를 미는 빠른 할당을 계속 쓸 수 있습니다.
  • 매번 압축하지는 않습니다. 압축으로 얻는 게 적으면 빈 공간을 free list로 엮는 Sweep만 합니다. 실제 단계는 다음 장에서 봅니다.

스레드는 어디서 멈추는가: 안전 지점

GC는 각 스레드의 스택 어디에 참조가 있는지 정확히 알아야 합니다. JIT은 메서드를 컴파일할 때 "이 지점에서는 이 슬롯과 레지스터가 참조다"라는 GC 정보를 함께 만들고, 이 정보가 있는 지점이 안전 지점(safe point)입니다.

스레드 상태런타임이 멈추는 방법
네이티브 코드 실행 중 (P/Invoke, 블로킹 I/O)멈출 필요 없음(preemptive 모드). 관리 코드로 돌아오는 순간 GC가 끝날 때까지 대기
partially interruptible 메서드 실행 중호출 지점에만 GC 정보가 있음. 반환 주소를 바꿔치기(return address hijacking)해 메서드가 리턴할 때 멈추게 함. JIT이 넣은 GC poll 지점에서 스스로 멈추기도 함
fully interruptible 메서드 (호출 없는 긴 루프 등)모든 명령에 GC 정보가 있어 어디서든 멈출 수 있음. 스레드를 세운 뒤 명령 포인터를 리디렉션함. 호출 없는 루프는 JIT이 이 방식으로 컴파일함

스레드를 모두 세우는 데 걸리는 시간(time to suspend)도 GC 멈춤의 일부입니다. 트레이스에서 GC 자체는 짧은데 멈춤이 길다면 스레드 정지 지연을 의심하세요.

05루트의 수명과 JIT

지역 변수는 메서드가 끝날 때까지 루트일 것 같지만 그렇지 않습니다. 최적화된(Release) 코드에서 JIT은 지역 변수를 마지막으로 사용한 지점까지만 살아 있다고 GC에 보고합니다. 메서드가 아직 실행 중이어도 객체가 회수될 수 있습니다.

System.Threading.Timer가 멈추는 버그

  • Debug 빌드나 디버거가 붙은 상태에서는 JIT이 지역 변수의 수명을 메서드 끝까지 늘립니다. 그래서 이 버그는 Release에서만 재현되곤 합니다.
  • GC.KeepAlive(obj)는 아무 일도 하지 않는 메서드지만, 호출 지점까지 obj를 사용 중인 것으로 만들어 수명을 늘립니다.
  • this도 마찬가지입니다. 인스턴스 메서드에서 this를 마지막으로 쓴 뒤 네이티브 핸들 값만 들고 작업하면, 그 사이 finalizer가 실행되어 핸들을 닫을 수 있습니다. SafeHandle은 호출 동안 참조 카운트로 이 문제를 막습니다.
  • 내부 포인터(byref): ref int r = ref arr[5];나 Span<T>는 객체 중간을 가리킵니다. GC는 이것도 추적해 객체를 살려 두고 압축 때 함께 고칩니다. 대신 byref는 스택에만 둘 수 있어서, Span<T>가 ref struct로 묶여 클래스 필드나 박싱이 금지됩니다.

06세대별 GC

대부분의 객체는 금방 죽고, 오래 산 객체는 계속 산다는 세대 가설에 기대어 힙을 세 세대로 나눕니다. 새 객체는 Gen0에 들어가고, GC를 한 번 살아남을 때마다 다음 세대로 승격됩니다. 자주 도는 Gen0 GC는 작은 영역만 보기 때문에 빠릅니다.

    통계는 "그 GC가 수거한 가장 높은 세대" 기준으로 셉니다(GC.CollectionCount와 세는 방식이 다름).

    • Gen1 GC는 Gen0과 Gen1을, Gen2 GC는 LOH·POH를 포함한 전체 힙(Full GC)을 수거합니다.
    • 빗금 칸을 보세요. 죽은 객체도 그 세대의 GC가 돌기 전까지 메모리를 차지합니다. Gen2로 넘어간 뒤 죽은 객체는 비싼 Full GC가 돌 때까지 남습니다.
    • 비율을 40% 이상으로 올리면 Gen2가 빠르게 차고 Full GC가 잦아집니다. 딱 Gen2까지 살아남고 곧 죽는 중간 수명 객체(요청 단위 캐시, 오래 걸리는 작업의 버퍼)가 성능 문제를 자주 일으킵니다. 이를 "mid-life crisis"라고 부릅니다.

    07쓰기 장벽과 카드 테이블

    Gen0만 수거하려면 Gen0 객체를 가리키는 참조를 모두 알아야 합니다. 그런데 Gen2 객체의 필드가 Gen0 객체를 가리킬 수도 있습니다. Gen2 전체를 뒤지면 세대 분리의 의미가 없어지므로, JIT은 힙에 있는 참조 필드에 값을 쓸 때마다 쓰기 장벽(write barrier) 코드를 넣고, 장벽은 해당 메모리 구간의 카드를 더티로 표시합니다.

    • 장벽은 힙 객체의 참조 타입 필드나 참조 배열 원소에 쓸 때 붙습니다. 지역 변수나 참조가 없는 값 타입 필드(int 등) 쓰기에는 없고, 참조를 담은 struct를 힙에 복사하면 그 참조 필드마다 장벽이 붙습니다.
    • 장벽은 저장하는 참조 값이 젊은 세대를 가리킬 때만 카드를 표시하도록 빠르게 걸러 내지만, 참조를 대량으로 쓰는 핫 루프에서는 비용이 쌓입니다. 오래된 객체가 젊은 객체를 많이 가리킬수록 Gen0 GC가 훑어야 할 카드도 많아집니다.

    08LOH와 POH

    큰 객체를 매번 복사하며 압축하면 비쌉니다. 그래서 85,000바이트 이상의 객체는 처음부터 LOH(Large Object Heap)에 할당되고 논리적으로 Gen2로 취급됩니다. Gen2 GC에서만 수거되고, 기본적으로 압축되지 않아 단편화가 생길 수 있습니다. .NET 5부터는 고정(pinned) 객체 전용 POH가 따로 있습니다.

    이 배열은 어디에 할당될까?

    new byte[]

    SOH · Gen0

    85,000B 미만. 세대별로 수거·압축. 대부분의 객체.

    LOH

    85,000B 이상. Gen2와 함께 수거. 기본 비압축.

    POH

    .NET 5+. 고정 객체 전용. 이동하지 않아 압축을 방해하지 않음.

    • LOH 압축이 꼭 필요하면 GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce;로 다음 블로킹 Gen2 GC에서 한 번 압축합니다.
    • 큰 버퍼를 자주 만들고 버리면 LOH 예산이 빨리 차서 Gen2 GC가 잦아집니다(02장의 AllocLarge). ArrayPool<T>로 재사용하세요.
    • 기준값은 GCLOHThreshold 설정으로 올릴 수 있습니다(낮출 수는 없음).

    09Pinning과 단편화

    네이티브 코드에 버퍼 주소를 넘기는 동안 GC가 그 객체를 옮기면 안 됩니다. 그래서 객체를 고정(pin)합니다. 고정된 객체는 압축 때 제자리에 남고, 다른 객체는 그 객체를 넘어 이동하지 못합니다. 그 앞에 생긴 빈틈은 연속 공간으로 합쳐지지 못하고 남습니다.

    고정할 객체를 골라 압축해 보기

    살아 있는 객체(대문자)를 클릭하면 고정을 켜고 끕니다. 소문자는 이미 죽은 객체입니다.

    고정 방법고정 기간메모

    P/Invoke 마샬링호출 동안blittable 배열·문자열은 복사 없이 자동 고정됨
    GCHandle.Alloc(obj, GCHandleType.Pinned)Free() 할 때까지오래 잡으면 단편화의 주범. Free 누락은 누수
    Memory<T>.Pin()MemoryHandle.Dispose() 할 때까지비동기 I/O에서 흔히 쓰임

    10Regions (.NET 7+)

    .NET 6까지 GC는 큰 연속 구간인 세그먼트로 힙을 관리했습니다. .NET 7부터 64비트 런타임(.NET 7 당시에는 macOS·NativeAOT 제외)은 힙을 작은 region들로 쪼개고, 각 세대를 region 목록으로 관리합니다. 세대, LOH, 압축이라는 개념은 그대로이고 메모리를 담는 그릇이 바뀌었습니다.

    • 기본 region 크기는 SOH용 4MB, LOH·POH용은 그 8배인 32MB입니다. 하드 리밋이 작은 컨테이너처럼 예약 범위가 작으면 2MB·1MB로 자동 축소됩니다. LOH·POH region보다 큰 객체는 전용 region을 받습니다.
    • 빈 region은 어느 세대나 힙에서도 가져다 쓸 수 있고, 남으면 OS에 반환(decommit)하기 쉽습니다. 세그먼트 시절에는 한 세그먼트 안의 빈 공간이 다른 세대로 넘어가기 어려웠습니다.
    • 생존율이 높은 region은 객체를 복사하지 않고 region째로 다음 세대에 넘길 수 있고, 고정 객체가 많은 region도 따로 다룰 수 있습니다.
    • .NET 7부터 세그먼트 기반 GC(clrgc.dll / libclrgc.so)를 함께 배포해, 문제가 생기면 DOTNET_GCName으로 되돌릴 수 있습니다(.NET 10에도 포함).

    14Finalizer와 IDisposable
    
      
    GC는 메모리만 관리합니다. 파일 핸들, 소켓, DB 연결 같은 비관리 리소스를 언제 정리할지 모르는 GC에 맡기면 안 됩니다. Finalizer(~ClassName())는 마지막 안전망일 뿐이고 비용도 큽니다. 세 흐름을 비교해 보세요.
    
      
    
        
    
          
          
          
        
    
        
    
        
    
          
          
          
        
    
        
    
      
    
      
    public sealed class FileHandle : IDisposable
{
    private IntPtr _handle;            // 비관리 리소스
    private bool _disposed;

    public void Dispose()
    {
        if (_disposed) return;
        NativeMethods.CloseHandle(_handle);
        _disposed = true;
        GC.SuppressFinalize(this);     // finalization 큐에서 빼서 일반 객체처럼 회수
    }

    ~FileHandle() => NativeMethods.CloseHandle(_handle);  // Dispose를 잊었을 때의 안전망
}

using var file = new FileHandle("log.txt");   // 스코프를 벗어나면 Dispose()
    
      
    실무에서는 finalizer를 직접 쓰기보다 SafeHandle을 상속해 핸들을 감싸는 방식을 권장합니다. 관리 리소스만 가진 클래스에는 finalizer를 만들지 마세요.
    
      
    Finalizer의 함정
    
      
      
        
    • Finalizer 스레드는 하나뿐입니다. finalizer 하나가 락이나 UI 스레드를 기다리며 막히면 뒤의 모든 finalizable 객체가 F-Reachable 큐에 쌓여 메모리가 새는 것처럼 보입니다(dotnet-dump의 finalizequeue로 확인).
      • 
        
    • 실행 순서가 보장되지 않습니다. finalizer 안에서 다른 관리 객체 필드를 쓰면 그 객체가 이미 finalize되었을 수 있습니다. 예외로 CriticalFinalizerObject(예: SafeHandle)의 finalizer는 같은 시점에 수거되는 일반 finalizer보다 뒤에 실행됩니다.
      • 
        
    • .NET Core / .NET 5+는 프로세스 종료 시 finalizer를 실행하지 않습니다(.NET Framework는 실행). 종료 정리는 AppDomain.ProcessExit나 호스트 수명 이벤트로 하세요.
      • 
        
    • finalizer에서 처리되지 않은 예외는 프로세스를 종료시킵니다.
      • 
        
    • 테스트에서 finalizer까지 확실히 돌리려면 GC.Collect(); GC.WaitForPendingFinalizers(); GC.Collect(); 순서로 호출합니다.
      • 
      
    
    
    

    
    
    
      
    15GC 핸들과 약한 참조
    
      
    GC 핸들은 런타임의 핸들 테이블에 있는 항목으로, 관리 코드 바깥(네이티브 코드, 런타임 내부)이 관리 객체를 붙잡거나 지켜보는 수단입니다. 강한 핸들은 그 자체가 루트입니다.
    
      
    
        
    핸들 종류객체를 살리나이동 가능쓰는 곳
    
        
          
    Normal (강한 핸들)예예네이티브 콜백에 관리 객체를 넘길 때 (GCHandle.ToIntPtr)
    
          
    Pinned예아니오네이티브에 버퍼 주소 전달 (09장)
    
          
    Weak (short)아니오-WeakReference<T> 기본값. 객체가 도달 불가가 되면 finalizer 실행 전에 null
    
          
    WeakTrackResurrection (long)아니오-trackResurrection: true. finalizer가 끝나고 실제로 회수될 때 null
    
          
    Dependent1차 객체가 살아 있는 동안 2차 객체를 살림-ConditionalWeakTable의 기반. DependentHandle로 공개(.NET 6+)
    
            
      
    
      
    GCHandle.Alloc으로 만든 핸들은 Free()를 부르지 않으면 영원히 남습니다. 강한 핸들이라면 대상 객체와 그 객체가 참조하는 모든 것이 함께 새어 나갑니다.
    
      
    
        
    
          
    WeakReference 실험
    
          
    
            
            
          
    
          
          
    
          
    
        
    
        
    var image = new Bitmap("big.png");
var weak  = new WeakReference<Bitmap>(image);

image = null;          // 강한 참조 제거
GC.Collect();
// Debug 빌드·디버거 연결 시에는 JIT이 지역 변수를
// 메서드 끝까지 살려 둘 수 있어 회수되지 않을 수 있음

if (weak.TryGetTarget(out var img))
    Draw(img);         // 아직 살아 있음
else
    Reload();          // 회수됨 → 다시 로드
    
      
    
      
    약한 참조로 캐시를 만들면 대상 객체가 속한 세대의 GC가 돌 때마다 항목이 사라져 히트율이 들쭉날쭉합니다. 일반적인 캐시는 크기 제한과 만료가 있는 MemoryCache가 낫습니다. ConditionalWeakTable<TKey,TValue>은 "키 객체가 살아 있는 동안만 부가 정보를 붙여 두기"에 맞습니다.

    16숨은 할당 찾기
    
      
    GC 부담을 줄이는 가장 확실한 방법은 할당 자체를 줄이는 것입니다. 문제는 new가 보이지 않는 할당입니다. 먼저 흔한 오해 하나부터 정리합니다.
    
      
    
        
    값 타입(struct)이 놓인 곳실제 위치
    
        
          
    메서드의 지역 변수스택 또는 레지스터
    
          
    클래스의 필드그 객체 안 (힙)
    
          
    배열 원소 new Point[100]배열 객체 안 (힙). 원소마다 따로 할당하지는 않음
    
          
    람다가 캡처한 지역 변수컴파일러가 만든 클로저 객체 안 (힙)
    
          
    async 메서드에서 await를 넘어 쓰는 지역 변수상태 머신의 필드. 실제로 비동기 대기하면 상태 머신이 힙으로 옮겨짐
    
          
    object나 인터페이스 타입 변수에 대입박싱되어 힙에 복사본 생성
    
            
      
    
      
    "struct는 스택, class는 힙"은 틀린 말입니다. 값 타입은 선언된 곳에 저장됩니다.
    
      
    
        
    이 코드는 힙에 할당할까? 
    
        
    
      
    
      
    .NET 9부터 JIT이 탈출 분석(escape analysis)으로 메서드 밖으로 나가지 않는 일부 박싱을 스택에 할당하기 시작했고, .NET 10에서는 작은 배열·delegate·일부 열거자까지 범위를 넓혔습니다. 다만 적용 범위가 좁고 버전마다 다르므로 기대지 말고 측정하세요.
    
    
    

    
    
    
      
    17진단과 체크리스트
    
      
    메모리가 계속 늘어나는 서비스를 추적하는 흐름입니다. 출력은 형식을 보여 주기 위한 예시입니다.
    
      
    
        
    
        
    
        
    
      
    
      
    증상별 체크리스트
    
      
    
        
    증상 / 상황흔한 원인대응
    
        
          
    Gen0 GC가 초당 수십~수백 번핫 경로의 짧은 할당(문자열 연결, LINQ, 박싱, 클로저)Span<T>, StringBuilder, struct, static 람다, 풀링
    
          
    Gen2 GC가 잦고 멈춤이 김중간 수명 객체 승격, 끝없이 커지는 캐시, LOH 할당캐시 상한·만료, ArrayPool<T>, 객체 풀
    
          
    GC 후에도 힙이 계속 증가해제 안 한 이벤트 구독, static 컬렉션, GCHandle 누수-=로 구독 해제, 덤프의 gcroot로 루트 경로 확인
    
          
    힙은 작은데 프로세스 메모리가 큼네이티브 메모리, Server GC의 힙별 예산, 단편화GetGCMemoryInfo().FragmentedBytes, DATAS, GCConserveMemory
    
          
    GC 시간은 짧은데 멈춤이 김스레드 정지 지연(긴 네이티브 전환, 루프)트레이스에서 suspension 시간 확인 (04장)
    
          
    코드에 GC.Collect()GC의 예산 조정을 망가뜨림제거하고 원인 할당을 줄이기. 테스트·벤치마크 외에는 쓰지 않기

byte[] buf = ArrayPool<byte>.Shared.Rent(1 << 20);
try { /* ... */ }
finally { ArrayPool<byte>.Shared.Return(buf); }

// 부분 문자열을 새로 만들지 않는다

    18Unity · Mono GC
    
      
    같은 C#이라도 런타임이 다르면 GC도 다릅니다. 지금까지의 내용은 .NET(CoreCLR) 기준입니다. Unity는 Mono와 IL2CPP 백엔드 모두 Boehm-Demers-Weiser GC를 씁니다.
    
      
    
        
    .NET (CoreCLR)Unity (Boehm)Mono SGen
    
        
          
    세대Gen0/1/2없음 (매번 전체 힙)nursery + major
    
          
    압축있음없음 (객체를 옮기지 않음)nursery는 복사, major는 상황에 따라
    
          
    스택 스캔정확(precise)보수적(conservative): 참조처럼 보이는 값은 참조로 간주스택은 보수적, 힙은 정확
    
          
    멈춤 줄이기Background GCIncremental GC: 수거 작업을 여러 프레임에 나눔concurrent mark 옵션
    
          
    쓰이는 곳.NET 서버·데스크톱, NativeAOTUnity 에디터·플레이어.NET의 Mono 기반 대상(모바일, WebAssembly)
    
            
      
    
      
    
        
    프레임 시간에서 보는 차이
    
        
    
          
          
        
    
        
    
        
    
      
    
      
      
        
    • 압축이 없으므로 단편화가 쌓이면 힙이 커지기만 할 수 있습니다. 큰 배열을 반복 생성하지 마세요.

    • Update()에서의 할당(문자열 조합, GetComponent 결과 배열, LINQ, 박싱)을 프로파일러의 GC.Alloc 열로 찾아 0으로 만드는 것이 기본 전략입니다.
      • 
        
    • UnityEngine.Pool.ObjectPool<T>로 재사용하고, 로딩 화면처럼 멈춰도 되는 시점에 수동 수거합니다.
      • 
        
    • UnityEngine.Scripting.GarbageCollector: GCMode(Enabled / Disabled / Manual), CollectIncremental(nanoseconds), incrementalTimeSliceNanoseconds로 직접 제어할 수 있습니다.
      • 
        
    • Unity는 CoreCLR 런타임으로의 전환을 예고했습니다. 사용하는 Unity 버전의 문서를 확인하세요.
