Kestrel·Pipelines와 스트리밍 업로드

선수 장 · HTTP 서버의 책임

큰 파일을 요청당 byte 배열 하나로 읽으면 동시 업로드 수만큼 메모리가 늘어납니다. 서버의 바이트 처리 경계에서 버퍼를 누가 소유하고 언제 돌려주는지 따라갑니다.

본문을 끝까지 모으기 전에 처리하기

먼저 await request.Body.CopyToAsync(destination, requestAborted)처럼 작은 버퍼로 복사하는 기준 경로를 만듭니다. 전체 본문을 문자열로 바꾸는 경로와 같은 입력으로 비교합니다. Content-Length가 없거나 실제 본문과 다를 수 있으므로 수신한 바이트를 누적해 애플리케이션의 허용 상한도 검사합니다.

Kestrel·앞단 프록시·앱의 크기와 시간 제한은 서로 다른 경계입니다. endpoint 로그 없이 거절됐다면 요청이 없었다는 뜻이 아닙니다. 거절 위치, 저장한 바이트 수, 임시 파일 정리 결과를 함께 남기고 성공 응답 전에 필요한 저장 완료 조건을 정의합니다.

PipeReader의 소유권을 읽는 순서

var read = await request.BodyReader.ReadAsync(ct)가 준 Buffer는 여러 구간의 ReadOnlySequence일 수 있습니다. 처리한 위치를 consumed, 더 확인한 위치를 examined로 계산하고 AdvanceTo(consumed, examined)를 호출합니다. AdvanceTo 뒤의 메모리 참조를 보관하거나 같은 바이트를 다음 호출에서 다시 처리하지 않는 불변식이 필요합니다.

부분 레코드가 남으면 미소비 구간은 보존하고 새 데이터가 필요한 위치까지 examined를 옮깁니다. examined를 잘못 주면 같은 버퍼를 반복해서 받거나 데이터가 있는데도 다음 입력을 기다릴 수 있습니다. framework가 제공한 BodyReader의 수명과 자신이 만든 PipeReader의 CompleteAsync 책임도 구분합니다.

실습과 예상 관찰

로컬 업로드 endpoint를 두 개 만들어 같은 작은 파일을 전체 버퍼링과 스트리밍으로 저장하세요. 전송량 상한과 요청 중단 토큰을 적용한 뒤 파일 크기·동시 요청 수·소비 속도를 한 가지씩 바꿉니다. 저장 파일 해시와 임시 파일 잔존 수, 프로세스 메모리를 함께 비교하세요.

소비자가 느린 스트리밍

수신 흐름에 역압력이 전달될 수 있고 전체 본문 보관을 줄입니다. 연결과 저장 자원은 더 오래 유지될 수 있습니다.

전송 도중 클라이언트 중단

하위 복사에 토큰을 전달하고 finally에서 임시 파일을 정리해야 합니다. 이미 완료한 외부 효과까지 자동 롤백되지는 않습니다.

실습의 경계와 다음 장

이 단원은 로컬 업로드의 메모리·수명 계약입니다. 실제 프록시 제한은 그 구성을 포함한 별도 검사로 확인하고, 최적화 장에서 응답 스트리밍의 실패 경계와 비교합니다.
