EF Core 저장·트랜잭션·경합 실험

선수 장 · LINQ 아래의 SQL과 트랜잭션

한 요청에서 저장이 성공해도 두 요청이 같은 버전을 갱신하면 다른 문제가 생깁니다. LINQ와 SQL의 연결을 실제 제약조건과 충돌 결과까지 확인합니다.

두 context가 같은 과거를 읽었을 때

서로 다른 DbContext에서 같은 행을 읽고 각각 값을 바꿉니다. Version 속성에 IsConcurrencyToken()을 설정하면 UPDATE의 조건에 읽었던 버전이 포함됩니다. 애플리케이션 관리 Guid 버전이라면 새 갱신마다 Guid.NewGuid()를 지정하는 코드도 함께 구현해야 합니다.

A를 SaveChangesAsync한 뒤 B를 저장하면 B가 본 버전이 더는 맞지 않아 DbUpdateConcurrencyException을 받을 수 있습니다. 낙관적 충돌은 모든 입력 오류나 unique 위반과 같은 예외가 아닙니다. 충돌 후 현재 값을 다시 읽고 재계산할지 사용자에게 돌려줄지 업무 계약으로 정합니다.

DB가 최종 불변식을 지키게 하기

같은 접수 키를 동시에 추가하지 못하게 하려면 메모리의 선행 조회만으로 부족합니다. 실제 테이블의 unique constraint가 최종 경쟁을 조정하고, provider가 돌려주는 제약 위반을 앱의 충돌 계약으로 변환합니다. DbContext를 여러 병렬 작업에서 공유하지 않습니다.

여러 변경을 하나의 DB 트랜잭션에 묶는 것과 외부 HTTP 효과를 함께 원자화하는 것은 다릅니다. 실행 전략이 재시도하는 단위를 읽고, 사용자가 시작한 트랜잭션을 그 전략과 함께 쓸 때의 공식 패턴을 확인합니다. 재시도해도 안전한 작업 키와 결과 기록이 없으면 중복 효과가 생길 수 있습니다.

실습과 예상 관찰

운영과 같은 종류의 로컬 테스트 DB를 준비하거나 차이를 명시한 관계형 SQLite 실습을 만드세요. 두 context에서 같은 버전을 읽고 A 저장 후 B 저장을 시도합니다. 이어 unique 키가 같은 두 삽입의 결과와 실행 SQL을 기록하고, 각 실패가 서로 다른 계약으로 응답되는지 검사하세요.

버전 조건 없는 갱신

나중 저장이 앞선 변경을 덮을 수 있습니다. 요청마다 성공 응답만 세면 잃은 변경을 놓칩니다.

concurrency token과 unique 제약 적용

갱신 충돌과 중복 삽입을 DB 결과로 분류할 수 있습니다. 충돌을 감지했다고 업무 재계산 정책까지 자동으로 정해지지는 않습니다.

실습의 경계와 다음 장

SQLite나 InMemory 테스트의 성공을 다른 provider의 격리·SQL 의미로 일반화하지 않습니다. 테스트 장에서는 실제 DB를 포함한 경합 경로를 검증 범위로 표시합니다.
