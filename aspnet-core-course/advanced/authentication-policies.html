인증 scheme·리소스 policy·키 수명

선수 장 · 인증과 리소스 권한

로그인한 사용자만 허용한 뒤에도 다른 사람의 작업을 읽을 수 있다면 리소스 정책이 빠진 것입니다. 테스트용 신원과 실제 자격 증명 검증을 분리해 범위를 확인합니다.

신원 선택과 리소스 결정

인증 scheme은 어떤 handler가 쿠키나 bearer 자격 증명을 읽을지 정합니다. RequireAuthorization은 선택한 정책과 신원을 연결하지만, 특정 작업의 소유자를 자동으로 판단하지는 않습니다. 작업을 로드한 뒤 IAuthorizationService.AuthorizeAsync(user, resource, policy)로 자원별 조건을 평가하는 흐름을 그립니다.

자신의 실습 계정 A·B와 A의 작업 하나로 본인 조회, 다른 사용자 조회, 미인증 조회를 나눕니다. 읽기와 취소는 다른 권한일 수 있습니다. 없는 리소스와 권한 없는 리소스를 같은 404로 감출지는 API 정책이며, 표준 401·403·리다이렉트와 혼동하지 않습니다.

자격 증명과 키를 갱신하는 경계

JWT 검증은 서명 외에 발급자·대상·만료와 허용한 알고리즘을 다룹니다. 키 회전에서는 새 토큰 발급과 이미 발급된 토큰 검증의 유예가 겹칩니다. 키가 바뀌었다고 기존 요청이나 모든 세션이 자동으로 폐기되는 것은 아니므로 갱신·철회 정책을 별도로 정합니다.

쿠키 기반 앱에서는 Data Protection 키가 여러 인스턴스 사이의 쿠키 해독과 배포 뒤 세션 유지에 영향을 줍니다. 개발용 임시 키 저장과 운영용 키 저장 수명을 구분합니다. 테스트에서 인증을 fake handler로 바꾸면 업무 인가를 검사할 수 있지만 실제 토큰 서명·키 회전 검증은 빠졌다고 기록합니다.

실습과 예상 관찰

본인이 관리하는 로컬 테스트 앱과 정상 자격 증명만 사용하세요. A·B·미인증의 조회/취소 응답 표를 만들고 실제 인증 scheme으로 실행합니다. 별도 테스트에서는 fake handler로 바꿔 결과를 비교하고, 개발 키 저장을 유지한 재시작과 새 저장소의 재시작에서 기존 쿠키가 어떻게 달라지는지 관측하세요.

인증만 검사하고 소유권 정책 생략

신원은 확인됐어도 리소스별 허용 여부는 결정되지 않았습니다. 실습의 A/B 권한 표가 이 공백을 드러냅니다.

정책과 실제 인증 검증을 각각 검사

리소스 규칙의 결과와 자격 증명 검증 결과를 분리해 설명할 수 있습니다. fake 인증 테스트를 실제 키 수명 검사로 보고하지 않습니다.

실습의 경계와 다음 장

이 단원은 정상 계정의 권한 경계 검증입니다. 자격 증명 위조나 공격 재현은 포함하지 않습니다. 다음 통합 테스트에서 신원·리소스·저장의 실제 경로를 함께 검증합니다.
