HttpClient 연결 수명과 복원력

선수 장 · 비동기와 취소

비동기 외부 호출을 해도 연결이 고갈되거나 이름 변경이 늦게 반영될 수 있습니다. await 계약에서 연결 풀과 전체 호출 예산으로 범위를 넓힙니다.

클라이언트 객체와 연결 풀의 수명

요청마다 새 SocketsHttpHandler를 만들고 버리면 연결 재사용을 잃습니다. 오래 쓰는 HttpClient에 PooledConnectionLifetime을 설정하는 방식과 IHttpClientFactory가 handler 수명을 관리하는 방식을 비교합니다. factory가 만든 HttpClient를 Dispose하는 것과 매번 새 연결 풀을 파괴하는 것은 같은 동작이 아닙니다.

DNS는 이미 열린 연결에 매 요청마다 적용되는 조회가 아닙니다. 연결 수명과 새 연결 생성 시점을 함께 봐야 합니다. 한 서버의 연결 수, 실제 동시 요청 수, 풀 대기 시간은 프로토콜과 제한에 따라 다르며 이름 하나를 설정했다고 모든 종류의 외부 호출이 무제한 병렬이 되지는 않습니다.

타임아웃을 전체 작업 예산으로 연결하기

요청 중단 토큰과 자체 마감 토큰을 연결한 뒤 SendAsync뿐 아니라 응답 본문 읽기에도 전달합니다. HttpCompletionOption.ResponseHeadersRead를 쓴다면 헤더 수신 완료와 본문 완료가 다른 시점입니다. response를 using으로 정리하고, 본문을 읽지 않는 실패 경로가 연결 재사용에 주는 영향도 확인합니다.

재시도마다 새 HttpRequestMessage를 만들고 응답을 정리합니다. 이미 전송한 본문을 그대로 재사용할 수 있는지와 총 예산이 남았는지를 먼저 검사합니다. 상태를 바꾸는 요청이 timeout났다면 상대가 이미 반영했을 수 있으므로 안정된 멱등 키와 정책 없이 재시도 횟수만 늘리지 않습니다.

실습과 예상 관찰

로컬 upstream에 지연 100ms와 1초인 정상 경로를 만들고 호출 앱에서 총 예산을 고정하세요. 요청 중단, 헤더만 빠른 응답/느린 본문, 동시 요청 수 증가를 따로 시험합니다. client 생성 횟수보다 실제 연결·풀 대기·완료 수와 취소 후 upstream 상태를 비교하세요.

헤더 수신만 끝난 뒤 본문이 지연

SendAsync 완료를 전체 외부 호출 완료로 세면 실제 대기를 놓칩니다. 본문 읽기까지 같은 마감과 정리 책임이 필요합니다.

여러 계층이 각자 재시도

전체 시도 수와 대기가 증폭될 수 있습니다. 호출 체인에서 재시도 소유자와 총 마감을 하나의 계약으로 정합니다.

실습의 경계와 다음 장

고정된 연결 수명은 DNS나 서비스 발견의 모든 문제를 해결하지 않습니다. 운영 장에서는 연결 생성·대기·외부 처리 시간을 trace로 나눠 관측합니다.
