화면의 모델을
실제 요청으로 확인하기

외부 NuGet 패키지 없이 실행하는 작은 ASP.NET Core 앱입니다. DI 수명, 미들웨어, 예외 처리와 비동기 대기를 직접 관찰합니다.

.NET 10 SDK가 필요합니다. 이 자료 제작 환경에는 dotnet이 없어 아래 C# 프로젝트의 컴파일·실행은 검증하지 못했습니다. HTML 실험의 브라우저 검증과 구분하세요. 학습 서버는 로컬에서만 실행하세요.

1. 서버 실행

다운로드한 코스 폴더에서 다음 명령을 실행합니다. .NET 10 SDK가 설치된 환경에서 진행하세요.

cd aspnet-core-course/examples/RequestLab
dotnet --version
dotnet run --urls http://127.0.0.1:5080

서버가 5080 포트에서 듣고 있다는 로그를 확인합니다. 포트가 사용 중이면 다른 포트를 지정하고 아래 curl 주소도 바꾸세요.

2. 객체 수명 비교

curl http://127.0.0.1:5080/lifetime
curl http://127.0.0.1:5080/lifetime

기본 Scoped에서는 한 응답의 first와 second가 같고 다음 요청에서는 다른 ID가 나옵니다. 서버 로그에 요청 scope 종료 시 Dispose가 출력되는지 확인하세요.

Program.cs의 AddScoped를 AddSingleton 또는 AddTransient로 바꾸고 서버를 재시작합니다. Singleton이면 요청 사이에도 같은 ID, Transient이면 같은 요청의 두 resolve도 다른 ID가 됩니다. Singleton의 Dispose는 앱 종료 시점에 확인합니다.

3. 대기 방식 비교

curl 'http://127.0.0.1:5080/delay?ms=200&mode=async'
curl 'http://127.0.0.1:5080/delay?ms=200&mode=blocking'

요청 한 건은 두 방식 모두 약 200ms 이상 걸릴 수 있습니다. async의 이점은 I/O 자체의 속도보다 대기 중 스레드 사용에 있습니다. 이 예제의 Task.Delay는 실제 DB I/O를 대신하는 대기 장치입니다.

# macOS/Linux 셸. 동시 요청 10개를 완료할 때까지 기다립니다.
for i in {1..10}; do
  curl -s 'http://127.0.0.1:5080/delay?ms=200&mode=async' &
done
wait

mode를 blocking으로 바꾸고 같은 조건에서 비교합니다. 이 소규모 실험만으로 프레임워크의 처리량 우열을 결론 내리지 마세요. 정식 측정에는 워밍업·반복·CPU·ThreadPool·오류율·부하 발생기 상태가 필요합니다.

4. 실패와 취소

curl -i http://127.0.0.1:5080/fail
curl --max-time 0.1 'http://127.0.0.1:5080/delay?ms=1000&mode=async'

/fail은 의도적으로 예외를 던집니다. IN → OUT 로그 뒤 바깥 예외 처리기가 오류를 기록하고 500 Problem 응답을 만듭니다. finally는 예외 상황에서도 실행되지만, 내부 finally에서 본 응답 상태가 최종 전송 상태와 같다고 가정하면 안 됩니다.

두 번째 명령은 클라이언트 timeout 오류가 예상됩니다. 서버는 RequestAborted를 전달받은 Task.Delay에서 취소를 관찰합니다. 연결 단절 감지 시점은 환경에 따라 다릅니다. blocking 모드의 Thread.Sleep은 진행 중 취소를 관찰하지 않으며, 잠에서 깨어난 다음에야 검사합니다.

5. 관찰 기록

실행 환경과 SDK 버전, 바꾼 설정, 예상한 결과, 실제 로그, 해석을 남기세요. 이 앱에는 DB·실제 사용자 인증·파일 저장·영속 작업 큐가 없습니다. 해당 단원은 장별 실습 지침에 따라 실제 의존성을 추가한 별도 프로젝트에서 검증합니다.
