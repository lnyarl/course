스레드 스케줄링

수천 개의 스레드가 몇 개의 코어를 나눠 쓰는 방법. 우선순위, 레디 큐, 퀀텀, 부스트, 선점, 그리고 멀티프로세서 위에서의 선택 알고리즘을 따라갑니다.

핵심⏱ 약 90분선수: 04장

학습 목표

  • 우선순위 클래스와 상대 우선순위로부터 스레드 우선순위(0–31)를 계산하고, 가변/실시간 범위의 차이를 설명할 수 있다.
  • 스레드 상태(Ready, Running, Standby, Waiting, Transition, DeferredReady, Terminated)와 전이 조건을 말할 수 있다.
  • 프로세서별 레디 큐와 ReadySummary 비트맵으로 다음 스레드를 O(1)에 고르는 원리를 이해한다.
  • 퀀텀, 우선순위 부스트와 감쇠, 선점과 라운드 로빈이 실제 실행 순서에 어떻게 작용하는지 예측할 수 있다.
  • 이상 프로세서·선호도·CPU Sets가 멀티프로세서 스레드 배치에 미치는 영향을 설명할 수 있다.

스케줄러 개관

Windows 스케줄러는 우선순위 기반 선점형입니다. 원칙은 단순합니다. 실행 가능한(Ready) 스레드 중 우선순위가 가장 높은 스레드가 실행된다. 같은 우선순위끼리는 퀀텀(시간 할당량) 단위로 돌아가며(라운드 로빈) 실행되고, 더 높은 우선순위 스레드가 준비되면 실행 중인 스레드는 퀀텀이 남아 있어도 즉시 선점됩니다.

별도의 "스케줄러 스레드"는 없다

스케줄링 코드(Ki* 디스패처)는 이벤트가 생긴 그 자리에서 실행됩니다: 스레드가 대기할 때, 객체가 시그널될 때, 클록 인터럽트에서 퀀텀이 끝날 때, 우선순위·선호도가 바뀔 때.

DISPATCH_LEVEL에서 동작

스레드 선택과 컨텍스트 스위치는 IRQL DISPATCH_LEVEL에서 일어납니다. 그래서 IRQL이 DISPATCH 이상인 코드는 스케줄러에게 선점되지 않습니다(06장).

단위는 스레드

프로세스는 스케줄링 대상이 아닙니다. 스레드 10개인 프로세스는 스레드 1개인 프로세스보다 (같은 우선순위라면) CPU를 더 많이 얻을 수 있습니다.

우선순위 0–31

커널 내부에서 스레드 우선순위는 0부터 31까지의 정수입니다. 숫자가 클수록 높습니다.

  • 0: 제로 페이지 스레드(빈 물리 페이지를 0으로 채우는 시스템 스레드) 전용. 유저 스레드는 0을 가질 수 없습니다. Idle 스레드는 별도 취급으로, 실행할 스레드가 없을 때만 돕니다.
  • 1–15 가변 범위: 일반 스레드. 커널이 상황에 따라 우선순위를 일시적으로 올렸다가(부스트) 서서히 내립니다(감쇠). 부스트는 15를 넘지 않습니다.
  • 16–31 실시간 범위: 커널이 우선순위를 절대 바꾸지 않습니다. 부스트도 감쇠도 없습니다. 많은 커널 시스템 스레드와 MMCSS(멀티미디어) 스레드가 이 범위를 씁니다. 유저 프로세스가 REALTIME_PRIORITY_CLASS를 얻으려면 SeIncreaseBasePriorityPrivilege가 필요하며, 없으면 High로 조정됩니다.
"실시간"은 하드 리얼타임이 아니다

16–31은 단지 "가변 범위보다 항상 우선"이라는 뜻입니다. 인터럽트·DPC는 여전히 어떤 스레드보다 먼저 실행되고(06장), 응답 시간 상한도 보장되지 않습니다. 또 실시간 우선순위의 CPU 바운드 스레드는 같은 코어의 모든 일반 스레드를 굶길 수 있습니다. 기아 방지 부스트는 15까지만 올리므로 이 상황을 구하지 못합니다.

스레드 상태와 전이

KTHREAD.State는 스레드가 지금 무엇을 하고 있는지 나타냅니다. 아래 상태도의 각 상태를 클릭하면 의미와 진입/이탈 조건이 표시됩니다. 괄호 안 숫자는 KTHREAD_STATE 열거 값입니다.

레디 큐와 ReadySummary

각 프로세서의 KPRCB(Processor Control Block)에는 우선순위별 레디 큐 32개 DispatcherReadyListHead[32]와, 어느 큐가 비어 있지 않은지를 나타내는 32비트 비트맵 ReadySummary가 있습니다. 비트 n이 1이면 우선순위 n 큐에 스레드가 있다는 뜻입니다.

다음 스레드를 고를 때 스케줄러는 큐를 하나씩 훑지 않고 ReadySummary에 최상위 비트 검색(x64의 bsr/lzcnt)을 한 번 수행해 가장 높은 우선순위를 찾습니다. 스레드 수와 무관한 O(1) 선택입니다. 

// 개념적 의사 코드: 실제 커널 코드와는 세부가 다름
PKTHREAD KiSelectReadyThread(PKPRCB Prcb, KPRIORITY LowPriority)
{
    ULONG summary = Prcb->ReadySummary >> LowPriority;   // LowPriority 이상만 고려
    if (summary == 0) return NULL;
    ULONG idx;
    _BitScanReverse(&idx, summary);                       // 가장 높은 1 비트
    KPRIORITY pri = idx + LowPriority;
    PLIST_ENTRY e = RemoveHeadList(&Prcb->DispatcherReadyListHead[pri]);
    if (IsListEmpty(&Prcb->DispatcherReadyListHead[pri]))
        Prcb->ReadySummary &= ~(1UL << pri);               // 큐가 비면 비트 클리어
    return CONTAINING_RECORD(e, KTHREAD, WaitListEntry);  // 레디 큐 링크는 대기 링크와 공용
}

퀀텀

퀀텀은 같은 우선순위의 다른 스레드에게 차례를 넘기기 전까지 스레드가 연속으로 실행할 수 있는 시간입니다. 퀀텀은 클록 인터벌(클록 인터럽트 주기) 단위로 정의되며, 내부적으로 클록 틱 1회 = 퀀텀 단위 3으로 셉니다.

클라이언트 (Windows 10/11)

기본 2 클록 틱 = 6 단위. 클록 인터벌이 일반적인 15.625ms라면 약 31ms. 짧은 퀀텀으로 응답성을 우선합니다. 포그라운드 프로세스는 퀀텀이 늘어날 수 있습니다(아래).

서버 (Windows Server)

기본 12 클록 틱 = 36 단위(약 188ms). 컨텍스트 스위치를 줄여 처리량을 우선합니다. 요청을 받은 서버 스레드가 한 번에 일을 끝낼 확률을 높입니다.

  • 클록 인터벌은 하드웨어·전원 정책에 따라 다르며 Sysinternals clockres로 확인합니다. timeBeginPeriod로 타이머 해상도를 높일 수 있지만, Windows 10 2004부터 이 함수는 시스템 전체가 아닌 호출 프로세스의 타이머에만 영향을 주도록 바뀌었습니다.
  • 사이클 기반 계산: Vista 이후 퀀텀 소모는 틱 개수가 아니라 CPU 사이클 카운터로 정밀하게 측정됩니다. 스레드의 퀀텀 목표가 사이클 수(KTHREAD.QuantumTarget)로 정해지고, 인터럽트·DPC 처리에 쓰인 사이클은 스레드에 청구되지 않습니다. 그래서 인터럽트가 많은 시스템에서도 스레드가 퀀텀을 부당하게 잃지 않습니다.
  • 퀀텀 종료 처리: 클록 인터럽트가 실행 중 스레드의 사이클 소모를 확인하고, 목표를 넘었으면 DISPATCH_LEVEL에서 퀀텀 종료 처리를 요청합니다. 이때 같은 우선순위 이상의 Ready 스레드가 없으면 스레드는 새 퀀텀을 받아 계속 실행합니다.

우선순위 부스트와 감쇠

가변 범위(1–15) 스레드는 특정 사건이 일어나면 커널이 현재 우선순위를 일시적으로 올립니다. 목적은 응답성(I/O를 끝낸 스레드가 결과를 빨리 처리)과 공정성(기아 방지, 우선순위 역전 완화)입니다.

부스트 규칙

부스트는 기본 우선순위에 더해집니다: 새 우선순위 = max(현재, 기본 + 증가분), 단 최대 15. 실시간(16–31) 스레드는 부스트하지 않습니다. SetProcessPriorityBoost/SetThreadPriorityBoost로 끌 수 있습니다.

감쇠 규칙

부스트된 스레드는 퀀텀이 끝날 때마다 1씩 내려가 기본 우선순위에서 멈춥니다. 예외적으로 기아 방지 부스트는 그 퀀텀이 끝나면 곧바로 원래 우선순위로 돌아갑니다.

드라이버 개발자에게: PriorityBoost 인자는 정책이다

IoCompleteRequest의 두 번째 인자는 단순한 숫자가 아니라 "이 I/O를 기다리던 스레드를 얼마나 빨리 깨울지"에 대한 결정입니다. 동기 I/O가 매우 빈번한 장치에서 큰 값을 쓰면 해당 스레드들이 다른 작업을 계속 선점해 시스템 응답성을 해칠 수 있고, IO_NO_INCREMENT를 쓰면 대화형 장치의 지연이 커질 수 있습니다. 장치 유형에 맞는 관례 상수를 쓰세요.

컨텍스트 스위치

스케줄러가 새 스레드를 고르면 KiSwapContext(내부적으로 SwapContext)가 실제 전환을 수행합니다. 핵심은 "나가는 스레드의 상태를 그 스레드의 커널 스택에 저장하고, 들어오는 스레드의 커널 스택에서 꺼낸다"입니다. 유저 모드 레지스터는 이미 시스템 콜/인터럽트 진입 시 트랩 프레임에 저장되어 있으므로, 스위치 시점에는 커널 문맥만 다루면 됩니다.

덤프에서 대기 중인 스레드의 콜스택이 늘 비슷한 이유

대기 중인 스레드는 모두 스위치 직전 지점에서 멈춰 있으므로 !thread 콜스택 맨 위가 거의 항상 nt!KiSwapContext → nt!KiSwapThread → nt!KiCommitThreadWait → nt!KeWaitForSingleObject 형태입니다. 분석할 때는 이 아래, 누가 무엇을 기다리는지를 보여 주는 프레임부터 읽으면 됩니다.

대기에서 깨어난 스레드는 DeferredReady를 거쳐 KiDeferredReadyThread에서 배치됩니다. 아래는 핵심 흐름을 단순화한 것입니다(실제로는 SMT 형제 코어, NUMA 노드, 공유 레디 큐, 전원 정책 등이 더 고려됩니다).

공유 레디 큐

최근 Windows 10/11에는 프로세서별 레디 큐 외에 여러 프로세서가 함께 쓰는 공유 레디 큐(KPRCB.SharedReadyQueue)도 있어, 스레드를 특정 프로세서 하나에 묶지 않고 같은 큐를 쓰는 프로세서 중 먼저 비는 쪽이 실행하게 합니다. 어떤 스레드가 어느 큐를 쓰는지는 버전과 하드웨어 구성에 따라 다르며 공개 문서가 없으므로, 분석할 때는 해당 빌드의 심볼로 확인해야 합니다.

CPU Sets와 이종 코어

CPU Sets (Windows 10+)

각 논리 프로세서를 ID가 있는 "CPU Set"으로 노출하고(GetSystemCpuSetInformation), 애플리케이션이 선호 집합을 지정하게 합니다. 하드 선호도와 달리 제안에 가깝고, 하드 선호도와 충돌하면 하드 선호도가 우선합니다.

시스템은 일부 CPU Set을 특정 프로세스용으로 할당(예약)할 수 있습니다. 예약된 CPU는 명시적으로 선택하지 않은 다른 스레드가 덜 쓰게 되어, 게임처럼 지연에 민감한 작업에 코어를 비워 줄 수 있습니다.

이종 코어 (P-core / E-core)

성능 코어와 효율 코어가 섞인 CPU에서 SYSTEM_CPU_SET_INFORMATION의 EfficiencyClass가 코어 종류를 구분합니다(값이 클수록 성능 지향).

Windows 11은 스레드의 QoS(서비스 품질) 수준 — 포그라운드 여부, 창 가시성, SetProcessInformation(ProcessPowerThrottling)으로 요청하는 EcoQoS 등 — 과 하드웨어 피드백(예: Intel Thread Director)을 함께 사용해 스레드를 코어 종류에 배치합니다. 세부 정책은 버전과 전원 설정에 따라 달라집니다.

선호도를 고정하기 전에

성능을 위해 스레드를 특정 코어에 하드 고정하면, 그 코어가 인터럽트·DPC나 더 높은 우선순위 스레드로 바쁠 때 다른 코어가 놀아도 기다리게 됩니다. 이종 코어 시스템에서는 고정된 코어가 E-core일 수도 있습니다. 대부분의 경우 이상 프로세서 힌트나 CPU Sets처럼 스케줄러에게 여지를 남기는 방법이 더 안전합니다.

스케줄러 시뮬레이터

이제 직접 스레드를 넣고 틱을 진행하며 지금까지의 규칙을 관찰해 봅시다. 프리셋으로 시작하거나 스레드를 직접 추가하세요. 표의 행을 클릭하면 그 스레드를 선택해 대기·깨우기·종료·우선순위 변경을 할 수 있습니다.

우선순위 선점형 스케줄러
프리셋:
선택: 없음
시뮬레이터 모델 (실제와 다른 점)
  • 틱 1회 = 퀀텀 3단위. 실제 커널은 사이클 기반으로 퀀텀을 측정합니다.
  • 준비된 스레드 배치: 선호도 안의 유휴 CPU(이상 프로세서 우선) → 이상 프로세서의 실행 스레드보다 높으면 선점 → 아니면 이상 프로세서 레디 큐 꼬리. 자기 큐가 빈 CPU는 다른 CPU의 큐에서 가져옵니다.
  • 대기 완료 시 +2 부스트(최대 15), 퀀텀 종료마다 1씩 감쇠. 실시간(16+)은 부스트 없음.
  • 기아 방지: Ready로 12틱 이상 기다린 가변 우선순위 스레드를 15로 올립니다. 실제로는 약 4초(수백 틱)이며, 1초 주기로 검사합니다.
  • 깨어난 스레드는 새 퀀텀을 받습니다. 실제 퀀텀 재설정 규칙은 더 복잡합니다.

실습: 스케줄링 관찰

실습 5-1 · 우선순위와 대기 상태 읽기

메모장과 CPU를 많이 쓰는 프로그램(예: 무한 루프 테스트 앱)을 실행한 뒤 커널 디버거에서 스레드 상태를 비교합니다. 주소와 값은 환경마다 다릅니다.

lkd> !process 0 2 notepad.exe          $$ 스레드 목록 + 대기 이유
        THREAD ffffc50a`1c4d5080  Cid 1a2c.1a30  Teb: ... WAIT: (WrUserRequest) UserMode Non-Alertable

lkd> !thread ffffc50a`1c4d5080
    ...
    Priority 10  BasePriority 8  PriorityDecrement 2  IoPriority 2  PagePriority 5
    ...                                $$ Priority > BasePriority → 부스트가 남아 있음

lkd> dt nt!_KTHREAD ffffc50a`1c4d5080 State Priority BasePriority WaitReason QuantumTarget
lkd> !ready                             $$ 프로세서별 레디 큐에 있는 스레드 (우선순위별)
lkd> !running -it                       $$ 각 프로세서의 현재/다음(Standby) 스레드와 스택
lkd> !prcb 0                            $$ 0번 프로세서의 KPRCB 요약
lkd> dt nt!_KPRCB ReadySummary DispatcherReadyListHead
  1. 창을 클릭해 메모장을 포그라운드로 만든 뒤 키를 입력하고 곧바로 !thread로 확인하세요. Priority가 BasePriority보다 높게 나타나는지(입력 처리 후 부스트) 관찰합니다.
  2. CPU 바운드 스레드를 우선순위 클래스별로 실행하고 !ready에서 어떤 우선순위 큐에 쌓이는지 확인하세요.
  3. 유저 모드에서는 Process Explorer의 스레드 탭(Dynamic/Base Priority, Context Switch Delta), 또는 Windows Performance Recorder의 CPU Usage (Precise) 그래프로 "Ready Time"과 "새 스레드를 깨운 스레드(ReadyingThread)"를 볼 수 있습니다.
PS> Get-ItemProperty HKLM:\SYSTEM\CurrentControlSet\Control\PriorityControl | Select Win32PrioritySeparation
PS> (Get-Process notepad).PriorityClass = 'AboveNormal'       # 기본 우선순위 8 → 10
PS> (Get-Process notepad).Threads | Select Id, PriorityLevel, BasePriority, CurrentPriority, ThreadState, WaitReason

확인 문제

Normal 클래스 프로세스의 THREAD_PRIORITY_HIGHEST 스레드가 키보드 I/O(IO_KEYBOARD_INCREMENT = 6) 완료로 깨어났습니다. 부스트 직후 현재 우선순위는?

  1. 16
  2. 15
  3. 14
  4. 10 (Normal 클래스는 부스트되지 않음)
기본 우선순위는 8 + 2 = 10, 부스트 결과는 10 + 6 = 16이지만 가변 범위 부스트는 15를 넘을 수 없습니다. 그래서 15이고, 이후 퀀텀이 끝날 때마다 1씩 내려가 10에서 멈춥니다.

우선순위 10 스레드가 퀀텀을 절반 쓴 상태에서 우선순위 12 스레드에게 선점되었습니다. 선점된 스레드는 어떻게 되나요?

  1. 우선순위 10 레디 큐의 꼬리로 가고 새 퀀텀을 받는다
  2. 우선순위 10 레디 큐의 머리로 가고 남은 퀀텀을 유지한다
  3. Standby 상태가 되어 같은 CPU에서 다음에 반드시 실행된다
  4. 우선순위가 1 감쇠된 뒤 큐 꼬리로 간다
선점은 스레드의 잘못이 아니므로 같은 우선순위 큐의 머리에 넣어 먼저 재개되게 하고, 남은 퀀텀을 그대로 씁니다. 퀀텀을 다 쓴 경우에만 꼬리로 갑니다. 감쇠는 퀀텀 종료 시에만 일어납니다.

스케줄러가 다음 스레드를 고를 때 32개 레디 큐를 순서대로 검사하지 않아도 되는 이유는?

  1. 레디 큐가 우선순위별로 정렬된 하나의 연결 리스트이기 때문
  2. 가장 최근에 실행한 스레드를 캐시해 두기 때문
  3. ReadySummary 비트맵에서 최상위 비트를 한 번에 찾으면 비어 있지 않은 최고 우선순위 큐를 알 수 있기 때문
  4. 실시간 범위 큐만 검사하기 때문
비트 n은 "우선순위 n 큐가 비어 있지 않음"을 뜻합니다. bsr 한 번으로 최고 우선순위를 찾고 그 큐의 머리를 꺼내므로 스레드 수와 무관하게 O(1)입니다.

CPU 바운드 실시간(24) 스레드가 단일 코어를 점유하고 있을 때, 같은 코어의 우선순위 8 스레드는?

  1. 기아 방지 부스트로 15가 되어 결국 실행된다
  2. 퀀텀이 끝날 때마다 라운드 로빈으로 번갈아 실행된다
  3. 기아 방지 부스트를 받아도 15 < 24이므로 실시간 스레드가 대기하거나 끝날 때까지 실행되지 못한다
  4. 커널이 실시간 스레드의 우선순위를 낮춰 공평하게 한다
라운드 로빈은 같은 우선순위끼리만 일어납니다. 기아 방지 부스트는 15가 상한이고, 커널은 실시간 범위 스레드의 우선순위를 바꾸지 않습니다. 실시간 우선순위를 남용하면 시스템 스레드와 UI가 굶을 수 있습니다.

같은 프로세스 내 스레드 간 컨텍스트 스위치가 다른 프로세스 스레드로의 전환보다 일반적으로 저렴한 주된 이유는?

  1. 레지스터를 저장할 필요가 없어서
  2. CR3(주소 공간)를 바꾸지 않아 TLB와 캐시의 유효한 변환을 유지하기 때문
  3. 커널 스택을 공유하기 때문
  4. IRQL을 올릴 필요가 없어서
레지스터 저장/복원과 IRQL 처리는 어느 경우든 필요하며, 스레드마다 커널 스택은 별개입니다. 차이는 주소 공간 전환과 그에 따른 TLB 비용입니다.

클라이언트 Windows의 기본 설정에서 포그라운드 앱이 받는 혜택으로 옳은 것은?

  1. 모든 스레드의 기본 우선순위가 +2 된다
  2. 실시간 범위로 승격된다
  3. 스레드 퀀텀이 배경 프로세스의 3배(6 → 18 단위)가 된다
  4. 전용 CPU 코어가 예약된다
기본 Win32PrioritySeparation(짧은·가변, 인덱스 2)는 포그라운드 프로세스에 18단위 퀀텀을 줍니다. 기본 우선순위는 바뀌지 않습니다. 별도로 포그라운드 프로세스의 스레드는 대기 완료 시 추가 부스트를 받을 수 있습니다.

핵심 요약

  • Windows는 우선순위 기반 선점형 스케줄러다. 가장 높은 우선순위의 Ready 스레드가 실행되고, 같은 우선순위끼리는 퀀텀 단위 라운드 로빈.
  • 우선순위 1–15는 가변(부스트·감쇠, 상한 15), 16–31은 실시간(커널이 바꾸지 않음). 클래스 기본값 + 상대값으로 정해진다.
  • 각 KPRCB의 32개 레디 큐와 ReadySummary 비트맵으로 O(1) 선택. 선점된 스레드는 큐 머리, 퀀텀 소진 스레드는 큐 꼬리.
  • 퀀텀은 클라이언트 2틱, 서버 12틱이 기본이며 사이클로 측정한다. 클라이언트 포그라운드 프로세스는 퀀텀이 3배.
  • 부스트: I/O 완료, 이벤트, GUI 입력, 기아 방지(→15), 락 소유자. 컨텍스트 스위치는 커널 스택에 상태를 저장/복원하고, 프로세스가 다를 때만 CR3를 바꾼다.
  • 멀티프로세서 배치는 유휴 프로세서 → 이상 프로세서 선점 → 레디 큐 순이며, 엄격한 전역 우선순위 보장은 없다. CPU Sets와 QoS가 현대 이종 코어 배치를 보완한다.
