Part V · Chapter 15

커널 디버깅과 크래시 분석

블루스크린 한 장, 덤프 파일 하나에서 원인 드라이버와 코드 한 줄까지 증거를 따라가는 법. 시스템 엔지니어와 드라이버 개발자의 장애 분석 실전 챕터입니다.

전문가⏱ 약 120분선수: 06 · 07 · 09 · 11 · 14장

학습 목표

  • 호스트/타깃 KDNET, 로컬 커널 디버깅, LiveKD의 차이를 알고 상황에 맞는 구성을 고를 수 있다.
  • 심볼 경로를 올바르게 설정하고, 심볼 문제를 스스로 진단할 수 있다.
  • 덤프 종류별로 무엇이 담기는지 알고, 운영 환경에 맞는 덤프 설정을 선택할 수 있다.
  • !analyze -v → 콜스택 → 트랩 프레임 → 디스어셈블리 → 구조체 순으로 크래시의 근본 원인을 입증할 수 있다.
  • 행(hang)·풀 손상·성능 저하를 각각 맞는 도구(!running/!locks, Special Pool·Driver Verifier, ETW/WPA)로 분석할 수 있다.

분석의 사고방식

크래시 분석은 추리 게임이 아니라 증거 사슬을 만드는 일입니다. 버그체크 코드와 파라미터는 "무엇이 일어났는가"를, 콜스택은 "누가 그 순간 실행 중이었나"를, 트랩 프레임과 디스어셈블리는 "정확히 어떤 명령이 왜 실패했나"를, 구조체 덤프는 "그 값이 어떻게 그렇게 되었나"를 알려 줍니다. 결론은 이 네 단계가 서로 모순 없이 이어질 때만 내립니다.

1. 현상 고정

버그체크 코드·파라미터, 커널 빌드, 가동 시간, 실패 프로세서. .bugcheck, vertarget.

2. 가설 세우기

!analyze -v는 출발점일 뿐입니다. 자동 결론(MODULE_NAME)을 가설로 다룹니다.

3. 입증·반증

레지스터 값의 출처를 거꾸로 추적하고, 구조체 상태가 가설과 맞는지 확인합니다.

스택 최상단의 드라이버가 범인이라는 보장은 없다

메모리 손상 계열(풀 손상, use-after-free, 스택 덮어쓰기)에서는 손상을 일으킨 코드와 손상을 발견한 코드가 다릅니다. 피해자의 스택만 보고 "ntfs.sys 버그"라고 결론 내리는 것이 가장 흔한 오진입니다. 이럴 때는 Special Pool·Driver Verifier로 범행 현장에서 잡히게 만들어야 합니다(아래 풀 손상 절).

디버깅 구성

커널 디버거는 디버깅 대상 커널(타깃) 안의 디버거 엔진(Kd*)과 다른 머신의 WinDbg(호스트)가 전송 계층을 통해 통신하는 구조입니다. 타깃이 브레이크(중단점, 예외, Ctrl+Break)에 걸리면 모든 프로세서가 멈추고 디버거 엔진이 호스트의 명령을 기다립니다. 그래서 실행 제어(중단점, 스텝)가 필요한 디버깅은 반드시 별도 머신 — 보통 VM을 타깃으로 씁니다. 도식의 요소를 클릭해 보세요.

구성중단점·스텝재부팅·설정대표 용도
호스트–타깃 (KDNET/직렬)가능타깃 debug on + 재부팅드라이버 개발, 재현 가능한 버그 추적, 부팅 문제

드라이버 개발 VM 팁

체크포인트를 "디버거 연결됨, 드라이버 로드 직전" 상태로 만들어 두면 크래시 후 몇 초 만에 복귀할 수 있습니다. 드라이버가 로드되는 순간 멈추려면 sxe ld:mydrv.sys, 출력이 안 보이는 DbgPrintEx는 ed nt!Kd_DEFAULT_Mask 0xFFFFFFFF로 필터를 엽니다.

심볼 경로

심볼(PDB) 없이 콜스택은 nt+0x3f2a10 같은 오프셋의 나열일 뿐입니다. Microsoft는 OS 바이너리의 공개(public) 심볼을 심볼 서버로 배포합니다. 공개 심볼에는 함수·전역 변수 이름과 문서화된 일부 타입이 들어 있고, 지역 변수·소스 줄 정보는 빠져 있습니다. 여러분 드라이버의 개인(private) 심볼은 빌드할 때 나온 PDB를 직접 경로에 추가해야 합니다. 

kd> .symfix C:\symbols
kd> .sympath+ C:\build\mydrv\x64\Release
kd> .sympath
Symbol search path is: srv*C:\symbols*https://msdl.microsoft.com/download/symbols;C:\build\mydrv\x64\Release
kd> .reload /f
kd> lm m nt
start             end                 module name
fffff806`0ee00000 fffff806`0fe46000   nt         (pdb symbols)          C:\symbols\ntkrnlmp.pdb\...\ntkrnlmp.pdb
kd> lm m mydrv
fffff806`1a2b0000 fffff806`1a2c4000   mydrv      (private pdb symbols)  C:\build\mydrv\x64\Release\mydrv.pdb

환경 변수 _NT_SYMBOL_PATH에 같은 문자열을 넣으면 WinDbg, WPA, Process Explorer 등 대부분의 도구가 공유합니다.

lm 표시의미조치
(pdb symbols)공개 PDB 로드됨정상
(private pdb symbols)지역 변수·줄 정보 포함 PDB정상 — dv, kP, 소스 매핑 가능
(deferred)아직 로드 시도 전(지연 로딩)필요할 때 자동 로드. 강제로는 .reload /f 모듈
(export symbols)PDB를 못 찾아 익스포트 테이블로 대체경로·네트워크 확인. !sym noisy 후 .reload /f

PDB는 GUID+Age로 짝이 맞아야 한다

같은 소스라도 다시 빌드하면 PDB GUID가 바뀝니다. 고객 덤프의 드라이버와 지금 빌드한 PDB는 맞지 않으므로 릴리스마다 PDB를 보관(사내 심볼 서버, symstore add)해야 합니다. .reload /i는 불일치를 무시하고 강제로 로드하지만, 줄 번호·오프셋이 틀릴 수 있어 마지막 수단입니다. 메모리의 코드가 디스크 이미지와 다른지(패치, 손상)는 !chkimg -d nt로 확인합니다.

메모리 덤프 종류와 설정

버그체크가 나면 커널은 정상 I/O 스택을 믿을 수 없는 상태에서 덤프를 써야 합니다. 그래서 부팅 시 미리 로드해 둔 덤프 전용 스토리지 스택 (crashdmp.sys가 준비한 dump_stornvme.sys 같은 미니포트 사본, BitLocker면 dumpfve.sys)으로 페이징 파일(또는 전용 덤프 파일)에 직접 기록합니다. 재부팅 후 세션 관리자가 페이징 파일에서 덤프를 발견해 %SystemRoot%\MEMORY.DMP(미니덤프는 %SystemRoot%\Minidump)로 옮기고, 시스템 로그에 BugCheck 이벤트 1001이 남습니다. 도식의 행을 클릭해 각 덤프에 무엇이 들어가는지 비교해 보세요.

레지스트리 설정 (HKLM\SYSTEM\CurrentControlSet\Control\CrashControl)

값의미
CrashDumpEnabled0=없음, 1=전체(또는 활성), 2=커널, 3=Small, 7=자동

라이브 커널 덤프

시스템을 죽이지 않고 덤프를 얻는 방법도 있습니다. 작업 관리자에서 System 프로세스 → 라이브 커널 메모리 덤프 파일 만들기, 또는 livekd -ml -o. 커널 구성요소가 심각하지만 복구 가능한 문제(예: 디스플레이 TDR)를 만나면 스스로 라이브 덤프를 남기며, %SystemRoot%\LiveKernelReports에서 찾을 수 있습니다.

WinDbg 핵심 명령 치트시트

커널 분석에서 자주 쓰는 명령을 범주별로 모았습니다. 명령 이름, 설명, 예시 어디든 검색됩니다(예: irp, 트랩, pool, 스택). .으로 시작하면 디버거 메타 명령, !로 시작하면 확장 DLL 명령입니다.

WinDbg 명령 검색
dx — 디버거 데이터 모델

dx는 디버거 객체(프로세스·스레드·모듈)를 LINQ로 질의합니다. 예: dx -g @$cursession.Processes.Select(p => new { Name = p.Name, Threads = p.Threads.Count() })는 프로세스별 스레드 수를 표로 보여 줍니다. dt가 "이 주소를 이 타입으로 해석"이라면, dx는 "디버거가 이미 아는 객체 그래프를 탐색·집계"입니다. 반복 분석은 JavaScript 확장(.scriptload)으로 자동화합니다.

크래시 덤프 분석 워크스루

가상의 mydrv.sys가 일으킨 DRIVER_IRQL_NOT_LESS_OR_EQUAL(0xD1) 커널 덤프를 처음부터 끝까지 따라가 봅니다. 출력은 실제 형식을 따른 가상의 값입니다. 각 단계에서 증거 보드가 어떻게 채워지는지 보세요.

주소만 보고 판단하는 감각

0x0000000000000028처럼 작은 값은 NULL+오프셋, 0xffffxxxx`xxxxxxxx는 커널 주소(해제됐거나 페이징 가능한 메모리일 수 있음 → !pte, !pool), 상위 비트가 유효하지 않은 값(예: 0x4141414141414141)은 비정규(non-canonical) 주소로 보통 #GP를 일으키며 데이터 덮어쓰기를 의심합니다. 해제된 풀은 특정 패턴으로 채워지지 않으므로 패턴만으로 단정하지 말고 Verifier로 확인하세요.

흔한 커널 버그 패턴

높은 IRQL의 잘못된 접근

DPC·스핀락 보유 중 페이징 가능 코드/데이터 접근, NULL 역참조. → 0xD1, 0x0A. 탐지: Verifier IRQL 검사(0x2).

Use-after-free

해제 후 남은 참조, 참조 카운트 누락. → 0x50, 0xD5, 무작위 손상. 탐지: Special Pool.

풀 오버런

길이 계산 실수, 유저 입력 길이 미검증. → 0x19, 0x13A, 0x139. 탐지: Special Pool.

IRP 수명 오류

두 번 완료, 완료 후 접근, 취소 경쟁. → 0x44, 0x50. 탐지: Verifier I/O 검증(0x10).

락 오류와 교착

락 순서 역전, 해제 누락, 유저 서비스 응답을 커널에서 무한 대기. → 행. 탐지: Verifier 교착 탐지(0x20), !locks.

스택 고갈·과도한 DPC

재귀, 큰 지역 배열, 깊은 필터 스택 → 0x7F(이중 폴트). 긴 DPC 루프 → 0x133. 탐지: knf, WPA DPC/ISR.

시스템 행(hang) 분석

행은 크래시보다 어렵습니다. 무엇이 "멈춘" 것인지부터 구분해야 합니다. 하드 행은 한 CPU 이상이 높은 IRQL에서 돌거나 인터럽트를 막고 있어 마우스조차 안 움직이는 상태, 소프트 행은 시스템은 살아 있지만 스레드들이 서로를 기다리며(교착) 특정 작업이 끝나지 않는 상태입니다.

멈춘 시스템에서 덤프 얻기

  • 키보드: CrashOnCtrlScroll=1(USB 키보드는 kbdhid\Parameters, PS/2는 i8042prt\Parameters) 후 오른쪽 Ctrl+Scroll Lock 두 번 → 0xE2 MANUALLY_INITIATED_CRASH. 키보드 ISR이 돌 수 있어야 하므로 하드 행에는 안 될 수 있습니다.
  • NMI: 서버 BMC(iLO/iDRAC)의 NMI 버튼, Hyper-V는 Debug-VM -Name vm1 -InjectNonMaskableInterrupt. NMI는 마스킹되지 않으므로 하드 행에서도 덤프를 얻을 수 있습니다(0x80).
  • 디버거 연결되어 있다면 Ctrl+Break 후 .dump /f, 또는 .crash.

핵심 명령

kd> !analyze -hang              $$ 행 관점의 자동 분석
kd> !running -it                $$ 각 CPU에서 실행 중인 스레드 + 스택 (-i: 유휴 CPU 포함)
kd> !ready                      $$ CPU별 레디 큐 — 오래 기다리는 스레드는 CPU 굶주림의 증거
kd> !locks                      $$ 경합 중인 ERESOURCE: 소유자와 대기자
kd> !qlocks                     $$ 큐드 스핀락 상태
kd> !stacks 2 mydrv             $$ 스택에 mydrv가 있는 모든 스레드
kd> !thread ffffc50b`41a2e080   $$ 대기 이유(WAIT: (WrResource) ...), 대기 객체, 대기 시간(Ticks)

소프트 행 분석의 핵심은 대기 체인입니다. 멈춘 스레드에서 출발해 "무엇을 기다리나 → 그것은 누가 갖고 있나 → 그 소유자는 무엇을 기다리나"를 반복하면, 체인은 결국 ① 자기 자신으로 돌아오거나(교착), ② 소유자 없는 이벤트·IRP 완료를 기다리거나(완료해 줄 쪽을 코드로 추론), ③ 실행 중인 스레드(CPU 독점)에서 끝납니다. 뮤턴트(KMUTEX)와 ERESOURCE는 소유자를 기록하지만 이벤트는 소유자가 없다는 점이 중요합니다.

풀 손상과 Special Pool · Driver Verifier

풀 오버런은 시한폭탄입니다. 넘친 바이트는 이웃 블록을 덮어쓰지만 그 순간에는 아무 일도 없고, 한참 뒤 이웃 블록의 주인이 해제하거나 할당자가 메타데이터를 검사할 때 터집니다. Windows 10 19H1부터 커널 풀이 세그먼트 힙 기반으로 바뀌어 손상 버그체크가 0x19 외에 0x13A, 0x139 등으로 다양해졌고 !pool 출력 형식도 달라졌습니다. 

C:\> verifier /standard /driver mydrv.sys        <- 표준 검사 세트
C:\> verifier /flags 0x1 /driver mydrv.sys       <- Special Pool만
C:\> verifier /querysettings                     <- 현재 설정 (재부팅 후 적용)
C:\> verifier /query                             <- 실행 중 통계
C:\> verifier /reset                             <- 해제
플래그검사잡아내는 버그
0x1Special Pool오버런, use-after-free
0x2Force IRQL checkingDISPATCH 이상에서 페이징 가능 메모리 접근 (페이징 가능 페이지를 강제로 내보냄)
0x8Pool tracking언로드 시 미해제 풀(0xC4, P1=0x62)
0x10I/O verificationIRP 이중 완료, 잘못된 상태 반환
0x20Deadlock detection락 획득 순서 위반 — 실제 교착 전에 경고
0x20000DDI compliance checkingWDK 규칙 위반(DDI 사용법)

Verifier는 반드시 테스트 환경에서 대상 드라이버를 지정해 씁니다. 모든 드라이버에 켜면 부팅조차 느려지고, 서드파티 드라이버의 위반으로 부팅이 안 될 수 있습니다(안전 모드에서 verifier /reset).

kd> !pool ffffc50b`3e2a1010
Pool page ffffc50b3e2a1010 region is Nonpaged pool
*ffffc50b3e2a1000 size:   70 previous size:    0  (Allocated) *MLnk
		Owning component : Unknown (update pooltag.txt)
kd> !poolused 2                 $$ 비페이징 풀 사용량 순 태그 목록 (누수 추적)
kd> !poolfind MLnk              $$ 특정 태그의 모든 할당 찾기
kd> !verifier 0x80 ffffc50b`3e2a1010   $$ (Verifier 사용 시) 할당/해제 스택 기록

태그 주인 찾기: 디버거 폴더의 triage\pooltag.txt에 없으면 findstr /m /l MLnk C:\Windows\System32\drivers\*.sys로 바이너리를 뒤집니다. 태그 단위로 Special Pool을 걸 수도 있습니다(GFlags 또는 메모리 관리자 레지스트리 PoolTag).

ETW/WPR/WPA와 Time Travel Debugging

크래시도 행도 아닌 "느리다"는 디버거로 잡기 어렵습니다. 이때는 ETW(Event Tracing for Windows)로 시스템 전체를 기록합니다. 커널 자체가 컨텍스트 스위치·DPC/ISR·디스크 I/O·페이지 폴트·스택 샘플 이벤트를 내보내는 거대한 공급자이고, 오버헤드가 낮아 운영 환경에서도 쓸 수 있습니다. 

C:\> wpr -profiles                                   # 내장 프로필 목록
C:\> wpr -start GeneralProfile -start CPU -filemode  # 기록 시작
     ... 문제 재현 ...
C:\> wpr -stop C:\traces\slow.etl "IOCTL 지연 재현"
C:\> wpr -addboot GeneralProfile                     # 부팅 추적: 재부팅 후
C:\> wpr -stopboot C:\traces\boot.etl

WPA에서 먼저 볼 그래프

  • CPU Usage (Sampled): CPU 시간이 어느 스택에서 쓰였나
  • CPU Usage (Precise): 컨텍스트 스위치 — 누가 기다렸고(Waits), 누가 깨웠나(ReadyingThread). 대기 분석의 핵심
  • DPC/ISR Duration: 긴 DPC를 일으키는 드라이버 (0x133 전조, 오디오 끊김)
  • Disk / File I/O, Pool 사용량

드라이버의 자체 로그

WPP 추적과 KMDF의 내장 기록기(IFR)는 링 버퍼를 메모리에 남겨 덤프 안에서도 읽을 수 있습니다.

!wdfkd.wdflogdump mydrv (KMDF 로그)
!rcdrkd.rcdrlogdump mydrv (WPP 기록기)

크래시 직전 드라이버가 무엇을 하고 있었는지 알려 주는 가장 값싼 증거입니다.

Time Travel Debugging (TTD)

TTD는 프로세스 실행을 명령 단위로 기록해 두고, 재생하면서 앞뒤로 자유롭게 오갈 수 있게 합니다. "이 값을 누가 마지막으로 썼나?"를 쓰기 중단점 + 역방향 실행 한 번으로 답할 수 있습니다. 단, 유저 모드 프로세스 전용이며 커널 코드는 기록하지 않습니다. 드라이버와 통신하는 서비스·앱 쪽 문제(잘못된 IOCTL 버퍼, 핸들 수명)를 좁힐 때 유용합니다. 

0:000> dx @$cursession.TTD.Calls("kernelbase!DeviceIoControl").Count()
0:000> ba w8 000001d2`3f2a10a8         $$ 이 주소에 쓰기 중단점
0:000> g-                              $$ 거꾸로 실행 → 마지막으로 쓴 지점에서 정지
0:000> !tt 50                          $$ 기록의 50% 지점으로 이동
0:000> p-                              $$ 한 단계 뒤로

기록은 WinDbg의 Launch/Attach → Record with Time Travel Debugging 또는 명령줄 TTD.exe로 합니다. 기록 오버헤드가 커서(수 배~수십 배 느려짐) 짧은 재현 구간에 씁니다.

테스트 VM에 Sysinternals NotMyFault를 받고 덤프 설정을 커널 메모리 덤프로 둡니다. 스냅숏을 찍은 뒤 진행하세요.

  1. NotMyFault에서 High IRQL fault (Kernel-mode)를 실행합니다. 재부팅 후 MEMORY.DMP를 호스트로 복사해 위 워크스루 순서(.bugcheck → !analyze -v → kv → .trap → ub)대로 myfault.sys의 실패 명령까지 추적하세요.
  2. Buffer overflow를 여러 번 실행해 크래시가 언제, 어떤 스택으로 나는지 기록합니다. 매번 다른지 관찰하세요.
  3. verifier /flags 0x1 /driver myfault.sys 후 재부팅하고 2번을 반복합니다. 버그체크 코드와 스택 최상단이 어떻게 바뀌었는지 비교하세요.
  4. KDNET로 호스트를 연결하고 bp myfault!* 대신 sxe ld:myfault.sys로 로드 시점에 멈춘 뒤 !drvobj myfault 2로 디스패치 루틴을 확인하세요.
  5. 도전: NotMyFault의 Hang 계열 옵션을 실행한 뒤 Hyper-V NMI로 덤프를 얻어 !running -it, !locks로 원인 스레드를 찾으세요.

확인 문제

0xD1 덤프에서 Arg1=0x0000000000000028, Arg2=2, Arg3=0입니다. 가장 타당한 첫 해석은?

  1. 물리 주소 0x28의 하드웨어 레지스터를 IRQL 2에서 썼다
  2. NULL 포인터의 오프셋 0x28 필드를 DISPATCH_LEVEL에서 읽었다
  3. IRQL을 0x28로 올리려다 실패했다
  4. 풀 태그 0x28 블록이 손상되었다
Arg1은 참조한 가상 주소, Arg2는 당시 IRQL(2=DISPATCH), Arg3은 접근 종류(0=읽기)입니다. 0x28 같은 작은 주소는 p->Field에서 p가 NULL인 전형적 패턴이며, .trap의 [reg+28h]로 확인합니다.

.trap 결과에서 rbx, rsi, r12~r15가 모두 0입니다. 올바른 해석은?

  1. 함수가 그 레지스터를 0으로 초기화했다
  2. 덤프가 손상되었다
  3. x64 트랩 프레임은 휘발성 레지스터만 저장하므로 비휘발성 레지스터 값은 신뢰할 수 없다
  4. CPU가 예외 시 레지스터를 지운다
KTRAP_FRAME은 rax, rcx, rdx, r8–r11 등 휘발성 레지스터와 rip/rsp/rflags를 저장합니다. 비휘발성 값은 호출 체인의 저장 위치에서 복원해야 하며, .frame /r이나 스택의 push 위치를 봐야 합니다.

고객 서버에서 BAD_POOL_HEADER(0x19) 덤프 다섯 개가 모두 다른 콜스택(ntfs, tcpip, 백신 필터…)을 보입니다. 가장 효과적인 다음 단계는?

  1. 가장 자주 보인 ntfs.sys를 업데이트한다
  2. 미니덤프로 바꿔 덤프를 더 많이 모은다
  3. 의심 드라이버들에 Special Pool(Verifier)을 걸어 손상 순간에 잡히게 만든다
  4. !analyze -v의 MODULE_NAME을 그대로 보고한다
스택이 매번 다르다는 것은 "발견자"가 매번 다르다는 뜻입니다. 범인은 이미 떠난 뒤입니다. Special Pool은 오버런·해제 후 접근을 그 명령에서 즉시 버그체크로 바꿔 범인의 스택을 보여 줍니다. 미니덤프는 풀 정보가 없어 오히려 불리합니다.

RAM 512GB인 Hyper-V 호스트입니다. 커널과 유저 서비스가 얽힌 교착을 분석할 수 있으면서 덤프 크기를 줄이려면?

  1. Small memory dump
  2. Kernel memory dump
  3. Active memory dump (CrashDumpEnabled=1, FilterPages=1)
  4. Complete memory dump
활성 메모리 덤프는 커널과 활성 유저 메모리를 담으면서 게스트 VM 메모리 등 쓸모없는 페이지를 제외합니다. 커널 덤프는 유저 모드 메모리가 없어 서비스 쪽 상태를 볼 수 없고, 전체 덤프는 너무 큽니다.

대기 체인을 따라가다 스레드가 SynchronizationEvent를 기다리는 것을 발견했습니다. 다음으로 할 일은?

  1. !locks로 이벤트의 소유 스레드를 찾는다
  2. 이벤트에는 소유자가 없으므로, 누가 이 이벤트를 Set해야 하는지 코드와 다른 스레드 스택(!stacks)으로 추론한다
  3. 이벤트 대기는 정상이므로 분석을 끝낸다
  4. .trap으로 이벤트의 트랩 프레임을 본다
뮤턴트와 ERESOURCE는 소유자를 기록하지만 이벤트는 신호 상태만 가집니다. 이벤트를 Set할 책임이 있는 코드 경로(완료 루틴, 워커, 유저 서비스 응답)를 찾아 그 쪽이 왜 진행하지 못하는지를 이어서 추적해야 합니다.

Time Travel Debugging에 대한 설명으로 옳은 것은?

  1. 커널 드라이버의 실행을 기록해 크래시 직전으로 되돌릴 수 있다
  2. 운영 서버에서 상시 켜 두어도 오버헤드가 거의 없다
  3. 유저 모드 프로세스를 기록하며, 쓰기 중단점과 역방향 실행으로 "누가 이 값을 썼나"를 찾을 수 있다
  4. ETW 세션의 다른 이름이다
TTD는 유저 모드 전용이고 기록 오버헤드가 큽니다. 커널 쪽 시간 흐름은 ETW/WPA나 드라이버 자체 로그(WPP/IFR)로 재구성합니다.

핵심 요약

  • 실행 제어가 필요하면 호스트–타깃(KDNET), 조회만 필요하면 로컬 KD·LiveKD, 사후 분석은 덤프. 심볼은 .symfix + 개인 PDB 경로, 문제 시 !sym noisy.
  • 덤프: Small(통계용) < Kernel/Automatic(드라이버 분석 표준) < Active(유저+커널, 서버) < Complete. 페이징 파일 크기가 덤프 생성의 전제 조건이다.
  • 분석 순서: .bugcheck → !analyze -v(가설) → kv → .trap/.cxr → ub·dt로 값의 출처 입증 → 버전과 함께 결론.
  • 행은 대기 체인(!thread·!locks·!irp)을 따라가고, CPU 독점은 !running -it·!ready로 본다. 이벤트는 소유자가 없다.
  • 풀 손상은 발견자 ≠ 범인. Special Pool·Driver Verifier로 범행 현장을 잡는다. 성능은 ETW/WPA, 유저 측 재현은 TTD.
