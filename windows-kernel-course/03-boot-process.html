Part I · Chapter 03

부팅 과정

전원 버튼에서 바탕화면까지. 각 단계가 무엇을 로드하고, 누가 누구를 검증하며, 어디서 실패할 수 있는지 추적합니다.

핵심⏱ 약 70분선수: 01장, 02장

학습 목표

  • UEFI 펌웨어 → bootmgfw.efi → winload.efi → ntoskrnl.exe → smss.exe로 이어지는 제어 이양을 순서대로 설명할 수 있다.
  • LOADER_PARAMETER_BLOCK이 부트 로더와 커널 사이에서 무엇을 전달하는지 말할 수 있다.
  • 커널 초기화 Phase 0과 Phase 1의 차이(인터럽트, 실행 스레드, 초기화되는 구성요소)를 구분할 수 있다.
  • Secure Boot(검증)와 Measured Boot(측정)의 차이, ELAM의 위치와 한계를 설명할 수 있다.
  • 드라이버 Start 타입별 로드 주체·시점을 알고, 부트 로깅·안전 모드·부트 디버깅으로 부팅 문제를 좁혀 갈 수 있다.

전체 흐름 한눈에 보기

Windows 부팅은 "작은 프로그램이 더 큰 프로그램을 메모리에 올리고 제어를 넘기는" 릴레이입니다. 각 주자는 다음 주자를 로드하고, 대부분 서명을 검증하며, 필요한 정보를 전달한 뒤 사라지거나 다른 역할로 바뀝니다. 아래 스테퍼로 전 구간을 먼저 훑고, 이어지는 절에서 각 구간을 확대합니다.

BIOS(레거시) 부팅은?

레거시 BIOS/MBR 경로에서는 MBR → 활성 파티션 VBR → bootmgr → winload.exe 순서로 진행합니다. Secure Boot는 UEFI 기능이므로 레거시 경로에서는 쓸 수 없고, Windows 11은 UEFI와 Secure Boot 지원 하드웨어를 요구합니다. 이 장은 UEFI x64를 기준으로 합니다.

UEFI 펌웨어와 Boot Manager

UEFI 펌웨어는 FAT 파일 시스템으로 포맷된 ESP를 읽을 수 있고, PE 형식의 UEFI 애플리케이션을 직접 실행합니다. 어떤 애플리케이션을 실행할지는 NVRAM 변수(Boot####, BootOrder)가 정합니다. 항목이 없으면 이동식 매체용 기본 경로 \EFI\Boot\bootx64.efi를 시도합니다. 펌웨어는 두 종류의 서비스를 제공합니다.

Boot Services

메모리 할당, 디스크/콘솔 프로토콜, 이미지 로드 등. 부트 로더만 쓸 수 있으며 OS 로더가 ExitBootServices()를 호출하면 영구히 사라집니다. 이 호출 이후 메모리 맵의 소유권은 OS로 넘어갑니다.

Runtime Services

NVRAM 변수 읽기/쓰기(GetVariable/SetVariable), 시각, 재설정 등. OS 실행 중에도 남아 있어 커널(HAL)이 호출합니다. Windows에서는 GetFirmwareEnvironmentVariable 같은 API가 이를 사용합니다.

BCD — 부트 구성 데이터

bootmgfw.efi는 같은 디렉터리의 BCD 파일을 읽습니다. BCD는 레지스트리 하이브 형식의 파일로, OS가 실행 중일 때는 HKLM\BCD00000000으로 마운트되어 보입니다(직접 편집하지 말고 bcdedit나 WMI BCD 공급자를 쓰는 것이 원칙입니다). BCD는 객체(GUID로 식별: {bootmgr}, {current}, {default} 등의 별칭이 있음)와 그 안의 요소(설정값)로 구성됩니다.

winload.efi와 LOADER_PARAMETER_BLOCK

winload는 아직 펌웨어 서비스를 쓸 수 있는 마지막 주자입니다. 커널이 스스로 디스크를 읽으려면 디스크·파일 시스템 드라이버가 필요한데, 그 드라이버는 커널이 있어야 동작합니다. winload는 이 순환을 끊기 위해 부팅에 필요한 최소 집합을 미리 메모리에 올려 둡니다.

  1. BCD의 OS 로더 옵션을 해석하고 부팅 볼륨에 접근합니다(BitLocker라면 TPM 등으로 볼륨 키를 얻습니다).
  2. \Windows\System32\config\SYSTEM 하이브를 읽어 Services 아래 Start=0(Boot) 드라이버 목록과 그룹 순서를 결정합니다.
  3. ntoskrnl.exe, hal.dll, 디버거 전송 DLL, 이들의 임포트 DLL(예: ci.dll)을 로드하고 서명을 검증합니다.
  4. ELAM 드라이버와 부트 드라이버(스토리지 컨트롤러, 볼륨, 파일 시스템, 일부 보안 제품 드라이버 등)를 로드합니다. 로드만 하고 실행(DriverEntry)은 하지 않습니다.
  5. NLS 테이블 등 커널 초기화에 필요한 데이터를 로드하고, 하이퍼바이저가 설정되어 있으면 하이퍼바이저 로더를 실행합니다.
  6. 커널 가상 주소 공간용 초기 페이지 테이블을 만들고, 모든 결과를 LOADER_PARAMETER_BLOCK에 담습니다.
  7. ExitBootServices 후 nt!KiSystemStartup으로 점프하면서 로더 블록 주소를 인자로 넘깁니다.

커널 초기화: Phase 0과 Phase 1

KiSystemStartup은 BSP에서 프로세서별 구조(KPCR, KPRCB, GDT, IDT, TSS)를 설정하고 KiInitializeKernel을 거쳐 ExpInitializeExecutive를 Phase 0으로 호출합니다. Phase 0의 핵심 제약은 두 가지입니다. 인터럽트가 비활성이고, BSP 하나만 동작합니다. 그래서 이 단계는 이후 단계가 의존할 최소 기반만 만듭니다.

Boot 드라이버를 만들 때의 함정

Boot 드라이버의 DriverEntry는 파일 시스템이 완전히 준비되기 전에 실행될 수 있습니다. 이 시점에 \SystemRoot\... 경로의 파일을 열거나, 아직 시작되지 않은 다른 드라이버·서비스에 의존하면 실패합니다. 필요한 작업은 IoRegisterBootDriverReinitialization(모든 부트 드라이버 초기화 후 재호출)이나 IoRegisterDriverReinitialization으로 미루는 것이 정석입니다. 또한 Boot 드라이버가 크래시하면 사용자는 안전 모드로도 들어가기 어려우니, 꼭 필요한 경우에만 Start=0을 쓰세요.

Secure Boot 신뢰 체인

Secure Boot의 아이디어는 단순합니다. 각 단계가 다음 단계를 실행하기 전에 서명을 검증하고, 첫 번째 검증자는 변조가 어려운 펌웨어에 둡니다. 펌웨어의 신뢰 루트는 NVRAM에 저장된 인증된 변수들입니다.

smss와 사용자 모드 초기화

smss.exe(Session Manager)는 Win32 서브시스템이 아직 없으므로 네이티브 애플리케이션(ntdll만 사용, 서브시스템 타입 Native)입니다. smss가 하는 대표 작업은 다음과 같습니다(설정은 대부분 HKLM\SYSTEM\CurrentControlSet\Control\Session Manager 아래).

BootExecute

부팅 시 실행할 네이티브 프로그램. 기본값은 autocheck autochk *로, 더티 플래그가 선 볼륨의 파일 시스템 검사를 수행합니다.

파일 교체 · KnownDLLs

PendingFileRenameOperations의 지연된 파일 이름 변경/삭제를 처리하고, \KnownDlls 섹션 객체를 만들어 시스템 DLL을 공유 매핑합니다.

페이지 파일 · 하이브

Memory Management\PagingFiles에 따라 페이지 파일을 만들고, 나머지 레지스트리 하이브(SOFTWARE, SAM, SECURITY, DEFAULT 등) 로드를 커널에 요청합니다.

준비가 끝나면 smss는 세션을 만듭니다. 마스터 smss는 세션마다 자기 사본을 만들고, 사본이 해당 세션의 프로세스를 띄운 뒤 종료합니다. 그래서 csrss·wininit·winlogon의 부모 PID는 "존재하지 않는 프로세스"를 가리킵니다.

"부팅 완료"는 언제인가

사용자가 바탕화면을 본 뒤에도 SCM은 지연 시작(Automatic Delayed Start) 서비스를 계속 올리고, PnP는 장치를 계속 열거합니다. 부팅 성능 분석에서는 "커널 초기화 끝", "로그온 UI 표시", "셸 준비", "부팅 후 유휴 상태 도달"을 구분해야 합니다. WPR/WPA의 부트 추적이 이 구간들을 나눠 보여줍니다.

빠른 시작(Fast Startup)과 재현되지 않는 버그

기본 설정의 "시스템 종료"는 사용자 세션을 닫은 뒤 커널 세션을 최대 절전 파일로 저장합니다. 다음 전원 투입 시 bootmgr는 winload 대신 winresume.efi로 그 상태를 복원하므로 드라이버 초기화가 다시 일어나지 않습니다. 드라이버의 부팅 경로를 시험할 때는 "다시 시작"을 쓰거나 빠른 시작을 끄세요.

C:\> bcdedit /deletevalue {current} bootlog

"Did not load"가 곧 오류를 뜻하지는 않습니다. 해당 하드웨어가 없거나 조건부로 로드되지 않는 드라이버도 기록됩니다. 비교 대상이 있어야 의미가 생깁니다.

안전 모드는 HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot\Minimal(또는 Network) 아래에 이름이나 그룹이 등록된 드라이버·서비스만 시작합니다. 서드파티 Auto 드라이버가 원인이라면 안전 모드에서는 대개 부팅되고, 그 상태에서 드라이버를 비활성화(Start=4)할 수 있습니다.

C:\> bcdedit /set {current} safeboot minimal
C:\> bcdedit /set {current} safeboot network
C:\> bcdedit /set {current} safebootalternateshell yes
C:\> bcdedit /deletevalue {current} safeboot
C:\> bcdedit /deletevalue {current} safebootalternateshell

세 번째 명령은 탐색기 대신 명령 프롬프트를 셸로 쓰는 "안전 모드(명령 프롬프트 사용)"입니다. safeboot 값을 지우는 것을 잊으면 계속 안전 모드로 부팅됩니다. Boot 드라이버가 원인인 경우 안전 모드도 실패할 수 있습니다.

커널 디버거는 부팅 초기부터 붙일 수 있습니다. 대상 VM에서 디버그 설정을 하고, 호스트 WinDbg에서 초기 브레이크를 요청하면 커널이 디버거와 연결되는 즉시 멈춥니다(WinDbg classic: Debug → Kernel Connection → Cycle Initial Break, Ctrl+Alt+K).

C:\> bcdedit /debug on
C:\> bcdedit /dbgsettings net hostip:192.168.50.1 port:50000
Key=...   (호스트 WinDbg에 입력할 키)
C:\> bcdedit /bootdebug {bootmgr} on      REM bootmgr 단계부터 디버깅이 필요할 때만
kd> sxe ld:MyStor.sys          $$ 특정 드라이버 이미지 로드 시 멈춤
kd> g
kd> bu MyStor!DriverEntry       $$ 심볼 로드 전이어도 지연 브레이크 설정
kd> g
kd> k                           $$ IoInitSystem 아래의 호출 경로 확인
kd> !analyze -v                 $$ 부팅 중 버그체크라면 먼저 실행

Secure Boot가 켜져 있으면 디버그 설정이 정책으로 막힐 수 있으므로 실습 VM에서는 Secure Boot를 끕니다(Hyper-V 2세대 VM의 경우 VM 설정에서 해제). KDNET 구성 상세는 15장·17장을 참고하세요.

  • Windows RE(복구 환경): 시동 복구, 시스템 복원, 명령 프롬프트, "시작 설정"(안전 모드·부트 로깅·드라이버 서명 강제 해제 등 일회성 옵션) 제공.
  • bcdboot C:\Windows: ESP에 부팅 파일과 BCD를 다시 만듭니다. BCD 손상 시의 정석 복구.
  • 오프라인 레지스트리 편집: WinRE에서 reg load로 SYSTEM 하이브를 마운트해 문제 드라이버의 Start를 4로 바꿀 수 있습니다. 마운트한 하이브에는 CurrentControlSet이 없으므로 Select\Current 값이 가리키는 ControlSet00x를 수정해야 합니다.
  • Procmon 부트 로깅: Process Monitor의 Enable Boot Logging으로 부팅 초기의 파일·레지스트리 접근을 기록할 수 있습니다(드라이버 서비스로 동작).

실습

실습 3-1 · 부팅 체인 파일 직접 보기

관리자 권한으로 mountvol S: /s를 실행해 ESP를 마운트하고 S:\EFI\Microsoft\Boot의 bootmgfw.efi와 BCD를 확인하세요. bcdedit /enum all로 모든 BCD 객체를 나열하고, {bootmgr}의 default가 {current}와 일치하는지 봅니다. 확인 후 mountvol S: /d로 해제합니다. 파일을 수정하지 마세요.

실습 3-2 · Start 타입별 드라이버 분포

PowerShell에서 Start 값별 커널 드라이버 수를 세어 보고, Boot(0) 드라이버가 어떤 그룹에 속하는지 확인하세요. 시스템 정보 → 보안 부팅 상태, 그리고 Confirm-SecureBootUEFI로 Secure Boot 상태를 확인합니다.

PS C:\> Get-CimInstance Win32_SystemDriver | Group-Object StartMode | Select Count, Name
PS C:\> Get-ChildItem HKLM:\SYSTEM\CurrentControlSet\Services |
         Get-ItemProperty | Where-Object { $_.Start -eq 0 } |
         Select-Object PSChildName, Group, Tag | Sort-Object Group
PS C:\> Confirm-SecureBootUEFI
PS C:\> Get-ItemProperty HKLM:\SYSTEM\CurrentControlSet\Control | Select SystemStartOptions
실습 3-3 · 부팅 초기의 커널 관찰 (커널 디버깅 VM)

15장/17장의 방식으로 KDNET을 구성한 VM에서 초기 브레이크를 켜고 재부팅하세요. 멈추면 아래 명령으로 로더 블록과 초기 상태를 확인하고, g로 진행한 뒤 부팅이 끝난 상태와 비교합니다.

kd> dt nt!_LOADER_PARAMETER_BLOCK poi(nt!KeLoaderBlock) LoadOrderListHead BootDriverListHead LoadOptions NtBootPathName
kd> dx -r1 Debugger.Utility.Collections.FromListEntry(((nt!_LOADER_PARAMETER_BLOCK*)*(void**)&nt!KeLoaderBlock)->LoadOrderListHead, "nt!_KLDR_DATA_TABLE_ENTRY", "InLoadOrderLinks").Select(m => m.BaseDllName)
kd> dt nt!_BOOT_DRIVER_LIST_ENTRY
kd> !process 0 0                $$ 이 시점엔 프로세스가 거의 없음
kd> g
$$ ---- 부팅 완료 후 Ctrl+Break ----
kd> dq nt!KeLoaderBlock L1      $$ 이제 0
kd> !process 0 0 smss.exe
kd> !process 0 0 csrss.exe      $$ ParentCid가 가리키는 프로세스가 없는지 확인
kd> lm o                         $$ 로드 순서: nt, hal, kd 전송 DLL, 부트 드라이버…

필드 이름은 공개 심볼 기준이며 일부는 빌드에 따라 다를 수 있습니다. dt nt!_LOADER_PARAMETER_BLOCK을 먼저 실행해 실제 필드를 확인하세요.

  1. 실습 3-2의 Boot(0) 드라이버 목록과 실습 3-3의 LoadOrderListHead 순서를 대조하세요.
  2. bootlog를 켜고 부팅한 뒤 ntbtlog.txt의 "Did not load" 항목이 왜 로드되지 않았는지 설명해 보세요(장치 없음, Disabled, 조건부 등).
  3. Process Explorer에서 csrss, wininit, winlogon의 부모 프로세스 열을 확인하고, 그림 3-5와 연결해 설명하세요.

확인 문제

Boot(Start=0) 드라이버에 대한 설명으로 옳은 것은?

  1. winload가 로드하고 DriverEntry까지 호출한다
  2. winload가 메모리에 올려 두고, 커널 Phase 1의 I/O 관리자가 DriverEntry를 호출한다
  3. SCM이 로그온 직전에 로드한다
  4. Phase 0에서 인터럽트가 꺼진 상태로 초기화된다
winload는 펌웨어 서비스로 디스크를 읽을 수 있는 마지막 주자라서 부팅 필수 드라이버를 미리 적재만 합니다. 초기화(DriverEntry)는 커널이 준비된 Phase 1의 IoInitSystem에서 합니다. SCM은 Start=2, Phase 0은 드라이버를 초기화하지 않습니다.

부팅이 끝난 시스템의 로컬 커널 디버깅에서 dt nt!_LOADER_PARAMETER_BLOCK poi(nt!KeLoaderBlock)이 유효한 값을 보여주지 않는 이유는?

  1. 로더 블록은 유저 모드 메모리에 있다
  2. 로컬 커널 디버깅은 전역 변수를 읽을 수 없다
  3. Phase 1 마무리 단계에서 로더 블록 메모리가 회수되고 KeLoaderBlock이 NULL로 지워진다
  4. HVCI가 로더 블록을 숨긴다
로더 블록은 winload와 커널 사이의 일회성 전달 수단입니다. 커널이 내용을 자기 자료구조로 옮긴 뒤 메모리를 회수하므로, 관찰하려면 부팅 초기 브레이크가 필요합니다.

Secure Boot와 Measured Boot의 차이로 가장 정확한 것은?

  1. 둘 다 서명이 맞지 않는 이미지의 실행을 막는다
  2. Secure Boot는 검증에 실패한 이미지의 실행을 막고, Measured Boot는 막지 않고 실행된 것을 TPM PCR과 로그에 기록한다
  3. Measured Boot는 TPM 없이도 동작하고 Secure Boot는 TPM이 필요하다
  4. Measured Boot는 커널 이후 단계만 측정한다
Secure Boot는 강제(enforcement), Measured Boot는 기록(attestation)입니다. Secure Boot는 TPM이 필요 없고 펌웨어의 db/dbx로 동작합니다. Measured Boot의 결과는 BitLocker 키 봉인이나 원격 증명에서 쓰입니다.

ELAM 드라이버가 할 수 없는 것은?

  1. 다른 부트 드라이버보다 먼저 초기화된다
  2. 부트 드라이버를 KnownGood/KnownBad/Unknown으로 분류한다
  3. 변조된 bootmgr나 winload를 탐지해 실행을 막는다
  4. 분류에 쓸 정보로 이미지 해시와 인증서 정보를 받는다
ELAM은 커널이 초기화된 뒤에야 실행되므로 그보다 앞선 부트 로더 단계는 볼 수 없습니다. 그 구간은 Secure Boot(차단)와 Measured Boot(기록)가 담당합니다.

Process Explorer에서 wininit.exe의 부모 프로세스가 "Non-existent Process"로 표시되는 이유는?

  1. wininit은 커널이 직접 만든다
  2. 세션 0용 smss 사본이 wininit을 만든 뒤 종료했기 때문이다
  3. csrss가 만든 뒤 PID를 숨기기 때문이다
  4. Protected Process라 부모 정보가 지워지기 때문이다
마스터 smss는 세션마다 사본을 만들고, 사본이 csrss와 wininit(세션 0) 또는 winlogon(세션 1)을 실행한 뒤 종료합니다. 부모 PID는 남지만 그 프로세스는 이미 없습니다.

드라이버를 수정한 뒤 "시스템 종료 → 전원 켜기"로 테스트했더니 DriverEntry의 변경 사항이 반영되지 않은 것처럼 보입니다. 가장 유력한 원인은?

  1. BCD 캐시
  2. 빠른 시작(Fast Startup)으로 커널 세션이 최대 절전 상태에서 복원되어 드라이버가 다시 초기화되지 않았다
  3. Secure Boot가 이전 버전을 캐시했다
  4. ELAM이 새 버전을 Unknown으로 분류했다
빠른 시작을 쓰면 시스템 종료가 커널 세션의 최대 절전이 되고, 다음 부팅은 winresume.efi로 복원합니다. 드라이버 초기화 경로를 시험하려면 "다시 시작"을 쓰세요.

핵심 요약

  • UEFI → bootmgfw.efi(BCD) → winload.efi(커널·HAL·부트 드라이버 적재, 로더 블록) → KiSystemStartup → Phase 0 → Phase 1 → smss → csrss/wininit/winlogon → services/lsass → 로그온.
  • LOADER_PARAMETER_BLOCK은 메모리 맵, 이미지 목록, 부트 드라이버 목록, SYSTEM 하이브를 커널에 넘기며, 부팅 후에는 회수된다.
  • Phase 0은 BSP 하나·인터럽트 비활성 상태의 기반 구축, Phase 1은 AP 기동·드라이버 초기화·첫 유저 프로세스 생성이다.
  • Start 0/1은 커널이 부팅 중에, 2는 SCM이, 3은 요청이나 PnP가 로드한다. Boot 드라이버는 "winload가 적재, 커널이 초기화"한다.
  • Secure Boot는 차단, Measured Boot는 기록, ELAM은 부트 드라이버 평판 판정, CI/DSE는 부팅 이후 서명 강제를 맡는다. dbx가 최신이어야 체인이 완성된다.
