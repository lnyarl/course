Part IV · Chapter 11

I/O 시스템과 IRP

모든 파일·디바이스·네트워크 요청은 IRP라는 패킷이 되어 계층형 드라이버 스택을 내려갔다가 완료되어 올라옵니다. 그 왕복을 정확히 따라가는 것이 드라이버 개발과 행(hang) 분석의 출발점입니다.

심화⏱ 약 120분선수: 06 IRQL·DPC·APC, 10 객체 관리자

학습 목표

  • DRIVER_OBJECT·DEVICE_OBJECT·FILE_OBJECT·IRP가 서로 어떻게 연결되는지 그릴 수 있다.
  • IRP의 스택 로케이션이 IoCallDriver로 내려가고 IoCompleteRequest로 올라오는 과정을 CurrentLocation 값 단위로 추적할 수 있다.
  • 완료 루틴, STATUS_PENDING, IoMarkIrpPending의 규칙을 지키지 않았을 때 생기는 버그를 설명할 수 있다.
  • 버퍼링 방식(Buffered/Direct/Neither)과 IOCTL 코드의 비트 구조를 해석하고 보안상 함정을 짚을 수 있다.
  • PnP 관리자가 디바이스 스택을 만들고 시작하는 순서, 전원 IRP와 I/O 우선순위의 개요를 설명할 수 있다.

I/O 시스템의 설계 철학

Windows I/O 관리자는 "패킷 기반, 계층형, 본질적으로 비동기"라는 세 원칙 위에 서 있습니다. 유저가 ReadFile을 부르든 메모리 관리자가 페이지 폴트를 해결하든, 요청은 IRP(I/O Request Packet)라는 자기 기술적 패킷으로 만들어져 드라이버에서 드라이버로 넘겨집니다. 각 드라이버는 패킷을 처리하거나, 변형해 아래로 넘기거나, 큐에 보관했다가 나중에 완료합니다.

패킷 기반

요청의 모든 상태(버퍼, 파라미터, 결과, 소유 스레드)가 IRP 하나에 담긴다. 호출 스택이 아니라 데이터 구조가 요청을 대표한다.

계층형

디바이스 스택의 각 층(필터·기능·버스 드라이버)이 같은 IRP를 차례로 처리한다. 층마다 자기 몫의 스택 로케이션을 가진다.

비동기

드라이버는 STATUS_PENDING을 반환하고 나중에 완료할 수 있다. 동기 I/O는 "비동기 I/O + 대기"로 구현된다.

이 장은 WDM 수준(I/O 관리자가 직접 다루는 구조체)에서 설명합니다. KMDF는 이 위에 큐·상태 기계를 얹은 프레임워크이며, KMDF 드라이버도 디버거에서 보면 결국 같은 IRP와 디바이스 스택으로 동작합니다(→ 14장).

드라이버 · 디바이스 · 파일 객체

I/O 시스템의 핵심 객체는 네 가지입니다. 드라이버 객체는 로드된 드라이버 이미지 하나를 대표하고, 디바이스 객체는 그 드라이버가 처리하는 논리/물리 장치 하나를 대표하며, 파일 객체는 디바이스(또는 파일)를 연 "열기 인스턴스" 하나를, IRP는 진행 중인 요청 하나를 대표합니다. 도식의 각 요소를 클릭해 보세요.

IRP는 "이름의 디바이스"가 아니라 "스택 최상단"으로 간다

FILE_OBJECT.DeviceObject가 PDO를 가리키더라도, I/O 관리자는 IoGetRelatedDeviceObject(FileObject)로 대상 스택의 최상단(파일 시스템 파일이면 Vpb->DeviceObject 스택의 최상단)을 구해 IRP를 보냅니다. 그래서 나중에 붙은 필터도 모든 요청을 볼 수 있습니다. 단, 필터가 붙기 전에 이미 열린 핸들의 요청도 새 최상단으로 가므로, 필터는 자신이 보지 못한 CREATE에 대한 READ를 받을 수 있다는 점을 처리해야 합니다.

디바이스 스택과 계층형 드라이버

PnP 장치 하나에는 아래부터 PDO(버스 드라이버) → [하위 필터] → FDO(기능 드라이버) → [상위 필터] 순으로 디바이스 객체가 쌓입니다. 스택에 붙는 함수는 IoAttachDeviceToDeviceStack(새 DO, 대상 DO)이며, 반환값은 대상 DO가 아니라 붙기 직전의 최상단 DO입니다. 드라이버는 이 반환값을 "내 아래 디바이스"로 저장해 IRP를 넘길 때 써야 합니다.

상위 필터 (Upper filter)

FDO 위. 기능 드라이버가 해석하기 전의 요청을 본다. 예: 디스크 위의 partmgr, 키보드 위의 kbdclass, 암호화·감시 필터.

하위 필터 (Lower filter)

FDO와 PDO 사이. 기능 드라이버가 버스로 보내는 요청(예: URB, SRB)을 본다. 하드웨어 버그 보정, 프로토콜 트레이싱.

기능 드라이버 (FDO)

장치를 "운영"한다. 전원 정책 소유자인 경우가 많다. 레지스트리 Service 값으로 지정.

버스 드라이버 (PDO)

자식 장치를 열거하고 PDO를 만든다. 자식에 대한 버스 수준 요청(설정 공간 접근, 리셋)을 처리.

NTSTATUS MyAddDevice(PDRIVER_OBJECT DriverObject, PDEVICE_OBJECT Pdo)
{
    PDEVICE_OBJECT fdo;
    NTSTATUS st = IoCreateDevice(DriverObject, sizeof(MY_EXT), NULL,
                                 FILE_DEVICE_UNKNOWN, FILE_DEVICE_SECURE_OPEN, FALSE, &fdo);
    if (!NT_SUCCESS(st)) return st;

    PMY_EXT ext = (PMY_EXT)fdo->DeviceExtension;
    ext->Self  = fdo;
    ext->Lower = IoAttachDeviceToDeviceStack(fdo, Pdo);   // 반환 = 붙기 직전의 최상단
    if (ext->Lower == NULL) { IoDeleteDevice(fdo); return STATUS_NO_SUCH_DEVICE; }

    // 아래 장치의 버퍼링/전원 특성을 물려받는다 (필터라면 DeviceType·Characteristics도 복사)
    fdo->Flags |= ext->Lower->Flags & (DO_BUFFERED_IO | DO_DIRECT_IO | DO_POWER_PAGABLE);
    fdo->Flags &= ~DO_DEVICE_INITIALIZING;               // 잊으면 이 장치는 열리지 않는다
    return STATUS_SUCCESS;                                // 하드웨어 접근은 START_DEVICE에서!
}
흔한 실수

DO_DEVICE_INITIALIZING을 지우지 않으면 I/O 관리자가 CREATE를 거부합니다. AddDevice에서는 하드웨어 리소스가 아직 할당되지 않았으므로 레지스터 접근은 IRP_MN_START_DEVICE 처리 이후에만 해야 합니다. 그리고 필터의 버퍼링 플래그가 아래 장치와 다르면 위아래 드라이버가 같은 IRP의 버퍼를 서로 다른 필드에서 찾게 됩니다.

IRP와 IO_STACK_LOCATION

IRP는 모든 층이 공유하는 헤더와 층마다 하나씩인 스택 로케이션 배열로 나뉩니다. 헤더에는 "요청 전체"에 관한 정보(버퍼, 최종 상태, 요청 스레드)가, 스택 로케이션에는 "이 층이 받은 명령"(MajorFunction, 파라미터, 대상 DO, 그리고 위층이 등록한 완료 루틴)이 들어갑니다.

새 IRP의 CurrentLocation은 StackCount + 1, 즉 배열 바깥을 가리킵니다. 요청자는 IoGetNextIrpStackLocation으로 #StackCount 로케이션을 채우고, IoCallDriver가 CurrentLocation을 1 감소시킨 뒤 최상단 드라이버를 호출합니다. 맨 아래 드라이버는 #1을 씁니다. 0이 되면 NO_MORE_IRP_STACK_LOCATIONS 버그체크입니다.

IoCallDriver로 내려가고 IoCompleteRequest로 올라오기

3층 스택(필터 → FDO → PDO)에서 읽기 요청 하나를 따라갑니다. 필터는 완료 루틴을 등록하고, PDO는 하드웨어에 요청을 건 뒤 STATUS_PENDING을 반환합니다. 오른쪽 IRP의 CurrentLocation과 각 로케이션의 Control 값 변화를 주목하세요. 

// (1) 관심 없는 요청: 내 로케이션을 하위가 재사용하게 한다
NTSTATUS FiltPassThrough(PDEVICE_OBJECT DeviceObject, PIRP Irp)
{
    PFLT_EXT ext = (PFLT_EXT)DeviceObject->DeviceExtension;
    IoSkipCurrentIrpStackLocation(Irp);          // CurrentLocation++ (IoCallDriver가 다시 --)
    return IoCallDriver(ext->Lower, Irp);        // 이 줄 이후 Irp는 내 것이 아니다
}

// (2) 결과를 봐야 하는 요청: 다음 로케이션을 만들고 완료 루틴을 건다
NTSTATUS FiltDispatchRead(PDEVICE_OBJECT DeviceObject, PIRP Irp)
{
    PFLT_EXT ext = (PFLT_EXT)DeviceObject->DeviceExtension;
    IoCopyCurrentIrpStackLocationToNext(Irp);    // CompletionRoutine 필드는 복사되지 않는다
    IoSetCompletionRoutine(Irp, FiltComplete, ext, TRUE, TRUE, TRUE);
    return IoCallDriver(ext->Lower, Irp);        // 하위의 반환값을 "그대로" 돌려준다
}

NTSTATUS FiltComplete(PDEVICE_OBJECT DeviceObject, PIRP Irp, PVOID Context)
{
    // IRQL <= DISPATCH_LEVEL, 임의 스레드 문맥. 페이지 가능 코드·유저 버퍼 접근 금지.
    if (Irp->PendingReturned) {
        IoMarkIrpPending(Irp);                   // 디스패치가 하위 반환값을 그대로 돌려준 경우의 필수 규칙
    }
    if (NT_SUCCESS(Irp->IoStatus.Status)) {
        // Irp->IoStatus.Information 바이트가 전송됨 — 후처리
    }
    return STATUS_CONTINUE_COMPLETION;
}
IoSkip 후 완료 루틴을 걸면 안 되는 이유

Skip은 "내 로케이션 = 하위 로케이션"으로 만듭니다. 이 상태에서 IoSetCompletionRoutine을 호출하면 위층이 내 로케이션에 걸어 둔 완료 루틴을 덮어씁니다. 완료 루틴이 필요하면 반드시 Copy를 쓰세요. 또한 드라이버가 언로드될 수 있는 필터라면 완료 루틴 실행 중 이미지가 사라지지 않도록 IoSetCompletionRoutineEx를 고려합니다.

IRP 스택 시뮬레이터

필터를 추가/제거하고 층마다 동작을 바꾼 뒤 IRP를 보내 보세요. Skip은 로케이션을 재사용하고, 완료 루틴은 아래 로케이션에 루틴을 기록하며, 동기 대기는 STATUS_MORE_PROCESSING_REQUIRED로 IRP 소유권을 되찾는 START_DEVICE 패턴입니다. 한 단계씩 넘기며 CurrentLocation, 펜딩 전파, 완료 루틴 호출 순서를 관찰하세요.

디바이스 스택 · IRP 왕복 시뮬레이터 (IRP_MJ_READ)
디바이스 스택 (위 → 아래)
IRP
시뮬레이터로 확인해 볼 것

① 상위 필터를 Skip으로 바꾸면 사용되는 로케이션이 하나 줄어드는 것. ② PDO를 즉시 완료로 바꾸면 완료 루틴이 디스패치 루틴들이 반환하기 전에, 같은 스레드에서 호출되는 것. ③ FDO를 동기 대기로 두면 완료가 FDO의 완료 루틴에서 멈췄다가, FDO가 IoCompleteRequest를 다시 호출해야 위층 완료 루틴이 불리는 것, 그리고 위층은 PENDING을 보지 않는 것.

STATUS_PENDING과 비동기 완료

디스패치 루틴이 IRP를 즉시 끝낼 수 없으면 IRP를 큐에 넣거나 하드웨어에 넘긴 뒤 STATUS_PENDING을 반환합니다. 이때 지켜야 할 규칙은 단 하나지만 어기면 치명적입니다.

펜딩 규칙: 반환값과 SL_PENDING_RETURNED는 반드시 일치해야 한다
  • STATUS_PENDING을 반환한다면, 반환 전에 자기 로케이션에 IoMarkIrpPending을 호출해야 한다.
  • IoMarkIrpPending을 호출했다면, 실제 상태가 무엇이든 반드시 STATUS_PENDING을 반환해야 한다.
  • 하위 반환값을 그대로 돌려주면서 완료 루틴을 등록했다면, 완료 루틴에서 if (Irp->PendingReturned) IoMarkIrpPending(Irp);로 표시를 위로 전파해야 한다.

I/O 관리자는 최상단의 펜딩 여부로 "요청자가 결과를 기다려야 하는가"와 "완료 처리를 어디서 할 것인가"를 결정합니다. 불일치하면 이벤트가 영원히 신호되지 않아 행이 걸리거나, 반대로 완료 처리가 두 번 일어나 이미 해제된 IRP를 건드립니다. Driver Verifier의 I/O 검증이 이 실수를 잡습니다.

NTSTATUS MyDispatchRead(PDEVICE_OBJECT DeviceObject, PIRP Irp)
{
    PMY_EXT ext = (PMY_EXT)DeviceObject->DeviceExtension;
    IoMarkIrpPending(Irp);                     // 큐에 넣기 "전에" — 넣는 순간 다른 CPU가 완료·해제할 수 있다
    IoCsqInsertIrp(&ext->CancelSafeQueue, Irp, NULL);
    KickHardwareIfIdle(ext);
    return STATUS_PENDING;                     // IoMarkIrpPending과 짝
}

완료 통지: 이벤트 · APC · I/O 완료 포트

IRP가 완료되는 순간은 대개 DPC, 즉 요청 스레드와 무관한 임의 문맥입니다. 그런데 결과를 유저 IOSB에 쓰거나 Buffered I/O 데이터를 유저 버퍼로 복사하려면 요청 프로세스의 주소 공간이 필요합니다. 그래서 I/O 관리자는 완료의 마지막 단계를 원래 스레드에 특수 커널 APC(IopCompleteRequest)로 보냅니다. 단, 펜딩되지 않았고 I/O 관리자가 반환 경로에서 처리하기로 표시한 요청(IRP_DEFER_IO_COMPLETION)은 APC 없이 반환 경로에서 바로 처리합니다.

요청 방식드라이버가 PENDING 반환 시 요청자 동작완료 통지
동기 핸들 (FILE_FLAG_OVERLAPPED 없음)I/O 관리자가 커널에서 FileObject->Event를 대기 후 결과 반환파일 객체 이벤트
비동기 핸들 + OVERLAPPED.hEvent즉시 ERROR_IO_PENDING 반환지정 이벤트 (또는 GetOverlappedResult)
ReadFileEx/WriteFileEx즉시 반환유저 APC (alertable 대기 필요)
IOCP 연결 핸들즉시 반환완료 포트 패킷. FILE_SKIP_COMPLETION_PORT_ON_SUCCESS로 동기 성공 시 패킷 생략 가능
스레드와 무관한(thread-agnostic) I/O

IOCP에 연결된 파일의 IRP는 특정 스레드에 묶일 필요가 적기 때문에, 최신 Windows는 이런 IRP를 스레드 대신 파일 객체/완료 포트와 연결해 APC 없이 완료할 수 있습니다. 세부 조건은 버전에 따라 다르므로 "항상 APC를 거친다"고 단정하지 마세요.

버퍼링 방식과 IOCTL 코드

유저 버퍼를 드라이버에 어떻게 보여줄지는 요청 종류에 따라 다르게 결정됩니다. READ/WRITE는 디바이스 객체의 Flags(DO_BUFFERED_IO/DO_DIRECT_IO/둘 다 없음)로, IOCTL은 제어 코드의 하위 2비트(Method)로 정해집니다.

I/O 관리자가 비페이지 풀에 max(입력, 출력) 크기의 SystemBuffer를 할당하고 입력을 복사해 넣습니다. 드라이버는 그 버퍼에서 읽고 같은 버퍼에 결과를 씁니다. 완료 시 I/O 관리자가 IoStatus.Information 바이트를 유저 출력 버퍼로 복사합니다.

  • 장점: 드라이버가 유저 주소를 만지지 않으므로 가장 안전. 임의 문맥/높은 IRQL에서도 접근 가능.
  • 단점: 복사 2회. 큰 전송에는 부적합.
  • 함정: 입력과 출력이 같은 버퍼이므로 출력을 쓰기 전에 입력을 다 읽어 둘 것. Information을 실제 쓴 크기보다 크게 설정하면 초기화되지 않은 풀 내용이 유저에게 새어 나간다(정보 노출 취약점).

I/O 관리자가 유저 버퍼를 프로브하고 페이지를 잠근 뒤 그 물리 페이지 목록을 MDL로 만들어 Irp->MdlAddress에 둡니다. 드라이버는 DMA에 MDL을 그대로 쓰거나, CPU로 접근해야 하면 MmGetSystemAddressForMdlSafe로 시스템 주소에 매핑합니다.

  • IOCTL에서는 입력은 SystemBuffer(버퍼링), 출력 버퍼만 MDL입니다. METHOD_IN_DIRECT는 출력 버퍼를 읽기 접근으로(디바이스가 그 버퍼에서 데이터를 가져감), METHOD_OUT_DIRECT는 쓰기 접근으로 프로브합니다.
  • 함정: 유저가 같은 물리 페이지를 다른 가상 주소로 동시에 보고 있으므로 "한 번 검증 후 다시 읽기"는 TOCTOU가 될 수 있습니다.

I/O 관리자는 아무것도 하지 않습니다. IOCTL 입력은 Parameters.DeviceIoControl.Type3InputBuffer, 출력은 Irp->UserBuffer에 원래 유저 주소 그대로 들어옵니다.

  • 드라이버는 요청 스레드 문맥(최상단, PASSIVE_LEVEL)에서만 접근할 수 있고, RequestorMode == UserMode면 __try 안에서 ProbeForRead/ProbeForWrite 후 접근하고 값을 커널로 복사(capture)해 써야 합니다.
  • 파일 시스템 FSCTL 중 일부(예: FSCTL_GET_RETRIEVAL_POINTERS)가 이 방식을 씁니다. 서드파티 드라이버 취약점의 단골 출처입니다.
NTSTATUS MyDeviceControl(PDEVICE_OBJECT DeviceObject, PIRP Irp)
{
    PIO_STACK_LOCATION sp = IoGetCurrentIrpStackLocation(Irp);
    ULONG inLen  = sp->Parameters.DeviceIoControl.InputBufferLength;
    ULONG outLen = sp->Parameters.DeviceIoControl.OutputBufferLength;
    NTSTATUS st = STATUS_INVALID_DEVICE_REQUEST;
    ULONG_PTR info = 0;
    UNREFERENCED_PARAMETER(DeviceObject);

    switch (sp->Parameters.DeviceIoControl.IoControlCode) {
    case IOCTL_MY_QUERY: {                                   // METHOD_BUFFERED
        if (inLen < sizeof(MY_IN) || outLen < sizeof(MY_OUT)) { st = STATUS_BUFFER_TOO_SMALL; break; }
        ULONG id = ((PMY_IN)Irp->AssociatedIrp.SystemBuffer)->Id;   // 입력을 먼저 읽어 둔다
        PMY_OUT out = (PMY_OUT)Irp->AssociatedIrp.SystemBuffer;      // 같은 버퍼
        RtlZeroMemory(out, sizeof(MY_OUT));                          // 패딩까지 초기화
        out->Value = LookupValue(id);
        info = sizeof(MY_OUT);                                       // I/O 관리자가 이만큼 복사
        st = STATUS_SUCCESS;
        break; }
    }
    Irp->IoStatus.Status = st;
    Irp->IoStatus.Information = info;
    IoCompleteRequest(Irp, IO_NO_INCREMENT);
    return st;                                                       // 펜딩 안 했으므로 실제 상태 반환
}

IOCTL 코드의 비트 구조

CTL_CODE(DeviceType, Function, Method, Access) = (DeviceType << 16) | (Access << 14) | (Function << 2) | Method. DeviceType 0x8000 이상(bit 31 = Common 비트)과 Function 0x800 이상(bit 13 = Custom 비트)은 서드파티용으로 예약되어 있습니다. Access는 I/O 관리자가 NtDeviceIoControlFile에서 핸들의 허가 접근을 검사하는 데 씁니다 — FILE_READ_ACCESS면 핸들에 FILE_READ_DATA가, FILE_WRITE_ACCESS면 FILE_WRITE_DATA가 있어야 합니다.

IOCTL 디코더 — 코드 ↔ 필드
보안 함정: FILE_ANY_ACCESS + 느슨한 DACL

디바이스 객체의 보안 설명자가 Everyone 열기를 허용하고 IOCTL이 FILE_ANY_ACCESS라면, 일반 사용자도 그 IOCTL을 호출할 수 있습니다. 물리 메모리·MSR·포트 접근을 IOCTL로 노출한 서명된 드라이버가 "취약한 드라이버(BYOVD)" 공격에 쓰이는 전형적 경로입니다. IoCreateDeviceSecure(SDDL 지정)와 FILE_DEVICE_SECURE_OPEN(디바이스 이름 뒤 경로 열기에도 같은 DACL 적용)을 사용하고, 위험한 IOCTL에는 읽기/쓰기 접근을 요구하세요.

Fast I/O

캐시에 이미 있는 파일 데이터를 읽는 데 IRP를 할당하고 스택을 왕복하는 것은 낭비입니다. 그래서 파일 시스템은 DRIVER_OBJECT.FastIoDispatch에 FAST_IO_DISPATCH 테이블(FastIoRead, FastIoWrite, FastIoQueryBasicInfo, FastIoDeviceControl …)을 제공합니다.

  • I/O 관리자는 (주로 동기 파일 객체에 대해) IRP를 만들기 전에 최상단 드라이버의 Fast I/O 루틴을 직접 함수 호출합니다.
  • 파일 시스템은 캐싱이 시작된 파일이고 바이트 범위 락 등 제약이 없으면 CcFastCopyRead/FsRtlCopyRead로 캐시에서 복사하고 TRUE를 반환합니다.
  • FALSE를 반환하면 "이 경로로는 못 한다"는 뜻일 뿐이며, I/O 관리자가 일반 IRP 경로로 다시 시도합니다. 즉 Fast I/O는 언제든 실패해도 되는 최적화입니다.
  • 파일 시스템이 아닌 드라이버도 쓸 수 있습니다. 예: FastIoDeviceControl은 IOCTL을 IRP 없이 처리하는 데 쓰입니다(AFD 등).
레거시 필터가 Fast I/O를 잊으면

레거시 파일 시스템 필터는 IRP뿐 아니라 Fast I/O 테이블도 패스스루로 구현해야 합니다. 빠뜨리면 그 볼륨의 Fast I/O가 꺼져 성능이 크게 떨어지거나, 반대로 필터가 Fast I/O 경로의 요청을 보지 못해 감시에 구멍이 납니다. 미니필터 모델(12장)에서는 Filter Manager가 Fast I/O를 콜백 데이터로 통일해 줍니다(FLTFL_CALLBACK_DATA_FAST_IO_OPERATION).

PnP 관리자와 디바이스 트리

PnP 관리자는 루트 열거자에서 시작해 각 버스 드라이버에게 "자식이 누구냐"고 물으며 장치 트리를 만듭니다. 트리의 각 노드(devnode)는 하나의 PDO에 대응하고, 그 위에 쌓인 디바이스 스택을 가집니다. 다음 스테퍼는 새 PCI 장치가 발견되어 드라이버가 붙고 시작되기까지의 과정입니다. 

static NTSTATUS SyncComplete(PDEVICE_OBJECT D, PIRP Irp, PVOID Ctx)
{
    UNREFERENCED_PARAMETER(D); UNREFERENCED_PARAMETER(Irp);
    KeSetEvent((PKEVENT)Ctx, IO_NO_INCREMENT, FALSE);
    return STATUS_MORE_PROCESSING_REQUIRED;     // 완료 처리를 멈추고 IRP 소유권을 되찾는다
}

NTSTATUS ForwardAndWait(PDEVICE_OBJECT Lower, PIRP Irp)   // PASSIVE_LEVEL에서만
{
    KEVENT evt;
    KeInitializeEvent(&evt, NotificationEvent, FALSE);
    IoCopyCurrentIrpStackLocationToNext(Irp);
    IoSetCompletionRoutine(Irp, SyncComplete, &evt, TRUE, TRUE, TRUE);
    NTSTATUS st = IoCallDriver(Lower, Irp);
    if (st == STATUS_PENDING) {
        KeWaitForSingleObject(&evt, Executive, KernelMode, FALSE, NULL);
        st = Irp->IoStatus.Status;
    }
    return st;   // 호출자는 하드웨어 초기화 후 IoCompleteRequest를 "다시" 호출해야 한다
}
PnP 마이너 코드의미와 처리 방향
IRP_MN_START_DEVICE리소스와 함께 시작. 아래부터 처리(위 패턴).
IRP_MN_QUERY_STOP_DEVICE / STOP_DEVICE리소스 재배치(rebalance)를 위한 일시 정지. 정지 중 들어온 IRP는 보류.
IRP_MN_QUERY_REMOVE_DEVICE / REMOVE_DEVICE정상 제거. REMOVE에서 위층부터 처리하고 아래로 넘긴 뒤 IoDetachDevice + IoDeleteDevice.
IRP_MN_SURPRISE_REMOVAL예고 없는 제거(USB 뽑기). 하드웨어 접근 중단, 대기 IRP 실패 처리. 이후 REMOVE가 온다.
IRP_MN_QUERY_DEVICE_RELATIONSBusRelations(자식 목록), RemovalRelations, TargetDeviceRelation 등.
IRP_MN_QUERY_CAPABILITIESD-상태 매핑(S→D), 제거 가능 여부, 웨이크 능력. 아래(버스)가 채우고 위가 보정.
REMOVE와 진행 중 I/O — Remove Lock

REMOVE 처리 중에도 다른 스레드의 IRP가 디스패치 루틴 안에 있을 수 있습니다. IoAcquireRemoveLock/IoReleaseRemoveLock/IoReleaseRemoveLockAndWait로 진행 중 I/O를 세고, 모두 빠져나간 뒤 장치를 삭제해야 use-after-free를 피할 수 있습니다. KMDF는 이를 자동으로 처리합니다.

전원 IRP 개요

S-IRP (시스템 전원)

IRP_MJ_POWER + IRP_MN_SET_POWER/QUERY_POWER, 타입 SystemPowerState(S0 작동 ~ S5 꺼짐). 전원 관리자가 각 스택에 보냅니다.

D-IRP (장치 전원)

타입 DevicePowerState(D0 완전 작동 ~ D3 꺼짐). 스택의 전원 정책 소유자(보통 FDO)가 S-IRP를 받으면 PoRequestPowerIrp로 적절한 D-IRP를 자기 스택에 요청합니다.

  • D0로 갈 때(켜기)는 START처럼 아래부터, 저전력으로 갈 때(끄기)는 위부터 상태를 저장하고 아래로 넘깁니다.
  • IRP_MN_WAIT_WAKE: 장치가 시스템/자신을 깨울 수 있도록 미리 걸어 두는 IRP. 깨우기 이벤트가 생기면 완료됩니다.
  • DO_POWER_PAGABLE이 설정된 DO는 전원 IRP를 PASSIVE_LEVEL에서 받습니다. 설정되지 않으면 DISPATCH_LEVEL에서 받을 수 있으므로 페이지 가능 코드를 쓰면 안 됩니다.
  • Windows Vista 이후로는 전원 IRP도 IoCallDriver로 전달하면 되며, 과거의 PoCallDriver/PoStartNextPowerIrp 규칙은 호환을 위한 것입니다.

I/O 우선순위 · 취소 · IRP 소유권

Windows는 CPU 스케줄링과 별개로 I/O 우선순위 힌트를 IRP에 실어 스토리지 스택이 순서를 정할 수 있게 합니다. 레벨은 IoPriorityVeryLow, Low, Normal, High, Critical입니다.

  • 스레드/프로세스를 백그라운드 모드(THREAD_MODE_BACKGROUND_BEGIN, PROCESS_MODE_BACKGROUND_BEGIN)로 바꾸면 그 I/O가 VeryLow가 됩니다. 인덱서·디펜더 검사·조각 모음 같은 작업이 사용.
  • 핸들 단위로는 SetFileInformationByHandle(FileIoPriorityHintInfo)로 지정합니다. 드라이버는 IoGetIoPriorityHint(Irp)로 읽습니다.
  • 힌트를 실제로 반영하는 것은 스토리지 스택(클래스/포트 드라이버)입니다. 낮은 우선순위 I/O가 락을 쥐고 있어 높은 우선순위 스레드가 막히는 우선순위 역전을 피하기 위한 부스트 메커니즘도 존재합니다.
  • Critical은 메모리 관리자의 일부 페이징 I/O처럼 시스템이 내부적으로 쓰는 레벨입니다.

취소

큐에 오래 머무는 IRP는 취소 가능해야 합니다. 스레드 종료, CancelIoEx가 IoCancelIrp를 부르면 I/O 관리자는 Irp->Cancel = TRUE로 설정하고 등록된 CancelRoutine을 호출합니다. 취소 루틴과 정상 완료 경로가 같은 IRP를 동시에 완료하려는 경쟁이 고전적인 버그 원천이므로, 직접 구현하지 말고 취소 안전 큐(IoCsq*)나 KMDF 큐를 쓰는 것이 정석입니다.

스레드 IRP (Threaded)

IoBuildSynchronousFsdRequest, IoBuildDeviceIoControlRequest로 만든 IRP. 스레드에 연결되고 I/O 관리자가 해제합니다. 만든 드라이버는 완료 후 IRP를 건드리지 않습니다.

드라이버 소유 IRP

IoAllocateIrp, IoBuildAsynchronousFsdRequest로 만든 IRP. 만든 드라이버의 완료 루틴이 STATUS_MORE_PROCESSING_REQUIRED를 반환하고 직접 IoFreeIrp해야 합니다.

실제 disk.sys는 원래 IRP를 그대로 내리지 않는다

교과서 그림과 달리 디스크 클래스 드라이버(classpnp 기반)는 읽기/쓰기 IRP를 받으면 미리 할당해 둔 "전송 패킷" IRP로 요청을 쪼개 포트 드라이버에 보내고, 모든 패킷이 끝나면 원래 IRP를 완료합니다. 그래서 !irp로 원래 IRP를 보면 디스크 아래 로케이션이 비어 있을 수 있습니다. 실제 스택을 분석할 때는 "이 층이 IRP를 전달하는가, 새로 만드는가"를 먼저 확인하세요.

확인 문제

필터 드라이버가 IoSetCompletionRoutine으로 등록한 완료 루틴은 IRP의 어느 스택 로케이션에 저장되나요?

  1. 필터 자신의 현재 로케이션
  2. 바로 아래 드라이버가 사용할 다음 로케이션
  3. IRP 헤더의 CompletionRoutine 필드
  4. 맨 아래(#1) 로케이션
IoSetCompletionRoutine은 IoGetNextIrpStackLocation에 씁니다. 아래 층이 완료하면 I/O 관리자가 그 로케이션의 루틴을 호출하는데, 그 전에 CurrentLocation을 올려 두므로 루틴 안에서 IoGetCurrentIrpStackLocation은 등록한 필터 자신의 로케이션이 됩니다. IRP 헤더에는 완료 루틴 필드가 없습니다.

디스패치 루틴이 IoMarkIrpPending을 호출한 뒤, 하위 드라이버가 즉시 성공 완료했다며 STATUS_SUCCESS를 반환했습니다. 무엇이 문제인가요?

  1. 문제없다. 실제 결과를 반환하는 편이 더 정확하다.
  2. 펜딩 표시와 반환값이 불일치해, I/O 관리자가 완료 처리를 중복하거나 요청자가 영원히 기다릴 수 있다.
  3. IRQL이 DISPATCH_LEVEL로 고정된다.
  4. IRP가 자동으로 취소된다.
IoMarkIrpPending을 호출했다면 반드시 STATUS_PENDING을 반환해야 합니다. I/O 관리자는 이 일치를 전제로 "반환 경로에서 처리할지, APC로 처리할지"를 정합니다. 불일치는 행 또는 해제된 IRP 접근(BSOD)으로 이어지며 Driver Verifier가 검출합니다.

CTL_CODE(FILE_DEVICE_UNKNOWN, 0x800, METHOD_NEITHER, FILE_ANY_ACCESS) IOCTL에서 드라이버가 출력 버퍼를 찾는 곳과 주의점은?

  1. Irp->AssociatedIrp.SystemBuffer — 이미 복사된 커널 버퍼라 안전
  2. Irp->MdlAddress — 잠긴 페이지라 아무 IRQL에서나 접근 가능
  3. Irp->UserBuffer — 원래 유저 주소이므로 요청 문맥에서 __try + ProbeForWrite 후 접근
  4. Parameters.DeviceIoControl.Type3InputBuffer — 출력 전용 커널 버퍼
METHOD_NEITHER는 I/O 관리자가 버퍼에 아무것도 하지 않습니다. 입력은 Type3InputBuffer, 출력은 UserBuffer로 유저 주소 그대로 옵니다. 요청 스레드 문맥에서만 유효하며, 프로브·예외 처리·캡처 없이 쓰면 임의 커널 메모리 쓰기 취약점이 됩니다. 게다가 FILE_ANY_ACCESS라 접근 검사도 느슨합니다.

IRP_MN_START_DEVICE를 처리하는 기능 드라이버의 올바른 순서는?

  1. 하드웨어 초기화 → IRP를 아래로 Skip 전달
  2. IRP를 즉시 완료하고 하드웨어는 DPC에서 초기화
  3. IRP를 아래로 보내 완료를 기다린 뒤(하위 성공 시) 하드웨어 초기화 → IoCompleteRequest
  4. AddDevice에서 이미 초기화했으므로 그냥 Skip 전달
START는 아래부터 처리해야 합니다. 버스(PDO)가 먼저 장치를 켜고 리소스를 활성화해야 기능 드라이버가 레지스터에 접근할 수 있습니다. 완료 루틴에서 STATUS_MORE_PROCESSING_REQUIRED로 IRP를 되찾고, 초기화 후 IoCompleteRequest를 다시 호출합니다. AddDevice 시점에는 리소스가 아직 없습니다.

Buffered I/O 읽기에서 데이터가 유저 버퍼로 복사되는 것은 언제, 어느 문맥에서인가요?

  1. 드라이버가 IoCompleteRequest를 호출하는 순간, DPC 문맥에서
  2. I/O 관리자의 완료 처리 단계에서, 보통 원래 스레드에 큐잉된 특수 커널 APC 문맥에서
  3. 드라이버가 직접 유저 버퍼에 써야 한다
  4. 유저 모드의 ntdll이 GetOverlappedResult에서 복사한다
DPC는 임의 프로세스 문맥이라 유저 주소에 쓸 수 없습니다. 그래서 I/O 관리자는 원래 스레드에 특수 커널 APC(IopCompleteRequest)를 보내 그 프로세스 주소 공간에서 SystemBuffer → UserBuffer 복사와 IOSB 기록을 합니다(펜딩 없이 동기 완료된 일부 요청은 반환 경로에서 바로 처리).

!irp 출력에서 디스크 드라이버 줄의 Completion 열에 partmgr!…가 아니라 CLASSPNP!TransferPktComplete가 보입니다. 이것이 의미하는 것은?

  1. disk.sys가 자신의 완료 루틴을 자기 로케이션에 등록했다
  2. 그 줄의 드라이버가 완료한 뒤 호출될 루틴으로, 바로 위 층(이 IRP를 만든/보낸 쪽)이 등록한 것이다
  3. IRP가 이미 완료되었다
  4. 완료 루틴은 항상 맨 아래 드라이버 것이 표시된다
각 로케이션의 Completion 열은 "이 로케이션의 드라이버가 완료한 다음 호출될, 위층이 등록한 루틴"입니다. 이 예에서는 classpnp가 만든 전송 패킷 IRP를 보고 있는 것이므로 classpnp의 완료 루틴이 보입니다. 이 규칙을 알아야 행 분석에서 IRP 소유자를 정확히 짚을 수 있습니다.

핵심 요약

  • DRIVER_OBJECT(디스패치 테이블) · DEVICE_OBJECT(스택의 층) · FILE_OBJECT(열기 인스턴스) · IRP(요청)가 I/O의 네 기둥이다. IRP는 이름의 디바이스가 아니라 스택 최상단으로 간다.
  • IRP의 스택 로케이션은 CurrentLocation = StackCount+1에서 시작해 IoCallDriver마다 1씩 내려가고, IoCompleteRequest가 다시 올라가며 각 로케이션의 (위층이 등록한) 완료 루틴을 호출한다.
  • STATUS_PENDING 반환과 IoMarkIrpPending은 반드시 짝을 이룬다. 완료 루틴은 PendingReturned를 위로 전파해야 한다. STATUS_MORE_PROCESSING_REQUIRED는 IRP 소유권을 되찾는 수단이다.
  • 완료의 마지막 단계는 보통 원래 스레드의 특수 커널 APC에서 일어나며, 이벤트·유저 APC·IOCP로 요청자에게 통지된다.
  • 버퍼링은 Buffered(복사)·Direct(MDL)·Neither(유저 주소)이며, IOCTL은 코드의 하위 2비트가 방식을, 비트 14–15가 필요 접근을 정한다. Neither와 FILE_ANY_ACCESS는 보안 감사의 1순위다.
  • PnP는 아래부터 AddDevice로 스택을 쌓고, START는 위에서 보내 아래부터 처리한다. REMOVE는 Remove Lock으로 진행 중 I/O를 기다린다.
