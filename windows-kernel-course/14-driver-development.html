Part V · Chapter 14

커널 드라이버 개발

지금까지 배운 IRQL, 동기화, 메모리, IRP를 코드로 옮기는 단계. 핵심은 "동작하는 드라이버"가 아니라 "시스템을 절대 무너뜨리지 않는 드라이버"입니다.

심화⏱ 약 120분선수: 06, 07, 11장

학습 목표

  • WDM, KMDF, UMDF의 차이를 알고 상황에 맞는 모델을 고를 수 있다.
  • 드라이버가 로드되어 요청을 처리하고 언로드되기까지의 생명주기를 설명할 수 있다.
  • KMDF 최소 드라이버의 구조(DriverEntry, EvtDeviceAdd, I/O 큐)를 이해한다.
  • IRQL·페이징·풀 할당·정리 순서에 관한 커널 코딩 규칙을 적용할 수 있다.
  • Driver Verifier와 정적 분석으로 드라이버를 검증하고, 서명·배포 경로를 이해한다.

드라이버 모델 고르기

Windows 드라이버는 세 가지 모델 중 하나로 작성합니다. WDM은 I/O 관리자의 IRP를 직접 다루는 원시 모델이고, WDF(Windows Driver Frameworks)는 그 위에 PnP·전원·동기화의 정형 코드를 대신 처리해 주는 프레임워크입니다. WDF는 커널 모드용 KMDF와 유저 모드용 UMDF로 나뉩니다.

새 커널 드라이버의 기본 선택. 프레임워크가 PnP/전원 상태 머신, IRP 취소, 객체 수명(부모-자식 자동 정리), 요청 동기화를 처리합니다. 개발자는 이벤트 콜백(EvtDeviceAdd, EvtIoDeviceControl …)만 구현합니다.

언제: 하드웨어 드라이버, 커널 상주가 필요한 소프트웨어 드라이버 대부분.

가능하면 유저 모드로. UMDF v2는 KMDF와 거의 같은 API를 쓰지만 드라이버가 WUDFHost.exe 프로세스에서 실행됩니다. 드라이버가 크래시해도 시스템이 아니라 호스트 프로세스만 재시작됩니다.

언제: USB·센서·HID 등 높은 IRQL에서 할 일이 없고, 성능 요구가 극단적이지 않은 장치. 커널 공격 표면을 줄이려면 첫 후보.

모든 것을 직접. DRIVER_OBJECT의 MajorFunction 테이블을 채우고 IRP를 직접 완료·전달합니다. PnP/전원 IRP를 올바르게 처리하는 코드는 길고 실수하기 쉽습니다.

언제: 기존 WDM 코드 유지보수, 프레임워크가 지원하지 않는 특수 상황, 그리고 11장의 IRP 메커니즘을 체득하기 위한 학습용.

특정 장치군은 Microsoft가 제공하는 포트/미니포트·클래스 확장 모델을 씁니다: 스토리지(Storport 미니포트), 네트워크(NDIS, NetAdapterCx), 디스플레이(WDDM), 오디오(PortCls/ACX), 파일 시스템 필터(Filter Manager 미니필터, 12장), 네트워크 필터(WFP 콜아웃).

언제: 해당 장치 클래스라면 반드시 그 모델을 따른다. 클래스 드라이버가 공통 로직을 처리한다.

선택 원칙

① 유저 모드로 가능하면 UMDF → ② 장치 클래스 모델이 있으면 그것 → ③ 나머지는 KMDF → ④ WDM은 이유가 있을 때만.

개발 환경

호스트 (개발 PC)

  • Visual Studio + WDK(Windows Driver Kit) — 버전을 맞춰 설치
  • 프로젝트 템플릿: Kernel Mode Driver, Empty (KMDF)
  • WinDbg + 심볼 서버 설정(15장)

타깃 (테스트 VM)

  • Hyper-V/VMware 가상 머신, 스냅샷 필수
  • KDNET 커널 디버깅 연결
  • 테스트 서명 모드 + Driver Verifier 활성화
개발 중인 드라이버는 절대 주 작업 PC에 올리지 않는다

커널 드라이버의 버그는 즉시 시스템 크래시, 최악의 경우 파일 시스템 손상이나 부팅 불가로 이어집니다. 항상 스냅샷을 찍은 테스트 VM에서 디버거를 연결한 상태로 실행하세요.

드라이버의 생명주기

소프트웨어(비 PnP) KMDF 드라이버를 기준으로, 로드부터 언로드까지 커널 안에서 일어나는 일을 따라가 봅니다.

최소 KMDF 드라이버

Microsoft Learn의 "Hello World" KMDF 샘플과 같은 구조입니다. 이 몇 줄 뒤에서 프레임워크가 PnP·전원·정리를 대신 처리하고 있다는 점이 핵심입니다.

#include <ntddk.h>
#include <wdf.h>

DRIVER_INITIALIZE DriverEntry;
EVT_WDF_DRIVER_DEVICE_ADD KmdfHelloWorldEvtDeviceAdd;

NTSTATUS
DriverEntry(
    _In_ PDRIVER_OBJECT  DriverObject,
    _In_ PUNICODE_STRING RegistryPath
)
{
    NTSTATUS status;
    WDF_DRIVER_CONFIG config;

    KdPrintEx((DPFLTR_IHVDRIVER_ID, DPFLTR_INFO_LEVEL, "KmdfHelloWorld: DriverEntry\n"));

    // EvtDeviceAdd 콜백을 등록하고 프레임워크 드라이버 객체를 만든다
    WDF_DRIVER_CONFIG_INIT(&config, KmdfHelloWorldEvtDeviceAdd);
    status = WdfDriverCreate(DriverObject, RegistryPath,
                             WDF_NO_OBJECT_ATTRIBUTES, &config, WDF_NO_HANDLE);
    return status;
}

NTSTATUS
KmdfHelloWorldEvtDeviceAdd(
    _In_    WDFDRIVER       Driver,
    _Inout_ PWDFDEVICE_INIT DeviceInit
)
{
    UNREFERENCED_PARAMETER(Driver);
    WDFDEVICE hDevice;

    KdPrintEx((DPFLTR_IHVDRIVER_ID, DPFLTR_INFO_LEVEL, "KmdfHelloWorld: EvtDeviceAdd\n"));

    // 디바이스 객체 생성. 실패해도 DeviceInit 정리는 프레임워크가 처리
    return WdfDeviceCreate(&DeviceInit, WDF_NO_OBJECT_ATTRIBUTES, &hDevice);
}

WDM이었다면?

IoCreateDevice, IoAttachDeviceToDeviceStack, MajorFunction 테이블 설정, PnP/전원 IRP 수십 가지의 올바른 처리, 제거 락(remove lock), 취소 처리까지 직접 작성해야 합니다. 이 부분이 WDM 드라이버 버그의 주된 원천이었습니다.

함수 역할 선언

DRIVER_INITIALIZE DriverEntry; 같은 역할 타입 선언은 정적 분석기(Code Analysis, SDV)에 "이 함수는 이 콜백이다"라고 알려 줍니다. 그래야 IRQL·반환값 규칙을 검사할 수 있습니다.

I/O 큐와 요청 흐름

KMDF에서는 IRP 대신 WDFREQUEST를 다루고, 요청은 큐를 통해 전달됩니다. 큐의 디스패치 방식이 곧 동기화 정책입니다. 상자를 클릭해 보세요.

커널 코딩 규칙

유저 모드 코드와 가장 크게 다른 점은 "지금 어떤 IRQL에서, 어떤 문맥에서 실행 중인가"를 항상 의식해야 한다는 것입니다.

① IRQL을 주석으로 계약하기

SAL 주석으로 함수의 IRQL 요구사항을 선언하면 컴파일러 분석이 위반을 잡아 줍니다.

_IRQL_requires_max_(PASSIVE_LEVEL)
NTSTATUS LoadConfig(VOID);

_IRQL_requires_max_(DISPATCH_LEVEL)
VOID UpdateCounter(_Inout_ PDEVICE_CTX Ctx);

② 페이지 가능 코드 표시

PASSIVE에서만 도는 함수는 페이지 가능 섹션에 넣고, 진입부에서 PAGED_CODE()로 단언합니다. 체크 빌드/Verifier에서 높은 IRQL 호출을 잡아냅니다.

#pragma alloc_text(PAGE, LoadConfig)

NTSTATUS LoadConfig(VOID)
{
    PAGED_CODE();
    ...
}

③ 풀 할당은 태그와 함께

ExAllocatePool2는 기본적으로 메모리를 0으로 초기화하고, 실패 시 NULL을 반환합니다(플래그로 예외 발생 선택 가능). 태그는 누수 추적의 단서입니다.

#define MY_TAG 'xEyM'   // 메모리에는 "MyEx"로 보임

PVOID p = ExAllocatePool2(POOL_FLAG_NON_PAGED, Size, MY_TAG);
if (p == NULL) {
    return STATUS_INSUFFICIENT_RESOURCES;
}
...
ExFreePoolWithTag(p, MY_TAG);

④ 정리는 획득의 역순

DriverEntry 중간에 실패하면 그때까지 만든 것을 모두 되돌려야 합니다. 언로드에서도 마찬가지로, 콜백 등록 해제 → 대기 중 작업 완료 대기 → 메모리 해제 순서를 지킵니다. 해제 후 콜백이 호출되면 언로드된 코드로 점프해 크래시합니다.

규칙이유위반 시
DISPATCH_LEVEL 이상에서 페이지 가능 메모리 접근 금지페이지 폴트를 처리하려면 대기가 필요한데, DISPATCH 이상에서는 대기할 수 없다0xA / 0xD1 버그체크
DISPATCH_LEVEL 이상에서 대기 금지스케줄러 자체가 DISPATCH에서 동작하므로 스레드 전환 불가0xA, 데드락
스핀락은 짧게, 중첩 순서 고정잡는 동안 해당 CPU의 스레드 전환이 멈춘다성능 저하, 데드락, 0x133 (DPC 워치독)
유저 버퍼는 신뢰하지 않는다길이·내용·포인터 모두 호출자가 통제한다크래시, 정보 노출, 권한 상승 취약점
요청은 정확히 한 번 완료두 번 완료하면 해제된 IRP를 건드린다0x44 MULTIPLE_IRP_COMPLETE_REQUESTS
언로드 시 모든 등록·할당 해제남은 콜백·타이머가 언로드된 코드를 호출0xCE DRIVER_UNLOADED_WITHOUT_CANCELLING_PENDING_OPERATIONS
IRQL 규칙 판정기 — 이 작업, 지금 해도 될까?

요청 처리의 안전 원칙

드라이버가 유저 모드에 인터페이스를 여는 순간, 그 인터페이스는 공격 표면이 됩니다. 실무에서 발견되는 드라이버 취약점 대부분은 아래 원칙 중 하나를 어긴 결과입니다.

접근 제어

디바이스 생성 시 SDDL로 열 수 있는 주체를 제한합니다(예: Administrators와 SYSTEM만). 기본값에 의존하지 말고 WdfDeviceInitAssignSDDLString으로 명시합니다.

길이 검증

입력/출력 버퍼 크기는 WdfRequestRetrieveInputBuffer의 최소 길이 인자로 검증합니다. 필요한 크기보다 작으면 즉시 STATUS_BUFFER_TOO_SMALL로 완료합니다.

최소 기능

"임의 주소 읽기/쓰기", "임의 MSR 접근", "물리 메모리 매핑" 같은 범용 기능을 IOCTL로 노출하지 않습니다. 이런 드라이버는 취약 드라이버 차단 목록(16장)의 단골입니다.

버퍼링 방식

가능하면 METHOD_BUFFERED를 쓰세요. I/O 관리자가 시스템 버퍼로 복사해 주므로 유저 포인터를 직접 다룰 일이 없습니다. METHOD_NEITHER는 프로브와 예외 처리를 모두 직접 해야 합니다(11장).

정보 노출 방지

출력 버퍼에 초기화되지 않은 커널 메모리를 돌려주지 않습니다. 반환 바이트 수(Information)는 실제로 채운 크기만큼만 설정합니다.

정수 오버플로

"개수 × 크기" 계산은 RtlSizeTMult 등 안전한 산술 함수(ntintsafe.h)로 합니다.

테스트와 검증

Driver Verifier

Driver Verifier는 지정한 드라이버의 커널 API 호출을 가로채 규칙 위반을 즉시 버그체크(주로 0xC4)로 드러냅니다. 숨어 있던 버그를 개발 단계에서 강제로 터뜨리는 도구입니다.

C:\> verifier /standard /driver MyDriver.sys
C:\> verifier /querysettings
C:\> verifier /reset          # 검증 해제 (재부팅 후 적용)
검사 항목잡아내는 버그
Special Pool풀 버퍼 경계 넘어 쓰기/읽기, 해제 후 사용
Force IRQL Checking높은 IRQL에서 페이지 가능 메모리 접근 (페이지를 강제로 내보내 확률을 높임)
Pool Tracking언로드 시 해제되지 않은 풀 할당(누수)
I/O Verification잘못된 IRP 처리, 이중 완료, 잘못된 상태 반환
Deadlock Detection락 획득 순서 위반 (잠재적 데드락)
DDI Compliance CheckingAPI 사용 규칙(IRQL, 인자) 위반
Low Resources Simulation할당 실패 경로의 처리 누락
KMDF Verifier도 함께

KMDF 드라이버는 프레임워크 자체의 검증기(WDF Verifier, VerifierOn 레지스트리 값 또는 WDF Verifier Control Application)를 켜면 객체 수명·요청 완료 오류를 더 정확히 보고합니다. WinDbg의 !wdfkd.wdflogdump로 프레임워크 내부 로그(IFR)를 볼 수 있습니다.

정적 분석

Code Analysis

VS의 /analyze. SAL 주석과 역할 타입을 바탕으로 IRQL·NULL·버퍼 크기 오류를 빌드 중에 찾습니다.

CodeQL

Microsoft가 제공하는 드라이버용 쿼리 팩. WHCP(인증) 제출 시 통과가 요구됩니다.

SDV

Static Driver Verifier. 드라이버 모델 규칙(예: 스핀락 획득/해제 쌍)을 모델 검사로 증명하려 시도합니다.

배포 전 체크리스트

릴리스 준비도

    로드, 서명, 배포

    실습

    실습 14-1 · Hello World KMDF를 테스트 VM에 올리기
    1. VS에서 Kernel Mode Driver, Empty (KMDF) 프로젝트를 만들고 위 코드를 넣어 x64 Debug로 빌드합니다.
    2. 테스트 VM에서 테스트 서명 모드를 켜고 재부팅한 뒤, 빌드 산출물(.sys, .inf, .cat)을 복사합니다.
    3. 호스트 WinDbg를 KDNET으로 연결하고 ed nt!Kd_IHVDRIVER_Mask 0xF로 디버그 출력을 켭니다.
    4. 장치 관리자 또는 devcon/pnputil로 설치하고 KmdfHelloWorld: DriverEntry 출력을 확인합니다.
    5. Driver Verifier를 켠 채로 설치·제거를 반복해 보고, 일부러 풀을 해제하지 않는 코드를 넣어 언로드 시 Verifier가 무엇을 보고하는지 관찰합니다.

kd> bu KmdfHelloWorld!DriverEntry
kd> g
Breakpoint 0 hit
KmdfHelloWorld!DriverEntry:
kd> k
kd> !wdfkd.wdfdriverinfo KmdfHelloWorld
kd> !drvobj KmdfHelloWorld 2

    확인 문제

    새로 USB 센서 장치 드라이버를 만든다. 높은 IRQL 처리가 필요 없고 성능 요구도 평범하다. 가장 적절한 선택은?

    1. WDM
    2. KMDF
    3. UMDF v2
    4. 파일 시스템 미니필터
    커널에 있을 이유가 없다면 유저 모드(UMDF)가 우선입니다. 드라이버 크래시가 시스템 크래시로 번지지 않고, 커널 공격 표면도 줄어듭니다.

    DISPATCH_LEVEL에서 실행 중인 DPC 안에서 Paged 풀 버퍼를 읽었다. 테스트에서는 문제가 없었지만 현장에서 간헐적으로 크래시한다. 이유는?

    1. Paged 풀은 DPC에서 접근하면 항상 크래시한다
    2. 테스트 때는 페이지가 우연히 메모리에 있었고, 페이지아웃된 순간 페이지 폴트를 처리할 수 없어 버그체크한다
    3. DPC는 다른 프로세스 문맥이라 주소가 달라진다
    4. Paged 풀은 유저 모드 메모리다
    페이지가 상주해 있으면 폴트가 안 나서 문제가 숨어 있다가, 메모리 압박으로 페이지아웃되면 IRQL_NOT_LESS_OR_EQUAL로 터집니다. Driver Verifier의 Force IRQL Checking이 이런 버그를 확정적으로 드러냅니다.

    Parallel 큐의 EvtIoDeviceControl에서 디바이스 컨텍스트의 카운터를 증가시킨다. 올바른 설명은?

    1. 프레임워크가 자동으로 직렬화하므로 그냥 Ctx->Count++로 충분하다
    2. 콜백이 여러 CPU에서 동시에 실행될 수 있으므로 Interlocked 연산이나 락이 필요하다
    3. Parallel 큐 콜백은 항상 PASSIVE_LEVEL이라 경쟁이 없다
    4. 카운터를 Paged 풀에 두면 해결된다
    Parallel 디스패치는 동시 호출을 허용합니다. 단순 카운터는 InterlockedIncrement, 복합 상태는 스핀락/WDFWAITLOCK 등으로 보호합니다(07장). 또는 Sequential 큐나 SynchronizationScope로 프레임워크에 직렬화를 맡길 수 있습니다.

    드라이버가 프로세스 생성 콜백을 등록한 뒤, 언로드 루틴에서 등록 해제를 빠뜨렸다. 어떤 일이 생기나?

    1. OS가 언로드 시 자동으로 해제하므로 문제없다
    2. 콜백이 더 이상 호출되지 않을 뿐이다
    3. 다음 프로세스 생성 때 언로드된 주소의 코드를 호출해 크래시한다
    4. 드라이버 언로드 자체가 거부된다
    커널은 등록된 함수 포인터를 그대로 호출합니다. 코드가 언로드된 뒤라면 해제된 메모리로 점프하게 됩니다. 등록한 모든 것을 언로드에서 역순으로 해제하는 것이 기본 규칙입니다.

    Secure Boot가 켜진 일반 Windows 11 PC에 새 커널 드라이버를 배포하려면?

    1. 자체 서명 인증서로 서명하면 된다
    2. 사용자에게 testsigning을 켜도록 안내한다
    3. EV 인증서로 서명해 Partner Center에 제출하고 Microsoft 서명(Attestation 또는 WHQL)을 받는다
    4. INF 파일만 있으면 서명 없이 설치된다
    현대 Windows는 새 커널 드라이버에 Microsoft 서명을 요구합니다. 테스트 서명 모드는 개발용 VM 전용이며, Secure Boot 환경에서는 켤 수도 없습니다.

    핵심 요약

    • 모델 선택: UMDF → 클래스 모델 → KMDF → WDM 순으로 검토한다.
    • KMDF는 객체 트리, 큐, 상태 머신으로 WDM의 정형 코드를 대신 처리한다. 큐 디스패치 방식이 곧 동시성 모델이다.
    • 항상 IRQL을 의식하라: DISPATCH 이상에서는 대기 금지, 페이지 가능 메모리 접근 금지.
    • 유저 인터페이스는 공격 표면이다: SDDL로 접근 제한, 길이 검증, 범용 기능 노출 금지.
    • Driver Verifier·Code Analysis·CodeQL·SDV로 검증하고, Microsoft 서명을 받아 배포한다.
