Part II · Chapter 04

프로세스와 스레드

프로세스는 자원을 담는 그릇, 스레드는 실행 단위. 커널이 이 둘을 어떤 구조체로 표현하고, 어떻게 만들고, 어떻게 보호하는지 해부합니다.

핵심⏱ 약 90분선수: 01·02장

학습 목표

  • EPROCESS/KPROCESS, ETHREAD/KTHREAD의 계층 관계와 핵심 필드를 설명하고 WinDbg로 직접 찾아갈 수 있다.
  • 커널 측 구조체와 유저 측 구조체(PEB/TEB)를 구분하고, 각각을 신뢰해도 되는지 판단할 수 있다.
  • CreateProcessW 한 번이 kernelbase → NtCreateUserProcess → csrss → 로더까지 거치는 단계를 순서대로 말할 수 있다.
  • CID/PspCidTable와 ActiveProcessLinks의 관계를 이해하고, 프로세스 열거가 어디에 의존하는지 설명할 수 있다.
  • Job, 최소/Pico 프로세스, 보호 프로세스(PP/PPL), 프로세스 생성 콜백의 역할과 한계를 안다.

프로세스와 스레드의 역할 분담

Windows에서 프로세스는 실행되지 않습니다. 프로세스는 실행에 필요한 자원을 묶는 컨테이너이고, CPU 위에서 실제로 명령을 수행하는 것은 언제나 스레드입니다. 스케줄러(05장)는 프로세스가 아니라 스레드를 고릅니다.

프로세스가 가진 것

가상 주소 공간(페이지 테이블 + VAD 트리), 핸들 테이블, 기본 접근 토큰, 하나 이상의 스레드, 이미지(실행 파일) 매핑, Job 소속, 프로세스 ID, 보호 수준, 완화 정책(mitigation) 설정.

스레드가 가진 것

CPU 레지스터 문맥, 커널 스택과 유저 스택, 스케줄링 상태(우선순위·퀀텀·선호도), 대기 블록, APC 큐, TEB, 스레드 ID, 선택적인 가장(impersonation) 토큰.

같은 프로세스의 스레드들은 주소 공간과 핸들을 공유합니다. 그래서 스레드 전환은 프로세스 전환보다 싸고(CR3를 바꿀 필요가 없음), 반대로 한 스레드의 메모리 손상이 같은 프로세스의 모든 스레드에 영향을 줍니다.

"현재 프로세스"는 두 가지 의미가 있다

커널 코드에서 PsGetCurrentProcess()는 현재 스레드의 ApcState.Process, 즉 지금 매핑된 주소 공간의 프로세스를 돌려줍니다. 드라이버가 KeStackAttachProcess로 다른 프로세스에 붙어(attach) 있으면 이 값은 스레드가 원래 속한 프로세스(PsGetThreadProcess)와 달라집니다. "누가 요청했나"와 "어느 주소 공간을 보고 있나"를 혼동하면 버그가 됩니다.

커널 구조체: EPROCESS와 ETHREAD

01장에서 본 Executive/Kernel 계층 분리는 구조체에도 그대로 나타납니다. Executive 계층(Ps, Ob, Mm, Se)이 쓰는 정보는 EPROCESS/ETHREAD에, Kernel 계층(Ke — 스케줄링·대기·APC)이 쓰는 정보는 그 첫 번째 멤버로 내장된 KPROCESS(필드명 Pcb)/KTHREAD(필드명 Tcb)에 들어 있습니다. 첫 멤버이므로 PEPROCESS와 PKPROCESS는 같은 주소이며 서로 캐스팅해 씁니다.

아래 도식의 각 필드를 클릭하면 의미와 실전에서의 쓰임이 표시됩니다.

오프셋을 하드코딩하지 말 것

EPROCESS와 ETHREAD는 불투명(opaque) 구조체입니다. WDK 헤더에 정의가 없고, 필드 오프셋은 Windows 빌드마다 바뀝니다. 드라이버는 반드시 PsGetProcessId, PsGetThreadId, PsGetProcessCreateTimeQuadPart, PsIsProtectedProcessLight 같은 문서화된 접근자를 써야 합니다. 오프셋을 하드코딩한 드라이버는 다음 업데이트에서 버그체크를 일으키는 단골 원인입니다.

유저 측 구조체: PEB와 TEB

커널 구조체는 커널 주소 공간에 있어 유저 코드가 볼 수 없습니다. 그래서 유저 모드에서 자주 필요한 정보 — 로드된 DLL 목록, 명령줄, 마지막 오류 코드, TLS — 는 커널이 프로세스·스레드 생성 시 유저 주소 공간에 만들어 주는 PEB와 TEB에 들어 있습니다. ntdll과 kernelbase는 시스템 콜 없이 이 블록을 직접 읽고 씁니다.

offsetfieldtype설명
+0x002BeingDebuggedUCHAR디버거가 붙어 있으면 1. IsDebuggerPresent의 실체
+0x010ImageBaseAddressPVOIDEXE가 매핑된 베이스 주소(ASLR 적용 후)
+0x018LdrPPEB_LDR_DATA로드된 모듈 리스트 3종(InLoadOrder / InMemoryOrder / InInitializationOrder)

+0x0bcNtGlobalFlagULONGgflags 설정(힙 검사 등). 디버거로 시작하면 일부 힙 플래그가 켜짐

// 유저 모드: 세그먼트 레지스터로 직접 접근 (x64)
PTEB teb = (PTEB)__readgsqword(0x30);   // NtCurrentTeb()와 동일
PPEB peb = (PPEB)__readgsqword(0x60);   // teb->ProcessEnvironmentBlock
// 32비트(x86) 프로세스에서는 FS 세그먼트: fs:[0x18] = TEB, fs:[0x30] = PEB

// 다른 프로세스의 PEB 주소: 문서화된 경로

NtQueryInformationProcess(hProcess, ProcessBasicInformation, &pbi, sizeof(pbi), NULL);
// pbi.PebBaseAddress → ReadProcessMemory로 읽음

커널 모드에서는 GS 베이스가 TEB가 아니라 KPCR(프로세서 제어 영역)을 가리킵니다. 시스템 콜 진입 시 swapgs로 두 값을 맞바꾸는 이유입니다(02장).

PEB/TEB는 "자기 신고"다

PEB와 TEB는 프로세스 자신이 쓸 수 있는 메모리입니다. 명령줄(ProcessParameters.CommandLine), 모듈 리스트(Ldr), BeingDebugged는 프로세스 코드가 언제든 바꿀 수 있습니다. 따라서 보안·포렌식 도구는 이 값들을 참고 정보로만 써야 하고, 권위 있는 정보는 커널 측(예: 프로세스 생성 콜백이 받는 PS_CREATE_NOTIFY_INFO.CommandLine, 이미지 섹션, VAD)에서 얻어야 합니다. 같은 이유로 커널 코드가 PEB를 읽을 때는 일반 유저 포인터처럼 __try/ProbeForRead로 보호해야 합니다.

CID와 PspCidTable, 프로세스 리스트

PID와 TID는 별도의 카운터가 아니라 하나의 커널 핸들 테이블 nt!PspCidTable에서 할당됩니다. 프로세스나 스레드가 생성될 때 ExCreateHandle로 이 테이블에 엔트리를 만들고, 그 핸들 값이 곧 ID가 됩니다. 일반 프로세스 핸들 테이블과 달리 이 테이블의 엔트리는 객체 헤더가 아닌 객체 본체를 가리킵니다.

  • ID → 객체: PsLookupProcessByProcessId/PsLookupThreadByThreadId가 이 테이블을 조회하고 참조 카운트를 올려 반환합니다. 사용 후 반드시 ObDereferenceObject.
  • 전체 열거: 반면 프로세스 목록은 PsActiveProcessHead에서 시작하는 ActiveProcessLinks 리스트로 얻습니다. 같은 사실(살아 있는 프로세스 집합)이 두 개의 독립된 자료구조에 기록되는 셈입니다.
  • PID 0과 4: PID 0은 Idle "프로세스"(CPU별 Idle 스레드의 컨테이너), PID 4는 System 프로세스입니다.
CID 테이블 · 프로세스 리스트 시뮬레이터
프로세스 엔트리 (P)스레드 엔트리 (T)주황 실선 = Flink · 회색 점선 = Blink슬롯 값 = 인덱스 × 4

시뮬레이터는 단순화를 위해 "가장 낮은 빈 슬롯"을 할당합니다. 실제 핸들 테이블은 프리 리스트 기반이라 순서가 다르지만, ID가 빠르게 재사용된다는 점과 PID·TID가 한 공간을 공유한다는 점은 동일합니다. 두 열거 결과를 비교하는 "교차 검증(cross-view)"은 메모리 포렌식 도구(예: Volatility의 pslist와 psscan 비교)가 일관성 점검에 쓰는 기본 기법입니다.

CreateProcess 내부 흐름

CreateProcessW는 Windows에서 가장 복잡한 API 중 하나입니다. Windows Vista 이후 핵심 작업은 단일 시스템 콜 NtCreateUserProcess가 커널 안에서 한 번에 처리하고, 유저 모드의 kernelbase는 인자 준비와 Windows 서브시스템(csrss) 등록을 맡습니다. 단계별로 따라가 봅시다.

"부모"와 "생성자"는 다를 수 있다

PROC_THREAD_ATTRIBUTE_PARENT_PROCESS 속성을 쓰면 다른 프로세스를 부모로 지정할 수 있습니다(UAC의 AppInfo 서비스가 상승된 프로세스를 사용자의 explorer 아래에 두는 방식). 그래서 InheritedFromUniqueProcessId(부모 PID)만으로 "누가 실행했는가"를 단정할 수 없습니다. 프로세스 생성 콜백의 PS_CREATE_NOTIFY_INFO는 ParentProcessId와 별도로 실제 생성 스레드의 CreatingThreadId를 제공하므로, 보안 제품은 둘을 함께 기록합니다.

DllMain에서 하면 안 되는 일

8단계의 DllMain은 로더 락을 잡은 채 호출됩니다. 여기서 다른 DLL을 로드하거나, 스레드를 만들고 기다리거나, COM을 초기화하면 교착 상태가 생기기 쉽습니다. 프로세스 시작 시 멈추는 앱을 덤프로 보면 콜스택에 LdrpInitializeProcess와 로더 락 대기가 함께 보이는 경우가 많습니다.

스레드 생명주기

스레드는 CreateThread(또는 다른 프로세스 대상의 CreateRemoteThread) → NtCreateThreadEx로 만들어집니다. 생성 경로의 커널 부분은 프로세스의 초기 스레드와 같은 함수(PspAllocateThread/PspInsertThread)를 씁니다. 종료는 생성보다 까다롭습니다. 스레드가 커널에 걸어 둔 자원(대기 중 I/O, APC, 참조)을 모두 정리해야 하기 때문입니다.

TerminateThread는 최후의 수단

강제 종료된 스레드는 자신이 잡은 크리티컬 섹션·힙 락·로더 락을 풀지 못할 수 있습니다. 그 결과 같은 프로세스의 다른 스레드가 영원히 멈추는 장애가 흔합니다. 스레드를 멈추려면 이벤트 등으로 협조적 종료를 설계하세요.

Job 객체

Job은 여러 프로세스를 하나의 단위로 묶어 한도(limit)와 정책을 적용하는 커널 객체입니다. 프로세스가 Job에 들어가면 그 자식 프로세스도 기본적으로 같은 Job에 들어갑니다. Windows 8부터 Job은 중첩될 수 있어, 한 프로세스가 여러 Job의 계층에 동시에 속할 수 있습니다(제한은 가장 엄격한 쪽이 적용).

자원 한도

프로세스/Job 전체 커밋 메모리, 활성 프로세스 수, CPU 시간, CPU 사용률 상한(CPU rate control), I/O·네트워크 대역폭.

보안·UI 제한

다른 데스크톱 핸들 사용, 클립보드, 시스템 설정 변경 등 USER 객체 접근 제한. 브라우저 샌드박스의 구성 요소로 쓰입니다.

수명 관리

JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE: 마지막 Job 핸들이 닫히면 Job 안의 모든 프로세스 종료. 자식 프로세스 누수 방지의 정석.

HANDLE job = CreateJobObjectW(NULL, NULL);

JOBOBJECT_EXTENDED_LIMIT_INFORMATION li = { 0 };
li.BasicLimitInformation.LimitFlags =
      JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE      // 핸들 닫히면 전부 종료
    | JOB_OBJECT_LIMIT_PROCESS_MEMORY         // 프로세스당 커밋 한도
    | JOB_OBJECT_LIMIT_ACTIVE_PROCESS;        // 동시 프로세스 수
li.ProcessMemoryLimit = 512ull * 1024 * 1024;
li.BasicLimitInformation.ActiveProcessLimit = 4;
SetInformationJobObject(job, JobObjectExtendedLimitInformation, &li, sizeof(li));

// 경쟁 없이 넣으려면: 일시 정지 상태로 만들고 → Job에 넣고 → 재개
CreateProcessW(app, cmd, NULL, NULL, FALSE, CREATE_SUSPENDED, NULL, NULL, &si, &pi);
AssignProcessToJobObject(job, pi.hProcess);
ResumeThread(pi.hThread);
사일로(Silo)와 컨테이너

Windows 컨테이너는 Job을 확장한 사일로 위에 구현됩니다. 서버 사일로는 자체 객체 이름 공간 루트, 레지스트리 뷰, 네트워크 구성을 가져 사실상 "가벼운 별도 OS 인스턴스"처럼 동작합니다. 커널 코드에서 PsGetCurrentServerSilo 같은 API가 보이면 이 메커니즘입니다. Job 알림(한도 초과, 프로세스 종료)은 I/O 완료 포트로 받을 수 있습니다(JobObjectAssociateCompletionPortInformation).

최소 프로세스와 Pico 프로세스

최소(Minimal) 프로세스

주소 공간에 ntdll·PEB·TEB를 만들지 않는 "빈 껍데기" 프로세스입니다. 유저 모드 코드를 실행하지 않고, 커널이 메모리 컨테이너나 시스템 스레드 묶음으로 씁니다.

예: Registry(레지스트리 하이브 매핑), Memory Compression(압축된 페이지 저장소), VBS 환경의 Secure System. 작업 관리자에는 보이지만 모듈 목록이 비어 있습니다.

Pico 프로세스

최소 프로세스에 Pico 공급자(provider) 드라이버를 결합한 형태입니다. 이 프로세스의 시스템 콜·예외·종료 등을 NT 대신 공급자가 처리합니다.

대표 사례는 WSL 1: lxcore.sys가 공급자로서 리눅스 시스템 콜을 NT 기능으로 번역합니다. 공급자 등록(PsRegisterPicoProvider)은 부팅 초기, Microsoft 서명 드라이버로 제한됩니다. WSL 2는 경량 VM을 쓰므로 Pico 프로세스와 무관합니다.

System 프로세스(PID 4)도 유저 모드 부분이 없는 특수 프로세스입니다. 커널 드라이버가 PsCreateSystemThread로 만든 스레드(프로세스 인자 NULL)는 System 프로세스에 속하며, 이 스레드들은 시스템 주소 공간만 사용합니다.

보호 프로세스 (PP / PPL)

일반적으로 관리자(SeDebugPrivilege)는 어떤 프로세스든 열어 메모리를 읽고 쓸 수 있습니다. 보호 프로세스는 이 원칙의 예외입니다. Vista에서 DRM(보호된 미디어 경로)용으로 도입된 PP(Protected Process)를 Windows 8.1이 PPL(Protected Process Light)로 확장해, 안티멀웨어 서비스·LSA(lsass.exe, RunAsPPL 구성 시)·핵심 시스템 프로세스를 보호합니다.

  • 비보호 프로세스는 보호 프로세스를 제한된 접근 권한(예: PROCESS_QUERY_LIMITED_INFORMATION)으로만 열 수 있습니다. PROCESS_VM_READ/PROCESS_VM_WRITE, 스레드 생성, 디버거 연결이 거부됩니다.
  • 보호 프로세스끼리는 Type과 Signer의 우위(dominance)로 판단합니다. PP는 PPL보다 우위이며, Signer 간 우위는 커널 내부 테이블로 결정됩니다.
  • 보호 프로세스가 로드하는 DLL도 해당 서명 수준을 만족해야 합니다(SignatureLevel/SectionSignatureLevel). 그래서 일반 DLL 주입이 실패합니다.
  • 한계: 보호는 커널이 강제하는 정책입니다. 커널 코드(드라이버)는 이 검사 밖에 있으므로, 취약한 서명 드라이버가 로드되면 보호가 무력화될 수 있습니다. 취약 드라이버 차단 목록과 HVCI가 이를 보완합니다(16장).
PS_PROTECTION 디코더
예시 값:

흔히 관찰되는 값: System = 0x72(WinSystem, PP), csrss·smss 등 핵심 시스템 프로세스 = 0x61(WinTcb, PPL), RunAsPPL이 켜진 lsass = 0x41(Lsa, PPL), Microsoft Defender의 MsMpEng = 0x31(Antimalware, PPL). 구성과 버전에 따라 다를 수 있으니 dt nt!_EPROCESS <addr> Protection으로 확인하세요.

프로세스·스레드·이미지 콜백

커널은 드라이버가 프로세스 활동을 관찰할 수 있도록 문서화된 콜백을 제공합니다. 보안 제품(EDR), 샌드박스, 프로파일러가 모두 이 위에 서 있습니다.

VOID OnProcessNotify(_Inout_ PEPROCESS Process, _In_ HANDLE ProcessId,
                     _Inout_opt_ PPS_CREATE_NOTIFY_INFO Info)
{
    UNREFERENCED_PARAMETER(Process);
    if (Info) {                                  // 생성 (PASSIVE_LEVEL, 생성하는 스레드 문맥)
        DbgPrint("create pid=%p parent=%p creator=%p:%p %wZ\n",
                 ProcessId, Info->ParentProcessId,
                 Info->CreatingThreadId.UniqueProcess,
                 Info->CreatingThreadId.UniqueThread,
                 Info->ImageFileName);           // FileOpenNameAvailable이 FALSE면 NULL일 수 있음
        // 정책상 차단하려면: Info->CreationStatus = STATUS_ACCESS_DENIED;
    } else {                                     // 종료 (종료하는 프로세스의 마지막 스레드 문맥)
        DbgPrint("exit pid=%p\n", ProcessId);
    }
}

NTSTATUS DriverEntry(PDRIVER_OBJECT DriverObject, PUNICODE_STRING RegistryPath)
{
    UNREFERENCED_PARAMETER(RegistryPath);
    DriverObject->DriverUnload = DriverUnload;   // Unload에서 반드시 Remove=TRUE로 해제
    // /INTEGRITYCHECK 링커 옵션 없이 빌드하면 STATUS_ACCESS_DENIED
    return PsSetCreateProcessNotifyRoutineEx(OnProcessNotify, FALSE);
}
콜백 작성 규칙

콜백은 프로세스 생성 경로의 동기적 일부입니다. 여기서 오래 블록하면 시스템 전체의 프로세스 생성이 느려지고, 유저 모드 서비스의 응답을 기다리다 그 서비스가 프로세스를 만들려 하면 교착 상태가 됩니다. 등록 슬롯은 시스템 전체에서 한정되어 있으며, 언로드 시 콜백을 해제하지 않으면 해제된 코드로 호출이 들어가 버그체크가 발생합니다.

실습: WinDbg로 프로세스와 스레드 해부

실습 4-1 · 프로세스 구조체 따라가기

가상 머신에서 메모장을 실행한 뒤 로컬 커널 디버깅(또는 KDNET) 세션에서 아래 명령을 차례로 실행합니다. 주소는 환경마다 다르므로 출력에 나온 값을 다음 명령에 넣으세요.

lkd> !peb
lkd> dx @$cursession.Processes.Where(p => p.Name == "notepad.exe").First().Threads
  1. dt nt!_EPROCESS(주소 없이)로 전체 레이아웃을 출력하고, Pcb가 +0x000인지 확인하세요.
  2. !process 0 0으로 smss → csrss/wininit → services → svchost의 ParentCid 체인을 추적해 보세요.
  3. notepad 스레드의 !thread 출력에서 Win32 Start Address와 Start Address(RtlUserThreadStart)를 구분해 보세요.
  4. !process 0 0 lsass.exe로 주소를 얻고 dt nt!_EPROCESS <addr> Protection 값을 위 디코더에 넣어 해석하세요(RunAsPPL 설정에 따라 다름).
  5. PID와 TID를 여러 개 적어 보고, 모두 4의 배수이며 서로 겹치지 않는지 확인하세요.
dx와 데이터 모델

최신 WinDbg의 dx는 프로세스·스레드를 LINQ 스타일로 질의할 수 있습니다. 예: dx -g @$cursession.Processes.Select(p => new { Name = p.Name, Id = p.Id, Threads = p.Threads.Count() }). 오프셋을 몰라도 구조화된 정보를 얻을 수 있어 스크립트화에 유리합니다.

확인 문제

PEPROCESS 포인터를 PKPROCESS로 캐스팅해 써도 되는 이유는?

  1. 두 구조체가 완전히 같은 정의이기 때문
  2. KPROCESS가 EPROCESS의 첫 번째 멤버(Pcb, +0x000)로 내장되어 있기 때문
  3. KPROCESS가 EPROCESS를 포인터로 가리키기 때문
  4. 캐스팅하면 커널이 자동으로 변환해 주기 때문
Executive 구조체는 Kernel 구조체를 첫 멤버로 포함합니다. 따라서 주소가 같고, Ke 계층은 KPROCESS 부분만 알면 됩니다. 두 구조체는 정의가 다르며(EPROCESS가 훨씬 큼), 포인터로 연결된 관계도 아닙니다.

PID와 TID에 대한 설명으로 옳은 것은?

  1. PID와 TID는 별도 카운터에서 1씩 증가하며 할당된다
  2. 한 번 쓰인 PID는 재부팅 전까지 재사용되지 않는다
  3. 둘 다 PspCidTable 핸들 테이블에서 할당되므로 동시에 존재하는 PID와 TID는 겹치지 않는다
  4. TID는 프로세스 안에서만 유일하다
PID/TID는 하나의 커널 핸들 테이블의 핸들 값이라 4의 배수이고 시스템 전역에서 유일합니다. 해제되면 곧 재사용되므로 PID만 저장했다가 나중에 다시 여는 패턴은 위험합니다.

새 프로세스의 초기 스레드가 유저 모드에서 가장 먼저 실행하는 코드는?

  1. EXE의 main
  2. EXE의 PE 진입점(AddressOfEntryPoint)
  3. kernel32의 BaseThreadInitThunk
  4. ntdll의 LdrInitializeThunk
모든 유저 스레드는 LdrInitializeThunk로 시작합니다. 첫 스레드라면 여기서 프로세스 초기화(DLL 로드, DllMain)가 이뤄지고, 그 뒤 RtlUserThreadStart → BaseThreadInitThunk → 진입점 → main 순으로 실행됩니다.

보안 도구가 프로세스의 명령줄을 판단 근거로 삼을 때 가장 신뢰할 수 있는 출처는?

  1. 대상 프로세스 PEB의 ProcessParameters.CommandLine
  2. 프로세스 생성 콜백이 받는 PS_CREATE_NOTIFY_INFO.CommandLine
  3. 대상 TEB의 ClientId
  4. EPROCESS.ImageFileName
PEB는 프로세스 자신이 수정할 수 있는 유저 메모리입니다. 생성 콜백은 프로세스 코드가 실행되기 전에 커널이 전달하는 값이라 신뢰도가 높습니다. ImageFileName은 15바이트로 잘린 이름일 뿐 명령줄이 아닙니다.

관리자 권한 + SeDebugPrivilege를 가진 일반 프로세스가 PPL인 MsMpEng.exe에 PROCESS_VM_READ로 OpenProcess를 호출하면?

  1. SeDebugPrivilege가 있으므로 성공한다
  2. 보호 프로세스 검사에 걸려 접근 거부된다 (제한된 권한만 허용)
  3. 성공하지만 읽기 결과가 0으로 채워진다
  4. 시스템이 버그체크한다
보호 수준 검사는 DACL·특권 검사와 별도로 적용되며, 비보호 호출자에게는 PROCESS_QUERY_LIMITED_INFORMATION 같은 제한된 권한만 허용됩니다. 특권으로 우회할 수 없다는 것이 PP/PPL의 핵심입니다.

모든 스레드가 종료된 프로세스가 작업 관리자 목록에서는 사라졌는데 핸들 누수 진단 도구에는 여전히 보입니다. 가장 그럴듯한 설명은?

  1. 프로세스가 숨어서 실행 중이다
  2. PspCidTable이 손상되었다
  3. 다른 프로세스가 그 프로세스 핸들을 닫지 않아 EPROCESS 객체가 참조로 유지되고 있다
  4. 최소 프로세스로 전환되었다
종료된 프로세스는 실행되지 않지만, 핸들·참조가 남아 있는 동안 객체는 삭제되지 않습니다(종료 코드 조회 등을 위해). CloseHandle을 빠뜨린 프로그램이 이런 "좀비" 프로세스 객체를 쌓아 커널 메모리를 소모합니다.

핵심 요약

  • 프로세스는 자원 컨테이너, 스레드는 실행 단위다. 스케줄러는 스레드만 본다.
  • EPROCESS/ETHREAD(Executive)는 첫 멤버로 KPROCESS/KTHREAD(Kernel)를 내장한다. 오프셋은 빌드마다 다르므로 문서화된 접근자를 쓴다.
  • PEB/TEB는 유저 모드에 있는 편의용 블록이며, 프로세스가 수정할 수 있으므로 보안 판단 근거로 신뢰하지 않는다.
  • PID/TID는 PspCidTable의 핸들 값이고, 프로세스 목록은 ActiveProcessLinks 리스트다. 같은 사실이 두 자료구조에 기록된다.
  • CreateProcessW = kernelbase 준비 → NtCreateUserProcess(이미지 섹션, EPROCESS, 초기 스레드, 콜백) → csrss 통지 → 재개 → LdrInitializeThunk → main.
  • Job은 프로세스 묶음에 한도를 적용하고, 최소/Pico 프로세스는 유저 모드 런타임이 없는 특수 프로세스이며, PP/PPL은 관리자도 넘을 수 없는 접근 제한을 제공한다.
