Part IV · Chapter 13

보안 모델

"누가(토큰) 무엇에(보안 설명자) 어떤 접근을(접근 마스크) 원하는가." Windows 보안의 모든 결정은 이 세 가지를 비교하는 하나의 알고리즘으로 귀결됩니다.

심화⏱ 약 100분선수: 10 객체 관리자와 핸들

학습 목표

  • 보안 참조 모니터(SRM)와 LSASS의 역할 분담, 로그온 시 토큰이 만들어지는 흐름을 설명할 수 있다.
  • 액세스 토큰의 구성(사용자/그룹 SID, 그룹 속성, 특권, 무결성 수준, 기본/가장 토큰)과 SID의 구조를 읽을 수 있다.
  • 보안 설명자(소유자·DACL·SACL)와 ACE 종류를 이해하고, SeAccessCheck의 판정을 손으로 재현할 수 있다.
  • 무결성 수준, UAC 분리 토큰, 가장 수준, PPL, AppContainer가 기본 DACL 검사 위에 어떤 추가 경계를 만드는지 구분할 수 있다.

세 가지 질문

10장에서 보았듯이 객체를 이름으로 열면 객체 관리자가 접근 검사를 요청합니다. 이 검사는 언제나 같은 세 재료를 씁니다.

누가 — 액세스 토큰

요청하는 스레드(가장 중이면 가장 토큰, 아니면 프로세스의 기본 토큰)가 지닌 신원: 사용자 SID, 그룹 SID들, 특권, 무결성 수준.

무엇에 — 보안 설명자

객체에 붙은 보안 정보: 소유자, DACL(누구에게 무엇을 허용/거부), SACL(감사·무결성 라벨).

어떻게 — 접근 마스크

요청하는 권리의 비트 집합(DesiredAccess). 예: 파일 읽기 + 쓰기 = FILE_READ_DATA | FILE_WRITE_DATA.

검사 결과로 얻는 것은 "허용된 접근 마스크(GrantedAccess)"이며, 이것이 핸들 테이블 엔트리에 기록됩니다(10장). 이후 그 핸들로 하는 작업은 다시 DACL을 보지 않고 엔트리의 GrantedAccess만 확인합니다. 즉 접근 검사는 열 때 한 번 일어납니다.

전문가 관점 — 열 때 한 번

핸들을 얻은 뒤 객체의 DACL을 바꿔도 이미 열린 핸들의 권한은 회수되지 않습니다. 그래서 침해 대응에서는 "권한을 고쳤다"로 끝내지 말고 이미 열린 핸들(handle.exe, !handle)을 확인해야 합니다. 반대로 개발자는 필요한 최소 접근만 요청해야 합니다 — PROCESS_ALL_ACCESS 습관은 불필요하게 실패하거나, 성공했을 때 과도한 권한 핸들을 남깁니다.

SRM과 LSASS의 역할 분담

보안 기능은 커널과 유저 모드에 나뉘어 있습니다. 정책과 인증은 복잡하고 자주 바뀌므로 유저 모드의 lsass.exe가 맡고, 매 접근마다 빠르고 우회 불가능해야 하는 판정은 커널의 보안 참조 모니터(SRM, Se*)가 맡습니다. 각 구성요소를 클릭해 보세요.

액세스 토큰

토큰은 "이 스레드/프로세스가 누구인가"를 담은 커널 객체입니다. 로그온 시 한 번 만들어지고, 그 세션에서 생성되는 프로세스들은 사본을 상속합니다. 그래서 그룹 멤버십을 바꿔도 다시 로그온하기 전까지 반영되지 않습니다 — 관리자가 자주 마주치는 현상의 원인입니다.

다음 특권은 사실상 SYSTEM과 같은 효과를 냅니다. 계정 권한 할당 정책에서 최소화하세요: SeDebugPrivilege(임의 프로세스 열기), SeImpersonatePrivilege(클라이언트 가장), SeAssignPrimaryTokenPrivilege, SeTcbPrivilege, SeLoadDriverPrivilege(드라이버 로드), SeBackupPrivilege/SeRestorePrivilege(DACL 우회 읽기/쓰기), SeTakeOwnershipPrivilege, SeCreateTokenPrivilege. 서비스는 RequiredPrivileges 설정으로 필요한 특권만 남길 수 있습니다.

SID의 구조

SID(Security Identifier)는 보안 주체의 영구 식별자입니다. 문자열 형식 S-R-I-S1-S2-…-Sn은 리비전(항상 1), 식별자 기관(6바이트, 예: 5 = NT Authority), 그리고 가변 개수의 32비트 하위 기관으로 이루어지며, 마지막 하위 기관이 보통 RID(상대 식별자)입니다. 이름(alice)은 바뀌어도 SID는 바뀌지 않으므로 ACL은 언제나 SID를 저장합니다.

SID 디코더

보안 설명자와 ACE

보안 설명자(SECURITY_DESCRIPTOR)는 객체에 붙는 보안 정보입니다. 커널 객체에서는 OBJECT_HEADER.SecurityDescriptor가 가리키며, 메모리에는 포인터 대신 오프셋을 쓰는 자기 상대(self-relative) 형식으로 저장됩니다. 각 부분을 클릭해 보세요.

접근 마스크(ACCESS_MASK)

32비트 접근 마스크는 영역이 나뉘어 있습니다. 하위 16비트는 타입별 권리(파일이면 FILE_READ_DATA…, 프로세스면 PROCESS_VM_READ…), 16~20비트는 모든 타입에 공통인 표준 권리, 상위 4비트는 제네릭 권리입니다. 제네릭 권리는 검사 전에 객체 타입의 GENERIC_MAPPING으로 구체 권리로 변환됩니다. 비트를 클릭해 의미를 확인하세요.

접근 검사 알고리즘

SeAccessCheck(내부 SepAccessCheck)의 핵심을 순서대로 정리하면 다음과 같습니다(예외적 세부사항은 생략).

  1. 제네릭 매핑: GENERIC_READ 등을 타입별 구체 권리로 변환.
  2. 필수 무결성 검사: 토큰 무결성 < 객체 라벨이면 정책(No-Write-Up 등)에 따라 해당 권리 차단. 보호 프로세스 신뢰 라벨 검사도 이 단계 근처에서 수행.
  3. 특권으로 부여되는 권리: ACCESS_SYSTEM_SECURITY(SeSecurityPrivilege), WRITE_OWNER(SeTakeOwnershipPrivilege) 등은 DACL 평가 전에 부여.
  4. 소유자 암묵 권리: 토큰이 소유자면 READ_CONTROL | WRITE_DAC(OWNER RIGHTS ACE가 없을 때).
  5. DACL 평가: NULL DACL이면 전부 허용. 아니면 ACE를 순서대로 보며 — INHERIT_ONLY는 건너뛰고, SID가 토큰에 (활성으로, 또는 거부 ACE에 한해 deny-only로) 있을 때만 적용. 거부 ACE가 아직 허용 안 된 요청 비트를 건드리면 즉시 거부, 허용 ACE는 비트를 누적. 요청이 모두 허용되면 즉시 종료.
  6. 종료: ACE를 다 봤는데 남은 비트가 있으면 거부(암묵적 거부). 제한 토큰·AppContainer 토큰은 별도 SID 집합으로 두 번째 검사를 통과해야 합니다.

개발자 관점 — 직접 검사가 필요할 때

서버가 클라이언트 대신 자원에 접근할 때는 두 방법이 있습니다. (1) 클라이언트를 가장한 채 실제 객체를 열어 커널이 검사하게 하거나, (2) 자체 자원(DB 레코드 등)에 SD를 붙여 AccessCheck(유저 모드) / SeAccessCheck(커널)를 직접 호출합니다. 드라이버가 디바이스 열기를 제한하려면 IoCreateDeviceSecure와 SDDL(D:P(A;;GA;;;SY)(A;;GA;;;BA) 등)을 쓰는 것이 정석입니다 — 기본 DACL에 맡기면 의도보다 넓게 열릴 수 있습니다.

무결성 수준과 필수 무결성 정책

DACL은 "누가"를 따지지만, 같은 사용자의 프로세스라도 신뢰도가 다를 수 있습니다(브라우저 렌더러 vs 메모장). 필수 무결성 제어(MIC)는 토큰과 객체에 무결성 라벨을 붙여 DACL보다 먼저 검사합니다.

수준SID대표 주체

  • 정책: NO_WRITE_UP(기본) — 낮은 수준은 쓰기 계열 권리 차단. NO_READ_UP — 읽기 차단. NO_EXECUTE_UP — 실행 차단.
  • 프로세스·스레드 객체는 기본적으로 No-Write-Up과 No-Read-Up이 함께 적용되어, 낮은 무결성 프로세스가 높은 무결성 프로세스의 메모리를 읽을 수 없습니다.
  • 창 메시지도 무결성으로 제한됩니다(UIPI): 낮은 수준 프로세스는 높은 수준 창에 대부분의 메시지를 보낼 수 없습니다.
  • MIC는 DACL보다 먼저, DACL과 독립적으로 적용됩니다. DACL이 Everyone에게 전체 허용이어도 Low 프로세스는 Medium 파일에 쓸 수 없습니다.

UAC와 분리 토큰

관리자 그룹 사용자가 로그온하면(UAC 활성 시) LSA는 두 개의 토큰을 만들어 서로 연결합니다. 평소에는 권한을 뺀 필터링된 토큰으로 일하다가, 필요할 때만 상승된 토큰을 씁니다.

필터링된 토큰 (Medium)

Administrators 그룹이 deny-only로 바뀌고(허용 ACE에 매칭 안 됨, 거부 ACE에는 매칭), 대부분의 강력한 특권이 제거됩니다(SeChangeNotifyPrivilege, SeShutdownPrivilege 등 일부만 남음). 무결성 Medium.

상승된 토큰 (High)

Administrators 그룹이 활성, 관리자 특권 전부 보유(대부분 비활성 상태로 존재). 무결성 High. TokenLinkedToken으로 필터링된 토큰과 서로 참조합니다.

가장(Impersonation)

서버 스레드가 일시적으로 클라이언트의 신원으로 동작하는 기능입니다. 스레드에 가장 토큰이 붙으면, 그 스레드의 접근 검사는 프로세스 토큰이 아닌 가장 토큰으로 이루어집니다. 명명된 파이프(ImpersonateNamedPipeClient), RPC(RpcImpersonateClient), ALPC 등에서 쓰이며, 클라이언트는 가장 수준(SQOS)으로 서버에 허용할 범위를 정합니다.

가장 수준서버가 할 수 있는 것
SecurityAnonymous클라이언트 신원을 알 수 없음
SecurityIdentification신원·그룹 조회와 AccessCheck 가능, 그 신원으로 객체를 열 수는 없음
SecurityImpersonation로컬 시스템에서 클라이언트로서 객체 접근 가능
SecurityDelegation원격 시스템으로도 신원 전달(Kerberos 위임)
방어 관점 — SeImpersonatePrivilege

Impersonation 수준 이상으로 다른 사용자를 가장하려면 서버가 SeImpersonatePrivilege를 가져야 합니다(없으면 Identification 수준으로 낮아짐). 서비스 계정(LocalService, NetworkService, IIS 앱 풀 등)은 이 특권을 기본으로 가지므로, 서비스가 침해되면 특권 있는 클라이언트를 가장해 SYSTEM으로 상승할 위험이 있습니다. 대응: 서비스별 가상 계정·서비스 SID, RequiredPrivileges로 불필요한 특권 제거, 클라이언트 측에서는 신뢰하지 않는 서버에 연결할 때 SQOS를 SecurityIdentification으로 지정(SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION).

보호 프로세스(PP/PPL)와 서명자 수준

관리자라도(심지어 SeDebugPrivilege가 있어도) 열 수 없는 프로세스가 있습니다. 보호 프로세스는 DACL과 별개로 커널이 EPROCESS.Protection(PS_PROTECTION: 유형 + 서명자)을 비교해 접근을 제한합니다.

보호 유형

Protected(PP) > Protected Light(PPL) > 없음. 원래 DRM 미디어 경로용이던 PP를 일반화한 것이 PPL입니다. 이미지가 해당 서명자 수준을 증명하는 서명을 가져야 그 보호로 시작할 수 있고, 로드하는 DLL도 같은 수준 이상의 서명이 요구됩니다.

서명자 수준(Signer)

Authenticode · CodeGen · Antimalware · Lsa · Windows · WinTcb · WinSystem · App. 보호 프로세스는 자신이 지배(dominate)하는 — 같은 유형이면 서명자 수준이 같거나 낮은 — 보호 프로세스만 완전히 열 수 있습니다.

  • 보호되지 않은 프로세스는 보호 프로세스에 대해 PROCESS_QUERY_LIMITED_INFORMATION 같은 제한된 권리만 얻습니다(정확한 허용 집합은 유형·서명자에 따라 다름). PROCESS_VM_READ, 스레드 주입 등은 불가.
  • LSA 보호(RunAsPPL): LSASS를 PPL(Lsa 서명자)로 실행해 자격 증명 덤프 도구의 메모리 읽기를 차단합니다.
  • Antimalware PPL: ELAM 드라이버로 등록된 백신 서비스는 PPL-Antimalware로 실행되어 악성코드가 종료·주입하기 어렵습니다.
  • 객체 수준에서는 SACL의 신뢰 라벨(SYSTEM_PROCESS_TRUST_LABEL_ACE, S-1-19-…)로 "일정 보호 수준 이상만 쓰기" 같은 제한을 걸 수 있습니다.
  • 한계: 커널 코드는 이 검사를 받지 않습니다. 취약한 서명 드라이버를 로드해 보호를 해제하는 공격(BYOVD)에는 드라이버 차단 목록·HVCI로 대응합니다(16장).

AppContainer와 기능(Capability) SID

AppContainer는 UWP 앱, 브라우저 샌드박스 등에 쓰이는 Windows의 기본 샌드박스입니다. AppContainer 토큰은 다음 특징을 가집니다.

  • 패키지 SID(S-1-15-2-…)와 앱에 선언된 기능 SID(S-1-15-3-…, 예: internetClient, picturesLibrary)를 가짐.
  • 무결성 수준 Low.
  • 이중 검사: 일반 DACL 검사(사용자·그룹 SID)와 별도로, DACL이 해당 패키지 SID, ALL APPLICATION PACKAGES(S-1-15-2-1), 또는 보유 기능 SID 중 하나에 명시적으로 허용해야 합니다. 두 검사를 모두 통과해야 접근이 허용됩니다. 즉 사용자 파일이 사용자에게 열려 있어도 AppContainer는 기본적으로 접근할 수 없습니다.
  • LPAC(Less Privileged AppContainer): ALL APPLICATION PACKAGES 허용에도 매칭되지 않고, ALL RESTRICTED APPLICATION PACKAGES(S-1-15-2-2) 또는 명시적 기능만 인정되는 더 엄격한 형태.
  • 이름 있는 객체는 \Sessions\N\AppContainerNamedObjects\<패키지 SID> 아래로 격리됩니다(10장의 네임스페이스).
개발자 관점 — 샌드박스 프로세스 만들기

CreateAppContainerProfile로 프로필(SID)을 만들고, SECURITY_CAPABILITIES를 PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES 속성으로 CreateProcess에 넘기면 AppContainer 프로세스가 생성됩니다. 접근을 허락할 디렉터리에만 패키지 SID 허용 ACE를 추가하세요. 문서 변환기·파서처럼 신뢰할 수 없는 입력을 다루는 구성요소를 분리하는 실용적인 방법입니다.

실습: 토큰과 보안 설명자 관찰

실습 13-1 · 유저 모드 도구

whoami /all로 자신의 토큰(그룹 속성·특권·무결성)을 보고, 관리자 권한 명령 프롬프트에서 다시 실행해 차이를 비교하세요. Sysinternals AccessChk와 Process Explorer(프로세스 속성 → Security 탭)로 객체의 실효 권한과 토큰을 확인할 수 있습니다.

# 토큰: 그룹(Attributes 열에서 "Group used for deny only" 확인), 특권, 무결성
PS> whoami /groups /priv

# 파일 SD를 SDDL로
PS> (Get-Acl C:\Windows\System32\notepad.exe).Sddl

# 무결성 라벨 확인·설정 (낮은 무결성 폴더 만들기)
PS> icacls C:\Temp\lowdir /setintegritylevel low

# 특정 사용자의 실효 권한 / 쓰기 가능한 서비스 찾기 (AccessChk)
PS> accesschk.exe -accepteula -uwcqv "Authenticated Users" *
$$ lsass 프로세스 찾기 → 출력의 Token 필드 주소 확인
lkd> !process 0 1 lsass.exe

$$ 토큰 내용: 사용자/그룹 SID와 속성, 특권, 무결성, 가장 수준
lkd> !token <토큰 주소>

$$ 현재 스레드의 실효 토큰
lkd> !token

$$ 객체의 보안 설명자 → OBJECT_HEADER.SecurityDescriptor (EX_FAST_REF 하위 비트 마스킹 필요)
lkd> !object <객체 주소>
lkd> !sd <SD 주소> 1

$$ 보호 수준
lkd> dt nt!_EPROCESS <EPROCESS 주소> Protection
lkd> dt nt!_PS_PROTECTION
  1. whoami /groups 출력에서 필터링된 관리자 토큰의 BUILTIN\Administrators가 "Group used for deny only"인 것을 확인하세요.
  2. Process Explorer에서 lsass.exe의 Protection 열을 보고, LSA 보호가 켜진 시스템이면 PsProtectedSignerLsa-Light를 확인하세요.
  3. icacls로 Low 라벨 폴더를 만들고, psexec -l(제한된 토큰) 또는 Low IL 프로세스에서 쓰기 가능 여부를 비교해 보세요.
  4. 위 시뮬레이터의 "UAC 필터링" 시나리오와 실제 whoami 결과를 대조해 보세요.

확인 문제

DACL이 [1] ALLOW Users READ|WRITE, [2] DENY Interns WRITE 순서입니다. Users·Interns 모두에 속한 사용자가 READ|WRITE를 요청하면?

  1. 거부 — 명시적 거부는 항상 우선한다
  2. 허용 — ACE [1]에서 요청이 모두 충족되어 검사가 끝난다
  3. READ만 허용된다
  4. DACL이 비정규 순서라 검사가 실패한다
SeAccessCheck는 ACE를 순서대로 평가하고 요청이 모두 허용되면 즉시 끝납니다. "거부 우선"은 거부 ACE가 앞에 오는 정규 순서 덕분이지 알고리즘 자체의 규칙이 아닙니다. 비정규 순서를 커널이 거부하지도 않습니다.

NULL DACL과 빈 DACL(ACE 0개)의 차이는?

  1. 둘 다 모두 거부
  2. 둘 다 모두 허용
  3. NULL DACL은 모두 허용, 빈 DACL은 (소유자 암묵 권리·특권 외에는) 모두 거부
  4. NULL DACL은 관리자만 허용
DACL이 없다는 것은 "제한 없음"을 뜻합니다. 개발자가 SetSecurityDescriptorDacl(sd, TRUE, NULL, FALSE)로 "보안 없음"을 만드는 실수는 공유 객체를 누구나 조작하게 만드는 고전적 취약점입니다.

UAC 필터링 토큰에서 Administrators 그룹이 "deny-only"라는 의미는?

  1. Administrators 그룹이 토큰에서 완전히 제거되었다
  2. 허용 ACE에는 매칭되지 않지만, Administrators를 대상으로 한 거부 ACE에는 매칭된다
  3. Administrators에 대한 접근을 거부하는 ACE가 자동 추가된다
  4. 로그오프할 때까지 일시 비활성화되었다가 자동 복구된다
완전히 제거하면 "Administrators 거부" ACE를 피하는 효과가 생깁니다. deny-only로 남겨야 거부는 여전히 적용되면서 허용은 받지 못합니다. 제한 토큰(CreateRestrictedToken)도 같은 속성을 씁니다.

DACL이 Everyone에게 FILE_ALL_ACCESS를 허용하는 Medium 라벨 파일에, Low 무결성 프로세스가 쓰기를 요청하면?

  1. DACL이 허용하므로 쓰기 성공
  2. 필수 무결성 검사(No-Write-Up)에서 쓰기 계열 권리가 차단되어 실패
  3. UAC 프롬프트가 뜬다
  4. Low 프로세스는 어떤 파일도 열 수 없다
MIC는 DACL과 독립적으로 먼저 적용됩니다. 읽기는 (No-Read-Up이 없다면) 허용됩니다. 그래서 샌드박스 프로세스는 사용자 파일을 읽을 수는 있어도 수정은 못 하며, 쓰기용으로 Low 라벨 폴더(예: %LOCALAPPDATA%Low)를 씁니다.

관리자가 SeDebugPrivilege를 활성화했는데도 LSA 보호가 켜진 LSASS를 PROCESS_VM_READ로 열 수 없습니다. 이유는?

  1. LSASS의 DACL이 Administrators를 거부한다
  2. SeDebugPrivilege는 서비스에만 적용된다
  3. LSASS가 PPL로 실행되어, 보호되지 않은 호출자에게는 DACL·특권과 무관하게 제한된 권리만 허용된다
  4. 무결성 수준이 Protected라 No-Read-Up이 적용된다
보호 프로세스 검사는 DACL 검사와 별개로 커널이 PS_PROTECTION을 비교해 수행합니다. SeDebugPrivilege는 DACL 검사를 넘어서게 해 줄 뿐 보호 수준 검사는 넘지 못합니다.

AppContainer 프로세스가 사용자 문서 폴더(DACL: alice 전체 허용)에 접근하지 못하는 이유는?

  1. AppContainer 토큰에는 사용자 SID가 없다
  2. 사용자 SID 검사와 별도로, DACL이 패키지 SID·ALL APPLICATION PACKAGES·기능 SID 중 하나를 명시적으로 허용해야 하는 두 번째 검사를 통과하지 못해서
  3. AppContainer는 파일 시스템 API를 호출할 수 없다
  4. 문서 폴더가 High 무결성 라벨을 가져서
AppContainer 토큰에도 사용자 SID와 그룹이 있어 첫 번째 검사는 통과합니다. 하지만 패키지/기능 SID 기반 두 번째 검사를 통과해야 하므로, 명시적으로 허용되지 않은 자원은 접근할 수 없습니다. picturesLibrary 같은 기능이 이 두 번째 검사의 열쇠 역할을 합니다.

핵심 요약

  • 판정은 커널 SRM(SeAccessCheck), 인증·정책·토큰 생성 요청은 LSASS. 검사는 객체를 열 때 한 번 일어나고 결과는 핸들의 GrantedAccess로 남는다.
  • 토큰 = 사용자/그룹 SID(+속성) + 특권(존재/활성) + 무결성 + 유형(기본/가장). 그룹 변경은 재로그온 후 반영.
  • SD = 소유자 + DACL + SACL. NULL DACL은 전부 허용, 빈 DACL은 전부 거부. 소유자는 암묵적으로 READ_CONTROL·WRITE_DAC.
  • DACL 평가는 순서대로: 거부는 남은 요청 비트를 건드리면 즉시 거부, 허용은 누적, 다 차면 즉시 종료. 정규 순서가 "거부 우선"을 보장한다.
  • DACL 위의 추가 경계: 필수 무결성(No-Write-Up), UAC 분리 토큰(deny-only), 가장 수준, PPL 서명자 지배, AppContainer 이중 검사.
