동기화

커널 코드는 모든 CPU에서 동시에, 그리고 인터럽트에 끼어들리며 실행됩니다. 공유 데이터를 지키는 도구를 IRQL 규칙과 함께 정확히 고르는 법을 다룹니다.

심화⏱ 약 100분선수: 05 스케줄링, 06 IRQL

학습 목표

  • read-modify-write 경쟁이 왜 생기는지 명령어 수준에서 설명하고, lock 접두사·Interlocked 연산으로 해결할 수 있다.
  • 스핀락이 IRQL을 DISPATCH_LEVEL로 올리는 이유, 큐드 스핀락이 확장성을 개선하는 원리를 설명할 수 있다.
  • 디스패처 객체(DISPATCHER_HEADER)의 signaled 상태와 KWAIT_BLOCK 기반 대기 메커니즘을 그릴 수 있다.
  • 이벤트·뮤텍스·패스트 뮤텍스·세마포어·ERESOURCE·푸시락·런다운 보호의 차이와 사용 IRQL을 구분해 상황에 맞게 선택할 수 있다.
  • 데드락의 조건과 락 순서 규칙을 이해하고, WinDbg·Driver Verifier로 락 문제를 진단할 수 있다.

경쟁 조건: counter++는 한 줄이 아니다

C의 counter++는 x64에서 보통 읽기 → 수정 → 쓰기(read-modify-write) 세 단계로 실행됩니다. 두 CPU가 같은 변수에 동시에 이 세 단계를 수행하면 단계가 섞이면서(interleaving) 한쪽의 결과가 사라집니다. 이것이 경쟁 조건(race condition)이며, 같은 CPU에서도 인터럽트·DPC·스레드 선점이 단계 사이에 끼어들면 똑같이 일어납니다.

단일 CPU에서도 경쟁은 있다

CPU가 하나여도 mov와 inc 사이에 인터럽트가 들어와 DPC가 같은 변수를 바꾸면 똑같이 유실됩니다. 그래서 "멀티코어니까 동기화한다"가 아니라 "이 데이터를 만지는 실행 문맥(스레드·DPC·ISR)이 둘 이상이면 동기화한다"가 올바른 기준입니다.

Interlocked 연산과 lock 접두사

x86의 lock 접두사는 뒤따르는 read-modify-write 명령을 원자적으로 실행하도록 보장합니다. 현대 CPU는 버스 전체를 잠그는 대신 캐시 일관성 프로토콜(MESI 계열)로 해당 캐시 라인을 독점(Modified/Exclusive) 상태로 확보한 채 읽기·쓰기를 끝냅니다. 그동안 다른 코어는 그 라인에 접근할 수 없습니다. xchg는 메모리 피연산자가 있으면 lock이 암묵적으로 붙습니다.

VOID AtomicMax(_Inout_ volatile LONG *p, _In_ LONG v)
{
    LONG cur = *p;
    while (v > cur) {
        LONG prev = InterlockedCompareExchange(p, v, cur);  // *p == cur 일 때만 v로 교체
        if (prev == cur) break;      // 성공
        cur = prev;                  // 다른 CPU가 먼저 바꿈 → 최신 값으로 재시도
    }
}
ABA 문제와 SLIST

CAS는 "값이 같으면 아무도 안 건드렸다"고 가정합니다. 락-프리 스택에서 A를 pop하려는 사이 다른 CPU가 A를 pop → B를 pop → A를 다시 push하면 헤드 포인터는 여전히 A이므로 CAS가 성공하지만 A의 Next는 이미 해제된 B를 가리킵니다. Windows의 SLIST_HEADER는 포인터와 함께 시퀀스 번호(Depth/Sequence)를 128비트로 묶어 cmpxchg16b로 한 번에 비교해 이 문제를 피합니다. 직접 락-프리 구조를 만들기 전에 SLIST로 충분한지 먼저 검토하세요.

메모리 순서 — 원자성만으로는 부족할 때

x64는 비교적 강한 메모리 모델(TSO)이라 "쓰기끼리", "읽기끼리"의 순서는 다른 CPU에게도 유지되지만, 나중 읽기가 앞선 쓰기보다 먼저 보일 수 있습니다(스토어 버퍼). lock 명령과 xchg는 완전한 메모리 배리어 역할도 합니다. ARM64는 훨씬 약한 모델이라 배리어 없이 쓴 "플래그 + 데이터" 패턴이 깨질 수 있습니다. Windows는 InterlockedXxx(완전 배리어), …Acquire/…Release/…NoFence 변형, ReadAcquire/WriteRelease, KeMemoryBarrier를 제공합니다. volatile은 컴파일러 최적화만 막을 뿐, CPU 재정렬이나 원자성을 보장하지 않는다는 점을 기억하세요.

스핀락

Interlocked는 변수 하나만 지킬 수 있습니다. 리스트 삽입처럼 여러 필드를 함께 바꿔야 하면 락이 필요합니다. DISPATCH_LEVEL 이상에서는 대기(스레드 전환)가 불가능하므로, 그 수준에서 쓸 수 있는 락은 바쁜 대기(busy-wait)하는 스핀락뿐입니다. KSPIN_LOCK은 포인터 크기의 정수 하나이며, 반드시 논페이지 메모리에 있어야 합니다. 

; KeAcquireSpinLock: 먼저 IRQL을 DISPATCH_LEVEL로 올린 뒤
acquire:
    lock bts qword ptr [rcx], 0    ; 비트 0 설정 시도, 이전 비트 → CF
    jnc     acquired               ; CF=0 → 비어 있었음 → 획득
spin:
    pause                          ; 스핀 힌트 (하이퍼스레딩·전력에 우호적)
    test    qword ptr [rcx], 1     ; 읽기만 하며 대기 → 캐시 라인을 공유 상태로 유지
    jnz     spin
    jmp     acquire                ; 비었다! 다시 원자적 시도 (test-and-test-and-set)
acquired:

왜 IRQL을 DISPATCH_LEVEL로 올리는가

스핀락은 "락 비트"와 "IRQL 상승"을 함께 씁니다. 락 비트만 쓰면 무슨 일이 생기는지, 같은 CPU에서 따라가 봅시다.

같은 논리가 ISR에도 적용된다 — 인터럽트 스핀락

ISR이 만지는 데이터를 DPC나 스레드에서 보호하려고 일반 스핀락을 쓰면, 락을 쥔 DPC를 같은 CPU의 ISR이 선점해 똑같은 데드락이 납니다(그리고 ISR에서는 일반 스핀락을 잡을 수도 없습니다). ISR과 공유하는 데이터는 KeSynchronizeExecution(Interrupt, SyncRoutine, Ctx) 또는 KeAcquireInterruptSpinLock으로 보호합니다. 이들은 IRQL을 KINTERRUPT.SynchronizeIrql까지 올리고 ISR이 쓰는 바로 그 인터럽트 스핀락을 잡습니다(06장).

KSPIN_LOCK  g_ListLock;      // 논페이지 전역 또는 디바이스 확장
LIST_ENTRY  g_List;
KeInitializeSpinLock(&g_ListLock);

VOID AddItem(_In_ PITEM item)                 // IRQL <= DISPATCH_LEVEL
{
    KIRQL old;
    KeAcquireSpinLock(&g_ListLock, &old);     // IRQL → DISPATCH, 락 획득
    InsertTailList(&g_List, &item->Link);     // 짧게! 논페이지 데이터만
    KeReleaseSpinLock(&g_ListLock, old);      // 락 해제, IRQL 복원
}

VOID MyDpc(PKDPC Dpc, PVOID Ctx, PVOID A1, PVOID A2)   // 이미 DISPATCH_LEVEL
{
    KeAcquireSpinLockAtDpcLevel(&g_ListLock);  // IRQL 변경 없이 락만
    /* ... */
    KeReleaseSpinLockFromDpcLevel(&g_ListLock);
}

스핀락 보유 중 금지 사항

대기·Zw* 호출·페이지 가능 코드/데이터 접근·페이지드 풀 할당·다른 드라이버로의 긴 콜아웃. 보유 시간은 수 µs 수준이어야 합니다. 재귀 획득은 즉시 자기 데드락입니다.

리더/라이터 스핀락 EX_SPIN_LOCK

ExAcquireSpinLockShared/Exclusive로 읽기 다수·쓰기 하나를 허용합니다. 읽기가 압도적으로 많은 테이블 조회(예: 콜백 목록)에 유리합니다. 역시 DISPATCH_LEVEL에서 보유합니다.

가상 머신에서의 스핀락 — Long Spin Wait 통지

게스트의 vCPU가 락을 쥔 채 하이퍼바이저에 의해 디스케줄되면 다른 vCPU가 오래 헛돌게 됩니다(lock-holder preemption). Hyper-V 계몽(enlightenment)이 켜진 Windows는 스핀이 일정 횟수를 넘으면 하이퍼바이저에 "오래 스핀 중"임을 알려(HvlNotifyLongSpinWait) 다른 vCPU에 시간을 양보하게 합니다. 덤프에서 이 함수가 보이면 스핀락 경합을 의심하세요.

실험: 세 가지 방식으로 카운터 증가시키기

여러 CPU가 공유 카운터를 각자 정해진 횟수만큼 증가시킵니다. 스케줄러는 매 스텝 무작위 CPU의 다음 명령 하나를 실행해 실제 병렬 실행의 임의 인터리빙을 흉내 냅니다. 방식을 바꿔 가며 결과값, 유실된 증가, 스핀으로 낭비된 스텝을 비교해 보세요. 기록은 아래 표에 누적됩니다.

관찰 포인트: "락 없음"은 매번 결과가 달라지고 기대값보다 작습니다. Interlocked는 스텝 수가 가장 적지만(한 명령) 실제 하드웨어에서는 경합 시 캐시 라인이 CPU 사이를 오가며 비싸집니다. 스핀락은 정확하지만 대기 CPU의 스텝이 낭비됩니다 — 보유 구간이 길수록, CPU가 많을수록 낭비가 커집니다.

큐드 스핀락

일반 스핀락은 모든 대기 CPU가 같은 락 워드를 두드립니다. 해제될 때마다 그 캐시 라인이 모든 대기 CPU로 무효화·재전송되고(cache line bouncing), 누가 다음에 잡을지도 운에 달려 있어 공정성이 없습니다. 큐드 스핀락(MCS 락 계열)은 대기자들을 큐로 줄 세우고, 각자 자기 큐 엔트리의 비트에서만 스핀하게 합니다. 

KSPIN_LOCK g_QLock;            // 이 락은 큐드 API로만 사용 (일반 KeAcquireSpinLock과 섞지 말 것)
KeInitializeSpinLock(&g_QLock);

VOID Update(void)                                  // IRQL <= DISPATCH_LEVEL
{
    KLOCK_QUEUE_HANDLE h;                          // 스택에 큐 엔트리 + 이전 IRQL
    KeAcquireInStackQueuedSpinLock(&g_QLock, &h);
    /* 임계 구역 */
    KeReleaseInStackQueuedSpinLock(&h);
    // DPC 안이면: KeAcquireInStackQueuedSpinLockAtDpcLevel / ...FromDpcLevel
}

커널 내부에도 KPRCB에 미리 할당된 큐 엔트리를 쓰는 전역 큐드 스핀락들이 있습니다(!qlocks로 상태 확인). Windows 7에서는 오랫동안 스케줄러 확장성의 병목이던 전역 디스패처 락이 제거되고 객체별·스레드별 락으로 세분화되었습니다. 경합이 예상되는 드라이버 락은 일반 스핀락보다 인스택 큐드 스핀락을 쓰는 것이 권장됩니다.

디스패처 객체와 대기

PASSIVE/APC_LEVEL 코드는 기다리는 동안 CPU를 다른 스레드에 양보할 수 있습니다. 이를 위한 커널 메커니즘이 디스패처 객체입니다. 이벤트, 뮤턴트(뮤텍스), 세마포어, 타이머, 프로세스, 스레드, 큐(KQUEUE), 게이트가 모두 맨 앞에 같은 헤더 DISPATCHER_HEADER를 가지며, KeWaitForSingleObject/KeWaitForMultipleObjects로 기다릴 수 있습니다. 유저 모드의 WaitForSingleObject도 결국 이 경로입니다.

KeWaitForSingleObject의 흐름

  1. 스레드 락과 객체 락을 잡고 객체가 signaled인지 확인합니다. signaled이면 부작용(리셋·카운트 감소·소유권)을 적용하고 즉시 반환 — 대기 없음.
  2. non-signaled이고 타임아웃이 0이면 STATUS_TIMEOUT을 즉시 반환합니다(폴링). DISPATCH_LEVEL에서는 이 형태만 허용됩니다.
  3. 그렇지 않으면 대기 블록을 객체의 WaitListHead에 연결하고, 타임아웃이 있으면 타이머를 설정하고, 스레드 상태를 Waiting(대기 이유 포함)으로 바꾼 뒤 다른 스레드로 전환합니다.
  4. 다른 문맥에서 KeSetEvent 등이 객체를 signaled로 만들면 대기 리스트를 검사해 충족되는 스레드를 깨웁니다(Ready). 대기 중 커널 APC가 도착하면 잠시 깨어 APC를 실행하고 다시 대기에 들어갑니다(호출자에게는 보이지 않음).
LARGE_INTEGER timeout;
timeout.QuadPart = -10LL * 1000 * 100;   // 100ms (음수 = 상대 시간, 100ns 단위)

NTSTATUS st = KeWaitForSingleObject(&g_Event,
                                    Executive,     // 대기 이유 (드라이버는 보통 Executive)
                                    KernelMode,    // WaitMode: KernelMode면 커널 스택이 페이지 아웃되지 않음
                                    FALSE,         // Alertable
                                    &timeout);     // NULL = 무한, 0 = 폴링
if (st == STATUS_TIMEOUT) { /* ... */ }
WaitMode가 KernelMode여야 하는 경우

대기 중인 스레드의 커널 스택은 메모리 압박 시 페이지 아웃될 수 있는데, WaitMode = UserMode일 때만 그렇습니다. 이벤트나 대기 대상이 스택 변수라면 반드시 KernelMode로 기다려야 합니다. 그렇지 않으면 다른 CPU의 KeSetEvent가 페이지 아웃된 스택의 이벤트를 건드려 크래시할 수 있습니다.

이벤트: Notification vs Synchronization

Notification 이벤트 (수동 리셋)

KeInitializeEvent(&e, NotificationEvent, FALSE). 시그널되면 기다리던 모든 스레드가 깨어나고, KeClearEvent/KeResetEvent를 호출할 때까지 signaled로 남아 이후 대기자도 즉시 통과합니다. "초기화 완료", "종료 요청" 같은 상태 알림에 적합합니다.

Synchronization 이벤트 (자동 리셋)

KeInitializeEvent(&e, SynchronizationEvent, FALSE). 시그널되면 대기자 하나만 깨우고 자동으로 non-signaled가 됩니다. 대기자가 없으면 signaled로 남아 있다가 다음 대기자 하나가 소비합니다. "작업이 하나 생겼다" 같은 사건 전달에 적합합니다.

KeSetEvent(Event, Increment, Wait)는 이전 상태를 반환하며 ≤ DISPATCH_LEVEL에서 호출할 수 있습니다. Wait=TRUE는 "바로 이어서 대기 함수를 호출하겠다"는 특수 최적화로, 호출자가 디스패처 상태를 쥔 채 돌아오는 미묘한 계약이 있으므로 일반 드라이버는 FALSE를 씁니다. KePulseEvent는 시그널 직후 리셋하는 레거시 함수로, "그 순간 대기 중이지 않던 스레드는 신호를 놓친다"는 경쟁 조건 때문에 사용을 피합니다.

이벤트 종류별 대기 스레드 해제 시뮬레이터
객체:
WaitListHead — 대기 중 (Waiting)
깨어남 (Ready/Running) — 클릭하면 다시 대기

대기 리스트 해제 순서는 이 시뮬레이터에서 FIFO로 표현했습니다. 실제 커널도 대체로 FIFO지만, 대기 중 커널 APC를 처리하고 다시 대기에 들어간 스레드는 리스트 뒤로 가는 등 순서가 보장되지는 않습니다. 공정성에 의존하는 설계는 피하세요.

세마포어

세마포어는 소유권 없는 카운터입니다. KeInitializeSemaphore(&s, 0, MAXLONG)로 만들고 생산자는 항목을 넣을 때마다 KeReleaseSemaphore(&s, IO_NO_INCREMENT, 1, FALSE), 소비자는 KeWaitForSingleObject(&s, …)로 항목 하나를 "가져갑니다". 큐 자체는 별도의 스핀락이나 SLIST로 보호해야 합니다. 커널에는 이 조합을 하나로 만든 KQUEUE(I/O 완료 포트, 시스템 워커 스레드의 기반)도 있습니다.

ERESOURCE와 푸시락 — 읽기/쓰기 락

읽기가 대부분이고 쓰기가 드문 데이터(파일 시스템의 FCB, 커널의 각종 테이블)는 공유(shared)/배타(exclusive) 락으로 보호하면 읽기끼리 병렬로 진행할 수 있습니다. Windows 커널에는 두 가지가 있습니다.

Executive Resource. 공유/배타 획득, 재귀 획득, 소유자 추적(owner table), 경합 통계를 지원하는 무거운 범용 R/W 락입니다. 파일 시스템과 캐시 관리자의 표준 락입니다.

  • 호출 전 반드시 KeEnterCriticalRegion — 락을 쥔 스레드가 일시 중지 APC로 멈추면 시스템 전체가 그 락에서 멈추기 때문입니다.
  • 공유 → 배타 승격 불가(같은 스레드가 공유를 쥔 채 배타를 요청하면 데드락). 배타 → 공유 강등은 ExConvertExclusiveToSharedLite.
  • 기아 제어: ExAcquireSharedStarveExclusive(배타 대기자가 있어도 공유 허용), ExAcquireSharedWaitForExclusive(배타 대기자 우선).
  • 소유자가 대기 중이면 소유 스레드의 우선순위를 높여 우선순위 역전을 완화합니다.
  • 해제 전 ExDeleteResourceLite 필수 — 커널이 전역 리소스 리스트로 추적하므로, 빠뜨린 채 메모리를 해제하면 리스트가 손상됩니다.
ERESOURCE g_Res;                       // 논페이지 메모리
ExInitializeResourceLite(&g_Res);

// 읽기
KeEnterCriticalRegion();
ExAcquireResourceSharedLite(&g_Res, TRUE);       // TRUE = 획득할 때까지 대기
/* 읽기 */
ExReleaseResourceLite(&g_Res);
KeLeaveCriticalRegion();

// 쓰기
KeEnterCriticalRegion();
ExAcquireResourceExclusiveLite(&g_Res, TRUE);
/* 쓰기 */
ExReleaseResourceLite(&g_Res);
KeLeaveCriticalRegion();

ExDeleteResourceLite(&g_Res);          // 메모리 해제 전

푸시락(EX_PUSH_LOCK)은 포인터 하나 크기의 가벼운 R/W 락입니다. 경합이 없으면 Interlocked 한 번으로 끝나고, 경합 시에는 대기자의 스택에 있는 대기 블록을 연결해 이벤트로 잠듭니다. 하위 비트가 상태 플래그(Locked, Waiting, Waking, MultipleShared)이고 나머지가 공유 카운트 또는 대기 블록 포인터입니다(dt nt!_EX_PUSH_LOCK).

  • 재귀 획득 불가, 소유자 추적 없음(디버깅 정보가 적음).
  • 핸들 테이블, 객체 관리자, 메모리 관리자 등 커널 내부의 핫 패스에 폭넓게 쓰입니다. CPU별로 분산한 cache-aware 변형도 있습니다.
  • 서드파티 드라이버는 주로 Filter Manager 래퍼(FltAcquirePushLockShared/Exclusive)로 사용합니다. 최근 WDK에 노출된 Ex…PushLock…Ex 계열을 쓰려면 지원 버전을 문서로 확인하세요.
  • 보유 중 일반 커널 APC가 막혀 있어야 합니다(크리티컬 리전). Flt 래퍼의 문서화된 동작을 확인하고 지키세요.
EX_PUSH_LOCK g_Push;
FltInitializePushLock(&g_Push);

FltAcquirePushLockShared(&g_Push);     // 또는 FltAcquirePushLockExclusive
/* 읽기 */
FltReleasePushLock(&g_Push);

FltDeletePushLock(&g_Push);

런다운 보호

"곧 해체될 객체를 아직 누군가 쓰고 있는가?"는 락으로 풀기 까다롭습니다. 사용자는 매우 자주, 해체는 단 한 번 일어나기 때문입니다. 런다운 보호(EX_RUNDOWN_REF)는 이 비대칭에 맞춘 도구입니다. 사용자는 Interlocked 한 번으로 참조를 얻고 놓으며, 해체자는 "이후 획득은 모두 실패시키고, 이미 얻은 참조가 0이 될 때까지 기다린다"를 한 번에 수행합니다. 

EX_RUNDOWN_REF g_Rundown;
ExInitializeRundownProtection(&g_Rundown);

VOID OnEvent(...)                                     // 아무 스레드, IRQL <= DISPATCH_LEVEL
{
    if (!ExAcquireRundownProtection(&g_Rundown))
        return;                                       // 해체 중 → 손대지 않고 빠짐
    UseSharedContext();
    ExReleaseRundownProtection(&g_Rundown);
}

VOID Teardown(void)                                   // PASSIVE_LEVEL
{
    UnregisterCallbacks();
    ExWaitForRundownProtectionRelease(&g_Rundown);    // 이후 Acquire 실패, 진행 중인 것 대기
    FreeSharedContext();
}

커널 자신도 같은 패턴을 씁니다. 예를 들어 EPROCESS.RundownProtect는 다른 스레드가 프로세스 주소 공간에 접근하는 동안 프로세스가 해체되지 않도록 막습니다. 참조가 매우 잦으면 CPU별로 분산한 cache-aware 런다운(EX_RUNDOWN_REF_CACHE_AWARE)을 씁니다.

데드락과 락 순서

데드락은 (1) 상호 배제, (2) 보유한 채 대기, (3) 선점 불가, (4) 순환 대기가 모두 성립할 때 발생합니다. 커널 락은 1–3을 본질적으로 갖고 있으므로, 현실적으로 깰 수 있는 것은 4번입니다. 가장 흔한 형태가 두 스레드가 두 락을 반대 순서로 잡는 ABBA 데드락입니다.

예방 규칙

  • 락 계층(순서)을 문서화하고 모든 경로에서 지킨다. 같은 종류 락 여러 개는 주소 순 등 전역 순서를 정한다.
  • 락을 쥔 채 콜백·다른 드라이버 호출(IoCallDriver, 등록된 알림 루틴)을 하지 않는다. 상대가 어떤 락을 잡을지 모른다.
  • 스핀락 안에서 다른 스핀락을 잡아야 한다면 순서를 고정하고 최소화한다.
  • 필요하면 Try 계열(ExTryToAcquireFastMutex, ExAcquireResource…Lite(…, FALSE))로 획득 실패 시 물러난다.

진단 도구

  • Driver Verifier – Deadlock Detection(verifier /flags 0x20 /driver my.sys): 실제 데드락이 나지 않아도 락 순서 위반을 감지해 0xC4로 알린다. !deadlock으로 순환을 출력.
  • !locks: ERESOURCE 소유자·대기자·경합 횟수.
  • !qlocks: 전역 큐드 스핀락 상태.
  • !running -ti, !stacks 2: 모든 CPU·스레드의 스택에서 락 대기 함수를 찾는다.
우선순위 역전

낮은 우선순위 스레드가 락을 쥔 채 중간 우선순위 스레드들에 밀려 실행되지 못하면, 그 락을 기다리는 높은 우선순위 스레드도 함께 멈춥니다. ERESOURCE는 소유자 부스트로 이를 완화하고, Windows 8 이후 커널은 AutoBoost로 일부 커널 락(예: 푸시락, 가디드 뮤텍스)의 소유자 우선순위를 일시적으로 올립니다. 일반 스핀락은 보유 중 선점 자체가 없으므로 이 문제가 없지만, 대신 보유 시간을 극도로 짧게 유지해야 합니다.

확인 문제

두 CPU가 g_count++를 각각 1000번 실행했더니 결과가 1873이었습니다. 원인으로 가장 정확한 것은?

  1. 컴파일러가 루프를 잘못 최적화했다
  2. 증가가 읽기·수정·쓰기 세 단계로 나뉘어, 두 CPU의 단계가 섞일 때 한쪽의 쓰기가 다른 쪽을 덮어썼다
  3. 캐시 일관성 프로토콜이 고장 나 값이 손실되었다
  4. volatile을 붙이지 않았기 때문이며, 붙이면 해결된다
갱신 유실(lost update)입니다. 캐시 일관성은 정상 동작해도 RMW의 원자성은 보장하지 않습니다. volatile은 컴파일러 최적화만 막고 원자성을 주지 않습니다. InterlockedIncrement나 락이 필요합니다.

KeAcquireSpinLock이 락 비트를 잡기 전에 IRQL을 DISPATCH_LEVEL로 올리는 가장 중요한 이유는?

  1. DISPATCH_LEVEL에서 lock 명령이 더 빠르게 실행되기 때문
  2. 다른 CPU가 락에 접근하지 못하게 하기 위해
  3. 같은 CPU에서 스레드 전환과 DPC 실행을 막아, 락 보유자가 같은 CPU의 다른 코드에 밀려 영원히 재개되지 못하는 상황(데드락)을 방지하기 위해
  4. 페이지 폴트를 허용하기 위해
IRQL은 CPU별 상태이므로 다른 CPU를 막는 것은 락 비트의 역할입니다. IRQL 상승은 같은 CPU에서의 선점을 막습니다. 락을 쥔 코드 위에 같은 락을 원하는 DPC가 쌓이면 보유자가 재개될 수 없습니다. DISPATCH 이상에서는 오히려 페이지 폴트가 금지됩니다.

Synchronization 이벤트에 스레드 3개가 대기 중일 때 KeSetEvent를 한 번 호출하면?

  1. 세 스레드가 모두 깨어나고 이벤트는 signaled로 남는다
  2. 한 스레드만 깨어나고 이벤트는 자동으로 non-signaled가 된다
  3. 세 스레드가 모두 깨어나고 이벤트는 자동 리셋된다
  4. 아무도 깨어나지 않고 이벤트만 signaled가 된다
자동 리셋 이벤트는 대기 충족의 부작용으로 리셋되므로 정확히 하나만 깨웁니다. 1번은 Notification 이벤트의 동작, 3번은 Notification 이벤트에 KePulseEvent를 쓴 결과에 가깝습니다.

DPC 루틴에서 다른 스레드가 설정할 이벤트를 100ms 동안 기다리고 싶습니다. 올바른 설계는?

  1. KeWaitForSingleObject에 100ms 타임아웃을 주어 기다린다
  2. IRQL을 PASSIVE_LEVEL로 낮춘 뒤 기다리고 다시 올린다
  3. DPC에서는 대기할 수 없으므로 작업을 워크 아이템(PASSIVE_LEVEL)으로 넘기거나, 타이머 DPC로 나중에 다시 확인하는 비동기 구조로 바꾼다
  4. 스핀락을 잡고 이벤트 상태를 루프로 확인한다
DISPATCH_LEVEL에서는 0이 아닌 타임아웃 대기가 금지되고(DPC 안이면 0xB8 위험), 진입 IRQL보다 낮추는 것도 규칙 위반입니다. 100ms 스핀은 DPC 워치독과 시스템 지연을 해칩니다. 대기가 필요한 작업은 PASSIVE_LEVEL 문맥으로 옮겨야 합니다.

ERESOURCE를 공유(shared)로 획득한 스레드가, 쓰기가 필요해져 같은 리소스를 배타(exclusive)로 획득하려 하면?

  1. 자동으로 배타로 승격된다
  2. 재귀 획득이 허용되므로 즉시 성공한다
  3. 자신이 쥔 공유 락이 풀리기를 스스로 기다리게 되어 데드락이 발생한다
  4. STATUS_INVALID_PARAMETER를 반환한다
ERESOURCE는 공유→배타 승격을 지원하지 않습니다. 재귀는 같은 모드(배타 보유 중 배타/공유 재획득)에서만 허용됩니다. 해제 후 배타로 다시 잡고, 그 사이 상태가 바뀌었을 수 있으니 재검증해야 합니다.

큐드 스핀락이 일반 스핀락보다 경합 상황에서 확장성이 좋은 이유는?

  1. IRQL을 올리지 않기 때문에
  2. 대기 CPU가 스핀 대신 잠들기 때문에
  3. 각 대기자가 자기 큐 엔트리에서만 스핀해 캐시 라인 경합이 줄고, 해제 시 다음 대기자에게 FIFO로 직접 넘기기 때문에
  4. 락 워드가 CPU마다 복제되어 있기 때문에
MCS 방식의 핵심은 로컬 스핀과 직접 핸드오프입니다. 여전히 DISPATCH_LEVEL로 올라가고 바쁜 대기도 합니다. 공정성(FIFO)이 덤으로 생깁니다.

핵심 요약

  • RMW는 원자적이지 않다. 변수 하나는 lock 접두사 기반 Interlocked로, 여러 필드는 락으로 보호한다. volatile은 원자성·순서를 보장하지 않는다.
  • 스핀락 = IRQL을 DISPATCH로 올리기(같은 CPU 보호) + 락 비트(다른 CPU 보호). 경합이 크면 인스택 큐드 스핀락, ISR과 공유하면 인터럽트 스핀락.
  • 디스패처 객체는 DISPATCHER_HEADER(Type·SignalState·WaitListHead)를 가지며, 대기는 KWAIT_BLOCK으로 스레드와 객체를 잇는다. 대기 충족의 부작용이 객체 종류를 구분한다.
  • Notification 이벤트는 모두 해제·유지, Synchronization 이벤트는 하나 해제·자동 리셋. 패스트 뮤텍스는 APC_LEVEL·비재귀, KMUTEX는 재귀·무겁다.
  • ERESOURCE·푸시락은 크리티컬 리전과 함께 쓰는 R/W 락, 런다운 보호는 해체 동기화. 데드락은 락 순서로 예방하고 Verifier로 검증한다.
