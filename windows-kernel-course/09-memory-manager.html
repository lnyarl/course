Part III · Chapter 09

메모리 관리자 내부

08장이 하드웨어의 규칙이었다면, 이 장은 그 규칙 위에서 Windows가 가상 주소와 물리 페이지를 어떻게 장부로 관리하는지 — VAD, 폴트 처리기, PFN 데이터베이스, 워킹셋, 섹션, 풀 — 를 해부합니다.

심화⏱ 약 120분선수: 08장, 06장(IRQL)

학습 목표

  • 예약·커밋·워킹셋(물리 사용)의 차이와 커밋 차지/커밋 한도를 정확히 설명할 수 있다.
  • VAD 트리가 기록하는 정보와, 0 PTE에서 VAD를 참조해 PTE를 만들어 내는 지연 생성 방식을 이해한다.
  • 페이지 폴트가 KiPageFault → MmAccessFault를 거쳐 디맨드 제로/트랜지션/하드/프로토타입/권한 위반으로 분기하는 과정을 추적할 수 있다.
  • 프로토타입 PTE와 섹션 객체(CONTROL_AREA, SEGMENT, SUBSECTION)가 공유 메모리를 구현하는 방식을 설명할 수 있다.
  • PFN 데이터베이스와 Zero/Free/Standby/Modified/Active 상태 전이, 워킹셋 트리밍, Modified Page Writer, 메모리 압축의 관계를 그릴 수 있다.
  • 커널 풀의 종류와 ExAllocatePool2, 풀 태그, 풀 손상 버그체크를 실무 수준으로 다룰 수 있다.

메모리 관리자의 구성

메모리 관리자(Mm*, 내부 Mi*)는 ntoskrnl 안에서 가장 큰 구성요소 중 하나입니다. 크게 보면 두 개의 장부를 관리합니다.

가상 쪽 장부

프로세스마다: 어떤 VA 범위가 예약/커밋되었고 무엇(개인 메모리, 파일, 이미지)으로 뒷받침되는지 — VAD 트리와 페이지 테이블. 그리고 현재 물리 메모리에 올라와 있는 페이지 목록 — 워킹셋.

물리 쪽 장부

시스템 전체: 물리 페이지 하나하나가 지금 무엇에 쓰이는지 — PFN 데이터베이스와 그 위의 페이지 리스트(Zero, Free, Standby, Modified …). 그리고 디스크 쪽 백업 저장소 — 페이지 파일과 매핑된 파일.

폴트 처리 같은 동기 경로 외에, 여러 시스템 스레드가 백그라운드에서 두 장부의 균형을 맞춥니다.

예약, 커밋, 그리고 실제 사용

유저 모드 가상 메모리는 세 단계 상태를 가집니다. 이 구분을 정확히 하지 못하면 "메모리 사용량"에 관한 거의 모든 질문에 틀린 답을 하게 됩니다.

Free

아무 것도 없음. 접근하면 액세스 위반.

Reserved (예약)

MEM_RESERVE. VA 범위만 확보(VAD 생성). 커밋 차지도, 물리 메모리도 쓰지 않음. 접근하면 여전히 액세스 위반. 시작 주소는 64KB 할당 단위로 정렬.

Committed (커밋)

MEM_COMMIT. "필요하면 반드시 물리 페이지 또는 페이지 파일로 뒷받침하겠다"는 약속 → 커밋 차지 증가. 그러나 처음 접근하기 전까지 물리 페이지는 없음(디맨드 제로).

커밋 차지(commit charge)는 시스템이 한 약속의 총량이고, 커밋 한도(commit limit)는 지킬 수 있는 약속의 상한 — 대략 물리 메모리 + 모든 페이지 파일 크기입니다(페이지 파일이 자동 확장되면 한도도 커집니다). 차지가 한도에 닿으면 커밋 요청은 STATUS_COMMITMENT_LIMIT(0xC000012D), Win32로는 ERROR_COMMITMENT_LIMIT(1455, "페이징 파일이 너무 작아…")로 실패합니다 — 물리 메모리가 남아 있어도. 커밋 차지에는 개인 커밋 메모리 외에 페이지 파일 기반 섹션, 쓰기 시 복사(Copy-on-Write) 뷰가 잠재적으로 만들 사본, 커널 풀, 커널 스택, 페이지 테이블 등이 포함됩니다.

예약 · 커밋 · 터치 실험실 — 무엇이 어떤 카운터를 움직이는가
이 프로세스의 예약된 가상 주소 (VAD)0 MB
시스템 커밋 차지 / 커밋 한도 (회색 = 다른 프로세스·커널)0 / 0 MB
이 프로세스의 워킹셋 (실제 물리 페이지)0 MB
작업 관리자의 숫자 읽기

커밋됨 X / Y GB = 시스템 커밋 차지 / 커밋 한도. 사용 중 ≈ 활성(워킹셋 등) 페이지. 사용 가능 = Zero + Free + Standby. 스탠바이는 캐시된 데이터지만 즉시 회수 가능하므로 "사용 가능"에 포함됩니다. 프로세스 열의 "메모리(개인 작업 집합)"는 물리 사용, "커밋 크기"는 개인 커밋 차지입니다. 메모리 누수 조사는 보통 커밋(Private Bytes)의 단조 증가로 판단합니다.

VAD 트리

프로세스의 유저 주소 공간에서 "어디가 어떤 용도로 할당되었는가"는 페이지 테이블이 아니라 VAD(Virtual Address Descriptor)가 기록합니다. 예약 한 번, 매핑 한 번이 VAD 노드 하나가 되고, 노드들은 시작 VPN(VA >> 12)을 키로 하는 균형 이진 트리(AVL)에 들어갑니다(EPROCESS.VadRoot, Windows 8+에서는 _RTL_AVL_TREE). 덕분에 "이 주소는 어느 VAD에 속하는가"를 O(log n)에 찾을 수 있고, 최근 찾은 노드는 VadHint로 캐시됩니다.

왜 페이지 테이블만으로는 안 될까요? 1GB를 예약/커밋할 때 PTE 262,144개를 미리 채우는 것은 낭비입니다. Windows는 커밋 정보를 VAD에만 적어 두고 PTE는 0으로 둔 채, 첫 폴트가 났을 때 VAD를 보고 PTE를 만들어 냅니다(08장의 "0 PTE"). VAD는 또 매핑된 파일·이미지와의 연결(섹션의 프로토타입 PTE 위치), 보호 속성, 상속 여부, 커밋 양을 보관합니다.

페이지 폴트 처리 흐름

페이지 폴트는 오류가 아니라 메모리 관리자의 정상적인 작동 방식입니다. 시스템은 초당 수천~수만 번의 폴트를 처리하며, 대부분은 디스크 I/O가 없는 소프트 폴트입니다. 아래는 하드웨어 예외에서 시작해 원인별 해결 루틴으로 분기하는 전체 흐름입니다.

드라이버 버그의 고전: DISPATCH_LEVEL에서 페이징 가능한 메모리 접근

스핀락을 잡은 채(IRQL = DISPATCH_LEVEL) Paged 풀이나 페이징 가능한 코드(#pragma alloc_text(PAGE, …))를 건드리면, 그 페이지가 마침 메모리에 있을 때는 아무 문제가 없다가 메모리 압박으로 트림된 날에만 0xA/0xD1로 죽습니다. 재현이 어려운 이유가 바로 이것입니다. Driver Verifier의 IRQL 검사는 IRQL을 올릴 때마다 페이징 가능한 메모리를 강제로 워킹셋에서 내보내 이 버그를 즉시 드러나게 합니다. 페이징 가능 함수 첫 줄에는 PAGED_CODE()를 두세요.

프로토타입 PTE와 공유 메모리

두 프로세스가 같은 파일 페이지를 매핑하면 물리 페이지 하나를 두 PTE가 가리킵니다. 문제는 그 페이지가 메모리에서 나갈 때입니다. PTE마다 "이 페이지는 이제 디스크에 있다"고 고쳐 써야 한다면, 메모리 관리자는 어떤 프로세스의 어떤 PTE가 그 페이지를 가리키는지 모두 추적해야 합니다(역매핑). Windows의 답은 프로토타입 PTE라는 한 단계의 간접 참조입니다. 섹션의 각 페이지마다 프로토타입 PTE 하나가 있고(섹션의 세그먼트에 배열로 존재), 프로세스 PTE는 페이지가 유효할 때만 PFN을 직접 가리키며, 그 외에는 "프로토타입 PTE를 보라"는 형식으로 남습니다.

개인 페이지에는 프로토타입 PTE가 없다

프로토타입 PTE는 공유 가능한 메모리(섹션)에만 있습니다. VirtualAlloc 개인 메모리는 매핑하는 PTE가 하나뿐이므로 PFN의 PteAddress가 그 하드웨어 PTE를 직접 가리키고, 페이지가 나갈 때 그 PTE를 바로 트랜지션/페이지 파일 형식으로 고칩니다. 쓰기 시 복사로 생긴 개인 사본도 마찬가지로 개인 페이지가 됩니다.

섹션 객체

섹션(Section)은 "매핑할 수 있는 메모리 덩어리"를 나타내는 커널 객체입니다(Win32 이름은 파일 매핑 객체, CreateFileMapping/NtCreateSection). 세 종류가 있습니다: 데이터 파일 섹션(일반 파일을 그대로 매핑), 이미지 섹션(SEC_IMAGE: PE 파일을 섹션별 보호 속성·정렬에 맞춰 매핑 — 로더가 DLL/EXE를 올리는 방식), 페이지 파일 기반 섹션(INVALID_HANDLE_VALUE로 만든 이름 있는/없는 공유 메모리 — 백업 저장소가 페이지 파일). 아래 구조도를 클릭해 보세요.

워킹셋과 트리밍

워킹셋(working set)은 "현재 이 주소 공간에서 유효한 PTE로 매핑된 물리 페이지들"의 목록입니다. 프로세스마다 하나씩 있고(EPROCESS.Vm의 워킹셋 리스트, WSLE 배열), 커널에도 시스템 워킹셋(Windows 8 이후 시스템 캐시·페이지드 풀·시스템 PTE(드라이버 이미지 등)로 나뉨)과 세션 워킹셋이 있습니다. 페이지가 워킹셋에 들어오는 길은 폴트이고, 나가는 길은 트리밍입니다.

  • 최소/최대 크기: 기본 최소 50페이지, 최대 345페이지지만 기본적으로 소프트 한도라 메모리가 충분하면 최대를 넘어 자랄 수 있습니다. SetProcessWorkingSetSizeEx로 하드 한도(QUOTA_LIMITS_HARDWS_MIN_ENABLE/MAX_ENABLE)를 걸 수 있습니다.
  • 에이징: 워킹셋 관리자는 PTE의 A 비트를 주기적으로 검사·클리어해 페이지별 나이를 매기고, 메모리가 부족해질수록 오래 쓰지 않은 페이지부터 더 공격적으로 내보냅니다. 오래 쉬고 있는 프로세스, 최소화된 GUI 앱이 먼저 트림됩니다.
  • 트림된 페이지의 행방: 바로 버려지지 않습니다. 깨끗하면(D=0, 디스크에 같은 내용이 있음) 스탠바이, 더티하면 수정 리스트로 갑니다. PTE는 트랜지션 형식으로 남아 다시 접근하면 소프트 폴트로 돌아옵니다. 그래서 "트림 = 성능 손실"이 아니라 "회수 가능 후보로 표시"에 가깝습니다.
  • EmptyWorkingSet/SetProcessWorkingSetSize(h, -1, -1)는 워킹셋 전체를 트림합니다. 작업 관리자의 메모리 수치는 즉시 줄지만 커밋은 그대로이며, 곧 소프트 폴트로 되돌아오는 경우가 많습니다.

시뮬레이터에서 꼭 확인할 것
  • 디맨드 제로 페이지는 처음부터 더티(●)입니다. 이 내용은 어디에도 백업이 없으므로, 트림되면 스탠바이가 아니라 수정 리스트로 가서 페이지 파일에 기록되어야 합니다.
  • 제로·프리가 바닥나면 스탠바이 페이지가 재사용(repurpose)됩니다. 이때 원래 소유자의 PTE(또는 프로토타입 PTE)는 트랜지션에서 페이지 파일/파일 참조 형식으로 바뀌고, 그 소유자의 다음 접근은 하드 폴트가 됩니다. "사용 가능" 메모리는 줄지 않았는데 하드 폴트가 늘어나는 현상의 정체입니다.
  • 프로세스가 종료되면 개인 수정 페이지는 기록 없이 바로 Free로 갑니다. 다시 읽힐 일이 없으니 쓸 이유가 없습니다. 반면 파일 페이지는 스탠바이(캐시)로 남아 다음 실행을 빠르게 합니다.

Modified Page Writer와 커밋

수정 리스트의 페이지는 디스크에 기록되기 전까지 재사용할 수 없습니다. Modified Page Writer(페이지 파일 대상)와 Mapped Page Writer(매핑 파일 대상) 스레드는 수정 리스트가 일정 크기를 넘거나 가용 페이지가 부족해지면 깨어나, 페이지들을 클러스터로 묶어 기록하고 스탠바이로 옮깁니다(기록 중에는 WriteInProgress, 그 사이 다시 더티해지면 수정 리스트로 복귀). 매핑 파일 쪽을 별도 스레드로 두는 이유는, 파일 시스템에 쓰는 과정에서 다시 페이지 폴트·메모리 할당이 필요할 수 있어 페이지 파일 기록 경로와 서로 막히지 않게(교착 방지) 하기 위해서입니다.

페이지 파일 공간은 언제 할당되나

커밋 시점이 아니라 실제로 기록할 때 페이지 파일 블록이 할당됩니다. 커밋 차지는 "페이지 파일에 자리를 만들어 줄 수 있다"는 보장일 뿐입니다. 그래서 페이지 파일이 거의 비어 있어도 커밋 한도에 걸릴 수 있습니다.

Modified No-Write 리스트

기록이 허용되기 전까지 묶어 둬야 하는 더티 페이지(예: 트랜잭션·로그 순서 제약이 있는 파일 시스템 메타데이터)를 따로 보관합니다. 일반 드라이버가 직접 다룰 일은 드뭅니다.

커널 풀

커널 코드의 범용 동적 메모리가 풀(pool)입니다. 유저 모드 힙에 해당하지만 실수의 대가가 시스템 크래시라는 점이 다릅니다.

풀상주할당 가능 IRQL접근 가능 IRQL용도
NonPaged (Nx)항상 물리 메모리≤ DISPATCH_LEVEL모든 IRQLISR/DPC가 만지는 데이터, 스핀락으로 보호되는 구조, I/O 버퍼
Paged페이징 가능≤ APC_LEVEL≤ APC_LEVEL그 외 대부분(문자열, 레지스트리 데이터, 큰 테이블)
NonPaged Execute항상≤ DISPATCH_LEVEL모든 IRQL실행 가능한 풀 — 특별한 이유가 없으면 쓰지 말 것(HVCI와도 충돌)
 
#define TAG_CTX 'xtCM'   // 도구에서는 "MCtx"로 보인다 (문자 리터럴은 역순 저장)

typedef struct _MY_CTX { LIST_ENTRY Link; KSPIN_LOCK Lock; ULONG State; } MY_CTX, *PMY_CTX;

NTSTATUS CreateCtx(_Out_ PMY_CTX* Out)
{
    // Windows 10 2004+. 기본으로 0 초기화된다 (원치 않으면 POOL_FLAG_UNINITIALIZED).
    PMY_CTX ctx = (PMY_CTX)ExAllocatePool2(POOL_FLAG_NON_PAGED, sizeof(MY_CTX), TAG_CTX);
    if (ctx == NULL) {                // 실패 시 NULL (POOL_FLAG_RAISE_ON_FAILURE면 예외)
        return STATUS_INSUFFICIENT_RESOURCES;
    }
    KeInitializeSpinLock(&ctx->Lock); // 스핀락으로 보호 → NonPaged 여야 한다
    *Out = ctx;
    return STATUS_SUCCESS;
}

VOID DestroyCtx(_In_ PMY_CTX Ctx)
{
    ExFreePoolWithTag(Ctx, TAG_CTX);  // 태그 불일치를 검출할 수 있게 태그와 함께 해제
}

ExAllocatePoolWithTag는 Windows 10 2004부터 사용 중단(deprecated)되었습니다. 이전 OS를 함께 지원해야 하면 ExAllocatePoolZero 등 다운레벨 지원 래퍼를 검토하세요. 기본 0 초기화는 "초기화 안 된 풀 메모리 유출" 취약점 계열을 크게 줄입니다.

태그는 4바이트 ULONG입니다. C의 다중 문자 리터럴 'xtCM'은 리틀 엔디언 메모리에 M C t x 순으로 놓이므로 poolmon, !poolused, !pool에서는 "MCtx"로 보입니다. 그래서 소스에는 역순으로 씁니다.

  • 드라이버마다 고유한 태그를 쓰고, 구조체 종류별로 다른 태그를 쓰면 누수 원인 추적이 쉬워집니다.
  • 각 문자는 0x20–0x7E 범위의 ASCII여야 합니다. pooltag.txt(디버거 설치 폴더)에 알려진 태그 목록이 있습니다.
  • 누수 조사: poolmon -b(바이트 순 정렬), WinDbg !poolused 2(NonPaged 사용량 순) / !poolused 4(Paged 순).

Windows 10 19H1(1903)부터 커널 풀은 유저 모드에서 쓰이던 세그먼트 힙을 기반으로 재구현되었습니다. 할당 크기에 따라 서로 다른 백엔드로 갑니다.

  • LFH(Low Fragmentation Heap): 자주 쓰이는 작은 크기 — 크기별 버킷에서 빠르게 할당.
  • VS(Variable Size): 그 밖의 작은~중간 크기.
  • 세그먼트 / Large: 큰 할당은 페이지 단위로 직접 할당. 대략 한 페이지 이상의 큰 할당은 별도의 "빅 풀" 테이블로 추적되어 !pool이 태그를 찾을 수 있습니다.

작은 할당 앞에는 호환성을 위해 여전히 16바이트 _POOL_HEADER(이전 크기, 블록 크기, 풀 타입, 태그 등)가 붙지만, 그 앞뒤의 힙 메타데이터 구조는 이전 풀과 다릅니다. 버전마다 세부가 바뀌므로 익스플로잇·포렌식 분석 시에는 대상 빌드의 심볼(dt nt!_POOL_HEADER, dt nt!_SEGMENT_HEAP)로 확인하세요.

자주 같은 크기를 할당·해제한다면 룩어사이드 리스트(ExInitializeLookasideListEx, ExAllocateFromLookasideListEx)가 풀 경합을 줄입니다.

버그체크전형적 원인
0x19 BAD_POOL_HEADER앞 블록의 버퍼 오버런이 다음 블록 헤더를 덮음
0xC2 BAD_POOL_CALLER이중 해제, 잘못된 IRQL에서 할당/해제, 풀이 아닌 주소 해제
0xC5 DRIVER_CORRUPTED_EXPOOL높은 IRQL에서 손상된 풀 접근(대개 이전 손상의 결과)
0x13A KERNEL_MODE_HEAP_CORRUPTION세그먼트 힙 기반 풀이 감지한 손상

풀 손상의 버그체크는 손상을 일으킨 순간이 아니라 발견한 순간에 납니다. 콜스택의 드라이버는 피해자일 가능성이 큽니다. Driver Verifier의 Special Pool을 켜면 할당마다 별도 페이지와 가드 페이지를 써서, 오버런하는 바로 그 명령에서 폴트가 나게 만듭니다.

메모리 압축

Windows 10부터 메모리 관리자는 수정 리스트의 개인 페이지를 곧바로 페이지 파일에 쓰는 대신 압축해서 메모리 안의 저장소(store)에 넣을 수 있습니다. 저장소를 관리하는 것은 스토어 관리자(Sm*/St*)이고, 압축된 데이터는 Memory Compression이라는 최소(minimal) 프로세스의 사용자 주소 공간에 담깁니다(Windows 10 1607 이후 별도 프로세스로 보임).

이득

여러 페이지가 압축되어 더 적은 물리 페이지에 담긴다. 다시 필요해지면 디스크 I/O 대신 압축 해제(CPU)로 복구 — 하드 폴트보다 훨씬 빠르다.

비용

압축/해제 CPU 시간. 저장소 페이지 자체도 메모리를 쓰며, 압박이 계속되면 저장소의 페이지가 다시 페이지 파일로 기록될 수 있다.

관찰과 설정

작업 관리자 메모리 탭의 "압축됨", Get-MMAgent의 MemoryCompression. Disable-MMAgent -MemoryCompression으로 끌 수 있다. 서버 SKU는 기본 비활성인 경우가 많다.

"Memory Compression 프로세스가 메모리를 많이 쓴다"는 오해

그 프로세스의 워킹셋은 다른 프로세스들의 페이지를 압축해 담은 것입니다. 그 수치가 크다는 것은 메모리 압박이 있다는 신호이지 그 프로세스가 원인이라는 뜻이 아닙니다. 원인은 커밋을 늘리고 있는 다른 프로세스에서 찾으세요.

확인 문제

VirtualAlloc(NULL, 1GB, MEM_RESERVE, PAGE_READWRITE)가 성공했을 때 변하는 것은?

  1. 시스템 커밋 차지가 1GB 증가
  2. 프로세스 워킹셋이 1GB 증가
  3. VAD가 하나 생기고 가상 주소 범위만 확보된다
  4. 페이지 파일에 1GB 공간이 할당된다
예약은 VAD만 만듭니다. 커밋 차지는 MEM_COMMIT 시점에, 물리 페이지는 첫 접근(디맨드 제로 폴트) 시점에, 페이지 파일 블록은 실제로 페이지를 기록할 때 할당됩니다.

작업 관리자의 "사용 가능" 메모리에 포함되는 페이지 리스트 조합은?

  1. Free + Zero
  2. Free + Zero + Standby
  3. Free + Zero + Standby + Modified
  4. Active를 제외한 모든 페이지
스탠바이 페이지는 내용이 디스크에도 있으므로 즉시 재사용할 수 있어 "사용 가능"입니다. 수정 페이지는 먼저 기록해야 하므로 포함되지 않습니다.

스핀락을 잡은 상태에서 Paged 풀 데이터를 읽었는데, 그 페이지는 스탠바이 리스트에 있었습니다(트랜지션 PTE). 결과는?

  1. 소프트 폴트이므로 I/O 없이 정상 처리된다
  2. MmAccessFault가 IRQL을 낮춘 뒤 처리한다
  3. DISPATCH_LEVEL에서는 폴트를 해결할 수 없어 버그체크(0xA/0xD1)한다
  4. STATUS_ACCESS_VIOLATION 예외가 드라이버의 __try로 전달된다
I/O가 필요 없는 트랜지션 폴트라도 워킹셋 락 획득 등이 필요하므로 DISPATCH_LEVEL 이상에서는 처리되지 않습니다. "운 좋게 Active면 괜찮고 아니면 죽는" 전형적인 간헐 버그입니다.

10개 프로세스가 매핑한 공유 파일 페이지가 모든 워킹셋에서 트림된 뒤 물리 페이지가 재사용될 때, 메모리 관리자가 고쳐 쓰는 PTE는?

  1. 10개 프로세스의 하드웨어 PTE 모두
  2. 프로토타입 PTE 하나
  3. 마지막으로 접근한 프로세스의 PTE 하나
  4. 고칠 필요 없음 — PFN 엔트리만 갱신
트림 시점에 각 프로세스 PTE는 이미 "프로토타입 PTE를 보라" 형식으로 돌아가 있습니다. 재사용 시에는 PFN의 PteAddress가 가리키는 프로토타입 PTE만 파일 참조 형식으로 바꾸면 됩니다.

프로세스가 종료될 때, 그 프로세스의 개인 메모리 중 수정 리스트에 있던 페이지는?

  1. Modified Page Writer가 페이지 파일에 기록한 뒤 스탠바이로 간다
  2. 스탠바이로 가서 다음 실행 때 재사용된다
  3. 기록 없이 Free 리스트로 간다
  4. 메모리 압축 저장소로 이동한다
종료된 프로세스의 개인 데이터는 다시 읽힐 일이 없으므로 기록할 이유가 없습니다. 반면 파일 기반 페이지는 파일 내용이므로 더티면 기록되고, 깨끗하면 캐시로 스탠바이에 남습니다.

ExAllocatePool2에 대한 설명으로 옳은 것은?

  1. Paged 풀은 DISPATCH_LEVEL에서도 할당할 수 있다
  2. 반환된 메모리는 이전 내용을 그대로 담고 있으므로 직접 0으로 채워야 한다
  3. 기본으로 0 초기화되며, 태그 'xtCM'은 도구에서 "MCtx"로 표시된다
  4. 실패하면 항상 예외를 던지므로 NULL 검사가 필요 없다
ExAllocatePool2는 POOL_FLAG_UNINITIALIZED를 주지 않는 한 0으로 초기화합니다. 실패 시 기본은 NULL 반환(POOL_FLAG_RAISE_ON_FAILURE일 때만 예외), Paged 풀 할당은 APC_LEVEL 이하에서만 가능합니다.

핵심 요약

  • 예약(VAD만) → 커밋(커밋 차지, 약속) → 터치(물리 페이지, 워킹셋). 커밋 한도 ≈ RAM + 페이지 파일이며 초과 시 물리 메모리가 남아도 실패한다.
  • VAD는 시작 VPN을 키로 한 AVL 트리. PTE는 지연 생성되며 0 PTE 폴트 시 VAD를 보고 만들어진다.
  • #PF → KiPageFault → MmAccessFault → 디맨드 제로 / 트랜지션(소프트) / 페이지 파일(하드) / 프로토타입 / 권한(CoW·가드·AV). DISPATCH_LEVEL 이상의 폴트는 해결 불가.
  • 공유 메모리는 섹션(CONTROL_AREA·SEGMENT·SUBSECTION)의 프로토타입 PTE로 구현되어, 페이지 회수 시 고칠 곳이 하나다.
  • PFN DB가 물리 페이지 상태를 기록한다. Zero/Free/Standby/Modified 리스트와 Active 상태 사이를 폴트·트림·MPW·제로 스레드·종료가 이동시킨다. 사용 가능 = Zero + Free + Standby.
  • 커널 풀: NonPaged(모든 IRQL 접근) vs Paged(≤ APC_LEVEL). ExAllocatePool2 + 고유 태그 + ExFreePoolWithTag. 19H1부터 세그먼트 힙 기반.
  • 메모리 압축은 수정 페이지를 디스크 대신 메모리 저장소에 압축해 담아 하드 폴트를 줄인다.
