Part IV · Chapter 10

객체 관리자와 핸들

파일, 프로세스, 이벤트, 레지스트리 키 — 겉모습이 다른 이 모든 자원을 커널은 하나의 추상 객체로 다룹니다. 그 통일된 세계를 만드는 것이 객체 관리자(Object Manager)입니다.

핵심⏱ 약 90분선수: 01 아키텍처, 04 프로세스/스레드

학습 목표

  • 객체의 물리적 구조(OBJECT_HEADER + 본문 + 선택적 헤더)와 InfoMask로 선택적 헤더 위치를 계산하는 방식을 설명할 수 있다.
  • 객체 타입(OBJECT_TYPE)과 타입별 프로시저(Open/Close/Delete/Parse/Security)가 객체 수명과 열기 과정에서 언제 호출되는지 안다.
  • 핸들 값이 핸들 테이블을 거쳐 객체로 변환되는 과정과, 핸들 수·포인터(참조) 수가 객체 수명을 어떻게 결정하는지 추적할 수 있다.
  • 객체 네임스페이스(\Device, \??, \BaseNamedObjects 등)와 심볼릭 링크를 통해 이름 기반 열기가 파싱되는 흐름을 그릴 수 있다.

왜 "객체"로 통일하는가

커널이 관리하는 자원은 종류가 많습니다 — 프로세스, 스레드, 파일, 이벤트, 세마포어, 섹션(메모리 매핑), 레지스트리 키, 토큰, 타이머, 잡(Job)…. 이들을 제각각 다루면 이름 짓기, 보안 검사, 수명 관리, 핸들 부여를 자원마다 새로 구현해야 합니다. NT는 이 공통 관심사를 객체 관리자(Object Manager, Ob*) 한 곳으로 모았습니다.

덕분에 CloseHandle 하나로 어떤 종류의 핸들이든 닫을 수 있고, \BaseNamedObjects\MyEvent처럼 모든 객체에 같은 규칙으로 이름을 붙일 수 있으며, 모든 열기(open)가 동일한 접근 검사(13장)를 거칩니다. 객체 관리자는 NT를 객체 기반 운영체제로 만드는 중심 축입니다.

전문가 관점

EDR·루트킷·익스플로잇의 상당수가 이 계층에서 벌어집니다. 핸들 복제로 LSASS 메모리에 접근하거나(PROCESS_VM_READ), 이름 충돌로 권한 상승을 노리거나, 참조 카운트 불균형(누수/UAF)으로 커널 메모리를 조작합니다. 객체 수명과 네임스페이스를 정확히 이해하는 것은 공격·방어 양쪽의 기본기입니다.

객체의 메모리 레이아웃

하나의 객체는 메모리에서 [선택적 헤더들] → OBJECT_HEADER → 객체 본문 순으로 놓입니다. ObReferenceObjectByHandle 같은 함수가 반환하는 "객체 포인터"는 본문의 시작 주소를 가리킵니다. 그래서 OBJECT_HEADER는 본문 바로 앞에 있고, 선택적 헤더들은 그보다 더 앞(낮은 주소)에 역순으로 쌓입니다.

InfoMask — 가변 헤더를 찾는 법

InfoMask는 비트맵입니다. 어떤 선택적 헤더가 존재하는지 비트로 표시하고, 커널은 원하는 헤더의 비트와 그보다 낮은 비트들만 남긴 값(InfoMask & ((Bit << 1) - 1))으로 ObpInfoMaskToOffset 테이블을 인덱싱해, 그 헤더가 OBJECT_HEADER로부터 얼마나 앞에 있는지를 상수 시간에 구합니다. 즉 낮은 비트의 헤더(CreatorInfo)일수록 OBJECT_HEADER에 가깝습니다. 아래 시뮬레이터로 비트를 켜고 끄며 레이아웃이 어떻게 바뀌는지 보세요.

객체 타입과 타입별 프로시저

같은 "열기/닫기/삭제"라도 파일과 이벤트는 동작이 다릅니다. 이 타입별 차이를 담는 것이 OBJECT_TYPE 구조체이며, 그 안의 TypeInfo에는 타입 프로시저 함수 포인터들이 들어 있습니다. 객체 관리자는 공통 뼈대를 돌리다가 "이 타입만의 동작"이 필요한 지점에서 이 콜백들을 호출합니다.

OBJECT_TYPE의 핵심

  • Name — "Process", "File", "Event" 등 타입 이름.
  • TotalNumberOfObjects/Handles — 현재 인스턴스 수(진단용).
  • TypeInfo — 풀 타입, 기본 접근권, 유효 접근 마스크(ValidAccessMask), 그리고 아래 프로시저들.
  • Key — 풀 태그(예: Proc, File, Even).

타입 프로시저 (선택적 콜백)

  • OpenProcedure — 핸들을 새로 만들 때(생성·열기·복제·상속).
  • CloseProcedure — 핸들을 닫을 때.
  • DeleteProcedure — 마지막 참조가 사라져 객체를 파괴할 때.
  • ParseProcedure — 이름 경로에 남은 부분을 넘겨 해석하게 할 때.
  • SecurityProcedure — 보안 설명자 질의/설정.
  • QueryNameProcedure — 이름을 역으로 조회할 때.
Parse 프로시저가 네임스페이스를 "확장"한다

\Device\HarddiskVolume3\dir\file.txt에서 객체 관리자는 \Device\HarddiskVolume3(디바이스 객체)까지만 알고, 그 뒤 \dir\file.txt는 모릅니다. 디바이스 타입의 Parse 프로시저(IopParseDevice)가 나머지 경로를 받아 파일 시스템 드라이버에게 넘기죠. 레지스트리 키(CmpParseKey)도 같은 방식입니다. 즉 객체 관리자 네임스페이스는 Parse를 통해 파일시스템·레지스트리 같은 다른 네임스페이스로 이어집니다.

핸들 테이블

유저 모드 코드는 객체의 커널 주소를 직접 만질 수 없습니다. 대신 핸들(HANDLE) — 프로세스별 핸들 테이블의 인덱스 — 을 받습니다. CreateFileW가 돌려주는 0x1a4 같은 값이 그것이고, 이는 "내 프로세스 핸들 테이블에서 몇 번째 칸"이라는 뜻입니다.

핸들 테이블은 메모리를 아끼기 위해 최대 3단계의 트리로 구성됩니다. 핸들이 몇 개 없으면 1단계만, 많아지면 2·3단계로 확장됩니다. 각 테이블 페이지는 여러 개의 HANDLE_TABLE_ENTRY를 담습니다.

가짜 핸들(pseudo handle)과 커널 핸들

GetCurrentProcess()는 실제 핸들이 아니라 (HANDLE)-1이라는 가짜 핸들을 돌려줍니다. 커널은 이 특수 값을 "현재 프로세스"로 해석합니다(-2는 현재 스레드). 테이블을 거치지 않으므로 빠르고 닫을 필요도 없습니다.

핸들의 최상위 비트가 켜지면(OBJ_KERNEL_HANDLE) 커널 핸들 테이블(System 프로세스, PID 4)에 속합니다. 유저 모드에서 접근할 수 없어, 드라이버가 자신의 핸들을 유저가 건드리지 못하게 보호할 때 씁니다(OBJ_KERNEL_HANDLE 플래그).

객체 수명: 핸들 수 vs 포인터 수

객체는 언제 사라질까요? "아무도 안 쓸 때"입니다. 그런데 "쓴다"에는 두 가지가 있습니다.

HandleCount (핸들 수)

유저/커널 코드가 이 객체에 대해 열어 둔 핸들의 개수. CreateX/OpenX로 늘고 CloseHandle로 줍니다. 핸들을 하나 만들면 보통 PointerCount도 함께 올라갑니다.

PointerCount (참조 수)

핸들 참조 + 커널 코드가 포인터로 직접 잡고 있는 참조의 합. ObReferenceObject*로 늘고 ObDereferenceObject로 줍니다. 핸들이 전혀 없어도 커널이 포인터로 붙잡고 있으면 객체는 살아 있습니다.

객체는 PointerCount가 0이 될 때 파괴됩니다 — HandleCount가 아니라. HandleCount가 0이 되면 CloseProcedure가 돌고, 이름이 있던 객체라면 네임스페이스에서 떨어져 나오지만, 커널이 여전히 참조를 들고 있으면 메모리는 유지됩니다. 마지막 참조까지 풀려 PointerCount=0이 되면 DeleteProcedure가 호출되고 메모리가 반환됩니다.

참조 카운트 버그 = 커널 취약점

참조 누수(dereference를 빼먹음)는 객체가 영원히 살아 메모리를 잠식합니다. 반대로 과다 해제(dereference를 한 번 더)는 PointerCount가 조기에 0이 되어 Use-After-Free를 만들고, 공격자가 그 자리에 가짜 객체를 심으면 커널 권한 탈취로 이어집니다. 드라이버 리뷰에서 ref/deref 짝 맞추기는 1순위 점검 항목입니다.

객체 네임스페이스

객체 관리자는 파일 시스템처럼 계층형 이름 공간을 유지합니다. 루트는 \이고, 디렉터리 객체(\Device, \Driver 등)와 심볼릭 링크 객체로 트리를 이룹니다. 이 트리는 Sysinternals WinObj로 눈으로 볼 수 있습니다. 아래 탐색기로 주요 가지를 둘러보세요.

왼쪽 트리에서 항목을 클릭하면 설명이 나옵니다.
\?? 와 DOS 디바이스 맵 — "C:"의 정체

C:, COM1, \\.\PhysicalDrive0 같은 DOS 장치 이름은 실제 디바이스 객체가 아니라 \?? 아래의 심볼릭 링크입니다. 예: \??\C: → \Device\HarddiskVolume3. 과거엔 \DosDevices로 불렸고 지금도 별칭으로 존재합니다.

중요한 점: \??는 세션·로그온별로 다릅니다. 각 로그온 세션은 전역 \GLOBAL??에 자기만의 드라이브 매핑(예: 네트워크 드라이브 Z:)을 덧씌운 프로세스별 DOS 디바이스 맵을 봅니다. 그래서 서비스(세션 0)에서 보이는 Z:와 사용자 세션의 Z:가 다를 수 있습니다 — 서비스 개발의 흔한 함정입니다.

이름으로 객체 열기 — 파싱 흐름

\??\C:\Users\me\a.txt를 여는 과정을 따라가 봅시다. 객체 관리자(ObpLookupObjectName)가 경로를 한 조각씩 내려가며 디렉터리를 뒤지고, 심볼릭 링크를 만나면 치환하고, Parse 프로시저가 있는 객체를 만나면 나머지 경로를 통째로 넘깁니다.

이름 충돌과 BaseNamedObjects — 스쿼팅 공격

CreateMutex(L"Global\\MyApp")는 \BaseNamedObjects\MyApp에 객체를 만들려 합니다(Global\ 접두사 없이는 세션별 \Sessions\N\BaseNamedObjects). 권한 낮은 공격자가 먼저 같은 이름의 객체를 선점하고 약한 DACL을 걸면, 나중에 그 이름을 여는 특권 서비스가 공격자 객체를 쓰게 될 수 있습니다(name squatting). 방어: 전용 디렉터리 + 강한 DACL, 또는 CreateXxx 성공 시 GetLastError()==ERROR_ALREADY_EXISTS 확인, Private Namespace(CreatePrivateNamespace) 사용.

확인 문제

객체가 메모리에서 실제로 파괴(DeleteProcedure 호출)되는 시점은?

  1. HandleCount가 0이 될 때
  2. PointerCount가 0이 될 때
  3. 마지막 CloseHandle이 호출될 때 항상
  4. 프로세스가 종료될 때만
핸들이 모두 닫혀 HandleCount=0이 되어도 커널이 ObReferenceObject로 참조를 들고 있으면 PointerCount>0이라 객체는 살아 있습니다. PointerCount가 0이 되어야 삭제됩니다. 핸들 참조도 PointerCount에 포함되므로, 핸들도 참조도 없을 때 비로소 0이 됩니다.

\??\C:의 정체로 가장 정확한 것은?

  1. 디스크 컨트롤러 디바이스 객체
  2. NTFS 볼륨의 루트 디렉터리 파일
  3. 프로세스별 DOS 디바이스 맵의 심볼릭 링크 객체 (→ \Device\HarddiskVolumeN)
  4. 레지스트리 키
C:는 심볼릭 링크입니다. \??는 세션/로그온별로 달라지며, 전역 매핑은 \GLOBAL??에 있습니다. 그래서 서비스와 사용자 세션의 드라이브 문자가 다를 수 있습니다.

객체 관리자가 \Device\HarddiskVolume3\dir\a.txt에서 \dir\a.txt 부분을 처리하는 방법은?

  1. 객체 디렉터리 트리를 계속 내려가며 각 조각을 디렉터리로 검색한다
  2. 디바이스 타입의 ParseProcedure(IopParseDevice)에 잔여 경로를 넘겨 파일 시스템이 해석하게 한다
  3. 심볼릭 링크로 재귀 치환한다
  4. SecurityProcedure가 경로를 해석한다
객체 관리자 네임스페이스는 디바이스 객체까지만 알고, 그 아래 파일 경로는 모릅니다. Parse 프로시저가 네임스페이스를 파일시스템으로 확장합니다. 레지스트리 키의 CmpParseKey도 동일한 패턴입니다.

핸들 값 0x1A4에서 "인덱스"를 얻으려면?

  1. 그대로 사용한다
  2. 하위 2비트(태그 비트)를 버린다 — 오른쪽으로 2비트 시프트
  3. 최상위 비트를 제거한다
  4. 객체 헤더 크기를 뺀다
핸들 값의 하위 2비트는 태그 비트로 커널이 무시합니다. 실제 테이블 인덱스는 handle >> 2입니다. 다단계 테이블의 레벨은 핸들 값이 아니라 HANDLE_TABLE.TableCode의 하위 비트가 알려 줍니다.

드라이버가 객체에 대한 참조를 ObReferenceObjectByHandle로 얻은 뒤 작업을 끝냈습니다. 빠뜨리면 안 되는 것은?

  1. CloseHandle로 핸들을 닫는다
  2. ObDereferenceObject로 참조를 1 내린다
  3. 객체 메모리를 ExFreePool로 해제한다
  4. 아무것도 필요 없다 — 커널이 자동 정리한다
ObReferenceObjectByHandle은 PointerCount를 올립니다. 짝이 되는 ObDereferenceObject를 호출하지 않으면 참조 누수로 객체가 영원히 남습니다. 객체 메모리를 직접 해제하는 것은 절대 금물입니다(과다 해제 → UAF).

OBJECT_HEADER.TypeIndex가 Windows 10 이후 XOR로 난독화된 주된 이유는?

  1. 메모리를 절약하려고
  2. 타입 혼동(type confusion) 익스플로잇을 어렵게 하려고 — 타입 인덱스를 임의로 덮어쓰기 힘들게
  3. 다국어 지원을 위해
  4. 캐시 성능을 위해
공격자가 객체 헤더를 덮어써 타입을 바꾸면(예: Event를 Process로 둔갑) 엉뚱한 타입 프로시저가 호출돼 권한 상승이 가능합니다. TypeIndex를 헤더 주소·전역 ObHeaderCookie와 XOR해 저장하면, 유효한 값을 위조하기 어려워집니다.

핵심 요약

  • 객체 = (선택적 헤더들) + OBJECT_HEADER + 본문. InfoMask가 어떤 선택적 헤더가 있는지 나타내고 오프셋 테이블로 위치를 구한다.
  • OBJECT_TYPE의 타입 프로시저(Open/Close/Delete/Parse/Security)가 공통 뼈대에 타입별 동작을 끼워 넣는다. 특히 Parse가 네임스페이스를 파일시스템·레지스트리로 확장한다.
  • 핸들 값 → (플래그 제거) → 다단계 핸들 테이블 인덱스 → HANDLE_TABLE_ENTRY(객체 포인터+부여 접근권) → 객체 본문.
  • 수명은 PointerCount가 결정한다. 핸들이 다 닫혀도 커널 참조가 남으면 산다. ref/deref 불균형은 누수 또는 UAF.
  • 네임스페이스: \Device, \Driver, \BaseNamedObjects, \Sessions, \KnownDlls, \??(세션별 DOS 맵, 전역은 \GLOBAL??). C:는 심볼릭 링크.
