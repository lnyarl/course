시스템 콜과 모드 전환

유저 코드가 커널에게 일을 맡기는 유일한 정문. syscall 명령 하나가 실행되는 동안 CPU와 커널이 하는 일을 레지스터 단위로 따라갑니다.

입문⏱ 약 75분선수: 01장, x64 레지스터 기초

학습 목표

  • 모드 전환이 왜 필요한지, 왜 스레드마다 유저 스택과 커널 스택이 따로 있는지 설명할 수 있다.
  • ntdll 시스템 서비스 스텁의 각 명령과 syscall/sysret의 하드웨어 동작, 관련 MSR의 역할을 설명할 수 있다.
  • KiSystemCall64가 스택 전환 → 트랩 프레임 저장 → 서비스 테이블 조회 → 인자 복사 → 복귀를 수행하는 순서를 그릴 수 있다.
  • 서비스 번호의 비트 의미와 서비스 테이블의 상대 오프셋 인코딩을 해석할 수 있다.
  • PreviousMode, ProbeForRead/Write, Nt와 Zw의 차이를 정확히 구분할 수 있다.

왜 모드 전환이 필요한가

01장에서 본 것처럼 유저 모드(CPL 3) 코드는 특권 명령을 실행할 수 없고, 커널 메모리에도 접근할 수 없습니다. 그런데 파일 읽기, 메모리 할당, 스레드 생성처럼 하드웨어나 공유 자원을 다루는 일은 모두 커널만 할 수 있습니다. 그래서 유저 코드에는 "정해진 입구로만 커널에 들어가는" 통로가 필요합니다. 이것이 시스템 콜입니다.

핵심은 입구가 커널이 정한 단 한 곳이라는 점입니다. 유저 코드가 커널 안의 임의 주소로 점프할 수 있다면 보호는 의미가 없습니다. x64에서 그 입구 주소는 커널만 쓸 수 있는 MSR(IA32_LSTAR)에 들어 있고, syscall 명령은 그 주소로만 갑니다. 유저가 고를 수 있는 것은 "몇 번 서비스를 원하는가"(서비스 번호)와 인자뿐이며, 커널은 그 둘을 믿지 않고 검증합니다.

스레드 하나, 스택 둘

시스템 콜은 다른 스레드에게 일을 넘기는 것이 아니라 같은 스레드가 모드만 바꿔 커널 코드를 실행하는 것입니다. 그런데 커널 코드는 유저 스택을 그대로 쓸 수 없습니다. 이유는 세 가지입니다.

신뢰할 수 없다

유저 RSP는 유저가 마음대로 정한 값입니다. 커널 주소나 매핑되지 않은 주소를 가리킬 수도 있습니다.

동시에 바뀔 수 있다

같은 프로세스의 다른 스레드가 이 유저 스택 메모리를 언제든 덮어쓰거나 해제할 수 있습니다.

커널 데이터 노출

커널이 유저 스택에 지역 변수를 두면, 커널 포인터나 비밀 값이 유저에게 그대로 보입니다.

그래서 Windows는 스레드마다 커널 스택을 따로 할당합니다(KTHREAD.InitialStack/StackLimit, x64 기본 크기는 수십 KB 수준이며 GUI 스레드 등은 필요 시 확장). 커널 진입 직후 가장 먼저 하는 일이 이 커널 스택으로 갈아타는 것입니다.

Win32 API에서 ntdll 스텁까지

ReadFile을 호출하면 kernel32 → kernelbase를 거쳐 Win32 의미(예: 동기/비동기 처리, 오류 코드 변환)를 네이티브 인자로 바꾼 뒤 ntdll!NtReadFile을 호출합니다. GUI 계열(user32/gdi32)은 win32u.dll의 스텁을 거칩니다. 두 DLL의 스텁은 모양이 같고, 사용하는 서비스 번호 범위만 다릅니다.

계층예하는 일
Win32 APIkernel32!ReadFile → kernelbase!ReadFile문서화된 계약. 핸들/오버랩 처리, NTSTATUS → GetLastError 값 변환
네이티브 API 스텁ntdll!NtReadFile서비스 번호를 eax에 넣고 syscall. 로직 없음
GUI 스텁win32u!NtUserGetMessage같은 형태, 번호가 0x1000 이상 → win32k 테이블

스텁 하나를 명령 단위로 뜯어 봅시다. 각 줄을 클릭하면 의미가 표시됩니다.

스텁에는 로직이 없다

Nt 스텁은 인자를 전혀 건드리지 않습니다. 인자 검증, 핸들 해석, 접근 검사는 전부 커널의 nt!NtReadFile이 합니다. 유저 모드의 어떤 검사도 보안 경계가 아니라는 원칙이 여기서 드러납니다 — 유저 모드 코드는 유저가 바꿀 수 있기 때문입니다.

syscall / sysret의 하드웨어 동작

syscall은 AMD가 도입하고 x64에서 표준이 된 "빠른 시스템 콜" 명령입니다. 인터럽트 방식보다 빠른 이유는 CPU가 하는 일이 극히 적기 때문입니다. IDT 조회도, 디스크립터 권한 검사도, 스택 전환도, 메모리에 push하는 것도 없습니다. 레지스터 몇 개를 바꾸는 것이 전부이고, 나머지는 모두 커널 소프트웨어의 책임입니다. 

; syscall  (64비트 모드, CPL 3 → 0)
RCX    = RIP                       ; 다음 명령 주소 (복귀 지점)
R11    = RFLAGS                    ; 플래그 보존
RFLAGS = RFLAGS AND NOT IA32_FMASK ; IF 등 지정 비트를 끈다 → 인터럽트 금지 상태로 진입
CS.sel = IA32_STAR[47:32]          ; 0x10  (CPL = 0)
SS.sel = IA32_STAR[47:32] + 8      ; 0x18
RIP    = IA32_LSTAR                ; nt!KiSystemCall64 (또는 ...Shadow)
; RSP는 그대로!  스택에 아무것도 push하지 않는다!

; sysretq  (CPL 0 → 3)
RIP    = RCX
RFLAGS = R11                       ; (일부 비트는 정리됨)
CS.sel = IA32_STAR[63:48] + 16     ; 0x33  (RPL = 3)
SS.sel = IA32_STAR[63:48] + 8      ; 0x2B
; RSP는 역시 그대로 → 커널이 sysret 직전에 유저 RSP를 직접 되돌려 놓아야 한다
MSR번호Windows에서의 역할
IA32_EFERC0000080비트 0(SCE)이 켜져 있어야 syscall/sysret이 동작. 꺼져 있으면 #UD
IA32_STARC0000081[47:32] 커널 CS 셀렉터 기준(0x10 → SS 0x18), [63:48] 복귀 기준(0x23 → 64비트 CS 0x33, SS 0x2B)
IA32_LSTARC000008264비트 코드에서 syscall 시 점프할 RIP = 시스템 콜 진입점
IA32_CSTARC0000083호환 모드(32비트 코드)에서의 진입점. WoW64는 64비트 ntdll을 거쳐 진입하므로 일반 경로가 아님
IA32_FMASKC0000084진입 시 RFLAGS에서 끌 비트 마스크(IF, TF, DF, AC 등)
IA32_KERNEL_GS_BASEC0000102swapgs가 현재 GS.base와 맞바꾸는 값. 유저 모드 동안 KPCR 주소를 보관

이 MSR들은 부팅 시 커널이 프로세서마다 설정합니다. wrmsr는 특권 명령이므로 유저는 진입점을 바꿀 수 없고, 커널 측에서도 이 값들은 무결성 감시(PatchGuard, HVCI 환경의 하이퍼바이저 보호) 대상입니다(→ 16장).

왜 IF를 끄고 들어오는가

syscall 직후의 RSP는 아직 유저 스택입니다. 이 상태에서 인터럽트가 들어오면 CPU는 이미 CPL 0이므로 스택을 바꾸지 않고 현재 스택(=유저 스택)에 프레임을 push하게 됩니다. 그래서 IA32_FMASK로 IF를 끈 채 진입하고, 커널 스택 전환이 끝난 뒤에야 sti로 인터럽트를 허용합니다. 같은 이유로 swapgs 전후 몇 명령은 매우 정교하게 짜여 있습니다.

KiSystemCall64: 커널 진입 루틴

IA32_LSTAR가 가리키는 nt!KiSystemCall64는 CPU가 하지 않은 나머지 일을 모두 해야 합니다. 아래 스테퍼는 ReadFile 한 번이 커널을 왕복하는 동안 오른쪽 레지스터 값이 어떻게 바뀌는지 보여줍니다.

진입부를 단순화하면 다음과 같습니다. 실제 코드는 빌드마다 다르고 KVA Shadow, 디버깅, 계측(instrumentation) 처리 등이 섞여 있으니 반드시 u nt!KiSystemCall64로 대조하세요.

swapgs                                  ; GS.base ← KPCR
mov   gs:[KPCR.UserRsp], rsp            ; 유저 RSP 임시 보관
mov   rsp, gs:[KPCR.Prcb.RspBase]       ; 커널 스택으로 전환
push  2Bh                               ; 유저 SS
push  qword ptr gs:[KPCR.UserRsp]       ; 유저 RSP
push  r11                               ; 유저 RFLAGS
push  33h                               ; 유저 CS
push  rcx                               ; 유저 RIP (복귀 주소)
; ... KTRAP_FRAME의 나머지 공간 확보, rax/r10/rdx/r8/r9 등 저장
sti                                     ; 이제 인터럽트 허용
; ... PreviousMode 기록, 스레드의 TrapFrame 갱신
; KiSystemServiceStart / KiSystemServiceRepeat:
;   edi = (eax >> 7) & 20h  → 테이블 디스크립터 선택 (비트 12)
;   eax = eax & 0FFFh        → 테이블 인덱스
KPCR과 KPRCB

KPCR(Processor Control Region)은 프로세서마다 하나씩 있는 구조체이고, 그 안에 더 큰 KPRCB(Processor Control Block)가 들어 있습니다. 커널 모드에서는 항상 gs:가 현재 프로세서의 KPCR을 가리키므로 "지금 이 CPU에서 실행 중인 스레드", "그 스레드의 커널 스택 꼭대기" 같은 정보를 레지스터 하나로 찾을 수 있습니다. 컨텍스트 스위치 때 커널이 RspBase를 새 스레드의 값으로 갱신합니다.

트랩 프레임 (KTRAP_FRAME)

트랩 프레임은 "커널에 들어오기 직전의 유저 상태" 중 커널이 저장해야 하는 부분입니다. 시스템 콜뿐 아니라 인터럽트, 예외 진입에서도 같은 구조체가 만들어집니다. 스레드의 KTHREAD.TrapFrame이 가장 최근 트랩 프레임을 가리키므로, 디버거의 .trap 명령이나 컨텍스트 조회(GetThreadContext)가 여기서 유저 레지스터를 읽습니다. 아래는 x64 KTRAP_FRAME의 주요 영역을 낮은 주소부터 나열한 것입니다. 각 영역을 클릭하세요.

서비스 디스패치 테이블

서비스 번호를 실제 함수로 바꾸는 표가 시스템 서비스 디스패치 테이블(흔히 SSDT)입니다. 커널에는 두 개의 서비스 디스크립터 테이블이 있고, 각 디스크립터에는 최대 두 개의 서비스 테이블이 등록됩니다.

디스크립터[0] (번호 0x0000–0x0FFF)[1] (번호 0x1000–0x1FFF)사용하는 스레드
KeServiceDescriptorTablent!KiServiceTable(비어 있음)일반(비 GUI) 스레드
KeServiceDescriptorTableShadownt!KiServiceTablewin32k!W32pServiceTableGUI 스레드

각 디스크립터 항목(KSERVICE_TABLE_DESCRIPTOR)은 Base(테이블 주소), Count, Limit(서비스 개수), Number(인자 테이블) 네 필드로 이루어집니다. 스레드는 KTHREAD.ServiceTable로 어느 디스크립터를 쓸지 가리키며, 처음에는 모두 일반 디스크립터를 씁니다. 일반 스레드가 처음 win32k 서비스를 호출하면 [1]의 Limit이 0이라 인덱스 검사에 실패하는데, 이때 커널은 오류 대신 스레드를 GUI 스레드로 변환(win32k 쪽 스레드 정보 할당, 더 큰 커널 스택 준비 등)하고 Shadow 디스크립터로 바꾼 뒤 재시도합니다. 최근 Windows에는 Win32k 시스템 콜 필터링 정책이 적용된 프로세스를 위한 필터 디스크립터도 있습니다.

번호의 비트 의미와 상대 오프셋 인코딩

eax의 비트 12가 디스크립터 안의 테이블([0] 또는 [1])을 고르고, 비트 0–11이 테이블 인덱스입니다(그래서 테이블당 최대 4096개). x64의 서비스 테이블 엔트리는 64비트 포인터가 아니라 32비트 값입니다. 상위 28비트는 테이블 시작 주소로부터의 부호 있는 상대 오프셋, 하위 4비트는 스택으로 전달되는 인자 개수입니다. 

LONG  entry   = ServiceTable[index];        // 32비트 엔트리
PVOID routine = (PUCHAR)ServiceTable + (entry >> 4);  // 산술 시프트: 부호 유지
ULONG stackArgs = entry & 0xF;              // 5번째 이후 인자 수 → 복사할 8바이트 개수

이렇게 하면 테이블 크기가 절반이 되고, 엔트리가 로드 주소와 무관하므로 KASLR로 커널 위치가 바뀌어도 테이블 내용은 재배치가 필요 없습니다. 인자 개수까지 한 엔트리에 담겨 디스패처가 메모리를 한 번만 읽으면 됩니다. 대가는 오프셋 범위가 ±128MB(28비트)로 제한된다는 점입니다.

PreviousMode와 인자 검증

같은 nt!NtReadFile이 유저의 요청도, 커널 구성요소의 요청도 처리합니다. 유저가 준 포인터는 검증해야 하지만, 커널이 준 커널 버퍼 포인터는 검증하면 오히려 실패합니다. 서비스는 이를 KTHREAD.PreviousMode로 구분합니다. 이름 그대로 "이 서비스를 요청한 쪽의 모드"이지 현재 CPU 모드가 아닙니다(서비스 코드는 언제나 CPL 0에서 실행됩니다). 드라이버는 ExGetPreviousMode()로 읽습니다.

ProbeForRead / ProbeForWrite

PreviousMode가 UserMode이면 서비스는 유저 포인터를 사용하기 전에 프로브합니다. 프로브는 정렬과 범위가 유저 주소 공간 안에 있는지(MmUserProbeAddress 미만)를 확인하고, 실패하면 예외를 발생시킵니다. 주의할 점은 프로브가 "지금 이 순간 접근 가능함"을 보장하지 않는다는 것입니다. 다른 스레드가 직후에 메모리를 해제하거나 보호 속성을 바꿀 수 있으므로, 유저 메모리 접근은 전부 __try/__except 안에서 해야 하고, 검사에 쓴 값은 커널 쪽으로 한 번 복사(캡처)한 뒤 그 사본만 써야 합니다. 

NTSTATUS QueryValue(_Out_writes_bytes_(Length) PVOID Buffer, ULONG Length)
{
    KPROCESSOR_MODE mode = ExGetPreviousMode();
    ULONG value = ComputeValue();

    if (Length < sizeof(ULONG))
        return STATUS_BUFFER_TOO_SMALL;

    if (mode != KernelMode) {
        __try {
            ProbeForWrite(Buffer, Length, sizeof(ULONG));  // 범위·정렬 검사
            *(ULONG *)Buffer = value;                      // 접근도 __try 안에서
        } __except (EXCEPTION_EXECUTE_HANDLER) {
            return GetExceptionCode();                     // 잘못된 포인터 → 오류 반환
        }
    } else {
        *(ULONG *)Buffer = value;                          // 커널 호출자: 신뢰
    }
    return STATUS_SUCCESS;
}

Nt vs Zw, 그리고 커널 내부 호출 경로

ntoskrnl에는 서비스마다 Nt 버전(실제 구현)과 Zw 버전(커널용 진입 래퍼)이 있습니다. 유저 모드의 ntdll에서는 두 이름이 같은 스텁을 가리키므로 차이가 없습니다. 커널의 Zw 함수는 시스템 콜을 흉내 내는 작은 스텁입니다. 

mov   rax, rsp
cli
sub   rsp, 10h
push  rax                    ; 원래 RSP  ┐
pushfq                       ; RFLAGS   │ 인터럽트 프레임과 같은 모양을
push  10h                    ; 커널 CS   │ 스택에 직접 구성
lea   rax, [nt!KiServiceLinkage]
push  rax                    ; 복귀 RIP  ┘
mov   eax, 6                 ; 서비스 번호 (ntdll과 동일)
jmp   nt!KiServiceInternal   ; PreviousMode = KernelMode 로 설정 후 디스패치

KiServiceInternal은 현재 PreviousMode를 트랩 프레임에 보관하고 KernelMode로 설정한 뒤, 시스템 콜과 같은 디스패치 경로로 NtReadFile을 호출합니다. 복귀할 때 보관한 값을 되돌립니다. 아래 스테퍼에서 세 가지 호출 방식을 비교해 보세요.

PreviousMode가 결정하는 것들

프로브 여부만이 아닙니다. 핸들 참조(ObReferenceObjectByHandle의 AccessMode), 접근 검사, 특권 검사, 대기의 경고 가능성(alertable) 처리 등 많은 결정이 "요청자 모드"를 인자로 받습니다. 드라이버가 이런 API에 KernelMode를 넘기면 "검사하지 말라"는 뜻이 되므로, 유저에게서 온 값을 다룰 때는 UserMode(또는 ExGetPreviousMode())를 넘기는 것이 안전한 기본값입니다.

다른 커널 진입 경로와의 비교

CPU가 커널로 들어가는 길은 시스템 콜만이 아닙니다. 예외와 인터럽트는 IDT(Interrupt Descriptor Table)를 거치며, CPU가 더 많은 일을 대신 해줍니다. 그러나 도착 후 커널이 만드는 것은 결국 같은 KTRAP_FRAME입니다.

  • TSS.RSP0: 컨텍스트 스위치 때 커널이 새 스레드의 커널 스택 꼭대기를 기록해 두는 곳입니다. 유저 모드에서 인터럽트가 들어오면 CPU가 이 값을 읽어 스택을 바꿉니다.
  • IST(Interrupt Stack Table): NMI, 더블 폴트, 머신 체크처럼 현재 스택을 믿을 수 없는 이벤트는 IDT 엔트리에 지정한 별도의 프로세서별 스택으로 무조건 전환합니다.
  • 예외의 행방: 유저 모드 예외는 KiDispatchException을 거쳐 ntdll의 KiUserExceptionDispatcher로 "되돌려 보내져" SEH/VEH가 처리합니다. 커널 모드 예외가 처리되지 않으면 버그체크입니다.
  • 비동기성: 시스템 콜과 예외는 현재 스레드가 원인이므로 그 스레드 문맥에서 처리하는 것이 자연스럽지만, 하드웨어 인터럽트는 우연히 실행 중이던 스레드를 "빌려" 처리합니다. 그래서 ISR은 현재 프로세스 문맥에 의존하면 안 됩니다(→ 06장).

KVA Shadow가 진입 경로에 미친 영향

2018년 공개된 Meltdown(CVE-2017-5754)은 일부 CPU에서 유저 코드가 투기적 실행을 통해, 페이지 테이블에 매핑되어 있지만 접근 권한이 없는 커널 메모리 내용을 간접적으로 추론할 수 있게 하는 하드웨어 취약점이었습니다. 근본 원인이 "유저 실행 중에도 커널 전체가 페이지 테이블에 매핑되어 있다"는 점이었으므로, Windows는 KVA Shadow(Kernel Virtual Address Shadow)로 대응했습니다. 유저 모드에서 실행되는 동안에는 커널 대부분이 빠진 별도의 페이지 테이블을 쓰는 방식입니다(Linux의 KPTI와 같은 발상).

결과적으로 모든 시스템 콜·인터럽트에 CR3 교체가 더해져 시스템 콜이 잦은 작업에서 성능 비용이 생겼습니다. 그래서 Windows는 CPU가 취약한지 판단해 필요할 때만 활성화하며, WinDbg에서 IA32_LSTAR가 가리키는 함수 이름으로 현재 상태를 간단히 확인할 수 있습니다(실습 참고). 투기적 실행 완화 전반은 16장에서 다룹니다.

확인 문제

ntdll 스텁이 syscall 전에 mov r10, rcx를 실행하는 이유는?

  1. 커널이 rcx를 읽을 수 없기 때문
  2. syscall이 복귀 주소를 rcx에 덮어쓰므로 첫 번째 인자를 보존하기 위해
  3. r10에 서비스 번호를 넣어야 하기 때문
  4. 스택 정렬을 맞추기 위해
syscall은 RCX ← RIP, R11 ← RFLAGS를 수행합니다. 그래서 첫 인자는 r10으로 옮겨 전달되고 커널은 거기서 읽습니다. 서비스 번호는 eax로 전달됩니다.

syscall 직후 커널 진입점의 첫 명령이 실행될 때, RSP는 어디를 가리키나요?

  1. TSS.RSP0가 가리키는 현재 스레드의 커널 스택
  2. IST의 전용 스택
  3. 여전히 유저 스택 — 커널 스택 전환은 KiSystemCall64가 소프트웨어로 한다
  4. KPCR 구조체
syscall은 스택을 바꾸지 않습니다. 그래서 진입 루틴은 IF가 꺼진 상태에서 swapgs → 유저 RSP 보관 → KPRCB.RspBase 로드 순으로 직접 전환합니다. TSS.RSP0를 CPU가 자동으로 쓰는 것은 인터럽트·예외(및 int 2Eh) 경로입니다.

서비스 번호 0x1045를 디스패처가 해석한 결과로 옳은 것은?

  1. 테이블 0, 인덱스 0x1045
  2. 테이블 1(win32k), 인덱스 0x45
  3. 테이블 4, 인덱스 0x45
  4. 범위를 벗어나 항상 STATUS_INVALID_SYSTEM_SERVICE
비트 12(0x1000)가 1이므로 디스크립터의 두 번째 테이블(win32k), 하위 12비트 0x045가 인덱스입니다. 호출 스레드가 아직 GUI 스레드가 아니라면 처음에는 Limit 검사에 실패하지만, 커널이 GUI 스레드로 변환한 뒤 재시도합니다.

x64 서비스 테이블 엔트리 0x02B4E705의 의미는?

  1. 서비스 함수의 절대 주소 하위 32비트
  2. 오프셋 0x02B4E705, 스택 인자 0개
  3. 테이블 시작 + 0x2B4E70 위치의 함수, 스택 인자 5개
  4. 테이블 시작 + 0x02B4E70 위치의 함수, 레지스터 인자 5개
엔트리를 산술 시프트로 4비트 오른쪽으로 밀면 상대 오프셋(0x2B4E70), 하위 4비트(5)는 스택으로 전달되는 인자 수입니다. 레지스터 인자 4개는 항상 레지스터로 오므로 개수를 기록할 필요가 없습니다.

유저 요청을 처리하던 스레드에서 드라이버가 커널 버퍼를 넘겨 NtReadFile을 직접 호출했습니다. 가장 가능성 높은 결과는?

  1. 정상 동작한다. 드라이버는 이미 커널 모드이므로
  2. IRQL이 올라가 버그체크가 발생한다
  3. PreviousMode가 UserMode로 남아 있어 커널 버퍼가 프로브에서 거부되고 오류가 반환된다
  4. CPU가 #GP 예외를 발생시킨다
PreviousMode는 CPU 모드가 아니라 "요청자 모드"입니다. Nt 함수 직접 호출은 일반 함수 호출이라 PreviousMode를 바꾸지 않습니다. ZwReadFile은 KiServiceInternal을 거치며 KernelMode로 설정하므로 커널 버퍼를 정상 처리합니다.

KVA Shadow가 켜진 시스템에서 IA32_LSTAR가 KiSystemCall64가 아닌 KiSystemCall64Shadow를 가리키는 이유는?

  1. Shadow 버전이 더 빠르기 때문
  2. win32k 서비스 전용 진입점이기 때문
  3. 유저 실행 중 쓰는 페이지 테이블에는 커널 대부분이 없으므로, 양쪽에 매핑된 전환 코드에서 CR3를 먼저 바꿔야 하기 때문
  4. PatchGuard가 원본 진입점을 숨기기 때문
섀도 페이지 테이블에는 KVASCODE 같은 최소한의 전환 코드와 데이터만 매핑됩니다. 진입 직후 커널 페이지 테이블로 CR3를 바꾼 뒤에야 본래의 KiSystemCall64 경로를 실행할 수 있습니다. 비용이 추가되므로 Shadow 버전이 더 느립니다.

핵심 요약

  • 시스템 콜은 같은 스레드의 모드 전환이다. 커널은 유저 스택을 믿지 않고 스레드별 커널 스택으로 갈아탄다.
  • ntdll/win32u 스텁: mov r10,rcx → mov eax,번호 → syscall. 번호는 빌드마다 다르다.
  • syscall은 RCX/R11/CS/SS/RIP만 바꾸고 스택은 그대로 둔다. 진입점은 IA32_LSTAR, 셀렉터는 IA32_STAR, 끌 플래그는 IA32_FMASK.
  • KiSystemCall64: swapgs → 커널 스택 → KTRAP_FRAME → 비트 12로 테이블, 하위 12비트로 인덱스 → 스택 인자 복사 → 서비스 → sysretq.
  • x64 서비스 테이블 엔트리 = (상대 오프셋 << 4) | 스택 인자 수. win32k 서비스는 Shadow 디스크립터의 두 번째 테이블.
  • PreviousMode는 요청자 모드다. UserMode면 프로브와 접근 검사, Zw는 KiServiceInternal로 KernelMode를 설정한다.
  • 예외·인터럽트는 IDT와 CPU의 자동 스택 전환을 쓰지만 결국 같은 트랩 프레임을 만든다. KVA Shadow는 모든 진입·복귀에 CR3 전환을 추가했다.
