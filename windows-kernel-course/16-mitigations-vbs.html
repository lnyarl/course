Part V · Chapter 16

커널 보안 메커니즘과 VBS

Windows 커널을 지키는 하드웨어·소프트웨어·하이퍼바이저 계층의 보호 기능. 각 기능이 무엇을 막고, 드라이버 개발자는 무엇을 지켜야 하는지 방어자 관점에서 정리합니다.

전문가⏱ 약 120분선수: 08 가상 메모리 · 13 보안 모델 · 14 드라이버 개발

학습 목표

  • KASLR, NX, SMEP/SMAP, KVA Shadow가 페이지 테이블과 CPU 제어 레지스터 수준에서 어떻게 동작하는지 설명할 수 있다.
  • PatchGuard·DSE·취약 드라이버 차단 목록이 각각 무엇을 보호하며, 드라이버가 이를 위반하지 않으려면 어떻게 설계해야 하는지 안다.
  • VBS의 VTL0/VTL1 분리와 SLAT(EPT) 권한으로 HVCI가 커널 W^X를 "커널보다 높은 곳에서" 강제하는 원리를 그릴 수 있다.
  • 보안 제품이 써야 하는 공식 인터페이스(콜백, 미니필터, ETW, ELAM)를 구분하고, HVCI 호환 드라이버 체크리스트를 적용할 수 있다.
이 챕터의 범위

이 챕터는 방어자·시스템 관리자·드라이버 개발자의 시선으로 보호 기능의 목적과 동작, 호환성 규칙을 다룹니다. 보호 기능을 우회하는 방법이나 익스플로잇 기법은 다루지 않습니다. "어떤 범주의 시도가 막히는가"는 개념 수준으로만 설명합니다.

심층 방어와 보호 기능의 역사

커널 버그 하나는 곧 시스템 전체의 권한입니다. 그래서 Windows는 "버그를 없앤다"는 목표와 별개로, 버그가 있어도 악용을 어렵게 만드는 층을 겹겹이 쌓아 왔습니다. 이 접근을 심층 방어(defense in depth)라고 합니다. 각 층은 서로 다른 단계를 겨냥합니다.

① 정보 숨기기

KASLR, KVA Shadow. 공격에 필요한 커널 주소·메모리 내용을 얻기 어렵게 한다.

② 실행 제한

NX, SMEP/SMAP, CFG, CET. 손상된 메모리가 있어도 "그 내용을 코드로 실행"하거나 "흐름을 엉뚱한 곳으로 돌리는" 것을 막는다.

③ 로드·무결성 통제

DSE, 차단 목록, PatchGuard. 신뢰할 수 없는 코드의 진입과 커널 핵심 구조의 변조를 막거나 탐지한다.

④ 상위 계층 강제

VBS, HVCI, KDP, Credential Guard. 커널(ring 0)이 장악돼도 하이퍼바이저와 VTL1이 규칙을 강제한다.

⑤ 관찰·대응

커널 콜백, 미니필터, ETW, ELAM. 보안 제품이 공식 경로로 행위를 보고 차단한다.

핵심 아이디어

어느 한 층도 완벽하지 않다. 공격자가 넘어야 할 조건의 개수와 비용을 늘리는 것이 목표다.

전문가 관점 — "누가 강제하는가"를 먼저 물어라

보호 기능을 평가할 때 가장 중요한 질문은 "그 규칙을 누가 강제하는가"입니다. NX 비트나 PatchGuard는 커널 자신과 같은 ring 0에서 동작하므로, 커널 권한을 완전히 얻은 공격자와 같은 높이에 서 있습니다. 반면 HVCI·KDP·Credential Guard는 하이퍼바이저와 VTL1이 강제하므로 VTL0 커널이 장악돼도 규칙이 유지됩니다. 2015년 이후 Windows 보안의 큰 흐름은 이 "높이 차이"를 만드는 것이었습니다.

하드웨어 기반 보호: KASLR · NX · SMEP · SMAP

KASLR — 커널 주소 무작위화

KASLR(Kernel Address Space Layout Randomization)은 부팅마다 ntoskrnl.exe, hal.dll, 드라이버 이미지, 그리고 여러 커널 영역(풀, 페이지 테이블 셀프맵 등)의 기준 주소를 바꿉니다. 메모리 손상 버그를 악용하려면 대개 "어디에 무엇이 있는지" 알아야 하므로, 주소를 숨기는 것만으로 공격 비용이 크게 늘어납니다. Windows 10 1607에서는 페이지 테이블 셀프맵(PML4 자기 참조 인덱스)도 무작위화되었습니다(→ 08장).

KASLR의 한계는 정보 유출(info leak) 하나로 무력화될 수 있다는 점입니다. 그래서 Windows는 낮은 권한(예: Medium 미만 무결성 수준)의 프로세스가 커널 주소를 얻는 경로를 줄여 왔습니다. 드라이버 개발자에게 주는 교훈은 명확합니다: 커널 포인터를 유저 모드로 돌려주지 마라. IOCTL 출력 버퍼에 구조체를 통째로 복사하다가 커널 주소나 초기화되지 않은 스택/풀 내용이 새는 것이 대표적인 실수입니다.

NX / DEP — 데이터는 실행하지 않는다

x64 페이지 테이블 엔트리의 비트 63(XD, Execute Disable — AMD 용어 NX)이 1이면 그 페이지에서 명령어를 가져올 수 없습니다(IA32_EFER.NXE가 켜져 있어야 의미가 있음). Windows는 커널 스택, 대부분의 풀(NonPagedPoolNx, Windows 8 이후), 이미지의 데이터 섹션을 NX로 매핑합니다. 커널이 NX 페이지에서 실행을 시도하면 ATTEMPTED_EXECUTE_OF_NOEXECUTE_MEMORY(0xFC)로 버그체크합니다.

SMEP / SMAP — 커널과 유저 페이지 사이의 벽

커널은 유저 주소 공간도 함께 매핑된 상태로 실행됩니다. 이 설계는 빠르지만, "커널 모드에서 유저가 통제하는 메모리를 코드나 데이터로 쓰는" 위험을 낳습니다. 이를 하드웨어로 막는 것이 두 개의 CR4 비트입니다.

KVA Shadow

2018년 공개된 Meltdown(CVE-2017-5754, Rogue Data Cache Load)은 일부 CPU에서 유저 모드 코드가 투기적 실행(speculative execution)을 통해 커널 메모리를 읽어낼 수 있는 하드웨어 취약점이었습니다. 페이지 권한 검사가 투기적 실행 결과의 캐시 흔적까지는 막지 못했기 때문입니다. Windows의 대응이 KVA Shadow(Kernel Virtual Address Shadow)이며, Linux의 KPTI와 같은 개념입니다.

  • 무엇을 보호하나: 유저 모드 실행 중에는 커널 대부분이 아예 매핑되어 있지 않으므로, 투기적 실행으로도 커널 메모리 내용을 끌어낼 수 없습니다.
  • 비용: 모든 시스템 콜·인터럽트마다 CR3 전환이 추가됩니다. PCID(Process-Context Identifier)를 지원하는 CPU에서는 TLB를 통째로 비우지 않아 오버헤드가 줄어듭니다. 시스템 콜이 많은 워크로드에서 차이가 납니다.
  • 언제 켜지나: 취약한 CPU에서만 켜집니다. 하드웨어 수준에서 수정된 CPU(예: IA32_ARCH_CAPABILITIES.RDCL_NO를 보고하는 CPU)나 해당 취약점이 없는 CPU에서는 꺼집니다.
  • 드라이버 영향: 공식 API만 쓰는 드라이버에는 영향이 없습니다. 인터럽트 진입 경로나 CR3를 직접 다루는 비정상적 드라이버만 문제가 됩니다.

Kernel Patch Protection (PatchGuard)

x64 Windows 초기(2005)부터 들어간 Kernel Patch Protection(KPP, 통칭 PatchGuard)은 커널 핵심 코드와 구조체가 변조되지 않았는지 주기적으로 검사하고, 변조를 발견하면 시스템을 CRITICAL_STRUCTURE_CORRUPTION(버그체크 0x109)으로 멈춥니다. x86 시절 보안 제품과 악성코드가 너도나도 SSDT를 후킹해 시스템 안정성을 망가뜨린 경험에서 나온 정책입니다.

감시 대상 (대표적)

  • ntoskrnl·HAL 등 핵심 모듈의 코드
  • 시스템 서비스 디스패치 테이블(SSDT)
  • IDT, GDT 등 디스크립터 테이블
  • 시스템 콜 진입점 MSR 등 중요 MSR
  • 일부 커널 객체 타입·리스트 등 내부 구조

정확한 목록은 공개되지 않으며 버전마다 늘어납니다.

동작 특성

  • 사후 탐지: 변조 순간이 아니라 무작위 시점의 검사에서 발견 → 버그체크가 몇 분 뒤에 날 수도 있다
  • 부팅 시 커널 디버거가 연결되어 있으면 동작하지 않는다
  • VBS가 켜지면 HyperGuard(Secure Kernel)가 일부 구조를 실시간으로 보호한다(위반 시 0x18C HYPERGUARD_VIOLATION)
드라이버 개발자를 위한 규칙
  • 커널 코드나 디스패치 테이블을 패치하지 않는다 — SSDT/IDT 후킹, 인라인 후킹, MSR 변경 모두 금지.
  • 문서화되지 않은 커널 구조를 수정하지 않는다 — 내부 리스트에서 항목 떼어내기, 객체 타입 구조 변경 등.
  • 필요한 기능은 공식 콜백·프레임워크로 얻는다 — 프로세스 감시는 PsSetCreateProcessNotifyRoutineEx, 파일은 미니필터, 레지스트리는 CmRegisterCallbackEx, 네트워크는 WFP (→ 공식 인터페이스).
  • 디버거를 붙인 상태의 테스트 통과는 증거가 아니다 — 디버거 없이, 가능하면 VBS/HVCI를 켠 상태로 장시간 테스트한다.

드라이버 서명 강제(DSE)와 코드 무결성

DSE(Driver Signature Enforcement)는 서명되지 않은 커널 코드의 로드를 막는 정책이고, 이를 실제로 판정하는 구성요소가 코드 무결성(Code Integrity, ci.dll)입니다. 커널은 부팅 초기에 ci.dll을 초기화하고, 이후 모든 커널 이미지 로드 시 서명 검증을 요청합니다.

정책내용
x64 커널 모드 코드 서명Vista x64부터 커널 드라이버는 반드시 서명되어야 로드된다.
Microsoft 서명 요구 (1607~)Secure Boot가 켜진 Windows 10 1607 이후 새 설치에서는, 새로 로드되는 커널 드라이버가 Microsoft(하드웨어 개발자 센터)의 서명을 받아야 한다 — HLK 테스트 기반 인증 서명 또는 attestation 서명. 일부 레거시 교차 서명 예외가 있다.
테스트 서명 모드bcdedit /set testsigning on — 개발용. Secure Boot가 켜져 있으면 설정할 수 없다. 운영 환경에서 켜 두면 안 된다.
취약 드라이버 차단 목록서명은 정상이지만 악용 가능한 취약점이 알려진 드라이버를 해시·서명자 기준으로 차단한다. HVCI·Smart App Control·S 모드에서 강제되며, Windows 11 2022 업데이트부터는 모든 장치에서 기본 켜짐. 목록은 Windows 업데이트로 갱신된다.
App Control for Business (WDAC)조직이 직접 커널·유저 코드 허용 정책을 정의. 차단 목록을 더 자주 반영하거나 특정 서명자만 허용할 때 사용.
관리자 관점: BYOVD 대응

관리자 권한을 얻은 공격자가 정상 서명된 취약 드라이버를 직접 설치해 커널 권한을 얻으려는 시도(BYOVD, Bring Your Own Vulnerable Driver)는 DSE만으로는 막을 수 없습니다. 대응은 ① 취약 드라이버 차단 목록 켜기(Windows 보안 → 장치 보안 → 코어 격리), ② HVCI 켜기, ③ App Control 정책으로 허용 드라이버 제한, ④ 드라이버 로드 이벤트(서비스 생성, CodeIntegrity 로그) 모니터링입니다.

VBS 아키텍처: VTL0 · VTL1 · Secure Kernel

지금까지의 보호는 모두 ring 0에서 커널이 스스로를 지키는 방식이었습니다. VBS(Virtualization-Based Security)는 질문을 바꿉니다: "커널이 뚫려도 지켜야 할 것을 커널보다 높은 곳에 두면 어떨까?" VBS가 켜지면 부팅 시 Hyper-V 하이퍼바이저가 먼저 올라오고, Windows 자체는 그 위의 루트 파티션으로 실행됩니다. 하이퍼바이저는 같은 파티션 안에 VTL(Virtual Trust Level)이라는 두 개의 세계를 만듭니다.

SLAT(EPT) 권한과 HVCI — 커널 W^X를 위에서 강제하기

HVCI(Hypervisor-protected Code Integrity), Windows 보안 UI 이름으로 메모리 무결성(Memory integrity)은 VBS 위에서 동작하는 핵심 기능입니다. 원리는 하나의 불변식으로 요약됩니다.

HVCI의 불변식: VTL0 커널 메모리는 W^X

VTL0 커널의 어떤 물리 페이지도 쓰기 가능하면서 동시에 커널 모드에서 실행 가능할 수 없다. 그리고 실행 가능해지는 페이지는 VTL1의 코드 무결성 검증을 통과한 이미지의 코드뿐이다. 이 규칙은 VTL0의 페이지 테이블이 아니라 EPT로 강제되므로, VTL0 커널이 자기 PTE를 어떻게 바꾸든 깨지지 않는다.

Credential Guard와 KDP

Credential Guard

보호 대상: NTLM 해시, Kerberos TGT 관련 키 등 lsass가 보관하던 파생 자격 증명.

방법: 비밀을 VTL1 트러스트릿 LsaIso.exe에 보관. VTL0의 관리자·커널 권한으로도 그 메모리를 읽을 수 없다.

한계: 입력 순간의 자격 증명, 일부 레거시 프로토콜(NTLMv1, Kerberos DES 등은 사용 불가해짐)은 보호 범위 밖. 레거시 인증에 의존하는 앱은 호환성 검토 필요.

KDP (Kernel Data Protection)

보호 대상: 초기화 후 바뀌면 안 되는 커널 데이터(설정, 정책, 콜백 테이블 등).

정적 KDP: 드라이버가 MmProtectDriverSection으로 자기 이미지의 섹션을 지정하면, VTL1이 EPT로 해당 페이지를 읽기 전용으로 고정한다.

동적 KDP: 보안 풀(secure pool, ExCreatePool/ExAllocatePool3 계열)에 데이터를 두고 VTL1을 통해서만 갱신한다.

VBS가 켜져 있어야 실제 보호가 적용됩니다.

제어 흐름 보호: 커널 CET · kCFG · XFG

NX·HVCI가 "새 코드를 실행하는 것"을 막자, 공격의 초점은 이미 있는 정상 코드를 비정상적인 순서로 실행하는 것(제어 흐름 탈취)으로 옮겨 갔습니다. 이를 겨냥한 것이 제어 흐름 무결성(CFI) 계열 보호입니다.

커널 모드 하드웨어 강제 스택 보호 (kCET)

Intel CET의 섀도 스택을 커널에 적용. call 시 반환 주소가 일반 스택과 함께 별도의 섀도 스택에도 기록되고, ret 시 CPU가 두 값을 비교해 다르면 #CP(Control Protection) 예외를 일으킵니다 → 시스템 버그체크.

섀도 스택 페이지는 일반 쓰기로 수정할 수 없는 특수 페이지이며, 커널에서는 Secure Kernel이 관리합니다.

요건: Windows 11 22H2 이상, VBS·HVCI 켜짐, CET 지원 CPU(Intel 11세대 이후, AMD Zen 3 이후). 기본값은 꺼짐.

kCFG / XFG

kCFG(Kernel Control Flow Guard): 커널·드라이버를 /guard:cf로 빌드하면 컴파일러가 간접 호출 앞에 검사를 넣고, 대상이 "유효한 함수 시작 주소" 비트맵에 있는지 확인합니다. 커널에서는 VBS가 켜져 있을 때 활성화되어 비트맵이 보호됩니다.

XFG(eXtended Flow Guard): 간접 호출 대상을 "함수 프로토타입 해시가 일치하는 함수"로 더 좁히는 CFG 확장입니다. 공개 정보가 제한적이므로 개념만 알아 두세요.

CFG는 "유효한 함수라면 어디든" 허용하므로 완화(mitigation)이지 완전한 차단은 아닙니다.

드라이버 빌드 설정

링커 옵션 /CETCOMPAT(섀도 스택 호환 표시)와 컴파일러 옵션 /guard:cf를 켜세요. kCET가 켜진 시스템에서는 비호환 드라이버가 기능 활성화를 막거나 로드되지 못할 수 있으며, Windows 보안 UI가 비호환 드라이버를 표시합니다. 반환 주소를 직접 조작하거나 스택을 수동으로 전환하는 코드(커스텀 코루틴, 비표준 예외 처리)는 섀도 스택과 충돌하므로 피해야 합니다.

"차단 (ring 0 강제)"는 정상 동작 중에는 확실히 막지만, 커널 권한을 완전히 얻은 주체는 같은 높이에서 설정을 바꿀 수 있다는 의미입니다. "차단 (상위 계층 강제)"는 하이퍼바이저·VTL1이 강제하므로 VTL0 커널 장악만으로는 무너지지 않습니다. 실제 시스템에서는 펌웨어·하드웨어 결함 등 이 표 밖의 변수도 있습니다. KVA Shadow는 취약한 CPU에서만 켜지고, Credential Guard는 버전·에디션·도메인 가입 여부에 따라 기본값이 다릅니다.

보안 제품을 위한 공식 인터페이스

PatchGuard와 HVCI가 "커널을 고치는" 길을 막은 대신, Windows는 보안 제품이 커널을 고치지 않고도 필요한 것을 보고 막을 수 있는 공식 인터페이스를 제공합니다. EDR·백신·DLP 제품의 커널 구성요소는 모두 이 위에 만들어져야 합니다.

API알림 시점할 수 있는 일

PsSetCreateThreadNotifyRoutine(Ex)스레드 생성·종료원격 스레드 생성(생성자 프로세스 ≠ 대상 프로세스) 관찰
PsSetLoadImageNotifyRoutine(Ex)이미지(EXE/DLL/드라이버) 매핑로드되는 모듈 관찰, 서명 정보 등 확인

PsSetCreateProcessNotifyRoutineEx와 ObRegisterCallbacks는 드라이버가 /INTEGRITYCHECK 링커 옵션으로 빌드되어 있어야 등록에 성공합니다(아니면 STATUS_ACCESS_DENIED). 모든 콜백은 DriverUnload에서 반드시 해제해야 하며, 콜백은 빠르게 끝내야 합니다(시스템 전체 경로에 놓이므로).

ObRegisterCallbacks는 프로세스·스레드(및 데스크톱) 객체에 대한 핸들 생성·복제 시점에 호출됩니다. 사전 콜백에서 요청된 접근 권한을 깎을 수 있어, 자사 에이전트 프로세스를 다른 프로세스의 종료·메모리 쓰기로부터 보호하는 데 씁니다.

OB_PREOP_CALLBACK_STATUS
PreOpenProcess(PVOID Ctx, POB_PRE_OPERATION_INFORMATION Info)
{
    UNREFERENCED_PARAMETER(Ctx);
    if (Info->KernelHandle) return OB_PREOP_SUCCESS;      // 커널 핸들은 건드리지 않음
    if (IsProtectedAgent((PEPROCESS)Info->Object)) {      // 자사 프로세스인지 판단(구현 생략)
        ACCESS_MASK strip = PROCESS_TERMINATE | PROCESS_VM_WRITE | PROCESS_VM_OPERATION;
        if (Info->Operation == OB_OPERATION_HANDLE_CREATE)
            Info->Parameters->CreateHandleInformation.DesiredAccess &= ~strip;
        else
            Info->Parameters->DuplicateHandleInformation.DesiredAccess &= ~strip;
    }
    return OB_PREOP_SUCCESS;
}

OB_OPERATION_REGISTRATION g_Op = {
    PsProcessType, OB_OPERATION_HANDLE_CREATE | OB_OPERATION_HANDLE_DUPLICATE,
    PreOpenProcess, NULL
};
OB_CALLBACK_REGISTRATION g_Reg = {
    OB_FLT_REGISTRATION_VERSION, 1, RTL_CONSTANT_STRING(L"321000"), NULL, &g_Op
};

// DriverEntry:  status = ObRegisterCallbacks(&g_Reg, &g_ObHandle);
// DriverUnload: ObUnRegisterCallbacks(g_ObHandle);

고도(altitude) 문자열은 여러 드라이버의 콜백 순서를 정합니다. 상용 제품은 Microsoft에 고도를 할당받습니다.

CmRegisterCallbackEx로 레지스트리 작업(키 생성·열기, 값 설정·삭제, 이름 변경 등)의 사전·사후 알림을 받습니다. 사전 알림에서 실패 상태를 반환하면 작업을 거부할 수 있어, 자동 실행 키·서비스 키 변조 방지나 자사 설정 보호에 씁니다.

고도(altitude)를 지정하며, CmUnRegisterCallback으로 해제합니다. 콜백 안에서 레지스트리를 다시 호출하면 재귀가 일어날 수 있으므로 주의합니다.

파일 시스템 미니필터(Filter Manager, FltRegisterFilter): 파일 생성·읽기·쓰기·이름 변경 등 IRP 단위 작업을 사전·사후 콜백으로 관찰·차단합니다. 실시간 검사, 랜섬웨어 행위 탐지, DLP의 기반입니다. 고도로 필터 스택 내 위치가 정해집니다(→ 12장).

WFP 콜아웃 드라이버(Windows Filtering Platform): 네트워크 연결·패킷을 공식 계층에서 검사·차단합니다. NDIS나 TCP/IP 스택을 후킹할 이유가 없습니다.

ETW(Event Tracing for Windows)는 커널과 OS 구성요소가 내보내는 고성능 이벤트 스트림입니다. 프로세스·파일·네트워크·레지스트리 등 다양한 공급자가 있어, 많은 탐지를 커널 드라이버 없이도 구현할 수 있습니다.

Microsoft-Windows-Threat-Intelligence 공급자는 커널 내부에서 보안상 민감한 작업(다른 프로세스의 메모리 할당·보호 변경·읽기/쓰기, 원격 APC 큐잉 등)을 이벤트로 알려 줍니다. 이 공급자는 아무나 구독할 수 없으며, Antimalware PPL로 실행되는 보안 제품 프로세스만 구독할 수 있습니다. 그 자격은 다음 탭의 ELAM 등록과 연결됩니다.

ELAM(Early Launch Anti-Malware) 드라이버는 다른 부트 시작 드라이버보다 먼저 로드되어, 이후 로드되는 부트 드라이버를 IoRegisterBootDriverCallback으로 보고 "양호·불량·알 수 없음"으로 분류합니다. 정책에 따라 불량 드라이버의 초기화를 막을 수 있습니다(→ 03장).

ELAM 드라이버는 Microsoft의 특별한 서명을 받아야 하고, ELAM에 등록된 공급업체의 사용자 모드 서비스는 Antimalware-Light PPL로 실행될 수 있습니다. PPL은 관리자 권한 프로세스라도 보호 프로세스의 메모리를 읽거나 종료하지 못하게 합니다(→ 13장).

보안 제품 드라이버의 책임

보안 제품 드라이버는 거의 모든 프로세스·파일 작업 경로에 놓입니다. 콜백 하나의 버그는 시스템 전체의 장애로 이어지며, 이는 실제 대규모 장애 사례로도 확인된 교훈입니다. 콜백에서 무거운 작업·차단 대기·유저 모드 왕복을 최소화하고, 외부 입력(정의 파일, 설정)을 커널에서 해석할 때는 철저한 검증과 단계적 배포를 적용하세요.

HVCI 호환 드라이버 체크리스트

HVCI가 켜진 시스템(Windows 11 새 설치 장치 다수)에서 비호환 드라이버는 로드되지 않거나, 사용자가 메모리 무결성을 켜지 못하게 막는 원인이 됩니다. Microsoft 문서의 요구 사항을 실무 체크리스트로 정리하면 다음과 같습니다.

  • 기본 NX 메모리 사용: ExAllocatePool2(POOL_FLAG_NON_PAGED, …)(기본 NX) 또는 NonPagedPoolNx. 구형 대상은 POOL_NX_OPTIN + ExInitializeDriverRuntime(DrvRtPoolNxOptIn).
  • 매핑도 NX로: MmMapLockedPagesSpecifyCache에 MdlMappingNoExecute, MmMapIoSpaceEx에 PAGE_READWRITE 등 실행 권한 없는 보호값.
  • W+X 섹션 금지: PE 이미지에 쓰기와 실행이 동시에 가능한 섹션이 없어야 한다. 코드와 데이터를 합치는 링커 옵션(/MERGE 등)에 주의.
  • 섹션 페이지 정렬: 코드와 데이터가 같은 페이지를 공유하지 않도록 섹션을 페이지 단위로 정렬.
  • 동적 코드 금지: 런타임 코드 생성, 자기 수정 코드, 실행 가능 메모리에 코드 복사 후 실행 — 모두 불가.
  • 커널 코드·구조 패치 금지: PatchGuard 규칙과 동일. 필요한 기능은 공식 콜백으로.
  • 빌드 옵션: /guard:cf, /CETCOMPAT, 필요 시 /INTEGRITYCHECK.
  • 검증: 테스트 장치에서 메모리 무결성을 켜고 실행, Driver Verifier의 코드 무결성 검사 옵션, HLK의 HVCI 호환성 테스트.
// ✗ 비호환: 실행 가능한 커널 메모리를 만든다
PVOID buf = ExAllocatePoolWithTag(NonPagedPool, size, 'vrDM');          // 실행 가능 풀
PVOID va  = MmMapLockedPagesSpecifyCache(mdl, KernelMode, MmCached, NULL,
                                         FALSE, NormalPagePriority);     // 실행 가능 매핑
PVOID io  = MmMapIoSpaceEx(pa, len, PAGE_EXECUTE_READWRITE);

// ✓ 호환: 데이터는 데이터로만
PVOID buf = ExAllocatePool2(POOL_FLAG_NON_PAGED, size, 'vrDM');          // 기본 NX (Win10 2004+)
PVOID va  = MmMapLockedPagesSpecifyCache(mdl, KernelMode, MmCached, NULL,
                                         FALSE, NormalPagePriority | MdlMappingNoExecute);
PVOID io  = MmMapIoSpaceEx(pa, len, PAGE_READWRITE | PAGE_NOCACHE);

// 읽기 전용으로 고정할 설정 데이터가 있다면 (VBS 켜짐 시 적용)

실습: 내 시스템의 보호 상태 점검

실습 16-1 · 보호 기능 인벤토리 만들기

테스트용 가상 머신(Hyper-V의 경우 중첩 가상화를 켜야 VM 안에서 VBS 가능)과 실제 장치 각각에서 아래를 확인하고 표로 정리해 보세요. 실습은 모두 관찰만 하며 보호 기능을 끄지 않습니다.

  1. msinfo32에서 VBS 상태, 실행 중인 서비스, 커널 DMA 보호를 기록합니다.
  2. PowerShell로 Win32_DeviceGuard를 조회해 msinfo32 결과와 대조합니다.
  3. Windows 보안의 코어 격리 페이지에서 메모리 무결성과 취약 드라이버 차단 목록 상태를 확인합니다. 켤 수 없다면 어떤 드라이버가 비호환으로 표시되는지 기록합니다.
  4. CodeIntegrity/Operational 로그에서 최근 로드가 거부된 이미지가 있는지 확인합니다.
  5. 커널 디버거(또는 로컬 커널 디버깅)에서 CR4의 보호 비트를 확인합니다.
kd> r cr4
kd> ? (@cr4 >> 0n20) & 1        $$ SMEP (비트 20)
kd> ? (@cr4 >> 0n21) & 1        $$ SMAP (비트 21)
kd> ? (@cr4 >> 0n23) & 1        $$ CET  (비트 23)

kd> !pte nt!KeBugCheckEx          $$ 커널 코드 페이지: VTL0 PTE 권한 확인 (-E 실행 가능, W 없음)
kd> !pool <풀 주소>               $$ 드라이버의 풀 할당이 NX 풀인지 확인

VTL0 커널 디버거가 보여주는 것은 VTL0 페이지 테이블입니다. EPT 권한과 VTL1 메모리(Secure Kernel, 트러스트릿)는 VTL0 디버거로 볼 수 없습니다 — 이것 자체가 VBS 격리의 증거입니다. CPU마다 값이 다르므로 결과 숫자보다 "어떤 비트가 켜져 있는가"에 집중하세요.

실습 16-2 · 자작 드라이버 HVCI 호환성 점검 (14장 드라이버 사용)

14장에서 만든 드라이버를 메모리 무결성이 켜진 테스트 VM에 설치하고, Driver Verifier로 코드 무결성 검사를 켭니다(verifier /?로 해당 옵션 확인). 이어서 체크리스트 항목을 하나씩 대조하고, 실행 가능 풀을 쓰는 코드를 일부러 넣었다 빼 보며 Verifier와 로드 결과가 어떻게 달라지는지 관찰합니다.

확인 문제

CR4.SMEP이 켜진 상태에서 페이지 폴트가 발생하는 경우는?

  1. 유저 모드 코드가 커널 페이지를 읽을 때
  2. 커널 모드(CPL 0)에서 U/S=1(유저) 페이지의 명령어를 실행하려 할 때
  3. 커널 모드에서 유저 페이지의 데이터를 읽을 때
  4. 커널이 읽기 전용 페이지에 쓸 때
SMEP은 슈퍼바이저 모드의 명령어 페치만 다룹니다. ①은 SMEP과 무관하게 U/S=0 페이지라서 막히고, ③은 SMAP의 영역, ④는 CR0.WP의 영역입니다.

HVCI가 켜진 시스템에서 VTL0 커널 권한을 가진 코드가 데이터 페이지의 PTE에서 NX 비트를 해제했습니다. 이 페이지를 커널 코드로 실행할 수 없는 이유는?

  1. PatchGuard가 PTE 변경을 즉시 되돌리기 때문에
  2. CPU가 PTE 변경 후 TLB를 비우지 않기 때문에
  3. 실행 권한은 VTL1·하이퍼바이저가 관리하는 EPT에서도 허용되어야 하는데, 검증되지 않은 페이지에는 EPT 실행 권한이 없기 때문에
  4. SMEP이 데이터 페이지 실행을 막기 때문에
실제 권한은 VTL0 PTE와 EPT 권한의 교집합입니다. VTL0는 EPT를 바꿀 수 없고, EPT 실행 권한은 Secure Kernel의 코드 무결성 검증을 통과한 페이지에만 부여됩니다. PatchGuard는 사후·주기적 검사이고, SMEP은 유저 페이지 실행에 관한 규칙입니다.

EDR 드라이버가 새 프로세스 생성을 감시하고 필요 시 차단하려 합니다. 올바른 방법은?

  1. SSDT의 NtCreateUserProcess 항목을 자체 함수로 바꾼다
  2. ntoskrnl의 프로세스 생성 함수 앞부분에 점프 명령을 패치한다
  3. PsSetCreateProcessNotifyRoutineEx로 콜백을 등록하고 CreationStatus로 생성을 거부한다
  4. 내부 프로세스 리스트를 주기적으로 스캔해 새 항목을 찾는다
①②는 PatchGuard가 탐지하는 커널 변조이며 HVCI 환경에서는 코드 패치 자체가 불가능합니다. ④는 문서화되지 않은 구조에 의존해 빌드마다 깨지고 경쟁 조건이 있습니다. 공식 콜백은 /INTEGRITYCHECK로 빌드한 드라이버에서 등록할 수 있습니다.

정상적인 공급업체 서명을 가진, 그러나 취약점이 알려진 드라이버의 로드를 막는 기능은?

  1. DSE(드라이버 서명 강제) — 서명을 확인하므로
  2. Microsoft 취약 드라이버 차단 목록(또는 App Control 정책)
  3. KASLR
  4. KVA Shadow
DSE는 "서명이 유효한가"만 묻기 때문에 정상 서명된 취약 드라이버는 통과합니다. 차단 목록은 해시·서명자 기준으로 알려진 취약 드라이버를 거부하며, Windows 11 2022 업데이트부터 기본으로 켜져 있습니다.

다음 중 HVCI(메모리 무결성)와 호환되지 않는 드라이버 구현은?

  1. ExAllocatePool2(POOL_FLAG_NON_PAGED, …)로 버퍼 할당
  2. MmMapLockedPagesSpecifyCache에 MdlMappingNoExecute 지정
  3. 런타임에 실행 가능 풀을 할당하고 코드를 복사해 호출
  4. 콜백 등록을 위해 /INTEGRITYCHECK로 링크
HVCI 환경에서 VTL0 커널은 실행 가능한 메모리를 새로 만들 수 없습니다. 동적 코드 생성·자기 수정 코드는 설계 단계에서 배제해야 합니다. 나머지는 모두 권장 패턴입니다.

KVA Shadow가 직접 겨냥하는 위협은?

  1. 서명되지 않은 드라이버 로드
  2. 유저 모드 코드가 투기적 실행을 통해 커널 메모리 내용을 유출하는 것 (Meltdown)
  3. 커널 스택의 반환 주소 변조
  4. lsass 메모리에서 자격 증명 탈취
KVA Shadow는 유저 모드 실행 중에 커널 대부분을 매핑에서 빼 버려, 투기적 실행으로 읽을 대상 자체를 없앱니다. 반환 주소 변조는 kCET, 자격 증명 탈취는 Credential Guard의 영역입니다.

핵심 요약

  • 커널 보호는 심층 방어다: 정보 숨기기(KASLR, KVA Shadow) → 실행 제한(NX, SMEP/SMAP, CFG, CET) → 로드·무결성 통제(DSE, 차단 목록, PatchGuard) → 상위 계층 강제(VBS).
  • SMEP은 커널의 유저 페이지 실행을, SMAP은 유저 페이지 데이터 접근을, CR0.WP는 읽기 전용 페이지 쓰기를 막는다. NX는 데이터 페이지 실행을 막는다.
  • PatchGuard는 커널 코드·SSDT·IDT·MSR 등의 변조를 사후 탐지해 0x109로 중단시킨다. 드라이버는 커널을 고치지 말고 공식 콜백을 써야 한다.
  • DSE는 "서명 여부"를, 취약 드라이버 차단 목록은 "서명됐지만 위험한 드라이버"를 다룬다.
  • VBS는 VTL0/VTL1을 나누고, HVCI는 EPT로 커널 W^X와 "검증된 코드만 실행"을 VTL0보다 높은 곳에서 강제한다. Credential Guard·KDP·kCET도 같은 높이 차이를 이용한다.
  • HVCI 호환 드라이버: NX 메모리, W+X 섹션 금지, 동적 코드 금지, 페이지 정렬, /guard:cf·/CETCOMPAT, 메모리 무결성을 켠 환경에서 검증.
