전문가 로드맵과 실습 랩

읽은 것을 손으로 확인하는 단계입니다. 안전한 실습 환경을 만들고, 챕터별 랩으로 지식을 검증하고, 진로 트랙에 맞는 프로젝트로 전문성을 증명합니다.

전문가⏱ 약 60분 (+ 랩 수행 시간)선수: 01–16장

학습 목표

  • 개발 VM과 타깃 VM 두 대로 KDNET 커널 디버깅, 심볼, WDK 빌드, 테스트 서명 배포 환경을 직접 구축할 수 있다.
  • 챕터별 랩을 수행하고 "검증 방법"으로 스스로 결과를 확인할 수 있다.
  • 8개 역량 영역에서 자신의 수준을 진단하고 다음에 공부할 곳을 고를 수 있다.
  • 드라이버 개발·장애 분석·보안 연구 중 하나를 골라 포트폴리오가 될 프로젝트를 계획할 수 있다.

전문가는 무엇이 다른가

커널 지식은 넓고, Windows는 소스가 공개되지 않았으며, 구조체와 내부 동작은 빌드마다 바뀝니다. 그래서 전문가를 가르는 것은 암기량보다 검증하는 습관입니다. 문서나 책의 설명을 디버거로 확인하고, 확인할 수 없는 것은 "확인하지 못함"이라고 구분해 말할 줄 압니다.

재현한다

현상을 VM에서 다시 일으킬 수 있어야 원인을 말할 수 있습니다. 스냅숏과 자동화가 재현 비용을 낮춥니다.

확인한다

dt, u, !pte, !irp로 책의 주장을 현재 빌드에서 직접 봅니다. 오프셋은 외우지 않고 매번 확인합니다.

설명한다

분석 결과를 다른 사람이 따라 할 수 있는 단계로 기록합니다. 블로그, 사내 위키, 덤프 분석 보고서가 곧 포트폴리오입니다.

실습 환경 구축

커널 실습은 반드시 가상 머신에서 합니다. 버그체크는 일상이고, 테스트 서명이나 디버그 모드는 시스템의 보안 수준을 낮추기 때문입니다. 권장 구성은 개발/디버거 VM 한 대와 타깃(디버기) VM 한 대입니다. 호스트 OS를 개발 머신으로 쓰고 타깃 VM 하나만 둘 수도 있지만, 두 VM 구성은 호스트를 깨끗하게 유지하고 환경 전체를 스냅숏으로 되돌릴 수 있다는 장점이 있습니다. 

C:\> mkdir C:\KDNET & cd C:\KDNET
REM 개발 VM의 ...\Windows Kits\10\Debuggers\x64 에서 kdnet.exe, VerifiedNICList.xml 복사
C:\KDNET> kdnet.exe
REM "Network debugging is supported on the following NICs" 류의 출력 확인
C:\KDNET> kdnet.exe 10.0.0.1 50000
Key=...   (이 키를 디버거에 입력)
C:\> bcdedit /set testsigning on
C:\> bcdedit /dbgsettings
C:\> shutdown /r /t 0

출력 문구는 도구 버전에 따라 다릅니다. bcdedit /dbgsettings로 key·hostip·port가 저장됐는지 확인하세요. 재부팅 후 바탕화면 오른쪽 아래에 "테스트 모드" 워터마크가 보이면 테스트 서명이 켜진 것입니다.

C:\> setx _NT_SYMBOL_PATH "srv*C:\symbols*https://msdl.microsoft.com/download/symbols"
C:\> windbg -k net:port=50000,key=1.2.3.4
kd> .symfix+ C:\symbols
kd> .sympath+ C:\src\MyDrv\x64\Debug
kd> .reload /f
kd> !sym noisy               $$ 심볼 로드 문제 추적 시
kd> lm m nt                  $$ (pdb symbols) 표시 확인
kd> vertarget                $$ 타깃 빌드 확인
kd> !sym quiet

Microsoft 공용 심볼은 public 심볼이라 지역 변수, 소스 줄 정보, 많은 내부 정적 함수 정보가 없습니다. 반면 자신의 드라이버 PDB는 private 심볼이므로 지역 변수와 소스 단계 실행이 가능합니다.

REM 레거시(비PnP) 드라이버
C:\> sc create MyDrv type= kernel binPath= C:\drv\MyDrv.sys
C:\> sc start MyDrv
C:\> sc stop MyDrv
C:\> sc delete MyDrv
REM PnP / KMDF 드라이버 패키지
C:\> pnputil /add-driver C:\drv\MyDrv.inf /install
REM Driver Verifier (재부팅 후 적용)
C:\> verifier /standard /driver MyDrv.sys
C:\> verifier /query
C:\> verifier /reset

sc의 type= 뒤 공백은 필수입니다. PnP 설치 시 서명 경고를 피하려면 테스트 인증서를 타깃의 "신뢰할 수 있는 루트 인증 기관"과 "신뢰할 수 있는 게시자" 저장소에 넣으라는 것이 Microsoft 문서의 권고입니다.

  • KDNET이 안 붙을 때: 타깃 NIC가 지원 목록에 있는지(kdnet.exe 출력), 호스트 IP가 디버거 VM의 IP인지, 방화벽, 키 오타, 두 VM이 같은 서브넷인지 순서로 확인합니다.
  • 시리얼(가상 COM) 대안: Hyper-V에서는 Set-VMComPort -VMName Target -Number 1 -Path \\.\pipe\kd로 명명된 파이프를 연결하고 bcdedit /dbgsettings serial debugport:1 baudrate:115200을 씁니다. 느리지만 NIC 문제와 무관합니다.
  • VBS/HVCI를 실습하려면: 타깃 VM 안에서 하이퍼바이저가 돌아야 하므로 중첩 가상화가 필요합니다. Hyper-V는 Set-VMProcessor -VMName Target -ExposeVirtualizationExtensions $true(VM 정지 상태에서).
  • 로컬 커널 디버깅: 디버거 VM 없이 관찰만 할 때는 bcdedit /debug on 후 WinDbg의 Local 커널 연결이나 Sysinternals LiveKD를 쓸 수 있습니다. 브레이크포인트·단계 실행은 불가합니다.
실습 환경 원칙

테스트 서명, 디버그 모드, Secure Boot 비활성화는 격리된 실습 VM에만 적용합니다. 업무용·개인용 실제 PC에 적용하지 마세요. 실습 VM은 중요한 계정으로 로그인하지 않고, 필요할 때만 네트워크에 연결합니다.

Bruce Dang, Alexandre Gazet, Elias Bachaalany · Wiley (2014)

  • Windows 드라이버 문서 (Microsoft Learn, learn.microsoft.com/windows-hardware/drivers/) — WDK 설치, KMDF/WDM 설계 가이드, 커널 모드 API 레퍼런스. 함수의 IRQL 요구 사항 항목을 습관적으로 확인하세요.
  • Windows 디버깅 도구 문서 (같은 사이트의 debugger 섹션) — WinDbg 명령, KDNET 설정, 심볼 경로, 디버거 확장 명령 레퍼런스.
  • 버그 검사 코드 참조 (Bug Check Code Reference) — 각 버그체크 코드의 매개변수 의미와 원인. 덤프 분석 시 !analyze 출력과 함께 반드시 대조.
  • Driver Verifier, Static Driver Verifier, CodeQL for drivers 문서 — 드라이버 품질 도구와 각 규칙의 의미.
  • Windows 보안 문서 — Secure Boot, BitLocker, VBS, HVCI(메모리 무결성), Credential Guard, 드라이버 차단 목록 등 16장 관련 기능의 공식 설명과 요구 사항.
  • Windows-driver-samples (github.com/microsoft/Windows-driver-samples) — Microsoft 공식 드라이버 예제. 미니필터(filesys/miniFilter), 일반 드라이버, WFP 등. 실습 프로젝트의 출발점으로 가장 좋습니다.
  • ReactOS (reactos.org) — NT 아키텍처와 호환을 목표로 독립 구현된 오픈소스 OS. Ob/Io/Mm 같은 구성요소가 어떤 모양으로 구현될 수 있는지 감을 잡는 데 유용하지만, Windows의 실제 코드가 아니며 대상 버전도 오래된 NT 계열이라 현대 Windows와 다른 점이 많습니다.
  • Geoff Chappell, Software Analyst (geoffchappell.com) — 비공개 커널 구조체와 API의 버전별 변화를 꼼꼼하게 정리한 연구 사이트.
  • Vergilius Project (vergiliusproject.com) — 공개 심볼에서 추출한 Windows 빌드별 커널 구조체 정의. 빌드 간 비교에 편리하지만, 최종 확인은 대상 시스템의 dt로 합니다.
  • phnt (github.com/winsiderss/phnt) — System Informer 프로젝트의 네이티브 API 헤더 모음. 비공식 정의이므로 근거로 인용할 때 주의합니다.
  • WinDbg — 커널 디버깅과 덤프 분석의 기본. dx와 데이터 모델, JavaScript 확장, Time Travel Debugging(유저 모드)까지 익혀 두면 좋습니다.
  • Sysinternals — Process Explorer, Process Monitor, WinObj, LiveKD, NotMyFault(의도적 크래시 생성), Autoruns 등.
  • System Informer(구 Process Hacker) — 커널 객체·핸들·서비스를 깊게 들여다보는 오픈소스 도구.
  • Windows Performance Recorder / Analyzer — ETW 기반 성능 분석. DPC/ISR 지연, 부팅 추적, CPU 사용 분석.
  • Ghidra / IDA — 공개 심볼과 함께 커널 바이너리를 읽어 문서화되지 않은 동작을 확인할 때.
  • Volatility 3 — 메모리 포렌식 프레임워크. 커널 구조체 해석을 코드로 확인할 수 있습니다.
  • OSR (osr.com) — 드라이버 개발 커뮤니티 NTDEV 포럼과 기술 글. 오래되고 깊은 실무 토론이 쌓여 있습니다.

진로 트랙별 프로젝트

세 트랙은 같은 기반 위에 서 있지만 매일 하는 일이 다릅니다. 하나를 골라 프로젝트를 순서대로 진행하고, 결과를 공개 저장소나 글로 남기세요. 각 프로젝트는 "무엇을 만들었다"보다 "무엇을 검증했는가"가 드러나도록 정리하는 것이 핵심입니다.

디바이스·필터·가상화 드라이버를 만드는 일. 필요 역량: 07·11·12·14장, IRQL 규칙, WDF, 품질 도구.

  1. IOCTL 정보 드라이버 — METHOD_BUFFERED IOCTL로 커널 정보를 유저 모드 클라이언트에 반환하는 레거시 드라이버. 입력 길이 검증, DriverUnload, Verifier 통과까지. 이후 같은 기능을 KMDF로 다시 작성해 차이를 정리합니다.
  2. 미니필터 감사 로거 — 특정 폴더의 쓰기·이름 변경을 기록하고, FltCreateCommunicationPort로 유저 모드 서비스에 이벤트를 전달. 고도(altitude) 선택 이유와 성능 영향(사후 콜백 최소화)을 문서화합니다.
  3. WFP 콜아웃 — Windows Filtering Platform으로 연결 이벤트를 관찰하는 드라이버. 네트워크 스택 계층(레이어)과 콜아웃 등록 흐름을 이해합니다.
  4. 품질 마무리 — SDV, CodeQL, Driver Verifier(풀 추적·IRQL 검사 포함)를 통과하고, HVCI 활성 환경에서 로드되는지 확인합니다. 결과 리포트를 저장소에 함께 올립니다.

블루스크린·행·성능 저하의 근본 원인을 찾는 일. 필요 역량: 05·06·07·09·15장, 덤프 분석, ETW.

  1. 버그체크 도감 — NotMyFault와 직접 만든 버그 드라이버로 대표 버그체크(0xA, 0xD1, 0x50, 0xC4, 0x133 등)를 실습 VM에서 일으키고, 덤프마다 "근거 → 결론" 형식의 분석 노트를 작성합니다.
  2. 행 분석 — 의도적으로 두 락의 획득 순서를 뒤집은 드라이버로 데드락을 만들고, !locks, !stacks, !thread, !ready로 대기 체인을 재구성합니다. Verifier의 데드락 감지가 어떻게 잡는지도 비교합니다.
  3. 풀 누수 추적 — 의도적으로 해제하지 않는 할당을 만들고 poolmon, !poolused, 풀 태그로 범인을 찾습니다. 태그 설계가 왜 중요한지 정리합니다.
  4. 지연 분석 — WPR로 추적을 수집하고 WPA에서 DPC/ISR 지속 시간을 드라이버별로 분석합니다. 오디오 끊김·입력 지연 같은 증상과 연결해 설명하는 보고서를 씁니다.

탐지·방어 제품과 플랫폼 보안을 만드는 일. 필요 역량: 04·10·13·16장, 커널 콜백, ETW, 메모리 포렌식.

  1. 텔레메트리 드라이버 — PsSetCreateProcessNotifyRoutineEx, 스레드·이미지 로드 콜백, CmRegisterCallbackEx, ObRegisterCallbacks로 이벤트를 모아 유저 모드에 전달합니다(일부 콜백은 링커 /INTEGRITYCHECK 필요). 각 콜백이 호출되는 IRQL과 문맥, 그리고 놓치는 이벤트를 문서화합니다.
  2. ETW 소비자 — 커널 공급자(프로세스, 이미지 로드 등)를 구독하는 유저 모드 도구를 만들고, 1번 드라이버의 데이터와 비교해 각 방식의 장단점을 정리합니다.
  3. 메모리 포렌식 교차 검증 — 실습 VM의 메모리 이미지를 Volatility 3로 분석해, 여러 출처(프로세스 리스트, 핸들 테이블, 스레드)를 교차 비교하는 방식으로 이상 징후를 찾는 원리를 정리합니다.
  4. 내 드라이버 견고성 검사 — 1번 드라이버의 IOCTL 인터페이스에 비정상 입력을 자동 생성해 넣는 퍼저를 만들고 Verifier와 함께 돌려, 입력 검증 버그를 스스로 찾아 고칩니다.
  5. 버그 클래스 연구 노트 — Microsoft 보안 업데이트 가이드와 공개 분석 글을 읽고, 커널 버그 클래스(입력 길이 미검증, 이중 페치/TOCTOU, 참조 카운트 오류 등)와 그에 대응하는 완화 기법을 정리합니다.
연구 윤리

분석과 테스트는 자신이 소유하거나 명시적으로 허가받은 시스템에서만 합니다. 취약점을 발견하면 공개 전에 해당 공급업체(Microsoft의 경우 MSRC)에 조율된 공개 절차로 보고하세요.

kd> vertarget                         $$ 타깃 빌드 · 가동 시간
kd> lm m nt                           $$ (pdb symbols) 확인

kd> g

  2. debug-ready 스냅숏을 만든 뒤, 일부러 verifier /standard /driver MyDrv.sys를 켜고 버그가 있는 빌드를 로드해 0xC4가 발생하는지 확인하고, 스냅숏으로 되돌려 보세요.
  3. 랩 체크리스트에서 이번 주에 할 랩 세 개를 고르고, 역량 매트릭스에서 가장 낮은 영역의 챕터를 다시 읽으세요.

확인 문제

타깃 VM에서 bcdedit /set testsigning on을 실행했더니 "Secure Boot 정책으로 보호되어 수정할 수 없다"는 오류가 납니다. 실습 환경에서 올바른 조치는?

  1. 레지스트리의 BCD 하이브를 직접 수정한다
  2. 실습 VM의 설정에서 Secure Boot를 끈 뒤 다시 실행한다
  3. 드라이버를 Boot 시작 타입으로 바꾼다
  4. 관리자 권한 없이 다시 실행한다
Secure Boot가 켜져 있으면 testsigning·debug 같은 신뢰 수준을 낮추는 BCD 값이 정책으로 보호됩니다. 실습 VM에서는 펌웨어(VM 설정)에서 Secure Boot를 끄는 것이 문서화된 방법입니다. BCD를 직접 편집하는 것은 해결책이 아니며 위험합니다.

KDNET 연결에서 디버거가 입력해야 하는 값의 조합으로 옳은 것은?

  1. 타깃 IP와 타깃 컴퓨터 이름
  2. 타깃에서 설정한 포트 번호와 kdnet.exe/bcdedit가 생성한 키
  3. 심볼 서버 URL과 PDB 경로
  4. VM의 MAC 주소
KDNET은 타깃이 디버거(호스트 IP)로 연결해 오는 구조입니다. 디버거는 포트에서 기다리고, 공유된 키로 세션을 인증·암호화합니다. 그래서 타깃 설정에는 디버거 머신의 IP가, 디버거 설정에는 포트와 키가 들어갑니다.

dt nt!_EPROCESS는 잘 되는데 nt 함수의 지역 변수는 보이지 않습니다. 이유는?

  1. 심볼 캐시 폴더가 손상되었다
  2. 커널 디버깅에서는 지역 변수를 볼 수 없다
  3. Microsoft 공용 심볼은 public 심볼이라 지역 변수·소스 줄 정보가 제거되어 있다
  4. KDNET 대역폭이 부족하다
공용 심볼 서버는 함수·전역 변수와 일부 타입 정보를 제공하지만 private 정보는 제거되어 있습니다. 자신이 빌드한 드라이버의 PDB는 private 심볼이라 지역 변수와 소스 단계 실행이 가능합니다.

새 드라이버를 개발할 때 Driver Verifier를 처음부터 켜 두는 가장 큰 이유는?

  1. 드라이버 실행 속도가 빨라진다
  2. 서명 없이 드라이버를 로드할 수 있다
  3. 규칙 위반(풀 손상, IRQL 위반 등)이 일어난 그 자리에서 버그체크를 일으켜, 증상이 나중에 다른 곳에서 나타나는 것을 막는다
  4. PatchGuard를 비활성화한다
커널 버그의 가장 큰 어려움은 원인과 증상의 거리입니다. Verifier는 추가 검사로 위반 시점에 DRIVER_VERIFIER_DETECTED_VIOLATION(0xC4) 등으로 멈추게 해 원인 근처의 스택을 남깁니다. 실행 속도는 오히려 느려집니다.

책에 적힌 _EPROCESS 필드 오프셋을 내 실습 VM에서 쓰려 합니다. 가장 신뢰할 수 있는 확인 방법은?

  1. 책의 오프셋을 그대로 사용한다
  2. 가장 최근 블로그 글의 값을 쓴다
  3. 대상 시스템에 맞는 심볼을 로드하고 dt nt!_EPROCESS로 직접 확인한다
  4. ReactOS 소스의 구조체 정의를 따른다
구조체 레이아웃은 빌드마다 바뀝니다. Vergilius 같은 레퍼런스는 비교에 편리하지만, 최종 근거는 대상 빌드의 심볼로 직접 확인한 값입니다. ReactOS는 독립 구현이라 레이아웃이 다릅니다.

핵심 요약

  • 실습은 개발 VM + 타깃 VM 구성에서 한다. 타깃은 Secure Boot 끔 → KDNET(포트·키) → 테스트 서명 → 스냅숏 순으로 준비한다.
  • 심볼은 .symfix+로 공용 심볼과 캐시를, .sympath+로 내 드라이버 PDB를 더한다. 공용 심볼에는 private 정보가 없다.
  • 개발 루프는 빌드 → 서명 → 배포 → 로드(Verifier) → 디버깅 → 기록이며, 스냅숏이 루프를 빠르게 만든다.
  • 챕터별 랩은 "검증 방법"으로 스스로 확인하고, 역량 매트릭스로 약한 영역을 골라 보강한다.
  • 트랙(드라이버 개발·장애 분석·보안 연구)별 프로젝트는 "무엇을 검증했는가"가 드러나게 기록해 포트폴리오로 만든다.
