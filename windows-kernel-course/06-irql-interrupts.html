Part II · Chapter 06

IRQL · 인터럽트 · DPC · APC

스레드 우선순위보다 한 층 위에 있는 "CPU의 우선순위". 커널 코드가 언제 무엇을 할 수 있는지는 전부 IRQL이 결정합니다.

심화⏱ 약 100분선수: 04 프로세스와 스레드, 05 스케줄링

학습 목표

  • x64 IRQL 사다리(0~15)와 CR8(TPR)의 관계, 인터럽트 벡터와 IRQL의 대응을 설명할 수 있다.
  • 장치 인터럽트가 IOAPIC/MSI → Local APIC → IDT → KiInterruptDispatch → ISR로 전달되는 경로를 그릴 수 있다.
  • ISR과 DPC로 일을 나누는 이유, DPC 큐의 동작(중요도·대상 CPU·워치독)을 설명하고 올바른 ISR/DPC 코드를 작성할 수 있다.
  • 커널/스페셜 커널/유저 APC의 전달 조건과 alertable 대기, 크리티컬/가디드 리전의 효과를 구분할 수 있다.
  • IRQL별로 허용되는 작업을 판단하고, IRQL_NOT_LESS_OR_EQUAL 계열 버그체크의 원인을 덤프에서 추적할 수 있다.

스레드 우선순위 위의 또 다른 우선순위

05장의 스케줄러는 스레드끼리의 우선순위(0~31)를 다룹니다. 하지만 스케줄러 자신도 코드이고, 그 코드가 실행되는 동안 네트워크 카드가 패킷을 받거나 클럭이 틱을 울리면 누가 먼저일까요? Windows는 이 질문에 IRQL(Interrupt Request Level)로 답합니다. IRQL은 각 CPU가 현재 어느 수준의 인터럽트까지 막고 있는가를 나타내는 값이며, 스레드가 아니라 프로세서의 상태입니다.

스레드 우선순위 (0–31)

스케줄러가 "다음에 어떤 스레드를 돌릴지" 고를 때 쓰는 값. 스레드 객체(KTHREAD.Priority)에 붙어 있고, 컨텍스트 스위치로 바뀝니다.

IRQL (x64: 0–15)

CPU가 "지금 어떤 인터럽트를 받아들일지" 정하는 값. CPU마다 하나(CR8). IRQL이 2 이상이면 그 CPU에서는 스케줄러 자체가 돌지 못하므로 스레드 우선순위는 의미가 없습니다.

규칙은 단 하나입니다. 현재 IRQL보다 높은 IRQL의 인터럽트만 CPU를 선점할 수 있고, 같거나 낮은 것은 IRQL이 내려갈 때까지 보류된다. 이 단순한 규칙에서 "DISPATCH_LEVEL에서는 페이지 폴트를 낼 수 없다", "스핀락을 잡으면 대기하면 안 된다" 같은 커널 프로그래밍의 거의 모든 금기가 파생됩니다.

x64 IRQL 사다리와 CR8

x64 Windows의 IRQL은 0~15의 16단계입니다. 아래 사다리의 각 단을 클릭하면 그 수준에서 무엇이 실행되는지, 무엇이 금지되는지 볼 수 있습니다.

32비트 x86 Windows는 0–31 범위를 쓰며 값이 다릅니다(예: CLOCK2_LEVEL 28). 이 코스는 x64 기준입니다.

CR8 — IRQL을 하드웨어가 직접 들고 있다

x64에서 IRQL은 소프트웨어 변수가 아니라 제어 레지스터 CR8에 들어 있습니다. CR8은 Local APIC의 TPR(Task Priority Register)의 우선순위 클래스(4비트)를 직접 읽고 쓰는 창구입니다. Local APIC는 대기 중인 인터럽트의 벡터 상위 4비트(우선순위 클래스)가 TPR보다 클 때만 CPU에 전달합니다. Windows는 벡터를 할당할 때 "벡터 >> 4 = IRQL"이 되도록 맞추므로, mov cr8, n 한 번으로 "IRQL n 이하 인터럽트 마스킹"이 하드웨어적으로 완성됩니다. 

; KIRQL KeGetCurrentIrql(void)
mov     rax, cr8            ; CR8[3:0] = 현재 IRQL

; KeRaiseIrql(DISPATCH_LEVEL, &OldIrql)
mov     rax, cr8
mov     byte ptr [rdx], al  ; OldIrql 저장
mov     ecx, 2
mov     cr8, rcx            ; IRQL 2 이하 벡터(0x00–0x2F 클래스) 마스킹

; KeLowerIrql(OldIrql)
movzx   ecx, byte ptr [OldIrql]
mov     cr8, rcx            ; 보류된 더 높은 인터럽트가 있으면 즉시 들어옴
IRQL은 CPU별 상태다 — 그래서 "IRQL로 동기화"는 단일 CPU에서만 통한다

CPU 0에서 IRQL을 DISPATCH로 올려도 CPU 1의 DPC는 자유롭게 돕니다. IRQL 상승은 같은 CPU에서의 선점만 막습니다. 여러 CPU 간 공유 데이터는 반드시 스핀락이나 Interlocked 연산(07장)으로 보호해야 합니다. 스핀락이 IRQL 상승과 락 비트를 함께 쓰는 이유가 이것입니다.

IRQL 1·2는 "소프트웨어" 수준

APC_LEVEL과 DISPATCH_LEVEL에 대응하는 장치 인터럽트는 없습니다. 커널이 "DPC를 처리해야 함", "APC를 전달해야 함"이라는 요청을 기록해 두고, IRQL이 그 아래로 내려가는 순간 처리합니다. IDT에도 이를 위한 벡터(KiApcInterrupt, KiDpcInterrupt)가 있지만, 실제로 자체 인터럽트를 쓸지 IRQL을 낮추는 경로에서 직접 확인할지는 상황과 빌드에 따라 다릅니다. 개념적으로는 "보류된 소프트웨어 인터럽트"로 이해하면 충분합니다.

IDT와 인터럽트 디스패치

CPU는 인터럽트나 예외가 발생하면 IDT(Interrupt Descriptor Table)에서 벡터 번호(0–255)에 해당하는 게이트를 찾아 그 주소로 점프합니다. IDT는 CPU마다 하나씩 있으며 KPCR에서 찾을 수 있습니다. 벡터 0–31은 CPU 예외용으로 예약되어 있고, 그 위는 OS가 자유롭게 배치합니다.

0x01 / 0x03#DB / #BPKiDebugTrapOrFault / KiBreakpointTrap
0x02NMIKiNmiInterrupt
0x08#DF 더블 폴트KiDoubleFaultAbort (별도 IST 스택)
0x0D / 0x0E#GP / #PFKiGeneralProtectionFault / KiPageFault
0x12#MC 머신체크KiMcheckAbort

핸들러 이름과 벡터 배치는 빌드·구성에 따라 다를 수 있습니다. 실제 값은 !idt로 확인하세요.

장치 인터럽트 하나가 ISR에 도달하기까지를 따라가 봅시다. 예시 장치에는 벡터 0x51(→ IRQL 5)이 할당되어 있다고 가정합니다.

KINTERRUPT — ISR 연결의 실체

드라이버가 IoConnectInterruptEx(또는 KMDF의 WdfInterruptCreate)를 호출하면 커널은 KINTERRUPT 객체를 만들어 벡터에 연결합니다. 같은 벡터를 여러 장치가 공유(레벨 트리거 라인)하면 KINTERRUPT들이 리스트로 이어지고, 커널은 하나가 TRUE를 반환할 때까지 차례로 ISR을 호출합니다.

필드 구성과 오프셋은 빌드마다 다릅니다. 위 표는 의미 위주이며 정확한 배치는 dt nt!_KINTERRUPT로 확인하세요.

Local APIC · IOAPIC · MSI

x64 시스템의 인터럽트 하드웨어는 세 부분으로 나뉩니다. CPU마다 하나씩 있는 Local APIC, 레거시 라인 인터럽트를 메시지로 바꿔 주는 IOAPIC, 그리고 장치가 IOAPIC을 거치지 않고 직접 메시지를 보내는 MSI/MSI-X입니다. 구성 요소를 클릭해 보세요.

장치 관리자에서 보는 인터럽트

장치 관리자 → 보기 → "연결별 리소스" → 인터럽트 요청(IRQ)에서 음수 IRQ 번호(예: -2147483xxx)로 표시되는 항목이 MSI 메시지입니다. 라인 기반 장치는 0~수백 범위의 GSI 번호로 보입니다.

ISR → DPC 분할 처리

ISR은 DIRQL에서 실행되므로, 실행되는 동안 그 CPU에서는 같거나 낮은 IRQL의 모든 인터럽트, 모든 DPC, 모든 스레드가 멈춥니다. 그래서 Windows 드라이버 모델은 일을 둘로 나눕니다. ISR은 "장치를 조용히 만들고 상태를 저장하는" 최소한만 하고, 나머지는 DPC(Deferred Procedure Call)로 미뤄 DISPATCH_LEVEL에서 처리합니다. DPC는 하드웨어 인터럽트를 막지 않으므로 다른 장치가 기다리지 않습니다.

KDPC와 CPU별 DPC 큐

DPC는 KDPC 객체로 표현되며 CPU마다 하나씩 있는 DPC 큐(KPRCB의 DpcData)에 들어갑니다. 기본적으로 KeInsertQueueDpc를 호출한 CPU의 큐에 들어가므로, ISR이 실행된 CPU에서 DPC도 실행되어 캐시 지역성이 좋습니다.

올바른 ISR/DPC 코드

typedef struct _DEV_EXT {
    PKINTERRUPT   Interrupt;
    KDPC          Dpc;              // KeInitializeDpc(&ext->Dpc, MyDpc, ext)
    volatile LONG PendingStatus;    // ISR이 누적, DPC가 소비
    PUCHAR        Regs;             // MmMapIoSpaceEx로 매핑한 장치 레지스터
} DEV_EXT, *PDEV_EXT;

// DIRQL, 인터럽트 스핀락 보유 상태로 호출됨
BOOLEAN MyIsr(_In_ PKINTERRUPT Interrupt, _In_ PVOID Context)
{
    PDEV_EXT ext = (PDEV_EXT)Context;
    ULONG st = READ_REGISTER_ULONG((PULONG)(ext->Regs + REG_INT_STATUS));
    if ((st & INT_MINE) == 0)
        return FALSE;                       // 공유 라인: 내 장치가 아님

    WRITE_REGISTER_ULONG((PULONG)(ext->Regs + REG_INT_STATUS), st);  // ack → 라인 내림
    InterlockedOr(&ext->PendingStatus, (LONG)st);                    // 덮어쓰지 말고 누적
    KeInsertQueueDpc(&ext->Dpc, NULL, NULL);   // 이미 큐에 있으면 FALSE — 괜찮다
    return TRUE;
}

// DISPATCH_LEVEL, DPC 스택에서 실행
VOID MyDpc(_In_ PKDPC Dpc, _In_opt_ PVOID Context, _In_opt_ PVOID A1, _In_opt_ PVOID A2)
{
    PDEV_EXT ext = (PDEV_EXT)Context;
    LONG st = InterlockedExchange(&ext->PendingStatus, 0);   // 누적분 한 번에 소비
    // 논페이지 데이터만 접근. 대기 금지. 완료할 IRP가 있으면:
    // IoCompleteRequest(Irp, IO_NETWORK_INCREMENT);
    UNREFERENCED_PARAMETER(Dpc); UNREFERENCED_PARAMETER(A1); UNREFERENCED_PARAMETER(A2);
    UNREFERENCED_PARAMETER(st);
}
// EvtDevicePrepareHardware 이전(보통 EvtDriverDeviceAdd)에서 생성
WDF_INTERRUPT_CONFIG cfg;
WDF_INTERRUPT_CONFIG_INIT(&cfg, EvtIsr, EvtDpc);
status = WdfInterruptCreate(Device, &cfg, WDF_NO_OBJECT_ATTRIBUTES, &devCtx->Interrupt);

BOOLEAN EvtIsr(_In_ WDFINTERRUPT Interrupt, _In_ ULONG MessageID)   // DIRQL
{
    PDEV_CTX ctx = DevGetContext(WdfInterruptGetDevice(Interrupt));
    if (!DeviceRaisedInterrupt(ctx)) return FALSE;
    AckDevice(ctx);
    WdfInterruptQueueDpcForIsr(Interrupt);   // 프레임워크가 내부 KDPC 관리
    return TRUE;
}

VOID EvtDpc(_In_ WDFINTERRUPT Interrupt, _In_ WDFOBJECT AssociatedObject)  // DISPATCH_LEVEL
{
    // ISR과 공유하는 데이터는 WdfInterruptAcquireLock / WdfInterruptSynchronize로 보호
}

KMDF는 PASSIVE_LEVEL 인터럽트 처리(PassiveHandling, EvtInterruptWorkItem)도 지원합니다. GPIO/I²C 기반 SoC 장치처럼 레지스터 접근 자체가 대기를 필요로 할 때 씁니다.

IO_CONNECT_INTERRUPT_PARAMETERS p;
RtlZeroMemory(&p, sizeof(p));
p.Version = CONNECT_MESSAGE_BASED;
p.MessageBased.PhysicalDeviceObject   = ext->Pdo;
p.MessageBased.ConnectionContext.InterruptMessageTable = &ext->MsgInfo; // PIO_INTERRUPT_MESSAGE_INFO
p.MessageBased.MessageServiceRoutine  = MyMsiIsr;   // BOOLEAN (PKINTERRUPT, PVOID, ULONG MessageId)
p.MessageBased.ServiceContext         = ext;
p.MessageBased.FallBackServiceRoutine = MyIsr;      // MSI를 쓸 수 없으면 라인 기반으로
status = IoConnectInterruptEx(&p);
// 성공 후 p.Version이 CONNECT_LINE_BASED로 바뀌어 있으면 폴백된 것
// 해제: IoDisconnectInterruptEx (IRP_MN_STOP/REMOVE_DEVICE)
DPC 시간 예산과 DPC 워치독

Microsoft 드라이버 성능 지침은 ISR은 수십 µs, DPC는 100 µs 안팎을 넘지 않도록 권고합니다. DPC가 길면 오디오 끊김·입력 지연 같은 증상이 나타나며, 더 심하면 DPC_WATCHDOG_VIOLATION(0x133)으로 버그체크합니다. Arg1=0은 단일 DPC가 시간 한도를 넘은 경우, Arg1=1은 DISPATCH_LEVEL 이상에서 누적으로 너무 오래 머문 경우(예: 스핀락을 오래 잡고 반복)입니다. 한도 값은 버전·설정마다 다르며 KeQueryDpcWatchdogInformation으로 현재 값을 조회할 수 있습니다.

스레드드 DPC

KeInitializeThreadedDpc로 초기화한 DPC는 DISPATCH_LEVEL 대신 PASSIVE_LEVEL에서 CPU별 우선순위 31 스레드가 실행합니다. 일반 DPC처럼 거의 모든 스레드보다 먼저 실행되지만, 일반 DPC와 하드웨어 인터럽트에 선점될 수 있어 시스템 지연을 덜 해칩니다. 다만 앞서 말했듯 비활성화되면 DISPATCH_LEVEL에서 돌기 때문에 대기·페이지 가능 메모리는 여전히 금지입니다. "PASSIVE에서 도니까 대기해도 된다"는 흔한 오해입니다.

타이머와 타이머 DPC

클럭 인터럽트는 CLOCK_LEVEL에서 시간을 갱신하고, 만료된 타이머가 있으면 타이머 만료 처리를 DPC로 요청합니다. 그러면 DISPATCH_LEVEL에서 만료된 KTIMER들이 시그널되고(타이머도 디스패처 객체 → 07장), 타이머에 연결된 DPC가 큐잉됩니다. 타이머는 CPU별 타이머 테이블(KPRCB)에 만료 시각 기준으로 해시되어 저장됩니다(구조는 버전마다 다름). 

KTIMER g_Timer;
KDPC   g_TimerDpc;

VOID TimerDpc(PKDPC Dpc, PVOID Ctx, PVOID A1, PVOID A2)   // DISPATCH_LEVEL
{
    // 짧게. 긴 작업은 IoQueueWorkItem으로 PASSIVE_LEVEL 워커에게 넘긴다
}

NTSTATUS StartTimer(PVOID ctx)
{
    LARGE_INTEGER due;
    KeInitializeTimerEx(&g_Timer, NotificationTimer);
    KeInitializeDpc(&g_TimerDpc, TimerDpc, ctx);
    due.QuadPart = -10LL * 1000 * 1000;         // 음수 = 상대 시간, 100ns 단위 → 1초 후
    KeSetTimerEx(&g_Timer, due, 500, &g_TimerDpc);  // 이후 500ms 주기
    return STATUS_SUCCESS;
}

VOID StopTimer(void)   // 언로드 경로, PASSIVE_LEVEL
{
    KeCancelTimer(&g_Timer);
    KeFlushQueuedDpcs();   // 이미 큐잉되었거나 실행 중인 DPC가 끝날 때까지 대기
}

타이머 해상도

기본 클럭 간격 15.625 ms. 해상도 요청(ExSetTimerResolution, 유저의 timeBeginPeriod)으로 짧아집니다. Windows 10 2004부터 timeBeginPeriod의 효과는 요청 프로세스 쪽으로 제한됩니다.

타이머 병합

KeSetCoalescableTimer의 TolerableDelay로 "이 정도는 늦어도 된다"고 알려 주면 커널이 여러 타이머를 같은 틱에 묶어 CPU를 덜 깨웁니다(전력 절감).

고해상도·Dynamic Tick

ExAllocateTimer + EX_TIMER_HIGH_RESOLUTION(Windows 8.1+)은 클럭 간격보다 정밀한 만료를 요청합니다. Windows 8부터 유휴 CPU는 틱을 건너뛰는 Dynamic Tick으로 동작합니다.

언로드 경합: KeCancelTimer만으로는 부족하다

KeCancelTimer가 FALSE를 반환했다면 타이머는 이미 만료되어 DPC가 큐에 있거나 다른 CPU에서 실행 중일 수 있습니다. 이 상태로 드라이버 이미지를 언로드하면 DPC가 사라진 코드를 실행해 DRIVER_UNLOADED_WITHOUT_CANCELLING_PENDING_OPERATIONS(0xCE) 등으로 크래시합니다. KeFlushQueuedDpcs로 모든 CPU의 DPC 큐가 한 번씩 비워질 때까지 기다리거나, 07장의 런다운 보호를 사용하세요.

APC — 특정 스레드의 문맥에서 실행하기

DPC는 "어느 스레드든 상관없이 이 CPU에서" 실행됩니다. 반면 APC(Asynchronous Procedure Call)는 특정 스레드의 문맥, 즉 그 스레드의 프로세스 주소 공간·보안 토큰을 그대로 쓰면서 실행되어야 하는 작업을 위한 장치입니다. I/O 완료 결과를 요청한 프로세스의 유저 버퍼에 복사하기, 스레드 종료·일시 중지, 다른 스레드의 레지스터 문맥 읽기/쓰기가 모두 APC로 구현됩니다.

KAPC와 스레드의 APC 상태

APC는 KAPC 객체(Thread, KernelRoutine, RundownRoutine, NormalRoutine, NormalContext, SystemArgument1/2, ApcMode, ApcStateIndex, Inserted)로 표현되고, 대상 스레드의 KTHREAD.ApcState.ApcListHead[KernelMode | UserMode] 두 리스트에 들어갑니다. 스레드에는 KernelApcPending, UserApcPending 같은 보류 플래그와 KernelApcDisable/SpecialApcDisable 카운터(크리티컬/가디드 리전 깊이)가 있습니다. KeStackAttachProcess로 다른 프로세스에 붙으면 SavedApcState로 원래 APC 상태가 옮겨져, 원래 프로세스 문맥을 기대하는 APC가 엉뚱한 주소 공간에서 실행되지 않게 합니다.

KeInitializeApc / KeInsertQueueApc는 비공개 API

두 함수는 익스포트되어 있지만 문서화되지 않았습니다. 보안 제품과 루트킷이 프로세스에 코드를 주입할 때 자주 쓰지만, 시그니처와 동작이 바뀔 수 있고 스레드 종료와의 경합(RundownRoutine 처리) 등 함정이 많습니다. 일반 드라이버는 워크 아이템·이벤트로 같은 목적을 달성하세요.

유저 APC는 어떻게 유저 코드까지 가는가

크리티컬 리전 KeEnterCriticalRegion

KernelApcDisable를 감소시켜 일반 커널 APC(그리고 유저 APC)를 막습니다. 특수 커널 APC는 여전히 전달됩니다. ERESOURCE·푸시락을 잡기 전에 필수 — 락을 쥔 채 일시 중지 APC로 멈추는 것을 막기 위해서입니다. 짝이 안 맞으면 APC_INDEX_MISMATCH(0x1)로 버그체크.

가디드 리전 KeEnterGuardedRegion

SpecialApcDisable를 감소시켜 특수 커널 APC까지 모든 APC를 막습니다. IRQL은 0으로 남으므로 APC_LEVEL로 올리는 것과 효과는 비슷하지만 IRQL을 바꾸지 않습니다. 가디드 뮤텍스가 원래 이 방식으로 구현되었습니다(07장).

보안 관점: APC는 공격과 방어 양쪽의 단골 도구

"Early Bird" 인젝션은 일시 중지 상태로 만든 프로세스의 메인 스레드에 유저 APC를 큐잉해 프로세스 초기화 중(NtTestAlert)에 실행시키는 기법이고, 일부 EDR은 커널 APC로 새 프로세스에 모니터링 DLL을 주입합니다. 반대로 커널 APC 큐잉은 ETW(Threat Intelligence 공급자) 등에서 관찰 대상이 됩니다(16장).

IRQL_NOT_LESS_OR_EQUAL은 왜 "페이지드 메모리"와 연결되는가

페이지가 메모리에 없으면 #PF가 나고 MmAccessFault가 디스크에서 페이지를 읽어 와야 합니다. 디스크 I/O를 기다리려면 스레드를 대기시켜야 하는데, IRQL ≥ DISPATCH_LEVEL에서는 스레드 전환이 불가능합니다. 그래서 페이지 폴트 처리기는 IRQL이 높으면 해결을 시도하지 않고 버그체크합니다. 같은 이유로 높은 IRQL에서 잘못된 포인터(NULL, 해제된 풀, 유저 주소)를 건드려도 PAGE_FAULT_IN_NONPAGED_AREA(0x50)가 아니라 이 계열로 보고됩니다.

0xA IRQL_NOT_LESS_OR_EQUAL

Arg1 = 참조한 주소, Arg2 = 당시 IRQL, Arg3 = 접근 종류 비트(bit0: 쓰기, bit3: 실행), Arg4 = 참조한 명령 주소.

0xD1 DRIVER_IRQL_NOT_LESS_OR_EQUAL

같은 상황이 드라이버 코드에서 발생했을 때 주로 보고됩니다. Arg4의 명령 주소가 어느 모듈인지(ln)가 1차 단서입니다.

확인 문제

x64 Windows에서 KeGetCurrentIrql()은 현재 IRQL을 어디에서 읽나요?

  1. 현재 스레드의 KTHREAD.Irql 필드
  2. CR8 레지스터 (Local APIC TPR과 연동)
  3. IDT의 현재 엔트리
  4. RFLAGS의 IF 비트
x64에서 IRQL은 CR8에 있으며, CR8은 Local APIC TPR의 우선순위 클래스를 반영합니다. IRQL은 스레드가 아니라 CPU 상태이므로 KTHREAD 필드가 아닙니다. IF 비트는 모든 마스커블 인터럽트를 끄고 켜는 스위치일 뿐 수준 개념이 없습니다.

DPC 루틴에서 페이지드 풀 버퍼를 읽는 코드가 테스트에서는 잘 돌다가 운영 환경에서 가끔 0xD1로 크래시합니다. 가장 정확한 설명은?

  1. DPC는 다른 프로세스 문맥에서 실행되므로 커널 주소가 바뀐다
  2. 페이지드 풀은 DISPATCH_LEVEL에서 읽기는 되고 쓰기만 금지된다
  3. 페이지가 상주할 때는 문제없지만, 페이지 아웃된 때 DISPATCH_LEVEL에서 페이지 폴트가 나면 디스크 I/O를 기다릴 수 없어 버그체크한다
  4. DPC 스택이 작아서 오버플로가 난다
페이지 폴트 해결에는 대기(스레드 전환)가 필요하고, IRQL ≥ 2에서는 불가능합니다. 메모리 압박 시에만 재현되는 간헐적 버그의 전형이며, Verifier의 Force IRQL checking으로 즉시 드러낼 수 있습니다. 커널 주소 공간은 모든 프로세스에서 공유되므로 1번은 틀렸고, 읽기/쓰기 구분은 없습니다.

ISR에서 KeInsertQueueDpc가 FALSE를 반환했습니다. 무엇을 의미하고 어떻게 해야 하나요?

  1. DPC 큐가 가득 찼으므로 인터럽트를 무시해야 한다
  2. 그 KDPC가 이미 큐에 있다는 뜻이다. ISR은 처리할 상태를 장치 확장에 누적해 두고, DPC가 실행될 때 누적분을 한꺼번에 처리하도록 설계해야 한다
  3. DIRQL에서는 DPC를 큐잉할 수 없으므로 IRQL을 낮춰 다시 시도한다
  4. 다른 CPU에서 DPC가 실행 중이므로 스핀하며 기다린다
한 KDPC는 동시에 한 번만 큐에 들어갈 수 있습니다. 여러 인터럽트가 DPC 실행 전에 몰리면 하나로 합쳐지므로, SystemArgument로 데이터를 넘기는 설계는 유실을 낳습니다. KeInsertQueueDpc는 모든 IRQL에서 호출 가능하고, ISR에서 스핀 대기는 금물입니다.

유저 스레드가 WaitForSingleObject(h, INFINITE)(bAlertable 없음)로 대기 중일 때 다른 스레드가 QueueUserAPC로 APC를 큐잉하면?

  1. 즉시 대기가 깨지고 APC가 실행된다
  2. APC가 거부되고 QueueUserAPC가 실패한다
  3. APC는 스레드의 유저 APC 큐에 보류되고, 스레드가 alertable 대기에 들어가거나 NtTestAlert를 호출할 때까지 실행되지 않는다
  4. 커널이 APC를 특수 커널 APC로 바꿔 즉시 실행한다
일반 유저 APC의 전달 조건은 UserMode alertable 대기(또는 NtTestAlert)입니다. 큐잉 자체는 성공합니다. 대기 없이도 전달하려면 Windows 11의 스페셜 유저 APC(QueueUserAPC2)가 필요합니다. 특수 커널 APC는 커널 코드만 큐잉할 수 있고 유저 함수를 실행하지 않습니다.

KeEnterCriticalRegion을 호출한 스레드(IRQL 0)에게 여전히 전달될 수 있는 것은?

  1. 일반 커널 APC
  2. 특수 커널 APC
  3. 유저 APC
  4. 아무것도 전달되지 않는다
크리티컬 리전은 KernelApcDisable만 건드려 일반 커널 APC(그리고 유저 APC)를 막습니다. 특수 커널 APC까지 막으려면 가디드 리전(SpecialApcDisable)이나 APC_LEVEL 상승이 필요합니다. 그래서 크리티컬 리전 안에서도 I/O 완료 APC는 정상 동작합니다.

스레드드 DPC에 대한 설명으로 옳은 것은?

  1. PASSIVE_LEVEL에서 실행되므로 KeWaitForSingleObject로 대기해도 된다
  2. 페이지드 메모리를 자유롭게 쓸 수 있다
  3. 보통 PASSIVE_LEVEL의 우선순위 31 스레드에서 실행되지만, 비활성화되면 DISPATCH_LEVEL에서 실행되므로 DISPATCH_LEVEL 규칙을 지켜야 한다
  4. 하드웨어 인터럽트를 막고 실행된다
스레드드 DPC는 지연 시간 개선을 위한 장치일 뿐, 실행 수준이 보장되지 않습니다. 시스템 설정에 따라 일반 DPC로 동작하므로 코드는 DISPATCH_LEVEL을 가정해야 하고, 락은 KeAcquireSpinLockForDpc를 씁니다.

핵심 요약

  • IRQL은 CPU별 상태이며 x64에서는 CR8(=LAPIC TPR)에 있다. 현재 IRQL보다 높은 인터럽트만 선점하고, 나머지는 IRQL이 내려갈 때 처리된다.
  • 장치 인터럽트: IOAPIC/MSI → Local APIC(IRR/ISR/TPR) → IDT[벡터] → KiInterruptDispatch(IRQL↑, 인터럽트 스핀락) → ISR → EOI → IRQL 복원.
  • ISR은 ack·상태 저장·DPC 큐잉만. DPC는 DISPATCH_LEVEL에서 CPU별 큐로 실행되며, 한 KDPC는 한 번만 큐잉된다(누적 설계 필요).
  • APC는 특정 스레드 문맥에서 실행된다. 특수 커널 → 일반 커널 → 유저 순으로 전달 조건이 까다로워지며, 유저 APC는 alertable 대기가 필요하다.
  • IRQL ≥ DISPATCH: 대기·페이지드 메모리 금지. 위반은 0xA/0xD1/0xB8/0x133 등으로 끝나며, Driver Verifier로 미리 드러내야 한다.
