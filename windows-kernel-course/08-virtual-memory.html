Part III · Chapter 08

가상 메모리와 페이징

모든 메모리 접근의 바닥에는 CPU의 주소 변환이 있습니다. 64비트 주소 한 개가 물리 바이트 하나로 바뀌는 과정을 비트 단위로 해부합니다.

핵심⏱ 약 100분선수: 01·02장, 이진수/16진수

학습 목표

  • x64 정규(canonical) 주소 규칙과 Windows의 유저/커널 주소 공간 분할(128TB/128TB)을 설명할 수 있다.
  • 임의의 64비트 가상 주소를 PML4/PDPT/PD/PT 인덱스와 오프셋으로 손으로 분해하고, CR3에서 시작하는 테이블 워크를 그릴 수 있다.
  • 하드웨어 PTE의 각 비트(P, R/W, U/S, PWT, PCD, A, D, PS, G, NX, PFN)의 의미와 Windows가 쓰는 소프트웨어 비트를 구분할 수 있다.
  • TLB·PCID·TLB shootdown이 왜 필요한지, 대형 페이지가 무엇을 절약하는지 설명할 수 있다.
  • PTE 셀프맵으로 PTE의 가상 주소를 계산하고, 유효하지 않은(소프트웨어) PTE의 종류를 구분할 수 있다.
  • WinDbg !pte, !vtop, !address로 실제 변환 과정을 검증할 수 있다.

가상 메모리가 해결하는 문제

프로세스가 사용하는 모든 포인터는 가상 주소(VA)입니다. CPU의 MMU는 메모리에 접근할 때마다 이 주소를 물리 주소(PA)로 변환하며, 변환 규칙은 운영체제가 만들어 둔 페이지 테이블에 들어 있습니다. 이 한 단계의 간접 참조 덕분에 다음이 가능해집니다.

격리

프로세스마다 다른 페이지 테이블(다른 CR3)을 쓰므로 같은 VA 0x7FF6`12345678이 프로세스마다 다른 물리 페이지를 가리킨다.

보호

페이지 단위로 읽기/쓰기/실행, 유저/커널 접근 권한을 하드웨어가 강제한다. 위반하면 #PF.

지연 할당과 페이징

"존재하지 않음(P=0)"을 표시해 두고 첫 접근 때 폴트로 채운다. 물리 메모리보다 큰 커밋, 파일 매핑, 공유가 모두 이 위에서 동작한다.

이 장은 하드웨어가 정의한 부분(주소 형식, 페이지 테이블 구조, PTE 비트, TLB)과 Windows가 그 위에 얹은 관례(주소 공간 배치, 셀프맵, 소프트웨어 PTE)를 다룹니다. 폴트가 실제로 어떻게 처리되는지, 물리 페이지가 어떻게 관리되는지는 09장의 몫입니다.

용어 정리 — Intel 이름과 Windows 이름

Intel/AMD 문서는 4단계 테이블을 PML4 → PDPT → PD → PT, 엔트리를 PML4E/PDPTE/PDE/PTE라고 부릅니다. Windows 디버거와 심볼은 같은 것을 PXE / PPE / PDE / PTE라고 부릅니다(!pte 출력의 "PXE at …", "PPE at …"). 이 장은 두 표기를 섞어 쓰니 짝을 기억해 두세요. 페이지 하나는 4KB(0x1000), 물리 페이지 번호는 PFN(Page Frame Number = PA >> 12)입니다.

x64 정규 주소

x64 레지스터는 64비트지만, 4단계 페이징에서 실제로 변환에 쓰이는 것은 하위 48비트뿐입니다. 대신 CPU는 상위 16비트(63–48)가 비트 47과 같아야 한다고 요구합니다. 이런 주소를 정규(canonical) 주소라 합니다.

  • 비트 47 = 0 → 상위 16비트 모두 0: 0x00000000`00000000 ~ 0x00007FFF`FFFFFFFF (아래쪽 128TB)
  • 비트 47 = 1 → 상위 16비트 모두 1: 0xFFFF8000`00000000 ~ 0xFFFFFFFF`FFFFFFFF (위쪽 128TB)
  • 그 사이의 거대한 구멍(약 16M TB)은 비정규 — 여기를 참조하면 페이지 워크조차 하지 않고 #GP(스택 참조면 #SS)가 발생합니다. #PF가 아니라는 점이 중요합니다.
왜 #GP인가가 실전에서 중요한가

크래시 덤프에서 0xFFFF0000`12345678 같은 값을 역참조하다 죽었다면 버그체크는 페이지 폴트 계열(0x50, 0xA)이 아니라 일반 보호 예외로 나타납니다(예: 커널에서 KMODE_EXCEPTION_NOT_HANDLED나 SYSTEM_SERVICE_EXCEPTION의 예외 코드 0xC0000005). 이때 CR2는 갱신되지 않으므로 "어느 주소에서 죽었는지"를 CR2로 찾을 수 없고, 폴트 명령을 디스어셈블해 레지스터 값을 직접 봐야 합니다. 해제된 메모리에 쓰레기 값이 채워진 포인터(UAF)가 흔한 원인입니다.

5단계 페이징(LA57)을 지원하는 CPU에서 CR4.LA57=1이면 PML5가 한 단계 추가되어 57비트 가상 주소(비트 56–48이 PML5 인덱스, 63–57이 부호 확장)를 씁니다. Windows도 지원 하드웨어와 버전(주로 대용량 메모리 서버)에서 5단계 페이징을 사용할 수 있으며, 이 경우 정규 주소 범위와 셀프맵 주소 계산이 모두 달라집니다. 드라이버는 "주소는 48비트" 같은 가정을 하드코딩하면 안 됩니다. 이 장의 나머지는 4단계를 기준으로 합니다.

Windows 주소 공간 레이아웃

Windows 8.1 이후 x64 Windows는 정규 주소의 두 반쪽을 그대로 나눠 아래 128TB는 프로세스별 유저 공간, 위 128TB는 모든 프로세스가 공유하는 커널 공간으로 씁니다. (Windows 8 이전에는 유저 8TB/커널 8TB만 사용했습니다.) 아래 지도의 영역을 클릭해 보세요. 비율은 실제 크기와 무관합니다.

고정 주소를 믿지 말 것

인터넷의 오래된 자료에는 "PTE 베이스 = 0xFFFFF680`00000000", "PFN DB = 0xFFFFFA80`00000000" 같은 고정 주소가 나옵니다. Windows 10 1607(RS1)부터 커널 VA 공간은 PML4 엔트리(512GB) 단위로 동적 할당되고 무작위화되므로 이 값들은 더 이상 유효하지 않습니다. 커널 코드와 디버거는 부팅 시 결정된 값(예: nt!MmPteBase, nt!MmPfnDatabase)을 읽어 씁니다.

4단계 페이지 테이블

48비트 가상 주소는 9비트 인덱스 × 4 + 12비트 오프셋으로 쪼개집니다. 각 테이블은 정확히 한 페이지(4KB)이고 8바이트 엔트리 512개(29)를 담습니다. 그래서 인덱스가 9비트입니다. 한 PML4 엔트리는 512GB, PDPT 엔트리는 1GB, PD 엔트리는 2MB, PT 엔트리는 4KB를 담당합니다.

워크의 출발점은 CR3 레지스터입니다. CR3의 비트 51–12는 현재 PML4 테이블의 물리 주소이고(페이지 테이블 안의 모든 포인터도 물리 주소입니다), CR4.PCIDE=1이면 하위 12비트는 PCID(아래 TLB 절)입니다. Windows는 프로세스의 CR3 값을 KPROCESS.DirectoryTableBase에 저장하고, 컨텍스트 스위치에서 다른 프로세스의 스레드로 바뀔 때 CR3를 다시 씁니다(!process 출력의 DirBase).

손 계산 요령

16진수에서 바로 읽는 법: 오프셋은 마지막 3자리(678). PT 인덱스는 VA >> 12의 하위 9비트, 즉 0x7FF612345 & 0x1FF = 0x145. WinDbg에서는 ? (0x7ff612345678 >> 0n39) & 0x1ff처럼 MASM 식으로 검산할 수 있고, .formats로 이진수 표기를 볼 수 있습니다.

실습 도구: 주소 변환기

아래 변환기에 64비트 주소를 넣으면 정규성 검사 → 비트 분해 → 테이블 워크 애니메이션 → 셀프맵 PTE 주소 계산까지 보여 줍니다. 물리 메모리의 내용(각 테이블의 PFN)은 가상의 결정적(deterministic) 값으로 만들어지지만, 인덱스·엔트리 주소·비트 연산은 실제 하드웨어 규칙 그대로입니다. 셀프맵 인덱스를 넣고 "셀프맵 영역" 예시를 눌러 워크가 PML4로 되돌아오는 것도 확인해 보세요.

에러 코드로 폴트 원인을 읽는다

#PF가 나면 CPU는 폴트 주소를 CR2에, 원인을 스택의 에러 코드에 넣습니다: 비트 0 P(0=존재하지 않는 페이지, 1=권한 위반), 비트 1 W/R(쓰기였는가), 비트 2 U/S(유저 모드였는가), 비트 3 RSVD(예약 비트 위반), 비트 4 I/D(명령 페치였는가), 비트 5 PK, 비트 6 SS(섀도 스택). 커널 덤프의 트랩 프레임(.trap)과 버그체크 0x50의 인자 2(읽기/쓰기/실행 구분)가 이 정보를 그대로 반영합니다. 예: 에러 코드 0x11 = 존재하는 페이지에서 명령 페치 위반 → NX 위반.

대형 페이지

PDE나 PDPTE의 PS=1이면 테이블 워크가 일찍 끝나고 남은 비트 전체가 오프셋이 됩니다. 이득은 두 가지입니다. 첫째, TLB 엔트리 하나가 2MB(또는 1GB)를 덮어 TLB 미스가 크게 줄어듭니다. 둘째, PT 페이지(512개 PTE = 4KB)가 필요 없어 페이지 테이블 메모리가 절약됩니다.

SeLockMemoryPrivilege("메모리에 페이지 잠금")가 필요하고, GetLargePageMinimum()(x64는 2MB)의 배수로 MEM_RESERVE | MEM_COMMIT | MEM_LARGE_PAGES를 한 번에 요청해야 합니다. 대형 페이지는 페이징되지 않습니다.

현실적인 함정

물리적으로 연속되고 정렬된 2MB가 필요하므로 오래 실행된 시스템에서는 단편화로 할당이 실패하거나 느릴 수 있습니다(메모리 관리자가 페이지를 옮겨 연속 공간을 만들려 시도). 데이터베이스 서버가 "부팅 직후 대형 페이지 확보"를 권장하는 이유입니다.

디버거에서 대형 페이지 알아보기

!pte로 커널 이미지 주소를 보면 PDE 줄에 대형 페이지 표시(L)가 있고 PTE 줄이 없거나 "LARGE PAGE"로 표시되는 경우가 있습니다. 이때 PFN은 2MB 정렬 기준 PFN이고, 실제 PFN = 그 값 + (VA의 비트 20–12).

TLB와 무효화

4단계 워크는 메모리 접근 4번입니다. 매번 이렇게 하면 성능이 무너지므로 CPU는 최근 변환을 TLB(Translation Lookaside Buffer)에 캐시합니다. TLB는 페이지 테이블을 자동으로 따라가지 않습니다. 즉, OS가 메모리의 PTE를 바꿔도 TLB에 남은 옛 변환은 그대로 쓰일 수 있습니다. 따라서 PTE를 "약하게 만드는" 변경(무효화, 권한 축소, PFN 변경) 뒤에는 반드시 TLB를 무효화해야 합니다.

수단효과
INVLPG [va]현재 CPU에서 해당 VA의 TLB 엔트리(및 관련 페이징 구조 캐시) 제거
MOV CR3PCID 미사용 시 전역(G=1)이 아닌 모든 엔트리 제거. PCID 사용 시 비트 63=1로 쓰면 그 PCID의 엔트리를 보존
INVPCID특정 PCID/주소, 특정 PCID 전체, 전역 포함 전체 등 선택적 무효화
CR4.PGE 토글전역 엔트리까지 포함한 전체 플러시

PCID(Process-Context Identifier)는 TLB 엔트리에 12비트 태그를 붙여, CR3를 바꿔도 다른 주소 공간의 엔트리를 버리지 않고 공존시키는 기능입니다. Meltdown 대응으로 도입된 KVA Shadow는 유저 모드용과 커널 모드용 페이지 테이블을 분리해 시스템 콜·인터럽트마다 CR3를 바꾸는데, Windows는 지원 CPU에서 PCID를 활용해 이 전환마다 TLB 전체가 날아가는 비용을 줄입니다. (KVA Shadow가 켜진 프로세스는 KPROCESS에 유저용 디렉터리 베이스도 따로 가집니다 → 16장)

멀티프로세서에서는 더 어렵습니다. INVLPG는 자기 CPU의 TLB만 지웁니다. 다른 CPU에 옛 변환이 남아 있을 수 있으므로, 메모리 관리자는 IPI(프로세서 간 인터럽트)로 다른 CPU에게 무효화를 요청하고 완료를 기다립니다. 이것이 TLB shootdown입니다.

드라이버 개발자에게 주는 교훈

드라이버가 직접 PTE를 고치는 일은 지원되지 않으며(PatchGuard·HVCI와도 충돌), 고친다 해도 shootdown을 빠뜨리면 다른 CPU가 옛 매핑을 씁니다. 매핑이 필요하면 MmMapLockedPagesSpecifyCache, MmMapIoSpaceEx 같은 공식 API를 쓰고, 해제(MmUnmapLockedPages)는 반드시 짝을 맞추세요 — 무효화는 그 API들이 책임집니다.

PTE 셀프맵 (재귀 매핑)

메모리 관리자는 PTE를 수시로 읽고 써야 하지만, 페이지 테이블 안의 포인터는 전부 물리 주소이고 CPU 명령은 가상 주소로만 메모리에 접근합니다. Windows의 해법은 PML4의 엔트리 하나(인덱스 S)가 PML4 자신의 물리 페이지를 가리키게 하는 것입니다. 그러면 PML4 인덱스가 S인 주소를 변환할 때 워크가 "한 단계 헛돌아" 마지막에 데이터 페이지 대신 페이지 테이블 페이지에 도착합니다. 

// PTE_BASE = 0xFFFF000000000000 | (S << 39)   (S = 셀프맵 PML4 인덱스, 256~511)
static inline ULONG64 PteAddress(ULONG64 Va) {
    // VA[47:12] (36비트 VPN) × 8 바이트 = 39비트 오프셋
    return PteBase + ((Va >> 9) & 0x7FFFFFFFF8ull);
}
static inline ULONG64 PdeAddress(ULONG64 Va) { return PteAddress(PteAddress(Va)); }
static inline ULONG64 PpeAddress(ULONG64 Va) { return PteAddress(PdeAddress(Va)); }
static inline ULONG64 PxeAddress(ULONG64 Va) { return PteAddress(PpeAddress(Va)); }
// 역변환: PTE 주소 → 그 PTE가 매핑하는 VA (부호 확장 필요)
static inline ULONG64 VaFromPte(ULONG64 Pte) {
    LONG64 v = (LONG64)(((Pte - PteBase) >> 3) << 12) << 16;
    return (ULONG64)(v >> 16);   // 산술 시프트로 비트 47 부호 확장
}
셀프맵의 부수 효과
  • PTE 영역은 프로세스마다 다른 내용을 보여 줍니다 — 같은 PTE 주소라도 현재 CR3의 페이지 테이블이 보입니다. 그래서 다른 프로세스의 PTE를 보려면 디버거에서 .process /p(또는 !pte가 내부적으로 하는 문맥 전환)가 필요합니다.
  • PTE 영역 주소에 접근했는데 상위 단계가 비어 있으면(예: 그 512GB 범위가 쓰인 적 없음) 그 자체로 #PF가 납니다. 메모리 관리자는 "PTE 주소의 폴트"를 특별히 처리해 페이지 테이블 페이지를 만듭니다.
  • KASLR 우회 연구에서 PTE_BASE를 알아내는 것은 단골 주제입니다. 무작위화는 공격 비용을 올릴 뿐 근본 방어는 HVCI 같은 하이퍼바이저 기반 보호입니다(16장).

유효하지 않은 PTE — 소프트웨어 PTE

P=0인 PTE의 나머지 63비트는 하드웨어가 보지 않으므로 Windows는 여기에 "이 페이지를 어떻게 되살릴지"를 기록합니다. 메모리 관리자는 폴트가 나면 이 PTE의 모양을 보고 처리 경로를 고릅니다(09장의 폴트 처리기). Windows는 이를 _MMPTE 공용체의 여러 해석으로 표현합니다: Hard, Soft, Trans, Proto, Subsect 등. 비트 배치는 빌드마다 달라지므로 반드시 dt nt!_MMPTE_SOFTWARE, dt nt!_MMPTE_TRANSITION 등으로 확인하세요.

모양: P=0, Prototype=0, Transition=0, 페이지 파일 위치 = 0, Protection 필드만 설정(예: READWRITE). Windows 10 x64에서 흔히 보는 값 0x80은 Protection=4(MM_READWRITE)를 비트 5부터 넣은 것입니다.

의미: "커밋은 되었지만 아직 한 번도 만지지 않은 페이지". 첫 접근 시 메모리 관리자는 0으로 채워진 물리 페이지를 꺼내(제로 리스트) 매핑합니다. 디스크 I/O가 없는 소프트 폴트입니다.

왜 0인가: 이전 사용자의 데이터가 새 프로세스에 보이면 보안 사고이므로, 유저 프로세스에 주는 새 페이지는 반드시 0으로 초기화됩니다.

모양: P=0, Prototype=0, Transition=0, PageFileLow(어느 페이지 파일인지) + PageFileHigh(파일 안의 페이지 오프셋) + Protection.

의미: 페이지 내용이 페이지 파일에만 있습니다. 접근 시 하드 폴트: 물리 페이지를 할당하고 디스크에서 읽어 온 뒤(인페이지 I/O) 매핑합니다. 스레드는 I/O 완료까지 대기하므로 높은 IRQL에서는 처리할 수 없습니다.

모양: P=0, Prototype=0, Transition=1, PFN 필드 유지 + Protection.

의미: 워킹셋에서 빠졌지만 물리 페이지는 아직 메모리(스탠바이 또는 수정 리스트)에 남아 있거나, 인페이지 I/O가 진행 중인 상태입니다. 접근하면 PFN만 리스트에서 떼어 다시 Valid로 만드는 소프트 폴트(트랜지션 폴트)로 끝납니다. 메모리가 넉넉할 때 "페이지 아웃"이 싸게 느껴지는 이유입니다.

모양: P=0, Prototype=1, 나머지는 프로토타입 PTE의 주소(또는 "VAD를 참조하라"는 특수 값).

의미: 섹션(공유 메모리, 매핑 파일, 이미지)의 페이지입니다. 공유 페이지의 진짜 상태는 프로세스 PTE가 아니라 섹션이 가진 프로토타입 PTE에 있습니다. 폴트 처리기는 프로토타입 PTE를 따라가 그 상태(유효/트랜지션/파일)에 맞게 처리합니다. → 09장 "프로토타입 PTE"

모양: 64비트 전체가 0 (또는 상위 테이블 자체가 없음).

의미: "아직 아무것도 정해지지 않음". Windows는 커밋 시 PTE를 미리 다 만들지 않고 VAD에만 기록해 두는 경우가 많습니다. 0 PTE에서 폴트가 나면 메모리 관리자는 VAD 트리를 검색해 주소가 커밋된 범위인지 확인하고, 그렇다면 VAD의 보호 속성으로 디맨드 제로(또는 프로토타입) PTE를 그 자리에서 만듭니다. VAD가 없으면 STATUS_ACCESS_VIOLATION입니다.

!pte는 소프트웨어 PTE도 해석해 준다

!pte는 P=0인 PTE를 만나면 "not valid" 다음에 DemandZero, PageFile: … Offset: …, Transition: …, Proto: … 같은 해석을 덧붙입니다. 덤프 분석에서 "이 주소가 왜 접근 불가였나"를 판단하는 가장 빠른 방법입니다.

확인 문제

VA 0xFFFFA000`00401000의 PD 인덱스와 PT 인덱스는?

  1. PD = 0x004, PT = 0x010
  2. PD = 0x002, PT = 0x001
  3. PD = 0x001, PT = 0x001
  4. PD = 0x002, PT = 0x000
하위 32비트 0x00401000에서: PT = (VA >> 12) & 0x1FF = 0x401 & 0x1FF = 0x001. PD = (VA >> 21) & 0x1FF = 0x00401000 >> 21 = 0x2. (0x400000 = 4MB = 2MB × 2.) 첫 번째 보기는 시프트 대신 16진수 자리를 그대로 자른 흔한 실수입니다.

커널 코드가 0x0000F000`00001000을 역참조했습니다. CPU가 일으키는 예외는?

  1. #PF — 해당 PML4 엔트리가 비어 있으므로
  2. #GP — 비정규 주소이므로 페이지 워크 전에 거부
  3. 예외 없음 — 커널 모드는 모든 주소에 접근 가능
  4. #PF — U/S 위반
하위 48비트 0xF000`00001000의 최상위 16진 자리 F는 비트 47–44 = 1111이므로 비트 47 = 1입니다. 그런데 상위 16비트(63–48)는 0x0000이라 비트 47의 복사본이 아닙니다 → 비정규. 비정규 주소는 페이지 워크 없이 #GP이며 CR2가 설정되지 않습니다. 커널 모드라도 정규성 규칙에는 예외가 없습니다.

워킹셋에서 막 제거된, 수정되지 않은(D=0) 페이지의 PTE 상태로 가장 알맞은 것은?

  1. P=1, A=0
  2. P=0, 페이지 파일 오프셋을 가진 PTE
  3. P=0, Transition=1, 원래 PFN을 유지한 PTE (페이지는 스탠바이 리스트)
  4. 모든 비트가 0인 PTE
워킹셋에서 빠진 페이지는 즉시 버려지지 않고 스탠바이(깨끗) 또는 수정(더티) 리스트에 남으며, PTE는 트랜지션 형식으로 PFN을 기억합니다. 다시 접근하면 소프트 폴트로 복구됩니다. 그 물리 페이지가 다른 용도로 재사용될 때 비로소 PTE가 페이지 파일(또는 프로토타입) 형식으로 바뀝니다.

CPU 0에서 PTE를 무효화하고 INVLPG만 실행한 뒤 곧바로 그 물리 페이지를 다른 프로세스에 주었습니다. 무엇이 문제인가요?

  1. 문제없다 — INVLPG는 모든 CPU의 TLB를 지운다
  2. CR3를 다시 쓰지 않아서 CPU 0의 TLB가 남아 있다
  3. 다른 CPU의 TLB에 옛 변환이 남아 있을 수 있어, 그 CPU의 스레드가 새 소유자의 데이터를 읽고 쓸 수 있다
  4. PCID가 없으면 INVLPG가 동작하지 않는다
INVLPG는 로컬 CPU에만 작용합니다. 해당 주소 공간이 실행된(또는 전역 매핑이면 모든) CPU에 IPI로 shootdown하고 완료를 확인한 다음에야 물리 페이지를 재사용할 수 있습니다.

셀프맵 인덱스가 S일 때, 주소 PTE_BASE + ((VA >> 9) & 0x7FFFFFFFF8)에 대해 다시 같은 공식을 적용하면 얻는 것은?

  1. 같은 PTE 주소 (멱등)
  2. 원래 VA의 PDE 주소
  3. 원래 VA의 물리 주소
  4. PML4의 물리 주소
PTE 영역 주소의 PTE는 "그 PTE를 담은 PT 페이지"를 매핑하는 엔트리, 즉 상위 단계인 PDE입니다. S가 앞에 하나 더 붙어 워크가 한 번 더 헛돌기 때문입니다. 네 번 적용하면 PXE, 다섯 번째에는 셀프맵 엔트리 자신으로 수렴합니다.

2MB 대형 페이지에 대한 설명으로 틀린 것은?

  1. PDE의 비트 7(PS)이 1이다
  2. VA의 하위 21비트가 페이지 내 오프셋이다
  3. 유저 모드에서는 특권 없이 요청할 수 있고, 필요하면 4KB 단위로 페이징된다
  4. TLB 엔트리 하나가 2MB를 덮어 TLB 미스를 줄인다
유저 모드 대형 페이지는 SeLockMemoryPrivilege가 필요하며 페이징되지 않습니다(물리적으로 연속·정렬된 2MB를 고정 점유). 나머지는 모두 맞는 설명입니다.

핵심 요약

  • x64 4단계 페이징은 48비트 VA = 9+9+9+9 인덱스 + 12 오프셋. 상위 16비트는 비트 47의 부호 확장이어야 하며(정규 주소), 아니면 #GP.
  • Windows는 아래 128TB를 프로세스별 유저 공간, 위 128TB를 공유 커널 공간으로 쓴다. 커널 영역 배치는 Windows 10 1607+에서 동적·무작위.
  • CR3(비트 51–12) → PML4 → PDPT → PD → PT → 페이지. 모든 테이블 포인터는 물리 주소이고, 권한은 모든 단계를 합성해 판단한다.
  • PTE 핵심 비트: P, R/W, U/S, PWT/PCD(PAT), A, D, PS, G, NX, PFN. 하드웨어가 무시하는 비트는 Windows가 소프트웨어 정보로 쓴다.
  • TLB는 PTE 변경을 따라가지 않는다 → INVLPG/INVPCID + 멀티프로세서 shootdown(IPI)이 필수. PCID는 주소 공간 전환 비용을 줄인다.
  • 셀프맵: PML4[S] = PML4. PTE(VA) = PTE_BASE + ((VA >> 9) & 0x7FFFFFFFF8). S는 무작위화되어 nt!MmPteBase로 확인한다.
  • P=0 PTE는 디맨드 제로 / 페이지 파일 / 트랜지션 / 프로토타입 / 0(VAD 참조) 중 하나로 해석되며, 이것이 09장 폴트 처리의 분기 기준이다.
