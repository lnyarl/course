Part IV · Chapter 12

파일 시스템 · 캐시 · 미니필터

I/O 스택의 가장 바쁜 구역. NTFS가 디스크를 어떻게 조직하고, 캐시 매니저와 메모리 관리자가 어떻게 손잡고 파일 데이터를 캐싱하며, 백신·EDR이 어떤 고도(altitude)에서 그 흐름을 가로채는지 해부합니다.

심화⏱ 약 100분선수: 09 메모리 관리자, 11 I/O 시스템

학습 목표

  • 볼륨 마운트 과정과 VPB가 스토리지 스택과 파일 시스템 스택을 잇는 방식을 설명할 수 있다.
  • NTFS의 MFT 파일 레코드, 속성, 상주/비상주, 런 리스트, ADS, $LogFile의 역할을 구분하고 런 리스트를 손으로 해독할 수 있다.
  • FILE_OBJECT.FsContext/FsContext2와 FCB/SCB/CCB, SECTION_OBJECT_POINTERS의 관계를 그릴 수 있다.
  • 캐시된 읽기/쓰기 경로에서 캐시 I/O와 페이징 I/O가 각각 언제 발생하는지 추적하고, Lazy Writer·Read-Ahead·쓰기 스로틀을 설명할 수 있다.
  • Filter Manager의 프레임·인스턴스·고도를 이해하고, pre/post 콜백 호출 순서와 반환값의 효과를 예측할 수 있다.

파일 시스템 드라이버의 위치와 볼륨 마운트

파일 시스템 드라이버(FSD)는 두 개의 디바이스 스택 사이에 있습니다. 아래에는 스토리지 스택(디스크 → 파티션 → 볼륨 관리자, 그 위의 볼륨 스냅샷·BitLocker 필터 등)이 "블록 장치"를 제공하고, 위에는 FSD가 만든 볼륨 디바이스 객체(VDO)와 그 위에 붙은 파일 시스템 필터들이 "파일" 의미론을 제공합니다. 두 세계를 잇는 끈이 VPB(Volume Parameter Block)입니다.

CDO (Control Device Object)

FSD가 DriverEntry에서 만드는 이름 있는 DO(예: \Ntfs). IoRegisterFileSystem으로 등록되어 마운트 요청을 받는다.

VDO (Volume Device Object)

마운트에 성공할 때마다 볼륨당 하나 생성. 이름이 없다. 파일 열기 IRP는 이 DO(그 위 필터 포함)로 온다.

VPB

디스크류 볼륨 DO에 붙는 구조. RealDevice = 스토리지 볼륨 DO, DeviceObject = 마운트된 FSD의 VDO, Flags에 VPB_MOUNTED.

FILE_OBJECT.DeviceObject의 함정

파일의 FILE_OBJECT에서 DeviceObject는 NTFS VDO가 아니라 스토리지 볼륨 DO입니다. 필터가 "이 파일이 어느 볼륨인가"를 알고 싶을 때 이 필드나 Vpb를 쓰고, IRP를 보낼 대상은 IoGetRelatedDeviceObject로 구합니다. 미니필터는 이런 계산 없이 FltObjects->Volume/Instance를 받습니다.

NTFS 구조

NTFS의 철학은 "모든 것은 파일이고, 파일은 속성의 집합"입니다. 볼륨의 메타데이터(할당 비트맵, 보안 설명자, 대문자 변환표, 로그)까지 모두 파일이며, 그 파일들의 목록이 MFT(Master File Table), 즉 $MFT라는 파일입니다. MFT는 고정 크기 파일 레코드의 배열이고, 파일 하나가 최소 하나의 레코드를 차지합니다.

파일 레코드와 속성

  • 레코드 크기는 보통 1KB입니다(4K 네이티브 섹터 볼륨 등에서는 4KB일 수 있음 — fsutil fsinfo ntfsinfo로 확인). 헤더는 서명 "FILE", 시퀀스 번호, 하드 링크 수, 플래그(사용 중/디렉터리), 첫 속성 오프셋 등을 가집니다.
  • 업데이트 시퀀스(fixup): 레코드가 여러 섹터에 걸치므로, 각 섹터의 마지막 2바이트를 시퀀스 값으로 바꿔 써 두고 원래 값은 헤더 배열에 보관합니다. 읽을 때 값이 다르면 "찢어진 쓰기(torn write)"를 탐지합니다.
  • 파일 참조 = 48비트 레코드 번호 + 16비트 시퀀스 번호. 레코드가 재사용될 때 시퀀스가 증가해, 오래된 참조(예: 디렉터리 엔트리)를 걸러냅니다.
  • 속성: $STANDARD_INFORMATION(0x10, 타임스탬프·속성 비트·Security Id), $FILE_NAME(0x30, 부모 디렉터리 참조 + 이름), $DATA(0x80), 디렉터리의 $INDEX_ROOT(0x90)/$INDEX_ALLOCATION(0xA0)/$BITMAP(0xB0), $REPARSE_POINT(0xC0) 등.
  • 상주(resident): 내용이 레코드 안에 들어 있음. 작은 파일은 데이터 클러스터를 하나도 쓰지 않습니다. 비상주(non-resident): 내용은 클러스터에 있고 레코드에는 런 리스트(VCN → LCN 매핑)만 있습니다.
  • 속성이 레코드에 다 안 들어가면(조각이 매우 많은 파일 등) $ATTRIBUTE_LIST로 확장 레코드를 연결합니다.
  • ADS(대체 데이터 스트림): 이름 있는 $DATA 속성. file.exe:Zone.Identifier가 대표적이며(웹 표시, MOTW), 탐색기는 보여주지 않으므로 악성코드 은닉에도 쓰입니다.

런 리스트 인코딩

각 런은 헤더 바이트로 시작합니다. 하위 니블 = 길이 필드 바이트 수, 상위 니블 = 오프셋 필드 바이트 수. 이어서 길이(부호 없는 리틀 엔디언, 클러스터 수), 오프셋(부호 있는 리틀 엔디언, 이전 런의 LCN 기준 상대값)이 옵니다. 헤더 0x00이 끝입니다. 오프셋 바이트 수가 0이면 디스크 공간이 없는 sparse 런입니다. 

33 00 20 00 00 00 10   헤더 0x33: 길이 3바이트(0x002000 = 8192 클러스터), 오프셋 3바이트(+0x100000)  → LCN 0x100000
22 00 10 00 50         헤더 0x22: 길이 0x1000, 오프셋 +0x5000                                      → LCN 0x105000
22 00 08 00 F0         헤더 0x22: 길이 0x0800, 오프셋 0xF000 = -0x1000 (부호 있음!)                 → LCN 0x104000
00                     끝

메타데이터 저널링: $LogFile과 $UsnJrnl

$LogFile (복구 로그)

NTFS는 메타데이터 변경(MFT 레코드, 인덱스, 비트맵)을 로그 파일 서비스(LFS)를 통해 먼저 로그에 쓰고(WAL) 나중에 실제 위치에 씁니다. 마운트 시 분석 → redo → undo 패스로 일관된 상태를 복구합니다. 사용자 데이터는 저널링하지 않습니다 — 크래시 후 파일 내용이 최신이 아닐 수 있는 이유입니다.

$UsnJrnl (변경 저널)

$Extend\$UsnJrnl:$J. 복구용이 아니라 애플리케이션용 변경 기록(생성/삭제/이름 변경/데이터 변경). 인덱서·백업·EDR이 전체 스캔 없이 변경분만 추적할 때 씁니다. fsutil usn으로 조회.

MFT 레코드 탐색기 — 레코드를 고르고 속성을 클릭하세요
막대 = 레코드 1024바이트 안의 대략적 배치 (회색 헤더 · 초록 상주 속성 · 주황 비상주 속성 헤더+런 리스트)

FCB · SCB · CCB와 FsContext

파일 시스템은 열린 파일마다 메모리 내 구조를 만듭니다. NTFS 기준으로 FCB는 파일(MFT 레코드) 하나, SCB는 그 파일의 스트림(기본 $DATA, 각 ADS, 인덱스) 하나, CCB는 열기(핸들) 하나에 대응합니다. I/O 관리자와 캐시 매니저가 알아야 할 공통 부분은 SCB 앞머리의 FSRTL_ADVANCED_FCB_HEADER로 표준화되어 있습니다.

캐시 매니저

Windows 캐시 매니저(Cc)는 자체 버퍼 풀을 갖지 않습니다. 대신 파일의 데이터 섹션을 시스템 가상 주소 공간에 매핑하고 그 주소로 memcpy할 뿐이며, 실제 디스크 읽기/쓰기와 물리 메모리 관리는 전부 메모리 관리자의 페이지 폴트·플러시 메커니즘이 합니다. 그래서 Windows 캐시는 디스크 블록 단위가 아닌 "파일 + 오프셋" 단위의 가상 블록 캐시이며, 캐시 크기는 물리 메모리 상황에 따라 워킹셋처럼 늘고 줄어듭니다.

VACB

Virtual Address Control Block. 시스템 캐시 VA의 256KB 뷰 하나를 기술: 기준 주소, 매핑된 파일 오프셋, 사용 중 카운트, 소속 SharedCacheMap.

SHARED_CACHE_MAP

스트림당 하나. VACB 인덱스 배열로 "이 오프셋은 어느 VACB에 매핑돼 있나"를 찾는다. 더티 정보, Lazy Writer 연결.

PRIVATE_CACHE_MAP

FILE_OBJECT당 하나. 최근 읽기 위치를 기억해 순차 패턴을 감지하고 Read-Ahead를 예약.

유저의 캐시 읽기 하나가 필터에게는 ① 유저의 IRP_MJ_READ(캐시 I/O)와 ② 캐시 미스로 생긴 페이징 IRP_MJ_READ로 두 번 보입니다. 쓰기는 유저 WRITE가 먼저, 디스크 쓰기는 나중에(Lazy Writer의 페이징 WRITE, 다른 스레드) 보입니다. 암호화 필터는 디스크에 닿는 페이징/비캐시 I/O에서만 암·복호화해야 하고, 감사 필터는 유저 요청(비페이징)만 기록해야 중복이 없습니다. 미니필터는 Data->Iopb->IrpFlags & IRP_PAGING_IO로 구분하거나 등록 시 FLTFL_OPERATION_REGISTRATION_SKIP_PAGING_IO를 씁니다.

유효 데이터 길이(VDL)와 보안

파일을 늘리고 일부만 쓰면 할당된 클러스터에 이전 파일의 잔해가 남아 있을 수 있습니다. NTFS는 ValidDataLength 너머를 읽으면 0을 반환하고, 캐시 쓰기 시 빈 구간을 0으로 채워 이를 막습니다. SetFileValidData는 이 보호를 건너뛰므로 SE_MANAGE_VOLUME_NAME 특권이 필요합니다.

Filter Manager와 미니필터

과거의 레거시 파일 시스템 필터는 VDO에 직접 붙어 모든 IRP와 Fast I/O를 처리해야 했고, 로드 순서와 언로드가 악명 높게 어려웠습니다. Filter Manager(fltmgr.sys)는 그 자신이 하나의 레거시 필터로서 볼륨에 붙고, 그 안에 미니필터들을 고도(altitude) 순으로 호스팅합니다.

프레임 (Frame)

FltMgr가 디바이스 스택에 붙이는 DO 하나 = 프레임 하나. 각 프레임은 고도 구간을 담당합니다. 레거시 필터가 중간에 끼면 그 위아래로 프레임이 나뉩니다(fltmc filters의 Frame 열).

인스턴스 (Instance)

미니필터 × 볼륨 조합마다 하나. InstanceSetup 콜백에서 볼륨 종류(NTFS/ReFS/네트워크/FAT…)를 보고 붙을지 결정합니다. 고도는 인스턴스 속성입니다.

고도 (Altitude)

Microsoft가 할당하는 문자열 형식의 십진수. 클수록 위(I/O 관리자 쪽). 같은 범주의 필터들이 정해진 로드 순서 그룹 범위 안에 배치됩니다.

콜백 데이터

IRP·Fast I/O·FsFilter 콜백을 FLT_CALLBACK_DATA 하나로 추상화. Iopb(메이저/마이너, 파라미터, 대상 파일 객체), IoStatus, RequestorMode, Thread.

호출 순서 규칙

  • pre 콜백은 고도가 높은 것부터 낮은 순(I/O 관리자 → 파일 시스템 방향)으로 호출됩니다.
  • post 콜백은 완료가 올라오는 방향이므로 낮은 것부터 높은 순으로, 그리고 pre에서 FLT_PREOP_SUCCESS_WITH_CALLBACK(또는 SYNCHRONIZE)을 반환한 필터만 호출됩니다.
  • FLT_PREOP_SUCCESS_NO_CALLBACK: 아래로 보내되 내 post는 생략.
  • FLT_PREOP_COMPLETE: 내가 여기서 완료한다. 아래 필터와 파일 시스템은 요청을 보지 못하고, 나 자신의 post도 호출되지 않으며, 나보다 위에서 post를 요청한 필터들의 post만 호출됩니다.
  • FLT_PREOP_PENDING: 나중에 FltCompletePendedPreOperation으로 재개. FLT_PREOP_SYNCHRONIZE: post를 pre와 같은 스레드·PASSIVE_LEVEL에서 받도록 FltMgr가 대기.
  • post 콜백은 DISPATCH_LEVEL·임의 문맥에서 호출될 수 있습니다(CREATE는 FltMgr가 동기화해 PASSIVE 보장). 무거운 일은 FltDoCompletionProcessingWhenSafe나 작업 큐로 미룹니다.
미니필터 고도 시뮬레이터 — 필터를 배치하고 요청을 보내 보세요

각 필터의 드롭다운으로 pre 콜백 반환값을 바꿀 수 있습니다.

요청을 보내면 콜백 호출 순서가 표시됩니다.

미니필터 골격

CONST FLT_OPERATION_REGISTRATION Callbacks[] = {
    { IRP_MJ_CREATE, 0, PreCreate, PostCreate },
    { IRP_MJ_WRITE,  FLTFL_OPERATION_REGISTRATION_SKIP_PAGING_IO, PreWrite, NULL },
    { IRP_MJ_OPERATION_END }
};
CONST FLT_CONTEXT_REGISTRATION Contexts[] = {
    { FLT_STREAM_CONTEXT, 0, StreamCtxCleanup, sizeof(STREAM_CTX), 'xtCS' },
    { FLT_CONTEXT_END }
};
CONST FLT_REGISTRATION Registration = {
    sizeof(FLT_REGISTRATION), FLT_REGISTRATION_VERSION, 0,
    Contexts, Callbacks, FilterUnload,
    InstanceSetup, NULL, NULL, NULL,          // QueryTeardown, TeardownStart, TeardownComplete
};
PFLT_FILTER gFilter;

NTSTATUS DriverEntry(PDRIVER_OBJECT DriverObject, PUNICODE_STRING RegistryPath)
{
    UNREFERENCED_PARAMETER(RegistryPath);
    NTSTATUS st = FltRegisterFilter(DriverObject, &Registration, &gFilter);
    if (NT_SUCCESS(st)) {
        st = FltStartFiltering(gFilter);
        if (!NT_SUCCESS(st)) FltUnregisterFilter(gFilter);
    }
    return st;   // 고도·인스턴스 정의는 INF가 레지스트리(Instances 키)에 기록
}

FLT_PREOP_CALLBACK_STATUS PreCreate(PFLT_CALLBACK_DATA Data, PCFLT_RELATED_OBJECTS FltObjects, PVOID *CompletionContext)
{
    UNREFERENCED_PARAMETER(FltObjects);
    *CompletionContext = NULL;
    PFLT_FILE_NAME_INFORMATION ni;
    if (NT_SUCCESS(FltGetFileNameInformation(Data, FLT_FILE_NAME_NORMALIZED | FLT_FILE_NAME_QUERY_DEFAULT, &ni))) {
        BOOLEAN deny = IsBlockedPath(&ni->Name);
        FltReleaseFileNameInformation(ni);
        if (deny) {
            Data->IoStatus.Status = STATUS_ACCESS_DENIED;
            Data->IoStatus.Information = 0;
            return FLT_PREOP_COMPLETE;            // 아래 필터·NTFS는 이 요청을 보지 못한다
        }
    }
    return FLT_PREOP_SUCCESS_WITH_CALLBACK;       // PostCreate 호출 요청
}

FLT_POSTOP_CALLBACK_STATUS PostCreate(PFLT_CALLBACK_DATA Data, PCFLT_RELATED_OBJECTS FltObjects,
                                      PVOID CompletionContext, FLT_POST_OPERATION_FLAGS Flags)
{
    UNREFERENCED_PARAMETER(CompletionContext);
    if (Flags & FLTFL_POST_OPERATION_DRAINING) return FLT_POSTOP_FINISHED_PROCESSING;   // 인스턴스 분리 중
    if (!NT_SUCCESS(Data->IoStatus.Status) || Data->IoStatus.Status == STATUS_REPARSE)
        return FLT_POSTOP_FINISHED_PROCESSING;
    PSTREAM_CTX ctx;
    if (NT_SUCCESS(FltAllocateContext(FltObjects->Filter, FLT_STREAM_CONTEXT, sizeof(STREAM_CTX), NonPagedPoolNx, (PFLT_CONTEXT*)&ctx))) {
        RtlZeroMemory(ctx, sizeof(*ctx));
        FltSetStreamContext(FltObjects->Instance, FltObjects->FileObject, FLT_SET_CONTEXT_KEEP_IF_EXISTS, ctx, NULL);
        FltReleaseContext(ctx);                   // 참조 카운트: Set이 자기 참조를 따로 잡는다
    }
    return FLT_POSTOP_FINISHED_PROCESSING;
}

확인 문제

같은 파일을 두 프로세스가 각각 열었습니다. 두 FILE_OBJECT에 대해 옳은 것은?

  1. FsContext와 FsContext2 모두 같다
  2. FsContext(SCB)는 같고 FsContext2(CCB)는 다르다
  3. FsContext는 다르고 FsContext2는 같다
  4. 둘 다 다르며, 캐시도 각자 따로 가진다
FsContext는 스트림을 대표하므로 같은 스트림을 연 모든 FILE_OBJECT가 공유합니다(그래서 캐시·섹션도 공유). FsContext2는 열기별 상태(CCB)입니다. 단, ADS를 열면 같은 파일이라도 FsContext가 다릅니다.

유저가 캐시된 파일을 처음 읽을 때, 이 파일에 대한 IRP_MJ_READ를 미니필터는 몇 번, 어떤 형태로 보게 되나요?

  1. 한 번 — 유저 요청만
  2. 두 번 — 유저의 캐시 READ와, 캐시 미스로 메모리 관리자가 보낸 페이징 READ
  3. 한 번 — 페이징 READ만
  4. 보지 못한다 — 캐시 I/O는 필터를 우회한다
FastIoRead가 실패해 IRP 경로를 타면 유저 READ가 보이고(Fast I/O로 처리돼도 FltMgr가 콜백 데이터로 보여 줌), CcCopyRead 중 페이지 폴트가 나면 Mm이 IRP_PAGING_IO READ를 보냅니다. 두 번째 읽기부터는 캐시 히트라 페이징 READ가 없습니다.

고도 385000(A), 328010(B), 141000(C)인 미니필터가 있습니다. B가 IRP_MJ_CREATE pre에서 FLT_PREOP_COMPLETE(ACCESS_DENIED)를 반환했습니다. A·C가 모두 SUCCESS_WITH_CALLBACK을 반환한다고 할 때 호출 순서는?

  1. A pre → B pre → C pre → NTFS → C post → B post → A post
  2. C pre → B pre → A post
  3. A pre → B pre → A post (C와 NTFS는 요청을 보지 못함)
  4. A pre → B pre → B post → A post
pre는 높은 고도부터: A → B. B가 COMPLETE를 반환하면 그 아래(C, NTFS)로 내려가지 않고, B 자신의 post도 호출되지 않습니다. 위에서 post를 요청한 A의 post만 호출됩니다.

NTFS의 $LogFile에 대한 설명으로 옳은 것은?

  1. 모든 파일 데이터 변경을 기록해 크래시 후 데이터 손실을 막는다
  2. 애플리케이션이 변경 이력을 조회하기 위한 USN 저널이다
  3. 메타데이터 변경의 redo/undo 로그로, 마운트 시 볼륨 구조의 일관성을 복구한다
  4. MFT의 백업 사본이다
$LogFile은 메타데이터만 저널링합니다(WAL). 사용자 데이터는 저널링되지 않으므로 크래시 후 파일 내용은 최신이 아닐 수 있지만 볼륨 구조는 일관됩니다. 변경 이력 조회용은 $UsnJrnl, MFT 사본은 $MFTMirr입니다.

런 리스트 바이트 21 10 00 01 01 20 21 10 00 01 00을 해독한 결과로 옳은 것은? (클러스터 단위)

  1. VCN 0–15 → LCN 0x100, VCN 16–47 → LCN 0x120, VCN 48–63 → LCN 0x200
  2. VCN 0–15 → LCN 0x100, VCN 16–47 → sparse, VCN 48–63 → LCN 0x200
  3. VCN 0–15 → LCN 0x100, VCN 16–47 → sparse, VCN 48–63 → LCN 0x100
  4. 잘못된 런 리스트다
0x21: 길이 1바이트(0x10), 오프셋 2바이트(0x0100) → LCN 0x100. 0x01: 길이 1바이트(0x20=32), 오프셋 0바이트 → sparse. 0x21: 길이 0x10, 오프셋 +0x100 — sparse 런은 기준 LCN을 바꾸지 않으므로 0x100 + 0x100 = 0x200. 아래 탐색기의 직접 해독 칸에 넣어 확인해 보세요.

Lazy Writer가 보낸 페이징 쓰기를 미니필터가 받았을 때, FltGetRequestorProcess로 얻는 프로세스는 대개 무엇인가요?

  1. 원래 WriteFile을 호출한 애플리케이션
  2. System 프로세스 (캐시 매니저의 워커 스레드)
  3. lsass.exe
  4. 요청마다 무작위
Lazy Writer의 플러시는 시스템 워커 스레드에서 실행되므로 요청자는 System입니다. "어떤 프로세스가 이 파일을 수정했는가"를 판단하려면 유저 WRITE(비페이징) 시점에 스트림/스트림핸들 컨텍스트에 기록해 두어야 합니다 — 랜섬웨어 탐지 필터의 기본 설계입니다.

핵심 요약

  • FSD는 스토리지 스택 위에서 볼륨마다 VDO를 만들고, VPB가 두 스택을 잇는다. FILE_OBJECT.DeviceObject는 스토리지 볼륨 DO다.
  • NTFS는 MFT 파일 레코드(보통 1KB)와 속성으로 모든 것을 표현한다. 작은 데이터는 상주, 큰 데이터는 런 리스트(상대 LCN, sparse 가능)로 비상주. ADS는 이름 있는 $DATA다. $LogFile은 메타데이터만 저널링한다.
  • FsContext = 스트림(SCB, 공유), FsContext2 = 열기(CCB, 개별). SECTION_OBJECT_POINTERS로 캐시 맵과 데이터 섹션이 공유된다.
  • 캐시 매니저는 파일 섹션을 256KB VACB 뷰로 매핑하고 복사만 한다. 미스는 페이지 폴트 → 페이징 I/O로, 더티 페이지는 Lazy Writer → 페이징 쓰기로 디스크에 간다. 필터는 같은 데이터를 두 번 본다.
  • 미니필터는 고도 순으로 pre(높은→낮은), post(낮은→높은)가 호출되며, COMPLETE는 아래를 차단하고 자기 post를 생략한다. 컨텍스트·이름 조회·통신 포트를 FltMgr가 제공한다.
