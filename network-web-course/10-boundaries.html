NAT와 방화벽: 주소 변환과 허용 정책의 경계

사설망 서버가 외부 API를 호출하는 과정을 주소·포트·상태 테이블로 추적합니다. NAT, 라우팅, 방화벽, 애플리케이션 인증을 서로 다른 검사로 구분합니다.

출발지 NAT를 켰는데 왜 외부 API 연결은 계속 타임아웃될까?

내부 클라이언트 10.0.0.2:51000이 외부 HTTPS 서비스로 연결한다. 경계 장비는 이를 교육용 공개 주소 198.51.100.5:62001로 변환할 수 있지만 방화벽 정책은 별도로 DROP 또는 ALLOW를 선택한다.

01. 도달·허용·변환·보호를 서로 다른 질문으로 나누기

내부 서버가 외부 API를 호출할 때 “인터넷이 된다”는 말에는 여러 성공이 섞여 있습니다. 목적지까지 갈 경로가 있어야 하고, 경계 정책이 통신을 허용해야 하며, 필요한 주소 변환과 반환 상태가 유지되어야 합니다. HTTPS라면 상대 인증과 전송 보호도 성립해야 합니다.

사례에서는 NAT가 10.0.0.2:51000 → 198.51.100.5:62001 매핑을 만들더라도 별도 정책이 DROP이면 응답을 받지 못할 수 있습니다. 따라서 “NAT가 켜짐”보다 매핑·정책·경로의 실제 관찰을 요청별로 이어야 합니다.

이 표는 기능의 책임을 분리한 것입니다. 실제 장비의 처리 순서는 구현과 설정에 따라 확인해야 하며, 나열 순서를 모든 제품의 패킷 처리 순서로 해석하면 안 됩니다.

02. SNAT: 외부에서는 어떤 출발지로 보일까

내부 서버 A가 10.0.1.10:51000에서 외부 203.0.113.20:443으로 연결한다고 가정합니다. 출구에서 출발지 주소와 포트를 198.51.100.8:62001로 바꾸면 외부 서버는 바뀐 출발지를 봅니다. 응답이 돌아올 때 NAT는 저장된 대응 관계를 찾아 원래 내부 서버로 되돌립니다. 여러 내부 서버가 같은 외부 주소를 사용할 때 포트 등으로 흐름을 구분합니다. 숫자는 이해를 위한 예시이며 모든 NAT가 항상 같은 포트 선택 규칙을 쓰는 것은 아닙니다.

이것이 외부 API의 IP 허용 목록에 앱의 사설 IP 대신 실제 출구 IP를 등록하는 이유입니다. 서버를 증설했거나 다른 가용 영역으로 경로를 바꾸면 출구 주소가 달라질 수 있습니다. 외부 서비스가 본 주소, NAT의 주소, 앱이 로컬에서 보는 주소를 구분해 기록해야 합니다. IPv6에서는 같은 방식의 주소 공유가 필요하지 않은 구조도 있으므로 “외부 호출은 언제나 NAT를 탄다”고 일반화하지 않습니다. 기본 NAT 개념은 RFC 3022를 참고합니다.

03. DNAT와 포트 전달: 공개 주소를 내부 대상으로 바꾼다

반대 방향으로 외부 사용자가 공개 주소의 8443 포트에 연결했을 때 내부 서버의 443으로 전달하도록 목적지를 바꿀 수 있습니다. 이를 목적지 변환 관점에서 DNAT라고 설명할 수 있습니다. 하지만 NAT 규칙을 만들었다고 방화벽이 허용하거나 앱이 그 포트에서 듣기 시작하는 것은 아닙니다. 라우팅, 허용 규칙, 대상 리스너, 응답 경로까지 각각 맞아야 합니다. 같은 장비가 이 기능을 함께 제공해도 개념적으로는 분리해서 확인합니다.

일부 관리형 NAT 게이트웨이는 내부에서 시작하는 외부 연결을 위한 서비스이며 일반적인 외부 시작 연결을 받는 용도로 쓰지 못합니다. 제품의 제한을 보편적인 모든 NAT 정의로 바꾸지 마세요. 예를 들어 AWS NAT gateway는 해당 VPC 내부에서 연결을 시작하는 사용 모델을 명시합니다. 공개 서비스를 노출하려면 해당 서비스 구조에 맞는 로드밸런서, 공개 경로, 보안 정책 등을 선택해야 합니다. AWS NAT gateway

04. Stateful 방화벽은 연결 상태를 함께 기억한다

서버의 외부 443 연결을 허용할 때 응답은 외부 서버의 443에서 내부 클라이언트의 임시 포트로 돌아옵니다. 매번 임시 포트를 사람이 미리 나열하기 어렵기 때문에, 상태를 추적하는 방화벽은 허용된 연결에 대응하는 반환 트래픽을 인식할 수 있습니다. 이 설명은 “모든 반환 패킷은 무조건 통과”가 아니라 제품이 정의한 연결 추적과 정책에 따른다는 뜻입니다. 연결 상태와 타이머가 사라지면 오래된 통신이 다시 정상 연결로 인식되지 않을 수 있습니다.

Stateless 정책은 각 방향의 패킷을 독립적으로 검사하므로 반환 경로의 주소·포트 허용도 고려해야 합니다. AWS의 security group과 network ACL은 이런 차이를 배우기 위한 한 제품 사례입니다. 다만 모든 방화벽의 평가 순서, 기본 정책, 연결 추적 예외가 같지는 않습니다. 규칙 이름보다 어떤 인터페이스에서 어느 방향으로 어떤 조건을 검사하는지 보세요. AWS security group, AWS network ACL

연결 상태를 함께 보는 정책과 방향별 정책
정책 모델새로 나가는 연결돌아오는 패킷조사 시 질문

상태 추적을 한다는 이유로 어떤 수신 패킷이든 허용되는 것은 아닙니다. 어떤 연결 상태와 어떤 규칙에 대응하는지 확인해야 합니다. AWS security group과 network ACL의 차이는 해당 제품 문서의 예이며 모든 방화벽에 같은 설정 용어를 적용하지 않습니다.

05. NAT와 방화벽은 같은 보안 기능이 아니다

NAT는 주소와 포트를 변환하는 기능입니다. 방화벽은 정책에 따라 통신을 허용하거나 거부하는 기능입니다. 주소 변환 때문에 외부에서 내부로 임의 연결을 만들기 어려운 배치가 흔하지만, 그것만으로 필요한 보안 정책 전체가 구현되었다고 볼 수 없습니다. 포트 전달 규칙, 기존 상태, 필터링 방식에 따라 접근 가능성이 달라집니다. IPv6에서 NAT가 없다고 자동으로 모든 접근을 허용해야 하는 것도 아닙니다. 변환 없이도 방화벽 정책을 적용할 수 있습니다.

서비스 설계에서는 “NAT 뒤라서 안전” 대신 필요한 출발지, 목적지, 프로토콜, 포트, 방향을 정리합니다. 외부에서 시작하는 요청을 막는 것과 내부 서버가 임의 외부 서버로 데이터를 보내는 것을 막는 것도 다릅니다. 출구 제어는 내부 침해 이후의 데이터 전송이나 의도하지 않은 외부 의존성을 제한하는 목적이 있습니다. HTTP 인증과 네트워크 IP 허용 목록은 서로 보완할 수 있지만 한쪽이 다른 쪽의 정확성을 자동으로 보증하지 않습니다. DNS 이름만 허용하는 정책도 실제 제품이 이름 변경과 주소를 어떻게 다루는지 확인해야 합니다.

06. 연결 수와 유휴 시간이 상태 테이블을 압박한다

NAT와 연결 추적 장치는 무한한 기억 공간을 갖지 않습니다. 매우 많은 연결을 빠르게 만들면 포트나 상태 자원이 부족할 수 있고, 매번 새 연결을 만드는 클라이언트는 그 압력을 키울 수 있습니다. 다만 연결이 실패했다는 사실만으로 포트 고갈을 확정하면 안 됩니다. 장비의 포트 할당 실패, 활성 연결, 드롭 지표와 대상별 분포를 확인해야 합니다. 같은 증상이 상대 서버 제한이나 로컬 자원 부족에서도 나타납니다.

유휴 연결의 상태가 중간 장비에서 먼저 만료되었는데 앱 연결 풀은 여전히 살아 있다고 생각하면 다음 사용 시 reset이나 지연이 나타날 수 있습니다. 연결 풀 idle 시간, 장비 timeout, keepalive 설정의 관계를 살펴야 합니다. 모든 문제에 keepalive 간격을 짧게 하는 처방은 비용과 다른 제한을 숨길 수 있습니다. AWS 문서는 NAT gateway의 특정 유휴 시간과 연결 제한 관련 진단을 제품별로 설명합니다. 수치는 제품·설정에 종속되므로 이 교재의 공통 기본값으로 외우지 않습니다. NAT gateway 문제 해결

07. 허용·거부·침묵은 관찰 결과가 다르다

방화벽이나 대상 장치가 명시적으로 거부하거나 연결을 재설정하면 클라이언트는 비교적 빠르게 실패를 알 수 있습니다. 아무 응답 없이 버리면 클라이언트는 설정된 시간까지 기다릴 수 있습니다. 그래서 즉시 connection refused와 긴 connect timeout은 다음 조사 지점을 다르게 고르는 힌트입니다. 하지만 특정 방화벽 동작을 직접 확인하지 않고 “timeout이면 반드시 방화벽”이라고 결론 낼 수는 없습니다. 경로 장애, 잘못된 주소, 응답 손실도 가능합니다.

ICMP ping과 TCP 443은 서로 다른 통신입니다. ping이 실패해도 HTTPS가 성공할 수 있고, ping이 성공해도 앱 포트가 닫혀 있을 수 있습니다. 라우팅 추적의 중간 홉이 응답하지 않는 것도 사용자 요청 실패의 충분한 증거가 아닙니다. 도구가 발생시키는 프로토콜과 실제 요청의 경로를 맞추세요. 예를 들어 브라우저는 프록시를 사용하지만 터미널 curl은 직접 연결한다면 서로 다른 출구 정책을 시험하는 것일 수 있습니다. 성공·실패를 비교하기 전에 같은 경로를 사용했는지부터 확인해야 합니다.

경계 정책과 클라이언트 관찰을 연결하되 단정하지 않는다
정책·현상대표 관찰다음 확인단정하면 안 되는 것
ALLOW이 정책에서는 통신을 통과시킴라우팅·반환·리스너·TLS 검증요청 전체가 성공했다
DROP명시적 응답 없이 패킷을 폐기할 수 있음정책 매칭 로그와 양쪽 패킷 관찰모든 timeout은 방화벽 때문이다
REJECT오류 통지로 비교적 빨리 실패할 수 있음거부 주체와 응답 방식언제나 같은 클라이언트 오류 문자열이 나온다
상태 만료·반환 경로 문제기존 연결의 지연·끊김 등 가능NAT·연결 추적 상태와 양방향 경로새 연결이 되므로 기존 연결도 정상이다

클라이언트의 timeout은 “제한 시간 안에 기대한 응답을 얻지 못했다”는 관찰입니다. 방화벽은 그 원인 후보 중 하나이므로 경계 로그와 연결해 가설을 확인합니다.

08. 경계 표를 작성하면 조사 범위가 작아진다

아래 형식으로 홉마다 한 행을 적어 보세요. 출발 프로세스, 논리적 목적지 이름, 해석된 주소, 실제 연결 상대, 출구 주소, 허용 정책 소유자, 암호화 종료자, 관측 로그입니다. 모든 칸을 추측해서 채우기보다 확인한 값과 미확인 값을 구분하세요. “개발 환경 성공, 운영 실패” 사례에서는 두 환경의 차이가 어느 칸에 나타나는지 비교하면 막연한 네트워크 탓을 줄일 수 있습니다.

사고 예시로 외부 API가 403을 응답했고 외부 접근 로그에 새 출구 IP가 찍혔다고 합시다. 이때 DNS·연결·TLS가 전부 실패했다는 가설은 해당 교환과 맞지 않습니다. 상대가 HTTP 응답을 만들었으므로 그 앞 단계는 응답을 받을 만큼 진행됐습니다. 출구 IP 정책 차이는 유력한 후보지만, 실제 거절 이유가 IP인지 인증 토큰인지 상대 로그와 설정을 더 확인해야 합니다. 최종 보고에는 직접 관찰, 배제한 가설, 남은 확인을 나누어 적습니다. 주소 표 하나를 정확히 완성하는 연습이 복잡한 네트워크 그림을 외우는 것보다 운영 진단에 유용합니다.

09. 반환 경로를 표로 검산한다

두 내부 서버 A와 B가 동시에 같은 외부 서버에 연결한다고 가정합니다. A의 내부 포트가 51000이고 B도 51000일 수 있습니다. 외부 주소를 공유하는 출구에서는 A 흐름을 62001, B 흐름을 62002처럼 구분할 수 있습니다. 외부 응답의 목적지가 62001이면 A로, 62002이면 B로 돌려보냅니다. 이때 내부 포트가 같다는 사실만으로 충돌이라고 결론 내리면 안 됩니다. 흐름 식별에는 주소와 프로토콜 등 여러 값이 관여합니다.

그다음 B의 상태만 만료되었다고 가정하세요. A의 응답은 정상인데 B의 응답은 대응 관계를 찾지 못할 수 있습니다. 이 현상을 DNS 변경이나 API 권한 오류와 혼동하지 않으려면 반환 패킷과 상태 테이블을 같은 시점에 관찰해야 합니다. 실제 장비가 모든 상태를 사용자에게 보여 주지는 않으므로 관련 지표나 흐름 로그를 사용할 수 있습니다. 표의 주소 변환 과정을 이해했다고 실제 장비의 모든 포트 할당·필터링 정책을 안다고 주장하지 않습니다. 동일한 교육용 표로 가능한 동작이더라도 제품 구현의 세부 규칙은 다를 수 있습니다.

NAT는 주소·포트 매핑이고 방화벽은 정책 판단이다. 허용되어도 라우팅·대상 서비스·반환 경로·TLS 검증이 남는다. 같은 장비가 기능 여러 개를 제공하더라도 성공 증거는 분리해야 한다.

HANDS ON

실습 · 실제 설정 변경 없이 경계 추적하기

이 실습은 방화벽·라우터·클라우드 구성을 변경하지 않습니다. 승인되지 않은 외부 대상을 스캔하지 않고 내 컴퓨터와 example.com에 대한 단일 요청만 관찰합니다.

  1. 로컬 실습 서버가 실행 중일 때 curl -v http://127.0.0.1:8765/inspect를 보냅니다. 루프백 연결에서는 공용 NAT를 사용하지 않는다고 설명합니다.
  2. curl -v --connect-timeout 3 --max-time 8 https://example.com/ -o /dev/null을 실행합니다. 프록시 환경 설정이 있으면 출력에 어떻게 드러나는지 봅니다. 민감한 프록시 자격 증명은 공유하지 않습니다.
  3. 연결 대상 IP, 포트, TLS, HTTP 응답을 단계별로 표시합니다. curl이 보여 주는 로컬 주소만으로 외부 NAT 이후의 출구 IP를 확정하지 않습니다.
  4. 시뮬레이터에서 NAT 매핑을 켜고 끕니다. 한 흐름의 내부 출발지와 외부에서 보이는 출발지가 어떻게 달라지는지 읽습니다. 여러 서버의 반환 매핑은 본문의 표를 종이에 그려 확인하며, 화면에서 두 서버를 직접 조작하는 기능은 제공하지 않습니다.
  5. 방화벽을 allow, drop, reject로 바꾸어 같은 NAT 설정에서도 통과·무응답·명시적 거절이 달라지는지 확인합니다. 경로 유무는 이 시뮬레이터의 조작 항목이 아니며 본문의 개념으로 구분합니다.
  6. 실제 사용 중인 환경이 있다면 읽기 권한 안에서 경계 표를 작성합니다. 설정과 로그가 없는 항목은 미확인이라고 적습니다. 이를 채우기 위해 운영 규칙을 임의로 변경하지 않습니다.
