풀링·Span·Memory와 버퍼 소유권

선수 장 · LOH와 POH

큰 버퍼를 풀에 돌려도 프로세스 메모리가 바로 줄지 않을 수 있습니다. LOH 할당 감소와 보유 메모리, 그리고 사용 가능한 버퍼의 수명을 나눕니다.

빌린 배열과 유효 데이터의 범위

ArrayPool<byte>.Shared.Rent(length)가 준 배열은 요청보다 길 수 있습니다. 실제 데이터 길이를 따로 보관하고 소비자에게 buffer.AsMemory(0, used)만 넘깁니다. 배열 전체를 응답에 쓰면 이번 작업이 채우지 않은 범위까지 보낼 수 있습니다.

finally의 Return은 해당 버퍼를 더는 쓰지 않는 시점과 일치해야 합니다. 비동기 전송을 시작만 하고 반환하면 전송 중 다른 작업이 같은 배열을 수정할 수 있습니다. 필요한 I/O와 소비자 완료를 await한 뒤 반납하고, 민감한 데이터라면 지울 범위와 정책을 정합니다.

뷰는 소유권을 연장하지 않는다

Span은 연속 메모리의 뷰이며 저장소를 새로 소유하지 않습니다. Memory를 사용해 async 경계에 값을 보관해도 풀 버퍼의 임대 기간이 자동으로 길어지지 않습니다. 소유자가 언제 반납 가능한지, 하위 호출이 완료 후 참조를 보유하는지 계약이 필요합니다.

코드 흐름을 Rent → 유효 범위 채움 → await 소비 → finally Return으로 그립니다. pool 도입 전후에는 연산당 신규 할당, GC 횟수, 동시 사용 버퍼, 풀에 보유한 메모리를 구분합니다. 적은 allocation과 작은 RSS는 같은 지표가 아닙니다.

실습과 예상 관찰

자신의 로컬 변환 함수에서 고정 길이 배열 생성과 ArrayPool 대여를 비교하세요. 정상·예외·취소 경로에 대여/반납 수를 세고 모든 소비 완료 뒤 수가 맞는지 검사합니다. 일부러 배열보다 작은 used 범위를 사용해 소비 결과에 그 범위만 포함되는지도 확인하세요.

사용 완료 뒤 한 번 반납

버퍼 임대가 닫히고 재사용할 수 있습니다. 풀은 배열을 보유할 수 있어 RSS가 즉시 감소할 필요는 없습니다.

I/O 완료 전에 반납

뷰가 남아 있어도 버퍼 소유권은 끝났습니다. 다른 임대와 겹쳐 결과가 달라질 수 있어 반납 위치를 뒤로 옮겨야 합니다.

실습의 경계와 다음 장

사용 후 반납된 버퍼를 읽는 코드를 정상 계약으로 만들지 않습니다. 숨은 할당 절에서는 pool 이익과 수명 복잡성을 같은 측정 조건으로 비교합니다.
