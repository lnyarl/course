GC trace와 일시정지 분석

선수 장 · GC 단계와 스레드 정지

GC 자체가 짧은데 응답 정지는 길 수 있습니다. 정지 단계 그림을 실제 이벤트의 시각과 대응해 수집 시간과 사용자 지연을 구분합니다.

한 개의 GC 시간으로 합치지 않기

blocking GC는 관리 스레드 정지 요청, 정지 도달, 수집 작업, 재개의 경계를 가집니다. background GC는 일부 일을 애플리케이션과 겹쳐 진행하므로 전체 수집 경과 시간이 그대로 stop-the-world 시간은 아닙니다. 같은 이름의 GC 이벤트라도 어느 경계를 잰 값인지 확인합니다.

요청 지연에는 실행 대기·외부 I/O·락도 포함됩니다. p99가 튄 시점에 GC가 있었다는 상관만으로 인과를 확정하지 않습니다. allocation rate, 생존·승격량, 세대, pause와 같은 시간대의 CPU·대기 정보를 같이 수집합니다.

원시 이벤트를 읽는 코드 흐름

자신의 로컬 프로세스에서 dotnet-counters monitor -p PID --counters System.Runtime로 추세를 보고, 필요한 구간을 dotnet-trace collect -p PID --profile gc-verbose로 남깁니다. 실행한 도구의 지원 profile과 런타임을 먼저 확인합니다. trace의 GC 시작·종료와 suspension 관련 이벤트를 별도 구간으로 읽습니다.

코드에서는 GC.GetGCMemoryInfo()의 세대·승격·단편화·pause 관련 관측을 같은 작업 ID와 시점에 기록할 수 있습니다. 이 API의 마지막 GC 정보와 수집 구간 전체의 누적 통계를 혼동하지 않습니다. 진단 도구의 오버헤드를 포함한 실행과 최종 성능 비교 실행도 구분합니다.

실습과 예상 관찰

짧게 할당하고 버리는 모드와 일부 객체를 여러 batch 동안 보유하는 모드를 만드세요. 동일 총 입력으로 trace와 경과 시간을 저장하고 세대별 횟수·승격량·pause를 비교합니다. 먼저 어떤 모드에서 오래 사는 객체가 늘지 예상한 뒤 실제 trace와 맞는지 확인하세요.

대부분 빠르게 도달성을 잃음

젊은 세대 중심으로 회수될 가능성이 큽니다. 횟수만 아니라 생존량과 실제 pause를 함께 봅니다.

여러 batch 동안 객체를 보유

승격과 오래된 세대 비용이 달라질 수 있습니다. 보유를 끝낸 직후 메모리가 바로 내려간다고 가정하지 않습니다.

실습의 경계와 다음 장

trace 수집과 분석 도구에 따라 표시하는 항목이 다릅니다. 제공되지 않은 실제 pause 값을 예시 숫자로 대신하지 말고 진단 절의 관측 기록으로 연결합니다.
