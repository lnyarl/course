선수 장 · Finalizer와 Dispose

Dispose를 구현했어도 네이티브 호출이 끝나기 전에 핸들을 닫으면 안 됩니다. 마지막 정리와 현재 사용 중인 작업의 수명을 한 경계로 연결합니다.

핸들 소유자와 호출 수명

파일 실습에서는 File.OpenHandle이 반환하는 SafeFileHandle을 using으로 소유하고 RandomAccess.Read(handle, buffer, offset)의 호출 범위를 따라갑니다. 외부 핸들을 raw 정수로 복사하면 래퍼 객체의 생존과 실제 네이티브 사용이 분리될 수 있습니다. 직접 finalizer를 추가하는 것보다 표준 SafeHandle 소유권을 먼저 사용합니다.

P/Invoke가 SafeHandle을 인자로 받는 정상 패턴과, raw 포인터를 받은 네이티브 코드가 나중에 callback하는 비동기 패턴은 수명이 다릅니다. 비동기 작업은 시작 호출이 돌아왔을 때 끝난 것이 아니므로 완료·취소 관측 뒤에 버퍼 pin과 callback 참조를 해제해야 합니다. GC.KeepAlive 하나가 동시 Dispose나 전체 비동기 수명 계약을 대신하지 않습니다.

비관리 할당과 GC에 주는 정보

작은 관리 래퍼가 큰 비관리 메모리를 소유하면 관리 힙 크기만으로 비용을 파악하기 어렵습니다. 직접 할당을 소유하는 경우 GC.AddMemoryPressure(bytes)와 실제 해제 때의 RemoveMemoryPressure(bytes)를 같은 크기로 짝지을 수 있습니다. 메모리 압박 정보는 실제 메모리를 해제하는 API가 아닙니다.

할당 성공 뒤 소유권 확정, 정상 Dispose, 부분 초기화 실패, 중복 Dispose를 따라가며 실제 native free가 한 번만 일어나는지 확인합니다. callback에 GCHandle을 썼다면 callback을 더 받지 않는다는 근거가 생긴 뒤 Free합니다. finalizer는 시간과 실행 순서를 보장하는 주 경로로 삼지 않습니다.

실습과 예상 관찰

먼저 표준 파일 SafeHandle을 여는 작은 로컬 예제를 만들고 정상·예외 경로에서 using이 닫히는지 확인하세요. 직접 네이티브 할당을 가진 기존 학습 래퍼가 있다면 작은 할당만 사용해 성공/해제/실패 수를 집계하고 압박 정보의 추가·제거 크기가 맞는지 검사하세요.

완료를 관측한 뒤 소유자가 해제

사용 중인 자원과 해제된 자원의 경계를 설명할 수 있습니다. Dispose와 GC 메모리 회수 시점도 구분됩니다.

시작 호출 반환을 비동기 완료로 오인

callback과 버퍼가 아직 필요할 수 있습니다. 완료·취소 join과 해제 책임을 먼저 정해야 합니다.

실습의 경계와 다음 장

외부 메모리 손상이나 취약점 재현은 다루지 않습니다. 다음 핸들 절에서는 루트 역할과 외부 자원 수명이 서로 다른 이유를 비교합니다.
