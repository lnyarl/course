CPU 프로파일링과 핫패스 최적화

"느리다"는 증상이고, 프로파일은 진단입니다. 추측으로 최적화하면 90%는 엉뚱한 곳을 고칩니다. 이 장은 V8 샘플링 프로파일러의 원리부터 플레임 그래프를 읽는 눈, 벤치마크가 거짓말하는 방식, 그리고 프로덕션에서 안전하게 프로파일을 뜨는 운영 절차까지 다룹니다.

학습 목표

  • 샘플링 프로파일러의 원리와 오차를 이해하고, --cpu-prof/--prof/inspector 세션 중 상황에 맞는 것을 고를 수 있다.
  • 플레임 그래프에서 핫패스, (program)/(garbage collector)/(idle)의 의미, 인라이닝으로 사라진 프레임을 읽어낼 수 있다.
  • JIT 워밍업, 죽은 코드 제거, GC 노이즈 같은 벤치마크 함정을 피해 유의미한 측정을 설계할 수 있다.
  • 프로덕션에서 오버헤드 예산 안에서 지속 프로파일링을 운영할 수 있다.

1. 측정의 원칙

  1. 먼저 "어디가" 느린지 측정한다. 전체 응답 시간에서 DB 대기가 80%라면 JS 최적화는 상한이 20%입니다(Amdahl). 15장의 트레이스로 구간을 나누고, CPU 구간이 지배적일 때만 이 장의 도구를 씁니다.
  2. 프로덕션과 같은 조건에서 잰다. 개발 머신의 M-시리즈 CPU, 빈 캐시, 작은 데이터셋은 전혀 다른 프로파일을 냅니다. 최소한 같은 Node 메이저 버전과 같은 플래그(--max-old-space-size 등)로.
  3. 한 번 재지 않는다. 샘플링 프로파일은 통계입니다. 짧은 프로파일은 노이즈이고, 부하 패턴에 따라 핫스팟이 바뀝니다. 여러 번, 충분히 길게(최소 수십 초, 수천 샘플).
  4. 바꾼 뒤 다시 잰다. 최적화 전후 프로파일을 같은 방법으로 비교하고, 개선이 측정 오차보다 큰지 확인합니다. "빨라진 것 같다"는 데이터가 아닙니다.
  5. 처리량과 지연을 따로 본다. 워커로 보내면 지연은 좋아지지만 처리량은 그대로(9장). 캐시는 평균은 좋아지지만 미스 시 꼬리 지연은 그대로.
최적화 전 체크리스트
  • 이 코드가 전체 CPU 시간의 몇 %를 차지하는가? (프로파일 수치)
  • 그 %가 사용자 체감(p99 지연, 비용)에 연결되는가?
  • 알고리즘/데이터 구조 수준의 개선 여지가 먼저 없는가? (O(n²) → O(n log n)이 마이크로 최적화 100개보다 낫다)
  • 측정 방법이 재현 가능하게 기록되어 있는가?

2. 샘플링 프로파일러의 원리와 오차

프로파일러는 두 종류입니다. 계측(instrumentation)은 모든 함수 진입·탈출에 코드를 끼워 넣어 정확하지만 느리고(수 배) 결과를 왜곡합니다. 샘플링(sampling)은 일정 간격(V8 기본 1000µs = 1ms)마다 "지금 콜 스택이 뭐지?"를 기록합니다. 오버헤드가 작고(보통 수 % 이내) 프로덕션에서 쓸 수 있지만, 통계적 추정입니다.

V8의 CPU 프로파일러는 별도 샘플러 스레드가 주기적으로 메인 스레드에 시그널(Linux에서 SIGPROF)을 보내거나 스레드를 잠시 멈추고, 현재 JS 스택을 걷어(walk) 기록합니다. 결과는 "함수 F가 샘플 N개에 등장" 형태이고, 시간은 N × 간격으로 추정됩니다.

샘플링 프로파일러 원리 시뮬레이터
가상의 실행 타임라인(함수별 실제 CPU 시간)에 일정 간격으로 샘플을 찍어 추정치를 만듭니다. 간격을 늘리면 짧은 함수가 사라지거나 과대평가되는 것을 보세요.

3. --cpu-prof와 .cpuprofile 포맷

# 프로세스 시작부터 종료까지 프로파일. 종료 시 파일 기록 (SIGKILL 되면 안 남는다!)
node --cpu-prof --cpu-prof-dir=./prof --cpu-prof-interval=500 app.js
#   → ./prof/CPU.20261021.172541.13896.0.001.cpuprofile
#   --cpu-prof-name=app.cpuprofile 로 이름 지정 가능. 워커 스레드도 각각 파일을 만든다.

# 실행 중인 프로세스에서 구간 프로파일 (프로덕션용). 재시작·플래그 불필요
node -e "
const inspector = require('node:inspector/promises');
const s = new inspector.Session(); s.connect();
await s.post('Profiler.enable');
await s.post('Profiler.setSamplingInterval', { interval: 1000 });
await s.post('Profiler.start');
await new Promise(r => setTimeout(r, 10_000));            // 10초간
const { profile } = await s.post('Profiler.stop');
require('fs').writeFileSync('p.cpuprofile', JSON.stringify(profile));
"
# 위 코드를 앱 안의 관리용 엔드포인트/시그널 핸들러에 넣어 두는 것이 운영 표준 (9절)

.cpuprofile은 JSON이며 Chrome DevTools(Performance 탭 → Load profile, 또는 chrome://inspect), VS Code(파일을 열면 바로 플레임 뷰), speedscope에서 엽니다. 구조를 알면 직접 분석 스크립트를 짤 수 있습니다.

{
  "nodes": [                                 // 호출 트리 노드 (함수 × 호출 경로)
    { "id": 1, "callFrame": { "functionName": "(root)", "url": "", "lineNumber": -1, "columnNumber": -1, "scriptId": "0" },
      "hitCount": 0, "children": [2, 3] },
    { "id": 2, "callFrame": { "functionName": "(program)", ... }, "hitCount": 12 },
    { "id": 3, "callFrame": { "functionName": "handler", "url": "file:///app/server.js", "lineNumber": 41, ... },
      "hitCount": 8, "children": [4], "positionTicks": [{ "line": 42, "ticks": 5 }, ...] },   // 줄 단위 히트
    ...
  ],
  "startTime": 1234567890,  "endTime": 1234667890,     // µs
  "samples":    [2, 3, 3, 4, 3, 2, ...],                 // 샘플마다 "그때 맨 위 노드"의 id
  "timeDeltas": [1002, 998, 1050, 970, ...]              // 샘플 간 간격 µs (누적하면 각 샘플의 시각)
}
  • self time = 그 노드가 samples에 직접 등장한 횟수 × 간격. total time = self + 자식들의 total. 플레임 그래프의 폭은 total, "Bottom-up" 뷰의 정렬 기준은 self입니다.
  • 같은 함수가 다른 경로로 호출되면 노드가 여럿입니다(호출 트리). 함수 기준으로 합치려면 callFrame으로 그룹화합니다.
  • timeDeltas를 보면 실제 간격이 요청한 값과 다른 것을 알 수 있습니다. GC나 긴 네이티브 호출 중엔 샘플이 밀리고, 그 시간은 다음 샘플에 뭉쳐 귀속됩니다.

4. 플레임 그래프 읽기

플레임 그래프는 샘플 스택들을 병합한 그림입니다. x축은 시간이 아니라 샘플 비율(알파벳순 정렬), y축은 스택 깊이, 각 막대의 폭이 그 함수가 스택에 있었던 샘플의 비율(total)입니다. 가장 위에 있는 넓은 막대(자식이 없는 평평한 윗면)가 self time이 큰 함수 = 실제로 CPU를 태운 곳입니다.

인터랙티브 플레임 그래프
가상 프로파일 3종. 막대에 마우스를 올리면 샘플 수와 비율, 클릭하면 그 서브트리로 줌인(다시 클릭하거나 "루트로" 버튼으로 복귀). 아래쪽이 (root), 위로 갈수록 호출된 함수입니다.
JS (앱 코드)JS (node_modules/코어 lib)네이티브/빌트인(garbage collector)(idle)/(program)

4.1 특수 프레임의 의미

프레임의미클 때 의심할 것
(root)모든 샘플의 뿌리-
(program)V8이 JS 스택을 귀속시키지 못한 시간: 네이티브 코드(libuv, 바인딩), JIT 컴파일, 일부 내장 함수네이티브 애드온, 과도한 JIT 재컴파일(deopt 루프, 4장), 동기 fs/zlib
(garbage collector)GC 일시정지할당률 과다, 큰 힙, 누수(5·11장). 10%를 넘으면 메모리 문제가 CPU 문제로 보이는 것
(idle)루프가 poll에서 잠든 시간크면 CPU가 병목이 아니라는 뜻. 그래프에서 제외하고 보는 것이 보통
이름 없는 (anonymous)익명 함수콜백·화살표 함수에 이름을 붙여야 읽을 수 있음

4.2 사라진 프레임: 인라이닝

TurboFan이 작은 함수를 호출자에 인라이닝하면(4장) 프로파일에서 그 함수는 호출자의 self time으로 흡수됩니다. "핫스팟이 handler인데 handler 자체는 별것 안 하는데?"라면 인라인된 피호출자를 의심하세요. 확인: --no-turbo-inlining으로 다시 프로파일(성능 특성이 바뀌므로 진단용으로만), 또는 소스 줄 단위 히트(positionTicks, DevTools에서 소스 뷰의 줄 옆 숫자)를 봅니다.

4.3 도구

  • Chrome DevTools: Performance 패널의 플레임 차트(이것은 시간순 차트), Bottom-up/Call tree 테이블. 프로파일 파일을 드래그해 로드.
  • speedscope: 플레임 그래프/시간순/샌드위치 뷰를 브라우저에서. .cpuprofile, perf script 출력, --prof 로그까지 읽음.
  • 0x: npx 0x app.js로 실행 → 종료 시 HTML 플레임 그래프. 내부적으로 --cpu-prof 또는 perf 사용.
  • clinic flame / doctor / bubbleprof: 플레임 그래프 + 자동 진단 힌트(이벤트 루프 지연, GC, 핸들 수). 입문에 좋지만 유지보수 상태를 확인하고 쓰세요.

5. --prof: V8 틱 프로세서와 네이티브 프레임

--cpu-prof가 JS 스택만 본다면, --prof는 V8의 로거로 JS 코드 주소 공간 + 공유 라이브러리의 틱을 기록합니다. C++ 바인딩, libc, OpenSSL 안에서 시간을 쓰는지 알고 싶을 때 씁니다.

node --prof app.js                      # isolate-0x....-v8.log 생성 (수십 MB까지 커질 수 있음)
node --prof-process --preprocess isolate*.log > p.json   # speedscope용 JSON
node --prof-process isolate*.log                        # 텍스트 리포트:

 [Summary]:
   ticks  total  nonlib   name
   4210   61.2%   78.9%  JavaScript
    512    7.4%    9.6%  C++
    380    5.5%    7.1%  GC
   1560   22.7%          Shared libraries      ← libc, libssl, node 바이너리의 C++ 등
    210    3.1%          Unaccounted

 [JavaScript]:
   ticks  total  nonlib   name
   1820   26.5%   34.1%  LazyCompile: *serialize /app/lib/json.js:12:21   ← * = 최적화됨(TurboFan), ~ = 인터프리터
 [Bottom up (heavy) profile]:                                            ← 호출자 역추적. 가장 유용한 섹션
   ...

이름 앞의 *는 최적화된 코드, ~는 Ignition 바이트코드(인터프리터)에서 돈 것입니다. 핫 함수가 계속 ~라면 4장의 deopt 원인을 찾으세요. Node 22의 --prof 리포트는 Maglev 코드를 별도로 표시하지 않을 수 있습니다(V8 버전에 따름).

6. Linux perf와 eBPF

커널·시스템 전체를 함께 보려면 perf입니다. 문제는 JIT 코드에 심볼이 없다는 것인데, Node는 perf map을 써 줄 수 있습니다.

node --perf-basic-prof app.js            # /tmp/perf-<pid>.map 에 "주소 크기 함수명" 기록 (JIT 코드 생성 때마다 추가 → 파일이 계속 커짐)
node --perf-basic-prof-only-functions    # 함수만(스텁·IC 제외). 운영에서는 이쪽
node --interpreted-frames-native-stack   # 인터프리터 프레임도 네이티브 스택에서 구분 (perf에서 JS 프레임이 보이려면 필요)

perf record -F 99 -g -p <pid> -- sleep 30        # 99Hz, 콜 그래프, 30초
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg      # Brendan Gregg의 FlameGraph 스크립트
  • 장점: 커널 함수(네트워크 스택, 페이지 폴트), libuv, OpenSSL, GC 내부까지 한 그림. off-CPU 분석(perf sched, eBPF offcputime)으로 "왜 기다렸나"도 볼 수 있습니다. JS 프로파일러로는 불가능.
  • 단점: 프레임 포인터가 필요(Node 바이너리는 기본 포함), 컨테이너에서는 CAP_PERFMON/CAP_SYS_ADMIN과 호스트 커널 심볼 접근 필요, perf map 파일이 무한히 커짐(주기적 정리 또는 --perf-basic-prof-only-functions).
  • eBPF 기반 지속 프로파일러(Parca, Pyroscope eBPF, Elastic Universal Profiling)는 프로세스에 플래그 없이도 perf map을 읽어 JS 프레임을 복원하려 시도합니다. 지원 수준은 도구별로 확인.

7. 흔한 핫스팟 카탈로그

프로파일에서 보이는 모습원인처방
JSON.stringify/JSON.parse가 넓다큰 응답/요청 본문, 로깅에서 객체를 매번 직렬화응답 크기 줄이기(필드 선택, 페이지네이션), 스키마 기반 직렬화(fast-json-stringify), 로그 샘플링, 스트리밍 파서
RegExp.prototype.exec/String.prototype.replace가 넓고 입력 길이에 따라 폭발백트래킹 정규식(중첩 수량자, (a+)+), 매 호출 정규식 재생성정규식 단순화·앵커링, 입력 길이 제한, RE2(선형 시간), 정규식 상수화(16장)
(garbage collector) > 10%단명 객체 폭증(스프레드, map/filter 체인, 클로저, 문자열 조각), 큰 힙할당 줄이기(5장), 객체 풀은 신중히, 힙 크기 조정
(program)이 넓다동기 네이티브: fs.*Sync, zlib.*Sync, crypto.pbkdf2Sync, 네이티브 애드온, 지속적 재컴파일비동기 API(스레드풀로), --trace-deopt로 deopt 루프 확인

8. 마이크로벤치마크와 그 함정

"A 방식이 B보다 빠른가?"를 재는 마이크로벤치마크는 JIT가 있는 언어에서 가장 틀리기 쉬운 측정입니다. 아래 데모는 전형적인 함정을 모사합니다.

8.1 함정 목록

  • JIT 워밍업: 처음 수십~수백 회는 인터프리터(Ignition) → Sparkplug → Maglev → TurboFan 단계를 거치며 점점 빨라집니다. 첫 측정은 "컴파일 시간"입니다. 워밍업 후 측정하고, 보고서에는 중앙값과 분포를.
  • 죽은 코드 제거(DCE): 결과를 쓰지 않으면 TurboFan이 계산 자체를 지웁니다. "0.001ns per op"은 측정이 아니라 삭제입니다. 결과를 누적하거나 외부로 내보내세요(benchmark 도구의 do_not_optimize 류).
  • 상수 접기·루프 불변 호이스팅: 입력이 상수면 컴파일러가 미리 계산합니다. 입력을 매 회 다르게, 혹은 불투명하게.
  • 모노모픽 편향: 벤치에서는 한 타입만 넘겨 IC가 모노모픽이지만 실제 코드는 메가모픽(4장). 실제 입력 분포를 흉내 내세요.
  • GC 노이즈: 할당하는 코드는 간헐적으로 GC 일시정지가 섞여 평균이 왜곡됩니다. 중앙값·최솟값을 함께 보고, --expose-gc로 측정 전 gc()를 호출하거나 충분히 많이 반복.
  • 측정 자체의 비용: performance.now()는 수십 ns, process.hrtime.bigint()도 비슷. 1µs 이하 연산은 수천 회 묶어 재야 합니다.
  • CPU 주파수·전원 관리·noisy neighbor: 노트북 터보부스트, 클라우드 VM의 CPU 스틸. 여러 번 반복해 분산을 보고하세요.

9. 프로덕션 지속 프로파일링

개발 환경 프로파일은 프로덕션의 핫스팟을 놓칩니다(데이터 분포, 캐시 상태, 트래픽 믹스). 그래서 성숙한 조직은 프로덕션에서 항상 낮은 빈도로 프로파일을 뜹니다.

  1. 오버헤드 예산: 샘플링 간격 10ms(100Hz)면 CPU 오버헤드는 보통 1~2% 이내. 1ms(1000Hz)는 부하가 높은 서비스에서 5%+를 볼 수 있습니다. 메모리: 프로파일 버퍼는 작지만 긴 프로파일은 노드 수가 커집니다.
  2. 주기적 스냅샷: 예를 들어 1분마다 10초 프로파일을 떠서 압축·업로드. inspector 세션 방식(3절)이면 플래그·재시작 없음.
  3. 트리거 기반: ELU > 0.8이 30초 지속, 또는 루프 지연 p99 > 200ms일 때 자동으로 30초 프로파일. 장애 중의 프로파일이 가장 가치 있습니다.
  4. 온디맨드: SIGUSR2 핸들러나 관리 엔드포인트(인증 필수)로 "지금 20초 프로파일". SIGUSR1은 Node가 inspector 활성화용으로 예약하므로 쓰지 마세요.
  5. 집계: 같은 버전·같은 엔드포인트의 프로파일을 병합해 "서비스 전체 플레임 그래프"를 봅니다. Pyroscope, Parca, Datadog/Google Cloud/Elastic의 Continuous Profiler가 이 역할. 배포 전후 차이(diff flame graph)가 회귀 탐지의 핵심.
// 최소 구현: 시그널로 20초 프로파일을 떠서 파일로
const inspector = require('node:inspector/promises');
process.on('SIGUSR2', async () => {
  const s = new inspector.Session(); s.connect();
  await s.post('Profiler.enable'); await s.post('Profiler.setSamplingInterval', { interval: 10_000 }); // 10ms
  await s.post('Profiler.start');
  setTimeout(async () => {
    const { profile } = await s.post('Profiler.stop'); s.disconnect();
    await fs.promises.writeFile(`/tmp/prof-${process.pid}-${Date.now()}.cpuprofile`, JSON.stringify(profile));
  }, 20_000).unref();
});
--cpu-prof를 프로덕션에서 쓰지 않는 이유 종료 시에만 파일을 쓰므로 OOMKilled·SIGKILL이면 아무것도 남지 않고, 긴 수명 프로세스에서는 파일이 거대해지며, 간격·구간을 런타임에 바꿀 수 없습니다. 부팅 시간 분석(스크립트 시작~listen)에는 적합합니다.

10. 현업 사례

사례 1: "DB가 느리다"가 실은 JSON이었다

API p99 2초. 팀은 DB 인덱스를 두 주 동안 손봄. 프로덕션 프로파일을 뜨자 JSON.stringify가 self time 38%: 응답에 불필요한 중첩 객체(관계 전체)를 포함해 평균 응답 4MB. 필드 선택으로 응답을 120KB로 줄이자 p99 300ms. 교훈: 측정 전에 고치지 말 것.

사례 2: 벤치에서 3배 빨랐던 라이브러리가 프로덕션에서 느려짐

마이크로벤치에서 새 직렬화 라이브러리가 3배 빠름. 배포 후 CPU 20% 상승. 원인: 벤치는 한 가지 객체 모양(모노모픽)만 썼고, 실제 트래픽은 수백 가지 모양 → 라이브러리 내부 IC가 메가모픽으로 전락. 교훈: 벤치 입력을 프로덕션 샘플에서 추출.

사례 3: (program) 45%의 정체

플레임 그래프에서 (program)이 절반. JS 핫스팟이 안 보여 포기할 뻔. --prof로 보니 Shared libraries의 libz: 요청마다 zlib.gzipSync로 응답 압축. 비동기 zlib.gzip(스레드풀)으로 바꾸고, 이후 압축을 리버스 프록시로 이관. 교훈: (program)이 크면 네이티브 측 프로파일러로 한 단계 내려갈 것.

핵심 요약

  • 측정 → 변경 → 재측정. 프로덕션과 같은 조건에서, 충분한 샘플로, 여러 번.
  • V8 CPU 프로파일러는 샘플링(기본 1ms). 오차 ≈ 1/√샘플수. 전체의 1% 미만 함수 수치는 노이즈.
  • --cpu-prof는 부팅/CLI용, 프로덕션은 inspector 세션으로 구간 프로파일. .cpuprofile = nodes + samples + timeDeltas.
  • 플레임 그래프: x = 샘플 비율(시간순 아님), 윗면이 넓은 곳이 self time. (program)=네이티브/JIT, (garbage collector)=GC, (idle)=대기. 인라이닝은 프레임을 숨긴다.
  • --prof/perf는 네이티브·커널까지. perf에는 --perf-basic-prof-only-functions + --interpreted-frames-native-stack.
  • 벤치 함정: 워밍업, DCE, 상수 접기, 모노모픽 편향, GC 노이즈, 측정 비용. 중앙값·분포·실제 입력으로.
  • 지속 프로파일링: 10ms 간격, 주기+트리거+온디맨드, 버전 간 diff가 회귀 탐지의 핵심.

확인 문제

플레임 그래프에서 함수 X의 막대가 가장 넓지만 그 위에 자식 막대들이 거의 전부를 덮고 있다. 해석은?
폭은 total time(스택에 있었던 샘플 비율)입니다. 자식이 덮고 있으면 그 시간은 자식의 것입니다. 최적화 대상은 "윗면이 노출된 넓은 막대"(self time)입니다.
1ms 간격 10초 프로파일에서 함수 F가 샘플 9개(0.09%)에 나타났다. F가 전체 CPU의 0.09%를 쓴다고 결론 내릴 수 있는가?
오차는 1/√n ≈ 1/3. 또한 0.1% 수준의 함수는 최적화해도 체감이 없습니다. 간격을 줄이면 샘플은 늘지만 오버헤드와 관측자 효과가 커집니다.
마이크로벤치에서 어떤 함수가 "0.3ns/op"로 측정되었다. 가장 가능성 높은 설명은?
0.3ns는 CPU 사이클 1개 수준입니다. 의미 있는 연산이 이 시간에 끝날 수 없으므로 컴파일러가 코드를 지운 것입니다. 결과를 싱크 변수에 누적하거나 외부로 내보내야 합니다.
프로덕션 서비스가 간헐적으로 CPU 100%를 찍는다. 원인 파악에 가장 적절한 방법은?
간헐적 문제는 "그 순간"의 프로파일이 필요합니다. 재시작 없이 런타임에 켤 수 있는 inspector 세션을 트리거 기반으로 돌리는 것이 정답입니다. --cpu-prof는 종료 시에만 기록하고 --prof 로그는 하루면 수 GB가 됩니다.
(program) 프레임이 전체의 40%를 차지한다. 다음 단계로 적절한 것은?
(program)은 V8이 JS 스택에 귀속시키지 못한 시간입니다. 동기 네이티브 호출, 애드온, 재컴파일 등이 후보이며 JS 프로파일러로는 더 내려갈 수 없으므로 네이티브 프로파일러가 필요합니다.

실습 과제

  1. 플레임 그래프 만들기. 2장 실습의 서버에 /slow(동기 300ms) 외에 /json(큰 객체를 stringify)을 추가하고 autocannon으로 부하를 주면서 3절의 inspector 세션 코드로 20초 프로파일을 뜨세요. speedscope에서 열어 self time 상위 3개를 적고, (program)과 (garbage collector) 비율을 기록하세요. 기대: JSON.stringify가 상위, (idle)은 부하에 따라 변동.
  2. 샘플링 오차 체감. 같은 부하에서 간격 100µs, 1ms, 10ms로 각각 프로파일을 뜨고 상위 함수의 비율이 어떻게 달라지는지, 프로파일 중 서버 처리량이 얼마나 떨어지는지(오버헤드) 표로 정리하세요.
  3. DCE 재현. tinybench로 Math.sqrt(i)를 ① 결과를 버리고 ② 싱크에 더하며 측정해 ops/sec 차이를 보세요. 그다음 --no-opt(TurboFan 비활성, 진단용 V8 플래그)로 다시 돌려 차이가 사라지는지 확인하세요.
  4. perf 맵. Linux에서 node --perf-basic-prof-only-functions --interpreted-frames-native-stack app.js를 띄우고 perf record -F 99 -g -p <pid> -- sleep 15 → FlameGraph로 SVG를 만들어 JS 프레임과 libuv/커널 프레임이 함께 보이는지 확인하세요.
