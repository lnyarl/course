프로덕션 배포: 컨테이너, 시그널, 리소스

로컬에서 node server.js로 잘 돌던 서비스가 컨테이너 안에서는 종료에 10초가 걸리고, 배포 때마다 502가 몇 개씩 튀고, 메모리는 넉넉한데 OOMKilled로 죽습니다. 이 장은 Node.js 프로세스가 컨테이너·오케스트레이터와 만나는 경계에서 일어나는 일을 다룹니다. 이미지 설계, PID 1과 시그널, 그레이스풀 셧다운, k8s 프로브, cgroup 한계와 V8 힙의 관계까지.

학습 목표

  • 레이어 캐시와 베이스 이미지 선택 근거를 설명하고, 멀티스테이지 Dockerfile을 올바르게 구성할 수 있다.
  • PID 1 문제·시그널 전달 경로를 이해하고 종료 코드까지 일관된 그레이스풀 셧다운을 구현할 수 있다.
  • k8s의 startup/readiness/liveness 프로브와 종료 시퀀스(preStop, terminationGracePeriodSeconds)를 앱 설정과 정합시켜 배포 중 요청 유실을 0에 가깝게 만들 수 있다.
  • cgroup 메모리·CPU 한계가 V8 힙 상한, 스레드풀, 워커 수에 미치는 영향을 계산하고 플래그로 명시할 수 있다.

1. 컨테이너 이미지 설계

이미지는 "레이어의 스택"이고, 각 RUN/COPY/ADD가 레이어 하나입니다. 빌드 캐시는 위에서 아래로 내려오다 처음으로 바뀐 레이어부터 끝까지 다시 만듭니다. 그래서 명령 순서가 빌드 시간을 결정합니다. 자주 바뀌는 것(소스)은 아래로, 드물게 바뀌는 것(의존성)은 위로.

FROM node:22
WORKDIR /app
COPY . .                 # 소스 한 줄만 바뀌어도 아래 전부 캐시 무효
RUN npm install          # lockfile 무시 가능, devDependencies 포함
CMD ["npm", "start"]     # 시그널이 node까지 전달되지 않음 (2절)
# ---- 1단계: 빌드 (devDependencies 포함, 네이티브 모듈 컴파일) ----
FROM node:22-bookworm AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci       # lockfile 그대로, 캐시 마운트
COPY . .
RUN npm run build && npm prune --omit=dev              # 또는 npm ci --omit=dev 를 별도 단계에서

# ---- 2단계: 실행 ----
FROM node:22-bookworm-slim
ENV NODE_ENV=production
WORKDIR /app
COPY --from=build --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/dist ./dist
COPY --chown=node:node package.json ./
USER node                                              # 공식 이미지에 있는 uid 1000
EXPOSE 3000
CMD ["node", "--enable-source-maps", "dist/server.js"] # exec 형식: node가 PID 1 (또는 --init 사용)

2. PID 1 문제: 시그널과 좀비

Linux 커널은 PID 1(init)을 특별 취급합니다. 핸들러를 등록하지 않은 시그널은 PID 1에게 전달되지 않습니다(기본 동작 "terminate"가 적용되지 않음). 일반 프로세스라면 SIGTERM을 받고 그냥 죽지만, PID 1인 node는 핸들러가 없으면 SIGTERM을 무시합니다. 그 결과 docker stop은 10초(기본 유예)를 기다린 뒤 SIGKILL을 보내고, k8s는 terminationGracePeriodSeconds(기본 30초)를 꽉 채운 뒤 죽입니다. 배포마다 파드 하나당 30초씩 늘어지는 "느린 롤아웃"의 가장 흔한 원인입니다.

두 번째 책무는 좀비 회수입니다. 자식 프로세스가 죽으면 부모가 wait()해야 프로세스 테이블에서 사라집니다. 부모가 먼저 죽은 고아는 PID 1에게 입양되는데, node는 자기가 만든 자식은 libuv가 회수하지만 입양된 손자(예: 자식 셸이 띄운 프로세스)는 회수하지 않습니다. child_process로 셸 명령을 자주 띄우는 서비스라면 좀비가 쌓여 PID 고갈에 이를 수 있습니다.

권장 조합 ENTRYPOINT ["tini", "--"] + CMD ["node", "server.js"](또는 Docker --init, k8s에서는 이미지에 tini 포함). 그리고 앱에 SIGTERM 핸들러. tini는 시그널을 "전달"할 뿐 그레이스풀 셧다운을 대신해 주지 않습니다. 자식 프로세스를 띄우지 않고 핸들러가 확실히 있다면 node를 PID 1로 두어도 실무상 문제는 없습니다.

4. 그레이스풀 셧다운 구현

올바른 종료는 네 단계입니다. ① 새 요청 받기를 멈춘다 ② 진행 중인 요청을 끝낸다 ③ 외부 리소스(DB 풀, 큐 컨슈머, 로그 전송)를 닫는다 ④ 정해진 시간 안에 안 끝나면 강제 종료한다. 함정은 ②에 있습니다. server.close()는 리스닝 소켓만 닫고 keep-alive로 열려 있는 유휴 커넥션은 닫지 않습니다. 클라이언트(로드밸런서)가 그 커넥션에 다음 요청을 보내면 서버는 응답한 뒤 Connection: close로 닫지만, 커넥션이 유휴 상태로 남아 있으면 keepAliveTimeout(기본 5초)까지 close 콜백이 지연됩니다.

const http = require('node:http');
const server = http.createServer(app);
server.listen(3000);

let shuttingDown = false;
async function shutdown(signal) {
  if (shuttingDown) return;
  shuttingDown = true;
  log.info({ signal }, 'shutdown start');

  // ④ 안전장치: 무슨 일이 있어도 N초 뒤엔 죽는다 (terminationGracePeriodSeconds보다 짧게)
  const killer = setTimeout(() => { log.error('forced exit'); process.exit(1); }, 8_000);
  killer.unref();

  // ① 리스닝 중단 + 유휴 keep-alive 커넥션 즉시 종료 (Node 18.2+)
  server.close(err => log.info({ err }, 'listener closed'));
  server.closeIdleConnections();
  // 진행 중인 요청은 응답 후 커넥션이 닫힌다. 아직 헤더를 안 보낸 요청에 Connection: close 를 강제하려면:
  // app.use((req, res, next) => { if (shuttingDown) res.setHeader('Connection', 'close'); next(); });

  // readiness 프로브가 503을 돌려주게 하여 새 트래픽 유입 차단 (6절)
  healthy = false;

  // ② 진행 중 작업 대기: 'close' 이벤트는 모든 커넥션이 끝나야 온다
  await new Promise(resolve => server.once('close', resolve));

  // ③ 외부 리소스
  await Promise.allSettled([db.end(), queue.consumer.close(), log.flush?.()]);
  clearTimeout(killer);
  process.exitCode = 0;          // 자연 종료: 남은 flush 를 기다림
}
for (const s of ['SIGTERM', 'SIGINT']) process.on(s, () => shutdown(s));
  • server.closeAllConnections()는 진행 중 요청까지 끊습니다. 강제 종료 직전(killer 안)에서만 쓰세요.
  • HTTP/2는 session.close()가 GOAWAY를 보내 스트림이 끝날 때까지 기다립니다. gRPC 서버도 tryShutdown 계열이 있습니다.
  • WebSocket/SSE 같은 장기 연결은 "진행 중 요청"이 끝나지 않습니다. 셧다운 시작 시 클라이언트에 close 프레임/재연결 신호를 보내고 짧은 유예 후 끊어야 합니다.
  • 큐 컨슈머는 먼저 새 메시지 수신을 멈추고(unsubscribe/pause), 처리 중인 메시지를 ack한 뒤 닫습니다. 순서가 바뀌면 메시지가 다른 워커에 중복 전달됩니다.
  • Node 18.x 이전에는 closeIdleConnections가 없어 직접 소켓을 추적(server.on('connection') + Set)해 닫아야 했습니다.

5. k8s 종료 시퀀스와 요청 유실

파드 삭제가 시작되면 두 가지 일이 병렬로, 서로 모르는 채 일어납니다. (a) kubelet이 컨테이너에 preStop 훅 → SIGTERM을 보낸다. (b) 엔드포인트 컨트롤러가 EndpointSlice에서 파드를 빼고, 각 노드의 kube-proxy와 인그레스 컨트롤러가 이를 반영한다. (b)는 전파에 수백 ms에서 수 초가 걸리는데, 그동안 로드밸런서는 SIGTERM을 이미 받은 파드에 새 요청을 보냅니다. 앱이 SIGTERM 즉시 server.close()를 하면 그 요청들은 connection refused(502)가 됩니다.

해결은 역설적으로 "SIGTERM을 받아도 잠깐 더 받아주는 것"입니다. preStop: sleep N으로 SIGTERM 자체를 늦추거나, 앱이 SIGTERM 후 N초 동안은 리스닝을 유지합니다. N은 엔드포인트 전파 시간보다 커야 하고, terminationGracePeriodSeconds는 preStop + 드레인 시간 + 여유보다 커야 합니다(유예 기간은 preStop 시작 시점부터 셉니다).

6. 프로브: startup·readiness·liveness

프로브질문실패 시무엇을 검사해야 하나
startup부팅이 끝났는가?실패 한도까지 다른 프로브 억제, 초과 시 재시작부팅이 느린 앱(스냅샷 없이 큰 번들, 워밍업)에서 liveness의 오탐을 막음. failureThreshold × periodSeconds가 최악 부팅 시간보다 길게
readiness지금 트래픽을 받아도 되는가?Service 엔드포인트에서 제거 (재시작 안 함)필수 의존성(DB 풀 연결, 캐시 워밍) 준비 여부, 셧다운 중 여부, 과부하 여부(ELU > 0.9 등). 일시적 상태를 표현
liveness이 프로세스를 죽이고 새로 띄우면 나아지는가?컨테이너 재시작프로세스 자체의 교착·루프 블로킹만. 외부 의존성(DB, 다른 서비스)을 넣으면 DB 장애가 전체 파드 재시작 폭풍이 된다(11절 사례 1)
// /healthz: liveness — 프로세스가 응답할 수 있는가만 본다
app.get('/healthz', (req, res) => res.status(200).end('ok'));

// /readyz: readiness — 트래픽을 받을 준비 + 셧다운 중이면 503
app.get('/readyz', (req, res) => {
  if (shuttingDown || !db.isConnected() || elu() > 0.9) return res.status(503).end('not ready');
  res.status(200).end('ready');
});

liveness 프로브는 이벤트 루프를 거치므로 2장의 루프 지연이 timeoutSeconds를 넘으면 실패합니다. 이것은 의도된 동작입니다. 다만 timeoutSeconds: 1처럼 공격적인 값은 GC 일시정지 한 번에 재시작을 일으킵니다. 루프 지연 p99.9를 측정해(15장) 그보다 넉넉하게, 보통 3~5초, failureThreshold: 3이 출발점입니다.

7. 리소스 한계와 V8: 메모리

컨테이너 메모리 한계(resources.limits.memory, cgroup v2의 memory.max)는 커널이 RSS 전체(힙 + 외부 버퍼 + 코드 + 스레드 스택 + 워커 힙 + 페이지 캐시 일부)에 적용합니다. 반면 V8의 --max-old-space-size는 JS 힙의 old space에만 적용됩니다. 두 값의 관계를 모르면 두 가지 장애 중 하나를 겪습니다.

  • 힙 상한 > 컨테이너 한계: V8은 아직 여유가 있다고 생각해 GC를 느긋하게 하고, 커널이 먼저 OOMKill(종료 코드 137). 힙 덤프도, 에러 로그도 없이 죽는다. 가장 흔한 "이유 없는 재시작".
  • 힙 상한이 너무 작음: 메모리가 남는데 FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory. 적어도 로그는 남는다.

Node는 v12부터 시작 시 사용 가능한 메모리(libuv uv_get_constrained_memory로 cgroup 한계 반영)를 보고 기본 힙 상한을 정합니다. 하지만 그 휴리스틱(대략 가용 메모리의 일정 비율, 64비트에서 상한 약 4GB)은 버전과 환경에 따라 달라서, 프로덕션에서는 명시하는 것이 정석입니다. 현재 값은 node -e "console.log(require('v8').getHeapStatistics().heap_size_limit/2**20)"로 확인합니다. 최신 Node에는 --max-old-space-size-percentage(가용 메모리 대비 %)도 추가되었습니다(버전 확인 필요).

8. 리소스 한계와 V8: CPU, 스레드, 워커

    
CPU limits는 CFS 쿼터(cpu.max)입니다. 예를 들어 limits.cpu: 500m은 "100ms 주기마다 50ms까지"입니다. 이 쿼터를 다 쓰면 프로세스는 주기 끝까지 스로틀되고, 그동안 이벤트 루프도 멈춥니다. 루프 지연 메트릭이 주기적으로 튀는데 앱에는 동기 작업이 없다면 CFS 스로틀링(cpu.stat의 nr_throttled)을 의심하세요.

    
중요한 함정: Node는 컨테이너 안에서 호스트의 CPU 수를 봅니다. os.cpus().length는 호스트 코어 수(예: 64)를 돌려주고, 이를 기준으로 cluster 워커 64개를 띄우면 쿼터 0.5코어를 64개 프로세스가 나눠 쓰며 스로틀에 시달립니다. os.availableParallelism()(Node 18.14+)은 CPU 어피니티(cpuset)는 반영하지만 CFS 쿼터 반영 여부는 libuv 버전에 따라 다르므로, 워커 수는 환경변수로 명시하는 것이 안전합니다.

    

      
스레드기본 수조정지침

      
메인(이벤트 루프)1-CPU limit이 1 미만이면 스로틀 각오. 요청 처리 서비스는 limit ≥ 1 권장

      CPU limit 없이 request만 설정하는 운영도 흔합니다(스로틀링 회피, burst 허용). 대신 노드 과점유를 막을 다른 장치(파드 수, 노드 풀 분리)가 필요합니다. 메모리는 반드시 limit을 거세요. 메모리는 압축되지 않고, 한계 없이 자라면 노드 전체가 영향을 받습니다. request=limit으로 두면 Guaranteed QoS가 되어 노드 압박 시 가장 늦게 축출됩니다.
    

  


  

    
9. 환경 설정, 시크릿, 프로세스 매니저

    
NODE_ENV와 NODE_OPTIONS

    
NODE_ENV=production은 Node 자체에는 아무 의미가 없습니다. 하지만 Express(뷰 캐시, 에러 스택 숨김), 많은 라이브러리(개발용 검증 생략), npm(--omit=dev)이 참조하므로 반드시 설정합니다. 반대로 NODE_ENV=production인데 테스트 코드가 돌면 검증이 꺼진 채 통과할 수 있습니다.

    
NODE_OPTIONS는 이미지를 다시 빌드하지 않고 런타임 플래그를 주입하는 통로입니다. --max-old-space-size, --enable-source-maps, --require ./tracing.js(OpenTelemetry 사전 로드) 등을 k8s 매니페스트에서 바꿀 수 있습니다. 보안상 일부 플래그(--inspect를 포함한 몇몇)는 허용되지 않습니다.

    
시크릿

    
    
      
  • 환경변수는 /proc/<pid>/environ, 크래시 덤프, 자식 프로세스 상속, 에러 리포트(process.report의 환경 섹션, --report-exclude-env로 제외)로 샙니다. 파일 마운트(k8s Secret volume) + 시작 시 메모리로 읽기가 더 안전하고, 회전(rotation)도 파일 감시로 처리할 수 있습니다.
    • 
      
  • Node 20.6+의 --env-file=.env는 로컬 개발용입니다. 프로덕션 이미지에 .env를 넣지 마세요.
    • 
      
  • 로그에 시크릿이 찍히는 경로: 요청 헤더 전체 로깅, 설정 객체 덤프, 에러 메시지에 연결 문자열 포함. 15장의 redaction.
    • 
    

    
프로세스 매니저와 오케스트레이터의 중복

    
컨테이너 안에서 pm2 cluster 모드로 N개 프로세스를 띄우는 구성은 k8s와 역할이 겹칩니다. 재시작·헬스체크·로그 수집·수평 확장을 두 레이어가 각자 하고, pm2가 자식을 재시작하는 동안 k8s는 컨테이너가 건강하다고 봅니다(liveness가 pm2 데몬에 응답). 원칙은 컨테이너 하나에 node 프로세스 하나, 복제는 replicas로. 멀티코어를 한 파드에서 써야 하면(9장) cluster를 직접 쓰되, 워커 죽음을 primary가 종료 코드로 전파하게 만드세요. pm2가 가치 있는 곳은 VM 직접 배포입니다.

    
무중단 배포 체크리스트

    
    
      
  • 롤링 업데이트 maxUnavailable: 0, maxSurge: 1 이상. 새 파드가 readiness를 통과한 뒤에만 구 파드 종료.
    • 
      
  • minReadySeconds로 워밍업 반영. readiness 통과 직후 트래픽이 몰리면 JIT 워밍업 전이라 지연이 튄다(4장).
    • 
      
  • preStop sleep ≥ 엔드포인트 전파 시간(보통 5~10초), terminationGracePeriodSeconds ≥ preStop + 앱 강제종료 타임아웃 + 5초.
    • 
      
  • 클라이언트/인그레스 재시도 정책: 멱등 요청(GET)에 한해 connection refused/reset 재시도(18장).
    • 
      
  • DB 마이그레이션은 앱 배포와 분리(Job), 하위 호환 스키마(expand-contract).
    • 
      
  • PodDisruptionBudget으로 노드 드레인 시 동시 종료 수 제한.

10. 스타트업 최적화

    
부팅 시간은 롤아웃 속도, 오토스케일 반응성, 그리고 startup 프로브 설계를 좌우합니다. 측정부터: node --cpu-prof로 부팅 구간을 프로파일하면(10장) 대개 require 체인(모듈 해석 + 컴파일)이 대부분입니다.

    
    
      
  • 컴파일 캐시(Node 22.1+): NODE_COMPILE_CACHE=/tmp/node-cache 또는 module.enableCompileCache(). V8 바이트코드를 디스크에 캐시해 두 번째 부팅부터 컴파일을 건너뜁니다. 컨테이너에서는 빌드 단계에서 한 번 실행해 캐시를 이미지에 포함시키는 방식이 가능합니다.
    • 
      
  • 번들링: 수천 개 파일을 하나로 합치면 fs 호출과 해석 비용이 줄어듭니다. 서버 코드도 esbuild 등으로 번들하는 팀이 늘고 있습니다. 단, 네이티브 모듈과 동적 require는 external 처리.
    • 
      
  • 유저랜드 스냅샷(--build-snapshot, Node 18.8+): 초기화가 끝난 힙 상태를 저장해 부팅 시 복원. 제약이 많아(비동기 초기화 불가, 일부 모듈 미지원) 큰 CLI나 함수 플랫폼에서 주로 씁니다. 1장 참고.
    • 
      
  • 지연 로드: 특정 라우트에서만 쓰는 무거운 모듈(pdf, 이미지 처리)은 첫 사용 시 await import().
    • 
      
  • startup 프로브: failureThreshold: 30, periodSeconds: 2면 최대 60초를 기다려 주며, 그동안 liveness는 억제됩니다.

11. 현업 장애 사례

    
사례 1: DB 점검 10분이 전체 서비스 30분 장애로
      
liveness 프로브가 SELECT 1을 포함. DB 페일오버 중 모든 파드의 liveness가 동시에 실패 → 전부 재시작 → 재시작한 파드들이 DB 연결 재시도로 DB에 커넥션 폭풍 → DB 복구 지연 → 다시 liveness 실패. DB가 복구된 뒤에도 CrashLoopBackOff 지수 백오프(최대 5분) 때문에 파드가 돌아오는 데 20분이 더 걸렸습니다. liveness는 프로세스만, DB 상태는 readiness로.

    

    
사례 2: 배포마다 0.1%의 502
      
앱은 SIGTERM 즉시 server.close()를 호출했고 preStop은 없었습니다. 인그레스 컨트롤러가 엔드포인트 변경을 반영하는 데 1~3초가 걸려, 그 사이 종료 중인 파드로 간 요청이 connection refused. 트래픽이 많을수록 비율이 높아졌습니다. preStop: exec sleep 8 추가와 terminationGracePeriodSeconds: 45로 해결. 위 시뮬레이터에서 preStop을 0과 5000ms로 비교해 보세요.

    

    
사례 3: 메모리 2GB 한계, 힙은 1.5GB까지 썼는데 OOMKilled
      
--max-old-space-size=1536. 이미지 리사이즈를 위해 sharp가 libvips로 수백 MB를 네이티브 할당했고, 업로드 버퍼(external)도 수백 MB. RSS = 힙 1.5G + external 0.4G + 네이티브 0.3G > 2G. V8은 힙 여유가 있다고 보고 GC를 미뤘고 커널이 먼저 죽였습니다. 힙 상한을 1024로 낮추고 이미지 처리를 메모리 한계가 큰 별도 워커 파드로 분리.

    

    
사례 4: 64코어 노드에서 cluster 워커 64개
      
os.cpus().length로 워커 수를 정한 코드가 limit 2코어 파드에서 64개 프로세스를 띄워 메모리 한계 초과 + CFS 스로틀 100%. 워커 수를 WEB_CONCURRENCY 환경변수로 명시하고 기본값을 1로.

    

  


  
핵심 요약
    
    
  • Dockerfile: lockfile 먼저 COPY → npm ci → 소스 COPY. 멀티스테이지로 빌드 도구와 dev 의존성을 실행 이미지에서 제거. USER node, exec 형식 CMD, slim 또는 distroless.
    • 
    
  • PID 1은 핸들러 없는 시그널을 무시하고 좀비를 회수하지 않는다. tini(--init) + 앱의 SIGTERM 핸들러. npm start는 시그널을 삼킨다.
    • 
    
  • 그레이스풀 셧다운: server.close() + closeIdleConnections() → in-flight 완료 → 외부 리소스 종료 → 타임아웃 강제 종료. 종료 코드 0/1/143/137의 의미를 알아둘 것.
    • 
    
  • k8s 종료는 kubelet 경로와 엔드포인트 제거 경로가 비동기. preStop sleep ≥ 전파 지연, grace ≥ preStop + 드레인 + 여유.
    • 
    
  • liveness에는 외부 의존성을 넣지 않는다. readiness가 트래픽 유입을, startup이 느린 부팅을 담당.
    • 
    
  • cgroup 메모리 한계는 RSS 전체, --max-old-space-size는 JS 힙만. 명시하되 external·네이티브·워커 몫을 뺀 값으로. CPU 수는 os.cpus()를 믿지 말고 환경변수로.

확인 문제

  

    
CMD npm start로 띄운 컨테이너에 docker stop을 하면 10초 뒤에야 종료된다. 가장 직접적인 원인은?

    
    
    
    
    
셸 형식 CMD는 /bin/sh -c "npm start"가 PID 1이 됩니다. sh는 시그널을 자식에게 전달하지 않고(그리고 PID 1이라 자신도 죽지 않음), Docker의 기본 유예 10초 후 SIGKILL이 갑니다. exec 형식 + tini 또는 직접 node 실행 + 핸들러로 해결합니다.

  

  

    
preStop 훅 sleep 5, 앱 드레인 최대 10초, 강제 종료 타임아웃 12초일 때 terminationGracePeriodSeconds의 최소 안전값에 가장 가까운 것은?

    
    
    
    
    
유예 기간은 preStop 시작부터 셉니다. preStop 5초 + 앱이 최대 12초(강제 종료 타임아웃)를 쓸 수 있으므로 17초 + 여유 5초 ≈ 22초. 유예가 더 짧으면 앱의 강제 종료 로직이 돌기 전에 SIGKILL이 옵니다.

  

  

    
컨테이너 memory limit 1GiB, --max-old-space-size=1024로 설정한 서비스가 로그 없이 종료 코드 137로 죽는다. 올바른 해석은?

    
    
    
    
    
137 = 128 + 9(SIGKILL)이고 로그가 없다는 것은 커널 OOM 킬러의 전형입니다. 힙 상한이 컨테이너 한계 전체를 차지하면 Buffer·네이티브·스택 몫이 없습니다. 힙 상한은 한계의 60~75% 수준으로 낮추고 external 사용량을 측정하세요. V8 힙 부족이면 "Reached heap limit" 로그가 남습니다.

  

  

    
liveness 프로브에 DB 연결 확인을 넣으면 안 되는 이유로 가장 적절한 것은?

    
    
    
    
    
liveness의 질문은 "재시작하면 나아지는가"입니다. 외부 의존성 장애는 재시작으로 나아지지 않고, 오히려 재시작 폭풍과 CrashLoopBackOff로 복구를 늦춥니다. 외부 의존성은 readiness로 표현합니다.

  

  

    
CPU limit 500m인 파드에서 동기 작업이 전혀 없는데 이벤트 루프 지연이 주기적으로 50ms씩 튄다. 유력한 원인은?

    
    
    
    
    
500m = 100ms 주기마다 50ms. 쿼터를 다 쓰면 남은 50ms 동안 프로세스 전체가 멈추고, 이는 루프 지연으로 관측됩니다. cpu.stat의 nr_throttled로 확인하고 limit을 올리거나 제거합니다.
