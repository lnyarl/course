모듈 시스템: CJS·ESM·로더

require('x') 한 줄 뒤에는 수십 번의 stat() 호출과 패키지 exports 맵 해석, 그리고 두 개의 전혀 다른 로더가 있습니다. CommonJS는 "실행하면서 연결"하고 ES Modules는 "연결한 뒤 실행"합니다. 이 차이가 순환 참조, 트리 셰이킹, 핫 리로드, dual package hazard까지 모든 모듈 관련 문제의 뿌리입니다.

학습 목표

  • CJS 해석 알고리즘(LOAD_AS_FILE / LOAD_AS_DIRECTORY / LOAD_NODE_MODULES)을 종이 위에서 따라갈 수 있다.
  • ESM의 파싱→인스턴스화→평가 3단계와 live binding, TLA가 로딩 그래프에 미치는 영향을 설명할 수 있다.
  • exports/imports 맵과 조건부 exports를 설계하고, dual package hazard를 피하는 패키지를 만들 수 있다.
  • require(esm), module.register() 훅, 타입 스트리핑 등 Node 20~24의 변화를 운영 관점에서 판단할 수 있다.

1. 두 로더, 두 철학

CommonJS(CJS)는 2009년 서버 사이드 JS를 위해 만들어진 동기 함수 호출 기반 규약입니다. require는 그냥 함수이고, 모듈은 함수 래퍼 안에서 실행되며, module.exports에 무엇이든 대입합니다. 따라서 어떤 모듈이 무엇을 export하는지는 실행해 봐야 압니다.

ES Modules(ESM)는 2015년 언어 표준으로 들어왔습니다. import/export는 문(statement)이며 파일 최상단에서 정적으로 분석됩니다. 실행하기 전에 전체 의존성 그래프를 만들고 바인딩을 연결합니다. 이 때문에 트리 셰이킹, 순환 참조의 안전한 처리, 비동기 로딩(브라우저)이 가능해졌습니다.

2. CJS 로더 내부: Module._load와 해석 알고리즘

require는 lib/internal/modules/cjs/loader.js의 Module.prototype.require → Module._load로 이어집니다. 핵심 흐름은 세 단계입니다.

2.1 해석 알고리즘 (Node 공식 의사코드 요약)

require(X) from module at path Y
1. X가 코어 모듈('node:fs', 'fs')이면 → 코어 반환. ('node:' 접두사는 캐시·오버라이드를 우회하므로 권장)
2. X가 '/'로 시작하면 Y = 파일시스템 루트
3. X가 './', '/', '../'로 시작하면
   a. LOAD_AS_FILE(Y + X)        b. LOAD_AS_DIRECTORY(Y + X)      c. THROW "not found"
4. X가 '#'로 시작하면 LOAD_PACKAGE_IMPORTS(X, dirname(Y))     ← package.json "imports"
5. LOAD_PACKAGE_SELF(X, dirname(Y))                            ← 자기 패키지 이름으로 자기 참조
6. LOAD_NODE_MODULES(X, dirname(Y))
7. THROW "not found"  (MODULE_NOT_FOUND)

LOAD_AS_FILE(X):  X → X.js → X.json → X.node         (.mjs, .cjs, .ts는 시도하지 않는다!)
LOAD_INDEX(X):    X/index.js → X/index.json → X/index.node
LOAD_AS_DIRECTORY(X): X/package.json의 "main" → LOAD_AS_FILE(X/main) → LOAD_INDEX(X/main) → (main 없으면) LOAD_INDEX(X)
LOAD_NODE_MODULES(X, START):
   DIRS = NODE_MODULES_PATHS(START)   // START부터 루트까지 모든 조상의 node_modules + $NODE_PATH + ~/.node_modules 등
   for each DIR in DIRS:
      LOAD_PACKAGE_EXPORTS(X, DIR)    // package.json에 "exports"가 있으면 여기서 결정, 실패 시 즉시 에러
      LOAD_AS_FILE(DIR/X)
      LOAD_AS_DIRECTORY(DIR/X)

세 가지가 실무에서 중요합니다. 첫째, 확장자 추론은 .js/.json/.node만이며 require('./util')이 util.mjs를 찾아주지 않습니다. 둘째, node_modules 탐색은 조상 디렉터리를 모두 올라가며 stat()을 호출하므로, 깊은 모노레포에서 존재하지 않는 패키지를 require하면 수십 번의 syscall이 발생합니다. 셋째, exports 필드가 있는 패키지에서 해당 서브패스가 없으면 fallback 없이 ERR_PACKAGE_PATH_NOT_EXPORTED입니다.

    3. ESM 로더 내부: 링킹 3단계와 live binding

    ESM은 lib/internal/modules/esm/의 ModuleLoader가 담당하며, V8의 v8::Module API 위에 올라갑니다. 로딩은 명확한 세 단계로 나뉘고, 한 단계가 그래프 전체에 대해 끝나야 다음 단계로 갑니다.

    3.1 live binding의 실체

    counter.mjs
    export let count = 0;
export function inc() { count++; }
    main.mjs
    import { count, inc } from './counter.mjs';
inc(); inc();
console.log(count);   // 2  ← 값 복사가 아니라 같은 변수
count = 5;            // TypeError: Assignment to constant variable

    CJS로 같은 것을 쓰면 const { count } = require('./counter')는 0을 복사해 와서 영원히 0입니다. ESM import는 읽기 전용 뷰입니다. 이것이 순환 참조에서 "나중에 채워지는 값"을 안전하게 볼 수 있는 이유이며, 동시에 모킹 도구들이 ESM에서 고생하는 이유입니다(바인딩을 바꿔치기할 수 없으므로 로더 훅이 필요).

    3.2 최상위 await(TLA)의 전파

    모듈 하나에 TLA가 있으면 V8은 그 모듈을 비동기 모듈로 표시하고, 그것을 import하는 모든 조상도 비동기로 평가합니다. 결과는 두 가지입니다.

    • 형제 모듈은 병렬 평가됩니다. import './a.mjs'; import './b.mjs'에서 a가 TLA로 기다리는 동안 b가 먼저 끝날 수 있습니다. 순서에 의존한 초기화(예: a가 DB 커넥션을 열고 b가 그걸 쓴다)는 깨집니다.
    • require()할 수 없습니다. require(esm)는 동기여야 하므로 TLA가 있는 그래프는 ERR_REQUIRE_ASYNC_MODULE을 던집니다(6절).
    • 영원히 resolve되지 않는 TLA는 프로세스를 조용히 종료시킵니다(Node 는 경고 "Detected unsettled top-level await"와 함께 exit code 13).
    권장 TLA는 진입점(main)에서만. 라이브러리나 공유 모듈에서 TLA를 쓰면 소비자의 로딩 그래프 전체를 비동기로 만들고 require 호환성을 잃습니다.

    4. 순환 참조: 부분 exports vs TDZ

    a → b → a 순환이 있을 때 두 로더는 완전히 다르게 행동합니다. CJS는 "지금까지 채워진 exports 객체"를 돌려주고, ESM은 "슬롯은 연결됐지만 값이 없는 바인딩"을 돌려줍니다.

    순환 참조 스텝 애니메이션
    같은 순환 구조를 CJS와 ESM으로 각각 로드할 때의 내부 상태 변화입니다. 실제 Node 22에서 검증한 출력과 같습니다.

    CJS에서 흔한 함정은 module.exports = { ... }로 객체를 통째로 교체하는 경우입니다. 순환 상대가 받은 것은 교체 전의 빈 exports 객체이므로, 나중에 채워져도 보이지 않습니다. exports.foo = ...처럼 기존 객체에 속성을 추가하면 나중에라도 보입니다(위 애니메이션의 a가 그 방식). 더 근본적인 해결은 순환을 끊는 것입니다. 보통 "두 모듈이 모두 필요로 하는 것"을 세 번째 모듈로 뽑아내면 됩니다. madge --circular src/ 같은 도구로 CI에서 순환을 탐지하세요.

    ESM에서는 순환이 있어도 함수 선언은 호이스팅되어 평가 전에도 호출 가능합니다. 문제가 되는 것은 let/const/class와 그 값을 모듈 최상위에서 즉시 쓰는 코드입니다. 에러 메시지가 "Cannot access 'x' before initialization"이면 거의 항상 순환입니다.

    5. 패키지 exports/imports 맵과 조건부 해석

    package.json의 "exports"는 패키지의 공개 API 표면을 선언합니다. 있으면 "main"은 무시되고, 선언되지 않은 경로는 require('pkg/lib/internal.js')처럼 접근할 수 없습니다. 이것이 라이브러리 작성자에게는 캡슐화를, 소비자에게는 "내부 파일 경로를 import했다가 패치 버전에서 깨지는" 사고의 종식을 의미합니다.

    {
  "name": "pkg",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",          // ① 조건은 "키 순서"대로 매칭된다. types는 항상 맨 앞
      "import": "./dist/index.js",           // ② import 또는 import() 로 로드될 때
      "require": "./dist/index.cjs",         // ③ require() 로 로드될 때
      "default": "./dist/index.js"           // ④ 항상 매칭되는 폴백. 반드시 마지막
    },
    "./feature": {
      "node": "./dist/feature-node.js",      // 런타임 조건: node / browser / deno ...
      "default": "./dist/feature.js"
    },
    "./utils/*": "./dist/utils/*.js",        // 서브패스 패턴. * 는 경로의 나머지 전체(/ 포함)
    "./internal/*": null,                    // 명시적 차단
    "./package.json": "./package.json"
  },
  "imports": {
    "#db": { "node": "./src/db-node.js", "default": "./src/db-mock.js" }   // 패키지 내부 전용 별칭
  }
}

    5.1 해석 규칙

    1. 서브패스 매칭: 정확히 일치하는 키 우선. 없으면 * 패턴 중 * 앞부분이 가장 긴 키(가장 구체적인 것)를 선택.
    2. 타깃 해석: 문자열이면 *를 치환해 끝. 배열이면 앞에서부터 유효한 첫 항목(잘못된 타깃을 건너뛰는 폴백용. 조건 폴백 아님). 객체면 키 순서대로 순회하며 조건 집합에 포함되거나 "default"인 첫 키로 재귀. null이면 "export되지 않음".
    3. 조건 집합: Node는 항상 ["node", "import" 또는 "require", "default"] + --conditions=로 추가한 것. 번들러는 browser, development/production, module 등을 추가. 객체 키 순서가 우선순위이고 조건 집합 순서는 무관합니다.
    4. 타깃은 ./로 시작해야 하고 패키지 밖(../)이나 node_modules를 가리키면 ERR_INVALID_PACKAGE_TARGET.
    exports 맵 조건 매처
    exports 객체, 요청 서브패스, 활성 조건을 바꾸면 선택되는 타깃과 탐색 경로를 보여줍니다. 알고리즘은 Node의 PACKAGE_EXPORTS_RESOLVE를 그대로 구현했습니다.
    exports (JSON)
    탐색 과정 (초록 = 선택, 취소선 = 조건 불일치로 건너뜀)
    exports 설계 체크리스트
    • "types" 조건을 맨 앞에, "default"를 맨 뒤에.
    • "./package.json": "./package.json"을 노출(도구들이 읽음).
    • 서브패스 패턴을 쓰더라도 "./internal/*": null로 내부를 명시적으로 차단.
    • 조건별 타깃이 서로 다른 모듈 인스턴스가 되지 않도록 설계(6절 dual package hazard).
    • npx publint, npx @arethetypeswrong/cli로 배포 전 검증.

    6. 상호운용: require(esm), import cjs, dual package hazard

    6.1 ESM에서 CJS import

    항상 가능했습니다. CJS 모듈의 module.exports가 default export가 되고, Node는 cjs-module-lexer로 소스를 정적 분석해 exports.foo = , Object.defineProperty(exports, 'foo', …), module.exports = { foo, bar } 같은 패턴을 찾아 named export도 제공합니다. 분석은 휴리스틱이므로 동적으로 만든 export(for (k of keys) exports[k] = …)는 named import가 실패하고 default를 통해야 합니다. 트랜스파일된 번들(esbuild, tsc 출력)은 lexer가 인식하는 패턴을 쓰므로 대체로 잘 됩니다.

    6.2 CJS에서 ESM: require(esm)

    Node 22.12와 20.19부터 플래그 없이 require()로 ESM을 로드할 수 있습니다(23.x에서 먼저 기본 활성화). 조건은 그래프에 TLA가 없을 것입니다. 반환값은 모듈 네임스페이스 객체([Symbol.toStringTag]: 'Module')이며, default export는 .default 속성으로 접근합니다(네임스페이스에 __esModule이 export돼 있으면 Babel 호환 규칙으로 default를 펼칩니다).

    // esm.mjs
export const x = 1; export default 'd';

// main.cjs
const m = require('./esm.mjs');
m.x;            // 1
m.default;      // 'd'
m[Symbol.toStringTag]; // 'Module'

// tla.mjs:  export const y = await fetchConfig();
require('./tla.mjs'); // ERR_REQUIRE_ASYNC_MODULE

    이 기능의 의미는 큽니다. ESM-only 라이브러리 생태계 이동이 CJS 앱을 깨뜨리지 않게 되었고, dual package를 배포할 이유가 줄었습니다. 2025년 이후 새 라이브러리는 ESM-only로 배포하고 CJS 소비자는 require(esm)에 기대는 흐름이 주류입니다.

    6.3 Dual package hazard

    해법은 세 가지입니다. ① ESM-only 배포(require(esm) 시대의 정답). ② 상태를 한쪽에만: ESM 래퍼가 CJS 구현을 import해 re-export하는 "CJS 우선 래퍼" 패턴(둘 다 같은 CJS 인스턴스를 공유). ③ 상태를 globalThis[Symbol.for('pkg.state')]에 두기(임시방편).

    7. 모듈 종류 판정과 TypeScript 타입 스트리핑

    Node가 파일을 CJS로 볼지 ESM으로 볼지는 확장자와 가장 가까운 package.json의 "type"으로 정합니다. Node 22.7부터는 "type"이 없을 때 구문 감지(import/export/import.meta가 있고 CJS 전용 식별자가 없으면 ESM)를 기본으로 수행합니다.

    모듈 종류 판정기
    파일 확장자, 가까운 package.json의 type, 플래그를 조합하면 Node가 어떤 로더를 쓰는지 보여줍니다.

    7.1 타입 스트리핑 (Node 22.6+ 실험, 23.6/22.18+ 기본)

    Node는 amaro(swc 기반)로 타입 주석만 공백으로 치환해 .ts를 직접 실행합니다. 핵심은 "트랜스파일이 아니다"라는 점입니다. 소스맵이 필요 없도록 위치를 보존하고, 타입 검사는 하지 않으며, 런타임 의미가 있는 TS 문법(enum, namespace, 파라미터 프로퍼티, 레거시 데코레이터)은 --experimental-transform-types를 켜야 합니다. 또 import './x.ts'처럼 확장자를 명시해야 하고('./x' 추론 없음), import type을 쓰거나 verbatimModuleSyntax를 켜서 타입 전용 import가 남지 않게 해야 합니다. node_modules 안의 .ts는 스트리핑하지 않습니다.

    운영 판단 개발·스크립트·테스트에는 좋지만, 프로덕션 배포는 여전히 빌드 단계에서 JS로 변환하는 것이 안전합니다. 타입 스트리핑은 Node 버전마다 세부 동작이 바뀌어 왔고(플래그 이름, 기본값), 콜드 스타트에 파싱 비용이 추가됩니다.

    8. 커스텀 로더 훅: module.register()

    Node 20.6+의 module.register(specifier, parentURL)는 별도 스레드에서 실행되는 훅을 등록합니다. 훅은 두 종류입니다. resolve(specifier, context, next)는 "어떤 URL로 갈지"를, load(url, context, next)는 "그 URL의 소스와 포맷"을 결정합니다. 체인 가능하고 next()로 다음 훅(기본 동작)에 위임합니다.

    // hooks.mjs
export async function resolve(specifier, context, next) {
  if (specifier.startsWith('@app/')) {                     // 경로 별칭
    return next(new URL(`./src/${specifier.slice(5)}.js`, import.meta.url).href, context);
  }
  return next(specifier, context);
}
export async function load(url, context, next) {
  if (url.endsWith('.yaml')) {                             // 새 포맷 지원
    const { source } = await next(url, { ...context, format: 'module' });
    return { format: 'module', shortCircuit: true,
             source: `export default ${JSON.stringify(parseYaml(String(source)))};` };
  }
  return next(url, context);
}

// register.mjs  (진입점보다 먼저: node --import ./register.mjs app.mjs)
import { register } from 'node:module';
register('./hooks.mjs', import.meta.url);
    • 훅은 별도 워커 스레드에서 돌므로 메인 스레드의 전역 상태를 볼 수 없습니다. 설정은 register(..., { data })와 initialize(data) 훅으로 전달합니다.
    • Node 22.15/23.5+에는 동기 훅 module.registerHooks()가 실험적으로 추가되어 메인 스레드에서 동기적으로 동작하며 require()도 가로챕니다. 훅 API는 아직 변동이 있으니 릴리스 노트를 확인하세요.
    • 용도: 계측(OpenTelemetry의 import-in-the-middle), 모킹(node:test의 mock.module()도 내부적으로 같은 메커니즘), 트랜스파일, 경로 별칭. CJS에서 흔히 쓰던 require.extensions 몽키패치의 공식 대체입니다.

    9. 모듈 캐시, 메모리, 핫 리로드

    require.cache(= Module._cache)는 공개 객체이고 삭제가 가능합니다. 그래서 "delete require.cache[path] 후 다시 require"로 핫 리로드를 구현한 코드가 많습니다. 문제는 세 가지입니다.

    • 구 모듈은 사라지지 않는다. 다른 모듈이 이미 받아 간 참조(클로저, 이벤트 리스너, 타이머)가 살아 있는 한 옛 인스턴스는 메모리에 남습니다. 반복하면 누수(11장).
    • ESM은 캐시 삭제 API가 없다. 모듈 맵은 V8 내부이며 의도적으로 노출하지 않습니다. 우회책인 import(url + '?t=' + Date.now())는 매번 새 모듈을 만들고 역시 옛것을 해제하지 못합니다.
    • 싱글턴 깨짐. 리로드된 모듈이 새 Map/EventEmitter를 만들면 이전 상태를 참조하는 코드와 분리됩니다.

    프로덕션에서 핫 리로드는 하지 마세요. 개발에서는 node --watch(Node 18.11+, 22에서 안정)가 프로세스를 통째로 재시작하는 올바른 방식입니다. 설정값처럼 "바뀌어야 하는 데이터"는 모듈이 아니라 데이터로 다루고, 모듈 로드 시점이 아니라 호출 시점에 읽으세요.

    메모리 측면에서는 모듈 수 자체가 부팅 시간과 힙에 직접 영향을 줍니다. node --cpu-prof로 부팅을 프로파일하면 큰 앱에서 모듈 로딩이 상당 비율을 차지합니다. 대책: lazy require(핸들러 안에서 로드), module.enableCompileCache(), 번들링(단일 파일은 syscall 수를 극적으로 줄임), 그리고 Node 22.6+의 --experimental-sea-config/스냅샷(1장).

    10. 현업 장애 사례

    사례 1: 패치 업데이트 후 ERR_PACKAGE_PATH_NOT_EXPORTED

    앱이 require('some-lib/lib/internal/parser')로 내부 파일을 직접 쓰고 있었는데, 라이브러리가 패치 버전에서 exports 맵을 추가하자 즉시 실패. semver상 patch였지만 "내부 경로"는 애초에 API가 아니었습니다. 교훈: 내부 경로 import는 CI에서 금지(eslint import/no-internal-modules), 락파일으로 버전 고정.

    사례 2: OpenTelemetry 계측이 조용히 빠짐

    앱을 ESM으로 전환하자 DB 호출 스팬이 사라짐. CJS에서는 require 몽키패치로 계측했지만 ESM의 live binding은 바꿔치기가 불가능. --import로 로더 훅(@opentelemetry/instrumentation의 ESM 지원)을 앱 코드보다 먼저 등록해야 하는데 진입점 안에서 등록해 이미 링크된 모듈은 계측되지 않음. 교훈: 로더 훅은 node --import ./otel.mjs app.mjs처럼 CLI에서.

    사례 3: 두 개의 "싱글턴" 커넥션 풀

    dual package로 배포된 ORM을 앱(ESM)과 레거시 플러그인(CJS)이 각각 로드해 커넥션 풀이 두 개 생김. 풀 크기 제한(10)이 실제로는 20이 되어 DB max_connections 초과. 진단: process.moduleLoadList나 힙 스냅샷에서 같은 클래스 이름이 두 경로로 보임. 해결: ESM-only 버전으로 업그레이드하고 플러그인은 require(esm).

    핵심 요약

    • CJS는 실행하며 연결(캐시 등록 → 래퍼 함수 실행), ESM은 파싱 → 링킹 → 평가의 3단계로 연결 후 실행.
    • CJS 해석: 코어 → 상대/절대(파일 → 디렉터리) → #imports → self → 조상 node_modules 순. 확장자 추론은 .js/.json/.node만.
    • 순환 참조: CJS는 부분 exports 객체, ESM은 TDZ ReferenceError. 해결은 순환 제거.
    • exports 맵은 공개 API 선언. 조건은 키 순서대로, types 먼저 default 마지막. 미선언 경로는 에러.
    • require(esm)(22.12+/20.19+)로 TLA 없는 ESM은 동기 로드 가능. 새 라이브러리는 ESM-only가 dual package hazard를 피하는 길.
    • 로더 훅 module.register()는 별도 스레드, --import로 앱보다 먼저. 타입 스트리핑은 타입만 지우며 enum 등은 transform 플래그 필요.
    • require.cache 삭제 기반 핫 리로드는 누수의 지름길. 개발은 --watch, 운영은 재시작.

    확인 문제

    /app/src/a.js에서 require('./util')을 호출했고 /app/src/util.mjs만 존재한다. 결과는?
    LOAD_AS_FILE은 X, X.js, X.json, X.node만 시도합니다. .mjs는 추론 대상이 아니므로 파일을 찾지 못하고, 디렉터리도 없으므로 MODULE_NOT_FOUND입니다.
    exports가 { ".": { "default": "./a.js", "import": "./b.js" } }일 때 ESM에서 import 'pkg'가 로드하는 파일은?
    조건 객체는 키 순서대로 순회하며 조건 집합에 포함되거나 "default"인 첫 키를 선택합니다. "default"는 항상 매칭되므로 먼저 나오면 뒤의 키는 절대 도달하지 않습니다. 에러는 아니지만 사실상 버그이고, publint가 경고합니다.
    ESM 순환 a.mjs ⇄ b.mjs에서 b가 평가 중 a의 export let x를 읽으면?
    링킹 단계에서 슬롯은 연결되었지만 a의 본문이 아직 평가되지 않아 x는 TDZ 상태입니다. "Cannot access 'x' before initialization". 단, export function은 호이스팅되어 호출 가능합니다.
    CJS 앱에서 require('esm-only-lib')가 ERR_REQUIRE_ASYNC_MODULE을 던진다. 가장 가능성 높은 원인은?
    require(esm)은 동기여야 하므로 그래프 어딘가에 TLA가 있으면 이 에러가 납니다. 버전이 낮으면 ERR_REQUIRE_ESM(구버전)이 납니다. 해결은 await import()로 전환하거나 라이브러리의 TLA 제거를 요청하는 것입니다.
    OpenTelemetry ESM 계측이 일부 모듈에만 적용된다. 원인으로 가장 적절한 것은?
    훅은 등록 이후의 resolve/load에만 개입합니다. 진입점 안에서 register()하면 진입점이 정적으로 import한 그래프는 이미 링크된 뒤입니다. node --import ./otel.mjs app.mjs로 앱보다 먼저 등록해야 합니다.

    실습 과제

    1. 해석 syscall 세기. 깊이 6단계의 디렉터리에서 존재하지 않는 패키지를 require하는 스크립트를 만들고 strace -e trace=stat,openat,newfstatat node app.js 2>&1 | grep node_modules | wc -l(macOS는 dtruss 또는 fs_usage)로 시도 횟수를 세세요. 기대: 조상 디렉터리 수 × (exports 확인 + 파일 4종 + 디렉터리) 규모의 호출. 같은 것을 번들된 단일 파일에서 측정해 비교하세요.
    2. 순환 참조 재현. 4절 애니메이션의 a.js/b.js, ea.mjs/eb.mjs를 그대로 만들어 실행하고, CJS에서 exports.loaded = true를 module.exports = { loaded: true }로 바꿨을 때 b가 보는 값이 어떻게 달라지는지 확인하세요. 기대: 객체 교체 시 b는 영원히 빈 객체를 봄.
    3. exports 맵 검증. 5절의 체크리스트대로 더미 패키지를 만들고 npm pack 후 npx publint와 npx @arethetypeswrong/cli --pack을 돌려 경고를 0으로 만드세요. 그다음 "default"를 맨 앞으로 옮겨 경고가 나는지 확인하세요.
    4. require(esm) 경계. TLA가 있는 ESM과 없는 ESM을 만들어 각각 require()하고 에러 코드를 확인하세요. 기대: 전자 ERR_REQUIRE_ASYNC_MODULE, 후자 성공 + [Symbol.toStringTag] === 'Module'.
