libuv 스레드풀과 I/O 모델

2장에서 이벤트 루프가 완료 통지만 받는다고 했습니다. 그렇다면 실제 일은 누가 하는가. 소켓은 커널이(epoll), 파일과 DNS와 무거운 암호 연산은 libuv의 워커 스레드 4개가 합니다. 이 장은 그 두 경로의 내부 구조, 각 경로가 포화되는 방식, 그리고 "스레드 4개"라는 숫자가 운영에서 만드는 장애를 다룹니다.

  • UV_THREADPOOL_SIZE를 언제 어떻게 조정해야 하는지, 그리고 조정해도 해결되지 않는 문제가 무엇인지 안다.

1. 두 가지 I/O 모델: 준비 통지 vs 완료 통지

운영체제가 비동기 I/O를 제공하는 방식은 크게 둘입니다.

준비 통지 (readiness)완료 통지 (completion)
대표Linux epoll, BSD/macOS kqueue, Solaris event portsWindows IOCP, Linux io_uring, POSIX AIO
커널이 알려주는 것"이 fd는 지금 읽으면(쓰면) 블로킹되지 않는다""네가 요청한 읽기가 끝났고 버퍼에 N바이트 있다"

핵심은 셋째 행입니다. Linux에서 "일반 파일은 epoll에 넣을 수 없다"(EPERM)는 사실이 파일 I/O에 스레드풀이 필요한 유일한 이유입니다. 소켓·파이프·TTY·eventfd·signalfd·inotify는 모두 epoll 가능하므로 스레드가 필요 없습니다. libuv는 두 모델 위에 하나의 콜백 API를 올려, Node 코드는 플랫폼을 모르게 합니다.

2. epoll 경로: 소켓은 스레드 없이 어떻게 비동기가 되나

libuv는 모든 fd를 uv__io_t라는 워처(watcher)로 감쌉니다. uv_read_start(socket)를 호출하면 libuv는 uv__io_start(loop, &w, POLLIN)으로 워처를 "관심 목록"에 넣고, 다음 poll 페이즈 직전에 epoll_ctl(ADD/MOD)로 커널에 반영합니다. epoll_wait가 "fd 7 읽기 가능"을 돌려주면, libuv는 워처의 콜백(uv__stream_io)을 호출하고, 그 안에서 메인 스레드가 직접 read(2)를 호출합니다. 소켓은 논블로킹 모드(O_NONBLOCK)이므로 데이터가 없으면 EAGAIN이 바로 돌아오고, libuv는 다시 기다립니다.

// libuv src/unix/stream.c uv__read() 요지
static void uv__read(uv_stream_t* stream) {
  int count = 32;                          // 한 번 깨어났을 때 최대 32회 read 시도
  while (stream->read_cb && (stream->flags & UV_HANDLE_READING) && count-- > 0) {
    stream->alloc_cb((uv_handle_t*)stream, 64 * 1024, &buf);   // Node: 64KiB 버퍼 할당 요청
    nread = read(uv__stream_fd(stream), buf.base, buf.len);
    if (nread < 0) {
      if (errno == EAGAIN || errno == EWOULDBLOCK) { /* 데이터 없음: 다시 epoll 대기 */ ... return; }
      ... // 에러 → read_cb(UV_E*)
    } else if (nread == 0) { uv__stream_eof(stream, &buf); return; }   // EOF
    else stream->read_cb(stream, nread, &buf);                       // → JS 'data' 이벤트
    if (nread < buf.len) return;      // 버퍼를 다 못 채웠으면 소켓이 비었다는 뜻
  }
}

이 코드에서 운영상 중요한 사실 세 가지가 나옵니다.

  • 한 소켓이 한 번 깨어났을 때 최대 32 × 64KiB = 2MiB까지 연속으로 읽는다. 대용량 업로드가 폭주하면 한 소켓이 poll 페이즈를 오래 점유할 수 있습니다(공정성 한계).
  • 읽기 버퍼는 매번 새로 할당된다. Node의 onStreamRead는 64KiB 풀 버퍼에서 슬라이스해 쓰지만, 'data' 핸들러가 청크를 오래 붙들면 그 64KiB 전체가 살아남습니다(11장 메모리 누수 패턴).
  • 쓰기는 먼저 동기 시도한다. uv_write는 uv__try_write로 즉시 write(2)를 시도하고, 커널 송신 버퍼가 차서 다 못 보낸 바이트만 큐에 넣고 POLLOUT을 기다립니다. socket.write()가 false를 돌려주는 시점(6장 백프레셔)이 바로 이 큐가 highWaterMark를 넘은 때입니다.

서버 소켓의 accept도 같은 구조입니다. listen 소켓이 읽기 가능 = 대기 중인 연결 있음. libuv는 accept4(SOCK_NONBLOCK)를 EAGAIN이 날 때까지 반복합니다. 그래서 연결 폭주 시 accept 루프 자체가 poll 페이즈를 점유할 수 있고, Node는 server.listen()의 backlog 기본값 511로 커널 대기열을 제한합니다.

level-triggered vs edge-triggered, 그리고 libuv의 선택

epoll은 두 모드를 제공합니다. level-triggered(LT)는 "읽을 데이터가 남아 있는 한 매번 알려줌", edge-triggered(ET)는 "상태가 변할 때 한 번만". libuv는 LT를 씁니다. 위 코드의 count = 32 제한이 가능한 이유입니다. 32번 읽고 중단해도 다음 epoll_wait가 다시 알려주기 때문입니다. ET였다면 EAGAIN까지 반드시 다 읽어야 하므로 공정성 제어가 어렵습니다. 대신 LT는 "처리하지 않은 fd가 매번 반환되는" 비용이 있어, 백프레셔로 읽기를 멈출 때는 uv_read_stop으로 관심 목록에서 빼야 합니다(socket.pause()가 하는 일).

3. 스레드풀 경로: 구조와 규칙

libuv 스레드풀(src/threadpool.c)은 놀랄 만큼 단순합니다. 프로세스 전체에 하나이고, 하나의 FIFO 큐와 조건 변수, 그리고 N개의 워커 스레드로 되어 있습니다. 메인 스레드가 uv__work_submit으로 작업을 큐에 넣고 uv_cond_signal로 워커를 깨웁니다. 워커는 작업의 work()(블로킹 함수)를 실행한 뒤, 루프의 완료 큐에 넣고 uv_async_send(&loop->wq_async)를 호출합니다. 이 async 핸들은 eventfd로 epoll에 등록되어 있어, 메인 루프가 poll 페이즈에서 깨어나 uv__work_done으로 완료 콜백(done())을 호출합니다. 즉 완료 콜백은 항상 메인 스레드의 poll 페이즈에서 실행됩니다.

3.1 크기와 초기화 규칙

  • 기본 4개. UV_THREADPOOL_SIZE 환경변수로 변경, 최대 1024(libuv MAX_THREADPOOL_SIZE). 0이나 음수면 1.
  • 스레드는 첫 작업 제출 시 지연 생성(uv_once(init_threads))됩니다. 이때 getenv("UV_THREADPOOL_SIZE")를 읽습니다. 따라서 process.env.UV_THREADPOOL_SIZE = 16을 메인 모듈 최상단에서 설정하면 보통 동작하지만, 그 전에 어떤 모듈이든 스레드풀을 건드렸다면(예: require 중 fs.readFile, dns.lookup) 무시됩니다. 안전한 방법은 프로세스 실행 전 환경변수입니다.
  • 워커 스레드(worker_threads)도 같은 풀을 공유합니다. 워커 8개가 각각 fs를 열심히 써도 스레드풀은 여전히 4개입니다.
  • 워커 스택은 libuv 기본(플랫폼 기본, Linux 8MB 가상)이며 실제 상주 메모리는 작습니다. 스레드 수를 64로 늘려도 메모리 비용은 미미하고, 문제는 CPU 코어 수를 초과하는 CPU 작업의 컨텍스트 스위칭입니다.

3.2 slow I/O 제한: dns.lookup은 4개가 아니라 2개

libuv는 작업을 세 종류로 표시합니다: UV__WORK_CPU(uv_queue_work: crypto, zlib, 애드온), UV__WORK_FAST_IO(fs 작업), UV__WORK_SLOW_IO(getaddrinfo, getnameinfo). SLOW_IO는 "얼마나 걸릴지 모르는" 작업으로 취급되어 동시 실행 수가 (nthreads + 1) / 2로 제한됩니다. 기본 4개 풀에서는 2개입니다. 나머지 슬롯은 fs와 CPU 작업을 위해 남겨 두는 것입니다. 이 규칙 덕분에 느린 DNS 서버 하나가 풀 전체를 점유하는 최악은 피하지만, 반대로 dns.lookup 동시성은 풀 크기의 절반을 넘지 못합니다. 호출 수백 개가 밀리면 각각 "앞선 2개가 끝날 때까지" 줄을 섭니다.

제출 순서가 곧 완료 순서는 아니다 큐는 FIFO지만 slow I/O가 제한에 걸리면 마커가 큐 뒤로 밀리고, 뒤에 들어온 fs 작업이 먼저 실행됩니다. 또 워커 4개가 병렬이므로 같은 종류라도 짧은 작업이 먼저 끝납니다. fs.readFile 두 번을 연달아 호출했을 때 둘째가 먼저 완료될 수 있고, 이것이 "파일 쓰기 순서"에 의존한 코드가 간헐적으로 깨지는 이유입니다. 순서가 중요하면 직렬화(await 체인)하세요.

4. fs.readFile 한 번의 여정

fs.readFile(path, cb) 하나가 실제로는 스레드풀 왕복을 여러 번 합니다. 아래 애니메이션으로 따라가 보세요.

readFile 여정 스텝 애니메이션
4KiB 파일 하나를 읽는 경우. 각 단계가 메인 스레드인지, 워커인지, 커널인지를 색으로 구분합니다.

왕복 하나의 비용은 작업 자체(캐시된 4KiB 읽기 ≈ 수 µs)보다 스레드 간 핸드오프(mutex·cond·eventfd·epoll 왕복, 수십 µs)가 큽니다. 그래서 작은 파일을 많이 읽는 워크로드(모듈 로딩, 템플릿)에서는 readFileSync가 오히려 빠르고, Node 자체도 require에 동기 읽기를 씁니다. 반대로 큰 파일은 청크 왕복이 여러 번이지만 각 왕복이 실제 디스크 시간을 숨겨 주므로 비동기가 맞습니다.

장애 메커니즘: 회사 DNS가 느려져 getaddrinfo가 5초씩 걸리면, 아웃바운드 HTTP 요청마다 스레드풀 슬롯(최대 2개)을 5초간 점유 → 세 번째 요청부터 큐 대기 → 그 뒤에 들어온 fs.readFile, pbkdf2, 심지어 zlib까지 줄을 섭니다. 증상은 "DNS와 무관해 보이는 파일 읽기 API가 느려짐"으로 나타나 원인 파악이 어렵습니다. 반대로 fs 폭주가 dns.lookup을 지연시켜 "외부 호출 타임아웃"으로 보이기도 합니다.

대응 (우선순위 순):

  1. 아웃바운드 HTTP에 이름 해석 캐시를 둔다. undici/http.Agent의 lookup 옵션에 캐시 구현(예: cacheable-lookup)을 꽂거나, 업스트림을 IP/서비스 메시 사이드카로 고정.
  2. keep-alive로 연결을 재사용해 해석 횟수 자체를 줄인다(12장). 연결당 한 번이면 DNS는 거의 문제가 되지 않습니다.
  3. dns.lookup에 의존하지 않아도 되면 dns.resolve4로 바꾼다. 단, /etc/hosts와 OS 캐시를 잃으므로 컨테이너·k8s 환경에서 서비스 디스커버리 규칙을 확인해야 합니다.
  4. UV_THREADPOOL_SIZE를 올린다. 임시방편이며 slow I/O 제한(절반)은 여전히 적용됩니다.
Node 20+ Happy Eyeballs net.connect는 기본으로 autoSelectFamily: true(Node 20부터 기본)를 적용해 IPv6/IPv4 주소를 autoSelectFamilyAttemptTimeout(기본 250ms) 간격으로 번갈아 시도합니다. "IPv6가 라우팅되지 않는 환경에서 요청이 정확히 N초 느려진다"는 과거 증상은 이 기능으로 대부분 사라졌지만, 로그에 ECONNREFUSED ::1이 섞여 보이는 것은 정상입니다.

8. stdio·파이프·TTY의 특이점

process.stdout과 process.stderr는 fd 1, 2가 무엇에 연결되어 있느냐에 따라 완전히 다른 스트림 클래스로 만들어지고, 쓰기의 동기/비동기 여부도 달라집니다. 공식 문서의 표를 옮기면:

fd 1의 종류클래스Linux/macOSWindows비고
파일 (node app.js > out.log)fs.SyncWriteStream동기동기디스크가 느리면 console.log가 루프를 막는다
TTY (터미널)tty.WriteStream동기비동기터미널이 느리면(원격 ssh) 블로킹
파이프/소켓 (node app.js | …, Docker 로그 드라이버, PM2)net.SocketLinux 동기 / macOS 비동기동기Linux 파이프 버퍼 64KiB가 차면 블로킹

즉 리눅스 프로덕션에서 console.log는 사실상 항상 동기입니다. 로그 수집기가 파이프 반대편을 느리게 읽으면 64KiB 버퍼가 차는 순간 write(2)가 블로킹되고 이벤트 루프가 멈춥니다. "로그를 많이 찍었더니 서비스가 느려졌다"의 정체이고, 15장의 pino 비동기 transport(워커 스레드로 로그를 넘김)가 해법입니다. 반대로 이 동기성 덕에 process.exit() 직전의 로그가 유실되지 않는 장점도 있습니다(macOS 파이프 제외).

process.stdin도 마찬가지로 TTY면 tty.ReadStream(raw 모드 가능), 파이프면 net.Socket, 파일이면 fs.ReadStream(스레드풀)입니다. stdin이 TTY일 때 process.stdin.on('data')를 붙이는 순간 핸들이 ref되어 프로세스가 종료되지 않는 것도 자주 묻는 현상입니다.

9. io_uring과 스레드풀의 미래

Linux 5.1에서 도입된 io_uring은 파일 I/O에도 완료 모델을 제공합니다. libuv 1.45(2023)가 fs 작업 일부(read/write/fsync/stat/open/close 등)를 io_uring으로 처리하는 지원을 넣었고, Node 20.3이 이를 포함하면서 파일 I/O가 스레드풀을 거치지 않게 되었습니다. 벤치마크에서 파일 읽기 처리량이 눈에 띄게 올랐습니다.

그러나 2024년 2월, io_uring 사용 시 process.setuid() 등이 워커에 전파되지 않는 권한 관련 취약점(CVE-2024-22017)이 보고되었고, Node는 io_uring을 기본 비활성으로 되돌렸습니다(Node 20.11.1 / 21.6.2부터). Node 22도 기본 비활성입니다. 명시적으로 켜려면:

$ UV_USE_IO_URING=1 node app.js      # libuv 1.45+, 커널 5.10 이상 권장. setuid 류를 쓰지 않는 서비스만.

켜면 fs 작업이 스레드풀 큐에서 빠지므로, 이 장에서 본 "DNS가 fs를 막는다"류 간섭이 fs 쪽에서는 사라집니다. 단 io_uring은 커널 버전·컨테이너 보안 프로파일(seccomp에서 io_uring_* syscall 차단이 흔함)에 민감하므로, 켠 뒤 실제로 사용되는지(strace -e io_uring_enter)를 확인해야 합니다. 향후 기본값이 바뀔 수 있으니 버전 릴리스 노트를 확인하세요.

10. 측정과 튜닝, 현업 장애 사례

10.1 스레드풀 대기 시간 측정

libuv는 스레드풀 큐 길이를 직접 노출하지 않습니다. 실용적 방법은 프로브입니다. 아주 작은 스레드풀 작업을 주기적으로 던지고 왕복 시간을 재면, 그 값이 곧 "큐 대기 + 핸드오프"입니다.

const { randomBytes } = require('node:crypto');
const { monitorEventLoopDelay } = require('node:perf_hooks');
const loopDelay = monitorEventLoopDelay({ resolution: 20 }); loopDelay.enable();

setInterval(() => {
  const t0 = process.hrtime.bigint();
  randomBytes(1, () => {                       // 스레드풀 CPU 작업 1건
    const tpMs = Number(process.hrtime.bigint() - t0) / 1e6;
    const loopMs = loopDelay.percentile(99) / 1e6;
    // tpMs - loopMs 가 크면 루프가 아니라 스레드풀이 밀린 것
    metrics.observe('threadpool_probe_ms', tpMs);
  });
}, 1000).unref();

루프 지연(2장)과 함께 보아야 합니다. 프로브가 느린데 루프 지연이 정상이면 스레드풀 포화, 둘 다 느리면 메인 스레드 블로킹입니다. 어떤 작업이 풀을 점유하는지는 async_hooks로 FSREQCALLBACK, GETADDRINFOREQWRAP, PBKDF2REQUEST, ZLIB 리소스의 init→destroy 시간을 집계하면 종류별로 보입니다(7장).

10.2 UV_THREADPOOL_SIZE 결정 규칙

  • I/O 지배 워크로드(fs, dns): 코어 수와 무관하게 늘려도 됩니다. 디스크 큐 깊이·DNS 동시성에 맞춰 8~32. 각 워커가 커널 대기만 하므로 CPU 경합이 없습니다.
  • CPU 지배 워크로드(pbkdf2, zlib, sharp): 코어 수 이상은 무의미하며 컨텍스트 스위치로 오히려 느려집니다. 컨테이너라면 cgroup CPU 할당량(예: 2 vCPU)이 상한. 더 필요하면 프로세스를 늘리세요(9장).
  • 워커 스레드(worker_threads)를 N개 띄우면 풀을 공유하므로, 워커당 fs 사용량을 합산해 결정합니다.
  • 변경 후 반드시 10.1의 프로브로 효과를 확인합니다. 효과가 없으면 병목이 풀이 아닙니다.
사례 1: 로그인 폭주와 썸네일

로그인 API가 bcrypt.hash(네이티브 애드온, 스레드풀 CPU 작업, 건당 ~80ms)를 씁니다. 마케팅 푸시로 로그인이 초당 50건이 되자, 같은 프로세스의 이미지 썸네일(sharp, 역시 스레드풀) 생성과 정적 파일 fs.readFile이 수 초씩 밀렸습니다. 스레드풀 4개 × 80ms = 초당 50건이 상한인데 그 상한을 로그인이 전부 썼기 때문입니다. 대응: 해시 cost 인자 재검토, 로그인 전용 프로세스 분리, UV_THREADPOOL_SIZE=16(코어 8개 머신). 교훈: 스레드풀은 서로 무관한 기능이 공유하는 단일 큐라는 점을 설계에 반영해야 합니다.

사례 2: NFS 위의 readFileSync

설정 파일을 요청마다 fs.readFileSync로 읽는 핸들러. 로컬 디스크에서는 50µs라 문제없었지만, 스토리지가 NFS로 바뀌자 네트워크 지연이 끼어 수십 ms씩 메인 스레드가 멈췄습니다. 비동기로 바꿔도 스레드풀이 NFS 지연에 점유됩니다. 올바른 대응은 "요청 경로에서 파일을 읽지 않는 것"(부팅 시 로드 + fs.watch로 갱신)이었습니다.

사례 3: 테스트에서만 실패하는 순서 의존

fs.writeFile(a); fs.writeFile(b); 뒤에 b의 존재를 전제로 a를 처리하는 코드. 로컬에서는 항상 a가 먼저 끝났지만 CI(느린 디스크, 다른 테스트의 스레드풀 사용)에서 간헐 실패. 스레드풀은 4개가 병렬이므로 완료 순서는 보장되지 않습니다. await 직렬화로 해결.

핵심 요약

  • 소켓·파이프·TTY는 epoll(readiness)로 메인 스레드가 직접 read/write. 스레드 0개. 일반 파일은 epoll이 불가능해 스레드풀이 필요하다.
  • libuv 스레드풀: 프로세스에 하나, 단일 FIFO 큐, 기본 4개(최대 1024, 첫 사용 전 UV_THREADPOOL_SIZE), 완료는 wq_async로 poll 페이즈에서 콜백. worker_threads도 공유.
  • slow I/O(getaddrinfo)는 동시 ⌈N/2⌉개로 제한. 기본 풀에서 dns.lookup 동시성은 2.
  • 풀 사용: fs 비동기, dns.lookup, crypto 비동기(pbkdf2·scrypt·randomBytes·WebCrypto), zlib 비동기, 많은 네이티브 애드온. 비사용: net/http/tls(TLS 연산은 메인 동기!), 모든 Sync, createHash.
  • readFile 하나 = open + fstat + read×청크 + close 왕복. 작은 파일 다수는 Sync가 빠를 수 있고, 큰 파일은 스트림.
  • Linux 프로덕션에서 stdout(파일·TTY·파이프)은 동기. 로그 폭주 = 루프 블로킹.
  • io_uring은 Node 20.3에서 켜졌다가 CVE로 기본 비활성(UV_USE_IO_URING=1로 옵트인).
  • 진단: 스레드풀 프로브(randomBytes 왕복) + 루프 지연을 함께 본다. 튜닝: I/O 지배면 풀을 키우고, CPU 지배면 프로세스를 늘린다.

확인 문제

Linux에서 일반 파일 읽기가 libuv 스레드풀을 거치는 근본 이유는?
epoll은 readiness 모델이고 일반 파일은 항상 '준비됨'으로 취급되어 등록 자체가 거부됩니다(EPERM). 블로킹을 숨길 유일한 방법이 다른 스레드에서 호출하는 것입니다(io_uring 제외).
기본 설정(풀 4개)에서 dns.lookup 10건이 동시에 제출되면 동시에 실행되는 최대 건수는?
getaddrinfo는 UV__WORK_SLOW_IO로 분류되어 (nthreads+1)/2 = 2개까지만 동시에 실행됩니다. 나머지 슬롯은 fs·CPU 작업용으로 남습니다.
HTTPS 서버에서 TLS 핸드셰이크 폭주 시 이벤트 루프 지연이 치솟는 이유는?
TLS는 스레드풀을 쓰지 않습니다. 모든 암호 연산이 루프 시간입니다. 프록시/로드밸런서에서 TLS를 종단하거나 세션 재개(resumption)로 핸드셰이크 비용을 줄입니다.
Linux 컨테이너에서 stdout이 Docker 로그 드라이버 파이프에 연결되어 있다. 로그 수집이 느려지면?
Linux에서 파이프로의 stdout 쓰기는 동기입니다. pino 비동기 transport처럼 워커 스레드로 로그를 넘기는 구조가 해법입니다(15장).
메인 모듈 첫 줄에 process.env.UV_THREADPOOL_SIZE = '32'를 썼는데 효과가 없다. 가장 가능성 높은 이유는?
스레드풀은 첫 작업 제출 시 한 번만 초기화되며 그때 환경변수를 읽습니다. 프리로드 모듈이나 require 체인에서 fs 비동기/dns.lookup 등을 썼다면 이미 늦습니다. 프로세스 실행 전 환경변수로 설정하세요.

실습 과제

  1. 간섭 재현. 아래 스크립트를 UV_THREADPOOL_SIZE 4와 16으로 각각 실행해 readFile 지연을 비교하세요. 기대: 4에서는 readFile이 pbkdf2 완료 후에야 끝나 수백 ms, 16에서는 수 ms. 
    const crypto = require('node:crypto'), fs = require('node:fs');
for (let i = 0; i < 8; i++) crypto.pbkdf2('pw', 'salt', 300_000, 64, 'sha512', () => {});
const t = performance.now();
fs.readFile(__filename, () => console.log('readFile took', (performance.now() - t).toFixed(1), 'ms'));
  2. slow I/O 제한 관찰. 존재하지 않는 DNS 서버를 가리키도록(/etc/resolv.conf를 건드리지 말고, 네트워크 차단 혹은 느린 리졸버로 흉내) dns.lookup 6건을 동시에 던지고 각 완료 시각을 찍어 보세요. 기대: 완료가 2건씩 묶여서 일어남(타임아웃 길이마다 2건). dns.resolve4 6건은 동시에 완료됨.
  3. stdout 동기성 확인. node -e "for(let i=0;i<1e5;i++)console.log('x'.repeat(100))" | (sleep 5; cat > /dev/null)을 Linux에서 실행하고 node 프로세스가 5초간 블로킹되는지(time으로) 확인하세요. macOS에서는 비동기라 즉시 종료되지 않을 수 있지만 메모리에 버퍼링됩니다.
