1. Promise의 실체: V8 안에서

Promise는 Node.js의 것이 아니라 V8의 것입니다. JSPromise 객체는 상태(pending/fulfilled/rejected), 결과값, 그리고 반응(PromiseReaction) 연결 리스트를 가집니다. p.then(f, r)은 반응 하나를 리스트에 추가하고 새 Promise를 돌려줄 뿐, 아무것도 실행하지 않습니다. p가 결정(settle)되는 순간 V8은 각 반응을 PromiseReactionJob으로 바꿔 isolate의 MicrotaskQueue에 넣습니다. 이미 결정된 Promise에 then을 붙이면 반응은 리스트를 거치지 않고 바로 잡이 됩니다.

이 큐를 비우는 것은 V8의 MicrotaskQueue::RunMicrotasks()이고, Node는 2장에서 본 processTicksAndRejections에서 runMicrotasks()로 호출합니다. 즉 "마이크로태스크 큐"는 V8 소유, "언제 비울지"는 Node 소유입니다. 잡 하나는 콜백 하나를 호출하고, 그 반환값으로 파생 Promise를 resolve합니다. 여기서 틱 수가 갈리는 분기가 하나 있습니다.

3. async 스택 트레이스

    
콜백 시절의 스택 트레이스는 "어느 이벤트 루프 콜백에서 시작했는가"만 보여 줬습니다. Promise 체인에서는 then 콜백이 마이크로태스크 잡에서 호출되므로 호출자 정보가 사라집니다. V8 7.3(Node 12)부터는 zero-cost async stack traces가 기본입니다: 에러를 만들 때 V8이 현재 async 함수의 "await 중인 외부 함수"를 Promise 반응 체인을 따라 거꾸로 걸어 올라가며 at async outer (file:line) 프레임을 합성합니다. 실행 중 비용이 없고(기록을 안 함) 에러 생성 시에만 비용이 듭니다.

    

      
return promise: 중간 함수가 사라짐
async function load() { return db.query(); } // await 없음
async function handler() { return await load(); }
// Error: ...
//   at Query.run (db.js:40)
//   at async handler (app.js:12)   ← load가 없다

      
return await: 체인이 보존됨
async function load() { return await db.query(); }
async function handler() { return await load(); }
// Error: ...
//   at Query.run (db.js:40)
//   at async load (app.js:5)       ← 남아 있다
//   at async handler (app.js:12)

    

    
이 합성은 await 체인에서만 동작합니다. .then() 체인, setTimeout, 이벤트 핸들러를 거치면 끊깁니다. 그런 경계에서는 Error.captureStackTrace로 호출 시점 스택을 미리 잡아 두거나, 10장에서 다룰 프로파일러처럼 async_hooks 기반 도구가 필요합니다. --async-stack-traces 플래그는 기본 on이며 끄면 성능 차이는 거의 없습니다.

  


  

    
4. unhandledRejection: 감지 시점과 모드

    
Promise가 거부되었는데 그 시점에 거부 핸들러(then의 두 번째 인자, catch)가 없으면 V8은 Node에 PromiseRejectWithNoHandler 훅으로 알립니다. 나중에 핸들러가 붙으면 PromiseHandlerAddedAfterReject로 다시 알립니다. Node는 이 알림을 모았다가 processTicksAndRejections의 do-while 끝에서(2장) processPromiseRejections()로 처리합니다. 즉 판정 시점은 "거부된 직후"가 아니라 "그 드레인의 마이크로태스크가 모두 끝난 뒤"입니다. 같은 드레인 안에서 catch를 붙이면 안전하고, 다음 매크로태스크(setTimeout)에서 붙이면 늦습니다.

5. 조합기의 실패 의미론

    

      
조합기결정 조건실패 시나머지 작업은?

      
Promise.all전부 fulfilled하나라도 reject → 즉시 reject (첫 번째 이유)계속 실행된다. 결과는 버려지고, 각자의 거부는 all이 이미 핸들러를 달았으므로 unhandled가 되지 않음

      
Promise.allSettled전부 결정reject 안 함. {status, value|reason} 배열전부 기다림

      
Promise.any하나라도 fulfilled전부 reject → AggregateError(errors 배열)첫 성공 후에도 계속 실행

      
Promise.race첫 결정 (성공/실패 무관)첫 번째가 reject면 reject계속 실행. 타임아웃 구현 시 타이머는 unref/clear 필요

    

    
표의 마지막 열이 운영에서 중요합니다. Promise.all로 DB 쿼리 다섯 개를 보내고 하나가 실패해 요청이 500으로 끝나도, 나머지 네 쿼리는 DB에서 계속 돕니다. 트래픽이 높을 때 이것이 커넥션 풀과 DB CPU를 낭비하고 장애를 증폭시킵니다. 해결은 6절의 취소입니다. 실패가 발생하면 같은 AbortSignal을 공유하는 나머지 작업을 abort합니다.


// 하나가 실패하면 나머지를 취소하는 all
async function allOrAbort(signal, tasks) {
  const ac = new AbortController();
  const onAbort = () => ac.abort(signal.reason);
  signal?.addEventListener('abort', onAbort, { once: true });
  try {
    return await Promise.all(tasks.map(t => t(ac.signal).catch(err => { ac.abort(err); throw err; })));
  } finally { signal?.removeEventListener('abort', onAbort); }
}

  


  

    
6. 취소: AbortSignal

    
Promise에는 취소가 없습니다. 대신 Node는 웹 표준 AbortController/AbortSignal을 모든 비동기 API에 받아들이는 방향으로 통일했습니다(Node 15+). 취소는 협조적(cooperative)입니다: signal을 받은 쪽이 확인하고 멈춰야 합니다.


const { setTimeout: sleep } = require('node:timers/promises');
const { once } = require('node:events');

const signal = AbortSignal.timeout(5_000);                     // 5초 뒤 자동 abort (TimeoutError)
const merged = AbortSignal.any([signal, req.signal]);          // Node 20.3+: 여러 신호 합치기

await fetch(url, { signal: merged });                          // undici fetch
await sleep(1000, undefined, { signal: merged });              // timers/promises
await once(emitter, 'ready', { signal: merged });              // events.once
await pipeline(src, dst, { signal: merged });                  // stream
fs.readFile(path, { signal: merged });                         // fs
child_process.spawn(cmd, args, { signal: merged });            // 자식 프로세스 kill

// 직접 만드는 취소 가능 작업
async function poll(signal) {
  while (true) {
    signal.throwIfAborted();                                   // 루프마다 확인 (Node 17.3+)
    await doStep();
    await sleep(100, undefined, { signal });                   // 대기 중에도 즉시 깨어남
  }
}

    
    
      
  • abort된 작업은 AbortError(err.name === 'AbortError', code 'ABORT_ERR')로 거부됩니다. AbortSignal.timeout은 TimeoutError. 로깅에서 이 둘은 "예상된 실패"로 분류하세요.
    • 
      
  • signal에 리스너를 붙였으면 작업 완료 시 반드시 제거하세요. 오래 사는 signal(요청 signal)에 짧은 작업들이 리스너를 누적시키면 MaxListenersExceededWarning과 메모리 누수가 납니다. { once: true } + 완료 시 removeEventListener, 또는 events.addAbortListener(Node 20+)가 돌려주는 disposer 사용.
    • 
      
  • HTTP 서버에서 클라이언트가 끊으면 req의 'close'/'aborted'로 알 수 있습니다. 이를 AbortController에 연결해 하류 호출을 끊는 것이 "클라이언트는 이미 떠났는데 서버는 30초 동안 일하는" 낭비를 막는 기본 패턴입니다(18장).
    • 
    

  


  

    
7. async_hooks: 비동기 자원의 생명주기

    
Node의 모든 비동기 작업은 내부적으로 비동기 자원(async resource)입니다. 타이머(Timeout), TCP 핸들(TCPWRAP), 파일 요청(FSREQCALLBACK), nextTick(TickObject), 그리고 Promise(PROMISE). 각 자원은 고유한 asyncId와, 그 자원을 만든 실행 컨텍스트의 id인 triggerAsyncId를 가집니다. async_hooks.createHook은 자원의 네 시점에 콜백을 끼웁니다.

    

      
훅시점인자

      
init(asyncId, type, triggerAsyncId, resource)자원 생성 시 (동기적으로, 만든 곳의 컨텍스트에서)type은 'Timeout', 'PROMISE', 'TCPWRAP' 등

      
before(asyncId)자원의 콜백이 실행되기 직전이때 executionAsyncId()가 asyncId가 됨

      
after(asyncId)콜백이 끝난 직후-

      
destroy(asyncId)자원이 파괴될 때 (GC 또는 명시적 close)Promise는 GC 시점이라 늦게/안 올 수 있음

      
promiseResolve(asyncId)Promise가 resolve될 때Promise 전용

    


// 실제 출력 (Node 22): 컨텍스트 id의 연쇄
const ah = require('node:async_hooks');
ah.createHook({ init(id, type, trigger) { fs.writeSync(1, `init ${type} id=${id} trigger=${trigger}\n`); } }).enable();
console.log('exec', ah.executionAsyncId());          // exec 1  (메인 모듈 = 1)
setTimeout(() => {
  fs.writeSync(1, `in timeout exec=${ah.executionAsyncId()} trig=${ah.triggerAsyncId()}\n`);
  Promise.resolve().then(() => {});
}, 1);
// init TickObject id=2 trigger=1      ← console.log가 내부적으로 nextTick 사용
// init Timeout id=3 trigger=1         ← setTimeout, 메인(1)에서 생성
// in timeout exec=3 trig=1            ← 콜백 실행 중엔 executionAsyncId가 타이머의 id
// init PROMISE id=4 trigger=3         ← Promise.resolve(), 타이머 콜백(3) 안에서 생성
// init PROMISE id=5 trigger=4         ← .then()이 만든 파생 Promise

    
비용: Promise 훅은 모든 Promise를 느리게 한다
      훅을 하나라도 enable하면(특히 init이 있으면) V8의 Promise 훅이 켜져 모든 Promise 생성·resolve·then마다 JS 콜백이 호출됩니다. await 하나에 Promise가 두세 개 생기므로, Promise가 많은 코드는 수십 % 느려질 수 있습니다. APM 에이전트가 성능을 떨어뜨리는 주원인이 이것입니다. 훅 안에서 console.log를 쓰면 nextTick 자원이 생겨 무한 재귀하므로 fs.writeSync를 써야 하는 것도 같은 이유입니다. 직접 쓸 일은 거의 없고, 8절의 AsyncLocalStorage가 훅 없이 같은 목적을 달성합니다.
    

  


  

    
8. AsyncLocalStorage와 컨텍스트 전파

    
AsyncLocalStorage(ALS)는 "이 비동기 흐름에 속하는 값"을 전역 변수 없이 들고 다니는 도구입니다. 요청 ID, 사용자, 트레이스 컨텍스트(15장의 OpenTelemetry가 이것으로 동작), 테넌트, 트랜잭션 핸들이 전형적인 내용물입니다.


const { AsyncLocalStorage } = require('node:async_hooks');
const als = new AsyncLocalStorage();

app.use((req, res, next) => {
  als.run({ reqId: crypto.randomUUID(), user: null }, () => next());   // 이 안에서 시작된 모든 비동기 흐름에 보임
});
// 어디서든 (인자로 안 넘겨도)
function log(msg) { const ctx = als.getStore(); console.log(JSON.stringify({ reqId: ctx?.reqId, msg })); }

    
8.1 전파 규칙

    
규칙은 하나입니다. 비동기 자원이 생성될 때 현재 스토어가 그 자원에 붙고, 그 자원의 콜백은 그 스토어를 본다. run() 안에서 만든 타이머, Promise, 소켓, 파일 요청은 모두 스토어를 물려받고, 그 콜백 안에서 만든 자원도 또 물려받습니다. 반대로 run() 밖에서(부팅 시) 만든 자원의 콜백에서는 스토어가 보이지 않습니다. 설령 그 콜백을 요청이 "유발"했더라도요. 이것이 9절의 유실 시나리오 전부를 설명합니다.

    

      
API용도

      
als.run(store, fn, ...args)fn과 그 안에서 시작된 비동기 흐름에 store 적용. 중첩 가능(안쪽이 이김).

      
als.getStore()현재 스토어. 밖이면 undefined.

      
als.enterWith(store)현재 동기 실행의 나머지와 이후 흐름에 적용. run보다 범위 통제가 어려워 미들웨어 안의 run을 권장.

      
als.exit(fn)fn 동안 스토어 없음(예: 요청과 무관한 백그라운드 작업 시작).

      
AsyncLocalStorage.bind(fn) / als.run + AsyncResource.bind지금의 컨텍스트를 함수에 고정. 콜백을 "다른 컨텍스트에서 나중에" 부르는 라이브러리에 넘길 때.

      
AsyncLocalStorage.snapshot() (Node 19.8+)현재 컨텍스트를 캡처한 함수 반환. snap(() => als.getStore())로 나중에 복원.

      
new AsyncResource(type) + runInAsyncScope큐, 풀처럼 "자원 생성과 콜백 실행이 다른 컨텍스트"인 구조에서 수동 전파.

      
EventEmitterAsyncResourceemit을 항상 생성 시 컨텍스트에서 하는 EventEmitter.

    

    
8.2 구현의 변화: async_hooks에서 AsyncContextFrame으로

    
원래 ALS는 async_hooks 위에 구현되어, ALS 인스턴스가 하나라도 있으면 Promise 훅이 켜지고 7절의 비용이 발생했습니다. Node 22.7에 --experimental-async-context-frame이 추가되었고, Node 24부터는 AsyncContextFrame 기반이 기본입니다(V8의 continuation-preserving embedder data 활용). 자원마다 훅을 부르는 대신 "현재 컨텍스트 프레임" 포인터를 Promise 반응과 콜백에 붙여 넘기므로 오버헤드가 크게 줄었습니다. 의미론은 같지만 미묘한 경계(예: enterWith의 범위)가 달라질 수 있으니 Node 24로 올릴 때 컨텍스트 전파 테스트를 돌려 보세요.

    9.1 수정 패턴
    
    
    
      
    
      
    // 부팅 시 만든 풀의 소켓이 콜백을 부르면 스토어가 없다.
// 해결 1: 콜백을 지금 컨텍스트에 바인딩
pool.query(sql, AsyncResource.bind((err, rows) => { log('done'); }));
// 해결 2: Promise API로 감싸면 await 이후는 run() 컨텍스트에서 재개된다 (Promise 반응이 run 안에서 생성됨)
const rows = await pool.query(sql);   // 이후 코드에서 getStore() 정상
    
      
    두 번째가 중요합니다. await 뒤의 코드는 await를 호출한 컨텍스트에서 재개됩니다. Promise 반응(= 비동기 자원)이 run() 안에서 만들어졌기 때문입니다. 그래서 async/await 코드는 콜백 코드보다 컨텍스트 유실이 훨씬 적습니다. 콜백 기반 라이브러리를 util.promisify로 감싸는 것만으로 대부분의 유실이 사라집니다.
    
      
    const { EventEmitterAsyncResource } = require('node:events');
// 핸들러는 emit한 쪽이 아니라 "emitter를 만든 쪽" 컨텍스트에서 실행된다
const em = new EventEmitterAsyncResource({ name: 'JobEvents' });   // run() 안에서 생성해야 의미 있음
// 또는 핸들러 등록 시 바인딩
em.on('data', AsyncResource.bind(handler));
    
      
    EventEmitter의 emit은 동기 호출입니다. 핸들러는 emit을 호출한 컨텍스트에서 실행됩니다. 소켓 'data' 이벤트는 소켓 자원의 콜백에서 emit되므로, 소켓이 요청 밖에서 만들어졌다면 스토어가 없습니다.
    
      
    // 요청 A에서 잡을 큐에 넣고, 부팅 시 만든 소비자 루프가 꺼내 실행하는 구조
const snap = AsyncLocalStorage.snapshot();          // 지금(요청 A) 컨텍스트 캡처
queue.push({ run: () => snap(() => processJob(job)) });
// 소비자 루프 (컨텍스트 없음)
setInterval(() => { const j = queue.shift(); j?.run(); }, 10);   // processJob 안에서 getStore() === A의 스토어
// 대안: 잡에 store를 명시적으로 싣고 소비자에서 als.run(job.store, ...) — 더 명시적이고 디버깅 쉬움
    
    
    
  
    

  
    
    
    10. 현업 장애 사례
    
    
    사례 1: 로그의 30%에 requestId가 없다
      
    pino + ALS로 요청 ID를 로그에 자동 주입. 그런데 DB 관련 로그에만 ID가 빠짐. 원인: 레거시 DB 드라이버가 콜백 방식이고, 커넥션 풀 소켓이 부팅 시 생성되어 콜백이 스토어 없는 컨텍스트에서 호출됨. 추적 도구에서 그 요청의 DB 쿼리가 보이지 않아 느린 쿼리 원인 분석이 불가능했음. 수정: 드라이버 호출을 util.promisify로 감싸 await 기반으로 바꾸자 해결(await 이후는 run 컨텍스트에서 재개).
    
    
    
    
    사례 2: 야간 배치마다 파드가 재시작
      
    배치 작업이 items.forEach(async item => { await process(item); })로 작성됨. forEach는 Promise를 기다리지 않으므로 수천 개가 동시에 뜨고, 그중 하나가 거부되면 아무도 catch하지 않아 unhandledRejection → 기본 throw 모드로 프로세스 종료 → 배치가 반쯤 처리된 채 재시작, 멱등하지 않은 작업이 중복 실행. 수정: for...of + 동시성 제한(p-limit 류) + allSettled로 실패 수집, 그리고 멱등 키(18장).
    
    
    
    
    사례 3: 타임아웃이 걸렸는데 DB는 계속 바쁘다
      
    API에 Promise.race([work(), timeout(3000)])로 3초 타임아웃. 트래픽 급증 시 타임아웃 응답은 빠르게 나가는데 DB CPU는 100%. race는 진 쪽을 취소하지 않으므로 타임아웃된 쿼리들이 DB에서 계속 실행되며 새 요청까지 느리게 만드는 양의 피드백. 수정: AbortSignal.timeout(3000)을 쿼리까지 전달해 서버 측 취소(드라이버가 지원하는 경우 DB에 cancel 요청), 지원하지 않는 드라이버는 커넥션 destroy.
    
    
    
  
    

  
    핵심 요약
      
    
    • Promise는 V8 객체. then은 반응을 등록할 뿐이고 결정 시 반응이 마이크로태스크 잡이 된다. 큐는 V8 소유, 비우는 시점은 Node(processTicksAndRejections) 소유.
      • 
    
    • 틱 수: await 값/네이티브 Promise = 1, await thenable = 2, return promise는 +2, return await이 한 틱 빠르고 스택 트레이스도 보존.
      • 
    
    • unhandledRejection 판정은 드레인 끝(processPromiseRejections). 기본 모드 throw. 리스너는 로그 후 종료 절차로. fire-and-forget에는 자체 catch.
      • 
    
    • all/any/race는 진 작업을 취소하지 않는다. AbortSignal을 공유해 직접 취소. 협조적 취소: throwIfAborted, 리스너 정리.
      • 
    
    • async_hooks: 자원 생성 시 init(asyncId, triggerAsyncId), 콜백 전후 before/after. Promise 훅은 모든 Promise에 비용. 직접 쓰지 말 것.
      • 
    
    • ALS 규칙 하나: 자원이 생성될 때의 스토어를 그 콜백이 본다. 부팅 시 만든 풀/소켓/타이머/큐 소비자의 콜백에서는 유실. await 이후는 run 컨텍스트에서 재개되므로 Promise 기반 코드는 거의 안전.
      • 
    
    • 수정: AsyncResource.bind, EventEmitterAsyncResource, AsyncLocalStorage.snapshot, 또는 콜백 API를 promisify. Node 24+는 AsyncContextFrame 기반으로 오버헤드 감소.
      • 
  
    

  
    확인 문제
    
  
    
    
    async function g(){ return Promise.resolve('x'); } 를 await g() 하면 몇 틱 뒤에 재개되는가? (Node 22)
    
    
    
    
    
    
    async 함수가 Promise를 return하면 결과 Promise를 그 Promise로 resolve해야 하므로 NewPromiseResolveThenableJob(1) + 반응(1) = 2틱 뒤에 g()의 Promise가 결정되고, 바깥 await가 1틱을 더 씁니다. return await이었다면 2틱.
    
  
    
  
    
    
    const p = Promise.reject(new Error('x')); setTimeout(() => p.catch(() => {}), 0); 기본 모드에서 어떻게 되는가?
    
    
    
    
    
    
    판정은 거부가 발생한 드레인의 마이크로태스크가 모두 끝난 시점입니다. setTimeout 콜백은 다음 루프 회차라 너무 늦습니다. 같은 드레인(동기 코드 또는 마이크로태스크) 안에서 catch를 붙여야 안전합니다.
    
  
    
  
    
    
    미들웨어에서 als.run(ctx, next)로 감쌌는데, 부팅 시 만든 Redis 클라이언트의 client.get(key, cb) 콜백에서 als.getStore()가 undefined다. 가장 적절한 설명은?
    
    
    
    
    
    
    스토어는 자원 생성 시점의 컨텍스트에 붙습니다. 풀 소켓은 부팅 시 생성되었으므로 그 'data' 콜백은 스토어가 없는 컨텍스트에서 실행됩니다. 콜백을 바인딩하거나, promisify해서 await하면 Promise 반응이 run() 안에서 생성되어 이어집니다.
    
  
    
  
    
    
    Promise.race([query(), timeout(3000)])으로 타임아웃을 걸었다. 타임아웃 후 query()는?
    
    
    
    
    
    
    race는 결과를 먼저 낸 것을 택할 뿐 진 쪽에 아무것도 하지 않습니다. query의 거부는 race가 핸들러를 달아 두었으므로 unhandled도 아닙니다. 조용히 자원을 소모합니다.
    
  
    
  
    
    
    APM 에이전트를 붙이자 Promise가 많은 서비스의 처리량이 30% 떨어졌다. 가장 가능성 높은 원인은?
    
    
    
    
    
    
    훅이 enable되면 V8 Promise 훅이 켜지고 await마다 생기는 2~3개의 Promise 각각에 JS 콜백이 호출됩니다. 에이전트가 ALS만 쓰고 Node 24+(AsyncContextFrame)라면 비용이 크게 줄어듭니다.
