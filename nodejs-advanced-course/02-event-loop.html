이벤트 루프 심층 해부

"싱글 스레드, 논블로킹"이라는 구호 뒤에는 libuv의 uv_run이 도는 여섯 개 페이즈와, Node.js가 그 위에 얹은 두 개의 특별한 큐(nextTick, 마이크로태스크)가 있습니다. 이 장에서는 그 기계를 분해해 콜백 하나가 정확히 언제 실행되는지, 그리고 그 규칙이 운영 중 어떤 장애로 나타나는지를 다룹니다.

학습 목표

  • libuv uv_run의 6개 페이즈와 각 페이즈에서 실제로 실행되는 코드를 설명할 수 있다.
  • process.nextTick·마이크로태스크·타이머·immediate·I/O 콜백의 실행 순서를 임의의 코드에 대해 예측할 수 있다.
  • poll 페이즈의 블로킹 타임아웃 계산 규칙을 알고, 왜 setTimeout(0)과 setImmediate 순서가 메인 모듈에서는 비결정적인지 설명할 수 있다.
  • 이벤트 루프 지연(lag)을 측정하고, 스타베이션과 블로킹 패턴을 진단·해소할 수 있다.

1. 왜 이벤트 루프인가

전통적인 서버(Apache prefork, Java 서블릿 스레드풀)는 연결 하나에 스레드 하나를 배정합니다. 스레드는 I/O가 끝날 때까지 커널 안에서 잠들고, 그동안 스택(기본 수 MB)과 커널 스케줄링 비용을 점유합니다. 연결이 만 개가 되면 스레드도 만 개가 되는 C10K 문제가 여기서 나옵니다.

Node.js는 반대 방향을 택했습니다. 스레드 하나가 수천 개의 I/O를 커널에 "걸어두고"(epoll/kqueue/IOCP), 완료된 것만 골라 콜백을 실행합니다. 스레드가 잠드는 곳은 단 한 곳, poll 페이즈의 epoll_wait뿐입니다. 그 대신 치러야 하는 대가가 있습니다. 콜백 하나가 오래 돌면 다른 모든 연결이 멈춘다는 것입니다. 이 장의 모든 내용은 결국 이 트레이드오프를 정확히 이해하는 일입니다.

한 줄 모델 이벤트 루프는 "완료된 일의 콜백을 정해진 순서로 호출하는 무한 while 루프"입니다. 비동기 작업 자체(디스크 읽기, 네트워크 수신)는 루프가 하지 않습니다. 커널이나 스레드풀이 하고, 루프는 완료 통지만 받습니다. (스레드풀은 3장에서 다룹니다.)

2. uv_run의 실제 구조: 6개 페이즈

Node.js 프로세스가 메인 모듈을 다 실행하고 나면 C++ 레이어(src/api/embed_helpers.cc의 SpinEventLoop)가 uv_run(loop, UV_RUN_DEFAULT)를 호출합니다. libuv의 src/unix/core.c에 있는 이 함수가 바로 "이벤트 루프"입니다. 핵심만 추리면 다음과 같습니다.

int uv_run(uv_loop_t* loop, uv_run_mode mode) {
  r = uv__loop_alive(loop);             // 활성 핸들/요청/closing 핸들이 있는가?
  if (!r) uv__update_time(loop);

  while (r != 0 && loop->stop_flag == 0) {
    uv__update_time(loop);              // 루프 시간 캐시 갱신 (uv_now)
    uv__run_timers(loop);               // ① timers
    ran_pending = uv__run_pending(loop);// ② pending callbacks
    uv__run_idle(loop);                 // ③ idle
    uv__run_prepare(loop);              //    prepare
    timeout = 0;
    if ((mode == UV_RUN_ONCE && !ran_pending) || mode == UV_RUN_DEFAULT)
      timeout = uv__backend_timeout(loop);   // 얼마나 블로킹할지 계산
    uv__io_poll(loop, timeout);         // ④ poll  (epoll_wait / kqueue)
    uv__run_check(loop);                // ⑤ check (setImmediate)
    uv__run_closing_handles(loop);      // ⑥ close callbacks
    r = uv__loop_alive(loop);
    if (mode == UV_RUN_ONCE || mode == UV_RUN_NOWAIT) break;
  }
  return r;
}

※ libuv 1.45+ 기준으로 단순화. 실제 코드는 uv__metrics_* 호출과 "poll 뒤 타이머 재실행" 분기가 추가로 있습니다.

페이즈 순환 애니메이션
재생을 눌러 한 회차(iteration)가 어떻게 도는지 보세요. 보라색은 Node.js가 각 콜백 사이에 끼워 넣는 nextTick/마이크로태스크 드레인입니다.
"페이즈"와 "큐"를 구분하라 페이즈는 libuv가 도는 순서이고, 큐는 각 페이즈가 꺼내 쓰는 자료구조입니다. 타이머는 최소 힙(libuv) + 리스트(Node), immediate는 연결 리스트, I/O는 epoll이 돌려주는 준비 완료 fd 배열입니다. 그리고 nextTick 큐와 마이크로태스크 큐는 libuv의 페이즈가 아닙니다. Node.js가 "JS에서 C++로 돌아오는 모든 지점"에 끼워 넣은 훅입니다. 이 구분이 뒤섞이면 실행 순서 예측이 틀립니다.

3. 페이즈별 상세와 poll 타임아웃 규칙

① timers

uv__run_timers → Node lib/internal/timers.js processTimers()

libuv는 "타이머 하나"만 가지고 있습니다. Node.js는 같은 delay를 가진 타이머들을 하나의 리스트로 묶고, 리스트들을 만료 시각 기준 우선순위 큐에 넣은 뒤, 가장 가까운 만료 시각 하나만 libuv 타이머에 등록합니다. 그래서 setTimeout 10만 개를 만들어도 libuv 타이머는 몇 개뿐입니다.

  • 지연값은 1ms 미만이면 1ms, 2^31-1(약 24.8일)을 넘으면 1ms로 바뀌며 경고(TimeoutOverflowWarning)가 납니다.
  • 만료 판정은 페이즈 진입 시 캐시된 now로 합니다. 콜백 안에서 새로 만든 setTimeout(0)은 _idleStart가 갱신된 시각이라 같은 페이즈에서 실행되지 않고 다음 회차로 갑니다.
  • Node 11부터 타이머 콜백 하나하나 사이에 nextTick/마이크로태스크를 드레인합니다(runNextTicks()). Node 10까지는 같은 페이즈의 타이머를 모두 돌린 뒤 드레인했습니다. 브라우저 의미론과 맞추기 위한 변경이며, 아래 퍼즐 5번이 바로 그 차이입니다.

② pending callbacks

uv__run_pending

이전 회차의 poll에서 "지금 바로 콜백을 부르기 곤란한" I/O 완료를 미뤄 둔 것을 실행합니다. 대표 예는 TCP connect()의 ECONNREFUSED 같은 일부 플랫폼의 에러 보고, uv_write 완료 콜백 일부입니다. 애플리케이션 코드가 여기에 직접 무언가를 넣을 방법은 없습니다.

③ idle / prepare

uv__run_idle, uv__run_prepare

내부용입니다. Node.js는 idle 핸들을 "immediate가 하나라도 대기 중"이라는 표시로 씁니다. idle 핸들이 활성이면 poll 타임아웃이 0이 되어 루프가 블로킹하지 않고 check로 직행합니다. 이것이 setImmediate가 "poll을 기다리지 않는" 메커니즘입니다.

④ poll

uv__io_poll(loop, timeout) → epoll_wait / kevent / GetQueuedCompletionStatusEx

루프가 유일하게 잠드는 곳입니다. 먼저 완료된 I/O의 콜백을 실행하고, 할 일이 없으면 커널에서 다음 이벤트를 기다립니다. 얼마나 기다릴지는 uv__backend_timeout이 정합니다.

조건 (위에서부터 먼저 맞는 것)타임아웃의미
stop_flag 설정됨 / 활성 핸들·요청 없음0곧 루프 종료
idle 핸들 활성 (= setImmediate 대기 중)0블로킹 없이 check로
pending 큐 비어있지 않음0미룬 콜백부터 처리
closing 핸들 있음0close 콜백 처리
타이머 있음가장 가까운 만료까지 ms타이머 시각에 맞춰 깨어남
그 외-1 (무한)I/O가 올 때까지 잠듦

한 번의 epoll_wait가 돌려주는 이벤트는 최대 1024개(libuv 내부 배열)이고, 처리 시간이 길어지면 libuv는 남은 타임아웃을 다시 계산해 반복합니다. 즉 I/O가 폭주하면 루프는 poll 페이즈에 머무르며 타이머를 굶길 수 있습니다(8절).

⑤ check

uv__run_check → Node lib/internal/timers.js processImmediate()

setImmediate 콜백을 실행합니다. 페이즈 진입 시점의 리스트를 통째로 떼어내 실행하므로, 실행 중 새로 등록된 immediate는 다음 회차로 갑니다(무한 재귀여도 I/O를 굶기지 않는 이유). 콜백 사이마다 nextTick/마이크로태스크 드레인.

⑥ close callbacks

uv__run_closing_handles

uv_close()된 핸들의 close 콜백. JS에서는 socket.on('close'), server.on('close') 등이 여기서 발화합니다. socket.destroy()를 호출해도 'close' 이벤트는 동기적으로 오지 않고 이 페이즈에서 온다는 점이 테스트 작성 시 자주 걸리는 부분입니다.

4. Node가 얹은 두 큐: nextTick과 마이크로태스크

libuv는 JavaScript를 모릅니다. C++ 콜백이 JS 함수를 호출하고 돌아올 때, Node.js는 InternalCallbackScope라는 RAII 객체의 소멸자에서 tick_callback(JS의 processTicksAndRejections)을 호출합니다. 이 함수가 두 큐를 비웁니다.

// lib/internal/process/task_queues.js (요지)
function processTicksAndRejections() {
  let tock;
  do {
    while ((tock = queue.shift()) !== null) {   // ① nextTick 큐를 완전히 비운다
      // ... 실행 중 추가된 nextTick도 이 while에서 함께 소진된다
      callback(...args);
    }
    runMicrotasks();                             // ② V8 마이크로태스크 큐를 완전히 비운다
  } while (!queue.isEmpty() || processPromiseRejections());  // ③ ②에서 nextTick이 생겼으면 반복
  setHasTickScheduled(false);
  setHasRejectionToWarn(false);
}

이 코드에서 다섯 가지 규칙이 나옵니다.

  1. nextTick이 마이크로태스크보다 먼저다. 같은 드레인에서 nextTick 큐가 먼저 바닥나야 runMicrotasks()가 호출된다.
  2. nextTick 안에서 등록한 nextTick은 같은 while 안에서 바로 이어 실행된다. 마이크로태스크보다도 먼저.
  3. 마이크로태스크 안에서 등록한 마이크로태스크는 V8이 runMicrotasks() 안에서 다 소진한다(V8의 MicrotaskQueue는 비워질 때까지 돈다).
  4. 마이크로태스크 안에서 등록한 nextTick은 그 마이크로태스크 큐가 다 빌 때까지 기다렸다가, do-while 두 번째 바퀴에서 실행된다.
  5. 이 드레인은 모든 매크로 콜백(타이머·I/O·immediate) 하나하나 사이에서 일어난다. 메인 모듈이 끝난 직후에도 한 번 일어난다.
왜 nextTick이 따로 존재하는가 (설계 배경)

process.nextTick은 Promise가 언어에 들어오기 전(2011년)부터 있었습니다. 목적은 "객체를 생성한 뒤, 사용자가 이벤트 핸들러를 붙일 기회를 준 다음, 이벤트를 발화한다"였습니다. 예를 들어 net.createServer().listen()이 동기적으로 'listening'을 emit하면 아직 .on('listening')을 붙이기 전이라 이벤트를 놓칩니다. 그래서 코어 API는 동기적 오류 보고를 process.nextTick(() => this.emit('error', err))로 미룹니다.

Promise가 들어온 후 두 큐를 합칠지 논의가 있었지만(nodejs/node#22323 등), nextTick이 마이크로태스크보다 먼저여야 하는 코어 코드가 많아 그대로 남았습니다. 공식 가이드는 새 코드에서는 queueMicrotask를 권하지만, 코어 내부는 여전히 nextTick을 광범위하게 씁니다. 차이가 중요해지는 경우는 거의 "순서에 의존한 버그"뿐이며, 그런 코드는 재설계하는 편이 낫습니다.

6. 고전 퍼즐 6선과 해설

각 퍼즐은 시뮬레이터 프리셋에 들어 있습니다. 먼저 답을 적고 실행해 보세요.

퍼즐 1. 메인 모듈에서 setTimeout(0) vs setImmediate

setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));

답: 비결정적. 메인 모듈이 끝나고 루프 첫 회차의 timers 페이즈에 들어갈 때 uv__update_time으로 갱신된 now가 타이머 등록 시각 + 1ms를 넘었는지에 달려 있습니다. 부팅이 빠른 머신에서는 immediate가, 느리거나 로드가 있는 머신에서는 timeout이 먼저입니다. 시뮬레이터의 "메인 모듈 비용"을 1ms 기준으로 움직여 보세요. 이런 순서에 의존하는 코드는 그 자체가 버그입니다.

퍼즐 2. I/O 콜백 안에서는 결정적

fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});

답: immediate → timeout, 항상. I/O 콜백은 poll 페이즈에서 실행되고, 바로 다음이 check 페이즈입니다. 타이머는 다음 회차의 timers 페이즈까지 기다려야 합니다. 이것이 "I/O 콜백 안에서 뭔가를 미루려면 setImmediate가 항상 더 빠르고 예측 가능하다"는 공식 권고의 근거입니다.

퍼즐 3. nextTick과 마이크로태스크의 교차

process.nextTick(() => { console.log('tick1'); Promise.resolve().then(() => console.log('micro-in-tick')); });
Promise.resolve().then(() => { console.log('micro1'); process.nextTick(() => console.log('tick-in-micro')); });
Promise.resolve().then(() => console.log('micro2'));
process.nextTick(() => console.log('tick2'));

답: tick1, tick2, micro1, micro2, micro-in-tick, tick-in-micro. 드레인 첫 바퀴: nextTick 큐 [tick1, tick2]를 비움(tick1이 등록한 micro-in-tick은 마이크로태스크 큐 끝에 붙음). 그다음 runMicrotasks()가 [micro1, micro2, micro-in-tick]을 비움(micro1이 등록한 tick-in-micro는 nextTick 큐로). do-while 조건에서 nextTick 큐가 비어있지 않으므로 두 번째 바퀴: tick-in-micro.

퍼즐 4. then에서 Promise를 반환하면 두 틱이 더 든다

Promise.resolve().then(() => { console.log('a'); return Promise.resolve('x'); }).then(v => console.log('b', v));
Promise.resolve().then(() => console.log('1')).then(() => console.log('2')).then(() => console.log('3')).then(() => console.log('4'));

답: a, 1, 2, 3, b x, 4. 'a' 콜백이 Promise를 반환하면 반환된 Promise의 결과로 바깥 Promise를 resolve해야 합니다. ECMAScript는 이를 NewPromiseResolveThenableJob이라는 별도 마이크로태스크로 처리하고(+1틱), 그 잡이 호출한 .then의 콜백이 또 한 틱 뒤에 실행됩니다(+1틱). 그래서 'b'는 'a'보다 세 틱 늦고, 그 사이에 '2', '3'이 끼어듭니다. 시뮬레이터 마이크로태스크 큐에서 resolveThenable이라는 항목이 바로 그 잡입니다. (V8은 await에 한해 네이티브 Promise면 이 비용을 1틱으로 줄이는 최적화를 넣었습니다. 7장 참고.)

퍼즐 5. 타이머 사이의 드레인 (Node 11 변경)

setTimeout(() => { console.log('t1'); Promise.resolve().then(() => console.log('p1')); }, 0);
setTimeout(() => { console.log('t2'); Promise.resolve().then(() => console.log('p2')); }, 0);

답(Node 11+): t1, p1, t2, p2. Node 10 이하에서는 t1, t2, p1, p2였습니다. 두 타이머는 같은 리스트(delay=1)에 있고 같은 페이즈에서 실행되지만, 콜백 사이에 runNextTicks()가 호출되기 때문입니다. 브라우저에서 setTimeout 두 개는 별개의 매크로태스크라 항상 t1, p1, t2, p2였고, Node가 이에 맞춘 것입니다.

퍼즐 6. immediate 안의 immediate, nextTick

setImmediate(() => { console.log('i1'); setImmediate(() => console.log('i-in-i')); process.nextTick(() => console.log('tick-in-i')); });
setImmediate(() => console.log('i2'));

답: i1, tick-in-i, i2, i-in-i. check 페이즈는 진입 시 리스트 [i1, i2]를 떼어내 실행합니다. i1 실행 후 드레인으로 tick-in-i. i1이 등록한 i-in-i는 새 리스트에 들어가 다음 회차의 check에서 실행됩니다. 그 사이 timers·poll 페이즈를 한 번 더 지나므로, 만약 1ms짜리 타이머가 있었다면 i-in-i보다 먼저 실행됐을 것입니다.

7. 루프 블로킹과 지연(lag) 측정

"이벤트 루프 지연"이란 타이머가 만료된 시각과 실제로 콜백이 실행된 시각의 차이입니다. 콜백 하나가 50ms 돌면 그 사이 만료된 모든 타이머, 도착한 모든 요청이 최소 50ms 기다립니다. 지연은 누적되지 않고 "가장 긴 콜백" 크기로 튀는 특성이 있어서, 평균은 멀쩡한데 p99가 튀는 형태로 나타납니다.

루프 지연 시뮬레이터
10ms 간격 setInterval 타이머가 있다고 할 때, 중간에 동기 작업(예: 큰 JSON.parse)이 끼어들면 타이머 발화 시각이 어떻게 밀리는지 봅니다. 막대 위의 숫자가 각 발화의 지연(ms)입니다.
최대 타이머 지연
-
지연된 요청 수
-
요청 지연 p50 / 최대
-
읽는 법 동기 작업이 끝나는 순간, 그동안 만료된 타이머는 한 번만 발화합니다(setInterval은 밀린 횟수만큼 몰아서 부르지 않고 다음 예정 시각을 "지금 + interval"로 다시 잡습니다). 그 사이 도착한 요청들은 모두 poll 페이즈에서 한꺼번에 처리되며, 각각 "도착 시각 → 작업 종료 시각"만큼 기다립니다.

실제로 측정하기

const { monitorEventLoopDelay } = require('node:perf_hooks');
const h = monitorEventLoopDelay({ resolution: 20 }); // 20ms마다 샘플
h.enable();
setInterval(() => {
  console.log({
    p50: h.percentile(50) / 1e6,   // 나노초 → ms
    p99: h.percentile(99) / 1e6,
    max: h.max / 1e6,
  });
  h.reset();
}, 10_000).unref();

libuv 타이머를 resolution 간격으로 걸어 두고 실제 발화 시각과의 차이를 히스토그램(HDR)으로 모읍니다. 프로덕션에서 상시 켜 두어도 비용이 거의 없고, 15장의 Prometheus 메트릭으로 내보내는 것이 표준 패턴입니다. 값이 resolution에 가까우면 정상이고, 수백 ms가 p99로 보이면 어딘가 동기 작업이 있는 것입니다.

const { performance } = require('node:perf_hooks');
let last = performance.eventLoopUtilization();
setInterval(() => {
  const cur = performance.eventLoopUtilization();
  const d = performance.eventLoopUtilization(cur, last);
  console.log('ELU', d.utilization.toFixed(3)); // 0.0 (내내 idle) ~ 1.0 (내내 바쁨)
  last = cur;
}, 5000).unref();

ELU(Event Loop Utilization)는 "루프가 poll에서 잠든 시간 대비 깨어 있던 시간의 비율"입니다. 지연 히스토그램이 튀는 콜백을 잡는다면, ELU는 전체 포화도를 봅니다. ELU가 0.7을 넘으면 그 프로세스는 더 이상 요청을 받으면 안 되는 상태로 보고 오토스케일 신호로 씁니다(Node.js 공식 블로그의 권고도 이 방식). 14장의 k8s HPA 연동 참고.

// 원리 이해용. 운영에서는 위 두 API를 쓸 것.
let expected = performance.now() + 100;
setInterval(() => {
  const now = performance.now();
  const lag = now - expected;          // 양수 = 그만큼 늦게 불렸다
  if (lag > 50) console.warn(`event loop lag ${lag.toFixed(1)}ms`);
  expected = now + 100;
}, 100).unref();

8. 스타베이션과 안티패턴

8.1 재귀 nextTick은 루프를 영원히 멈춘다

I/O 스타베이션
function pump() {
  doSmallWork();
  process.nextTick(pump);   // 큐가 영원히 비지 않음
}
pump();
// 루프가 poll 페이즈에 도달하지 못함
// → 어떤 요청도, 타이머도 실행 안 됨
루프에 양보
function pump() {
  doSmallWork();
  setImmediate(pump);       // 매 회차 한 번씩만
}
pump();
// 회차마다 timers → poll → check 를 지남
// → I/O와 타이머가 사이사이 실행됨

같은 이유로 마이크로태스크 재귀(Promise.resolve().then(pump))도 스타베이션을 일으킵니다. V8의 runMicrotasks()는 큐가 빌 때까지 반환하지 않기 때문입니다. "비동기니까 괜찮겠지"는 틀린 직관입니다. 비동기이지만 루프에 돌아가지 않는 비동기가 있습니다.

8.2 긴 동기 작업 쪼개기

// 100만 건 처리: 1,000건 단위로 쪼개고 사이마다 루프에 양보
async function processAll(items) {
  for (let i = 0; i < items.length; i += 1000) {
    for (const it of items.slice(i, i + 1000)) handle(it);
    await new Promise(r => setImmediate(r));   // ← setTimeout(r, 0)보다 낫다: 1ms 최소 지연이 없음
  }
}

단, 쪼개기는 지연을 줄일 뿐 처리량을 늘리지 않습니다. CPU 총량이 같다면 워커 스레드(9장)로 보내는 것이 정답입니다. 쪼개기는 "작업이 가끔 있고, 그동안 다른 요청의 지연이 중요할 때"의 도구입니다.

8.3 poll 페이즈 포화

I/O 완료가 폭주하면 루프는 poll 페이즈에서 준비된 fd를 계속 처리합니다. libuv는 이를 막기 위해 한 번의 poll 호출에서 처리하는 양을 제한하지만, 각 콜백이 무거우면 타이머가 밀립니다. 증상은 "트래픽이 많을 때만 setTimeout 기반 타임아웃이 늦게 발화해 더 많은 요청이 쌓이는" 양의 피드백입니다. 해결은 요청 수락 자체를 제한하는 백프레셔(6장, 18장)입니다.

8.4 unref와 프로세스 종료

uv__loop_alive는 활성 핸들이 하나라도 있으면 루프를 계속 돕니다. setInterval 하나, 열려 있는 소켓 하나가 프로세스 종료를 막습니다. 모니터링용 타이머에는 .unref()를, 테스트 종료가 안 될 때는 process.getActiveResourcesInfo()(Node 17+)로 무엇이 살아있는지 확인하세요. (process._getActiveHandles()는 비공개 API.)

$ node -e "setInterval(()=>{},1000); console.log(process.getActiveResourcesInfo())"

9. 현업 장애 사례

사례 1: 헬스체크 실패로 인한 연쇄 재시작

k8s liveness 프로브 타임아웃 1초. 대형 리포트 생성 요청이 들어오면 JSON.stringify에 2~3초가 걸렸고, 그동안 /healthz 응답이 밀려 프로브가 실패 → 파드 재시작 → 남은 파드에 트래픽 집중 → 또 리포트 요청 → 재시작. 루프 지연 p99 메트릭이 있었다면 재시작 전에 경보가 났을 것입니다. 해결: 리포트 생성을 워커로 분리, liveness 타임아웃을 루프 지연 기대치보다 넉넉히, readiness는 ELU 기반으로.

사례 2: 캐시 TTL 타이머 드리프트

5초 setInterval로 캐시를 갱신하는 코드. 부하가 높아지자 루프 지연이 늘어 실제 갱신 간격이 7~8초로 벌어졌고, TTL 5초짜리 캐시가 "만료됐지만 갱신 전" 상태에 자주 빠져 DB로 폭주. setInterval은 드리프트를 보정하지 않습니다. 해결: 갱신 주기를 TTL보다 충분히 짧게, 또는 만료 시각을 기준으로 다음 타이머를 재계산.

사례 3: 'close' 이벤트가 안 와서 새는 커넥션 카운터

socket.destroy() 직후 동기적으로 카운터를 감소시키고, 'close' 핸들러에서 또 감소시킨 코드. close 콜백은 ⑥ 페이즈에서 비동기적으로 오므로 이중 감소. 커넥션 수 메트릭이 음수가 되어 오토스케일러가 축소 결정. 상태 전이는 한 곳(이벤트)에서만.

핵심 요약

  • 이벤트 루프 = libuv uv_run의 while 루프. 회차마다 timers → pending → idle/prepare → poll → check → close 순. 루프가 잠드는 곳은 poll의 epoll_wait 하나.
  • nextTick 큐와 마이크로태스크 큐는 페이즈가 아니라 매 콜백 경계에서 드레인된다. 순서: nextTick 전부 → 마이크로태스크 전부 → (nextTick이 또 생겼으면) 반복.
  • poll 타임아웃: immediate 대기 중이면 0, 아니면 가장 가까운 타이머까지, 둘 다 없으면 무한.
  • 메인 모듈의 setTimeout(0) vs setImmediate는 비결정적, I/O 콜백 안에서는 항상 immediate가 먼저.
  • then에서 Promise 반환은 +2틱. 타이머 콜백 사이에도 드레인(Node 11+). immediate 안의 immediate는 다음 회차.
  • 재귀 nextTick/마이크로태스크는 I/O를 굶긴다. 양보는 setImmediate로. 긴 CPU 작업은 쪼개기가 아니라 워커가 답.
  • 운영 지표: monitorEventLoopDelay(p99 지연), eventLoopUtilization(포화도). 둘 다 상시 수집.

확인 문제

다음 코드의 출력 순서는? setImmediate(()=>console.log('A')); process.nextTick(()=>console.log('B')); Promise.resolve().then(()=>console.log('C')); setTimeout(()=>console.log('D'),0); (메인 모듈 실행에 2ms가 걸렸다고 가정)
메인 모듈 종료 직후 드레인: nextTick(B) → 마이크로태스크(C). 루프 진입 시 2ms가 지났으므로 1ms 타이머 D는 이미 만료 → timers 페이즈에서 D. 그다음 check에서 A. 메인 모듈 비용이 1ms 미만이었다면 B, C, A, D.
poll 페이즈에서 루프가 "무한히" 블로킹하는 조건은?
uv__backend_timeout은 깨울 이유(immediate=idle 핸들, pending, closing, 타이머)가 하나도 없을 때 -1을 돌려주고, 이 경우 epoll_wait는 I/O 이벤트가 올 때까지 잠듭니다. 활성 핸들조차 없으면 루프는 종료됩니다.
마이크로태스크 콜백 안에서 process.nextTick(f)를 호출했다. f는 언제 실행되는가?
processTicksAndRejections의 do-while: runMicrotasks()가 큐를 완전히 비우고 반환한 뒤, nextTick 큐가 비어있지 않으면 한 바퀴 더 돕니다. 따라서 같은 드레인 안이지만 남은 마이크로태스크가 모두 끝난 뒤입니다.
10만 건 레코드를 CPU 집약적으로 변환해야 한다. 요청 지연이 중요한 API 서버에서 가장 적절한 접근은?
쪼개기(2번)는 지연을 줄이지만 CPU 총량은 그대로여서 처리량이 늘지 않고 다른 요청의 지연도 여전히 늘어납니다. 3번은 I/O 스타베이션, 4번은 1ms 최소 지연 때문에 100번 이상 양보하면 눈에 띄게 느려집니다. CPU 작업은 루프 밖으로 보내는 것이 정답입니다.
Node 10에서 11로 올리자 두 타이머 사이의 Promise 콜백 실행 순서가 바뀌었다. 무엇이 달라졌는가?
Node 11(nodejs/node#22842)부터 timers와 immediates 처리 시 콜백 하나마다 runNextTicks()를 호출합니다. 브라우저 의미론과 일치시키기 위한 변경입니다.
