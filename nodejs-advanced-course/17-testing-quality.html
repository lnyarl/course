테스트 전략과 품질 게이트

테스트는 "코드가 맞다"를 증명하지 못합니다. 테스트가 하는 일은 회귀를 싸게 잡는 것이고, 그래서 테스트 전략의 핵심 질문은 "무엇을 어느 층에서 얼마의 비용으로 잡을 것인가"입니다. 이 장은 Node.js 내장 러너 node:test의 실행 모델부터 모킹 경계, 플래키 테스트의 원인 분류, 계약·성능 회귀 테스트, 그리고 CI 품질 게이트의 순서까지 다룹니다.

학습 목표

  • node:test의 프로세스·동시성 모델을 알고, 파일 병렬/테스트 직렬 규칙이 격리와 속도에 미치는 영향을 설명할 수 있다.
  • 의존성 주입, 모듈 모킹, 네트워크 인터셉트, 가짜 시계 중 어떤 모킹 기법을 어느 경계에 쓸지 결정할 수 있다.
  • 플래키 테스트를 타이밍·순서·공유 상태·포트·외부 의존 다섯 가지 원인으로 분류하고 재현·수정할 수 있다.
  • 계약 테스트와 성능 회귀 테스트를 CI에 넣을 때의 변동성 문제를 다룰 수 있고, 품질 게이트의 순서를 비용 기준으로 설계할 수 있다.

1. 테스트는 무엇을 사는가: 피라미드와 트로피

테스트 한 개의 가치는 잡아내는 결함의 기대값 − (작성 비용 + 실행 비용 × 실행 횟수 + 유지보수 비용)입니다. 단위 테스트는 실행이 ms 단위라 수천 번 돌려도 싸지만, 모듈 경계 바깥의 결함(잘못된 SQL, 직렬화 불일치, 타임아웃 설정)은 못 잡습니다. E2E는 그런 결함을 잡지만 느리고, 깨지는 이유가 결함이 아닌 경우(환경, 타이밍)가 많아 신호 대 잡음비가 낮습니다.

"피라미드"(단위 다수, 통합 소수, E2E 극소수)는 2009년의 비용 구조를 반영합니다. 당시 통합 테스트는 실제 DB를 띄우기 어려워 비쌌습니다. 컨테이너로 DB를 초 단위로 띄우고, HTTP 인터셉트로 외부 API를 결정적으로 만들 수 있는 지금은 "트로피"(통합 테스트가 가장 두꺼운 형태)가 Node.js 백엔드에 더 맞는 경우가 많습니다. 백엔드 결함의 대부분이 모듈 사이에서 나기 때문입니다.

2. node:test의 실행 모델

Node 20부터 안정화된 내장 러너는 Jest/Mocha와 다른 실행 모델을 가집니다. 이 모델을 모르면 "왜 전역 설정이 안 먹지", "왜 테스트가 끝나도 프로세스가 안 죽지"가 설명되지 않습니다.

$ node --test                     # 기본 패턴: **/*.test.{js,mjs,cjs}, **/*-test.*, **/*_test.*,
                                  #            **/test-*.*, **/test.*, **/test/**/*.{js,mjs,cjs}
$ node --test tests/unit/         # 디렉터리 지정
$ node --test --watch             # 변경 감지 재실행
$ node --test --test-concurrency=4            # 동시에 실행할 파일 수 (기본: os.availableParallelism() - 1)
$ node --test --test-name-pattern="결제"      # 이름으로 필터
$ node --test --test-reporter=spec --test-reporter-destination=stdout \
              --test-reporter=junit --test-reporter-destination=report.xml   # 리포터 다중 지정
$ node --test --test-timeout=10000            # 테스트당 타임아웃 (기본 무한)
$ node --test --test-force-exit               # 완료 후 남은 핸들 무시하고 종료

2.1 파일 안에서의 구조와 수명주기

import { test, describe, before, after, beforeEach, afterEach } from 'node:test';
import assert from 'node:assert/strict';

describe('OrderService', { concurrency: 1 }, () => {
  let db;
  before(async () => { db = await connect(); });        // describe 단위 1회
  after(async () => { await db.close(); });             // 반드시 정리 → 안 하면 프로세스가 안 끝난다
  beforeEach(async () => { await db.query('BEGIN'); });
  afterEach(async () => { await db.query('ROLLBACK'); }); // 트랜잭션 롤백으로 격리

  test('총액은 수량×단가의 합', async (t) => {
    t.diagnostic('fixture: 3 items');                   // 리포터에 메모
    const svc = new OrderService(db);
    assert.equal(await svc.total(orderId), 12_000);
  });

  test('재고 부족이면 거부', { skip: process.env.CI === 'true' && 'CI에서는 외부 재고 API 없음' }, async () => {
    await assert.rejects(() => svc.place(order), { code: 'OUT_OF_STOCK' });
  });

  test.todo('부분 환불');                                // 리포트에 TODO로 표시
});
  • 서브테스트: test('부모', async (t) => { await t.test('자식', ...) }). 자식을 await하지 않으면 부모가 먼저 끝나 "test did not finish before its parent" 에러가 납니다(4절).
  • t.plan(n)(22.2+): 이 테스트가 정확히 n개의 단언/서브테스트를 수행해야 함을 선언. 콜백 안의 단언이 실행조차 안 되는 "조용한 통과"를 잡습니다.
  • only: test('x', { only: true }) + --test-only. 플래그 없이 only만 붙이면 무시됩니다(실수로 커밋돼도 CI가 전체를 돌리게 하는 설계).

2.2 리포터와 커버리지

리포터는 spec(TTY 기본), tap(비TTY 기본), dot, junit, lcov가 내장이며 --test-reporter=./my-reporter.mjs로 커스텀 가능합니다(이벤트 스트림을 받는 async generator 또는 Transform). 커버리지는 V8의 내장 커버리지(NODE_V8_COVERAGE와 같은 메커니즘)를 쓰므로 계측 도구가 필요 없고 소스를 변형하지 않습니다.

$ node --test --experimental-test-coverage \
    --test-coverage-include='src/**' --test-coverage-exclude='src/**/*.test.js' \
    --test-coverage-lines=80 --test-coverage-branches=70      # 임계치 미달 시 실패 (22.x 기준 플래그명)
버전 주의 커버리지 기능은 Node 22 문서에서도 실험(Stability 1)으로 표기되어 있습니다. 플래그 이름이 마이너 버전에서 바뀐 적이 있으니(--test-coverage-include는 22.5 무렵 추가) 사용하는 정확한 버전의 문서로 확인하세요. 모듈 모킹(mock.module, 22.3+ --experimental-test-module-mocks)과 스냅샷(t.assert.snapshot, 22.3+ --experimental-test-snapshots)도 같은 처지입니다.

3. 모킹 경계: 무엇을 어디서 가짜로 만들 것인가

모킹의 목적은 두 가지뿐입니다. 결정성(시간·랜덤·네트워크를 고정) 과 속도/격리(비싼 외부 자원 제거). 그 외의 모킹, 특히 "내 코드의 다른 모듈"을 모킹하는 것은 테스트를 구현에 결합시켜 리팩터링 때마다 테스트가 깨지게 만듭니다. 경계는 내 프로세스가 통제하지 못하는 것에 그어야 합니다.

대상권장 기법이유
시간 (Date, 타이머)t.mock.timers.enable({ apis: ['setTimeout','Date'] })실제 대기 없이 tick()으로 전진. 타임아웃·재시도 로직을 ms 단위로 검증
랜덤 (Math.random, crypto.randomUUID)t.mock.method(Math, 'random', () => 0.42) 또는 주입된 RNG시드 고정. 속성 기반 테스트는 시드를 로그에 남겨 재현
외부 HTTPundici MockAgent / mswfetch·undici 레벨에서 가로채므로 코드 변경 없음. 요청 내용까지 검증 가능
DB모킹하지 않음. 실제 DB(컨테이너) + 트랜잭션 롤백SQL·제약·직렬화 결함이 가장 흔한 결함. 모킹하면 그 층을 통째로 못 봄
내 코드의 협력 객체생성자/팩토리 의존성 주입모듈 모킹보다 명시적. ESM에서는 모듈 모킹이 원래 어렵다(라이브 바인딩)
어쩔 수 없는 모듈 경계t.mock.module() (22.3+, 실험)서드파티 SDK처럼 주입 지점이 없을 때의 최후 수단
메시지 큐·캐시인메모리 구현체(같은 인터페이스) 또는 컨테이너인터페이스 계약이 있으면 가짜 구현을 바꿔 끼우기 쉽다
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { MockAgent, setGlobalDispatcher } from 'undici';

test('재시도: 503 두 번 뒤 성공', async (t) => {
  t.mock.timers.enable({ apis: ['setTimeout'] });            // 백오프 대기를 가짜 시계로
  const agent = new MockAgent(); agent.disableNetConnect();  // 실제 네트워크 차단 → 빠진 모킹이 즉시 드러남
  setGlobalDispatcher(agent);
  const pool = agent.get('https://api.example.com');
  pool.intercept({ path: '/v1/items' }).reply(503, {}).times(2);
  pool.intercept({ path: '/v1/items' }).reply(200, { ok: true });

  const p = fetchWithRetry('https://api.example.com/v1/items', { retries: 3, baseMs: 100 });
  t.mock.timers.tick(100);      // 1차 백오프
  t.mock.timers.tick(200);      // 2차 백오프 (지수)
  assert.deepEqual(await p, { ok: true });
  agent.assertNoPendingInterceptors();
});

4. 비동기 테스트 함정과 러너 행(hang)

Node.js 테스트의 실패 모드 중 가장 시간을 잡아먹는 것은 "실패"가 아니라 "끝나지 않음"입니다. 러너는 테스트 함수가 반환한 Promise를 기다리고, 테스트가 모두 끝난 뒤에는 프로세스가 자연 종료되기를 기다립니다(2장의 uv__loop_alive). 어느 한 쪽이 영원히 기다리면 CI는 타임아웃까지 멈춥니다.

각 시나리오에서 러너·테스트 함수·이벤트 루프 핸들의 상태가 어떻게 흘러가는지 단계별로 봅니다.

5. 플래키 테스트의 다섯 원인

    
플래키(간헐 실패) 테스트는 재시도로 덮는 순간 테스트 스위트 전체의 신뢰가 무너집니다. 원인은 거의 예외 없이 아래 다섯 범주에 들어가며, 범주별로 재현 방법이 다릅니다.

    

      
원인증상재현수정

      
타이밍 의존느린 CI에서만 실패. setTimeout(…, 50)으로 "기다렸다가" 확인CPU 부하 걸고 실행(stress), 워커 수 늘리기이벤트/Promise를 await. 가짜 시계

      
순서 의존단독 실행은 통과, 전체 실행은 실패(또는 반대)테스트 순서 섞기, 해당 테스트만 실행beforeEach에서 상태 초기화. 모듈 레벨 싱글턴 제거

      
공유 상태병렬 실행에서만 실패. 같은 DB 행/파일/환경 변수--test-concurrency 올리기테스트별 고유 키(uuid), 트랜잭션 롤백, 임시 디렉터리

      
포트 충돌EADDRINUSE, 또는 다른 테스트의 서버에 연결같은 파일을 두 프로세스로 동시 실행listen(0)으로 OS가 포트를 주게 하고 server.address().port 사용

  • 외부 API: 호출당 1.5% 확률로 네트워크 오류. 워커와 무관.
    • 
        
  • 3회 재시도 후 통과율: 재시도로 숨겨지는 비율. 이 숫자가 높을수록 "재시도가 문제를 감추고 있다"는 뜻.
    • 
      

    

  


  

    
6. 통합 테스트와 계약 테스트

    
6.1 실제 DB를 쓰는 통합 테스트

    
DB를 모킹하면 가장 흔한 결함(잘못된 JOIN, 제약 위반, 타입 캐스팅, 트랜잭션 격리)을 전부 놓칩니다. 컨테이너(testcontainers 류 라이브러리 또는 docker compose)로 실제 DB를 띄우고, 격리는 트랜잭션 롤백으로, 속도는 스키마 1회 생성 + 테스트별 고유 키로 확보합니다.


// 전역 1회: 컨테이너 기동 (--test-isolation=none 이거나, 파일별이라면 재사용 가능한 외부 컨테이너)
// 파일별 before: 풀 연결. beforeEach: BEGIN. afterEach: ROLLBACK.
// 주의: 트랜잭션 안에서 커밋되는 로직(별도 커넥션, 외부 큐 발행)은 롤백으로 못 되돌린다 → 이런 테스트는 고유 키 + 명시적 삭제
beforeEach(async (t) => {
  const client = await pool.connect();
  await client.query('BEGIN');
  t.ctx = { client, tenant: `t_${randomUUID()}` };   // 테스트 간 충돌 없는 테넌트 키
});
afterEach(async (t) => { await t.ctx.client.query('ROLLBACK'); t.ctx.client.release(); });

    
파일 병렬 × 공유 DB 2절에서 본 대로 파일은 병렬로 돕니다. 같은 DB를 쓰면 트랜잭션끼리는 격리되지만, 유니크 제약이 걸린 고정 값(이메일 test@example.com)을 두 파일이 동시에 넣으면 한쪽이 블록되거나 데드락이 납니다. 고정 값 대신 생성된 값을 쓰거나, 파일마다 스키마(search_path)를 분리하세요.


    
6.2 계약 테스트

    
서비스 A가 서비스 B의 API를 호출할 때, A의 테스트는 B를 모킹하고 B의 테스트는 자기 API만 검증합니다. 둘 다 통과해도 A가 기대하는 응답과 B가 실제로 주는 응답이 다를 수 있습니다. 계약 테스트는 이 틈을 메웁니다.

    
    
      
  • 소비자 주도(Pact 방식): A가 "나는 이런 요청을 보내고 이런 응답을 기대한다"를 계약 파일로 기록 → B의 CI가 그 계약을 자기 서버에 재생해 검증. 양쪽 배포 전에 "이 버전 조합이 호환되는가"를 브로커가 답합니다.
    • 
      
  • 스키마 기반(OpenAPI): B가 OpenAPI 명세를 공개 → A의 모킹 응답과 B의 실제 응답을 모두 명세로 검증. Pact보다 가볍지만 "A가 실제로 쓰는 필드"까지는 보장하지 않습니다.
    • 
      
  • 둘 다 직렬화 수준(날짜 포맷, null vs 누락, 숫자 정밀도)을 잡는 것이 핵심입니다. TypeScript 타입 공유는 컴파일 타임 보장일 뿐 런타임 직렬화는 못 봅니다.
    • 
    

  


  

    
7. 성능 회귀 테스트

    
"이 PR이 p99를 20% 올렸다"를 머지 전에 알고 싶다면 벤치마크를 CI에 넣어야 하는데, 문제는 CI 러너의 변동성이 보통 회귀 크기보다 큽니다(공유 머신, 터보 부스트, 노이즈 네이버). 다루는 원칙:

    
    
      
  1. 절대값이 아니라 같은 러너에서의 상대값: 기준 브랜치와 PR 브랜치를 같은 잡에서 번갈아(ABAB) 측정하고 비율을 본다.
    2. 
      
  2. 중앙값·최소값을 쓰고 평균은 버린다. 10장의 벤치마크 함정(워밍업, GC, deopt)을 그대로 적용.
    3. 
      
  3. 임계치보다 추세: 한 번의 5% 변화는 노이즈일 수 있지만, 5커밋 연속 상승은 회귀다. 결과를 시계열로 저장해 그래프로 본다.
    4. 
      
  4. 마이크로벤치보다 시나리오 벤치: 함수 하나의 ns는 전체 요청 지연과 상관이 약하다. autocannon으로 실제 엔드포인트를 때리고 p50/p99/처리량을 기록.
    5. 
      
  5. 신뢰 구간이 겹치면 "변화 없음"으로 판정하고, 겹치지 않을 때만 사람에게 알린다. 경보 피로를 막는 것이 지속의 조건.
    6. 
    


// 간단한 상대 비교 스크립트의 골격 (CI 잡 안에서 실행)
import { spawnSync } from 'node:child_process';
const run = (ref) => JSON.parse(spawnSync('node', ['bench/scenario.mjs', '--ref', ref], { encoding: 'utf8' }).stdout);
const samples = { base: [], pr: [] };
for (let i = 0; i < 5; i++) { samples.base.push(run('main').p99); samples.pr.push(run('HEAD').p99); }  // ABAB 교차
const med = a => a.toSorted((x, y) => x - y)[Math.floor(a.length / 2)];
const ratio = med(samples.pr) / med(samples.base);
console.log(`p99 ratio ${ratio.toFixed(3)}`);
if (ratio > 1.15) process.exitCode = 1;   // 15%는 노이즈 상한을 측정해 정한 값이어야 한다

  


  

    
8. 품질 게이트 설계

    
게이트는 싼 것부터, 실패 확률이 높은 것부터 배치합니다. 10분짜리 E2E 뒤에 10초짜리 lint 실패를 보는 것은 10분 낭비입니다.

    

    
커버리지 숫자의 함정

    
라인 커버리지 90%는 "코드의 90%가 실행됐다"이지 "검증됐다"가 아닙니다. 단언 없는 테스트도 커버리지를 올립니다. 커버리지는 하한 게이트(예: 신규 코드 70% 미만이면 경고)로만 쓰고, 목표 수치로 쓰지 마세요. 목표가 되면 사람들은 숫자를 맞추는 테스트를 씁니다. 더 유용한 지표는 변경된 라인의 커버리지(diff coverage)와 뮤테이션 점수(코드를 일부러 망가뜨렸을 때 테스트가 잡는 비율. Stryker 같은 도구)입니다.


    
테스트 속도

    
    
      
  • 프로세스 격리 비용: 파일당 Node 부팅 ~40ms + 모듈 로딩. 파일이 500개면 격리만으로 20초. 작은 파일을 합치거나 --test-isolation=none(전역 누수 감수)을 검토.
    • 
      
  • 워커 수는 코어 수가 아니라 병목 자원으로 정한다. DB 통합 테스트는 DB 커넥션·CPU가 병목이라 코어 수만큼 늘려도 느려진다.
    • 
      
  • 가장 느린 테스트 10개를 리포터로 뽑아 주기적으로 본다(junit 리포트의 time 속성 정렬).
    • 
    

  


  

    
9. 현업 장애 사례

    
사례 1: 재시도 3회로 덮은 플래키가 실제 결함을 숨김
      
CI에 "실패 시 3회 재시도"가 있었고, 결제 테스트가 가끔 실패했지만 재시도로 통과. 원인은 금액 반올림 로직이 특정 랜덤 수량에서 1원 차이를 내는 진짜 버그였습니다. 랜덤 시드를 로그에 남기지 않아 재현도 못 했고, 재시도 통과율 98%라는 숫자에 가려 6개월 뒤 고객 민원으로 발견. 교훈: 재시도는 금지하거나 "재시도로 통과한 테스트"를 별도 보고하고, 랜덤은 시드를 출력한다.

    

    
사례 2: 모킹한 DB 드라이버와 실제 드라이버의 null 처리 차이
      
단위 테스트는 DB 드라이버를 모킹해 { deletedAt: null }을 돌려줬습니다. 실제 드라이버는 컬럼이 없으면 키 자체를 생략해 undefined. 코드의 row.deletedAt === null 체크가 프로덕션에서 항상 false → 삭제된 계정이 로그인됨. 통합 테스트가 하나라도 실제 DB를 거쳤다면 잡혔을 결함.

    

    
사례 3: 테스트가 끝났는데 CI가 60분 타임아웃
      
한 통합 테스트가 Redis 클라이언트를 열고 닫지 않았습니다. 테스트는 모두 통과했지만 프로세스가 종료되지 않아 러너가 기다리다 잡 타임아웃. 누군가 --test-force-exit을 추가해 "해결"했고, 그 뒤로 커넥션 누수 테스트가 전부 통과. 6개월 뒤 프로덕션에서 같은 패턴의 커넥션 누수(11장)로 장애. after에서 getActiveResourcesInfo()를 검사하는 가드가 답이었습니다.

    

  


  
핵심 요약
    
    
  • 테스트 전략은 결함 분포 × 층별 비용. Node 백엔드는 결함 대부분이 경계에서 나므로 실제 DB를 쓰는 통합 테스트가 두꺼운 트로피형이 맞는 경우가 많다.
    • 
    
  • node:test: 파일은 프로세스 격리 + 병렬(--test-concurrency), 파일 안은 직렬. 메모리는 격리되지만 포트·DB·파일은 공유된다.
    • 
    
  • 모킹 경계는 "내 프로세스가 통제 못 하는 것"(시간, 랜덤, 외부 네트워크). DB는 모킹하지 말고 트랜잭션 롤백. 내 모듈은 주입.
    • 
    
  • 행(hang)은 await 누락, 미해결 Promise, 미정리 핸들, 서브테스트 await 누락. --test-timeout과 t.after 정리, getActiveResourcesInfo 가드.
    • 
    
  • 플래키 다섯 원인: 타이밍, 순서, 공유 상태, 포트, 외부 의존. 재시도로 덮지 말고 원인별 재현법으로 잡는다.
    • 
    
  • 성능 회귀는 같은 러너에서 ABAB 상대 비교, 중앙값, 추세. 게이트는 싼 것부터, 커버리지는 하한으로만.
    • 
  


  
확인 문제

  

    
node --test 기본 설정에서 두 테스트 파일이 모두 포트 3000에 서버를 띄운다. 어떤 일이 일어나는가?

    
    
    
    
    
파일은 기본적으로 별도 프로세스에서 병렬(availableParallelism() - 1)로 돕니다. 프로세스 격리는 메모리만 격리하고 포트·파일·DB는 공유됩니다. listen(0)으로 OS가 포트를 배정하게 하세요.

  

  

    
재시도 로직(지수 백오프 100ms, 200ms, 400ms)을 테스트할 때 가장 적절한 방법은?

    
    
    
    
    
가짜 시계는 대기 없이 "정확히 100ms 뒤에 재시도했는가"까지 검증합니다. 3번은 백오프가 올바른지 검증하지 못하고, 4번은 테스트 대상을 바꿔 버립니다.

  

  

    
테스트가 모두 통과했는데 node --test 프로세스가 종료되지 않는다. 가장 먼저 할 일은?

    
    
    
    
    
살아있는 핸들(서버, 풀, 인터벌)이 원인입니다. 강제 종료는 리소스 누수 테스트를 전부 무력화합니다(사례 3).

  

  

    
단독 실행하면 통과하고 전체 스위트에서 실행하면 실패하는 테스트가 있다. 가장 유력한 원인은?

    
    
    
    
    
단독/전체 차이는 전형적인 순서·공유 상태 신호입니다. 재현은 테스트 순서를 섞거나 의심되는 테스트를 앞뒤로 배치해서 합니다.

  

  

    
CI에서 벤치마크 p99가 PR 브랜치에서 8% 높게 나왔다. 올바른 해석은?

    
    
    
    
    
CI 변동성은 보통 수 %에서 수십 %입니다. ABAB 교차 측정, 중앙값, 사전에 측정한 노이즈 상한, 그리고 여러 커밋에 걸친 추세가 판단 근거입니다.

  


  
실습 과제

    2. 
    
  2. 플래키 재현. setTimeout(check, 50)으로 검증하는 테스트를 하나 만들고, 같은 머신에서 CPU 부하(node -e "while(1){}" 코어 수만큼)를 건 채 for i in $(seq 20); do node --test flaky.test.js || echo FAIL; done로 실패를 유도하세요. 그다음 이벤트/Promise를 await하는 방식으로 고쳐 20회 모두 통과하는지 확인합니다.
