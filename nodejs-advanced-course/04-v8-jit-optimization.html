V8 JIT와 최적화·역최적화

같은 JavaScript 함수가 어떤 때는 C에 가까운 속도로, 어떤 때는 100배 느리게 돕니다. 그 차이를 만드는 것은 코드가 아니라 V8이 코드에 대해 무엇을 "관찰"했는가입니다. 이 장은 V8의 4단계 실행 파이프라인, 관찰 결과가 저장되는 피드백 벡터와 인라인 캐시, 객체 모양(히든 클래스)과 배열 종류(elements kind), 그리고 최적화가 무효화되는 역최적화를 다룹니다. 10장의 CPU 프로파일을 읽는 데 필요한 전제 지식입니다.

학습 목표

  • Ignition → Sparkplug → Maglev → TurboFan 파이프라인에서 각 티어가 무엇을 입력으로 받아 무엇을 만드는지, 언제 승격·강등되는지 설명할 수 있다.
  • 히든 클래스(Map) 전이와 인라인 캐시 상태(mono/poly/mega)를 코드에서 예측하고, 피드백이 오염되는 패턴을 식별할 수 있다.
  • 배열의 elements kind 전이 규칙을 알고 홀(hole)·타입 혼합이 만드는 비용을 설명할 수 있다.
  • --trace-opt/--trace-deopt/%GetOptimizationStatus로 실제 최적화 상태를 관찰하고 역최적화 원인을 읽을 수 있다.

1. 왜 티어가 네 개인가

컴파일에는 비용이 듭니다. 한 번만 실행될 코드를 공들여 최적화하면 손해이고, 백만 번 실행될 코드를 인터프리터로 돌리면 손해입니다. 어느 코드가 어느 쪽인지는 실행해 보기 전에는 모릅니다. 그래서 V8은 "일단 싸게 시작하고, 뜨거워진 코드만 점점 비싸게 컴파일하는" 적응형 구조를 택했고, 티어가 하나 늘 때마다 그 사이의 틈을 메워 왔습니다.

각 티어의 역할을 한 줄씩 정리하면:

  • Ignition: 파싱 직후 바이트코드를 만들어 바로 실행. 실행하면서 "이 자리에서 본 객체의 Map은 무엇이었나, 이 덧셈의 피연산자는 Smi였나"를 피드백 벡터에 기록합니다. 모든 상위 티어는 이 기록을 먹고 삽니다.
  • Sparkplug: 바이트코드를 거의 1:1로 기계어로 "번역"만 합니다. 추측이 없으므로 deopt도 없습니다. 인터프리터의 디스패치 오버헤드만 제거해서, "뜨겁지만 아직 피드백이 안정되지 않은" 구간을 메웁니다.
  • Maglev: 피드백을 써서 타입 특화·간단한 인라이닝을 하되 TurboFan보다 훨씬 빨리 컴파일합니다. 실무 코드의 대부분(짧게 뜨거운 함수)은 Maglev에서 끝납니다. Node 22(V8 12.4)부터 기본 활성입니다.
  • TurboFan: Sea-of-nodes IR 위에서(최근은 Turboshaft IR로 이행 중) 공격적 인라이닝, 탈출 분석(객체 할당 제거), 루프 최적화, 범위 분석을 수행합니다. 가장 뜨거운 소수 함수를 위한 것입니다.

승격은 호출 횟수와 루프 반복으로 소모되는 interrupt budget이 바닥날 때 검토되며, 뜨거운 루프 안에서는 함수 호출이 끝나기를 기다리지 않고 실행 중인 프레임을 교체하는 OSR(On-Stack Replacement)이 일어납니다. 컴파일은 기본적으로 백그라운드 스레드(1장의 V8 플랫폼 워커)에서 동시(concurrent)에 수행되고, 완료되면 다음 호출부터 새 코드가 쓰입니다.

2. Ignition: 바이트코드와 레지스터 머신

Ignition은 레지스터 머신입니다. 누산기(accumulator) 하나와 함수별 레지스터 파일(r0, r1…)이 있고, 인자는 a0, a1…로 접근합니다. 실제 출력을 보겠습니다.

$ node --print-bytecode --print-bytecode-filter=add -e "function add(a,b){return a+b} add(1,2)"
[generated bytecode for function: add]
Bytecode length: 6
Parameter count 3          ← this + a + b
Register count 0
   0 : Ldar a1              ← b 를 누산기에 로드
   2 : Add a0, [0]          ← 누산기 += a.  [0]은 피드백 벡터 슬롯 0
   5 : Return

세 가지를 눈여겨보세요. (1) Add a0, [0]의 [0]이 피드백 슬롯 인덱스입니다. Ignition은 이 덧셈을 실행할 때마다 슬롯 0에 "둘 다 Smi였다" 같은 힌트를 갱신합니다. (2) 바이트코드는 함수가 처음 호출될 때 지연 컴파일됩니다(파싱은 pre-parse로 가볍게 한 번 하고, 호출 시 full parse). 거대한 모듈을 로드해도 호출되지 않은 함수는 바이트코드가 없습니다. (3) 바이트코드는 힙에 있고 GC 대상입니다. V8은 오래 실행되지 않은 함수의 바이트코드를 flush(버림)하고 재호출 시 재컴파일할 수 있습니다. 메모리 압박이 큰 환경에서 "가끔 호출되는 함수가 느린" 이유 중 하나입니다.

바이트코드의 길이는 뒤에 나올 인라이닝 판단의 기준이기도 합니다. 함수가 "작다"는 말은 소스 줄 수가 아니라 바이트코드 바이트 수로 정의됩니다.

3. 관찰의 저장소: 피드백 벡터와 인라인 캐시

함수마다 FeedbackVector라는 배열이 하나 붙습니다. 바이트코드에서 "타입에 따라 동작이 달라질 수 있는 지점"(프로퍼티 접근, 호출, 산술 연산, instanceof 등)마다 슬롯이 하나씩 배정됩니다. 프로퍼티 접근 슬롯이 바로 인라인 캐시(IC)입니다.

o.x를 실행하려면 원칙적으로 o의 Map을 보고, 디스크립터 배열에서 'x'를 찾아, 오프셋을 알아내 메모리를 읽어야 합니다. IC는 "지난번에 Map M이 왔고 x는 오프셋 12였다"를 기억해 두고, 이번 객체의 Map이 M이면 조회를 건너뛰고 바로 오프셋 12를 읽습니다. 상태는 네 가지입니다.

비용 감각: 모노모픽은 Map 비교 1회 + 고정 오프셋 로드(몇 사이클). 폴리모픽은 최대 4개 Map을 순서대로 비교. 메가모픽은 전역 StubCache를 (Map, 이름) 해시로 조회하며, 그래도 없으면 런타임 조회(수백 사이클). 더 중요한 것은 셋째 통계입니다. TurboFan은 모노/폴리모픽 피드백만 특화 코드로 바꿀 수 있습니다. 메가모픽 접근은 최적화 코드 안에서도 일반 조회로 남고, 인라이닝 대상에서도 빠집니다.

피드백은 "함수의 자리"에 붙는다, 객체에 붙지 않는다 같은 o.x라도 다른 함수 안에 있으면 다른 슬롯입니다. 그래서 "범용 유틸리티 함수"가 위험합니다. 예를 들어 function get(obj, key) { return obj[key]; }를 코드베이스 전체가 공유하면, 그 한 슬롯에 수십 개의 Map이 모여 메가모픽이 되고, 그 함수를 호출하는 모든 핫패스가 느려집니다. lodash의 _.get, 공용 직렬화기, ORM의 필드 접근기가 전형적인 자리입니다.

4. 히든 클래스(Map)와 전이 트리

JavaScript 객체는 사전(dictionary)이지만, V8은 가능한 한 C 구조체처럼 다루려 합니다. 객체마다 Map(히든 클래스, 다른 엔진의 Shape)을 가리키는 포인터가 있고, Map은 "어떤 프로퍼티가 어떤 순서로 어떤 오프셋에 있는가"(DescriptorArray)와 프로토타입, elements kind를 담습니다. 같은 순서로 같은 프로퍼티를 추가한 객체는 같은 Map을 공유하고, Map들은 "프로퍼티 추가"를 간선으로 하는 전이 트리를 이룹니다.

4.1 Map이 갈라지는 순간들

  • 추가 순서가 다르면 다른 Map. {x:1, y:2}와 {y:2, x:1}은 형제가 아니라 다른 가지입니다. 리터럴로 만들면 순서가 고정되므로 생성자나 리터럴로 모든 필드를 한 곳에서 같은 순서로 초기화하는 것이 규칙입니다.
  • 값의 표현(representation)도 Map에 기록됩니다. 필드 x에 처음 Smi(정수)를 넣었다가 나중에 1.5를 넣으면 "x는 Double"로 Map 자체가 일반화되고, 이미 최적화된 코드는 그 가정이 깨져 deopt됩니다. null→객체도 마찬가지입니다(초기값은 undefined가 아닌 "같은 타입의 기본값"이 좋습니다. 단 이 규칙은 핫패스에서만 의미가 있습니다).
  • In-object 슬롯 수는 생성 시 추정됩니다. 생성자 본문을 보고 "이 객체는 필드 N개"로 잡아 두며(slack tracking), 그보다 많이 추가하면 out-of-object 백킹 스토어(PropertyArray)로 밀려 간접 참조가 하나 늘어납니다.
  • dictionary(slow) 모드로 떨어지는 조건: delete(마지막에 추가한 프로퍼티를 지우는 경우만 예외적으로 fast 유지), 프로퍼티가 매우 많아짐(한도 1020개, kMaxNumberOfDescriptors), 전이 트리가 지나치게 분기함, 프로퍼티를 계산된 이름으로 대량 추가(객체를 해시맵처럼 쓰는 경우). 느린 모드 객체의 프로퍼티 접근은 해시 조회이고 IC 혜택이 거의 없습니다. 해시맵이 필요하면 Map을 쓰세요.
  • Object.freeze, Object.defineProperty(비기본 속성), 접근자(getter/setter) 추가, __proto__ 변경도 Map 전이를 일으킵니다. 특히 프로토타입 변경은 그 프로토타입을 쓰는 모든 IC를 무효화하므로 핫패스에서 절대 하지 않습니다.

클래스를 쓰면 이 규칙이 자연스럽게 지켜집니다. 클래스 필드와 생성자가 같은 순서로 초기화하기 때문입니다. TypeScript의 ? 옵셔널 필드를 조건부로 할당하는 코드가 흔한 위반입니다.

5. 배열의 종류: elements kinds

배열의 요소는 프로퍼티와 별도의 저장소(elements)에 있고, 그 저장소의 "종류"도 Map에 기록됩니다. V8은 요소 타입이 균일할수록 더 빠른 코드를 만듭니다. 종류는 격자(lattice)를 이루며 전이는 한 방향(더 일반적인 쪽)으로만 갑니다. 한번 일반화되면 되돌아가지 않습니다.

5.1 왜 hole이 비싼가

a[i]를 읽을 때 PACKED이면 범위 검사 후 바로 로드합니다. HOLEY이면 로드한 값이 the_hole(V8 내부 센티널)인지 검사하고, 홀이면 프로토타입 체인(Array.prototype → Object.prototype)을 올라가며 그 인덱스를 찾아야 합니다(누군가 Array.prototype[3] = 'x'를 했을 수 있으니까). V8은 프로토타입 체인에 인덱스 프로퍼티가 없다는 사실을 "protector"로 캐시해 두어 빠른 경로를 유지하지만, 홀 검사 자체는 남습니다. 또 new Array(n)으로 만든 배열은 처음부터 HOLEY입니다. 크기를 미리 잡는 최적화가 오히려 손해일 수 있는 이유입니다(큰 배열을 채우는 경우에는 재할당 비용이 더 커서 여전히 이득인 경우도 있으니 측정하세요).

Double 배열은 실수를 언박싱해 8바이트 연속으로 저장하므로 수치 계산에 유리합니다. 그러나 거기에 문자열이나 객체를 하나라도 넣으면 PACKED_ELEMENTS로 일반화되며 모든 실수가 HeapNumber로 박싱되어 재할당됩니다. 대량 수치 데이터는 Float64Array 같은 TypedArray가 종류 전이 자체를 없애 주는 정답입니다.

Node 특이점: Node의 V8은 포인터 압축 없이 빌드되므로 Smi는 32비트 부호 정수 범위입니다(Chrome은 31비트). 2**31부터는 HeapNumber가 되어 배열이 DOUBLE로 전이합니다. 타임스탬프(ms)는 Smi 범위를 넘으므로 [Date.now(), …]는 처음부터 DOUBLE 배열입니다.

6. 승격과 역최적화

티어 승격 타임라인 시뮬레이터

6.1 역최적화의 종류와 원인

최적화 코드는 "가정"을 코드에 박아 넣고, 가정 검사(check)가 실패하면 그 지점의 상태를 인터프리터 프레임으로 재구성해 Ignition으로 빠져나옵니다. 이것이 deopt이고, 비용은 프레임 변환 자체(수 µs)보다 최적화 코드를 잃고 다시 올라와야 한다는 것입니다.

종류언제예
eager최적화 코드 실행 중 검사 실패. 즉시 탈출wrong map(다른 Map 유입), not a Smi(정수 가정 깨짐), out of bounds, hole, wrong call target
lazy코드는 멀쩡하지만 의존하던 외부 가정이 바뀜. 다음 복귀 시점에 탈출인라인한 함수의 프로토타입이 변경됨, 의존하던 전역 상수가 바뀜, Map이 deprecated됨(필드 표현 일반화)
soft피드백이 부족해 추측 불가. 더 수집하러 내려감insufficient type feedback: 아직 실행된 적 없는 분기가 최적화 코드에서 처음 실행됨
$ node --trace-deopt app.js
[bailout (kind: deopt-eager, reason: wrong map): begin. deoptimizing 0x… <JSFunction getX>,
  0x… <Code TURBOFAN_JS>, opt id 0, bytecode offset 0, deopt exit 1, …]
                      ↑ 종류          ↑ 원인                                   ↑ 바이트코드 위치

원인 문자열이 곧 진단입니다. wrong map이면 4절(모양 불일치), not a Smi / not a Number면 5절(타입 섞임)이나 필드 표현 변화, hole이면 홀 배열, insufficient type feedback이면 콜드 분기가 뒤늦게 실행된 것(한 번은 정상). 같은 함수가 반복적으로 deopt되면 V8은 결국 그 함수의 최적화를 포기합니다(deopt loop 방지). --trace-opt에서 더 이상 marking이 안 보이면 그 상태입니다.

7. 인라이닝과 그 한계

TurboFan 최적화의 대부분은 인라이닝 이후에 가능해집니다. 호출을 본문으로 치환해야 상수 전파, 탈출 분석(임시 객체 할당 제거), 범위 검사 제거가 함수 경계를 넘어 작동하기 때문입니다. 따라서 "인라이닝이 안 되는 이유"가 곧 "최적화가 안 되는 이유"입니다.

  • 크기 한도: 피호출 함수 바이트코드 ≤ --max-inlined-bytecode-size(기본 460바이트), 한 함수에 누적 ≤ --max-inlined-bytecode-size-cumulative(기본 920). 뜨거운 작은 함수 여러 개를 호출하는 함수는 뒤쪽 호출이 누적 한도에 걸립니다.
  • 호출 대상이 하나여야: 호출 지점의 피드백이 모노모픽(같은 함수)이거나 소수 폴리모픽이어야 합니다. 콜백을 받는 범용 고차 함수(arr.map(fn)의 내부, 이벤트 에미터의 emit)는 대상이 수십 개라 인라이닝되지 않습니다. 단 Array.prototype.map/forEach/reduce 등은 TurboFan이 빌트인 자체를 인라이닝하고, 그 안의 콜백도 호출 지점이 모노모픽이면 함께 인라이닝합니다.
  • 인라이닝 불가 대상: 일부 네이티브 바인딩 호출, eval/with를 포함한 함수, 제너레이터·async 함수의 일부 경로, 거대 함수.
  • 관찰: --trace-turbo-inlining으로 어떤 호출이 왜 인라이닝되지 않았는지 출력됩니다.
인라이닝 한도 때문에 "작은 함수로 쪼개기"가 항상 이득은 아니다 핫 루프에서 유틸 함수 10개를 호출하면 누적 920바이트 한도에 걸려 뒤쪽은 실제 call이 됩니다. 반대로 함수 하나가 너무 크면(수천 바이트) 그 자체가 최적화 대상에서 제외되기도 합니다. 프로파일(10장)로 핫패스를 확인한 뒤 그 경로만 조정하세요. 코드베이스 전체에 적용할 규칙이 아닙니다.

8. 관찰 도구와 Node 특이점

$ node --trace-opt --trace-deopt app.js 2>&1 | grep -E "sum|getX"
[marking 0x… <JSFunction sum> for optimization to MAGLEV, ConcurrencyMode::kConcurrent, reason: hot and stable]
[compiling method 0x… <JSFunction sum> (target MAGLEV), mode: ConcurrencyMode::kConcurrent]
[completed compiling 0x… <JSFunction sum> (target MAGLEV) - took 0.1, 0.8, 0.0 ms]
[marking 0x… <JSFunction sum> for optimization to TURBOFAN, …, reason: hot and stable]
[bailout (kind: deopt-eager, reason: wrong map): begin. deoptimizing … <JSFunction sum> …]

# 특정 함수만: --trace-opt-verbose, 출력이 많으면 grep. 프로덕션에서는 짧은 구간만 켠다.
// --allow-natives-syntax 필요. 테스트/벤치마크 전용 (프로덕션 금지)
function getX(o) { return o.x; }
%PrepareFunctionForOptimization(getX);   // 피드백 벡터 확보 (없으면 최적화가 거부됨)
getX({ x: 1 }); getX({ x: 1 });          // 피드백 수집
%OptimizeFunctionOnNextCall(getX);        // 다음 호출 때 최적화 (기본 Maglev 또는 TurboFan: 버전에 따라)
getX({ x: 1 });
console.log((%GetOptimizationStatus(getX)).toString(2));
// 비트 (V8 runtime-test.cc, 버전 간 변동 가능):
//  1 함수임   2 never optimize   4 always optimize   8 maybe deopted
// 16 optimized(TurboFan)   32 Maglev 코드   64 TurboFan 코드   128 interpreted
getX({ y: 2, x: 1 });                     // 다른 Map → wrong map deopt
console.log((%GetOptimizationStatus(getX)).toString(2)); // 16/32 비트가 사라짐

벤치마크에서 "최적화가 된 상태"를 보장하려면 이 네이티브 구문이 가장 확실합니다. 단 --allow-natives-syntax는 파서를 바꾸므로 프로덕션 플래그에 절대 넣지 마세요.

$ node --print-bytecode --print-bytecode-filter=함수이름 app.js   # Ignition 바이트코드
$ node --log-ic app.js && node v8/tools/ic-processor v8.log         # IC 전이 로그 (V8 소스의 도구 필요)
$ node --print-opt-code --code-comments app.js                       # 최적화된 기계어 (매우 많음)
$ node --cpu-prof app.js                                             # 10장: 어떤 함수가 뜨거운가가 먼저
$ node --no-opt app.js          # Maglev·TurboFan 끔: 성능 차이로 "최적화 의존도" 측정
$ node --no-maglev app.js       # Maglev만 끔 (Node 20 이하 동작 재현)
$ node --always-sparkplug app.js
$ node --jitless app.js         # JIT 전면 금지(인터프리터만). 보안 격리 환경·메모리 절약용. WASM 불가
$ node --max-inlined-bytecode-size=1000 app.js   # 인라이닝 한도 조정 (측정 없이 바꾸지 말 것)

// 런타임에서 (프로세스 초기에만 안전)
require('node:v8').setFlagsFromString('--no-maglev');

Node에서만 신경 쓸 것

  • 포인터 압축 없음: Smi 32비트, 객체 포인터 8바이트. Chrome 수치(Smi 31비트, 힙 4GB 캡)와 다릅니다. 힙 상한은 --max-old-space-size로 수 GB 이상 가능(5장).
  • 백그라운드 컴파일 스레드: 최적화 컴파일은 V8 플랫폼 워커에서 돕니다. 컨테이너 CPU 할당량이 1 vCPU면 메인 스레드와 경쟁합니다. 부팅 직후 CPU 스파이크의 일부는 JIT 컴파일입니다.
  • 장기 실행 프로세스: 피드백은 프로세스 수명 내내 누적됩니다. 부팅 시 한 번 실행되는 경로가 핫 함수의 피드백을 오염시키면(예: 마이그레이션 코드가 같은 유틸을 다른 Map으로 호출) 그 함수는 영원히 폴리모픽입니다. 벤치마크는 항상 워밍업 후 측정하고, 프로덕션 프로파일은 부팅 후 충분히 지난 시점에 뜹니다.

9. 실전 규칙과 신화 정리

지키면 이득인 것 (핫패스 한정)

  • 객체는 생성자/리터럴에서 모든 필드를 같은 순서로 초기화한다. 조건부 필드는 undefined/null로라도 자리를 만든다.
  • 필드의 타입을 바꾸지 않는다(정수→실수, 숫자→문자열, null→객체). 처음부터 해당 타입으로.
  • delete를 쓰지 않는다. 필요하면 undefined 대입. 동적 키 집합은 Map.
  • 배열은 한 종류의 값만 담고, 홀을 만들지 않는다(push로만 채우기). 수치 대량 데이터는 TypedArray.
  • 범용 접근자 함수(get(obj, key))를 핫패스 공용으로 쓰지 않는다. 메가모픽의 온상.
  • 프로토타입을 런타임에 바꾸지 않는다(Object.setPrototypeOf, 클래스 패치). 부팅 시 한 번은 괜찮다.
  • 최적화 상태를 측정한다. 규칙을 지켰다고 가정하지 말고 --trace-deopt로 확인한다.

더 이상 사실이 아닌 것 (Crankshaft 시절의 민간 전승)

신화현재(TurboFan/Maglev)
try/catch가 있는 함수는 최적화되지 않는다2017년(V8 5.x)부터 최적화됩니다. 핫 루프 안에 try/catch를 두어도 됩니다.
arguments 객체를 쓰면 최적화 불가대부분의 사용 패턴(arguments.length, 인덱스 접근, Array.from)은 최적화됩니다. 레스트 파라미터가 더 명확하니 권장하지만 성능 이유는 아닙니다.
함수가 짧을수록 무조건 빠르다인라이닝 누적 한도(920바이트)가 있습니다. 측정 없이 쪼개지 마세요.
for가 forEach보다 항상 빠르다콜백 호출 지점이 모노모픽이면 forEach/map도 빌트인 인라이닝으로 거의 동일합니다. 차이가 나는 경우는 콜백이 폴리모픽일 때입니다.
클래스는 느리고 객체 리터럴이 빠르다반대에 가깝습니다. 클래스는 Map 일관성을 강제합니다.
const/let이 var보다 느리다차이 없습니다(TDZ 검사는 대부분 제거됨).

10. 현업 장애 사례

사례 1: ORM 모델 접근이 메가모픽

API 응답 직렬화가 느렸고 CPU 프로파일에서 serializeField(obj, name)라는 작은 함수가 전체의 25%. 수십 개의 모델 클래스를 모두 같은 함수로 직렬화하니 obj[name]의 IC가 메가모픽. 모델별 직렬화 함수를 코드 생성(new Function)으로 만들어 각 함수의 IC를 모노모픽으로 바꾸자 직렬화 비용 70% 감소. fast-json-stringify, ajv가 스키마별 함수를 생성하는 이유가 정확히 이것입니다.

사례 2: 배포 후 p99만 나빠진 타임스탬프 파싱

이벤트 객체에 ts 필드를 정수(초)로 저장하다가 밀리초 정밀도로 바꾸면서 일부 경로가 실수를 넣기 시작. Map의 필드 표현이 Smi→Double로 일반화되면서 그 Map을 가정한 모든 최적화 코드가 lazy deopt, 재최적화 반복. 한동안 p99가 두 배. --trace-deopt에서 not a Smi와 Map deprecation이 반복 관측됨. 모든 생성 경로에서 Number(실수)로 통일하자 안정화.

사례 3: 1 vCPU 컨테이너의 부팅 직후 타임아웃

부팅 후 첫 1~2분간 요청 지연이 높고 헬스체크가 간헐 실패. 원인은 세 가지 합: (a) 모든 핫 함수가 Ignition에서 시작해 승격 중, (b) 백그라운드 컴파일 스레드가 메인과 1 vCPU를 나눠 씀, (c) 첫 요청들이 피드백을 수집하는 동안 soft deopt 반복. 대응: k8s startupProbe와 워밍업 트래픽(합성 요청 수백 건)으로 승격을 끝낸 뒤 readiness를 올림(14장). CPU 할당량을 1에서 2로 올리는 것도 효과가 컸습니다.

핵심 요약

  • 파이프라인: Ignition(바이트코드·피드백 수집) → Sparkplug(비추측 베이스라인) → Maglev(Node 22+, 빠른 중간 최적화) → TurboFan(최상위). 승격은 interrupt budget, 루프는 OSR, 컴파일은 백그라운드.
  • 최적화의 원료는 피드백 벡터. 프로퍼티 접근 슬롯 = 인라인 캐시. mono(1) → poly(2~4) → mega(5+). 메가모픽은 최적화 코드에서도 느리고 되돌아가지 않는다.
  • Map(히든 클래스)은 프로퍼티 추가 순서로 결정되는 전이 트리. 순서 불일치, 타입 변경, delete, 과다 프로퍼티가 Map을 분기·일반화·dictionary화한다.
  • elements kind는 PACKED/HOLEY × SMI/DOUBLE/ELEMENTS 격자, 전이는 일반화 방향으로만. new Array(n)은 HOLEY, 타입 섞으면 박싱. Node의 Smi는 32비트.
  • 역최적화: eager(검사 실패) / lazy(외부 가정 변경) / soft(피드백 부족). --trace-deopt의 reason이 진단이다. 반복되면 최적화 포기.
  • 인라이닝 한도 460/920바이트, 호출 대상 모노모픽 필요. try/catch·arguments 신화는 끝났다.
  • 측정 없이 규칙을 적용하지 말 것. 핫패스를 프로파일로 찾고(10장) 그 경로만 손본다.

확인 문제

function f(o){return o.v}가 {v:1}, {v:1, w:2}, {w:2, v:1}, {v:1, w:2, x:3}, {u:0, v:1} 다섯 종류의 객체로 반복 호출된다. 이 접근의 IC 상태는?
프로퍼티 집합이 아니라 Map이 기준입니다. 다섯 객체는 추가 순서·집합이 모두 달라 Map이 5개이고, 5개째에서 메가모픽으로 떨어집니다. 이후 TurboFan은 이 접근을 특화하지 못합니다.
const a = [1, 2, 3]; a.push(4.5); a.push(1); 이후 a의 elements kind는?
4.5를 넣는 순간 SMI→DOUBLE로 전이하고, 이후 정수를 넣어도 DOUBLE로 남습니다(정수도 double로 저장). 전이는 일반화 방향으로만 일어납니다.
--trace-deopt에 reason: insufficient type feedback이 한 번 찍혔다. 적절한 해석은?
soft deopt입니다. 피드백이 없는 분기를 최적화 코드가 만나면 수집하러 내려갑니다. 같은 자리에서 반복되면 그 분기가 사실상 핫한데 피드백이 계속 리셋되는 것이므로 원인을 봐야 합니다.
Sparkplug에서 실행 중인 코드가 역최적화될 수 있는가?
Sparkplug는 바이트코드를 기계어로 1:1 번역할 뿐 타입 가정을 넣지 않습니다. 그래서 컴파일이 매우 빠르고 안전하며, 피드백이 안정되기 전 구간을 메우는 역할을 합니다.
핫 함수 A가 작은 유틸 함수 12개를 차례로 호출한다. TurboFan에서 관찰될 가능성이 가장 높은 것은?
--max-inlined-bytecode-size-cumulative가 함수 하나에 인라이닝할 수 있는 총량을 제한합니다. --trace-turbo-inlining으로 어느 호출에서 멈췄는지 볼 수 있습니다.
