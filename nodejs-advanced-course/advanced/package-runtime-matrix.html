패키지 호환성과 런타임 업그레이드

선수 장 · exports와 조건부 해석

앱 소스의 import가 같아도 exports 조건이나 네이티브 바이너리 때문에 업그레이드 결과가 달라질 수 있습니다. 모듈 해석에서 소비자 환경별 검증 행렬로 이동합니다.

공개 표면과 두 소비자

작은 테스트 패키지에 exports를 두고 CJS 소비자와 ESM 소비자를 따로 만듭니다. require("pkg")와 import ... from "pkg"가 선택하는 엔트리를 로그로 확인합니다. 두 엔트리가 별도의 상태 객체를 만들면 같은 패키지를 두 방식으로 읽은 소비자가 서로 다른 singleton을 볼 수 있습니다.

내부 파일 경로를 직접 참조하는 소비자는 공개 exports 경계를 벗어납니다. package.json의 type, 파일 확장자, import/require 조건을 함께 검사합니다. TypeScript 타입 검사가 통과해도 실제 Node가 선택한 런타임 파일이 맞다는 증거는 아니므로 설치된 패키지 산출물로 실행합니다.

호환성 행렬에 포함할 축

지원하기로 정한 Node 메이저별로 CJS/ESM·정상 시작·종료·주요 API를 실행하고 process.version과 process.versions를 결과에 남깁니다. lockfile로 의존성을 고정한 비교와 의존성 업데이트를 함께 한 비교를 분리해야 원인을 좁힐 수 있습니다.

Node-API를 사용해도 플랫폼·아키텍처·런타임이 제공하는 API 버전과 외부 공유 라이브러리 조건은 남습니다. V8 API에 직접 의존한 애드온과 Node-API ABI 계약을 구분합니다. 빌드 머신에서 실행됐다는 사실만으로 배포 이미지의 libc·아키텍처 호환성을 주장하지 않습니다.

실습과 예상 관찰

자신의 작은 패키지를 임시 프로젝트에 설치해 CJS/ESM 소비자 두 개를 실행하세요. 지원할 두 Node 버전에서 같은 lockfile과 입력으로 반복하고 공개 API 결과·선택된 엔트리·종료 코드를 기록합니다. 네이티브 의존성이 있으면 실제 배포 이미지에서도 같은 smoke test를 수행하세요.

소스만 실행하고 패키지 산출물 생략

잘못된 exports 대상이나 배포 누락 파일을 놓칠 수 있습니다. 소비자가 설치할 형태의 파일을 검사해야 합니다.

버전·모듈 방식·배포 환경을 나눠 검사

어느 축에서 달라졌는지 좁힐 수 있습니다. 한 행의 성공을 전체 지원 범위 성공으로 확대하지 않습니다.

실습의 경계와 다음 장

실험은 지원 범위를 스스로 정한 로컬 패키지에 한정합니다. 다음 배포 장에서는 빌드한 산출물의 기동·의존성·종료를 동일하게 확인합니다.
