실제 자료로 푸는 장애 분석

선수 장 · 가상 장애 상황실

상황실에서 정답 도구를 골랐다면 이제 자신이 만든 로컬 작업의 원시 자료로 같은 판단을 해 봅니다. 그래프와 설명을 실제 파일의 어느 위치에서 확인했는지 남깁니다.

가설별로 필요한 파일 고르기

CPU 계산이 많은 정상 작업은 node --cpu-prof app.js로 프로파일을 만들고 정상 종료해 파일을 남깁니다. 일시 대기나 외부 지연은 CPU 샘플이 적게 보여도 전체 지연이 길 수 있으므로 경과 시간과 이벤트 루프 지표를 함께 봅니다. flame graph의 폭을 시간순 사건 목록으로 읽지 않습니다.

메모리 보유는 같은 입력 전후의 heap snapshot과 memoryUsage 추세로 비교합니다. GC 전후 한 숫자만으로 누수라고 단정하지 말고 retained 경로와 반복 증가를 확인합니다. snapshot은 수집 자체가 메모리·정지를 추가하므로 작은 로컬 작업에서 시작합니다.

관측과 해석을 분리한 분석서

원시 파일, Node 버전, 입력 크기, 실행 옵션, 수집 시점과 종료 상태를 함께 저장합니다. 프로파일에서 JSON.stringify 비중이 크다는 관측과 로그 직렬화가 원인이라는 해석은 다른 문장으로 적습니다. 관련 코드를 한 가지 바꾼 뒤 같은 입력과 지표로 다시 비교합니다.

대안 가설 하나 이상을 남기고 어떤 자료가 그것을 지지하거나 기각하는지 적습니다. 샘플링에 안 잡힌 짧은 함수, trace 수집 구간 밖 사건, snapshot이 보지 못하는 네이티브 메모리의 한계를 명시합니다. 도구 출력이 없다는 사실을 사건이 없었다는 증거로 바꾸지 않습니다.

실습과 예상 관찰

로컬에서 문자열 직렬화를 반복하는 작업과 timer로 기다리는 작업을 같은 경과 시간 규모로 만드세요. 각각 cpuprofile·Diagnostic Report·memoryUsage 로그를 수집하고 CPU/대기 가설을 구분합니다. 작은 보유 배열을 반복 생성·해제한 snapshot 비교도 수행해 관측·해석·다음 검증을 세 칸으로 제출하세요.

CPU 샘플이 계산 함수에 집중

해당 수집 구간의 CPU 사용 경로를 지지합니다. 전체 요청 지연이 같은 비중으로 줄어든다는 뜻은 아닙니다.

지연은 긴데 CPU 샘플이 적음

외부 대기·스케줄링·수집 범위 같은 가설이 남습니다. 큐·연결·경과 시간 자료로 교차 확인해야 합니다.

실습의 경계와 다음 장

이 장은 제공되지 않은 실제 artifact의 결과를 대신 만들어 내지 않습니다. 프로파일 장으로 돌아가 원시 파일의 근거와 반복 측정 조건을 직접 연결합니다.
