에러 처리와 복원력 패턴

Node.js 프로세스 하나가 수천 요청을 동시에 처리한다는 사실은 에러 처리의 의미를 바꿉니다. 예외 하나가 프로세스를 죽이면 수천 요청이 함께 죽고, 반대로 죽어야 할 프로세스를 살려 두면 오염된 상태로 수천 요청을 망칩니다. 이 장은 "어떤 에러는 삼키고 어떤 에러는 죽어야 하는가"의 원칙에서 시작해, 외부 의존성이 흔들릴 때 서비스가 버티는 복원력 패턴까지 다룹니다.

학습 목표

  • 프로그래머 에러와 운영 에러를 구분하고 uncaughtException·unhandledRejection의 올바른 정책을 설명할 수 있다.
  • Error.cause, 커스텀 에러 클래스, code 프로퍼티로 진단 가능한 에러 객체를 설계할 수 있다.
  • SIGTERM부터 프로세스 종료까지의 그레이스풀 셧다운을 keep-alive 커넥션까지 포함해 구현할 수 있다.
  • 타임아웃·재시도·백오프·서킷 브레이커·벌크헤드를 조합해 외부 의존성 장애를 격리할 수 있다.

1. 에러의 두 종류

Joyent의 고전 가이드 "Error Handling in Node.js"가 세운 구분은 지금도 유효합니다. 에러는 운영 에러(operational error)와 프로그래머 에러(programmer error) 둘 중 하나이며, 둘은 처리 방법이 정반대입니다.

운영 에러프로그래머 에러
정의올바른 프로그램이 런타임에 만나는 예상 가능한 실패코드의 버그. 프로그램이 잘못 작성됨
예ECONNREFUSED, ETIMEDOUT, DB 연결 끊김, 디스크 가득 참, 잘못된 사용자 입력, 429/503 응답undefined의 프로퍼티 읽기, 잘못된 인자 타입, 없는 콜백 호출, Promise reject 누락
복구가능: 재시도, 폴백, 사용자에게 보고, 로그 후 진행불가능: 프로그램 상태를 신뢰할 수 없음. 가장 안전한 것은 크래시 후 재시작
잡는 위치발생 지점에 가장 가까운, 복구 결정을 내릴 수 있는 곳잡지 않는다. 프로세스 수준 핸들러에서 로그만 남기고 종료
에러 객체code, 컨텍스트 정보, 재시도 가능 여부를 담아 설계TypeError, RangeError, AssertionError 등 언어가 던짐
왜 프로그래머 에러에서 계속 진행하면 안 되는가 uncaughtException에 도달했다는 것은 어떤 콜백 스택 중간에서 예외가 튀어나왔다는 뜻입니다. 그 콜백이 잠그려던 락, 갱신 중이던 Map, 반쯤 쓴 응답, 끊으려던 DB 커넥션이 모두 미완 상태로 남습니다. 프로세스를 살려 두면 그 상태 위에서 다음 수천 요청이 실행됩니다. 크래시는 상태를 확실히 버리는 유일한 방법이고, 재시작은 프로세스 매니저·오케스트레이터(14장)의 일입니다. "에러 하나로 프로세스가 죽으면 안 된다"는 요구는 크래시를 막는 것이 아니라 프로그래머 에러를 운영 에러로 바꾸는 것(입력 검증, 타입 체크)으로 충족해야 합니다.

2. 프로세스 수준 핸들러

2.1 uncaughtException

process.on('uncaughtException', (err, origin) => {
  // origin: 'uncaughtException' | 'unhandledRejection'
  logger.fatal({ err, origin }, 'uncaught exception, exiting');   // 동기 flush 되는 로거여야 한다 (15장)
  // 할 수 있는 일: 로그, 메트릭 전송(동기), 셧다운 시작 신호
  // 하면 안 되는 일: 정상 동작 재개, 새 요청 수락
  shutdown({ reason: 'uncaught', timeoutMs: 5_000 }).finally(() => process.exit(1));
});

핸들러를 등록하면 Node.js는 기본 동작(스택 출력 후 종료 코드 1)을 하지 않습니다. 즉 핸들러에서 직접 종료하지 않으면 프로세스는 계속 돕니다. 공식 문서는 이 핸들러를 "동기 리소스 정리 후 종료" 용도로만 쓰라고 못박습니다. 핸들러 안에서 또 예외가 나면 프로세스는 즉시 종료됩니다. 셧다운이 끝나지 않는 상황에 대비해 타임아웃 후 process.exit(1)을 강제하세요.

디버깅 시에는 --abort-on-uncaught-exception으로 코어 덤프를 남기거나, process.setUncaughtExceptionCaptureCallback()으로 단일 캡처 콜백을 둘 수 있습니다(이 콜백이 있으면 'uncaughtException' 이벤트는 발화하지 않음).

2.2 unhandledRejection

Node 15부터 처리되지 않은 Promise 거부는 기본적으로 uncaughtException으로 승격되어 프로세스를 죽입니다(--unhandled-rejections=throw가 기본). 콜백 세계의 "에러를 던지면 죽는다"와 같은 의미론을 Promise에도 적용한 것입니다. 다른 모드:

--unhandled-rejections=동작
throw (기본)'unhandledRejection' 핸들러가 있으면 호출, 없으면 uncaughtException으로 던짐
strict핸들러 유무와 무관하게 항상 uncaughtException으로 던짐 (핸들러는 그 뒤에 호출)
warn경고만 출력하고 계속 (Node 14 이하의 동작)
warn-with-error-code경고 + 종료 코드 1 설정
none무시
process.on('unhandledRejection', (reason, promise) => {
  // 'throw' 모드에서 이 핸들러를 달면 프로세스가 죽지 않는다 → 프로그래머 에러를 삼키게 됨
  // 권장: 로그만 남기고 다시 던져 uncaughtException 경로로 보낸다
  logger.error({ err: reason }, 'unhandled rejection');
  throw reason;
});

"처리되지 않음"의 판정 시점은 마이크로태스크 큐가 비워진 직후(2장의 processTicksAndRejections 끝)입니다. 같은 틱 안에서 나중에 .catch를 붙이면 처리된 것으로 간주되고, 한 틱 뒤에 붙이면 먼저 'unhandledRejection'이 나고 이어서 'rejectionHandled'가 납니다. const p = fetchX(); await other(); await p; 같은 코드에서 fetchX가 먼저 거부되면 바로 이 상황이 됩니다. 병렬 실행은 Promise.all/allSettled로 즉시 묶으세요.

2.3 exit, beforeExit, 시그널

  • 'exit': 종료 직전. 동기 코드만 실행됨. 타이머·I/O를 걸어도 실행되지 않는다. 종료 코드 기록, 동기 로그 flush 정도.
  • 'beforeExit': 이벤트 루프가 비어 자연 종료하려 할 때. 여기서 비동기 작업을 걸면 루프가 계속 돈다. process.exit() 호출 시에는 발화하지 않음.
  • SIGTERM/SIGINT: 핸들러를 달면 기본 동작(즉시 종료)이 사라진다. 그레이스풀 셧다운(5절)의 진입점. SIGKILL은 잡을 수 없다.
  • process.exitCode = 1: process.exit()와 달리 진행 중인 I/O를 끊지 않고 자연 종료 시 코드만 설정. 가능하면 이쪽을 쓴다.

3. 에러가 전달되는 네 가지 통로

Node.js에는 에러를 전달하는 경로가 네 가지 있고, 각 통로마다 "안 받으면 어떻게 되는가"가 다릅니다. 라이브러리 설계와 호출 코드 모두 이 표를 따라야 합니다.

통로언제받는 법안 받으면
throw동기 함수. 프로그래머 에러(잘못된 인자)는 비동기 함수에서도 동기적으로 throw하는 것이 관례try/catch스택을 타고 올라가 uncaughtException
Promise rejectasync 함수, Promise 기반 APIawait + try/catch, .catch()unhandledRejection → 기본 throw
callback(err)Node 스타일 콜백 API (error-first)첫 인자 검사조용히 무시됨 (가장 위험). util.promisify로 Promise 통로로 바꾸자
'error' 이벤트EventEmitter: 스트림, 소켓, 서버, 자식 프로세스.on('error', fn)리스너가 없으면 throw → uncaughtException. 스트림/소켓 'error' 미처리가 Node 크래시의 1위 원인

스트림과 pipeline

// 나쁜 예: 세 스트림 중 하나라도 'error' 리스너가 없으면 크래시. pipe()는 에러를 전파하지 않고 소스를 정리하지도 않는다.
fs.createReadStream(src).pipe(zlib.createGzip()).pipe(fs.createWriteStream(dst));

// 좋은 예: pipeline은 모든 스트림에 에러·종료를 전파하고, 실패 시 전부 destroy한다
const { pipeline } = require('node:stream/promises');
try { await pipeline(fs.createReadStream(src), zlib.createGzip(), fs.createWriteStream(dst), { signal }); }
catch (err) { if (err.name !== 'AbortError') throw err; }

4. 에러 객체 설계

좋은 에러 객체는 세 질문에 답합니다. 무엇이(code), 어디서(stack, 컨텍스트), 원래 원인은(cause). Node.js 코어의 에러(ERR_INVALID_ARG_TYPE 등)가 좋은 모델입니다.

class AppError extends Error {
  constructor(message, { code, status = 500, retryable = false, cause, ...ctx } = {}) {
    super(message, { cause });                     // ES2022 Error.cause: 원인 체인 보존 (Node 16.9+)
    this.name = new.target.name;                   // 서브클래스 이름이 스택 첫 줄에 나오도록
    this.code = code;                              // 기계가 분기할 안정적 식별자. message는 사람용이라 바뀔 수 있다
    this.status = status; this.retryable = retryable;
    Object.assign(this, ctx);                      // userId, orderId 같은 진단 컨텍스트
    Error.captureStackTrace?.(this, new.target);   // 생성자 프레임을 스택에서 제외 (V8)
  }
}
class UpstreamError extends AppError {}
class ValidationError extends AppError { constructor(msg, ctx) { super(msg, { code: 'E_VALIDATION', status: 400, ...ctx }); } }

// 사용: 하위 레이어의 에러를 감싸 의미를 더하되 원인을 잃지 않는다
try { await db.query(sql); }
catch (err) { throw new UpstreamError('order lookup failed', { code: 'E_DB', retryable: err.code === 'ECONNRESET', cause: err, orderId }); }

// 로거는 cause 체인을 재귀적으로 직렬화해야 한다 (pino의 err serializer는 cause를 지원)
// util.inspect(err)도 [cause]를 출력한다
  • code로 분기, message로 분기 금지. err.message.includes('timeout') 같은 코드는 라이브러리 버전 업에서 깨집니다.
  • AggregateError: Promise.any가 던지며, 여러 병렬 실패를 하나로 묶을 때 직접 쓸 수도 있습니다(errors 배열).
  • 스택 깊이: Error.stackTraceLimit 기본 10. 깊은 미들웨어 체인에서 원인 프레임이 잘리면 늘리되, 스택 캡처는 비싸므로(V8이 프레임을 걷는다) 핫패스에서 Error를 흐름 제어용으로 만들지 마세요.
  • 비동기 스택: V8의 async stack trace는 await 체인은 이어 주지만 setTimeout·이벤트 경계는 잇지 못합니다. 7장의 AsyncLocalStorage로 요청 ID를 모든 로그에 실어 보완합니다.
  • HTTP 응답으로 변환은 한 곳(최종 에러 미들웨어)에서. 운영 에러는 status·code를 노출하고, 프로그래머 에러는 500 + 내부 ID만 노출합니다(스택·내부 메시지 노출은 16장의 정보 유출).

5. 그레이스풀 셧다운

배포·스케일인·노드 교체 때마다 프로세스는 SIGTERM을 받습니다(14장: k8s는 SIGTERM 후 terminationGracePeriodSeconds, 기본 30초 뒤 SIGKILL). 이 30초 안에 진행 중인 요청을 끝내고, 새 요청은 받지 않고, 외부 리소스를 정리해야 합니다. 순서가 중요합니다.

그레이스풀 셧다운 스텝 애니메이션
SIGTERM 수신 시점에 진행 중인 요청 3개와 keep-alive 유휴 커넥션 4개가 있는 서버. 각 단계에서 커넥션이 어떻게 처리되는지 봅니다. "느린 요청" 옵션을 켜면 타임아웃 분기로 갑니다.
const server = http.createServer(app).listen(PORT);
let shuttingDown = false;

async function shutdown(signal) {
  if (shuttingDown) return; shuttingDown = true;
  logger.info({ signal }, 'shutdown: start');
  const forceTimer = setTimeout(() => { logger.error('shutdown: timeout, forcing exit'); process.exit(1); }, 25_000).unref();  // grace period보다 짧게

  // ① readiness를 실패시켜 LB/k8s가 새 트래픽을 보내지 않게 (전파까지 수 초 걸리므로 잠시 대기)
  healthz.setReady(false);
  await sleep(3_000);

  // ② listen 중단 + 유휴 keep-alive 커넥션 종료. Node 19+의 server.close()는 closeIdleConnections()를 자동 호출.
  //    진행 중인 요청의 커넥션은 응답 완료 후 닫힌다 (응답에 Connection: close 헤더가 붙음).
  server.close();
  server.closeIdleConnections();            // Node 18.2+. 19 미만에서는 명시 호출 필요

  // ③ in-flight 작업 완료 대기 (큐 컨슈머 중단, 배치 flush 등)
  await Promise.allSettled([queue.stop(), jobs.drain()]);

  // ④ 외부 리소스 정리: DB 풀, 캐시, 트레이서 flush
  await Promise.allSettled([db.end(), redis.quit(), tracer.shutdown()]);

  clearTimeout(forceTimer);
  logger.info('shutdown: done');
  process.exitCode = 0;                      // 자연 종료. 남은 핸들이 있으면 위 forceTimer가 처리
}
process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT', () => shutdown('SIGINT'));
server.close()만으로는 끝나지 않는다 server.close(cb)의 콜백은 모든 커넥션이 닫혀야 호출됩니다. keep-alive 유휴 커넥션은 클라이언트가 닫기 전까지 살아 있으므로, Node 18 이하에서는 close 콜백이 keepAliveTimeout(5s)이나 LB가 끊어 줄 때까지 오지 않았습니다. Node 18.2의 closeIdleConnections()가 이를 해결했고 19부터 close()가 자동 호출합니다. 그래도 요청 처리 중인 커넥션은 응답이 끝나야 닫히므로, 오래 걸리는 요청(스트리밍, 롱폴링)에는 별도의 종료 신호(AbortSignal)를 주고 closeAllConnections()를 최후 수단으로 둡니다.

6. 타임아웃과 데드라인 전파

복원력 패턴의 첫 번째이자 가장 중요한 규칙: 모든 외부 호출에는 타임아웃이 있다. 타임아웃이 없는 호출은 상대가 멈추면 함께 멈추고, 그 사이 소켓·메모리·요청 슬롯을 점유하며(12장 사례 2), 호출자의 호출자까지 연쇄로 멈춥니다.

두 번째 규칙: 타임아웃은 데드라인으로 전파되어야 합니다. 클라이언트가 3초를 기다린다면, 그 요청이 거치는 DB·캐시·외부 API 호출의 타임아웃 합이 3초를 넘어서는 안 되고, 클라이언트가 떠난 뒤의 작업은 취소되어야 합니다. Node.js에서 이를 위한 표준 수단이 AbortSignal입니다.

// 요청 진입: 전체 데드라인 하나를 만든다
app.use((req, res, next) => {
  const deadline = AbortSignal.timeout(3_000);                     // Node 17.3+
  const clientGone = new AbortController();
  res.on('close', () => { if (!res.writableFinished) clientGone.abort(); });
  req.signal = AbortSignal.any([deadline, clientGone.signal]);     // Node 20.3+: 둘 중 먼저 오는 것
  next();
});

// 지원하지 않는 API는 직접 레이스
function withSignal(promise, signal) {
  return new Promise((ok, no) => {
    if (signal.aborted) return no(signal.reason);
    const onAbort = () => no(signal.reason);
    signal.addEventListener('abort', onAbort, { once: true });
    promise.then(ok, no).finally(() => signal.removeEventListener('abort', onAbort));  // 리스너 해제 (11장 4.2)
  });
}
  • 타임아웃 값은 상대의 p99 응답 시간 + 여유로 정합니다. 평균으로 정하면 정상 요청의 상당수가 잘립니다.
  • 연결 타임아웃(connect)과 응답 타임아웃(headers/body)은 따로 둡니다. 연결은 보통 수백 ms면 충분하고, 응답은 작업에 따라 다릅니다.
  • AbortError는 운영 에러이며 보통 재시도 대상이 아닙니다(데드라인이 이미 지났으므로). 클라이언트가 떠난 경우는 로그 레벨을 낮춥니다.

7. 재시도와 백오프

재시도는 "일시적 실패"에만 유효합니다. 429, 503, ECONNRESET, ETIMEDOUT(연결 단계)은 후보이고, 400, 401, 404, 그리고 비멱등 요청의 타임아웃(상대가 처리했을 수도 있음)은 재시도하면 안 됩니다. 재시도의 위험은 재시도 폭풍입니다. 서버가 과부하로 실패하는데 모든 클라이언트가 즉시 3번씩 재시도하면 부하가 3배가 되어 복구가 불가능해집니다.

재시도·백오프 계산기와 thundering herd

async function retry(fn, { attempts = 4, base = 100, cap = 10_000, signal, isRetryable = defaultRetryable } = {}) {
  let lastErr;
  for (let n = 0; n < attempts; n++) {
    try { return await fn({ attempt: n, signal }); }
    catch (err) {
      lastErr = err;
      if (!isRetryable(err) || n === attempts - 1 || signal?.aborted) throw err;
      const exp = Math.min(cap, base * 2 ** n);
      const delay = err.retryAfterMs ?? Math.random() * exp;          // Retry-After 헤더가 있으면 그것을 존중
      await setTimeoutP(delay, undefined, { signal });                // timers/promises: 데드라인이 지나면 여기서 AbortError
    }
  }
  throw lastErr;
}
const defaultRetryable = e => e.retryable === true || ['ECONNRESET', 'ECONNREFUSED', 'ETIMEDOUT', 'EAI_AGAIN'].includes(e.code) || [429, 502, 503, 504].includes(e.status);
재시도 예산 시도 횟수 상한만으로는 부족합니다. 서비스 전체에서 "원 요청 대비 재시도 비율"에 예산(예: 10%)을 두고, 초과하면 재시도를 멈추는 retry budget(Google SRE 책, Finagle의 RetryBudget)이 폭풍을 구조적으로 막습니다. 또한 재시도는 호출 체인의 한 계층에서만 하세요. 3계층이 각각 3번 재시도하면 최악의 경우 27배입니다.

8. 서킷 브레이커

재시도가 "잠깐 실패"를 다룬다면 서킷 브레이커는 "한동안 실패"를 다룹니다. 상대가 죽어 있는데 요청마다 타임아웃(3초)을 기다리는 것은 자원 낭비이자 상대의 복구를 방해하는 일입니다. 브레이커는 실패율이 임계를 넘으면 즉시 실패(fail fast)로 전환해 호출자의 자원을 보호하고 상대에게 회복할 시간을 줍니다.

// 최소 구현 (운영에서는 opossum, cockatiel 같은 검증된 라이브러리 권장)
class CircuitBreaker {
  constructor(fn, { threshold = 0.5, minVolume = 10, resetTimeout = 5_000, windowMs = 10_000, halfOpenMax = 1 } = {}) {
    Object.assign(this, { fn, threshold, minVolume, resetTimeout, windowMs, halfOpenMax });
    this.state = 'closed'; this.events = []; this.openedAt = 0; this.probes = 0;
  }
  async call(...args) {
    const now = Date.now();
    if (this.state === 'open') {
      if (now - this.openedAt < this.resetTimeout) throw Object.assign(new Error('circuit open'), { code: 'E_CIRCUIT_OPEN', retryable: false });
      this.state = 'half'; this.probes = 0;
    }
    if (this.state === 'half' && this.probes >= this.halfOpenMax) throw Object.assign(new Error('circuit half-open'), { code: 'E_CIRCUIT_OPEN' });
    if (this.state === 'half') this.probes++;
    try { const r = await this.fn(...args); this.record(true, now); return r; }
    catch (err) { this.record(false, now); throw err; }
  }
  record(ok, now) {
    if (this.state === 'half') { if (ok) { this.state = 'closed'; this.events = []; } else { this.state = 'open'; this.openedAt = now; } return; }
    this.events.push({ ok, at: now });
    this.events = this.events.filter(e => now - e.at < this.windowMs);          // 슬라이딩 윈도
    const n = this.events.length, fails = this.events.filter(e => !e.ok).length;
    if (n >= this.minVolume && fails / n >= this.threshold) { this.state = 'open'; this.openedAt = now; }
  }
}
  • 무엇을 실패로 셀 것인가가 가장 중요한 설계 결정입니다. 타임아웃, 5xx, 연결 에러는 실패. 4xx(클라이언트 잘못)는 실패로 세지 않습니다. 세면 잘못된 입력 몇 개가 브레이커를 열어 전체를 막습니다.
  • 브레이커는 의존성(호스트) 단위로 둡니다. 엔드포인트마다 두면 표본이 부족하고, 전체에 하나를 두면 한 의존성 장애가 다른 의존성 호출까지 막습니다.
  • OPEN일 때 즉시 실패 대신 폴백(캐시된 값, 기본값, 축소된 기능)을 돌려주면 사용자에게는 "느려짐"이 아니라 "약간 오래된 데이터"로 보입니다(9절).
  • 상태 전이는 메트릭·로그로 반드시 남깁니다. 브레이커가 열렸는데 아무도 모르는 상황이 가장 흔한 운영 실수입니다.

9. 벌크헤드, 폴백, 멱등성

벌크헤드 (격벽)

배의 격벽처럼 자원을 구획해 한 의존성의 장애가 다른 기능의 자원을 소진하지 못하게 합니다. Node.js에서 구획할 자원은 동시 요청 수(세마포어), 커넥션 풀(의존성별 Agent/DB 풀 분리), 프로세스/워커(CPU 작업을 별도 워커 풀로, 9장)입니다. 한 의존성이 느려질 때 그 의존성 호출에 허용된 동시 요청 N개만 묶이고, 나머지 요청은 즉시 "사용 불가"를 받습니다(큐에서 기다리다 함께 죽는 대신).

class Semaphore {
  constructor(max) { this.max = max; this.cur = 0; this.q = []; }
  async run(fn, { signal, queueLimit = 100 } = {}) {
    if (this.cur >= this.max) {
      if (this.q.length >= queueLimit) throw Object.assign(new Error('bulkhead full'), { code: 'E_BULKHEAD', status: 503 });   // 큐도 상한
      await new Promise((ok, no) => { const e = { ok, no }; this.q.push(e); signal?.addEventListener('abort', () => { this.q.splice(this.q.indexOf(e), 1); no(signal.reason); }, { once: true }); });
    }
    this.cur++;
    try { return await fn(); } finally { this.cur--; const next = this.q.shift(); next?.ok(); }
  }
}
const paymentsLimiter = new Semaphore(20);   // 결제 API 동시 호출 20개까지. 나머지는 짧게 대기 후 503

폴백과 그레이스풀 디그레이드

실패했을 때 "에러"가 유일한 선택지는 아닙니다. 추천 서비스가 죽으면 인기 상품 목록을, 환율 API가 죽으면 마지막 캐시 값을, 프로필 이미지 서비스가 죽으면 기본 아바타를 돌려줍니다. 폴백은 핵심 기능과 부가 기능을 구분하는 데서 시작합니다. 결제는 폴백이 없지만 추천은 있습니다. 폴백이 발동되면 반드시 메트릭으로 남기고(폴백 비율이 곧 장애 지표), 응답에 표시(X-Degraded: recommendations)해 클라이언트와 운영자가 알 수 있게 합니다.

멱등성: 재시도의 전제

타임아웃된 POST를 재시도하면 주문이 두 번 생길 수 있습니다. 상대가 요청을 처리했는지 호출자는 모르기 때문입니다. 해법은 요청에 멱등성 키(Idempotency-Key 헤더, UUID)를 실어 보내고, 서버가 키별 결과를 저장(TTL 24h 등)해 같은 키의 재요청에 저장된 응답을 돌려주는 것입니다. Stripe가 대중화한 패턴이며, 18장에서 큐 컨슈머의 "at-least-once + 멱등 처리"와 함께 더 다룹니다. 멱등성이 보장되지 않는 호출은 재시도하지 않는 것이 원칙입니다.

10. 현업 장애 사례

사례 1: 'error' 리스너 하나가 없어서 매일 새벽 재시작

배치 작업이 S3로 스트리밍 업로드하는 코드에서 네트워크 끊김 시 Readable 스트림이 'error'를 emit했고, 리스너가 없어 uncaughtException → 프로세스 종료. 새벽 네트워크 점검 시간마다 반복되었지만 재시작 정책 덕에 "가끔 느리다" 정도로만 보고됨. pipeline()으로 교체하고 uncaughtException 로그에 알람을 걸어 해결. 교훈: uncaughtException 발생 횟수는 0이어야 하는 지표이며, 재시작 정책이 버그를 숨긴다.

사례 2: 재시도가 만든 자기 유발 DDoS

DB 페일오버로 30초간 ECONNREFUSED. API 서버(50대)가 각 요청을 즉시 3회 재시도하고, 그 앞의 BFF도 3회, 모바일 앱도 3회. DB가 돌아온 순간 평소의 27배 요청이 동시 도착해 다시 다운, 이를 3번 반복. 지터 백오프 + 재시도를 BFF 한 계층으로 통일 + DB 호출에 브레이커 적용 후 같은 페일오버에서 45초 만에 정상화. 교훈: 재시도는 한 계층에서, 지터와 함께, 예산 안에서.

사례 3: 그레이스풀 셧다운이 30초를 꽉 채우고 SIGKILL

k8s 롤링 배포 때마다 일부 요청이 502. SIGTERM 핸들러는 server.close(cb)만 호출했고(Node 16), keep-alive 유휴 커넥션 때문에 cb가 오지 않아 30초 뒤 SIGKILL. 그 사이 readiness는 여전히 OK라 새 요청이 계속 들어와 강제 종료 시 함께 끊김. 해결: readiness 먼저 내리기 + 3초 대기 + closeIdleConnections() + 25초 강제 타이머. 교훈: 셧다운의 첫 단계는 "새 트래픽 차단"이고, 그것은 프로세스 혼자 할 수 없다(14장).

핵심 요약

  • 운영 에러는 가까운 곳에서 복구, 프로그래머 에러는 잡지 말고 크래시 후 외부에서 재시작. uncaughtException 핸들러는 로그·정리 후 반드시 종료.
  • unhandledRejection은 Node 15+에서 기본 throw. 핸들러를 달아 삼키지 말고 다시 던진다. 병렬 Promise는 즉시 Promise.all로 묶어 "한 틱 뒤 catch"를 피한다.
  • 네 통로(throw/reject/callback/'error' 이벤트) 중 'error' 미처리가 크래시 1위. 스트림은 pipeline.
  • 에러 객체: code로 분기, cause로 원인 보존, 컨텍스트 프로퍼티, 서브클래스. message로 분기 금지.
  • 셧다운 순서: readiness 내림 → 대기 → server.close() + closeIdleConnections() → in-flight 완료 → 리소스 정리 → 강제 타이머. grace period보다 짧게.
  • 모든 외부 호출에 타임아웃, 요청 단위 데드라인을 AbortSignal로 전파. 타임아웃은 p99 기준.
  • 재시도는 멱등 요청에만, 지터 백오프로, 한 계층에서만, 예산 안에서. 브레이커는 의존성 단위로 fail fast + 폴백. 감싸는 순서: 데드라인 → 벌크헤드 → 브레이커 → 재시도 → 타임아웃.

확인 문제

process.on('uncaughtException', err => logger.error(err))만 등록한 서비스의 문제는?
핸들러를 등록하면 Node는 종료하지 않습니다. 예외가 튀어나온 콜백이 남긴 미완 상태(락, 반쯤 쓴 응답 등) 위에서 다음 요청들이 실행됩니다. 로그 후 셧다운·종료가 필수입니다.
const a = fetchA(); const b = await fetchB(); const r = await a;에서 fetchA가 fetchB보다 먼저 거부되면?
거부된 Promise에 핸들러가 없는 채로 틱이 끝나면 unhandledRejection입니다. 기본 throw 모드에서는 프로세스가 죽습니다. 병렬 실행은 Promise.all([fetchA(), fetchB()])로 즉시 묶어야 합니다.
다음 중 재시도하면 안 되는 것은?
응답 타임아웃은 서버가 요청을 처리했을 수도 있다는 뜻입니다. 비멱등 요청을 재시도하면 중복 주문이 생깁니다. 멱등성 키가 있다면 재시도해도 됩니다. 나머지는 일시적 실패이며 Retry-After는 그 값을 존중해 재시도합니다.
서킷 브레이커를 열 때 4xx 응답을 실패로 집계하면 생기는 문제는?
4xx는 상대 서비스의 건강과 무관한 클라이언트 오류입니다. 이를 실패로 세면 상대가 멀쩡한데도 브레이커가 열립니다. 실패 판정에는 타임아웃·연결 에러·5xx만 넣습니다.
SIGTERM 핸들러에서 가장 먼저 해야 할 일은?
새 요청이 계속 들어오는 상태에서 리소스를 닫으면 그 요청들이 실패합니다. 먼저 트래픽을 차단(readiness 실패)하고 LB/k8s에 전파될 시간을 준 뒤 listen을 중단하고 in-flight를 완료시킵니다. closeAllConnections는 최후 수단입니다.
