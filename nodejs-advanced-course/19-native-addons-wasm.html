네이티브 확장: N-API, WASM, FFI

JavaScript로 충분하지 않을 때가 있습니다. 기존 C/C++/Rust 라이브러리를 써야 하거나, 특정 수치 연산이 V8의 한계에 부딪히거나, OS API에 직접 닿아야 할 때입니다. 이 장은 세 가지 길(Node-API 네이티브 애드온, WebAssembly, FFI)의 메커니즘과 비용, 그리고 "굳이 가지 말아야 할 때"를 다룹니다.

학습 목표

  • 네이티브 확장이 정당화되는 조건과, 먼저 시도해야 할 대안(워커, 순수 JS 최적화, WASM)을 판단할 수 있다.
  • Node-API의 ABI 안정성, 핸들 스코프·참조의 수명 규칙, AsyncWorker와 ThreadSafeFunction의 스레드 모델을 설명할 수 있다.
  • WebAssembly의 선형 메모리 모델과 JS↔WASM 데이터 교환 비용을 이해하고, 실제 메모리를 다뤄 볼 수 있다.
  • JS↔네이티브 호출 오버헤드를 정량화해 "작은 호출을 많이"가 왜 손해인지 계산할 수 있다.
  • 플랫폼별 바이너리 빌드·배포(prebuild)와 컨테이너 빌드 체인의 함정을 피할 수 있다.

1. 정말 네이티브가 필요한가

네이티브 코드는 세 가지 비용을 가져옵니다. 빌드 복잡도(플랫폼 × 아키텍처 × Node 버전), 안전성(세그폴트 하나가 프로세스 전체를 죽이고, 메모리 오염은 조용히 퍼진다), 경계 비용(JS↔네이티브 호출마다 수십~수백 ns). 그래서 결정 순서는 다음과 같습니다.

  1. 정말 CPU가 병목인가? 10장의 프로파일로 확인. 대부분의 "느린 Node"는 I/O 대기, 동기 블로킹, GC 압력이지 연산 속도가 아니다.
  2. 순수 JS 최적화: 4장의 단형성 유지, TypedArray 사용, 할당 줄이기. 수치 루프는 TypedArray + 정수 연산으로 WASM의 70~90%까지 나오는 경우가 흔하다.
  3. 워커 스레드(9장): 문제가 "느림"이 아니라 "루프를 막음"이라면 네이티브가 아니라 병렬화가 답이다.
  4. WASM: 기존 C/C++/Rust 코드를 쓰되 플랫폼 독립·샌드박스가 필요할 때. 빌드 산출물이 하나(.wasm)라 배포가 단순하다.
  5. Node-API 애드온: OS API·하드웨어·시스템 라이브러리(libpq, OpenSSL 확장, GPU)에 직접 닿아야 하거나, WASM이 못 하는 것(스레드 생성, 파일 디스크립터, SIMD 특수 명령)이 필요할 때.

Node-API 애드온

OS·하드웨어 접근 ○, 최고 성능 ○, 플랫폼별 빌드 ×, 크래시 시 프로세스 사망 ×. 예: sharp(libvips), better-sqlite3, bcrypt.

WebAssembly

단일 바이너리 ○, 샌드박스(메모리 격리) ○, OS 접근 × (WASI로 제한적), 메모리 복사 비용 △. 예: esbuild의 wasm 빌드, sql.js, 이미지 코덱(squoosh).

FFI (koffi 등)

컴파일 없이 공유 라이브러리 호출 ○, 빠른 프로토타입 ○, 호출 오버헤드 큼 ×, 타입 선언 실수가 곧 메모리 오염 ×.

2. Node-API: ABI 안정 바인딩

Node 8 이전의 애드온은 V8 C++ API를 직접 호출했습니다(nan 라이브러리). V8 API는 버전마다 바뀌어 Node 메이저가 오를 때마다 모든 애드온을 재컴파일해야 했습니다. Node-API(N-API, 2017)는 V8을 숨기는 C ABI입니다. napi_* 함수들은 한 번 추가되면 시그니처가 바뀌지 않으므로, Node 16에서 빌드한 .node 파일이 Node 24에서 그대로 로드됩니다. 이것이 prebuild 배포(8절)를 가능하게 한 전제입니다.

// C++ 래퍼 node-addon-api 사용 (napi_* C API를 RAII 클래스로 감싼 헤더 전용 라이브러리)
#include <napi.h>

Napi::Value Sum(const Napi::CallbackInfo& info) {
  Napi::Env env = info.Env();
  if (info.Length() < 1 || !info[0].IsTypedArray()) {
    Napi::TypeError::New(env, "Float64Array expected").ThrowAsJavaScriptException();   // JS 예외로 변환
    return env.Undefined();                                                          // throw 후 반드시 return
  }
  Napi::Float64Array arr = info[0].As<Napi::Float64Array>();
  double* data = arr.Data();            // ArrayBuffer의 백킹 스토어를 복사 없이 직접 가리킨다
  double s = 0; for (size_t i = 0; i < arr.ElementLength(); i++) s += data[i];
  return Napi::Number::New(env, s);
}

Napi::Object Init(Napi::Env env, Napi::Object exports) {
  exports.Set("sum", Napi::Function::New(env, Sum));
  return exports;
}
NODE_API_MODULE(addon, Init)          // 모듈 로드 시 Init 호출
// JS 측
const addon = require('./build/Release/addon.node');   // 또는 node-gyp-build()로 prebuilt 탐색
addon.sum(new Float64Array([1, 2, 3]));                // 6
Rust라면 napi-rs napi-rs는 같은 Node-API 위에 Rust 바인딩을 올립니다. 메모리 안전 언어라 세그폴트·UAF 위험이 크게 줄고, 매크로로 타입 변환 보일러플레이트가 사라지며, 빌드·prebuild 도구 체인이 통합돼 있습니다. 2024년 이후 새로 만드는 애드온(Prisma 엔진, swc, Rspack 등)의 주류입니다.

3. 핸들 스코프와 참조 수명

네이티브 코드가 JS 값을 들고 있는 방식은 두 가지입니다. 핸들(napi_value)은 현재 핸들 스코프 안에서만 유효한 임시 포인터이고, 참조(napi_ref)는 명시적으로 만들고 해제하는 영속 포인터입니다. GC는 핸들 스코프가 살아있는 동안 그 안의 값을 이동시키지 않고(정확히는 핸들이 갱신됨) 수집하지 않습니다.

네이티브 객체의 수명: ObjectWrap과 finalizer

class Connection : public Napi::ObjectWrap<Connection> {
 public:
  Connection(const Napi::CallbackInfo& info) : ObjectWrap(info) { handle_ = lib_open(...); }
  ~Connection() { if (handle_) lib_close(handle_); }     // JS 객체가 GC될 때 호출 (finalizer)
  // 주의: finalizer는 GC 타이밍에 호출된다. 파일 디스크립터·소켓처럼 희소한 자원은
  //       GC에 맡기지 말고 명시적 close() 메서드를 제공하고, finalizer는 안전망으로만.
 private:
  lib_handle* handle_;
};
finalizer 안에서 JS를 호출하지 말 것 Node-API의 finalizer는 GC 도중에 호출되며 그 시점에 JS를 실행하는 것은 금지됩니다(napi_call_function 불가). 정리 작업을 JS로 넘겨야 하면 node_api_post_finalizer(Node 21+ / 20.x 백포트, 실험)로 미루거나, 처음부터 FinalizationRegistry 대신 명시적 close()를 설계하세요. 또한 napi_add_env_cleanup_hook으로 프로세스/워커 종료 시 네이티브 리소스를 정리합니다. 워커 스레드(9장)에서 로드된 애드온은 워커마다 별도 인스턴스이며, 정적 변수 공유가 레이스를 만듭니다(NAPI_MODULE_INIT 컨텍스트 인식 모듈로 작성).

4. 비동기: AsyncWorker와 ThreadSafeFunction

네이티브 함수가 오래 걸리면 이벤트 루프를 막습니다(2장). 두 가지 도구가 있습니다.

  • Napi::AsyncWorker: libuv 스레드풀(3장)에서 Execute()를 돌리고, 끝나면 루프 스레드에서 OnOK()/OnError()가 호출됩니다. Execute() 안에서는 JS 값을 절대 만지면 안 됩니다(다른 스레드). 입력은 생성자에서 C++ 값으로 복사해 두고, 결과도 C++ 값으로 보관했다가 OnOK()에서 JS 값으로 변환합니다. 스레드풀 크기(기본 4)를 같이 쓰므로 fs·crypto·DNS와 경합합니다.
  • Napi::ThreadSafeFunction(TSFN): 애드온이 직접 만든 스레드(또는 외부 라이브러리의 콜백 스레드)에서 JS 함수를 호출해야 할 때. 호출 요청을 큐에 넣으면 Node가 루프 스레드에서 꺼내 실행합니다. 하드웨어 이벤트, 스트리밍 디코더, 외부 라이브러리의 비동기 콜백이 전형적 용도.
ThreadSafeFunction 흐름
네이티브 스레드가 JS 콜백을 "직접" 부르는 것이 아니라, 큐와 루프를 거치는 과정을 단계별로 봅니다. 큐가 가득 찼을 때의 블로킹/논블로킹 선택도 포함합니다.
// TSFN 생성 (루프 스레드에서)
tsfn_ = Napi::ThreadSafeFunction::New(env, jsCallback, "sensor", /*maxQueueSize*/ 64, /*initialThreadCount*/ 1,
          [](Napi::Env) { /* finalizer: 모든 스레드가 Release 한 뒤 */ });
// 네이티브 스레드에서
void onSensor(Sample* s) {
  auto status = tsfn_.NonBlockingCall(s, [](Napi::Env env, Napi::Function cb, Sample* s) {   // 이 람다는 루프 스레드에서 실행
    cb.Call({ Napi::Number::New(env, s->value) });
    delete s;
  });
  if (status == napi_queue_full) { /* 드롭하거나 집계. BlockingCall이면 큐가 빌 때까지 이 스레드가 멈춤 */ }
}
// 종료: 스레드마다 tsfn_.Release(). 마지막 Release 뒤 finalizer. Release 전에는 루프가 살아있다 (Unref()로 바꿀 수 있음)

5. WebAssembly와 선형 메모리

WASM 모듈은 선형 메모리(하나의 큰 바이트 배열, 64KiB 페이지 단위로 성장)만 볼 수 있습니다. JS 객체, 문자열, 힙 포인터 같은 것은 모릅니다. 그래서 JS↔WASM 데이터 교환은 "숫자(i32/i64/f32/f64)를 넘기거나, 메모리에 바이트를 써 놓고 오프셋과 길이를 넘기는" 것뿐입니다. 이 복사 비용이 WASM 성능 이야기의 절반입니다.

WASI, 툴체인, 한계

  • WASI(WebAssembly System Interface): 파일·시계·랜덤·환경변수 같은 OS 기능을 표준 import로 제공. Node의 node:wasi 모듈(WASI 클래스, wasi_snapshot_preview1)은 Node 22 기준 아직 실험 단계로 표기되어 있으며, 소켓·스레드는 preview1에 없습니다. 프로덕션에서는 WASI 없이 순수 연산 모듈로 쓰거나 필요한 호스트 함수를 직접 import로 제공하는 쪽이 안정적입니다.
  • Rust → wasm: wasm-pack/wasm-bindgen이 문자열·객체 변환 글루 코드를 생성해 위 뷰어가 하는 일을 자동화합니다. C/C++ → wasm: Emscripten(런타임 포함, 큼) 또는 clang --target=wasm32(최소).
  • 성능: 수치 연산은 네이티브의 60~90%(바운드 체크, 경계 비용). SIMD(128비트)는 V8에서 안정이고, 스레드(shared memory + atomics)는 Node에서 워커와 SharedArrayBuffer로 가능하지만 툴체인 지원이 들쭉날쭉합니다. 큰 데이터를 자주 복사하면 네이티브 애드온(복사 없이 버퍼 공유)보다 느려질 수 있습니다.
  • 메모리: WASM 메모리는 V8 힙 밖(ArrayBuffer 백킹)이라 --max-old-space-size와 무관하지만 RSS에는 잡힙니다(5장·14장의 컨테이너 메모리 한계 계산에 포함).

6. 호출 오버헤드: 경계 비용의 경제학

JS→네이티브 호출은 인자 변환(napi_get_value_*), 핸들 스코프 생성, 예외 상태 확인, 반환값 래핑을 거칩니다. 호출당 대략 수십~수백 ns. JS→WASM 호출은 V8이 직접 인라인에 가깝게 처리해 더 쌉니다(수~수십 ns). 그래서 "호출당 일의 양"이 오버헤드보다 작으면 네이티브가 JS보다 느립니다. 배열 원소 하나씩 100만 번 호출하는 설계가 전형적인 패턴입니다. 답은 배치: 한 번의 호출에 TypedArray 전체를 넘깁니다.

경계 비용 계산기
호출당 고정 비용과 각 실행 환경의 상대 처리 속도를 넣으면, "호출 한 번에 처리하는 일의 양"에 따라 어느 쪽이 유리한지 그립니다. 기본값은 대략적인 경험치이며, 실제 값은 process.hrtime.bigint()로 직접 재야 합니다.
JSWASMN-API
// 측정 골격: 같은 일을 JS / 애드온으로 N회 하고 호출당 ns를 비교
const N = 1e6;
let t = process.hrtime.bigint(); for (let i = 0; i < N; i++) addon.tiny(i); 
console.log('tiny native call ns', Number(process.hrtime.bigint() - t) / N);      // 보통 50~200ns
t = process.hrtime.bigint(); addon.sum(bigFloat64Array);                             // 한 번에 배치
console.log('batched ms', Number(process.hrtime.bigint() - t) / 1e6);

7. FFI와 안전성

Node.js에는 내장 FFI가 없습니다(Deno·Bun과 다름). 커뮤니티 라이브러리(koffi가 활발, ffi-napi는 유지보수가 뜸함)는 libffi로 런타임에 호출 규약을 조립해 공유 라이브러리(.so/.dylib/.dll)의 함수를 컴파일 없이 부릅니다. 프로토타이핑에는 좋지만 호출 오버헤드가 N-API보다 수 배 크고, 타입 선언을 틀리면 즉시 메모리 오염입니다(컴파일러가 없으니 아무도 검사하지 않음).

네이티브 코드의 실패는 격리되지 않는다
  • 세그폴트 → 프로세스 전체 즉사. uncaughtException도, 13장의 어떤 복원 패턴도 소용없다. 코어 덤프와 --report-on-signal만 남는다.
  • 버퍼 오버런 → 당장 안 죽고 V8 힙을 조용히 오염. 며칠 뒤 무관한 곳에서 "불가능한" 크래시. 가장 비싼 종류의 버그.
  • 스레드 안전 위반(네이티브 스레드에서 JS 호출) → 간헐적 크래시, 재현 불가.

완화: Rust(napi-rs)로 작성, 주소 살균기(-fsanitize=address)로 테스트, 퍼징, 애드온을 별도 워커/프로세스에 격리해 크래시 반경 제한, 가능하면 WASM 샌드박스.

컨테이너 빌드 체인의 함정

  • glibc vs musl: node:22-alpine은 musl. glibc용 prebuilt가 없으면 설치 시 소스 빌드로 떨어지고, 빌드 도구가 없으면 실패. linux-x64-musl 바이너리를 제공하는지 확인하거나 -slim(Debian) 이미지를 쓴다.
  • 멀티스테이지: 빌드 스테이지에 python3 make g++를 넣고, 런타임 스테이지에는 node_modules만 복사. 런타임 이미지에 컴파일러를 남기지 않는다(14장).
  • 아키텍처: Apple Silicon에서 npm ci 한 node_modules를 x64 이미지에 복사하면 .node 로드 실패(wrong ELF class / invalid ELF header). 반드시 타깃 플랫폼에서 설치.
  • npm 스크립트 보안: 애드온 설치는 install 스크립트를 실행한다. --ignore-scripts를 켠 CI에서는 prebuilt가 없는 패키지가 깨진다. 16장의 공급망 정책과 조율.
  • Node-API 버전 확인: process.versions.napi. 애드온의 package.json binary.napi_versions가 요구하는 최소 버전을 런타임이 제공하는지.

9. 현업 장애 사례

사례 1: 알파인 이미지로 바꾸자 설치가 10분 걸리고 가끔 실패

이미지 크기를 줄이려고 -alpine으로 전환. 이미지 처리 애드온이 musl prebuilt를 제공하지 않아 매 빌드마다 libvips를 소스 컴파일. CI 캐시가 날아가면 20분, 가끔 메모리 부족으로 실패. 해결: Debian slim으로 복귀하고 멀티스테이지로 크기 회수(최종 이미지 차이는 30MB 남짓이었음).

사례 2: 네이티브 스레드에서 직접 콜백 호출 → 주 1회 크래시

외부 SDK의 이벤트 콜백(SDK 자체 스레드)에서 napi_call_function을 바로 호출. 대부분 운 좋게 동작했지만 GC와 겹치면 세그폴트. 코어 덤프의 스택에 v8::internal::Heap이 보였고, TSFN으로 바꾼 뒤 사라짐. 교훈: "JS는 루프 스레드에서만"은 권고가 아니라 규칙.

사례 3: 원소별 WASM 호출로 JS보다 5배 느려짐

해시 함수를 WASM으로 옮기고 for (const x of arr) wasm.hash(x). 원소당 일이 20ns인데 호출 오버헤드 + 문자열을 메모리에 복사하는 글루 코드가 200ns. 배열 전체를 한 번에 메모리에 쓰고 단일 호출로 바꾸자 JS 대비 2.5배 빨라짐. 6절의 계산기가 보여 주는 그대로.

핵심 요약

  • 순서: 프로파일 → 순수 JS 최적화 → 워커 → WASM → Node-API. 네이티브는 OS/하드웨어/시스템 라이브러리 접근이 필요할 때.
  • Node-API는 ABI 안정. 한 번 빌드한 바이너리가 Node 메이저를 넘어 동작하며, prebuild 배포의 전제.
  • 핸들은 호출 동안만, 참조는 삭제할 때까지. finalizer에서 JS 호출 금지. 희소 자원은 명시적 close.
  • 긴 작업은 AsyncWorker(스레드풀), 외부 스레드의 JS 호출은 반드시 ThreadSafeFunction. 큐 가득 찼을 때 정책을 정한다.
  • WASM은 선형 메모리 + 숫자만. 문자열·객체는 (ptr, len)으로 복사. grow는 이전 ArrayBuffer를 분리한다.
  • 경계 비용은 호출당 수십~수백 ns. 작은 호출을 많이 하면 JS보다 느리다. 배치로 넘긴다.
  • 네이티브 크래시는 프로세스 전체. Rust(napi-rs), 살균기, 격리. 빌드는 musl/glibc·아키텍처·install 스크립트에 주의.

확인 문제

Node 18에서 빌드한 Node-API 애드온(.node)을 Node 24에서 쓰려면?
Node-API의 핵심 설계 목표입니다. V8 API에 직접 의존하는 nan 기반 애드온은 재컴파일이 필요합니다.
Napi::AsyncWorker::Execute() 안에서 해도 되는 것은?
Execute는 스레드풀 스레드에서 실행됩니다. JS 값(env, napi_value, Function)은 루프 스레드 전용입니다. OnOK()에서만 JS 값을 만듭니다.
WebAssembly.Memory를 grow()한 뒤, grow 이전에 만들어 둔 Uint8Array 뷰를 읽으면?
grow는 새 백킹 스토어를 할당하고 이전 ArrayBuffer를 detach합니다. 글루 코드가 "메모리 뷰 캐시"를 매번 buffer 동일성으로 검사하는 이유입니다.
원소당 15ns의 일을 100만 개 원소에 대해 수행한다. N-API 호출 오버헤드가 100ns, 네이티브가 JS보다 3배 빠르다면 어떤 설계가 맞는가?
호출당 오버헤드가 호출당 일보다 크면 호출 수를 줄여야 합니다. 배치하면 네이티브의 속도 이점이 그대로 나옵니다.
외부 C 라이브러리가 자기 스레드에서 이벤트 콜백을 호출한다. JS로 이벤트를 전달하려면?
JS는 루프 스레드에서만 실행 가능합니다. AsyncWorker는 "한 번의 작업"용이고, 반복 이벤트에는 TSFN입니다.

실습 과제

  1. 최소 애드온과 배치 벤치마크. 2절의 sum 애드온을 node-addon-api로 빌드하고(npm i node-addon-api node-gyp, binding.gyp 작성), (a) 원소별 호출 100만 회와 (b) Float64Array 1개 전달의 소요 시간을 process.hrtime.bigint()로 비교하세요. 기대: (a)는 순수 JS 합산보다 느리고, (b)는 비슷하거나 빠름(V8이 단순 합산은 이미 잘 최적화하므로 큰 차이는 없을 수 있음).
  2. WASM 문자열 왕복. Rust + wasm-pack(또는 손으로 쓴 .wat → wabt)으로 "바이트 배열을 받아 대문자로 바꾸는" 함수를 만들고, JS에서 TextEncoder로 메모리에 쓰고 호출 후 TextDecoder로 읽는 글루를 직접 작성하세요. 그다음 1MB 문자열에서 복사 비용(인코딩+디코딩)과 WASM 실행 시간을 각각 측정합니다. 기대: 복사가 실행 시간과 같은 자릿수.
  3. 크래시 반경 확인. 의도적으로 null 포인터를 역참조하는 네이티브 함수를 만들고 process.on('uncaughtException')이 잡지 못함을, 그리고 node --report-on-signal(또는 --report-on-fatalerror)로 리포트가 남는지 확인하세요. 워커 스레드 안에서 호출해도 메인 프로세스가 죽는지 확인합니다(기대: 죽는다).
