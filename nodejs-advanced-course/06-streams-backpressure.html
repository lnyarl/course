스트림과 백프레셔

Node.js의 스트림은 "데이터를 조각으로 다루는 API"가 아니라 생산자와 소비자의 속도 차이를 메모리 상한 안에서 흡수하는 프로토콜입니다. write()가 false를 돌려주는 순간부터 'drain'까지, pipe()가 내부에서 pause()/resume()을 호출하는 방식까지 분해하면, 왜 어떤 서버는 트래픽이 늘면 메모리가 폭증하고 어떤 서버는 그렇지 않은지가 보입니다.

학습 목표

  • Readable/Writable의 내부 상태(버퍼, flowing, highWaterMark, needDrain)와 그 상태가 바뀌는 규칙을 설명할 수 있다.
  • write() 반환값·'drain'·pipe()로 이루어지는 백프레셔 메커니즘을 직접 구현하고 시뮬레이션할 수 있다.
  • pipe()와 stream.pipeline()의 에러 전파·정리 차이를 알고, 에러·취소·종료를 올바르게 다룰 수 있다.
  • Transform·async iterator·웹 스트림을 적재적소에 쓰고, 흔한 스트림 버그(drain 무시, 미소비 요청, 'end' 혼동)를 진단할 수 있다.

1. 스트림이 푸는 문제

1GiB 파일을 HTTP로 내보내는 가장 단순한 코드는 res.end(await fs.readFile(path))입니다. 이 코드는 동시 요청 수만큼 1GiB를 메모리에 올립니다. 스트림 버전 fs.createReadStream(path).pipe(res)는 동시 요청이 몇 개든 요청당 수십 KiB만 씁니다. 차이는 "조각으로 읽는다"가 아닙니다. 조각으로 읽어도 소비자(클라이언트 소켓)가 느리면 조각이 쌓입니다. 차이는 소비자가 느릴 때 생산자(디스크 읽기)를 멈춘다는 데 있습니다. 이것이 백프레셔(backpressure)입니다.

한 줄 모델 모든 스트림은 내부 버퍼 + 수위 표시(highWaterMark)입니다. 수위를 넘으면 스트림은 "더 주지 마"라고 신호(write() → false, push() → false)를 보내고, 수위가 내려가면 "다시 줘"라고 신호('drain', _read() 호출)를 보냅니다. 이 신호를 무시해도 동작은 합니다. 메모리가 허락하는 동안은.

2.1 highWaterMark의 정확한 의미

highWaterMark는 상한이 아니라 임계입니다. 버퍼가 그 값에 닿으면 "더 받지 않겠다"는 신호를 보낼 뿐, 그 이상 넣는 것을 막지 않습니다. 단위는 두 가지입니다.

  • 바이트 모드: 바이트 수. 기본값은 Node 22부터 65536(64KiB), 그 이전은 16384. 현재 값은 stream.getDefaultHighWaterMark(false)로 확인하고, setDefaultHighWaterMark로 프로세스 전역 변경 가능(Node 19.9+ / 18.17+).
  • objectMode: 객체 개수. 기본 16. 객체 하나가 1바이트든 10MiB든 16개입니다. 큰 객체를 흘리는 objectMode 스트림은 메모리 수위를 바이트로 통제할 수 없다는 뜻입니다.

Readable의 highWaterMark는 "미리 읽어 둘 양"(prefetch)이기도 합니다. 소비자가 느려도 이만큼은 선행해 읽어 두므로 I/O 지연을 숨기고 처리량을 높입니다. 파일 복사처럼 양쪽이 빠른 경우 highWaterMark를 1MiB로 키우면 시스템 콜 횟수가 줄어 처리량이 오릅니다. 반대로 수천 개의 동시 스트림(소켓)은 각자 이만큼을 버퍼링할 수 있으므로 총량이 커집니다.

3. Writable: write()의 반환값과 'drain'

writable.write(chunk)의 내부는 다음 순서입니다(lib/internal/streams/writable.js의 writeOrBuffer).

function writeOrBuffer(stream, state, chunk, encoding, callback) {
  const len = state.objectMode ? 1 : chunk.length;
  state.length += len;
  const ret = state.length < state.highWaterMark;   // ← 반환값은 "넣은 후" 수위가 임계 미만인가
  if (!ret) state.needDrain = true;                  // ← 임계 도달: 나중에 'drain'을 내보내야 함
  if (state.writing || state.corked || state.errored || !state.constructed) {
    state.buffered.push({ chunk, encoding, callback }); // 이미 쓰는 중이면 큐에
  } else {
    state.writing = true;
    stream._write(chunk, encoding, state.onwrite);     // 아니면 바로 하부 쓰기
  }
  return ret && !state.errored && !state.destroyed;
}

핵심 규칙 네 가지:

  1. 반환값은 "이번 청크를 받았는가"가 아니다. 항상 받습니다(버퍼에 넣습니다). 반환값은 "다음 청크를 지금 보내도 되는가"입니다.
  2. false는 length >= highWaterMark일 때. 등호 포함. highWaterMark 10에 5바이트 두 번을 쓰면 두 번째가 false입니다.
  3. 'drain'은 needDrain이 설정된 상태에서 버퍼가 완전히 비었을 때(length가 0) 한 번 발화. 임계 아래로 내려왔을 때가 아닙니다. 그래서 drain을 기다리는 동안 생산자는 완전히 멈추고, 소비자는 버퍼를 다 비운 뒤에야 다시 받습니다. 처리량을 위해 highWaterMark만큼의 여유가 필요한 이유입니다.
  4. _write는 한 번에 하나. 이전 _write의 콜백이 불릴 때까지 다음 청크는 큐에 머뭅니다. _writev를 구현하면 큐에 쌓인 청크를 한 번에 받습니다(cork()와 함께 쓰면 작은 쓰기를 모아 시스템 콜을 줄임).
drain 무시 (메모리 폭증)
for (const row of millionRows) {
  res.write(JSON.stringify(row) + '\n');
  // 반환값 무시. 소켓이 느리면
  // 100만 줄이 writableState.buffered에 쌓인다
}
res.end();
drain 준수
for (const row of millionRows) {
  if (!res.write(JSON.stringify(row) + '\n')) {
    await once(res, 'drain');   // events.once
  }
}
res.end();

3.1 끝내기: end, finish, close

  • end([chunk]): 마지막 청크를 넣고 "더 없음" 표시. 버퍼가 남아있으면 계속 비운다.
  • _final(cb): 버퍼가 다 비워진 뒤, 'finish' 직전에 호출. 파일 닫기 전 플러시 같은 마무리.
  • 'finish': 모든 데이터가 하부 자원에 전달됨(_write 콜백 완료). 디스크에 fsync됐다는 뜻은 아니다.
  • 'close': 하부 자원(fd, 소켓)이 닫힘. autoDestroy: true(기본)면 finish 후 자동으로 destroy → close. 에러로 끝나도 close는 온다. 정리(cleanup)는 'close'에서.

4. Readable: 두 모드, 세 상태

Readable은 paused 모드와 flowing 모드가 있고, 내부적으로 readableFlowing이 null(초기, 소비자 없음), false(명시적으로 멈춤), true(흐름) 세 값을 가집니다. 전이 규칙은 간단해 보이지만 실제로는 자주 헷갈립니다. 아래 위젯은 실제 Node 22/24에서 확인한 전이를 그대로 구현했습니다.

4.1 _read와 push의 계약

구현자 관점에서 Readable은 "_read(size)가 불리면 push(chunk)를 호출하고, push()가 false를 돌려주면 다음 _read까지 push를 멈춘다"는 계약입니다. false는 버퍼가 highWaterMark에 닿았다는 뜻이고, 소비자가 꺼내 가 수위가 내려가면 Node가 _read를 다시 부릅니다. 이 계약을 어기고 _read 밖에서 push를 계속하면(예: 이벤트 핸들러에서 무조건 push) Readable 쪽 버퍼가 무한히 자랍니다. 그래서 이벤트 소스를 Readable로 감쌀 때는 내부 큐와 pause 신호가 필요합니다.

4.2 async iterator: 가장 안전한 소비 방식

for await (const chunk of readable) {      // Symbol.asyncIterator
  await processSlowly(chunk);              // await하는 동안 readable은 paused → 백프레셔 자동
}
// 루프를 break/throw로 빠져나오면 readable.destroy()가 호출된다 (기본 동작)

async iterator는 한 청크를 처리하는 동안 스트림을 읽지 않으므로 백프레셔가 공짜로 따라옵니다. 단점은 청크당 Promise 비용이 있어 수백만 개의 작은 청크에서는 'data' 이벤트보다 느리다는 것입니다. Readable.from(iterable)은 반대 방향으로, 제너레이터/배열을 Readable로 만듭니다(기본 objectMode).

5. 백프레셔 메커니즘과 시뮬레이터

src.pipe(dest)의 핵심은 lib/internal/streams/readable.js의 다음 코드입니다.

src.on('data', ondata);
function ondata(chunk) {
  const ret = dest.write(chunk);
  if (ret === false) {            // dest 버퍼가 highWaterMark에 닿음
    pause();                      // src.pause() → src 버퍼가 차면 _read도 멈춤 → 하부 소스(fd, 소켓 read) 중단
  }
}
dest.on('drain', ondrain);        // dest 버퍼가 비면
function ondrain() { if (state.flowing !== false) src.resume(); }  // 다시 흐름

src.on('end', () => dest.end());  // { end: false } 옵션이 아니면 src 종료 시 dest도 종료
// 주의: src 'error'는 dest로 전파되지 않고, dest 'error'는 src.unpipe()만 한다

즉 압력은 하류 → 상류로 pause/resume 신호가 되어 전달되고, 소켓이라면 결국 커널 수신 버퍼가 차서 TCP 윈도우가 닫히는 것으로 네트워크 반대편까지 전달됩니다. 체인의 어느 한 단계가 신호를 무시하면 그 지점에서 버퍼가 자랍니다.

관찰 포인트: (1) 생산이 소비보다 빠르고 drain을 무시하면 수위가 선형으로 올라가며 끝이 없습니다. (2) drain을 지키면 수위는 "highWaterMark + 청크 하나" 근처에서 톱니 모양으로 오르내립니다. 톱니가 바닥(0)까지 내려가는 이유가 3절의 규칙 3입니다. (3) highWaterMark를 키우면 톱니 주기가 길어지고 생산자 대기 횟수는 줄지만 평균 메모리는 늘어납니다. (4) 생산이 소비보다 느리면 백프레셔는 한 번도 발동하지 않습니다. 백프레셔는 병목이 하류에 있을 때만 보이는 현상입니다.

6. pipeline, finished, 에러 전파

pipe()의 가장 큰 결함은 에러가 전파되지 않고, 에러 난 스트림만 정리된다는 것입니다. 중간 Transform이 에러로 destroy되면 상류 파일 스트림의 fd는 열린 채 남고, 하류 소켓은 영원히 끝나지 않는 응답을 기다립니다. stream.pipeline()(Node 10+)은 이 문제를 풀기 위해 모든 스트림에 finished()를 걸고, 하나라도 에러/조기 종료되면 전부 destroy합니다.

에러 전파: pipe() vs pipeline()
파일 → gunzip → 소켓 체인에서 gunzip이 손상된 데이터로 에러를 냈을 때, 두 방식이 각 스트림을 어떻게 남기는지 단계별로 봅니다.
const { pipeline } = require('node:stream/promises');
const { createReadStream } = require('node:fs');
const { createGunzip } = require('node:zlib');

app.get('/export', async (req, res) => {
  try {
    await pipeline(
      createReadStream('data.gz'),
      createGunzip(),
      res,                       // 마지막 스트림. 에러 시 res도 destroy됨 → 클라이언트는 끊긴 연결을 봄
      { signal: AbortSignal.timeout(30_000) },   // Node 17.3+: 취소/타임아웃
    );
  } catch (err) {
    if (err.name === 'AbortError') logger.warn('export timed out');
    else if (err.code === 'ERR_STREAM_PREMATURE_CLOSE') logger.info('client disconnected');
    else logger.error(err);
    // 여기서 res에 다시 쓰려 하지 말 것: 이미 destroy됨. 헤더 전송 전이라면 res.headersSent로 확인 후 처리.
  }
});
  • stream.finished(stream, cb): 스트림이 끝나거나(end/finish) 에러 나거나 조기 종료(premature close)되면 호출. 정리 함수를 반환하므로 리스너 누수 방지에 쓴다. pipeline의 구성 요소.
  • ERR_STREAM_PREMATURE_CLOSE: 'end'/'finish' 전에 'close'가 왔다는 뜻. HTTP에서는 거의 항상 클라이언트 연결 끊김. 에러 로그 레벨로 찍으면 노이즈가 된다.
  • pipeline의 마지막 인자로 async 함수/제너레이터도 넣을 수 있다(Node 15+): pipeline(src, async function* (source) { for await (const c of source) yield transform(c); }, dest). 간단한 Transform은 클래스 없이 이렇게.
  • stream.compose()(실험적): 여러 스트림을 하나의 Duplex로 합쳐 재사용.

7. Transform과 파이프라인 설계

7.1 청크 경계는 의미 경계가 아니다

가장 흔한 Transform 버그는 "청크 = 한 줄" 또는 "청크 = 한 JSON"이라고 가정하는 것입니다. 소켓과 파일은 바이트 스트림이고 청크 경계는 버퍼 크기와 타이밍이 정합니다. 라인 파서는 잔여(carry-over)를 들고 있어야 합니다.

class LineSplit extends Transform {
  constructor() { super({ readableObjectMode: true }); this.rest = ''; }
  _transform(chunk, enc, cb) {
    const lines = (this.rest + chunk).split('\n');
    this.rest = lines.pop();                 // 마지막 조각은 다음 청크와 이어짐
    for (const l of lines) this.push(l);
    cb();
  }
  _flush(cb) { if (this.rest) this.push(this.rest); cb(); }   // 스트림 끝의 잔여
}

멀티바이트 문자(UTF-8 한글)는 바이트 경계에서 잘릴 수 있습니다. chunk.toString()을 직접 하지 말고 readable.setEncoding('utf8') 또는 string_decoder를 써야 불완전한 바이트가 다음 청크와 합쳐집니다.

7.2 동시성 있는 변환

Transform은 _transform 콜백이 불릴 때까지 다음 청크를 주지 않습니다. 즉 순차입니다. 청크마다 외부 API를 호출한다면 동시성 N이 필요한데, 이때 흔히 저지르는 실수가 콜백을 바로 불러 버리는 것입니다(백프레셔 무력화). 올바른 방법은 "진행 중 작업 수가 N 미만일 때만 콜백을 부르는" 세마포어를 두는 것입니다. Node 22의 Readable.prototype.map(fn, { concurrency })(실험적)이 이 패턴을 내장했습니다.

7.3 objectMode 파이프라인의 메모리

objectMode의 highWaterMark 16은 객체 수입니다. DB 커서 → 변환 → 응답 체인에서 각 단계가 16개씩 버퍼링하면 48개 행이 메모리에 있는 것이고, 행이 1MiB짜리 문서라면 48MiB입니다. 큰 객체를 흘리는 objectMode는 highWaterMark를 1~2로 줄이거나, 아예 바이트 스트림으로 직렬화해서 흘리는 것이 안전합니다.

8. 웹 스트림 상호운용

Node 18부터 WHATWG 스트림(ReadableStream, WritableStream, TransformStream)이 전역에 있고, fetch()의 body가 이것입니다. Node 스트림과는 백프레셔 모델이 비슷하지만(큐잉 전략의 highWaterMark + size() 함수) API가 다릅니다.

const { Readable, Writable } = require('node:stream');
// Node → Web
const webReadable = Readable.toWeb(fs.createReadStream('big.bin'));
new Response(webReadable);                         // 예: 웹 표준 프레임워크(Hono 등)에 전달
// Web → Node
const nodeReadable = Readable.fromWeb((await fetch(url)).body);
await pipeline(nodeReadable, createGunzip(), fs.createWriteStream('out'));
// 또는 Node 전용 undici로 fetch를 쓰면 body를 바로 Node 스트림으로 소비 가능 (12장)
  • 변환 어댑터는 청크마다 Promise 왕복이 있어 대량의 작은 청크에서는 느립니다. 측정 없이 핫패스에 넣지 마세요.
  • 웹 스트림의 ReadableStream은 locked 개념이 있어 리더가 둘일 수 없고, tee()로 분기하면 느린 쪽 속도에 맞춰 버퍼가 자랍니다(백프레셔가 빠른 쪽에 안 걸림).
  • 한쪽 세계의 에러/취소가 다른 쪽으로 전파되는지 반드시 테스트하세요. 어댑터는 destroy ↔ cancel/abort를 매핑하지만 경계 조건이 있습니다.

9. 흔한 버그와 안티패턴

증상원인고치기
트래픽이 늘면 RSS 폭증, writableLength가 수백 MiBwrite() 반환값 무시 (루프 안의 res.write, 로그 스트림, 소켓 브로드캐스트)drain 대기, 또는 Readable.from + pipeline으로 위임. 브로드캐스트는 느린 클라이언트 끊기 정책.
요청을 처리하지 않고 응답했는데 소켓이 안 닫힘 / keep-alive 커넥션이 멈춤req(IncomingMessage) 본문을 소비하지 않음. 'end'가 안 와서 다음 요청으로 못 넘어감본문이 필요 없어도 req.resume() 또는 req.destroy(). 프레임워크는 보통 처리하지만 직접 http.createServer를 쓰면 책임이 있다.
'end'가 영원히 안 옴Readable을 소비하는 리스너가 없음 (flowing이 null). 'end'는 데이터를 다 소비해야 온다on('data')/resume()/pipe/for await 중 하나로 소비.
파일 디스크립터 누수 (EMFILE)pipe() 체인 중간 에러로 상류 파일 스트림이 destroy되지 않음pipeline()으로 교체. 테스트에서 process.getActiveResourcesInfo() 확인.
간헐적 한글 깨짐chunk.toString()이 멀티바이트 경계를 자름setEncoding('utf8') 또는 StringDecoder.
마지막 줄/레코드 누락Transform에 _flush 미구현 (잔여 버퍼 버림)_flush에서 잔여 push.
Buffer.concat(chunks) 후 OOM"스트림을 쓴다"면서 결국 전체를 모음. 스트림이 아님진짜 전체가 필요한지 재검토. 필요하면 크기 상한 검사 후 모으기(16장).
에러 후 write after end / ERR_STREAM_DESTROYEDpipeline 실패 후 catch에서 res에 다시 씀res.headersSent, res.destroyed 확인. 이미 보낸 응답은 되돌릴 수 없다.

10. 현업 장애 사례

사례 1: CSV 내보내기가 서버를 죽이다

관리자 화면의 "전체 내보내기"가 DB 커서를 돌며 res.write(line)을 반환값 확인 없이 호출. 사무실 Wi-Fi(느린 소비자)에서 500만 행을 요청하자 2분 만에 writableLength가 1.5GiB, 파드 OOMKilled. 다른 관리자 요청 전부 실패. 수정: Readable.from(cursor) → 직렬화 Transform → pipeline(..., res). 같은 요청에서 메모리 증가 0, 완료 시간은 클라이언트 대역폭에 맞춰 길어짐(그게 맞는 동작).

사례 2: 가끔 멈추는 업로드 프록시

클라이언트 → 프록시 → 스토리지로 req.pipe(storageReq). 스토리지가 4xx로 일찍 응답하고 소켓을 닫으면 storageReq가 에러로 destroy되지만 req는 pipe의 특성상 unpipe만 되고 소비되지 않음. 클라이언트는 업로드를 계속 보내고, 프록시는 req의 'end'를 기다리며 응답을 안 보냄 → 타임아웃까지 멈춤. 동시에 keep-alive 소켓이 그 요청에 묶여 커넥션 풀 고갈. 수정: pipeline(req, storageReq) + 에러 시 req.destroy(), 그리고 요청 본문 크기 상한.

사례 3: objectMode 파이프라인의 보이지 않는 48MiB

MongoDB 커서(objectMode) → 변환 → JSON 직렬화 → 응답. 문서 하나가 수 MiB인 컬렉션에서 동시 요청 10개가 들어오자 힙이 급증. 각 단계가 기본 highWaterMark 16개씩 버퍼링해 요청당 48개 문서가 메모리에 상주. 수정: objectMode 단계의 highWaterMark를 2로, 직렬화를 커서 바로 뒤로 옮겨 바이트 스트림으로 흘림.

핵심 요약

  • 스트림 = 내부 버퍼 + highWaterMark 임계. 임계는 상한이 아니라 "더 주지 마" 신호를 보내는 지점이다. 바이트 모드 기본 64KiB(Node 22+), objectMode 16개.
  • write()는 항상 받고, 반환값은 "다음 것을 지금 보내도 되는가". false는 length >= hwm. 'drain'은 버퍼가 완전히 빈 뒤 한 번.
  • Readable의 readableFlowing은 null/false/true. pause()는 명시적 false이며 그 뒤의 'data' 리스너는 흐름을 못 켠다. 'readable' 리스너가 'data'보다 우선.
  • pipe()는 dest.write()가 false면 src.pause(), 'drain'이면 resume(). 압력은 하류에서 상류로, 소켓이면 TCP 윈도우까지 전달된다.
  • pipe()는 에러를 전파하지 않는다. 항상 pipeline()(+ AbortSignal). 정리는 'close'에서. ERR_STREAM_PREMATURE_CLOSE는 대개 클라이언트 끊김.
  • 청크 경계 ≠ 의미 경계. Transform은 잔여 버퍼와 _flush가 필요하고, 멀티바이트는 setEncoding/StringDecoder.
  • 요청 본문은 필요 없어도 소비(resume())하거나 destroy. objectMode의 큰 객체는 highWaterMark를 낮춰라.

확인 문제

highWaterMark: 100인 Writable에 50바이트 청크를 연속으로 쓴다. 몇 번째 write()가 처음으로 false를 반환하는가? (하부 _write는 아직 완료되지 않았다고 가정)
반환값은 length < highWaterMark. 첫 번째 후 length 50 (<100 → true), 두 번째 후 length 100 (100 < 100은 거짓 → false). 등호가 포함된다는 점이 핵심입니다.
readable.pause()를 호출한 뒤 readable.on('data', fn)을 붙였다. 데이터가 흐르는가?
'data' 리스너는 flowing !== false일 때만 resume()을 호출합니다. 명시적 pause()는 사용자의 의도로 간주되어 resume()을 직접 부르기 전까지 유지됩니다. 반면 pipe()는 내부에서 resume()을 호출하므로 흐름이 시작됩니다.
a.pipe(b).pipe(c)에서 b가 에러로 destroy되었다. a와 c의 상태는?
pipe()는 에러를 전파하지 않습니다. dest 에러 시 src는 unpipe만 하고, src의 'end'가 dest.end()를 부르는 연결도 끊어집니다. 결과적으로 a의 하부 자원(fd)은 누수되고 c는 끝나지 않습니다. pipeline()은 셋 모두 destroy합니다.
백프레셔를 지키는 Writable에 highWaterMark를 64KiB에서 1MiB로 키웠다. 기대되는 변화로 옳은 것은?
highWaterMark는 생산자가 멈추기 전까지 쌓아 둘 수 있는 양입니다. 크면 멈춤이 드물어져 처리량이 오르지만 그만큼의 메모리를 스트림마다 쓸 수 있습니다. 소비자 속도와는 무관하고, 생산이 소비보다 빠른 한 false는 여전히 반환됩니다.
직접 만든 http.createServer 핸들러가 POST 본문을 읽지 않고 바로 res.end()했다. keep-alive 클라이언트에서 어떤 문제가 생기나?
HTTP/1.1 파서는 요청 본문이 소비되어야 같은 소켓의 다음 요청으로 넘어갑니다. 읽지 않은 본문은 소켓 버퍼에 남고 Node는 해당 요청의 'end'를 기다립니다. Express 등은 내부적으로 처리하지만 저수준 서버에서는 직접 소비하거나 연결을 끊어야 합니다.

실습 과제

  1. drain 실험. 아래 두 서버를 각각 띄우고 curl --limit-rate 100k http://localhost:3000/ > /dev/null로 느리게 받으면서 다른 터미널에서 process.memoryUsage().rss를 1초마다 찍어 보세요(핸들러 밖 setInterval). 기대: 첫 서버는 RSS가 초당 수십 MiB씩 증가, 두 번째는 평평. 
    // A: drain 무시
http.createServer((req, res) => {
  for (let i = 0; i < 2e6; i++) res.write('x'.repeat(1000) + '\n');
  res.end();
}).listen(3000);
// B: Readable.from + pipeline
const { pipeline } = require('node:stream/promises');
http.createServer((req, res) => {
  function* gen() { for (let i = 0; i < 2e6; i++) yield 'x'.repeat(1000) + '\n'; }
  pipeline(Readable.from(gen()), res).catch(() => {});
}).listen(3000);
  2. pipe vs pipeline fd 누수. 존재하는 큰 파일을 createReadStream으로 열고 손상된 gzip 데이터로 createGunzip()을 거쳐 fs.createWriteStream('/dev/null')로 보내는 코드를 pipe() 체인과 pipeline()으로 각각 100번 반복 실행한 뒤 process.getActiveResourcesInfo()와 lsof -p <pid> | wc -l을 비교하세요. 기대: pipe 버전은 열린 fd가 남음.
  3. 라인 파서 경계 테스트. 7.1절의 LineSplit에 "가나다\n라마바" 같은 한글 문자열을 Buffer로 만든 뒤 1바이트씩 잘라 write()하는 테스트를 작성하세요. setEncoding('utf8') 유무에 따라 출력이 어떻게 달라지는지 확인합니다.
