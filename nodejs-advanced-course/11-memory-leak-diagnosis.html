메모리 누수 진단

가비지 컬렉터가 있는 언어에서 "누수"란 해제를 잊은 메모리가 아니라, 아직 도달 가능하지만 더는 쓸 일이 없는 객체입니다. GC는 "도달 가능한가"만 보지 "필요한가"는 모르기 때문에, 누수의 범인은 언제나 어딘가에서 그 객체를 붙들고 있는 참조입니다. 이 장은 그 참조를 힙 스냅샷에서 찾아내는 기술과, 프로덕션에서 안전하게 덤프를 뜨는 운영 절차를 다룹니다.

학습 목표

  • retainer 경로, dominator, shallow/retained size의 정의를 알고 힙 스냅샷에서 범인 객체를 추적할 수 있다.
  • Node.js 서비스에서 반복적으로 나타나는 누수 패턴 7종을 코드만 보고 식별할 수 있다.
  • rss, heapUsed, external의 관계를 이해하고 "메모리가 안 내려간다"가 누수인지 아닌지 판별할 수 있다.
  • 프로덕션에서 힙 스냅샷을 안전하게 뜨고 비교 분석하는 절차를 설계할 수 있다.

1. 누수의 정의: 도달 가능성과 필요성의 간극

V8의 GC(5장)는 GC 루트(전역 객체, 현재 스택, 모듈 캐시, 활성 타이머·핸들, 내부 테이블)에서 출발해 참조를 따라가며 도달 가능한 객체를 표시하고, 나머지를 회수합니다. 따라서 Node.js에서 메모리 누수는 정확히 다음 한 문장으로 정의됩니다.

정의 누수 = GC 루트에서 도달 가능한 경로가 남아 있지만, 프로그램 의미상 다시는 사용되지 않을 객체가 시간이 지남에 따라 누적되는 것.

두 조건이 모두 중요합니다. 도달 가능하지 않으면 GC가 회수하므로 누수가 아니고, 누적되지 않으면(상한이 있으면) 그저 "메모리를 많이 쓰는 것"이지 누수가 아닙니다. 1GB를 쓰더라도 평형 상태에 도달하면 설계 문제일지언정 누수는 아니며, 요청당 1KB씩이라도 끝없이 늘면 누수입니다.

이 정의에서 진단의 전략이 바로 나옵니다. (1) 정말 누적되는가를 GC 이후 잔존량(post-GC baseline)으로 확인하고, (2) 누적되는 객체가 무엇인지 스냅샷 비교로 찾고, (3) 그 객체를 누가 붙들고 있는지 retainer 경로로 추적합니다. 세 단계 모두 도구가 있고, 이 장에서 각각을 다룹니다.

2. 힙 스냅샷의 구조: retainer, dominator, shallow/retained

힙 스냅샷(.heapsnapshot)은 특정 순간의 전체 객체 그래프를 JSON으로 직렬화한 것입니다. 노드(객체)마다 타입·이름·자기 크기(self size)·ID가 있고, 엣지(참조)마다 종류(property, element, context, weak, hidden 등)와 이름이 있습니다. Chrome DevTools와 모든 분석 도구는 이 그래프 위에서 다음 세 개념을 계산합니다.

개념정의진단에서의 쓰임
Shallow size객체 자체가 차지하는 바이트. 포인터·헤더·인라인 프로퍼티. 문자열·배열의 백킹 스토어는 별도 노드.작은 객체가 수만 개면 shallow는 작아도 개수(Count)가 단서.
Retained size이 객체를 제거했을 때 함께 회수될 모든 객체의 shallow 합. 즉 이 객체가 "붙들고 있는" 총량.Retained가 큰 순서로 정렬하면 범인 후보가 맨 위에 온다.
Retainer이 객체를 참조하는 객체(들). 역방향 엣지.범인 객체에서 retainer를 거슬러 올라가면 GC 루트까지의 경로 = "왜 안 지워지는가".
Dominator루트에서 객체 X로 가는 모든 경로가 반드시 지나는 객체 D. D를 지우면 X도 사라진다.Retained size는 dominator 트리로 계산된다. 거대한 retained를 가진 dominator가 곧 누수의 "소유자".

retained size와 dominator의 관계는 흔히 혼동됩니다. 객체 X를 A와 B 둘 다 참조하면 A를 지워도 X는 살아 있으므로 X는 A의 retained에 포함되지 않습니다. 오직 X로 가는 모든 경로가 A를 지날 때만(=A가 X를 dominate할 때만) A의 retained에 X가 더해집니다. 아래 탐색기에서 이 규칙을 직접 확인하세요.

스냅샷을 뜨는 방법

const v8 = require('node:v8');
// 동기. 완료될 때까지 이벤트 루프가 멈춘다. 파일명 생략 시 Heap-{date}-{pid}.heapsnapshot
const file = v8.writeHeapSnapshot(`/tmp/heap-${process.pid}-${Date.now()}.heapsnapshot`);
console.log('written', file);

// 스트림으로 받아 S3 등으로 직접 보낼 수도 있다
const stream = v8.getHeapSnapshot();   // Readable
stream.pipe(uploadStream);
# 프로세스 시작 시 플래그를 주면, 해당 시그널을 받을 때마다 CWD(또는 --diagnostic-dir)에 스냅샷을 쓴다
node --heapsnapshot-signal=SIGUSR2 --diagnostic-dir=/var/dumps server.js

# 운영 중 트리거
kill -USR2 <pid>
# 컨테이너라면
kubectl exec <pod> -- kill -USR2 1

코드 수정 없이 켤 수 있어 운영 표준으로 삼기 좋습니다. 단 SIGUSR1은 인스펙터 활성화용으로 예약되어 있으므로 SIGUSR2를 씁니다.

# 힙 사용량이 한계(--max-old-space-size)에 가까워지면 자동으로 스냅샷을 최대 N번 쓴다
node --heapsnapshot-near-heap-limit=3 --max-old-space-size=1024 server.js

# 런타임에서도 설정 가능 (Node 18.10+)
require('node:v8').setHeapSnapshotNearHeapLimit(3);

OOM으로 죽기 직전의 상태를 잡아 주므로 "가끔 터지는데 재현이 안 되는" 누수에 특히 유용합니다. 단 스냅샷을 쓰는 동안 추가 메모리가 필요하므로 한계가 너무 빡빡하면 스냅샷 도중 OOM이 날 수 있습니다. 컨테이너 메모리 한도를 --max-old-space-size보다 넉넉히 둡니다(14장).

node --inspect server.js
# chrome://inspect → Memory 탭 → "Take heap snapshot"
# 또는 "Allocation instrumentation on timeline"로 할당 추적

# 이미 떠 있는 프로세스에 인스펙터 붙이기
kill -USR1 <pid>          # 9229 포트로 인스펙터 열림
# 또는
node -e "process._debugProcess(<pid>)"

프로덕션에서 인스펙터 포트를 열어 두는 것은 보안상 금물입니다(16장). 로컬 재현이나 스테이징에서만.

탐색기에서 확인할 것 세 가지입니다. (1) reqLog 배열은 shallow가 작지만 retained가 가장 큽니다. 범인은 늘 "작은 컨테이너"입니다. (2) config는 app과 interval 두 경로로 도달 가능하므로, 둘 중 하나만 끊어서는 회수되지 않고 어느 쪽의 retained에도 포함되지 않습니다. (3) 엣지 종류 중 weak(점선)은 도달 가능성에 기여하지 않습니다. DevTools에서 "Retainers" 패널을 읽을 때도 weak 엣지는 건너뛰어야 합니다.

4. 누수 패턴 7종

십 년 넘게 Node.js 서비스에서 보고된 누수는 놀라울 만큼 적은 수의 패턴으로 수렴합니다. 각 패턴마다 "스냅샷에서 어떻게 보이는가"를 함께 기억해 두면 진단 속도가 열 배 빨라집니다.

4.1 상한 없는 캐시 (Map / 객체 / 배열)

끝없이 자란다
const cache = new Map();
app.get('/user/:id', async (req, res) => {
  if (!cache.has(req.params.id))
    cache.set(req.params.id, await db.user(req.params.id));
  res.json(cache.get(req.params.id));
});
// 키 공간이 무한(사용자 ID) → 평형 없음
상한 + 만료
// 직접 만든다면 Map의 삽입 순서를 이용한 LRU
class LRU {
  constructor(max) { this.max = max; this.m = new Map(); }
  get(k) { if (!this.m.has(k)) return; const v = this.m.get(k);
    this.m.delete(k); this.m.set(k, v); return v; }
  set(k, v) { this.m.delete(k); this.m.set(k, v);
    if (this.m.size > this.max) this.m.delete(this.m.keys().next().value); }
}
// 운영에서는 lru-cache 같은 검증된 구현(크기·TTL·maxSize 바이트)

스냅샷에서: Map 하나의 retained가 수백 MB, Summary 뷰에서 (string)이나 특정 클래스 Count가 요청 수에 비례해 증가.

4.2 이벤트 리스너 누적

// 요청마다 전역 emitter에 리스너를 붙이고 떼지 않음
app.use((req, res, next) => {
  configWatcher.on('change', () => { req.config = loadConfig(); });  // req를 클로저로 붙듦
  next();
});
// → (node:1234) MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 change listeners added to [EventEmitter]

리스너 자체는 작지만 클로저가 req/res/소켓을 통째로 붙듭니다. 경고는 리스너 11개째에 한 번만 나옵니다(events.defaultMaxListeners = 10). 경고를 setMaxListeners(0)으로 끄는 것은 누수를 숨기는 것입니다. 해결: 요청 수명과 함께 끝나는 리스너는 res.on('finish', () => emitter.off(...))로 정리하거나, events.on(emitter, 'change', { signal })로 AbortSignal에 묶습니다. 스냅샷에서: EventEmitter의 _events 아래 배열이 거대하고, 각 클로저의 context에 IncomingMessage가 매달려 있음.

4.3 해제하지 않은 타이머

function createSession(user) {
  const session = { user, data: new Map() };
  session.timer = setInterval(() => session.touch(), 30_000);   // 세션 종료 시 clearInterval 누락
  return session;
}

활성 타이머는 GC 루트입니다(libuv 핸들 → Timeout 객체 → 콜백 → 클로저 → session). 세션 객체를 다른 곳에서 모두 지워도 타이머가 살아 있는 한 회수되지 않고, 프로세스도 종료되지 않습니다. 스냅샷에서: Timeout 클래스 Count가 세션 수만큼, retainer 경로 최상단이 (Timers)/timer list.

4.4 클로저의 공유 컨텍스트

function handler() {
  const huge = loadBigBuffer();           // 50MB
  const small = () => 1;                  // huge를 쓰지 않는다
  const uses = () => huge.length;         // 같은 스코프의 다른 클로저가 huge를 쓴다
  registry.keep(small);                   // small만 오래 보관
  return uses();
}

V8은 함수 스코프마다 하나의 Context 객체를 만들고, 그 스코프의 클로저들이 공유합니다. 어떤 클로저든 huge를 참조하면 Context에 huge 슬롯이 생기고, 그 Context는 huge를 전혀 쓰지 않는 small에서도 도달 가능합니다. 결과: small을 보관하는 것만으로 50MB가 붙들립니다. 스냅샷에서: 작은 함수의 retainer 경로에 context 엣지로 거대한 객체가 매달림. 해결: 큰 데이터를 쓰는 코드와 오래 보관될 클로저를 다른 함수 스코프로 분리하거나, 사용 후 huge = null.

4.5 영원히 pending인 Promise와 그 체인

const results = new Map();
async function query(id) {
  const p = new Promise((resolve) => {
    socket.once(`reply:${id}`, resolve);   // 응답이 영영 안 오면 resolve 안 됨
  });
  results.set(id, p);                       // ← Map이 Promise를, Promise가 리스너·클로저를 붙듦
  return p;
}

pending Promise는 reaction(then 핸들러)들과 resolve 함수를 붙들고, 그것들이 다시 요청 컨텍스트를 붙듭니다. 타임아웃 없는 외부 대기는 모두 잠재적 누수입니다(13장: 모든 외부 호출에 데드라인). 스냅샷에서: Promise Count 증가, 각 Promise의 retainer에 PromiseReaction, PromiseCapability.

4.6 모듈 레벨 상태에 요청 데이터 저장

// logger.js
const recent = [];
module.exports.log = (req, msg) => { recent.push({ req, msg, at: Date.now() }); };  // req 전체를 저장
// '최근 100개만' 자르는 코드가 없거나, 다른 분기에서 빠짐

모듈은 require.cache(또는 ESM 모듈 맵)를 통해 프로세스 수명 내내 GC 루트에 가깝습니다. 모듈 레벨 변수에 들어간 것은 명시적으로 빼지 않는 한 영원합니다. 특히 요청 객체(IncomingMessage)를 통째로 보관하면 소켓·헤더·바디 버퍼까지 딸려옵니다. 로그에는 필요한 필드만 복사하세요. 스냅샷에서: retainer 경로 최상단이 (module) 또는 system / Context.

4.7 V8 sliced string: 부분 문자열이 원본을 붙든다

const lines = hugeLog.split('\n');     // 각 요소가 hugeLog를 참조하는 SlicedString일 수 있음
const ids = lines.map(l => l.slice(0, 12));
cache.set(key, ids);                    // 12바이트짜리 수천 개를 보관했는데 원본 100MB가 살아 있다

V8은 길이 13 이상(SlicedString::kMinLength)의 부분 문자열을 복사하지 않고 부모 문자열 + offset으로 표현합니다. 부분 문자열 하나만 살아 있어도 부모 전체가 회수되지 않습니다. 짧은 조각(13 미만)은 복사됩니다. 대형 텍스트에서 추출한 조각을 오래 보관한다면 Buffer.from(s).toString()처럼 강제로 평탄화(flatten)하거나, JSON.parse(JSON.stringify(s)) 같은 복사 경로를 거칩니다. (concat으로 만든 ConsString도 비슷하게 양쪽을 붙듭니다.) 스냅샷에서: Summary에서 (sliced string) 타입, retainer에 parent 엣지.

패턴 공통점 일곱 패턴 모두 "작은 것을 보관했는데 큰 것이 딸려온다"입니다. 보관하는 쪽(Map, 배열, 리스너 배열, 타이머, 모듈 변수)은 언제나 작고 평범해 보입니다. 그래서 스냅샷 분석의 첫 정렬 기준은 shallow가 아니라 retained size여야 합니다.

이 시뮬레이션이 보여주는 운영 교훈은 heapUsed 그래프만 보고는 누수를 판단할 수 없다는 것입니다. 톱니의 꼭대기는 할당 속도에 따라 얼마든지 올라갑니다. 봐야 할 것은 Mark-Sweep 직후의 최저점이 시간에 따라 어떻게 움직이는지이며, 이것이 15장에서 nodejs_heap_size_used_bytes를 min_over_time()으로 보는 이유입니다. 또한 요청당 누수가 수백 바이트에 불과해도 RPS가 높으면 시간 단위로 OOM에 도달합니다. "요청당 누수 × RPS × 가동 시간"을 계산하는 습관을 들이세요.

6. 스냅샷 비교 분석 절차

스냅샷 하나로는 "지금 무엇이 많은가"만 알 수 있습니다. 누수는 변화이므로 두 개 이상을 비교해야 합니다. 표준 절차는 다음과 같습니다.

  1. 워밍업: 서버를 띄우고 수백 요청을 처리해 모듈 로딩·JIT·캐시 초기화가 끝난 상태로 만든다. 이 전의 스냅샷은 "정상적 성장"과 누수를 구분하지 못한다.
  2. 스냅샷 1 (가능하면 직전에 --expose-gc로 global.gc() 또는 DevTools의 "Collect garbage" 버튼).
  3. 부하: 의심 경로에 정확히 N번(예: 1,000번) 요청. 숫자를 기억해 둔다.
  4. 스냅샷 2 (역시 GC 후).
  5. DevTools에서 스냅샷 2를 열고 Comparison 뷰, 기준을 스냅샷 1로. #Delta(개수 변화) 또는 Size Delta로 정렬.
  6. Delta가 N 또는 N의 배수에 가까운 클래스를 찾는다. 1,000번 요청에 Delta 1,000인 클래스가 요청당 하나씩 새는 객체다.
  7. 그 클래스의 인스턴스 하나를 선택해 하단 Retainers 패널에서 경로를 루트까지 따라간다. 첫 번째로 만나는 "내 코드의 컨테이너"(배열, Map, 클로저 context)가 범인.

Comparison이 "무엇이 늘었나"라면, Allocation instrumentation on timeline은 "어느 코드가 언제 할당했나"를 기록합니다. 기록 중 각 할당의 스택을 남기므로 오버헤드가 커서 프로덕션에는 부적합하지만, 로컬 재현에서는 범인 코드 줄까지 바로 보여줍니다. 기록 후 파란 막대(아직 살아 있는 할당)가 시간이 지나도 남는 구간을 선택하면 해당 할당의 호출 스택이 나옵니다.

프로덕션용으로는 sampling heap profiler(--heap-prof, 기본 512KB마다 샘플)가 있습니다. 샘플링이라 오버헤드가 낮고, 결과(.heapprofile)는 "어느 함수가 할당한 메모리가 아직 살아 있는가"를 호출 트리로 보여줍니다. 스냅샷(상태)과 프로파일(흐름)은 상호보완적입니다.

7. 메모리 지표 해석: rss는 왜 안 내려가나

process.memoryUsage()는 다섯 숫자를 줍니다. 각각이 가리키는 영역이 다르고, 누수 진단에서 의미도 다릅니다.

"GC가 돌았는데 rss가 안 내려가요"

정상입니다. 세 가지 이유가 있습니다. (1) V8은 회수한 힙 페이지를 바로 OS에 반환하지 않고 재사용을 위해 보유합니다(heapTotal이 서서히 줄어드는 이유). (2) external 메모리(Buffer)는 glibc malloc을 거치는데, glibc는 해제된 청크를 arena에 보관하고 힙 끝부분이 연속으로 비어야만 brk를 되돌립니다. 작은 할당이 섞여 있으면 사실상 반환되지 않습니다. 이것이 Alpine(musl) 대비 Debian(glibc) 이미지에서 rss가 높게 유지되는 이유이고, MALLOC_ARENA_MAX=2나 jemalloc으로 완화하는 운영 요령이 있습니다(14장). (3) 페이지 캐시·공유 라이브러리 매핑은 애초에 돌려줄 것이 아닙니다.

따라서 rss의 단조 증가는 누수의 충분조건이 아닙니다. 누수를 판정하려면 heapUsed 최저점 또는 external의 추세를 보세요. 반대로 rss가 컨테이너 한도에 닿으면 누수든 아니든 죽으므로, 한도 설정은 --max-old-space-size + external 예상치 + 할당자 여유분을 합쳐 잡아야 합니다.

8. 약한 참조: WeakMap, WeakRef, FinalizationRegistry

"객체에 메타데이터를 붙이되, 객체가 사라지면 메타데이터도 사라지게" 하는 것이 약한 참조의 용도입니다. 세 도구의 차이를 정확히 알아야 합니다.

도구의미적합한 용도함정
WeakMap/WeakSet키 객체가 다른 곳에서 도달 불가능해지면 엔트리 자동 제거. 순회 불가.요청 객체 → 부가 정보 매핑(예: WeakMap<IncomingMessage, Context>)키가 원시값이면 못 씀(Symbol 키는 일부 가능). 값→키 역참조가 있으면 여전히 누수(값이 키를 잡음).
WeakRefderef()로 대상을 꺼내되, GC가 회수했으면 undefined."있으면 쓰고 없으면 다시 만드는" 캐시같은 틱 안에서는 회수되지 않음(V8은 잡 완료까지 보존). 회수 시점이 비결정적이라 캐시 적중률 예측 불가.
FinalizationRegistry대상이 회수된 후 콜백 실행.네이티브 리소스 정리의 안전망(주 정리 수단이 아님)콜백 실행 시점·실행 여부 자체가 보장되지 않음(프로세스 종료 시 미실행). 여기에 비즈니스 로직을 두면 안 됨.
// 요청 컨텍스트를 WeakMap으로: 요청이 끝나 req가 회수되면 컨텍스트도 함께 사라진다
const ctx = new WeakMap();
app.use((req, res, next) => { ctx.set(req, { startedAt: performance.now(), traceId: newId() }); next(); });

// 7장의 AsyncLocalStorage가 같은 문제를 더 깔끔하게 푼다. WeakMap은 "객체에 매달아야 할 때"의 도구.
약한 참조는 누수 해법이 아니다 약한 참조로 바꿔서 누수가 "사라졌다면" 그 데이터는 애초에 보관할 이유가 없었던 것입니다. 보관이 필요하다면 상한(LRU)과 만료(TTL)로 수명을 명시하세요. WeakRef 캐시는 GC 압력에 따라 적중률이 널뛰어 성능 예측을 망칩니다.

9. 프로덕션 덤프 운영 절차

힙 스냅샷은 비쌉니다. writeHeapSnapshot은 동기이며, 힙 전체를 순회·직렬화하는 동안 이벤트 루프가 멈춥니다(수백 MB 힙에서 수 초~수십 초). 또한 직렬화 과정에서 추가 메모리가 필요해 힙 크기와 비슷한 양의 여유 메모리가 없으면 스냅샷 도중 OOM이 납니다. 그러므로 "아무 때나 덤프"가 아니라 절차가 필요합니다.

자동화 예시: 메모리 워치독

// 프로세스 안에서 스스로 판단해 덤프하는 워치독. 시그널 방식이 안 되는 환경용.
const v8 = require('node:v8');
const { monitorEventLoopDelay } = require('node:perf_hooks');
const LIMIT = v8.getHeapStatistics().heap_size_limit;
let dumped = 0, lows = [];
setInterval(() => {
  const used = process.memoryUsage().heapUsed;
  lows.push(used); if (lows.length > 30) lows.shift();          // 최근 30분(1분 간격)
  const rising = lows.length === 30 && Math.min(...lows.slice(-10)) > Math.min(...lows.slice(0, 10)) * 1.3;
  if ((rising || used > LIMIT * 0.85) && dumped < 2) {
    dumped++;
    markUnready();                                               // readiness 프로브를 실패시켜 트래픽 제외 (14장)
    setTimeout(() => { v8.writeHeapSnapshot(`/dumps/heap-${process.pid}-${dumped}.heapsnapshot`); markReady(); }, 10_000);
  }
}, 60_000).unref();

스냅샷을 열 때는 DevTools 외에 CLI 도구도 유용합니다. 수 GB짜리는 DevTools가 버티지 못하므로, heapsnapshot-parser 류 라이브러리로 노드를 Constructor별로 집계하는 스크립트를 미리 준비해 두세요. 또한 Node 20+의 node --inspect 없이도 node:inspector 모듈의 Session으로 HeapProfiler.takeHeapSnapshot을 프로세스 내부에서 호출할 수 있습니다.

10. 현업 장애 사례

사례 1: "메모리 누수"로 보고됐지만 누수가 아니었던 Buffer 풀

rss가 배포 후 6시간 동안 400MB→1.4GB로 증가해 누수로 보고됨. heapUsed 최저점은 평평했고 external만 증가. 원인은 대용량 파일 업로드 핸들러가 요청마다 64MB Buffer.allocUnsafe를 만들고, glibc가 해제된 큰 청크를 arena에 보유. 평형은 1.6GB 근처였지만 컨테이너 한도가 1.5GB라 OOM. 해결: 스트리밍 처리로 청크 크기 축소 + MALLOC_ARENA_MAX=2 + 한도 조정. 교훈: external과 heapUsed를 분리해서 알람.

사례 2: 로그 라이브러리의 child logger 누적

요청마다 logger.child({ reqId })를 만들었고, 라이브러리의 오래된 버전이 child를 부모의 배열에 등록해 두고 제거하지 않음. 요청당 약 2KB, 300 RPS → 시간당 2GB. 스냅샷 Comparison에서 Logger 클래스 Delta가 요청 수와 정확히 일치해 10분 만에 식별. 라이브러리 업그레이드로 해결. 교훈: Delta가 요청 수와 일치하는 클래스부터.

사례 3: 스냅샷을 뜨다가 죽은 프로세스

1.2GB 힙에서 kill -USR2로 스냅샷을 뜨자 25초간 루프가 멈춰 LB 헬스체크가 실패했고, 직렬화 중 메모리가 2.3GB까지 올라 컨테이너 한도(2GB)에서 OOM kill. 스냅샷 파일도 불완전. 교훈: 덤프 전 트래픽 제외 + 한도 여유 확인. 이후 --heapsnapshot-near-heap-limit를 한도의 60% 지점에 걸리도록 --max-old-space-size를 조정해 자동화.

핵심 요약

  • 누수 = 도달 가능하지만 불필요한 객체의 누적. 판정 지표는 heapUsed의 GC 후 최저점(또는 external)의 추세이지 rss나 heapUsed 피크가 아니다.
  • 스냅샷 분석의 세 개념: retainer 경로(왜 안 지워지나), dominator(누가 소유하나), retained size(얼마나 붙들고 있나). 정렬은 항상 retained 기준.
  • 패턴 7종: 상한 없는 캐시, 리스너 누적, 타이머 미해제, 클로저 공유 컨텍스트, pending Promise, 모듈 레벨 상태, sliced string. 공통점은 "작은 컨테이너가 큰 것을 붙든다".
  • 비교 절차: 워밍업 → GC → 스냅샷1 → 정확히 N회 요청 → GC → 스냅샷2 → Comparison에서 Delta≈N인 클래스 → Retainers로 루트까지.
  • rss가 안 내려가는 것은 V8 페이지 보유 + glibc arena 때문이며 그 자체로는 누수가 아니다. 단 컨테이너 한도는 rss를 본다.
  • 약한 참조는 "객체에 매달린 메타데이터"용이지 누수 해법이 아니다. 보관이 필요하면 상한과 TTL로 수명을 명시한다.
  • 프로덕션 덤프는 동기 정지 + 힙만큼의 추가 메모리가 든다. 트래픽 제외 → SIGUSR2 → 반출 → 재시작. 두 장 이상.

확인 문제

객체 X를 A와 B가 모두 참조하고, A와 B는 각각 서로 다른 경로로 GC 루트에 도달한다. A의 retained size에 X는 포함되는가?
retained size는 dominator 트리로 계산됩니다. 루트에서 X로 가는 모든 경로가 A를 지나야만 A가 X를 dominate하고, 그때만 A의 retained에 X가 더해집니다. 두 경로가 독립적이면 X의 dominator는 둘의 공통 조상(여기선 루트)입니다.
모니터링에서 rss는 계속 증가하는데 heapUsed의 GC 직후 최저점은 일정하고 external이 증가하고 있다. 가장 가능성 높은 원인은?
external은 V8 힙 밖의 메모리(Buffer 백킹 스토어 등)입니다. heapUsed가 평평하면 JS 객체 누수는 아니고, external이 늘면 Buffer를 붙들고 있거나(예: 소켓 버퍼를 배열에 보관) glibc arena 보유분이 늘어난 것입니다. arrayBuffers 필드와 함께 보면 구분됩니다.
다음 중 V8에서 "작은 조각을 보관했는데 큰 원본이 회수되지 않는" 상황을 만드는 것은?
길이 13 이상의 부분 문자열은 SlicedString으로 부모를 참조합니다. 5글자는 복사되고, Number로 변환하면 문자열이 아니므로 무관합니다. 1번도 사실 원본 Buffer의 ArrayBuffer를 공유하므로 같은 문제가 있지만(subarray는 뷰), 이 문제는 V8 문자열 표현을 묻는 것으로 4번이 가장 직접적입니다. 1번처럼 Buffer 뷰도 원본을 붙든다는 점을 함께 기억하세요.
프로덕션 인스턴스에서 힙 스냅샷을 뜨기 전에 반드시 확인해야 할 것은?
writeHeapSnapshot은 동기로 루프를 멈추고(헬스체크 실패), 직렬화 중 추가 메모리를 쓰며(OOM 위험), 힙 크기만 한 파일을 씁니다(디스크). 인스펙터 포트를 외부에 여는 것은 보안 사고입니다.
함수 안에서 50MB 버퍼를 지역 변수로 만들고, 그 버퍼를 쓰지 않는 작은 콜백만 전역 레지스트리에 등록했다. 버퍼가 회수되지 않는 이유는?
V8은 스코프당 하나의 Context 객체를 만들어 그 스코프의 클로저들이 공유합니다. 어떤 클로저든 변수를 캡처하면 Context에 슬롯이 생기고, 그 변수를 쓰지 않는 클로저도 Context를 통해 도달 가능하게 합니다.

실습 과제

  1. 누수 재현과 비교 분석. 아래 서버를 node --inspect leak.js로 띄우고 DevTools Memory 탭에서 절차(워밍업 → 스냅샷1 → 1,000회 요청 → 스냅샷2 → Comparison)를 수행하세요. 기대: Comparison에서 (closure) 또는 IncomingMessage Delta가 약 1,000이고, Retainers 경로가 _events → bus로 이어진다. 그다음 res.on('finish')에서 bus.off를 추가해 Delta가 0 근처가 되는지 확인. 
    const http = require('node:http'); const { EventEmitter } = require('node:events');
const bus = new EventEmitter(); bus.setMaxListeners(0);
http.createServer((req, res) => {
  bus.on('reload', () => { req.headers['x-reloaded'] = '1'; });   // req를 캡처하는 리스너 누적
  res.end('ok');
}).listen(3000);
// 부하: for i in $(seq 1000); do curl -s localhost:3000 > /dev/null; done
  2. 시그널 덤프 자동화. 같은 서버를 node --heapsnapshot-signal=SIGUSR2 --diagnostic-dir=/tmp/dumps leak.js로 띄우고, 부하 전후로 kill -USR2를 두 번 보내 두 파일을 만든 뒤 DevTools의 "Load"로 불러와 Comparison 하세요. 기대: 1번과 동일한 결과를 코드 수정 없이 얻는다. 추가로 스냅샷 생성에 걸린 시간(루프 정지 시간)을 monitorEventLoopDelay의 max로 측정해 보세요.
  3. sliced string 확인. 100MB 문자열을 만들고 slice(0, 20) 1,000개를 배열에 보관한 뒤 원본 참조를 null로 만들고 global.gc()(--expose-gc)를 호출해 heapUsed가 내려가지 않음을 확인하세요. 이어서 각 조각을 Buffer.from(s).toString()으로 평탄화하면 내려가는지 비교. 기대: 전자는 약 100MB 잔존, 후자는 수십 KB.
