관측성: 로그·메트릭·트레이스

장애는 "에러 로그가 없는데 느리다", "메트릭은 정상인데 사용자는 실패한다"처럼 신호 사이의 틈에서 옵니다. 이 장은 Node.js 프로세스에서 세 가지 신호를 비용 없이 뽑아내고, 서로 연결하고, 그 위에 알람을 세우는 방법을 다룹니다. 특히 로깅이 이벤트 루프를 막는 조건, 히스토그램 버킷이 p99를 왜곡하는 방식, 트레이스 컨텍스트가 async 경계를 넘는 메커니즘처럼 Node 특유의 함정에 집중합니다.

학습 목표

  • stdout의 동기/비동기 규칙을 알고, 루프를 막지 않으면서 유실도 없는 로그 파이프라인(pino + transport)을 구성할 수 있다.
  • RED/USE 메트릭을 prom-client로 노출하고, 히스토그램 버킷과 레이블 카디널리티를 설계할 수 있다.
  • OpenTelemetry로 분산 트레이싱을 켜고, AsyncLocalStorage 기반 컨텍스트 전파와 W3C traceparent를 설명할 수 있다.
  • 진단 리포트와 인스펙터를 프로덕션에서 안전하게 쓰고, Node 서비스용 대시보드·알람 세트를 설계할 수 있다.

1. 세 기둥과 상관관계

로그는 무슨 일이 있었는지(이산 이벤트), 메트릭은 얼마나(집계된 수치), 트레이스는 어디서 시간이 갔는지(요청 하나의 인과 관계)를 답합니다. 셋 중 하나만으로는 "p99가 튀었다(메트릭) → 어떤 요청이?(트레이스) → 그 요청에서 무슨 에러가?(로그)"라는 질문 체인을 끝까지 따라갈 수 없습니다. 연결 고리는 trace_id입니다. 모든 로그 라인에 현재 트레이스 ID를 찍고, 메트릭에는 exemplar(샘플 trace_id)를 붙입니다.

2. 구조화 로깅과 stdout의 진실

2.1 console.log는 언제 블로킹하는가

process.stdout이 무엇에 연결되어 있느냐에 따라 쓰기가 동기인지 비동기인지가 달라집니다(Node 공식 문서 "A note on process I/O").

stdout 대상POSIX(Linux/macOS)Windows운영 의미
파일 (node app.js > out.log)동기동기디스크가 느리면 루프가 그만큼 멈춤. 유실 없음
TTY (터미널)동기비동기로컬 개발에서 대량 로그는 체감 느림
파이프/소켓 (컨테이너 stdout, | tee)비동기동기루프를 안 막지만, 소비자가 느리면 메모리에 쌓이고 process.exit() 시 유실

컨테이너 환경의 stdout은 거의 항상 파이프입니다. 직접 확인해 볼 수 있습니다. 아래 첫 명령은 파이프 버퍼(Linux 기본 64KiB)만큼만 나오고 나머지는 process.exit()에 의해 버려집니다.

$ node -e "process.stdout.write('x'.repeat(5e6)); process.exit(0)" | wc -c
   65536
$ node -e "process.stdout.write('x'.repeat(5e6)); process.exit(0)" > out.txt; wc -c < out.txt
 5000000

즉 console.log는 컨테이너에서 "안전한 비동기"가 아닙니다. 백프레셔(6장)를 무시하므로 로그 소비자(Docker 로깅 드라이버, fluent-bit)가 밀리면 쓰기 큐가 힙에 쌓여 OOM까지 갈 수 있고, 크래시 직전의 가장 중요한 로그가 사라집니다. 또 JSON 직렬화와 문자열 포맷은 메인 스레드 CPU를 씁니다.

2.2 pino의 설계

pino가 빠른 이유는 세 가지입니다. ① 로그 라인을 미리 컴파일된 문자열 조립으로 만든다(JSON.stringify 대신 fast-json-stringify 류). ② 기본 목적지(pino.destination(), 내부적으로 sonic-boom)는 동기 쓰기를 쓰되 버퍼링으로 시스템콜 수를 줄인다. 동기라서 유실이 없고, 백프레셔가 자연스럽게 걸린다. ③ 포맷 변환·전송(pretty, 파일 로테이션, Elasticsearch/Loki 전송)은 워커 스레드의 transport로 분리한다. 메인 스레드는 SharedArrayBuffer 링 버퍼에 라인을 쓰기만 하고 실제 I/O는 워커가 한다.

// logger.js
const pino = require('pino');
const { getActiveSpan } = require('./tracing'); // OTel trace.getSpan(context.active())

const logger = pino({
  level: process.env.LOG_LEVEL ?? 'info',
  // 매 라인에 현재 trace_id/span_id 를 섞는다 (ALS 기반)
  mixin() {
    const span = getActiveSpan();
    if (!span) return {};
    const { traceId, spanId } = span.spanContext();
    return { trace_id: traceId, span_id: spanId };
  },
  // 민감 정보 마스킹 (fast-redact 경로 문법)
  redact: { paths: ['req.headers.authorization', 'req.headers.cookie', '*.password', 'user.ssn'], censor: '[redacted]' },
  // 타임스탬프/레벨 포맷은 수집기 규약에 맞춤
  timestamp: pino.stdTimeFunctions.isoTime,
  formatters: { level: label => ({ level: label }) },
  // 프로덕션: stdout 에 동기 쓰기(기본). 전송이 필요하면 transport (워커 스레드)
  transport: process.env.LOG_TRANSPORT ? {
    targets: [
      { target: 'pino/file', options: { destination: 1 } },                 // stdout
      { target: 'pino-opentelemetry-transport', level: 'warn', options: {} } // 예: OTLP 로 warn 이상
    ]
  } : undefined,
});
module.exports = logger;

// 요청 범위 child logger: 공통 필드를 한 번만 바인딩
app.use((req, res, next) => { req.log = logger.child({ req_id: req.id, route: req.route?.path }); next(); });
transport의 두 가지 함정 ① 워커 링 버퍼가 가득 차면 pino는 기본적으로 메인 스레드가 동기로 기다립니다(유실 대신 블로킹). 소비자가 지속적으로 느리면 결국 루프가 막힙니다. ② 프로세스가 process.exit()로 즉시 끝나면 워커가 flush할 시간이 없습니다. 14장의 그레이스풀 셧다운에서 logger.flush() 후 자연 종료, 또는 pino.final 패턴(v7 이전)을 쓰세요. 크래시 핸들러에서는 pino.destination({ sync: true })로 만든 별도 로거를 씁니다.
로그 파이프라인 시뮬레이터

2.3 무엇을 어떻게 찍을 것인가

  • 이벤트 하나 = JSON 한 줄. 멀티라인 스택은 err 필드에 직렬화(pino의 err serializer). 수집기는 줄 단위로 파싱합니다.
  • 레벨 규약: error=사람이 봐야 함, warn=자동 복구됐지만 추세 감시, info=비즈니스 이벤트(주문 생성), debug=개발. 요청마다 info 한 줄(access log)은 큰 서비스에선 비용 때문에 샘플링하거나 메트릭으로 대체.
  • 필드 이름 고정: trace_id, req_id, user_id, duration_ms처럼 전사 규약. 같은 값이 userId/user_id/uid로 흩어지면 검색이 불가능해집니다.
  • 민감 정보: 헤더(Authorization, Cookie), 비밀번호, 개인정보는 redact. 요청 바디 전체 로깅 금지.
  • 로그 레벨 런타임 변경: logger.level = 'debug'를 SIGUSR2 핸들러나 관리 엔드포인트로. 재배포 없이 특정 파드만 상세 로그를 켤 수 있습니다.

3. 로그 샘플링과 비용

로그 비용은 "생성"이 아니라 "저장·색인"에서 나옵니다. 요청당 600바이트 access log를 초당 5,000건 찍으면 하루 약 260GB. 전형적인 로그 SaaS 가격이면 이것만으로 월 수천 달러입니다. 비용을 줄이는 순서는 다음과 같습니다.

  1. 메트릭으로 옮길 수 있는 것은 옮긴다. "요청 수, 지연, 상태코드"는 히스토그램 하나가 수백만 로그 라인을 대체합니다.
  2. 성공 요청은 샘플링, 실패·느린 요청은 전부. 예: 2xx이고 지연 < p95면 1%만 기록. 트레이스의 tail sampling과 같은 발상.
  3. 레벨 분리 저장: error/warn은 장기 보관, info는 단기(7일), debug는 수집 안 함.
  4. 반복 로그 억제: 같은 에러가 초당 수백 번 나오면 첫 N개 + "…and 4,310 more"로 집계. 장애 때 로그 폭주가 수집기와 비용을 함께 터뜨립니다.
// 성공 요청 1% 샘플링 (결정적: req_id 해시 기반이면 같은 요청은 항상 같은 결정)
function shouldLogAccess(res, durationMs) {
  if (res.statusCode >= 400 || durationMs > SLOW_MS) return true;
  return (hash(req.id) % 100) === 0;
}

4. 메트릭: prom-client, RED/USE, 히스토그램

4.1 네 가지 타입과 Node 기본 메트릭

타입의미Node 예쿼리 패턴
Counter단조 증가. 리셋만 됨http_requests_total{route,method,status}rate(x[5m])
Gauge현재 값nodejs_active_handles, 힙 사용량, 큐 길이그대로, 또는 max_over_time

//   nodejs_heap_size_used_bytes, nodejs_heap_space_size_used_bytes{space}

const httpDuration = new client.Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP 요청 처리 시간',
  labelNames: ['method', 'route', 'status_class'],   // status_class = 2xx/4xx/5xx: 카디널리티 억제
  buckets: [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10],
});
app.use((req, res, next) => {
  const end = httpDuration.startTimer();
  res.on('finish', () => end({ method: req.method, route: req.route?.path ?? 'unmatched', status_class: `${Math.floor(res.statusCode / 100)}xx` }));
  next();
});
app.get('/metrics', async (req, res) => { res.set('Content-Type', client.register.contentType); res.end(await client.register.metrics()); });
카디널리티 폭발 레이블 값의 조합 수만큼 시계열이 생깁니다. route에 /users/123처럼 실제 경로를 넣으면 사용자 수만큼, user_id를 넣으면 무한히 늘어납니다. Prometheus는 시계열당 메모리를 쓰므로 서버가 죽거나 스크레이프가 실패합니다. 규칙: 레이블은 경로 템플릿(req.route.path), 상태 클래스, 메서드처럼 값의 집합이 유한하고 작은 것만. 404 경로는 'unmatched'로 뭉치세요(스캐너가 임의 경로로 카디널리티를 터뜨립니다).

4.2 RED와 USE

RED(Rate, Errors, Duration)는 요청을 처리하는 서비스의 사용자 관점 지표이고, USE(Utilization, Saturation, Errors)는 자원 관점입니다. Node 프로세스에 대입하면:

지표소스
R초당 요청 수 (라우트별)rate(http_requests_total[1m])
E5xx 비율, 미처리 예외 수, 클라이언트 타임아웃counter + process.on('uncaughtException') 카운터
D지연 p50/p95/p99히스토그램
U (이용률)ELU, CPU 사용률 / limitperformance.eventLoopUtilization(), process_cpu_seconds_total
S (포화)루프 지연 p99, 스레드풀 대기, 커넥션 풀 대기 수, 큐 길이nodejs_eventloop_lag_p99_seconds, 풀 라이브러리 메트릭
E (자원 에러)OOM, GC 시간 비율, EMFILE, ECONNRESETnodejs_gc_duration_seconds, 에러 코드 카운터

4.3 히스토그램 버킷 설계

histogram_quantile은 각 버킷 안에서 값이 균등 분포한다고 가정하고 선형 보간합니다. 따라서 p99가 떨어지는 버킷이 넓으면(예: 1s~10s) 추정 오차가 커지고, p99가 마지막 유한 버킷을 넘으면 그 버킷 상한값으로 잘립니다. 버킷은 "관심 있는 SLO 경계 근처가 촘촘하게"가 원칙입니다. SLO가 300ms라면 200·250·300·400·500ms를 넣어야 합니다.

5. 분산 트레이싱: OpenTelemetry

5.1 구성

OpenTelemetry(OTel)는 API(코드가 호출), SDK(실제 구현: 샘플러, 프로세서, 익스포터), 자동 계측(http, undici, express, pg, mysql, redis, grpc… 라이브러리를 monkey-patch해 span 생성)으로 나뉩니다. Node에서는 앱 코드보다 먼저 SDK가 로드되어야 계측 대상 모듈이 패치됩니다. 그래서 --require 또는 --import로 선로드합니다.

// tracing.js — 앱보다 먼저 로드: node --require ./tracing.js server.js  (ESM이면 --import)
const { NodeSDK } = require('@opentelemetry/sdk-node');
const { getNodeAutoInstrumentations } = require('@opentelemetry/auto-instrumentations-node');
const { OTLPTraceExporter } = require('@opentelemetry/exporter-trace-otlp-grpc');
const { ParentBasedSampler, TraceIdRatioBasedSampler } = require('@opentelemetry/sdk-trace-base');

const sdk = new NodeSDK({
  serviceName: 'orders-api',
  traceExporter: new OTLPTraceExporter({ url: process.env.OTEL_EXPORTER_OTLP_ENDPOINT }),
  sampler: new ParentBasedSampler({ root: new TraceIdRatioBasedSampler(0.1) }), // 루트 10%, 부모가 샘플이면 따라감
  instrumentations: [getNodeAutoInstrumentations({
    '@opentelemetry/instrumentation-fs': { enabled: false },   // fs span 은 노이즈가 큼
  })],
});
sdk.start();
process.on('SIGTERM', () => sdk.shutdown());   // 미전송 span flush (14장 셧다운 순서에 포함)

// 또는 코드 없이: node --require @opentelemetry/auto-instrumentations-node/register server.js
//   + OTEL_SERVICE_NAME, OTEL_EXPORTER_OTLP_ENDPOINT, OTEL_TRACES_SAMPLER=parentbased_traceidratio, OTEL_TRACES_SAMPLER_ARG=0.1

5.2 컨텍스트 전파: 두 개의 경계

프로세스 안에서는 7장의 AsyncLocalStorage가 현재 span을 비동기 체인을 따라 실어 나릅니다. await, 콜백, 타이머, 이벤트 에미터(일부 예외)까지 자동으로 따라가지만, 직접 만든 큐나 커넥션 풀처럼 "등록 시점과 실행 시점의 비동기 컨텍스트가 다른" 구조에서는 끊깁니다. 이때는 context.with(ctx, fn)이나 context.bind로 명시적으로 이어야 합니다.

프로세스 사이에서는 W3C Trace Context 헤더가 전파됩니다. 자동 계측이 outgoing http/undici 요청에 헤더를 붙이고 incoming 요청에서 읽습니다.

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                │
             │  trace-id (16바이트, 전체 요청 공통)  parent span-id    flags: 01 = sampled
             version
tracestate: vendor=... (벤더별 부가 상태, 선택)

메시지 큐(Kafka, SQS, BullMQ)는 HTTP 헤더가 없으므로 메시지 속성에 traceparent를 직접 넣고 꺼내야 합니다(일부 계측 라이브러리가 지원). 끊긴 트레이스의 대부분은 큐 경계와 커스텀 풀에서 생깁니다.

트레이스 워터폴 뷰어
주문 조회 요청 하나의 span 트리입니다. 행을 클릭하면 속성과 그 span 구간에 찍힌 로그(trace_id로 조인)를 보여 줍니다. 어디서 시간이 갔는지, 어떤 호출이 직렬로 묶여 있는지 찾아보세요.
span을 클릭하세요.

위 트레이스에서 읽어야 할 것: ① redis.get과 pg.query가 직렬인데 서로 의존하지 않는다면 Promise.all로 병렬화할 수 있다. ② http GET inventory가 전체의 절반을 차지한다. 그 서비스의 자식 span이 짧다면 네트워크/커넥션 수립 비용(12장 keep-alive 미사용)이다. ③ 루트 span의 시작과 첫 자식 사이의 공백은 미들웨어나 이벤트 루프 지연이다.

6. 진단 리포트와 인스펙터

6.1 진단 리포트 (Diagnostic Report)

프로세스의 "현재 상태 전체"를 JSON 한 파일로 떨어뜨리는 내장 기능입니다. 크래시 직후 사후 분석, 또는 "지금 행(hang) 걸린 프로세스가 뭘 하고 있나"를 볼 때 씁니다.

6.2 프로덕션에서 인스펙터

실행 중인 프로세스에 SIGUSR1을 보내면 인스펙터가 127.0.0.1:9229에서 열립니다(--inspect-port로 변경). 여기에 Chrome DevTools를 붙여 CPU 프로파일(10장), 힙 스냅샷(11장)을 라이브로 뜰 수 있습니다. 규칙:

  • 인스펙터는 임의 코드 실행 권한입니다. 절대 0.0.0.0에 바인딩하지 말고, 컨테이너 포트로 노출하지 마세요. 접근은 kubectl port-forward pod 9229:9229로 로컬 루프백만.
  • 힙 스냅샷은 힙 크기의 몇 배 메모리와 수 초~수십 초의 완전 정지를 유발합니다. 트래픽에서 뺀(readiness 503) 파드에서만.
  • CPU 프로파일링은 오버헤드가 작아(수 %) 트래픽 중에도 짧게 가능합니다.
  • 끝나면 inspector.close()나 프로세스 교체로 닫으세요. 열어 둔 채 잊는 것이 흔한 실수입니다.

7. 대시보드와 알람 설계

Node 서비스 대시보드의 상단 한 줄은 RED(요청률·에러율·p99)이고, 그 아래가 "왜"를 설명하는 Node 내부 지표입니다. 알람은 증상(사용자가 느끼는 것)에만 페이지를 울리고, 원인 지표는 티켓이나 대시보드로 보냅니다.

알람 피로를 막는 규칙 ① 모든 알람에 런북 링크. ② 증상 알람은 SLO 소진율(burn rate)로: 1시간에 월 예산의 2%를 태우면 페이지. ③ 원인 알람은 "증상 알람이 울렸을 때 보는 대시보드"로 격하. ④ 파드 하나의 지표로 울리지 말고 서비스 합계로. 파드 하나의 GC 스파이크는 정상입니다.

8. 현업 장애 사례

사례 1: 로그 수집기 장애가 API 장애로

fluent-bit가 백엔드 연결을 잃고 파이프 소비를 멈췄습니다. 앱은 console.log로 요청당 2줄을 찍었고, 파이프 쓰기가 비동기라 Node 쓰기 큐가 힙에 쌓이기 시작. 20분 뒤 힙 1.5GB로 OOMKilled. 재시작 후에도 반복. 로그를 pino 동기 목적지로 바꾸자 수집기 장애 시 루프가 느려지긴 했지만(백프레셔) 죽지는 않았고, 궁극적으로 수집기 버퍼 설정과 access log 샘플링으로 해결.

사례 2: p99가 "정확히 1초"

대시보드의 p99가 몇 주째 정확히 1.0s. 버킷이 [0.1, 0.5, 1, 5]였고 실제 p99는 1.2~1.8s 사이를 오갔는데 1~5s 버킷에서 보간되어 1s 근처로 뭉개졌습니다. 더 나쁜 것은 SLO 알람(p99 > 1.5s)이 한 번도 울리지 않았다는 점. 버킷을 0.75·1·1.5·2·3·5로 바꾸자 실제 값이 드러났습니다. 위 설계기에서 "성긴 버킷"을 눌러 보세요.

사례 3: 트레이스가 큐에서 끊김

주문 API → BullMQ 큐 → 워커의 결제 호출 체인에서 결제 지연을 추적하려는데 트레이스가 큐 앞에서 끝났습니다. 큐 잡 데이터에 traceparent를 넣고 워커에서 propagation.extract로 복원해 자식 span을 만들자 체인이 이어졌고, 지연 원인이 워커의 동시성 1 설정임이 바로 보였습니다.

사례 4: 메트릭 엔드포인트가 OOM의 원인

라우트 레이블에 req.path(실제 경로)를 썼고, 봇 스캐너가 수십만 개의 랜덤 경로를 두드려 prom-client 레지스트리가 수십만 시계열을 들고 있게 됐습니다. /metrics 응답이 50MB, 직렬화에 2초(루프 블로킹), 프로세스 힙 증가. req.route.path와 'unmatched'로 교체.

핵심 요약

  • 컨테이너의 stdout은 파이프이고 POSIX에서 비동기: console.log는 소비자가 느리면 메모리에 쌓이고 process.exit() 시 유실된다. pino 기본 목적지(동기+버퍼) 또는 transport(워커)로.
  • 로그는 JSON 한 줄, 필드명 규약, redaction, trace_id mixin. 비용은 샘플링(성공 요청)과 메트릭 대체로 줄인다.
  • 메트릭은 RED + Node 내부(루프 지연 p99, ELU, 힙, GC). 레이블은 유한 집합만. 히스토그램 버킷은 SLO 경계 근처를 촘촘히, p99가 마지막 유한 버킷을 넘지 않게.
  • OTel은 앱보다 먼저 로드(--require). 프로세스 안 전파는 ALS, 밖은 W3C traceparent. 큐 경계는 수동 전파.
  • 진단 리포트는 행/OOM 사후 분석의 1차 도구. 인스펙터는 루프백 + 포트포워딩으로만, 힙 스냅샷은 트래픽에서 뺀 파드에서만.
  • 페이지는 증상(에러율, p99 SLO 소진율)에만. 원인 지표는 대시보드와 티켓으로.

확인 문제

Linux 컨테이너에서 console.log로 대량 로깅하는 서비스가, 로그 수집기가 멈춘 뒤 20분 만에 OOMKilled 되었다. 가장 직접적인 메커니즘은?
파이프 stdout은 POSIX에서 비동기이며 console.log는 백프레셔를 무시합니다. 소비자가 멈추면 쓰기 요청이 메모리에 계속 쌓입니다. 동기 목적지였다면 루프가 느려졌겠지만 메모리는 안전했을 것입니다.
버킷 [0.1, 0.5, 1, 5]인 히스토그램으로 p99를 구했더니 항상 1.0 근처다. 실제 p99가 1.7s일 때 무엇이 잘못됐나?
histogram_quantile은 버킷 내부 균등 분포를 가정합니다. 1~5s 버킷에 소수의 샘플이 들어가면 그 안에서 보간된 값은 실제와 크게 다를 수 있습니다. SLO 경계 근처 버킷을 추가해야 합니다. Summary는 서버 간 합산이 불가능해 대안이 아닙니다.
OpenTelemetry 자동 계측이 http span을 전혀 만들지 않는다. 가장 흔한 원인은?
자동 계측은 모듈 로드를 가로채 패치합니다. 앱 코드(또는 프레임워크)가 먼저 http를 require하면 패치되지 않은 원본을 쥐고 있게 됩니다. --require ./tracing.js로 선로드하세요. 샘플링 0.1이나 Collector 다운은 span이 "만들어지지만 전송/저장되지 않는" 상황입니다.
메트릭 레이블로 적절하지 않은 것은?
user_id는 값의 집합이 무한에 가까워 시계열 수를 폭발시킵니다. 사용자 단위 분석은 로그나 트레이스의 역할입니다.
프로덕션 파드가 요청에 응답하지 않고 CPU 100%다. 재시작 전에 원인을 남기려면?
행/CPU 100% 상황에서 가장 싸고 빠른 증거는 진단 리포트의 JS 스택입니다. 리포트는 시그널 핸들러에서 생성되므로 루프가 막혀 있어도 동작합니다. 힙 스냅샷은 메모리 문제용이고 비용이 큽니다.

실습 과제

  1. stdout 유실 재현. 2.1절의 두 명령을 실행해 파이프에서 64KiB만 남는 것을 확인하고, process.exit(0)를 process.exitCode = 0으로 바꿔 전체가 출력되는지 확인하세요. 이어서 pino 기본 로거로 같은 양을 찍고 process.exit() 해도 유실이 없는지(동기 목적지) 확인합니다.
  2. 버킷 설계 검증. prom-client로 두 히스토그램(버킷 A: 기본, 버킷 B: SLO 300ms 근처 촘촘)에 같은 지연 샘플(로그정규, 예: Math.exp(Math.log(0.08) + 0.8 * gaussian()))을 10만 개 넣고, /metrics를 Prometheus에 스크레이프시켜 histogram_quantile(0.99, ...)를 비교하세요. 샘플 배열에서 직접 구한 p99와의 오차를 기록합니다.
  3. 트레이스 연결. 두 개의 Express 서비스(A가 B를 undici로 호출)에 --require @opentelemetry/auto-instrumentations-node/register와 OTLP → Jaeger(docker)를 붙이고, A의 pino 로그에 mixin으로 trace_id를 찍어 Jaeger UI의 트레이스와 로그의 trace_id가 일치하는지 확인하세요. 그다음 B 호출을 setTimeout 안에서 만든 커스텀 큐로 옮겨 트레이스가 끊기는지, context.with로 복구되는지 확인합니다.
