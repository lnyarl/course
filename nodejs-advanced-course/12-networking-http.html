네트워킹 심층: HTTP/1.1·2, 커넥션 관리

Node.js 서비스의 장애 중 가장 흔하면서 가장 오래 걸려 잡는 부류가 "간헐적 502", "ECONNRESET", "소켓 고갈"입니다. 모두 커넥션의 수명을 양쪽 끝(서버·클라이언트·중간의 로드밸런서)이 다르게 이해해서 생깁니다. 이 장은 TCP 커넥션이 태어나서 닫히기까지 Node.js가 관여하는 모든 타이머와 풀을 분해하고, HTTP/2·TLS·DNS까지 운영자가 손대야 하는 설정을 정리합니다.

학습 목표

  • HTTP 서버의 타임아웃 7종이 커넥션 수명의 어느 구간에 적용되는지 설명하고 기본값을 안다.
  • keep-alive 커넥션에서 서버·LB 타임아웃 불일치가 502를 만드는 메커니즘을 재현하고 올바른 값을 정할 수 있다.
  • http.Agent와 undici의 커넥션 풀 동작(maxSockets, 스케줄링, 유휴 소켓 수명)을 이해하고 외부 호출 설정을 설계할 수 있다.
  • HTTP/2 멀티플렉싱, TLS 세션 재개, DNS 조회 경로의 비용을 알고 적절한 선택을 할 수 있다.

1. 커넥션의 일생

HTTP 요청 하나의 비용은 "서버가 핸들러를 실행하는 시간"보다 커넥션을 만들고 유지하고 닫는 비용에 좌우되는 경우가 많습니다. 아래 도식은 TLS를 쓰는 keep-alive 커넥션의 전형적인 일생이며, 각 구간에 어떤 Node.js 설정이 관여하는지 표시했습니다.

2. 서버 내부: llhttp 파서와 요청 객체

http.createServer()가 만든 서버에 소켓이 들어오면(net.Server의 'connection'), Node.js는 소켓마다 HTTP 파서를 하나 붙입니다. 파서는 Node 12부터 llhttp(TypeScript로 기술한 상태 머신을 C로 생성)이며, 바이트가 도착할 때마다 parser.execute(buf)로 밀어 넣고, 파서는 헤더 완료·바디 청크·메시지 완료 시점에 C++→JS 콜백을 호출합니다. 파서 객체는 비싸서 FreeList(기본 1,000개)로 풀링합니다.

파서 단계에서 적용되는 한계값은 다음과 같습니다. 이들은 애플리케이션 코드보다 먼저 요청을 거부하므로, 미들웨어에 로그가 남지 않아 "요청이 사라졌다"고 느끼기 쉽습니다.

server.on('clientError', (err, socket) => {
  if (err.code === 'ECONNRESET' || !socket.writable) return;     // 이미 닫힌 소켓에 쓰지 않기
  metrics.inc('http_client_error', { code: err.code });           // HPE_HEADER_OVERFLOW, HPE_INVALID_METHOD, ERR_HTTP_REQUEST_TIMEOUT ...
  const status = err.code === 'HPE_HEADER_OVERFLOW' ? 431 : err.code === 'ERR_HTTP_REQUEST_TIMEOUT' ? 408 : 400;
  socket.end(`HTTP/1.1 ${status} ${http.STATUS_CODES[status]}\r\nConnection: close\r\n\r\n`);
});

3. 서버 타임아웃 7종

http.Server에는 서로 다른 구간을 지키는 타이머가 일곱 개 있습니다. 이름이 비슷해 혼동하기 쉬우니, "커넥션 수명의 어느 구간"을 지키는지로 기억하세요. 기본값은 Node 22/24 기준이며 아래 실습에서 직접 확인합니다.

설정기본값지키는 구간초과 시 동작운영 메모
server.headersTimeout60,000 ms소켓에 첫 바이트가 온 뒤(또는 keep-alive 재사용 시작 뒤) 헤더가 완성될 때까지408 + 소켓 종료 ('clientError', ERR_HTTP_REQUEST_TIMEOUT)Slowloris 방어. keepAliveTimeout보다 커야 한다(아래).
server.requestTimeout300,000 ms (Node 18+)요청 시작부터 바디 수신 완료까지408 + 소켓 종료대용량 업로드 경로에서는 라우트별로 req.setTimeout으로 늘림. 0이면 무제한(권장 안 함).
server.keepAliveTimeout5,000 ms응답 완료 후 다음 요청을 기다리는 유휴 시간서버가 소켓을 닫음(FIN)LB/프록시 idle timeout보다 커야 함. 4절의 핵심.
server.timeout0 (Node 13+, 무제한)소켓의 비활성(읽기·쓰기 모두 없음) 시간. socket.setTimeout'timeout' 이벤트만 emit. 핸들러가 없으면 소켓 destroyNode 12까지는 120s였음. 응답을 오래 스트리밍하는 핸들러(SSE)에서 의도치 않게 끊지 않도록 주의.
server.connectionsCheckingInterval30,000 msheadersTimeout·requestTimeout을 검사하는 주기-타이머가 소켓마다 있는 게 아니라 주기적으로 훑는다. 따라서 실제 만료는 설정값 + 최대 30s 늦을 수 있다.
server.maxRequestsPerSocket0 (무제한)한 keep-alive 커넥션에서 처리할 최대 요청 수초과 요청에 503 + Connection: closeLB 뒤에서 커넥션을 주기적으로 재분배하고 싶을 때(롤링 배포 시 트래픽 균등화).
socket.setTimeout / req.setTimeout / res.setTimeout없음개별 소켓·요청·응답의 비활성'timeout' emit라우트별 미세 조정. 'timeout' 핸들러에서 반드시 응답하거나 destroy.
headersTimeout > keepAliveTimeout 이어야 하는 이유 유휴 소켓에서 keepAliveTimeout이 끝나면 서버는 소켓을 닫습니다. 만약 headersTimeout이 더 짧으면, 유휴 중인 소켓이 "헤더가 안 온다"는 이유로 먼저 408을 받고 끊길 수 있습니다(구현상 헤더 타이머는 유휴 시작 시점부터 잽니다). Node 공식 문서도 두 값을 조정할 때 headersTimeout을 keepAliveTimeout보다 크게 두라고 안내하며, 흔한 관례는 keepAliveTimeout + 1000입니다.

4. keep-alive와 로드밸런서: 간헐적 502의 해부

Node.js 운영에서 가장 자주 반복되는 장애입니다. 구조는 단순합니다. ALB·NGINX·Envoy 같은 중간자는 백엔드와의 커넥션을 자기 idle timeout(ALB 기본 60s, NGINX upstream keepalive_timeout 기본 60s)까지 유지하고 재사용합니다. 그런데 Node 서버의 keepAliveTimeout은 기본 5s입니다. 응답 후 5초가 지나면 Node가 FIN을 보내는데, LB는 "아직 60초 안 됐으니 살아 있는 커넥션"이라 믿고 다음 요청을 그 소켓에 씁니다. 결과는 LB 쪽에서 ECONNRESET 또는 "upstream prematurely closed connection"이고, 클라이언트는 502를 받습니다.

keepAliveTimeout vs LB idle timeout 레이스
두 타임아웃과 "다음 요청까지의 간격"을 조정하고 재생하세요. 누가 먼저 끊는지, 그 결과 요청 2가 어떻게 되는지가 바뀝니다.

올바른 설정

const server = http.createServer(app);
// LB idle timeout이 60s라면: 서버는 그보다 '더 오래' 기다려야 한다. 서버가 먼저 끊는 일이 없도록.
server.keepAliveTimeout = 65_000;
server.headersTimeout  = 66_000;   // keepAliveTimeout보다 크게
server.listen(3000);

원칙은 "커넥션은 클라이언트 쪽(LB)이 먼저 닫는다"입니다. LB가 닫으면 LB는 그 소켓을 다시 쓰지 않으므로 레이스가 없습니다. 반대로 서버가 먼저 닫으면 FIN이 날아가는 동안 LB가 요청을 써 버리는 수 ms의 창이 항상 존재합니다. 그래서 값을 같게 맞추는 것으로는 부족하고 서버 쪽이 더 커야 합니다. 그래도 완전히 0이 되지는 않습니다(서버가 maxRequestsPerSocket이나 재시작으로 닫는 경우). LB 측에서 멱등 요청(GET)에 한해 재시도를 켜 두는 것이 두 번째 방어선입니다.

Node 서비스 간 직접 호출에서도 같은 문제 클라이언트 쪽 http.Agent의 유휴 소켓 타임아웃(Node 19+ 기본 5s)과 서버의 keepAliveTimeout(5s)이 같으면 레이스가 생깁니다. 서버 간 통신에서는 서버 keepAliveTimeout을 클라이언트 Agent timeout보다 크게 두거나, 클라이언트가 ECONNRESET을 받은 멱등 요청을 재시도하게 합니다. undici는 서버가 보내는 Keep-Alive: timeout=N 헤더를 읽어 자기 유휴 시간을 그보다 짧게 맞춥니다(6절). Node http 서버는 이 헤더를 응답에 자동으로 넣습니다.

시뮬레이터에서 확인할 것: keep-alive를 끄면 모든 요청이 핸드셰이크를 치르고, 핸드셰이크가 요청 시간보다 길면 총 소요가 두 배 이상이 됩니다. maxSockets를 줄이면 핸드셰이크는 줄지만 큐 대기가 늘고, 늘리면 그 반대입니다. 최적점은 "요청 시간 ÷ 도착 간격" 근처, 즉 Little의 법칙으로 추정한 동시 요청 수입니다.

6. undici와 fetch

Node 18부터 전역 fetch는 undici로 구현되어 있습니다. undici는 http.Agent와 별개의 커넥션 풀을 가지며, HTTP/1.1 파이프라이닝과 더 엄격한 스펙 준수, 훨씬 빠른 처리량이 특징입니다. 핵심 추상은 Dispatcher입니다.

클래스역할주요 옵션 (undici 6 기준)
Clientorigin 하나에 대한 소켓 하나. 파이프라이닝 지원pipelining (기본 1 = 파이프라이닝 없음), keepAliveTimeout 4s, keepAliveMaxTimeout 10분, headersTimeout/bodyTimeout 300s
Poolorigin 하나에 Client 여러 개connections (기본 null = 무제한)
Agentorigin별 Pool을 자동 생성. fetch의 기본 디스패처Pool 옵션 전부 + connect(TLS, lookup 등)
BalancedPool여러 upstream origin에 라운드로빈-
RetryAgent, EnvHttpProxyAgent 등재시도, 프록시 등 데코레이터-
import { Agent, setGlobalDispatcher, fetch } from 'undici';     // Node 내장 fetch도 같은 전역 디스패처를 쓴다

setGlobalDispatcher(new Agent({
  connections: 64,                 // origin당 소켓 상한 (http.Agent의 maxSockets에 해당)
  pipelining: 1,
  keepAliveTimeout: 4_000,         // 서버의 Keep-Alive: timeout=N 헤더가 있으면 그보다 짧게 자동 조정
  connect: { timeout: 3_000 },     // TCP+TLS 연결 타임아웃
  headersTimeout: 10_000,
  bodyTimeout: 30_000,
}));

const res = await fetch('https://api.example.com/x', { signal: AbortSignal.timeout(5_000) });
fetch의 바디는 반드시 소비하라 응답 바디를 읽지 않고(res.json()/res.text()/res.body.cancel()) 버리면 소켓이 재사용 가능 상태로 돌아가지 못합니다. undici는 일정 크기 이하면 남은 바디를 자동으로 비우지만, 큰 응답에서는 소켓이 새거나 닫힙니다. 상태 코드만 확인하는 경우에도 await res.body?.cancel()을 호출하세요.

파이프라이닝(pipelining > 1)은 응답을 기다리지 않고 같은 소켓에 다음 요청을 쓰는 HTTP/1.1 기능입니다. 핸드셰이크 없이 동시성을 얻지만 head-of-line blocking(앞 응답이 늦으면 뒤도 늦음)이 있고, 중간 프록시가 지원하지 않는 경우가 많아 내부 서비스 간 통신에서 실측 후 쓰는 옵션입니다.

7. HTTP/2

HTTP/1.1의 "소켓 하나 = 동시 요청 하나" 제약을 깨는 것이 HTTP/2의 멀티플렉싱입니다. 한 TCP 커넥션 위에 여러 스트림을 프레임 단위로 섞어 보냅니다. 핸드셰이크 1번으로 수백 요청을 동시에 처리하고, 헤더는 HPACK으로 압축(반복되는 쿠키·UA가 수 바이트로)됩니다.

HTTP/1.1 (소켓 6개) vs HTTP/2 (소켓 1개, 멀티플렉싱)
N개의 리소스를 가져올 때의 타임라인입니다. HTTP/1.1은 소켓 수만큼만 동시에, HTTP/2는 한 소켓에서 전부 동시에 진행되지만 대역폭을 나눠 씁니다.

모델에서 보이듯 HTTP/2의 이득은 RTT가 클수록, 리소스가 많고 작을수록 큽니다. 반대로 리소스가 크고 수가 적으면 대역폭을 나눠 쓰는 HTTP/2가 더 느릴 수도 있습니다. 또 하나의 TCP 위에 모든 스트림이 있으므로 패킷 손실 시 TCP 레벨 head-of-line blocking이 모든 스트림을 멈춥니다(HTTP/3·QUIC이 푸는 문제).

Node.js에서

const http2 = require('node:http2');
// Compat API: 기존 (req, res) 핸들러 재사용. Express 등은 이 API로 http2를 탄다.
const server = http2.createSecureServer({ key, cert, allowHTTP1: true }, (req, res) => {
  res.end(`via ${req.httpVersion}`);     // '2.0' 또는 '1.1' (ALPN 협상 결과)
});
server.listen(8443);

// Core API: 스트림을 직접 다룬다. 서버 푸시, 우선순위, 세션 설정 접근 가능
server.on('stream', (stream, headers) => { stream.respond({ ':status': 200 }); stream.end('hi'); });
  • 브라우저는 HTTP/2를 TLS 위에서만(ALPN으로 협상) 씁니다. 평문 h2c는 내부 서비스 간이나 gRPC에서 씁니다.
  • 스트림 수 한계: Node는 기본적으로 maxConcurrentStreams를 광고하지 않아 사실상 무제한입니다. 운영에서는 세션당 100~250으로 명시해 한 클라이언트가 자원을 독점하지 못하게 하세요. 세션당 메모리(maxSessionMemory, 기본 10MiB)도 있습니다.
  • LB 뒤에서는 보통 LB가 HTTP/2를 종단하고 백엔드와는 HTTP/1.1로 통신합니다. 백엔드에서 http2를 켜도 이득이 없는 이유입니다. gRPC처럼 end-to-end h2가 필요하면 LB 설정(ALB의 "gRPC" 타깃 그룹 등)을 확인하세요.
  • http2 서버는 http.Server의 타임아웃 7종을 그대로 갖지 않습니다. server.timeout(세션 비활성, 기본 0), session.setTimeout, 스트림별 setTimeout으로 따로 설계해야 합니다.

8. TLS 핸드셰이크 비용과 세션 재개

TLS 1.3 핸드셰이크는 1 RTT, TLS 1.2는 2 RTT입니다. RTT 외에 CPU 비용이 있습니다. 서버 인증서의 RSA-2048 서명 1회는 대략 1ms 안팎, ECDSA P-256은 그 1/10 수준이며, 키 교환(ECDHE)도 매번 듭니다. 초당 수천 개의 새 TLS 커넥션은 CPU 코어를 통째로 먹습니다. 이것이 TLS를 LB에서 종단하는 가장 큰 이유입니다.

Node.js 안에서 TLS를 직접 종단해야 한다면(mTLS 등) 세션 재개가 핵심입니다. TLS 1.3의 PSK 기반 재개(세션 티켓)는 전체 키 교환을 생략합니다. 서버 쪽은 Node가 기본으로 티켓을 발급하며, 다중 프로세스·다중 인스턴스에서는 티켓 키를 공유해야 재개가 됩니다(tls.createServer({ ticketKeys }), server.setTicketKeys(); cluster에서는 primary가 자동 공유). 클라이언트 쪽 https.Agent는 maxCachedSessions(기본 100)만큼 세션을 캐시해 재개합니다.

// 서버: 여러 인스턴스가 같은 키로 티켓을 발급하도록 (48바이트, 주기적으로 회전)
const server = https.createServer({ key, cert, ticketKeys: loadSharedTicketKeys(), minVersion: 'TLSv1.2' }, app);
server.on('newSession', (id, data, cb) => cb());     // TLS1.2 세션 ID 캐시를 직접 구현할 때

// 관측: 재개 비율이 낮으면 티켓 키 불일치 의심
server.on('secureConnection', (sock) => metrics.inc('tls_handshake', { resumed: sock.isSessionReused() }));

또한 https.Agent의 keep-alive는 TLS에서 더욱 중요합니다. 핸드셰이크를 아끼는 효과가 평문보다 2~3배 크기 때문입니다. 외부 API 호출에서 Node 18 이하의 기본 Agent(keepAlive false)를 그대로 쓰고 있다면 지금 바로 바꿀 가치가 있는 항목입니다.

9. DNS: 캐시 없는 lookup의 함정

http.request('https://api.example.com')는 매 커넥션마다 dns.lookup()을 호출하고, 이것은 libuv 스레드풀에서 getaddrinfo(3)를 실행합니다(3장). 두 가지 문제가 있습니다.

  1. Node.js는 DNS 응답을 캐시하지 않습니다. OS 리졸버(systemd-resolved, nscd)가 캐시할 수도 있지만 컨테이너 기본 이미지에는 대개 없습니다. 커넥션마다 UDP 왕복이 추가되고, DNS 서버가 느려지면 모든 외부 호출이 느려집니다.
  2. 스레드풀 점유. 기본 4개 스레드가 getaddrinfo로 막히면 fs·crypto·zlib까지 함께 기다립니다. DNS 서버가 응답하지 않을 때(타임아웃 5s × 재시도) 스레드풀 전체가 몇 초씩 멈추는 증상이 "파일 읽기가 갑자기 느려졌다"로 보고됩니다.
// 대안 1: 캐시하는 lookup을 Agent에 주입 (cacheable-lookup 등, 또는 직접 구현)
const CacheableLookup = require('cacheable-lookup');
const cacheable = new CacheableLookup({ maxTtl: 60 });
const agent = new https.Agent({ keepAlive: true, lookup: cacheable.lookup });
// undici: new Agent({ connect: { lookup: cacheable.lookup } })

// 대안 2: dns.resolve4()는 c-ares로 비동기 처리되어 스레드풀을 쓰지 않는다.
// 단 /etc/hosts와 nsswitch를 무시하므로 컨테이너 내부 서비스 이름 해석에서 차이가 날 수 있다.

Node 20부터 기본인 autoSelectFamily(Happy Eyeballs: IPv6/IPv4 주소를 번갈아 시도, 기본 250ms 간격)는 듀얼 스택 환경에서 연결 지연을 줄이지만, IPv6가 라우팅되지 않는 환경에서 첫 시도 250ms가 그대로 지연으로 보이기도 합니다. --network-family-autoselection-attempt-timeout이나 Agent의 family: 4로 조정합니다.

10. 소켓 옵션, 에러 코드, 한계값

소켓 옵션

  • TCP_NODELAY(socket.setNoDelay): Nagle 알고리즘 비활성. 작은 쓰기를 모으지 않고 즉시 보냄. http.createServer는 기본 noDelay: true이고, net 소켓은 기본 false입니다. 지연에 민감한 RPC에서 켭니다.
  • SO_KEEPALIVE(socket.setKeepAlive(true, initialDelay)): HTTP keep-alive와 다른 TCP 레벨 프로브. 상대가 조용히 사라졌을 때(NAT 테이블 만료, 전원 차단) 죽은 커넥션을 감지합니다. 장시간 유휴 커넥션(DB, 메시지 큐)에 필수. 프로브 간격은 OS tcp_keepalive_intvl에 의존.
  • backlog: server.listen(port, host, backlog) 기본 511. 커널의 accept 큐 길이이며 net.core.somaxconn(Linux 5.4+ 기본 4096)으로 상한이 잘립니다. 큐가 차면 SYN이 버려지고 클라이언트는 연결 지연 또는 ECONNREFUSED를 봅니다. 루프가 블로킹돼 accept를 못 하는 동안 차오릅니다.

11. 현업 장애 사례

사례 1: 0.1%의 502, 야간에만 증가

ALB(idle 60s) 뒤 Node 18(keepAliveTimeout 5s). 트래픽이 많을 땐 소켓이 5초 안에 재사용되어 문제가 없었고, 야간에 요청 간격이 5초를 넘기 시작하자 서버가 먼저 끊은 소켓에 ALB가 요청을 써 502 발생. ALB 액세스 로그의 target_status_code = "-"와 Node 쪽 'clientError' ECONNRESET 로그가 시각이 일치. keepAliveTimeout=65s, headersTimeout=66s로 즉시 소멸. 교훈: "트래픽이 적을 때 늘어나는 에러"는 타임아웃 레이스.

사례 2: 외부 API 지연이 전체 서비스를 멈춤 (소켓 고갈)

결제 API 호출에 keep-alive 없는 기본 Agent(Node 16) + 타임아웃 없음. 결제사 장애로 응답이 30초씩 걸리자 미완 요청이 쌓여 소켓 수천 개 → EMFILE → 로그 파일조차 못 열어 프로세스 크래시. 해결: Agent에 maxSockets: 100, 요청에 AbortSignal.timeout(3000), Agent 큐 길이 메트릭·알람, 13장의 서킷 브레이커. 교훈: 외부 호출에는 동시성 상한과 데드라인이 모두 있어야.

사례 3: DNS 장애가 파일 업로드 실패로 보고됨

사내 DNS가 간헐적으로 5초 지연. 외부 API 호출의 getaddrinfo가 스레드풀 4개를 모두 점유, 같은 풀을 쓰는 fs.writeFile(업로드 저장)이 5초씩 밀려 클라이언트 타임아웃. 증상과 원인이 완전히 다른 서브시스템이라 진단에 이틀 소요. 캐시형 lookup 주입 + UV_THREADPOOL_SIZE=16으로 해결. 교훈: 스레드풀은 공용 자원이며 DNS도 그 사용자다.

핵심 요약

  • 커넥션 비용 = 핸드셰이크(RTT·CPU) + 유휴 유지(메모리) + 종료(TIME_WAIT). keep-alive는 첫 비용을 아끼기 위한 투자다.
  • 서버 타임아웃 7종의 구간: headersTimeout(60s, 헤더) → requestTimeout(300s, 바디) → keepAliveTimeout(5s, 유휴). server.timeout은 비활성(기본 0). 검사 주기는 30s.
  • 서버 keepAliveTimeout > LB idle timeout > …, headersTimeout > keepAliveTimeout. 커넥션은 클라이언트 쪽이 먼저 닫아야 레이스가 없다.
  • http.Agent는 Node 19부터 keepAlive true, 유휴 5s. maxSockets는 Infinity라 상한을 직접 정해야 하며, Agent 큐 대기는 어떤 타임아웃에도 안 잡힌다.
  • fetch = undici. Dispatcher(Agent/Pool/Client)로 풀을 제어하고 바디는 반드시 소비한다.
  • HTTP/2는 RTT가 크고 작은 리소스가 많을 때 유리. LB가 종단하면 백엔드 h2는 무의미. 스트림 상한을 명시.
  • TLS는 세션 재개(티켓 키 공유)와 keep-alive로 비용을 줄인다. DNS는 캐시가 없고 스레드풀을 쓰므로 캐시형 lookup을 주입한다.

확인 문제

NGINX(upstream keepalive_timeout 60s) 뒤의 Node 서버에서 간헐적 502가 난다. 가장 올바른 조치는?
서버가 먼저 끊지 않도록 서버 유휴 타임아웃을 LB보다 크게 둡니다. 같게 맞추면 FIN 전송 중의 수 ms 레이스가 남습니다. keep-alive를 끄면 502는 사라지지만 모든 요청이 핸드셰이크를 치릅니다. requestTimeout은 바디 수신 구간이라 무관합니다.
http.Agent에 maxSockets: 10을 설정했고 동시에 요청 100개를 보냈다. 요청 타임아웃을 2초로 걸었는데 일부 요청은 10초 뒤에야 실패했다. 왜인가?
요청 타임아웃(socket timeout)은 소켓이 배정된 뒤부터 잽니다. 큐 대기는 어떤 타이머에도 잡히지 않으므로 전체 데드라인은 AbortSignal.timeout처럼 요청 생성 시점부터 재는 수단으로 따로 걸어야 합니다.
다음 중 Node.js HTTP 서버가 기본적으로 제한하지 않는 것은?
헤더 크기(16KiB), 헤더 시간(60s), 바디 시간(300s)은 기본값이 있지만 바디 크기는 코어가 제한하지 않습니다. 프레임워크나 직접 구현으로 반드시 제한해야 합니다(16장 DoS).
ECONNRESET과 EPIPE의 차이로 옳은 것은?
ECONNRESET은 상대 측에서 비정상 종료(RST)가 왔다는 뜻이고(keep-alive 레이스, 크래시 등), EPIPE는 로컬에서 닫힌 파이프/소켓에 write한 것입니다(클라이언트가 떠난 뒤 응답 스트리밍 등).
HTTP/2가 HTTP/1.1보다 뚜렷이 유리한 조건은?
멀티플렉싱과 HPACK의 이득은 요청 수가 많고 RTT가 클 때 극대화됩니다. 큰 리소스 소수에서는 대역폭 분할로 오히려 불리할 수 있고, 패킷 손실에서는 단일 TCP의 HOL 블로킹이 약점입니다. LB가 종단하면 백엔드 h2는 효과가 없습니다.
