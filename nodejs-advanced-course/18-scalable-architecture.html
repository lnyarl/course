확장 가능한 서비스 아키텍처

Node.js 프로세스 하나는 한 코어의 이벤트 루프입니다. 서비스가 커지면 프로세스를 늘리고, 상태를 밖으로 빼고, 느린 것을 캐시하고, 비싼 것을 큐로 미루고, 넘치는 것을 거절해야 합니다. 이 장은 그 각각이 "어떻게 터지는지"를 먼저 보고, 실제 숫자로 설계하는 법을 다룹니다.

학습 목표

  • 무상태 프로세스 설계의 조건과 세션·파일·타이머 같은 "숨은 상태"를 외부화하는 방법을 설명할 수 있다.
  • 캐시 스탬피드를 재현하고 single-flight·확률적 조기 만료·TTL 지터로 막을 수 있다.
  • 토큰 버킷·고정 창·슬라이딩 창 레이트 리미터의 차이를 알고 분산 환경에서 원자적으로 구현할 수 있다.
  • at-least-once 전달과 멱등성 키, 아웃박스 패턴으로 "DB 커밋과 메시지 발행"의 원자성 문제를 풀 수 있다.
  • Little의 법칙으로 커넥션 풀·동시성 상한을 산정하고, 과부하 시 로드 셰딩으로 자신을 지킬 수 있다.

1. 확장의 세 축과 무상태 프로세스

확장은 세 방향으로 합니다. 수직(더 큰 머신: Node는 코어 하나만 쓰므로 한계가 빨리 옴), 수평(프로세스/인스턴스 복제: 9장의 cluster, 14장의 k8s 레플리카), 기능 분할(도메인별 서비스 분리). 수평 확장이 가능하려면 프로세스가 무상태여야 합니다. 어떤 요청이 어느 인스턴스로 가도 같은 결과가 나와야 로드밸런서가 자유롭게 분배하고, 인스턴스를 죽이고 띄울 수 있습니다.

배치 작업의 함정 인스턴스 안의 setInterval로 돌리던 "매시 정산"은 레플리카가 3개가 되는 순간 3번 실행됩니다. 큐에 스케줄 잡을 넣어 워커 하나가 가져가게 하거나(BullMQ repeatable job), Redis SET NX PX 기반 분산 락으로 리더만 실행하게 하세요. 락은 반드시 TTL이 있어야 하고(락 보유자가 죽을 수 있다), 작업 시간이 TTL을 넘길 수 있으면 작업 자체가 멱등해야 합니다.

2. 캐시 계층과 스탬피드

2.1 어디에 캐시할 것인가

계층지연장점문제
인프로세스 (Map, LRU)~100ns네트워크 없음. 직렬화 없음인스턴스마다 따로. 무효화가 어렵다. 힙 메모리를 먹어 GC 압력(5장)
공유 캐시 (Redis/Memcached)0.2~1ms모든 인스턴스가 같은 값. 중앙 무효화직렬화 비용, 네트워크 왕복, 단일 장애점(클러스터로 완화)
CDN / HTTP 캐시엣지서버에 도달조차 안 함개인화 불가. Cache-Control·Vary 설계 필요

실전은 보통 L1 인프로세스(짧은 TTL, 작은 크기) + L2 Redis 조합입니다. L1은 같은 키를 1초에 수백 번 조회하는 핫키의 Redis 왕복을 없애고, L2는 인스턴스 간 일관성을 줍니다. L1의 TTL이 L2 무효화 지연의 상한이 됩니다.

2.2 스탬피드(thundering herd)

핫키의 TTL이 만료되는 순간, 그 키를 조회하는 모든 요청이 동시에 캐시 미스를 보고 전부 DB로 갑니다. 초당 1,000 요청, 재계산 200ms라면 만료 순간 200개의 동일 쿼리가 DB를 때립니다. DB가 느려지면 재계산이 더 오래 걸리고, 더 많은 요청이 미스를 봅니다. 양의 피드백입니다.

// 같은 키의 진행 중인 재계산 Promise를 공유한다. 프로세스 내에서 완벽, 인스턴스 간에는 인스턴스 수만큼만 DB 히트.
const inflight = new Map();
async function getOrCompute(key, compute, ttlMs) {
  const hit = await cache.get(key);
  if (hit !== undefined) return hit;
  if (inflight.has(key)) return inflight.get(key);          // 두 번째 이후 요청은 기다린다
  const p = (async () => {
    try { const v = await compute(); await cache.set(key, v, ttlMs); return v; }
    finally { inflight.delete(key); }                        // 실패해도 반드시 제거 → 안 하면 영원히 실패값 공유
  })();
  inflight.set(key, p);
  return p;
}
// Vattani et al. "Optimal Probabilistic Cache Stampede Prevention" (2015)
// 만료 전에 각 요청이 확률적으로 미리 재계산한다. 재계산이 오래 걸릴수록(delta), 만료가 가까울수록 확률이 높아진다.
// 캐시에 값과 함께 { expiry, delta(재계산 소요 ms) }를 저장
async function getXFetch(key, compute, ttlMs, beta = 1) {
  const e = await cache.get(key);                           // { value, expiry, delta }
  const now = Date.now();
  if (e && now - e.delta * beta * Math.log(Math.random()) < e.expiry) return e.value;
  //            ↑ log(rand)는 음수 → now + (양수) < expiry 이면 아직 사용. 만료에 가까워질수록 재계산 확률↑
  const t0 = Date.now(); const value = await compute(); const delta = Date.now() - t0;
  await cache.set(key, { value, expiry: Date.now() + ttlMs, delta });
  return value;
}
// 수천 개 키가 같은 순간에 만료되는 "동기화된 만료"를 막는다. 배포 직후 워밍업한 캐시가 전형적.
const ttl = baseTtl * (0.9 + Math.random() * 0.2);   // ±10% 지터
await cache.set(key, value, ttl);
// 인스턴스 간 single-flight. 락을 잡은 하나만 재계산, 나머지는 짧게 대기 후 재조회(또는 stale 값 반환).
const got = await redis.set(`lock:${key}`, id, 'NX', 'PX', 5000);
if (got) { try { v = await compute(); await cache.set(key, v, ttl); } finally { await releaseIfOwner(key, id); } }
else { await sleep(50); return cache.get(key) ?? staleValue; }   // stale-while-revalidate 와 결합하면 대기도 없앨 수 있다
캐시 스탬피드 시뮬레이터
핫키 하나에 초당 λ개의 요청이 오고, TTL마다 만료되며, 재계산에 R ms가 걸립니다. 60초 동안 DB 히트 수와 최대 동시 DB 쿼리 수를 세 전략으로 비교합니다. (시드 고정)

2.3 캐시 키와 무효화

  • 키에 버전을 넣는다: user:v3:{id}. 직렬화 형식이 바뀌면 버전을 올려 옛 값을 자연 소멸시킨다. 배포와 캐시 포맷 불일치로 인한 파싱 에러를 막는 가장 싼 방법.
  • 무효화는 쓰기 경로에서: 데이터 변경 트랜잭션 커밋 후 삭제(커밋 전에 지우면 다른 요청이 옛 값을 다시 채운다). 삭제 실패 대비로 TTL은 항상 둔다.
  • "값 갱신"보다 "삭제": 두 쓰기가 경합하면 옛 값이 나중에 캐시에 남을 수 있다. 삭제는 경합해도 다음 읽기가 최신을 가져온다.
  • 네거티브 캐시: "없음"도 짧게 캐시한다. 존재하지 않는 ID를 반복 조회하는 공격/버그가 DB를 때리는 것을 막는다.

3. 레이트 리미팅

레이트 리미터는 두 질문에 답합니다. "누구를 기준으로"(IP, API 키, 사용자, 테넌트) 와 "어떤 알고리즘으로". 알고리즘 선택은 버스트를 얼마나 허용할 것인가의 문제입니다.

알고리즘메모리/키버스트문제
고정 창 (분당 N)카운터 1개창 경계에서 최대 2N59초에 N, 61초에 N → 2초에 2N 통과
슬라이딩 창 로그타임스탬프 N개정확히 N/창키당 메모리 O(N). 높은 한도에 부적합
슬라이딩 창 카운터카운터 2개근사 (이전 창 가중 평균)근사이지만 실용적으로 충분. Cloudflare 방식
토큰 버킷토큰 수 + 마지막 시각버킷 크기만큼 허용, 이후 보충률로 제한"평균 r, 버스트 b"를 명시적으로 설계 가능. 가장 범용
레이트 리미터 알고리즘 비교
같은 트래픽(60초)에 네 알고리즘을 적용합니다. 한도는 "10초당 10회". 초록은 허용, 빨강은 429. 창 경계 버스트 패턴에서 고정 창이 20개를 통과시키는 것을 확인하세요.

분산 환경에서의 원자성

인스턴스가 여럿이면 카운터는 Redis에 있어야 하고, "읽고 → 비교하고 → 쓰기"는 반드시 하나의 원자 연산이어야 합니다. GET 후 INCR 사이에 다른 인스턴스가 끼어들면 한도가 뚫립니다. Lua 스크립트(EVAL)나 Redis 함수가 표준 해법입니다.

-- 토큰 버킷 (Redis Lua). KEYS[1]=키, ARGV = rate(토큰/초), burst, now(ms), cost
local tokens = tonumber(redis.call('HGET', KEYS[1], 't') or ARGV[2])
local ts     = tonumber(redis.call('HGET', KEYS[1], 'ts') or ARGV[3])
local elapsed = math.max(0, ARGV[3] - ts) / 1000
tokens = math.min(tonumber(ARGV[2]), tokens + elapsed * tonumber(ARGV[1]))   -- 보충
local allowed = 0
if tokens >= tonumber(ARGV[4]) then tokens = tokens - tonumber(ARGV[4]); allowed = 1 end
redis.call('HSET', KEYS[1], 't', tokens, 'ts', ARGV[3])
redis.call('PEXPIRE', KEYS[1], math.ceil(tonumber(ARGV[2]) / tonumber(ARGV[1]) * 1000) + 1000)  -- 가득 찰 때까지의 시간 뒤 자동 삭제
return { allowed, tokens }
// 응답: 429 + 표준 헤더. 클라이언트가 백오프할 수 있게 "언제 다시"를 알려 준다.
res.writeHead(429, {
  'Retry-After': Math.ceil(msUntilToken / 1000),          // 초 단위 (RFC 9110)
  'RateLimit-Limit': limit, 'RateLimit-Remaining': 0, 'RateLimit-Reset': secondsToReset,  // IETF draft 헤더
});
리미터의 위치 가장 바깥(API 게이트웨이, 인그레스)에서 거친 한도를, 애플리케이션에서 사용자·테넌트 단위의 세밀한 한도를 겁니다. 애플리케이션 리미터는 인증 직후, 비즈니스 로직 전에 두어 비싼 작업을 보호합니다. 그리고 Redis가 죽었을 때의 정책(fail-open: 통과 / fail-closed: 거부)을 반드시 명시적으로 정하세요. 보통 읽기 API는 fail-open, 비용이 큰 쓰기는 fail-closed.

4. 큐, 멱등성, 아웃박스

4.1 왜 큐인가

요청 처리 중 이메일 발송, 썸네일 생성, 외부 API 호출처럼 느리고 실패할 수 있는 일을 동기로 하면 응답 시간과 실패율이 그 외부 시스템에 묶입니다. 큐에 넣고 202를 돌려주면 (1) 응답이 빨라지고 (2) 외부 장애가 격리되고 (3) 재시도·속도 조절을 워커가 담당합니다. Node 생태계에서는 Redis 기반 BullMQ, 또는 SQS/Pub/Sub/RabbitMQ 클라이언트가 흔합니다.

4.2 at-least-once와 멱등성

현실의 큐는 거의 모두 at-least-once입니다. 워커가 처리 완료 직전에 죽으면 메시지는 다시 전달됩니다. 그러므로 모든 소비자는 같은 메시지를 두 번 받아도 안전해야 합니다. 방법은 멱등성 키: 메시지에 고유 ID를 붙이고, 처리 전에 "이 ID를 처리했는가"를 원자적으로 기록합니다.

// 처리 기록 테이블의 유니크 제약을 멱등성 가드로 사용 (같은 트랜잭션 안에서)
await db.transaction(async (tx) => {
  const inserted = await tx.query(
    'INSERT INTO processed_messages (id) VALUES ($1) ON CONFLICT DO NOTHING RETURNING id', [msg.id]);
  if (inserted.rowCount === 0) return;             // 이미 처리됨 → 조용히 ACK
  await applyBusinessEffect(tx, msg);              // 효과와 기록이 같은 트랜잭션 → 둘 다 되거나 둘 다 안 됨
});
await queue.ack(msg);

외부 효과(결제 API, 이메일)는 트랜잭션으로 되돌릴 수 없으므로, 외부 API 자체의 멱등성 키(Stripe의 Idempotency-Key 헤더 등)를 메시지 ID에서 파생해 넘깁니다.

4.3 아웃박스 패턴

"주문을 DB에 저장하고 order.created 이벤트를 발행한다"는 두 시스템에 쓰는 일입니다. DB 커밋 후 발행이 실패하면 이벤트가 사라지고, 발행 후 커밋이 실패하면 유령 이벤트가 남습니다. 아웃박스는 이벤트를 같은 DB 트랜잭션의 outbox 테이블에 쓰고, 별도 릴레이가 그것을 읽어 큐로 보냅니다. 릴레이는 at-least-once이므로 소비자의 멱등성(4.2)이 전제입니다.

아웃박스 패턴 단계별 흐름
정상 흐름과, 릴레이가 발행 직후 죽는 실패 흐름을 봅니다. 어느 시점에 죽어도 이벤트가 유실되지 않고 중복만 생기는 것, 그리고 그 중복을 소비자가 흡수하는 것을 확인하세요.

4.4 DLQ와 재처리

  • 재시도는 지수 백오프 + 지터, 횟수 상한. 상한을 넘으면 DLQ(dead-letter queue)로 보내고 경보. DLQ가 조용히 쌓이면 없는 것과 같다.
  • DLQ 메시지에는 실패 사유·횟수·마지막 스택을 메타로 붙인다. 재처리 도구(수동 재투입)를 처음부터 만든다. 장애 때 만들면 늦다.
  • "독 메시지"(항상 실패하는 메시지)는 워커를 반복 점유한다. 재시도 상한이 없으면 큐 전체가 멈춘다.
  • 순서가 중요한 메시지(같은 주문의 이벤트)는 파티션 키로 같은 워커에 보낸다. 재시도는 순서를 깨므로, 순서 의존 소비자는 버전 번호로 늦게 온 옛 이벤트를 무시한다.

5. 동시성 상한, 커넥션 풀, Little의 법칙

시스템 안에 머무는 요청 수 L = λ × W (도착률 × 평균 체류 시간). 이것이 Little의 법칙이고, 거의 모든 용량 계산의 출발점입니다. 초당 200 쿼리, 쿼리당 평균 25ms면 동시에 5개의 쿼리가 진행 중이고, 커넥션은 평균 5개면 됩니다. 그런데 평균으로 풀을 잡으면 피크에 대기열이 생깁니다. 얼마나 기다리는지는 대기행렬 이론(M/M/c, Erlang C)으로 추정할 수 있습니다.

커넥션 풀 크기 계산기
쿼리 도착률과 평균 쿼리 시간으로 필요한 평균 커넥션 수(Little)를 구하고, 풀 크기별로 "커넥션을 기다릴 확률"과 평균 대기 시간(Erlang C)을 계산합니다. 인스턴스 수를 곱한 값이 DB가 받는 총 커넥션입니다.
평균 사용 커넥션 (L = λW)
-
풀 이용률 ρ
-
대기 확률 (Erlang C)
-
평균 대기 시간 (대기 시)
-
DB 총 커넥션 (풀 × 인스턴스)

DB 쪽 한계가 먼저다 PostgreSQL은 커넥션당 프로세스를 띄우므로 수백 개를 넘기면 DB 자체가 느려집니다. HikariCP 위키의 경험칙 "connections = cores × 2 + spindles"는 DB 서버 기준이며, 보통 수십 개가 최적입니다. 인스턴스 20개 × 풀 10 = 200은 이미 과합니다. 해결은 PgBouncer 같은 풀러를 DB 앞에 두거나, 인스턴스당 풀을 줄이는 것. pg의 Pool 기본 max는 10입니다.

6. 백프레셔와 로드 셰딩

용량을 넘는 트래픽이 오면 시스템은 셋 중 하나를 합니다. 모두 받아서 모두 느려지기(최악: 타임아웃으로 전부 실패), 큐에 쌓기(지연이 무한히 늘어남), 일부를 빠르게 거절하기(로드 셰딩). 세 번째만이 "받은 요청은 제대로 처리한다"를 지킵니다.

// 동시 처리 상한 세마포어 + 큐 길이 상한 + ELU 기반 셰딩
import { performance } from 'node:perf_hooks';
const MAX_INFLIGHT = 100, MAX_QUEUE = 50;
let inflight = 0; const waiting = [];
let elu = performance.eventLoopUtilization();
setInterval(() => { const cur = performance.eventLoopUtilization(); shedding = performance.eventLoopUtilization(cur, elu).utilization > 0.85; elu = cur; }, 1000).unref();
let shedding = false;

async function withCapacity(req, res, handler) {
  if (shedding && req.priority !== 'high') return reject503(res, 1);    // 루프가 포화면 저우선순위 즉시 거절
  if (inflight >= MAX_INFLIGHT) {
    if (waiting.length >= MAX_QUEUE) return reject503(res, 2);         // 큐도 가득 → 거절 (무한 대기 금지)
    await new Promise(r => waiting.push(r));
  }
  inflight++;
  try { await handler(req, res); }
  finally { inflight--; const next = waiting.shift(); if (next) next(); }
}
function reject503(res, retryAfter) { res.writeHead(503, { 'Retry-After': retryAfter }); res.end(); }
  • 거절은 싸야 한다. 인증·파싱 전에, 가능한 한 가장 앞에서. 거절 자체가 비싸면 셰딩이 의미 없다.
  • 우선순위: 헬스체크·결제·로그인은 셰딩에서 제외하거나 별도 예산. 배치성 읽기는 먼저 버린다.
  • 503 + Retry-After로 클라이언트가 백오프하게 한다. 로드밸런서가 503을 "인스턴스 불량"으로 해석해 뺄 수 있으니(14장) 헬스체크 경로는 별도.
  • 스트림 수준의 백프레셔(6장 pipeline, write()의 반환값)는 이 요청 수준 셰딩과 별개로 항상 지킨다.

7. 타임아웃 예산, 디그레이드, 설정

7.1 데드라인 전파

클라이언트가 2초를 기다린다면, 내가 DB에 1.5초, 외부 API에 1.5초를 주는 것은 의미가 없습니다(합계 3초 > 2초). 예산은 상류에서 받아 하류로 나눠 줍니다. 요청 진입 시 데드라인을 정하고(헤더 X-Request-Deadline 또는 gRPC의 deadline), 각 하류 호출에 "남은 시간 − 여유"를 AbortSignal.timeout()으로 전달합니다. 13장의 서킷 브레이커·재시도는 이 예산 안에서만 동작해야 합니다(재시도 3번 × 1초 = 예산 초과).

const deadline = Date.now() + 2000;
const remaining = () => Math.max(0, deadline - Date.now() - 50);          // 50ms 여유
const user = await db.query(sql, { signal: AbortSignal.timeout(remaining()) });
const price = await fetch(url, { signal: AbortSignal.timeout(remaining()) });   // 앞 호출이 쓴 만큼 줄어든 예산

7.2 그레이스풀 디그레이드

추천 서비스가 죽으면 "인기 상품"을 보여 주고, 재고 API가 느리면 "재고 확인 중"을 보여 줍니다. 핵심 경로(결제)와 보조 경로(추천, 리뷰 수)를 코드에서 구분하고, 보조 경로는 짧은 타임아웃 + 폴백 + 서킷 브레이커로 감쌉니다. 기능 플래그로 보조 기능을 런타임에 끌 수 있으면 장애 대응 시간이 배포 시간에서 초 단위로 줄어듭니다.

7.3 설정 관리

  • 환경 변수는 전부 문자열이다. 부팅 시 스키마로 검증·변환(zod/valibot 등)하고, 하나라도 틀리면 즉시 종료. 잘못된 설정으로 "일단 뜨는" 프로세스가 가장 위험하다.
  • 시크릿은 환경 변수보다 파일 마운트/시크릿 매니저. 환경 변수는 자식 프로세스·크래시 덤프·/proc로 샌다(16장).
  • 런타임 리로드가 필요한 값(기능 플래그, 한도)은 설정 서비스에서 폴링/푸시. 재배포 없이 바꿀 수 있는 값과 없는 값을 문서로 구분.
  • 설정의 기본값은 프로덕션 안전 쪽으로(디버그 off, 타임아웃 있음, 셰딩 on). 개발 환경에서 명시적으로 푼다.

8. 모놀리스에서 분리까지

서비스 분리는 네트워크 경계, 분산 트랜잭션, 배포 조합 폭발, 관측 복잡도를 사는 일입니다. 그 비용을 정당화하는 이유는 보통 셋뿐입니다. 독립 배포(팀이 서로를 막는다), 독립 확장(이미지 처리와 API의 자원 프로파일이 다르다), 장애 격리(한 기능의 OOM이 전체를 죽인다). 이 중 하나도 아프지 않다면 모듈러 모놀리스(도메인별 디렉터리, 모듈 간 공개 인터페이스만 import, DB 스키마 분리)가 답이고, 분리는 그 경계가 이미 깨끗해진 뒤에 합니다.

신호먼저 시도할 것그래도 안 되면
배포 때마다 다른 팀 코드가 깨짐모듈 경계 + 소유권 + 계약 테스트(17장)팀 경계로 서비스 분리
특정 기능이 CPU/메모리를 독점워커 스레드(9장) 또는 별도 큐 워커 프로세스그 기능만 서비스로
한 기능의 버그가 전체 다운프로세스 격리(cluster), 셰딩, 서킷 브레이커장애 도메인 단위로 분리
그냥 "마이크로서비스가 좋다더라"하지 않는다하지 않는다

9. 현업 장애 사례

사례 1: 배포 직후 DB CPU 100%

롤링 배포로 인스턴스 12개가 2분 안에 재시작. 모두 빈 캐시로 시작해 같은 핫키 200개를 동시에 재계산. DB가 느려지자 재계산이 길어지고 더 많은 미스가 발생. 복구는 트래픽을 절반으로 줄이고 나서야. 수정: single-flight + 인스턴스 기동 시 캐시 워밍업(배포 전 미리 채움) + TTL 지터로 동기화 만료 방지.

사례 2: 레이트 리미터가 되레 장애를 키움

Redis 기반 리미터가 fail-closed. Redis 페일오버 15초 동안 모든 요청이 429. 클라이언트 SDK는 429에 즉시 재시도(백오프 없음) → 요청 수가 10배로 폭증 → Redis 복구 후에도 한동안 포화. 수정: 읽기 API는 fail-open, Retry-After 준수하는 SDK 백오프, 리미터 장애 자체에 대한 경보.

사례 3: 중복 이메일 3만 통

큐 소비자가 이메일 발송 후 ACK 직전에 OOM으로 재시작. 브로커가 메시지 전체를 재전달(visibility timeout). 멱등성 키가 없어 같은 사용자에게 3~5통씩 발송. 수정: 메시지 ID 기반 처리 기록 테이블, 이메일 API에 멱등성 키 전달, 워커 메모리 상한과 재시작 시 in-flight 상한.

핵심 요약

  • 수평 확장의 전제는 무상태. 세션·파일·배치·캐시·WS 매핑은 프로세스 밖으로. 배치는 큐/분산 락으로 단 한 번.
  • 캐시는 L1 로컬 + L2 공유. 스탬피드는 single-flight·XFetch·TTL 지터·분산 락으로. 키에 버전, 무효화는 커밋 후 삭제.
  • 레이트 리미터: 토큰 버킷이 범용, 고정 창은 경계 버스트 2N. 분산이면 Redis Lua로 원자적으로. 장애 시 fail-open/closed를 명시.
  • 큐는 at-least-once. 소비자는 멱등성 키로 중복을 흡수. DB 쓰기와 이벤트 발행은 아웃박스로 원자화. DLQ는 경보와 재처리 도구가 있어야 존재 의미가 있다.
  • L = λW로 풀 크기 출발, Erlang C로 대기 확률 확인. DB 총 커넥션 = 풀 × 인스턴스가 DB 한계를 넘지 않게.
  • 과부하는 빠르게 거절(셰딩). 동시성 상한 + 큐 상한 + ELU. 데드라인은 상류에서 받아 하류로 나눠 준다.

확인 문제

"분당 100회" 고정 창 리미터에서 클라이언트가 실제로 2초 안에 통과시킬 수 있는 최대 요청 수는?
59초에 100회, 61초(다음 창)에 100회. 고정 창은 창 경계에서 한도의 2배를 허용합니다. 슬라이딩 창이나 토큰 버킷이 이를 막습니다.
초당 400 쿼리, 평균 쿼리 시간 50ms인 인스턴스의 풀 크기를 "평균 사용량"으로 잡으면 20이다. 이렇게 잡았을 때 생기는 문제는?
L = 400 × 0.05 = 20은 평균 동시 사용량이고, 풀이 20이면 ρ = 1.0입니다. 대기행렬 이론에서 ρ가 1에 가까우면 대기 시간은 발산합니다. 보통 ρ 0.6~0.8을 목표로 여유를 둡니다.
아웃박스 패턴에서 릴레이가 메시지를 브로커에 발행한 직후, 아웃박스 행을 "발행됨"으로 표시하기 전에 죽었다. 결과는?
아웃박스는 "유실 없음"을 보장하고 중복을 허용하는 at-least-once 설계입니다. 중복 제거는 소비자 측 멱등성 키의 몫입니다.
single-flight 구현에서 finally로 in-flight 맵에서 키를 제거하지 않으면(성공 시에만 제거) 어떤 일이 생기는가?
거부된 Promise가 맵에 남아 모든 요청이 그것을 공유합니다. 실패도 반드시 제거해야 하고, 실패 결과를 짧게 네거티브 캐시할지 별도로 결정합니다.
과부하 상황에서 가장 나쁜 대응은?
무한 큐는 지연을 무한히 늘려 결국 모든 요청이 클라이언트 타임아웃으로 실패합니다. 처리한 요청조차 쓸모없어지는 최악의 결과입니다.

실습 과제

  1. 스탬피드 재현. 200ms 걸리는 compute()를 10초 TTL 캐시로 감싼 HTTP 핸들러를 만들고, autocannon -c 100 -d 30을 돌리면서 compute() 호출 횟수를 로그로 세세요. 기대: 만료 순간마다 수십~백여 회 호출. single-flight를 적용하면 만료당 1회로 떨어지는지 확인합니다.
  2. Redis 토큰 버킷. 위 Lua 스크립트를 ioredis의 defineCommand로 등록하고, 두 Node 프로세스에서 동시에 1,000회 호출해 총 허용 수가 정확히 버킷 크기 + 경과 시간 × 보충률인지 검증하세요. 그다음 Lua 없이 GET/SET으로 구현해 같은 테스트에서 한도가 뚫리는 것을 확인합니다.
  3. 멱등 소비자. 처리 기록 테이블 + 트랜잭션으로 멱등 소비자를 만들고, 같은 메시지를 3번 전달했을 때 부수 효과가 1번만 일어나는지, 그리고 효과 적용 후 기록 전에 예외를 던지면 둘 다 롤백되는지 확인하세요.
