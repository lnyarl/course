실전 진단 워크숍

앞의 19개 장은 각각 하나의 메커니즘을 설명했습니다. 실제 장애는 메커니즘 이름표를 달고 오지 않습니다. "응답이 없다", "메모리가 는다", "가끔 502가 난다"로 옵니다. 이 장은 그 증상에서 출발해 가설을 세우고, 올바른 도구로 측정하고, 원인을 격리하는 훈련입니다. 여섯 개의 가상 장애 상황실에서 직접 진단해 보세요.

학습 목표

  • 증상 → 가설 → 측정 → 격리 → 수정 → 검증의 진단 루프를 체계적으로 돌릴 수 있다.
  • CPU·메모리·지연·에러율·커넥션 각각에 대해 "가장 먼저 볼 도구"를 즉시 고를 수 있다.
  • 여섯 가지 전형적 Node.js 프로덕션 장애를 가상 출력만 보고 원인까지 좁힐 수 있다.
  • 배포 전·장애 중·사후 체크리스트를 팀의 운영 절차로 가져갈 수 있다.

1. 진단 방법론

장애 대응에서 가장 흔한 실수는 측정 전에 고치는 것입니다. "아마 메모리겠지"로 재시작하면 증상은 사라지고 원인은 남습니다. 두 번째 실수는 가설 없이 측정하는 것입니다. 대시보드 40개를 멍하니 보는 상태입니다. 루프는 다음 여섯 단계입니다.

① 증상무엇이, 언제부터, 어디서. 변경 이력(배포·설정·트래픽) 확인
② 가설증상을 설명하는 메커니즘 2~3개. 가장 싸게 기각할 수 있는 것부터
③ 측정가설을 기각/확인할 도구 하나. 프로파일, 스냅샷, 리포트
④ 격리원인을 한 컴포넌트·한 코드 경로로 좁힘. 재현 가능하면 최고
⑤ 수정완화(롤백·재시작·셰딩)와 근본 수정을 구분. 완화 먼저
⑥ 검증같은 지표가 정상으로 돌아왔는지. 사후 분석과 재발 방지

USE와 RED

자원 관점의 USE(Utilization·Saturation·Errors: CPU, 메모리, 이벤트 루프, 커넥션 풀, 스레드풀 각각에 대해 사용률·포화·에러)와 요청 관점의 RED(Rate·Errors·Duration)를 함께 봅니다. Node.js에서 USE의 자원 목록은 이벤트 루프(ELU, 지연), V8 힙(사용량, GC 시간), libuv 스레드풀(큐 길이), 커넥션 풀(대기), 소켓(열린 수, TIME_WAIT)입니다. 이 다섯 자원의 포화 신호가 15장의 메트릭으로 항상 수집되고 있어야 아래 워크숍이 "현실"이 됩니다.

5. 운영 체크리스트

배포 전

  • 이벤트 루프 지연 p99, ELU, 힙 사용량, GC 시간, 활성 핸들 수가 메트릭으로 수집된다 (15장)
  • --max-old-space-size가 컨테이너 메모리 한계의 60~75%로 설정되어 있다 (5, 14장)
  • SIGTERM 핸들러가 서버 close → 진행 중 요청 완료 → 풀 종료 순으로 동작하고, 타임아웃 뒤 강제 종료한다 (13, 14장)
  • server.keepAliveTimeout > LB idle timeout, headersTimeout > keepAliveTimeout (12장)
  • 모든 외부 호출에 타임아웃과 AbortSignal이 있고, 재시도는 예산 안에서만 (13, 18장)
  • readiness는 의존성과 워밍업을 반영하고, liveness는 루프 지연만 본다 (14장)
  • --report-on-signal(또는 --report-on-fatalerror)과 --heapsnapshot-signal이 켜져 있다 (11, 15장)
  • lockfile 고정, provenance 검증, 권한 모델 적용 여부 결정 (16장)
  • 부하 테스트에서 셰딩이 작동하고 503이 올바르게 나간다 (18장)

장애 중

  • 최근 변경(배포·설정·의존성·트래픽 패턴)부터 확인. 롤백이 가능하면 먼저 완화
  • 재시작 전에 증거 수집: 진단 리포트, 힙 스냅샷, CPU 프로파일 중 증상에 맞는 것 하나
  • 한 인스턴스를 트래픽에서 빼서(readiness 실패) 살아있는 채로 조사
  • 가설 하나당 측정 하나. 측정 결과를 채널에 기록하며 진행
  • 완화 후에도 지표가 정상인지 10분 이상 관찰

사후

  • 타임라인(감지 → 대응 → 완화 → 복구)과 각 구간의 시간. 감지가 늦었다면 경보 보강
  • 근본 원인과 기여 요인 분리. "사람 실수"는 원인이 아니라 증상
  • 같은 종류의 장애를 미리 잡을 테스트·경보·가드레일 하나 이상 추가 (17장)
  • 런북 갱신: 이 증상에 대한 "첫 번째 도구"를 2절 표에 추가

종합 복습

핵심 요약

  • 측정 전에 고치지 말고, 가설 없이 측정하지 말 것. 증상→가설→측정→격리→수정→검증.
  • Node의 USE 자원은 이벤트 루프, V8 힙, 스레드풀, 커넥션 풀, 소켓. 이 다섯의 포화 신호를 평시에 수집한다.
  • CPU 100%는 스택(리포트), 메모리는 분해 후 스냅샷 비교, p99는 루프 지연+GC, 502는 keep-alive 타임아웃, ETIMEDOUT은 풀 고갈, 배포 직후 느림은 콜드 스타트 요소 분해.
  • 완화와 근본 수정을 구분하고, 재시작 전에 증거를 남긴다. 사후에는 가드레일 하나를 반드시 추가한다.
