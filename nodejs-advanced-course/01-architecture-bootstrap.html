런타임 내부 · Chapter 01

Node.js 아키텍처와 부트스트랩

node app.js를 치면 무슨 일이 일어나는가. JavaScript 한 줄이 실행되기 전에 C++ 레이어는 V8 Isolate를 만들고, 바이너리에 구워진 스냅샷에서 부트스트랩된 컨텍스트를 복원하고, libuv 루프를 준비합니다. 이 장은 Node.js를 구성하는 부품과 그 부품들이 조립되는 순서를 다룹니다. 이후 모든 장의 지도(map)에 해당합니다.

학습 목표

  • Node.js를 구성하는 레이어(JS 코어 → internalBinding → C++ → V8/libuv/의존 라이브러리)와 각 레이어의 책임을 그릴 수 있다.
  • 임의의 Node API 호출이 어느 레이어와 어느 실행 주체(V8, 스레드풀, epoll, c-ares, 동기)로 가는지 분류할 수 있다.
  • Isolate · Context · Environment · process의 관계와, 프로세스 시작부터 메인 모듈 실행까지의 부트스트랩 순서를 설명할 수 있다.
  • 스타트업 스냅샷과 컴파일 캐시로 기동 시간을 줄이는 방법과 그 제약을 안다.

1. 한 장의 그림: Node.js의 부품들

Node.js는 "V8 위에 올린 JavaScript 런타임"이라고 흔히 소개되지만, 실제 바이너리의 절반 이상은 V8이 아닌 코드입니다. process.versions를 찍어 보면 바이너리에 정적으로 링크된 의존 라이브러리 목록이 그대로 나옵니다.

"비동기"는 네 가지 서로 다른 메커니즘의 총칭이다
  1. 논블로킹 소켓 + epoll: TCP/UDP/파이프/TTY. 커널이 준비 상태를 알려 주고 메인 스레드가 직접 read/write. 스레드 없음.
  2. libuv 스레드풀: 파일 I/O, dns.lookup, CPU 무거운 crypto/zlib. 워커 스레드 4개(기본)가 블로킹 호출을 대신 수행.
  3. c-ares: dns.resolve*. 자체 UDP 소켓으로 DNS 프로토콜을 직접 말하고, 소켓은 epoll에 등록.
  4. V8 플랫폼 워커: GC 병렬 마킹, 백그라운드 컴파일. 애플리케이션 API는 아니지만 CPU를 쓴다(--v8-pool-size, 기본 4).

어느 메커니즘인지에 따라 포화 지점과 장애 양상이 완전히 다릅니다. 3장이 이 구분을 깊게 다룹니다.

2. JS와 C++의 경계: internalBinding과 primordials

2.1 lib/와 src/

Node.js 저장소의 lib/는 JavaScript, src/는 C++입니다. 공개 모듈(lib/fs.js)은 대부분 얇고, 실제 로직은 lib/internal/에 있으며, 거기서 internalBinding('fs')로 C++ 함수를 호출합니다. 바이너리를 빌드할 때 lib/의 모든 JS는 js2c 도구로 C++ 문자열 상수로 변환되어 실행 파일에 내장되고, 코드 캐시(V8이 컴파일한 바이트코드)도 함께 구워집니다. 그래서 require('fs')는 디스크를 읽지 않습니다.

// lib/fs.js (요지)
const binding = internalBinding('fs');
function readFile(path, options, callback) {
  callback = maybeCallback(callback || options);
  options = getOptions(options, { flag: 'r' });
  const context = new ReadFileContext(callback, options.encoding);
  const req = new FSReqCallback();          // C++ FSReqCallback 객체 (ReqWrap)
  req.context = context;
  req.oncomplete = readFileAfterOpen;
  binding.open(path, flags, 0o666, req);    // → src/node_file.cc Open() → uv_fs_open
}

internalBinding은 사용자 코드에서 접근할 수 없습니다(--expose-internals를 켜고 require('internal/test/binding')으로만 가능하며 테스트 전용). 과거의 process.binding()은 같은 테이블의 일부를 노출했지만 DEP0111로 폐기되었고, 접근 시 경고가 납니다. 이를 쓰는 레거시 네이티브 모듈(오래된 fsevents, 일부 APM 에이전트)이 Node 메이저 업그레이드에서 깨지는 전형적 이유입니다.

2.2 primordials: 코어는 왜 arr.push를 안 쓰나

lib/ 코드를 열어 보면 ArrayPrototypePush(arr, x), StringPrototypeSlice(s, 0, 3), SafeMap 같은 낯선 이름이 가득합니다. 이것이 primordials입니다. 부트스트랩 가장 첫 단계(lib/internal/per_context/primordials.js)에서 모든 내장 객체의 메서드를 동결된 복사본으로 떠 놓은 것입니다.

// 사용자 코드가 이렇게 해도
Array.prototype.push = function () { throw new Error('nope'); };
// 코어는 자기 복사본을 쓰므로 영향받지 않는다
const { ArrayPrototypePush } = primordials;
ArrayPrototypePush(list, item);   // uncurryThis(Array.prototype.push)의 원본

이유는 두 가지입니다. (1) 격리: 사용자 땅의 프로토타입 오염이 코어 동작을 바꾸지 못하게 한다(16장 보안). (2) 성능: 매번 프로토타입 체인을 조회하지 않고 직접 호출한다. 단, Promise는 예외적으로 SafePromise*와 일반 Promise를 섞어 씁니다. 사용자 thenable과 상호작용해야 하기 때문입니다.

2.3 HandleWrap · ReqWrap · AsyncWrap

C++ 레이어의 핵심 계층 구조입니다. libuv의 두 개념(핸들 = 수명이 긴 것, 요청 = 일회성 작업)을 JS 객체로 감싼 것입니다.

C++ 클래스libuv 대응JS에서 보이는 모습예
AsyncWrap-async_hooks의 asyncId, triggerAsyncId를 가진 모든 것의 베이스모든 아래 클래스
HandleWrapuv_handle_t소켓·서버·타이머·프로세스 등 "열려 있는 것". close()가 close 콜백 페이즈로 감TCPWrap, PipeWrap, TTYWrap, ProcessWrap, FSEventWrap
ReqWrapuv_req_t한 번 완료되면 끝나는 작업. oncomplete 속성에 콜백FSReqCallback, WriteWrap, ConnectWrap, GetAddrInfoReqWrap

JS로 콜백이 돌아올 때 C++는 반드시 MakeCallback 계열(내부적으로 InternalCallbackScope)을 거칩니다. 이 스코프가 종료될 때 async_hooks의 after 훅과 2장에서 본 processTicksAndRejections가 호출됩니다. 즉 "콜백 하나마다 nextTick/마이크로태스크 드레인"이라는 규칙은 이 C++ 스코프에서 구현되어 있습니다.

3. Isolate · Context · Environment · process

네 개념이 자주 혼동됩니다. 소속을 정확히 알아야 워커 스레드, vm 모듈, 스냅샷, 임베딩(Electron 등)이 이해됩니다.

  • Isolate: V8 힙 하나. GC는 Isolate 단위로 돕니다. --max-old-space-size는 Isolate 힙 상한이므로 워커마다 따로 적용됩니다(워커는 resourceLimits 옵션). 메모리 한계를 잡을 때 "프로세스 = 메인 힙 + 워커 힙 × N + 네이티브 메모리"로 계산해야 합니다(14장).
  • Context: 전역 객체와 내장 객체 세트. vm.createContext()는 같은 Isolate 안에 새 Context를 만듭니다. 힙을 공유하므로 샌드박스가 아니며(this.constructor.constructor('return process')()류 탈출), 격리가 필요하면 워커나 별도 프로세스를 써야 합니다.
  • Environment: Node.js가 Context 위에 얹는 상태 묶음. uv_loop_t가 여기 소속입니다. 즉 "이벤트 루프 하나 = Environment 하나"입니다.
  • process: Environment가 만드는 JS 객체. 부트스트랩 초기에 C++ process 템플릿에서 생성된 뒤, JS 부트스트랩이 process.nextTick, process.env(프록시 객체), process.stdout(lazy getter) 등을 덧붙입니다. process.env가 일반 객체가 아니라 setenv를 호출하는 인터셉터라는 점, process.stdout이 첫 접근 시점에 fd 1의 종류를 보고 TTY/파이프/파일 스트림 중 하나로 생성된다는 점이 자주 걸리는 세부입니다.

4. 부트스트랩: main()에서 메인 모듈까지

아래 순서는 Node 22 소스 기준입니다. C++(src/node.cc, src/node_main_instance.cc)에서 시작해 JS(lib/internal/bootstrap/*, lib/internal/main/*)로 넘어옵니다. 스냅샷 덕분에 보라색 JS 단계 상당수는 실제로는 실행되지 않고 역직렬화됩니다.

부트스트랩 타임라인
재생을 누르면 단계가 순서대로 진행됩니다. 오른쪽 라벨은 해당 단계가 C++인지, 스냅샷에서 복원되는지, JS인지, 사용자 코드인지입니다.

4.1 주요 단계 해설

InitializeOncePerProcess는 프로세스에 단 한 번 일어나는 일입니다. CLI 인자와 NODE_OPTIONS를 파싱해 per_process::cli_options에 넣고, NodePlatform(V8이 GC·컴파일 작업을 던질 워커 스레드 풀)을 만들고, OpenSSL 설정(openssl.cnf, FIPS)과 ICU 데이터를 초기화한 뒤 V8::Initialize()를 호출합니다. 여기까지가 performance.nodeTiming.v8Start입니다.

Isolate와 Environment 생성에서 Node는 바이너리에 내장된 스타트업 스냅샷(node_snapshot.cc, 빌드 시 node_mksnapshot이 생성)을 V8에 넘겨 Isolate를 만듭니다. 스냅샷에는 primordials가 준비되고 internal/bootstrap/node.js까지 실행된 상태의 힙이 들어 있습니다. 따라서 이 단계는 "JS를 실행"하는 것이 아니라 "힙을 복사"하는 것입니다. --no-node-snapshot으로 끄면 같은 JS를 실제로 실행하며, 기동이 눈에 띄게(수십 ms) 느려집니다. nodeTiming.environment가 이 시점입니다.

StartExecution은 "무엇을 실행할 것인가"에 따라 lib/internal/main/의 진입점 하나를 고릅니다.

모든 진입점은 prepareMainThreadExecution()(lib/internal/process/pre_execution.js)을 먼저 호출합니다. 스냅샷은 환경에 독립적이어야 하므로, 환경 의존적인 것은 모두 여기서 뒤늦게 붙습니다: process.argv/execArgv 패치, process.env 기반 설정(NODE_V8_COVERAGE, NODE_DEBUG), 경고·deprecation 핸들러, inspector 훅, --require/--import 프리로드 실행, CJS·ESM 로더 초기화, 권한 모델(--permission) 활성화. 끝에 markBootstrapComplete()가 nodeTiming.bootstrapComplete를 찍습니다.

그다음 runEntryPointWithESMLoader가 메인 모듈을 로드합니다. 메인 모듈의 동기 코드(그리고 그것이 require하는 모든 트리)가 끝나야 C++로 제어가 돌아가고, SpinEventLoop가 uv_run을 시작합니다(nodeTiming.loopStart). 대부분의 서비스에서 기동 시간의 지배적 부분은 이 "require 트리 동기 실행"입니다.

종료 시퀀스도 대칭이다

uv_run이 반환하면(활성 핸들 없음) EmitProcessBeforeExit → 'beforeExit' 이벤트. 여기서 새 비동기 작업을 걸면 루프가 다시 돕니다(지연 종료 패턴). 루프가 정말 비었으면 EmitProcessExit → 'exit' 이벤트(동기 코드만 가능) → Environment 정리 → process.exitCode 반환. process.exit()는 이 순서를 건너뛰고 즉시 'exit'만 발화한 뒤 C++ exit()를 부르므로, stdout 파이프에 쌓인 비동기 쓰기가 유실될 수 있습니다. 13장 그레이스풀 셧다운에서 다시 봅니다.

구간을 더 쪼개려면 node --cpu-prof --cpu-prof-interval 100 app.js로 기동 구간의 CPU 프로파일을 뜨거나(10장), NODE_DEBUG=module로 어떤 모듈이 언제 로드되는지 찍어 봅니다. 모듈 로드 시간만 간단히 보려면 --require로 Module._load를 감싸는 작은 스크립트도 유효합니다(8장).

6. 스타트업 스냅샷과 컴파일 캐시

6.1 사용자 정의 스타트업 스냅샷 (Node 18.8+, 실험적)

Node 자체가 쓰는 기법을 애플리케이션에도 적용할 수 있습니다. 초기화를 끝낸 힙을 파일로 저장했다가, 다음 실행에서 그 힙을 그대로 복원하는 것입니다.

// entry.js — 스냅샷에 담을 초기화
const { setDeserializeMainFunction, addSerializeCallback } = require('node:v8').startupSnapshot;
const config = loadAndParseBigConfig();       // 무거운 초기화: 스냅샷 빌드 때 1회만 실행
const routes = buildRouteTable();
addSerializeCallback(() => { /* 직렬화 직전: 열린 핸들 닫기 등 */ });
setDeserializeMainFunction(() => {           // 복원 후 실제 진입점
  require('./server').start(config, routes);
});

$ node --snapshot-blob snap.blob --build-snapshot entry.js   # 빌드
$ node --snapshot-blob snap.blob                              # 실행 (수십 ms → 수 ms)

제약이 큽니다. 스냅샷 시점에 열린 핸들(소켓, 타이머, 파일)이 있으면 안 되고, 네이티브 애드온은 불가하며, 코어 모듈 중 일부만 스냅샷 가능 목록에 있습니다(목록은 lib/internal/bootstrap/의 supportedModules류 상수로 관리되며 버전마다 늘어남). 사용자 모듈 로더(ESM)도 Node 22 기준 제한이 있어, 실전에서는 "순수 계산으로 만들 수 있는 큰 자료구조"를 담는 용도에 적합합니다. 이 기능은 Node 22에서도 Stability 1(실험적)입니다.

6.2 컴파일 캐시 (Node 22.1+)

스냅샷보다 훨씬 적용하기 쉬운 것이 컴파일 캐시입니다. V8이 각 모듈을 파싱·컴파일한 결과(바이트코드와 메타데이터)를 디스크에 저장해 두고 다음 실행 때 재사용합니다. 실행 의미론은 그대로이고 "파싱 시간"만 아낍니다.

// 방법 1: 코드에서 (가능한 한 가장 먼저 호출)
const { enableCompileCache } = require('node:module');
enableCompileCache();                 // 기본 디렉터리: os.tmpdir()/node-compile-cache
// 반환값 { status, message, directory } 로 활성 여부 확인

// 방법 2: 환경변수 (코드 수정 없이, 프리로드까지 포함)
$ NODE_COMPILE_CACHE=/var/cache/node-cc node app.js

// 상태 확인/강제 저장 (22.10+)
module.getCompileCacheDir();  module.flushCompileCache();

캐시 키는 파일 경로·내용 해시·Node 버전·V8 플래그를 포함하므로 소스가 바뀌면 자동으로 무효화됩니다. 의존성 수백 개를 로드하는 서비스에서 기동의 "bootstrapComplete → loopStart" 구간이 전형적으로 20~40% 줄어듭니다(코드 규모에 비례하므로 수치는 참고치). 컨테이너에서는 캐시 디렉터리를 이미지 빌드 단계에서 미리 채워 두면(빌드 시 한 번 실행) 첫 기동부터 효과를 봅니다. 주의: 캐시 디렉터리가 읽기 전용이거나 없으면 조용히 비활성화되므로 반환값의 status를 로그로 남기세요.

세 가지 기법의 자리
  • 컴파일 캐시: 거의 모든 서비스. 적용 비용 0, 부작용 없음. 먼저 켠다.
  • 번들링(esbuild 등): 파일 수천 개의 stat/open을 한 파일로. 서버리스·CLI에 효과 큼. 단 네이티브 애드온·동적 require 주의.
  • 스냅샷: 콜드 스타트가 비즈니스 지표인 경우(서버리스, CLI 도구)에만. 제약을 감수할 가치가 있는지 측정 후 결정.

7. 단일 실행 파일(SEA, Node 20+ 실험적)

Node 바이너리 복사본에 애플리케이션 번들을 주입해 하나의 실행 파일로 배포하는 기능입니다. pkg·nexe 같은 서드파티가 하던 일을 코어가 공식화한 것입니다.

// sea-config.json
{ "main": "dist/app.js",            // 반드시 CommonJS (Node 22 기준 ESM 메인 미지원)
  "output": "sea-prep.blob",
  "disableExperimentalSEAWarning": true,
  "useCodeCache": true,             // 컴파일 캐시 내장
  "useSnapshot": false,             // true면 main이 스냅샷 엔트리 규칙을 따라야 함
  "assets": { "schema.json": "./schema.json" } }

$ node --experimental-sea-config sea-config.json          # blob 생성
$ cp "$(command -v node)" myapp
$ npx postject myapp NODE_SEA_BLOB sea-prep.blob \
    --sentinel-fuse NODE_SEA_FUSE_fce680ab2cc467b6e072b8b5df1996b2
# macOS: codesign --sign - myapp  /  Windows: signtool

// 앱에서 에셋 접근
const { isSea, getAsset } = require('node:sea');
if (isSea()) JSON.parse(getAsset('schema.json', 'utf8'));

동작 원리: 바이너리의 특정 섹션(NODE_SEA_BLOB)에 blob을 넣고, "fuse"라는 센티널 바이트열을 뒤집어 "나는 SEA다"라고 표시합니다. 기동 시 C++가 fuse를 검사해 켜져 있으면 run_main_module 대신 internal/main/embedding.js로 진입해 blob의 main을 실행합니다. 결과물 크기는 node 바이너리 크기(약 100MB)가 하한이고, 네이티브 애드온은 별도 파일로 두고 process.dlopen해야 합니다. 배포 단순화(사내 CLI, 에이전트)에는 유용하지만 "번들링 + 컴파일 캐시"로 충분한 경우가 더 많습니다.

8. 훈련: 이 호출은 어디로 가나

전문가의 첫 번째 습관은 API를 보는 순간 그 실행 주체를 떠올리는 것입니다. 아래 각 호출의 도착지를 고르세요. 틀리면 이유가 표시됩니다.

실행 주체 분류 훈련
도착지: V8만(Node 레이어 없음) · 동기(메인 스레드가 syscall/연산을 직접 수행해 블로킹) · 스레드풀(libuv 워커) · epoll(논블로킹 fd, 메인 스레드) · c-ares(자체 DNS 클라이언트).

9. 현업 장애 사례

사례 1: 서버리스 콜드 스타트 1.8초의 정체

Lambda 함수의 콜드 스타트가 1.8초. nodeTiming을 찍어 보니 bootstrapComplete까지는 40ms, loopStart까지가 1.7초. 즉 런타임이 아니라 require 트리였습니다. AWS SDK v2 전체(require('aws-sdk'))와 moment-timezone 데이터 로드가 지배적. v3 모듈식 클라이언트로 교체 + esbuild 번들 + 컴파일 캐시로 300ms. 교훈: "Node가 느리다"가 아니라 "내 require가 느리다"를 먼저 의심하라.

사례 2: Node 메이저 업그레이드 후 APM 에이전트 크래시

Node 16 → 20 업그레이드 뒤 기동 즉시 TypeError: process.binding is not a function… 은 아니고, 실제로는 process.binding('http_parser')가 다른 내부 구조를 돌려줘서 에이전트가 undefined 프로퍼티를 읽다 죽은 경우. process.binding은 DEP0111로 폐기되었고 노출 목록은 버전마다 줄어듭니다. 내부 바인딩에 의존하는 모듈은 메이저 업그레이드 전에 반드시 별도 검증. 공식 대안은 diagnostics_channel(15장)과 공개 API뿐입니다.

사례 3: 워커 8개를 띄웠더니 OOM

4GB 컨테이너에서 --max-old-space-size=3072를 주고 워커 8개를 생성. 각 워커는 자기 Isolate를 가지며 힙 상한을 상속하지는 않지만, 메인과 별도로 힙을 키울 수 있어 합계가 컨테이너 한계를 넘어 OOM Kill. 워커마다 resourceLimits: { maxOldGenerationSizeMb }를 명시하고, 총합(메인 + 워커 + 네이티브 버퍼 + V8 플랫폼 스레드 스택)이 cgroup 한계의 70~80% 이내가 되도록 계산해야 합니다(9장, 14장).

핵심 요약

  • Node.js = JS 코어(lib/) + internalBinding 경계 + C++ 래퍼(src/) + V8 + libuv + c-ares/OpenSSL/zlib/llhttp/nghttp2/ada/ICU/simdutf/undici. process.versions가 그 목록이다.
  • "비동기"의 실체는 넷 중 하나: epoll(소켓), libuv 스레드풀(fs·dns.lookup·crypto·zlib), c-ares(dns.resolve), V8 플랫폼 워커(GC·컴파일). 포화 지점이 각각 다르다.
  • 코어는 primordials로 작성되어 프로토타입 오염에 면역이고, process.binding은 폐기되었다.
  • Isolate(힙·GC) ⊃ Context(전역 객체) + Environment(루프·process). 워커는 셋 다 새로 만들지만 스레드풀은 프로세스에 하나.
  • 부트스트랩: InitializeOncePerProcess → Isolate(스냅샷 복원) → Environment → internal/main/* 진입점 → prepareMainThreadExecution(환경 의존 패치, 프리로드) → 메인 모듈 동기 실행 → uv_run.
  • performance.nodeTiming으로 기동을 분해하라. 대개 지배 구간은 require 트리. 컴파일 캐시(NODE_COMPILE_CACHE) → 번들링 → 스냅샷 순으로 적용.

확인 문제

dns.lookup('example.com', cb)과 dns.resolve4('example.com', cb)의 실행 주체로 옳은 것은?
dns.lookup은 OS 리졸버(getaddrinfo)를 쓰기 때문에 블로킹 호출이고, libuv가 스레드풀 워커에서 대신 호출합니다. dns.resolve*는 c-ares가 직접 DNS 패킷을 보내며 그 소켓은 epoll에 등록됩니다. 3장에서 이 차이가 만드는 장애를 다룹니다.
vm.createContext()로 만든 컨텍스트에서 실행한 코드에 대한 설명으로 옳은 것은?
Context는 전역 객체의 단위입니다. 힙, GC, 마이크로태스크 큐를 메인과 공유하고 Environment가 없으므로 process/require도 없습니다. 신뢰할 수 없는 코드 격리에는 워커나 프로세스를 쓰세요.
기동 시 process.argv, --require 프리로드, 권한 모델 활성화가 스냅샷이 아니라 prepareMainThreadExecution에서 처리되는 이유는?
스냅샷은 빌드 시점에 한 번 만들어 모든 실행이 공유합니다. 실행마다 달라지는 값(argv, env, CLI 플래그에 따른 동작)은 복원 후에 덧붙여야 하므로 pre_execution 단계가 존재합니다.
performance.nodeTiming에서 bootstrapComplete와 loopStart 사이가 1.5초라면 가장 먼저 의심할 것은?
그 구간은 정확히 "메인 모듈이 동기적으로 실행되는 시간"입니다. 컴파일 캐시, 번들링, 지연 로딩, 최상위 동기 I/O 제거가 대응입니다.
Node.js 코어가 arr.push(x) 대신 ArrayPrototypePush(arr, x)(primordials)를 쓰는 주된 이유는?
primordials는 부트스트랩 최초 단계에서 내장 메서드의 동결된 복사본을 떠 둔 것입니다. 이후 누가 Array.prototype.push를 바꿔도 코어는 영향을 받지 않습니다.

실습 과제

  1. 기동 분해. 여러분 서비스의 진입 파일 첫 줄에 setImmediate(() => console.log(JSON.stringify(performance.nodeTiming)))를 넣고 10회 실행해 평균을 구한 뒤, 위 뷰어에 붙여 넣으세요. 그다음 NODE_COMPILE_CACHE=/tmp/cc node app.js로 두 번째 실행부터의 loopStart 변화를 비교하세요. 기대: bootstrapComplete→loopStart 구간만 줄어들고 나머지는 거의 동일.
  2. 스냅샷 끄기 실험. node --no-node-snapshot -e "setImmediate(()=>console.log(performance.nodeTiming.environment))"와 기본 실행을 비교하세요. 기대: environment 시점이 수십 ms 뒤로 밀림(머신에 따라 다름). 이것이 바이너리 내장 스냅샷이 매 실행마다 절약하는 시간입니다.
  3. 분류 검증. 8절 훈련에서 "스레드풀"로 분류된 API 중 하나(예: crypto.pbkdf2)를 100개 동시에 호출하면서 동시에 fs.readFile 한 번의 소요 시간을 재 보세요. 그다음 UV_THREADPOOL_SIZE=32로 다시 재세요. 기대: readFile 지연이 pbkdf2 작업 길이 × (100/4) 수준에서 × (100/32) 수준으로 감소. 3장에서 원리를 다룹니다.
