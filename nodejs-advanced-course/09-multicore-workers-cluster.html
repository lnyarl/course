멀티코어: Worker, Cluster, 자식 프로세스

이벤트 루프 하나는 코어 하나만 씁니다. 64코어 머신에서 Node 프로세스 하나는 1.5%의 CPU를 쓰는 셈입니다. Node.js는 이 간극을 메우는 세 가지 도구를 제공하지만 각각 메모리 모델, 통신 비용, 실패 격리가 완전히 다릅니다. 이 장은 "무엇을 언제 쓰는가"를 비용 모델로 설명합니다.

학습 목표

  • worker_threads, cluster, child_process의 메모리 모델과 통신 메커니즘 차이를 설명하고 결정 트리로 선택할 수 있다.
  • structured clone, transferList, SharedArrayBuffer의 비용 차이를 데이터 크기에 따라 추정하고 측정할 수 있다.
  • Atomics.wait/notify로 스레드 간 동기화를 구현하고 그 위험(데드락, 메인 스레드 블로킹)을 안다.
  • cluster의 연결 분배 메커니즘과 컨테이너 환경에서의 선택 기준, 무중단 재시작 절차를 설명할 수 있다.

1. 문제: 1 루프 = 1 코어

JavaScript 실행은 V8 Isolate 하나당 스레드 하나입니다. libuv 스레드풀(3장)이 fs·dns·crypto·zlib 작업을 병렬로 처리하지만, 여러분이 쓴 JS 코드는 항상 메인 스레드에서 돕니다. JSON 파싱, 템플릿 렌더링, 이미지 리사이즈 루프, 정규식, 암호화 전처리 같은 CPU 작업이 늘어나면 2장에서 본 루프 지연이 늘고, 다른 코어는 놀고 있습니다.

코어 수는 os.availableParallelism()(Node 18.14+)으로 얻습니다. os.cpus().length와 달리 CPU 친화도(affinity)를 반영합니다. 다만 컨테이너의 cgroup CPU 할당량(quota)은 libuv 버전에 따라 반영되지 않을 수 있으니(9절) 운영 환경에서 실측하세요.

먼저 물어야 할 것 "정말 CPU가 병목인가?" 10장의 프로파일로 확인하기 전에 워커를 도입하면, I/O 대기였던 문제에 스레드 비용만 추가됩니다. ELU(2장)가 0.7 이상이고 플레임 그래프에 뚜렷한 JS 핫스팟이 있을 때가 이 장의 도구를 꺼낼 때입니다.

3. worker_threads 내부

워커는 같은 프로세스 안에서 새 OS 스레드를 만들고 그 위에 V8 Isolate, Node Environment, libuv 루프를 새로 띄운 것입니다. 즉 워커 하나는 "작은 Node.js"입니다. 메인과 공유하는 것은 프로세스 메모리 공간(그래서 ArrayBuffer를 복사 없이 넘길 수 있음)과 OS 자원뿐이고, JS 객체·힙·전역·모듈 캐시는 모두 분리됩니다.

// main.js
const { Worker } = require('node:worker_threads');
const w = new Worker('./task.js', {
  workerData: { n: 1e7 },                       // 시작 시 1회 복제(structured clone)
  resourceLimits: { maxOldGenerationSizeMb: 256, maxYoungGenerationSizeMb: 32, stackSizeMb: 4 },
  env: process.env,                             // 기본: 부모 env 복사. SHARE_ENV 심볼로 공유 가능
});
w.on('message', r => console.log('result', r));
w.on('error', e => console.error('worker threw', e));   // 워커의 uncaught 예외 → 여기로. 워커는 종료됨
w.on('exit', code => { if (code !== 0) console.error('worker exit', code); }); // 1: 에러, 또는 terminate()

// task.js
const { parentPort, workerData } = require('node:worker_threads');
let s = 0; for (let i = 0; i < workerData.n; i++) s += i;
parentPort.postMessage(s);
  • 시작 비용: Node는 워커용 스냅샷을 써서 수 ms~수십 ms에 부팅합니다. 요청마다 워커를 만들면 이 비용이 지배적이므로 반드시 풀로 재사용합니다.
  • resourceLimits: 워커별 힙 상한. 초과하면 워커만 ERR_WORKER_OUT_OF_MEMORY로 죽고 메인은 삽니다. 신뢰할 수 없는 입력을 처리하는 워커에 필수.
  • stdout/stderr: 기본적으로 메인의 것을 통해 비동기로 전달됩니다(순서가 섞일 수 있음). 15장의 로거를 워커에서도 그대로 쓰되 transport는 메인에서만.
  • 종료: worker.terminate()는 실행 중인 JS를 강제로 멈춥니다(V8 TerminateExecution). 정리가 필요하면 메시지로 요청하고 워커가 스스로 process.exit()하게 하세요. 워커의 process.exit()은 스레드만 끝냅니다.
  • unref: worker.unref()하면 워커가 살아 있어도 메인 루프가 종료될 수 있습니다. 반대로 워커가 떠 있으면 프로세스가 안 끝나는 "테스트가 안 끝나요"의 흔한 원인.

4. 워커 풀 패턴과 스케줄링 시뮬레이터

실무에서는 new Worker를 직접 다루지 않고 풀을 씁니다. 핵심 설계 요소는 다음과 같고, piscina가 이 모두를 구현한 사실상 표준입니다.

  • 풀 크기: 기본 availableParallelism() - 1(메인 스레드 몫을 남김) 근처. CPU 작업이면 코어 수를 넘겨도 처리량이 늘지 않고 컨텍스트 스위치만 늡니다. 메모리는 Isolate 수에 비례.
  • 큐와 백프레셔: 워커가 모두 바쁘면 작업은 큐에 쌓입니다. 큐 길이 상한(maxQueue)을 두고 넘치면 즉시 거부해야 메인 메모리가 폭주하지 않습니다.
  • 워커 재활용: 작업 N개마다 또는 힙이 커지면 워커를 교체해 누수 영향을 제한(maxThreads, idleTimeout).
  • 취소와 타임아웃: 실행 중인 JS를 멈추는 방법은 terminate()뿐이므로, 타임아웃 = 워커 교체 비용입니다. AbortSignal을 메시지로 전달해 협조적으로 멈추는 것이 우선.
  • 전달 비용: 작업당 입력·출력이 크면 5절의 transfer/SAB를 써야 합니다. 안 그러면 메인 스레드가 복제에 묶여 워커의 이점이 사라집니다.
// piscina 사용 예
const Piscina = require('piscina');
const pool = new Piscina({ filename: new URL('./task.mjs', import.meta.url).href,
                           maxThreads: os.availableParallelism() - 1, maxQueue: 1000, idleTimeout: 30_000 });
app.post('/resize', async (req, res) => {
  const buf = await readBody(req);                       // Buffer
  const out = await pool.run({ buf }, { transferList: [buf.buffer] });   // 복사 없이 이전
  res.end(out);
});

5. 데이터 전달 비용: clone · transfer · share

postMessage(value)는 HTML의 structured clone 알고리즘으로 값을 직렬화합니다. 일반 객체·배열·Map·Set·Date·RegExp·ArrayBuffer·TypedArray·Error를 지원하고, 함수·심볼·DOM/네이티브 핸들·프로토타입 체인(클래스 인스턴스는 평범한 객체가 됨)은 안 됩니다. 비용은 객체 그래프 크기에 비례하고, 직렬화는 보내는 쪽에서, 역직렬화는 받는 쪽에서 각각 동기적으로 일어납니다. 메인에서 100MB를 보내면 메인 루프가 그 직렬화 시간만큼 멈춥니다.

데이터 크기와 형태를 바꾸면 각 방식의 예상 비용을 모델로 보여줍니다. 절대값은 모델(일반적인 서버 기준 가정)이지 실측이 아닙니다. 비율과 추세를 보고, 실제 값은 실습 과제로 측정하세요.
// transfer: 원본은 detached 된다
const ab = new ArrayBuffer(64 * 1024 * 1024);
worker.postMessage(ab, [ab]);
console.log(ab.byteLength);          // 0  ← 더 이상 접근 불가. 실수로 쓰면 TypeError

// Buffer는 풀(pool)을 공유할 수 있어 주의: Buffer.from('x') 같은 작은 버퍼는 8KB 슬랩을 공유한다.
// buf.buffer를 통째로 transfer하면 같은 슬랩을 쓰는 다른 Buffer까지 detached 된다.
// 안전하게: const copy = Uint8Array.prototype.slice.call(buf).buffer  또는 Buffer.allocUnsafeSlow 로 독립 할당.

worker.postMessage(sab);               // transferList 없이도 복사되지 않고 공유된다
const view = new Int32Array(sab);

6. Atomics와 스레드 동기화

SharedArrayBuffer를 쓰는 순간 JavaScript에 처음으로 데이터 레이스가 생깁니다. 두 스레드가 같은 Int32Array 슬롯을 view[0]++하면 결과가 틀릴 수 있습니다. Atomics는 원자적 읽기·쓰기·증감(add/sub/and/or/xor/exchange/compareExchange)과 블로킹 대기(wait)·깨우기(notify)를 제공합니다.

// 공유 상태: [0] = 작업 준비 플래그, [1] = 결과
const sab = new SharedArrayBuffer(8), st = new Int32Array(sab);

// 워커: 플래그가 1이 될 때까지 블로킹 대기(스레드 잠듦, CPU 안 씀)
Atomics.wait(st, 0, 0);                 // st[0]이 0인 동안 잠든다. 'ok' | 'not-equal' | 'timed-out'
const input = Atomics.load(st, 1);
Atomics.store(st, 1, heavy(input));
Atomics.store(st, 0, 2); Atomics.notify(st, 0);   // 완료 알림

// 메인
Atomics.store(st, 1, 42); Atomics.store(st, 0, 1);
Atomics.notify(st, 0, 1);               // 대기 중인 스레드 1개 깨움. 반환값 = 깨운 수
// 메인에서 Atomics.wait는 Node에서는 허용되지만(브라우저 메인 스레드는 금지) 루프 전체를 멈춘다.
// 대신 Atomics.waitAsync(st, 0, 1).value.then(...)  (Node 16+, V8 8.7+)

위험 목록
  • 잃어버린 깨우기(lost wake-up): notify가 wait보다 먼저 호출되면 아무도 깨우지 못합니다. 그래서 wait(arr, idx, expected)는 "값이 아직 expected면 잠든다"는 조건 검사와 잠들기를 원자적으로 수행합니다. 항상 상태 변수를 먼저 바꾸고 notify하세요.
  • 데드락: 두 스레드가 서로를 기다리면 영원히 멈춥니다. wait에 타임아웃(ms)을 두고 로그를 남기세요.
  • 메인 스레드 wait: HTTP 서버가 있는 메인에서 Atomics.wait는 루프 전체를 멈춥니다. waitAsync 또는 메시지로 바꾸세요.
  • 메모리 모델: Atomics가 아닌 일반 읽기·쓰기는 재정렬·캐시될 수 있습니다. 플래그는 반드시 Atomics.load/store로.

7. cluster: 소켓 공유와 연결 분배

cluster는 child_process.fork()로 같은 스크립트를 여러 프로세스로 띄우고, 워커들이 같은 포트에 listen()할 수 있게 해 줍니다. 마법은 net.Server.listen이 워커 안에서 호출될 때 실제 바인딩을 하지 않고 primary에 IPC로 "이 주소로 listen 핸들을 달라"고 요청하는 데 있습니다. 그 뒤의 동작은 스케줄링 정책에 따라 둘로 갈립니다.

정책누가 accept하나분배기본
SCHED_RR (round-robin)primary가 accept하고, 연결된 소켓 핸들을 워커에 IPC로 전달primary가 순서대로 공평하게Windows 제외 모든 플랫폼
SCHED_NONEprimary가 listen 핸들을 워커들에게 복제해 주고, 각 워커가 직접 acceptOS 스케줄러에 맡김 → 특정 워커에 쏠리는 경향(Linux에서 흔히 70%+가 한두 워커로)Windows

정책은 cluster.schedulingPolicy = cluster.SCHED_NONE 또는 환경변수 NODE_CLUSTER_SCHED_POLICY=none으로 바꿉니다. RR은 공평하지만 primary가 모든 accept를 처리하는 단일 지점이 됩니다(실제로는 accept만 하므로 병목이 되는 경우는 드뭅니다).

cluster 연결 분배 애니메이션
연결 12개가 들어올 때 RR과 NONE 정책에서 워커별 분배가 어떻게 달라지는지 봅니다. NONE의 쏠림은 OS가 "가장 최근에 깨어난 프로세스"를 선호하는 경향을 모사했습니다.

7.1 워커 생명주기와 재시작

const cluster = require('node:cluster');
if (cluster.isPrimary) {
  const n = os.availableParallelism();
  for (let i = 0; i < n; i++) cluster.fork();
  cluster.on('exit', (w, code, signal) => {
    if (w.exitedAfterDisconnect) return;         // 우리가 의도적으로 내린 것
    console.error(`worker ${w.process.pid} died (${signal || code}), restarting`);
    setTimeout(() => cluster.fork(), 1000);        // 즉시 재시작하면 크래시 루프가 CPU를 태운다 → 백오프
  });
} else {
  http.createServer(handler).listen(3000);
}
  • 크래시 루프 방지: 재시작 횟수를 세고 임계치를 넘으면 전체를 내려 오케스트레이터에 맡기세요. 무한 재시작은 장애를 숨깁니다.
  • 워커 간 상태 공유 불가: 인메모리 세션·캐시·레이트리밋 카운터는 워커마다 따로 있습니다. 이것이 sticky session 문제입니다(WebSocket/Socket.IO는 같은 워커로 가야 핸드셰이크가 유지됨). 해결은 외부 저장소(Redis) 또는 L7 로드밸런서의 sticky 라우팅. cluster 자체는 sticky를 지원하지 않습니다.
  • primary는 얇게: primary에서 요청을 처리하거나 무거운 일을 하지 마세요. 죽으면 전체가 죽습니다.

8. child_process: 파이프, IPC, 함정

API셸출력용도
spawn(cmd, args)없음 (옵션 shell: true)스트림큰 출력, 장시간 실행, 기본 선택
exec(cmdString)있음 (/bin/sh -c)버퍼 (maxBuffer)짧은 셸 명령. 인젝션 위험
execFile(file, args)없음버퍼 (maxBuffer)셸 없이 짧은 출력
fork(module)없음스트림 + IPC 채널Node 자식과 메시지 통신
*Sync동일반환값CLI 스크립트, 부팅 시점만
  • maxBuffer: exec/execFile의 stdout+stderr 상한, 기본 1024 × 1024 바이트(1 MiB). 넘으면 자식을 SIGTERM으로 죽이고 에러("maxBuffer length exceeded", Sync 계열은 ENOBUFS). 출력이 클 수 있으면 spawn으로 스트리밍하세요.
  • 파이프 역압: spawn한 자식의 stdout을 읽지 않으면 OS 파이프 버퍼(Linux 기본 64KB)가 차고 자식이 write에서 블로킹됩니다. "자식이 멈춰 있다"의 흔한 원인. 안 쓸 출력은 stdio: 'ignore'.
  • 셸 인젝션: exec(`convert ${userFile}`)는 ; rm -rf /를 받습니다. 사용자 입력은 항상 execFile/spawn의 args 배열로.
  • IPC 직렬화: fork의 process.send()는 기본 serialization: 'json'(JSON.stringify, 빠르지만 타입 손실). 'advanced'는 structured clone(Buffer·Map·순환 참조 지원, 조금 느림).
  • 핸들 전달: child.send(msg, socketOrServer)로 TCP 소켓/서버 핸들을 넘길 수 있습니다. cluster가 내부적으로 쓰는 메커니즘입니다.
  • 좀비와 고아: 부모가 'exit'를 처리하지 않아도 Node가 자동으로 reap합니다. 그러나 detached: true + unref()로 떼어낸 자식은 부모가 죽어도 살아남습니다(의도적인 데몬화가 아니면 피하세요). 반대로 컨테이너의 PID 1 문제는 14장.
  • 시그널 전파: child.kill()은 기본 SIGTERM. 자식이 셸(shell: true)이면 셸만 죽고 손자는 살아남습니다. 프로세스 그룹을 죽이려면 detached: true로 띄우고 process.kill(-child.pid).

9. 컨테이너 시대의 선택과 무중단 재시작

Kubernetes 같은 오케스트레이터가 있으면 cluster 대신 복제본(replica)을 늘리는 것이 표준입니다. 이유: ① 프로세스 격리가 파드 단위로 이미 제공됨, ② 리소스 요청·제한, 헬스체크, 롤링 업데이트를 플랫폼이 더 잘함, ③ cluster primary가 또 하나의 단일 실패 지점. "파드당 1 프로세스, 코어 수만큼 파드"가 기본이고, 큰 코어 수의 노드에서 파드 수를 줄이고 싶을 때만 cluster를 고려합니다. 워커 스레드는 이와 무관하게 CPU 작업용으로 함께 씁니다.

availableParallelism과 cgroup os.availableParallelism()은 libuv의 uv_available_parallelism()을 호출하며, Linux에서 sched_getaffinity(사용 가능한 CPU 집합)를 봅니다. 컨테이너에 CPU limit 2를 걸어도 affinity는 노드 전체(예: 64)이므로, libuv가 cgroup 할당량을 반영하기 전 버전에서는 64를 돌려줍니다(최근 libuv는 cgroup v2 cpu.max를 반영하도록 개선되었으나 Node 버전별 포함 여부는 릴리스 노트로 확인). 워커 풀 크기를 이 값으로 잡으면 2코어 할당량에 63개 스레드가 경쟁합니다. 운영에서는 환경변수로 풀 크기를 명시하세요.

9.1 무중단 재시작 (cluster)

  1. primary가 SIGHUP(또는 배포 신호) 수신.
  2. 새 워커 하나 fork → 'listening' 이벤트 대기 (준비됨).
  3. 옛 워커 하나에 worker.disconnect() → 워커는 새 연결 수락을 멈추고(server.close()) 진행 중 요청을 끝낸 뒤 종료. 끝나지 않으면 타임아웃 후 kill().
  4. 남은 옛 워커에 대해 2~3 반복.

keep-alive 연결(12장)은 server.close()가 기다려 주지 않으므로 Node 18.2+의 server.closeIdleConnections()/closeAllConnections()를 함께 써야 합니다. 상세 절차는 13장의 그레이스풀 셧다운과 같습니다.

10. 현업 장애 사례

사례 1: 워커를 썼는데 더 느려짐

이미지 메타데이터 추출을 워커 풀로 옮겼더니 p99가 악화. 원인: 요청마다 20MB Buffer를 postMessage(buf)로 복제(메인에서 직렬화 ~10ms) + 결과 객체 그래프 복제. 워커의 실제 작업은 8ms. 해결: transferList로 이전하고 결과는 작은 JSON만 반환. 메인 블로킹이 10ms → 0.1ms.

사례 2: 64코어 노드의 2코어 파드에서 OOM

워커 풀 크기를 availableParallelism()으로 잡은 서비스가 cgroup 할당량과 무관하게 64 워커를 띄움. Isolate당 힙 + 코드 공간으로 메모리 limit 초과 → OOMKilled 반복. 해결: WORKER_POOL_SIZE 환경변수로 명시, 기본값은 Math.min(availableParallelism(), 4).

사례 3: 자식 프로세스가 "멈춤"

spawn('ffmpeg', …) 후 'close'만 기다리고 stderr를 읽지 않음. ffmpeg의 진행 로그가 64KB 파이프 버퍼를 채우자 ffmpeg가 write에서 블로킹되어 영원히 끝나지 않음. 타임아웃 후 kill하면서 "ffmpeg가 느리다"로 오진. 해결: stdio: ['ignore', 'pipe', 'ignore'] 또는 stderr를 소비.

사례 4: cluster에서 WebSocket 연결이 간헐 실패

Socket.IO 폴링 폴백 핸드셰이크가 여러 요청으로 이뤄지는데, RR 분배로 요청이 서로 다른 워커에 가서 세션을 못 찾음. 해결: 로드밸런서 sticky 라우팅 + Redis 어댑터, 또는 cluster 대신 파드 복제본 + LB sticky.

핵심 요약

  • JS는 Isolate당 한 스레드. 멀티코어 활용 도구는 worker_threads(스레드+별도 Isolate), cluster(프로세스+포트 공유), child_process(프로세스+파이프/IPC).
  • 워커는 풀로 재사용. 크기 ≈ 코어 수 − 1, 큐 상한, 재활용, 협조적 취소. 전달 비용이 작업 비용과 비슷하면 이득 없음.
  • postMessage = structured clone(O(크기), 양쪽 동기). 큰 바이너리는 transferList(O(1), 원본 detached) 또는 SharedArrayBuffer(공유 + Atomics).
  • Atomics.wait는 조건 검사와 잠들기가 원자적. 상태 변경 → notify 순서. 메인 스레드에서는 waitAsync.
  • cluster: 워커의 listen은 primary에 핸들 요청. RR(기본)은 primary가 accept 후 전달, NONE은 워커가 직접 accept(쏠림). 상태는 워커마다 분리 → sticky 문제.
  • child_process: exec는 셸 경유(인젝션), maxBuffer 1MiB, 파이프 안 읽으면 자식 블로킹, 셸 자식 kill은 손자를 못 죽임.
  • 컨테이너에서는 cluster보다 복제본. availableParallelism은 cgroup 할당량을 반영 못 할 수 있으니 풀 크기는 명시.

확인 문제

메인 스레드에서 50MB Buffer를 워커에 postMessage(buf)로 보낸 뒤 buf.length를 출력하면?
transferList 없이 보내면 structured clone으로 복사되고 원본은 그대로입니다. detached가 되는 것은 postMessage(buf, [buf.buffer])처럼 transferList에 넣었을 때입니다.
Linux에서 cluster 기본 정책(SCHED_RR)의 동작은?
RR에서는 primary만 listen 소켓을 가지고 accept합니다. 연결된 소켓 핸들을 순서대로 워커에 넘깁니다. 3번처럼 HTTP를 파싱하지는 않습니다(L4 수준). SO_REUSEPORT 방식은 Node 22.12+/23.1+의 net reusePort 옵션으로 cluster와 무관하게 가능해졌습니다.
워커가 Atomics.wait(st, 0, 0)에서 영원히 깨어나지 않는다. 가장 흔한 원인은?
wait는 st[0]이 expected(0)와 같을 때만 잠들고, 깨어나려면 notify가 와야 합니다. 값을 바꾸지 않으면 notify로 깨어나도 다시 wait 루프에 들어가는 코드가 흔하고, notify가 없으면 값이 바뀌어도 모릅니다. 항상 "Atomics.store → Atomics.notify" 순서로.
exec('ls -R /')이 "stdout maxBuffer length exceeded" 에러를 낸다. 올바른 해결은?
큰 출력은 버퍼링이 아니라 스트리밍이 답입니다. maxBuffer를 무한으로 두면 메모리 폭주 위험, Sync는 루프 블로킹, inherit는 출력을 프로그램이 받을 수 없습니다.
k8s에서 CPU limit 2인 파드가 64코어 노드에 떴다. 워커 풀 크기를 os.availableParallelism()으로 잡으면 생길 수 있는 문제는?
이 함수는 CPU affinity 기반이며 cgroup 할당량 반영은 libuv 버전에 따릅니다. 운영에서는 풀 크기를 환경변수로 명시하세요.

실습 과제

  1. 전달 비용 실측. 1MB, 16MB, 128MB Buffer를 ① clone ② transfer ③ SharedArrayBuffer로 워커에 보내고 performance.now()로 메인 스레드가 postMessage 호출에 쓴 시간을 측정하세요. 기대: clone만 크기에 비례, 나머지는 거의 상수. 5절 비교기의 모델과 비율을 비교하세요.
  2. 풀 크기 실험. piscina로 CPU 작업(예: 10만 회 해시)을 처리하는 서버를 만들고 autocannon으로 부하를 주며 maxThreads를 1, 코어−1, 코어×2로 바꿔 처리량과 p99를 기록하세요. 기대: 코어 수 근처에서 처리량 포화, 그 이상은 p99 악화.
  3. cluster 분배 관찰. 4 워커 cluster 서버에서 각 워커가 처리한 요청 수를 세고, NODE_CLUSTER_SCHED_POLICY=none으로 다시 실행해 분포를 비교하세요(Linux). 기대: RR은 균등, NONE은 쏠림.
  4. 파이프 블로킹 재현. spawn('yes')(무한 출력)를 stdout을 읽지 않고 띄운 뒤 ps로 상태를 보세요. 자식이 파이프 write에서 멈춰 있을 것입니다. stdio: 'ignore'로 바꾸면 CPU를 계속 씁니다.
