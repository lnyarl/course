V8 메모리 구조와 GC

Node.js 프로세스의 메모리는 "V8 힙"이라는 하나의 덩어리가 아닙니다. 세대별로 나뉜 여러 스페이스, 그 밖에 있는 Buffer의 백킹 스토어, C++ 객체, JIT 코드가 각각 다른 규칙으로 커지고 줄어듭니다. 이 장은 그 구조와 가비지 컬렉터(Scavenger, Mark-Compact, Orinoco)의 동작을 분해해, "GC가 왜 이벤트 루프를 멈추는가", "컨테이너가 왜 OOMKilled 되는가", "--max-old-space-size를 어디에 맞춰야 하는가"에 답할 수 있게 합니다.

학습 목표

  • V8 힙의 스페이스 구성과 각 스페이스가 담는 객체, 그리고 힙 밖 메모리(external, arrayBuffers, RSS)의 관계를 설명할 수 있다.
  • Scavenger(Cheney 복사)와 Mark-Sweep-Compact의 동작, 승격 규칙, 쓰기 장벽과 remembered set의 역할을 설명할 수 있다.
  • Orinoco가 일시정지를 어떻게 줄이는지(병렬·증분·동시) 알고, GC 일시정지가 이벤트 루프 지연으로 나타나는 경로를 추적할 수 있다.
  • --trace-gc 출력과 process.memoryUsage()를 읽고, 컨테이너 환경에서 힙 상한을 올바르게 설정할 수 있다.

1. 왜 메모리 구조를 알아야 하나

Node.js 운영에서 메모리는 두 가지 얼굴로 나타납니다. 하나는 지연입니다. V8의 GC는 상당 부분을 백그라운드 스레드로 옮겼지만, 여전히 메인 스레드를 멈추는 구간(stop-the-world 일시정지)이 있고, 그 시간은 2장에서 본 이벤트 루프 지연에 그대로 더해집니다. 힙이 클수록, 살아있는 객체가 많을수록 그 일시정지는 길어집니다. 다른 하나는 생존입니다. 힙 상한을 넘으면 V8은 FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory를 내고 프로세스를 죽이며, 컨테이너 메모리 한계를 넘으면 커널 OOM killer가 먼저 죽입니다. 두 상한은 서로 다른 것을 재며, 기본값은 서로를 모릅니다.

이 두 얼굴을 다루려면 "힙 사용량"이라는 숫자 하나로는 부족합니다. 어떤 스페이스가 커졌는지, 어떤 GC가 얼마나 자주 도는지, 힙 밖에서 무엇이 메모리를 쓰는지를 분리해서 봐야 합니다.

이 장의 한 줄 모델 V8 힙은 "자주 죽는 작은 객체를 위한 new space"와 "오래 사는 객체를 위한 old space"로 나뉘고, 각각 다른 알고리즘(복사 vs 마킹)으로 수거됩니다. 대부분의 성능 문제는 new space에서 죽어야 할 객체가 old space로 흘러들어가는 것(조기 승격)이거나, old space에서 죽어야 할 객체가 참조에 붙잡혀 있는 것(누수, 11장)입니다.

2. V8 힙의 지도: 스페이스

V8은 힙을 용도별 스페이스(space)로 나누고, 각 스페이스는 페이지(page)(기본 256KiB, 대형 객체 스페이스는 객체마다 전용 페이지) 단위로 OS에서 메모리를 받습니다. node -e "console.log(require('v8').getHeapSpaceStatistics())"로 현재 프로세스의 스페이스 목록과 크기를 볼 수 있습니다. 이름과 개수는 V8 버전마다 조금씩 바뀌므로(예: 과거의 map_space는 old space로 통합됨, Node 22의 V8 12.x부터 샌드박스용 trusted_space 추가) 반드시 실제 출력으로 확인하세요.

3. 세대 가설과 Scavenger

GC 설계는 세대 가설(generational hypothesis)에서 출발합니다. "대부분의 객체는 만들어진 직후 죽는다." HTTP 요청 하나를 처리하며 생기는 파싱 결과, 임시 배열, 클로저, Promise 객체는 응답을 보내는 순간 전부 쓰레기가 됩니다. 이런 객체를 위해 V8은 작은 new space를 두고, 살아있는 것만 복사해 내고 나머지는 통째로 버리는 복사 수집기(Scavenger)를 씁니다. 복사 비용은 살아있는 객체 수에만 비례하고 쓰레기 양과는 무관합니다. 세대 가설이 맞는 워크로드에서는 거의 공짜입니다.

3.1 Cheney 알고리즘

new space는 같은 크기의 semi-space 둘(from, to)로 나뉩니다. 할당은 항상 from-space에서 포인터를 범프(bump)하며 이루어집니다(그래서 V8의 객체 할당은 malloc보다 훨씬 쌉니다). from-space가 차면 Scavenge가 시작됩니다.

  1. 루트(스택, 전역, 핸들)와 remembered set(old → new 포인터, 3.3절)에서 직접 가리키는 new-space 객체를 to-space로 복사하고, 원래 자리에 포워딩 주소를 남긴다.
  2. to-space를 스캔 포인터로 순서대로 훑으며, 각 객체가 가리키는 new-space 객체를 또 복사한다(너비 우선). 이미 복사된 객체는 포워딩 주소로 참조를 고친다.
  3. 스캔 포인터가 할당 포인터를 따라잡으면 끝. from-space는 통째로 비우고 두 공간의 역할을 교환(flip)한다.

한 번 살아남은 객체는 to-space에 "나이 1"로 남고, 두 번째 Scavenge에서도 살아남으면 old space로 승격됩니다(V8의 기본 승격 규칙. to-space 사용량이 임계를 넘으면 더 일찍 승격하는 예외도 있습니다). V8 6.2부터 Scavenger는 여러 헬퍼 스레드로 병렬 복사합니다(parallel scavenge). 그래도 메인 스레드는 멈춥니다.

3.2 승격이 왜 문제인가

승격은 "이 객체는 오래 살 것"이라는 V8의 추측입니다. 추측이 틀리면, 즉 곧 죽을 객체가 old space로 가면 비싼 Mark-Compact가 치워야 합니다. 이것을 조기 승격(premature promotion)이라 합니다. 전형적인 원인은 다음과 같습니다.

  • semi-space가 할당 속도에 비해 너무 작다. 요청 처리 중 생긴 객체가 응답 전에 Scavenge를 두 번 맞으면 승격됩니다. 할당 속도가 높은 서버에서 --max-semi-space-size를 키우면(예: 16 → 64MiB) 승격률이 떨어지고 처리량이 오르는 경우가 실제로 많습니다. 5절 시뮬레이터에서 확인하세요.
  • 요청보다 오래 사는 중간 버퍼. 큐에 쌓이는 로그 객체, 응답을 기다리는 동안 유지되는 큰 파싱 결과.
  • 큰 객체. 처음부터 large object space로 갑니다. 복사 대상이 아니라 마킹 대상입니다.

3.3 쓰기 장벽과 remembered set

Scavenger가 old space 전체를 스캔하지 않고도 "old 객체가 가리키는 new 객체"를 알려면, old → new 포인터가 생길 때마다 기록해야 합니다. V8은 모든 포인터 저장(store) 명령에 쓰기 장벽(write barrier)을 끼워 넣어, 대상이 new space이고 출처가 old space이면 그 슬롯을 remembered set(페이지별 슬롯 집합)에 추가합니다. Scavenge 시 이 집합이 추가 루트가 됩니다. 쓰기 장벽은 JIT 코드에 인라인되며, 대부분의 저장은 빠른 경로(둘 다 new거나 둘 다 old)로 빠집니다. 같은 장벽이 Orinoco의 증분/동시 마킹에서는 "마킹 중 바뀐 포인터"를 기록하는 데도 쓰입니다.

실무 함의 오래 사는 큰 구조(캐시 Map, 커넥션 풀)에 새 객체를 자주 끼워 넣는 패턴은 remembered set을 키워 Scavenge 비용을 올립니다. 캐시 값으로 매번 새 객체를 만들어 넣기보다, 필요한 경우 기존 객체를 재사용하거나 캐시 항목 수 자체를 제한하는 것이 GC 관점에서 유리합니다.

4. Old space: Mark-Sweep-Compact와 Orinoco

old space는 복사하기엔 너무 큽니다. 대신 마킹(mark)으로 살아있는 객체를 찾고, 스위핑(sweep)으로 죽은 객체의 공간을 free list에 돌려주며, 조각화가 심한 페이지는 컴팩션(compact)으로 살아있는 객체를 다른 페이지로 옮겨 통째로 반납합니다.

  1. Mark: 루트에서 출발해 도달 가능한 모든 객체를 삼색(흰/회/검) 마킹으로 방문. 비용은 살아있는 객체 그래프 크기에 비례. 가장 비싼 단계.
  2. Sweep: 페이지를 훑어 마킹 안 된 영역을 free list에 등록. 비용은 힙 크기에 비례하지만 지연(lazy) 처리 가능.
  3. Compact: 조각화 비율이 높은 페이지(evacuation candidates)를 골라 살아있는 객체를 이동하고 포인터를 갱신. 선택적으로 수행.

4.1 Orinoco: 일시정지를 쪼개고 옮기기

2016~2018년에 걸쳐 V8 팀은 GC를 Orinoco라는 이름으로 재설계해 메인 스레드 일시정지를 줄였습니다. 핵심 기법 세 가지는 "어떤 스레드가, 메인 스레드가 멈춘 채로 하느냐"로 구분됩니다.

기법메인 스레드누가 일하나V8에서 적용된 곳
병렬(parallel)멈춤메인 + 헬퍼 스레드가 동시에Scavenge 복사, 컴팩션(evacuation), 마킹 마무리
증분(incremental)잠깐씩 멈춤 (조각으로 분할)메인 스레드가 JS 실행 사이사이에마킹. 할당량 기반으로 스텝 실행
동시(concurrent)멈추지 않음헬퍼 스레드가 JS 실행과 동시에마킹(concurrent marking), 스위핑(concurrent sweeping)

동시 마킹 중 JS가 포인터를 바꾸면 마킹 결과가 깨질 수 있습니다. 그래서 3.3절의 쓰기 장벽이 마킹 중에도 켜져, 바뀐 객체를 다시 회색으로 되돌리거나(Dijkstra 식 장벽) 워크리스트에 넣습니다. 마킹이 끝나면 메인 스레드가 멈춘 채로 마무리(finalize)를 하는데, 이 짧은 일시정지가 --trace-gc에서 "Mark-Compact ... ms" 로 찍히는 시간입니다. 괄호 안의 "+ N ms in M steps since start of marking"이 증분 마킹에 쓰인 시간입니다.

또 하나, idle-time GC: 임베더(Node의 경우 libuv 루프)가 "지금 여유가 있다"고 알려주면 V8은 그 시간에 GC 작업을 미리 합니다. Node.js는 --max-semi-space-size 등 플래그로 V8 설정을 넘기지만, 브라우저만큼 적극적으로 idle 시간을 알려주지는 않습니다.

컨테이너 CPU 제한과 GC 동시·병렬 GC는 여유 CPU 코어를 전제합니다. CPU 0.5코어로 제한된 파드에서는 헬퍼 스레드가 메인 스레드와 CPU를 두고 경쟁하므로, Orinoco의 이점이 사라지고 오히려 JS 실행이 느려집니다. CPU 1코어 미만 파드에서 GC 일시정지가 유난히 길다면 이것이 원인일 수 있습니다. --single-threaded-gc로 헬퍼를 끄고 비교해 볼 수 있습니다.

5. 시뮬레이터: 할당 패턴이 GC 비용을 결정한다

아래 모델은 단순화했지만 방향은 실제와 같습니다. Scavenge 비용은 살아남은 바이트에, Mark-Compact 비용은 old space의 살아있는 바이트에 비례합니다. 할당 속도, 단명 객체 비율, semi-space 크기, 누수 속도를 바꿔 보며 GC 빈도와 일시정지가 어떻게 달라지는지 보세요.

실험해 볼 것:

  • 할당 속도를 300MiB/s로 올리고 semi-space를 4MiB로 줄이면 초당 수십 번의 Scavenge가 돌고 승격률이 치솟습니다. semi-space를 32MiB 이상으로 키우면 승격률과 Mark-Compact 빈도가 함께 떨어집니다. 이것이 --max-semi-space-size 튜닝의 효과입니다.
  • 누수 속도를 올리면 old space가 선형으로 자라고, Mark-Compact 일시정지도 함께 길어지다가 상한에 닿으면 "heap out of memory"로 끝납니다. 누수는 OOM 전에 먼저 지연 문제로 나타납니다.
  • 단명 객체 비율을 낮추면(요청보다 오래 사는 객체가 많으면) semi-space를 키워도 소용이 없습니다. 이 경우는 설계 문제입니다.

6. 힙 플래그와 상한: 컨테이너 환경

6.1 기본 상한은 어떻게 정해지나

V8은 시작 시 물리 메모리 크기를 보고 old space 상한을 정합니다(Heap::HeapSizeFromPhysicalMemory). 64비트에서는 대략 물리 메모리의 1/4, 최대 2~4GiB 근처로 잡히며 정확한 공식은 버전마다 다릅니다. 지금 프로세스의 값은 다음으로 확인합니다.

$ node -e "console.log(require('v8').getHeapStatistics().heap_size_limit / 1024 / 1024 | 0, 'MiB')"
4144 MiB     # 예: 16GiB 머신의 Node 22

문제는 컨테이너입니다. 파드에 메모리 1GiB 제한을 걸어도 커널이 보고하는 물리 메모리는 호스트 전체(예: 64GiB)이므로, V8은 상한을 수 GiB로 잡습니다. 힙이 1GiB를 넘는 순간 V8은 아직 여유가 있다고 믿고 계속 할당하지만, cgroup이 먼저 프로세스를 죽입니다(OOMKilled, exit code 137). Node.js의 로그에는 아무것도 남지 않습니다. 최근 Node는 libuv의 uv_get_constrained_memory()로 cgroup 한계를 반영하려 시도하지만, 그 동작에 의존하지 말고 명시적으로 설정하는 것이 운영 표준입니다.

6.2 어떻게 설정하나

# 컨테이너 메모리 한계 1GiB 기준의 보수적 설정 예
NODE_OPTIONS="--max-old-space-size=768 --max-semi-space-size=32"

# 또는 실행 시
node --max-old-space-size=768 server.js
플래그의미권장
--max-old-space-size=<MiB>old space 상한. 넘으면 치명적 OOM.컨테이너 한계의 약 75%. 나머지는 new space, 코드, Buffer, 스레드 스택, 단편화 몫.
--max-semi-space-size=<MiB>semi-space 하나의 최대 크기. new space는 이 값의 2~3배를 쓴다.할당이 많은 API 서버는 32~64로 키워 보고 승격률·처리량 비교.
--heapsnapshot-near-heap-limit=<n>상한 근처에서 힙 스냅샷을 n번 자동 저장(Node 15.1+). 11장.스테이징에서 켜 두면 OOM 원인 확보.
--expose-gcglobal.gc() 노출.벤치마크·테스트 전용. 프로덕션 금지.
--trace-gc, --trace-gc-verboseGC마다 한 줄 로그.조사 시 일시적으로.
v8.setFlagsFromString()런타임에 V8 플래그 변경.힙 크기류는 시작 후 변경해도 반영되지 않는 것이 많다. 주의.
"힙 상한 = 컨테이너 한계"로 두지 마라 RSS에는 힙 외에 external 메모리, 스레드 스택(libuv 풀 4개 + V8 헬퍼 + 워커), 코드, malloc 단편화가 포함됩니다. 힙 상한을 컨테이너 한계와 같게 두면 힙이 상한에 닿기 전에 반드시 OOMKilled 됩니다. 또한 Mark-Compact가 상한 근처에서 "마지막 수단 GC"를 반복하며 CPU를 태우는 구간이 생기므로, 상한 자체에 닿지 않도록 알림 임계를 상한의 80% 정도에 둡니다.

워커 스레드(9장)는 각자 독립된 V8 isolate와 힙을 가집니다. 워커의 힙 상한은 new Worker(file, { resourceLimits: { maxOldGenerationSizeMb, maxYoungGenerationSizeMb } })로 따로 정하며, 메인의 --max-old-space-size는 워커 힙을 제한하지 않습니다. 워커 4개 × 힙 상한 512MiB면 최악의 경우 2GiB가 더 필요합니다.

7. 관측: --trace-gc, memoryUsage, perf_hooks

7.1 --trace-gc 출력 읽기

node --trace-gc app.js는 GC가 끝날 때마다 한 줄을 stdout에 씁니다. 형식은 다음과 같습니다.

[12345:0x5c0a3c0]  1523 ms: Scavenge 42.1 (58.3) -> 38.4 (59.3) MB, 1.8 / 0.0 ms  (average mu = 0.996, current mu = 0.995) allocation failure;
[12345:0x5c0a3c0]  4870 ms: Mark-Compact 410.2 (452.0) -> 120.7 (300.5) MB, 25.3 / 0.1 ms  (+ 48.2 ms in 37 steps since start of marking, biggest step 3.1 ms, walltime since start of marking 210 ms) (average mu = 0.981, current mu = 0.912) finalize incremental marking via stack guard; GC in old space requested
 ^pid:isolate   ^프로세스 시작 후 경과   ^GC 종류   ^GC 전 used (total)  ^GC 후 used (total)   ^메인 스레드 일시정지 / external 시간   ^증분 마킹 상세    ^mu = mutator utilization   ^원인
--trace-gc 로그 해석기
로그 줄을 붙여 넣으면 필드를 분해하고 요약 통계를 냅니다. 기본으로 샘플이 들어 있습니다.

mu(mutator utilization)는 "최근 구간에서 JS(mutator)가 CPU를 쓴 비율"입니다. 1.0에 가까우면 GC 비용이 미미하고, 0.9 아래로 자주 떨어지면 GC가 처리량을 갉아먹는 상태입니다. Scavenge 줄의 "GC 후 used"가 "GC 전 used"와 거의 같다면(살아남는 게 많다면) 조기 승격이 일어나고 있다는 신호입니다. Mark-Compact 줄에서 "GC 후 used"가 매번 조금씩 올라가면 누수입니다.

7.2 process.memoryUsage()

> process.memoryUsage()
{
  rss: 61_200_000,        // 커널 기준 상주 메모리 (힙 + 힙 밖 + 코드 + 스택 + 단편화)
  heapTotal: 12_300_000,  // V8이 예약한 힙 페이지 합
  heapUsed: 9_800_000,    // 그중 사용 중 (GC 직후가 가장 정확)
  external: 2_100_000,    // V8이 "외부"로 추적하는 C++ 메모리 (Buffer 백킹 포함)
  arrayBuffers: 1_050_000 // external 중 ArrayBuffer/Buffer 백킹 스토어
}
memoryUsage 분해 계산기
값을 MiB로 넣으면 관계를 막대로 그리고, 어떤 영역이 비정상적으로 큰지 진단합니다.

7.3 GC 이벤트를 코드로 받기

const { PerformanceObserver, constants } = require('node:perf_hooks');
const KIND = {
  [constants.NODE_PERFORMANCE_GC_MAJOR]: 'major',        // Mark-Compact
  [constants.NODE_PERFORMANCE_GC_MINOR]: 'minor',        // Scavenge
  [constants.NODE_PERFORMANCE_GC_INCREMENTAL]: 'incremental',
  [constants.NODE_PERFORMANCE_GC_WEAKCB]: 'weakcb',
};
const obs = new PerformanceObserver(list => {
  for (const e of list.getEntries()) {
    // e.duration = 메인 스레드 일시정지(ms), e.detail.kind, e.detail.flags
    if (e.duration > 20) console.warn(`GC ${KIND[e.detail.kind]} pause ${e.duration.toFixed(1)}ms`);
    metrics.gcPause.observe({ kind: KIND[e.detail.kind] }, e.duration);
  }
});
obs.observe({ entryTypes: ['gc'] });

이 방법이 --trace-gc보다 운영에 적합합니다. 15장에서 이 값을 Prometheus 히스토그램으로 내보내고, 2장의 루프 지연 p99와 같은 대시보드에 놓고 상관관계를 봅니다. "루프 지연 스파이크 = GC major 일시정지"인지, "= 동기 작업"인지가 거기서 갈립니다.

8. 힙 밖 메모리: Buffer, external, RSS

Buffer는 JS 객체(힙 안, 수십 바이트)와 백킹 스토어(힙 밖, 실제 데이터)로 이루어집니다. 100MiB 파일을 fs.readFile로 읽으면 heapUsed는 거의 그대로이고 external/arrayBuffers/RSS만 100MiB 오릅니다. V8은 external 메모리의 양을 힌트로 받아(AdjustAmountOfExternalAllocatedMemory) GC를 더 자주 돌리긴 하지만, 백킹 스토어 자체는 JS 객체가 수거될 때 소멸자에서 해제됩니다. 즉 Buffer를 붙잡고 있는 작은 JS 객체 하나가 큰 external 메모리를 붙잡을 수 있고, 힙 스냅샷에서는 작은 객체로만 보입니다.

  • Buffer 풀: 4KiB 미만의 Buffer.allocUnsafe/Buffer.from(string)은 8KiB 공용 슬랩(Buffer.poolSize)에서 잘라 씁니다. 슬랩의 한 조각이라도 살아있으면 슬랩 전체가 유지됩니다. 작은 Buffer를 오래 보관하면 예상보다 메모리가 큽니다. 오래 보관할 것은 Buffer.alloc(풀 미사용)으로.
  • RSS가 heapTotal + external보다 훨씬 클 때: (1) glibc malloc의 단편화 또는 반납 지연(해제한 메모리가 OS로 돌아가지 않음), (2) 스레드 스택(워커마다 수 MiB), (3) 공유 라이브러리와 JIT 코드, (4) 힙 페이지가 GC 후에도 예약 상태로 남음. 1번은 MALLOC_ARENA_MAX=2 설정이나 jemalloc 교체로 줄어드는 사례가 보고되어 있지만, 측정 없이 적용하지 마세요.
  • 문자열: 긴 문자열 연결은 콘스(cons) 문자열로 힙 안에 남고, 네이티브에서 넘어온 외부 문자열은 external로 잡힙니다.
진단 순서 RSS가 자라는데 heapUsed가 평평하면 힙 밖 문제입니다. 먼저 arrayBuffers를 보고(Buffer 누수), 다음 external - arrayBuffers(네이티브 애드온, 외부 문자열), 그래도 설명이 안 되면 malloc 단편화나 스레드 수를 의심합니다. 힙 스냅샷은 이 경우 거의 도움이 되지 않습니다.

9. WeakRef, FinalizationRegistry, WeakMap

GC의 결정에 참여하지 않으면서 객체를 참조하는 수단입니다. 세 가지는 쓰임이 다릅니다.

보장적합한 용도함정
WeakMap/WeakSet키가 수거되면 항목도 사라짐. 열거 불가.객체에 메타데이터 붙이기(캐시된 파생값, 프라이빗 데이터)키는 객체만. 값이 키를 참조하면 순환이 되지만 V8의 ephemeron 처리로 수거됨.
WeakRefderef()가 같은 잡(job) 안에서는 일관됨. 수거 시점 보장 없음."있으면 쓰고 없으면 다시 만든다"가 허용되는 캐시수거가 늦어 메모리를 오래 잡을 수 있음. 강한 캐시 + 크기 제한이 대개 더 예측 가능.
FinalizationRegistry수거 후 콜백이 "언젠가" 불림. 프로세스 종료 시에는 안 불릴 수 있음.네이티브 리소스 해제 누락 감지(경고 로그)리소스 해제의 주 수단으로 쓰면 안 됨. 명시적 close()/Symbol.dispose가 정답.
// 네이티브 핸들을 잊고 버렸는지 감시하는 용도
const registry = new FinalizationRegistry(label => {
  logger.warn(`handle ${label} was GC'd without close()`);
});
class Handle {
  constructor(label) { this.label = label; registry.register(this, label, this); }
  close() { registry.unregister(this); /* 실제 해제 */ }
}

10. 현업 장애 사례

사례 1: 로그 없는 OOMKilled

메모리 2GiB 파드. Node 기본 힙 상한은 호스트(64GiB) 기준으로 4GiB 근처로 잡혔고, 캐시가 커지며 힙이 1.9GiB를 넘자 cgroup이 프로세스를 죽였습니다. 애플리케이션 로그에는 아무 흔적이 없고 kubectl describe pod에 OOMKilled, exit code 137만 남았습니다. 해결: --max-old-space-size=1536으로 V8이 먼저 알아차리게 하고, --heapsnapshot-near-heap-limit=1을 스테이징에 켜 원인(무제한 캐시)을 확보. 근본 해결은 캐시에 LRU 상한.

사례 2: semi-space 튜닝으로 처리량 20% 회복

요청당 수백 KiB를 할당하는 JSON API. --trace-gc에서 초당 Scavenge 40회, 각 3~5ms, Scavenge 후 used가 전보다 거의 줄지 않음(조기 승격). Mark-Compact도 수십 초마다 50ms. --max-semi-space-size=64로 바꾸자 Scavenge가 초당 8회로, 승격률과 Mark-Compact 빈도가 크게 줄고 p99가 개선. 메모리는 new space 몫으로 100MiB 남짓 더 사용. 비슷한 결과가 공개 사례(예: Node.js 공식 블로그와 여러 기업 기술 블로그)에도 보고되어 있지만, 워크로드마다 다르므로 반드시 측정으로 결정.

사례 3: heapUsed는 평평한데 RSS가 자람

이미지 썸네일 서비스. 힙 스냅샷을 아무리 찍어도 이상이 없는데 RSS가 하루에 수백 MiB씩 증가. process.memoryUsage().arrayBuffers가 함께 증가하는 것을 확인하고, 네이티브 이미지 라이브러리가 돌려준 Buffer를 요청별 Map에 디버그용으로 보관하는 코드를 발견. 힙 스냅샷에서는 Map 항목이 수십 바이트의 Buffer 객체로만 보였습니다. 8절의 진단 순서가 그대로 적용된 사례.

핵심 요약

  • V8 힙 = new space(semi-space 둘, Scavenger 복사) + old space(Mark-Sweep-Compact) + large object/code/read-only 등. Buffer 데이터는 힙 밖(external/arrayBuffers).
  • Scavenge 비용은 살아남은 바이트에, Mark-Compact 비용은 old space 살아있는 그래프에 비례. 두 번 살아남으면 승격. 조기 승격이 흔한 성능 문제이고 --max-semi-space-size로 완화된다.
  • 쓰기 장벽이 old → new 포인터를 remembered set에 기록해 Scavenger가 old space를 훑지 않게 하고, 동시 마킹의 정합성도 지킨다.
  • Orinoco = 병렬·증분·동시 GC. 메인 스레드 일시정지는 finalize 구간으로 줄지만 CPU 여유 코어를 전제한다.
  • 기본 힙 상한은 물리 메모리 기준이라 컨테이너 한계를 모른다. --max-old-space-size는 컨테이너 한계의 약 75%, 알림은 그 80%에.
  • 관측: --trace-gc(조사), PerformanceObserver('gc')(상시), process.memoryUsage()(rss/heapTotal/heapUsed/external/arrayBuffers 관계로 어디가 자라는지 분리).
  • WeakRef/FinalizationRegistry는 보조 수단. 리소스 해제는 명시적으로.

확인 문제

Scavenge 한 번의 비용은 주로 무엇에 비례하는가?
복사 수집기는 살아있는 객체만 to-space로 옮기고 나머지는 통째로 버립니다. 쓰레기가 아무리 많아도 비용이 늘지 않는 것이 세대별 GC의 핵심 이점입니다. old space는 remembered set으로만 참여합니다.
메모리 1GiB 제한 컨테이너에서 Node 앱이 로그 없이 exit code 137로 죽는다. 가장 가능성 높은 원인과 첫 조치는?
137 = 128 + SIGKILL(9). V8 OOM이면 "Reached heap limit" 로그와 함께 종료되지만, cgroup이 먼저 죽이면 로그가 없습니다. 기본 힙 상한은 호스트 메모리 기준이므로 컨테이너 한계보다 큽니다. 상한을 낮추면 V8이 먼저 GC를 더 적극적으로 돌리고, 정말 부족하면 로그와 함께 죽어 원인을 남깁니다.
old space의 객체 A에 방금 생성한 객체 B를 저장했다(A.x = B). 다음 Scavenge에서 B가 살아남는 메커니즘은?
old → new 포인터 저장은 쓰기 장벽의 느린 경로를 타고 remembered set에 슬롯이 추가됩니다. Scavenger는 스택·전역과 함께 이 집합만 루트로 봅니다. old space 전체 스캔은 Scavenge의 목적(짧은 일시정지)에 반합니다.
--trace-gc에서 Scavenge 줄이 "42.1 (58.3) -> 40.9 (59.3) MB"처럼 GC 후 used가 거의 줄지 않는 패턴이 반복된다. 의미는?
Scavenge가 메모리를 거의 못 줄인다는 것은 살아남는 비율이 높다는 뜻입니다. 요청 처리 중 두 번의 Scavenge를 맞는 경우가 전형적이며, --max-semi-space-size를 키우면 개선되는지 확인합니다. 누수 여부는 Mark-Compact 후 used 추세로 봅니다.
RSS는 계속 늘지만 heapUsed와 heapTotal은 평평하다. 다음으로 볼 지표는?
힙 지표가 평평하면 힙 밖(Buffer 백킹, 네이티브, 단편화)이 원인입니다. 힙 스냅샷은 힙 안만 보여주고, Buffer는 작은 객체로만 나타나 오해를 부릅니다. external/arrayBuffers 추세로 범위를 좁힌 뒤 코드에서 Buffer 보관처를 찾습니다.

    // alloc.js — 요청 처리를 흉내: 요청당 2,000개의 객체를 만들고 짧게 보관
const live = [];
for (let req = 0; req < 20000; req++) {
  const objs = Array.from({ length: 2000 }, (_, i) => ({ id: i, req, data: 'x'.repeat(50) }));
  live.push(objs);
  if (live.length > 5) live.shift();   // 최근 5개 요청분만 유지 (요청보다 약간 긴 수명)
}
console.log(process.memoryUsage());
  2. 컨테이너 상한 실험. docker run --memory=256m node:22 node -e "const a=[]; setInterval(()=>a.push(Buffer.alloc(10<<20).fill(1)),50)"를 실행해 어떻게 죽는지(로그 유무, exit code) 확인하고, --max-old-space-size=128을 붙였을 때와 비교하세요. Buffer는 힙 밖이므로 두 번째 경우에도 V8 OOM이 아닌 cgroup OOM이 먼저 올 수 있습니다. 그 이유를 8절로 설명해 보세요.
  3. GC 메트릭 수집. 7.3절의 PerformanceObserver 코드를 2장의 monitorEventLoopDelay와 함께 한 서버에 넣고, 1번 과제의 할당 코드를 요청 핸들러로 바꿔 부하를 주면서 "GC major 일시정지"와 "루프 지연 p99"가 같이 움직이는지 콘솔에서 확인하세요.
