디스크 로그와 재시작

성공 응답을 보내도 되는 시점을 정합니다.

이번 장의 산출물: 재시작 시 정상 레코드를 재생해 Ready 큐를 복구합니다.

개념부터 연결합니다

메모리 큐는 재시작하면 사라집니다

Publish를 받으면 먼저 Enqueue 레코드를 로그에 쓰고 내구성 경계까지 진행한 뒤 접수 확인을 보냅니다. 메모리 큐는 로그에서 재구성할 수 있는 인덱스로 취급합니다.

레코드를 구분하고 손상을 검출합니다

로그 형식은 length, payload, checksum입니다. checksum은 선택한 알고리즘으로 기록과 검증을 맞춥니다. 여기서는 프레임 길이와 체크섬을 갖춘 WAL을 직접 설계합니다. 파일 끝의 불완전 레코드는 마지막 정상 위치까지 잘라냅니다. 파일 중간의 손상은 운영자 확인 없이 건너뛰지 않습니다.

flush의 범위를 구분합니다

WriteAsync 완료, OS 버퍼 반영, 디스크 flush는 같은 사건이 아닙니다. FileStream.Flush(true)를 내구성 경계로 사용합니다. 실제 정전 내구성은 장치와 파일시스템 보장에도 의존합니다. 프로세스 kill 실험만으로 정전 내구성을 입증할 수는 없습니다.

C#으로 구현하는 순서

  1. Storage 프로젝트에 AppendAsync와 Recover를 만듭니다.
  2. Broker의 한 소유자가 로그 쓰기 순서를 직렬화합니다.
  3. Enqueue 로그 flush가 끝난 뒤 Publish 응답을 보냅니다.
  4. 재시작 시 정상 레코드를 재생해 Ready 큐를 복구합니다.
핵심 계약과 코드 발췌

프로젝트 문맥에 맞게 통합하는 학습용 발췌입니다. 생략한 부분은 구현 순서와 완료 기준을 따라 작성합니다.

// Storage/Journal.cs — AppendAsync 내부의 순서 예시
// framedRecord에는 길이, payload, checksum이 들어 있습니다.
// 동일 FileStream에 대한 append는 단일 소유자가 직렬화합니다.
await file.WriteAsync(framedRecord, ct);
file.Flush(flushToDisk: true);
// 이 다음에 메모리 인덱스를 갱신하고 접수 확인을 보냅니다.
