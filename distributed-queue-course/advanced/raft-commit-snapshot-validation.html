Raft 커밋·스냅샷 설치와 장애 불변식

선수 장 · 기존 10장 · 현재 term 커밋과 분단

이전 term의 항목이 과반수에 복제되었다면 곧바로 커밋할 수 있을까요? 오래 뒤처진 follower에게 로그 전체를 보내기 어렵다면 무엇을 스냅샷에 담아야 할까요? 커밋 순번과 적용 순번, snapshot의 경계를 분리해 완료 작업이 되살아나지 않는지 점검합니다.

사본 수로 직접 커밋하는 항목의 term

현재 term=4인 리더가 index 3의 term=2 항목을 두 노드에 갖고 있다고 합시다. 그 개수만으로 index 3을 직접 커밋하지 않습니다. 현재 term의 새 항목 index 4를 과반수에 영속 복제한 뒤 commitIndex=4로 전진하면 앞 항목도 그 접두부 안에서 함께 확정됩니다. 복제 ACK의 수와 안전한 커밋 경계를 구분하는 반례입니다.

commitIndex는 확정된 접두부, lastApplied는 상태 머신에 실제 적용한 접두부입니다. 응답에 어떤 시점을 보장할지 명시하고 적용은 순서대로 한 번씩 진행합니다. 재시작 시 이미 완료한 업무 결과를 다시 반영하지 않으려면 로그 위치뿐 아니라 적용 상태나 업무 ID 멱등 경계도 일치해야 합니다. 큐의 Enqueue뿐 아니라 ACK·Retry·DLQ도 같은 상태 머신에 속합니다.

스냅샷은 로그 절단과 함께 검증하기

스냅샷이 lastIncludedIndex=100, lastIncludedTerm=6이라면 그 지점까지 적용한 큐 상태와 구성 정보를 함께 담습니다. follower가 20에 멈췄고 리더가 101 이후만 보관한다면 snapshot 100을 설치하고 101~120을 이어 적용해야 합니다. Ready만 복사하고 Done·dedup 정보를 빼면 완료 작업이 다시 살아날 수 있습니다.

설치 과정은 임시 snapshot 검증·내구화·원자적 게시·메타데이터 일치·불필요 로그 회수의 순서를 정해야 합니다. 더 새로운 applied 상태를 이미 가진 노드에 낡은 snapshot을 덮어씌우면 상태가 후퇴합니다. 전송 중 중단, 게시 직후 중단, 후속 로그 적용 중 중단에서 다시 시작해 accepted ID가 Done·Ready·InFlight·Retry·DLQ 중 유효한 상태로 설명되는지 확인하세요.

실습과 예상 관찰

현재 term=4, old entry=(index3,term2), current entry=(index4,term4)를 적고 커밋 경계를 예측하세요. 이어 follower=20, snapshot=100, leader=120의 복구 순서를 선택합니다. 실제 파일 실험은 임시 3노드 데이터에서만 수행하고 복구를 두 번 반복한 ID 집합이 같은지 대조하세요.

이전 term의 index3만 2/3 복제

그 사본 개수만으로 직접 커밋했다고 표시하지 않습니다. 현재 term의 항목을 통한 안전한 접두부 확정 조건이 더 필요합니다.

현재 term index4가 2/3 영속 복제

커밋 경계가 4까지 전진하면 앞의 index3도 확정된 접두부에 포함됩니다. 적용은 순번대로 진행합니다.

snapshot100 설치 후 101~120 적용

상태는 120까지 따라잡아야 하며 Done·dedup도 보존되어야 합니다. snapshot에 없는 임의의 Ready 목록으로 대체하면 안 됩니다.

applied110에 snapshot90 덮어쓰기

상태 후퇴를 만드는 잘못된 경로입니다. snapshot의 포함 경계와 현재 적용 경계를 비교해야 합니다.

실습의 경계와 다음 장

커밋·스냅샷 경계의 유한 모형이며 실제 InstallSnapshot RPC와 디스크 게시를 구현한 것은 아닙니다. 기존 ClusterLab의 검증과 이 확장 규칙을 따로 기록해야 합니다. 완전한 제품 보장은 구성 변경·동시 장애·저장소 내구성까지 추가 검증이 필요합니다.
