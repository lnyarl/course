하이브리드 아키텍처 사례

실제 게임에서 효용 AI는 혼자 쓰이는 경우보다 행동 트리(BT)나 상태 트리 같은 기존 구조 안에 끼워 넣어 쓰이는 경우가 더 많다. 이 장에서는 세 가지 사례를 직접 조작해 본다. BT에 Utility Selector를 꽂은 Bill Merrill의 방식, 장비에 붙은 snippet에 점수를 매기는 Dragon Age: Inquisition의 Behavior Decision System, 그리고 UE5 StateTree의 utility 선택이다. 이어서 숙고와 반응을 분리하는 설계를 보고, 언제 하이브리드로 가야 하는지 정리한다.

학습 목표

  • 정적 우선순위 BT가 "상황에 따라 우선순위가 바뀌는 행동"을 어떻게 다루지 못하는지, Utility Selector가 이를 어떻게 푸는지 Listing 수준으로 설명한다.
  • Utility가 composite를 따라 위로 전파되는 방식(자식 max)과 decorator 변환(cube)의 효과를 계산한다.
  • DA:I BDS의 snippet·evaluation tree·Target Selector·점수 관례를 이해하고, 정규화 0~1·점수 대역·dual rank를 비교한다.
  • UE5 StateTree의 consideration 결합(AND=min, OR=max, × Weight)을 우리 엔진의 보정 곱과 비교한다.
  • 숙고와 반응을 분리하는 Action Selector가 우리 엔진의 think(a, interruptOnly)와 어떻게 대응하는지 설명하고, 상황별로 어떤 하이브리드를 고를지 판단한다.

1. 왜 하이브리드인가

01장 지형도에서 본 것처럼 의사결정 아키텍처마다 강점과 약점이 다르다. BT는 구현이 쉽고 시각화가 좋아 팀 전체가 빨리 익힌다. 대신 우선순위가 트리 구조에 고정되고, 조건이 참/거짓뿐이라 "둘 다 그럴듯한" 회색지대 결정에 약하다. 효용 AI는 바로 그 회색지대에 강하지만 결과를 예측하기 어렵고, 연출상 반드시 나와야 하는 행동은 스크립트로 덮어써야 하며, 튜닝은 기술보다 감각에 가깝다(GAP1 4장).

그래서 현업에서는 둘 중 하나를 고르기보다 잘 돌아가는 구조는 그대로 두고 회색지대에만 효용을 꽂는다. Merrill은 이 접근을 "기존 구현을 갈아엎지 않고, BT의 좋은 성질을 포기하지 않고" 효용을 섞는 방법이라고 설명한다. 이 장의 세 사례는 효용을 꽂는 위치가 서로 다르다.

2. BT + Utility: Utility Selector (Merrill)

2.1 Monster Hunter의 문제: 같은 행동을 트리에 두 번 넣기

Merrill의 예제는 Monster Hunter다. 루트 아래 Combat(Reload · Shoot · Seek Medic)과 Relaxed(Eat · Nap · Patrol) 두 가지가 있다. 표준 BT에서는 우선순위가 트리에 박혀 있다. 문제는 같은 행동이 상황에 따라 다른 우선순위를 가져야 할 때 생긴다. 탄창을 채워 두는 일은 정글을 순찰할 때도 고려할 일이지만, 괴물과 싸우는 중이라면 계속 피해를 주는 쪽이 절대적으로 중요하다.

Seek Medic은 더 곤란하다. 원래 이 행동의 전제조건은 "쏠 수 없음"이다. 체력이 "매우 낮을 때"는 사격보다 먼저, "괴물이 시야 밖이고 체력이 다소 낮을 때"는 사격 다음에 와야 한다면 트리에 Seek Medic을 두 번 넣는 수밖에 없다. 서브트리 인스턴싱이나 참조를 써도 장황하고 깨지기 쉽다. 그렇다고 Seek Medic의 조건을 엄격하게 만들어 Shoot보다 앞에 두면 반대 문제가 생긴다. 조건이 통과되는 순간 사냥꾼이 곧바로 Seek Medic으로 달려간다.

2.2 입력을 같은 단위로 만들기: 수식 10.1~10.4

Utility Selector를 쓰려면 자식마다 비교 가능한 utility 값이 있어야 한다. Merrill이 먼저 권하는 것은 공통 단위를 찾는 일이다. 사냥꾼이 의무병에게 달려갈지 정할 때, 치료로 얻는 체력과 이동 중 괴물에게 노출되어 잃을 체력을 둘 다 "체력 점수"로 표현하면 바로 뺄 수 있다.

RawUtility = HealthGained − HealthLost   (10.1)

본전치기라면 괴물을 때릴 시간을 버린 셈이므로 손실에 가중치를 더 준다. 예측이 낙관적이었더라도 순손실로 끝나지 않으려는 것이다. 지수를 씌우면 위험이 커질수록 효용이 더 빨리 떨어진다.

Value = HealthGained − (HealthLost × 2.0)   (10.2)
Value = HealthGained − pow(HealthLost, 1.2)   (10.3)

공통 단위가 없을 때는 여러 입력을 "Morale", "Threat" 같은 상위 개념으로 묶어 각각 0~1로 정규화한다. 위 식을 정규화해 Heal로, 괴물을 공격하지 못하고 잃은 시간을 정규화해 Delay로 두면 가중 차이로 합칠 수 있다.

Utility = (Heal × HealPower − Delay × DelayPower) / (HealPower + DelayPower)   (10.4)

Merrill은 이런 공식과 반응 커브를 다시 불러올 수 있는 데이터로 만들어 디자이너가 즉석에서 고치게 하라고 권한다. 우리 엔진의 consideration이 이미 그렇게 되어 있다(03장 반응 커브). 아래 위젯의 Seek Medic은 수식 10.4를 그대로 쓴다. HealPower=2, DelayPower=1이고, Heal은 잃은 체력 비율(1 − 체력/100), Delay는 괴물과 가까운 정도(1 − 거리/40)다. 이 값들은 교육용으로 정한 것이다.

2.3 Utility Selector 알고리즘 (Listing 10.1 → 10.2)

BT는 결국 트리 순회이고, 어느 가지로 갈지는 노드가 스스로 정한다. 그래서 새 Selector 종류를 하나 만들면 된다. 평범한 Selector(Listing 10.1)는 자식을 정해진 순서대로 실행하다가 Busy나 Done을 돌려주는 첫 자식에서 멈춘다. Utility Selector(Listing 10.2)는 그 앞에 단계 하나가 붙는다.

// Listing 10.1 기본 Selector
Status Execute() {
  if (CurrChild == null) CurrChild = FirstChild;
  // 유효한 자식을 만날 때까지 실행
  while (CurrChild != null) {
    Status s = CurrChild.Execute();
    if (s == Busy || s == Done) return s;
    CurrChild = CurrChild.Next;
  }
  return Failed;
}
Status Execute() {  if (Utility.Size() == 0) {    // 자식 utility 질의    for (child in Children)      Utility[child] = child.CalculateUtility();    SortChildrenByUtility();   // 내림차순    CurrChild = FirstChild;  }  // utility 순서로 실행: 첫 유효 자식 선택  while (CurrChild != null) {    Status s = CurrChild.Execute();    if (s == Busy) return Busy;    else if (s == Done) { Utility.Clear(); return Done; }    CurrChild = CurrChild.Next;  }  Utility.Clear();  return Failed;}

핵심은 세 가지다. ① utility는 Utility 테이블이 비어 있을 때만, 즉 첫 실행 시에만 계산한다. ② 정렬된 순서는 "누구를 먼저 시도할지"일 뿐이다. 정렬 1위가 실행에 실패하면(Failed) 2위로 넘어가므로, 효용과 BT의 유효성 검사가 함께 일한다. ③ 자식이 Busy인 동안에는 테이블이 그대로 남는다. 그 사이에 상황이 바뀌어도 다시 계산하지 않는다는 뜻이다. Done이나 전체 실패가 나야 테이블을 비운다.

Merrill은 정렬 후 순서대로 실행하는 방법 외의 선택 방식도 열어 둔다. 최고점 자식만 고르거나, 자식을 버킷으로 나눈 뒤 가중 랜덤을 쓰거나(05장 Dual Utility), 일정 임계값을 넘는 자식들 중 가중치 없이 랜덤으로 고를 수도 있다. 어느 방식이든 하는 일은 같다. 기존 Selector에 utility 수집을 더해 우선순위를 동적으로 정하는 것이다. Merrill은 이것으로 BT의 가장 큰 약점이라 할 정적 우선순위를 깨뜨렸다고 평가한다.

2.4 Utility 전파와 Utility Decorator

보통 utility는 리프 행동이 계산한다. 하지만 Utility Selector의 자식은 Sequence일 수도, Selector일 수도, 또 다른 Utility Selector일 수도 있다. utility가 위로 자연스럽게 올라가게 하려면 모든 composite가 CalculateUtility()를 재정의해야 한다. 가장 단순한 규칙은 Selector든 Sequencer든 자식 중 최댓값을 돌려주는 것이다.

U(composite) = max( U(child₁), U(child₂), … )

대가도 있다. Utility Selector가 값을 모으려면 자식 서브트리를 전부 펼쳐야 한다. 큰 트리에서 utility 계산이 비싸고 플랫폼이 무작위 메모리 접근에 민감하다면 부담이 된다. Merrill이 제시한 완화책은 두 가지다. 리프가 일정 주기로만 계산하고 그 사이에는 캐시를 돌려주게 하거나, 모든 리프 계산을 자체 부하 분산이 있는 별도 패스로 빼서 CalculateUtility()는 캐시만 읽게 한다. 우리 엔진이 09장에서 thinkEvery와 thinkOffset으로 결정을 시간에 분산한 것과 같은 고민이다.

전파 경로에서 utility를 변환할 수도 있다. 자식 하나를 받는 decorator로 가중치를 곱하거나 함수를 씌우면 된다. Reload가 내부적으로 정규화 utility를 계산하는 블랙박스라 해 보자. 평소에는 형제와 그대로 비교해도 되지만, 탄약이 정말 바닥나기 전까지는 Reload를 미루고 싶을 때가 있다. 그럴 때 Reload 위에 square()나 cube() decorator를 얹는다.

원래 U가 0.5면 cube 후 0.125다. 탄창이 절반 남았을 때는 거의 장전하지 않는다는 뜻이다. 원래 U가 0.9(탄약 3발)면 0.73으로, 여전히 대부분의 형제를 이긴다. 곡선 하나로 "급할 때만 급해지는" 성질을 만든 것이고, 06장의 cooldown 커브 x⁵와 같은 발상이다.

decorator 방식의 장점은 Reload 내부를 건드리지 않는다는 데 있다. 같은 Reload 리프를 다른 트리에서는 decorator 없이 재사용할 수 있다.

2.5 평가와 실행의 분리

Merrill의 구현은 트리 평가(Evaluate)와 실행(Execute)을 나눈다. 덕분에 Utility Selector는 먼저 자식의 유효성을 평가한 뒤 유효한 자식에 대해서만 utility를 계산한다. 비싼 계산은 리프가 조건을 확인하는 Evaluate()에서 해 두고, CalculateUtility()는 캐시를 돌려준다. 에이전트가 행동을 실행하는 동안 트리를 병렬로 평가해 두었다가, 평가 결과가 지금 실행 중인 계획과 다를 때만 끼어드는 것도 가능하다. 트리 전체를 미리 평가하면 계획이 끝까지 유효한지 확인한 뒤 실행하는 제한적 look-ahead도 할 수 있다. 이 평가/실행 분리는 다음 절의 DA:I에서 아키텍처의 중심이 된다.

3. Dragon Age: Inquisition의 Behavior Decision System

DA:I의 전투에서는 플레이어가 조종하는 Inquisitor 옆에서 AI 동료 셋이 함께 싸운다. 전투원 하나가 쓸 수 있는 어빌리티는 2~20개이고, 각 어빌리티는 mana나 stamina를 쓴다. 자원이 한정되어 있으니 지금 하나를 쓰면 나중에 다른 것을 못 쓰는 기회비용이 생긴다. BioWare의 Hanlon과 Watts는 이 문제를 풀려고 효용 기반 Behavior Decision System(BDS)을 만들었다.

3.1 네 가지 가정과 탐욕 알고리즘

BDS는 네 가지를 가정한다. ① 어느 순간이든 AI가 할 수 있는 행동 집합은 유한하다. ② 한 번에 하나만 한다. ③ 행동마다 효용이 다르다. ④ 모든 행동의 효용을 정량화할 수 있다. 이 가정 아래서는 단순한 탐욕 알고리즘이 나온다. 합법적인 행동을 나열하고, 각각 점수를 매기고, 최고점을 실행한다(Graham 2014). 남는 질문은 "가능한 행동을 어떻게 나열하나"와 "효용을 어떻게 매기나"다.

3.2 Behavior Snippet: 어빌리티가 아니라 "쓰는 방식"이 단위

DA:I에는 어빌리티가 60개가 넘지만, 행동 수는 어빌리티 수가 아니다. 전사의 Charging Bull은 적진으로 돌진해 길을 막는 적을 쳐 내는 기술이다. 그런데 부상당한 전사가 전투에서 빠르게 빠져나갈 때도 같은 기술을 쓸 수 있다. 기술은 같아도 동기가 완전히 다르다. 그래서 BDS의 기본 단위는 "어빌리티를 특정한 방식으로 평가하고 실행하는 데 필요한 정보"인 behavior snippet이다.

snippet은 지식의 조각이고, 캐릭터에 등록(register)된다. 예를 들어 무기에 snippet 몇 개가 붙어 있으면, 캐릭터가 그 무기를 장착할 때 등록되고 해제할 때 등록이 풀린다. 그러면 행동을 나열하는 일이 등록된 snippet 목록을 읽는 것으로 끝난다. 평균적인 AI 캐릭터는 snippet 10~20개, 가장 복잡한 캐릭터는 50개 이상을 동시에 등록한다.

3.3 평가 트리와 점수 관례

각 snippet은 자기 효용을 계산하는 방법을 품고 있어야 한다. DA:I는 이를 변형된 BT인 evaluation tree로 표현했다. 트리는 루트에서 점수 0으로 출발하고, scoring 노드를 지날 때마다 그 값을 더한다. 평가는 "맥락 안에서" 이루어지므로 노드는 평가하는 캐릭터 같은 정보를 읽을 수 있다. 예를 들어 "내 체력이 50% 미만인가?" Filter 아래 "Score: 5"를 두면, 체력이 절반 미만일 때 5점, 아니면 0점을 돌려준다(Merrill 2014를 인용한 맥락 의존 평가).

여기서 BioWare는 자동 정규화나 스케일링을 여러 방식으로 검토했다. 그리고 결국 디자이너용 점수 관례를 쓰기로 했고, 그것을 권한다. 이 관례는 콘텐츠 제작자를 위한 지침일 뿐 게임 데이터에 따로 표현되지 않는다.

행동 유형점수의미 (Table 31.1)
Basic10아무것도 안 하는 것보다는 낫다. 여럿이면 서로 동등하다.
Offensive20–40부류 전체가 Basic보다 항상 낫다. 부류 안에서는 상황에 따라 20점의 "urgency dynamic range"로 우선순위를 다툰다.
Support25–45같은 긴급도의 Offensive보다 낫다. 공격 전에 써야 하는 준비 행동이거나, 나빠지는 상황에 대한 대응이기 때문이다.
Reaction50–70임박한 위협 같은 구체적·즉각적 실행 조건에 반응한다. 조건이 맞으면 다른 모든 유효 선택지보다 먼저 실행해야 한다.

평가 트리를 만드는 디자이너는 점수가 적절한 대역 안에 들어오도록 조건부로 점수를 배분할 책임을 진다. DA:I에서는 행동 부류마다 그 대역의 값을 돌려주도록 만든 점수 로직 자산을 따로 두었다. 예를 들어 Support 평가 트리는 기본 25점을 주고, 상황에 따라 최대 45점까지 더한다.

왜 정규화 대신 관례인가 대역을 정해 두면 점수 하나만 보고도 의미를 읽을 수 있다. 디버그 테이블에 "55"가 보이면 무언가에 반응하고 있다는 뜻이다. Offensive와 Support는 25~40에서 겹치므로 그 구간에서는 맥락이 승부를 낸다. 반면 Reaction(50~)은 Offensive(~40)와 겹치지 않아, 조건이 맞는 순간 사실상 rank처럼 동작한다. 하나의 숫자 축 위에 "겹치는 구간"과 "절대 우선 구간"을 함께 만든 셈이다. 대가는 규율이다. 관례가 데이터에 강제되지 않으므로 누군가 Offensive에 45점을 주면 아무도 막지 못한다. 그래서 BioWare는 부류별 점수 로직 자산을 재사용해 관례를 지켰다.

3.4 Target Selector: 행동과 대상을 함께 고르기

DA:I의 어빌리티는 대부분 대상이 필요하다. 그냥 "Immolate를 시전"할 수는 없고 특정 적에게 써야 한다. 화염에 약한 적에게 쓰면 큰 피해를 주지만 화염 면역인 적에게 쓰면 마나만 버린다. 그래서 평가 트리는 점수와 함께 대상도 돌려준다(08장 행동 × 대상과 같은 문제다). 이를 맡는 Target Selector 노드는 다음 알고리즘으로 동작한다.

  1. 현재 맥락 점수를 "초기 점수"로 기록한다.
  2. 디자이너가 지정한 대상 후보마다: (a) 맥락 점수를 초기 점수로 되돌리고 (b) "behavior target iterator" 슬롯에 그 후보를 넣고 (c) 자식 노드를 평가해서 (d) 자식이 true를 돌려주면 그 후보의 점수를 기록한다.
  3. 기록된 후보가 하나라도 있으면 최고점 후보를 Behavior Target으로 정하고, 맥락 점수를 그 점수로 바꾸고, true를 돌려준다.
  4. 기록된 후보가 없으면 false를 돌려준다.

논문의 예(Figure 31.2)는 "나로부터 10m 안의 적"을 하나씩 평가한다. "대상이 화염 면역이 아닌가?" Filter를 통과하면 +5, 이어서 "대상이 화염에 약한가?"를 통과하면 +5를 더 준다. 면역인 적은 Filter에서 걸려 기록되지 않고, 약점이 있는 적이 더 높은 점수를 받는다.

3.5 snippet 비교 (Listing 31.1)

struct SnippetEvaluation { BehaviorSnippet snippet; Boolean result; Integer score; Character target; };

// 등록된 behavior를 평가해 효용이 가장 높은 것을 돌려준다
Optional<SnippetEvaluation> EvaluateSnippets() {
  list<SnippetEvaluation> evaluatedSnippets;
  for (BehaviorSnippet snippet : registeredBehaviors) {
    SnippetEvaluation evaluation = snippet.evaluate();
    if (evaluation.result == true) evaluatedSnippets.push(evaluation);
  }
  sortByDescendingScore(evaluatedSnippets);
  if (evaluatedSnippets.empty() == false) return evaluatedSnippets.first();
  else return None;
}

실행 단계에 필요한 것은 최고점 snippet과 선택된 대상뿐이므로, 평가 결과를 따로 남길 필요는 없다. 그런데 BioWare는 평가 결과를 디버그로 볼 수 있는 테이블로 남겨 두는 것이 디버깅과 반복 작업에 큰 도움이 되었다고 말한다. 우리 엔진의 Reasoner.evaluate()가 행 전체(rows)를 돌려주는 것도 같은 이유다(11장).

3.6 실행 트리와 재평가 계약

snippet은 평가 트리와 함께 execution tree도 가진다. 실행 트리는 실제 효과가 나기 전에 필요한 준비와 위치 잡기를 담당한다. BDS는 평가에서 고른 대상과 snippet의 어빌리티를 맥락에 넣어 주고, Execute Ability 태스크 노드는 "맥락의 어빌리티를 맥락의 대상에게 쓰라"는 일만 한다. 대상과 어빌리티를 트리에 직접 적지 않고 맥락에서 받으니 실행 트리가 범용이 된다. "사거리까지 이동해서 친다" 트리 하나를 펀치·찌르기·물기에 모두 재사용할 수 있다. 근접 거리에서만 일어나면 된다.

선택된 snippet의 실행 트리는 Execute Ability가 발동할 때까지 매 AI 업데이트마다 실행된다. 그 동안에도 BDS는 평가를 계속한다. 그래야 상황이 바뀌었을 때 이미 최선이 아니게 된 snippet을 기계적으로 끝까지 하지 않는다. 여기서 둘 사이의 계약이 생긴다. 실행 트리의 지시를 수행할 수 없게 만드는 조건은 평가 트리가 찾아내 막아야 한다. 실행 도중 대상이 죽으면 재평가가 무효해진 snippet을 유효한 것으로 바꿔 준다. 다만 Execute Ability가 발동한 뒤에는 어빌리티가 끝날 때까지 AI 업데이트를 멈춰도 된다. 어차피 수행할 수 없는 결정을 낭비하지 않기 위해서다.

Merrill과 정반대의 재평가 정책 Merrill의 Utility Selector는 자식이 Busy인 동안 utility를 다시 계산하지 않는다. BDS는 실행 중에도 매번 다시 평가하고, Execute Ability 이후에만 쉰다. 어느 쪽도 정답은 아니다. 캐시 쪽은 싸고 행동이 안정적이지만 상황 변화에 둔하다. 매번 평가하는 쪽은 반응이 빠르지만 진동을 막을 장치가 따로 필요하다(06장 관성).

3.7 이동과 패시브 행동: 점수 0과 tether

BDS는 원래 개별 행동용으로 설계되었지만, BioWare는 계속 이어지는 "패시브" 행동을 다스리는 데도 쓸모가 있다는 것을 알게 되었다.

  • 리더 따라가기: 할 일이 없는 동료는 플레이어를 따라간다. 평가 트리가 어떤 행동보다 낮은 상수(점수 관례에서 0)를 돌려주고, 실행 트리는 "follow the leader" 이동만 켜는 snippet으로 만들었다. 0보다 높은 유효 snippet이 하나도 없을 때 저절로 선택된다.
  • 변형된 따라가기: 전투 중이거나 플레이어가 특정 위치에 대기하라고 명령했을 때의 이동은 조건부로 기본 이동보다 높게 평가하되, 능동 행동에는 양보하게 했다.
  • tether: 지정 구역 안에 머물러야 하는 캐릭터에게는 구역 중심으로 돌아가게 하는 snippet을 붙였다. 이 snippet은 구역 밖에 있을 때만 어떤 전투 어빌리티보다도 높은 점수를 낸다. 그래서 대상에게 끌려 점점 멀어지는 일 없이 항상 교전을 끊고 돌아온다.

우리 Hamlet 엔진의 wander(weight 0.12)가 "리더 따라가기"에 해당하고, flee(rank 10)가 tether에 해당한다. 같은 문제를 BDS는 점수 대역으로, 우리 엔진은 rank로 풀었다.

3.8 모듈성: 플레이어가 장비를 바꿔도 AI가 따라온다

snippet 덕분에 BDS는 모듈식이다. 디버깅할 때 특정 행동의 평가 로직만 떼어 보거나, 평가 테이블로 캐릭터의 우선순위를 비교하기 쉽다. 더 중요한 것은 DA:I가 플레이어에게 동료의 장비와 어빌리티를 마음대로 바꾸게 한다는 점이다. snippet을 장비·어빌리티 자산에 묶고 일관된 점수 체계를 지키면, 무엇을 들려 주든 AI가 그것을 효과적으로 쓴다. 이 모듈성은 원래 동료 AI 때문에 필요했지만 적에게도 이득이었다. 한 적 유형을 위해 만든 행동을 애니메이션·VFX 같은 자산만 있으면 다른 팩션과 공유할 수 있었다. 대부분의 snippet은 자주 재사용되는 소수의 트리 자산으로 구현했고, 복잡한 행동 몇 개만 전용 로직이 필요했다.

4. UE5 StateTree의 utility 선택

Unreal Engine의 StateTree는 계층 상태 기계에 BT의 selector 개념을 섞은 범용 구조다. 부모 상태는 selection behavior에 따라 어느 자식 상태로 들어갈지 정한다. 기본 동작은 Try Enter, Try Select Children in Order(목록 순서), Try Select Children at Random(섞은 뒤 Enter Condition을 통과하는 첫째), Try Follow Transitions이고, UE 5.5부터 utility 기반 두 가지가 더해졌다.

selection behavior동작 (공식 문서)우리 엔진 대응
Try Select Children with Highest Utilityutility 점수가 가장 높은 자식 상태를 시도한다. 동점이면 목록의 첫 번째.UAI.select(c, {strategy:"best"}). 동점이면 배열 앞쪽(pool.find)
Try Select Children at Random Weighted by Utility각 상태의 utility로 랜덤 선택한다. 선택 확률은 정규화된 utility 점수.UAI.select(c, {strategy:"weighted"}). p = U / ΣU

점수는 Consideration이라는 새 노드 종류로 만든다. consideration은 상태를 점수 매길 때 고려할 한 측면이며 0~1로 정규화된 점수를 낸다. 여러 consideration은 연산자로 묶는다. AND는 두 입력 중 작은 값, OR는 큰 값을 내고, 들여쓰기로 연산 우선순위(괄호)를 정한다. 결합된 점수에는 상태의 Weight(기본 1)를 곱하는데, 문서는 이 Weight가 곱해진 최종 점수를 정규화하지 않는다고 명시한다.

Score(state) = combine_{AND=min, OR=max}(consideration₁ … consideration_n) × Weight

재평가 시점도 짚어 두자. selection behavior는 자식 상태를 고르는 순간에 적용된다. 이미 활성화된 상태는 다른 형제의 점수가 높아졌다고 저절로 바뀌지 않는다. 바뀌려면 transition(완료·실패·이벤트·조건)이 일어나 다시 선택해야 한다. 공식 selector 문서도 이 선택 단계만 설명한다. 그래서 "상황이 바뀌면 다시 고르라"는 동작이 필요하면 디자이너가 transition으로 명시해야 한다. 예를 들어 위협 이벤트가 오면 부모로 transition시키는 식이다. 실행 중에도 매번 다시 평가하는 DA:I BDS나 주기적으로 인터럽트를 검사하는 우리 엔진과는 철학이 다르다.

위젯 10-3: consideration 트리 빌더 (AND=min · OR=max · 들여쓰기)
Hamlet 주민의 "빵집 가기" 상태에 consideration을 조합한다. 행마다 연산자(AND/OR), 들여쓰기(◀ ▶), 값을 정한다. 이 위젯은 더 들여쓴 연속 행을 하나의 괄호 묶음으로 보고, 묶음 첫 행의 연산자로 바깥과 잇는다. 왼쪽부터 순서대로 계산한다. 실제 에디터에서는 표시되는 괄호식을 함께 확인하자. 아래에서 같은 값들을 우리 엔진의 곱셈·보정 곱으로 합친 결과와 비교하고, 형제 상태와 함께 두 selection behavior의 결과를 본다.
프리셋:

결합 방식 비교 (같은 consideration 값)

형제 상태와 선택

min 결합 vs 보정 곱: 무엇이 다른가

AND=min은 "가장 약한 고리"만 본다. consideration이 몇 개든 점수가 깎이지 않아, 04장에서 본 곱셈의 희석 문제(n이 늘수록 점수 하락)가 아예 없다. 보정 곱이 필요 없는 이유다. 대신 최솟값이 아닌 consideration은 점수에 전혀 기여하지 않는다. 배고픔 0.9·거리 0.6과 배고픔 0.6·거리 0.6이 똑같이 0.6이다. 곱셈 계열은 모든 요소가 점수를 조금씩 움직이므로 미세한 차이로 순위가 갈린다. 프리셋 "AND만"에서 최솟값이 아닌 슬라이더를 움직여 보자. min 결과는 그대로이고 곱 계열만 변한다.

OR는 우리 엔진에 없는 표현이다. 우리 엔진에서 "지갑 여유 또는 외상 가능"을 표현하려면 행동을 둘로 나누거나 커스텀 입력 함수 안에서 Math.max를 써야 한다. 반대로 StateTree는 상태 하나에 OR를 쓸 수 있는 대신, 결과가 0~1이고 정규화 안 된 Weight만 곱해지므로 형제 사이에 우선 "부류"를 두려면 계층(부모 상태)을 하나 더 만들어야 한다. 우리 엔진의 rank에 해당하는 것이 StateTree에서는 트리 구조다.

5. 숙고와 반응의 분리 (Côté, 권·서)

5.1 Côté의 Action Selector

Carle Côté(GAP1 11장)는 하이브리드를 다른 각도에서 본다. 어떤 결정 모델을 쓰느냐보다 반응(reactivity)과 숙고(deliberation)를 하나의 모델로 합치지 말라는 것이다. 반응은 자극에 즉시 응답하는 일이다. 통증·질식·재채기 같은 비자발적 반응도 있고, 맥락을 해석하는 인지적 반응도 있다. 도서관의 큰 소리에는 놀라지만 공사장의 큰 소리에는 놀라지 않는 것이 인지적 반응이다. 숙고는 아는 것을 고려해 다음 행동을 정하는 일이다. 둘은 트리거가 다르고(반응 = 높은 우선순위의 인터럽트, 숙고 = 현재 행동이 끝나거나 무효해졌을 때) 목표도 다르다(반응 = 즉각적 변화, 숙고 = 오래 유지할 최선).

Côté의 예에서 Chase/Patrol/Combat/Flee FSM에 Hurt·Suffocate 같은 반응 상태를 넣으면, 숙고 상태는 언제든 끊길 수 있으므로 모든 숙고 상태에서 모든 반응 상태로 가는 전이가 필요해진다. 반응을 하나 추가하면 기존 숙고 상태마다 전이를 하나씩 새로 달아야 하고, 숙고 상태를 추가해도 마찬가지다. 해법은 두 모듈이 같은 자극을 받아 각자 행동을 내고, Action Selector가 그 사이를 스위치하는 구조다. 셀렉터는 숙고 모듈에 새 결정을 요청하거나 반응을 실행하려고 현재 숙고 행동을 취소하라는 신호를 보낸다. 모듈마다 서로 다른 결정 모델을 써도 된다. 숙고는 FSM, 반응은 단순 규칙이나 결정 트리로 해도 된다.

우리 엔진은 이미 이 구조를 축소한 형태로 갖고 있다. 06장에서 만든 World.tick은 할 일이 없을 때만 숙고(전체 결정)를 하고, 바쁠 때는 thinkEvery 틱마다 인터럽트만 검사한다.

        // 2) 결정 (06장, GAP1 11장): 숙고는 할 일이 끝났을 때만, 반응(인터럽트)은 주기적으로 검사
        const due = (this.tickCount + a.thinkOffset) % this.thinkEvery === 0;
        if (!a.current) this.think(a);
        else if (due) this.think(a, true);
      if (interruptOnly) {
        const curAct = this.reasoner.actions.find(x => x.id === a.current.action);
        if (c.rank <= curAct.rank) return;
      }

숙고와 반응이 같은 Reasoner를 공유하지만, 반응 경로는 "rank가 더 높은 후보"만 받아들인다. rank 10인 flee가 반응 모듈 역할이고, think(a, true)의 rank 비교가 Action Selector의 스위치 역할이다. Côté가 경고한 모든 숙고 상태 × 모든 반응 상태의 전이 폭발이 우리 엔진에서 생기지 않는 이유는 rank가 전이를 대신하기 때문이다. 다만 Côté가 요구한 세부 사항, 즉 비자발적 반응이 인지적 반응보다 우선하고, 동시에 일어난 비자발적 반응을 결합하는 것(질식 중 원거리 피격)까지 다루려면 반응 모듈을 따로 키워야 한다.

Côté가 지적한 또 하나의 함정: 진동 시야 시스템의 "위협 보임" 신호를 FSM 전이에 직접 연결하면, 추격 중 장애물 때문에 시야가 깜빡일 때마다 Chase↔Patrol이 몇 초 안에 여러 번 바뀐다. 애니메이션이 튀는 문제도 생긴다. 해법은 히스테리시스 같은 필터를 거친 "논리적 위협 인지"에 연결하는 것이다. 숙고에서는 반응성만큼이나 행동을 적절한 시간 동안 유지하는 것이 중요하다는 교훈이다.

5.2 권·서(2022)의 숙고형 행동트리

국내 연구로는 권·서(2022, 동의대)의 「효용이론과 행동 트리를 결합한 숙고형 행동트리」가 있다. 행동 트리에 노드를 추가해, 자식을 고를 때 하위 트리의 효용값을 평가하게 한 것이다. 접근 자체는 Merrill의 Utility Selector와 같은 계열이다. BT의 구조와 도구를 유지하면서 선택 지점에만 효용을 넣는다. 한국어로 된 정리를 원하면 함께 읽어 볼 만하다.

7. 하이브리드에서 자주 밟는 함정

① 서로 다른 스케일을 섞어 비교 BT 리프 하나는 0~1 utility를 내고 다른 리프는 BDS식 정수 점수를 내면, 정렬은 되지만 의미는 없다. 하이브리드에서는 한 selector 안의 형제들이 같은 스케일을 쓰도록 강제해야 한다. Merrill이 공통 단위를 먼저 강조하고, BioWare가 부류별 점수 로직 자산을 공유한 이유다.
② 캐시가 낡은 줄 모르고 디버깅 Utility Selector는 Busy 동안 utility를 다시 계산하지 않는다. 디버거에 찍힌 "지금의 utility"와 실제 실행 순서가 다를 수 있다. 디버그 뷰에는 live 값과 캐시 값을 둘 다 보여 주자(위젯 10-1의 "Combat 캐시").
③ 자식 max 전파가 숨기는 것 composite가 자식 max를 돌려주면, 그 서브트리에서 유효하지 않은 자식의 높은 utility가 부모를 끌어올릴 수 있다. 부모가 선택되어도 실제로는 낮은 자식이 실행된다. 그래서 Merrill은 평가/실행을 분리해 유효한 자식만 utility를 계산하게 했다.
④ 정규화 안 된 Weight가 부류를 흉내 낸다 StateTree에서 Weight 2를 주면 최종 점수가 1을 넘을 수 있다. 이것으로 "항상 우선"을 흉내 내다 보면 점수 의미가 흐려진다. 절대 우선이 필요하면 BDS의 대역 분리나 우리 엔진의 rank, StateTree라면 상위 상태로 구조적으로 분리하는 편이 명확하다.
⑤ 평가와 실행의 계약 누락 BDS의 규칙대로, 실행 트리가 해낼 수 없는 조건(대상 사망, 사거리 밖으로 영구 이탈)은 평가 트리가 막아야 한다. 이 계약이 없으면 최고점 snippet이 실행에서 매번 실패하는데도 다음 평가에서 또 1위가 되는 루프가 생긴다. 우리 엔진에서는 consideration의 스위치 커브(early-out)가 같은 역할을 한다.

핵심 요약

  • 하이브리드의 핵심은 효용을 어디에 꽂느냐다. BT의 노드 하나(Merrill), 최상위 선택 전체(DA:I BDS), 자식 상태 선택(StateTree), 숙고 모듈 내부(Côté)가 있다.
  • Utility Selector(Listing 10.2)는 첫 실행 때 자식 utility를 계산해 내림차순으로 정렬하고 순서대로 실행한다. Busy면 캐시를 유지하고, Done이나 전체 실패에서 비운다. composite는 자식 max로 utility를 전파하고, decorator(cube 등)로 변환한다.
  • DA:I BDS: 장비에 붙은 snippet이 등록되면 평가 트리가 점수를 가산하고, Target Selector가 대상을 고르며, Listing 31.1이 정렬 후 1위를 고른다. 실행 트리는 맥락으로 받은 어빌리티·대상을 쓰는 범용 트리다. 자동 정규화 대신 점수 관례 대역을 쓴다(10 / 20–40 / 25–45 / 50–70). 따라가기는 0점, tether는 최고점이다.
  • StateTree: consideration 0~1을 AND=min, OR=max, 들여쓰기 괄호로 묶고 Weight를 곱한다(정규화 안 함). Highest(동점이면 첫째) 또는 Random Weighted로 고르며, 선택은 transition 시점에 일어난다.
  • 정규화 0~1은 모든 행동이 겹치고, 점수 대역은 겹침과 절대 우선을 한 축에 담고, dual rank는 절대 우선을 별도 축으로 뺀다. 우리 엔진은 마지막 방식을 쓴다.
  • 반응과 숙고는 트리거와 목표가 다르다. 한 모델에 섞으면 전이가 폭발한다. 우리 엔진의 think(a, interruptOnly)와 rank가 Côté식 Action Selector의 축소판이다.

StateTree에서 consideration A=0.8, B=0.3, C=0.7을 A AND (B OR C)로 묶고 Weight 1.5를 주었다. 최종 점수는?
B OR C = max(0.3, 0.7) = 0.7, A AND 0.7 = min(0.8, 0.7) = 0.7, × 1.5 = 1.05. 문서에 따르면 Weight를 곱한 최종 점수는 정규화하지 않으므로 1을 넘을 수 있다.
Côté가 반응 상태(Hurt, Suffocate)를 숙고 FSM에 함께 넣지 말라고 한 핵심 이유는?
반응은 인터럽트, 숙고는 유지가 목적이라 전이 역학이 정반대다. 해법은 모듈을 나누고 Action Selector가 스위치하는 것이다. 우리 엔진은 rank와 interruptOnly로 이 전이를 대신한다.
다음 장으로 이 장에서는 Utility Selector의 캐시, BDS의 평가 테이블, StateTree의 consideration 트리처럼 서로 다른 구조로 결정을 만들었다. 그런데 NPC가 이상한 선택을 했을 때 "왜"를 어떻게 찾아낼까? 11장에서는 lastEval·trace·log로 결정을 기록하고, 진동과 점수 희석을 찾아 튜닝·밸런싱하는 방법을 다룬다.
