욕구 모델과 스마트 오브젝트

지금까지는 행동 하나하나에 consideration을 손으로 붙였다. 마을 시뮬레이션에서는 이 방식이 금방 한계에 부딪힌다. 오브젝트가 수십 개로 늘어나면 주민 AI가 오브젝트를 전부 알아야 하기 때문이다. 이 장에서는 주민에게 욕구를 주고, 지능의 상당 부분을 오브젝트 쪽으로 옮긴다. 오브젝트는 "나는 배고픔을 60만큼 채워 준다"고 광고하고, 주민은 그 광고를 자기 긴급도로 저울질한다.

학습 목표

  • 욕구값(0~100)이 시간에 따라 감소하는 모델과, 욕구값을 긴급도로 바꾸는 반응 커브의 역할을 설명한다.
  • 배고픔에 수식 곡선 대신 구간 선형(piecewise) 커브를 쓰는 이유를 시뮬레이션 수치로 확인한다.
  • 스마트 오브젝트·광고(advertisement) 구조가 왜 확장에 강한지, 주민 코드를 건드리지 않고 오브젝트를 추가해 본다.
  • UAI.adValue의 room = min(광고량, 100 − 현재값)이 한계효용 체감을 구현한다는 것과 음수 광고(부작용 비용)의 의미를 이해한다.
  • 성격(trait) 가중치와 오브젝트 수용량(capacity)이 마을 전체의 창발적 행동을 어떻게 만드는지 관찰한다.
엔진 부품 UAI.NEEDS UAI.NEED_DECAY UAI.NEED_CURVE UAI.OBJECT_TYPES UAI.adValue() World.addObject() agent.traits — 욕구가 줄고, 오브젝트가 광고하고, 주민이 긴급도로 광고를 저울질하는 Hamlet의 심장부.

1. 왜 욕구 모델인가: 행동 목록의 한계

04장 Consideration에서 만든 행동은 "빵집에서 먹기 = 배고픔 consideration × 거리 consideration"처럼 행동마다 입력과 커브를 직접 정했다. 행동이 대여섯 개일 때는 이게 가장 명확하다. 그런데 마을에 밭, 우물, 선술집, 광장 무대가 하나씩 생길 때마다 다음 일이 반복된다.

  • 주민 행동 목록에 "밭에서 일하기", "우물가에서 쉬기"를 새로 추가한다.
  • 각 행동에 맞는 consideration을 고르고 커브를 튜닝한다.
  • 새 행동이 기존 행동들과 점수 스케일이 맞는지 다시 밸런싱한다.

오브젝트 N개, 주민 종류 M개면 작업량이 N×M으로 늘어난다. 욕구 모델은 이 문제를 두 단계로 쪼갠다.

  1. 주민은 욕구만 안다. 배고픔·기력·재미·사교 네 개의 수치와, 각 수치가 얼마나 급한지(긴급도)만 계산한다.
  2. 오브젝트는 자기가 채워 주는 욕구만 안다. 빵집은 "배고픔 +60", 선술집은 "재미 +45, 사교 +40, 배고픔 +10, 기력 −10"이라고 스스로 광고한다.

둘 사이를 잇는 공식은 단 하나, UAI.adValue(agent, obj)다. 그래서 오브젝트를 추가할 때 주민 코드는 바뀌지 않는다. 오브젝트 하나가 광고 표 한 줄을 들고 들어오면 끝이다.

The Sims와 스마트 오브젝트 Will Wright가 만든 The Sims(Maxis)는 이 방식으로 널리 알려져 있다. 행동 지식을 캐릭터가 아니라 오브젝트가 갖고 있어서, 오브젝트가 "나를 쓰면 무엇이 채워지는지"를 알리고 그 상호작용에 필요한 행동과 애니메이션까지 함께 제공한다. 새 오브젝트(확장팩 가구 등)를 넣어도 심(Sim)의 AI를 고칠 필요가 없는 이유다. Graham은 Game AI Pro 9장에서 The Sims의 심이 "각 오브젝트의 개별 행동을 점수화"하되 가장 급한 욕구(motive)를 채우는 행동만 본다고 설명한다. 이 장의 Hamlet은 그 구조를 교육용으로 단순화한 것이며, 실제 The Sims의 수치를 재현한 것은 아니다.

욕구 기반 행동은 The Sims만의 이야기가 아니다. Dill은 Zoo Tycoon 2에서 동물의 욕구 행동(배고픔·오락·화장실 등)을 모두 rank 0에 두고 weight만 상황에 따라 바꿨다고 설명한다(05장 Dual Utility). Hamlet의 "이용하기" 행동이 rank 0인 것도 같은 설계다.

2. 욕구값과 시간에 따른 감소

Hamlet에서 욕구는 0(완전 결핍) ~ 100(완전 충족)이다. "배고픔 80"은 배가 꽤 부르다는 뜻이다. 이름과 방향이 헷갈리기 쉬운데, The Sims의 Hunger 수치도 "얼마나 배부른가"를 재는 값이라 낮을수록 배고프다(Graham). 엔진은 이 관례를 따른다.

  UAI.NEEDS = ["hunger", "energy", "fun", "social"];
  UAI.NEED_LABEL = { hunger: "배고픔", energy: "기력", fun: "재미", social: "사교" };
  UAI.NEED_DECAY = { hunger: 0.2, energy: 0.11, fun: 0.16, social: 0.12 }; // 게임 분당 감소량

감소 속도를 시간으로 환산하면 설계 의도가 보인다.

욕구분당 감소100 → 0까지의도
배고픔0.20500분 ≈ 8.3시간하루 두세 번 식사
재미0.16625분 ≈ 10.4시간오후~저녁 여가 수요
사교0.12≈ 13.9시간하루 한두 번 만남
기력0.11≈ 15.2시간하루 한 번 긴 잠

감소는 09장 World.tick의 첫 단계에서 일어난다. 모든 주민의 모든 욕구가 tick마다 깎이고, 기력만 밤에 더 빨리 준다.

        // 1) 욕구 감소
        for (const n of UAI.NEEDS) a.needs[n] = Math.max(0, a.needs[n] - UAI.NEED_DECAY[n] * this.dt * (n === "energy" && this.hour() >= 22 ? 1.8 : 1));

밤 가속(×1.8)은 "밤이 되면 졸리다"를 욕구값 하나로 표현한 장치다. 시간대를 별도 consideration으로 넣지 않아도, 기력이 빨리 떨어지면 긴급도가 올라가고 결국 집으로 향한다. 상태를 바꿔서 행동을 유도하는 방식은 행동 점수에 직접 손을 대는 것보다 시스템 전체에 일관되게 작용한다.

코드 읽기: "밤"은 몇 시부터 몇 시까지인가? hour()는 (time / 60 + 6) % 24로 06:00에서 시작해 0~24를 돈다. 조건 hour() >= 22는 22:00~23:59에만 참이고, 자정이 지나 hour()가 0으로 돌아가면 다시 거짓이 된다. 이름만 보면 "밤 내내"처럼 읽히지만 실제로는 두 시간짜리 창이다. 의도대로 새벽까지 적용하려면 h >= 22 || h < 6처럼 써야 한다. 이런 시간 경계 버그는 시뮬레이션에서 흔하고, 증상(새벽에 주민이 덜 졸려함)만 보고 원인을 찾기는 어렵다. 11장의 trace 도구가 필요한 이유다.

3. 욕구 → 긴급도 커브 (배고픔은 왜 piecewise인가)

욕구값을 그대로 점수로 쓰지는 않는다. "배고픔 50"과 "배고픔 10"의 차이는 "90"과 "50"의 차이보다 훨씬 크게 느껴져야 한다. 그래서 욕구값을 0~1로 정규화한 뒤 03장 반응 커브로 긴급도(urgency)로 바꾼다. 네 커브 모두 invert되어 있거나 감소형이라, 욕구가 낮을수록 긴급도가 높다.

  UAI.NEED_CURVE = {
    hunger: { type: "piecewise", points: [[0, 1], [0.3, 0.85], [0.6, 0.25], [0.85, 0.02], [1, 0]] },
    energy: { type: "poly", m: 1, k: 2.5, invert: true },
    fun: { type: "poly", m: 1, k: 1.5, invert: true },
    social: { type: "poly", m: 1, k: 2, invert: true },
  };

기력·재미·사교는 (1−x)^k 꼴의 다항 커브다. k가 클수록 "어느 정도 차 있을 때는 거의 신경 쓰지 않다가 바닥 근처에서 급해지는" 모양이 된다. 기력(k=2.5)이 가장 늦게 급해지고, 재미(k=1.5)는 조금만 줄어도 슬슬 신경 쓰인다.

배고픔만 손으로 찍은 점(piecewise)인 이유

Graham은 The Sims의 배고픔을 예로 든다. 배고픔을 회전된 2차 곡선 같은 수식으로 모델링하면 배고픔이 낮을 때 강하게 먹고 싶어지는 건 맞지만, 배가 거의 찼을 때도 먹을 확률이 작게나마 남는다. 그 확률이 아무리 작아도 시뮬레이션이 길어지면 결국 언젠가 선택된다. 디자이너가 원하는 건 "일정 수준까지는 배고픔을 완전히 무시하다가, 조금 배고파지고, 그러다 갑자기 몹시 배고파지는" 모양인데, 단순한 수식 하나로는 그 모양을 원하는 대로 만들고 튜닝하기 어렵다. 그래서 2D 점을 손으로 찍고 사이를 선형 보간하는 구간 선형 커브를 쓴다. Graham은 이것이 "정확히 The Sims가 쓰는 방식"이라고 쓴다.

엔진의 점을 읽어 보면 세 구간이 보인다.

  • x 0.85~1 (배부름): 긴급도 0.02 → 0. 사실상 무시.
  • x 0.6~0.85 (출출함): 0.25 → 0.02. 다른 할 일이 없으면 먹는다.
  • x 0~0.6 (배고픔~굶주림): 0.25에서 0.85, 1로 가파르게 오른다. 이 구간에서는 거의 항상 이긴다.

"정말 그런가?"는 10절 실험에서 시뮬레이션으로 확인한다. 미리 말하면, 엔진 기본 설정(시드 20개)에서 배고픔 70 이상일 때 내린 식사 결정은 piecewise에서 0건, 선형 커브로 바꾸면 816건 중 226건(28%)이었다.

단, piecewise가 모든 수식 곡선보다 "덜 먹게" 만드는 것은 아니다. 핵심은 통제력이다. (1−x)² 같은 수식은 k 하나로 곡선 전체가 함께 움직여서 "0.85 위는 무시, 0.6~0.85는 적당히, 0.3 아래는 급격히"처럼 구간마다 다른 요구를 독립적으로 맞출 수 없다. piecewise는 점 하나를 옮겨 한 구간만 고친다.

4. 스마트 오브젝트와 광고

이제 오브젝트 쪽을 보자. Hamlet의 일곱 오브젝트 타입은 각자 광고표(ads), 이용 시간(duration, 분), 동시 수용량(capacity)을 갖는다.

  UAI.OBJECT_TYPES = {
    bakery: { label: "빵집", icon: "🍞", ads: { hunger: 60 }, duration: 20, capacity: 2 },
    farm: { label: "밭", icon: "🌾", ads: { hunger: 25, fun: -5 }, duration: 25, capacity: 3 },
    house: { label: "집", icon: "🏠", ads: { energy: 80 }, duration: 60, capacity: 2 },
    bench: { label: "벤치", icon: "🪑", ads: { energy: 20, social: 10 }, duration: 15, capacity: 2 },
    tavern: { label: "선술집", icon: "🍺", ads: { fun: 45, social: 40, hunger: 10, energy: -10 }, duration: 30, capacity: 4 },
    well: { label: "우물", icon: "⛲", ads: { social: 20, fun: 5 }, duration: 10, capacity: 3 },
    stage: { label: "광장 무대", icon: "🎭", ads: { fun: 60 }, duration: 25, capacity: 5 },
  };

광고는 약속이기도 하다. 주민이 오브젝트를 실제로 이용하면 엔진은 광고량을 이용 시간에 고르게 나눠 욕구에 더한다. 빵집은 20분 동안 분당 3씩, 합계 60을 채워 준다. 광고와 실제 효과가 같은 숫자에서 나오므로 "광고는 60인데 실제로는 10만 채워 주는" 거짓 광고가 생길 수 없다.

        for (const n in o.ads) a.needs[n] = Math.min(100, Math.max(0, a.needs[n] + (o.ads[n] / o.duration) * world.dt));

광고 가치 공식

주민 a가 오브젝트 o의 광고를 들었을 때의 가치는 욕구별 항의 합이다.

adValue(a, o) = clamp₀₁( Σₙ room(n)/100 × urgencyₙ(needₙ/100) × traitₙ )
  UAI.adValue = function (agent, obj) {
    let v = 0;
    for (const n in obj.ads) {
      const urgency = UAI.curve(UAI.NEED_CURVE[n])(agent.needs[n] / 100);
      const room = Math.min(obj.ads[n], 100 - agent.needs[n]); // 한계효용: 이미 찬 만큼은 의미 없음
      v += (Math.max(room, Math.min(0, obj.ads[n])) / 100) * urgency * (agent.traits[n] || 1);
    }
    return clamp01(v);
  };

세 요소가 곱해진다는 점이 중요하다. 광고량(오브젝트가 결정), 긴급도(주민 상태가 결정), 성격(주민 개성이 결정). 하나라도 0이면 그 욕구 항은 사라진다. 아리(배고픔 25)에게 빵집은 0.60 × 0.875 = 0.525, 기력이 70이라 집은 0.30 × 0.049 ≈ 0.015에 그친다.

adValue는 행동의 최종 점수가 아니라 consideration 하나다. Hamlet의 "이용하기" 행동은 오브젝트마다 대상(target)을 하나씩 만들고(08장), 광고 가치에 거리와 혼잡을 곱해 최종 점수를 낸다.

      targets: ({ world }) => world.objects.filter(o => o.users < o.capacity || false),
      considerations: [
        // 광고된 욕구 충족량 × 그 욕구의 긴급도 합 → 0~1 (07장)
        { name: "광고 가치", input: ({ agent, target }) => UAI.adValue(agent, target), lo: 0, hi: 1, curve: "선형 증가" },
        // 거리: 가까울수록 좋다. 너무 멀면 0 근처 (08장)
        { name: "거리", input: ({ agent, target }) => Math.abs(agent.x - target.x) + Math.abs(agent.y - target.y), lo: 0, hi: 30, curve: { type: "poly", m: -1, k: 2, b: 1 } },
        // 이미 사용 중이면 붐빔 감점
        { name: "혼잡", input: ({ target }) => target.users / target.capacity, lo: 0, hi: 1, curve: { type: "linear", m: -0.7, b: 1 } },
      ],

세 consideration은 04장 compensated 곱으로 결합되고, 행동 선택은 05장 dual 전략(최고 rank 안에서 최고점의 85% 이상만 남겨 가중 랜덤)을 쓴다.

왜 이렇게 설계했나: 지식의 위치 "무엇이 무엇을 채우는가"는 오브젝트에 대한 지식이고, "지금 무엇이 급한가"는 주민에 대한 지식이다. 각 지식을 그 주인에게 두면 오브젝트 추가 = 데이터 한 줄, 주민 성격 추가 = 가중치 네 개가 된다. 디자이너는 코드 없이 광고표만 고쳐 밸런싱할 수 있다. 03장에서 말한 "데이터 주도" 원칙이 오브젝트 단위로 확장된 셈이다.

5. 한계효용: room과 음수 광고

02장 효용과 기대 효용에서 같은 양의 재화라도 이미 많이 가진 사람에게는 가치가 작다는 한계효용 체감을 봤다. adValue의 한 줄이 그것을 그대로 구현한다.

room = min(광고량, 100 − 현재값)

배고픔 70인 주민에게 빵집의 "+60"은 실제로 30만 의미가 있다. 나머지 30은 욕구가 100에 막혀 버려진다(엔진의 실행 코드도 Math.min(100, …)으로 넘친 양을 버린다). 광고 가치를 매길 때 이 30을 빼 주지 않으면, 주민은 배가 꽤 찼는데도 "빵집은 60짜리"라고 착각하고 큰 오브젝트를 과대평가한다. 작은 간식(+15)과 잔치(+60)를 비교할 때 이 차이가 결정적이다.

계산기: room과 버려지는 광고
현재 욕구값과 광고량을 바꿔 보자. 파란 칸이 실제로 채워지는 양(room), 빨간 점선 칸이 넘쳐서 버려지는 양이다. 오른쪽 숫자는 이 욕구 항 하나의 adValue 기여(배고픔 커브, 성격 1 기준)다.
70 60

음수 광고 = 부작용 비용

선술집은 재미와 사교를 크게 채우지만 기력을 10 깎는다(energy: -10). 밭은 배를 채워 주지만 재미가 5 준다. 음수 광고에는 room 제한이 없다: 코드의 Math.max(room, Math.min(0, obj.ads[n]))는 광고량이 음수면 room 대신 광고량 자체를 쓴다. 그리고 이 비용도 긴급도로 곱해진다.

  • 기력 100인 주민에게 선술집의 기력 −10은 긴급도 0이라 비용 0이다. 쌩쌩하면 술 한잔쯤 상관없다.
  • 기력 10인 주민에게는 긴급도가 높아 −10이 크게 깎인다. 같은 주민(배고픔 90·재미 20·사교 30)으로 계산하면 선술집 가치가 기력 100일 때 0.52, 기력 10일 때 0.44다.

"비용은 그 자원이 아쉬울 때만 비싸다"는 직관을 별도 규칙 없이 같은 공식이 표현한다. 부작용은 또 하나의 연쇄를 만든다. 선술집에서 놀고 나온 주민은 기력이 더 빨리 바닥나 집으로 향하고, 그 사이 배고픔이 쌓여 빵집으로 간다. 오브젝트 하나의 광고표가 하루 일과의 순서를 바꾼다.

엔진의 단순화 두 가지 (1) 음수 광고는 room처럼 제한되지 않는다. 기력이 5 남은 주민에게도 −10 전체가 비용으로 계산되지만, 실제 실행에서는 Math.max(0, …)으로 5만 깎인다. 교육용으로는 무해하지만, 비용이 큰 오브젝트를 설계할 때는 평가와 실행이 어긋날 수 있다는 점을 기억하자. (2) 합계를 clamp01로 자르므로 비용이 이득보다 크면 0이 되고, 음수 점수끼리의 비교("덜 나쁜 오브젝트")는 사라진다. 점수 0은 04장 early-out에 걸려 그 대상을 아예 고려하지 않는다.

6. 피드백 루프 한 바퀴 따라가기

욕구 모델은 음의 피드백 루프다. 욕구가 줄면 그 욕구를 채우는 행동의 점수가 오르고, 행동이 욕구를 채우면 점수가 다시 내려간다. 온도 조절기처럼 주민의 상태를 일정 범위에 붙잡아 두는 구조다. 아래 스텝 애니메이션은 엔진 함수를 실제로 호출해 아리의 숫자를 한 단계씩 보여 준다.

7. 욕구 대시보드: 주민 한 명의 머릿속

이제 주민 한 명의 상태를 실시간으로 돌려 보자. 왼쪽 막대는 UAI.NEED_DECAY 속도로 줄어들고(22시 이후엔 기력 ×1.8), 오른쪽은 일곱 오브젝트의 UAI.adValue 순위다. 시간이 흐르면 순위가 계속 뒤바뀐다. "자동 이용"을 켜면 주민이 1위 오브젝트를 골라 엔진과 같은 방식(광고량 ÷ 이용 시간을 분마다 더함)으로 이용한다. 이 위젯은 거리·혼잡을 빼고 광고 가치 consideration 하나만 보여 준다.

  • 배고픔이 60 근처를 지나면 빵집이 갑자기 1위로 치고 올라온다. piecewise 커브의 꺾임점(0.6 → 0.25, 0.3 → 0.85)이 순위 변화로 그대로 보인다.
  • 배고픔 슬라이더를 90으로 올리면 빵집 가치가 거의 0이 된다. 긴급도가 0.02 이하이고 room도 10뿐이기 때문이다.
  • 선술집은 여러 욕구를 동시에 채우는 "만능 오브젝트"라 아무 욕구도 극단적이지 않을 때 자주 1위가 된다. 광고를 여러 욕구로 나누면 평범한 상태에서 강해지고, 한 욕구에 몰면 위기 상황에서 강해진다.
  • "22:00로 점프"를 누르면 기력 막대가 눈에 띄게 빨리 준다. 자정이 지나면 다시 원래 속도로 돌아온다(2절의 경계 문제).

8. 성격(traits): 같은 마을, 다른 사람

모든 주민이 같은 커브, 같은 광고표를 쓰면 같은 상황에서 같은 행동을 한다. 개성을 주는 가장 싼 방법은 욕구별 가중치다. World.addAgent는 traits를 기본값 1로 채우고, adValue는 각 욕구 항에 agent.traits[n]을 곱한다.

      const a = { id: "a" + this.agents.length, name, x, y, needs, traits: Object.assign({ hunger: 1, energy: 1, fun: 1, social: 1 }, traits),

사교 1.6인 주민은 같은 사교 결핍에서도 우물·선술집을 1.6배 강하게 원한다. 커브 모양은 그대로 두고 높이만 바꾸므로, "언제 급해지는가"는 모두 같고 "얼마나 원하는가"만 다르다. 커브 자체를 성격별로 바꾸는 것보다 튜닝 축이 적어 밸런싱이 쉽다.

실험: 성격만 다른 여섯 주민의 하루
UAI.makeHamlet으로 같은 마을을 두 번 만든다. 한 번은 모든 traits가 1, 한 번은 주민마다 다른 traits. 각각 하루(1,440 tick)씩 시드 5개로 돌려 하루 평균 욕구와 이용 횟수를 비교한다. 괄호 안은 "모두 기본값" 대비 변화이고, 성격이 겨냥한 욕구 칸은 강조했다.
실행 버튼을 누르세요.

실행해 보면 방향은 모두 의도대로다. 먹보(배고픔×2)는 하루 평균 배고픔이 약 4 높고, 잠꾸러기는 기력이 약 5 높고, 파티광은 재미가 약 6 높다. 외톨이(사교×0.3)는 선술집을 덜 가고 광장 무대를 더 간다. 부지런(기력×0.5)은 평균 기력이 4 낮은 채로 지낸다. 다만 효과의 크기는 수 포인트로 크지 않다. 모든 주민이 같은 감소 속도와 같은 커브 위에 있어서, 성격은 "언제 무엇을 먼저 채우는가"의 순서를 바꿀 뿐 욕구를 일정 범위에 붙잡는 피드백 루프 자체는 그대로이기 때문이다. 더 극적인 개성이 필요하면 감소 속도(대사량)나 커브 자체를 주민별로 바꾸는 축을 추가할 수 있지만, 튜닝할 숫자가 그만큼 늘어난다.

함정: trait 0은 0이 아니다 (agent.traits[n] || 1)은 trait가 0이면 0 || 1 = 1이 된다. "이 주민은 재미에 전혀 관심 없음"을 0으로 표현하려 하면 기본값으로 되돌아가 버린다. JavaScript의 || 기본값 관용구가 0·빈 문자열을 "없음"으로 취급하기 때문이다. 엔진에서 0을 허용하려면 ?? 1을 써야 한다. 이 장의 위젯은 trait 슬라이더 최솟값을 0.2로 막아 두었다.

9. 오브젝트 광고 에디터: 엔진을 고치지 않고 마을 확장하기

스마트 오브젝트 구조의 진짜 가치는 확장에서 드러난다. 아래 에디터에서 새 오브젝트의 광고표·이용 시간·수용량을 정하고 지도를 클릭해 위치를 고른 뒤 "마을에 추가"를 누르자. 위젯은 uai.js를 한 줄도 고치지 않는다. UAI.makeHamlet()으로 만든 마을에 world.addObject()로 오브젝트를 넣고, 반환된 객체에 광고표를 덮어쓸 뿐이다.

const w = UAI.makeHamlet({ seed });
// OBJECT_TYPES에 없는 타입이면 addObject는 {id, type, x, y, users: 0}만 만든다 → 광고표를 덮어쓴다
Object.assign(w.addObject("custom", x, y), { label: "목욕탕", ads: { energy: 40, fun: 20 }, duration: 30, capacity: 3 });
오브젝트 광고 에디터
"하루 시뮬레이션"은 새 오브젝트가 없는 기준 마을과, 추가한 마을을 각각 시드 5개로 하루씩 돌린다. 회색 가는 막대가 기준 마을, 초록 막대가 새 마을의 이용 선택 횟수(하루 평균)다.

해 볼 만한 실험.

  • 목욕탕(기력 +40, 재미 +20): 집 이용이 크게 줄고 목욕탕이 그 자리를 차지한다. 기력과 재미를 함께 채우는 오브젝트가 "기력만 채우는" 집보다 평범한 상태에서 유리하기 때문이다.
  • 노점(배고픔 +35, 8분, 수용량 1): 빠르지만 좁다. 빵집 옆(6,5)에 두면 빵집 선택이 하루 31.8회에서 18.8회로 줄고 노점이 17.4회를 가져간다. 먼 구석(20,14)에 둬도 14.8회로 꽤 쓰인다. 주민이 산책으로 마을 곳곳을 돌아다니므로 거리 consideration이 생각보다 덜 결정적이다. 직관 대신 수치로 확인해야 하는 이유다.
  • 도서관(재미 +35, 사교 −5, 40분): 광장 무대(재미 +60)보다 약해서 거의 선택되지 않는다. 광고량이 기존 오브젝트에 지배당하면 그 오브젝트는 사실상 죽은 콘텐츠가 된다. 실제 게임에서 "아무도 안 쓰는 가구"가 생기는 전형적인 원인이다.

10. 실험: 배부른데 먹는 주민

3절의 주장을 직접 재 보자. 배고픔 커브만 바꿔 끼우고 Hamlet을 하루씩 돌린 뒤, 빵집·밭을 고른 순간의 배고픔 값을 기록한다. 그 값이 "배부름 기준" 이상이면 배부른데 먹기로 센다. 실험 동안만 UAI.NEED_CURVE.hunger를 교체하고 끝나면 원래대로 되돌린다(엔진 파일은 그대로).

욕구 곡선 비교 실험
세 커브를 같은 시드로 돌린다. 왼쪽 그래프는 커브 모양, 오른쪽은 빵집에 대한 adValue(= room/100 × 긴급도)다. 아래 히스토그램은 식사 결정 시점의 배고픔 분포이며, 빨간 영역이 "배부름" 구간이다.
선형 1−x2차 (1−x)²piecewise (엔진)
실행 버튼을 누르세요.

엔진 기본값(dual, 기준 70, 시드 20)으로 돌려 보면 선형은 816건 중 226건(28%)이 배부른 식사이고, 2차와 piecewise는 0건이다. 기준을 60으로 낮추면 piecewise만 274건이 나오는데, 이는 의도된 결과다. 0.6~0.85를 "다른 할 일이 없으면 먹는 출출함 구간"으로 찍어 두었기 때문이다. 두 가지 방어선이 겹쳐 있다는 점에 주목하자.

  1. 커브: piecewise는 0.85 위에서 긴급도를 0.02 이하로 누른다. 선형은 배고픔 80에서도 0.2를 준다.
  2. room: 배가 찰수록 room이 줄어 adValue가 한 번 더 깎인다. 오른쪽 그래프에서 모든 커브가 오른쪽 끝에서 0으로 수렴하는 이유다. room만으로도 상당 부분 막히지만 선형 커브에서는 충분하지 않다.

전략을 weighted로 바꾸면 세 커브 모두 배부른 식사가 생긴다(기준 70에서 선형 803 · 2차 314 · piecewise 426건). 순수 가중 랜덤은 점수가 아무리 작아도 0보다 크면 언젠가 뽑기 때문이다. 기준을 85, 90으로 올려 보면 piecewise와 2차는 수십 건 이하로 떨어지지만 선형은 여전히 수백 건(85에서 223건)이다. 출출함 구간을 넓게 둔 piecewise가 70~80대에서는 2차보다 오히려 더 먹는다는 점도 보인다. 커브는 "얼마나 덜 먹는가"보다 "어느 구간에서 먹게 할 것인가"를 정하는 도구다. Graham이 지적한 "작은 확률도 결국 선택된다"는 문제는 커브만이 아니라 선택 전략과 함께 풀어야 한다. dual 전략의 "최고점 대비 일정 비율 미만 제거"(05장)가 두 번째 방어선 역할을 한다.

11. 창발: 점심시간의 빵집

지금까지는 주민 한 명을 봤다. 여러 명이 같은 규칙을 따르면 아무도 명시하지 않은 패턴이 나타난다. 가장 단순한 예가 동시에 배고파지는 주민들이다. 모두가 빵집을 최고로 평가하지만 빵집 수용량은 2명뿐이다.

  • 빵집이 차면 targets 필터(o.users < o.capacity)가 빵집을 후보에서 아예 뺀다.
  • 먼저 도착한 사람이 자리를 차지하면 다른 사람에게 혼잡 consideration이 감점을 준다(이용자 1/2이면 커브 출력 0.65).
  • 빵집으로 걷다가 자리가 없음을 알게 된 주민은 행동이 취소되어(a.current = null) 다시 생각한다. 그때 2순위인 밭이 선택된다.

결과적으로 "빵집이 붐비면 밭으로 분산된다"는 행동이 나온다. 누구도 "빵집이 차면 밭에 가라"는 규칙을 쓰지 않았다. 광고·거리·혼잡 세 consideration과 수용량 데이터의 상호작용이 만든 것이다.

Hamlet 라이브: 점심 종을 울려라

일괄 실험에서는 수용량이 작을수록 밭 선택이 급격히 늘어난다(수용량 6에서 밭은 거의 쓰이지 않고, 1에서는 빵집과 비슷해진다). 같은 데이터를 보고 디자이너가 할 수 있는 판단은 여러 가지다. 빵집을 하나 더 짓거나, 수용량을 늘리거나, 밭의 광고를 올려 처음부터 분산시키거나. 어느 쪽이든 광고표와 수용량이라는 데이터로 해결되고, 주민 AI는 그대로다.

창발은 공짜가 아니다 같은 구조가 원치 않는 패턴도 만든다. 모든 주민의 배고픔이 같은 속도로 줄고 시작값이 비슷하면 식사 시간이 동기화되어 매번 빵집 앞이 붐빈다. Hamlet은 시작 욕구를 난수(40~89)로 주고 생각하는 tick을 주민마다 어긋나게(thinkOffset, 09장) 해서 동기화를 완화한다. 성격 가중치도 같은 효과를 낸다.

12. 트레이드오프와 함정

설계 선택얻는 것잃는 것 / 주의
지능을 오브젝트에 둠오브젝트 추가가 데이터 작업. 주민 코드 불변.오브젝트가 광고하지 않는 행동(수다, 산책, 도망)은 여전히 행동으로 따로 만들어야 한다. Hamlet도 chat·wander·flee를 별도로 둔다.
광고량 = 실제 효과거짓 광고가 없다. 밸런싱 숫자가 하나."맛있어 보이지만 실은 별로인" 오브젝트 같은 의도된 착각은 별도 필드가 필요하다.
욕구별 곱(광고 × 긴급도 × 성격)각 축을 독립적으로 튜닝.광고량이 큰 오브젝트가 모든 상황을 지배하기 쉽다. 죽은 콘텐츠(9절 도서관) 점검 필요.
room 한계효용배부를 때 큰 오브젝트 과대평가 방지.음수 광고에는 적용되지 않는다(5절).
배고픔 piecewise배부를 때 먹지 않음. 꺾임점을 손으로 튜닝.점이 많아지면 의도를 잃기 쉽다. 점마다 "왜 이 값인가"를 기록하자.
합을 clamp01다른 consideration과 같은 0~1 스케일.여러 욕구가 동시에 급하면 1에 포화되어 오브젝트 간 차이가 사라질 수 있다.
실제 게임에서 나타나는 문제
  • 욕구 하나가 모든 걸 잡아먹음: 감소 속도가 너무 빠른 욕구가 있으면 주민이 그 욕구만 채우러 다닌다. 표(2절)처럼 "100 → 0 시간"으로 환산해 하루 일과에 맞는지 검산하자.
  • 오브젝트 독점: 만능 오브젝트(선술집)가 너무 강하면 마을이 선술집 앞에만 모인다. 이용 횟수 통계(9절 에디터)를 정기적으로 확인하자.
  • 굶주림 직전의 산책: 광고 가치가 거리·혼잡에 곱해져 너무 작아지면 산책(weight 0.12)에 진다. Graham의 Sims 예처럼 아주 급한 욕구는 버킷(rank)으로 끌어올리는 방법을 고려하자(05장).

핵심 요약

  • 욕구는 0(결핍)~100(충족) 값이고 UAI.NEED_DECAY만큼 매 분 줄어든다. 기력은 hour() >= 22일 때 1.8배 빨리 준다(실제로는 22:00~23:59만).
  • 욕구값은 UAI.NEED_CURVE로 긴급도가 된다. 배고픔은 piecewise로 배부른 구간을 거의 0으로 눌러 "배부른데 먹기"를 막는다. 수식 곡선은 작은 확률을 남긴다(Graham).
  • 스마트 오브젝트는 자기가 채워 주는 욕구를 광고하고, 주민은 adValue = Σ room/100 × 긴급도 × 성격으로 저울질한다. 오브젝트 추가는 데이터 한 줄이다.
  • room = min(광고량, 100 − 현재값)이 한계효용 체감을 구현한다. 음수 광고는 부작용 비용이며 그 욕구가 급할 때만 비싸다.
  • 성격 가중치는 커브 모양은 두고 높이만 바꿔 개성을 만든다. traits[n] || 1 때문에 0은 1로 취급된다.
  • 수용량·혼잡·거리의 상호작용이 "빵집이 차면 밭으로" 같은 창발적 분산을 만든다.

확인 문제

Hamlet에 새 오브젝트 "목욕탕"을 추가하려면 최소한 무엇을 바꿔야 하는가?
스마트 오브젝트 구조에서는 "무엇이 무엇을 채우는가"를 오브젝트가 들고 온다. "이용하기" 행동의 targets가 world.objects 전체를 돌기 때문에 새 오브젝트는 자동으로 후보가 된다.
배고픔 70인 주민(성격 1)에게 빵집(배고픔 +60)의 adValue는? piecewise 커브에서 x=0.7의 긴급도는 약 0.158이다.
room = min(60, 100 − 70) = 30. 넘치는 30은 가치가 없으므로 30/100 × 0.158 ≈ 0.047. 한계효용 체감이 이 한 줄에 들어 있다.
선술집의 "기력 −10" 광고에 대한 설명으로 옳은 것은?
음수 광고는 Math.min(0, ads[n])로 그대로 쓰이고 긴급도가 곱해진다. 기력 100이면 긴급도 0이라 비용 0. room 제한은 양수 광고에만 걸린다(그래서 C는 틀렸다).
10절 실험에서 dual 전략 + piecewise는 배부른 식사가 0건이었지만 weighted 전략에서는 생겼다. 가장 정확한 이유는?
커브가 작은 값을 남기면, 선택 전략이 그 작은 값을 기회로 바꾼다. 커브와 선택 전략은 함께 설계해야 한다(05장).
"재미에 전혀 관심 없는 주민"을 만들려고 traits.fun = 0을 줬다. 엔진에서 실제로 일어나는 일은?
0 || 1은 1이다. 0을 유효한 값으로 쓰려면 ??(nullish coalescing)를 써야 한다. 작은 관용구가 디자이너의 의도를 조용히 무시하는 전형적인 사례다.
빵집 수용량을 6에서 1로 줄였더니 밭 이용이 크게 늘었다. 이 분산을 만든 메커니즘이 아닌 것은?
그런 규칙은 어디에도 없다. 필터·혼잡·재결정이라는 일반 규칙이 조합되어 분산이 "창발"했다.
this.hour() >= 22 조건(기력 감소 ×1.8)이 참인 시간대는?
hour()는 % 24로 자정에 0으로 돌아간다. 새벽까지 적용하려면 h >= 22 || h < 6이 필요하다.
다음 장으로 이 장에서 주민은 "빵집"이라는 오브젝트 타입 하나만 평가했다. 그런데 빵집이 두 곳이면? 가까운데 붐비는 빵집과 멀지만 한산한 빵집 중 어디로 갈까? 08장에서는 행동 하나를 여러 대상(target)과 짝지어 행동 × 대상 쌍을 평가하는 컨텍스트 구조를 다룬다.
