컨텍스트와 타깃 평가

07장까지의 주민은 "무엇을 할까"만 고민했다. 그런데 "빵집에 간다"와 "밭에 간다"는 같은 '먹기'여도 전혀 다른 선택이다. 이 장에서는 행동과 대상을 한 쌍으로 묶은 컨텍스트(decision context)를 평가 단위로 삼는다. 거리·방향 같은 공간 consideration을 설계하는 법, 행동 × 대상 × consideration 조합이 폭발하는 비용, 여러 주민이 한 대상에 몰리는 문제도 함께 다룬다.

학습 목표

  • 행동과 대상을 따로 고르면 왜 틀리는지 설명하고, (행동, 대상) 쌍 단위로 평가하는 구조를 만든다.
  • action.targets(ctx)가 Reasoner의 평가 루프에 어떻게 들어가는지 읽고, Dragon Age: Inquisition의 Target Selector 노드와 비교한다.
  • 거리 커브를 단조 감소로 할지 역 U자로 할지 정하고, 공간 utility field로 결과를 눈으로 확인한다.
  • 내적으로 방향 consideration을 만들고, 같은 입력에 다른 커브를 붙여 성격이 다른 행동을 만든다.
  • A×T×C 평가 비용을 추정하고 사전 필터, early-out, 평가 순서로 줄인다.
  • 여러 주민이 같은 대상을 고르는 문제를 혼잡 consideration, 예약(capacity), 주변 밀도 프록시로 다룬다.

1. "무엇을"과 "누구에게"는 분리할 수 없다

지금까지 행동의 점수는 "배고프니 먹는 게 좋다" 같은 행동 자체의 점수처럼 보였다. 하지만 실제로 실행되는 것은 언제나 무언가에 대한 행동이다. 주민은 그냥 '먹지' 않고 빵집에서 또는 밭에서 먹는다. 마법사는 그냥 'Immolate를 쓰지' 않고 특정 적에게 쓴다. 점수를 정하는 정보의 상당수, 곧 거리·혼잡·면역·방향은 행동이 아니라 대상에 붙어 있다.

그래서 평가 단위를 바꾼다. 행동 하나와 대상 하나를 묶은 쌍을 컨텍스트(decision context)라 부르고, 점수는 컨텍스트마다 매긴다. 대상이 없는 행동(산책, 도망치기)은 대상 자리에 null이 하나 들어간 컨텍스트로 취급한다.

컨텍스트 = (행동 a, 대상 t)　·　score(a, t) = combine( c₁(a,t), c₂(a,t), … ) × weight(a)

두 단계로 나눠 고르면 무엇이 틀리나

직관적인 구현은 두 단계다. ① 행동 점수로 "먹기"를 고르고, ② 먹을 곳 중 하나를 고른다. 문제는 ①에서 쓸 행동 점수가 이미 대상에 달려 있다는 점이다. 아래는 엔진 UAI.makeHamlet() 마을에서 아리가 집(21,13) 옆 (20,12)에 있고, 배고픔 25·기력 35·재미 70·사교 70일 때 Reasoner.evaluate()가 실제로 낸 값이다.

이용하기 @빵집 (4,3)0.5325칸0.310.309

대상을 보지 않고 행동부터 고르면 "가장 큰 광고 가치"인 빵집의 0.53 때문에 '먹기'가 이긴다. 그다음 "가까운 먹을 곳"을 고르면 밭(0.255)으로 간다. 두 단계 모두 그럴듯했는데 결과는 세 후보 중 꼴찌다. 컨텍스트 단위로 한 번에 평가하면 바로 옆 집에서 쉬는 쪽(0.336)이 이긴다. 행동의 가치는 대상이 정해져야 비로소 정해진다.

왜 이렇게 설계하나행동 점수를 "모든 대상 중 최고값"으로 미리 요약해 두면 두 단계 구조도 쓸 수 있다. 하지만 그 요약을 계산하려면 결국 모든 대상을 평가해야 한다. 그렇다면 처음부터 (행동, 대상) 쌍을 표의 행으로 두는 편이 단순하고, 디버그 표에서 "왜 저 대상인가"도 바로 보인다.

2. 엔진에서: action.targets와 컨텍스트 지도

uai.js에서 대상 열거는 행동 정의의 targets 함수 하나가 맡는다. Reasoner는 행동마다 이 함수를 불러 후보 목록을 얻고, 후보마다 ctx = { agent, world, target }를 만들어 consideration을 평가한다. targets가 없는 행동은 [null] 하나로 취급하므로 같은 루프를 그대로 탄다.

    evaluate(agent, world) {
      const rows = [];
      const now = world ? world.time : 0;
      for (const a of this.actions) {
        const targets = a.targets ? a.targets({ agent, world }) : [null];
        for (const target of targets) {
          const ctx = { agent, world, target };
          const parts = [];
          let alive = true;
          const cdLeft = a.cooldown && agent.lastUsed && agent.lastUsed[a.id] != null
            ? a.cooldown - (now - agent.lastUsed[a.id]) : 0;
          if (cdLeft > 0) alive = false;
          for (const c of a.considerations) {
            if (!alive) { parts.push({ name: c.name, raw: null, x: null, y: null, skipped: true }); continue; }
            const raw = c.input(ctx);
            const x = UAI.normalize(raw, c.lo, c.hi);
            const y = c.fn(x);
            parts.push({ name: c.name, raw, x, y });
            if (y <= 0) alive = false;
          }

Hamlet의 use(이용하기) 행동은 마을의 오브젝트를 대상으로 삼는다. consideration 세 개 중 광고 가치는 07장의 UAI.adValue이고, 나머지 둘은 대상에 따라 값이 달라지는 거리와 혼잡이다.

      id: "use", label: "이용하기", rank: 0,
      targets: ({ world }) => world.objects.filter(o => o.users < o.capacity || false),
      considerations: [
        // 광고된 욕구 충족량 × 그 욕구의 긴급도 합 → 0~1 (07장)
        { name: "광고 가치", input: ({ agent, target }) => UAI.adValue(agent, target), lo: 0, hi: 1, curve: "선형 증가" },
        // 거리: 가까울수록 좋다. 너무 멀면 0 근처 (08장)
        { name: "거리", input: ({ agent, target }) => Math.abs(agent.x - target.x) + Math.abs(agent.y - target.y), lo: 0, hi: 30, curve: { type: "poly", m: -1, k: 2, b: 1 } },
        // 이미 사용 중이면 붐빔 감점
        { name: "혼잡", input: ({ target }) => target.users / target.capacity, lo: 0, hi: 1, curve: { type: "linear", m: -0.7, b: 1 } },
      ],

눈여겨볼 점이 두 가지 있다. 첫째, 만석인 오브젝트는 targets 단계에서 아예 빠진다. 점수 0으로 떨어뜨리는 대신 후보에서 지우는 하드 필터다. 그래서 혼잡 consideration의 입력은 실제로는 (capacity−1)/capacity까지만 올라간다. 둘째, 거리는 격자 세계에 맞춰 맨해튼 거리 |dx|+|dy|이고, bookend 30칸 이상이면 1−x² 커브가 0이 되어 그 컨텍스트는 early-out된다.

컨텍스트 지도: 아리를 끌어 보자
아리(파란 원)를 드래그하면 (이용하기, 오브젝트) 컨텍스트마다 world.reasoner.evaluate()를 다시 돌린다. 선 굵기와 후광 크기가 점수이고, 파란 굵은 선이 전체 1위 컨텍스트다. 오브젝트를 클릭하면 사용자 수가 0 → … → 만석 순으로 바뀐다(혼잡·만석 필터 확인용). "다른 주민도 대상으로"를 켜면 보람·찬이 수다 떨기(chat)의 대상으로 나타난다(8절).
전체 1위이용하기 컨텍스트수다 떨기 컨텍스트점선 원 = 만석이라 후보에서 제외됨
해 볼 것① 아리를 빵집 쪽으로 끌면 빵집 선이 굵어지다가, 배고픔 슬라이더를 올리면(덜 배고프게) 다시 가늘어진다. 광고 가치와 거리가 곱으로 묶여 있기 때문이다. ② 빵집을 두 번 클릭해 만석(2/2)으로 만들면 빵집 컨텍스트가 표에서 사라진다. ③ 표의 도망치기 행은 첫 consideration "위협 존재"가 0이라 나머지가 "생략(early-out)"으로 표시된다.

3. Dragon Age: Inquisition의 Target Selector

BioWare의 Dragon Age: Inquisition(DA:I)은 같은 문제를 행동 트리 안에서 풀었다(Hanlon & Watts, Game AI Pro 3, 31장). DA:I에서 AI가 평가하는 단위는 어빌리티를 "특정 방식으로" 쓰는 behavior snippet이고, 각 snippet은 점수를 내는 evaluation tree를 가진다. 트리는 점수 0에서 출발해 scoring 노드를 지날 때마다 점수를 더한다. 저자들의 설명은 이렇다. 대부분의 어빌리티는 대상이 있어야 동작하고(그냥 "Immolate를 쓴다"가 아니라 특정 적에게 쓴다), 화염에 약한 적에게 쓰면 큰 피해를 주지만 화염 면역인 적에게 쓰면 마나만 버린다. 그래서 대상 선택이 평가 단계의 일부여야 하고, evaluation tree는 점수와 함께 대상도 돌려준다.

이를 위해 도입한 것이 Target Selector 노드다. 문헌에 실린 알고리즘은 다음과 같다.

  1. 평가 컨텍스트의 현재 점수를 "초기 점수"로 기록한다.
  2. iterator가 지정한 대상마다: (a) 점수를 초기 점수로 되돌리고, (b) "behavior target iterator" 슬롯에 그 대상을 넣고, (c) 자식 노드를 평가해서, (d) 자식이 true를 돌려주면 그 대상의 점수를 기록한다.
  3. 기록된 대상이 하나라도 있으면 최고점 대상을 Behavior Target으로 정하고, 점수를 그 대상의 점수로 맞춘 뒤 true를 돌려준다.
  4. 기록된 대상이 없으면 false를 돌려준다.

문헌의 예시 트리(그림 31.2)는 "나로부터 10m 이내의 적 각각을 대상으로 평가" → "화염 면역이 아닌가?" 필터 → +5 → "화염에 약한가?" 필터 → +5 이다. 아래 애니메이션은 이 트리를 적 넷에 돌린다. 적의 배치와 앞 노드에서 쌓인 초기 점수 20점(DA:I 점수 관례에서 Offensive가 20–40)은 설명을 위해 정한 가정이다.

4. 거리 커브의 형태와 공간 utility field

거리는 대상 평가에서 가장 흔한 consideration이다. Mike Lewis는 Guild Wars 2: Heart of Thorns의 consideration 설계를 정리하면서(Game AI Pro 3, 13장) 응답 커브를 고르는 체크리스트를 제시했다.

  1. 입력과 bookend: 무엇을 점수화하나? 어떤 입력값이 x=0이고 어떤 값이 x=1인가? (예: 0–100m를 0–1로, 최댓값 이상은 1)
  2. 증가인가 감소인가: 소매치기에게 대상의 재산은 증가 커브, 대상까지의 거리는 감소 커브.
  3. 단조성: 대개 단조 커브가 이해하기 쉽다. 특별한 행동이 필요할 때만 중간에 봉우리나 골짜기를 둔다.
  4. 끝점: 완벽한 입력이면 점수 1을 주는 것이 보통 가장 단순하다. 끝점에서 0으로 무효화할지, 우선순위만 낮출지 정한다.

3번의 대표적인 예외가 거리다. Lewis는 거리 consideration에 뒤집힌 U자 커브를 쓰면 적이 너무 가깝지도 멀지도 않을 때만 접근하게 만들어 "팔 길이만큼 거리를 유지"할 수 있다고 했다. 실제 Heart of Thorns의 돌진 공격(Charge Attack) DSE도 거리 consideration에 중거리에서 높은 특수 커브를 쓴다. 이미 공격 범위 안에 있는 대상에게 돌진 기술을 쓰는 것도, 돌진해도 닿지 않는 대상에게 쓰는 것도 말이 되지 않기 때문이다.

Hamlet에서는 광장 무대 구경이 이런 예다. 무대에 바짝 붙으면 목이 아프고, 너무 멀면 보이지 않는다. 아래 위젯은 공간 utility field, 곧 "주민이 이 칸에 있다면 점수가 몇인가"를 격자 전체에 칠한다. 칸마다 Reasoner를 실제로 돌린 결과다.

공간 utility field: 칸마다 점수를 칠한다
지도 위로 마우스를 움직이거나(터치는 탭) 칸을 가리키면 그 위치의 점수와 커브 위 위치가 표시된다. 진할수록 점수가 높다. 주황 선은 0.25 / 0.5 / 0.75 등고선이다. "엔진 use 전체" 모드는 칸마다 8개 오브젝트 컨텍스트 중 최고점을 칠하고, 1위 대상이 바뀌는 경계를 검은 선으로 그린다.
지도를 가리켜 보자.

몇 가지가 눈에 띈다. 등고선이 원이 아니라 마름모다. 엔진이 맨해튼 거리를 쓰기 때문이며, 유클리드 거리였다면 원이 된다. 거리 지표를 무엇으로 정하느냐가 "주민이 어디까지를 가깝다고 느끼는가"의 모양을 정한다. 역 U자 커브를 고르면 무대 둘레에 도넛 모양 띠가 생긴다. 이 띠 위의 주민은 무대로 다가가지 않고 그 자리에서 구경하는 것이 최선이다. 이것이 "적정 거리 유지"가 공간에서 나타나는 모습이다.

"엔진 use 전체" 모드에서 1위 대상의 경계선은 일종의 보로노이 영역이다. 다만 순수한 거리 영역이 아니라 욕구에 따라 경계가 움직인다. 배고픈 주민에게는 빵집의 영역이 지도 대부분을 덮는다. 주민의 욕구가 변하면 이 영역도 매 순간 다시 그려지고, 그것이 마을의 동선이 된다.

함정: 끝점이 0인 감소 커브엔진의 거리 커브 1−x²는 bookend(30칸)에서 정확히 0이다. 30칸 너머의 대상은 자격이 박탈되어 early-out된다. 계산을 아끼는 데는 좋지만 "멀어도 다른 대안이 없으면 간다"는 행동은 불가능해진다. 넓은 맵에서 주민이 굶어 죽는 버그가 이렇게 생긴다. 끝점을 0으로 둘지 작은 양수로 둘지는 Lewis 체크리스트 4번의 질문이다.

5. 방향 consideration: 내적 하나로 옆·뒤 공격

Heart of Thorns의 일부 캐릭터는 대상이 등을 돌렸을 때 주로 공격한다. 이 측면/후방 공격(Side and Rear Attacks) DSE의 두 번째 consideration은 대상의 정규화된 facing 벡터와, 대상에서 AI로 향하는 정규화 벡터의 내적을 입력으로 쓴다. 내적이 1에 가까울수록 대상이 AI를 정면으로 보고 있다는 뜻이다. 그래서 응답 커브는 내적이 1에 다가갈수록 줄어들고, 결과적으로 대상이 옆(수직)이나 반대쪽을 보고 있을수록 점수가 높다(Lewis, Game AI Pro 3 13장).

d = f̂target · normalize(pAI − ptarget) ∈ [−1, 1]　→　x = normalize(d, −1, 1) = (d+1)/2　→　y = curve(x)

내적은 bookend [−1, 1]로 정규화하면 일반 consideration과 똑같이 다룰 수 있다. 같은 입력에 증가 커브를 붙이면 정반대 성격이 된다. Hamlet 주민이 말을 걸 때는 상대가 자기를 보고 있을수록 좋다. 같은 Heart of Thorns DSE 안에도 방향 검사가 하나 더 있다. 이번에는 AI 자신의 facing과 AI→대상 벡터를 비교해서, AI가 대상에게서 고개를 돌릴수록 점수가 0으로 떨어진다(시야 콘 안의 대상 우선). 돌진 공격에서도 대상이 대체로 AI 앞에 있을 때를 선호하게 해서 애니메이션이 휙 돌아가거나 방향이 오락가락하는 것을 막았다.

방향 consideration 실험대
가운데 원이 대상, 대상에서 뻗은 파란 화살표 끝의 손잡이를 돌려 대상이 바라보는 방향을 바꾼다. 초록 원(AI)을 끌어 위치를 바꾼다. 배경은 "AI가 그 칸에 있다면" 받을 점수의 field다.

field를 보면 "뒤·옆 선호" 커브는 대상의 시선 방향에 좁은 그늘(낮은 점수)을 만들고 나머지를 거의 1로 둔다. 1−x⁴ 커브는 x가 0.5(수직)일 때 0.94, 0.75(내적 0.5)일 때 0.68, 1(정면)일 때 0이다. 입력과 커브를 분리해 두었기 때문에 커브만 바꿔서 "등 뒤를 노리는 암살자"와 "눈을 맞추고 말을 거는 이웃"을 같은 입력으로 만들 수 있다. Heart of Thorns 팀이 100개가 넘는 사전 정의 패턴을 만들어 새 생물을 몇 분 만에 조립했다고 한 것도 이런 재사용 덕분이다.

하드코딩하지 않은 스위치의 가치이 측면/후방 공격 DSE에는 거의 모든 이동 DSE에 들어가는 "속박 상태면 금지" 스위치가 없다. 제자리에서 칼을 휘두르는 기술이라 묶여 있어도 쓸 수 있기 때문이다. 스위치를 엔진에 박아 넣었다면 이 예외를 위해 "하드코딩을 우회하는 하드코딩"이 필요했을 것이다. Heart of Thorns는 새 DSE에 흔한 스위치를 미리 채워 두고, 필요 없으면 빼는 방식을 택했다.

6. 조합 폭발: A × T × C

컨텍스트 평가의 대가는 비용이다. 에이전트 한 명이 한 번 생각할 때 consideration 계산 횟수의 상한은 다음과 같다.

비용 ≤ Σa |targets(a)| × |considerations(a)|　≈　A × T × C　　(N명이 초당 f번 생각하면 × N × f)

Hamlet은 작다. 행동 4개, 대상 최대 8개, consideration 3개 정도다. 그런데 주민 300명이 오브젝트 200개 중에서 고른다면 한 번 생각할 때마다 수만 번, 마을 전체로는 수백만 번의 계산이 된다. 게다가 시야(LOS) 레이캐스트처럼 비싼 consideration이 끼면 단가 자체가 수십 배 뛴다. 줄이는 방법은 크게 네 가지다.

  1. 후보 대상 사전 필터: 반경 쿼리로 T를 줄인다. 반경을 거리 consideration의 bookend와 같게 잡으면 어차피 0점이 될 대상만 빼는 것이라 결과가 바뀌지 않는다.
  2. early-out: consideration 하나가 0이면 나머지를 계산하지 않는다. 곱셈 결합에서는 하나가 0이면 전체가 0이기 때문에 가능하다(Lewis: 이 특성 덕분에 "절대 쓰면 안 되는 때"를 쉽게 표현하고, 평가 자체도 최적화할 수 있다).
  3. 싼 것 먼저, 비싼 것은 맨 끝: early-out이 있으니 순서가 비용을 바꾼다. Heart of Thorns의 측면/후방 공격 DSE는 꽤 비싼 LOS 레이캐스트를 일부러 맨 마지막에 둔다. Lewis는 이런 최적화가 Heart of Thorns AI가 충분히 빠르게 동작한 이유의 큰 부분이라고 했다. 돌진 공격에서는 비용 때문에 내비메시 경로 검사까지는 하지 않고 LOS만 봤다. 모든 대상에 대해 항상 경로를 계산하기엔 너무 비쌌고, 차이가 눈에 띄는 경우는 드물었기 때문이다.
  4. 평가 주기 분산: 모두가 매 tick 생각할 필요는 없다. 언제, 누가, 얼마나 자주 생각할지는 09장 엔진 아키텍처에서 다룬다.
평가 비용 측정기 (엔진 실측)
64×64 격자에 벽을 뿌리고 주민 N명, 오브젝트 T개를 시드 고정으로 뿌리고 모든 주민에 대해 Reasoner.evaluate()를 한 번씩 실제로 돌린다. consideration은 엔진 use의 세 개에 Bresenham 레이캐스트 LOS 스위치를 더한 4개다. consideration 호출을 세어 비용을 계산한다(싼 consideration 1단위, LOS는 지나간 칸 수만큼). 비교 기준은 "전체 대상 · LOS 먼저"다. 선택 전략은 결과 비교를 위해 best로 고정했다.

두 최적화를 켜고 끄면서 "결정 일치"를 확인해 보자. 반경 필터의 반경이 거리 bookend와 같고 consideration 순서는 곱의 값을 바꾸지 않으므로, 모든 주민의 선택이 기준과 똑같다. 그러면서 비용은 크게 줄어든다(N=100, T=80, 벽 3%에서 172,813 → 34,366단위). 반경을 bookend보다 작게 잡으면 그때부터는 결과가 바뀌는 근사가 된다. 그때는 "빨라졌다"가 아니라 "행동이 바뀌었다"로 다뤄야 한다.

이번에는 반경 필터를 켠 채 벽 밀도를 12% 이상으로 올리고 "LOS를 맨 끝에"를 꺼 보자. 오히려 LOS를 앞에 둘 때 더 싸진다(벽 12%: 23,729 → 20,024단위). 반경 필터가 거리 0점짜리를 이미 걸러 냈으므로 남은 싼 consideration은 거의 0을 내지 않는다. 반면 벽이 많으면 LOS 통과율이 30% 아래로 떨어져 LOS 자체가 가장 강한 필터가 된다. "싼 것 먼저"의 정확한 의미는 0을 낼 확률 대비 비용이 낮은 것 먼저다. Lewis의 배치가 맞는 것은 앞쪽의 싼 consideration이 실제로 후보를 많이 떨어뜨릴 때다. 평가 순서는 감으로 정하지 말고 이런 계측으로 정해야 한다.

반경 쿼리도 공짜는 아니다위 측정기의 반경 필터는 오브젝트 배열을 한 번 훑는 단순 구현이라 필터 자체에 O(T) 비교가 든다. 단가가 consideration보다 훨씬 싸서 이득이지만, 대상이 수천 개라면 격자 버킷이나 공간 해시로 후보를 꺼내야 한다. 이런 공간 인덱스도 09장의 엔진 구조에서 다룬다.

7. 모두가 같은 대상을 고를 때

컨텍스트 평가는 에이전트마다 따로 이루어진다. 비슷한 상태의 주민 여섯이 같은 순간에 생각하면 여섯 모두 같은 최고점 대상을 고른다. 아침 6시에 모두 배가 고프면 모두 빵집으로 뛴다. 빵집의 capacity는 2다. 넷은 헛걸음을 하고 밭으로 다시 걸어간다. 개별적으로는 합리적인 선택이 모이면 비합리적인 마을이 된다.

엔진에는 이미 혼잡 consideration(users / capacity)이 있는데 왜 이런 일이 생길까? users는 주민이 도착해서 사용을 시작할 때 올라가기 때문이다. 같은 tick에 결정하는 주민들은 모두 users = 0을 본다. 정보가 행동보다 늦게 갱신되는 것이다. 해결책은 결정 시점에 자리를 잡아 두는 예약(reservation)이다. 결정하는 순간 대상의 점유 수에 자기를 더하면, 다음 주민은 그 결정을 반영한 혼잡도와 만석 필터를 본다.

예약은 엔진에 없는 기능이라 이 장 안에 교육용 변형으로 두었다. use의 targets와 혼잡 입력이 users + reserved를 보고(자기 예약은 뺀다), 도착하면 예약을 실제 사용으로 바꾸며, 다른 행동으로 갈아타면 예약을 돌려준다.

// 08장 변형: 점유 = 사용 중 + 예약 (자기 예약은 제외)
const occ = (agent, o) => o.users + (o.reserved || 0)
  - (agent.current && agent.current.target === o && agent.current.reserved ? 1 : 0);
use.targets = ({ agent, world }) => world.objects.filter(o => occ(agent, o) < o.capacity);
use.considerations[2] = { name: "혼잡", input: ({ agent, target }) => occ(agent, target) / target.capacity,
                          lo: 0, hi: 1, curve: { type: "linear", m: -0.7, b: 1 } };
빵집 러시: 엔진 기본 vs 예약
엔진 UAI.makeHamlet({ seed: 11 }) 마을의 주민 6명을 지도 곳곳에 두고 배고픔 12·나머지 85로 맞춘 뒤 world.tick()을 실제로 돌린다(1 tick = 게임 1분). 헛걸음은 도착했는데 만석이라 행동이 취소된 횟수다. 실선은 사용 중, 점선은 이동 중인 대상이다.

60분을 돌리면 엔진 기본은 헛걸음 6번, 예약 변형은 0번이고, 60분 뒤 배고픔 충족도 평균도 49.5 대 57.2로 차이가 난다(이 시드 기준). 엔진 기본의 로그를 보면 6시 1분에 여섯 명이 모두 빵집을 고른다. 예약 변형에서는 둘이 빵집을 잡은 뒤 나머지는 밭과 선술집으로 흩어진다. 셋째 주민부터는 빵집이 만석 필터에 걸려 후보에서 사라지기 때문이다.

세 가지 도구: 혼잡, 예약, 주변 밀도

도구무엇을 보나잘 맞는 상황약점
혼잡 consideration지금 사용 중인 수 / capacity붐비는 곳을 부드럽게 피하기 (만석이 아니어도 감점)결정과 도착 사이의 공백을 못 본다

세 번째는 Lewis의 돌진 공격 DSE에 나온다. 이 DSE에는 영향맵을 조회해 대상 주변에 이미 아군이 적당히 있는지 보는 consideration이 있다. 이미 적 둘과 싸우고 있는 플레이어가 셋째 적이 갑자기 돌진해 와 몰매를 맞을까 걱정할 필요가 없게 하려는 것이다. Lewis는 이를 utility AI와 모듈식 AI 정보 시스템으로 쉽게 표현할 수 있는 설계 제약의 좋은 예로 꼽았다. 플레이어에게는 capacity가 없으니 "몇 명까지"를 예약표 대신 공간 정보로 대신 잰 셈이다. Hamlet에서는 이렇게 옮길 수 있다.

// 대상 주변 r칸 안의 다른 주민 수 → 많을수록 감점 (영향맵 조회의 단순 대용)
{ name: "주변 주민", input: ({ agent, world, target }) =>
    world.agents.filter(b => b !== agent && b !== target &&
      Math.abs(b.x - target.x) + Math.abs(b.y - target.y) <= 3).length,
  lo: 0, hi: 4, curve: "선형 감소" }
주의: 이 consideration은 비싸다위 구현은 컨텍스트마다 주민 전체를 훑으므로 비용이 A × T × C에 N이 하나 더 곱해진다. Heart of Thorns가 영향맵을 몇 프레임마다 한 번 채워 두고 조회만 한 이유가 여기에 있다. 공유 정보를 미리 만들어 두고 consideration은 읽기만 하게 하는 구조는 09장에서 다시 나온다.

구조는 use와 같지만 에이전트를 대상으로 삼으면 오브젝트에는 없던 문제가 생긴다.

  • 자기 자신 제외: b !== agent가 없으면 거리 0인 자기 자신이 늘 최고점 대화 상대가 된다. 대상 목록이 에이전트 목록과 같은 배열에서 나오면 반드시 확인해야 할 조건이다.
  • 움직이는 대상: 오브젝트는 제자리에 있지만 주민은 움직인다. 결정할 때 3칸이던 상대가 걸어가는 동안 10칸이 될 수 있다. 실행 중 재평가(06장 인터럽트, DA:I도 실행 중 평가를 계속한다)와 실행 쪽 종료 조건이 필요하다.
  • 상대의 동의: A가 B를 골랐다고 B가 A를 고르는 것은 아니다. 엔진의 "상대 한가함"은 상대가 도망치는 중인지만 보는 최소한의 스위치다. 상대가 다른 일을 하는 중인지, 상대도 사교 욕구가 있는지를 볼수록 대화가 자연스러워진다.
  • 예약 대상이 되는 에이전트: 인기 있는 주민 한 명에게 다섯이 몰리는 것은 7절의 빵집 러시와 같은 문제다. 에이전트에도 "대화 정원"을 두거나 주변 밀도 consideration을 쓸 수 있다.

함정: 대상이 많은 행동은 추첨권도 많다

3절에서 짚었듯 uai.js는 (행동, 대상) 쌍을 모두 펼친 채 선택한다. Hamlet World의 기본 선택 전략은 dual이며 최고점의 85% 이상(pct: 0.15)을 가중 랜덤으로 뽑는다. 이용하기@빵집 0.50 하나와 수다 떨기 컨텍스트 다섯 개(각 0.45)가 경쟁한다고 하자. 모두 0.425 이상이라 추첨에 남는다.

선택 방식P(이용하기@빵집)P(수다 떨기, 합계)
펼친 채 가중 랜덤 (uai.js 기본 구조)0.50 / (0.50 + 5×0.45) = 0.1820.818
행동마다 최고 대상으로 접은 뒤 (DA:I 방식)0.50 / (0.50 + 0.45) = 0.5260.474

두 값 모두 UAI.select(rows, { strategy: "topPct", pct: 0.15 })가 돌려준 pool의 확률이다. 점수는 빵집이 더 높은데도 마을 사람이 늘수록 주민들은 점점 수다만 떨게 된다. 이 효과를 원하지 않는다면 Target Selector처럼 행동마다 최고점 대상 하나로 접은 다음 행동끼리 추첨하면 된다. 반대로 "아는 사람이 많을수록 수다를 더 떤다"를 의도했다면 지금 구조가 맞다. 어느 쪽이든 의도해서 고르는 것이 중요하다.

위의 컨텍스트 지도에서 "다른 주민도 대상으로"를 켜고 사교 슬라이더를 낮춰 보자. 보람·찬을 아리 가까이 끌면 보라색 수다 떨기 선이 굵어진다. 상대와 거리 bookend가 12칸이라 멀리 있는 친구는 금세 0점이 된다.

후보에서 뺄까, 0점을 줄까?"절대 불가"는 targets 필터 또는 맨 앞 스위치. "덜 좋음"은 커브.만석 의자에 계속 걸어감 / 반대로 디버그 표에서 이유가 안 보임

핵심 요약

  • 평가 단위는 행동이 아니라 (행동, 대상) 컨텍스트다. 행동부터 고르고 대상을 나중에 고르면 둘 다 그럴듯한데 결과는 틀릴 수 있다.
  • uai.js에서는 action.targets(ctx)가 후보를 열거하고, Reasoner가 후보마다 { agent, world, target }로 consideration을 평가해 행을 하나씩 만든다.
  • DA:I의 Target Selector는 대상마다 점수를 초기화하고 자식 트리를 평가한 뒤, 최고점 대상 하나를 snippet의 결과로 돌려준다. 펼치기 대 접기의 차이는 가중 랜덤에서 확률 왜곡으로 나타난다.
  • 거리 커브는 대개 단조 감소지만, 적정 거리 유지에는 역 U자(Lewis의 돌진 공격, 체크리스트의 단조성 예외)를 쓴다. 공간 utility field로 그려 보면 의도대로인지 바로 보인다.
  • 방향은 내적을 [−1, 1] bookend로 정규화해 consideration으로 만든다. 같은 입력에 커브만 바꿔 "등 뒤 공격"과 "정면 대화"를 만든다.
  • 비용은 A × T × C (× N × 빈도)다. bookend와 같은 반경 필터는 결과를 바꾸지 않고 비용만 줄이며, early-out이 있으므로 0을 낼 확률 대비 비용이 낮은 consideration을 앞에 둔다. 보통은 비싼 LOS가 맨 끝이다.
  • 혼잡 consideration만으로는 동시 결정의 쏠림을 못 막는다. 결정 시점에 자리를 잡는 예약, 정원 없는 대상에는 주변 밀도 프록시를 쓴다.

확인 문제

1절의 예에서 "행동 먼저(가장 큰 광고 가치), 대상은 나중(가장 가까운 곳)" 방식이 나쁜 결과를 낸 근본 원인은?
행동 점수를 매기는 데 필요한 정보의 상당 부분이 대상에 붙어 있다. 대상을 보지 않은 행동 점수는 근거 없는 요약이 되고, 두 단계 각각은 합리적이어도 조합은 틀린다. 그래서 (행동, 대상) 쌍을 한 번에 평가한다.
DA:I Target Selector 노드가 각 대상을 평가하기 직전에 점수를 "초기 점수"로 되돌리는 이유는?
evaluation tree는 scoring 노드를 지날 때마다 점수를 더한다. 되돌리지 않으면 대상 A에서 받은 +10이 대상 B에 누적된다. 초기 점수를 기록해 두고 대상마다 복원해야 대상끼리 공정하게 비교된다.
측면/후방 공격 consideration에서 AI가 대상의 정확히 등 뒤에 있다. 대상의 facing과 (대상→AI) 단위 벡터의 내적 d와, 1−x⁴ 커브(x=(d+1)/2)의 점수는?
등 뒤에 있으면 대상→AI 벡터가 facing의 정반대라 d = −1, x = 0, 1−0⁴ = 1이다. 대상이 AI를 정면으로 보면 d = 1이고 점수 0, 옆이면 d = 0이고 0.94다.
consideration이 [광고 가치, 거리, 혼잡, LOS 레이캐스트]인 행동이 있다. 사전 필터가 없어 후보 대부분이 멀리 있고(거리 점수 0), LOS는 대체로 통과한다. 점수가 같게 나오면서 평가 비용을 가장 줄이는 배치는?
곱의 값은 순서와 무관하지만 early-out 때문에 비용은 순서에 좌우된다. 앞의 싼 거리 consideration이 대부분의 후보를 0으로 떨어뜨리므로, 비싼 레이캐스트는 살아남은 소수에게만 쓰인다. Lewis는 측면/후방 공격 DSE에서 꽤 비싼 LOS 레이캐스트를 일부러 맨 끝에 두었고, 이런 최적화가 Heart of Thorns AI 성능의 큰 부분이라고 했다. 반대로 LOS가 가장 자주 0을 낸다면 6절 측정기처럼 앞에 두는 편이 쌀 수도 있다.
엔진 기본 Hamlet에서 혼잡 consideration이 있는데도 6명이 동시에 빵집으로 몰리는 이유는?
혼잡 정보가 결정보다 늦게 갱신된다. 결정 시점에 점유를 올리는 예약을 쓰면 다음 주민은 이미 반영된 혼잡도와 만석 필터를 본다. 위젯에서 헛걸음이 6 → 0으로 줄어든다.
이용하기@빵집(0.50) 1개와 수다 떨기 컨텍스트 5개(각 0.45)가 pct 0.15 가중 랜덤으로 경쟁한다. (행동, 대상) 쌍을 펼친 채 뽑을 때 빵집이 뽑힐 확률은?
0.50 / (0.50 + 5×0.45) = 0.182. 행동마다 최고 대상으로 접으면 0.50 / 0.95 = 0.526이다. 대상이 많은 행동이 추첨권을 더 많이 쥐는 효과다.
다음 장으로이 장에서 한 명이 한 번 생각하는 데 드는 일을 다뤘다. 마을에는 수십·수백 명이 있고 시간은 계속 흐른다. 09장에서는 World.tick 루프, thinkEvery·thinkOffset으로 평가를 tick에 나눠 싣는 time-slicing, 시드 고정으로 재현 가능한 시뮬레이션까지, 이 모든 평가를 언제 어떻게 돌릴지 정하는 엔진 구조를 짠다.
