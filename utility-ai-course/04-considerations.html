기초 · Chapter 04

Consideration과 점수 결합

반응 커브 하나는 질문 하나에 답한다. "배가 얼마나 고픈가?", "빵집이 얼마나 먼가?" 그런데 행동은 이런 질문 여러 개에 한꺼번에 답해야 정해진다. 이 장에서는 원시 입력이 정규화와 커브를 거쳐 consideration 점수가 되고, 그 점수들이 하나의 행동 점수로 합쳐지는 과정을 엔진 코드와 함께 끝까지 따라간다. 결합 방식 하나를 고르는 데에도 설계 판단이 많이 들어간다.

학습 목표

  • 원시 입력 → bookend 정규화 → 반응 커브 → 결합 → × weight로 이어지는 점수 파이프라인을 Hamlet 예제로 직접 계산한다.
  • 평균·곱·최솟값·기하평균·보정 곱의 성질(거부권, 개수 편향, 민감도)을 비교하고 상황에 맞게 고른다.
  • IAUS 보정(make-up value) 공식을 유도하고, 보정이 무엇을 고치고 무엇은 못 고치는지 설명한다.
  • 점수 0의 거부권과 early-out을 이해하고, 비용과 0 확률을 보고 consideration 순서를 최적화한다.
  • Lewis의 세 범주(필수 스위치 / 행동 구분 / 밸런스·느낌), DSE 템플릿, 프록시 변수로 consideration을 설계한다.
  • 행동 weight와 consideration을 구분하고, Graham 결투 데모의 결합식(Heal = HealthDesire × Threat)이 왜 그렇게 생겼는지 설명한다.

1. Consideration: 질문 하나, 점수 하나

Utility AI에서 consideration(Graham은 decision factor라고 부른다)은 행동을 고를 때 따지는 질문 하나다. 각 consideration은 게임 상태에서 숫자 하나를 읽어 0~1 점수 하나를 내놓는다. Graham의 설명으로는 고양이 장난감을 어느 쇼핑몰에서 살지 정할 때도 가격만 보지 않는다. 브랜드 충성도, 배송 기간, 리뷰를 함께 본다. 이 하나하나가 decision factor이고, 이것들을 합쳐야 그 쇼핑몰에서 살지에 대한 최종 효용이 나온다.

왜 행동 점수를 한 번에 계산하는 큰 함수 하나로 쓰지 않고 이렇게 쪼갤까? 이유는 세 가지다.

  • 독립성: Graham은 이 방식의 힘을 "각 decision factor는 다른 모든 factor와 사실상 격리되어 있다. 우리가 알거나 신경 쓰는 것은 출력이 정규화된 점수라는 것뿐이다"라고 설명한다. 그래서 factor를 새로 추가하거나 다른 행동으로 옮기기 쉽다.
  • 데이터 주도: Lewis(Guild Wars 2: Heart of Thorns)는 입력 선택과 곡선 설정이 전부 데이터라서 "AI 캐릭터의 선호를 바꾸는 데 엔지니어링 부담이 없다"고 쓴다. consideration은 디자이너가 조립하는 부품이다.
  • 재사용: "거리", "체력", "쿨다운" 같은 consideration은 거의 모든 행동에 다시 나온다. Heart of Thorns에서는 이런 사전 정의 패턴이 100개 넘게 만들어졌고, 디자이너는 이것들을 섞어 새 생물을 "몇 분 만에" 만들었다고 한다.

Hamlet 마을에서 주민이 오브젝트를 "이용하기"로 할 때 엔진은 세 가지를 묻는다. 이 오브젝트가 내 욕구를 얼마나 채워 주나(광고 가치), 얼마나 먼가(거리), 얼마나 붐비나(혼잡). 실제 uai.js 코드는 다음과 같다.

      considerations: [
        // 광고된 욕구 충족량 × 그 욕구의 긴급도 합 → 0~1 (07장)
        { name: "광고 가치", input: ({ agent, target }) => UAI.adValue(agent, target), lo: 0, hi: 1, curve: "선형 증가" },
        // 거리: 가까울수록 좋다. 너무 멀면 0 근처 (08장)
        { name: "거리", input: ({ agent, target }) => Math.abs(agent.x - target.x) + Math.abs(agent.y - target.y), lo: 0, hi: 30, curve: { type: "poly", m: -1, k: 2, b: 1 } },
        // 이미 사용 중이면 붐빔 감점
        { name: "혼잡", input: ({ target }) => target.users / target.capacity, lo: 0, hi: 1, curve: { type: "linear", m: -0.7, b: 1 } },
      ],

consideration 하나는 네 부분으로 이루어진다. ① 무엇을 읽을지(input), ② 어느 범위를 0과 1로 볼지(lo, hi: bookend), ③ 정규화된 값을 어떤 모양으로 바꿀지(curve, 03장 반응 커브), ④ 사람이 읽을 이름(name)이다. 이 이름은 11장의 디버그 표에서 "왜 이 행동을 골랐나"를 설명하는 단위가 된다.

용어 정리 Graham(Game AI Pro 1)은 decision factor, Lewis·Mark(IAUS)는 consideration, 행동 하나를 평가하는 묶음은 DSE라고 부른다. 이 코스와 uai.js는 action.considerations라는 이름을 쓴다. 가리키는 대상은 모두 같다.

2. 점수 파이프라인: 빵집에 갈까?

Lewis는 Heart of Thorns의 consideration 처리 과정을 이렇게 설명한다. 원시 숫자 입력을 [0, 1]로 정규화하고, 응답 곡선으로 다시 매핑한 다음, 모든 consideration 점수를 곱해 DSE 점수를 얻는다. 정규화에는 bookend를 쓴다. 예를 들어 거리 0m를 최소, 100m를 최대로 정하면 25m는 0.25가 되고, 100m를 넘는 거리는 모두 1로 고정된다. 이 0.25를 알맞은 곡선에 넣으면 0.95 같은 값이 나올 수 있다. 엔진의 정규화는 한 줄짜리다.

  // bookend 정규화: [lo, hi] 구간을 [0, 1]로. 범위를 벗어나면 끝값에 고정 (GAP3 13장)
  UAI.normalize = (v, lo, hi) => (hi === lo ? 0 : clamp01((v - lo) / (hi - lo)));

bookend의 "고정(clamp)"은 생각보다 중요하다. 이것이 없으면 31칸 떨어진 오브젝트의 정규화 값이 1.03이 되고, 1 − x² 커브는 음수를 내놓는다. 엔진은 커브 출력도 한 번 더 clamp01로 자르지만, 입력 단계에서 범위를 지켜 두면 커브 설계자가 [0, 1] 정사각형만 생각하면 된다. Lewis도 곡선은 정의역·치역 [0, 1]의 정사각형 안에서만 신경 쓰면 된다고 말한다.

이제 Hamlet 마을의 주민 찬이 빵집 이용하기를 평가하는 과정을 엔진 그대로 한 단계씩 따라가 보자. 아래 위젯은 UAI.makeHamlet()으로 마을을 만들고 찬의 욕구와 빵집 이용자 수만 바꾼 뒤, 기본 Reasoner의 evaluate()가 내놓은 값을 단계별로 펼쳐 보여 준다. 숫자는 전부 엔진이 계산한 값이다.

스텝 애니메이션: 찬 → 빵집 이용하기의 점수 계산
▶ 재생으로 단계를 진행한다. 슬라이더를 바꾸면 엔진이 다시 계산한다. 배고픔을 100으로 올리면 광고 가치가 0이 되어 early-out이 일어나는 것도 볼 수 있다.
25 1 / 2

마지막 단계에서 보듯 엔진이 내놓은 점수와 손으로 계산한 점수는 같다. 중요한 관찰이 두 가지 있다.

  • 세 consideration 모두 0.5~0.8로 "꽤 괜찮은" 값인데, 그냥 곱하면 0.27로 뚝 떨어진다. 이 문제가 4절의 보정을 만든 이유다. Hamlet의 기본 World는 combine: "compensated"를 쓴다.
  • 배고픔이 100이면 채울 여지가 0이라 광고 가치가 0이 되고, 엔진은 거리와 혼잡을 아예 계산하지 않는다. 이것이 5절의 early-out이다.
빵집 이용자가 2명이면? 슬라이더 최댓값이 1인 이유가 있다. 빵집 정원은 2명이라 2명이 이용 중이면 targets()가 빵집을 아예 후보 목록에서 뺀다(o.users < o.capacity). "꽉 찼다"는 조건은 consideration이 아니라 대상 필터로 처리된다. 대상을 고르는 단계는 08장에서 다룬다.

3. 결합 방식 비교: 평균, 곱, 최솟값, 기하평균

consideration 점수가 여러 개 나왔다. 이것들을 어떻게 하나로 합칠까? 문헌에 나오는 두 대표 방식부터 보자.

3.1 평균: Graham의 개미 군체

Graham은 개미 군체 시뮬레이션으로 결합을 설명한다. 군체를 확장(Expand)할지 번식(Breed)할지 정할 때 세 factor를 본다.

decision factor원시 값정규화
Crowdedness (혼잡도)개체 수 4500 / 최대 50000.90
Health (식량 비축)Food 92 / 1000.92
Nursery (육아방 여유 공간)15 / 1000.15
Expand = Average(Crowdedness, Health) = (0.90 + 0.92) / 2 = 0.91
Breed  = Average(Health, Nursery)    = (0.92 + 0.15) / 2 = 0.535

평균은 직관적이고, Graham이 강조하듯 factor를 "끝없이 연결"할 수 있다. 그가 권하는 도구도 화살표마다 평균, 곱, max, min을 고르고 factor에 가중치를 주는 형태다. 하지만 평균에는 구조적 약점이 있다. 어떤 factor도 혼자서는 행동을 막을 수 없다. 육아방이 꽉 차서 Nursery가 0이어도 Breed는 (0.92 + 0)/2 = 0.46을 받는다. 알을 놓을 곳이 없는데 번식을 고를 수 있다는 뜻이다.

3.2 곱: IAUS와 Heart of Thorns

Lewis가 설명하는 IAUS 기반 구조는 consideration 점수를 모두 곱한다. 그 결과 핵심 성질이 생긴다. 어떤 consideration이든 0점을 내면 그 결정 전체를 선택 대상에서 뺄 수 있다. Lewis의 표현으로는 이 덕분에 "결정을 절대 쓰면 안 되는 상황에 대한 규칙을 쉽게 인코딩"할 수 있다. 0은 거부권(veto)이다.

곱의 대가는 개수 편향이다. 1보다 작은 수를 곱할수록 결과는 작아지므로, consideration이 많은 행동은 점점 불리해진다. 이 문제는 4절에서 다룬다.

최솟값과 기하평균은 개수 편향이 없으면서 거부권도 지킨다. 그런데도 곱이 표준처럼 쓰이는 이유는 아래 위젯으로 직접 확인해 보자. 최솟값은 가장 낮은 값 하나만 보기 때문에 나머지 consideration이 아무리 바뀌어도 점수가 움직이지 않는다. 두 행동이 같은 최솟값을 가지면 나머지 차이로 구분할 수 없다. 기하평균은 반대로 낮은 값을 너무 너그럽게 봐준다. 0.1 하나와 1 세 개의 기하평균은 0.56이다. 한 축이 "거의 안 된다"고 말하는데 행동 점수는 절반을 넘는다.

결합 방식 비교기
consideration 개수 n과 각 점수를 정하면 다섯 결합 방식의 결과가 막대로 나온다. 모두 UAI.combine(vals, method)를 그대로 호출한다. 프리셋 버튼으로 전형적인 상황을 불러올 수 있다.
"항상 1인 스위치 추가" 버튼을 눌러 보자 스위치는 보통 1을 내고, 꺼질 때만 0을 낸다. 곱에서는 1을 곱해도 결과가 그대로다. 그런데 보정 곱에서는 n이 하나 늘어난 만큼 다른 consideration의 보정량도 커져서 점수가 오른다. 예를 들어 [0.5]에 항상 1인 스위치 두 개를 붙이면 0.5가 0.667이 된다. 보정 곱을 쓰는 엔진에서 템플릿에 스위치를 많이 미리 넣어 두면, 행동마다 스위치 개수에 따라 점수가 조금씩 달라진다. 큰 문제는 아니지만 튜닝할 때 알아 둘 필요가 있다.

4. 곱의 개수 편향과 보정(make-up value)

2절의 빵집 예에서 세 값은 0.525, 0.782, 0.65였고 곱은 0.267이었다. 숫자를 더 단순하게 바꿔 보자. 모든 consideration이 0.8, 곧 "꽤 좋다"고 말하는 행동이 있다.

n=1: 0.8  ·  n=2: 0.64  ·  n=3: 0.512  ·  n=5: 0.328  ·  n=10: 0.107

consideration을 꼼꼼히 설계한 행동일수록 점수가 바닥으로 떨어진다. Hamlet에서 "이용하기"는 consideration이 3개이고 "산책"은 1개다. 조건이 같다면 consideration이 적은 행동이 늘 유리하다. 디자이너가 행동을 정교하게 만들수록 그 행동이 덜 선택되는 셈이다.

4.1 보정 공식

IAUS(Dave Mark)에서 쓰이는 보정은 consideration마다 "1까지 남은 거리"의 일부를 되돌려 준다. n개 consideration이 있을 때 점수 s 하나에 대해:

modification = 1 − 1/n
makeUp = (1 − s) · modification
s′ = s + makeUp · s

식을 하나씩 읽어 보자. 1 − s는 이 consideration이 만점에서 모자란 양이다. 그중 1 − 1/n만큼을 메워 주는데, n이 클수록 많이 메운다. 마지막으로 그 보충분에 다시 s를 곱한다. 원래 점수가 낮으면 보충도 적게 받는다는 뜻이다. 그래서 s = 0이면 s′ = 0이고(거부권 유지), s = 1이면 s′ = 1이다(만점 유지). n = 1이면 modification이 0이라 아무 변화가 없다.

엔진 구현은 식을 그대로 옮긴 것이다. combine("compensated")는 각 값을 보정한 뒤 곱한다.

  // 곱셈 결합은 consideration이 많을수록 점수가 깎이므로 보정한다 (IAUS make-up value)
  //   modification = 1 − 1/n,  makeUp = (1 − s)·modification,  s' = s + makeUp·s
  UAI.compensate = function (s, n) {
    if (n <= 1) return s;
    const mod = 1 - 1 / n;
    return s + (1 - s) * mod * s;
  };
  UAI.combine = function (vals, method) {
    const n = vals.length;
    if (!n) return 0;
    switch (method || "product") {
      case "product": return vals.reduce((a, v) => a * v, 1);
      case "compensated": return vals.reduce((a, v) => a * UAI.compensate(v, n), 1);
      case "mean": return vals.reduce((a, v) => a + v, 0) / n;
      case "min": return Math.min(...vals);
      case "max": return Math.max(...vals);
      case "geomean": return Math.pow(vals.reduce((a, v) => a * v, 1), 1 / n);
    }
    throw new Error("unknown combine: " + method);
  };

4.2 보정이 고치는 것과 못 고치는 것

그래프를 s = 0.8로 두고 오른쪽 끝을 보자. n = 10에서 곱은 0.107이고 보정 곱은 약 0.56이다. 꽤 많이 회복했다. 하지만 보정 곱도 n이 늘면 계속 줄어든다. 같은 s가 n개일 때 각 항은 s + (1−s)(1−1/n)s인데, n → ∞이면 s(2 − s)로 수렴한다. s = 0.8이면 0.96이다. 0.96을 무한히 곱하면 결국 0이 된다. 보정은 개수 편향을 완화할 뿐 없애지는 못한다.

그런데도 보정을 쓰는 이유는 곱의 다른 장점을 지키기 때문이다. 0은 여전히 거부권이고, 낮은 값 하나는 여전히 행동 점수를 강하게 끌어내린다. 3절 비교기에서 "0.1 하나 + 나머지 1"(n = 4)을 보면 기하평균은 0.56이지만 보정 곱은 0.17이다. "거의 안 된다"는 신호를 기하평균보다 훨씬 정직하게 전달한다. 실전에서 consideration 개수는 보통 행동마다 몇 개 정도다. 그 범위에서는 보정이 행동 간 점수를 비교 가능한 수준으로 맞춰 준다.

심화: 보정 곱을 쓰면 행동 간 비교가 완전히 공정해지나?

아니다. 점수 s인 consideration 하나만 있는 행동 A와, s인 consideration 하나에 1점짜리 consideration 세 개를 더한 행동 B를 비교해 보자. 순수 곱에서는 둘 다 s다. 보정 곱에서는 B가 comp(s, 4)를 받으므로 A보다 높아진다. 개수 편향의 방향이 뒤집힌 것이다. 보정은 "모든 consideration이 비슷하게 중간쯤"인 경우를 기준으로 만든 근사다. 행동 간 균형은 결국 weight(7절)와 곡선 튜닝(11장)으로 맞춰야 한다.

5. 거부권(0)과 early-out: 싼 것부터

곱 결합에서 0은 단순히 낮은 점수가 아니다. 결과가 이미 0으로 정해졌다는 뜻이므로, 나머지 consideration은 계산할 필요가 없다. Lewis는 이렇게 쓴다. consideration 하나가 결정 점수를 0으로 떨어뜨리는 순간 시스템은 나머지 처리를 멈추고 early-out해서 다음 결정으로 넘어간다. 그리고 이 덕분에 "더 싼 consideration을 먼저 배치하고 early-out으로 비싼 것을 피하는" 최적화가 가능하다.

Lewis가 든 예가 Side/Rear Attack DSE의 마지막 consideration인 시야(LOS) 검사다. 레이캐스트가 꽤 비싸서 순서가 실제로 중요하다. 실제 검사를 하기 전에 early-out할 수 있다면 그만큼 이득이다. 그는 이런 최적화가 Heart of Thorns AI의 성능을 충분히 확보한 큰 요인이었다고 말한다. Charge Attack에서는 내비메시 경로 검사가 "모든 대상에 대해 매번 계산하기엔 너무 비싸서" 아예 빼고 LOS 스위치만 썼다.

          for (const c of a.considerations) {
            if (!alive) { parts.push({ name: c.name, raw: null, x: null, y: null, skipped: true }); continue; }
            const raw = c.input(ctx);
            const x = UAI.normalize(raw, c.lo, c.hi);
            const y = c.fn(x);
            parts.push({ name: c.name, raw, x, y });
            if (y <= 0) alive = false;
          }
          const ys = parts.filter(p => !p.skipped).map(p => p.y);
          let score = alive ? UAI.combine(ys, this.opt.combine) * a.weight : 0;

Reasoner.evaluate()는 y <= 0이 되는 순간 alive = false로 바꾸고, 이후 consideration은 input()을 호출하지 않은 채 skipped로만 기록한다. 생략된 항목도 기록하는 이유는 11장 디버그 표에서 "어디서 거부되었나"를 보여 주기 위해서다. 그런데 여기에는 조건이 하나 있다. early-out이 안전하려면 결합 방식이 0을 흡수해야 한다. 곱, 보정 곱, min, 기하평균은 0이 하나라도 있으면 결과가 0이다. 평균이나 max로 결합하면서 early-out을 쓰면 계산 결과가 달라진다. 이 엔진은 0이 나오면 결합 방식과 상관없이 점수를 0으로 두므로, 평균을 고르더라도 거부권은 유지된다.

5.1 어떤 순서가 가장 싼가

"싼 것부터"는 좋은 출발점이지만 전부는 아니다. 자주 0을 내는 consideration을 앞에 두는 것도 이득이다. consideration i의 비용을 cᵢ, 0을 낼 확률을 pᵢ라 하고 서로 독립이라고 하면, 한 번 평가할 때의 기대 비용은 다음과 같다.

E[비용] = c₁ + (1−p₁)·c₂ + (1−p₁)(1−p₂)·c₃ + …

이웃한 두 항목 i, j의 순서를 바꿔 보면, i가 앞에 있을 때 비용은 cᵢ + (1−pᵢ)cⱼ, j가 앞에 있으면 cⱼ + (1−pⱼ)cᵢ다. 정리하면 cᵢ/pᵢ < cⱼ/pⱼ일 때 i를 앞에 두는 편이 낫다. 그래서 cᵢ / pᵢ(0 하나를 얻는 데 드는 비용)가 작은 순서로 정렬하면 기대 비용이 최소가 된다. 절대 0을 내지 않는 consideration(pᵢ = 0)은 맨 뒤로 간다. 이 결과는 Lewis 원문이 아니라 이 코스가 덧붙이는 계산이다. 실제 엔진에서 pᵢ는 플레이 로그로 측정해야 한다.

    6.2 DSE 템플릿: 스위치를 하드코딩하지 않는 이유

    Heart of Thorns의 거의 모든 DSE는 "다른 결정 실행 중 아님", "이동 불가 아님" 같은 기본 스위치로 시작한다. 이 검사를 엔진 코드에 박아 넣을 수도 있었다. 실제로 하드코딩된 제어 요소도 몇 개 있었다. 하지만 팀은 새로 만드는 DSE에 자주 쓰는 스위치를 미리 채워 두는 방식을 택했다. Lewis의 이유는 이렇다. 하드코딩 로직이 늘수록 예외가 필요할 때 시스템이 깨지기 쉬워진다. 언젠가는 누군가 스위치를 우회할 좋은 이유를 찾아낸다. 그날이 오면 "첫 번째 하드코딩을 우회하는 하드코딩"을 추가하는 것보다 consideration 하나를 빼는 편이 훨씬 낫다.

    그날은 실제로 왔다. Side/Rear Attack(측면·후방 공격) DSE는 이동형 DSE와 달리 이동 불가 상태에서도 꺼지면 안 됐다. 제자리에서 휘두르는 공격이기 때문이다. 팀은 이동 불가 스위치를 그 DSE에서 빼기만 했다.

    6.3 Evade Dangerous Areas 재현

    Lewis가 "비교적 단순하지만 매우 교육적"이라고 소개한 DSE다. 마법 주문, 기계 함정 같은 위험 지역에 너무 가까우면 캐릭터가 빠르게 빠져나가고, 종종 회피 애니메이션을 재생한다. consideration은 여섯 개다.

    1. 다른 결정 실행 중 아님, 이동 불가 아님: 필수 스위치. "얼어붙은 채로 움직이려는" 우스꽝스러운 행동을 막는다.
    2. 위험도(무한 해상도 영향 맵): 이 DSE의 핵심 일꾼이다. 곡선 y = 1 − (x − 1)⁴는 중간 정도 위험을 증폭하고 사소한 위험은 억누른다. 위험의 가장자리에 있는 캐릭터도 비켜서게 하되, 위험 근처이지만 유효 반경 밖에 있는 캐릭터는 그대로 두려는 의도다.
    3. runtime y = 1 − x⁶: 일정 반복 후에는 이 결정이 반드시 멈추게 한다. 캐릭터가 계속 회피만 하며 "맞힐 수 없게" 되는 경우를 막는다.
    4. cooldown y = x⁵: 쿨다운이 거의 끝날 때까지는 아주 작은 점수만 내다가 막판에 급등한다. 경쟁하는 두 결정 사이의 깜빡임(strobing)을 막는다.
    5. 자기 체력: 체력이 넉넉하면 점수를 낮춘다. 그래서 캐릭터가 적에게 한 방 먹이려고 아픔을 조금 참기도 하고, 체력이 줄수록 조심스러워진다. 개성이 여기서 나온다.

    아래 위젯은 이 DSE를 UAI.Reasoner 행동으로 그대로 옮긴 것이다. 위험도·runtime·cooldown 곡선은 엔진 프리셋("회피: 1−(x−1)⁴", "runtime: 1−x⁶", "cooldown: x⁵")이다. 원문에는 체력 곡선의 식이 없어서, 이 위젯은 "넉넉하면 낮추되 0으로 만들지는 않는" y = 1 − 0.7x를 골랐다. 입력은 이미 정규화된 값으로 둔다(runtime: 0 = 방금 시작, 1 = 허용 최대 / cooldown: 0 = 방금 끝남, 1 = 쿨다운 완료).

    6.5 프록시 변수: "왜 하나?"를 먼저 묻기

    Close to Melee when Invisible은 "투명 상태가 풀리기 전에 대상에게 닿을 수 있을 때만 접근"해야 한다. 투명 지속 시간, 양쪽 속도 등을 정확히 모델링할 수도 있었지만, 팀은 시간 상수 하나를 프록시 변수로 썼다. 상수 값은 원하는 효과가 나오도록 일부러 골랐다. Lewis에 따르면 정밀 모델과 프록시의 차이는 아주 드물게만 눈에 보인다. 그리고 보이더라도 플레이어가 "아까는 너무 멀어서 포기했나 보다" 같은 서사를 스스로 붙여 준다.

    그가 권하는 순서는 이렇다. ① "나는 왜 이 행동을 하나(혹은 안 하나)?"라고 묻고 동기 목록을 만든다. 캐릭터 입장이 되어 보는 "응용 롤플레이"다. ② 그 추상적 동기에 가장 잘 맞는, 이미 있거나 쉽게 만들 수 있는 데이터를 찾는다. 여러 consideration을 한꺼번에 담는 프록시(예: 모듈식 영향 맵 조합)가 특히 좋다. ③ 입력마다 상대적 중요도를 정하고 곡선을 설계한다. 프록시는 같은 종류의 지표일 필요도 없다. 거리 문제를 시간 상수로 푼 것처럼.

    Hamlet에 적용하면 "이용하기"의 광고 가치는 이미 프록시다. 빵의 맛, 찬의 입맛, 빵집 주인과의 친분을 모델링하지 않고 "배고픔을 얼마나 채우나 × 지금 얼마나 급한가" 하나로 묶었다(07장). 거리도 실제 경로 길이가 아니라 맨해튼 거리를 쓴다. Charge Attack이 내비메시 경로 대신 LOS로 만족했던 것과 같은 판단이다.

    7. 행동 weight와 결합식 설계: Graham의 결투

    7.1 weight는 consideration이 아니다

    엔진의 마지막 단계는 combine(...) * a.weight다. weight는 결합 바깥에서 행동 전체의 점수 크기를 조절한다. consideration과 무엇이 다를까?

    • 보정 대상이 아니다: weight 0.5를 consideration으로 넣으면 보정 곱에서 0.5보다 크게 보정되고, n도 하나 늘어 다른 항까지 바뀐다. weight는 정확히 곱해진다.
    • 1을 넘을 수 있다: consideration은 0~1이지만 weight는 아니다. Lewis는 비슷한 점수의 두 결정이 진동하는 문제의 대처법 중 하나로 "결정마다 가중치를 줘서 총점이 1이 아니라 3이나 4가 될 수 있게 하는 것"을 든다(진동은 06장에서 자세히 다룬다).
    • 행동의 "격"을 정한다: Hamlet의 wander(산책)은 consideration이 "기본값 1" 하나뿐이고 weight: 0.12를 갖는다. 다른 할 일이 0.12보다 나을 때는 절대 산책하지 않고, 아무것도 내키지 않을 때만 산책한다. 기본 행동(fallback)이다.
    • 0은 행동을 끈다: Dill의 dual utility에서는 weight ≤ 0인 선택지를 먼저 제거하므로, 디자이너가 weight를 0으로 두어 행동을 무효화할 수 있다(05장).

    Graham도 decision factor에 가중치를 줘서 AI가 그 factor를 얼마나 신경 쓸지 정하고, 이것으로 성격을 흉내 낼 수 있다고 쓴다. 정리하면 이렇다. consideration은 "지금 상황이 이 행동에 얼마나 맞나"를 묻고, weight는 "이 캐릭터에게 이 행동이 얼마나 중요한가"를 정한다.

    7.2 Graham 결투 데모

    Game AI Pro 1권 9장의 데모는 80년대 메뉴식 RPG처럼 괴물 한 마리와 싸우는 텍스트 결투다. 양쪽 다 공격, 회복 물약(3개) 사용, 도주(성공 확률 50%)를 할 수 있다. AI는 decision factor 네 개를 계산하고, 그것을 결합해 행동 점수를 만든 뒤 가중 랜덤으로 하나를 고른다.

    decision factor의미식 (원문 9.5~9.8)
    Attack Desire기본값은 공격성 a. 상대를 한 방에 죽일 수 있을수록 선형으로 증가 → 막판에 공격적으로범위 제한 선형: 상대 HP가 minDmg 이하면 1, maxDmg 이상이면 a
    Threat상대가 최대 피해로 때리면 내 현재 HP의 몇 %가 날아가나min(maxDmg / hp, 1)
    Health DesireHP가 줄수록 회복 욕구 상승 (로지스틱 변형)1 − 1/(1 + (e×0.68)^(−(hp/maxHp)×12 + 6))
    Run Desire물약이 많으면 거의 0, 없으면 빠르게 증가1 − (hp/maxHp)^(0.25 / (p+1)⁴)
    Attack = AttackDesire    Heal = HealthDesire × Threat    Run = RunDesire × Threat

    왜 Heal에 Threat를 곱했을까? Graham은 이것이 "너무 일찍 회복하려는 경우를 완화하고, 플레이어의 최대 피해에 따라 행동을 바꾼다"고 설명한다. HP가 60%로 줄면 회복하고 싶어지지만, 상대가 약해서 한 방에 HP의 10%밖에 못 깎는다면 지금 물약을 쓸 이유가 없다. HealthDesire는 "내 상태"를, Threat는 "상대가 만드는 상황"을 본다. 둘을 곱하면 둘 다 해당할 때만 회복한다. 곱 결합을 고른 이유 자체가 설계 판단이다.

    튜닝 일화도 하나 있다. 처음에는 Threat에 플레이어의 평균 피해를 썼다. 기대 효용의 취지에는 그쪽이 맞지만, 결과가 충분히 엄격하지 않아서 최대 피해로 바꿨다. Graham은 이것을 "효용 곡선과 공식의 튜닝은 과학보다 예술에 가깝다"는 좋은 예로 든다. 아래 위젯에서 두 버전을 바꿔 볼 수 있다.

    결투 AI: decision factor → 행동 점수 → 가중 랜덤
    식은 Graham 9장을 따른다. HP 최댓값 100, AI 피해 10~20, 플레이어 최소 피해 = 최대 피해의 절반은 이 위젯의 가정값이다. "물약 0개면 회복 불가" 스위치도 이 위젯이 덧붙인 것이다(필수 스위치 예). 식 9.5는 본문 설명("기본값은 a")에 맞춰 범위를 제한한 형태로 구현했다. 선택 확률은 UAI.select(…, {strategy: "weighted"})가 돌려준 값이다.
    해 보기 ① AI HP를 45로 두고 플레이어 최대 피해를 10 ↔ 45로 바꿔 보자. HealthDesire는 그대로인데 Heal 확률만 크게 움직인다. Threat 곱의 효과다. ② 물약을 0으로 내리면 RunDesire가 확 뛰고 Heal은 스위치로 꺼진다. ③ "평균 피해" 체크를 켜면 Threat가 줄어 Heal·Run이 덜 엄격해진다. Graham이 바꾼 이유가 보인다.

    8. 함정 모음

    8.1 평균이 거부권을 무력화한다

    평균으로 결합하면 "절대 안 됨"을 표현할 수 없다. 육아방이 0인데 번식하는 개미, 위협이 없는데 도망치는 주민이 나온다. Hamlet의 수다 떨기는 "상대 한가함" 스위치로 도망 중인 상대를 거른다. 평균 결합이었다면 스위치가 0이어도 "사교 결핍"과 "상대와 거리" 항이 점수를 남겨서, 늑대에게서 도망치는 친구를 쫓아가 말을 거는 주민이 나온다. 평균을 쓰고 싶다면(예: 여러 장점의 균형) 스위치는 결합 밖에서 처리해야 한다. 이 엔진은 consideration이 0을 내면 결합 방식과 상관없이 점수를 0으로 둔다. 평균을 직접 구현하는 엔진에서는 이 처리가 자주 빠진다.

    8.2 곱의 개수 편향

    consideration이 많은 행동이 체계적으로 손해를 본다(4절). 증상은 이렇다. "새 consideration을 하나 넣었더니 그 행동을 거의 안 한다." 새 항목이 대부분 0.9를 내더라도 점수는 10% 깎인다. 보정 곱으로 완화하고, 남는 차이는 weight로 맞추자. 거꾸로 보정 곱에서는 항상 1인 스위치를 더하면 점수가 오르는 역효과도 있다(3절 경고).

    8.3 스케일 불일치

    Graham은 일관성을 강조한다. 시스템 전체가 같은 스케일을 써야 하고 0~1 정규화를 권한다. consideration 하나가 0~1 밖의 값(예: 원시 거리 14)을 내면 그 항이 곱을 지배한다. 정규화했더라도 bookend가 다르면 같은 원시 값이 다른 의미가 된다. Hamlet에서 "이용하기"의 거리 bookend는 0~30칸이고 "수다 떨기"는 0~12칸이다. 6칸 떨어진 빵집은 거리 점수 0.96, 6칸 떨어진 친구는 0.5다. 의도한 설계일 수 있다(수다는 가까운 사람과 떠는 것). 하지만 의도한 것인지 확인해야 한다. Lewis의 곡선 체크리스트도 첫 질문이 "무엇을 입력으로 쓰고, bookend를 어디로 잡나"다.

    정규화 대신 점수 관례를 쓰는 길 모든 게임이 0~1 정규화를 쓰는 것은 아니다. Dragon Age: Inquisition은 자동 정규화 대신 디자이너 점수 관례(기본 10, 공격 20~40, 지원 25~45, 반응 50~70)로 행동 범주 간 크기를 맞췄다. 스케일 문제를 "규칙"으로 푼 사례다. 10장에서 비교한다.

    8.4 순서에 의존하는 early-out

    early-out은 결과를 바꾸지 않는 최적화여야 한다. 그런데 consideration의 input()이 부작용을 갖는다면(예: 캐시를 채움, 타깃을 기록함) 순서에 따라 동작이 달라진다. consideration 입력 함수는 순수하게 유지하자. 기록이 필요하다면 엔진처럼 skipped로 남기면 된다.

    핵심 요약

    • consideration = 입력 + bookend + 커브 + 이름. 각자 0~1 점수를 내고 서로 격리되어 있어 조립·재사용이 쉽다.
    • 파이프라인: 원시 입력 → UAI.normalize(범위 밖은 고정) → UAI.curve → UAI.combine → × weight → 행동 점수.
    • 평균은 거부권이 없고, 곱은 0의 거부권이 있지만 개수가 늘수록 점수가 sⁿ으로 떨어진다. min은 둔하고, 기하평균은 낮은 값에 너그럽다.
    • IAUS 보정: s′ = s + (1−s)(1−1/n)·s. 0과 1은 보존하고 개수 편향을 완화하지만 없애지는 못한다.
    • 0이 나오면 즉시 중단(early-out)한다. 기대 비용은 cᵢ/pᵢ 오름차순일 때 최소이고, 비싼 검사(LOS 레이캐스트)는 뒤로 보낸다.
    • Lewis의 세 범주는 필수 스위치 / 행동 구분 / 밸런스·느낌이다. 스위치는 하드코딩하지 말고 DSE 템플릿에 넣고, 복잡한 지표는 프록시 변수로 바꾼다.
    • weight는 결합 밖에서 행동 전체를 조절한다(1 초과 가능, 보정 대상 아님). 결합식 자체도 설계다. Heal = HealthDesire × Threat.

    확인 문제

    consideration 세 개(0.9, 0.9, 0)를 평균으로 결합하고 early-out이 없는 엔진이 있다. 어떤 일이 생기나?
    (0.9+0.9+0)/3 = 0.6. 평균에는 거부권이 없으므로 스위치가 0이어도 행동이 살아남는다. 곱(또는 엔진의 early-out)을 써야 0이 거부권이 된다.
    모든 consideration이 0.8인 행동이 있다. consideration이 5개일 때 순수 곱 점수는 대략 얼마인가?
    0.8⁵ ≈ 0.328. "모두 꽤 좋다"는 행동이 1/3로 떨어진다. 이것이 개수 편향이고, IAUS 보정이 이를 완화한다(보정 곱은 약 0.69).
    IAUS 보정 s′ = s + (1−s)(1−1/n)s에 대한 설명으로 틀린 것은?
    보정 곱도 n이 커지면 계속 줄어든다. 각 항이 s(2−s)로 수렴하는데, 이 값이 1보다 작으면 무한히 곱할 때 0으로 간다. 보정은 완화일 뿐 제거가 아니다.
    consideration A(비용 1, 0 확률 0.1)와 B(비용 4, 0 확률 0.8)가 있다. early-out 기대 비용을 줄이려면 어느 것을 먼저 평가해야 하나?
    A 먼저: 1 + 0.9×4 = 4.6. B 먼저: 4 + 0.2×1 = 4.2. c/p 오름차순(B=5, A=10)이 최적이다. "싼 것부터"는 좋은 경험칙이지만, 자주 0을 내는 항목은 조금 비싸도 앞에 둘 가치가 있다.
    Heart of Thorns 팀이 "이동 불가 아님" 같은 필수 스위치를 엔진에 하드코딩하지 않고 DSE 템플릿에 미리 채워 둔 이유는?
    Lewis: 하드코딩 로직이 늘수록 예외 앞에서 시스템이 깨지기 쉽다. 제자리 공격인 Side/Rear Attack은 이동 불가 스위치를 생략하는 것으로 해결했다.
    Graham 결투 데모에서 Heal = HealthDesire × Threat로 정의한 효과는?
    곱은 "둘 다 해당할 때만"이다. Graham은 이것이 이른 회복을 완화하고 플레이어의 최대 피해에 따라 행동을 바꾼다고 설명한다. 평균 피해 대신 최대 피해를 쓴 것도 튜닝 결과다.
    Hamlet의 산책(wander) 행동이 weight: 0.12를 consideration이 아닌 weight로 갖는 이유로 가장 적절한 것은?
    consideration으로 0.12를 넣으면 보정 곱에서 값이 바뀌고 n도 늘어난다. weight는 행동 전체의 크기를 그대로 조절한다.
    다음 장으로 이제 모든 (행동, 대상) 쌍에 점수가 붙었다. 그럼 무엇을 고를까? 늘 최고점만 고르면 로봇 같고, 점수 비례로 뽑으면 가끔 바보 같은 선택을 한다. 05장에서는 최고점·가중 랜덤·상위 N·dual utility(rank + weight)를 UAI.select로 구현하고 비교한다.
