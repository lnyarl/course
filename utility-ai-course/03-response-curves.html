반응 커브: 상태를 효용으로

체력 37, 늑대까지 9칸, 탄약 2발, 배고픔 64. 게임 상태는 단위도 범위도 제각각인 숫자다. 효용 AI는 이 숫자들을 먼저 0~1 사이의 "얼마나 원하나"로 바꿔야 비교하고 결합할 수 있다. 그 변환을 맡는 함수가 반응 커브(response curve)이고, 캐릭터의 성격과 게임의 손맛은 대부분 여기서 정해진다.

학습 목표

  • bookend 정규화로 원시 입력을 [0, 1]로 옮기고, 범위 밖 입력이 끝값에 고정되는 이유를 설명한다.
  • 선형·다항·로지스틱·로짓·종형·사인·스위치·구간 선형 커브의 모양과 쓰임새를 구별한다.
  • uai.js의 m, k, b, c 관례를 읽고, IAUS 매뉴얼·ProjectBorealis 구현과 의미가 어떻게 다른지 비교한다.
  • 커브 에디터와 구간 선형 에디터로 직접 커브를 만들어 엔진 spec(JSON)으로 내보낸다.
  • 같은 입력에 서로 다른 커브를 주면 "성격"이 생긴다는 것을 Hamlet 주민과 Graham의 결투 데모로 확인한다.
  • 커브 선택 체크리스트와 실무 함정(거부권, 극단 지수, clamp, 비정수 지수)을 적용한다.
엔진 부품 UAI.normalize() UAI.CURVES UAI.curve() UAI.piecewise() UAI.PRESETS — 원시 게임 값을 bookend로 정규화하고, 커브 spec 하나로 0~1 효용 함수를 만든다.

1. 왜 커브인가

02장에서 효용은 값(value)과 다르다고 했다. 같은 붕대라도 다쳤을 때 더 가치 있다. 이제 이 "맥락에 따라 달라지는 선호"를 코드로 옮겨야 한다. 방법은 단순하다. 게임이 이미 알고 있는 숫자(체력, 거리, 탄약, 욕구 수치)를 입력으로 받아 0~1 점수를 내는 함수를 하나 고르면 된다.

문제는 어떤 함수를 고르느냐다. Graham은 Game AI Pro 9장에서 이 단계를 이렇게 평가한다. 게임 값을 효용으로 바꾸는 일은 "매우 주관적"이어서, 같은 입력을 받아도 프로그래머 둘이 서로 다른 출력을 내는 함수를 쓴다. 그리고 알맞은 함수를 찾는 일은 "과학이라기보다 예술(more art than science)"이며 대부분의 시간이 여기에 든다고 덧붙인다. 이 코스의 출발점인 DeepBlue의 블로그 글도 같은 맥락에서 선형·2차·로지스틱·구간 선형(piecewise) 커브를 소개한다.

정답 수식이 없으니 커브를 고르는 기준이 필요하다. 이 장은 세 가지를 갖춘다.

  • 어휘: 자주 쓰는 커브 모양 몇 가지와, 각 모양이 행동에 주는 느낌.
  • 표현: 커브를 코드가 아닌 데이터(spec)로 적는 방법. 디자이너가 프로그래머 없이 바꿀 수 있어야 한다.
  • 절차: 입력 범위 → 방향 → 단조성 → 끝점 순으로 고르는 체크리스트(10절).
커브는 "얼마나"를 담당한다

if 문은 "도망칠까 말까"만 답한다. 커브는 "지금 얼마나 도망치고 싶은가"를 답한다. 늑대가 14칸 밖에 있을 때와 3칸 앞에 있을 때의 차이, 체력 40과 체력 39의 미세한 차이까지 연속적인 점수로 바뀌기 때문에, 행동이 문턱에서 갑자기 뒤집히지 않고 상황에 맞게 부드럽게 바뀐다.

2. bookend 정규화: 먼저 [0, 1]로

커브에 넣기 전에 입력부터 공통 눈금으로 맞춘다. Mike Lewis(Game AI Pro 3, 13장, Guild Wars 2: Heart of Thorns)는 이를 bookend라고 부른다. 거리라면 "0 m는 최솟값, 100 m는 최댓값"처럼 양 끝을 정하고, 그 사이 값을 0~1로 옮긴다. 최댓값을 넘는 거리는 자동으로 1이 된다. 그의 예에서 25 m 떨어진 대상의 원시 점수는 25/100 = 0.25이고, 가까울수록 좋다는 커브를 거치면 "예컨대 0.95" 같은 점수가 된다.

IAUS 매뉴얼(Dave Mark)도 같은 일을 Input Parameter로 한다. 거리 consideration에 RangeMax를 20으로 주면 20 m가 x = 1.0이 되도록 커브가 자동으로 맞춰진다. 오픈소스 ProjectBorealis IAUS 플러그인은 (Input − Minimum) / (Maximum − Minimum)을 계산한 뒤 clamp한다. 우리 엔진의 한 줄도 같은 일을 한다.

// ───────────────────────── 0. 공통 ─────────────────────────
const clamp01 = x => (x > 1 ? 1 : x > 0 ? x : 0); // NaN → 0
UAI.clamp01 = clamp01;

// bookend 정규화: [lo, hi] 구간을 [0, 1]로. 범위를 벗어나면 끝값에 고정 (GAP3 13장)
UAI.normalize = (v, lo, hi) => (hi === lo ? 0 : clamp01((v - lo) / (hi - lo)));

clamp가 중요한 이유는 두 가지다. 첫째, 커브 함수는 [0, 1] 밖에서 이상하게 행동할 수 있다(다항 커브는 1을 넘으면 폭주하고, 로짓은 정의되지 않는다). 둘째, 디자이너가 "100 m 밖이면 다 똑같이 멀다"는 결정을 데이터로 표현하게 해 준다. 결정 범위 바깥의 차이는 의미 없는 잡음이기 때문이다.

파이프라인 따라가기: 원시 입력 → bookend → 커브 → 점수
Lewis의 예(0–100 m, 25 m)를 그대로 재현한다. 단계 버튼으로 값이 흘러가는 순서를 보고, 거리와 bookend를 바꿔 결과가 어떻게 바뀌는지 확인하라. 계산은 UAI.normalize와 UAI.curve를 그대로 호출한다.
bookend는 커브만큼 중요한 튜닝 손잡이다

위 위젯에서 hi를 100에서 40으로 줄여 보라. 25 m의 x가 0.25에서 0.625로 뛰고 점수가 크게 떨어진다. 커브 모양은 그대로인데 행동이 바뀐다. 실무에서 "커브를 고쳤는데 효과가 없다"거나 "조금만 고쳐도 확 바뀐다"는 일은 대개 bookend가 문제다. 커브를 만지기 전에 입력 범위가 실제 플레이에서 나오는 값 분포와 맞는지부터 확인하라.

3. 커브 도감

Graham은 자주 쓰는 형태를 수식으로 정리한다. 여기서 x는 입력값, m은 그 입력의 최댓값이다.

(9.2) 선형   U = x / m      (9.3) 2차   U = (x / m)k      (9.4) 로지스틱   U = 1 / (1 + e−x)
  • 선형(9.2)은 사실상 정규화 그 자체다. 입력이 두 배면 욕구도 두 배다.
  • 2차(9.3)는 지수 k가 커질수록 가팔라진다. 출력이 0과 1로 수렴하도록 정규화되어 있으니 큰 k는 작은 x에서 거의 영향이 없다. 0 < k < 1이면 커브가 "회전"해서 작은 x에서 더 급해진다(Graham의 예는 k = 0.333).
  • 로지스틱(9.4)은 시그모이드의 하나로, 변화가 가운데 몰리고 양 끝에서 0과 1로 잦아든다. 입력은 사실상 [−10, 10]이면 충분하고, x = 6이면 이미 0.9975다. 밑 e를 키우면 계단처럼 날카로워지고 줄이면 부드러워진다.
  • 구간 선형은 디자이너가 점 몇 개를 찍고 사이를 직선으로 잇는 맞춤 커브다. The Sims가 배고픔에 이 방식을 쓴다고 Graham은 적는다(7절).

IAUS 매뉴얼은 여기에 로짓(Logit), 정규 분포 모양(Normal), 사인(Sine)을 더해 여섯 타입을 둔다. 우리 엔진은 그 여섯에 스위치(step)와 상수(constant), 구간 선형을 더했다. 아래 도감의 모든 그림은 UAI.curve(spec)로 그렸다. 카드 아래 회색 글씨가 그 spec이다.

4. 엔진 구현: m, k, b, c와 CURVES

Graham의 수식은 커브마다 변수 이름이 제각각이다. 데이터로 다루려면 모든 커브가 같은 모양의 파라미터를 받는 편이 낫다. IAUS를 따라 우리 엔진도 네 변수 m, k, b, c로 통일했다. 관례는 다음과 같다.

m = 기울기/세기  ·  k = 지수  ·  b = 수직 이동  ·  c = 수평 이동

실제 수식은 아래가 전부다. 커브마다 m과 k가 맡는 역할이 조금씩 다르다는 점에 주의해서 읽자. 특히 logistic은 k가 높이, normal은 m이 높이이고 k가 폭이다.

// ───────────────────────── 1. 반응 커브 (03장) ─────────────────────────
// 파라미터 관례: m=기울기/세기, k=지수, b=수직 이동, c=수평 이동
const CURVES = {
  linear: (x, p) => p.m * (x - p.c) + p.b,
  // 다항: 음수 밑에 비정수 지수를 쓰면 NaN이 되므로 부호를 보존해 계산
  poly: (x, p) => {
    const d = x - p.c;
    return p.m * Math.sign(d) ** (Number.isInteger(p.k) ? p.k : 1) * Math.pow(Math.abs(d), p.k) + p.b;
  },
  // 로지스틱: c가 변곡점, m이 가파름, k가 높이
  logistic: (x, p) => p.k / (1 + Math.exp(-p.m * (x - p.c))) + p.b,
  // 로짓: 로지스틱의 역함수 꼴. 가운데가 평평하고 양 끝이 가파르다 (IAUS 구현과 같은 /5 스케일)
  logit: (x, p) => {
    const z = Math.min(Math.max(x - p.c, 1e-4), 1 - 1e-4);
    return p.m * Math.log(z / (1 - z)) / 5 + 0.5 + p.b;
  },
  // 정규(종형): c가 봉우리 위치, k가 폭(작을수록 좁음), m이 높이
  normal: (x, p) => p.m * Math.exp(-((x - p.c) ** 2) / (2 * p.k * p.k)) + p.b,
  // 사인: 주기적 선호 (하루 주기 등)
  sine: (x, p) => p.m * 0.5 * Math.sin(2 * Math.PI * p.k * (x - p.c)) + 0.5 + p.b,
  // 스위치: x ≥ c 이면 1, 아니면 0 (m < 0 이면 반대)
  step: (x, p) => ((p.m >= 0 ? x >= p.c : x < p.c) ? 1 : 0),
  constant: (x, p) => p.b,
};
UAI.CURVES = CURVES;
const DEFAULTS = { m: 1, k: 1, b: 0, c: 0 };

그다음 UAI.curve(spec)가 spec 객체 하나를 x → [0, 1] 함수로 바꾼다. 빠진 파라미터는 DEFAULTS로 채우고, invert면 입력을 1 − x로 뒤집고, 결과는 항상 clamp01을 거친다. 문자열을 주면 프리셋 이름으로, 함수를 주면 그 함수의 출력을 clamp해서 쓴다.

// 구간 선형 커브: points = [[x0,y0],[x1,y1],...] (x 오름차순)
function piecewise(points) {
  return x => {
    if (x <= points[0][0]) return points[0][1];
    for (let i = 1; i < points.length; i++) {
      const [x1, y1] = points[i];
      if (x <= x1) {
        const [x0, y0] = points[i - 1];
        return y0 + ((y1 - y0) * (x - x0)) / (x1 - x0 || 1);
      }
    }
    return points[points.length - 1][1];
  };
}
UAI.piecewise = piecewise;

// spec → (x∈[0,1]) → y∈[0,1]. spec.invert면 입력을 1−x로 뒤집는다
UAI.curve = function (spec) {
  if (typeof spec === "function") return x => clamp01(spec(x));
  if (typeof spec === "string") spec = UAI.PRESETS[spec];
  const f = spec.type === "piecewise" ? piecewise(spec.points) : null;
  const p = Object.assign({}, DEFAULTS, spec);
  const g = f || (x => CURVES[p.type](x, p));
  return x => clamp01(g(p.invert ? 1 - x : x));
};
왜 invert를 따로 두나

"늑대가 가까울수록 도망치고 싶다"를 만들 때, 감소 커브를 새로 설계하는 대신 증가 커브에 invert: true만 붙이면 된다. {type:"poly", m:1, k:2, invert:true}는 (1 − x)2이다. 엔진의 NEED_CURVE가 기력·재미·사교 긴급도를 전부 이렇게 적는다. 욕구 수치는 "충족도"(100이면 가득)인데 긴급도는 결핍에 비례해야 하기 때문이다.

invert는 입력을 뒤집는다는 점을 기억하라. 출력을 뒤집는 1 − f(x)와는 다르다. 예를 들어 x2에 invert를 주면 (1 − x)2이지만, 출력을 뒤집으면 1 − x2이다. 둘 다 감소 커브지만 모양이 정반대로 휜다. 아래 에디터에서 "2차 증가"에 invert를 켠 것과 "2차 감소 (1−x²)" 프리셋을 비교해 보라.

마지막으로 프리셋 팔레트가 있다. 이름만 적으면 되는 커브 14개다. 아래 셋은 Lewis가 Heart of Thorns의 "Evade Dangerous Areas" 결정에 쓴 곡선을 그대로 옮긴 것이다. 영향 맵 위험도 1−(x−1)⁴, 무한 회피를 막는 runtime 1−x⁶, 쿨다운이 끝날 무렵에야 급등해 같은 행동이 깜빡이듯 반복되는(strobing) 것을 막는 cooldown x⁵.

// 프리셋 팔레트: "소수의 프리셋 + 고급 모드" (GAP3 13장 권고)
UAI.PRESETS = {
  "선형 증가": { type: "linear", m: 1, b: 0, c: 0 },
  "선형 감소": { type: "linear", m: -1, b: 1, c: 0 },
  "2차 증가 (x²)": { type: "poly", m: 1, k: 2 },
  "2차 감소 (1−x²)": { type: "poly", m: -1, k: 2, b: 1 },
  "제곱근 (√x)": { type: "poly", m: 1, k: 0.5 },
  "3차 지연 (x³)": { type: "poly", m: 1, k: 3 },
  "로지스틱 중앙": { type: "logistic", m: 12, k: 1, c: 0.5 },
  "로지스틱 감소": { type: "logistic", m: -12, k: 1, c: 0.5 },

5. 구현마다 파라미터 의미가 다르다

"m, k, b, c를 쓴다"는 말은 생각보다 많은 것을 약속하지 않는다. IAUS 매뉴얼은 변수 이름과 의미만 정의하고 실제 수식은 싣지 않는다(계산은 Consideration::GetConsiderationValue에 있다고만 적는다). 그래서 구현마다 같은 이름에 다른 의미가 붙는다. 아래 표는 매뉴얼, 오픈소스 ProjectBorealis(PB) 플러그인의 IAUSResponseCurve.h, 우리 uai.js를 나란히 놓은 것이다.

타입IAUS 매뉴얼의 의미ProjectBorealis 수식 (원문 변수명)uai.js 수식
Linearm 기울기(+상승/−하강), b y절편, c x절편Slope·(x−XShift)+YShiftm·(x−c)+b

Logisticm 가운데 기울기, k 세로 크기·방향, b 세로 이동, c 가로 이동Slope/(1+Exp(−10·Exponent·(x−0.5−XShift)))+YShiftk/(1+e−m(x−c))+b

Normalm 혹의 폭(표준편차와 비슷), k 혹의 높이, b, c 이동Slope·Exp(−30·Exponent·(x−XShift−0.5)²)+YShiftm·e−(x−c)²/(2k²)+b

실무 함정: 같은 이름, 다른 커브
  • Normal: 매뉴얼은 m이 폭이고 k가 높이다. PB는 Slope가 높이이고 Exponent가 클수록 혹이 좁아진다. uai.js는 m이 높이이고 k가 σ라서 클수록 넓어진다. 세 구현 중 같은 것이 하나도 없다.
  • Logistic: 매뉴얼과 uai.js는 m이 기울기, k가 높이다. PB는 반대로 Slope가 높이, Exponent가 기울기(×10)다. 변곡점도 PB는 기본이 x = 0.5이고 XShift는 거기서부터의 이동량인데, uai.js의 c는 변곡점의 절대 위치다.
  • Sine: PB에는 진동수 파라미터가 없다. uai.js의 k(주기 수)는 PB로 옮길 방법이 없다.
  • Logit: PB는 x − XShift가 정확히 1이면 1/0 = ∞가 되고, Sanitize가 "유한값이 아님"으로 보고 0을 돌려준다. 가장 높아야 할 끝점에서 점수가 0으로 떨어진다. uai.js는 z를 [10−4, 1 − 10−4]로 막아 이 문제를 피한다.

엔진을 옮기거나, 다른 툴에서 만든 커브 데이터를 가져오거나, 블로그 수식을 복사할 때마다 이 차이에 걸린다. 커브 데이터에는 반드시 "어느 구현의 m, k, b, c인지"를 함께 기록하라.

같은 숫자, 다른 커브: uai.js vs ProjectBorealis
같은 m, k, b, c를 uai.js(실선)와 PB 수식(점선, Slope=m, Exponent=k, XShift=c, YShift=b로 이름만 맞춤)에 넣는다. "PB 의미로 번역"을 켜면 아래 변환식으로 옮겨 넣어 두 커브가 겹치는지 확인할 수 있다. PB 수식은 비교용으로 이 장 안에 따로 구현했다(엔진에는 없음).
uai.jsProjectBorealis
uai.js → PB 변환식
  • linear, poly, logit: 그대로. Slope = m, Exponent = k, XShift = c, YShift = b (단, poly의 음수 밑 처리는 다르다. 11절)
  • logistic: Slope = k, Exponent = m / 10, XShift = c − 0.5, YShift = b
  • normal: Slope = m, Exponent = 1 / (60·k²), XShift = c − 0.5, YShift = b (−30·E = −1/(2k²)에서 유도)
  • sine: Slope = m, XShift = c, YShift = b. k = 1일 때만 대응된다

7. 구간 선형 커브와 Sims의 배고픔

Graham은 수식 커브의 한계를 The Sims의 배고픔으로 보여 준다. 심(Sim)의 Hunger 수치는 "얼마나 배부른가"를 잰다. 낮을수록 배고프다. 이걸 회전된 2차 커브로 점수화하면 배고플 때는 잘 먹지만, 거의 배부를 때도 먹을 확률이 0이 아니다. 작더라도 0이 아니면 가중 랜덤 선택(05장)에서 언젠가는 뽑힌다. 디자이너가 원하는 것은 "어느 문턱까지는 배고픔을 완전히 무시하다가, 조금 배고파지다가, 갑자기 매우 배고파지는" 모양인데, 이건 간단한 수식 하나로는 만들 수 없다.

해법이 구간 선형 커브다. 원하는 문턱을 나타내는 2D 점 몇 개를 손으로 찍어 두고, x가 주어지면 가장 가까운 두 점 사이를 선형 보간한다. Graham은 이것이 "바로 The Sims가 쓰는 방식"이라고 적는다. 엔진 구현은 4절의 piecewise()다. x 오름차순 점 배열을 받아 첫 점 왼쪽과 끝 점 오른쪽은 끝값으로 고정한다.

Hamlet의 배고픔 긴급도 커브도 이 방식이다. 욕구 수치 0~100을 100으로 나눈 값이 x이고, 결핍이 클수록(x가 작을수록) 긴급도가 높다.

// 욕구 → 긴급도 커브: 결핍이 클수록 급격히 중요해진다 (07장)
UAI.NEED_CURVE = {
  hunger: { type: "piecewise", points: [[0, 1], [0.3, 0.85], [0.6, 0.25], [0.85, 0.02], [1, 0]] },

    "처음으로"를 눌러 직선에서 시작해, 체크리스트 네 항목을 모두 통과하는 배고픔 커브를 만들어 보라. 통과한 뒤에는 포만도 x = 0.95에서 내 커브와 점선 수식 커브의 값을 비교하라. 수식 커브는 0.0025처럼 아주 작지만 0은 아니다. 구간 선형 커브는 정확히 0을 줄 수 있다. 이 차이가 "배부른 심이 가끔 냉장고를 여는" 버그와 그렇지 않은 게임의 차이다.

    "Graham 그림 9.6 근사"의 점 좌표는 원문 그림을 눈으로 읽은 근삿값이다. 원문은 점 좌표를 수치로 밝히지 않는다.

    구간 선형의 대가: 데이터, 툴, 그리고 매끄러움

    구간 선형은 어떤 모양이든 만들 수 있지만 대가가 있다. 점마다 손으로 튜닝해야 하고, 점이 많아지면 의도를 읽기 어렵다. 꺾이는 지점에서 기울기가 갑자기 변하므로 입력이 그 근처를 오가면 점수 변화율이 튄다. Graham도 그림 9.6의 15~60 구간만 2차 커브로 바꾸는 식의 혼합을 예로 든다. "필요한 곳만 맞춤 커브로"가 현실적인 타협이다.

    또 하나: 구간 선형은 그래프 툴이 있어야 의미가 있다. 숫자 배열만 보고 커브를 튜닝하는 디자이너는 없다. 위 에디터 정도의 툴이 엔진과 함께 가야 한다.

    8. 같은 입력, 다른 성격

    커브가 성격을 만든다는 말을 눈으로 확인해 보자. Hamlet에 늑대가 나타났다. 세 주민 모두 같은 입력, 즉 늑대까지의 맨해튼 거리를 엔진의 도망 행동과 같은 bookend [0, 14칸]으로 정규화해 받는다. 다른 것은 커브뿐이다.

    9. Graham의 결투 데모: 커브 네 개로 만든 적

    Graham의 데모는 80년대 메뉴식 RPG를 닮은 텍스트 결투다. 적은 공격, 회복 물약 사용(물약 3개), 도주(성공률 50%) 중 하나를 고르고, ChooseNextAction()이 점수를 계산한 뒤 가중 랜덤으로 고른다. 판단 재료(decision factor)는 네 개의 커브다.

    (9.5) Attack   U = max(min((1 − (hp − minDmg)/(maxDmg − minDmg)) × (1 − a) + a, 1), 0)
    (9.6) Threat   U = min(maxDmg / hp, 1)
    (9.7) Health   U = 1 − 1 / (1 + (e × 0.68)−(hp/maxHp)×12 + 6)
    (9.8) Run     U = 1 − (hp / maxHp)(1/(p+1)⁴) × 0.25
    • Attack Desire: 상대를 한 방에 죽일 수 있게 될수록 선형으로 오른다. a는 튜닝된 공격성, 즉 기본 점수다(그림은 a = 0.6). 막판에 더 공격적이 되고 위험을 감수한다. 여기서 hp는 상대의 체력이다.
    • Threat: 상대가 최대 피해로 때리면 내 현재 체력의 몇 %가 날아가는가.
    • Health Desire: 로지스틱의 변형. 지수의 +6이 커브를 양의 x축 쪽으로 민다. 체력이 줄수록 회복 욕구가 오른다.
    • Run Desire: 남은 물약 수 p가 가파름을 정하는 2차형 커브. 물약이 여럿이면 도주 가능성은 극히 작고, 0개면 훨씬 빨리 커진다.

    행동 점수는 이 넷을 조합한다. 공격 = Attack Desire, 회복 = Health Desire × Threat, 도주 = Run Desire × Threat. Threat을 곱하는 이유는 너무 이른 회복을 막고 상대의 최대 피해에 따라 행동을 바꾸기 위해서다. Graham은 원래 Threat에 상대의 평균 피해를 썼다고 한다. 기대 효용의 정신에는 그쪽이 맞지만 결과가 충분히 엄격하지 않아서 최대 피해로 바꿨고, 그는 이 일을 "커브와 수식 튜닝이 과학보다 예술인 좋은 예"로 든다.

    원문 식 (9.5)와 그림 9.8은 일치하지 않는다

    그림 9.8(a = 0.6)은 상대 hp 약 10까지 1, 약 30까지 직선으로 0.6까지 내려가고, 그 뒤로는 0.6에서 평평하다. 그런데 식 (9.5)를 글자 그대로 계산하면 hp가 maxDmg를 넘은 뒤에도 계속 내려가 결국 0이 된다. 그림과 같은 모양을 얻으려면 분수 항 (hp − minDmg)/(maxDmg − minDmg)를 먼저 [0, 1]로 clamp해야 한다. 아래 위젯은 기본값으로 그림 형태를 쓰고, 체크박스로 식 그대로의 버전을 볼 수 있다. 문헌의 수식을 옮길 때는 그림과 대조해 보는 습관이 필요하다.

    원문은 minDmg, maxDmg 값을 밝히지 않는다. 그림 9.8에서는 대략 10과 30, 그림 9.9(Threat이 hp 약 25부터 내려가 hp 100에서 약 0.25)에서는 maxDmg가 대략 25로 읽힌다. 위젯 기본값은 10/30이다.

    결투 AI 커브 플로터
    x축은 hp / maxHp (maxHp = 100). 네 커브를 동시에 그리고, 세로 점선은 내 hp(Threat·Health·Run 입력)와 상대 hp(Attack 입력)다. 오른쪽은 세 행동 점수와, 그 점수로 가중 랜덤을 했을 때의 선택 확률(UAI.select, strategy "weighted")이다.
    Attack (상대 hp)ThreatHealthRun

    해 볼 것: 물약 p를 3에서 0으로 줄이면 Run 커브가 확 부풀어 오른다. 내 hp를 20 근처로 내리고 p = 0으로 두면 도주 확률이 눈에 띄게 커지지만, 물약이 하나라도 있으면 회복이 압도한다. 공격성 a를 0.9로 올리면 상대 hp와 무관하게 공격 점수가 높게 깔린다. 이것이 Graham이 말한 "적은 값과 가중치로 성격을 더하는" 방식이다.

    위젯은 물약이 0개일 때 회복 점수를 0으로 둔다. 물약 없이 회복할 수 없다는 상식적인 가정이며, 원문 수식에는 이 조건이 적혀 있지 않다.

    10. 커브 선택 체크리스트와 프리셋 팔레트

    Lewis는 응답 곡선 선택이 효용 AI를 "살리거나 망친다"고 말하며 간단한 체크리스트를 제시한다. 에디터의 진단 칩이 바로 이 순서를 따른다.

    1. 입력과 bookend: 무엇을 점수화하는지 정하고, 어떤 값이 0이고 어떤 값이 1인지 clamp 범위를 정한다.
    2. 방향: 입력이 1에 가까워질수록 이 결정이 더 중요해지는가, 덜 중요해지는가. Lewis의 예에서 도둑은 대상의 재산에 증가 커브를, 대상까지의 거리에 감소 커브를 쓴다. 멀수록 접근이 위험하기 때문이다.
    3. 단조성: 특별한 행동이 필요하지 않다면 단조 커브가 낫다. 점수를 이해하기가 훨씬 쉽다. Heart of Thorns의 커브도 대부분 단조였다. 예외는 역U 모양 거리 커브로, 적이 너무 가깝지도 너무 멀지도 않을 때만 다가가게 만든다.
    4. 끝점: 최소·최대 입력에서 점수가 0이 되어야 하는가, 아니면 우선순위만 낮춰야 하는가. 대부분은 "완벽한 상황이면 완벽한 점수", 즉 1로 두는 것이 가장 단순하다.

    프리셋 팔레트와 advanced mode

    Lewis에 따르면 Heart of Thorns에서 쓴 응답 곡선은 "대부분 작은 프리셋 팔레트에서 골랐다". 임의 곡선을 허용하는 것은 강력하지만 겁을 주고 직관적이지 않을 수 있으므로, 그런 설정 능력은 "advanced mode" 뒤에 숨기고 대부분의 경우 프리셋을 쓰게 하라는 것이 그의 권고다. 우리 엔진의 UAI.PRESETS와 위 에디터의 구조(프리셋 버튼이 먼저, 파라미터 슬라이더는 접히는 고급 모드)가 이 원칙을 따른다.

    왜 프리셋이 결국 더 빠른가
    • 공유 어휘: "이건 cooldown 커브야"라는 한마디로 팀 전체가 모양과 의도를 안다. m = 4.37 같은 숫자는 대화가 되지 않는다.
    • 재사용 단위: Heart of Thorns는 미리 정의한 결정 패턴이 100개가 넘었고, 그것을 조합해 새 생물을 몇 분 만에 구성했다. 패턴이 재사용되려면 그 안의 커브도 표준화되어 있어야 한다.
    • 버그 표면 축소: 프리셋은 한 번 검증해 두면 된다. 자유 커브는 데이터 하나하나가 검증 대상이다(11절의 함정들).

    11. 실무 함정

    11.1 0으로 떨어지는 커브 = 거부권

    Lewis의 구조에서 consideration 점수는 모두 곱해진다. 그래서 어떤 consideration이든 결정 전체를 무효화할 수 있다. 하나가 0이면 나머지가 아무리 높아도 0이다. 우리 엔진의 Reasoner도 같은 성질을 이용해, 점수가 0이 되는 순간 남은 consideration 계산을 건너뛴다(early-out).

    for (const c of a.considerations) {
  if (!alive) { parts.push({ name: c.name, raw: null, x: null, y: null, skipped: true }); continue; }
  const raw = c.input(ctx);
  const x = UAI.normalize(raw, c.lo, c.hi);
  const y = c.fn(x);
  parts.push({ name: c.name, raw, x, y });
  if (y <= 0) alive = false;
}

    이 성질은 스위치 커브의 존재 이유이기도 하지만, 의도치 않게 생기면 찾기 어려운 버그가 된다. "선형 감소"는 x = 1에서 정확히 0이다. bookend 끝까지 간 입력이 조용히 행동 전체를 꺼 버린다. 끝점을 0으로 둘지 조금 띄울지(b = 0.05 등)는 체크리스트 4단계에서 의도적으로 정해야 한다. 여러 커브를 곱했을 때 점수가 깎이는 문제와 그 보정은 04장의 주제다.

    11.2 극단 지수의 민감도

    xk에서 k가 크면 커브 대부분이 0 근처에 깔리고 모든 변화가 1 바로 앞에 몰린다. 입력이 조금만 흔들려도 점수가 크게 출렁인다. 아래 표는 UAI.curve({type:"poly", m:1, k})의 실제 값이다.

    k = 10이면 x가 0.90에서 0.95로 0.05만 움직여도 점수가 두 배 가까이 뛰고, x = 0.5까지는 사실상 0이다. 이 커브가 곱셈 결합에 들어가면 x = 0.5 근처에서 사실상 거부권을 행사한다. Lewis의 cooldown x5처럼 "끝 무렵에 급등"이 정확히 원하는 효과라면 괜찮지만, 그렇지 않다면 k를 낮추거나 로지스틱으로 문턱 위치(c)를 직접 정하는 편이 튜닝하기 쉽다. 또한 bookend가 실제 입력 분포보다 넓으면 입력이 늘 x = 0.3~0.6에 머물러 커브의 평평한 부분만 쓰게 된다. 지수를 올리기 전에 bookend부터 의심하라.

    11.3 범위 밖 입력과 clamp

    UAI.normalize는 범위 밖 입력을 끝값으로 고정하고, UAI.curve는 출력도 [0, 1]로 자른다. 두 clamp 모두 필요하다. 입력 clamp가 없으면 x = 1.3 같은 값이 다항 커브에 들어가 1을 훌쩍 넘거나(1.36 ≈ 4.8), 로짓처럼 [0, 1] 밖에서 정의되지 않는 커브에서 NaN이 나온다. 출력 clamp가 없으면 b로 위로 민 커브(에디터의 "해 볼 것" 3번)가 1을 넘어 다른 consideration과 곱할 때 점수를 부풀린다. 반대로 clamp는 정보를 버린다는 점도 기억하라. 100 m와 1000 m가 같은 점수라는 것은 의도한 결정이어야 한다.

    11.4 비정수 지수와 음수 밑

    c로 수평 이동한 다항 커브에서 x < c이면 밑 x − c가 음수가 된다. 정수 지수라면 문제없지만, k = 0.5 같은 비정수 지수에서 Math.pow(-0.2, 0.5)는 NaN이다. 엔진은 이를 피하려고 부호를 따로 떼어 |d|k를 계산하고 부호를 다시 붙인다(4절의 poly). PB는 FMath::Pow를 그대로 쓰고 NaN을 Sanitize가 0으로 바꾼다. 같은 spec {type:"poly", m:-1, k:0.5, b:1, c:0.5}, 즉 "x가 0.5를 넘으면 1 − √(x − 0.5)"를 세 방식으로 계산하면 이렇다.

    x < 0.5 구간에서 엔진은 1(1 + √|d|가 clamp됨), PB는 0이다. 디자이너가 "0.5 아래는 만점"을 기대했다면 PB에서는 정반대로 거부권이 걸린다. 이런 커브는 어느 엔진에서나 같은 결과가 나오도록 c = 0인 형태로 다시 쓰거나(예: 구간 선형), 이동 없이 invert로 방향을 바꾸는 편이 안전하다. 마지막 행은 5절에서 본 PB 로짓의 끝점 문제를 같은 방식으로 보여 준다.

    커브 데이터 검증 체크
    • 모든 커브를 x = 0, 0.25, 0.5, 0.75, 1에서 샘플링해 NaN·무한대가 없는지 툴에서 검사한다(에디터 아래의 샘플 행).
    • 0이 되는 구간이 있는 커브는 "의도한 거부권인가?" 표시를 데이터에 남긴다.
    • 엔진을 옮기면 프리셋 전체를 두 구현에서 샘플링해 비교하는 테스트를 만든다. 이 장의 비교 위젯이 그 테스트의 축소판이다.

    핵심 요약

    • 반응 커브는 게임 상태값을 0~1 효용으로 바꾸는 함수다. 정답 수식은 없고, Graham의 말대로 "과학보다 예술"에 가깝다. 그래서 어휘·데이터 표현·체크리스트가 필요하다.
    • 커브 앞에는 항상 bookend 정규화가 있다. UAI.normalize(v, lo, hi)는 범위 밖을 끝값에 고정한다. bookend는 커브만큼 강력한 튜닝 손잡이다.
    • 선형·다항(지연/회전)·로지스틱·로짓·종형·사인·스위치·구간 선형은 각각 다른 행동 느낌을 준다. 구간 선형은 Sims의 배고픔처럼 수식으로 못 만드는 모양을 점으로 만든다.
    • uai.js는 m, k, b, c 네 변수로 모든 커브를 spec 데이터로 표현한다. 그러나 IAUS 매뉴얼·ProjectBorealis·uai.js의 m, k, b, c 의미는 서로 다르다(특히 Normal, Logistic). 커브 데이터에는 구현을 함께 기록하라.
    • 같은 입력에 다른 커브를 주면 성격이 생긴다. 성격을 코드가 아니라 데이터로 표현하면 새 캐릭터는 커브 교체로 만들어진다.
    • 체크리스트: 입력·bookend → 증가/감소 → 단조성(역U 예외) → 끝점. 대부분은 프리셋 팔레트로 해결하고 임의 커브는 advanced mode 뒤에 둔다.
    • 함정: 0이 되는 끝점은 곱셈 결합에서 거부권이다. 극단 지수는 민감하고, 비정수 지수와 음수 밑은 구현마다 다른 결과를 낸다.

    확인 문제

    Lewis의 예처럼 거리 bookend를 [0 m, 100 m]로 두었다. 대상이 130 m에 있을 때 정규화된 입력 x는?
    최댓값을 넘는 입력은 자동으로 1이 된다(UAI.normalize의 clamp01). 1.3이 그대로 커브에 들어가면 다항 커브는 1을 넘고 로짓은 NaN이 될 수 있다.
    uai.js에서 {type:"normal", m:1, k:0.15, c:0.5}의 혹을 더 넓게 만들려면?
    uai.js의 normal은 m·exp(−(x−c)²/(2k²)) + b여서 k가 σ 역할을 한다. 키우면 넓어진다. 매뉴얼에서는 m이 폭이고, PB에서는 Exponent가 클수록 오히려 좁아진다. 이 차이가 5절의 함정이다.
    Graham이 The Sims 배고픔 예에서 회전 2차 커브 대신 구간 선형 커브가 필요하다고 한 이유는?
    디자이너는 "문턱까지 완전히 무시 → 조금 배고픔 → 갑자기 매우 배고픔"을 원한다. 간단한 수식으로는 이 모양을 만들기 어렵고, 작지만 0이 아닌 점수는 결국 선택된다. 구간 선형은 정확히 0을 줄 수 있다.
    "상대와 거리" consideration에 "선형 감소"를 쓰고 bookend를 [0, 12]로 두었다. 상대가 15칸 떨어져 있을 때 그 행동의 최종 점수는?
    x = clamp(15/12) = 1이고, 선형 감소는 x = 1에서 정확히 0이다. 곱셈 결합이라 다른 점수와 상관없이 0이 되고, Reasoner는 early-out으로 나머지를 건너뛴다. 의도한 거부권이 아니라면 끝점을 b로 띄워야 한다.
    spec {type:"poly", m:-1, k:0.5, b:1, c:0.5}를 x = 0.3에서 계산하면 uai.js와 ProjectBorealis 수식은 각각 얼마인가?
    밑 x − c = −0.2에 지수 0.5. uai.js는 부호를 보존해 −1·(−1)·√0.2 + 1 ≈ 1.447 → clamp 1. PB는 Pow(−0.2, 0.5) = NaN → Sanitize → 0. 같은 데이터가 한쪽에선 만점, 한쪽에선 거부권이다.
    Graham의 결투 데모에서 회복 행동 점수는 Health Desire × Threat이다. Threat에 상대의 평균 피해 대신 최대 피해를 쓰게 된 이유는?
    Graham은 평균 피해가 기대 효용의 정신에는 더 맞지만 "충분히 엄격한 결과를 내지 못해" 최대 피해로 바꿨다고 적는다. 이론보다 플레이 결과로 커브를 고르는, "과학보다 예술"의 사례다.
    다음 장으로커브 하나는 consideration 하나의 점수만 만든다. 실제 행동에는 거리·체력·쿨다운 같은 consideration이 여럿 붙는다. 04장에서는 이 점수들을 하나로 합치는 방법(곱·평균·최솟값)과, 곱할수록 점수가 깎이는 문제를 IAUS의 보정식 UAI.compensate로 푸는 법을 다룬다.
