캡스톤: Hamlet 마을 시뮬레이터

11개 장에 걸쳐 한 부품씩 만든 uai.js를 이제 한꺼번에 돌린다. 늑대를 풀고, 빵집을 닫고, 결합 방식과 선택 전략을 바꿔 가며 Hamlet 주민들이 왜 그렇게 움직이는지 숫자로 추적한다. 끝으로 과제와 종합 문제로 코스 전체를 점검하고, 블로그 원문에서 시작한 여정을 되짚는다.

학습 목표

  • 한 tick 안에서 욕구 감소 → 결정 트리거 → 평가 → 선택 → 전환 판단 → 실행이 어떤 순서로 일어나는지 엔진 코드로 설명할 수 있다.
  • 인스펙터의 후보 표(consideration 분해·rank·점수·선택 확률)를 보고 "왜 이 행동을 골랐나"에 답할 수 있다.
  • 결합 방식·선택 전략·관성·thinkEvery·긴급도 커브를 바꿨을 때 마을 통계가 어떻게 변하는지 실험으로 확인할 수 있다.
  • 엔진 파일을 고치지 않고 Reasoner 재생성과 데이터 교체만으로 행동을 튜닝하는 방법을 안다.

1. 부품 조립도: 한 tick 해부

샌드박스를 돌리기 전에 World.tick() 한 번이 무슨 일을 하는지 순서대로 짚어 보자. 각 단계는 코스의 한 장에 대응한다. 샌드박스에서 이상한 행동을 봤을 때 "몇 번 단계에서 어긋났나"를 물으면 원인을 훨씬 빨리 찾는다.

한 tick의 8단계
재생을 누르면 단계별로 강조된다. ①~⑦은 uai.js 안에서, ⑧은 이 페이지가 tick 바깥에서 하는 일이다.

③이 핵심이다. 엔진은 주민이 할 일이 없을 때만 숙고하고, 바쁠 때는 thinkEvery tick마다 "rank가 더 높은 일이 생겼나"만 확인한다. 이 두 갈래가 06장 관성에서 본 "결정 보류"와 09장 time-slicing의 실제 구현이다.

// 2) 결정 (06장, GAP1 11장): 숙고는 할 일이 끝났을 때만, 반응(인터럽트)은 주기적으로 검사
const due = (this.tickCount + a.thinkOffset) % this.thinkEvery === 0;
if (!a.current) this.think(a);
else if (due) this.think(a, true);
think(a, interruptOnly) {
  const res = this.reasoner.decide(a, this, this.rng);
  a.lastEval = res;
  const c = res.chosen;
  if (!c) return;
  if (a.current && a.current.action === c.action.id && a.current.target === c.target) return;
  if (interruptOnly) {
    const curAct = this.reasoner.actions.find(x => x.id === a.current.action);
    if (c.rank <= curAct.rank) return;
  }

그래서 같은 rank끼리는 실행 도중에 갈아타지 않는다. 늑대(도망치기, rank 10)만이 빵집에 가던 주민(이용하기, rank 0)을 멈춰 세울 수 있다. 05장 Dual Utility의 rank가 여기서 "인터럽트 권한"으로도 쓰인다.

2. Hamlet 샌드박스

아래 마을은 UAI.makeHamlet({ seed })가 만든 기본 마을이다. 격자 24×16칸, tick 하나는 게임 시간 1분, 06:00에 시작한다. 같은 시드와 같은 설정이면 언제 돌려도 똑같이 흘러간다(09장 시드 RNG).

  • 도구: 선택(주민 클릭 → 인스펙터), 늑대(클릭한 칸에 위협 출현, 점선 마름모는 도망 판단 반경 14칸), 배치(팔레트의 오브젝트 설치), 삭제(오브젝트 철거), 주민 추가.
  • 속도는 화면 프레임당 tick 수다. 1×면 초당 약 60분이 흐르고, 200×면 하루가 0.1초 남짓에 지나간다. 움직임을 눈으로 따라가려면 0.25× 이하가 좋다.
  • 점선은 지금 향하는 곳(엔진의 step()은 x를 먼저 맞추고 y를 맞추므로 ㄱ자 경로), 옅은 선은 최근 지나온 칸이다.
  • 탭을 다른 곳으로 옮기면 자동으로 멈추고, 돌아오면 다시 재생된다.

3. 인스펙터 읽는 법: "왜 저기로 갔지?"

효용 AI의 고질적인 약점은 "예측하기 어렵다"는 것이다(01장). 그래서 실무에서는 결정마다 후보와 점수를 표로 남긴다. Dragon Age: Inquisition 팀도 평가 결과를 디버그 테이블로 기록한 것이 디버깅에 큰 도움이 됐다고 적었다(10장). 인스펙터의 후보 표가 바로 그 테이블이다. 읽는 순서는 이렇다.

  1. 상태 열부터 본다. rank 탈락이 보이면 dual 전략이 더 높은 rank 후보 때문에 버킷째 버린 것이다. 늑대가 있으면 이용하기·수다 떨기가 전부 이 상태가 된다.
  2. 점수가 낮은 후보의 consideration 칩을 본다. 빨간 칩(0.2 미만)이 범인이다. 예를 들어 빵집 점수가 낮다면 "광고 가치"가 낮은지(배가 별로 안 고프다) "거리"가 낮은지(멀다) 칩 하나로 갈린다. 생략으로 표시된 칩은 앞 consideration이 0이 되어 early-out된 것이다(04장).
  3. 관성 표시를 확인한다. 현재 후보에는 inertia가 더해져 있다. 차점과의 차이가 inertia보다 작다면 관성 덕분에 유지되고 있는 것이다(06장).
  4. 선택 확률을 본다. weighted·topPct·dual에서는 1등이 아니어도 뽑힐 수 있다. 확률 열이 UAI.select가 돌려준 pool의 p다(05장).
  5. trace 띠로 패턴을 본다. 한 행동이 짧게 쪼개져 반복되면 진동(dithering), 한 색이 하루 종일 이어지면 특정 오브젝트 쏠림이다(11장).
자기 혼잡 효과 — 인스펙터에서 보이는 엔진의 특성 주민이 오브젝트를 이용 중이면 그 오브젝트의 users에 자기 자신이 포함된다. 그래서 바쁜 동안 다시 평가하면 지금 쓰고 있는 오브젝트의 "혼잡" 칩이 스스로 깎이고, 정원이 꽉 차면 후보 목록(targets)에서 아예 빠진다. 기본 엔진은 같은 rank끼리 갈아타지 않으므로 행동에는 영향이 없지만, 전면 재평가를 켜면 이 효과가 진동의 원인이 된다. 6절 "진동 관찰" 시나리오와 8절 과제 9에서 다룬다.

표의 점수는 UAI.combine(ys, 결합방식) × weight에 현재 행동이면 inertia를 더한 값이다. 산책(wander)은 weight가 0.12라서 consideration이 1개뿐인데도 항상 0.12 근처에 머문다. 이 "바닥 점수"보다 나은 일이 없을 때 주민은 산책한다.

4. 엔진 설정: 파일을 고치지 않고 튜닝하기

설정 패널은 uai.js를 한 줄도 바꾸지 않는다. 엔진이 노출한 데이터와 생성자만 갈아 끼운다. 실제 게임에서 디자이너가 데이터 파일과 슬라이더로 AI를 다듬는 것과 같은 구조다. Guild Wars 2: Heart of Thorns의 consideration·커브도 데이터 주도로 조합되었다(11장).

설정을 바꾸면 페이지는 아래 코드를 실행한다. Reasoner는 생성할 때 consideration마다 커브 함수를 미리 만들어 두므로(fn: UAI.curve(...)) 옵션을 바꾸려면 새로 만드는 편이 깔끔하다. 진행 중인 행동은 그대로 이어진다. 행동 id가 같으니 act()가 새 Reasoner에서 같은 행동의 run을 찾는다.

// 페이지 코드 (엔진 아님)
function applyEngine(sim) {
  applyNeedCurves(sim.cfg);                       // UAI.NEED_CURVE[n] ← 프리셋 사본 또는 원본 사본
  sim.world.reasoner = makeReasoner(sim.cfg, sim.factory);
  sim.world.thinkEvery = Math.max(1, sim.cfg.thinkEvery | 0);
  // 새 행동 세트에 없는 행동을 하던 주민은 정리 (과제에서 행동을 바꿀 때 대비)
  ...
}
function makeReasoner(cfg, factory) {
  return new UAI.Reasoner((factory || UAI.hamletActions)(),
    { combine: cfg.combine, strategy: cfg.strategy, pct: cfg.pct, n: cfg.n, inertia: cfg.inertia });
}

긴급도 커브는 UAI.adValue가 호출될 때마다 UAI.NEED_CURVE[n]을 새로 읽으므로 교체 즉시 반영된다. 페이지는 로드 시점에 원본을 깊은 복사해 두고, "원래 커브"를 고르면 그 사본을 되돌려 놓는다.

계측 래퍼와 "전면 재평가" 변형은 어떻게 만드나

통계(결정 수, 실행 중 전환 수)를 세려고 페이지는 월드 인스턴스의 think만 감싼다. World.prototype은 건드리지 않는다. tick()은 this.think(...)로 부르므로 인스턴스 속성이 먼저 잡힌다.

const base = UAI.World.prototype.think;
w.think = function (a, interruptOnly) {
  base.call(this, a, sim.cfg.fullReplan ? false : interruptOnly);
  // ... trace가 늘었으면 decisions++, 원래 하던 일이 있었으면 switches++
};

전면 재평가는 interruptOnly를 false로 바꿔 넘기는 것뿐이다. 엔진의 "할 일이 끝나야 숙고" 규칙을 없앤, 일부러 나쁘게 만든 교육용 변형이다. 이것을 켜고 thinkEvery=1, inertia=0으로 두면 블로그 원문이 경고한 진동이 그대로 재현된다.

5. 통계 대시보드

한 주민을 들여다보는 인스펙터와 달리 대시보드는 마을 전체를 본다. 튜닝은 대개 "이 숫자를 이 범위에 넣자"는 목표에서 시작한다(11장). 통계는 tick마다 표본을 모으고, 리셋·시나리오·가져오기 때 초기화된다.

마을 통계
굶주림 = 배고픔 수치 15 미만, 기력 고갈 = 기력 10 미만인 주민·tick의 비율. 실행 중 전환 = 하던 행동을 끝내기 전에 다른 결정으로 바꾼 횟수.
주민 평균 욕구 (10분 간격, 최근 3일)
행동 분포 (주민·tick 비율)
오브젝트 이용률 (평균 점유 = users ÷ capacity)

통계를 해석할 때 주의할 점이 있다. 평균 욕구가 높아도 굶주림 비율이 높을 수 있다. 다섯 명이 배부르고 한 명만 굶어도 평균은 괜찮아 보이기 때문이다. 그래서 "평균"과 "꼬리(임계치 미만 비율)"를 함께 본다. The Sims처럼 아사 직전의 주민이 TV를 보는 장면이 플레이어의 신뢰를 무너뜨린다는 점을 떠올리자(05장).

6. 시나리오 실험실

시나리오 버튼은 현재 시드로 마을을 리셋하고 엔진 설정을 기본값으로 돌린 뒤 시나리오의 변경만 적용한다. 그래서 같은 시드에서 두 시나리오를 돌리면 공정하게 비교할 수 있다. 적용하면 샌드박스로 이동해 재생을 시작하고, 상단 배너에 관찰 포인트를 띄운다. 속도를 20× 이상으로 올려 하루 이틀 돌린 뒤 대시보드를 보자.

비교 실험 요령 시나리오 하나를 돌린 뒤 대시보드 숫자를 메모하고, 같은 시드로 "기본 마을"(리셋)을 같은 시간만큼 돌려 비교한다. 시계가 같은 시각일 때 숫자를 읽어야 낮/밤 차이가 섞이지 않는다. 시드를 2~3개 바꿔 반복하면 우연인지 경향인지 구별된다.

7. 설정 내보내기·가져오기

튜닝 결과는 코드가 아니라 데이터로 남겨야 공유와 회귀 비교가 쉽다(11장). 아래 JSON에는 시드, 엔진 설정, 커브 선택, 오브젝트 배치, 주민 이름·위치·성격이 들어간다. 가져오면 그 시드로 새로 시작한다. 욕구 초깃값은 시드에서 다시 생성되고 시각은 06:00으로 돌아간다.

설정 JSON
내보내기 → 복사해 두었다가 → 붙여 넣고 가져오기. 잘못된 값은 기본값으로 바꾸고 알려 준다.

8. 실습 과제

★는 샌드박스 조작만으로, ★★는 콘솔 몇 줄로, ★★★는 설계와 코드 작성이 필요한 과제다. 콘솔 과제는 이 페이지가 노출한 HAMLET 객체를 쓴다. HAMLET.setActions(factory)는 행동 세트를 바꾸고 Reasoner를 다시 만든다. 이후 설정 패널을 바꿔도 이 행동 세트가 유지되며, HAMLET.resetActions()로 원래대로 돌린다. uai.js를 직접 고치는 과제는 반드시 코스 폴더를 통째로 복사한 사본에서 한다.

★ 과제 1. 관성 스윕 06 관성

"진동 관찰" 시나리오를 적용한 뒤 inertia를 0, 0.05, 0.1, 0.2, 0.3으로 바꿔 가며 각각 하루씩 돌리고 "실행 중 전환/시간"을 표로 적어라. 전환이 급감하는 문턱값은 어디인가? 그 값이 후보 표에서 1등과 2등의 전형적인 점수 차와 어떤 관계인지 설명하라.

★ 과제 2. 늑대 반응 지연 측정 09 루프 05 dual

일시정지 상태에서 빵집으로 걸어가는 주민 근처에 늑대를 놓고 "1 tick"을 눌러 가며 도망치기로 바뀔 때까지의 tick 수를 센다. thinkEvery 1, 5, 20에서 반복하라. 할 일이 없던 주민과 바빴던 주민의 차이를 엔진 코드(due 계산과 thinkOffset)로 설명하라.

★★ 과제 3. 결합 방식 비교 04 결합

같은 시드로 결합 방식을 compensated, product, min, mean으로 바꿔 각각 2일씩 돌리고 행동 분포에서 "산책" 비율과 굶주림 비율을 비교하라. 이용하기는 consideration이 3개, 산책은 1개다. 왜 곱셈 계열에서 산책 비율이 달라지는지 UAI.compensate 수식으로 설명하라. mean에서는 어떤 거부권이 사라지는가?

★★ 과제 4. 블라인드 성격 테스트 07 욕구·traits

친구에게 주민 세 명의 traits를 몰래 바꾸게 하고(예: 미식가 hunger 2.5, 잠꾸러기 energy 2.5, 외톨이 social 0.2) 내보낸 JSON의 traits 부분만 지운 채 받아라. trace 띠와 행동 분포만으로 누가 어떤 성격인지 맞혀 보라. 맞히기 어려웠다면 traits가 효용 계산의 어디에 곱해지기 때문인지 UAI.adValue로 설명하라.

★★ 과제 5. 낮/밤 sine 커브로 수면 시간대 선호 03 커브(sine) 08 타깃 컨텍스트

지금은 주민이 기력만 떨어지면 대낮에도 집에 간다. 집에 대해서만 "밤일수록 선호"하는 consideration을 추가하라. 이용하기 행동은 모든 오브젝트가 공유하므로 대상이 집이 아닐 때는 1(영향 없음)을 돌려줘야 한다. 아래 출발점에서 c와 b를 조정해 22시~06시 수면 비율을 높이되, 기력이 바닥난 주민의 낮잠은 막지 않게 하라. 
const night = UAI.curve({ type: "sine", m: 0.6, k: 1, c: 0.75, b: 0.2 }); // 자정 1.0, 정오 0.4
HAMLET.setActions(() => {
  const acts = UAI.hamletActions();
  const use = acts.find(a => a.id === "use");
  use.considerations.push({
    name: "수면 시간대",
    input: ({ world, target }) => (target.type === "house" ? night(world.hour() / 24) : 1),
    curve: "선형 증가", // 이미 0~1이므로 그대로 통과
  });
  return acts;
});
생각할 점: consideration이 4개가 되면 compensated의 보정량(1 − 1/n)도 바뀐다. 집이 아닌 오브젝트 점수도 조금 달라지는 이유다.

★★ 과제 6. dual rank로 "축제 참여" 강제 05 Dual Utility 10 rank 체계

18시~21시에는 욕구와 상관없이 광장 무대에 모이게 하라. 욕구 행동(rank 0)보다 높고 도망치기(rank 10)보다 낮은 rank 5 행동을 추가한다. 
HAMLET.setActions(() => {
  const acts = UAI.hamletActions();
  const use = acts.find(a => a.id === "use");
  acts.push(Object.assign({}, use, {
    id: "festival", label: "축제 참여", rank: 5,
    targets: ({ world }) => world.objects.filter(o => o.type === "stage" && o.users < o.capacity),
    considerations: [
      { name: "18시 이후", input: ({ world }) => world.hour(), lo: 0, hi: 24, curve: { type: "step", m: 1, c: 0.75 } },
      { name: "21시 이전", input: ({ world }) => world.hour(), lo: 0, hi: 24, curve: { type: "step", m: -1, c: 0.875 } },
      use.considerations[1], // 거리
    ],
  }));
  return acts;
});
관찰: 축제 중 늑대가 나오면 무엇이 이기는가? 무대 정원(5)을 넘는 주민은 어떻게 되는가? 그리고 시간 창을 step 대신 종형(normal) 커브로 바꿔 보라. 종형은 0이 되지 않으므로 rank 5 버킷이 하루 종일 살아 있어 욕구 행동이 영영 선택되지 않는다. "버킷 밖에서는 정확히 0"이라는 dual utility의 전제를 직접 확인하라.

★★★ 과제 7. 새 욕구 "위생" 추가 설계 07 욕구·스마트 오브젝트 03 커브

코스 폴더를 복사한 사본의 assets/uai.js에 다섯 번째 욕구 hygiene(위생)를 추가하라. 손댈 곳은 NEEDS, NEED_LABEL, NEED_DECAY, NEED_CURVE, OBJECT_TYPES(새 오브젝트 "목욕탕" 추가, 우물에 위생 광고 추가)이고, 필요하면 makeHamlet의 배치 목록도 고친다. adValue와 tick은 NEEDS와 ads를 순회하므로 수정이 필요 없다는 것을 코드로 확인하라. 이 페이지의 인스펙터·커브 패널·차트는 UAI.NEEDS를 순회하므로 사본에서도 다섯 번째 막대가 자동으로 나타난다. 설계 질문: 위생 감소 속도는 얼마가 적당한가? 선술집은 위생을 깎아야 하는가? 위생 긴급도는 배고픔처럼 구간 선형이 좋은가, 2차 커브가 좋은가?

★★★ 과제 8. 흉년 밸런싱 챌린지 11 튜닝 07 욕구

"흉년" 시나리오에서는 굶주림 비율은 0 근처로 버티지만 3일 평균 배고픔이 약 79에서 59로 떨어진다. 오브젝트를 추가하지 않고 엔진 설정·커브·traits만 바꿔 평균 배고픔을 기본 마을 수준에 최대한 가깝게 되돌려라(차트에서 배고픔 선을 본다). 주민을 여섯 명 더 넣어 난도를 올려도 좋다. 결과를 JSON으로 내보내 시드 3개에서 재현되는지 확인하라. 어떤 손잡이가 가장 효과적이었는가? 밭(배고픔 +25, 재미 −5)을 더 자주 쓰게 만든 대가는 무엇이었는가?

★★★ 과제 9. 자기 혼잡 효과 고치기 04 consideration 08 타깃 11 디버깅

3절 경고의 원인을 고쳐라. 혼잡 계산에서 자기 자신을 빼고, 자기가 쓰고 있는 오브젝트는 정원이 차도 후보에 남겨야 한다. 
HAMLET.setActions(() => {
  const acts = UAI.hamletActions();
  const use = acts.find(a => a.id === "use");
  const mine = (agent, o) => (agent.current && agent.current.target === o && agent.current.using ? 1 : 0);
  use.targets = ({ agent, world }) => world.objects.filter(o => o.users - mine(agent, o) < o.capacity);
  use.considerations[2].input = ({ agent, target }) => (target.users - mine(agent, target)) / target.capacity;
  return acts;
});
"진동 관찰" 시나리오에서 수정 전후의 실행 중 전환 수를 비교하라. 진동이 완전히 사라지지 않는다면 남은 원인은 무엇인가? (힌트: 이용하는 동안 욕구가 차면서 광고 가치 자체가 떨어진다. 06장의 "행동이 끝날 때까지 결정 보류"가 왜 필요한지 다시 생각해 보라.)

★★ 과제 10. 거리 bookend 점검 03 정규화 08 거리

이용하기의 거리 consideration은 lo 0, hi 30, 커브 1 − x²다. 24×16 격자에서 맨해튼 거리는 최대 38이다. 지도 구석(0,0)에 주민을 추가하고 반대편 구석(23,15) 근처에 빵집을 하나 더 배치해 후보 표에서 그 빵집의 거리 칩을 확인하라. 30칸 너머는 모두 0이 되어 early-out된다. 의도된 설계인가? hi를 40으로 바꾸면 마을 전체 행동이 어떻게 달라질지 예측하고, 콘솔에서 use.considerations[1].hi = 40으로 바꿔 검증하라.

9. 종합 확인 문제

1~11장 전 범위다. 틀린 문제는 옆에 붙은 장으로 돌아가 복습하자.

[01장] Game AI Pro 1권 4장이 효용 기반 AI의 단점으로 꼽은 것으로 가장 알맞은 것은?
첫째는 FSM/HFSM, 둘째는 BT, 넷째는 GOAP의 함정이다. 효용 AI는 적응성과 창발성을 얻는 대신 예측 가능성과 튜닝 비용을 치른다. 01장
[02장] 고양이 장난감 A는 $4.99에 2일 배송, B는 $2.99에 5일 배송이다. 기다리는 하루를 $1로 환산하면 어느 쪽이 나은가?
A = 4.99 + 2 = 6.99, B = 2.99 + 5 = 7.99. 효용은 가격표가 아니라 맥락(기다림의 비용)까지 포함한 선호다. 단위를 하나로 맞추는 것이 효용 설계의 첫걸음이다. 02장
[02장] 선택지 A의 효용 D=0.85·성공 확률 P=0.6, 선택지 B의 D=0.6·P=0.9다. 기대 효용 EU = Σ D·P 기준으로 고르면?
0.85 × 0.6 = 0.51, 0.6 × 0.9 = 0.54. 효용이 큰 선택지라도 성공 확률이 낮으면 기대 효용에서 진다. 02장
[03장] UAI.normalize(130, 0, 100)의 값은?
clamp01((v − lo) / (hi − lo))이므로 1.3이 1로 잘린다. 과제 10의 거리 30칸 bookend도 같은 원리로 30칸 너머가 전부 같은 값이 된다. 03장
[03장·07장] Hamlet의 배고픔 긴급도(NEED_CURVE.hunger)가 수식 곡선이 아니라 구간 선형(piecewise)인 이유로 가장 알맞은 것은?
Graham은 Sims의 배고픔 곡선을 예로 들며 수식 곡선은 배가 불러도 가끔 먹게 만든다고 지적했다. 6절 "배고픔 커브를 선형으로" 시나리오에서 식사 결정 시 평균 배고픔이 어떻게 변하는지 확인할 수 있다. 03장
[04장] consideration이 3개인 행동에서 한 consideration 점수가 0.5일 때 UAI.compensate(0.5, 3)의 값은?
modification = 1 − 1/3 = 0.667, makeUp = (1 − 0.5) × 0.667 = 0.333, 결과 = 0.5 + 0.333 × 0.5 = 0.667. consideration이 많아질수록 곱이 깎이는 것을 보정한다. 04장
[04장] Reasoner.evaluate는 consideration 하나가 0이 되면 나머지를 건너뛴다(early-out). 이 사실에서 나오는 실무 규칙은?
GAP3 13장(Lewis)도 싼 consideration을 먼저, 비싼 LOS 검사를 맨 끝에 두라고 권한다. 하한을 올리면 거부권이 사라져 오히려 버그가 된다. 04장
[05장] 늑대가 가까이 있어 도망치기(rank 10) 점수가 0.05, 선술집 이용(rank 0) 점수가 0.9다. 전략이 dual이면?
Dill의 dual utility는 먼저 최고 rank만 남기고 그 안에서 weight로 고른다. 같은 상황에서 best라면 선술집을 고른다. Sims에서 배고픔 버킷이 재미 버킷의 높은 TV 점수를 무시하는 것과 같은 구조다. 05장
[05장] 후보 점수가 0.8, 0.7, 0.5이고 { strategy: "topPct", pct: 0.15 }일 때 0.7 후보가 뽑힐 확률은?
문턱 = 0.8 × (1 − 0.15) = 0.68. 0.5는 탈락하고 0.8과 0.7만 남아 점수 비례로 뽑는다. 0.7 / (0.8 + 0.7) ≈ 0.467. 05장
[06장] 기본 엔진에서 빵집에 가던 주민이 도중에 "선술집 점수가 더 높아졌다"는 이유로 방향을 틀지 않는 까닭은?
if (c.rank <= curAct.rank) return; 줄 때문이다. Sims Medieval처럼 행동 큐가 비었을 때만 숙고하는 방식이다. "전면 재평가"를 켜면 이 보호막이 사라지고 진동이 나타난다. 06장
[07장] 배고픔 수치 70인 주민에게 빵집(배고픔 +60, 성격 1)의 광고 가치는? (배고픔 긴급도 커브의 충족도 0.7 값은 0.158)
한계효용 처리: room = min(60, 100 − 70) = 30 → 30/100 × 0.158 × 1 ≈ 0.047. 이미 찬 만큼은 의미가 없다는 것을 adValue가 반영한다. 07장
[08장] 기본 마을(오브젝트 8개 모두 빈 상태, 주민 6명)에서 한 주민을 평가하면 후보 행(row)은 몇 개인가?
대상이 있는 행동은 (행동, 대상) 쌍마다 한 줄이다. 수다 상대는 자기를 뺀 5명이다. 그래서 오브젝트와 주민이 늘면 평가 비용이 곱으로 커진다. 08장
[09장] thinkEvery = 5일 때 늑대가 나타난 뒤 바쁜 주민이 도망치기로 바꾸기까지 걸리는 시간은?
연속한 5개 tick 중 정확히 하나가 due다. thinkOffset이 주민마다 달라 인터럽트 검사가 여러 tick에 흩어진다(time-slicing). 할 일이 없던 주민은 바로 다음 tick에 숙고한다. 과제 2에서 측정해 보자. 09장
[10장] Zoo Tycoon 2에서 동물의 "죽음" 행동 rank를 1,000,000으로 둔 이유는?
Dill이 소개한 사례다. 욕구 행동은 rank 0, 나무 위 코알라 행동은 약 5, Marine Mania 쇼는 98~102, 죽음은 1,000,000이다. rank는 "무엇이 무엇을 끊을 수 있나"를 정하는 절대 서열이다. Dragon Age: Inquisition은 rank 대신 점수 대역(Basic 10, Reaction 50~70 등)으로 같은 효과를 냈다. 10장
[11장] GAP3 13장(Lewis)이 두 결정 사이의 진동(ping-pong)을 잡는 "가장 단순한 해법"으로 든 것은?
Lewis는 runtime/cooldown은 진동 위치만 옮긴다고 지적하고, 한쪽 결정에 consideration을 추가하는 것을 가장 단순한 해법으로 들었다. 안 되면 커브를 조정해 진동 구간을 최소화한다. 과제 9의 혼잡 수정도 consideration 입력을 바로잡는 방식이다. 11장
[09장·11장] 버그 제보: "3일차 저녁에 은솔이 늑대를 무시했다." 가장 먼저 할 일은?
시드 고정 RNG 덕분에 같은 입력이면 같은 시뮬레이션이 나온다. 재현부터 하고, 후보 표에서 도망치기가 0점이었는지(늑대가 14칸 밖이었나), rank 탈락이었는지, 아직 due가 오지 않았는지를 확인한다. 원인을 보기 전에 숫자부터 고치면 다른 곳이 망가진다. 11장

10. 코스 회고와 다음 학습 경로

이 코스는 블로그 글 「효용기반 의사결정 (Utility based Decision Making)」(DeepBlue, 2015)에서 출발했다. 원문이 다룬 여덟 주제가 코스 어디에서 엔진 코드가 되었고, 샌드박스 어디에서 눈으로 확인할 수 있는지 정리한다.

#블로그 원문 주제코스 챕터엔진 / 샌드박스에서 확인하는 곳
1효용 이론: "얼마나 원하는가"를 수로01 02모든 후보 점수가 0~1 스케일. 후보 표의 점수 열

원문 이후 코스가 덧붙인 것은 "시뮬레이션 엔진"으로 가는 부분이다. 욕구와 스마트 오브젝트(07), 행동×대상 평가(08), tick 루프와 시드 재현성(09), 다른 아키텍처와의 결합(10), 디버깅과 튜닝(11)이다. 판단 하나를 점수화하는 법에서 출발해, 수십 개의 판단이 매 tick 맞물리는 세계를 돌리는 법까지 온 셈이다.

다음 학습 경로

  • Game AI Pro 3, 13장 — Mike Lewis, "Choosing Effective Utility-Based Considerations". Guild Wars 2: Heart of Thorns에서 consideration과 커브를 고르는 실전 기준, 진동 대처, 프록시 변수. 이 코스의 PRESETS 팔레트와 bookend 정규화가 여기서 왔다.
  • Game AI Pro 3, 31장 — Sebastian Hanlon·Cody Watts, "Behavior Decision System: Dragon Age Inquisition". 정규화 대신 점수 대역 관례, behavior snippet, Target Selector, 평가 트리와 실행 트리의 분리.
  • Dave Mark, 『Behavioral Mathematics for Game AI』 — 효용 이론과 반응 커브를 게임 AI 관점에서 다룬 단행본. 블로그 원문의 참고 문헌이기도 하다.
  • IAUS (Infinite Axis Utility System) — Dave Mark. GDC AI Summit 2013 "Architecture Tricks: Managing Behaviors in Time, Space, and Depth"에서 일부 소개되었고, GDC 2015 Dave Mark·Mike Lewis "Building a Better Centaur: AI at Massive Scale"에서 Guild Wars 2 적용 사례가 발표되었다. UAI.compensate의 make-up value가 IAUS의 보정 방식이다. 그 전 단계로 GDC 2010 Mark·Dill "Improving AI Decision Modeling Through Utility Theory"도 함께 보자.
  • Unreal Engine 5 StateTree — UE 5.5에서 도입된 utility 선택. "Try Select Children with Highest Utility"(동점이면 목록의 첫 번째)와 "Try Select Children at Random Weighted by Utility"가 각각 이 코스의 best와 weighted에 해당한다. Consideration 노드는 0~1 점수를 내고 AND는 최솟값, OR는 최댓값으로 묶인다. 결합 점수에 state Weight가 곱해진다. 코스에서 만든 개념이 상용 엔진에서 어떤 UI로 노출되는지 비교해 보자.

핵심 요약

  • 한 tick은 욕구 감소 → 결정 트리거(할 일 없음 / due) → evaluate → select → 전환 판단·기록 → act 순서다. 결정은 매 tick이 아니라 조건이 맞을 때만 일어난다.
  • "왜 그랬나"는 후보 표로 답한다. rank 탈락 → 낮은 consideration 칩 → 관성 → 선택 확률 순으로 읽는다.
  • 튜닝은 엔진 코드가 아니라 데이터(Reasoner 옵션, 커브 spec, traits, 오브젝트 광고)로 한다. 그래서 JSON으로 내보내 재현·공유할 수 있다.
  • 같은 시드 + 같은 설정 = 같은 시뮬레이션. 시나리오 비교와 버그 재현은 모두 이 성질에 기댄다.
  • dual utility의 rank는 선택 범주이자 인터럽트 권한이다. 버킷 밖에서 점수가 정확히 0이 되도록 설계해야 버킷이 의도대로 작동한다.
코스를 마치며 이제 Hamlet을 출발점 삼아 자기 세계를 만들 차례다. 욕구를 하나 더하고(과제 7), 행동을 rank로 층층이 쌓고(과제 6), 결정 하나하나를 후보 표로 설명할 수 있다면 Game AI Pro 3권 13장과 31장의 상용 사례를 읽을 준비가 된 것이다.
