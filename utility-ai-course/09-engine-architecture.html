시뮬레이션 엔진 아키텍처

지금까지 커브, 결합, 선택, 관성, 욕구, 대상 평가를 부품 단위로 만들었다. 이 장은 그 부품들이 assets/uai.js 안에서 어떻게 조립되어 "살아 있는 마을"이 되는지 해부한다. 루프의 순서, 결정과 실행의 경계, 부하 분산, 재현성, 데이터 주도 설계처럼 코드 한 줄로는 안 보이지만 엔진의 성패를 가르는 결정들이 주제다.

학습 목표

  • uai.js의 모듈 의존 구조를 그리고, 각 모듈이 어느 장에서 왜 생겼는지 설명한다.
  • World.tick의 세 단계(욕구 감소 → 결정 → 실행)와 주민 단위 순차 처리가 만드는 순서 효과를 설명한다.
  • Reasoner(평가)와 action.run(실행)을 분리한 이유를 Merrill, Côté, Dragon Age: Inquisition의 구조와 비교한다.
  • thinkEvery·thinkOffset으로 결정 부하를 tick에 나누는 time-slicing을 계산하고, 실제 평가 비용을 측정한다.
  • 시드 고정 RNG로 시뮬레이션을 재현하고, 재현성을 깨는 흔한 실수를 찾아낸다.
  • 행동을 JSON 데이터로 정의하고 실행 중에 교체(핫 리로드)하며, 데이터와 실행 코드 사이의 계약을 이해한다.
엔진 부품 UAI.World World.tick() World.think() World.act() thinkEvery thinkOffset UAI.rng(seed) — 부품을 하나의 루프로 묶는 "몸통". 새 수학은 없고, 순서·주기·경계가 전부다.

1. uai.js 해부: 모듈 지도

uai.js는 400줄이 안 되는 파일이지만 층이 분명하다. 맨 아래에는 상태가 없는 순수 함수(커브, 결합, 선택, 난수)가 있고, 가운데에는 그 함수들을 "행동 목록"에 적용하는 Reasoner가 있으며, 맨 위에는 시간과 공간과 주민을 가진 World가 있다. 화살표는 "호출한다 / 사용한다"의 방향이다. 아래층은 위층을 모른다. 이 한 방향 의존이 엔진을 테스트 가능하게 만든다. UAI.curve는 월드 없이 node에서 바로 검증할 수 있고, Reasoner는 가짜 agent 객체 하나로 돌려 볼 수 있다.

모듈 지도: 블록을 눌러 실제 코드 보기
각 블록을 클릭(또는 Tab 후 Enter)하면 해당 부분의 uai.js 원문 발췌와, 그 부품을 처음 다룬 장으로 가는 링크가 나온다. 실선은 호출, 점선은 데이터 전달이다.

      .forEach(([t, x, y]) => w.addObject(t, x, y));

  class World {
    constructor(opt) {
      opt = opt || {};
      this.w = opt.w || 24; this.h = opt.h || 16;
      this.rng = UAI.rng(opt.seed || 7);
      this.time = 0; // 게임 시간(분)
      this.dt = opt.dt || 1; // tick당 분
      this.objects = []; this.agents = []; this.log = [];
      this.thinkEvery = opt.thinkEvery || 5; // 바쁠 때 몇 tick마다 인터럽트 검사를 할지 (09장 time-slicing)

  // ───────────────────────── 5. Reasoner (04·06·08장) ─────────────────────────
  // action = {
  //   id, label, weight=1, rank=0,
  //   targets?: (ctx) => [target, ...]           // 08장: 행동 × 대상 평가
  //   considerations: [{ name, input: (ctx) => raw, lo=0, hi=1, curve }],
  //   cooldown?: 초, duration?: 초
  // }
  // ctx = { agent, world, target }
  class Reasoner {
    constructor(actions, opt) {
      this.actions = actions.map(a => Object.assign({ weight: 1, rank: 0 }, a, {
        considerations: (a.considerations || []).map(c => Object.assign({ lo: 0, hi: 1 }, c, { fn: UAI.curve(c.curve || "선형 증가") })),
      }));
      this.opt = Object.assign({ combine: "compensated", strategy: "best", inertia: 0, pct: 0.1, n: 3 }, opt);
    }
    // 모든 (행동, 대상) 쌍을 점수화. 점수 0이 되는 순간 나머지 consideration은 생략(early-out)
    evaluate(agent, world) {
      const rows = [];
      const now = world ? world.time : 0;
      for (const a of this.actions) {
        const targets = a.targets ? a.targets({ agent, world }) : [null];
        for (const target of targets) {
          const ctx = { agent, world, target };
          const parts = [];
          let alive = true;
          const cdLeft = a.cooldown && agent.lastUsed && agent.lastUsed[a.id] != null
            ? a.cooldown - (now - agent.lastUsed[a.id]) : 0;
          if (cdLeft > 0) alive = false;
          for (const c of a.considerations) {
            if (!alive) { parts.push({ name: c.name, raw: null, x: null, y: null, skipped: true }); continue; }
            const raw = c.input(ctx);
            const x = UAI.normalize(raw, c.lo, c.hi);
            const y = c.fn(x);
            parts.push({ name: c.name, raw, x, y });
            if (y <= 0) alive = false;
          }
          const ys = parts.filter(p => !p.skipped).map(p => p.y);
          let score = alive ? UAI.combine(ys, this.opt.combine) * a.weight : 0;
          const cur = agent.current;
          const isCurrent = cur && cur.action === a.id && cur.target === target;
          if (isCurrent && score > 0) score += this.opt.inertia;
          rows.push({ action: a, target, parts, score, rank: a.rank, isCurrent, cooldown: Math.max(0, cdLeft) });
        }
      }
      return rows;
    }
    decide(agent, world, rng) {
      const rows = this.evaluate(agent, world);
      const res = UAI.select(rows, this.opt, rng);
      return { rows, chosen: res.chosen, pool: res.pool };
    }
  }
  UAI.Reasoner = Reasoner;
  // Hamlet 기본 행동 세트. 욕구 행동은 rank 0, 위협 회피는 rank 10 (dual utility)
  UAI.hamletActions = function () {
    const useObject = {
      id: "use", label: "이용하기", rank: 0,
      targets: ({ world }) => world.objects.filter(o => o.users < o.capacity || false),
      considerations: [
        // 광고된 욕구 충족량 × 그 욕구의 긴급도 합 → 0~1 (07장)
        { name: "광고 가치", input: ({ agent, target }) => UAI.adValue(agent, target), lo: 0, hi: 1, curve: "선형 증가" },
        // 거리: 가까울수록 좋다. 너무 멀면 0 근처 (08장)
        { name: "거리", input: ({ agent, target }) => Math.abs(agent.x - target.x) + Math.abs(agent.y - target.y), lo: 0, hi: 30, curve: { type: "poly", m: -1, k: 2, b: 1 } },
        // 이미 사용 중이면 붐빔 감점
        { name: "혼잡", input: ({ target }) => target.users / target.capacity, lo: 0, hi: 1, curve: { type: "linear", m: -0.7, b: 1 } },
      ],
      duration: null,
      run(world, a, cur) {
        const o = cur.target;
        if (a.x !== o.x || a.y !== o.y) return world.step(a, o.x, o.y);
        if (!cur.using) { if (o.users >= o.capacity) { a.current = null; return; } o.users++; cur.using = true; cur.until = world.time + o.duration; }
        for (const n in o.ads) a.needs[n] = Math.min(100, Math.max(0, a.needs[n] + (o.ads[n] / o.duration) * world.dt));
        if (world.time >= cur.until) { world.release(a); a.lastUsed["use:" + o.id] = world.time; a.current = null; }
      },
    };
  // bookend 정규화: [lo, hi] 구간을 [0, 1]로. 범위를 벗어나면 끝값에 고정 (GAP3 13장)
  UAI.normalize = (v, lo, hi) => (hi === lo ? 0 : clamp01((v - lo) / (hi - lo)));
  // spec → (x∈[0,1]) → y∈[0,1]. spec.invert면 입력을 1−x로 뒤집는다
  UAI.curve = function (spec) {
    if (typeof spec === "function") return x => clamp01(spec(x));
    if (typeof spec === "string") spec = UAI.PRESETS[spec];
    const f = spec.type === "piecewise" ? piecewise(spec.points) : null;
    const p = Object.assign({}, DEFAULTS, spec);
    const g = f || (x => CURVES[p.type](x, p));
    return x => clamp01(g(p.invert ? 1 - x : x));
  };
  // ───────────────────────── 2. 결합 (04장) ─────────────────────────
  // 곱셈 결합은 consideration이 많을수록 점수가 깎이므로 보정한다 (IAUS make-up value)
  //   modification = 1 − 1/n,  makeUp = (1 − s)·modification,  s' = s + makeUp·s
  UAI.compensate = function (s, n) {
    if (n <= 1) return s;
    const mod = 1 - 1 / n;
    return s + (1 - s) * mod * s;
  };
  UAI.combine = function (vals, method) {
    const n = vals.length;
    if (!n) return 0;
    switch (method || "product") {
      case "product": return vals.reduce((a, v) => a * v, 1);
      case "compensated": return vals.reduce((a, v) => a * UAI.compensate(v, n), 1);
      case "mean": return vals.reduce((a, v) => a + v, 0) / n;
      case "min": return Math.min(...vals);
      case "max": return Math.max(...vals);
      case "geomean": return Math.pow(vals.reduce((a, v) => a * v, 1), 1 / n);
    }
    throw new Error("unknown combine: " + method);
  };
  // ───────────────────────── 4. 선택 (05장) ─────────────────────────
  // cands: [{score, rank?}, ...]
  // opt.strategy: "best" | "weighted" | "topN" | "topPct" | "dual"
  //   topN: 상위 n개 중 가중 랜덤 / topPct: 최고점의 (1−pct) 이상만 가중 랜덤
  //   dual: 최고 rank만 남기고 → (pct 있으면) 최고 weight 대비 필터 → 가중 랜덤 (GAP2 3장)
  // 반환: { chosen, pool: [{cand, p}] }  — p는 선택 확률(위젯 시각화용)
  UAI.select = function (cands, opt, rng) {
    opt = opt || {};
    const r = rng ? rng.next : Math.random;
    let pool = cands.filter(c => c.score > 0);
    if (!pool.length) return { chosen: null, pool: [] };
    const st = opt.strategy || "best";
    if (st === "dual") {
      const top = Math.max(...pool.map(c => c.rank || 0));
      pool = pool.filter(c => (c.rank || 0) === top);
    }
    const maxS = Math.max(...pool.map(c => c.score));
    if (st === "best") {
      const best = pool.find(c => c.score === maxS);
      return { chosen: best, pool: [{ cand: best, p: 1 }] };
    }
    if (st === "topN") pool = [...pool].sort((a, b) => b.score - a.score).slice(0, opt.n || 3);
    if (st === "topPct" || (st === "dual" && opt.pct)) pool = pool.filter(c => c.score >= maxS * (1 - (opt.pct || 0.1)));
    const sum = pool.reduce((a, c) => a + c.score, 0);
    const probs = pool.map(c => ({ cand: c, p: c.score / sum }));
    let x = r() * sum;
    for (const c of pool) { x -= c.score; if (x <= 0) return { chosen: c, pool: probs }; }
    return { chosen: pool[pool.length - 1], pool: probs };
  };
  // ───────────────────────── 3. 난수 (05장) ─────────────────────────
  // 시드 고정 RNG(mulberry32): 같은 시드면 같은 시뮬레이션 → 재현 가능한 디버깅 (09장)
  UAI.rng = function (seed) {
    let a = seed >>> 0 || 1;
    const next = () => {
      a = (a + 0x6d2b79f5) >>> 0;
      let t = a;
      t = Math.imul(t ^ (t >>> 15), t | 1);
      t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
      return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
    };
    return {
      next, seed,
      range: (lo, hi) => lo + (hi - lo) * next(),
      int: n => Math.floor(next() * n),
      pick: arr => arr[Math.floor(next() * arr.length)],
    };
  };
  // 오브젝트 광고 가치: Σ (충족량/100 × 그 욕구의 긴급도 × 성격 가중치), 0~1로 제한
  UAI.adValue = function (agent, obj) {
    let v = 0;
    for (const n in obj.ads) {
      const urgency = UAI.curve(UAI.NEED_CURVE[n])(agent.needs[n] / 100);
      const room = Math.min(obj.ads[n], 100 - agent.needs[n]); // 한계효용: 이미 찬 만큼은 의미 없음
      v += (Math.max(room, Math.min(0, obj.ads[n])) / 100) * urgency * (agent.traits[n] || 1);
    }
    return clamp01(v);
  };

지도를 보면 몇 가지 설계 결정이 읽힌다.

  • Reasoner는 World를 모른다. evaluate(agent, world)는 world를 인자로 받아 consideration의 input(ctx)에 넘길 뿐, 월드의 내부 구조를 직접 쓰지 않는다. 그래서 같은 Reasoner를 늑대 무리나 상인 NPC에도 쓸 수 있다. 월드를 아는 것은 행동 정의(hamletActions)뿐이다.
  • 행동은 "데이터 + 실행 함수"의 묶음이다. considerations·rank·weight는 점수를 만드는 데이터이고, run은 월드를 바꾸는 코드다. Reasoner는 run을 한 번도 호출하지 않는다(3절).
  • 난수는 월드가 소유한다. select는 rng를 인자로 받을 뿐 직접 만들지 않는다. 한 시뮬레이션의 모든 무작위성이 world.rng 한 줄기에서 나오므로 시드 하나로 전체가 재현된다(5절).
  • 점선 화살표 하나가 확장의 입구다. Reasoner는 행동 배열을 생성자에서 받는다. 이 배열을 JS 코드 대신 JSON에서 만들면 데이터 주도 엔진이 된다(6절).
각 장이 엔진에 남긴 것 03장에서 curve/normalize, 04장에서 combine/compensate와 Reasoner의 뼈대, 05장에서 select/rng, 06장에서 inertia·cooldown·think(interruptOnly), 07장에서 욕구와 스마트 오브젝트, 08장에서 targets가 생겼다. 이 장은 이들을 움직이게 하는 World.tick을 다룬다.

2. 시뮬레이션 루프: World.tick의 세 단계

게임 AI 문헌은 에이전트의 한 주기를 흔히 Sense–Think–Act로 나눈다. 행동 선택 알고리즘(FSM, BT, 효용, GOAP, HTN)은 이 중 Think를 맡는 여러 선택지이고, 정답은 게임과 플랫폼에 따라 다르다(Dawe 외, GAP1 4장). uai.js의 한 tick은 이렇게 생겼다.

    tick() {
      this.time += this.dt; this.tickCount++;
      if (this.threat && this.time >= this.threat.until) this.threat = null;
      for (const a of this.agents) {
        // 1) 욕구 감소
        for (const n of UAI.NEEDS) a.needs[n] = Math.max(0, a.needs[n] - UAI.NEED_DECAY[n] * this.dt * (n === "energy" && this.hour() >= 22 ? 1.8 : 1));
        // 2) 결정 (06장, GAP1 11장): 숙고는 할 일이 끝났을 때만, 반응(인터럽트)은 주기적으로 검사
        const due = (this.tickCount + a.thinkOffset) % this.thinkEvery === 0;
        if (!a.current) this.think(a);
        else if (due) this.think(a, true);
        // 3) 실행
        this.act(a);
      }
    }

세 단계를 Sense–Think–Act에 대응시키면 다음과 같다.

단계코드Sense–Think–Act무엇을 바꾸나

② 결정this.think(a) / this.think(a, true)Sense + Think. consideration의 input(ctx)가 필요할 때 월드를 직접 읽는다(pull 방식 감지)a.current, 로그, RNG 상태

2.1 고정 시간 간격

dt는 tick당 흐르는 게임 분이다(기본 1). 욕구 감소량(NEED_DECAY는 분당 값)도, 오브젝트 이용 시간(duration, 분)도, 쿨다운도 전부 게임 시간으로 적혀 있다. 화면 프레임과는 무관하다. 브라우저가 60fps든 20fps든, 1초에 tick을 몇 번 돌릴지는 위젯(호스트)이 정한다. 이렇게 하면 같은 입력에 같은 결과가 나오고(5절), 배속 재생은 "프레임당 tick 수"만 바꾸면 된다.

// 호스트 쪽 루프의 전형: 누적기(accumulator)로 실시간과 게임 시간을 분리
let acc = 0;
function frame(realMs) {
  acc += realMs * speed;              // 배속
  while (acc >= MS_PER_TICK) { world.tick(); acc -= MS_PER_TICK; }
  render(world);                      // 렌더는 시뮬레이션 상태를 읽기만 한다
}

가변 dt(프레임 시간을 그대로 넘기기)를 쓰면 어떻게 될까? 욕구 감소처럼 선형인 부분은 괜찮지만, step()은 tick당 정확히 한 칸 움직이고 thinkEvery는 tick 수로 센다. 프레임이 느린 기기에서는 같은 게임 시간 동안 결정 횟수가 줄어 행동이 달라진다. 결정 주기를 tick에 묶은 엔진이라면 dt는 고정해야 한다.

2.2 주민 단위 순차 처리와 순서 효과

코드를 다시 보면 바깥 루프가 주민, 안쪽이 단계다. 즉 "모든 주민의 욕구 감소 → 모든 주민의 결정 → 모든 주민의 실행"이 아니라, 아리의 ①②③이 끝난 다음 보람의 ①②③이 돈다. 결과적으로 보람은 아리가 이미 한 칸 움직이고 빵집 자리를 차지한 뒤의 세계를 보고 결정한다. 아래 애니메이션으로 실제 한 tick을 따라가 보자.

한 tick 안에서 주민 3명이 처리되는 순서
아리·보람·찬 3명만 있는 마을(시드 11)을 실제로 돌리다가, 한 tick 안에 "한가해서 결정", "인터럽트 검사", "검사 생략"이 모두 일어나는 순간을 골랐다. 숫자는 엔진 메서드(think, act)를 그대로 호출해 얻은 값이다.

순서 효과는 버그가 아니라 선택이다. 장점은 단순함과 일관성이다. 아리가 마지막 자리를 차지하면 보람은 같은 tick에 그 사실을 본다(빵집이 targets 필터에서 빠진다). 단점은 공정성이다. 배열 앞쪽 주민이 매 tick 먼저 움직이므로, 자리 경쟁에서 체계적으로 유리하다. 실제 엔진이 쓰는 대안은 세 가지다.

  • 처리 순서 섞기: 매 tick 시드 RNG로 주민 순서를 섞는다. 공정하고 결정론도 유지된다.
  • 이중 버퍼: 모든 주민이 "tick 시작 시점의 스냅샷"을 읽고 결정한 뒤, 결과를 한꺼번에 적용한다. 순서 효과가 사라지는 대신 같은 자리에 두 명이 동시에 들어가는 충돌을 따로 풀어야 한다. 7절의 멀티스레드 평가가 이 구조를 쓴다.
  • 예약(reservation): 결정 순간에 오브젝트를 예약해 다른 주민의 targets에서 빼 버린다. uai.js는 도착해서야 users++를 하므로 두 명이 같은 빵집을 향해 걸어갈 수 있고, 늦게 온 쪽은 run 안에서 포기한다(3절).

2.3 언제 생각하나

② 단계는 두 갈래다. 할 일이 없으면(!a.current) 즉시 숙고하고, 할 일이 있으면 thinkEvery tick마다 한 번 인터럽트 검사만 한다. 인터럽트 검사는 think(a, true)로, 현재 행동보다 rank가 높은 후보가 나왔을 때만 갈아탄다. 이는 Côté가 말한 반응성(고우선 인터럽트)과 숙고(현재 행동이 끝났을 때 다음 최선)의 분리이고(GAP1 11장), The Sims Medieval이 interaction queue가 비었을 때만 결정했다는 사례와도 같은 발상이다(Graham, GAP1 9장). 자세한 배경은 06장 시간, 관성, 반응성에 있다.

    // interruptOnly=true: 실행 중인 행동보다 rank가 높은 후보가 생겼을 때만 갈아탄다
    think(a, interruptOnly) {
      const res = this.reasoner.decide(a, this, this.rng);
      a.lastEval = res;
      const c = res.chosen;
      if (!c) return;
      if (a.current && a.current.action === c.action.id && a.current.target === c.target) return;
      if (interruptOnly) {
        const curAct = this.reasoner.actions.find(x => x.id === a.current.action);
        if (c.rank <= curAct.rank) return;
      }
      if (a.current && a.current.using) this.release(a);
      a.current = { action: c.action.id, target: c.target, label: c.action.label, started: this.time, using: false };
      a.trace.push({ t: this.time, action: c.action.id, target: c.target && (c.target.id || c.target.name), score: c.score });
      if (a.trace.length > 60) a.trace.shift();
      this.log.push(`[${UAI.clock(this.time)}] ${a.name} → ${c.action.label}${c.target ? " @" + (c.target.label || c.target.name) : ""} (${c.score.toFixed(2)})`);
      if (this.log.length > 200) this.log.shift();
    }

3.1 왜 나누나

  • 평가는 자주, 실행은 길게. 이용하기 하나가 20~60분(=tick) 동안 이어지는데, 평가는 그 사이에도 주기적으로 돈다. 둘이 한 함수에 섞이면 "평가만 해 보기"가 불가능하다.
  • 평가는 부작용이 없어야 재사용된다. 디버그 패널(11장)이 "지금 점수표"를 보여 주려면 evaluate를 아무 때나 불러도 월드가 변하지 않아야 한다. 읽기 전용이면 병렬화도 가능하다(7절).
  • 실행 코드는 행동 수보다 적게. "이용하기" 하나의 run이 빵집·밭·집·벤치·선술집·우물·무대를 전부 처리한다. 점수 규칙은 오브젝트마다 달라도(광고 값), 걸어가서 쓰고 반납하는 절차는 같다.

3.3 평가와 실행 사이의 계약

Dragon Age: Inquisition은 이 분리에 계약을 붙였다. 실행 트리는 범용이라 맥락을 모르므로, 실행이 불가능한 조건(예: 대상 사망)은 평가 트리가 미리 막아야 한다(Hanlon·Watts, GAP3 31장). uai.js에서는 "이용하기"의 targets가 꽉 찬 오브젝트를 걸러 내는 것이 이 계약이다. 하지만 평가와 실행 사이에는 시간이 흐른다. 걸어가는 동안 다른 주민이 자리를 채울 수 있다. 그래서 run은 도착 순간 o.users >= o.capacity를 다시 확인하고, 안 되면 a.current = null로 포기한다. 다음 tick에 한가해진 주민이 즉시 다시 생각한다.

실패 처리의 차이Merrill의 Utility Selector는 최고점 자식이 실패하면 같은 정렬 목록의 다음 자식을 곧바로 시도한다. uai.js는 목록을 버리고 다음 tick에 처음부터 다시 평가한다. 구현은 단순하지만 한 tick을 잃는다. 또 같은 실패가 반복될 수 있다. 꽉 찬 빵집 앞에 두 명이 서 있으면, 자리가 나는 순간 둘 중 배열 앞쪽 주민이 가져간다(2.2절의 순서 효과).

6절에서는 이 계약이 데이터 주도 설계에서 어떻게 깨지는지 직접 볼 것이다. 데이터(점수)는 디자이너가 바꿀 수 있지만 실행 코드에 박힌 가정은 그대로 남는다.

4. 스케줄링과 성능: time-slicing

주민 6명이면 매 tick 전원이 생각해도 문제없다. 하지만 마을이 1,000명이 되면 이야기가 다르다. 평가 한 번의 비용은 "행동 × 대상 × consideration" 수에 비례하고, 대상에 다른 주민이 들어가는 "수다 떨기"는 주민 수에 비례하므로, 전원 평가는 N² 작업이 된다.

uai.js의 대책은 두 줄이다. 바쁜 주민은 thinkEvery tick마다 한 번만 인터럽트 검사를 하고, 그 "한 번"이 언제인지를 주민마다 다르게(thinkOffset = 추가된 순서) 둔다.

due = (tickCount + thinkOffset) mod thinkEvery == 0

offset이 없으면 모든 주민이 같은 tick에 생각한다. 총 작업량은 같지만 5 tick 중 한 tick에 몰려 스파이크가 된다. 프레임 예산은 평균이 아니라 최악의 tick이 깨뜨린다. offset을 나누면 각 tick에 약 N/thinkEvery명씩 고르게 퍼진다. Merrill이 말한 "별도 패스로 분산"이 바로 이것이다.

4.1 측정에서 읽어야 할 것

  • 평가 1회 비용은 N에 따라 커진다. 벤치마크 결과의 "평가한 행 수"를 보면 주민 1명당 (오브젝트 8 + 다른 주민 N−1 + 산책 1 + 도망 1)행이다. N=2,000이면 대부분이 수다 상대 후보다. time-slicing은 상수 배(÷thinkEvery)만 줄일 뿐 N²을 없애지 못한다. 근본 해법은 후보 자체를 줄이는 것, 즉 targets에서 공간 질의(반경 12칸 이내만)로 미리 걸러 내는 것이다. "상대와 거리" consideration이 어차피 12칸 밖을 0점으로 만들기 때문에 결과는 같고 비용만 준다.
  • early-out은 순서가 중요하다. Reasoner는 한 consideration이 0이 되면 나머지를 건너뛴다. Lewis는 그래서 싼 consideration을 앞에, 비싼 레이캐스트 시야 검사를 맨 끝에 두었고, 내비메시 경로 검사는 비용 때문에 아예 생략했다(GAP3 13장). hamletActions의 "이용하기"는 가장 비싼 adValue가 맨 앞이다. 거리 커브가 0이 되려면 30칸 이상 떨어져야 해서 순서를 바꿔도 이득은 작지만, 원칙은 알아 둘 것.
  • 숨은 할당. adValue는 호출될 때마다 UAI.curve(UAI.NEED_CURVE[n])로 커브 함수를 새로 만든다. 교육용으로는 읽기 쉽지만, 실제 엔진이라면 욕구 커브는 한 번 만들어 캐시한다. Merrill의 "비싼 계산은 Evaluate에서 한 번, 이후에는 캐시"와 같은 이야기다.
time-slicing의 대가: 반응 지연바쁜 주민은 늑대가 나타나도 자기 due tick이 올 때까지 모른다. thinkEvery = 5면 최대 4 tick(게임 4분) 늦게 도망친다. 한가한 주민은 즉시 반응하므로, 같은 장면에서 "어떤 주민은 바로 뛰고 어떤 주민은 빵을 마저 먹는" 차이가 생긴다. 이 지연을 없애는 방법이 7절의 이벤트 기반 재평가다.

5. 결정론과 재현성

효용 AI에는 무작위성이 들어간다. dual 전략은 최고 rank 안에서 가중 랜덤으로 고르고(05장), 산책 목적지도 무작위이며, 주민의 초기 욕구도 난수로 정한다. 그런데 "아까 보람이 왜 선술집에 갔지?"를 조사하려면 같은 장면을 다시 볼 수 있어야 한다. 그래서 uai.js의 모든 난수는 시드 고정 생성기 하나에서 나온다.

  // ───────────────────────── 3. 난수 (05장) ─────────────────────────
  // 시드 고정 RNG(mulberry32): 같은 시드면 같은 시뮬레이션 → 재현 가능한 디버깅 (09장)
  UAI.rng = function (seed) {
    let a = seed >>> 0 || 1;
    const next = () => {
      a = (a + 0x6d2b79f5) >>> 0;
      let t = a;
      t = Math.imul(t ^ (t >>> 15), t | 1);
      t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
      return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
    };
    return {
      next, seed,
      range: (lo, hi) => lo + (hi - lo) * next(),
      int: n => Math.floor(next() * n),
      pick: arr => arr[Math.floor(next() * arr.length)],
    };
  };

mulberry32는 32비트 정수 상태 하나(a)만 가진 작은 생성기다. 같은 시드면 같은 수열이 나오고, 상태가 정수 연산(Math.imul, 비트 시프트)만으로 바뀌므로 어떤 JS 엔진에서든 같은 수열을 낸다. World는 생성자에서 this.rng = UAI.rng(opt.seed || 7)를 만들고, think는 decide(a, this, this.rng)로, 산책의 run은 world.rng.int로 같은 줄기를 쓴다.

5.1 재현성이 사는 곳

  • 버그 재현: "시드 42, tick 1,830에 찬이 벽에 끼었다"는 한 줄이면 누구나 같은 장면을 다시 본다. 시드가 없으면 "가끔 끼어요"로 끝난다.
  • 리플레이: 시드와 외부 입력(늑대 출현 시각 같은 플레이어 개입)만 저장하면 전체 시뮬레이션을 다시 돌릴 수 있다. 상태 스냅샷보다 훨씬 작다.
  • 회귀 테스트: 커브 하나를 고친 뒤 "시드 1~100으로 1,000 tick씩 돌린 로그"를 이전 버전과 비교하면, 의도한 변화인지 아닌지가 diff로 보인다. 위젯의 해시 비교가 그 축소판이다.
  • 밸런싱 실험: 같은 시드로 A/B를 돌리면 차이가 순전히 파라미터 때문임을 보장할 수 있다(11장).

6. 데이터 주도 설계와 핫 리로드

hamletActions를 다시 보면 행동 정의의 대부분은 사실 코드가 아니라 값이다. consideration 이름, 입력, 구간(lo/hi), 커브 종류, weight, rank. 코드인 부분은 두 가지뿐이다. 입력을 읽는 짧은 함수(input)와 실행부(run). 이 둘을 "이름으로 고르는 사전"으로 만들면 행동 전체를 JSON으로 쓸 수 있다.

이것이 Lewis가 Guild Wars 2: Heart of Thorns에서 쓴 IAUS 방식의 핵심이다. 행동마다 DSE(Decision Score Evaluator)를 데이터로 정의하고, 미리 만들어 둔 consideration 패턴 100개 이상을 조합해 새 생물의 행동을 몇 분 만에 만든다. 커브는 소수의 프리셋 팔레트로 고르고, 임의 커브는 "고급 모드" 뒤에 숨긴다(GAP3 13장). Merrill도 커브를 리로드 가능한 데이터로 두라고 권한다(GAP1 10장). 디자이너가 숫자를 바꿀 때마다 프로그래머가 빌드하지 않아도 되기 때문이다.

6.2 프리셋으로 보는 세 가지 교훈

  • 빵집 우선: rank 1짜리 "빵 먹으러 가기"를 추가했다. 배고픔 결핍이 50을 넘는 순간(lo: 50, √x 커브라 그 아래는 0점) 이 행동만 유효 후보가 되고, 바쁜 주민도 다음 인터럽트 검사에서 하던 일을 놓는다. 숫자 하나(rank)가 행동의 성격을 "욕구 중 하나"에서 "다른 욕구를 끊는 강제 행동"으로 바꾼다. Dill의 dual utility에서 rank가 범주라는 말이 바로 이것이다(05장).
  • 은둔자 마을: 행동을 지웠다. 수다를 떨던 주민만 하던 일을 놓고(리로드 메시지의 "재결정" 수), 나머지는 하던 일을 계속한다. 핫 리로드가 월드 상태를 보존한다는 뜻이다.
  • 겁쟁이 마을: 도망 consideration의 hi를 14에서 24로 늘렸다. 늑대를 부르면 주민들이 14칸쯤에서 멈춘 채 로그에 "도망치기"가 매 tick 찍힌다. flee.run은 world.dist(a, t) >= 14이면 스스로 끝내도록 코드에 박혀 있기 때문이다. 데이터는 "24칸까지 도망쳐라"라고 하는데 실행부는 "14칸이면 끝"이라고 한다. 끝나면 한가해진 주민은 즉시 다시 생각하고, 다시 도망을 고르고, 실행부는 다시 바로 끝낸다. 3.3절의 계약이 데이터 쪽에서 깨진 사례다.
데이터 주도의 진짜 비용 데이터로 열어 둔 값은 디자이너가 마음껏 바꾼다. 그 값과 묶여 있는 가정이 실행 코드나 다른 데이터에 숨어 있으면, 겁쟁이 마을처럼 "아무 에러 없이 이상하게" 동작한다. 해결은 두 가지다. 가정을 데이터로 끌어올리거나(도망 종료 거리도 JSON 필드로), 로딩 시점에 검증한다(flee의 threat:dist 구간이 실행부 종료 거리와 다르면 경고). 위젯의 컴파일러는 이름 오타·입력과 대상 종류 불일치·없는 커브 프리셋은 잡지만, 이런 의미상 불일치는 못 잡는다. Lewis가 "필수 스위치도 하드코딩하지 말고 DSE 템플릿에 넣으라"고 한 것도 같은 문제의식이다(GAP3 13장).

6.3 핫 리로드를 안전하게

위젯의 리로드는 다음 순서로 동작한다. 이 순서 자체가 설계다.

  1. 먼저 전부 검증하고, 하나라도 틀리면 아무것도 바꾸지 않는다. 반쯤 적용된 행동 집합은 원래 집합보다 위험하다.
  2. 새 Reasoner를 만들어 world.reasoner를 통째로 바꾼다. 선택 옵션(combine, strategy, pct, inertia)은 이전 것을 그대로 쓴다.
  3. 현재 행동이 새 집합에 없거나 실행부가 바뀐 주민은 world.release(a)로 자리를 반납하고 current를 비운다. 이 처리가 없으면 다음 act에서 reasoner.actions.find(...)가 undefined를 돌려주고 act.run에서 예외가 난다. World.act와 think(a, true)는 현재 행동 id가 Reasoner 안에 반드시 있다고 가정하기 때문이다.
  4. tick 카운터, 시간, RNG, 위치, 욕구는 그대로 둔다. 그래서 리로드 후에도 시뮬레이션은 결정론적이다. "시드 + 리로드한 tick + JSON"을 기록하면 재현된다.

7. 확장 포인트: 실제 엔진으로 가는 길

uai.js는 일부러 작게 만들었다. 상용 엔진으로 키울 때 가장 먼저 손대게 되는 네 곳을 정리한다. 아래 코드는 모두 확장 스케치이고 uai.js에는 없다.

7.1 지각(sensor)과 블랙보드

지금은 consideration이 월드를 직접 읽는다. "늑대까지 거리"는 늑대의 실제 좌표다. 그러면 주민은 벽 너머의 늑대도 알고, 늑대가 사라지는 순간 즉시 잊는다. 실제 엔진은 그 사이에 센서를 두고, 센서가 지각한 결과를 에이전트별 블랙보드(기억)에 시간 표시와 함께 써 둔다. consideration은 블랙보드를 읽는다.

Côté가 든 FSM 사례가 이 층이 왜 필요한지 보여 준다. "위협 발견"을 시야 판정에 직결하면, 장애물 때문에 시야가 깜빡일 때 추적과 순찰 사이를 오가며 애니메이션이 튄다. 해법은 히스테리시스 같은 필터를 거친 "논리적 위협 인지"에 연결하는 것이다(GAP1 11장). 블랙보드는 그 필터를 둘 자리다. 비싼 지각(시야 레이캐스트)을 consideration마다 반복하지 않고 센서가 주기적으로 한 번 하게 되는 성능상 이점도 있다.

// 센서: 일정 주기로 지각해 블랙보드에 기록 (마지막으로 본 시각 포함)
function senseThreat(world, a) {
  const t = world.threat;
  if (t && world.dist(a, t) < 16) a.bb.threat = { x: t.x, y: t.y, seen: world.time };
  else if (a.bb.threat && world.time - a.bb.threat.seen > 10) a.bb.threat = null; // 10분 뒤에야 잊는다
}
// consideration은 블랙보드를 읽는다
{ name: "위협 거리", input: ({ agent }) => agent.bb.threat ? dist(agent, agent.bb.threat) : 99, lo: 0, hi: 14, curve: "선형 감소" }

7.2 LOD: 멀리 있는 에이전트는 덜 자주 생각한다

4절의 thinkEvery는 월드 공용 값이다. 화면 밖 주민이 화면 앞 주민만큼 자주 생각할 이유는 없다. 결정 주기를 카메라와의 거리(또는 중요도)에 따라 주민마다 다르게 두면, 플레이어가 보는 곳의 반응성은 유지하면서 전체 비용을 크게 줄일 수 있다.

LOD조건 (예)결정 주기기타 절감
0 근거리카메라 10칸 이내매 tick전체 consideration
1 중거리30칸 이내5 tick비싼 consideration(시야) 생략
2 원거리그 밖20 tick이동은 순간 이동, 욕구는 통계적으로 갱신
// 주민마다 다른 주기. offset 분산은 그대로 유지한다
const every = a => { const d = dist(a, camera); return d < 10 ? 1 : d < 30 ? 5 : 20; };
const due = (world.tickCount + a.thinkOffset) % every(a) === 0;

주의할 점: LOD가 바뀌는 순간(카메라가 다가올 때) 원거리에서 대충 갱신된 상태가 갑자기 정밀 시뮬레이션으로 넘어온다. 그 경계에서 주민이 "순간 이동"한 것처럼 보이지 않게, LOD를 올릴 때 즉시 한 번 재평가하는 것이 보통이다.

7.3 이벤트 기반 재평가

4절의 반응 지연(최대 thinkEvery−1 tick)을 없애려면 주기 대신 사건으로 결정을 깨워야 한다. 늑대 출현, 오브젝트 파괴, 대화 요청 같은 이벤트가 발생하면 관련된 주민의 다음 tick을 강제로 due로 만든다. 평소에는 주기를 길게 잡아 비용을 아끼고, 중요한 순간에만 즉시 반응한다.

상용 엔진에서도 같은 고민이 보인다. UE5 StateTree는 5.5부터 자식 상태를 utility로 고르는 selector("Try Select Children with Highest Utility", "Try Select Children at Random Weighted by Utility")를 제공한다. 이 선택은 상태를 고르는 시점에 일어나므로, 한 상태가 실행 중이면 그 상태가 끝나거나 전이가 일어날 때까지 점수를 다시 매기지 않는다. 실행 중에 더 나은 선택지로 갈아타게 하려면 이벤트나 전이 조건으로 재선택을 강제해야 한다. 즉 uai.js의 "한가할 때만 숙고"를 엔진 차원에서 택한 셈이고, 인터럽트는 이벤트로 설계해야 한다.

// 이벤트를 받으면 해당 주민을 다음 tick에 반드시 생각하게 만든다
world.emit = (type, data) => {
  for (const a of world.agents) if (type === "threat" && world.dist(a, data) < 14) a.wake = true;
};
// tick의 ② 단계
if (!a.current) this.think(a);
else if (due || a.wake) { this.think(a, true); a.wake = false; }

7.4 멀티스레드 평가: 읽기 전용 평가 + 순차 적용

3절에서 평가를 읽기 전용으로 분리한 덕분에 평가는 병렬화할 수 있다. 하지만 2.2절의 순서 효과와 5절의 결정론을 생각하면, 병렬화할 수 있는 부분은 정확히 evaluate까지다.

  • 평가는 스냅샷을 읽는다. 2.2절의 이중 버퍼 방식이 된다. 스레드들이 같은 월드를 읽는 동안 아무도 쓰지 않아야 하므로, 실행 단계와 겹칠 수 없다.
  • rng는 평가 단계에서 쓰지 않는다. Reasoner.evaluate가 rng를 받지 않는 것이 여기서 빛난다. 선택(select)은 순차 단계에서 정해진 순서로 rng를 소비하므로 스레드 수와 무관하게 같은 결과가 나온다. 선택까지 병렬로 하고 싶다면 "시드·주민 id·tick"으로 주민별 rng를 파생해 쓰는 방법이 있다.
  • 충돌은 적용 단계가 푼다. 두 주민이 같은 스냅샷에서 빵집의 마지막 자리를 보고 둘 다 고를 수 있다. 순차 적용에서 앞선 쪽만 성공하고 뒤쪽은 다음 tick에 다시 생각한다. useObject.run의 도착 시 재확인이 이미 이 역할을 하고 있다.
// 1단계(병렬 가능): 읽기 전용 평가
const tables = agents.map(a => reasoner.evaluate(a, snapshot));   // 워커에 나눠 줄 수 있다
// 2단계(순차): 고정 순서로 선택 → 갈아타기 → 실행
agents.forEach((a, i) => {
  const res = UAI.select(tables[i], reasoner.opt, world.rng);
  applyChoice(world, a, res.chosen);
  world.act(a);
});

핵심 요약

  • uai.js는 순수 함수(curve·combine·select·rng) → Reasoner → World의 3층 구조다. 아래층은 위층을 모르므로 각 층을 따로 테스트할 수 있다.
  • World.tick은 주민마다 ① 욕구 감소 ② 결정 ③ 실행을 차례로 돈다. 주민 단위 순차 처리라 뒤 주민은 앞 주민이 바꾼 세계를 본다(순서 효과).
  • Reasoner는 읽기 전용 평가만 하고, 월드를 바꾸는 것은 action.run뿐이다. 평가가 막아야 할 조건과 실행이 재확인할 조건 사이에 계약이 있다(Merrill·Côté·DAI도 같은 분리).
  • 한가한 주민은 즉시, 바쁜 주민은 thinkEvery마다 인터럽트만 검사한다. thinkOffset이 그 검사를 tick에 고르게 나눠 스파이크를 없앤다. 대가는 최대 thinkEvery−1 tick의 반응 지연이다.
  • 모든 난수는 world.rng 한 줄기에서 나온다. 같은 시드면 같은 로그가 나오고, Math.random이나 관찰자의 rng 소비가 그 보장을 깬다.
  • 행동을 JSON(입력 이름, lo/hi, 커브 프리셋, weight, rank, exec)으로 정의하면 빌드 없이 바꿀 수 있다. 다만 실행 코드에 숨은 가정과 데이터가 어긋나면 에러 없이 이상하게 동작한다.
  • 실제 엔진으로 키우는 네 갈래: 센서·블랙보드, LOD 결정 주기, 이벤트 기반 재평가, 병렬 평가 + 순차 적용.

확인 문제

World.tick에서 주민 루프가 바깥, 단계(욕구 감소·결정·실행)가 안쪽에 있다. 그 결과로 맞는 것은?
아리의 ①②③이 모두 끝난 뒤 보람의 ①이 시작된다. 그래서 뒤 주민은 앞 주민의 실행 결과를 보고 결정하고, 배열 앞쪽 주민이 자리 경쟁에서 체계적으로 유리하다. 스냅샷 방식(이중 버퍼)은 7.4절의 확장이다.
주민 1,000명이 모두 바쁜 상태이고 thinkEvery = 5다. thinkOffset이 주민 번호일 때와 모두 0일 때, tick당 최대 인터럽트 검사 수는?
총 작업량(5 tick에 1,000회)은 같지만, offset이 없으면 모두 같은 tick에 몰려 스파이크가 된다. 프레임 예산을 깨는 것은 평균이 아니라 최악의 tick이다.
디버그 패널이 매 프레임 "이 주민이 지금 고를 행동"을 보여 주려고 world.reasoner.decide(a, world, world.rng)를 호출한다. 무엇이 문제인가?
decide는 월드를 바꾸지 않지만 rng 상태를 진행시킨다. 관찰이 결과를 바꾸면 안 된다. 관찰은 rng가 필요 없는 evaluate로 하거나 별도 rng를 쓴다. 5절 위젯의 "디버그 미리보기" 체크박스가 이 상황이다.
겁쟁이 마을 프리셋에서 도망 consideration의 hi를 24로 늘리자, 주민들이 약 14칸에서 멈추고 매 tick "도망치기"가 로그에 찍혔다. 원인은?
실행부가 끝나 current가 비면 한가한 주민은 즉시 다시 생각하고, 14~24칸에서는 도망 점수가 아직 0보다 커서 다시 도망을 고른다. 그리고 실행부는 바로 다시 끝난다. 평가와 실행 사이 계약이 데이터 쪽에서 깨진 경우다. 가정을 데이터로 끌어올리거나 로딩 시점에 검증해야 한다.
평가를 여러 스레드로 나누려 한다. 가장 안전한 분할은?
evaluate는 읽기 전용이고 rng를 받지 않으므로 병렬화해도 결과가 같다. 월드를 바꾸는 run과 rng 소비 순서는 스레드 스케줄에 따라 달라지면 안 되므로 순차 단계에 둔다. 같은 자리를 두 명이 고른 충돌도 순차 단계에서 풀린다.
바쁜 주민이 늑대에 늦게 반응하는 문제(최대 thinkEvery−1 tick)를 비용을 크게 늘리지 않고 없애는 방법은?
thinkEvery = 1은 time-slicing을 포기하는 것이다. rank는 인터럽트 검사가 일어난 뒤의 우선순위일 뿐 검사 시점을 앞당기지 못한다. 이벤트 기반 재평가는 평소에는 긴 주기를 유지하고 중요한 순간에만 즉시 생각하게 한다. UE5 StateTree처럼 실행 중 상태를 재평가하지 않는 엔진에서도 같은 방식으로 재선택을 강제한다.
다음 장으로우리 엔진은 효용 하나로 숙고와 반응을 모두 처리했다. 하지만 상용 게임은 대부분 효용을 BT나 StateTree 안의 "선택 노드"로 넣었다. 10장에서는 Merrill의 Utility Selector, Dragon Age: Inquisition의 평가·실행 트리, Zoo Tycoon 2의 rank 체계를 따라가며 효용과 BT/StateTree를 어떻게 섞었는지 본다.
