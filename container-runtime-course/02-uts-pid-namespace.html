프로세스와 격리 · Chapter 02

UTS · PID 네임스페이스

1장의 myctr는 자식을 띄우기만 했습니다. 이제 처음으로 격리를 붙입니다. 바꿀 것은 딱 한 줄입니다. fork()를 clone(CLONE_NEWUTS | CLONE_NEWPID)로 바꾸면 자식은 자기만의 hostname을 갖고, 자기가 PID 1이라고 믿게 됩니다. 그런데 PID 1이 되는 순간 커널은 그 프로세스를 특별하게 대합니다. Ctrl+C가 먹지 않고, kill도 무시되고, PID 1이 죽으면 함께 있던 프로세스가 전부 죽습니다. 이 장에서는 그 이유를 이해하고, Docker의 --init과 같은 작은 init을 직접 만듭니다.

학습 목표

  • Linux의 8가지 네임스페이스와 이를 다루는 세 API(clone, unshare, setns)를 구분할 수 있다.
  • nix의 clone으로 자식을 새 UTS·PID 네임스페이스에 만들고, 스택과 종료 시그널 인자의 의미를 설명할 수 있다.
  • 한 프로세스가 네임스페이스마다 다른 PID를 갖는 구조(NSpid)를 읽을 수 있다.
  • PID 1이 받는 세 가지 특별 대우를 설명하고, 미니 init으로 해결할 수 있다.
  • Rust 런타임이 자식에게 흘리는 SIGPIPE 설정을 찾아 고칠 수 있다.
  • myctr run --hostname box --init ...을 구현해 완료 기준 15개를 통과시킨다.

1. 네임스페이스: 커널이 보여 주는 다른 세계

네임스페이스는 커널의 전역 자원 하나(hostname, PID 번호표, 마운트 목록, 네트워크 스택 ...)를 여러 벌로 만들고, 프로세스마다 어느 벌을 볼지 정해 주는 기능입니다. 모든 프로세스는 종류별로 정확히 하나의 네임스페이스에 속합니다. 아무것도 하지 않으면 부모의 것을 그대로 물려받습니다. 1장에서 본 대로 fork는 네임스페이스를 공유하고, exec는 유지합니다.

2. clone · unshare · setns

네임스페이스를 다루는 시스템 콜은 세 개뿐이고, 각각 "언제" 네임스페이스에 들어가느냐가 다릅니다.

API누가 옮겨 가나쓰는 곳
clone(fn, stack, flags)새로 만든 자식이 장의 myctr, runc의 초기 단계
unshare(flags)호출한 프로세스 자신. 단 PID(와 Time)은 자신이 아니라 이후에 만드는 자식부터unshare 명령, 3장의 mount ns
setns(fd, type)호출한 프로세스 자신이 기존 네임스페이스로 합류. fd는 /proc/<pid>/ns/*를 연 것nsenter, docker exec, 9장의 myctr exec
PID만 예외인 이유 프로세스의 PID는 태어날 때 정해지고 평생 바뀌지 않는다는 것이 Unix의 대전제입니다. glibc는 getpid() 결과를 캐시하기도 했고, 많은 프로그램이 자기 PID를 파일에 적어 둡니다. 그래서 unshare(CLONE_NEWPID)는 호출자를 옮기지 않고 "다음에 만드는 자식은 새 PID 네임스페이스에 넣어라"라고 표시만 합니다. 실제로 확인한 결과입니다. 
before unshare: getpid=93
after unshare:  getpid=93     ← 그대로
forked child:   getpid=1      ← 자식부터 새 번호표
이때 /proc/self/ns/pid는 그대로이고, /proc/self/ns/pid_for_children만 새 네임스페이스를 가리킵니다.

3. UTS 네임스페이스

가장 단순한 네임스페이스입니다. UTS는 "UNIX Time-sharing System"의 약자로, uname()이 돌려주는 struct utsname에서 이름을 따왔습니다. 그중 바꿀 수 있는 필드인 nodename(hostname)과 domainname을 격리합니다. 커널 버전(release)은 격리 대상이 아닙니다. 커널이 하나이기 때문입니다. 컨테이너 안에서 uname -r을 치면 호스트 커널 버전이 나오는 이유입니다.

  • sethostname은 CAP_SYS_ADMIN이 필요합니다. 그래서 이 장부터 myctr는 sudo로 실행합니다(5장에서 user 네임스페이스로 이 제약을 풉니다).
  • 이름은 최대 64바이트(HOST_NAME_MAX)입니다. 70자를 주면 EINVAL이 납니다.
  • 위험: CLONE_NEWUTS 없이 sethostname을 부르면 호스트의 hostname이 바뀝니다. 위 실험실에서 UTS 플래그를 끄고 결과를 보세요. 플래그를 잘못 다루는 실수는 대부분 이렇게 호스트를 망가뜨리는 형태로 나타납니다. VM에서 실험해야 하는 이유입니다.

4. fork에서 clone으로

glibc의 fork()가 내부적으로 clone을 부른다는 것을 1장 strace에서 봤습니다. 이제 그 clone을 직접 부릅니다. nix의 시그니처는 이렇습니다.

pub unsafe fn clone(
    cb: Box<dyn FnMut() -> isize + '_>,   // 자식이 실행할 함수
    stack: &mut [u8],                       // 자식이 쓸 스택
    flags: CloneFlags,                      // CLONE_NEWUTS | CLONE_NEWPID ...
    signal: Option<c_int>,                  // 자식이 죽을 때 부모에게 보낼 시그널
) -> Result<Pid>
1장: fork
match unsafe { fork() }? {
    ForkResult::Child => {
        // 자식: fork 다음 줄부터 이어서 실행
        let err = execvp(..).unwrap_err();
        unsafe { libc::_exit(127) }
    }
    ForkResult::Parent { child } => {
        waitpid(child, None)?
    }
}
2장: clone
let mut stack = vec![0u8; 1024 * 1024];
let flags = CloneFlags::CLONE_NEWUTS
          | CloneFlags::CLONE_NEWPID;
// 자식: 이 클로저만 실행하고, 반환값으로 종료
let cb = Box::new(|| container_main(..));
let child = unsafe {
    clone(cb, &mut stack, flags,
          Some(Signal::SIGCHLD as i32))
}?;
waitpid(child, None)?

달라진 점 세 가지

forkclone왜
자식이 실행하는 코드fork 다음 줄부터, 부모와 같은 흐름넘겨준 클로저 하나clone은 원래 스레드를 만드는 데도 쓰는 범용 호출이라, 자식의 시작점을 함수로 받습니다.
클로저가 반환하면(해당 없음)그 값으로 자식이 종료glibc의 clone 래퍼가 반환값으로 exit 시스템 콜을 부릅니다. 1장에서 걱정했던 "자식이 부모의 main으로 돌아가는" 일이 구조적으로 불가능해집니다. 그래서 exec 실패 시 _exit(127) 대신 127을 반환하면 됩니다.
스택부모 스택을 COW로 복제호출자가 메모리를 넘김스레드처럼 메모리를 공유(CLONE_VM)하는 경우 스택을 같이 쓸 수 없으므로 API가 스택을 요구합니다. 우리는 CLONE_VM을 주지 않으므로 자식은 이 Vec의 복사본 위에서 돕니다. nix가 끝 주소 계산과 16바이트 정렬을 해 줍니다.
함정 1: signal 인자를 None으로 주면 네 번째 인자는 자식이 죽을 때 부모에게 보낼 시그널입니다. fork는 항상 SIGCHLD를 씁니다. 여기에 None을 주면 clone은 성공하지만, 부모의 평범한 waitpid가 그 자식을 못 찾습니다. Linux는 종료 시그널이 SIGCHLD가 아닌 자식을 "clone 자식"으로 분류하고, __WCLONE이나 __WALL 플래그 없이는 기다리지 않기 때문입니다. 실제로 실행하면 이렇게 됩니다. 
clone ok pid=92
waitpid -> Err(ECHILD)
그러면 자식은 좀비로 남고 myctr는 종료 코드를 잃습니다. 항상 Some(Signal::SIGCHLD as i32)를 넘기세요.
함정 2: 스택 크기 넘긴 스택에는 가드 페이지가 없습니다. 자식이 깊은 재귀나 큰 지역 배열로 스택을 넘치면 segfault가 아니라 조용한 메모리 오염이 날 수 있습니다. 그래서 nix의 clone이 unsafe입니다. 자식은 몇 가지 시스템 콜 후 곧바로 exec하므로 1 MiB면 충분합니다. exec하면 커널이 새 프로그램에 새 스택을 만들어 주므로 이 크기는 사용자 프로그램과 무관합니다.

5. PID 네임스페이스

PID 네임스페이스는 트리를 이룹니다. 새 PID 네임스페이스는 만든 프로세스의 네임스페이스를 부모로 갖습니다. 그리고 한 프로세스는 자기가 속한 네임스페이스와 그 모든 조상 네임스페이스에서 각각 PID를 하나씩 갖습니다. 컨테이너 안의 sh는 컨테이너 안에서는 1번이고, 호스트에서는 4242번입니다. 둘 다 진짜 PID입니다. 보는 위치에 따라 번호가 다를 뿐입니다.

규칙은 단순합니다. 프로세스는 자기 네임스페이스와 그 자손 네임스페이스의 프로세스만 볼 수 있습니다. 호스트는 모든 컨테이너를 보지만, 컨테이너는 호스트도 옆 컨테이너도 보지 못합니다. 커널은 /proc/<pid>/status의 NSpid 줄에 바깥부터 안쪽 순서로 모든 PID를 보여 줍니다.

$ sudo myctr run grep NSpid /proc/self/status
NSpid:	96	1        ← 호스트에서 96, 컨테이너에서 1
PID 네임스페이스 탐색기
"여기서 보기"를 누르면 그 네임스페이스에서 보이는 PID로 모든 칩이 바뀝니다. 보이지 않는 프로세스는 흐려집니다. 칩을 누르면 그 프로세스의 NSpid가 나옵니다. "+ 프로세스"로 새 프로세스를 만들어 각 네임스페이스의 번호표가 따로 증가하는 것을 확인하세요.
칩을 눌러 보세요.
  • 새 PID 네임스페이스의 첫 프로세스가 PID 1이 됩니다. myctr의 clone 자식이 바로 그 프로세스이고, 그 자식이 exec하면 사용자 프로그램이 PID 1이 됩니다.
  • PID 네임스페이스는 최대 32단계까지 중첩할 수 있습니다. "컨테이너 안의 컨테이너"가 가능한 이유입니다.
  • 프로세스는 평생 같은 PID 네임스페이스에 머뭅니다. setns로 PID 네임스페이스에 들어가도(nsenter -p) 호출자 자신은 그대로이고, 이후 fork한 자식부터 그 안에서 태어납니다. nsenter가 -p를 주면 자동으로 fork하는 이유입니다.

6. /proc의 착시

지금 만든 컨테이너 안에서 실제로 실행한 결과입니다.

$ sudo myctr run /bin/sh -c 'echo $$'
1
$ sudo myctr run /bin/sh -c 'readlink /proc/self'
466                        ← 1이 아니다!
$ sudo myctr run ps -e -o pid,comm
    PID COMMAND
      1 bash               ← 호스트의 프로세스들이 보인다
    499 myctr
    500 head
    501 ps

echo $$는 getpid() 시스템 콜을 부르고, 커널은 호출자의 네임스페이스 기준으로 답하므로 1이 나옵니다. 하지만 /proc는 파일시스템이고, 이 /proc는 호스트가 부팅할 때 호스트 PID 네임스페이스 기준으로 마운트한 것입니다. procfs는 마운트될 때의 PID 네임스페이스를 기준으로 내용을 보여 줍니다. 그래서 /proc/self는 호스트 PID로 풀리고, /proc를 읽는 ps와 top은 호스트 프로세스를 보여 주거나, 자기 자신을 찾지 못해 fatal library error, lookup self 같은 에러를 냅니다.

3장 예고 해결책은 컨테이너 안에서 새로 mount -t proc proc /proc를 하는 것입니다. 그러면 새 procfs가 컨테이너의 PID 네임스페이스 기준으로 만들어집니다. 그런데 그냥 마운트하면 호스트의 /proc 위에 덮여서 호스트의 ps까지 망가집니다. 그래서 마운트 네임스페이스(CLONE_NEWNS)가 먼저 필요하고, 이것이 3장의 출발점입니다. 그전까지는 절대 컨테이너 안에서 /proc를 다시 마운트하지 마세요.

7. PID 1의 특별 대우

호스트에서 PID 1은 init(systemd)이고, init이 죽으면 커널 패닉입니다. 그래서 커널은 PID 1을 보호합니다. PID 네임스페이스의 PID 1도 같은 대우를 받습니다(커널 패닉 대신 네임스페이스가 끝납니다). man 7 pid_namespaces에 정리된 규칙은 세 가지입니다.

규칙내용컨테이너에서 나타나는 증상
① 시그널 보호PID 1은 자기가 핸들러를 등록한 시그널만 받는다. 핸들러가 없는(기본 동작인) 시그널은 같은 네임스페이스에서 오든, 터미널에서 오든 무시된다. 예외: 조상 네임스페이스에서 보낸 SIGKILL과 SIGSTOP은 강제로 전달된다docker run ubuntu sleep 100에 Ctrl+C가 안 먹고, docker stop이 10초를 기다린 뒤 SIGKILL로 끝난다
② 고아 입양네임스페이스 안에서 부모를 잃은 프로세스는 그 네임스페이스의 PID 1에게 입양된다PID 1이 wait하지 않는 프로그램(대부분의 앱)이면 좀비가 쌓인다
③ 동반 종료PID 1이 끝나면 커널이 네임스페이스의 나머지 모든 프로세스에 SIGKILL을 보낸다. 이후 그 네임스페이스에서 fork는 ENOMEM으로 실패한다메인 프로세스가 끝나면 백그라운드 작업이 정리 없이 즉사한다

myctr로 직접 확인한 결과입니다. 1장의 완료 기준 중 두 개(kill -TERM $$ → 143, kill -KILL $$ → 137)가 더는 성립하지 않습니다.

$ sudo myctr run /bin/sh -c 'kill -TERM $$; echo survived TERM'; echo $?
survived TERM
0                                    ← PID 1이라 자기 자신에게 보낸 TERM도 무시
$ sudo myctr run /bin/sh -c 'kill -KILL $$; echo survived KILL'; echo $?
survived KILL
0                                    ← 같은 ns에서 보낸 KILL조차 무시
$ sudo myctr run /bin/sh -c 'sleep 300 & echo bg=$!'; pgrep sleep || echo "no sleep left"
bg=2
no sleep left                        ← sh(PID 1)가 끝나자 sleep도 SIGKILL
PID 1 시그널 판정기

시그널을 보낼 때 커널(kernel/signal.c)은 대상이 "죽일 수 없는 프로세스"(SIGNAL_UNKILLABLE 플래그. 네임스페이스의 init이 이 플래그를 받습니다)인지 확인합니다. 그렇다면 처리 방식이 기본값(SIG_DFL)인 시그널은 버립니다. 예외는 "강제 전달" 표시가 붙은 SIGKILL/SIGSTOP뿐이고, 송신자가 대상의 PID 네임스페이스 안에서 보이지 않을 때(즉 조상 네임스페이스에서 보냈을 때) 그 표시가 붙습니다.

bash나 Node.js처럼 SIGTERM 핸들러를 직접 등록하는 프로그램은 PID 1이어도 정상 종료할 수 있습니다. 문제는 sleep, 많은 Go/Python 스크립트, 셸 스크립트처럼 "기본 동작으로 죽는 것"에 기대는 프로그램입니다.

8. 미니 init 만들기

해결책은 사용자 프로그램을 PID 1에 두지 않는 것입니다. clone된 자식(PID 1)이 exec하지 않고 작은 init으로 남아 사용자 프로그램을 PID 2로 fork + exec합니다. init이 할 일은 둘입니다.

  1. 모든 자식을 거둔다. waitpid(-1)(nix에서는 waitpid(None, None))을 반복해 입양된 고아까지 회수합니다.
  2. 메인 자식의 결과를 자기 결과로 삼는다. PID 2가 끝나면 그 종료 코드(또는 128 + 시그널)를 반환합니다. PID 1이 끝나면 규칙 ③에 따라 남은 프로세스는 커널이 정리합니다.

Docker의 --init(tini), Kubernetes의 pause 컨테이너, dumb-init이 모두 이 일을 합니다. 실제 tini는 여기에 더해 받은 시그널을 자식에게 전달합니다(도전 과제).

--init 모드에서 Ctrl+C가 처리되는 과정
sudo myctr run --init sleep 100을 실행하고 Ctrl+C를 누릅니다. 각 프로세스 옆의 두 숫자는 호스트 PID / 컨테이너 PID입니다.

9. Rust가 흘리는 것: SIGPIPE

컨테이너 안의 프로세스 상태를 보다가 이상한 값을 발견했습니다.

$ grep SigIgn /proc/self/status
SigIgn:	0000000000000000
$ sudo myctr run /bin/sh -c 'grep SigIgn /proc/self/status'
SigIgn:	0000000000001000         ← 비트 12 = 시그널 13 = SIGPIPE가 무시됨
$ sudo myctr run /bin/sh -c 'yes | head -1'
y
yes: standard output: Broken pipe  ← 호스트에서는 나지 않는 에러

원인은 Rust 표준 라이브러리입니다. Rust 프로그램은 main 전에 SIGPIPE를 SIG_IGN으로 바꿉니다. 닫힌 파이프에 쓸 때 프로세스가 조용히 죽는 대신 EPIPE 에러를 받게 하려는 설계입니다. 그리고 1장에서 배운 대로 SIG_IGN은 fork와 exec를 넘어 유지됩니다. 결국 myctr가 실행하는 모든 컨테이너 프로세스가 SIGPIPE를 무시한 채로 태어납니다. yes | head에서 head가 먼저 끝나면 원래 yes는 SIGPIPE로 조용히 죽어야 하는데, 무시하고 있으니 에러를 찍고 1로 끝납니다. 셸 스크립트의 파이프라인 동작이 호스트와 달라지는 미묘한 버그입니다.

이 버그는 1장 코드에도 있었습니다. std::process::Command는 exec 직전에 SIGPIPE를 기본값으로 되돌려 주지만, 우리는 fork/clone을 직접 쓰므로 그 처리도 직접 해야 합니다. exec 직전에 한 줄이면 됩니다.

unsafe { signal(Signal::SIGPIPE, SigHandler::SigDfl) }?;   // exec 직전, 자식 쪽에서
일반화: "런타임이 가진 것"은 전부 의심하라 런타임 프로세스의 모든 속성(시그널 처리 방식, 시그널 마스크, 열린 fd, 환경 변수, rlimit, umask)은 기본적으로 컨테이너로 흘러 들어갑니다. 실제 런타임은 exec 직전에 이것들을 명시적으로 정리합니다. runc는 시그널 마스크를 초기화하고, 넘길 fd 외에는 전부 닫는 데 공을 들입니다. 앞으로 장마다 "이번에 추가한 것이 컨테이너로 새지 않는가"를 확인하는 습관을 들이세요.

참조 구현 (막혔을 때만 여세요)

Linux aarch64(커널 7.0, Debian bookworm, Rust 1.86)에서 빌드하고 위 check.sh 15개 항목을 통과하는 것을 확인한 코드입니다.

use std::ffi::CString;

use anyhow::{Context, Result, bail};
use clap::{Parser, Subcommand};
use nix::errno::Errno;
use nix::libc;
use nix::sched::{CloneFlags, clone};
use nix::sys::signal::{SigHandler, Signal, signal};
use nix::sys::wait::{WaitStatus, waitpid};
use nix::unistd::{ForkResult, Pid, execvp, fork, sethostname};

const STACK_SIZE: usize = 1024 * 1024;

#[derive(Parser)]
#[command(name = "myctr", about = "나만의 컨테이너 런타임")]
struct Cli {
    #[command(subcommand)]
    command: Command,
}

#[derive(Subcommand)]
enum Command {
    /// 명령을 새 UTS·PID 네임스페이스에서 실행한다
    Run {
        /// 컨테이너 안에서 보일 hostname
        #[arg(long, default_value = "myctr")]
        hostname: String,
        /// PID 1에 작은 init을 두고 명령은 PID 2로 실행한다
        #[arg(long)]
        init: bool,
        /// 실행할 프로그램과 인자
        #[arg(required = true, trailing_var_arg = true, allow_hyphen_values = true)]
        cmd: Vec<String>,
    },
}

fn main() -> Result<()> {
    match Cli::parse().command {
        Command::Run { hostname, init, cmd } => {
            let code = run(&hostname, init, &cmd)?;
            std::process::exit(code);
        }
    }
}

fn run(hostname: &str, init: bool, cmd: &[String]) -> Result<i32> {
    let argv: Vec<CString> = cmd
        .iter()
        .map(|s| CString::new(s.as_bytes()))
        .collect::<Result<_, _>>()
        .context("인자에 NUL 바이트가 있습니다")?;

    // 자식이 쓸 스택. clone은 fork와 달리 스택을 직접 넘겨야 한다.
    let mut stack = vec![0u8; STACK_SIZE];
    let flags = CloneFlags::CLONE_NEWUTS | CloneFlags::CLONE_NEWPID;
    let cb = Box::new(|| container_main(hostname, init, &argv));
    // SIGCHLD를 넘겨야 부모가 평범한 waitpid로 자식을 기다릴 수 있다.
    let child = unsafe { clone(cb, &mut stack, flags, Some(Signal::SIGCHLD as i32)) }
        .context("clone 실패 (root 권한으로 실행했나요?)")?;

    // 1장 8절: SIGINT 무시는 자식이 생긴 뒤 부모 쪽에서만
    unsafe { signal(Signal::SIGINT, SigHandler::SigIgn) }.context("signal 설정 실패")?;
    wait_exit_code(child)
}

fn wait_exit_code(child: Pid) -> Result<i32> {
    match waitpid(child, None).context("waitpid 실패")? {
        WaitStatus::Exited(_, code) => Ok(code),
        WaitStatus::Signaled(_, sig, _) => Ok(128 + sig as i32),
        other => bail!("예상하지 못한 상태: {other:?}"),
    }
}

/// clone된 자식. 새 네임스페이스 안의 PID 1이다.
/// 반환값이 곧 이 프로세스의 종료 코드가 된다.
fn container_main(hostname: &str, init: bool, argv: &[CString]) -> isize {
    if let Err(e) = sethostname(hostname) {
        eprintln!("myctr: sethostname: {e}");
        return 1;
    }
    if init { mini_init(argv) } else { exec(argv) }
}

/// 성공하면 돌아오지 않는다. 돌아오면 127.
fn exec(argv: &[CString]) -> isize {
    // Rust 런타임은 시작할 때 SIGPIPE를 SIG_IGN으로 바꾼다. SIG_IGN은 exec를 넘어
    // 유지되므로, 사용자 프로그램에 넘기기 전에 기본값으로 되돌린다.
    if let Err(e) = unsafe { signal(Signal::SIGPIPE, SigHandler::SigDfl) } {
        eprintln!("myctr: SIGPIPE 복원 실패: {e}");
        return 1;
    }
    let err = execvp(&argv[0], argv).unwrap_err();
    eprintln!("myctr: {}: {err}", argv[0].to_string_lossy());
    127
}

/// PID 1로 남아 명령을 PID 2로 띄우고, 입양된 고아까지 거두다가
/// 명령이 끝나면 그 종료 코드로 끝난다.
fn mini_init(argv: &[CString]) -> isize {
    let main_child = match unsafe { fork() } {
        Ok(ForkResult::Child) => unsafe { libc::_exit(exec(argv) as i32) },
        Ok(ForkResult::Parent { child }) => child,
        Err(e) => {
            eprintln!("myctr-init: fork: {e}");
            return 1;
        }
    };
    loop {
        match waitpid(None, None) {
            Ok(WaitStatus::Exited(pid, code)) if pid == main_child => return code as isize,
            Ok(WaitStatus::Signaled(pid, sig, _)) if pid == main_child => return 128 + sig as isize,
            Ok(_) => continue, // 입양된 고아를 거뒀다
            Err(Errno::EINTR) => continue,
            Err(e) => {
                eprintln!("myctr-init: waitpid: {e}");
                return 1;
            }
        }
    }
}

핵심 요약

  • 네임스페이스는 커널 전역 자원을 여러 벌로 만들어 프로세스마다 다른 벌을 보여 주는 기능입니다. 8종류가 있고, /proc/<pid>/ns/*의 inode가 같으면 같은 네임스페이스입니다.
  • clone은 자식을 새 네임스페이스에 만들고, unshare는 자신을 옮기며(PID는 이후 자식부터), setns는 기존 네임스페이스에 합류합니다.
  • nix의 clone은 클로저, 스택, 플래그, 종료 시그널을 받습니다. 클로저의 반환값이 종료 코드이고, 종료 시그널로 SIGCHLD를 주지 않으면 waitpid가 ECHILD를 냅니다.
  • PID 네임스페이스는 트리이고, 프로세스는 조상 네임스페이스마다 PID를 하나씩 갖습니다(NSpid). 하지만 /proc는 마운트 시점의 네임스페이스 기준이라 아직 호스트를 보여 줍니다(3장에서 해결).
  • PID 1은 ① 핸들러 없는 시그널을 무시하고(조상 ns의 SIGKILL/SIGSTOP만 예외) ② 고아를 입양하며 ③ 죽으면 네임스페이스 전체를 끝냅니다. 미니 init이 이 문제를 해결합니다.
  • Rust 런타임의 SIGPIPE=SIG_IGN은 exec를 넘어 컨테이너로 샙니다. exec 직전에 기본값으로 되돌립니다.

확인 문제

두 프로세스가 같은 UTS 네임스페이스에 있는지 가장 확실하게 확인하는 방법은?
hostname은 우연히 같을 수 있고, 커널 버전은 모든 컨테이너가 같습니다. 네임스페이스 객체의 inode 번호가 같아야 같은 네임스페이스입니다.
unshare(CLONE_NEWPID)를 호출한 직후 호출자의 getpid()는?
PID는 평생 바뀌지 않으므로 unshare는 호출자를 옮기지 않습니다. 이후에 fork하는 첫 자식이 새 네임스페이스의 PID 1이 됩니다.
nix의 clone에 signal 인자로 None을 주고 부모가 waitpid(child, None)을 부르면?
종료 시그널이 SIGCHLD가 아닌 자식은 "clone 자식"으로 분류되어 __WCLONE/__WALL 없이는 기다릴 수 없습니다. 실제 실행 결과도 Err(ECHILD)였습니다.
컨테이너 안에서 echo $$는 1인데 readlink /proc/self는 466이 나왔다. 이유는?
getpid()는 호출자의 네임스페이스 기준으로 답하지만, procfs는 마운트할 때의 PID 네임스페이스 기준으로 내용을 보여 줍니다. 컨테이너 기준 /proc를 새로 마운트하는 것은 마운트 네임스페이스가 생기는 3장의 일입니다.
init 없이 sudo myctr run sleep 100을 실행했다. 호스트에서 sleep에게 보냈을 때 sleep을 죽일 수 있는 시그널은?
sleep은 PID 1이고 어떤 핸들러도 등록하지 않았습니다. 기본 동작인 시그널은 모두 무시되고, 조상 네임스페이스(호스트)에서 보낸 SIGKILL과 SIGSTOP만 강제로 전달됩니다.
PID 1이 종료되면 같은 PID 네임스페이스의 백그라운드 프로세스는?
PID 네임스페이스의 init이 끝나면 커널이 나머지 모든 프로세스에 SIGKILL을 보냅니다. sh -c 'sleep 300 & ...' 실험에서 sleep이 남지 않았던 이유입니다.
myctr 컨테이너 안에서 yes | head -1이 "Broken pipe" 에러를 낸 근본 원인은?
yes는 PID 1이 아니라 sh의 자식입니다. Rust가 main 전에 SIGPIPE를 무시로 설정하고, SIG_IGN은 exec 후에도 유지되므로 컨테이너 프로세스 전체가 SIGPIPE를 무시합니다. exec 직전에 SigDfl로 되돌려 고칩니다.

실습 과제

  1. 격리 완성. 11절 단계 A~E를 구현하고 sudo ./check.sh를 통과시킨 뒤 git tag ch02를 남기세요. 기대: 통과 15 / 15.
  2. 밖에서 들여다보기. 터미널 1에서 sudo ./target/debug/myctr run --hostname box sleep 1000. 터미널 2에서 pgrep -x sleep으로 호스트 PID를 찾은 뒤 다음을 실행하세요. grep NSpid /proc/<pid>/status(기대: <pid> 1), sudo ls -l /proc/<pid>/ns/와 ls -l /proc/self/ns/를 비교(기대: uts, pid, pid_for_children만 다름), sudo nsenter -t <pid> -u hostname(기대: box), lsns -t uts. 끝나면 sudo kill -9 <pid>. 이 sleep은 PID 1이라 kill(TERM)로는 끝나지 않습니다.
  3. Ctrl+C 비교. sudo ./target/debug/myctr run sleep 100과 sudo ./target/debug/myctr run --init sleep 100에서 각각 Ctrl+C를 누르고 echo $?를 확인하세요. 기대: 전자는 반응이 없어 다른 터미널에서 sudo pkill -9 -x sleep 후 137, 후자는 즉시 130.
  4. 동반 종료 관찰. sudo ./target/debug/myctr run /bin/sh -c 'sleep 300 & echo bg=$!'; pgrep -x sleep || echo gone. 기대: bg=2 뒤 gone. 같은 명령에 --init을 붙이면 어떻게 될지 예측하고 확인하세요(힌트: sh가 끝나면 init은 무엇을 하나?).
  5. unshare 체험. myctr 없이 sudo unshare -u -p -f --mount-proc /bin/sh를 실행하고 hostname x; hostname; echo $$; ps를 해 보세요. ps가 깔끔하게 두 줄만 나오는 것은 --mount-proc 덕분입니다. 3장에서 이것을 직접 만듭니다.
  6. 도전: IPC 네임스페이스. 플래그에 CLONE_NEWIPC를 추가하고, 호스트에서 ipcmk -Q로 만든 메시지 큐가 컨테이너 안의 ipcs -q에는 보이지 않는지 확인하세요.
  7. 도전: 시그널 전달. 지금은 호스트에서 myctr에게 kill -TERM을 보내면 myctr만 죽고 컨테이너는 고아로 남습니다. myctr가 SIGTERM을 받으면 자식(PID 1)에게 전달하고, init은 받은 SIGTERM을 PID 2에게 전달하도록 만드세요. 힌트: init은 SIGTERM 핸들러를 등록해야 규칙 ①을 통과해 시그널을 받을 수 있습니다. 핸들러에서는 kill()만 부르고(async-signal-safe), 대상 PID는 AtomicI32에 넣어 두세요. 기대: sudo myctr run --init sleep 100 & 후 sudo kill -TERM %1 → 143.
