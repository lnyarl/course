rootless 권한·자원·파일 소유권 조합

선수 장 · user 네임스페이스와 rootless

5장의 단일 UID 매핑은 안의 UID0과 바깥 일반 사용자를 연결했습니다. 다중 사용자 이미지·cgroup 제한·네트워크까지 조합하려면 각각 다른 권한 위임이 필요합니다.

ID 대응표는 호스트 권한 획득이 아니다

uid_map·gid_map은 안과 밖의 ID 범위를 연결합니다. subordinate ID를 쓰는 구성에서는 /etc/subuid·/etc/subgid 할당과 newuidmap/newgidmap 도우미의 승인 범위를 확인합니다. 일반 사용자가 임의의 호스트 ID 범위를 선택할 수 있다고 설명하면 안 됩니다. 이미 있는 할당을 읽는 일과 시스템 계정 매핑을 새로 승인하는 일도 구분합니다.

이미지 파일의 소유 ID가 대응표에 없으면 안에서 보이는 ID나 파일 접근 결과가 기대와 달라질 수 있습니다. 단일 ID rootless가 UID1·UID1000의 모든 파일 작업까지 지원한다는 결론은 나오지 않습니다. idmapped mount 같은 방법도 커널·파일 시스템·권한 제약을 확인해야 하며 단순 chown과 동일한 동작으로 취급하지 않습니다.

cgroup·네트워크 위임은 별도 계약

user namespace를 만들었다고 호스트의 cgroup tree에 새 제한을 자유롭게 쓸 수 있는 것은 아닙니다. 위임된 subtree와 controller·파일 쓰기 권한을 확인하고, 부모의 제한보다 자식이 넓어질 수 없다는 계층 규칙을 유지합니다. 호스트 메모리가 남는데도 rootless 작업이 제한되는 경우 부모와 자기 cgroup을 함께 조사합니다.

새 network namespace 안에서의 capability와 호스트 bridge·방화벽을 바꿀 권한은 다릅니다. rootless 네트워크는 사용자 공간 전달이나 별도 도우미 등 선택한 구조의 성능·주소·포트 제약을 가집니다. 기존 6장의 rootful veth/bridge/NAT 성공을 rootless 성공 증거로 재사용하지 않습니다.

실습과 예상 관찰

기존에 준비된 자신의 rootless 컨테이너에서 id, cat /proc/self/uid_map, cat /proc/self/gid_map, cat /proc/self/cgroup만 읽습니다. 매핑·위임·네트워크 모드를 표의 서로 다른 열에 기록하고, 권한이 없다고 관리자 설정을 자동 변경하지 않습니다.

UID0 하나만 바깥 일반 사용자에 매핑

예상 판정: 안의 root가 호스트 root가 되지 않으며 다른 ID 사용은 별도 지원이 필요합니다. 파일 접근은 실제 소유권과 권한을 읽어 확인합니다.

userns 가능하지만 cgroup 쓰기 권한 없음

예상 판정: ID 격리와 자원 위임이 별개이므로 모순이 아닙니다. 현재 실행을 무제한으로 우회시키지 말고 미지원 조합으로 기록합니다.

실습의 경계와 다음 장

rootless 환경을 새로 설치하거나 권한 위임을 변경하지 않습니다. 기존 myctr의 단일 매핑·이미지 모드 제한을 확인한 뒤 6장에서 어느 주체가 호스트 네트워크를 구성하는지 연결합니다.
