CNI·IPAM과 네트워크 자원 회수

선수 장 · 컨테이너 네트워크

6장의 veth·bridge·DNS를 플러그인 호출 계약으로 확장합니다. 성공한 ADD 하나만 보는 대신 IP 할당 뒤 연결 구성이 실패한 경우의 정리 책임을 추적합니다.

CNI가 교환하는 식별자와 결과

CNI는 런타임과 네트워크 플러그인 사이의 구성·실행 프로토콜을 정의합니다. CNI_COMMAND, CNI_CONTAINERID, CNI_NETNS, CNI_IFNAME 같은 입력과 stdin의 설정, stdout의 결과를 구분합니다. 동일한 컨테이너 ID라도 network attachment나 인터페이스가 다르면 별도 자원일 수 있으므로 ID 하나로 모든 연결을 덮어쓰지 않습니다.

IPAM은 주소·경로 등 필요한 할당을 맡는 별도 책임입니다. 네트워크 플러그인이 veth를 만들었고 IPAM이 IP를 골랐다고 전체 연결이 사용 가능하다는 뜻은 아닙니다. ADD 결과가 어느 인터페이스·주소·route에 적용됐는지, 다음 체인 플러그인에 무엇을 넘기는지 정확히 보관해야 합니다.

부분 성공과 DEL 반복을 설계하기

IP 할당 후 veth 설정이 실패하면 성공 응답을 못 받았어도 할당이 남을 수 있습니다. 런타임은 ADD 실패·중단 경로에서도 해당 attachment의 DEL 정리를 고려해야 하며, namespace가 이미 사라진 상황의 정리도 가능해야 합니다. DEL은 컨테이너의 업무 완료가 아니라 연결 자원의 반환입니다.

정리의 불변식은 살아 있는 다른 attachment의 주소·인터페이스를 건드리지 않으면서 실패한 attachment의 할당을 회수하는 것입니다. 같은 정리를 반복할 수 있고 이미 없는 자원을 적절히 처리해야 합니다. 호스트의 공통 bridge·공통 NAT 정책과 실행별 veth/IPAM 상태도 소유권이 다릅니다. 기존 myctr는 CNI 플러그인을 구현하지 않으므로 이 계약을 자동으로 만족한다고 가정하지 않습니다.

실습과 예상 관찰

호스트에서 ADD/DEL을 실행하지 말고 세 개의 원장 카드(IP 할당, veth 생성, 런타임 성공 기록)를 만듭니다. 실패를 두 번째 단계에 놓고 attachment ID별 정리 결과를 계산합니다. 이미 설치된 CNI 설정이 있다면 읽기만 하고 다른 런타임의 자원을 지우지 않습니다.

IP 할당 성공 후 veth 구성 실패

예상 모델 결과: 런타임 성공 기록이 없어도 IPAM 할당을 회수해야 합니다. 성공 응답 부재를 자원 부재로 간주하면 누수가 남습니다.

동일 attachment의 DEL이 두 번 도착

예상 모델 결과: 두 번째 정리가 다른 attachment를 지우거나 새 오류 상태를 만들지 않아야 합니다. 실제 플러그인의 결과는 전용 실습에서 반복 호출로 별도 검증합니다.

실습의 경계와 다음 장

실제 IPAM·CNI 네트워크를 설치하거나 호스트 연결을 바꾸지 않습니다. 9장 lifecycle에 attachment 원장을 연결해 생성 실패와 컨테이너 삭제가 같은 정리 계약을 쓰도록 설계합니다.
