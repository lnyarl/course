OCI 상태 전이와 생성 실패 복구

선수 장 · OCI 런타임 스펙

9장의 create와 start를 분리한 뒤에는 런타임 명령 자체가 도중에 실패했을 때 남은 상태를 설명해야 합니다. 상태 파일·프로세스·cgroup이 항상 동시에 바뀌는 것은 아닙니다.

명령 결과와 컨테이너 상태를 분리하기

OCI runtime의 creating·created·running·stopped 상태는 런타임이 보고하는 생명주기입니다. create는 namespace·마운트·자원을 준비하고 사용자 프로그램 실행 전 경계를 만들며, start는 실행을 진행시킵니다. state 조회의 PID와 상태만으로 초기화 중인 모든 자원이 정상이라고 결론내리지 않습니다. 기존 myctr의 상태 조회 코드가 어떤 근거로 stopped를 판단하는지 읽으세요.

create 도중 자식은 만들어졌지만 상태 파일을 쓰기 전에 부모가 실패할 수 있습니다. 반대로 상태 파일은 있는데 자식이 이미 종료됐을 수도 있습니다. 컨테이너 ID별 동시 명령을 직렬화하고, 상태를 임시 파일에 쓴 뒤 교체하는 절차와 자원 획득표를 둡니다. 파일 교체의 원자성과 정전 내구성은 별도이며 PID 숫자의 재사용도 복구 판단에 포함합니다.

rollback을 반복해도 이웃 자원을 지우지 않기

실패 복구에서는 이번 생성이 소유한 cgroup·mount·FIFO·자식만 정리해야 합니다. 이름이 비슷한 기존 디렉터리를 찾아 무조건 지우는 방식은 올바른 소유권 계약이 아닙니다. 생성 단계마다 획득 여부와 정확한 경로를 기록하면 반쯤 준비된 상태도 역순으로 설명할 수 있습니다.

동시에 start와 delete가 오면 각각 상태 파일을 따로 읽고 판단하는 것만으로는 충분하지 않습니다. 상태 확인과 해당 전이를 하나의 잠금 범위로 묶거나 동등한 직렬화가 필요합니다. 불변식은 stopped 자원의 정리가 새 running 세대의 자원을 해제하지 않는 것입니다. 강제 삭제도 실행 중 작업 종료와 자원 회수의 완료 조건을 명확히 해야 합니다.

실습과 예상 관찰

9장의 코드를 읽고 clone·cgroup 생성·FIFO 생성·state 저장·start의 각 지점에 실패 카드를 한 장씩 놓습니다. 파일이나 프로세스를 실제로 종료시키지 말고 획득표에 남을 자원과 재실행 때의 처리 방식을 적습니다. 기존 전용 실습이 있다면 자신이 만든 컨테이너의 state 조회만 비교하세요.

자식 생성 후 state 저장 전 실패

예상 설계 판정: 상태 파일 부재가 자식 부재를 뜻하지 않습니다. 부모가 소유한 자식 식별과 획득표로 정리할 경로가 필요합니다. 이 카드 결과는 실제 장애 주입 로그가 아닙니다.

두 번째 delete가 이미 정리된 ID에 도착

예상 설계 판정: 명령의 계약에 맞는 부재 결과를 반환하고 다른 세대·다른 컨테이너 자원은 건드리지 않아야 합니다. 실제 idempotency는 반복 명령의 로그로 검증해야 합니다.
