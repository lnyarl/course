2장의 myctr는 자기 hostname과 PID를 가졌지만, ls /는 여전히 호스트의 파일을 보여 줍니다. 이번에는 Alpine의 작은 루트 파일시스템을 준비하고 프로세스가 바라보는 /를 교체합니다. 마운트 목록을 나누고, 전파를 끊고, 루트를 바꾸고, 새 PID 공간에 맞는 /proc와 최소한의 /dev를 붙입니다. 끝나면 ls /에는 Alpine이, ps에는 컨테이너 프로세스만 나옵니다.

  • myctr run --rootfs ./rootfs --init /bin/sh을 구현하고 완료 기준 17개를 통과시킨다.

1. /를 바꾸려면 무엇을 나눠야 하나

Linux에서 /는 모든 프로세스에 고정된 문자열 하나가 아닙니다. 프로세스는 경로 탐색을 시작할 루트 디렉터리와 상대 경로의 기준인 현재 디렉터리(cwd)를 가지고 있습니다. 그 경로에 어떤 파일시스템이 붙어 있는지는 mount namespace의 마운트 트리가 정합니다. 세 가지를 구분해야 루트를 바꾼 뒤에도 호스트가 보이는 실수를 피할 수 있습니다.

동작바뀌는 것그대로인 것
clone(CLONE_NEWNS)자식이 별도 마운트 목록을 갖는다처음에는 부모와 같은 마운트·파일이 보인다
mount(..., MS_PRIVATE | MS_REC, ...)자식의 트리에서 마운트 이벤트 전파를 끊는다같은 파일에 대한 읽기·쓰기는 여전히 공유될 수 있다
pivot_root(new, old)루트 마운트를 교체하고 이전 루트를 old 아래에 둔다old를 떼기 전까지는 이전 트리가 남아 있다
execvp프로그램 이미지를 바꾼다준비한 루트·마운트 namespace·cwd가 유지된다

위 순서는 모두 clone으로 만든 자식에서, exec 전에 수행합니다. 부모가 루트를 바꾸면 컨테이너를 관리하는 myctr 자신도 호스트의 파일 경로를 잃습니다. 이 장은 자식의 setup()에 파일시스템 준비 단계를 추가하는 작업입니다.

2. mount namespace와 마운트 전파

플래그 이름은 CLONE_NEWNS입니다. 새 namespace의 마운트 목록은 부모 목록에서 시작합니다. 여기서 놓치기 쉬운 것이 전파 속성입니다. 부모와 자식의 마운트가 같은 shared peer group에 속하면, 그 아래의 mount·umount 이벤트가 서로 전달됩니다. namespace가 다르다는 사실만으로 이 연결이 끊기지는 않습니다. mount_namespaces(7)

속성이벤트 방향이 장에서의 선택
shared같은 peer group과 양방향 전파자식의 마운트가 부모에 나타날 수 있다
private전파를 보내지도 받지도 않는다MS_PRIVATE | MS_REC로 전체 트리를 변경
slavemaster에서 받지만 역방향으로 보내지 않는다여기서는 사용하지 않는다
마운트 전파 실험실
자식이 /mnt/demo에 tmpfs를 마운트합니다. 호스트에도 나타날지 먼저 예상하세요.

호스트

자식

모델의 전제: 복제 시 /mnt의 마운트가 shared peer 관계에 있고, 그 바로 아래에 새 마운트를 만듭니다. 파일 내용의 동기화 실험은 아닙니다.

첫 mount 호출은 전파 차단

mount(
    None::<&str>, "/", None::<&str>,
    MsFlags::MS_REC | MsFlags::MS_PRIVATE, None::<&str>,
)?;

MS_PRIVATE는 마운트의 전파 속성을 바꾸고, MS_REC는 하위 마운트에도 재귀 적용합니다. /만 private으로 바꾸고 이미 존재하는 하위 shared 마운트를 남기지 않도록 둘을 함께 씁니다. 이것은 파일을 복사하거나 읽기 전용으로 만드는 호출이 아닙니다. 커널 Shared Subtrees 문서

관찰: shared 누수와 pivot_root의 EINVAL

privileged Linux 컨테이너에서 재검증한 결과, shared peer 관계를 남긴 별도 namespace의 마운트가 부모 namespace에도 나타났고, private으로 바꾸면 나타나지 않았습니다. 새 루트의 부모 마운트 등을 shared로 남긴 경우에는 pivot_root도 EINVAL로 거절되었습니다. 따라서 rprivate은 누수 차단과 루트 교체의 전제 조건을 함께 해결합니다.

이 실험에서 바깥 또는 호스트는 일회용 Linux 컨테이너의 부모 mount namespace를 뜻합니다. 물리 macOS에 Linux 마운트가 나타났다는 의미가 아닙니다.

직접 재현할 때는 일회용 Linux VM 또는 전용 privileged 컨테이너 안에서만 수행하세요. unshare -m은 util-linux에서 기본적으로 전파를 private으로 바꿉니다. shared를 관찰하려면 --propagation unchanged 등으로 그 동작을 명시해야 합니다. 명령 하나만 보고 커널 기본 동작으로 해석하면 안 됩니다.

3. Alpine minirootfs 준비

rootfs는 컨테이너 안에서 /로 보일 디렉터리입니다. 커널 이미지는 들어 있지 않습니다. 컨테이너는 호스트 Linux 커널을 공유하고, Alpine의 /bin·/lib·/etc 같은 사용자 공간 파일을 사용합니다. 작은 BusyBox와 musl을 포함한 공식 Alpine minirootfs로 시작합니다.

아래 명령은 Linux VM 안의 로컬 파일시스템에서 실행하세요. Mac의 공유 폴더는 권한·마운트 동작이 다를 수 있으므로 myctr 프로젝트와 rootfs를 VM 내부 작업 디렉터리에 두는 편이 재현하기 쉽습니다. 다운로드는 일반 사용자로, 압축 해제와 실행은 root 권한으로 합니다.

# Linux의 myctr 프로젝트 루트에서 실행
case "$(uname -m)" in
  aarch64|arm64) arch=aarch64 ;;
  x86_64)       arch=x86_64 ;;
  *) echo "이 예제는 aarch64/x86_64용입니다"; exit 1 ;;
esac
ver=3.22.2
archive="alpine-minirootfs-${ver}-${arch}.tar.gz"
url="https://dl-cdn.alpinelinux.org/alpine/v3.22/releases/${arch}"
curl -fLO "$url/$archive"
curl -fLO "$url/$archive.sha256"
sha256sum -c "$archive.sha256"

# 비어 있는 새 디렉터리에 추출한다. 기존 rootfs에 덮어쓰지 않는다.
mkdir rootfs
sudo tar --numeric-owner -xzf "$archive" -C rootfs
sudo mkdir -p rootfs/proc rootfs/dev
ls rootfs
file rootfs/bin/busybox

버전은 재현을 위해 3.22.2로 고정했습니다. aarch64 Linux에는 aarch64 rootfs를, x86_64에는 x86_64 rootfs를 사용합니다. tar에는 실행 파일·심볼릭 링크·공유 라이브러리가 함께 들어 있습니다. 호스트의 /bin/ls 하나만 복사하면 동적 로더와 라이브러리가 없어 실행되지 않을 수 있습니다.

Alpine 안의 프로그램을 실행한다myctr 바이너리는 호스트에서 실행합니다. 루트 교체 뒤에는 Alpine의 /bin/sh 등을 exec하므로, myctr 자체를 rootfs 안에 복사할 필요가 없습니다. 뒤의 chroot 비교용 Rust 프로그램은 예외입니다. Alpine 안에서 별도로 실행하므로 musl 정적 빌드가 필요합니다.
오류를 구분하기: 파일은 있는데 No such file?
  • ENOEXEC: CPU 아키텍처가 다르거나 실행 형식이 맞지 않는 경우를 확인하세요.
  • ENOENT: 실행 파일 경로뿐 아니라 ELF 인터프리터(/lib/ld-…) 또는 스크립트의 shebang 인터프리터가 없는 경우에도 나올 수 있습니다.
  • EACCES: 실행 권한, 경로 탐색 권한, noexec 마운트 여부를 확인하세요.

호스트에서 file rootfs/bin/busybox, readelf -l rootfs/bin/busybox로 형식과 인터프리터를 확인할 수 있습니다. rootfs를 완성하기 전까지는 성공한 경로와 실패 원인을 나눠서 보세요.

4. chroot와 pivot_root의 차이

chroot는 프로세스의 경로 탐색 기준을 바꿉니다. pivot_root는 mount namespace 안에서 새 루트를 올리고 기존 루트를 지정한 하위 디렉터리로 옮깁니다. 이 장은 후자에 이어 기존 루트를 떼어 내는 것까지 수행합니다.

chroot: 보이는 기준만 변경
chroot("rootfs")
chdir("/")
# 기존 마운트 트리는 남아 있다.
# 열린 FD도 닫히지 않는다.
pivot_root: 이전 루트까지 분리
pivot_root(rootfs, rootfs/.oldroot)
chdir("/")
# /proc, /dev 준비 뒤
umount2("/.oldroot", MNT_DETACH)
rmdir("/.oldroot")

chroot는 cwd를 자동으로 옮기지 않습니다. 권한이 남은 프로세스가 내부 디렉터리로 다시 chroot하면서 cwd를 밖에 남기면, ..를 따라 기존 트리를 올라갈 수 있습니다. chroot가 보안 격리 장치 자체는 아니라는 경고가 매뉴얼에 명시되어 있습니다. chroot(2)

실험: 같은 탈출 시도를 두 환경에 넣어 보기

scratchpad의 비교 프로그램은 먼저 현재 OS 정보를 읽고, /tmp/esc로 다시 chroot한 뒤 cwd를 바꾸지 않은 채 상위로 이동합니다. 마지막으로 도달한 디렉터리를 루트로 정하고 OS 정보를 다시 읽습니다.

// 의도적으로 cwd를 새 루트 밖에 남기는 비교 실험
std::fs::create_dir_all("/tmp/esc")?;
chroot("/tmp/esc")?;
for _ in 0..64 { let _ = chdir(".."); }
chroot(".")?;
// 여기에서 /etc/os-release 를 다시 읽어 비교한다.

Linux aarch64 재검증에서 단순 chroot 환경은 Alpine에서 바깥 Debian으로 돌아왔습니다. myctr의 pivot_root·oldroot 분리 뒤에는 같은 방법으로는 바깥 루트에 도달하지 못했고 Alpine에 머물렀습니다. 두 비교 모두 CAP_SYS_CHROOT 권한을 가진 프로세스에서 수행했습니다. 이 관찰은 특정 경로 탈출을 비교한 결과입니다. 권한과 열린 FD까지 모두 제한된 샌드박스를 증명하지는 않습니다.

5. 루트 교체의 순서와 실패 조건

pivot_root(new_root, put_old)는 새 루트로 쓸 마운트 지점과 이전 루트를 둘 하위 디렉터리를 받습니다. 그냥 압축을 푼 디렉터리는 마운트 지점이 아닐 수 있습니다. 자기 자신에게 bind mount해 조건을 맞춥니다. 호출 뒤에는 명시적으로 chdir("/")하여 cwd도 새 루트로 정합니다. pivot_root(2)

왜 장치를 먼저 준비하고 oldroot를 나중에 떼나?

pivot 직후 기존 /dev/null은 /.oldroot/dev/null에 있습니다. 7절에서 이 장치를 새 /dev/null에 bind합니다. 그다음 oldroot를 떼어도 새 위치의 bind mount는 살아 있습니다. 먼저 떼면 빌려 올 원본 경로를 잃습니다.

MNT_DETACH는 마운트를 경로 트리에서 즉시 분리하고 참조가 없어질 때 정리하는 lazy unmount입니다. 열린 FD를 강제로 닫는 연산은 아닙니다. 따라서 cwd를 새 루트로 옮기는 것과 불필요한 FD를 남기지 않는 것은 별도 책임입니다.

6. 새 PID 공간에 맞는 /proc

2장에서 echo $$는 1인데 ps에는 호스트 프로세스가 나오는 현상을 봤습니다. PID namespace를 바꿔도 이미 마운트된 procfs의 기준은 바뀌지 않기 때문입니다. 이번에는 새 PID namespace의 자식 안에서 /proc를 새로 마운트합니다. procfs의 프로세스 목록은 그 마운트가 속한 PID namespace를 기준으로 보입니다. pid_namespaces(7)

mount(
    Some("proc"), "/proc", Some("proc"),
    MsFlags::MS_NOSUID | MsFlags::MS_NODEV | MsFlags::MS_NOEXEC,
    None::<&str>,
)?;

mount 대상인 /proc 디렉터리가 rootfs에 있어야 합니다. nosuid,nodev,noexec는 procfs에서 setuid·장치 노드·직접 실행의 의미를 제한합니다. /proc를 전부 읽기 전용으로 만드는 옵션은 아닙니다.

getpid와 ps의 관찰 기준
명령은 새 PID namespace에서 실행됩니다. procfs와 --init을 바꿔 PID와 관찰 목록을 비교하세요.

명령의 getpid()

호스트 모드의 PID와 명령명은 설명용입니다. 실제 ps에는 ps 자신이나 셸 등 실행 방법에 따른 프로세스가 추가됩니다.




완료 기준의 run ps -o pid는 셸을 거치지 않고 ps를 PID 1로 직접 exec합니다. 그래서 출력의 유일한 PID가 1인지를 검사할 수 있습니다. 반면 대화형 셸에서 실행하는 ps에 여러 프로세스가 보이는 것은 정상입니다.







7. 최소한의 /dev 구성


Alpine tar를 푸는 것만으로 실행 환경 전체가 생기지는 않습니다. /dev/null은 이름이 null인 빈 파일이 아니라 커널 장치에 연결된 특수 파일입니다. 이번 구현은 새 tmpfs에 빈 마운트 대상을 만들고, 아직 남아 있는 이전 루트의 장치 여섯 개를 파일 단위로 bind합니다.


장치용도
null쓰기를 버리고 읽으면 EOF
zero0 바이트 공급
full쓰기에 ENOSPC를 돌려주는 테스트 장치
random, urandom커널 난수 장치
tty프로세스의 제어 터미널에 접근. 제어 터미널이 없으면 사용 불가


mount(Some("tmpfs"), "/dev", Some("tmpfs"),
      MsFlags::MS_NOSUID | MsFlags::MS_STRICTATIME,
      Some("mode=755,size=65536k"))?;
// 각 장치에 대해: 마운트 대상 파일을 만들고 이전 루트의 장치를 bind
File::create("/dev/null")?;
mount(Some("/.oldroot/dev/null"), "/dev/null", None::<&str>,
      MsFlags::MS_BIND, None::<&str>)?;
// 같은 방법으로 나머지 5개도 구성한다.


/dev tmpfs에는 MS_NODEV를 붙이지 않는다이 마운트에서는 장치를 사용해야 합니다. MS_NOSUID와 MS_NODEV는 다른 제한입니다. 장치 bind mount도 자체 마운트 속성을 갖기 때문에 실제 적용 옵션은 /proc/self/mountinfo에서 각각 확인해야 합니다. 64 MiB size는 tmpfs의 상한이지 즉시 예약하는 메모리 양은 아닙니다.


추가로 /dev/fd → /proc/self/fd, /dev/stdin → /proc/self/fd/0, stdout·stderr 링크를 만듭니다. 이 링크는 새 procfs가 있어야 의미가 있습니다. 파일 이름만 만들어서는 터미널이나 스트림이 생기지 않습니다.


왜 /dev 전체 bind나 devtmpfs 대신 일부만 빌리나?


호스트의 /dev 전체를 붙이면 불필요한 장치까지 노출됩니다. 이번에는 셸과 기본 명령에 필요한 항목만 선택합니다. 다만 이 코드는 capability나 장치 접근 정책까지 완성한 구현은 아닙니다.


/dev/pts·/dev/ptmx를 위한 새 devpts, pseudo-terminal 할당, 별도 세션 설정은 구현하지 않습니다. --init /bin/sh는 호출자의 표준 입출력을 물려받아 동작하며, Docker의 -it와 같은 터미널 기능은 아닙니다. /sys도 이 장에서는 마운트하지 않습니다.









8. 루트가 바뀌어도 남는 것: 환경 변수와 FD


검증 중 드러난 연결고리가 하나 있습니다. 호스트가 myctr에 넘긴 환경 변수는 clone·pivot_root·execvp를 지나 그대로 전달됩니다. execvp는 상속한 PATH로 프로그램을 찾지만, 그 경로는 이제 새 루트 안에서 해석합니다. 호스트의 /opt/homebrew/bin은 컨테이너 안에도 같은 디렉터리가 있을 때만 의미가 있습니다.


같은 PATH, 다른 /
모형 rootfs에는 /bin/ls와 /bin/sh만 있습니다. PATH에 /bin이 있는지와 절대 경로 실행의 차이를 보세요.




실제 execvp의 모든 오류 처리·기본 PATH 규칙을 구현한 모형은 아닙니다. 선택한 PATH와 파일 존재 여부를 비교합니다.


이번 참조 구현은 환경을 자동 정리하지 않습니다. 결과를 재현하려면 아래처럼 myctr 바깥에서 최소 환경을 지정할 수 있습니다. sudo가 환경을 바꿀 수 있으므로 sudo 뒤에서 env -i를 실행합니다.


sudo env -i PATH=/usr/sbin:/usr/bin:/sbin:/bin HOME=/root   ./target/debug/myctr run --rootfs ./rootfs /bin/sh -c 'echo "$PATH"; ls /'

# PATH와 무관하게 셸 자체를 찾으려면 절대 경로를 사용한다.
sudo ./target/debug/myctr run --rootfs ./rootfs /bin/sh


표준 입출력 FD 0·1·2도 물려받습니다. 열린 파일·디렉터리 FD가 있다면 루트 교체만으로 접근이 취소되지 않습니다. 이후 런타임을 강화할 때는 환경 변수 허용 목록과 불필요한 FD 닫기를 별도로 설계해야 합니다. 여기서는 발견한 동작을 숨기지 않고 완료 범위를 분명히 둡니다.

use std::ffi::CString;
use std::fs::{self, File};
use std::os::unix::fs::symlink;
use std::path::{Path, PathBuf};

use anyhow::{Context, Result, bail};
use clap::{Parser, Subcommand};
use nix::errno::Errno;
use nix::libc;
use nix::mount::{MntFlags, MsFlags, mount, umount2};
use nix::sched::{CloneFlags, clone};
use nix::sys::signal::{SigHandler, Signal, signal};
use nix::sys::wait::{WaitStatus, waitpid};
use nix::unistd::{ForkResult, Pid, chdir, execvp, fork, pivot_root, sethostname};

const STACK_SIZE: usize = 1024 * 1024;
const OLD_ROOT: &str = ".oldroot";
/// 호스트에서 빌려 올 장치 파일
const DEVICES: [&str; 6] = ["null", "zero", "full", "random", "urandom", "tty"];

#[derive(Parser)]
#[command(name = "myctr", about = "나만의 컨테이너 런타임")]
struct Cli {
    #[command(subcommand)]
    command: Command,
}

#[derive(Subcommand)]
enum Command {
    /// 명령을 새 네임스페이스와 rootfs 안에서 실행한다
    Run {
        /// 컨테이너의 루트가 될 디렉터리
        #[arg(long)]
        rootfs: PathBuf,
        /// 컨테이너 안에서 보일 hostname
        #[arg(long, default_value = "myctr")]
        hostname: String,
        /// PID 1에 작은 init을 두고 명령은 PID 2로 실행한다
        #[arg(long)]
        init: bool,
        /// 실행할 프로그램과 인자
        #[arg(required = true, trailing_var_arg = true, allow_hyphen_values = true)]
        cmd: Vec<String>,
    },
}

/// clone된 자식에게 넘길 설정
struct Config {
    rootfs: PathBuf,
    hostname: String,
    init: bool,
    argv: Vec<CString>,
}

fn main() -> Result<()> {
    match Cli::parse().command {
        Command::Run { rootfs, hostname, init, cmd } => {
            let argv = cmd
                .iter()
                .map(|s| CString::new(s.as_bytes()))
                .collect::<Result<_, _>>()
                .context("인자에 NUL 바이트가 있습니다")?;
            // 자식은 cwd가 바뀌기 전에 경로를 해석해야 하므로 절대 경로로 만든다
            let rootfs = fs::canonicalize(&rootfs)
                .with_context(|| format!("rootfs를 찾을 수 없습니다: {}", rootfs.display()))?;
            let code = run(&Config { rootfs, hostname, init, argv })?;
            std::process::exit(code);
        }
    }
}

fn run(cfg: &Config) -> Result<i32> {
    let mut stack = vec![0u8; STACK_SIZE];
    let flags = CloneFlags::CLONE_NEWUTS | CloneFlags::CLONE_NEWPID | CloneFlags::CLONE_NEWNS;
    let cb = Box::new(|| container_main(cfg));
    let child = unsafe { clone(cb, &mut stack, flags, Some(Signal::SIGCHLD as i32)) }
        .context("clone 실패 (root 권한으로 실행했나요?)")?;

    unsafe { signal(Signal::SIGINT, SigHandler::SigIgn) }.context("signal 설정 실패")?;
    wait_exit_code(child)
}

fn wait_exit_code(child: Pid) -> Result<i32> {
    match waitpid(child, None).context("waitpid 실패")? {
        WaitStatus::Exited(_, code) => Ok(code),
        WaitStatus::Signaled(_, sig, _) => Ok(128 + sig as i32),
        other => bail!("예상하지 못한 상태: {other:?}"),
    }
}

/// clone된 자식. 새 네임스페이스 안의 PID 1이다.
fn container_main(cfg: &Config) -> isize {
    if let Err(e) = setup(cfg) {
        eprintln!("myctr: {e:#}");
        return 1;
    }
    if cfg.init { mini_init(&cfg.argv) } else { exec(&cfg.argv) }
}

/// fork와 exec 사이에서 컨테이너의 모양을 만든다
fn setup(cfg: &Config) -> Result<()> {
    sethostname(&cfg.hostname).context("sethostname")?;
    setup_rootfs(&cfg.rootfs)
}

fn setup_rootfs(rootfs: &Path) -> Result<()> {
    // 1. 이후의 마운트가 호스트로 전파되지 않도록 모든 마운트를 private으로
    mount(None::<&str>, "/", None::<&str>, MsFlags::MS_REC | MsFlags::MS_PRIVATE, None::<&str>)
        .context("/ 를 rprivate으로 바꾸기")?;

    // 2. pivot_root의 new_root는 마운트 지점이어야 하므로 자기 자신에게 bind
    mount(Some(rootfs), rootfs, None::<&str>, MsFlags::MS_BIND | MsFlags::MS_REC, None::<&str>)
        .context("rootfs bind mount")?;

    // 3. 루트를 바꾼다. 이전 루트는 /.oldroot 에 걸린다
    let old_root = rootfs.join(OLD_ROOT);
    fs::create_dir_all(&old_root).context(".oldroot 만들기")?;
    pivot_root(rootfs, &old_root).context("pivot_root")?;
    chdir("/").context("chdir /")?;

    // 4. 이 PID 네임스페이스 기준의 procfs
    mount(
        Some("proc"),
        "/proc",
        Some("proc"),
        MsFlags::MS_NOSUID | MsFlags::MS_NODEV | MsFlags::MS_NOEXEC,
        None::<&str>,
    )
    .context("/proc 마운트")?;

    // 5. 최소한의 /dev. 장치 파일은 아직 붙어 있는 이전 루트에서 bind로 빌려 온다
    setup_dev().context("/dev 구성")?;

    // 6. 이전 루트를 떼어 내고 흔적을 지운다
    let old = format!("/{OLD_ROOT}");
    umount2(old.as_str(), MntFlags::MNT_DETACH).context("이전 루트 분리")?;
    fs::remove_dir(&old).context(".oldroot 지우기")?;
    Ok(())
}

fn setup_dev() -> Result<()> {
    mount(
        Some("tmpfs"),
        "/dev",
        Some("tmpfs"),
        MsFlags::MS_NOSUID | MsFlags::MS_STRICTATIME,
        Some("mode=755,size=65536k"),
    )?;
    for dev in DEVICES {
        let target = format!("/dev/{dev}");
        File::create(&target).with_context(|| format!("{target} 만들기"))?;
        let source = format!("/{OLD_ROOT}/dev/{dev}");
        mount(Some(source.as_str()), target.as_str(), None::<&str>, MsFlags::MS_BIND, None::<&str>)
            .with_context(|| format!("{target} bind"))?;
    }
    for (link, to) in [
        ("/dev/fd", "/proc/self/fd"),
        ("/dev/stdin", "/proc/self/fd/0"),
        ("/dev/stdout", "/proc/self/fd/1"),
        ("/dev/stderr", "/proc/self/fd/2"),
    ] {
        symlink(to, link).with_context(|| format!("{link} 링크"))?;
    }
    Ok(())
}

/// 성공하면 돌아오지 않는다. 돌아오면 127.
fn exec(argv: &[CString]) -> isize {
    if let Err(e) = unsafe { signal(Signal::SIGPIPE, SigHandler::SigDfl) } {
        eprintln!("myctr: SIGPIPE 복원 실패: {e}");
        return 1;
    }
    let err = execvp(&argv[0], argv).unwrap_err();
    eprintln!("myctr: {}: {err}", argv[0].to_string_lossy());
    127
}

/// PID 1로 남아 명령을 PID 2로 띄우고, 입양된 고아까지 거두다가
/// 명령이 끝나면 그 종료 코드로 끝난다.
fn mini_init(argv: &[CString]) -> isize {
    let main_child = match unsafe { fork() } {
        Ok(ForkResult::Child) => unsafe { libc::_exit(exec(argv) as i32) },
        Ok(ForkResult::Parent { child }) => child,
        Err(e) => {
            eprintln!("myctr-init: fork: {e}");
            return 1;
        }
    };
    loop {
        match waitpid(None, None) {
            Ok(WaitStatus::Exited(pid, code)) if pid == main_child => return code as isize,
            Ok(WaitStatus::Signaled(pid, sig, _)) if pid == main_child => return 128 + sig as isize,
            Ok(_) => continue,
            Err(Errno::EINTR) => continue,
            Err(e) => {
                eprintln!("myctr-init: waitpid: {e}");
                return 1;
            }
        }
    }
}

마운트가 성공했는데 exec가 127인 경우
루트 교체와 프로그램 실행은 다른 단계입니다. mount·pivot_root가 성공했다면 PATH, 실행 파일 경로, CPU 아키텍처, 동적 로더를 먼저 확인하세요. mount 실패가 아니라 exec 실패일 수 있습니다. 참조 구현은 setup 실패를 1, execvp 실패를 127로 돌려줍니다. 126/127을 오류 종류별로 나누는 셸의 세부 관례까지 구현하지는 않습니다.







11. 이번 장의 경계와 다음 단계


이제 컨테이너는 별도 UTS·PID·mount namespace와 자기 rootfs를 가집니다. rootfs는 공유 파일시스템에 있는 실제 디렉터리이므로 /etc에 쓰면 다음 실행에서도 남습니다. tmpfs /dev와 procfs는 자식의 마운트 환경에만 붙습니다. 실패 경로·동시 실행까지 다루는 rootfs 수명 관리는 아직 추가하지 않았습니다.


  • 신뢰하는 입력: 본인의 실습용 Alpine rootfs를 사용합니다. 임의 rootfs의 심볼릭 링크·중첩 마운트·장치 파일을 검증하는 로더는 아닙니다.
  • 권한: root·capability를 유지합니다. user namespace와 rootless는 5장, capability·seccomp 제한은 7장에서 다룹니다.
  • 자원: CPU·메모리·프로세스 수를 제한하지 않습니다. 루트를 바꿔도 메모리 폭주를 막을 수 없습니다.
  • 연결: 네트워크는 공유하고 DNS 설정은 별도로 구성하지 않았습니다. minirootfs만으로 패키지 다운로드까지 보장하지 않습니다.


다음 4장에서는 이 rootfs·mount namespace·새 /proc·/dev를 유지한 채 cgroups v2를 추가합니다. 4장의 자식은 pivot_root 전에 cgroup에 들어갑니다. 5장에서는 이를 부모의 PID 배치와 파이프 장벽으로 바꾸고, 6장의 네트워크와 7장의 보안 정책까지 같은 코드에 쌓습니다. --rootfs는 이후 장에서도 필수입니다.

확인 문제


CLONE_NEWNS만 추가한 직후 자식의 파일시스템은?
새 목록은 부모 목록의 복사에서 시작합니다. rootfs 준비와 루트 교체는 별도 작업입니다.


마운트 전파를 전체 트리에서 끊는 플래그 조합은?
PRIVATE은 전파 속성, REC는 하위 마운트까지 재귀 적용하는 범위입니다.


pivot_root 전에 rootfs를 자기 자신에게 bind하는 이유는?
압축을 푼 일반 디렉터리만으로는 pivot_root의 마운트 조건을 충족하지 못할 수 있습니다.


루트 교체 뒤 /proc를 자식에서 새로 마운트하는 이유는?
getpid의 번호표와 procfs가 보여 주는 PID 공간을 맞춰야 합니다.


이 구현이 oldroot를 떼는 시점은?
장치 원본 경로를 사용한 뒤 이전 루트를 분리합니다. 성공한 exec는 돌아오지 않습니다.


pivot_root가 환경 변수에 미치는 영향은?
환경 변수는 별도 정책이 필요합니다. PATH의 문자열은 같아도 경로 탐색은 새 루트 기준입니다.


17개 완료 기준을 통과했다는 의미는?
권한 제한, FD 정리, 악성 rootfs 검증, 동시 실행과 실패 복구는 이 스위트의 범위 밖입니다.
