user 네임스페이스와 rootless

지금까지 myctr를 실행할 때마다 sudo가 필요했습니다. 이번에는 호스트의 일반 사용자로 실행하면서 안에서는 UID 0이 되게 만듭니다. 핵심은 UID/GID 번호의 대응표와 권한의 적용 범위입니다. 부모가 매핑을 쓰는 동안 자식은 파이프에서 기다리고, 준비가 끝나야 hostname 설정과 exec를 시작합니다.

학습 목표

  • 컨테이너 안의 UID 0과 바깥의 UID 1000이 같은 프로세스를 가리키는 구조를 설명한다.
  • uid_map·gid_map의 세 열을 읽고, 단일 ID와 범위 매핑을 계산한다.
  • setgroups=deny를 gid_map보다 먼저 쓰는 이유를 이해한다.
  • 부모의 매핑·cgroup 배치와 자식의 실행 사이에 파이프 장벽을 구현한다.
  • 3·4장의 파일시스템 격리를 유지한 채 일반 사용자로 실행하고 누적 rootless 완료 기준을 통과한다.
4장의 rootfs와 cgroup을 유지합니다3~4장의 mount namespace·pivot_root·새 /proc·/dev에 user namespace를 더합니다. 부모가 매핑과 cgroup 배치를 마치면 자식은 ID 0을 선택하고 rootfs를 준비합니다. 따라서 id -u는 0, ls /는 Alpine, ps는 컨테이너 PID 공간을 봅니다. rootless에서는 호출자가 소유한 별도 rootfs를 사용합니다.

1. rootless: 어느 쪽의 root인가

UID 0이라는 숫자는 그것을 해석하는 user namespace와 함께 봐야 합니다. 호스트에서 UID 1000인 프로세스를 새 user namespace 안의 UID 0에 대응시키면, id -u는 안에서 0, 바깥에서 본 소유자는 1000이 됩니다. 번호를 다르게 표시하는 것과 바깥 시스템을 관리할 권한을 얻는 것은 다릅니다.

CLONE_NEWUSER와 CLONE_NEWUTS | CLONE_NEWPID를 함께 주면 user namespace를 먼저 만들고 나머지 namespace를 그 권한 범위 아래 생성할 수 있습니다. 그래서 호스트의 일반 사용자도 새 UTS·PID 공간을 만들 수 있습니다. 다만 커널·보안 정책에서 비특권 user namespace를 허용해야 합니다. clone(2)

상태호스트 EUID안의 UID이 장의 실행
기존 root 실행00user namespace를 새로 만들지 않고 4장 동작 유지
일반 사용자 실행1000 예시0자기 UID/GID 하나씩 매핑하는 rootless 모드
root + 범위 옵션00으로 명시 전환--userns-base 100000으로 넓은 매핑 실험

rootless 모드는 옵션 이름이 아니라 실행자의 effective UID로 고릅니다. sudo myctr run --rootfs ./rootfs id는 rootless 검사가 아닙니다. 일반 사용자 셸에서 ./target/debug/myctr run --rootfs ./rootfs-user id를 실행해야 합니다.

2. uid_map·gid_map 읽기

부모는 자식의 호스트 PID로 /proc/<pid>/uid_map과 gid_map을 엽니다. 이 예제의 부모가 쓰는 한 줄은 안쪽 시작 ID · 바깥쪽 시작 ID · 길이입니다. 두 매핑은 별도이며 UID를 썼다고 GID가 함께 바뀌지 않습니다. 아래의 바깥은 이 장에서 직접 부모인 user namespace를 뜻합니다. 중첩 user namespace에서는 물리 머신의 초기 namespace와 다를 수 있습니다.

# 부모 namespace에서 자식 PID가 4201이라면
# 안쪽 시작   바깥쪽 시작   길이
# 0           1000         1
printf '0 1000 1' > /proc/4201/uid_map
# gid_map도 별도 설정한다. rootless 순서는 4절에서 다룬다.

한 범위 안에서는 바깥 ID = 바깥 시작 + (안쪽 ID − 안쪽 시작)으로 계산합니다. 길이에 끝점이 포함되는지 주의하세요. 0 100000 65536은 안쪽 0..65535를 바깥 100000..165535에 대응시킵니다. 0 1000 1에는 안쪽 UID 1이 없습니다.

UID 매핑 계산기
왼쪽의 ID 범위를 바꾸고 안쪽 UID가 바깥에서 누구인지 계산하세요. 하나의 extent만 다루는 모형입니다.

번호 계산만 보여 줍니다. 계산 가능한 범위라는 사실이 그 매핑을 쓸 권한을 뜻하지는 않습니다.

65534가 보이면 매핑 실패인가?

매핑되지 않은 ID는 여러 사용자 공간 인터페이스에서 overflow ID로 표시되며 기본값은 65534입니다. 설정에 따라 값은 달라질 수 있습니다. 이는 여러 ID가 실제로 같은 사용자로 합쳐졌다는 뜻이 아니라 현재 namespace에서 표현할 매핑이 없다는 뜻입니다.

특히 root가 0 100000 65536을 쓰더라도, 자식이 원래 물려받은 호스트 UID 0은 그 범위에 없습니다. 따라서 매핑 후 자식이 setgid(0)·setuid(0)으로 안쪽 ID 0을 선택해야 합니다. 참조 구현은 이 전환을 파이프에서 깨어난 뒤 수행합니다. 매핑만 쓰고 exec하면 의도와 다른 ID로 실행할 수 있습니다.

매핑은 해당 namespace에서 한 번 설정하는 초기화 작업입니다. 실행 중 임의로 덮어쓰는 설정 파일처럼 다루면 안 됩니다. 전체 매핑 규칙과 쓰기 권한 조건은 user_namespaces(7)에서 확인할 수 있습니다.

3. 단일 ID와 subordinate ID 범위

이번 rootless 기본 모드는 자신의 effective UID/GID 하나만 안의 0에 대응시킵니다. helper나 subordinate ID 설정 없이 이해할 수 있는 최소 단위입니다. 안에서 UID 1·1000 같은 다른 계정으로 전환하거나 다양한 소유권의 이미지를 표현할 수 있는 구현은 아닙니다.

일반 사용자: 자기 ID 한 개
# 일반 사용자 (예: UID/GID 1000)
./target/debug/myctr run --rootfs ./rootfs-user id
# 기대: uid=0(root) gid=0(root) ...
# 바깥 관점의 자식 소유자는 여전히 1000
root의 범위 실험
# root + 쓰기 가능한 cgroup v2 실습 환경
sudo ./target/debug/myctr run --rootfs ./rootfs-range --userns-base 100000 id
# 안쪽 0..65535 → 바깥 100000..165535
# 안쪽 ID 0은 부모 매핑 뒤 자식이 명시적으로 선택

--userns-base는 root 전용 학습 옵션입니다. root가 직접 매핑을 쓰며 길이는 65536으로 고정합니다. 일반 사용자가 이 옵션으로 남의 ID를 임의로 얻을 수는 없습니다. base와 범위의 합이 유효 ID 영역을 벗어나는 입력도 거부합니다.

실제 rootless 런타임의 여러 ID는 어디서 오나

/etc/subuid·/etc/subgid는 사용자에게 할당한 subordinate ID 범위의 자료입니다. 예를 들어 alice:100000:65536은 alice에게 그 시작점과 길이의 범위를 위임하는 항목입니다. 파일을 읽었다고 커널 매핑이 자동 생성되지는 않습니다. subuid(5)

일반 사용자의 넓은 매핑은 newuidmap·newgidmap 같은 권한 있는 helper가 위임 범위를 검사한 뒤 설정하는 방식으로 구성할 수 있습니다. root조차 이 helper를 쓸 때는 helper가 요구하는 위임 조건을 따라야 합니다. 이 장의 root 전용 직접 쓰기 옵션과 helper 호출을 구분하세요. newuidmap(1), newgidmap(1)

단일 매핑의 제한: chown과 setuid

0만 매핑한 namespace에서 UID 123으로 바꾸거나 파일 소유자를 123으로 설정하려면 대응할 바깥 ID가 없습니다. 해당 연산이 실패할 수 있습니다. 이미지의 소유권을 보존하려면 여러 ID 범위와 저장소 소유권 전략까지 함께 설계해야 합니다. 이번 참조 구현은 subuid를 읽거나 helper를 자동 실행하지 않습니다.

4. setgroups를 먼저 막는 이유

비특권 부모가 단일 GID 매핑을 쓰려면 먼저 자식의 /proc/<pid>/setgroups에 deny를 씁니다. 이 namespace에서 setgroups(2)를 못 하게 한 뒤 gid_map을 허용하는 조건입니다. uid_map과 혼동하지 마세요.

# 일반 사용자 UID/GID가 모두 1000인 예시. 쓰는 주체는 부모.
printf deny       > /proc/4201/setgroups
printf '0 1000 1' > /proc/4201/uid_map
printf '0 1000 1' > /proc/4201/gid_map
# 중요: gid_map 전에 deny. uid_map/gid_map은 각각 한 번 설정.

deny는 보조 그룹 목록을 비우는 호출이 아닙니다. 목록을 바꾸는 setgroups() 자체를 막는 정책이며, 이 namespace에서 다시 allow로 되돌릴 수 없습니다. 상속한 보조 그룹까지 없어졌다고 가정해서는 안 됩니다. 보조 그룹 목록과 effective GID도 다른 값입니다. setgroups(2)

참조 구현의 root 범위 매핑 모드는 이와 달리 매핑 뒤 setgroups(&[])로 상속한 보조 그룹을 비우고, 기본 GID와 UID를 안의 0으로 옮깁니다. rootless 경로에서는 deny 때문에 같은 호출을 할 수 없으므로 기존 보조 그룹을 유지합니다.

실험: deny여도 기존 그룹의 파일은 읽을 수 있다

별도 fixture에서 바깥 UID/GID 1000에 보조 그룹 2000을 준 뒤 rootless로 실행했습니다. 안에서는 id의 보조 그룹에 매핑 없는 overflow 값이 나타났고, setgroups는 deny였습니다. 그런데 바깥 그룹 2000에 읽기를 허용한 fixture는 계속 읽혔습니다. 매핑되지 않은 번호가 보이지 않는 것과 커널의 기존 그룹 자격 증명이 없어지는 것은 다릅니다.

보조 그룹을 버리면 왜 권한이 늘 수 있나?

파일의 group 권한이 other보다 좁은 경우가 있습니다. 그 그룹 소속을 버리면 오히려 other 권한을 적용받아 이전에는 못 읽던 파일을 읽을 수 있습니다. 새 namespace의 capability가 이 우회로를 열지 않도록 비특권 gid_map 경로에 setgroups 제한이 있습니다.

이번 코드의 rootless 경로는 deny를 씁니다. 부모가 충분한 권한으로 범위 매핑을 직접 쓰는 경로는 같은 제한 경로를 사용하지 않습니다. 두 경우를 무조건 같은 셸 명령 목록으로 처리하지 않습니다.

5. 부모와 자식 사이의 파이프 장벽

clone은 부모와 자식을 동시에 실행 가능하게 만듭니다. 부모가 매핑 파일을 쓰기도 전에 자식이 id·setuid·exec를 시작하면 준비 전 상태를 관찰합니다. 4장의 자식이 스스로 cgroup에 들어가는 방식도 바꿉니다. 부모가 자식의 호스트 PID로 배치·매핑을 완료하고 1바이트를 보낼 때까지 자식이 기다리게 만듭니다.

매핑 장벽 실험실
clone 뒤에 부모의 준비 순서를 진행하세요. 일부러 gid_map을 먼저 쓰거나 일찍 깨워 결과를 비교할 수 있습니다.

    부모

    자식

    부모·자식의 준비 상태를 설명하는 모형입니다. 실제 커널의 모든 매핑 권한 조건·errno를 구현하지 않습니다. 실제 참조 코드는 준비 오류가 나면 1바이트를 보내지 않습니다.

    자식의 쓰기 끝도 닫아야 한다

    파이프는 복제된 FD를 통해 부모와 자식 양쪽에 남습니다. 자식이 자기 쓰기 끝을 닫지 않으면 부모가 실패해 writer를 닫아도 아직 writer가 하나 있으므로 read가 EOF를 받지 못합니다. O_CLOEXEC는 성공한 exec 시점의 누출을 막지만, exec 전 대기 중의 EOF 문제를 대신 해결하지는 않습니다.

    실패 시에도 wait가 필요하다

    부모에서 map.write(child)?만 쓰고 바로 반환하면, 자식이 EOF를 받고 종료하기 전에 cgroup 정리가 먼저 실행될 수 있습니다. 참조 구현은 준비 결과를 보관하고 writer를 닫은 뒤, 실패한 경우에도 waitpid로 자식을 회수하고 나서 오류를 반환합니다. 기다리던 시스템 콜이 EINTR로 끊기면 재시도합니다.

    6. user namespace의 capability 경계

    새 user namespace의 자식은 그 namespace 안에서 capability를 가집니다. 그렇다고 부모 user namespace에 속한 자원을 마음대로 바꾸지는 못합니다. UTS·PID 등 자원을 소유한 namespace와 그 namespace의 소유 user namespace가 권한 판정의 기준이 됩니다. capabilities(7)

    이 구현의 새 UTS는 자식 user namespace의 권한 범위에 있습니다. 그래서 hostname 설정은 가능합니다. 반면 바깥 UID 0 소유의 mode 600 파일은 자기 UID로 읽을 수 없으며, 새 namespace의 root라는 이유로 이를 우회하지 못합니다. 호출자의 UID가 소유한 파일에는 접근할 수 있습니다. 다만 3장의 rootfs가 적용되어 그 파일은 rootfs 안에 있어야 합니다. 호스트 경로를 그대로 넘겨도 컨테이너에서 같은 파일을 찾을 수는 없습니다.

    안의 root는 어디까지 할 수 있나
    UID 1000 → 안의 0 단일 매핑을 사용합니다. 표준 입출력을 상속하고 파일 경로는 rootfs 안에서 해석하는 모델입니다.

    DAC·ID 매핑·위임 관계를 설명합니다. 실제 결과에는 ACL, LSM, seccomp, 마운트 속성 같은 다른 제한도 영향을 줍니다.

    경로 격리와 ID 권한을 함께 확인하세요rootfs는 접근할 경로를 나누고 user namespace는 ID와 권한의 범위를 바꿉니다. rootfs 안의 호출자 소유 파일은 수정할 수 있으며 변경은 다음 실행에도 남습니다. 환경·FD 허용 목록은 아직 없고, 네트워크 격리와 seccomp는 6·7장에서 추가합니다.

    7. 4장의 cgroup과 연결하기

    4장에서는 자식이 cgroup.procs에 0을 썼습니다. 이제 준비 중인 부모가 자식의 호스트 PID를 씁니다. 자식의 user namespace capability로 바깥 cgroup을 관리할 수 있다고 가정하지 않기 위한 구조입니다. root 실행에서는 4장 제한을 유지하고, rootless에서는 cgroup을 만들지 않습니다.

    실행 모드별 준비 계획
    같은 run 명령도 실행자와 범위 옵션에 따라 준비할 자원이 달라집니다.

    rootless에서 --memory·--cpus·--pids를 주면, 무시하거나 적용한 척하지 않고 오류를 냅니다. cgroup v2의 권한 위임은 user namespace 생성과 별도입니다. systemd 환경에서는 위임받은 subtree에서 작업하는 방식으로 확장할 수 있지만 이번 코드에는 그 경로 탐색·권한 처리를 넣지 않습니다. cgroup v2 문서, systemd cgroup delegation

    cgroup을 생략하면 자원 제한이 전부 사라지나?

    프로세스는 부모의 cgroup을 상속합니다. rootless 모드에서 새 cgroup을 만들지 않는다는 것은 myctr가 컨테이너별 제한을 추가하지 않는다는 뜻입니다. 바깥 로그인 세션·서비스·Docker 컨테이너의 상위 cgroup 제한이 있다면 계속 적용됩니다.

    8. 구현 가이드

    4장의 참조 구현에서 출발합니다. 새 명령 사용법은 다음과 같습니다. rootless 기본 실행에 sudo를 붙이지 않는 것이 핵심입니다.

    # 일반 사용자 셸에서

fn main() -> Result<()> {
    match Cli::parse().command {
        Command::Run { rootfs, hostname, init, memory, cpus, pids, userns_base, cmd } => {

                .iter()
                .map(|s| CString::new(s.as_bytes()))

/// "64M", "1G", "512K", "1048576" 을 바이트 수로
fn parse_bytes(s: &str) -> Result<u64, String> {
    let (num, mul) = match s.chars().last() {
        Some('K' | 'k') => (&s[..s.len() - 1], 1 << 10),
        Some('M' | 'm') => (&s[..s.len() - 1], 1 << 20),
        Some('G' | 'g') => (&s[..s.len() - 1], 1 << 30),
        _ => (s, 1),
    };
    num.parse::<u64>().map(|n| n * mul).map_err(|e| format!("{s}: {e}"))
}

fn run(rootfs: PathBuf, 
    hostname: String,
    init: bool,
    argv: Vec<CString>,
    limits: &Limits,
    userns_base: Option<u32>,
) -> Result<i32> {
    let rootless = !Uid::effective().is_root();
    let idmap = match (rootless, userns_base) {
        (true, Some(_)) => bail!("--userns-base는 root로 실행할 때만 쓸 수 있습니다"),
        (true, None) => Some(IdMap::rootless()),
        (false, Some(base)) => {
            if base.checked_add(USERNS_RANGE - 1).is_none_or(|last| last == u32::MAX) {
                bail!("--userns-base는 0..4294901759 범위여야 합니다 (65536개 ID, UID/GID -1 제외)");
            }
            Some(IdMap::range(base))
        },
        (false, None) => None,
    };
    let cgroup = if rootless {
        if limits.any() {
            bail!("rootless 모드에서는 --memory/--cpus/--pids를 쓸 수 없습니다 (cgroup 위임이 필요합니다)");
        }
        None
    } else {
        Some(Cgroup::create(&format!("ctr-{}", std::process::id()), limits)?)
    };

    // O_CLOEXEC: 사용자 프로그램으로 새지 않게
    let (sync_rd, sync_wr) = pipe2(OFlag::O_CLOEXEC).context("pipe")?;
    let cfg = Config { rootfs,
        hostname, init, argv,
        sync: (sync_rd.as_raw_fd(), sync_wr.as_raw_fd()),
        userns: idmap.is_some(),
        // 특권 range 모드에서는 상속한 호스트 보조 그룹을 남기지 않는다.
        // rootless는 setgroups=deny이므로 변경할 수 없다.
        clear_groups: idmap.as_ref().is_some_and(|map| !map.deny_setgroups),
    };

    let mut flags = CloneFlags::CLONE_NEWUTS | CloneFlags::CLONE_NEWPID | CloneFlags::CLONE_NEWNS;
    if idmap.is_some() {
        flags |= CloneFlags::CLONE_NEWUSER;
    }
    let mut stack = vec![0u8; STACK_SIZE];
    let cb = Box::new(|| container_main(&cfg));
    let child = unsafe { clone(cb, &mut stack, flags, Some(Signal::SIGCHLD as i32)) }
        .context("clone 실패")?;
    drop(sync_rd);

    // 준비 실패 시 먼저 파이프를 닫는다. 자식은 EOF를 받고 종료하며,
    // 부모는 반드시 wait로 회수한 뒤 cgroup을 정리한다.
    let prepared = (|| -> Result<()> {
        if let Some(cg) = &cgroup {
            cg.add(child)?;
        }
        if let Some(map) = &idmap {
            map.write(child)?;
        }
        unsafe { signal(Signal::SIGINT, SigHandler::SigIgn) }
            .context("signal 설정 실패")?;
        write(&sync_wr, &[1]).context("자식 깨우기")?;
        Ok(())
    })();
    drop(sync_wr);
    if let Err(error) = prepared {
        // EOF로 종료한 PID 1을 회수하기 전에 Cgroup::drop이 실행되면
        // cgroup.procs가 비어 있지 않아 정리가 실패할 수 있다.
        wait_exit_code(child).context("준비 실패한 자식 회수")?;
        return Err(error);
    }
    let code = wait_exit_code(child)?;
    if cgroup.as_ref().is_some_and(|cg| cg.oom_kills() > 0) {
        eprintln!("myctr: 메모리 상한을 넘어 OOM killer가 프로세스를 종료했습니다");
    }
    Ok(code)
}

fn wait_exit_code(child: Pid) -> Result<i32> {
    loop {
        match waitpid(child, None) {
            Ok(WaitStatus::Exited(_, code)) => return Ok(code),
            Ok(WaitStatus::Signaled(_, sig, _)) => return Ok(128 + sig as i32),
            Ok(other) => bail!("예상하지 못한 상태: {other:?}"),
            Err(Errno::EINTR) => continue,
            Err(error) => return Err(error).context("waitpid 실패"),
        }
    }
}

/// user 네임스페이스의 UID/GID 매핑
struct IdMap {
    uid_map: String,
    gid_map: String,
    /// 비특권 프로세스가 gid_map을 쓰려면 먼저 setgroups를 막아야 한다
    deny_setgroups: bool,
}

impl IdMap {
    /// 컨테이너 root(0) 하나를 나 자신에게
    fn rootless() -> Self {
        IdMap {
            uid_map: format!("0 {} 1", Uid::effective()),
            gid_map: format!("0 {} 1", Gid::effective()),
            deny_setgroups: true,
        }
    }

    /// 컨테이너의 0..65535 를 호스트의 base..base+65535 로
    fn range(base: u32) -> Self {
        IdMap {
            uid_map: format!("0 {base} {USERNS_RANGE}"),
            gid_map: format!("0 {base} {USERNS_RANGE}"),
            deny_setgroups: false,
        }
    }

    fn write(&self, pid: Pid) -> Result<()> {
        let proc = PathBuf::from(format!("/proc/{pid}"));
        if self.deny_setgroups {
            fs::write(proc.join("setgroups"), "deny").context("setgroups 막기")?;
        }
        fs::write(proc.join("uid_map"), &self.uid_map)
            .with_context(|| format!("uid_map 쓰기 ({})", self.uid_map))?;
        fs::write(proc.join("gid_map"), &self.gid_map)
            .with_context(|| format!("gid_map 쓰기 ({})", self.gid_map))?;
        Ok(())
    }
}

struct Cgroup {
    path: PathBuf,
}

impl Cgroup {
    fn create(name: &str, limits: &Limits) -> Result<Self> {
        let parent = Path::new(CGROUP_ROOT).join(CGROUP_PARENT);
        fs::create_dir_all(&parent).with_context(|| format!("{} 만들기", parent.display()))?;
        // 부모에서 컨트롤러를 켜야 자식 cgroup에 memory.max 같은 파일이 생긴다
        fs::write(parent.join("cgroup.subtree_control"), "+memory +cpu +pids")
            .context("컨트롤러 활성화 (상위 cgroup의 cgroup.subtree_control에 memory cpu pids가 켜져 있나요?)")?;

        let path = parent.join(name);
        fs::create_dir(&path).with_context(|| format!("{} 만들기", path.display()))?;
        let cg = Cgroup { path };
        if let Some(bytes) = limits.memory {
            cg.write("memory.max", &bytes.to_string())?;
            // 스왑으로 도망가지 못하게. 스왑 계정이 꺼진 커널에는 파일이 없다
            if cg.path.join("memory.swap.max").exists() {
                cg.write("memory.swap.max", "0")?;
            }
        }
        if let Some(cpus) = limits.cpus {
            let quota = (cpus * CPU_PERIOD_US as f64) as u64;
            cg.write("cpu.max", &format!("{quota} {CPU_PERIOD_US}"))?;
        }
        if let Some(n) = limits.pids {
            cg.write("pids.max", &n.to_string())?;
        }
        Ok(cg)
    }

    fn write(&self, file: &str, value: &str) -> Result<()> {
        fs::write(self.path.join(file), value)
            .with_context(|| format!("{}/{file} 에 {value} 쓰기", self.path.display()))
    }

    /// 프로세스를 이 cgroup으로 옮긴다 (호스트 PID)
    fn add(&self, pid: Pid) -> Result<()> {
        self.write("cgroup.procs", &pid.to_string())
    }

    /// memory.events 의 oom_kill 카운터
    fn oom_kills(&self) -> u64 {
        fs::read_to_string(self.path.join("memory.events"))
            .ok()
            .and_then(|s| {
                s.lines()
                    .find_map(|l| l.strip_prefix("oom_kill ").and_then(|n| n.parse().ok()))
            })
            .unwrap_or(0)
    }
}

impl Drop for Cgroup {
    fn drop(&mut self) {
        // 프로세스가 남아 있으면 EBUSY. PID 1이 끝나면 네임스페이스 전체가 정리되므로 비어 있다
        if let Err(e) = fs::remove_dir(&self.path) {
            eprintln!("myctr: cgroup 정리 실패 {}: {e}", self.path.display());
        }
    }
}

/// clone된 자식. 새 네임스페이스 안의 PID 1이다.
fn container_main(cfg: &Config) -> isize {
    // 부모가 cgroup과 ID 매핑을 끝낼 때까지 기다린다.
    // 쓰는 쪽을 닫아 두어야 부모가 죽었을 때 read가 EOF(0)로 깨어난다
    let _ = close(cfg.sync.1);
    let mut buf = [0u8; 1];
    loop {
        match read(cfg.sync.0, &mut buf) {
            Ok(1) => break,
            Err(Errno::EINTR) => continue,
            _ => {
                eprintln!("myctr: 부모가 준비를 마치지 못했습니다");
                return 1;
            }
        }
    }
    let _ = close(cfg.sync.0);

    if let Err(e) = setup(cfg) {
        eprintln!("myctr: {e:#}");
        return 1;
    }
    if cfg.init { mini_init(&cfg.argv) } else { exec(&cfg.argv) }
}

/// fork와 exec 사이에서 컨테이너의 모양을 만든다
fn setup(cfg: &Config) -> Result<()> {
    if cfg.userns {
        // 매핑은 ID의 대응표만 만든다. 특히 range 모드에서 host UID 0은
        // 매핑 밖이므로, 새 namespace의 ID 0으로 자격 증명을 옮긴다.
        if cfg.clear_groups {
            setgroups(&[]).context("보조 그룹 비우기")?;
        }
        setgid(Gid::from_raw(0)).context("컨테이너 GID 0으로 전환")?;
        setuid(Uid::from_raw(0)).context("컨테이너 UID 0으로 전환")?;
    }
    sethostname(&cfg.hostname).context("sethostname")?;
    setup_rootfs(&cfg.rootfs)?;
    Ok(())
}

/// 실습 중 호스트 /를 rootfs로 지정하거나 준비를 빠뜨리는 실수를 막는다.
/// 신뢰하는 Alpine 입력을 전제로 하며 악성 rootfs 검증기는 아니다.
fn validate_rootfs(rootfs: &Path) -> Result<()> {
    if rootfs == Path::new("/") || !rootfs.is_dir() {
        bail!("rootfs는 호스트 /가 아닌 디렉터리여야 합니다");
    }
    if !fs::symlink_metadata(rootfs.join("bin/sh")).is_ok_and(|meta| meta.is_file() || meta.file_type().is_symlink())
        || !rootfs.join("proc").is_dir() || !rootfs.join("dev").is_dir() {
        bail!("rootfs에 bin/sh와 proc·dev 디렉터리를 준비하세요");
    }
    Ok(())
}

fn setup_rootfs(rootfs: &Path) -> Result<()> {
    // 1. 이후의 마운트가 호스트로 전파되지 않도록 모든 마운트를 private으로
    mount(None::<&str>, "/", None::<&str>, MsFlags::MS_REC | MsFlags::MS_PRIVATE, None::<&str>)
        .context("/ 를 rprivate으로 바꾸기")?;

    // 2. pivot_root의 new_root는 마운트 지점이어야 하므로 자기 자신에게 bind
    mount(Some(rootfs), rootfs, None::<&str>, MsFlags::MS_BIND | MsFlags::MS_REC, None::<&str>)
        .context("rootfs bind mount")?;

    // 3. 루트를 바꾼다. 이전 루트는 /.oldroot 에 걸린다
    let old_root = rootfs.join(OLD_ROOT);
    fs::create_dir_all(&old_root).context(".oldroot 만들기")?;
    pivot_root(rootfs, &old_root).context("pivot_root")?;
    chdir("/").context("chdir /")?;

    // 4. 이 PID 네임스페이스 기준의 procfs
    mount(
        Some("proc"),
        "/proc",
        Some("proc"),
        MsFlags::MS_NOSUID | MsFlags::MS_NODEV | MsFlags::MS_NOEXEC,
        None::<&str>,
    )
    .context("/proc 마운트")?;

    // 5. 최소한의 /dev. 장치 파일은 아직 붙어 있는 이전 루트에서 bind로 빌려 온다
    setup_dev().context("/dev 구성")?;

    // 6. 이전 루트를 떼어 내고 흔적을 지운다
    let old = format!("/{OLD_ROOT}");
    umount2(old.as_str(), MntFlags::MNT_DETACH).context("이전 루트 분리")?;
    fs::remove_dir(&old).context(".oldroot 지우기")?;
    Ok(())
}

fn setup_dev() -> Result<()> {
    mount(
        Some("tmpfs"),
        "/dev",
        Some("tmpfs"),
        MsFlags::MS_NOSUID | MsFlags::MS_STRICTATIME,
        Some("mode=755,size=65536k"),
    )?;
    for dev in DEVICES {
        let target = format!("/dev/{dev}");
        File::create(&target).with_context(|| format!("{target} 만들기"))?;
        let source = format!("/{OLD_ROOT}/dev/{dev}");
        mount(Some(source.as_str()), target.as_str(), None::<&str>, MsFlags::MS_BIND, None::<&str>)
            .with_context(|| format!("{target} bind"))?;
    }
    for (link, to) in [
        ("/dev/fd", "/proc/self/fd"),
        ("/dev/stdin", "/proc/self/fd/0"),
        ("/dev/stdout", "/proc/self/fd/1"),
        ("/dev/stderr", "/proc/self/fd/2"),
    ] {
        symlink(to, link).with_context(|| format!("{link} 링크"))?;
    }
    Ok(())
}

/// 성공하면 돌아오지 않는다. 돌아오면 127.
fn exec(argv: &[CString]) -> isize {
    if let Err(e) = unsafe { signal(Signal::SIGPIPE, SigHandler::SigDfl) } {
        eprintln!("myctr: SIGPIPE 복원 실패: {e}");
        return 1;
    }
    let err = execvp(&argv[0], argv).unwrap_err();
    eprintln!("myctr: {}: {err}", argv[0].to_string_lossy());
    127
}

/// PID 1로 남아 명령을 PID 2로 띄우고, 입양된 고아까지 거두다가
/// 명령이 끝나면 그 종료 코드로 끝난다.
fn mini_init(argv: &[CString]) -> isize {
    let main_child = match unsafe { fork() } {
        Ok(ForkResult::Child) => unsafe { libc::_exit(exec(argv) as i32) },
        Ok(ForkResult::Parent { child }) => child,
        Err(e) => {
            eprintln!("myctr-init: fork: {e}");
            return 1;
        }
    };
    loop {
        match waitpid(None, None) {
            Ok(WaitStatus::Exited(pid, code)) if pid == main_child => return code as isize,
            Ok(WaitStatus::Signaled(pid, sig, _)) if pid == main_child => return 128 + sig as isize,
            Ok(_) => continue,
            Err(Errno::EINTR) => continue,
            Err(e) => {
                eprintln!("myctr-init: waitpid: {e}");
                return 1;
            }
        }
    }
}

    11. 누적된 격리와 다음 단계

    이번 참조 구현은 3장의 rootfs와 새 procfs를 유지합니다. rootless용 rootfs는 일반 사용자 소유로 준비하고, root의 범위 매핑용 rootfs는 지정한 바깥 UID/GID가 소유하도록 별도로 준비합니다. 매핑 방식에 맞는 파일 소유권은 rootfs 격리와 함께 필요한 실행 조건입니다.

    • 마운트: user namespace와 함께 새 mount namespace를 만들고 rprivate·self-bind·pivot_root를 수행합니다.
    • rootfs 소유권: 안의 0이 바깥의 누구인지 기준으로 준비합니다. 단일 ID 매핑은 이미지의 여러 계정을 표현하지 못합니다.
    • /dev: 이전 루트에서 필요한 장치를 개별 bind한 뒤 oldroot를 분리합니다. 비특권 실행에서도 같은 경로를 검사합니다.
    • cgroup: root 모드는 부모가 배치하고 호스트에서 관찰합니다. rootless의 컨테이너별 제한은 위임 기능이 필요하므로 아직 거부합니다.

    rootless는 권한 범위를 좁힌 실행 방식입니다. 현재는 rootfs 격리와 ID 매핑이 연결되었고, rootless의 개별 cgroup 위임·네트워크 연결·시스템 콜 정책은 각각 별도 단계입니다. 다음 6장에서는 net namespace와 veth로 네트워크 연결을 구성합니다. 누가 새 network namespace를 소유하고 바깥 링크를 설정할 권한이 있는지가 다시 중요해집니다.

    핵심 요약

    • user namespace의 root는 바깥 root와 다릅니다. 매핑은 ID의 대응표입니다.
    • 부모가 uid_map·gid_map을 쓰고, rootless에서는 gid_map 전에 setgroups deny를 설정합니다.
    • 파이프 장벽 뒤에 ID 0 선택·hostname·rootfs 준비·exec가 옵니다. 실패 경로도 writer 닫기와 자식 회수가 필요합니다.
    • rootless 기본 경로는 cgroup을 만들지 않고 제한 옵션을 거부합니다. 파일시스템 격리는 3장에서 이어받습니다.

    확인 문제

    rootless에서 안쪽 UID 0, 바깥 UID 1000인 프로세스는?
    UID 매핑은 번호의 대응표이며 부모 namespace의 root 권한을 부여하지 않습니다.
    uid_map의 0 100000 65536에서 안쪽 UID 65535는?
    100000 + (65535 - 0) = 165535입니다. 길이는 65536개입니다.
    비특권 gid_map 설정 전에 필요한 동작은?
    비특권 GID 매핑 경로에서는 setgroups를 먼저 제한합니다. 보조 그룹 목록을 비우는 호출은 아닙니다.
    자식이 파이프의 쓰기 끝을 닫지 않으면?
    자식 자신도 writer를 가지고 있으면 아직 열린 쓰기 끝이 있습니다.
    rootless에서 --memory 64M을 지정한 이번 구현은?
    이번 구현은 컨테이너별 cgroup을 생략하고 제한 옵션을 명시적으로 거부합니다.
    root의 범위 매핑 뒤 자식이 ID 0을 명시적으로 선택하는 이유는?
    매핑 파일 작성과 현재 프로세스 ID 선택은 다른 단계입니다.
    이번 누적 구현에서 rootless로 실행하면 /와 UID는 어떻게 보이나?
    3장의 rootfs·새 procfs와 5장의 ID 매핑을 함께 사용합니다. user namespace가 rootfs를 자동 생성하는 것은 아닙니다.
    부모의 매핑 쓰기가 실패했을 때 올바른 정리는?
    실패한 자식이 EOF로 종료할 수 있게 하고 wait로 회수해야 정리 순서도 맞습니다.

    실습 과제

    1. rootless 실행 완성. 단계 A~D를 구현하고 일반 사용자로 기본 검사를 실행하세요. 기대: 통과 33 / 33. root로 실행한 결과와 구분해 기록하고 git tag ch05를 남기세요.
    2. --print-map 옵션 추가. 부모가 사용할 uid_map·gid_map과 cgroup 생략 여부를 stderr에 출력하는 옵션을 구현하세요. 기대: 일반 사용자 실행에서 0 <현재 EUID> 1 매핑을 확인하고 stdout의 자식 출력은 그대로입니다. 기본 검사는 계속 통과해야 합니다.
    3. 실패 뒤 자식 회수 확인. 전용 실험 브랜치에서 매핑 쓰기 실패를 주입하고, 사용자 명령의 표식 파일이 생성되지 않는지·myctr가 종료되는지·자식이 남지 않는지 확인하세요. 기대: 명령은 미실행, 부모 오류, 자식 회수. 커널이나 시스템 전체 매핑 정책은 변경하지 않습니다.
    4. 호출자 파일 소유권 관찰. 본인이 소유한 rootfs의 /tmp 안에 파일을 생성하고, 바깥에서 rootfs-user/tmp의 소유권을 확인하세요. 기대: 안에서는 UID 0, 바깥에서는 호출자의 UID로 보입니다. root가 소유한 mode 600 파일 읽기 성공과 혼동하지 마세요.
