cgroups v2 자원 제한

네임스페이스는 프로세스가 무엇을 보는지를 바꿉니다. 하지만 PID 1이 된 sleep도 마음먹으면 호스트의 메모리를 전부 먹고, CPU를 모두 태우고, 프로세스를 끝없이 만들 수 있습니다. 이 장에서는 얼마나 쓸 수 있는지를 정하는 cgroup을 붙입니다. 컨테이너마다 cgroup 디렉터리를 만들고, 파일 몇 개에 숫자를 쓰고, 자식이 그 안에 들어간 뒤 exec하면 끝입니다. 그 단순한 인터페이스 아래에서 OOM killer가 어떻게 137을 만들고, CPU 상한이 왜 지연 시간을 늘리는지까지 실험으로 확인합니다.

학습 목표

  • cgroup v2의 단일 계층 구조와 인터페이스 파일, 세 가지 트리 규칙(위에서 아래로 활성화, 내부 프로세스 금지, 빈 cgroup만 삭제)을 설명할 수 있다.
  • memory.max를 넘을 때 회수와 OOM kill이 일어나는 과정을 설명하고 memory.events로 확인할 수 있다.
  • cpu.max의 quota/period 모델과 throttling이 지연 시간에 미치는 영향을 계산할 수 있다.
  • pids.max로 프로세스 폭증을 막을 수 있다.
  • 자식을 exec 전에 cgroup에 넣는 방법을 비교하고, 컨테이너가 끝나면 cgroup을 정리할 수 있다.
  • myctr run --rootfs ./rootfs --memory 64M --cpus 0.5 --pids 20 ...을 구현해 누적 완료 기준 31개를 통과시킨다.
3장 구현 위에 자원 제한을 더합니다 --rootfs, mount namespace, pivot_root, 새 /proc와 /dev를 그대로 유지합니다. 자식은 pivot_root 전에 호스트의 cgroup.procs에 들어간 뒤 루트를 바꿉니다. 호스트의 /sys/fs/cgroup 전체는 컨테이너에 노출하지 않습니다. 제한값과 통계는 부모 쪽 경로에서 검사하고, 이후 5~7장에서도 이 구조를 이어갑니다.

1. cgroup: 얼마나 쓸 수 있나

cgroup(control group)은 프로세스들을 묶어 그 묶음 단위로 자원 사용량을 세고, 제한하는 커널 기능입니다. 프로세스는 반드시 하나의 cgroup에 속하고, fork한 자식은 부모의 cgroup을 물려받습니다. 컨테이너 안의 모든 프로세스가 같은 cgroup에 모이므로 "컨테이너 전체의 메모리 합계"를 제한할 수 있습니다.

네임스페이스 (1~3장)cgroup (이 장)
질문무엇이 보이나?얼마나 쓸 수 있나?
인터페이스시스템 콜 (clone, unshare, setns)파일시스템 (/sys/fs/cgroup 아래 파일 읽기/쓰기)
상속fork 시 공유, exec 후 유지fork 시 같은 cgroup, exec 후 유지
위반하면애초에 보이지 않음회수, 지연(throttle), 실패(EAGAIN), 강제 종료(OOM kill)

v1과 v2

cgroup v1은 컨트롤러(memory, cpu, pids ...)마다 계층이 따로 있었습니다. 한 프로세스가 memory 트리에서는 A에, cpu 트리에서는 B에 있을 수 있었고, 이 자유도가 관리를 지옥으로 만들었습니다. 커널 4.5에서 안정화된 v2는 계층을 하나로 합치고 각 cgroup에서 어떤 컨트롤러를 켤지 고르게 했습니다. 최신 배포판(Ubuntu 21.10+, Fedora 31+, Debian 11+)은 v2만 마운트합니다. 이 코스는 v2만 다룹니다.

# 내 시스템이 v2인지 확인
stat -fc %T /sys/fs/cgroup                 # cgroup2fs 면 v2
cat /sys/fs/cgroup/cgroup.controllers      # 쓸 수 있는 컨트롤러: cpuset cpu io memory hugetlb pids ...
cat /sys/fs/cgroup/cgroup.subtree_control  # 자식들에게 켜 준 컨트롤러 (아래 3절)
cat /proc/self/cgroup                      # 지금 셸이 속한 cgroup

2. cgroupfs: 모든 것이 파일

cgroup에는 전용 시스템 콜이 없습니다. /sys/fs/cgroup에 마운트된 cgroup2 파일시스템에서 디렉터리가 곧 cgroup이고, 그 안의 파일이 설정과 통계입니다. mkdir로 만들고, 파일에 써서 설정하고, rmdir로 지웁니다. 아래는 참조 구현이 만든 컨테이너 cgroup 안에서 실제로 ls한 결과 중 이 장에서 쓰는 파일입니다.

파일용도예
cgroup.procs소속 프로세스 목록. PID를 쓰면 그 프로세스를 옮긴다. "0"을 쓰면 쓰는 프로세스 자신을 옮긴다echo 0 > cgroup.procs
cgroup.controllers이 cgroup에서 쓸 수 있는 컨트롤러 (= 부모가 켜 준 것, 읽기 전용)cpu memory pids
cgroup.subtree_control자식 cgroup들에게 켜 줄 컨트롤러echo "+memory +cpu" > ...
cgroup.eventspopulated 1/0: 안에 프로세스가 있는지정리 시점 판단
cgroup.kill1을 쓰면 안의 모든 프로세스를 SIGKILL (커널 5.14+)정리

쓰기 형식은 텍스트 값은 숫자를 텍스트로 씁니다. "제한 없음"은 숫자가 아니라 문자열 max입니다. Rust에서는 fs::write(path, "67108864") 한 줄이면 되고, strace로 보면 write(3, "67108864", 8)로 나타납니다(9절).

3. 트리의 세 가지 규칙

v2가 단순한 대신 지켜야 할 규칙이 생겼습니다. 런타임을 짜다가 만나는 에러의 대부분이 이 셋에서 나옵니다. 아래 에러는 모두 실제로 재현해 확인했습니다.

규칙내용어기면
① 위에서 아래로 활성화자식 cgroup에 memory 파일이 생기려면 부모의 subtree_control에 +memory가 있어야 하고, 부모가 그것을 켜려면 부모의 controllers에 memory가 있어야 한다(= 조부모가 켜 줘야 한다)ENOENT (No such file or directory). 파일이 없다는 뜻이 아니라 켤 수 없는 컨트롤러라는 뜻이라 헷갈린다
② 내부 프로세스 금지루트가 아닌 cgroup은 "프로세스를 직접 갖는 것"과 "자식에게 컨트롤러를 나눠 주는 것"을 동시에 할 수 없다. 자원 분배는 잎(leaf)에서만 일어난다EBUSY (Device or resource busy)
③ 빈 cgroup만 삭제안에 프로세스가 있으면 rmdir 불가. 먼저 끝내거나(cgroup.kill) 옮겨야 한다EBUSY
cgroup 트리 실험실
myctr가 만드는 구조(/sys/fs/cgroup → myctr → ctr-4241)입니다. 컨트롤러를 켜고 끄거나 프로세스를 옮겨 보세요. 각 cgroup에 어떤 인터페이스 파일이 생기는지, 어떤 동작이 어떤 에러로 막히는지 보여 줍니다.
Docker 안에서 실험한다면 Docker 컨테이너(--privileged --cgroupns=private) 안에서는 /sys/fs/cgroup이 진짜 루트가 아니라 그 컨테이너의 cgroup입니다. 그래서 규칙 ②의 루트 예외가 적용되지 않고, 셸이 그 안에 있는 한 컨트롤러를 켤 수 없습니다. 셸을 하위 cgroup으로 옮긴 뒤 켜면 됩니다. 이 장의 검증도 그렇게 했습니다. 
mkdir /sys/fs/cgroup/shell && echo $$ > /sys/fs/cgroup/shell/cgroup.procs
echo "+memory +cpu +pids" > /sys/fs/cgroup/cgroup.subtree_control
systemd를 쓰는 일반 VM(OrbStack, Lima의 Ubuntu)에서는 루트 cgroup에 이미 컨트롤러가 켜져 있어서 이 과정이 필요 없습니다.

4. 메모리: memory.max와 OOM

memory.current는 그 cgroup의 프로세스들이 쓰는 익명 메모리(힙, 스택)와 그들이 읽고 쓴 파일의 page cache, 일부 커널 메모리를 합친 값입니다. 사용량이 memory.max에 닿으면 커널은 먼저 회수를 시도합니다. page cache는 디스크에 있는 내용이라 버리면 그만이고, 익명 메모리는 스왑이 있으면 스왑으로 내보냅니다. 회수로도 자리를 못 만들면 cgroup 안의 OOM killer가 가장 큰 프로세스를 골라 SIGKILL을 보냅니다. 이것이 1장에서 본 137의 정체입니다.

memory.max 시뮬레이터
작업 종류를 고르고 실행하세요. 파란색은 익명 메모리, 청록색은 page cache입니다. 빨간 선이 memory.max, 주황 선이 memory.high입니다. 같은 64M 상한에서 "큰 파일 읽기"는 왜 죽지 않는지 비교해 보세요.

rootfs 안의 Alpine 도구로 실행합니다. 정상 버퍼는 0, 상한을 크게 넘긴 버퍼는 OOM으로 137을 돌려주는지 검사합니다. 출력 바이트·처리 시간은 도구와 환경마다 다릅니다.

sudo ./target/debug/myctr run --rootfs ./rootfs --memory 64M dd if=/dev/zero of=/dev/null bs=16M count=1
echo $?  # 기대: 0
sudo ./target/debug/myctr run --rootfs ./rootfs --memory 64M dd if=/dev/zero of=/dev/null bs=200M count=1
echo $?  # 기대: 137, 부모의 OOM 안내

# --init의 셸은 dd의 실패 뒤에도 계속할 수 있다.
sudo ./target/debug/myctr run --rootfs ./rootfs --init --memory 64M sh -c 'dd if=/dev/zero of=/dev/null bs=200M count=1; echo dd_exit=$?'
# dd_exit=137이어도 마지막 echo가 성공하면 셸과 myctr의 종료 코드는 0일 수 있다.
cgroup 파일은 호스트에서 관찰합니다pivot_root 뒤에는 호스트의 /sys/fs/cgroup을 볼 수 없습니다. 컨테이너에 전체 cgroupfs를 붙이는 대신 부모의 경로 /sys/fs/cgroup/myctr/ctr-<myctr PID>를 읽습니다. 프로세스가 살아 있는 동안 memory.events·memory.current·cpu.stat을 확인하고, 종료 후에는 leaf가 정리되는지 봅니다. 아래 완료 검사도 같은 방식입니다.
OOM이 났는데 종료 코드가 0일 수 있다 마지막 실험에서 OOM killer는 메모리를 가장 많이 쓰던 dd만 죽였고, 메인 프로세스인 sh는 살아남아 정상 종료했습니다. 종료 코드만 보는 모니터링은 이 OOM을 놓칩니다. 그래서 myctr는 종료 코드와 별개로 memory.events의 oom_kill 카운터를 읽어 알립니다. Docker의 OOMKilled 플래그, Kubernetes의 OOM 이벤트도 같은 카운터를 봅니다. 컨테이너 안의 프로세스 하나라도 죽으면 전체를 죽이고 싶다면 memory.oom.group에 1을 쓰면 됩니다.
  • 왜 swap.max = 0인가: 스왑이 있으면 상한을 넘은 익명 메모리가 스왑으로 밀려나 OOM 대신 극심한 느려짐이 옵니다. 결과가 호스트의 스왑 설정에 따라 달라지지 않도록 myctr는 --memory를 주면 스왑도 막습니다. Docker는 기본적으로 메모리와 같은 양의 스왑을 더 허용합니다(--memory-swap).
  • page cache도 셉니다: 로그를 많이 읽는 컨테이너의 memory.current가 상한 근처에 붙어 있어도 정상일 수 있습니다. 회수 가능한 캐시이기 때문입니다. "실제로 위험한가"는 memory.stat의 anon과 memory.events의 oom_kill로 판단하세요.
  • memory.high: 넘으면 죽이지 않고, 할당하는 프로세스에게 회수 작업을 시키고 지연을 걸어 속도를 늦춥니다. "죽기 전에 느려지는" 완충 구간입니다.

5. CPU: cpu.max와 throttling

cpu.max는 "period마다 quota만큼만 실행해도 된다"는 예산입니다. 50000 100000이면 100ms마다 50ms, 즉 평균 0.5코어입니다. 예산은 cgroup 전체가 공유합니다. 스레드 4개가 동시에 돌면 50ms 예산을 12.5ms 만에 다 쓰고, 그 period의 나머지 87.5ms 동안 전부 멈춥니다. 이것이 throttling입니다.

cpu.max 타임라인
CPU를 쓰려는 스레드 수와 상한을 바꿔 보세요. 각 줄은 스레드 하나, 초록은 실행, 빨강 빗금은 throttle로 멈춘 구간입니다. 아래의 "요청 지연"은 throttle 구간이 시작될 때 도착한 요청이 얼마나 기다리는지를 보여 줍니다.

호스트의 root 셸에서 실행 중인 cgroup을 관찰하는 예시입니다. 0.5코어 제한에서는 충분한 측정 구간에 CPU 사용량이 벽시계 시간의 약 절반으로 증가하고, nr_throttled가 증가하는지 확인합니다.

# 실습용 Linux의 root 셸에서. $!가 myctr 자체의 PID가 되게 실행한다.
B=$(realpath ./target/debug/myctr)
R=$(realpath ./rootfs)
"$B" run --rootfs "$R" --cpus 0.5 /bin/sh -c 'while :; do :; done' &
launcher=$!
cg="/sys/fs/cgroup/myctr/ctr-$launcher"
for i in $(seq 1 100); do [ -r "$cg/cpu.stat" ] && break; sleep 0.05; done
sleep 2
cat "$cg/cpu.stat"
# 관찰 뒤 자신이 띄운 PID 1만 종료한다. 부모는 자식을 회수하고 cgroup을 정리한다.
child=$(head -n 1 "$cg/cgroup.procs")
kill -KILL "$child"
wait "$launcher"  # 137 예상
CPU 상한은 평균이 아니라 지연을 만든다 "0.5코어면 절반 속도로 돌겠지"라고 생각하기 쉽지만, 실제로는 전속력으로 달리다 멈추기를 반복합니다. 멀티스레드 서버(JVM, Go, Node.js의 libuv 스레드풀)는 예산을 빠르게 소진하고, 그 period의 남은 시간 동안 들어온 요청은 다음 period까지 기다립니다. 평균 CPU 사용률은 낮은데 p99 지연이 수십 ms씩 튀는 Kubernetes의 전형적인 증상입니다. 위 위젯에서 스레드를 8로 올려 보세요. 진단은 cpu.stat의 nr_throttled 비율로 합니다.

cpu.weight는 상한이 아니라 경쟁할 때의 비율입니다. CPU가 남으면 weight가 낮아도 다 쓸 수 있습니다. Kubernetes의 requests.cpu가 weight로, limits.cpu가 cpu.max로 바뀝니다.

6. PID: pids.max

메모리와 CPU를 막아도, 프로세스를 끝없이 만드는 프로그램은 호스트 전체의 PID(/proc/sys/kernel/pid_max)를 고갈시켜 호스트에서도 새 프로세스를 못 만들게 할 수 있습니다. pids.max는 cgroup 안의 태스크(프로세스와 스레드) 수를 제한합니다. 넘으면 fork/clone이 EAGAIN으로 실패하고, 기존 프로세스는 죽이지 않습니다.

pids.max 시뮬레이터
sh -c 'for i in 1 2 3 4 5 6 7 8; do sleep 1 & done; wait'를 실행한다고 합시다. 처음부터 sh(1개)가 있고, 반복마다 sleep을 하나씩 fork합니다. --init을 켜면 init이 하나 더 있습니다.
실행을 누르세요.
$ sudo myctr run --rootfs ./rootfs --pids 5 sh -c 'for i in 1 2 3 4 5 6 7 8; do sleep 1 & done; wait'; echo $?
sh: 0: Cannot fork
2

pids.max는 스레드도 셉니다. 스레드를 많이 쓰는 런타임(JVM, Go)에 너무 낮게 주면 스레드 생성 실패로 이상하게 죽습니다. 실무에서는 수백~수천 단위로 줍니다.

7. 컨테이너를 cgroup에 넣기

제한은 사용자 프로그램이 첫 명령을 실행하기 전부터 걸려 있어야 합니다. exec 후에 넣으면 그 사이에 이미 메모리를 할당하거나 fork했을 수 있기 때문입니다. cgroup 소속은 fork와 exec를 넘어 유지되므로, 결국 "fork와 exec 사이에 넣으면" 됩니다. 방법은 세 가지입니다.

방법어떻게장단점
A. 자식이 스스로 들어감자식이 exec 전에 cgroup.procs에 "0"을 씀가장 단순하고 경쟁 상태가 없음. 자식이 cgroupfs에 접근할 수 있어야 함(3장 이후엔 pivot_root 전에). 이 장의 방식
B. 부모가 넣고 신호clone 후 부모가 자식의 호스트 PID를 cgroup.procs에 쓰고, 파이프로 "이제 exec해도 된다"고 알림자식은 아무 권한도 필요 없음. 동기화 파이프가 필요함(5장에서 uid_map 때문에 어차피 만들게 됨)
C. 처음부터 그 안에서 태어남clone3에 CLONE_INTO_CGROUP과 cgroup 디렉터리 fd를 넘김 (커널 5.7+)가장 정확함. nix 0.29에는 clone3 래퍼가 없어 직접 시스템 콜을 불러야 함
왜 "0"인가 자식은 새 PID 네임스페이스에서 PID 1이지만, cgroupfs에 PID를 쓰면 커널은 쓰는 프로세스의 네임스페이스 기준으로 해석합니다. 그러니 "1"을 써도 자기 자신이 맞긴 하지만 읽는 사람을 헷갈리게 합니다. "0"은 PID 네임스페이스와 상관없이 "나"를 뜻하는 약속입니다.
cgroup을 붙인 myctr의 생애주기
sudo myctr run --rootfs ./rootfs --memory 64M --cpus 0.5 --pids 20 dd ... bs=200M을 실행했을 때 일어나는 일입니다. 9절의 누적 구현 흐름과 순서가 같습니다.

8. 정리와 누수

컨테이너가 끝나면 cgroup 디렉터리를 지워야 합니다. 안 지우면 /sys/fs/cgroup/myctr/에 빈 디렉터리가 계속 쌓입니다. 참조 구현은 Rust의 Drop으로 정리합니다. run 함수가 끝날 때(에러로 빠져나갈 때도) cgroup 구조체가 drop되며 rmdir합니다. 2장에서 확인했듯이 PID 1이 끝나면 커널이 네임스페이스의 나머지 프로세스를 모두 죽이므로, waitpid가 돌아온 시점에는 cgroup이 비어 있습니다.

Drop이 clone 자식에서는 돌지 않는 이유 clone된 자식도 부모 메모리의 복사본이라 Cgroup 구조체를 갖고 있습니다. 자식이 끝날 때 Drop이 돌면 자식이 cgroup을 지우려 하겠지요. 하지만 2장에서 봤듯이 clone 클로저가 반환하면 glibc가 exit 시스템 콜을 직접 부르므로 Rust의 소멸자는 실행되지 않습니다. mini_init의 fork 자식도 _exit로 끝납니다. 같은 이유로 main의 std::process::exit도 소멸자를 부르지 않으므로, 참조 구현은 cgroup을 run 안에 두어 exit 전에 drop되게 했습니다.

하지만 Drop으로는 막을 수 없는 경우가 있습니다. 실제로 확인했습니다.

$ sudo myctr run --rootfs ./rootfs --init sleep 30 &
$ sudo kill -9 %1                    # myctr 자체를 SIGKILL
$ ls -d /sys/fs/cgroup/myctr/ctr-*
/sys/fs/cgroup/myctr/ctr-178        ← cgroup이 남음
$ cat /sys/fs/cgroup/myctr/ctr-178/cgroup.procs
180                                 ← init과 sleep도 계속 살아 있음
181
$ echo 1 | sudo tee /sys/fs/cgroup/myctr/ctr-178/cgroup.kill; sudo rmdir /sys/fs/cgroup/myctr/ctr-178

SIGKILL은 잡을 수 없으므로 소멸자도, 시그널 핸들러도 돌지 않습니다. 컨테이너는 고아가 되어 계속 돌고, 아무도 회수하지 않습니다. 실제 런타임은 이 문제를 구조로 풉니다. Docker는 containerd-shim이라는 별도 프로세스가 컨테이너의 부모 역할을 하고, 런타임이 죽어도 shim이 남아 정리합니다. 9장에서 상태 파일과 myctr delete로 같은 문제를 다룹니다. 그전까지는 실습 5의 정리 명령을 쓰세요.

#[derive(Parser)]

#[derive(Subcommand)]

fn main() -> Result<()> {
    match Cli::parse().command {
        Command::Run { rootfs, hostname, init, memory, cpus, pids, cmd } => {
            let argv = cmd
                .iter()
                .map(|s| CString::new(s.as_bytes()))
                .collect::<Result<_, _>>()
                .context("인자에 NUL 바이트가 있습니다")?;
            let rootfs = fs::canonicalize(&rootfs).context("rootfs 경로 확인")?;
            validate_rootfs(&rootfs)?;
            let code = run(rootfs, hostname, init, argv, &Limits { memory, cpus, pids })?;
            std::process::exit(code);
        }
    }
}

/// "64M", "1G", "512K", "1048576" 을 바이트 수로
fn parse_bytes(s: &str) -> Result<u64, String> {
    let (num, mul) = match s.chars().last() {
        Some('K' | 'k') => (&s[..s.len() - 1], 1 << 10),
        Some('M' | 'm') => (&s[..s.len() - 1], 1 << 20),
        Some('G' | 'g') => (&s[..s.len() - 1], 1 << 30),
        _ => (s, 1),
    };
    num.parse::<u64>().map(|n| n * mul).map_err(|e| format!("{s}: {e}"))
}

fn run(rootfs: PathBuf, hostname: String, init: bool, argv: Vec<CString>, limits: &Limits) -> Result<i32> {
    let cgroup = Cgroup::create(&format!("ctr-{}", std::process::id()), limits)?;
    let cfg = Config { rootfs, hostname, init, argv, cgroup_procs: cgroup.path.join("cgroup.procs") };

    let mut stack = vec![0u8; STACK_SIZE];
    let flags = CloneFlags::CLONE_NEWUTS | CloneFlags::CLONE_NEWPID | CloneFlags::CLONE_NEWNS;
    let cb = Box::new(|| container_main(&cfg));
    let child = unsafe { clone(cb, &mut stack, flags, Some(Signal::SIGCHLD as i32)) }
        .context("clone 실패 (root 권한으로 실행했나요?)")?;

    unsafe { signal(Signal::SIGINT, SigHandler::SigIgn) }.context("signal 설정 실패")?;
    let code = wait_exit_code(child)?;
    if cgroup.oom_kills() > 0 {
        eprintln!("myctr: 메모리 상한을 넘어 OOM killer가 프로세스를 종료했습니다");
    }
    Ok(code)
    // cgroup은 여기서 drop되며 지워진다
}

fn wait_exit_code(child: Pid) -> Result<i32> {
    match waitpid(child, None).context("waitpid 실패")? {
        WaitStatus::Exited(_, code) => Ok(code),
        WaitStatus::Signaled(_, sig, _) => Ok(128 + sig as i32),
        other => bail!("예상하지 못한 상태: {other:?}"),
    }
}

struct Cgroup {
    path: PathBuf,
}

impl Cgroup {
    fn create(name: &str, limits: &Limits) -> Result<Self> {
        let parent = Path::new(CGROUP_ROOT).join(CGROUP_PARENT);
        fs::create_dir_all(&parent).with_context(|| format!("{} 만들기", parent.display()))?;
        // 부모에서 컨트롤러를 켜야 자식 cgroup에 memory.max 같은 파일이 생긴다
        fs::write(parent.join("cgroup.subtree_control"), "+memory +cpu +pids")
            .context("컨트롤러 활성화 (상위 cgroup의 cgroup.subtree_control에 memory cpu pids가 켜져 있나요?)")?;

        let path = parent.join(name);
        fs::create_dir(&path).with_context(|| format!("{} 만들기", path.display()))?;
        let cg = Cgroup { path };
        if let Some(bytes) = limits.memory {
            cg.write("memory.max", &bytes.to_string())?;
            // 스왑으로 도망가지 못하게. 스왑 계정이 꺼진 커널에는 파일이 없다
            if cg.path.join("memory.swap.max").exists() {
                cg.write("memory.swap.max", "0")?;
            }
        }
        if let Some(cpus) = limits.cpus {
            let quota = (cpus * CPU_PERIOD_US as f64) as u64;
            cg.write("cpu.max", &format!("{quota} {CPU_PERIOD_US}"))?;
        }
        if let Some(n) = limits.pids {
            cg.write("pids.max", &n.to_string())?;
        }
        Ok(cg)
    }

    fn write(&self, file: &str, value: &str) -> Result<()> {
        fs::write(self.path.join(file), value)
            .with_context(|| format!("{}/{file} 에 {value} 쓰기", self.path.display()))
    }

    /// memory.events 의 oom_kill 카운터
    fn oom_kills(&self) -> u64 {
        fs::read_to_string(self.path.join("memory.events"))
            .ok()
            .and_then(|s| {
                s.lines()
                    .find_map(|l| l.strip_prefix("oom_kill ").and_then(|n| n.parse().ok()))
            })
            .unwrap_or(0)
    }
}

impl Drop for Cgroup {
    fn drop(&mut self) {
        // 프로세스가 남아 있으면 EBUSY. PID 1이 끝나면 네임스페이스 전체가 정리되므로 비어 있다
        if let Err(e) = fs::remove_dir(&self.path) {
            eprintln!("myctr: cgroup 정리 실패 {}: {e}", self.path.display());
        }
    }
}

/// clone된 자식. 새 네임스페이스 안의 PID 1이다.
fn container_main(cfg: &Config) -> isize {
    if let Err(e) = setup(cfg) {
        eprintln!("myctr: {e:#}");
        return 1;
    }
    if cfg.init { mini_init(&cfg.argv) } else { exec(&cfg.argv) }
}

/// fork와 exec 사이에서 컨테이너의 모양을 만든다
fn setup(cfg: &Config) -> Result<()> {
    // "0"을 쓰면 쓰는 프로세스 자신이 그 cgroup으로 옮겨진다. exec 전에 들어가야 한다
    fs::write(&cfg.cgroup_procs, "0").context("cgroup 들어가기")?;
    sethostname(&cfg.hostname).context("sethostname")?;
    setup_rootfs(&cfg.rootfs)?;
    Ok(())
}

/// 실습 중 호스트 /를 rootfs로 지정하거나 준비를 빠뜨리는 실수를 막는다.
/// 신뢰하는 Alpine 입력을 전제로 하며 악성 rootfs 검증기는 아니다.
fn validate_rootfs(rootfs: &Path) -> Result<()> {
    if rootfs == Path::new("/") || !rootfs.is_dir() {
        bail!("rootfs는 호스트 /가 아닌 디렉터리여야 합니다");
    }
    if !fs::symlink_metadata(rootfs.join("bin/sh")).is_ok_and(|meta| meta.is_file() || meta.file_type().is_symlink())
        || !rootfs.join("proc").is_dir() || !rootfs.join("dev").is_dir() {
        bail!("rootfs에 bin/sh와 proc·dev 디렉터리를 준비하세요");
    }
    Ok(())
}

fn setup_rootfs(rootfs: &Path) -> Result<()> {
    // 1. 이후의 마운트가 호스트로 전파되지 않도록 모든 마운트를 private으로
    mount(None::<&str>, "/", None::<&str>, MsFlags::MS_REC | MsFlags::MS_PRIVATE, None::<&str>)
        .context("/ 를 rprivate으로 바꾸기")?;

    // 2. pivot_root의 new_root는 마운트 지점이어야 하므로 자기 자신에게 bind
    mount(Some(rootfs), rootfs, None::<&str>, MsFlags::MS_BIND | MsFlags::MS_REC, None::<&str>)
        .context("rootfs bind mount")?;

    // 3. 루트를 바꾼다. 이전 루트는 /.oldroot 에 걸린다
    let old_root = rootfs.join(OLD_ROOT);
    fs::create_dir_all(&old_root).context(".oldroot 만들기")?;
    pivot_root(rootfs, &old_root).context("pivot_root")?;
    chdir("/").context("chdir /")?;

    // 4. 이 PID 네임스페이스 기준의 procfs
    mount(
        Some("proc"),
        "/proc",
        Some("proc"),
        MsFlags::MS_NOSUID | MsFlags::MS_NODEV | MsFlags::MS_NOEXEC,
        None::<&str>,
    )
    .context("/proc 마운트")?;

    // 5. 최소한의 /dev. 장치 파일은 아직 붙어 있는 이전 루트에서 bind로 빌려 온다
    setup_dev().context("/dev 구성")?;

    // 6. 이전 루트를 떼어 내고 흔적을 지운다
    let old = format!("/{OLD_ROOT}");
    umount2(old.as_str(), MntFlags::MNT_DETACH).context("이전 루트 분리")?;
    fs::remove_dir(&old).context(".oldroot 지우기")?;
    Ok(())
}

fn setup_dev() -> Result<()> {
    mount(
        Some("tmpfs"),
        "/dev",
        Some("tmpfs"),
        MsFlags::MS_NOSUID | MsFlags::MS_STRICTATIME,
        Some("mode=755,size=65536k"),
    )?;
    for dev in DEVICES {
        let target = format!("/dev/{dev}");
        File::create(&target).with_context(|| format!("{target} 만들기"))?;
        let source = format!("/{OLD_ROOT}/dev/{dev}");
        mount(Some(source.as_str()), target.as_str(), None::<&str>, MsFlags::MS_BIND, None::<&str>)
            .with_context(|| format!("{target} bind"))?;
    }
    for (link, to) in [
        ("/dev/fd", "/proc/self/fd"),
        ("/dev/stdin", "/proc/self/fd/0"),
        ("/dev/stdout", "/proc/self/fd/1"),
        ("/dev/stderr", "/proc/self/fd/2"),
    ] {
        symlink(to, link).with_context(|| format!("{link} 링크"))?;
    }
    Ok(())
}

/// 성공하면 돌아오지 않는다. 돌아오면 127.
fn exec(argv: &[CString]) -> isize {
    if let Err(e) = unsafe { signal(Signal::SIGPIPE, SigHandler::SigDfl) } {
        eprintln!("myctr: SIGPIPE 복원 실패: {e}");
        return 1;
    }
    let err = execvp(&argv[0], argv).unwrap_err();
    eprintln!("myctr: {}: {err}", argv[0].to_string_lossy());
    127
}

/// PID 1로 남아 명령을 PID 2로 띄우고, 입양된 고아까지 거두다가
/// 명령이 끝나면 그 종료 코드로 끝난다.
fn mini_init(argv: &[CString]) -> isize {
    let main_child = match unsafe { fork() } {
        Ok(ForkResult::Child) => unsafe { libc::_exit(exec(argv) as i32) },
        Ok(ForkResult::Parent { child }) => child,
        Err(e) => {
            eprintln!("myctr-init: fork: {e}");
            return 1;
        }
    };
    loop {
        match waitpid(None, None) {
            Ok(WaitStatus::Exited(pid, code)) if pid == main_child => return code as isize,
            Ok(WaitStatus::Signaled(pid, sig, _)) if pid == main_child => return 128 + sig as isize,
            Ok(_) => continue,
            Err(Errno::EINTR) => continue,
            Err(e) => {
                eprintln!("myctr-init: waitpid: {e}");
                return 1;
            }
        }
    }
}

핵심 요약

  • cgroup은 프로세스 묶음 단위로 자원을 세고 제한합니다. v2는 단일 계층이고, 디렉터리가 cgroup이며 파일 쓰기가 설정입니다.
  • 트리 규칙 세 가지: 컨트롤러는 위에서 아래로 켜야 하고(어기면 ENOENT), 루트가 아닌 cgroup은 프로세스와 자식 컨트롤러를 동시에 가질 수 없고(EBUSY), 빈 cgroup만 지울 수 있습니다(EBUSY, cgroup.kill로 해결).
  • memory.max를 넘으면 회수 후 OOM kill(SIGKILL, 137). OOM killer는 가장 큰 프로세스를 고르므로 메인 프로세스가 살아 종료 코드가 0일 수 있습니다. memory.events의 oom_kill로 판정합니다.
  • cpu.max는 period당 quota입니다. 멀티스레드는 예산을 빨리 소진하고 period의 나머지 동안 멈추며, 이것이 지연 시간 급증으로 나타납니다. cpu.stat의 nr_throttled로 진단합니다.
  • pids.max를 넘으면 fork가 EAGAIN으로 실패합니다. 스레드도 셉니다.
  • 컨테이너는 exec 전에 cgroup에 들어가야 합니다. myctr는 자식이 cgroup.procs에 "0"을 씁니다. 정리는 Drop으로 하지만, 런타임이 SIGKILL되면 남습니다(9장).

확인 문제

/sys/fs/cgroup/myctr/cgroup.subtree_control에 +memory를 쓰는데 ENOENT가 났다. 가장 가능성 높은 원인은?
컨트롤러는 위에서 아래로만 켤 수 있습니다. 자기 cgroup.controllers에 없는 컨트롤러를 자식에게 켜 주려 하면 ENOENT가 납니다. 파일이 없다는 뜻이 아니라서 헷갈리는 에러입니다.
프로세스가 들어 있는 cgroup A의 subtree_control에 컨트롤러를 켜려 했더니 EBUSY가 났다. 왜인가?
v2는 자원 분배를 잎에서만 하도록 강제합니다. 프로세스를 하위 cgroup으로 옮긴 뒤 켜야 합니다. 루트 cgroup만 예외입니다.
--memory 64M 컨테이너에서 1 GB 로그 파일을 cat했다. 어떻게 되나?
page cache도 memory.current에 포함되지만 디스크에 원본이 있어 버릴 수 있습니다. 상한에 닿으면 회수가 일어나고(memory.events의 max 증가) OOM은 나지 않습니다. 위험한 것은 회수할 수 없는 익명 메모리입니다.
cpu.max = "50000 100000"인 컨테이너에서 스레드 4개가 동시에 CPU를 쓰면, 각 period에서 대략 어떻게 되나?
50ms 예산은 cgroup 전체가 공유합니다. 4개가 병렬로 쓰면 50 / 4 = 12.5ms 만에 소진되고, period가 끝날 때까지 throttle됩니다. 그 사이에 도착한 요청은 최대 87.5ms를 기다립니다.
컨테이너 안에서 dd가 OOM으로 죽었지만 myctr의 종료 코드는 0이었다. 어떻게 가능한가?
OOM killer는 cgroup에서 가장 큰 프로세스를 고릅니다. 메인 프로세스가 아닐 수 있습니다. 그래서 OOM 판정은 종료 코드가 아니라 memory.events의 oom_kill로 해야 합니다. 그룹 전체를 죽이고 싶으면 memory.oom.group을 씁니다.
myctr가 kill -9로 죽으면 cgroup 디렉터리가 남는 이유는?
SIGKILL은 어떤 정리 코드도 실행하지 않습니다. 게다가 init과 sleep은 myctr가 죽어도 계속 돌고 있어 cgroup은 비어 있지 않습니다. cgroup.kill 후 rmdir로 수동 정리하거나, shim 같은 별도 감시 프로세스 구조로 해결합니다.
