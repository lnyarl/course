프로세스 실행: fork · exec · wait

docker run alpine sh를 아무리 쪼개도 결국 남는 것은 "커널에게 새 프로세스를 만들어 달라고 부탁하고, 그 프로세스가 끝나기를 기다린다"는 동작입니다. 이 장에서는 그 뼈대를 직접 만듭니다. 목표는 myctr run <명령>이 명령을 자식 프로세스로 실행하고, 자식의 종료 코드를 셸 관례 그대로 돌려주는 것입니다. 아직 격리는 없습니다. 하지만 2장부터 붙일 네임스페이스, pivot_root, cgroup은 모두 fork와 exec 사이의 틈에 끼워 넣는 코드입니다. 그 틈을 정확히 이해하는 것이 이 장의 핵심입니다.

학습 목표

  • macOS에서 Linux VM을 준비하고 Rust 프로젝트(nix, clap, anyhow)를 세팅할 수 있다.
  • fork가 무엇을 복제하고 무엇을 복제하지 않는지, 왜 Rust에서 unsafe인지 설명할 수 있다.
  • exec가 무엇을 교체하고 무엇을 남기는지 알고, 그것이 컨테이너 런타임 설계의 출발점인 이유를 설명할 수 있다.
  • wait 종료 상태의 비트 인코딩을 해석하고 셸 관례(0, 126, 127, 128+n)로 변환할 수 있다.
  • 좀비·고아 프로세스가 생기는 조건과 Ctrl+C가 프로세스 그룹에 전달되는 경로를 설명할 수 있다.
  • myctr run을 직접 구현해 완료 기준 스크립트를 통과시킨다.

1. 컨테이너는 결국 프로세스다

VM은 하드웨어를 흉내 내고 그 위에 커널을 하나 더 띄웁니다. 컨테이너는 그렇게 하지 않습니다. 호스트 커널 하나를 모든 컨테이너가 공유하고, 커널이 프로세스마다 "보이는 세상"과 "쓸 수 있는 자원"을 다르게 보여 줄 뿐입니다. 그래서 컨테이너 안에서 ps를 치면 프로세스 몇 개만 보이지만, 호스트에서 ps를 치면 그 프로세스들이 평범하게 섞여 있습니다.

그러니 런타임을 만드는 첫걸음은 "프로세스를 하나 띄우고 끝날 때까지 지켜보는 프로그램"입니다. 오늘 장이 끝나면 아래처럼 동작해야 합니다.

$ myctr run /bin/sh -c 'echo "hi from $$"; exit 3'
hi from 4242
$ echo $?
3
$ myctr run no-such-command
myctr: no-such-command: ENOENT: No such file or directory
$ echo $?
127
Docker도 똑같은 일을 합니다 docker run → dockerd → containerd → containerd-shim → runc로 이어지는 사슬의 맨 끝에서, runc는 결국 clone(fork의 일반형)과 execve를 호출합니다. 우리가 만드는 myctr는 그 맨 끝, runc 자리입니다. 9장에서는 실제로 Docker가 runc 대신 myctr를 부르게 만듭니다.

3. fork · exec · wait 한눈에 보기

Unix는 "새 프로그램을 새 프로세스로 실행하라"는 단일 호출 대신 두 단계로 나눕니다. fork는 지금 프로세스를 통째로 복제하고, exec는 지금 프로세스의 프로그램을 다른 프로그램으로 갈아 끼웁니다. 부모는 wait로 자식의 끝을 기다립니다. 처음 보면 번거로워 보이지만, 이 분리 덕분에 fork와 exec 사이에서 자식 자신의 환경을 마음대로 고칠 수 있습니다. 셸이 리다이렉션(> out.txt)을 구현하는 방법도, 런타임이 컨테이너를 만드는 방법도 이 틈을 씁니다.

myctr run의 생애주기
myctr run /bin/sh -c 'exit 3'을 실행했을 때 커널 안팎에서 일어나는 일을 한 단계씩 따라갑니다. PID가 언제 생기고, 언제 바뀌지 않는지에 주목하세요.
이 틈이 왜 중요한가: 런타임의 전체 구조 미리보기 2장 이후 myctr의 자식 쪽 코드는 이렇게 자랍니다. fork(정확히는 플래그를 준 clone) → hostname 설정 → 새 root로 pivot_root → /proc 마운트 → capability 제거 → seccomp 필터 설치 → execve. 굵게 쓴 부분이 전부 "fork와 exec 사이"입니다. exec 이후에는 사용자 프로그램이 돌기 때문에 런타임이 더는 끼어들 수 없습니다.

4. fork: 프로세스 복제

fork()는 호출한 프로세스와 거의 똑같은 자식을 만듭니다. 그리고 한 번 호출되어 두 번 반환합니다. 부모에게는 자식의 PID를, 자식에게는 0을 돌려줍니다. 두 프로세스는 같은 코드의 같은 지점(fork 직후)에서 각자 실행을 이어 가고, 반환값으로 자기가 누구인지 구분합니다. nix에서는 이 반환값이 ForkResult::Parent { child }와 ForkResult::Child라는 enum입니다.

Copy-on-Write: 복제가 싼 이유

수백 MB짜리 프로세스를 fork할 때마다 메모리를 다 복사하면 느릴 겁니다. 커널은 실제로 복사하지 않고 페이지 테이블만 복사한 뒤 양쪽 페이지를 읽기 전용으로 표시합니다. 누군가 쓰려고 하면 그때 페이지 폴트가 나고, 커널이 그 페이지 하나만 복사합니다. fork 직후 exec하는 런타임 패턴에서는 자식이 거의 아무것도 쓰지 않고 바로 이미지를 버리므로 복사가 거의 일어나지 않습니다.

왜 nix의 fork는 unsafe인가

    
fork는 호출한 스레드 하나만 자식에 복제합니다. 다른 스레드가 fork 순간에 malloc 내부 락이나 stdout 락을 잡고 있었다면, 자식에는 락은 잠긴 채로 복사되고 그 락을 풀 스레드는 없는 상태가 됩니다. 자식이 malloc을 부르면 영원히 멈춥니다. 그래서 POSIX는 멀티스레드 프로그램에서 fork한 자식은 exec 전까지 async-signal-safe 함수만 부르라고 규정하고, nix는 이 규칙을 컴파일러가 검증할 수 없으므로 unsafe fn fork()로 표시합니다.

심화: print!가 두 번 찍히는 버그

      
Rust의 stdout은 줄 단위 버퍼(LineWriter)를 씁니다. 줄바꿈 없는 print!의 내용은 메모리 버퍼에 머물러 있고, fork는 그 버퍼까지 복사합니다.


print!("a");                       // 버퍼에 "a"가 남아 있음
match unsafe { fork() }.unwrap() {
    ForkResult::Child => {}
    ForkResult::Parent { child } => { waitpid(child, None).unwrap(); }
}
println!();                        // 출력: "a\na\n"  ← a가 두 번

      
부모와 자식이 각자 자기 버퍼의 "a"를 내보내기 때문입니다. 그래서 fork 직전에 std::io::stdout().flush()를 하거나, 자식이 _exit로 끝나 버퍼를 비우지 않게 합니다. 자식에서 에러를 eprintln!(stderr)으로 찍는 것은 안전합니다. Rust의 stderr는 버퍼링하지 않습니다.

    

  


  
  

    
5. exec: 프로그램 이미지 교체

    
execve(path, argv, envp)는 현재 프로세스의 메모리(코드·데이터·힙·스택)를 버리고 path의 프로그램을 새로 적재해 그 진입점부터 실행합니다. 새 프로세스를 만들지 않습니다. PID도 그대로입니다. 성공하면 호출한 코드가 메모리에서 사라졌으니 돌아올 곳이 없습니다. 그래서 exec는 실패했을 때만 반환합니다. nix의 execvp 반환 타입이 Result<Infallible>인 이유입니다. Ok는 만들 수 없는 타입이라 사실상 에러만 돌아옵니다.

      네임스페이스, cgroup, root 디렉터리, capability, seccomp 필터, rlimit, uid/gid가 전부 exec를 넘어 유지됩니다. 그래서 런타임은 이렇게 동작할 수 있습니다. "자식 프로세스의 환경을 먼저 컨테이너 모양으로 바꿔 놓고, 마지막에 사용자 프로그램으로 exec한다." 사용자 프로그램은 처음부터 그 환경에서 태어난 것처럼 보입니다. 사용자 프로그램 입장에서는 자기가 컨테이너 안에 있다는 사실조차 모를 수 있습니다.
    
  
    

  
  
    
    
    6. wait: 종료 상태 읽기
    
    
    부모는 waitpid(pid, flags)로 자식의 상태 변화를 기다립니다. 커널은 상태를 16비트 정수 하나에 담아 돌려줍니다. C에서는 WIFEXITED, WEXITSTATUS, WIFSIGNALED, WTERMSIG 같은 매크로로 이 비트를 해석합니다. nix는 이 해석을 대신 해서 WaitStatus enum으로 줍니다. 그래도 원시 비트를 알아 두면 strace 출력이나 C 코드를 읽을 때 도움이 됩니다.
    

    
    
      
    종료 상태 디코더
    
      
    자식이 어떻게 끝났는지 고르면 커널이 돌려주는 원시 status의 비트, C 매크로 값, nix의 WaitStatus, 그리고 myctr가 돌려줄 셸 종료 코드를 보여 줍니다. 원시 값을 직접 입력해 역으로 해석할 수도 있습니다.

    셸 종료 코드 관례
    
    
    myctr는 사용자가 셸에서 직접 실행한 것과 똑같은 $?를 돌려줘야 합니다. 그래야 스크립트와 CI가 myctr를 투명하게 쓸 수 있습니다. bash와 Docker가 따르는 관례는 이렇습니다.
    
    
    
      
    코드의미myctr에서 언제
    
      
    0–125프로그램이 exit(n)한 값 (하위 8비트)WaitStatus::Exited(_, n) → n
    
      
    126찾았지만 실행할 수 없음 (권한 없음 등)exec가 EACCES로 실패 (도전 과제)
    
      
    127명령을 찾을 수 없음exec가 ENOENT로 실패
    
      
    128 + n시그널 n으로 죽음WaitStatus::Signaled(_, sig, _) → 128 + sig. SIGINT(2)=130, SIGKILL(9)=137, SIGTERM(15)=143
    
    
    
    
    137을 보면 OOM부터 의심하세요
      Kubernetes에서 "Exit Code 137"은 SIGKILL로 죽었다는 뜻이고, 가장 흔한 원인은 cgroup 메모리 한계를 넘어 커널 OOM killer가 보낸 SIGKILL입니다. 4장에서 우리 컨테이너로 직접 137을 만들어 봅니다. 숫자 하나에 이 정보가 실리려면 런타임이 이 관례를 정확히 지켜야 합니다.
    
  
    

  
  
    
    
    7. 좀비와 고아
    
    
    자식이 끝나도 커널은 그 프로세스를 바로 지우지 않습니다. 메모리와 파일은 해제하지만 PID와 종료 상태는 남겨 둡니다. 부모가 언젠가 wait로 물어볼 수 있게 하기 위해서입니다. 이 "죽었지만 아직 회수되지 않은" 상태가 좀비(ps의 STAT Z, <defunct>)입니다. 반대로 부모가 먼저 죽은 자식은 고아가 되고, 커널은 그 자식을 PID 1(또는 가장 가까운 subreaper)에게 입양시킵니다. 입양한 부모가 대신 wait해 줍니다.
    

    
    
      
    좀비 · 고아 시뮬레이터
    
      
    버튼 순서를 바꿔 가며 눌러 보세요. 아래 표는 그 순간의 ps -o pid,ppid,stat,cmd입니다. 특히 "자식 종료 → (한참 뒤) 부모 wait" 순서와 "부모 종료 → 자식 종료" 순서를 비교해 보세요.
    
      
    
        
        
        
        
      
    
      
    
      
    
    
    

    
      
      
    • 좀비는 메모리를 먹지 않지만 PID를 먹습니다. 회수하지 않는 부모가 오래 돌면 좀비가 쌓이고, pid_max나 4장의 pids.max에 닿으면 새 프로세스를 못 만듭니다.
      • 
      
    • myctr는 반드시 wait합니다. 우리 구조에서 myctr는 자식이 끝날 때까지 waitpid에 묶여 있으므로 좀비가 오래 남지 않습니다.
      • 
      
    • 2장 예고: PID 네임스페이스 안에서는 우리 자식이 PID 1이 됩니다. 컨테이너 안에서 생긴 고아는 그 PID 1에게 입양되는데, 사용자 프로그램(예: sh나 Node.js 서버)은 회수 코드를 갖고 있지 않은 경우가 많습니다. docker run --init과 tini가 존재하는 이유가 이것입니다.
      • 
    
    
    
    심화: SIGCHLD와 자동 회수
    
      
    자식이 끝나면 커널은 부모에게 SIGCHLD를 보냅니다. 기본 처리 방식은 "무시"라서 보통은 아무 일도 일어나지 않습니다. 그런데 부모가 명시적으로 SIGCHLD를 SIG_IGN으로 설정하면 Linux는 자식을 좀비로 남기지 않고 즉시 회수합니다. 그 상태에서 waitpid를 부르면 ECHILD가 돌아옵니다. 종료 코드를 알아야 하는 런타임에서는 쓰면 안 되는 설정입니다.
    
      
    subreaper: prctl(PR_SET_CHILD_SUBREAPER)를 설정한 프로세스는 자기 자손 중 고아가 된 프로세스를 PID 1 대신 입양합니다. systemd 사용자 세션이나 containerd-shim이 이 기능을 씁니다. 그래서 데스크톱 Linux에서 고아의 PPID가 1이 아닐 수 있습니다.
    
    
    
  
    

  
  
    
    
    8. Ctrl+C는 누구에게 가나
    
    
    myctr로 sleep 100을 띄우고 Ctrl+C를 누르면 무슨 일이 생길까요? 터미널은 키 입력을 받아 포그라운드 프로세스 그룹 전체에 SIGINT를 보냅니다. 셸은 myctr를 새 프로세스 그룹으로 띄우고, fork된 sleep은 그 그룹을 물려받습니다. 그래서 myctr와 sleep이 동시에 SIGINT를 받습니다.
    

    

    
    둘 다 기본 동작(종료)을 따르면 myctr는 자식을 wait하지 못한 채 먼저 죽을 수 있고, 셸은 myctr가 SIGINT로 죽었다고 보고합니다($? = 130). 이번에는 결과가 우연히 맞지만, 런타임이 자식의 결과를 보고하지 못하고 사라지는 구조입니다. 좋은 런타임은 부모가 SIGINT를 무시하고, 자식이 시그널로 죽는 것을 지켜본 뒤 그 결과(130)를 돌려줍니다.
    

    
    
      
    함정: fork 전에 무시
    // 부모가 SIGINT를 무시하도록 설정
unsafe { signal(SIGINT, SigIgn) }?;
match unsafe { fork() }? {
    Child => execvp(..),   // ← SIG_IGN을 물려받고
                            //   exec 후에도 유지!
    Parent { child } => ..
}
// 결과: sleep 100이 Ctrl+C로 안 죽는다
    
      
    올바름: fork 후 부모 쪽에서만
    match unsafe { fork() }? {
    Child => execvp(..),    // 기본 처리 방식 그대로
    Parent { child } => {
        unsafe { signal(SIGINT, SigIgn) }?;
        waitpid(child, None)?  // 자식이 죽는 걸 지켜봄
    }
}
// 결과: sleep만 죽고 myctr는 130을 반환
    
    
    
    
    5절 퀴즈에서 본 규칙이 그대로 작동합니다. 직접 등록한 핸들러 함수는 exec 때 기본값으로 돌아가지만, SIG_IGN은 그대로 유지됩니다. 실습 4에서 두 버전을 직접 비교합니다. 엄밀히는 fork와 부모의 signal() 호출 사이에 아주 짧은 틈이 있습니다. 이 틈을 없애는 방법(시그널 마스크로 막아 두기)과 SIGTERM을 자식에게 전달하는 방법은 2장에서 PID 1 문제와 함께 다룹니다.
    
  
    

  
  
    
    
    9. 구현 가이드: myctr run
    
    
    이제 직접 짤 차례입니다. 아래 순서로 진행하고, 각 단계에서 막히면 힌트를 하나씩 여세요. 참조 구현은 맨 마지막 상자에 있습니다.
    

    
    단계 A. CLI 뼈대

    힌트 B-3: WaitStatus 매칭
    
      
    플래그 없이(None) waitpid하면 돌아오는 경우는 WaitStatus::Exited(pid, code)와 WaitStatus::Signaled(pid, signal, core_dumped) 둘뿐입니다. Signal은 sig as i32로 번호를 얻습니다. 나머지 경우는 bail!로 처리하세요.

    참조 구현 (막혔을 때만 여세요)
    
      
    이 코드는 nix 0.29, clap 4, Rust 2024 에디션에서 빌드하고 위 check.sh 8개 항목을 통과하는 것을 확인했습니다.
    

    use std::ffi::CString;

use anyhow::{Context, Result, bail};
use clap::{Parser, Subcommand};
use nix::libc;
use nix::sys::wait::{WaitStatus, waitpid};
use nix::unistd::{ForkResult, execvp, fork};

#[derive(Parser)]
#[command(name = "myctr", about = "나만의 컨테이너 런타임")]
struct Cli {
    #[command(subcommand)]
    command: Command,
}

#[derive(Subcommand)]
enum Command {
    /// 명령을 자식 프로세스로 실행한다
    Run {
        /// 실행할 프로그램과 인자 (예: /bin/sh -c "echo hi")
        #[arg(required = true, trailing_var_arg = true, allow_hyphen_values = true)]
        cmd: Vec<String>,
    },
}

fn main() -> Result<()> {
    match Cli::parse().command {
        Command::Run { cmd } => {
            let code = run(&cmd)?;
            std::process::exit(code);
        }
    }
}

fn run(cmd: &[String]) -> Result<i32> {
    // fork 전에 CString을 전부 만들어 둔다. 자식에서는 할당을 최소화한다.
    let argv: Vec<CString> = cmd
        .iter()
        .map(|s| CString::new(s.as_bytes()))
        .collect::<Result<_, _>>()
        .context("인자에 NUL 바이트가 있습니다")?;

    match unsafe { fork() }.context("fork 실패")? {
        ForkResult::Child => {
            // 성공하면 돌아오지 않는다. 돌아왔다면 실패한 것.
            let err = execvp(&argv[0], &argv).unwrap_err();
            eprintln!("myctr: {}: {}", cmd[0], err);
            // 부모의 main으로 돌아가면 안 된다. 즉시 종료.
            unsafe { libc::_exit(127) }
        }
        ForkResult::Parent { child } => match waitpid(child, None).context("waitpid 실패")? {
            WaitStatus::Exited(_, code) => Ok(code),
            WaitStatus::Signaled(_, sig, _) => Ok(128 + sig as i32),
            other => bail!("예상하지 못한 상태: {other:?}"),
        },
    }
}

    11. 왜 std::process::Command를 쓰지 않나
    
    
    Rust 표준 라이브러리의 Command::new("sh").status()를 쓰면 이 장의 기능은 몇 줄로 끝납니다. 실제로 일반 애플리케이션에서는 Command가 정답입니다. 그래도 직접 fork를 쓰는 이유는 다음과 같습니다.
    
    
    
      
    std::process::Command직접 fork / clone
    
      
    내부 동작조건이 맞으면 posix_spawn, 아니면 fork + exec. 구현이 숨겨져 있음무엇이 언제 불리는지 전부 보임
    
      
    fork와 exec 사이 개입CommandExt::pre_exec 클로저로 가능 (역시 unsafe)자유롭게 가능
    
      
    clone 플래그 (네임스페이스)지정할 방법이 없음. pre_exec에서 unshare를 부를 수는 있지만 PID 네임스페이스는 unshare한 프로세스 자신이 아니라 그다음 자식부터 적용되어 구조가 꼬임clone(CLONE_NEWPID | ...)로 자식을 처음부터 새 네임스페이스에 만들 수 있음
    
      
    학습 가치낮음runc · youki · crun이 실제로 하는 일과 같음
    
    
    
    
    2장 첫 작업은 오늘의 fork()를 nix::sched::clone()으로 바꾸는 것입니다. 그 한 줄 교체로 자식이 자기만의 hostname과 PID 공간을 갖게 됩니다.
    
  
    

  
    핵심 요약
      
    
    • 컨테이너는 호스트 커널을 공유하는 평범한 프로세스이고, 런타임의 뼈대는 fork → (환경 준비) → exec → wait입니다.
      • 
    
    • fork는 한 번 불려 두 번 반환합니다. 메모리는 Copy-on-Write로 복제되고, fd·시그널 처리 방식·네임스페이스·cgroup은 그대로 물려받습니다. 호출 스레드만 복제되므로 Rust에서는 unsafe입니다.
      • 
    
    • exec는 PID를 유지한 채 메모리만 교체하고 실패할 때만 반환합니다. 네임스페이스·cgroup·root·capability·seccomp·SIG_IGN은 exec를 넘어 유지됩니다. 이 성질이 "자식 환경을 먼저 바꾸고 마지막에 exec"하는 런타임 설계를 가능하게 합니다.
      • 
    
    • wait 상태는 16비트에 인코딩됩니다. myctr는 셸 관례대로 정상 종료는 그 코드, 시그널 사망은 128+n, 실행 실패는 127(126)을 돌려줍니다.
      • 
    
    • 회수되지 않은 자식은 좀비로 PID를 점유하고, 부모를 잃은 자식은 PID 1(또는 subreaper)에게 입양됩니다. PID 네임스페이스에서는 우리 자식이 그 PID 1이 됩니다(2장).
      • 
    
    • Ctrl+C는 포그라운드 프로세스 그룹 전체로 갑니다. SIGINT 무시는 fork 이후 부모에서만 설정해야 합니다.
      • 
  
    

  
    확인 문제
    
  
    
    
    fork 직후 자식 프로세스에서 fork()의 반환값(C 기준)은?
    
    
    
    
    
    
    자식은 0, 부모는 자식의 PID를 받습니다. -1은 실패입니다. 자식이 자기 PID를 알고 싶으면 getpid()를 부릅니다. nix에서는 각각 ForkResult::Child, ForkResult::Parent { child }입니다.
    
  
    
  
    
    
    execvp가 성공하면 호출한 코드에서 무슨 일이 일어나나?
    
    
    
    
    
    
    exec는 현재 프로세스의 이미지를 교체합니다. 성공하면 돌아갈 코드가 없으므로 반환하지 않고, 실패했을 때만 반환합니다. 그래서 nix의 반환 타입이 Result<Infallible>입니다.
    
  
    
  
    
    
    컨테이너 안의 프로세스가 SIGKILL로 죽었다. myctr가 셸 관례를 따른다면 $?는?
    
    
    
    
    
    
    128 + 시그널 번호(SIGKILL = 9) = 137입니다. Kubernetes의 "Exit Code 137"이 바로 이것이며, OOM killer가 가장 흔한 원인입니다.
    
  
    
  
    
    
    자식에서 exec가 실패했을 때 return Err(..) 대신 libc::_exit(127)을 쓰는 가장 중요한 이유는?
    
    
    
    
    
    
    fork된 자식은 부모 코드의 복제본입니다. return하면 부모의 호출 스택을 그대로 거슬러 올라가 부모만 해야 할 일을 하게 됩니다. _exit는 atexit 핸들러나 stdio 버퍼 비우기 같은 정리 없이 즉시 종료합니다.
    
  
    
  
    
    
    부모가 fork 전에 SIGINT를 SIG_IGN으로 설정하고 fork + exec로 sleep 100을 실행했다. Ctrl+C를 누르면?
    
    
    
    
    
    
    시그널 처리 방식은 fork로 복사되고, exec는 직접 등록한 핸들러만 기본값으로 되돌릴 뿐 SIG_IGN은 유지합니다. 그래서 무시 설정은 fork 이후 부모 쪽에서만 해야 합니다.
    
  
    
  
    
    
    좀비 프로세스가 계속 쌓일 때 실제로 고갈되는 자원은?
    
    
    
    
    
    
    좀비는 메모리와 fd를 이미 해제했고 실행되지도 않습니다. 남은 것은 PID와 종료 상태를 담은 작은 커널 구조체입니다. 그래도 PID가 고갈되면 시스템이나 cgroup(pids.max)에서 새 프로세스를 만들 수 없습니다.
    
  
    
  
    
    
    aarch64 Linux에서 glibc의 fork()를 strace로 보면 어떤 시스템 콜이 보이나?
    
    
    
    
    
    
    aarch64에는 fork 시스템 콜이 없고, glibc는 clone(flags=...|SIGCHLD)로 fork를 구현합니다. posix_spawn은 라이브러리 함수이지 시스템 콜이 아닙니다. 2장에서는 clone에 네임스페이스 플래그를 직접 넣습니다.
