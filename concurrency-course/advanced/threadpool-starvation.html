ThreadPool과 starvation 진단

선수 장 · Task와 비동기 상태 머신

Task가 전용 스레드가 아니라는 사실을 알았는데도 CPU가 한가한 서버의 응답이 느릴 수 있습니다. 실행할 일이 없다는 상태와, 실행할 스레드가 대기에 묶인 상태를 구분합니다.

큐와 실행 자원의 위치

ThreadPool은 준비된 작업을 실행할 관리 스레드를 공급합니다. 긴 동기 대기를 가진 작업을 계속 넣으면 스레드가 반환되지 않아 후속 작업이 기다릴 수 있습니다. ThreadPool은 스레드 수를 조정하지만, 늘어난 스레드 자체가 네트워크나 DB 용량을 늘리지는 않습니다.

Task.Run(() => BlockingCall()) 뒤에 await를 붙여도 BlockingCall을 실행하는 다른 풀 스레드가 대기합니다. 반면 실제 비동기 I/O의 미완료 Task를 await하는 동안에는 요청마다 풀 스레드 하나를 붙잡을 필요가 없습니다. 이 구분은 실행 API의 이름보다 하위 호출이 어떻게 기다리는지에 달려 있습니다.

지표에서 대기 스택까지 좁히기

로컬 실습 서버에 await Task.Delay(200) 경로와 Task.Delay(200).GetAwaiter().GetResult() 경로를 따로 만듭니다. 같은 작은 동시 부하를 주고 dotnet-counters monitor -p PID --counters System.Runtime로 CPU, 스레드 수, 풀 큐와 완료 작업 추세를 함께 봅니다. 런타임에 따라 지표 이름과 표시 형식은 달라질 수 있습니다.

지연 증가와 낮은 CPU만으로 원인을 확정하지 않습니다. dotnet-stack report -p PID나 dotnet-trace collect -p PID로 풀 스레드가 어디서 기다리는지 확인합니다. 긴 대기가 외부 서비스·락·연결 풀 중 어디에 있는지 찾아야 하며, 최소 스레드 수를 늘린 결과만으로 원인을 해결했다고 보고하지 않습니다.

실습과 예상 관찰

공식 진단 샘플 또는 자신의 로컬 서버에서 두 대기 경로를 준비하세요. 요청 수를 작게 시작해 한 단계씩 올리고, 동일 기간의 지연·오류·CPU·스레드 수·스택을 저장합니다. 부하 발생기 자체가 먼저 포화되지 않는지 확인한 뒤 비동기 경로로 바꿔 같은 조건을 재실행하세요.

동기 대기가 풀 스레드를 점유

낮은 CPU와 함께 스레드 수 증가·응답 지연이 나타날 수 있습니다. 대기 스택이 관측을 뒷받침해야 starvation 가설을 지지할 수 있습니다.

하위 API까지 비동기로 연결

I/O 지연 자체는 유지돼도 대기 중 스레드 점유를 줄일 수 있습니다. DB나 서버가 한계라면 처리량 개선은 제한됩니다.

실습의 경계와 다음 장

고정 슬롯 브라우저 모델은 ThreadPool의 조정 알고리즘을 재현하지 않습니다. 작은 작업 처리기로 돌아가 실행 수·대기열·외부 자원의 상한을 각각 정합니다.
