CPU 병렬화와 데이터 분할

선수 장 · 프로세스·스레드와 CPU

코어 두 개에서 실행이 겹치는 그림을 실제 계산 작업으로 옮깁니다. 작업 수를 늘리는 것보다 공유 갱신과 분할·병합 비용을 줄이는 일이 먼저일 수 있습니다.

독립 구간을 정하는 불변식

입력 배열의 서로 다른 인덱스를 각 반복이 한 번씩 처리하면 results[i] = Compute(input[i])의 출력 위치를 분리할 수 있습니다. 공용 List.Add를 동시에 호출하거나 하나의 합계를 매 항목마다 갱신하는 구조와 구분합니다. 계산 함수의 숨은 전역 상태도 공유 데이터입니다.

ParallelOptions.MaxDegreeOfParallelism으로 실행 상한을 두고 순차 결과와 값이 같은지 먼저 검사합니다. I/O를 기다리는 작업의 수와 CPU 계산 병렬도는 다른 기준입니다. CPU quota가 작은 환경에서 보이는 프로세서 개수만큼 무조건 worker를 늘리지 않습니다.

지역 누적 후 병합하는 코드

Parallel.For의 localInit에서 0L을 만들고 body가 지역 합계를 반환하게 한 뒤 localFinally에서 한 번씩 합칩니다. 항목마다 공용 합계에 Interlocked.Add하는 방법과 비교하면 경합 횟수가 달라집니다. 부동소수점 덧셈은 결합 순서에 따라 오차가 달라지므로 정수 합계와 같은 정확 일치를 요구하지 않습니다.

배열의 서로 다른 칸도 같은 캐시 라인을 쓰면 false sharing 비용이 생길 수 있습니다. 이는 논리 데이터 레이스와 다른 현상입니다. 작업당 계산량·분할 크기·지역 누적 여부를 하나씩 바꾸고 예열 후 반복 측정합니다. 실행 시간만 줄고 결과가 빠졌다면 최적화가 아닙니다.

실습과 예상 관찰

고정 시드의 정수 배열을 만들고 순차 합계, 항목별 Interlocked 합계, 지역 누적 병렬 합계를 비교하세요. 각 버전의 결과를 먼저 검사한 뒤 동일 Release 빌드에서 여러 번 시간을 잽니다. 배열 크기와 계산 반복 수를 각각 바꿔 분할 비용이 우세한 구간을 찾으세요.

작은 작업을 많은 단위로 분할

스케줄링·병합 비용 때문에 순차보다 느릴 수 있습니다. 병렬화가 계산량을 줄이지는 않습니다.

충분한 독립 계산과 지역 누적

공유 갱신 횟수를 줄여 병렬 실행의 이익을 얻을 여지가 있습니다. 실제 상한은 코어·quota·메모리 대역폭에 달려 있습니다.

실습의 경계와 다음 장

측정한 한 환경의 배율을 다른 CPU에 일반화하지 않습니다. 작업 처리기로 돌아가 CPU 단계와 I/O 단계를 다른 상한으로 구성해 봅니다.
