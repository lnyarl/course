01

24.1 소스 버전만 같다고 빌드 환경이 같지는 않다

Linux 커널 빌드는 Kconfig로 선택한 기능과 아키텍처, 컴파일러, 생성된 헤더를 함께 사용합니다. 이 교재의 소스 기준은 v6.18이고 실행 실습은 6.18 LTS 계열의 정확한 패치 버전과 설정을 기록합니다. 배포판이 추가한 패치와 설정도 동작에 영향을 줄 수 있습니다.

외부 모듈은 실행 중인 커널에 맞는 준비된 빌드 디렉터리를 사용해야 합니다. /lib/modules/$(uname -r)/build가 그 연결점인 경우가 일반적입니다. 임의의 최신 헤더만 내려받아 컴파일했다고 현재 커널에서 로드할 수 있는 것은 아닙니다.

커널 전체를 처음 빌드한다면 소스 태그 확인, 별도 출력 디렉터리, 대상 아키텍처의 설정, 빌드, VM 부팅, uname과 config 확인 순서로 진행합니다. 호스트 부트로더를 바꾸는 작업은 이 실습에 포함하지 않습니다. 먼저 준비된 일회용 VM에서 작은 모듈의 수명부터 관찰합니다.

02

24.2 드라이버는 장치와 커널 규약을 연결한다

실제 장치 드라이버는 버스 탐색과 probe, 자원 할당, 인터럽트, DMA, 전원 관리, 제거를 처리합니다. 문자 장치는 이런 기능을 사용자 공간에 파일 연산으로 제공할 수 있는 한 방식입니다. 모든 드라이버가 문자 장치 파일 하나로 표현되는 것은 아닙니다.

여기서는 물리 장치 대신 고정 문자열을 반환하는 miscdevice를 사용합니다. misc_register가 등록을 담당하고 file_operations의 read 콜백을 VFS가 호출합니다. 핵심은 사용자 read가 커널의 우리가 정의한 함수로 연결되는 지점을 직접 보는 것입니다.

커널은 사용자 포인터를 일반 커널 주소처럼 직접 역참조하면 안 됩니다. simple_read_from_buffer 같은 도우미는 버퍼 복사와 파일 위치 처리를 제공해 예제를 작게 유지합니다. 실제 드라이버에서는 짧은 복사, 잘못된 주소, 동시 접근과 장치 제거가 함께 고려되어야 합니다.

03

24.3 등록과 해제는 대칭이어야 한다

모듈의 init이 성공하면 사용자에게 기능이 노출되고, exit는 노출과 자원을 정리합니다. 초기화 중간에 실패하면 이미 획득한 자원을 역순으로 반환해야 합니다. 성공 경로만 구현하면 재시도와 로드 실패에서 누수나 잘못된 참조가 남습니다.

file_operations의 owner에 THIS_MODULE을 연결하면 열린 파일 참조와 모듈 수명 관리가 이어집니다. 작업 중인 코드가 사라지는 상황을 막기 위한 참조 관리의 일부입니다. 실제 비동기 작업이 있는 드라이버는 workqueue 취소, IRQ 해제, 진행 중 작업 종료까지 설계해야 합니다.

외부 모듈 로드는 커널 taint 상태를 바꿀 수 있고, Secure Boot와 서명 정책이 로드를 막을 수 있습니다. 이를 우회하기 위해 호스트의 보안을 끄지 않습니다. 실습용 VM의 정책과 준비 조건을 확인하고, 로드 실패도 오류 메시지와 함께 관측 결과로 기록합니다.

04

24.4 최소 장치로 전체 호출 경로를 확인한다

cat이 장치 파일을 열면 VFS가 등록된 연산을 찾아 read 콜백을 호출합니다. 첫 호출은 문자열을 반환하고, 파일 위치가 끝에 도달한 다음 호출은 0을 반환해 EOF를 알립니다. 파일 위치 처리를 생략하면 cat이 같은 데이터를 끝없이 읽는 버그가 생길 수 있습니다.

실습의 mode 0400은 root만 읽도록 범위를 좁힙니다. 장치 노드 생성은 devtmpfs·udev 등의 환경에 달려 있으므로 등록 성공 후 /dev/kernel_lesson의 존재를 확인합니다. 없을 때는 생성 메커니즘을 조사하고 임의의 major/minor를 추측하지 않습니다.

빌드 성공, 모듈 로드 성공, read 결과 확인, 모듈 제거 성공은 각각 다른 검증입니다. 마지막까지 확인해야 최소 수명 주기를 수행했다고 말할 수 있습니다. 이 교재는 코드와 절차를 제공하며, 브라우저 실험이 실제 모듈 실행을 대신하지는 않습니다.

05

24.5 전체 커널 빌드와 외부 모듈 빌드를 구분한다

전체 커널 빌드는 부팅 가능한 커널 이미지와 선택한 모듈들을 만듭니다. 외부 모듈 빌드는 이미 정해진 커널의 인터페이스와 설정을 사용해 추가 코드를 만듭니다. 두 경우 모두 소스 버전만으로 충분하지 않고 생성 헤더, 설정, 컴파일 환경이 관련됩니다. 모듈 예제가 짧다고 일반 C 프로그램처럼 cc 한 번으로 올바른 결과를 얻는 구조는 아닙니다.

별도 출력 디렉터리를 사용하면 소스와 생성 결과를 분리할 수 있습니다. 예를 들어 커널 소스가 준비된 VM에서 make O=... defconfig 같은 흐름으로 설정을 만들고 필요한 옵션을 확인합니다. 하지만 현재 장치와 루트 파일 시스템을 지원하지 않는 설정으로 만든 이미지를 곧바로 호스트 기본 부팅 항목으로 바꾸는 것은 학습에 불필요한 범위입니다.

본 실습은 사전 준비된 6.18 LTS VM의 실행 커널과 일치하는 build 디렉터리를 사용합니다. uname -r, build 링크의 실제 대상, CONFIG_MODULES, 빌드 로그를 기록하면 컴파일 실패를 코드 오류와 환경 불일치로 나누기 쉽습니다. 버전 문자열의 일부가 같다는 이유만으로 실행 커널과 정확히 일치한다고 추측하지 않습니다.

06

24.6 read 콜백의 인자를 하나씩 해석한다

lesson_read의 struct file *f는 열린 사용 상태를 가리키고 char __user *buf는 사용자 공간의 목적지입니다. count는 사용자가 요청한 최대 크기이며 loff_t *pos는 현재 읽기 위치를 다룹니다. 반환값은 실제로 읽은 바이트 수, EOF의 0, 또는 음수 오류 코드입니다. 인자를 외우기보다 사용자 read 호출의 어느 부분이 각각으로 전달되는지 연결합니다.

문자열 길이가 18바이트인데 count가 4이면 한 번에 4바이트만 반환하고 위치를 앞으로 옮겨야 합니다. 다음 읽기는 다음 바이트부터 이어가며 마지막 이후에는 0을 반환합니다. simple_read_from_buffer는 이런 작은 읽기와 위치, 사용자 복사의 규약을 도와줍니다. 고정 문자열을 매번 처음부터 반환하는 잘못된 구현은 cat을 끝나지 않게 만들 수 있습니다.

사용자 포인터는 커널이 믿고 직접 쓰는 주소가 아닙니다. 잘못된 주소나 접근 불가 페이지가 있을 수 있으므로 해당 API의 복사 규약과 반환값을 따라야 합니다. 커널 안에서 잘못된 포인터 사용은 한 프로세스의 예외로 끝나지 않고 전체 시스템 안정성에 영향을 줄 수 있습니다. 짧은 교육 예제에서도 사용자·커널 주소 공간의 경계를 유지하는 이유입니다.

07

24.7 miscdevice를 선택한 이유와 생략한 책임

문자 장치를 직접 등록하려면 장치 번호 범위, cdev, 장치 모델과 노드 생성의 연결을 다루어야 합니다. miscdevice는 작은 문자 장치의 등록을 간결하게 만드는 경로를 제공합니다. 이 장은 동작 가능한 최소 read 경로에 집중하기 위해 동적 minor와 misc_register를 사용합니다. 따라서 이 예제만으로 모든 장치 드라이버 등록 모델을 배웠다고 말하지 않습니다.

실제 PCI나 platform 장치는 하드웨어 발견과 probe, 자원 요청, 오류 시 rollback, suspend와 resume, remove가 필요합니다. 읽기 한 번이 레지스터 접근이나 DMA 완료를 기다릴 수 있고 여러 사용자가 동시에 접근할 수도 있습니다. 현재 예제는 물리 장치가 없는 고정 문자열이므로 이런 복잡성을 의도적으로 제외합니다.

다음 단계로 확장할 때에는 한 번에 하나의 책임을 추가합니다. 예를 들어 읽기 전용 상태 카운터를 만들면 동시 읽기와 갱신의 동기화 질문이 생깁니다. 비동기 작업을 추가하면 workqueue와 모듈 제거의 수명 질문이 생깁니다. 단순히 기능 수를 늘리기보다 새로 생긴 공유 상태와 종료 조건을 명확히 하는 방향으로 진행합니다.

08

24.8 열린 fd가 있을 때 모듈 제거를 생각한다

모듈 코드가 제공하는 read 콜백을 실행할 수 있는 fd가 열려 있는데 코드가 먼저 제거되면 호출 대상이 사라집니다. .owner = THIS_MODULE은 열린 파일 연산과 모듈 참조를 연결하는 데 중요한 역할을 합니다. 정상 제거가 사용 중인 모듈을 거부하는 것은 불편한 장애가 아니라 수명 계약을 보호하는 동작일 수 있습니다.

하지만 owner만 설정하면 모든 비동기 문제가 해결되는 것은 아닙니다. 타이머나 workqueue, IRQ handler가 나중에 모듈의 데이터와 코드를 사용할 수 있다면 제거 경로에서 새 작업을 막고 진행 중 작업이 끝나는 것을 기다려야 합니다. 등록 해제, 취소, 대기, 메모리 반환 순서를 잘못 정하면 재현이 드문 use-after-free가 생길 수 있습니다.

실습에서는 cat이 끝나 fd가 닫힌 뒤 rmmod를 수행합니다. 제거가 실패하면 force 옵션을 사용하지 말고 열린 참조와 오류를 확인합니다. 모듈의 정상 종료를 검증하는 목적은 “강제로 사라지게 만들었다”는 결과가 아니라 코드와 자원을 더 이상 참조하는 경로가 없다는 계약을 확인하는 데 있습니다.

09

24.9 오류를 어느 단계의 문제로 분류할 것인가

컴파일 오류는 헤더·API·코드·도구 체계의 문제일 수 있습니다. 빌드 디렉터리가 없으면 먼저 실행 커널에 맞는 개발 환경이 준비됐는지 확인합니다. 함수 선언이 없거나 구조체 필드가 다르면 교재 기준 v6.18과 실제 대상으로 빌드한 버전이 일치하는지 확인한 뒤 API 차이를 조사합니다. 무작정 다른 헤더를 복사해 섞지 않습니다.

insmod 오류는 ABI와 심볼, 서명 정책, 모듈 기능 비활성, 이미 등록된 이름 등 여러 원인이 가능합니다. 빌드 성공이 로드 권한과 런타임 호환성을 보장하지 않습니다. dmesg를 읽을 권한이 있는 VM에서 관련 커널 메시지와 사용자 errno를 함께 기록하면 어느 조건이 실패했는지 좁힐 수 있습니다.

로드는 성공했는데 /dev 노드가 없다면 devtmpfs와 udev, 등록 이름과 sysfs 상태를 확인합니다. 노드가 있는데 cat이 실패하면 접근 권한과 read 경로를 확인합니다. 각 단계의 실패를 하나의 “드라이버 안 됨”으로 합치지 않으면 필요한 증거와 다음 행동이 구체화됩니다.

10

24.10 사용자 프로그램과 커널 코드의 디버깅 차이

사용자 프로그램의 잘못된 메모리 접근은 일반적으로 해당 프로세스에 예외를 일으킵니다. 커널 코드의 오류는 공유된 커널 상태를 망가뜨려 다른 작업이나 전체 시스템에 영향을 줄 수 있습니다. 그래서 학습용 모듈은 일회용 VM에서 실행하고 재부팅 가능한 상태와 로그 수집 경로를 준비합니다. 이 차이는 무서움을 강조하려는 것이 아니라 실험 경계를 정확히 설정하려는 것입니다.

printk를 추가하면 실행 경로를 볼 수 있지만 빈번한 출력은 시간과 스케줄링을 바꿀 수 있습니다. 동시성 버그가 로그를 넣었더니 사라지는 경우에는 문제가 해결된 것이 아니라 실행 타이밍이 달라졌을 수 있습니다. 필요에 맞는 tracepoint와 검출 도구를 선택하고, 로그 없는 상태에서도 같은 결과가 유지되는지 확인해야 합니다.

KASAN과 lockdep 같은 검사 설정은 문제가 드러나는 조건을 확대할 수 있지만 검사 비용도 바꿉니다. 일반 커널과 디버그 커널의 성능을 직접 비교해 드라이버가 느려졌다고 결론내리지 않습니다. 정확성 검증 환경과 성능 측정 환경의 목적을 분리하고 각각의 커널 설정을 기록합니다.

11

24.11 검증 표를 작성하고 다음 실습을 고른다

최소 검증 표에는 대상 커널 release와 config, 모듈 빌드 결과, 로드 결과, 장치 노드 생성, 첫 read, EOF, 제거 결과가 들어갑니다. 각 항목에 실제 출력과 실패 이유를 남깁니다. 제공된 코드가 눈으로 보기 타당하다는 사실과 해당 환경에서 실행해 성공했다는 사실은 다른 수준의 증거입니다.

다음 실험은 읽기 크기를 1바이트와 큰 버퍼로 바꾸어 같은 내용을 얻는지, 두 번 독립적으로 open하면 각자 처음부터 읽는지 확인하는 것입니다. 이렇게 사용자 공간의 file offset 학습을 자신의 커널 콜백으로 연결할 수 있습니다. 멀티스레드 쓰기나 실제 장치 제어를 바로 추가하기 전에 기본 파일 계약이 유지되는지 확인합니다.

코드를 확장한다면 오류를 재현할 수 있는 작은 사용자 프로그램을 함께 작성하세요. 커널 코드의 내부 함수가 호출됐다는 로그만으로 사용자 기능이 맞다고 검증하지 않습니다. 사용자가 받을 바이트, 반환값, 종료 조건을 기준으로 확인하면 구현이 바뀌어도 같은 계약을 계속 검증할 수 있습니다.

12

24.12 확인 과제: 새 요청 차단과 기존 요청 종료

모듈 제거를 설계할 때에는 새 사용자가 들어오는 경로를 막는 일과 이미 진행 중인 사용이 끝나는 일을 기다리는 것을 나누어 생각합니다. 브라우저 모델의 열린 참조 수와 남은 비동기 작업 수는 이 두 책임을 드러내는 개념적 값입니다. 두 값이 0인지 확인하는 모형 자체가 실제 Linux의 module reference와 모든 드라이버 수명 규칙을 완전히 구현하는 것은 아닙니다.

예제의 .llseek 항목은 지정하지 않습니다. Linux 6.18에서는 오래된 예제의 no_llseek 이름을 그대로 복사하지 않고 지원되는 file_operations 계약을 따라야 합니다. 사용자 read의 파일 위치 처리는 simple_read_from_buffer와 전달된 pos로 설명하며, seek 기능을 별도로 구현하지 않은 읽기 전용 장치라는 범위를 유지합니다.

검증 표에 로드·읽기·EOF·제거가 모두 채워지면 최소 장치의 수명 주기를 확인한 것입니다. 실제 하드웨어 드라이버로 확장할 때에는 IRQ, DMA, 전원 상태, 장치 제거와 진행 중 작업의 관계를 새 검증 항목으로 추가해야 합니다. 작은 예제가 성공했다는 사실을 복잡한 장치 전체의 안전성으로 확대하지 않습니다.

환경 준비와 명령 실행 전제 · 아래는 제공 실습이며 이 교재 제작 환경에서 Linux 실행 결과를 검증하지 않았습니다.

Linux VM / Shell · C
work=$(mktemp -d /tmp/kernel-lesson-XXXXXX)
cd "$work" || exit 1
cat > lesson.c <<'C'
#include <linux/module.h>
#include <linux/fs.h>
#include <linux/miscdevice.h>
static ssize_t lesson_read(struct file *f, char __user *buf,
                           size_t count, loff_t *pos)
{
  static const char text[] = "hello from kernel\n";
  return simple_read_from_buffer(buf, count, pos, text, sizeof(text)-1);
}
static const struct file_operations ops = {
  .owner = THIS_MODULE, .read = lesson_read,
};
static struct miscdevice device = {
  .minor = MISC_DYNAMIC_MINOR, .name = "kernel_lesson",
  .fops = &ops, .mode = 0400,
};
static int __init lesson_init(void) { return misc_register(&device); }
static void __exit lesson_exit(void) { misc_deregister(&device); }
module_init(lesson_init);
module_exit(lesson_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Read-only learning device");
C
printf 'obj-m += lesson.o\n' > Makefile
make -C "/lib/modules/$(uname -r)/build" M="$PWD" modules
# 아래는 빌드 성공 후 일회용 VM에서만 실행
sudo insmod ./lesson.ko
ls -l /dev/kernel_lesson
sudo cat /dev/kernel_lesson
sudo rmmod lesson
