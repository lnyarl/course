BPF의 검증·연결·이식성

선수 장 · 실행 중인 커널 추적

25장에서 BPF map 집계를 소개했습니다. 프로그램이 안전하게 로드됐다는 사실, 원하는 hook에 연결됐다는 사실, 수집한 지표가 질문에 맞는다는 사실을 이제 세 단계로 나눕니다.

open·load·attach는 서로 다른 성공

libbpf의 open 단계는 객체와 map·program을 파악하고 설정을 준비합니다. load 단계에서는 map 생성·relocation·verifier 검사와 프로그램 로드가 이뤄집니다. attach 단계가 돼야 실제 hook에서 실행됩니다. 로드 성공만 보고 이벤트가 수집되고 있다고 설명하지 말고 attach 결과와 실제 대상 이벤트를 확인합니다.

verifier는 허용된 접근과 실행 조건을 검사하지만 분석 의도의 정확성을 보장하지 않습니다. map lookup 결과가 NULL일 수 있는 경로를 검사해야 한다는 예시는 프로그램 자체의 안전 계약입니다. 이를 보안 우회나 커널 오류 재현으로 바꾸지 않습니다. 잘못된 단위·PID 필터는 안전하게 로드되는 잘못된 계측을 만들 수 있습니다.

CO-RE가 바꾸는 것과 유지하는 것

BTF는 타입 정보를 제공하고 CO-RE는 대상 커널의 타입 배치에 맞게 접근을 조정하는 기반입니다. 필드 위치가 달라도 올바른 타입 정보를 이용해 이식할 수 있지만 없는 필드·없는 hook·권한·의미 변화까지 자동 해결하지 않습니다. 내부 함수 이름에 의존한 kprobe와 문서화된 tracepoint는 안정성 경계가 다릅니다.

고빈도 이벤트마다 문자열을 출력하면 전송·포맷·버퍼 비용이 늘 수 있습니다. map에 개수·히스토그램을 모으면 전달량을 줄일 수 있지만 map 갱신과 경합 비용은 남습니다. 프로그램 전후의 동일 작업량·시간 구간과 dropped event 여부를 함께 기록해야 계측 오버헤드를 비용 없는 관측으로 오해하지 않습니다.

실습과 예상 관찰

설치된 환경에서 test -r /sys/kernel/btf/vmlinux와 bpftool version을 읽습니다. 도구가 없으면 설치하지 않고 미준비로 기록합니다. 공식 libbpf 예제의 open→load→attach→destroy 호출을 찾아 표에 적고, 수집 전후 동일한 짧은 자기 작업의 완료량을 비교할 계획을 만듭니다.

load 성공·attach 미수행

예상: map·프로그램은 준비돼도 hook에서의 실행 증거는 없습니다. 이벤트 0을 시스템 동작이 없었다는 증거로 사용할 수 없습니다.

attach 성공·필터가 다른 PID를 선택

예상: 실행은 가능해도 대상 작업에 대한 통계는 비어 있을 수 있습니다. 필터와 hook·시간 범위를 확인한 뒤 결론을 내려야 합니다. 실제 수집 값은 실행한 경우 별도 기록합니다.

실습의 경계와 다음 장

이 단원은 BPF 프로그램의 로드 생명주기와 계측 의미를 분석하며 권한 변경·검증 우회·위험한 프로그램 실행은 하지 않습니다. 26장 성능 조사에서는 줄이려는 실제 구간과 계측 구간을 먼저 맞춥니다.
