KVM VM·vCPU와 호스트 실행 경계

선수 장 · 컨테이너와 가상 머신

23장에서 VM은 별도 게스트 커널을 실행한다고 배웠습니다. 이제 /dev/kvm의 디스크립터와 KVM_RUN의 복귀 이유를 통해 게스트 진행과 호스트 스케줄링을 연결합니다.

디스크립터의 계층이 자원 소유권을 나눈다

/dev/kvm을 열면 시스템 ioctl의 진입점을 얻습니다. KVM_CREATE_VM은 VM fd를, KVM_CREATE_VCPU는 vCPU fd를 만듭니다. 게스트 메모리 등록은 게스트 물리 주소 범위와 사용자 공간 VMM의 버퍼 관계를 설정하는 작업이며, 그 버퍼의 수명을 VM 실행보다 짧게 잡으면 안 됩니다. ioctl 종류마다 허용하는 fd가 다릅니다.

지원 기능은 KVM_CHECK_EXTENSION 등으로 확인합니다. 문서에 이름이 있다는 이유만으로 현재 호스트·아키텍처·권한에서 사용할 수 있다고 가정하지 않습니다. 실행 kernel과 6.18 API 기준의 차이를 기록하고, VM ioctls의 프로세스·vCPU ioctl의 스레드 관련 사용 계약도 해당 API 항목에서 확인합니다.

KVM_RUN에서 돌아왔다고 게스트가 실패한 것은 아니다

vCPU 스레드는 KVM_RUN으로 게스트 실행을 요청하고, 사용자 공간 처리가 필요한 exit 등에서 복귀할 수 있습니다. exit_reason에 따라 I/O 처리·종료·오류 등을 분기하며 알 수 없는 이유를 정상 완료로 처리하지 않습니다. VM exit, VMM의 처리 시간, 호스트가 vCPU 스레드를 실행하지 못한 시간을 구분해야 지연을 설명할 수 있습니다.

게스트에서 runnable인 작업이 있어도 해당 vCPU 스레드가 호스트 CPU를 받지 못하면 실제 진행은 늦습니다. 게스트 CPU 평균과 호스트의 실행·대기를 서로 다른 범위로 기록합니다. dirty 추적은 게스트 메모리 변경을 관측하는 기반이지만 그 자체로 live migration의 장치 상태·정지·재개 순서까지 완성하지 않습니다.

실습과 예상 관찰

현재 Linux에서 ls -l /dev/kvm과 uname -r을 읽어 인터페이스 존재·권한만 확인합니다. 접근 권한을 변경하지 않습니다. 이후 시스템 fd→VM fd→vCPU fd→RUN→exit_reason 분기 카드로 I/O exit와 종료 exit를 각각 추적하세요.

처리 가능한 I/O exit 뒤 다시 RUN

예상 모델 결과: VMM이 해당 I/O를 올바르게 처리한 뒤 게스트를 계속 실행할 수 있습니다. exit 횟수가 곧 실패 횟수는 아닙니다.

호스트에서 vCPU 스레드가 실행 대기

예상 모델 결과: 게스트 내부 작업의 준비 상태만으로 종단 지연을 설명할 수 없습니다. 실제 호스트 스케줄링 trace가 있어야 대기 시간을 주장할 수 있습니다.

실습의 경계와 다음 장

이 단원은 VMM을 실행하거나 VM 성능을 측정하지 않습니다. 호스트·게스트 경계를 분리한 뒤 26장의 실행 시간·배정 대기 분석으로 돌아가 같은 요청의 시간을 정렬합니다.
