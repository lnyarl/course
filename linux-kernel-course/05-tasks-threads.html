01

커널이 실행하는 단위

사용자에게 프로세스는 실행 중인 프로그램으로 보이지만 스케줄러가 CPU에 올리는 단위는 task입니다. Linux의 task_struct는 실행 상태, 스케줄링 정보, 식별자와 여러 자원 객체에 대한 참조를 보관합니다. 하나의 다중 스레드 프로그램에도 여러 task가 존재합니다.

각 task는 자신의 실행 레지스터 상태와 커널 스택 등 실행에 필요한 상태를 가집니다. 한 스레드가 파일을 기다려 잠든 동안 같은 프로세스의 다른 스레드는 실행될 수 있습니다. 프로세스 전체를 한 덩어리로만 생각하면 이런 독립적인 실행·대기를 설명하기 어렵습니다.

task_struct에 연결되어 있다는 이유로 모든 자원이 task마다 복제되는 것은 아닙니다. 주소 공간을 나타내는 mm_struct, 파일 디스크립터 테이블과 시그널 관련 상태는 생성 옵션에 따라 공유할 수 있습니다. 핵심은 구조체의 이름보다 공유 관계입니다.

02

프로세스와 스레드는 공유 정책이 다르다

일반적인 pthread 스레드들은 같은 주소 공간과 열린 파일 테이블을 공유합니다. 따라서 전역 변수에 대한 한 스레드의 쓰기를 다른 스레드가 볼 수 있지만, 올바른 동기화 없이 동시에 접근하면 언어와 메모리 모델 차원의 데이터 경쟁이 생깁니다.

스레드마다 사용자 스택과 thread-local storage는 별도로 관리됩니다. 그러나 같은 주소 공간 안에 있으므로 다른 스레드의 스택이 하드웨어 보호 경계로 완전히 격리되는 것은 아닙니다. 포인터가 알려지면 다른 스레드가 그 메모리에 접근할 수 있다는 점이 프로세스 격리와 다릅니다.

fork로 생성한 별도 프로세스는 보통 독립 주소 공간을 갖습니다. 초기 내용은 같고 물리 페이지를 COW로 공유할 수 있지만, 이후 일반적인 메모리 쓰기는 서로 다른 논리 주소 공간의 변경입니다. 명시적인 공유 메모리는 또 다른 공유 정책입니다.

03

PID, TID, TGID

Linux에서는 task별 식별자와 스레드 그룹 식별자를 구분합니다. 사용자 공간에서 getpid가 돌려주는 값은 일반적인 스레드 그룹 관점의 프로세스 ID이고 gettid는 호출한 task의 ID입니다. 그룹 리더는 자신의 TID와 그룹의 TGID가 같습니다.

/proc/PID/task 아래에서 해당 프로세스의 스레드 목록을 볼 수 있습니다. ps의 프로세스 목록만 보면 숨겨졌던 CPU 사용자가 스레드 표시 옵션에서는 드러납니다. 특정 프로세스가 CPU 여러 개를 쓰는지 분석할 때 스레드별 상태와 CPU 사용량을 확인합니다.

PID namespace에서는 같은 실행 주체가 관측 위치에 따라 다른 숫자로 보일 수 있습니다. 따라서 컨테이너 로그의 PID와 호스트 도구의 PID를 숫자만으로 연결하면 틀릴 수 있습니다. 숫자는 자원의 본질이 아니라 특정 이름 공간에서의 식별자입니다.

04

자원 수명과 종료

스레드가 종료된다고 공유 주소 공간과 열린 파일이 즉시 모두 사라지는 것은 아닙니다. 공유 객체는 남은 참조와 그룹 수명에 따라 유지될 수 있습니다. 커널 코드를 읽을 때 get과 put, 참조 카운트, 마지막 해제 경로를 함께 찾아야 하는 이유입니다.

프로세스 종료의 사용자 공간 의미와 개별 task 종료의 커널 경로는 구별해야 합니다. 일반적인 프로그램의 exit는 런타임 정리와 스레드 그룹 종료로 이어질 수 있지만 저수준 종료 인터페이스의 의미는 다를 수 있습니다. API 이름만으로 범위를 추정하지 않습니다.

장애 분석에서는 어느 task가 기다리는지, 공유 자원을 누가 보유하는지, 다른 task가 진행할 수 있는지를 함께 봅니다. 한 스레드의 긴 대기가 전체 프로세스 멈춤으로 보이는 이유가 전역 락이나 작업 의존성일 수도 있습니다.

05

사례: 작업자 네 개가 한 파일을 처리한다

파일의 서로 다른 구간을 처리하는 작업자 네 개를 만든다고 합시다. 네 개를 스레드로 만들면 보통 하나의 주소 공간과 파일 디스크립터 테이블을 공유합니다. 큐에 넣은 작업 포인터를 다른 스레드가 직접 읽을 수 있고 결과를 같은 자료구조에 기록할 수 있습니다. 데이터 전달이 편리한 대신 작업 큐와 결과 상태를 동시에 바꾸는 순서를 올바르게 정해야 합니다. 공유가 쉬운 구조에서는 경쟁도 쉽게 생깁니다.

작업자 네 개를 별도 프로세스로 만들면 각 프로세스의 일반적인 메모리 쓰기는 다른 프로세스의 주소 공간을 바꾸지 않습니다. 부모가 가진 포인터 숫자를 자식에게 전송했다고 그 주소의 객체를 모든 프로세스가 공유하는 것도 아닙니다. 통신에는 파이프·소켓·공유 매핑처럼 명시적인 수단이 필요합니다. 이 설계는 전달 형식과 동기화 비용을 추가하지만 잘못된 포인터 접근이 다른 프로세스의 메모리를 직접 손상시키는 범위를 줄일 수 있습니다.

프로세스를 나눴다고 파일 읽기 위치까지 자동으로 분리되는 것은 아닙니다. fork 전에 파일을 열고 그 fd를 자식들이 상속했다면 별도 fd 테이블이 같은 열린 파일 객체를 참조할 수 있습니다. 작업자가 같은 파일 위치를 변경하면서 읽는 설계인지, 각자 새로 열었는지, pread처럼 위치를 인자로 전달하는지에 따라 동작이 달라집니다. 주소 공간의 독립성과 열린 자원의 공유를 따로 그려 보세요.

이 장의 모델에서 작업자 수를 4로 놓고 프로세스와 스레드를 번갈아 고르면 task_struct는 둘 다 4개입니다. 달라지는 것은 주소 공간과 fd 테이블의 수입니다. 모델은 일반적인 생성 방식을 단순화해 비교하며 스택 메모리 크기나 실제 생성 시간은 측정하지 않습니다. 숫자만 보지 말고 각 task에서 어떤 공유 객체로 화살표가 이어지는지를 해석하는 것이 목적입니다.

실제 선택에서는 단순히 스레드가 빠르다는 문장으로 끝내지 않습니다. 공유 데이터의 양, 장애 격리 요구, 작업의 독립성, 통신 빈도, 언어 런타임의 실행 제약을 함께 봅니다. 여러 프로세스도 공유 메모리를 사용하면 데이터 복사를 줄일 수 있고, 여러 스레드도 전역 락 하나 때문에 사실상 직렬 실행될 수 있습니다. 실행 주체 수와 실제 병렬 진행 정도는 별개의 값입니다.

06

스택·TLS·레지스터가 서로 다른 상태인 이유

함수 호출을 중단했다가 나중에 이어 실행하려면 어느 명령을 실행하던 중이었는지와 계산 중인 값들을 보관해야 합니다. 각 task가 실행 레지스터 상태와 스택을 가지는 이유입니다. 한 스레드가 함수 A 안에서 기다리는 동안 다른 스레드는 함수 B를 실행할 수 있으므로 하나의 호출 스택으로 둘의 진행 상태를 표현할 수 없습니다. 사용자 스택과 커널 진입 후 사용하는 커널 스택의 역할도 구분합니다.

사용자 스택이 스레드별로 마련되어 있다는 말은 그 스택에 다른 스레드가 절대 접근할 수 없다는 말이 아닙니다. 일반적인 pthread들은 같은 주소 공간을 공유합니다. 스택의 객체 주소가 다른 스레드에 전달되면 그 스레드도 접근할 수 있습니다. 하지만 원래 함수가 반환해 객체의 수명이 끝난 뒤에도 주소를 사용하면 버그가 됩니다. 스레드 사이 포인터 전달에서 보호 경계와 객체 수명을 함께 생각해야 합니다.

TLS는 같은 변수 이름을 사용해도 스레드마다 별도의 저장 위치를 선택하도록 하는 장치입니다. 예를 들어 스레드별 오류 정보나 임시 상태를 보관할 때 공유 전역 변수의 경쟁을 줄일 수 있습니다. 그렇다고 TLS에 저장된 포인터가 가리키는 객체까지 자동으로 스레드 전용이 되는 것은 아닙니다. 두 TLS 슬롯에 같은 힙 객체의 주소를 넣으면 그 객체 자체는 여전히 공유될 수 있습니다.

커널 스택은 task가 시스템 콜 같은 경로를 수행할 때 필요한 호출 상태를 보관합니다. 사용자 스택과 혼동해 임의로 큰 데이터를 올려도 된다고 생각하면 안 됩니다. 커널 스택의 크기와 배치는 아키텍처·설정에 의존하며, 중첩 호출과 실행 문맥도 고려해야 합니다. 이 장에서는 크기 숫자를 외우기보다 task별 실행 상태가 공유 데이터 객체와 다른 수명을 가진다는 관계를 이해합니다.

프로세스가 같은 주소 공간을 공유하는지 확인하는 것과 특정 변수가 경쟁하는지 판단하는 것은 연결되지만 같지는 않습니다. 읽기만 하는 불변 객체는 공유해도 안전하게 설계할 수 있고, 수정 가능한 객체는 누가 언제 접근하는지에 따라 보호가 필요합니다. 이후 동기화 장에서는 데이터의 소유자와 접근 규칙을 먼저 정한 뒤 mutex나 atomic을 선택합니다. 실행 단위의 이름만으로 락이 필요한지 결정하지 않습니다.

07

PID가 같아 보여도 실행 중인 task는 여러 개다

다중 스레드 프로그램의 모든 스레드에서 getpid를 호출하면 보통 같은 프로세스 ID를 얻습니다. 이것은 스레드 그룹을 사용자에게 하나의 프로세스로 보여 주는 인터페이스입니다. 반면 gettid는 현재 실행 중인 개별 task를 구분합니다. 그룹 리더의 TID와 TGID는 같으므로 단일 스레드 프로그램만 관찰하면 두 식별자가 항상 같다고 착각하기 쉽습니다. 스레드가 여러 개일 때 관계가 드러납니다.

ps -L은 프로세스 안의 실행 단위를 펼쳐 보는 데 도움이 됩니다. PID와 TID 열을 함께 보면 같은 PID 아래 서로 다른 TID가 있는 형태를 확인할 수 있습니다. PSR은 관측 시점에 연결된 CPU 정보를 해석하는 단서이지 그 task가 영원히 고정될 CPU의 번호가 아닙니다. 실제 허용 CPU 집합은 affinity와 cpuset 같은 제약을 따로 확인해야 합니다.

/proc/PID/task의 하위 디렉터리는 해당 프로세스의 task를 탐색하는 출발점입니다. 스레드가 생성되거나 종료되는 동안 목록은 변할 수 있으므로 목록을 읽은 뒤 개별 경로를 열었을 때 이미 사라질 수도 있습니다. 조사 스크립트는 이런 수명 변화를 비정상적인 파일 손상으로 다루지 않아야 합니다. 스냅샷에서 보이지 않는 짧은 task는 이벤트 기반 추적이 더 적합할 수 있습니다.

컨테이너 안에서는 같은 task가 namespace에 따라 다른 PID로 보일 수 있습니다. 애플리케이션 로그에는 PID 12인데 호스트 도구에서는 훨씬 큰 숫자로 보이는 상황이 가능합니다. 숫자가 다르다고 즉시 다른 실행 주체라고 판단하지 말고 관측 위치를 기록합니다. namespace 관련 필드와 호스트·컨테이너의 프로세스 관계를 연결해야 같은 사건을 정확히 따라갈 수 있습니다.

이 장의 기본 명령은 현재 셸을 관찰하므로 하나의 task만 나와도 정상입니다. 여러 스레드 관계를 보고 싶다면 자신이 실행한 다중 스레드 프로그램을 대상으로 바꾸세요. 실행 결과를 미리 정해진 스레드 개수에 맞추려 하지 말고, 어떤 런타임이 작업 스레드·GC 스레드·타이머 스레드를 만들었는지 질문하는 것이 더 유용합니다. 라이브러리가 만든 실행 주체도 스케줄러 입장에서는 CPU와 자원을 사용하는 task입니다.

ps -L -p $$ -o pid,tid,tgid,stat,psr,comm
ls /proc/$$/task
grep -E "^(Name|Pid|Tgid|Threads|NSpid):" /proc/$$/status
08

공유 객체의 마지막 참조와 종료 순서

네 스레드가 같은 주소 공간을 사용하다 한 스레드만 종료했다고 합시다. 남은 스레드는 그 주소 공간에서 계속 실행해야 하므로 종료한 스레드가 공유 메모리를 전부 없애서는 안 됩니다. 공유 객체의 수명은 한 task의 수명보다 길 수 있습니다. 커널에서 참조를 얻고 놓는 코드가 반복해서 나타나는 이유는 이처럼 여러 소유자가 같은 객체의 생존에 관여하기 때문입니다.

열린 파일도 fd 숫자만으로 수명을 판단하면 안 됩니다. 한 task가 자신의 테이블에서 fd를 닫아도 다른 참조가 남아 있으면 열린 파일 객체는 유지될 수 있습니다. 반대로 스레드끼리 같은 fd 테이블을 공유하는 일반적인 구성에서는 한 스레드의 close가 다른 스레드의 이후 fd 사용에 영향을 줄 수 있습니다. fd 숫자가 재사용되면 오래 저장해 둔 숫자가 다른 자원을 가리키는 문제도 생각해야 합니다.

실행 종료와 사용자 런타임 정리는 서로 연결되지만 같은 단계가 아닙니다. 언어 런타임은 버퍼를 비우거나 종료 훅을 실행할 수 있고, 저수준 커널 종료 경로는 실행 주체와 자원을 정리합니다. 개별 스레드만 끝내는 API인지 스레드 그룹 전체를 끝내는 API인지에 따라 공유 객체의 남은 참조도 달라집니다. 이름이 비슷한 종료 함수의 범위를 설명 없이 서로 바꾸어 쓰면 안 됩니다.

장애 사례에서 한 worker가 오래 기다리는데 나머지도 진행하지 못한다면, 스케줄러가 프로세스 전체를 재웠다고 추정하기 전에 의존 관계를 그려 보세요. 첫 worker가 전역 락을 가진 채 I/O를 기다리고 나머지가 그 락을 기다릴 수 있습니다. 이 경우 각각의 task는 독립적으로 잠들었지만 응용 프로그램의 자원 의존성이 전체 정지처럼 보이게 만듭니다. 실행 상태와 공유 자원 소유자를 함께 관측해야 합니다.

소스 탐색에서는 task_struct의 포인터 필드를 찾은 뒤 kernel/fork.c의 복제·공유 선택과 종료 경로의 해제를 연결합니다. 처음부터 전체 필드를 외우기보다 mm과 files 같은 두 객체만 골라 누가 참조하는지 그리세요. 생성 때 복사한 것, 같은 객체를 공유한 것, 마지막 참조가 사라질 때 해제되는 것을 구분하면 프로세스와 스레드라는 이름 뒤의 실제 상태 구조가 보입니다.
