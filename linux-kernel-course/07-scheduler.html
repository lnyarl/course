01

CPU를 기다리는 task

실행할 준비가 된 task라도 CPU에서 즉시 실행되는 것은 아닙니다. CPU보다 runnable task가 많으면 실행 큐에서 차례를 기다려야 합니다. I/O 결과를 기다려 잠든 task는 CPU 배분 후보와 상태가 다르므로 모든 task 수를 CPU 경합의 크기로 볼 수 없습니다.

스케줄러는 CPU별 실행 큐와 여러 스케줄링 클래스를 관리합니다. 일반 작업, 실시간 정책, deadline 정책을 하나의 동일한 알고리즘으로 처리하지 않습니다. 이 장의 EEVDF 모델은 일반적인 fair 클래스의 선택 원리를 설명하는 제한된 모델입니다.

CPU 사용률이 낮아도 응답이 느릴 수 있습니다. 작업이 I/O를 기다리거나, CPU affinity 때문에 특정 CPU만 사용하거나, cgroup의 quota에 의해 잠시 실행이 제한될 수 있기 때문입니다. 먼저 실행 가능한지와 실행할 자격이 있는지를 구분합니다.

02

CFS에서 EEVDF로 이어지는 원리

CFS의 핵심 배경은 실제 실행 시간을 가중치에 맞게 가상 시간으로 환산해 공정한 CPU 배분을 추구하는 것입니다. EEVDF 역시 공정성을 유지하면서 작업이 받아야 할 서비스와 실제 받은 서비스의 차이를 고려합니다. 과거 구현의 자료구조 설명을 그대로 최신 선택 규칙으로 쓰지 않습니다.

EEVDF에서는 서비스가 모자란 작업의 eligibility를 판단하고, 자격 있는 후보 중 가상 deadline이 이른 작업을 고릅니다. 이 deadline은 애플리케이션이 약속한 벽시계 마감 시각이 아닙니다. 가중치와 요청한 실행 구간을 반영하는 스케줄링 내부의 비교 기준입니다.

짧은 실행 구간이 필요한 작업에 더 이른 선택 기회를 주는 것과 무조건 높은 우선순위로 모든 작업을 선점하는 것은 다릅니다. 실제 구현에는 선점 판단과 잠든 작업 처리 등 추가 조건이 있습니다. 애니메이션의 단순 후보 선택을 전체 커널 알고리즘과 동일시하지 않습니다.

03

nice, affinity, quota

nice는 일반 스케줄링 클래스에서 경합하는 작업의 상대적 가중치에 영향을 줍니다. CPU가 비어 있다면 낮은 가중치의 작업도 CPU를 사용할 수 있습니다. nice 값을 특정 CPU 사용률 상한이나 고정 응답 시간 보장으로 해석하면 안 됩니다.

affinity는 task가 실행될 수 있는 CPU 집합을 제한합니다. 캐시 지역성을 유지하는 데 도움이 될 수 있지만 허용 CPU에 작업이 몰리면 다른 CPU가 남아도 기다릴 수 있습니다. CPU 번호를 고정하기 전에 현재 허용 집합과 컨테이너 cpuset을 확인해야 합니다.

cgroup CPU quota는 정해진 기간 동안 사용할 수 있는 실행 시간 예산을 제한합니다. 예산을 소진하면 runnable 상태의 작업도 throttling으로 실행 기회를 잃을 수 있습니다. 낮은 CPU 평균 사용률과 높은 지연이 함께 나타나는 경우 quota 사용과 제한 횟수를 확인합니다.

04

관측으로 대기 원인 분리

프로세스의 사용자 시간과 시스템 시간은 CPU에서 소비한 시간을 나타냅니다. 실제 경과 시간에는 CPU 대기와 I/O 대기도 포함됩니다. 경과 시간이 긴데 CPU 시간이 짧다면 곧바로 더 빠른 CPU를 제안하기보다 대기 원인을 조사합니다.

문맥 교환 수가 많다는 사실만으로 문제라고 판단하지 않습니다. 작업을 짧게 나누어 서로 깨우는 서비스는 자연스럽게 교환이 많을 수 있습니다. 중요한 것은 불필요한 교환이 처리량이나 지연에 미치는 영향과 다른 병목의 존재입니다.

부하 평균은 단순 CPU 사용률과 다른 지표이며 Linux에서는 특정 대기 상태도 영향을 줍니다. CPU 경합을 판정하려면 runnable 수, 스케줄링 지연, affinity, cgroup 상태를 함께 봅니다. 지표 하나를 원인과 일대일로 대응시키지 않습니다.

05

동일한 task 수라도 CPU 경합은 달라진다

CPU가 두 개이고 task가 네 개 있다고 합시다. 네 task가 모두 계산을 계속하려면 어느 순간에도 두 task만 실행하고 나머지는 실행 기회를 기다려야 합니다. 반대로 두 task가 I/O 결과를 기다려 잠들어 있다면 실행 가능한 두 task만 CPU를 쓰면 됩니다. 전체 프로세스 개수나 스레드 개수보다 runnable 상태의 수가 CPU 경합을 설명하는 데 더 직접적인 이유입니다.

스케줄러가 관리하는 상태는 단순한 전역 줄 하나가 아닙니다. CPU별 실행 큐와 task가 실행될 수 있는 CPU 집합이 있으며, 여러 CPU 사이에 부하를 나누는 과정도 필요합니다. 모든 task가 특정 CPU 하나에만 허용되어 있다면 다른 CPU가 비어 있어도 그 task들은 한 곳에서 경쟁할 수 있습니다. 시스템 전체 평균 CPU 사용률만 보면 이런 국소적인 경합을 놓칠 수 있습니다.

실행 중인 task가 잠들거나 선점되거나 실행을 끝내면 다음 실행 대상을 정해야 합니다. 이 선택에는 스케줄링 클래스의 정책과 task의 상태가 함께 작용합니다. 일반적인 fair 작업의 선택 원리를 배우는 장면에서 실시간 정책이나 deadline 정책까지 모두 같은 규칙으로 돌아간다고 생각하면 안 됩니다. 커널의 공통 선택 틀과 각 클래스 내부의 결정을 나누어 읽습니다.

작업을 여러 스레드로 나누면 병렬 실행 가능성이 생기지만 자동으로 CPU 수만큼 빨라지는 것은 아닙니다. 공유 락 때문에 한 스레드만 진행하거나, 메모리 대역폭과 캐시 경쟁이 커지거나, 작업을 너무 잘게 나눠 깨우기와 문맥 교환이 늘 수 있습니다. 스케줄러가 잘 배분해도 응용 프로그램에 독립적으로 진행할 일이 없다면 병렬성은 제한됩니다.

따라서 느린 프로그램을 보면 먼저 원하는 실행량과 실제 실행량의 차이를 찾습니다. CPU를 원하지만 못 받는다면 실행 큐와 정책을 보고, CPU를 받았는데 처리량이 낮다면 실행 스택과 메모리 접근 등을 봅니다. CPU를 원하지 못하고 I/O나 락을 기다린다면 다른 경로를 조사합니다. 모두 느리다는 같은 증상으로 나타날 수 있지만 확인할 증거가 다릅니다.

06

EEVDF를 작은 숫자로 읽기: lag와 가상 deadline

공정성을 직관적으로 생각하면 각 task가 받아야 할 CPU 서비스와 실제 받은 서비스를 비교할 수 있습니다. 아직 받아야 할 몫이 남은 후보와 이미 앞서 받은 후보를 구분하는 것입니다. 이 장의 한 번의 선택 모델에서는 A의 lag를 조절하고 B의 lag는 반대 부호로 둡니다. 같은 가중치의 두 후보를 비교하는 개념 예제이며 전체 실행 이력과 계층 스케줄링을 재현하지 않습니다.

A의 lag가 +2이고 B가 −2라면 모델은 A에 자격이 있다고 봅니다. A의 가상 deadline을 바꾸더라도 먼저 자격을 확인한다는 원칙이 중요합니다. 반대로 A의 lag가 −2일 때 A의 deadline을 아주 작게 만들어도 그 이유만으로 A가 선택되는 것은 아닙니다. 이 경우 B가 실행 후보가 됩니다. deadline이라는 단어가 보인다고 무조건 가장 작은 숫자만 고르는 알고리즘으로 읽으면 안 됩니다.

두 lag를 모두 0으로 놓으면 모델에서 두 후보가 자격을 갖습니다. 이제 A의 가상 deadline을 6으로 두고 B의 고정값 10과 비교하면 A를 선택하고, A를 15로 바꾸면 B를 선택합니다. 이 두 조작은 자격 판정과 후보 사이 순서 결정을 분리해 보여 줍니다. 막대가 나타내는 것은 내부 비교값이지 사용자가 체감하는 완료 시간이나 실제 밀리초가 아닙니다.

가상 deadline은 요청한 실행 구간과 가중치를 반영하는 내부 기준입니다. 짧은 실행 구간을 원하는 작업의 응답성을 고려하면서 공정성을 유지하려는 목적이 있습니다. 그러나 실제 Linux에는 잠든 작업의 lag 처리, 선점 판단, 실행 중인 후보와의 비교처럼 추가 상태가 있습니다. 두 슬라이더의 결과만으로 실제 서버에서 다음에 실행될 TID를 예측할 수 있다고 생각하지 않습니다.

예전 CFS 설명에서 배운 가상 실행 시간과 공정성은 배경 지식으로 유용합니다. 다만 과거의 특정 자료구조에서 가장 작은 항목을 고르는 그림을 현재 EEVDF의 모든 결정이라고 그대로 쓰면 자격과 deadline의 역할을 놓칩니다. v6.18의 kernel/sched/fair.c를 읽을 때는 이름만 찾기보다 어떤 값으로 자격을 계산하고 어떤 후보 집합에서 비교하는지 질문을 정하세요.

07

nice·affinity·quota는 서로 대체할 수 없다

같은 CPU에서 두 일반 작업이 계속 경합할 때 nice는 상대적인 배분 가중치에 영향을 줍니다. 가중치가 낮은 작업은 경쟁자가 있을 때 더 적은 몫을 받을 수 있지만 경쟁자가 없으면 CPU를 사용할 수 있습니다. 그래서 nice를 특정 값으로 바꾸었다고 CPU 사용률이 항상 어떤 백분율 아래로 제한된다고 말할 수 없습니다. nice 숫자의 차이와 서비스 비율도 단순한 선형 관계로 읽지 않습니다.

affinity는 어느 CPU에서 실행할 수 있는지 정하는 제약입니다. 한 CPU로 묶으면 캐시 지역성과 실행 위치를 통제하는 데 도움이 될 수 있지만, 그 CPU에 경쟁 작업이 많으면 다른 CPU가 남아도 기다립니다. 실제 허용 집합에는 cpuset과 시스템 구성도 영향을 줄 수 있으므로 taskset 출력과 컨테이너 환경을 함께 봅니다. CPU 번호 하나를 고정하는 변화는 성능 개선이 아니라 실행 가능 범위를 바꾸는 행동입니다.

CPU quota는 정해진 기간의 총 CPU 시간 예산입니다. 두 CPU에서 동시에 25 ms씩 실행했다면 합계 50 CPU-ms를 소비합니다. 따라서 100 ms 기간에 50 CPU-ms 예산을 가진 cgroup은 단순한 병렬 부하에서 초반에 예산을 소진하고 남은 기간에 제한될 수 있습니다. 장기간 평균 사용률이 낮아도 짧은 요청에는 지연이 나타날 수 있는 이유입니다. 실제 구간 분배는 커널의 bandwidth 관리와 계층 제약을 따릅니다.

세 제어를 섞어 쓰면 진단도 복잡해집니다. 낮은 가중치, 좁은 CPU 집합, 작은 예산이 동시에 적용된 작업은 다른 조건을 바꾸지 않고 한 숫자만 보아 원인을 확정하기 어렵습니다. 먼저 현재 정책과 허용 CPU, cgroup 제약을 읽고 어떤 제한이 실제로 발동했는지 확인합니다. 설정 파일에 값이 있다는 사실과 그 제한이 현재 지연을 만들었다는 증거는 다릅니다.

이 장의 실습은 정책을 읽는 데서 멈춥니다. 실시간 우선순위를 높이거나 특정 CPU를 강제로 점유하는 변화 없이도 현재 작업의 제약을 배울 수 있습니다. 나중에 설정을 바꿔 비교할 때는 별도 VM에서 하나의 변수를 바꾸고 처리량과 지연을 함께 기록하세요. 변경 후 CPU 사용률이 높아졌다는 것만으로 사용자가 체감하는 결과까지 좋아졌다고 판단하지 않습니다.

실행 시간과 기다린 시간을 분리한 조사 사례

한 요청의 경과 시간이 100 ms인데 사용자·시스템 CPU 시간의 합은 10 ms인 가상 사례를 생각해 봅시다. 이 정보는 CPU에서 실제로 계산한 시간보다 나머지 시간이 크다는 단서를 줍니다. 그러나 남은 90 ms가 전부 스케줄러 대기라는 결론은 아직 아닙니다. I/O·락·타이머 대기도 포함될 수 있으므로 runnable이었던 구간과 잠들었던 구간을 구분하는 관측이 필요합니다.

현재 셸의 chrt -p와 taskset -pc 출력은 정책과 CPU 집합을 확인하는 출발점입니다. 이것은 실행 이력 전체를 보여 주는 측정은 아닙니다. vmstat의 runnable 관련 값은 시스템 전체 관점의 단서이고, 특정 요청의 대기 시간을 직접 보여 주지는 않습니다. 첫 행과 뒤의 구간별 행이 같은 집계 범위를 가진다고 가정하지 말고 도구의 의미를 확인합니다.

문맥 교환 누적값을 보면 자발적 교환과 비자발적 교환을 구분할 수 있습니다. 하지만 횟수가 많다는 이유만으로 과도한 교환이 성능 문제라고 확정하지는 않습니다. 대화형 프로그램이나 짧은 작업을 주고받는 서버는 정상적으로 자주 잠들고 깨어날 수 있습니다. 교환이 늘어난 시각에 지연과 CPU 소비가 어떻게 바뀌었는지, 불필요한 작업 분할이 있는지 추가로 확인합니다.

스케줄링 지연을 더 직접적으로 보려면 wakeup 이후 실행 시작까지의 이벤트를 연결하는 방식이 도움이 됩니다. 언제 runnable이 되었는지와 언제 CPU를 얻었는지를 분리하면 I/O 완료가 늦은 것인지 완료 후 배정이 늦은 것인지 나눌 수 있습니다. 관측 자체가 오버헤드를 만들 수 있으므로 대상과 시간을 제한하고, 실제 요청의 지연과 같은 시간 축에서 비교해야 합니다.

개선도 가설에 맞춰 선택합니다. runnable 경합이 확인되었다면 CPU 배분과 작업 수를 살펴보고, quota 제한이 확인되었다면 실제 예산과 사용 패턴을 검토합니다. 실행 중 계산이 비싸다면 함수와 알고리즘을 봅니다. I/O를 기다리는 문제에 스케줄러 정책만 바꾸는 식으로 다른 계층을 건드리면 효과가 없거나 새로운 불공정성을 만들 수 있습니다. 관측한 구간과 변경할 원인을 연결하는 것이 핵심입니다.
