01

특권과 실행 모드

사용자 프로그램이 CPU에서 실행된다고 해서 모든 명령을 실행할 권한을 갖는 것은 아닙니다. 페이지 테이블이나 장치 제어처럼 시스템 전체에 영향을 주는 동작은 보호됩니다. x86-64의 사용자/커널 권한 수준과 arm64의 예외 수준은 표현이 다르지만 통제된 진입 경계를 만든다는 목적이 같습니다.

시스템 콜은 사용자 프로그램이 커널에 서비스를 요청하는 약속입니다. 함수 인자 전달 규칙과 시스템 콜 ABI는 구별되며, libc의 래퍼 함수가 인자를 ABI에 맞게 준비할 수 있습니다. 커널은 호출 번호와 인자를 받아 해당 동작을 수행하고 결과를 반환합니다.

일반 함수 호출은 같은 권한으로 다른 코드 위치를 실행합니다. 시스템 콜은 권한 경계와 진입·복귀 처리 비용을 동반합니다. 그렇다고 모든 시스템 콜이 느리거나 디스크를 기다리는 것은 아닙니다. 짧은 검사만으로 바로 복귀하는 경로도 있습니다.

02

진입과 복귀에 필요한 일

커널 진입 코드는 돌아갈 위치와 레지스터 상태를 보존하고 올바른 커널 실행 상태를 구성해야 합니다. 이때 추적, RCU 상태, 시간 회계와 보안 검사도 고려합니다. 처음 몇 명령부터 아무 추적 함수를 호출하면 안 되는 이유는 필요한 상태가 아직 준비되지 않았기 때문입니다.

요청 인자에 사용자 주소가 들어 있으면 커널은 그 주소를 무조건 역참조하지 않습니다. 범위나 접근 가능성을 검사하고 안전한 사용자 메모리 접근 도우미를 사용합니다. 요청 중에도 매핑이 바뀌거나 fault가 발생할 수 있으므로 검사 한 번으로 모든 접근이 보장되는 것은 아닙니다.

복귀는 단순한 return과 다릅니다. 보류된 시그널이나 재스케줄 필요 여부처럼 사용자 공간으로 나가기 전에 처리할 작업이 있을 수 있습니다. 실제 경로와 비용은 아키텍처, 보안 완화 설정, 추적 도구 활성화 여부에도 영향을 받습니다.

03

모드 전환과 문맥 교환

한 task가 read를 호출했다가 즉시 돌아오면 사용자 모드와 커널 모드를 오가지만 계속 같은 task일 수 있습니다. 이것이 모드 전환입니다. 시스템 콜 수를 곧바로 task 간 문맥 교환 수로 해석하면 실행 흐름을 잘못 읽게 됩니다.

읽을 데이터가 없어 task가 잠들면 스케줄러가 다른 runnable task를 선택할 수 있습니다. 이때 실행 레지스터와 커널 스택 등 실행 상태를 바꾸는 문맥 교환이 발생합니다. 주소 공간이 다른 task로 바뀌는 경우와 같은 주소 공간을 공유하는 스레드로 바뀌는 경우의 비용도 같지 않습니다.

반대로 시스템 콜을 호출하지 않은 계산 중에도 타이머나 다른 이벤트를 계기로 선점될 수 있습니다. 따라서 사용자 코드에 시스템 콜이 보이지 않는다는 이유로 문맥 교환이 없다고 결론 내리지 않습니다. CPU 시간과 벽시계 시간을 함께 보아야 합니다.

04

시스템 콜 없이 커널의 도움을 받는 경우

시계 읽기처럼 자주 필요한 일부 기능은 vDSO를 통해 사용자 공간에서 처리할 수 있습니다. 커널이 제공한 코드와 공유 데이터를 이용하되 지원되는 경우 실제 시스템 콜 진입을 피합니다. 동일한 라이브러리 API라도 플랫폼과 조건에 따라 경로가 달라질 수 있습니다.

페이지 폴트는 명시적인 함수 호출 없이도 커널에 진입하는 예입니다. 아직 물리 페이지가 준비되지 않은 주소에 접근하면 CPU가 예외를 발생시키고 커널이 매핑을 준비할 수 있습니다. 해결 가능한 fault는 정상 실행의 일부이며 곧바로 프로그램 오류를 뜻하지 않습니다.

strace는 시스템 콜 관찰에 유용하지만 사용자 공간 함수 전체를 보여 주지 않습니다. vDSO 경로는 출력에 나타나지 않을 수 있고 추적 자체가 시간을 늘릴 수 있습니다. 호출 경로를 확인하는 실험과 순수 성능 측정은 목적을 분리합니다.

05

한 번의 write를 바이트와 반환값으로 따라가기

사용자 코드가 write(fd, buf, 5)를 호출하는 상황을 생각해 봅시다. fd는 열린 대상, buf는 프로세스의 가상 주소, 5는 요청할 바이트 수입니다. 이 세 값만으로 모든 일이 보장되지는 않습니다. fd가 닫혔을 수 있고, buf가 읽을 수 없는 주소일 수 있으며, 대상이 그 순간 5바이트를 모두 받아들이지 못할 수 있습니다. 커널 인터페이스는 요청을 받는 것과 요청을 성공적으로 완료하는 것을 구분합니다.

libc의 일반적인 write 래퍼는 아키텍처 ABI에 맞게 번호와 인자를 준비하고 커널 진입 명령을 실행합니다. x86-64의 시스템 콜 레지스터 배치와 C 함수 호출의 인자 규칙은 완전히 같은 것으로 취급하면 안 됩니다. 이 강좌에서는 번호를 외우기보다 ABI가 사용자 코드와 커널 사이의 약속이라는 사실을 기억합니다. 다른 아키텍처에서는 같은 write 의미를 다른 진입 규칙으로 전달할 수 있습니다.

커널은 현재 task의 fd 테이블에서 대상을 찾고, 요청 크기와 사용자 메모리 접근을 포함한 여러 조건을 확인해 해당 파일 연산 경로로 전달합니다. 여기서 파일이라는 말에는 일반 파일뿐 아니라 파이프와 소켓 같은 대상도 연결될 수 있습니다. 같은 함수 형태가 서로 다른 내부 처리를 호출하는 것입니다. 실제 바이트가 어느 순간 복사되거나 장치에 전달되는지는 대상과 I/O 방식에 따라 달라집니다.

반환값 5는 이 호출이 5바이트를 처리했다는 API 수준의 결과입니다. 일반 파일에 대한 write 성공이 전원 손실 이후의 영구 보관까지 뜻하지는 않습니다. 반대로 반환값이 3이면 남은 2바이트를 어떻게 처리할지 프로그램이 결정해야 합니다. 오류 때 libc가 -1과 errno를 제공하는 계약도 커널 내부의 원시 반환 표현과 구분해야 합니다. 성공, 부분 성공, 실패를 모두 처리하는 코드가 인터페이스를 올바르게 사용하는 코드입니다.

그래서 시스템 콜을 이해할 때는 함수 이름 다음에 입력의 소유자, 변경 가능한 상태, 반환값의 의미, 실패 경로를 읽습니다. write를 불렀다는 한 줄만으로 장치 쓰기 횟수나 영구 저장 여부를 알 수 없고, read를 불렀다는 한 줄만으로 실제 디스크 접근을 알 수 없습니다. 내부 경로를 보는 이유는 바로 이런 API 계약과 하드웨어 동작 사이의 간격을 설명하기 위해서입니다.

06

사용자 포인터는 왜 평범한 커널 포인터가 아닐까

포인터의 숫자만 보고 어느 메모리인지 판단할 수는 없습니다. 사용자 포인터는 현재 프로세스의 가상 주소 공간을 기준으로 해석되며, 커널의 유효한 내부 객체를 가리킨다는 보장이 없습니다. 잘못된 주소뿐 아니라 유효한 주소의 경계에 걸쳐 있는 버퍼도 생각해야 합니다. 첫 페이지는 읽을 수 있지만 다음 페이지는 매핑되지 않은 8 KiB 버퍼를 넘길 수도 있습니다.

커널이 사용자 버퍼를 직접 믿고 일반 메모리처럼 읽으면 공격적인 입력이나 단순한 프로그램 버그가 커널 실행에 영향을 줍니다. 따라서 copy_from_user 같은 사용자 메모리 접근 도우미와 오류 경로가 필요합니다. 도우미를 쓴다고 요청 전체가 항상 성공하는 것은 아닙니다. 접근 실패를 호출자가 처리해야 하며, 반환값이 일반적인 성공 바이트 수인지 복사하지 못한 바이트 수인지도 각 API 계약을 확인해야 합니다.

주소 범위를 먼저 검사한 뒤 나중에 접근하는 두 동작 사이에도 상태는 바뀔 수 있습니다. 같은 프로세스의 다른 스레드가 매핑을 바꾸거나 버퍼 내용을 수정할 수 있기 때문입니다. 검사를 통과한 값을 여러 번 다시 읽으면서 서로 일치할 것이라고 가정하면 일관성 문제가 생길 수 있습니다. 어떤 입력은 커널 소유의 복사본으로 가져와 검증하고 그 복사본만 사용하도록 설계해야 합니다.

사용자 메모리에 접근하는 동안 page fault가 발생할 수도 있습니다. 이 경우 접근이 허용된 주소라면 페이지를 준비하는 경로가 필요할 수 있고, 그 과정에서 대기가 가능한지도 실행 문맥에 따라 따져야 합니다. 그래서 커널 코드를 읽을 때 포인터 타입 하나만 보는 대신 현재 어떤 락을 잡고 있는지, 이 경로가 잠들어도 되는지, 오류를 어떻게 되돌리는지를 함께 확인합니다.

초보자가 실수하기 쉬운 부분은 사용자 메모리 접근을 단순한 memcpy 비용으로만 생각하는 것입니다. 복사할 바이트가 적어도 권한 경계와 fault 처리의 의미는 남습니다. 반대로 크기가 크다고 매번 모든 페이지를 새로 할당하는 것도 아닙니다. 메모리 관리 장에서 다룰 주소 공간과 페이지의 상태가 시스템 콜의 실제 경로를 바꾼다는 점을 여기서 연결해 두세요.

07

시간선으로 비교하는 즉시 반환과 대기

같은 task A가 read를 네 번 호출한다고 합시다. 첫 사례에서는 네 번 모두 필요한 데이터가 준비되어 있어 A가 커널에서 처리한 뒤 바로 사용자 공간으로 돌아옵니다. 이 단순 시간선에는 사용자→커널→사용자 전환이 네 쌍 있지만 A에서 다른 task로 넘어가는 장면은 없습니다. 모드 전환 횟수와 문맥 교환 횟수가 서로 다른 숫자임을 가장 작게 보여 주는 사례입니다.

두 번째 사례에서는 매번 데이터가 준비되지 않아 A가 잠들고 B가 실행됩니다. 이후 I/O 완료가 A를 runnable로 만들고, 나중에 스케줄러가 A를 선택하면 중단되었던 커널 경로를 이어서 실행한 뒤 사용자 공간으로 복귀합니다. 실험은 한 번의 대기마다 A→B와 B→A 두 문맥 교환이 있다고 가정합니다. 실제로는 그 사이 다른 task가 여러 번 실행되거나 CPU가 idle에 들어갈 수 있습니다.

잠든 시간은 A의 사용자 코드가 실행한 시간도, A의 커널 코드가 계속 계산한 시간도 아닙니다. 이 차이 때문에 시스템 콜의 경과 시간이 길다고 커널이 그 시간 내내 CPU를 소비했다고 결론 내리면 안 됩니다. CPU 사용량이 낮은데 요청이 느린 상황은 모순이 아닙니다. 필요한 이벤트, 락, 자원 예산 또는 CPU 배정을 기다리는 시간이 길 수 있습니다.

문맥 교환에는 실행 상태를 바꾸는 직접 비용뿐 아니라 새 작업이 CPU 캐시와 주소 변환 캐시를 다시 채우는 간접 영향도 있을 수 있습니다. 그러나 모든 교환이 동일한 비용이라고 단정할 수는 없습니다. 같은 주소 공간의 스레드인지, 다른 프로세스인지, 같은 CPU로 돌아오는지, 어떤 작업 집합을 사용하는지에 따라 상황이 달라집니다. 실험의 문맥 교환 개수는 시간 측정값으로 환산하지 않습니다.

반대로 사용자 공간에서 계속 계산하는 코드도 타이머 이벤트와 스케줄링 정책에 의해 선점될 수 있습니다. 호출을 줄이는 개선이 문맥 교환을 모두 없애는 것은 아닙니다. 실험에서 즉시 반환을 고른 뒤에는 실제 시스템에서 선점·시그널·동시 작업이라는 생략한 조건을 떠올려 보세요. 단순 모델이 성립하는 범위를 아는 것이 복잡한 실행 기록을 읽는 첫 단계입니다.

08

관측 사례: strace에 보이는 호출과 보이지 않는 계산

Linux VM에서 strace -e trace=openat,read,write,close /bin/cat /proc/version을 실행하면 선택한 시스템 콜 경계만 볼 수 있습니다. 화면에 출력할 내용과 추적 로그가 서로 다른 출력 스트림에 섞여 보일 수 있다는 점도 확인하세요. 프로그램 시작에는 동적 로더와 라이브러리 초기화가 포함될 수 있으므로 첫 openat을 곧바로 /proc/version을 여는 호출이라고 가정하지 말고 실제 경로 인자를 읽습니다.

각 행에서는 이름뿐 아니라 fd와 버퍼 길이, 반환값을 함께 읽습니다. read의 반환값 0은 해당 읽기 대상의 EOF 의미를 가질 수 있으며 일반적인 오류 코드와 다릅니다. openat이 성공한 결과로 얻은 fd가 이후 read와 close에 이어지는지 연결하면 프로세스가 어떤 자원을 획득하고 반환했는지 작은 수명선을 만들 수 있습니다. 전체 커널 스택을 알지 못해도 인터페이스 수준의 흐름을 재구성할 수 있습니다.

clock_gettime 같은 라이브러리 호출은 지원되는 환경에서 vDSO를 이용할 수 있습니다. 그 경우 프로그램은 시각을 얻었어도 일반적인 시스템 콜 진입이 없으므로 strace 목록에 같은 이름이 나타나지 않을 수 있습니다. 목록에 없다는 관측으로 함수가 호출되지 않았다고 결론 내리기 전에, 도구가 추적하는 경계가 사용자 함수인지 시스템 콜인지 구분해야 합니다.

페이지 폴트나 외부 장치 인터럽트도 프로그램의 명시적인 시스템 콜 호출 목록과 같은 것으로 읽지 않습니다. 사용자 코드가 처음 접근한 유효한 메모리 때문에 커널이 개입할 수 있고, CPU에서 실행 중인 코드와 무관한 장치 이벤트가 들어올 수도 있습니다. 따라서 strace는 유용한 관찰 창이지만 커널의 모든 실행을 보여 주는 녹화 장치가 아닙니다. 다른 질문에는 fault 카운터나 이벤트 추적이 필요합니다.

마지막으로 추적을 켠 실행과 끈 실행은 같은 측정 조건이 아닙니다. 시스템 콜마다 관측 장치가 개입하면 실행 시점과 지연이 달라질 수 있습니다. 먼저 추적으로 호출의 종류와 실패 여부를 확인하고, 성능을 비교할 때는 같은 입력·환경에서 추적을 끈 측정도 별도로 수행하세요. 이 강좌의 예상 출력은 해석 방향을 설명하는 것이며 여기서 실제 VM 실행 결과를 제공하는 것은 아닙니다.

strace -e trace=openat,read,write,close /bin/cat /proc/version
strace -c /bin/true
