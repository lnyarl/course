01

사용자 malloc과 커널 할당은 다른 층

사용자 공간의 malloc은 libc가 객체용 공간을 관리하는 API입니다. 커널 내부의 kmalloc·kmem_cache_alloc·alloc_pages·vmalloc은 커널 코드가 필요한 메모리를 얻는 별도 인터페이스입니다. 이름에 alloc이 들어 있다는 공통점보다 어떤 주소를 반환하고 어떤 실행 문맥에서 호출할 수 있는지가 중요합니다.

커널은 파일과 task, 네트워크 패킷과 장치 요청을 표현하는 수많은 작은 객체를 만듭니다. 매번 최소 페이지 단위로만 할당하면 작은 객체에서 낭비가 큽니다. 반대로 물리 페이지 자체나 큰 버퍼가 필요한 경로도 있으므로 하나의 할당 API가 모든 요구에 가장 적합할 수는 없습니다.

이 장에서는 물리 페이지를 관리하는 기반과 그 위에서 객체를 효율적으로 나누는 층을 분리합니다. “커널 heap” 하나가 모든 메모리를 같은 방식으로 처리한다고 생각하지 않습니다. 크기, 연속성, 정렬, 장치 접근, 회수 가능성, 실패 처리라는 질문이 API 선택을 결정합니다.

할당 성공 이후의 사용 수명도 설계의 일부입니다. 어디서 할당하고 누가 마지막으로 해제하는지, 다른 CPU나 장치가 아직 참조하는지를 알아야 합니다. 메모리를 얻는 코드 몇 줄만 보고 안전성을 판정하면 비동기 완료나 오류 정리 경로의 use-after-free를 놓칠 수 있습니다.

02

node·zone·page의 지도

물리 메모리는 플랫폼의 NUMA node와 zone 같은 관리 구분 아래 다뤄집니다. NUMA node는 접근 거리와 메모리 위치를, zone은 주소 제한 등 할당 조건과 관련된 구분을 표현합니다. 모든 머신이 동일한 zone 조합이나 여러 node를 갖는 것은 아닙니다.

기본 페이지는 물리 메모리 관리의 중요한 단위입니다. 페이지 크기는 아키텍처와 설정에 의존하므로 4KiB를 모든 Linux 시스템의 불변값으로 외우지 않습니다. 이 강좌의 수치 예시가 4KiB를 사용할 때는 가정이라고 표시하고 실습에서는 getconf PAGESIZE로 확인합니다.

커널 내부에서 페이지를 설명하는 메타데이터와 실제 데이터 페이지는 같은 것이 아닙니다. struct page나 folio 관련 포인터를 읽을 때 메타데이터 객체를 데이터 버퍼 자체로 취급하지 않습니다. 어떤 API가 메타데이터를 돌려주는지, 어떤 API가 접근 가능한 가상 주소를 주는지 확인합니다.

여유 메모리가 충분해 보이는데 할당이 실패할 수 있는 이유도 여기 있습니다. 요청이 특정 node나 zone, 물리 연속 범위 또는 실행 문맥 제약을 요구하면 시스템 전체 free 합계가 충분해도 적합한 메모리가 없을 수 있습니다. 합계 바이트만으로 모든 요청 가능성을 판단하지 않습니다.

03

Buddy: 크기별 블록과 분할

Buddy 기반 페이지 할당은 2의 거듭제곱 개수로 이루어진 물리 연속 페이지 블록을 관리하는 핵심 원리를 사용합니다. order가 n이면 2의 n제곱 개 페이지를 요청하는 형태입니다. 기본 페이지가 4KiB라는 예시에서 order 0은 4KiB, order 2는 16KiB가 됩니다.

필요한 크기의 빈 블록이 없으면 더 큰 블록을 둘로 나누어 적절한 크기를 만들 수 있습니다. 해제할 때는 같은 크기의 올바른 buddy가 비어 있고 병합 조건을 만족하면 더 큰 블록으로 합칠 수 있습니다. 단순히 주소가 인접했다는 이유만으로 어떤 두 블록이나 합치는 것은 아닙니다.

실제 커널은 CPU별 캐시, 이동 가능성 분류와 여러 최적화를 함께 사용합니다. 현재 브라우저는 트리나 개별 분할 조작 대신 요청 크기·최대 빈 블록과 결과 막대를 표시합니다. 이 비교로 연속성 제약을 이해하고 분할·병합은 본문의 사고실험으로 살펴봅니다. 실제 코드에서는 zone과 migratetype 같은 추가 조건을 읽습니다.

작은 페이지 요청은 충분히 처리되는데 큰 order 요청만 실패하는 상황을 생각해 보세요. 빈 페이지 총합이 많아도 사이사이에 이동하기 어려운 사용 페이지가 끼면 큰 연속 블록을 만들기 어렵습니다. 이것은 단순 부족과 다른 외부 조각화 문제이며 compaction 같은 대응이 관련됩니다.

04

worked example: 16페이지 중 8페이지가 비었는데

물리 페이지 16개가 연속된 장난감 메모리를 가정합니다. 짝수 번호 페이지는 사용 중이고 홀수 번호 페이지는 비어 있습니다. 전체의 절반인 8페이지가 비어 있지만 두 페이지짜리 연속 빈 구간조차 없으므로 order 1 이상 요청을 그대로 만족시킬 수 없습니다.

이제 일부 사용 페이지가 이동 가능하고 다른 곳에 옮길 공간이 있다면 내용을 이동하고 매핑을 갱신해 큰 빈 구간을 만들 수 있습니다. 이것이 compaction을 이해하는 출발점입니다. 하지만 핀된 페이지나 이동 불가능한 커널 객체가 끼면 모든 배치를 마음대로 바꿀 수 없습니다.

사용자가 보는 free 값은 같은데 요청 결과가 달라지는 이유가 배치와 제약입니다. 이 모델에서 “빈 칸 8개”와 “연속 빈 칸 8개”는 다른 자원입니다. 큰 물리 연속 버퍼를 자주 요구하는 설계는 메모리 압박뿐 아니라 사용 시간이 길어지며 생기는 조각화에도 민감할 수 있습니다.

해법은 무조건 더 큰 메모리를 추가하는 것만이 아닙니다. 실제 요구가 물리 연속성인지 확인하고 가상 연속성이나 scatter-gather로 충족할 수 있다면 다른 API·장치 계약을 사용할 수 있습니다. 다만 장치가 지원하는 DMA 주소 방식은 별도로 확인해야 하며 CPU 가상 주소의 연속성을 장치 요구와 혼동하지 않습니다.

05

SLUB: 작은 객체를 페이지 위에 나누기

SLUB은 같은 종류나 크기의 작은 커널 객체를 효율적으로 관리하기 위한 slab 계열 할당자입니다. 페이지 기반 메모리를 여러 객체 슬롯으로 나누고 빈 슬롯을 재사용할 수 있습니다. 페이지 할당자가 매 요청마다 아주 작은 객체의 의미까지 알도록 만드는 대신 층을 나누는 구조입니다.

kmalloc은 일반 크기의 버퍼 요청에 사용되고 kmem_cache 계열은 특정 객체 캐시를 다루는 데 사용됩니다. 전용 캐시는 객체의 크기·정렬과 디버깅 등 요구를 표현할 수 있지만 캐시를 너무 세분화하면 부분 사용 slab과 관리 비용이 늘 수 있습니다. 전용 캐시가 항상 더 절약되는 것은 아닙니다.

CPU별 빠른 경로는 빈번한 객체 할당의 공유 경합을 줄일 수 있습니다. 그러나 다른 CPU에서 해제되는 객체, 부분적으로 찬 slab과 회수 경로는 더 복잡한 관리가 필요합니다. 로컬 재사용이 빠른 이유와 전체 메모리 보유량이 즉시 줄지 않는 이유를 함께 이해합니다.

Linux 6.18을 공부하면서 오래된 문서의 SLAB·SLOB 선택 설명을 현재 기본 선택지라고 반복하지 않습니다. slab이라는 개념, SLUB이라는 구현, kmalloc이라는 API를 구분합니다. 이름이 비슷해도 각각 추상화 수준이 다르므로 소스 파일과 설정을 기준으로 현재 구현을 확인합니다.

06

kmalloc·vmalloc·페이지 할당 비교

kmalloc이 반환하는 일반 버퍼는 CPU 가상 주소로 연속되어 있고 물리적으로도 연속된 요구를 만족하는 형태입니다. 작은 버퍼에 흔히 사용하지만 크기가 커질수록 적절한 연속 블록을 얻는 제약이 커질 수 있습니다. 성공한 주소를 이후 어떤 장치에서 사용할지는 DMA API의 별도 계약입니다.

vmalloc은 물리적으로 떨어진 페이지들을 연속된 커널 가상 주소 범위에 매핑할 수 있습니다. 큰 가상 연속 영역이 필요하지만 물리 연속성이 필요하지 않은 경우에 유용합니다. 페이지 테이블 구성과 변환 관련 비용이 있으므로 kmalloc과 완전히 같은 성능·문맥·장치 사용 조건이라고 생각하지 않습니다.

alloc_pages는 페이지 단위의 메모리를 다루는 인터페이스입니다. 객체 버퍼 포인터가 필요한지 페이지 메타데이터가 필요한지에 따라 적합성이 달라집니다. kvmalloc 같은 조합 API도 존재하지만 반환 경로에 따라 특성을 보수적으로 이해하고 대응하는 해제 함수를 사용해야 합니다.

해제 API는 획득 API의 계약에 맞춰야 합니다. 잘못된 free 함수, 이중 해제, 오류 경로의 누락은 기능이 정상일 때는 보이지 않다가 예외 상황에서 드러날 수 있습니다. 요청 크기만 적는 대신 소유자·반환 형식·해제 함수·실패 동작을 한 묶음으로 기록하면 실수를 줄일 수 있습니다.

07

GFP는 성공 확률보다 실행 계약

GFP 플래그는 어떤 메모리를 어디서 어떤 방식으로 찾을지에 영향을 줍니다. 특히 회수·I/O·sleep 허용 여부는 호출 문맥과 직접 연결됩니다. 일반적인 GFP_KERNEL 경로는 메모리 압박에서 직접 회수와 대기를 포함할 수 있으므로 sleep 가능한 문맥이어야 합니다.

잠들 수 없는 문맥에서는 nonblocking 제약을 맞춰야 하며 실패 가능성을 처리해야 합니다. 6.18 할당 가이드는 이런 상황에 GFP_NOWAIT를 설명하고, reserve 접근이 정당화되는 경우 GFP_ATOMIC을 구분합니다. 인터럽트 안이라는 이유만으로 무조건 reserve를 쓰는 처방을 반복하지 않습니다.

파일 시스템이나 I/O 경로에서 메모리 회수가 다시 같은 자원으로 들어오면 재귀적인 대기와 교착 위험이 있습니다. NOFS·NOIO와 관련 scope API는 이런 제약을 표현하는 데 관련됩니다. 플래그를 실패를 덜 나게 하는 마법의 옵션처럼 고르지 말고 현재 보유한 자원과 호출 경로를 봅니다.

지나치게 강한 재시도 정책이나 실패 불가 가정을 쓰면 시스템 진행성이 나빠질 수 있습니다. 할당 실패를 반환할 수 있는지, 작업을 줄일지, 미리 확보한 pool을 쓸지 설계해야 합니다. 오류 경로가 정상 경로보다 덜 중요하지 않으며 kernel allocation은 항상 성공한다고 가정하지 않습니다.

08

초기화·정보 노출·장치 접근

일반 할당으로 받은 메모리에 이전 내용이 남아 있을 수 있으므로 초기화 계약을 확인해야 합니다. kzalloc은 0으로 초기화된 버퍼가 필요한 경우에 사용합니다. 필요한 필드를 쓰지 않은 채 사용자 공간에 돌려주면 이전 데이터가 노출되는 보안 문제로 이어질 수 있습니다.

사용자 요청에 따라 커널 객체를 많이 만들 수 있다면 메모리 회계를 고려해야 합니다. 커널 메모리라고 해서 자원 제한을 무시해도 되는 것은 아닙니다. 적절한 accounting 정책은 한 사용자나 컨테이너가 시스템 자원을 과도하게 보유하는 상황을 제어하는 데 관련됩니다.

DMA에는 장치가 이해하는 주소와 캐시 일관성·동기화 요구가 있습니다. kmalloc의 반환 주소를 정수로 바꿔 장치에 그대로 전달하는 식의 추측은 잘못된 접근입니다. IOMMU와 DMA mapping API를 통해 장치 계약을 지켜야 하며 CPU 가상 주소와 DMA 주소를 구분합니다.

장치가 비동기로 메모리를 읽고 쓰는 동안 CPU가 버퍼를 해제하면 할당자 관점에서는 재사용 가능한 메모리를 장치가 계속 접근하게 됩니다. 완료 확인과 DMA 해제·소유권 전환까지 수명 프로토콜에 포함해야 합니다. CPU 코드에 직접적인 포인터 사용이 끝났다는 사실만으로 충분하지 않습니다.

09

관측으로 부족과 조각화 나누기

/proc/buddyinfo는 node·zone별로 여러 order의 빈 블록 상황을 보는 데 도움을 줍니다. 작은 order가 많고 큰 order가 적은 패턴은 연속성 요구를 조사할 단서가 될 수 있습니다. 그러나 한 스냅샷의 빈 블록 수만으로 특정 요청의 실패 원인을 확정하지 않습니다.

/proc/slabinfo나 slabtop은 객체 캐시의 크기와 사용 상태를 살펴보는 데 유용하지만 권한과 빌드 설정이 영향을 줍니다. 특정 캐시가 크다는 사실은 곧 누수라는 뜻이 아닙니다. live 객체 수, workload와 함께 늘었다 줄어드는지, reclaimable 상태가 어떤지 추가로 확인합니다.

할당 실패 로그에는 order·GFP·호출 스택 같은 중요한 조건이 담길 수 있습니다. 전체 메모리 여유만 보지 말고 실패한 요청이 어느 문맥에서 어떤 연속성을 요구했는지 읽습니다. 같은 서버에서도 작은 비동기 객체 요청과 큰 연속 DMA 버퍼 요청은 다른 문제일 수 있습니다.

실습에서는 상태를 읽기만 합니다. drop_caches나 강제 compaction을 실행하면 관측하려던 상태가 바뀌고 다른 작업에도 영향을 줍니다. 실제 튜닝은 동일한 부하와 목표 지표를 갖춘 일회용 VM에서 따로 수행하고, 개선이 전체 처리량·지연·메모리 보유에 어떤 영향을 주는지 함께 확인합니다.

10

요청 크기와 실제 블록 크기

현재 실험은 총 여유 64페이지를 가정하고 요청 페이지 수와 가장 큰 빈 buddy 블록을 바꿉니다. 예를 들어 9페이지를 직접 고차 페이지 블록으로 받으려면 16페이지 블록이 필요하므로 7페이지의 여분이 생깁니다. 가장 큰 빈 블록이 8페이지라면 총합이 충분해도 현재 배치에서는 요청을 충족하지 못합니다.

이 결과는 reclaim·compaction과 zone 제약을 생략한 개념 비교이며 실제 kmalloc의 모든 내부 낭비를 계산한 값이 아닙니다. 작은 객체를 SLUB 슬롯에서 받는 경우와 직접 order 블록을 요구하는 경우를 나눠 읽어야 합니다.

최대 빈 블록 선택을 크게 바꾸는 것은 모델에서 메모리 배치 조건이 좋아졌다고 가정하는 조작입니다. 실제 시스템에서 버튼 하나로 그런 블록이 생긴다는 뜻은 아닙니다. 회수·이동 가능성과 비용을 확인하지 않고 강제 compaction으로 같은 효과를 보장한다고 설명하지 않습니다.
