01

커널이 실행되기 전

전원을 켠 직후에는 커널의 스케줄러나 파일 시스템을 사용할 수 없습니다. 펌웨어가 하드웨어를 초기화하고 부팅 대상을 선택합니다. 부트로더는 커널 이미지와 필요한 초기 파일 시스템 이미지를 메모리에 준비하고 커널이 받을 인자를 전달합니다.

이 순서는 플랫폼에 따라 표현이 달라집니다. UEFI 환경에서 EFI stub을 통해 커널 이미지를 시작할 수 있고, arm64 시스템은 장치 정보를 Device Tree나 ACPI로 전달할 수 있습니다. 모든 머신이 동일한 BIOS·GRUB 경로를 사용한다고 가정하지 않습니다.

부트로더 화면이 보이지 않는 문제와 커널이 루트 파일 시스템을 찾지 못하는 문제는 단계가 다릅니다. 진단할 때는 마지막으로 확인된 출력의 주체부터 찾습니다. 커널 로그에 도달하기 전의 실패를 사용자 공간 서비스 설정으로 고치려 하면 원인을 놓칩니다.

02

커널 내부의 초기화

아키텍처별 초기 진입 코드는 CPU 상태, 초기 메모리 매핑, 스택 등 C 코드를 실행할 기반을 마련합니다. 이후 공통 초기화 경로가 메모리 관리자와 스케줄러, 타이머 등 핵심 기반을 준비합니다. 이는 이미 완성된 운영체제 위에서 main을 실행하는 사용자 프로그램과 다릅니다.

초기화에는 순서 의존성이 있습니다. 일반적인 동적 할당자가 준비되기 전에는 초기 부팅용 메모리 관리가 필요하고, 장치를 사용하려면 버스와 드라이버 초기화가 진행되어야 합니다. initcall 단계는 여러 하위 시스템의 초기화 순서를 조직하는 수단입니다.

부팅이 끝나면 초기화에만 사용된 일부 코드와 데이터는 회수될 수 있습니다. 소스의 __init 표시를 볼 때는 함수의 실행 시점과 수명을 함께 읽습니다. 초기화 전용 메모리를 나중에 참조하는 것은 단순한 기능 오류를 넘어 수명 오류가 될 수 있습니다.

03

initramfs와 진짜 루트

실제 루트 파일 시스템에 접근하려면 저장 장치 드라이버, 파일 시스템 지원, 암호 해제나 네트워크 설정이 먼저 필요할 수 있습니다. initramfs는 이 준비를 수행할 초기 사용자 공간을 제공합니다. 커널 이미지에 모든 가능한 부팅 정책을 넣는 대신 초기 프로그램이 필요한 절차를 수행합니다.

initramfs의 /init이 존재하면 커널이 이를 실행할 수 있습니다. 이 프로그램이 실제 루트를 찾아 마운트하고 이후 사용자 공간으로 전환합니다. 단순한 구성에서는 initramfs 없이 직접 루트를 사용하기도 하므로 initramfs는 모든 Linux 부팅에 반드시 같은 방식으로 존재하는 단계가 아닙니다.

루트 전환 실패를 조사할 때는 커널 명령행의 root 관련 인자, 사용 가능한 장치, 해당 파일 시스템 드라이버와 초기 사용자 공간의 로그를 연결합니다. 파일 이름이 맞다는 것만으로 장치가 해당 시점에 준비되어 있다는 보장은 없습니다.

04

PID 1과 서비스 시작

커널은 첫 사용자 공간 프로그램을 시작하지만 그 이후 어떤 서비스를 실행할지는 사용자 공간의 정책입니다. 일반 배포판에서는 systemd 같은 init 시스템이 PID 1 역할을 맡습니다. 임베디드 시스템이나 실험 VM에서는 다른 프로그램이 그 역할을 수행할 수 있습니다.

PID 1의 실행이 시작되었다면 커널 초기화의 상당 부분을 통과한 것입니다. 그 뒤 로그인 화면까지 오래 걸린다면 장치 대기, 마운트, 네트워크 준비, 서비스 의존성 등 여러 가능성을 나누어 봅니다. 전체 부팅 시간을 하나의 커널 성능 숫자로 보지 않습니다.

부팅 로그의 시간은 각 로그가 기록된 시점을 나타냅니다. 두 줄 사이 간격이 크다고 바로 앞의 함수가 그 시간을 모두 소비했다고 단정할 수는 없습니다. systemd 분석 도구나 커널 부팅 추적은 담당 구간이 다르며 함께 읽어야 실행 지연을 좁힐 수 있습니다.

05

부팅의 첫 문제: 아직 준비되지 않은 기능으로 준비하기

일반 프로그램의 main에 도착했을 때는 이미 주소 공간, 스택, 파일 디스크립터 같은 실행 기반이 마련되어 있습니다. 커널의 시작점에서는 그 기반 일부를 직접 만들어야 합니다. 예를 들어 완성된 페이지 할당자를 쓰려면 사용할 수 있는 물리 메모리 영역을 알아야 하고, 그 목록을 저장하는 공간도 필요합니다. 초기 부팅 코드가 일반 실행 경로와 다른 메모리 관리 방법을 사용하는 이유입니다.

펌웨어가 넘긴 메모리 정보에는 사용 가능한 영역과 예약된 영역이 섞여 있을 수 있습니다. 커널은 자기 이미지, 초기 데이터, 플랫폼이 예약한 영역 등을 피하면서 초기 메모리를 관리해야 합니다. 부팅 직후 물리 RAM 전체를 같은 상태의 여유 페이지로 간주하면 안 됩니다. 이후 정상 메모리 관리가 준비되면 초기 단계에서 쓰던 관리 정보를 일반적인 페이지 관리 체계와 연결합니다.

장치 초기화도 비슷한 순서 의존성을 가집니다. 특정 저장 장치를 사용하려면 그 장치가 연결된 버스와 제어기를 먼저 인식해야 하고, 파일 내용을 해석하려면 해당 파일 시스템 지원이 필요합니다. 아직 루트 디스크를 읽을 수 없는데 그 디스크 안에서 필요한 드라이버 모듈을 읽으려 하면 순환 의존성이 생깁니다. 드라이버를 커널에 포함하거나 초기 이미지에 넣는 선택은 이 순환을 끊는 방법입니다.

초기화 순서에는 성능과 유연성의 비용도 있습니다. 모든 가능한 드라이버를 커널에 넣으면 부팅에 필요한 기능을 일찍 사용할 수 있지만 이미지 크기와 유지 관리 범위가 커질 수 있습니다. 모듈로 분리하면 필요한 것만 로드하는 구성이 가능하지만 모듈 파일을 구할 시점과 의존성을 해결해야 합니다. 어느 선택이 적절한지는 범용 배포판인지 고정된 장치의 임베디드 환경인지에 따라 달라집니다.

소스에서 __init과 initcall을 볼 때는 특별한 문법 이름으로만 외우지 마세요. 이 함수가 사용할 기반은 언제 준비되는지, 어떤 객체를 다음 단계에 넘기는지, 초기화 후 어떤 메모리가 사라져도 되는지 질문합니다. 초기화 전용 데이터의 수명이 끝난 뒤 일반 실행 경로가 그 주소를 계속 사용하는 버그는, 부팅은 성공했지만 나중에 시스템이 깨지는 형태로 나타날 수 있습니다.

06

initramfs는 압축된 파일 묶음이고 initrd와는 다르다

초기 사용자 공간을 이야기할 때 initrd와 initramfs라는 이름이 혼용되기도 하지만 구조는 구분해야 합니다. initramfs는 cpio 형식의 파일 묶음을 초기 루트에 풀어 사용하는 방식입니다. 그 안에 /init, 필요한 실행 파일, 설정과 모듈 등을 포함할 수 있습니다. 과거의 initrd는 메모리에 놓인 블록 장치 이미지와 파일 시스템이라는 접근을 사용했습니다. 파일 이름에 initrd가 들어 있다는 사실만으로 내부 형식을 단정하지 않습니다.

중요한 점은 initramfs의 /init도 사용자 공간 프로그램이라는 사실입니다. 커널이 파일 묶음을 준비한 뒤 이 프로그램을 실행하면, 초기 프로그램이 장치 노드를 확인하고 필요한 모듈을 로드하며 암호화된 볼륨이나 복합 저장 구성을 준비할 수 있습니다. 암호 입력을 받거나 특정 장치가 나타날 때까지 기다리는 정책을 모든 커널의 공통 C 코드에 직접 넣지 않아도 됩니다.

실제 루트를 마운트한 뒤에는 그 루트의 init 프로그램으로 실행을 이어가는 전환이 필요합니다. 여기서 새로운 사용자 프로그램으로 exec한다고 해서 PID가 반드시 새로 생기는 것은 아닙니다. 같은 PID 1의 실행 이미지가 바뀔 수 있습니다. 따라서 도식의 초기 사용자 공간과 최종 서비스 관리자라는 두 상자는 항상 서로 다른 PID를 뜻하지 않으며, 단계와 프로세스 식별자를 혼동하면 안 됩니다.

initramfs가 커널과 맞지 않으면 커널 이미지 자체는 실행되지만 루트 장치를 준비하는 단계에서 실패할 수 있습니다. 예를 들어 필요한 저장 장치 드라이버가 모듈인데 초기 이미지에 없거나, 준비 스크립트가 다른 장치 이름을 기대할 수 있습니다. 이런 경우 커널 로그가 보인다는 사실과 최종 루트의 파일을 읽을 수 있다는 사실을 분리해 기록하면 조사 범위가 좁아집니다.

이 강좌에서는 이미지를 만들거나 부트로더 설정을 바꾸는 작업보다 현재 부팅의 증거를 먼저 읽습니다. 초기 이미지에는 장치 설정과 환경에 따라 민감한 내용이 포함될 수 있으므로 내용을 무심코 공개하지 않습니다. 구조를 배우기 위한 실습은 별도 VM과 공개된 최소 구성으로 진행할 수 있지만, 현재 머신의 이미지를 추출해 공유하는 행동은 이 장의 필수 실습이 아닙니다.

07

작은 장애 사례: 커널은 떴는데 루트를 찾지 못한다

가상의 VM이 커널 시작 메시지까지 출력한 뒤 루트 준비 단계에서 멈췄다고 합시다. 먼저 이미 입증된 사실을 적습니다. 펌웨어와 부팅 경로는 커널을 실행할 정도로 진행되었고, 콘솔 출력도 최소한 동작합니다. 아직 입증되지 않은 것은 실제 루트 장치 인식, 해당 파일 시스템 지원, 초기 사용자 공간의 준비 완료입니다. 로그인 화면이 없다는 결과만으로 커널 전체가 실행되지 않았다고 말할 수 없습니다.

다음으로 마지막 출력의 주체를 구분합니다. 커널의 장치 인식 메시지인지, initramfs의 셸이 띄운 오류인지, 이미 실행된 서비스 관리자의 실패 메시지인지에 따라 다음 질문이 달라집니다. initramfs의 응급 셸까지 도달했다면 초기 사용자 공간 실행은 성공한 것입니다. 그 상태에서 일반 서비스 설정을 고치기 전에 루트 준비 스크립트와 장치 목록을 확인하는 것이 논리적인 순서입니다.

root 관련 인자가 가리키는 대상과 실제 보이는 장치가 일치하는지 확인합니다. 장치가 아예 보이지 않으면 제어기와 드라이버 인식 경로부터 봅니다. 장치는 보이지만 원하는 파일 시스템을 읽지 못하면 파일 시스템 지원과 마운트 오류를 봅니다. 암호화나 논리 볼륨 구성이라면 원시 장치가 존재한다는 사실과 최종 루트 볼륨이 준비되었다는 사실 사이에 추가 단계가 있습니다.

이 장의 조작 실험에서 루트 장치 준비를 끄고 마지막 단계까지 이동해 보세요. 모델은 세 번째 단계까지 완료하고 루트 준비에서 멈춥니다. 슬라이더를 더 움직여도 PID 1의 최종 실행 단계로 넘어가지 않습니다. 이는 부족한 선행 조건을 시간 경과만으로 해결할 수 없다는 뜻입니다. 실제 시스템에서는 장치가 늦게 나타나는 경우도 있으므로 timeout과 영구적인 구성 오류를 로그로 구분해야 합니다.

정상 부팅 프리셋으로 바꾼 뒤에는 왜 성공했는지를 설명해 보세요. 단순히 시간이 더 흘러서가 아니라 선행 조건이 충족되었기 때문에 다음 단계가 가능해진 것입니다. 실제 수정에서도 같은 방식으로 누락된 조건이 무엇이었는지, 수정 후 해당 조건과 후속 단계가 각각 관측되었는지 기록합니다. 재부팅 한 번이 성공했다는 결과만으로 원래 원인을 완전히 입증했다고 보지는 않습니다.

08

부팅 시간을 읽는 법과 소스 탐색 순서

부팅의 총시간을 비교할 때는 어디부터 어디까지 재는지 먼저 정해야 합니다. 전원 인가부터 로그인 화면까지의 시간과 커널 시작부터 PID 1 실행까지의 시간은 다릅니다. 펌웨어가 장치를 찾는 시간, 커널 초기화 시간, 초기 사용자 공간의 장치 준비 시간, 일반 서비스의 시작 시간이 섞이면 어느 계층을 개선했는지 알기 어렵습니다. 측정의 시작점과 끝점을 기록하세요.

systemd 환경의 systemd-analyze time은 부팅 구간을 나누어 보는 출발점입니다. 그러나 이 도구가 출력한 한 줄을 모든 하드웨어와 모든 배포판에서 같은 의미의 전체 부팅 시간으로 읽어서는 안 됩니다. 펌웨어 정보 제공 여부, initramfs 구성, 서비스 관리자와 부팅 모드에 따라 얻을 수 있는 항목이 다를 수 있습니다. 명령이 없거나 항목이 빠져 있으면 관측 가능 범위의 차이로 기록합니다.

커널 로그의 시간 간격도 실행 시간을 직접 측정한 것과 구분합니다. 서로 다른 작업이 동시에 진행될 수 있고 어떤 단계는 자세한 메시지를 남기지 않을 수 있습니다. 2초의 로그 다음에 12초의 로그가 보인다는 이유만으로 앞 줄의 함수가 10초 실행되었다고 계산할 수 없습니다. 구체적인 함수나 initcall의 시간을 확인하려면 해당 목적의 추적과 설정을 추가해야 합니다.

소스를 처음 읽을 때는 init/main.c의 start_kernel을 시작점으로 큰 초기화 순서를 살펴봅니다. 이어서 첫 사용자 공간 실행을 준비하는 경로와 init/initramfs.c의 이미지 처리 역할을 연결합니다. 모든 호출 안으로 즉시 들어가기보다 메모리, 스케줄러, 장치, 사용자 공간 준비가 어느 구간에 등장하는지 표시하세요. 자세한 알고리즘은 이후 각 하위 시스템 장에서 다시 읽으면 됩니다.

마지막으로 소스의 순서와 실제 로그의 순서가 완벽히 일치해야 한다는 가정을 버립니다. 조건부 설정과 아키텍처별 진입, 비동기 초기화, 모듈 로드가 실행 경로를 바꿀 수 있습니다. 이 장에서 읽는 v6.18 소스는 고정된 구현의 출발점이며 실습 커널은 유지보수 패치와 배포판 변경을 포함할 수 있습니다. 차이를 발견하면 함수 이름보다 환경과 활성화된 경로를 먼저 확인합니다.

cat /proc/cmdline
ps -p 1 -o pid,comm,args
journalctl -b -k --no-pager -n 60
systemd-analyze time
