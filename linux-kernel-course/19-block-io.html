01

19.1 파일의 바이트를 장치의 블록으로

파일의 4096번째 바이트를 읽는 요청은 파일 시스템에서 저장 위치를 해석한 뒤 블록 계층으로 내려갑니다. bio는 블록 I/O에 필요한 범위와 메모리 조각을 표현합니다. 파일의 논리적 연속성이 장치의 물리적 연속성과 같다는 보장은 없습니다.

블록 계층은 장치가 처리할 request를 구성합니다. 조건이 맞는 인접 I/O는 합쳐질 수 있고, 장치 제약 때문에 나뉠 수도 있습니다. 그래서 사용자 read 한 번, bio 한 개, 장치 request 한 개가 일대일로 대응한다고 외우면 추적 결과를 해석하기 어렵습니다.

page cache hit이면 이 경로 자체를 지나지 않을 수 있습니다. 파일 I/O를 분석할 때 먼저 buffered/direct 경로와 캐시 효과를 확인하세요. 빠른 두 번째 read를 장치가 빨라진 증거로 해석하면 소프트웨어 캐시의 역할을 놓칩니다.

02

19.2 blk-mq는 병렬 장치에 맞춰 경쟁을 줄인다

여러 CPU가 하나의 전역 큐에 매번 접근하면 락과 캐시 일관성 비용이 커집니다. blk-mq는 CPU에 가까운 제출 경로와 장치 하드웨어 큐의 대응을 사용해 제출을 분산합니다. 핵심은 큐가 많다는 숫자보다 서로 독립적으로 진행할 수 있는 경로를 만드는 데 있습니다.

I/O scheduler는 요청의 순서와 공정성, 지연을 조정할 수 있습니다. NVMe에서 none을 사용한다고 큐가 없는 것은 아닙니다. 소프트웨어의 재정렬 정책을 생략해도 장치 제출 큐, 태그 한도, 완료 큐는 남습니다.

실제 장치의 scheduler와 큐 설정은 /sys/block 아래에서 확인합니다. 가상 머신의 virtio 장치와 호스트의 실제 NVMe는 다른 계층이므로 게스트 통계만으로 물리 장치 내부의 모든 대기를 설명할 수 없습니다. 성능 조사에서는 관측한 경계를 정확히 적어야 합니다.

03

19.3 DMA와 완료는 CPU 복사를 줄인다

드라이버는 장치가 접근할 메모리를 DMA API로 매핑하고 명령을 제출합니다. DMA는 장치가 메모리와 데이터를 주고받는 경로입니다. CPU가 바이트마다 복사하지 않아도 되지만 매핑, 명령 작성, 캐시 일관성, IOMMU 같은 관리 비용은 존재합니다.

장치가 작업을 마치면 인터럽트 또는 폴링으로 완료를 전달합니다. 드라이버와 블록 계층은 request와 bio를 완료하고, 그 결과가 파일 시스템과 대기 중인 작업으로 전파됩니다. 장치 완료 시각과 잠든 애플리케이션이 실제 CPU를 얻는 시각 사이에도 시간이 있습니다.

따라서 장치 서비스 시간만 짧다고 응답이 빠르다고 보장할 수 없습니다. 제출 전 큐 대기와 완료 후 스케줄링 대기를 함께 보아야 합니다. 지연을 구간으로 나누면 장치 교체가 필요한지, CPU 경합을 해결해야 하는지 판단할 수 있습니다.

04

19.4 큐를 깊게 하면 언제 도움이 되는가

동시에 하나만 요청하면 장치 내부 병렬성을 활용하지 못할 수 있습니다. 큐 깊이를 늘리면 처리량이 올라가다가 장치나 호스트 처리 능력에 도달합니다. 그 이후에는 처리량이 거의 늘지 않고 기다리는 요청만 많아지는 구간이 생깁니다.

안정적인 시스템에서 평균 진행 중 요청 수는 처리율과 평균 응답 시간의 곱으로 해석할 수 있습니다. 예를 들어 초당 1000개를 처리하고 평균 10ms가 걸린다면 경계 안의 평균 요청 수는 약 10개입니다. 이 계산은 순간 최고치나 서로 다른 측정 구간을 섞으면 성립하지 않습니다.

관측 실습에서는 lsblk로 계층을 확인하고 iostat의 await, 평균 큐 길이, 처리량을 함께 봅니다. %util 100만 보고 최신 병렬 장치가 포화됐다고 확정하지 않습니다. 장치가 바쁜 시간 비율과 남은 병렬 처리 용량은 다른 질문입니다.

05

19.5 캐시 miss 하나를 끝까지 따라간다

프로세스가 파일의 아직 캐시에 없는 64KiB를 읽는다고 가정합니다. VFS와 파일 시스템은 해당 범위의 저장 위치를 찾고 page cache에 채울 메모리를 준비합니다. 요청한 범위보다 넓게 readahead가 발생할 수도 있으므로 사용자 요청 크기와 장치에서 실제 읽은 크기가 다를 수 있습니다. 이것이 나쁜 낭비인지 다음 읽기를 위한 유용한 준비인지는 접근 패턴에 따라 달라집니다.

파일의 논리 블록이 장치에서 떨어져 있거나 장치의 최대 전송 길이 제약이 있으면 I/O가 나뉠 수 있습니다. 반대로 인접한 다른 읽기와 병합될 수도 있습니다. 여러 bio가 하나의 request에 연결되거나 하나의 상위 동작이 여러 request의 완료를 기다리는 구조가 가능합니다. 객체의 개수만 세기보다 어느 완료 조건이 상위 작업을 깨우는지 표시해 보세요.

데이터가 메모리에 채워져 사용할 수 있게 되면 대기 작업이 다시 진행할 수 있습니다. 이후 파일 오프셋 갱신과 사용자 버퍼 복사, 실제 CPU 배정이 남습니다. 블록 요청 완료 시간과 read 시스템 콜 반환 시간을 함께 보면 이 차이를 관찰할 수 있습니다. 디스크가 빠른데 read가 느리다는 보고는 모순이 아니라 서로 다른 경계를 측정했을 가능성입니다.

06

19.6 큐 깊이와 병렬성의 구별

장치가 독립적인 작업 네 개를 동시에 처리할 수 있고 각 작업이 1ms 걸리는 교육용 모델을 생각합니다. 동시 요청이 하나면 이상적으로 초당 약 1000개, 네 개면 약 4000개까지 처리할 수 있습니다. 여기서는 데이터 전송 대역폭, CPU 제출 비용, 캐시와 장치 내부 간섭을 생략했으므로 실제 NVMe의 벤치마크 숫자로 읽지 않습니다.

요청을 40개까지 늘려도 처리 능력이 네 개로 제한되면 나머지는 기다립니다. 같은 시간에 더 많은 작업이 시스템 안에 있으므로 평균 응답 시간은 늘어나지만 지속 가능한 처리량은 크게 늘지 않습니다. 큐 깊이는 동시에 넣어 둔 수요이고 병렬성은 실제로 동시에 진행할 수 있는 능력이라는 차이를 구분해야 합니다.

실제 장치에서는 큐 깊이를 늘릴 때 어떤 자원이 먼저 한계에 닿는지 측정합니다. 장치 내부 병렬성, PCIe 대역폭, 요청 크기, CPU 코어, 파일 시스템 락이 서로 다른 한도를 만들 수 있습니다. 최대 IOPS 하나를 모든 작업 크기의 예측치로 사용하지 않고, 동일한 read/write 비율과 요청 크기에서 지연 분포를 확인합니다.

07

19.7 태그와 제출 제한은 메모리도 보호한다

blk-mq의 태그는 진행 중인 요청을 식별하고 가용 슬롯을 관리하는 데 사용됩니다. 드라이버와 하드웨어가 한 번에 처리할 수 있는 요청 수는 유한합니다. 태그가 없으면 제출 측이 기다리거나 나중에 다시 진행해야 할 수 있습니다. 큐에 넣는 동작 자체가 항상 즉시 끝난다는 가정은 이 자원 제한을 놓칩니다.

무제한 요청을 메모리에 쌓으면 지연뿐 아니라 요청 메타데이터와 데이터 버퍼가 차지하는 메모리도 늘어납니다. 요청당 128KiB 버퍼를 고정하고 1000개를 진행 중으로 유지하면 데이터만 약 125MiB입니다. 여기에 커널·사용자 메타데이터와 다른 캐시가 더해집니다. 비동기 제출량의 한도는 성능과 메모리 사용을 함께 제어하는 정책입니다.

따라서 큐가 길다는 증상에 큐 한도를 늘리는 처방은 신중해야 합니다. 짧은 버스트를 흡수하려는 목적이면 유용할 수 있지만 지속적인 처리 능력 부족을 숨기면 타임아웃 직전의 오래된 작업만 많아집니다. 완료를 받을 때 다음 요청을 제출하는 제한된 파이프라인으로도 충분한 병렬성을 유지할 수 있는지 먼저 실험합니다.

08

19.8 DMA 주소는 사용자 포인터가 아니다

드라이버가 사용자 프로그램에서 받은 주소 숫자를 그대로 장치에 전달할 수 있는 것은 아닙니다. 사용자 가상 주소, 커널 가상 주소, CPU 물리 주소, 장치가 사용하는 DMA 주소는 역할이 다릅니다. IOMMU가 있으면 장치용 주소가 다시 변환될 수 있습니다. 이 구분은 메모리 단원의 주소 변환을 I/O 경로로 확장하는 지점입니다.

DMA 매핑 API는 장치 접근 가능성과 플랫폼의 캐시 일관성 규칙을 다루는 계약입니다. CPU와 장치가 같은 버퍼를 언제 읽고 쓸 수 있는지, 소유권을 언제 넘기는지, 동기화가 필요한지 정해야 합니다. x86의 익숙한 일관성 동작만 보고 모든 아키텍처에서 별도 관리가 불필요하다고 일반화하지 않습니다.

완료 전에 버퍼를 해제하거나 재사용하면 장치가 다른 데이터가 들어간 메모리에 쓰는 문제가 생길 수 있습니다. 이 오류는 CPU 코드가 정상으로 보여도 비동기 장치가 뒤늦게 접근하면서 드러날 수 있습니다. 드라이버의 제거 경로가 DMA와 진행 중 요청까지 종료해야 하는 이유도 동일한 수명 규칙으로 설명됩니다.

09

19.9 direct I/O와 buffered I/O의 선택

buffered I/O는 page cache를 통해 재사용과 쓰기 결합을 얻고 사용자에게 편리한 접근을 제공합니다. direct I/O는 지원되는 파일·정렬 조건 아래에서 page cache 경로를 우회할 수 있습니다. 캐시를 중복 관리하는 데이터베이스처럼 사용자 공간이 자체 정책을 가진 경우에 의미가 있지만 모든 작업에서 빠른 방식은 아닙니다.

direct I/O에도 파일 시스템의 메타데이터 처리와 블록 계층, 장치 캐시는 남습니다. O_DIRECT를 설정했다고 요청이 자동으로 영속 저장되거나 모든 복사가 사라진다고 생각하지 않습니다. 주소·길이·오프셋 정렬 조건과 다른 buffered 접근과의 상호작용도 검토해야 합니다. 실패하거나 다른 경로로 처리되는 조건은 파일 시스템과 API 규약에 따라 확인합니다.

비교 실험에서는 같은 데이터 크기와 접근 패턴, 동시성, 캐시 상태를 사용합니다. buffered I/O의 warm-cache 읽기와 direct I/O의 장치 읽기를 비교해 direct가 느리다고 결론내리면 다른 일을 비교한 것입니다. 두 방식이 애플리케이션에서 제공해야 하는 의미가 같은지부터 확인한 다음 CPU 비용과 지연을 측정합니다.

10

19.10 지표 세 개가 같은 사건을 다르게 본다

애플리케이션이 측정한 read 지연은 사용자 호출 경계의 시간입니다. iostat의 await는 블록 장치 계층에서 관측한 요청 시간의 집계이고, 장치 내부 서비스 시간과 정확히 같지 않을 수 있습니다. CPU가 iowait로 회계된 시간은 또 다른 관점의 지표입니다. 이 세 숫자를 하나의 “디스크가 느린 시간”으로 치환하면 원인 분석이 불안정해집니다.

가령 await는 비슷한데 read 지연만 늘었다면 캐시 miss 이전의 락 대기, 완료 이후 runnable 대기, 사용자 공간의 측정 범위를 조사합니다. 둘 다 늘고 큐 길이도 증가하면 장치 또는 하위 경로의 포화 가설이 강해집니다. 오류 카운터가 함께 늘었다면 재시도와 장치 상태가 별도의 단서입니다. 한 숫자보다 여러 지표의 같은 구간 변화가 중요합니다.

소스에서는 block/blk-mq.c의 제출과 완료를 별도로 표시하고 드라이버에서 하드웨어 큐로 넘기는 지점을 찾아보세요. 한 번에 전체 NVMe 구현을 이해하려 하지 말고 상위 요청을 소유하는 주체가 언제 바뀌는지, 실패 시 누가 완료를 전달하는지 확인합니다. 정상 완료와 오류 완료가 모두 상위 대기자를 해제해야 한다는 계약이 핵심입니다.

11

19.11 확인 과제: 처리량은 같고 지연만 늘었다

두 설정을 같은 크기의 읽기로 비교했더니 A는 진행 중 요청 8개에서 초당 8000개, B는 64개에서 역시 초당 8000개를 처리했다고 합시다. 장치와 작업이 안정적인 교육용 모형이면 평균 진행 중 요청 수를 처리율로 나누어 응답 시간의 규모를 생각할 수 있습니다. A는 약 1ms, B는 약 8ms가 됩니다. 실제 평균 관계를 적용하려면 같은 시스템 경계와 안정 구간이어야 합니다.

이 결과에서 B의 큐가 더 크다는 사실을 더 많은 유용한 병렬성이 생겼다는 증거로 읽으면 안 됩니다. 동일한 처리량을 유지하는 데 필요한 병렬성보다 많은 요청이 대기했을 가능성이 있습니다. 지연 목표가 중요한 서비스라면 충분한 처리량을 유지하는 더 작은 진행 중 한도를 찾는 것이 합리적인 다음 실험입니다. 최대 깊이를 무조건 선택하는 것이 최적화는 아닙니다.

하지만 이 계산만으로 장치 내부 서비스 시간이 1ms에서8ms로 느려졌다고 말하지 않습니다. 더 많은 시간이 제출 전 소프트웨어 큐나 장치 큐에서 생겼을 수 있습니다. 요청의 enqueue, issue, complete와 사용자 반환 경계를 확인해야 대기가 어느 위치에 추가됐는지 알 수 있습니다. 사용자 동시성, blk-mq 태그, 하드웨어 큐 깊이도 각각 다른 한도라는 점을 유지합니다.

마지막으로 오류와 타임아웃을 확인합니다. B에서 일부 요청이 실패해 처리량 집계에서 빠졌다면 성공 완료 수만으로 같은 일을 했다고 판단할 수 없습니다. 전체 제출 수, 성공 수, 오류 수, 지연 분포와 메모리 사용을 함께 비교해야 합니다. I/O 최적화는 큐의 숫자를 크게 만드는 작업이 아니라 필요한 처리량을 정확성과 지연 조건 안에서 달성하는 작업입니다.

복습할 때는 사용자 요청 수, bio 수, request 수, 장치 명령 수를 각각 다른 열에 두세요. 병합과 분할, 캐시 hit 때문에 값이 다를 수 있다는 이유를 각 화살표 옆에 적으면 외운 용어가 실제 데이터 경로의 역할로 바뀝니다.
