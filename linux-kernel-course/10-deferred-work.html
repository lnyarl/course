01

알림을 받은 장소에서 모두 끝내지 않는 이유

장치가 이벤트를 알렸다고 해서 그 자리에서 긴 계산이나 블로킹 작업을 모두 수행해야 하는 것은 아닙니다. hardirq 구간을 짧게 유지하면 중단된 작업의 복귀 지연과 다른 이벤트의 처리 지연을 제한할 수 있습니다. 필요한 상태를 기록하고 후속 처리를 예약하면 역할을 나눌 수 있습니다.

이 분리는 공짜가 아닙니다. 큐에 작업을 넣고 실행 주체를 깨우며 데이터를 전달하는 비용이 생깁니다. 장치 이벤트와 실제 처리 사이에는 대기 시간이 추가될 수 있습니다. 따라서 무조건 작업을 더 많은 큐로 나누는 것이 빠른 설계라고 볼 수는 없습니다.

후속 처리 방식은 지금 해야 할 동작이 sleep을 요구하는지, 순서 보장이 필요한지, 어떤 CPU에서 수행할지, 어느 정도의 지연을 허용하는지에 따라 선택합니다. 이 네 질문을 먼저 하면 softirq와 workqueue를 이름만 보고 고르는 실수를 줄일 수 있습니다.

02

softirq의 실행 특성

softirq는 네트워크 같은 높은 빈도의 후속 처리를 수행하는 메커니즘입니다. 비 RT 기본 문맥에서는 일반적인 sleep 가능한 사용자 task 코드처럼 다룰 수 없습니다. CPU별로 처리될 수 있으며 같은 종류의 softirq가 다른 CPU에서 동시에 실행될 가능성도 고려해야 합니다.

즉시 처리할 양이 많거나 실행 조건에 따라 ksoftirqd 같은 커널 스레드가 처리를 맡을 수 있습니다. 출력에서 커널 스레드가 보인다는 이유만으로 softirq 콜백의 API 제약이 모두 사라졌다고 판단하지 않습니다. 어떤 계약 아래 실행되는 콜백인지가 중요합니다.

softirq 통계는 각 종류의 실행 횟수를 보여 주지만 그 한 번이 처리한 작업 수나 소요 시간을 고정하지 않습니다. NET_RX가 증가한 횟수만으로 수신 패킷 개수를 계산하지 않습니다. 장치·네트워크 계층의 처리 카운터와 CPU 시간은 별도로 봅니다.

03

threaded IRQ가 제공하는 실행 주체

threaded IRQ는 IRQ 관련 처리 일부를 스케줄링 가능한 스레드 문맥에서 수행할 수 있게 합니다. 장치가 요구하는 빠른 최소 처리와 더 긴 후속 작업을 나누는 데 유용합니다. 스레드가 생기면 일반 task처럼 CPU 선택과 우선순위의 영향을 받는 구간이 생깁니다.

등록 옵션과 장치 특성에 따라 핸들러의 분담과 마스킹 정책이 달라집니다. 스레드 핸들러가 동작하는 동안 다음 알림을 어떻게 다룰지도 중요합니다. 스레드로 옮겼다는 사실만으로 장치 상태를 동시 접근해도 안전하거나 이벤트 순서가 자동 보장되는 것은 아닙니다.

PREEMPT_RT는 IRQ 처리의 스레드화를 폭넓게 활용하지만 예외와 제약이 남습니다. 따라서 기본 커널에서 직접 threaded IRQ를 사용하는 경우와 RT 구성으로 실행 문맥이 달라진 경우를 구분합니다. 문서에 나온 코드가 어느 구성의 계약을 가정하는지 확인합니다.

04

일반 workqueue와 BH workqueue

일반적인 thread-backed workqueue는 work item을 큐에 넣으면 worker 스레드가 실행합니다. sleep이 필요한 후속 작업을 수행할 수 있는 문맥을 제공하지만, 콜백이 보유한 락이나 실행 중인 다른 제약까지 무시해도 된다는 뜻은 아닙니다. 잠들 수 있는 조건은 여전히 코드 전체에서 확인해야 합니다.

Linux 6.18에는 BH workqueue처럼 softirq 문맥에서 실행되는 형태도 있습니다. 따라서 workqueue라는 이름만 보고 모든 콜백이 sleep 가능하다고 일반화하면 틀립니다. 이 강좌에서 별도 표시 없이 말하는 일반 workqueue는 worker 스레드 기반 경로이며 BH 형태는 구분해 설명합니다.

workqueue는 논리적인 작업 큐와 실제 worker pool을 분리할 수 있습니다. 큐 하나를 만들었다고 CPU마다 완전히 독립된 전용 스레드 집합이 반드시 생기는 것은 아닙니다. 동시성·CPU 바인딩·메모리 회수 관련 옵션은 처리 목적과 시스템 진행 가능성을 반영하는 선택입니다.

05

worked example: 이벤트와 해제의 경쟁

장치 객체 D를 가리키는 work item W를 예약했다고 가정합니다. 예약 직후 드라이버 제거 경로가 D를 해제하면, 나중에 실행되는 W는 이미 수명이 끝난 메모리를 접근할 수 있습니다. 큐 등록이 성공했다는 사실은 D의 수명을 자동으로 연장해 주지 않습니다.

올바른 종료 경로는 새 작업이 더 이상 등록되지 않도록 하고, 이미 등록되거나 실행 중인 작업을 취소·대기하는 API의 계약에 맞춰 정리한 뒤 객체를 해제해야 합니다. 참조 카운트로 수명을 연장하는 설계도 가능하지만 마지막 해제와 재등록의 경쟁을 함께 해결해야 합니다.

여기서 동기 취소 함수가 작업 종료를 기다린다면 해당 작업이 필요로 하는 락을 보유한 채 호출해서는 교착할 수 있습니다. W가 락 L을 기다리는데 제거 경로가 L을 가진 채 W 종료를 기다리는 순환입니다. 비동기화는 실행 시점만 바꾸는 것이 아니라 수명과 락 순서까지 바꿉니다.

06

순서 보장의 범위

A와 B를 순서대로 큐에 넣었다는 사실만으로 서로 다른 큐나 여러 worker에 걸친 모든 효과가 같은 순서로 완료된다고 가정할 수는 없습니다. 순차 실행이 정말 필요한 경우 그 요구를 지원하는 ordered workqueue 등 알맞은 도구를 선택하고 문서의 보장 범위를 확인합니다.

동시 실행 수를 늘리면 독립 작업의 처리량이 좋아질 수 있지만 공유 락과 메모리 대역폭에서 경쟁이 커질 수 있습니다. 또한 큐에서 대기하던 작업들이 동시에 장치 요청을 만들어 하위 계층에 더 큰 burst를 보낼 수 있습니다. 상위 큐만 짧아졌다고 시스템 전체 지연이 줄었다고 단정하지 않습니다.

순서를 보장하는 큐는 추론하기 쉽지만 긴 작업 하나가 뒤 작업을 모두 지연시킬 수 있습니다. 이를 head-of-line blocking 관점으로 볼 수 있습니다. 올바른 선택은 모든 작업을 병렬화하는 것도, 모든 작업을 직렬화하는 것도 아니라 공유 상태와 필요한 순서의 범위를 좁히는 것입니다.

07

delayed work와 실행 시각

delayed work는 일정 지연 뒤 작업을 실행할 수 있게 만드는 수단이지 정확한 벽시계 시각에 CPU를 예약하는 기능은 아닙니다. 타이머 조건이 충족된 뒤 큐와 worker의 실행 여건에 따라 실제 콜백 시작은 늦어질 수 있습니다. 타이머 만료와 작업 시작을 별도 이벤트로 관측합니다.

짧은 작업을 너무 자주 예약하면 큐 조작과 깨우기 비용이 실제 유용한 일보다 커질 수 있습니다. 반대로 너무 많이 묶으면 응답이 늦어집니다. 적절한 batch 크기는 이벤트율과 처리 비용, 허용 지연에 달려 있습니다. 이 설명은 설계상의 교환이며 현재 UI는 batch 수치 대신 실행 문맥과 sleep 필요 조건을 비교합니다.

재시도 작업은 종료 시점에도 다시 자신을 예약할 수 있습니다. 따라서 취소 한 번으로 끝이라고 생각하지 말고 재등록 조건과 stop 상태를 함께 설계해야 합니다. 드라이버 제거, suspend, 오류 복구처럼 수명 경계가 있는 경로에서 이 문제가 드러납니다.

08

관측과 설계 선택 연결

ps에서 kworker와 ksoftirqd를 본다면 그것이 어떤 장치나 작업을 처리하는지 추가 추적이 필요합니다. 이름만으로 특정 드라이버 원인을 확정하지 않습니다. workqueue tracepoint, 함수 추적과 스택은 예약·시작·완료 사이의 시간을 나누는 데 도움을 줄 수 있습니다.

문제가 큐 대기인지 콜백 실행 시간인지 먼저 분리합니다. 예약부터 시작까지 길면 worker 가용성·동시성 제한·다른 작업을 보고, 시작부터 완료까지 길면 실제 코드와 대기를 봅니다. 두 구간을 합친 값만 보면 엉뚱한 부분을 최적화할 수 있습니다.

이 장의 실습은 관측만 수행합니다. 임의의 커널 큐를 강제로 flush하거나 우선순위를 바꾸지 않습니다. 실제 드라이버 작성 실습에서는 객체 수명, 중복 등록, 취소 경쟁을 별도 테스트로 확인해야 하며 UI의 정상 순서 애니메이션만으로 동시성 안전성을 입증할 수는 없습니다.

09

큐에 쌓인 작업은 메모리와 지연을 함께 쓴다

개념적으로 초당 120개의 work가 들어오는데 worker가 초당 100개만 처리할 수 있다면 큐는 초당 20개씩 늘어납니다. 처음에는 정상처럼 보이지만 시간이 지나며 대기 시간과 작업 객체의 메모리 보유량이 커집니다. worker를 비동기로 만들었다는 사실은 입력률과 처리 능력의 차이를 해결하지 않습니다.

작업 하나가 큰 버퍼를 참조하면 큐 길이 증가가 실제 버퍼 수명도 늘릴 수 있습니다. 할당 시점과 처리 완료 시점 사이가 길어져 메모리 압박이 생기고, 압박이 다시 worker의 처리 속도를 늦추면 악순환이 될 수 있습니다. 큐 길이·대기 시간·참조 메모리 양을 함께 관측해야 하는 이유입니다.

입력 제어, 작업 병합, 중복 이벤트 통합, 제한된 큐와 실패 반환은 상황에 따라 대응이 될 수 있습니다. 어떤 이벤트는 최신 상태만 중요하고 어떤 이벤트는 하나도 잃으면 안 됩니다. 의미가 다른 작업을 무조건 덮어쓰거나 버리면 성능은 좋아 보여도 기능 요구를 위반하게 됩니다.

이 예시는 실제 workqueue가 항상 무제한 큐라는 주장이 아니라 비동기 설계 일반의 수요·공급 관계를 설명합니다. 실제 큐 정책과 중복 등록 의미는 사용 API를 확인합니다. 같은 work item을 다시 예약하는 동작을 새로운 독립 항목이 항상 하나 더 생긴다고 가정하지 않습니다.

10

메모리 회수 중 필요한 작업

어떤 작업이 메모리를 해제하는 데 꼭 필요한데 그 작업을 실행할 worker 자체가 메모리 확보를 기다린다면 진행 순환이 생길 수 있습니다. 메모리 압박에서는 평소 충분했던 자원이 부족하므로 이런 의존성이 드러납니다. 정상 부하에서 작업이 잘 실행된다는 테스트만으로 회수 경로의 진행성을 보장할 수 없습니다.

workqueue에는 메모리 회수와 관련된 진행 요구를 표현하는 옵션과 설계가 있습니다. 이를 모든 큐에 기계적으로 붙이는 대신 해당 작업이 실제로 어떤 회수 의존성을 갖는지 확인해야 합니다. 옵션은 의미 있는 계약을 표현해야 하며 잘못된 락 순서나 무한 재시도를 자동으로 해결하지 않습니다.

코드를 읽을 때는 큐 생성 위치만 보지 말고 콜백이 할당하는 메모리와 보유하는 락, 완료를 기다리는 다른 경로를 연결합니다. A의 완료가 B를 기다리고 B의 실행이 A가 가진 자원을 기다리면 실행 스레드를 늘리는 것만으로 해결되지 않을 수 있습니다.

실습 VM에서 의도적인 메모리 압박을 줄 때도 이런 경로가 실제로 실행되었는지 확인해야 합니다. 단순히 메모리 사용률을 높였다는 사실은 특정 회수 work의 실행 증거가 아닙니다. 검증은 원하는 경로의 이벤트·오류·완료 결과를 묶어 보고해야 합니다.

11

현재 실험의 선택 규칙 읽기

이 장의 실험에서는 실행 문맥을 hard IRQ·softirq·일반 worker 중에서 선택하고 작업이 sleep을 요구하는지 바꿉니다. 기본 비 RT 조건에서 sleep을 요구하는 작업은 일반 worker 경로가 필요하다는 판단을 표시합니다. 작업을 오래 실행하는 시간 시뮬레이션이 아니라 실행 가능 조건을 분류하는 모델입니다.

실험에서 worker와 sleep을 선택해 조건 충족이 나와도 실제 콜백이 무조건 안전하다는 뜻은 아닙니다. spinlock을 보유했거나 다른 atomic 제약이 있다면 잠들면 안 됩니다. UI는 대표 문맥 하나만 보여 주며 실제 코드는 호출한 함수의 제약과 객체 수명까지 추가로 확인해야 합니다.

반대로 sleep이 필요 없다고 hardirq에서 어떤 양의 작업이나 해도 된다는 뜻도 아닙니다. 긴 계산은 응답 지연을 키울 수 있으므로 최소 처리와 후속 처리의 분리 원칙은 남습니다. 가능 여부와 좋은 설계인지라는 두 질문을 구분하면 단순한 초록색 표시를 과도하게 해석하지 않게 됩니다.

실제 장애 조사에서는 문맥 위반, 큐의 과부하, 작업 실행 중 대기, 종료 시 수명 경쟁 중 어느 범주인지 먼저 분류합니다. 모두 사용자가 보기에는 “비동기 작업이 끝나지 않는다”로 보일 수 있지만 필요한 증거와 수정은 다릅니다. 실행 장소와 작업 수명을 그린 도식이 이 분류의 출발점입니다.

12

동기 호출과 비동기 예약의 반환값

동기 함수의 성공 반환은 호출 계약에 따라 작업 완료를 뜻할 수 있지만 비동기 예약 함수의 성공은 보통 예약 상태에 대한 정보입니다. 콜백의 최종 성공, 장치의 완료와 사용자에게 결과가 전달되었다는 사실까지 한 번에 보장한다고 해석하지 않습니다. 각 API가 어떤 시점의 상태를 돌려주는지 문서를 확인합니다.

오류도 여러 단계에서 생길 수 있습니다. 예약 전에 인자가 거부되거나, 예약 후 콜백에서 메모리 확보가 실패하거나, 장치 I/O가 나중에 실패할 수 있습니다. 이를 호출자에게 어떻게 전달하고 어느 단계에서 자원을 정리할지 정해야 합니다. 반환값 하나만 검사하고 나머지 완료 경로를 무시하면 작업 유실과 메모리 누수가 생길 수 있습니다.

이 구분은 테스트 설계에도 영향을 줍니다. 큐에 들어갔다는 검사와 실제 콜백이 끝났다는 검사, 최종 결과가 맞다는 검사는 별도 근거입니다. 강좌 UI의 문맥 조건 충족 표시도 완료나 성공의 증명이 아니며 실제 동작을 검증할 때 필요한 추가 질문을 남깁니다.
