01

프로그램이 요청하지 않은 진입

네트워크 패킷 도착이나 저장 장치 작업 완료는 현재 CPU에서 실행 중인 프로그램의 명령 흐름과 별개로 일어납니다. CPU가 장치를 계속 확인하는 대신 장치가 이벤트를 알리면 CPU는 실행 흐름을 잠시 바꿔 대응할 수 있습니다. 이 통지 경로가 외부 인터럽트의 기본 역할입니다. 알림 자체와 알림을 받은 뒤 수행할 실제 데이터 처리는 구분해야 합니다.

동기적 예외는 현재 실행한 명령과 연결됩니다. 유효하지 않은 명령, 나눗셈 오류, 페이지 폴트가 대표적입니다. 예를 들어 매핑은 유효하지만 물리 페이지가 아직 없는 주소를 읽으면 해당 명령과 관련된 fault를 처리하고 재시도할 수 있습니다. 반면 NIC의 완료 알림은 현재 실행 중인 사용자 명령이 원인이 아닐 수 있습니다.

인터럽트라는 말을 모든 커널 진입의 통칭처럼 사용하면 원인을 잃습니다. 시스템 콜은 의도한 서비스 요청이고, 예외는 실행 명령에 대한 CPU의 반응이며, 장치 IRQ는 외부 사건의 알림입니다. 각 진입은 저장해야 할 상태와 복귀 방식, 중첩 가능성에 차이가 있으므로 도식에서도 서로 다른 화살표로 생각합니다.

02

장치에서 CPU까지

장치의 이벤트는 인터럽트 컨트롤러와 플랫폼 경로를 거쳐 특정 CPU로 전달됩니다. Linux의 공통 IRQ 계층은 서로 다른 컨트롤러의 세부 동작과 드라이버의 이벤트 처리를 분리합니다. 드라이버가 플랫폼별 레지스터 방식 전체를 직접 알고 있어야 하는 구조보다 재사용이 쉽지만, 어느 계층에서 알림을 마스킹하거나 완료했는지 추적할 필요가 있습니다.

전통적인 선 기반 IRQ와 MSI/MSI-X 같은 메시지 기반 인터럽트는 전달 방식이 다릅니다. 장치가 여러 큐에 대응하는 여러 벡터를 제공하면 작업을 여러 CPU로 나눌 수 있습니다. 그러나 큐·IRQ·CPU 관계는 장치 능력과 드라이버 설정에 달렸고, 모든 벡터가 항상 고르게 사용된다고 가정할 수는 없습니다.

IRQ affinity는 어느 CPU가 특정 IRQ를 처리할 수 있는지에 영향을 줍니다. 사용자의 task affinity와 별도 설정입니다. 애플리케이션을 CPU 하나에 고정했더라도 네트워크 IRQ가 다른 CPU에서 처리될 수 있습니다. 데이터가 CPU 사이를 이동하면서 생기는 캐시 비용까지 생각하면 단순히 IRQ 수만 균등하게 만드는 것이 최적은 아닐 수 있습니다.

03

짧게 끝내야 하는 이유

hard IRQ 핸들러는 일반 사용자 task의 평범한 함수 호출 문맥이 아닙니다. 다른 작업을 중단시키고 실행되므로 오래 머무르면 그 CPU가 정상 작업으로 돌아가는 시점이 늦어집니다. 비 RT 커널의 hardirq 문맥에서는 잠드는 mutex나 블로킹 I/O를 호출할 수 없습니다. 필요한 최소 상태를 확인하고 적절한 후속 처리로 넘기는 이유입니다.

핸들러가 짧아야 한다는 원칙이 단순히 줄 수를 줄이라는 뜻은 아닙니다. 장치의 사건을 확인하고 알림 상태를 올바르게 다루며, 후속 처리가 참조할 데이터를 안전하게 게시해야 합니다. 너무 일찍 완료를 알리거나 필요한 상태를 저장하지 않으면 이벤트 유실·중복 처리·수명 오류가 생길 수 있습니다.

인터럽트가 사용자 task를 중단했다고 해서 핸들러가 그 task의 일반 작업을 대신 수행하는 것은 아닙니다. 현재 task 포인터가 보이더라도 이를 임의로 잠들 수 있는 문맥의 증거로 사용하면 안 됩니다. 코드 리뷰에서는 지금 실행되는 문맥과 공유 데이터를 누가 함께 접근하는지를 먼저 확인합니다.

04

edge·level과 acknowledge

edge-triggered 알림은 신호의 변화가 사건을 의미하고, level-triggered 알림은 특정 상태가 유지되는 동안 요청이 살아 있다는 관점입니다. 컨트롤러와 장치가 요구하는 acknowledge, mask, end-of-interrupt 순서는 방식에 따라 달라질 수 있습니다. 공통 IRQ flow handler가 존재하는 이유를 이해할 수 있는 지점입니다.

level 방식에서 장치의 원인 상태를 해소하지 않은 채 복귀하면 같은 요청이 다시 관찰될 수 있습니다. 반대로 사건을 잘못 지우면 후속 처리가 필요했던 일을 잃을 수도 있습니다. 실제 장치 레지스터의 의미는 하드웨어 문서와 드라이버가 정하므로 이 장의 단순 스위치 모델을 모든 장치에 그대로 적용하면 안 됩니다.

공유 IRQ라면 드라이버가 이번 알림이 자기 장치의 사건인지 확인해야 할 수 있습니다. IRQ 번호 하나와 장치 한 개를 항상 일대일 대응시키지 않습니다. 관측에서 예상보다 IRQ가 많은 경우에는 이벤트율뿐 아니라 공유 여부, 반복 알림, 드라이버 처리 방식도 함께 확인합니다.

05

worked example: 패킷 여덟 개와 알림 두 번

개념적인 NIC 큐에 패킷 여덟 개가 순서대로 들어온다고 가정합니다. 패킷마다 IRQ를 보낸다면 알림 여덟 번과 각각의 진입·복귀 비용이 생깁니다. 장치나 드라이버가 여러 패킷을 한 번의 알림에 묶으면 IRQ가 두 번만 발생해도 패킷 여덟 개를 처리할 수 있습니다. 이 숫자는 원리를 설명하기 위한 예시이며 실제 장치 측정이 아닙니다.

첫 알림에서 핸들러가 데이터 처리의 필요성을 표시하고 이후 polling 단계가 큐에서 준비된 항목을 처리한다고 생각해 봅니다. IRQ 카운터는 둘 늘었는데 처리 카운터는 여덟 늘 수 있습니다. 이 둘을 같다고 가정하면 패킷 손실을 잘못 판단하거나 처리량을 네 배 낮게 추정하게 됩니다.

묶음 처리는 진입 비용을 줄이지만 첫 패킷이 다음 항목을 기다리는 시간이나 polling까지의 지연을 늘릴 수 있습니다. 처리량에 유리한 설정이 짧은 요청의 지연에는 불리할 수 있다는 뜻입니다. 변화 전후에 초당 IRQ뿐 아니라 처리량·드롭·지연 분포를 함께 비교해야 합니다.

06

타이머와 CPU 간 알림

타이머는 일정 시간이 지났다는 사건을 커널에 알립니다. 스케줄링 회계, 타임아웃과 지연 작업 등 여러 기능이 시간 기반 사건에 의존합니다. 다만 현대 커널은 모든 CPU가 항상 고정 간격 tick을 같은 방식으로 받는 단순 모델만으로 설명할 수 없습니다. idle과 tickless 관련 설정에 따라 동작이 달라집니다.

다른 CPU에 작업을 요청하는 IPI도 외부 장치 IRQ와 구분해 볼 필요가 있습니다. 예를 들어 다른 CPU가 특정 상태를 다시 확인하게 하거나 주소 변환 관련 변경을 알리는 작업은 CPU 사이의 협력을 요구합니다. 장치가 없는데 인터럽트 관련 카운터가 증가하는 것이 이상한 현상은 아닙니다.

타이머가 만료된 시점과 기다리던 task가 실제 실행된 시점은 다릅니다. 알림 처리, runnable 전환, 스케줄러 선택이 사이에 들어갈 수 있습니다. 실시간 응답을 분석할 때는 이 구간을 분리하고, 단순한 타이머 해상도 숫자로 최악 지연을 보장하지 않습니다.

07

PREEMPT_RT와 실행 문맥

PREEMPT_RT 구성에서는 많은 IRQ 처리를 스레드 문맥으로 옮겨 선점 가능성과 우선순위 제어를 높입니다. 하지만 모든 인터럽트 처리 코드가 자유롭게 잠들 수 있게 바뀐다는 뜻은 아닙니다. 최소 hardirq 처리와 raw lock 등 남아 있는 제약을 구분해야 합니다.

같은 이름의 락도 RT와 비 RT에서 구현 의미가 달라질 수 있으므로 오래된 책의 규칙을 모든 빌드에 기계적으로 적용하면 안 됩니다. 드라이버가 사용하는 API의 계약과 실제 실행 문맥을 함께 읽어야 합니다. 기능이 커널에 포함된 것과 실습 VM에서 RT가 활성화된 것은 별도 사실입니다.

RT 차이는 이 본문의 개념 비교이며 현재 인터랙티브 실험은 로컬 IRQ 마스킹과 pending 알림만 다룹니다. threaded IRQ에서는 스케줄링 가능한 실행 주체가 추가된다는 점을 별도로 생각하세요. RT를 켜면 모든 interrupt-off 구간이 사라진다고 설명하지 않습니다.

08

관측할 때 지켜야 할 단위

/proc/interrupts는 CPU별 누적 통계와 IRQ 관련 정보를 보여 주지만 환경에 따라 상세 항목이 다릅니다. 한 번의 스냅샷보다 일정 시간 간격의 증가량이 유용합니다. 증가량은 사건 처리 빈도에 대한 근거이며 해당 경로가 소비한 CPU 시간이나 사용자 지연 자체는 아닙니다.

게스트 VM에서는 가상 장치와 하이퍼바이저의 스케줄링이 개입합니다. 게스트의 IRQ 처리 지연이 모두 물리 장치 지연이라는 결론은 성립하지 않습니다. 호스트가 vCPU를 실행하지 않은 시간과 게스트 내부 경쟁을 분리해야 더 정확한 설명을 할 수 있습니다.

읽기 전용 실습에서는 짧은 관측으로 IRQ와 softirq 통계가 독립적인 집계임을 확인합니다. IRQ affinity나 interrupt coalescing을 변경하는 튜닝은 별도 실험으로 남깁니다. 설정 변경을 원인 입증 전에 수행하면 여러 변수가 한꺼번에 달라져 비교가 어려워집니다.

09

로컬 IRQ 마스킹은 무엇을 멈추는가

인터랙티브 모델에서 pending 알림을 켜고 로컬 IRQ 마스킹을 켜면 알림은 보류 상태로 남습니다. 이 모델은 하나의 마스킹 가능한 알림을 컨트롤러가 유지한다고 가정합니다. CPU가 아직 핸들러를 실행하지 않았다는 뜻이지, 장치가 데이터를 받거나 DMA를 수행하는 물리 동작 자체가 모두 중지했다는 뜻은 아닙니다.

마스크를 해제하면 보류된 요청을 처리할 기회가 생깁니다. 실제 하드웨어는 사건을 합치거나 큐에 쌓거나 넘칠 때 잃는 방식이 다를 수 있습니다. 그러므로 인터럽트 열 번을 막았다가 풀면 반드시 핸들러가 열 번 실행된다는 산술을 적용하지 않습니다. 데이터 큐의 상태를 확인하는 드라이버 로직이 필요한 이유입니다.

로컬이라는 범위도 중요합니다. CPU A의 IRQ를 비활성화해도 CPU B가 같은 공유 메모리를 접근하는 것을 막지 못합니다. 또한 NMI와 동기적 예외까지 일반 마스킹으로 모두 막는다고 생각해서는 안 됩니다. 로컬 IRQ 제어는 특정 재진입을 통제하는 수단이며 시스템 전체의 만능 락이 아닙니다.

IRQ를 오래 막는 구간이 있다면 CPU 사용률이 낮아 보이는 순간에도 응답 지연이 커질 수 있습니다. 중요한 것은 막은 총시간뿐 아니라 가장 긴 연속 구간과 그 구간에 도착한 중요한 이벤트입니다. 평균값만으로 최대 지연 요구를 검증하지 않는다는 원칙을 이 사례에서 확인할 수 있습니다.

10

지연을 네 구간으로 나누기

개념적인 요청에서 장치 완료까지 40단위, 완료 후 IRQ 핸들러 진입까지 5단위, 후속 처리까지 10단위, 대기 task의 CPU 재획득까지 15단위가 걸렸다고 가정합니다. 전체 응답 지연은 70단위입니다. 장치만 두 배 빨라져도 마지막 세 구간이 그대로라면 50단위가 되어 전체가 두 배 빨라지지는 않습니다. 숫자는 설명용이며 실측이 아닙니다.

이 분해는 최적화 대상을 선택하게 해 줍니다. 핸들러 진입 전 구간이 길다면 IRQ 마스킹이나 CPU 가용성 관련 증거를 보고, 후속 처리 큐 대기가 길면 worker 또는 polling 진행을 봅니다. 깨어난 task가 CPU를 늦게 얻는 문제를 장치 timeout 설정으로 해결하려는 시도는 원인 계층이 다릅니다.

실제 추적에서는 각 이벤트가 같은 시계 기준으로 기록되었는지 확인해야 합니다. 장치 timestamp와 CPU 추적 시각이 다른 기준일 수 있고, 관측 지점이 작업 시작인지 완료인지도 구분해야 합니다. 서로 다른 도구의 숫자를 근거 없이 빼서 정확한 지연이라고 보고하지 않습니다.

IRQ 처리 시간이 짧아졌는데 전체 응답이 개선되지 않을 수도 있습니다. 핸들러에서 하던 일을 후속 큐로 옮기면 한 구간의 숫자는 줄지만 전체 작업량은 남고 큐 대기가 늘 수 있기 때문입니다. 개선은 개별 함수 시간과 요청 전체 지연을 함께 비교해야 한다는 원칙을 다시 적용합니다.

11

polling을 선택할 때의 비용

이벤트가 아주 자주 발생하면 매번 알림을 받고 진입하는 비용이 커질 수 있습니다. 일정 구간 동안 큐를 직접 확인하며 여러 항목을 처리하는 polling은 이런 비용을 묶을 수 있습니다. 그러나 일이 없을 때도 계속 확인하면 CPU와 전력을 사용하므로 낮은 부하에서는 다른 선택이 유리할 수 있습니다.

실제 네트워크 수신처럼 알림과 polling을 조합하는 설계는 부하에 따라 두 접근의 장점을 활용하려는 것입니다. 인터럽트가 적어졌다는 사실만 보지 말고 polling이 CPU를 얼마나 쓰며 장치 큐가 넘치지 않는지 확인합니다. 이후 네트워크 장에서 NAPI의 예산과 완료 조건으로 이 관계를 확장합니다.

전력 절약과 최저 지연도 교환 관계가 될 수 있습니다. CPU가 깊은 idle 상태에 들어가면 전력은 줄어들 수 있지만 깨어나는 비용이 추가될 수 있습니다. 여기서 특정 튜닝 값을 보편적 정답으로 제시하지 않고 workload의 지연 목표·처리량·전력 요구를 함께 정하는 이유입니다.

현재 UI에서 pending을 끈 상태는 처리할 요청이 없는 상황입니다. 마스크를 해제해도 새 사건을 만들어 내지는 않습니다. 알림의 존재와 CPU의 처리 허용 여부라는 두 독립 상태를 나눠 보면 장치·컨트롤러·CPU의 책임이 더 분명해집니다.
