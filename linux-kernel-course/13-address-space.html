01

주소 공간·할당자·물리 메모리

프로그램이 malloc으로 1MiB를 요청할 때 적어도 세 층을 구분해야 합니다. 응용 프로그램은 사용할 객체 공간을 요청하고, libc 할당자는 자신이 관리하는 영역에서 적절한 블록을 찾으며, 커널은 프로세스의 가상 주소 영역과 물리 페이지를 관리합니다. malloc 호출 하나와 커널 페이지 할당 하나는 같은 단위의 사건이 아닙니다.

작은 요청은 이미 확보한 공간의 빈 블록에서 처리될 수 있습니다. 이 경우 malloc이 반환하더라도 새로운 brk나 mmap 시스템 콜이 발생하지 않을 수 있습니다. 반대로 할당자가 새 영역을 확보한 경우에도 그 영역의 모든 물리 페이지가 즉시 준비되는 것은 아닙니다. API, 가상 매핑, 실제 접근이라는 세 시점을 분리합니다.

이 장에서는 malloc을 이해하는 데서 시작해 VMA·페이지 테이블·TLB·페이지 폴트까지 내려갑니다. libc 내부를 커널의 일부로 설명하지 않습니다. 다른 할당자를 쓰면 bin·arena·반환 정책은 바뀔 수 있지만 가상 주소와 물리 페이지를 구분해야 한다는 기본 원리는 유지됩니다.

숫자도 계층에 맞춰 읽습니다. 요청한 객체 크기, 할당자가 예약한 총 영역, 프로세스의 가상 주소 크기, 실제 resident 페이지의 양은 서로 다릅니다. 사용자가 보는 메모리 그래프가 어느 값을 표시하는지 모르면 malloc과 free 결과를 잘못 해석할 수 있습니다.

02

VMA는 영역의 정책, 페이지 테이블은 변환

커널의 VMA는 연속된 가상 주소 구간과 그 속성을 설명합니다. 읽기·쓰기·실행 권한, 사적 또는 공유 매핑, 파일과의 연결 같은 정보가 여기 관련됩니다. 여러 스레드가 공유하는 주소 공간은 mm_struct로 나타내며 Linux 6.18에서는 VMA 탐색에 Maple Tree 기반 관리가 사용됩니다.

페이지 테이블은 특정 가상 주소의 페이지가 어떤 물리 메모리에 대응하는지와 접근 관련 상태를 다룹니다. VMA가 있다고 모든 페이지 테이블 항목에 물리 페이지가 이미 연결된 것은 아닙니다. 유효한 영역을 예약해 두고 첫 접근 시 페이지를 준비하는 demand paging이 가능하기 때문입니다.

같은 프로세스에서 VMA 메타데이터를 안정적으로 읽는 락과 페이지 테이블을 갱신하는 락은 역할이 다릅니다. 영역의 존재를 확인한 것만으로 그 영역 아래 모든 페이지의 현재 변환이 고정되는 것은 아닙니다. 소스를 읽을 때 영역 정책과 실제 매핑 상태를 한 구조로 합쳐 생각하지 않습니다.

/proc/PID/maps는 영역과 권한을 빠르게 보는 데 유용합니다. 하지만 각 페이지가 RAM에 있는지, 공유 비율은 얼마인지까지 보여 주지는 않습니다. 그런 질문에는 smaps·smaps_rollup 등 추가 정보가 필요하며 읽는 동안 상태가 변할 수 있다는 관측 한계도 있습니다.

03

TLB와 주소 변환의 빠른 경로

CPU는 매번 메모리 접근마다 모든 단계의 페이지 테이블을 메모리에서 다시 읽으면 비용이 커집니다. TLB는 최근 주소 변환을 캐시해 이 비용을 줄입니다. TLB hit라면 빠르게 변환을 사용할 수 있고, miss라면 하드웨어 또는 아키텍처별 처리로 필요한 변환을 찾아 채워야 합니다.

TLB miss와 페이지 폴트는 같은 사건이 아닙니다. TLB에 변환이 없어도 유효한 페이지 테이블 항목이 있으면 페이지를 새로 할당하거나 디스크를 읽지 않고 변환을 찾아 진행할 수 있습니다. fault는 매핑 부재나 권한 조건 등 별도의 이유로 커널의 처리가 필요한 경우입니다.

커널이 매핑이나 권한을 바꾸면 CPU가 오래된 변환을 계속 사용하지 않도록 필요한 TLB 무효화를 수행해야 합니다. 여러 CPU에서 같은 주소 공간이 실행 중이면 CPU 간 협력이 필요할 수 있습니다. 주소 공간 변경은 페이지 테이블 메모리에 값을 쓰는 것만으로 끝나는 작업이 아닙니다.

큰 페이지는 하나의 TLB 항목으로 더 넓은 주소 범위를 덮을 수 있어 변환 부담을 줄일 수 있습니다. 그러나 물리 연속성, 메모리 낭비, 할당·분할·회수 비용의 교환이 생깁니다. 16장에서 huge page를 메모리 압박과 함께 다시 다루며 항상 빠르다는 단정은 피합니다.

WATCH THE STATE CHANGE

주소 토큰이 TLB hit와 page fault 경로를 지나간다

같은 유효한 가상 주소를 접근합니다. 준비된 변환을 쓰는 경우와 첫 접근으로 페이지를 준비하는 경우를 비교하세요.

작은 화면에서는 그림을 좌우로 밀어 전체 경로를 볼 수 있습니다.

가상 주소 접근

아직 준비되지 않은 유효 매핑의 first-touch 사례입니다. 모든 TLB miss가 이 경로로 가는 것은 아닙니다.

이렇게 비교해 보세요

  1. fault 경로에서는 물리 페이지 토큰이 free pool에서 사용 영역으로 이동합니다.
  2. 유효 PTE가 있는 TLB miss는 별도의 숫자 실험에서 비교합니다.

유효 VMA·허용된 접근·페이지 1개의 개념 모델. 실제 페이지 테이블 단계·fault 실패·THP·TLB shootdown 비용은 생략합니다.

04

malloc의 재사용과 glibc 정책

glibc malloc은 크기에 따른 재사용 구조와 스레드 관련 캐시를 사용해 빈번한 작은 요청의 비용을 줄일 수 있습니다. tcache나 bin에 적합한 블록이 있다면 커널에 새 영역을 요청하지 않고 반환할 수 있습니다. 이 동작은 특정 libc 구현의 정책이며 Linux 시스템 콜 계약 자체는 아닙니다.

할당자가 더 넓은 영역을 필요로 할 때 brk를 통해 전통적인 heap 영역을 조절하거나 mmap을 통해 별도 영역을 얻을 수 있습니다. 어느 크기에서 어떤 경로를 선택하는지는 구현·설정·동적 정책에 달려 있습니다. 흔히 언급되는 임계값 하나를 모든 glibc 버전과 프로세스에 고정된 규칙처럼 외우지 않습니다.

여러 스레드가 전역 할당자 상태 하나에서 경쟁하면 병목이 생길 수 있어 arena와 스레드 캐시 같은 구조가 쓰입니다. 이는 경합을 줄이는 대신 메모리 보유량과 조각화를 늘릴 수 있습니다. 스레드 수가 많아진 뒤 RSS가 커졌을 때 요청한 객체 크기만 계산하면 이 차이를 설명하지 못합니다.

할당자의 메타데이터는 사용자 객체 앞뒤나 별도 구조에 있을 수 있지만 교육용 관찰에서 p[-1] 같은 잘못된 메모리 접근을 하지 않습니다. C 객체의 범위를 벗어난 읽기는 정의되지 않은 동작입니다. 문서화된 통계 API나 시스템 콜 추적, 별도 모델을 통해 내부 원리를 배웁니다.

CHANGE ONE THING

주소 변환과 page fault

가상 주소를 페이지 번호·offset으로 나누고 TLB hit, 유효 PTE의 TLB miss, PTE not present를 비교합니다. first touch는 fault 원인 중 하나이며 모든 TLB miss가 fault는 아닙니다.

JavaScript를 켜면 조건을 바꾸며 실험할 수 있습니다. 아래 본문과 실습은 그대로 읽을 수 있습니다.

05

worked example: 예약, 첫 쓰기, 해제

기본 페이지 크기가 4KiB라고 가정하고 16MiB 익명 매핑을 예약합니다. 계산상 4096개의 기본 페이지 범위입니다. 매핑 생성 직후에는 가상 주소 영역이 늘어도 전체 범위에 쓰기용 물리 페이지가 준비되지 않았을 수 있습니다. 실제 페이지 크기와 THP 정책에 따라 물리 매핑의 단위는 달라질 수 있습니다.

이제 각 4KiB 구간에 한 바이트씩 씁니다. 첫 쓰기는 아직 준비되지 않은 페이지의 fault 처리를 유발할 수 있고 커널은 페이지를 준비해 사용자 매핑에 연결합니다. 16MiB의 객체를 선언한 시점과 이 루프에서 실제 resident 메모리가 늘어나는 시점이 다른 이유입니다.

4096이라는 계산을 곧바로 minor fault 증가량의 정답으로 사용하지 않습니다. THP, 이미 준비된 매핑, 다른 런타임 초기화와 측정 자체의 동작이 영향을 줄 수 있습니다. 실험의 목적은 정확한 카운터 일치보다 예약 단계와 first-touch 단계의 방향 차이를 관찰하는 것입니다.

그다음 free를 호출하면 libc가 해당 블록을 재사용 가능 상태로 돌릴 수 있습니다. 커널에 즉시 반환하지 않으면 가상 매핑과 resident 페이지가 남을 수 있습니다. mmap 기반의 독립 영역 해제, heap 축소, madvise를 통한 물리 페이지 반환은 서로 다른 경로입니다. “끝부분만 RAM을 반환할 수 있다”는 일반화는 틀립니다.

06

왜 free 뒤에도 RSS가 남는가

free의 API 약속은 해당 객체 공간을 더 이상 사용하지 않고 할당자가 재사용할 수 있게 한다는 것입니다. 프로세스의 RSS가 바로 줄어든다는 약속은 아닙니다. 반복해서 비슷한 크기를 할당한다면 메모리를 보유해 재사용하는 정책이 시스템 콜과 페이지 fault 비용을 줄일 수 있습니다.

내부 조각화는 요청 크기보다 큰 관리 단위를 사용하면서 남는 공간이고 외부 조각화는 빈 공간이 여러 조각으로 나뉘어 필요한 형태의 요청을 충족하기 어려운 상황입니다. 합계 빈 바이트가 충분해도 적절한 연속 블록이나 반환 가능한 페이지 구간이 없을 수 있습니다.

arena와 tcache에 남은 블록, 일부 살아 있는 작은 객체가 들어 있는 페이지 때문에 요청한 live 객체 총량보다 실제 보유량이 클 수 있습니다. 이것이 항상 누수는 아니지만 무조건 정상이라고 무시해서도 안 됩니다. live 객체 추이, 할당자 통계, RSS/PSS와 반복 부하 후 안정 여부를 함께 봅니다.

glibc의 malloc_trim 같은 인터페이스는 가능한 메모리를 반환하려는 시도에 사용할 수 있지만 모든 메모리를 강제로 회수하는 보편적인 해법은 아닙니다. 호출 비용과 이후 재할당 비용도 있고 다른 할당자에 그대로 적용되지 않습니다. 먼저 어떤 계층이 메모리를 보유하는지 확인한 뒤 평가합니다.

07

페이지 폴트는 여러 종류의 작업이다

유효한 익명 매핑의 첫 쓰기, fork 뒤 COW 쓰기, 파일 매핑의 아직 준비되지 않은 페이지 접근은 모두 fault 경로와 연결될 수 있지만 해야 하는 일은 다릅니다. 어떤 경우는 새 페이지를 준비하고 어떤 경우는 기존 내용을 복사하며 어떤 경우는 파일 데이터를 가져와야 합니다.

minor fault는 저장 장치에서 페이지를 가져오는 I/O 없이 해결되는 경우를 나타내는 분류이고 major fault는 I/O를 수반하는 처리와 연결됩니다. 하지만 카운터 이름만으로 모든 지연 크기를 예측하지 않습니다. minor fault도 페이지 할당과 락 경쟁 때문에 비용이 클 수 있고 측정 구간의 다른 활동이 섞일 수 있습니다.

유효한 영역이 아니거나 허용되지 않은 접근이면 fault를 정상 매핑 준비로 해결하지 못할 수 있습니다. 사용자 공간에서 시그널로 나타나는 경우가 대표적입니다. 따라서 “page fault가 많다”는 말과 “프로그램이 잘못된 주소를 읽었다”는 말은 동의어가 아닙니다.

프로세스가 받은 가상 주소 예약 성공이 미래의 모든 메모리 접근 성공을 보장하지는 않습니다. 시스템의 overcommit 정책과 실제 메모리 압박, cgroup 제한이 이후 할당 시점에 영향을 줄 수 있습니다. allocation API 반환과 실제 실행 중 자원 확보를 구분해야 합니다.

08

COW·공유 매핑·보호 변경

fork 뒤의 사적 매핑은 논리적 독립성을 유지하면서 물리 페이지 복사를 늦출 수 있습니다. 읽기만 하면 페이지를 공유하고 쓰기 시 필요한 분리가 일어납니다. 주소 숫자가 같아도 부모와 자식의 주소 공간은 별개이며 나중에 서로 다른 물리 페이지로 연결될 수 있습니다.

MAP_SHARED 매핑은 쓰기를 다른 매핑 참여자와 공유하려는 정책입니다. MAP_PRIVATE는 사적 변경을 유지하기 위한 정책이므로 파일 매핑에서 쓰기가 COW로 익명 메모리에 나타날 수 있습니다. 둘 다 mmap으로 생성된다는 이유만으로 변경의 가시성과 저장 의미가 같다고 보지 않습니다.

mprotect 같은 보호 변경은 VMA 속성과 페이지 테이블·TLB 관련 작업을 수반할 수 있습니다. 사용자 주소 영역 하나의 권한 변경도 여러 내부 상태의 일관성을 유지해야 하는 일입니다. 빠른 사용자 공간 읽기 경로를 위해 관리 작업이 커널 쪽에 모이는 구조를 이해할 수 있습니다.

주소 공간의 배치를 읽을 때 ASLR 때문에 실행마다 주소가 바뀔 수 있습니다. 실습에서는 특정 절대 주소를 정답으로 쓰지 않고 구간 크기, 권한, 파일 연결, 변화 전후의 관계를 비교합니다. 이 방식이 다른 배포판과 아키텍처에서도 더 잘 적용됩니다.

09

관측 계획: 무엇을 비교할 것인가

실습은 시작 직후, 예약 직후, 페이지별 쓰기 후, free 후의 네 시점을 비교하는 방식이 유용합니다. 같은 프로세스의 같은 실행 안에서 보면 런타임 초기화 차이를 줄일 수 있습니다. 가상 크기·RSS·fault 누적값·시스템 콜을 각각 어떤 계층의 증거인지 표시합니다.

getrusage의 ru_maxrss는 최대 resident 크기이므로 메모리를 반환해도 내려가지 않는 값입니다. 이 필드를 현재 RSS라고 표시하면 free 이후 메모리가 줄지 않는다는 잘못된 결론을 낼 수 있습니다. 현재 상태가 필요하면 적합한 procfs 필드를 사용하고 최고점과 구별합니다.

strace에서 brk·mmap·munmap·madvise를 보면 할당자가 커널에 요청한 영역 관련 작업을 볼 수 있습니다. 그러나 재사용 bin에서 처리한 모든 malloc/free는 보이지 않습니다. 시스템 콜이 없다는 관측을 allocation이 없었다는 결론으로 바꾸지 않습니다.

별도 malloc 실험실에서는 split·coalesce와 재사용 정책을 조작해 볼 수 있습니다. 이 장의 모델은 주소 변환과 first touch를, 부록은 사용자 공간 할당자의 관리 결정을 강조합니다. 두 모델을 연결하되 glibc의 모든 최적화와 실제 CPU 비용을 정확히 재현한다고 주장하지 않습니다.

10

현재 실험에서 직접 확인할 것

주소 변환 실험은 가상 주소를 4KiB 페이지 번호와 offset으로 나누고 TLB hit, 유효 PTE가 있는 TLB miss, PTE가 준비되지 않은 상태를 비교합니다. 예를 들어 12345는 3×4096+57이므로 페이지 번호 3과 offset 57입니다. malloc의 first-touch 과정은 이 중 매핑 준비가 필요한 경로와 연결되지만 모든 TLB miss가 allocation을 일으키는 것은 아닙니다.

모델은 유효한 읽기 가능 VMA를 가정하므로 권한 위반이나 잘못된 주소의 오류 시그널은 별도 사례입니다. 상태 선택을 바꿀 때 CPU의 변환 캐시에 없는 것과 커널이 새로 매핑을 준비해야 하는 것을 구분해 설명해 보세요.

같은 숫자의 가상 주소라도 프로세스의 주소 공간이 다르면 다른 데이터에 연결될 수 있습니다. 반대로 서로 다른 가상 주소가 같은 물리 페이지를 공유할 수도 있습니다. 현재 실험은 한 주소 공간의 변환을 보여 주므로 프로세스 간 공유와 COW는 본문의 별도 사례와 연결해 해석합니다.

#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/resource.h>
static void snap(const char *name) {
    struct rusage u;
    if (getrusage(RUSAGE_SELF, &u) == 0)
        printf("%s: minor=%ld major=%ld peak_rss_kib=%ld\n",
               name, u.ru_minflt, u.ru_majflt, u.ru_maxrss);
}
int main(void) {
    size_t n = 16u * 1024u * 1024u;
    long page = sysconf(_SC_PAGESIZE);
    if (page <= 0) return 1;
    snap("before");
    volatile unsigned char *p = malloc(n);
    if (!p) return 1;
    snap("allocated");
    for (size_t i = 0; i < n; i += (size_t)page) p[i] = 1;
    snap("touched");
    free((void *)p);
    snap("freed");
    return 0;
}

예상 관측과 해석

allocated와 touched 사이 fault 누적값 변화가 관측될 수 있습니다. peak_rss_kib는 최고점이므로 free 뒤 줄지 않아도 정상이며 현재 RSS를 나타내지 않습니다.

혼동하기 쉬운 점

  • glibc의 크기 임계값과 arena·tcache 정책을 모든 Linux 할당자의 불변 규칙으로 설명하지 않습니다.
  • heap 축소 제약을 모든 물리 메모리 반환에 일반화하지 않습니다. madvise 등 다른 경로가 있습니다.
  • 할당 블록 앞의 비공개 메타데이터를 포인터 범위 밖 접근으로 읽지 않습니다.
