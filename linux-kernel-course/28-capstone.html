01

28.1 먼저 네 가지 가설을 분리한다

교육용 사례입니다. 8 vCPU 서버에서 API p99가 80ms에서 240ms로 늘었지만 호스트 CPU 평균은 25%입니다. 요청률과 응답 크기는 이전과 같고 오류율은 변하지 않았습니다. 이 숫자만으로 CPU 원인을 배제하거나 네트워크를 원인으로 지목할 수 없습니다.

가설 A는 특정 CPU 또는 run queue 경합, B는 메모리 회수, C는 저장 장치 대기, D는 cgroup CPU 제한입니다. 네 가설은 다른 관측을 요구합니다. A는 CPU별 실행과 runnable 대기, B는 reclaim·fault·PSI, C는 block latency·큐, D는 cpu.max와 throttling 증가를 조사합니다.

첫 조사에서는 변경 없이 같은 10초 구간의 지표를 모읍니다. 서비스 PID와 cgroup, 배포 버전, 요청률, CPU affinity를 확인합니다. 다른 시간의 CPU 평균과 지금의 p99를 연결하거나 시스템 전체 수치와 서비스 한정 수치를 섞지 않습니다.

02

28.2 증거 카드를 읽고 결론의 강도를 정한다

추가 교육 데이터에서는 서비스 cgroup cpu.max가 100000 100000으로 설정되어 있습니다. 8 vCPU 호스트라도 서비스의 CPU 예산은 기간당 합계 1 CPU 상당입니다. 네 개의 계산 스레드가 동시에 달리면 예산을 빠르게 소모하고 나머지 기간에 제한될 수 있습니다.

같은 10초 동안 nr_throttled가 90 증가하고 요청 지연이 긴 구간과 겹칩니다. memory PSI와 I/O PSI는 낮고 장치 지연도 이전과 비슷합니다. 이 조합은 CPU quota 제한을 우선 조사할 근거이지만, 다른 원인이 절대 없다는 증명은 아닙니다.

다음 증거로 runnable 상태인데 cgroup 제한 때문에 실행하지 못한 구간과 응답 지연의 관계를 확인합니다. 예산 소모가 높은 이유도 조사합니다. 최근 코드가 계산량을 늘렸다면 quota 증가는 증상을 완화할 수 있어도 불필요한 CPU 비용이라는 문제를 남길 수 있습니다.

03

28.3 개선 시험은 한 가지 원인을 검증한다

시험 환경에서 요청률·데이터·동시성을 유지하고 CPU 한도만 바꾸는 실험을 계획합니다. throttling과 p99가 함께 줄면 제한 가설이 강화됩니다. 공유 서버에서는 한도 변경이 다른 작업의 성능에 영향을 줄 수 있으므로 서비스 전체와 이웃 작업의 지표도 확인합니다.

한도를 바꿀 권한이 없다면 작업 동시성을 줄이는 대안을 시험할 수 있습니다. 예산을 소비하는 형태가 달라져 꼬리 지연이 줄 수도 있지만 처리량도 줄 수 있습니다. p99 하나만 보고 성공이라고 결론내리지 말고 완료 요청 수, 큐 길이, 오류를 함께 비교합니다.

실제로 메모리 압력이나 디스크 대기가 높은 변형 사례라면 같은 처방을 반복하지 않습니다. 메모리에서는 working set과 한도·회수를, I/O에서는 캐시와 블록 대기를 조사합니다. 하나의 성공 사례를 모든 느린 서버에 적용하지 않는 것이 종합 실습의 핵심입니다.

04

28.4 조사 보고서를 재현 가능한 형태로 마친다

보고서의 첫 부분에는 사용자 영향과 측정 경계를 씁니다. 예를 들어 같은 요청률에서 p99가 증가했고 서비스 cgroup의 quota 제한 카운터가 함께 증가했다고 적습니다. CPU가 낮다는 모호한 문장 대신 호스트 전체 평균인지 서비스 CPU 사용인지 명시합니다.

다음에는 배제하지 못한 가설과 필요한 증거를 기록합니다. 스케줄링 추적을 하지 않았다면 quota 카운터만으로 개별 요청의 지연을 완전히 설명했다고 쓰지 않습니다. 실험 데이터와 실제 운영 관측도 분리해서 읽는 사람이 증거의 수준을 알 수 있게 합니다.

마지막에는 변경 전후의 동일 조건, 실행 횟수, 지연 분포, 처리량, 오류, 자원 비용을 나란히 둡니다. 이 과정의 도달점은 도구 이름을 많이 아는 것이 아니라 요청이 어느 경계에서 기다렸는지 설명하고 다음 검증을 스스로 고르는 능력입니다.

05

28.5 교육용 관측표를 시간과 범위로 정렬한다

가상 사례의 첫 표에는 시각 12:00:00부터 12:00:10까지 요청률 200/s, 완료율 200/s, p99 240ms, 호스트 전체 CPU 평균 25%, 서비스 cpu.max 100000 100000을 둡니다. 두 번째 표에는 같은 구간의 nr_throttled 증가 90, 낮은 memory·I/O PSI, 이전과 비슷한 장치 지연을 둡니다. 이 숫자는 실제 실행 결과가 아니라 추론을 연습하기 위한 교육 데이터입니다.

누적 카운터는 시작값과 종료값을 빼고 gauge는 그 구간의 요약 방식을 명시합니다. p99는 요청 표본에서 계산한 분포 값이므로 카운터처럼 두 시점을 빼지 않습니다. 서로 다른 성격의 지표를 같은 표에 놓더라도 계산 방식은 다릅니다. 단위를 생략하면 CPU 시간의 마이크로초와 벽시계 밀리초를 혼동할 수 있습니다.

호스트 평균 25%와 1 CPU 상당의 서비스 한도는 모순되지 않습니다. 다른 프로세스도 CPU를 쓰고, 서비스가 제한되는 시점에는 호스트에 여유가 남을 수 있습니다. 이 표에서 확인한 사실은 서비스가 제한을 경험했다는 것이며 개별 느린 요청의 원인을 완전히 확정하려면 요청 시간과 제한 구간의 연결이 더 필요합니다.

06

28.6 가설마다 반증 가능한 예측을 적는다

CPU 경합 가설은 서비스가 runnable인데 실행을 기다리는 구간이 늘고 CPU별 경쟁 또는 제한이 관측될 것이라고 예측합니다. 메모리 압력 가설은 회수와 fault, memory PSI 또는 메모리 관련 대기 변화가 같은 구간에 나타날 것이라고 예측합니다. 단순히 모든 지표를 수집하는 대신 각 가설이 맞다면 어떤 증거가 달라져야 하는지 미리 적습니다.

스토리지 가설은 요청의 파일 I/O 구간과 블록 지연, 큐 변화가 연결될 것이라고 예측합니다. 네트워크 가설을 추가한다면 소켓 대기, 재전송, 상대 응답과 큐의 위치를 봅니다. 관측이 예측과 맞지 않으면 가설을 낮추거나 범위가 잘못됐는지 확인합니다. 가설을 지키기 위해 관측하지 않은 원인을 계속 덧붙이지 않습니다.

quota 가설의 반증 실험은 같은 작업량에서 제한을 완화했을 때 제한 카운터와 지연이 어떻게 변하는지 보는 것입니다. 제한은 줄었는데 p99가 그대로라면 다른 지배적 경로가 남았을 가능성이 있습니다. 한 번의 상관으로 원인을 확정하는 것보다 이런 조건부 예측과 실패 가능성을 갖춘 실험이 더 강한 증거를 제공합니다.

07

28.7 요청의 critical path를 그린다

API 요청이 인증 5ms, CPU 계산 20ms, 동시에 실행한 두 외부 조회 40ms와 80ms, 응답 조립 5ms로 구성됐다고 가정합니다. 외부 조회가 실제로 병렬이면 두 시간을 더한 120ms가 아니라 늦게 끝나는 의존 경로가 응답 시점을 결정할 수 있습니다. 실행 흐름의 의존 관계를 모르고 모든 span을 합치면 요청 시간이 과장됩니다.

CPU quota로 계산 구간 중간에 75ms의 정지가 삽입되면 이후 외부 조회의 시작도 늦어질 수 있습니다. 요청 말미에 네트워크 대기가 보인다고 최초 원인이 네트워크라고 단정하면 안 됩니다. 앞선 CPU 제한이 후속 작업의 시작 시점을 밀었는지, 이미 시작한 외부 작업을 기다렸는지 타임라인으로 구분해야 합니다.

실험에서는 동일 요청 식별자와 monotonic 시간 기준으로 단계의 시작과 끝을 기록합니다. 서로 다른 기계의 wall clock은 오차가 있을 수 있으므로 직접 뺄 때 동기화 조건을 확인합니다. 커널 이벤트와 애플리케이션 span을 연결할 때에도 PID·스레드·시간 기준이 맞는지 검증합니다.

08

28.8 변형 사례 A: 낮은 free 메모리의 함정

같은 p99 증가 상황에서 free 메모리가 적다는 신호를 추가해 봅시다. 이것만으로 메모리 부족을 확정하면 안 됩니다. page cache가 큰 정상 상태일 수도 있습니다. memory.current의 구성, reclaim과 swap 변화, memory PSI, 요청의 fault 지연을 확인해야 메모리가 실제로 진행을 방해했는지 판단할 수 있습니다.

교육용 변형에서 memory PSI가 높고 major fault와 저장소 읽기가 함께 증가하며 working set이 cgroup 한도보다 크다면 회수와 재읽기 가설이 강해집니다. 이 경우 CPU quota를 늘려도 필요한 페이지가 계속 밀려나면 문제는 남을 수 있습니다. 원래 사례의 성공 처방을 숫자 하나가 비슷한 다른 장애에 그대로 적용하지 않습니다.

시험 환경에서는 working set이나 동시 작업 수를 줄이거나 메모리 한도를 변경해 압력과 지연이 함께 변하는지 확인할 수 있습니다. 캐시를 지워 상태를 강제로 바꾸는 실험은 기존 부하를 교란하므로 기본 관측 단계에서 수행하지 않습니다. 실험의 목적과 영향을 명확히 한 뒤 별도 환경에서 한 변수만 바꿉니다.

09

28.9 변형 사례 B: 빠른 디스크인데 느린 read

장치의 블록 완료 시간은 이전과 비슷하지만 애플리케이션의 read 시간이 늘었다는 변형을 생각합니다. 디스크가 빠르다는 관측이 read 경로 전체가 빠르다는 뜻은 아닙니다. 파일 시스템 락, 메모리 할당, 완료 후 runnable 대기, 사용자 공간에서 측정한 추가 작업이 포함되었을 수 있습니다.

먼저 두 측정의 경계를 맞춥니다. read 호출 시작부터 반환까지인지, 버퍼 처리와 파싱까지 포함했는지 확인합니다. block tracepoint의 요청 시간과 해당 read를 연결할 수 있는지 검토하고, 그 안의 실행·대기 구간을 스케줄링 관측과 함께 봅니다. 서로 다른 파일과 작업의 평균을 비교해 모순이라고 판단하지 않습니다.

이 변형에서 quota로 완료 후 실행이 늦어졌다면 장치 교체는 핵심 처방이 아닐 수 있습니다. 반대로 block 지연과 큐도 증가했다면 하위 I/O 경로 조사로 이동합니다. 좋은 조사는 미리 정한 도구나 처방을 끝까지 고수하는 것이 아니라 새 증거에 따라 원인 경계를 좁혀 갑니다.

10

28.10 개선 전후 결과를 읽는 세 가지 경우

첫 번째 결과는 quota 완화 후 throttling이 크게 줄고 p99도 240ms에서 90ms로 낮아지며 처리량과 오류가 유지된 경우입니다. 교육용 이 결과는 제한이 중요한 기여 원인이었다는 근거를 강화합니다. 그러나 증가한 CPU 비용과 다른 서비스에 미친 영향, 반복 실행에서의 일관성을 확인하기 전에는 운영 적용의 최종 판단이 끝난 것은 아닙니다.

두 번째 결과는 p99가 낮아졌지만 완료율이 200/s에서 100/s로 줄어든 경우입니다. 동시성 축소로 부하 자체가 낮아졌을 수 있으므로 같은 처리량에서 더 빨라졌다고 보고할 수 없습니다. 대기열이 외부 클라이언트나 upstream으로 이동했는지 확인합니다. 측정 경계 밖으로 대기를 밀어냈다면 사용자의 종단 지연은 개선되지 않을 수 있습니다.

세 번째 결과는 제한 카운터는 줄었지만 p99가 그대로인 경우입니다. quota가 존재한 사실은 맞더라도 현재 p99의 지배적 원인이 아니었을 수 있습니다. 큰 다른 대기나 데이터 경로가 남았는지 다시 분해합니다. 효과 없는 변경을 계속 쌓는 대신 원래 조건과 새로운 증거를 기록하고 다음 가설을 선택합니다.

11

28.11 최종 보고서의 문장을 근거 수준에 맞춘다

관측 문장은 “같은 10초 동안 서비스 cgroup의 nr_throttled가 90 증가했고 p99가 240ms였다”처럼 씁니다. 가설 문장은 “CPU budget 제한이 긴 응답에 기여했을 가능성이 높다”로 분리합니다. 검증 문장은 “같은 요청률의 시험 환경에서 quota만 바꾸어 제한과 지연의 변화를 비교했다”로 쓰며 실제 수행하지 않았다면 계획이라고 표시합니다.

소스 근거는 가능한 동작을 설명하고 로그와 계측은 실제 실행을 보여줍니다. kernel/sched/fair.c에 bandwidth 제한 코드가 있다는 사실만으로 이번 요청이 그 경로 때문에 느렸다고 입증되지는 않습니다. 반대로 카운터만 보고 왜 그런 제한이 가능한지 설명하지 못하면 다른 환경에서 결과를 일반화하기 어렵습니다. 두 종류의 근거를 역할에 맞게 연결합니다.

마지막으로 미확인 항목과 재현 범위를 적습니다. 다른 배포판 config나 CPU 아키텍처, 다른 트래픽에서는 결과가 달라질 수 있습니다. 이 교재의 28장은 모든 커널 문제의 답을 외우는 과정이 아니라 사용자의 현상을 실행 주체와 자원, 대기, 수명으로 분해하고 증거에 맞는 다음 행동을 고르는 훈련입니다.

12

28.12 조사 방향을 먼저 고르고 다음 증거로 검증한다

이 장의 브라우저에는 증거 묶음과 먼저 조사할 영역이라는 두 선택지가 있습니다. CPU 사용률과 runnable 대기, 디스크 지연과 I/O PSI, 호스트 CPU 여유와 throttling, major fault와 memory PSI라는 네 조합을 바꿀 수 있습니다. 정답을 외우기 전에 각 신호가 어느 자원의 진행 방해를 시사하는지 설명하세요. 결과 카드는 첫 조사 우선순위를 평가하며 원인 확정을 대신하지 않습니다.

예를 들어 호스트 CPU 여유와 nr_throttled 증가 묶음에서 스토리지 I/O를 먼저 선택해 보세요. 모델은 우선순위를 재검토하라고 안내합니다. 디스크 문제는 절대로 없다는 뜻이 아니라, 지금 제공한 증거를 더 직접적으로 설명하는 제한 경로가 있다는 뜻입니다. CPU 예산으로 바꾼 뒤에는 cpu.max의 범위와 같은 기간의 cpu.stat 변화가 실제 대상 서비스에 해당하는지 확인할 계획을 적습니다.

major fault와 memory PSI 묶음에서는 작업 집합과 회수를 우선 조사합니다. 여기서 모든 major fault가 swap이라는 결론을 내리지 않습니다. 파일 기반 페이지를 가져오는 경로도 고려해야 하고, 압력이 전체 호스트인지 해당 cgroup인지 구분해야 합니다. 실제로는 프로세스 매핑과 메모리 구성, 회수·swap·파일 I/O 카운터를 같은 구간에 연결해 어떤 페이지가 반복해서 필요해지는지 좁힙니다.

가상의 보고서를 완성할 때 첫 줄은 현재 증거가 직접 보여 주는 사실로 쓰고, 둘째 줄은 원인 가설, 셋째 줄은 가설이 맞다면 추가로 보일 변화, 넷째 줄은 이를 검증할 제한된 비교 실험으로 씁니다. 예를 들어 quota를 바꾸는 시험은 요청률과 완료 작업량을 유지해야 하며, 권한이나 환경이 준비되지 않았다면 실행 결과가 아니라 제안된 검증 계획으로 남깁니다.

마지막으로 같은 카드에 다른 병목이 겹친 경우를 상상해 보세요. quota 제한을 완화한 뒤 메모리 압력이 커질 수 있고, 장치 대기를 줄이자 CPU 계산이 다음 병목이 될 수 있습니다. 이때 원래 판정이 전부 틀렸다고 단정하거나 모든 조정을 한꺼번에 추가하지 않습니다. 새 상태의 실행 지도를 다시 그리고 다음 큰 구간을 같은 절차로 조사합니다. 한 번의 정답 선택보다 재현 가능한 관측과 수정의 반복이 이 과정의 최종 실습입니다.

Linux VM / Shell · C
cg_rel=$(awk -F: '$1=="0" {print $3}' /proc/$$/cgroup)
cg_dir="/sys/fs/cgroup$cg_rel"
for sample in 1 2; do
  printf '\n--- sample %s ---\n' "$sample"
  date -Is
  for f in cpu.max cpu.stat memory.current memory.events cpu.pressure memory.pressure io.pressure; do
    if [ -r "$cg_dir/$f" ]; then printf '%s\n' "$f"; cat "$cg_dir/$f"; fi
  done
  if [ "$sample" = 1 ]; then sleep 2; fi
done
