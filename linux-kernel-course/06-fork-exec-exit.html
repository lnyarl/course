01

fork는 실행 주체를 만든다

셸이 새 명령을 실행하는 대표적인 경로는 자식 실행 주체를 만들고 그 안에서 프로그램 이미지를 교체하는 것입니다. fork는 부모와 유사한 상태로 자식을 만들며 부모에는 자식 PID, 자식에는 0을 반환합니다. 반환값이 이후 제어 흐름을 나누는 기준입니다.

fork 직후 부모와 자식의 메모리 내용이 같다고 해서 모든 메모리 바이트를 즉시 두 벌 복사한 것은 아닙니다. 페이지 테이블 등 필요한 관리 상태를 준비하면서 일반적인 사적 쓰기 가능 페이지는 COW를 이용해 물리 페이지 공유를 유지할 수 있습니다.

열린 파일 디스크립터도 구분이 필요합니다. 부모와 자식의 fd 테이블은 별개일 수 있지만 항목이 같은 open file description을 참조하면 파일 오프셋과 상태 플래그를 공유합니다. 메모리 복사 방식과 파일 상태 공유 방식은 동일하지 않습니다.

02

execve는 프로그램 이미지를 교체한다

execve가 성공하면 현재 실행 주체의 주소 공간과 실행 이미지를 새 프로그램으로 바꿉니다. 새로운 PID를 만드는 호출이 아니며 기존 프로그램의 다음 명령으로 정상 반환하지 않습니다. 실패한 경우에는 오류를 반환하므로 호출한 코드가 처리할 수 있습니다.

실행 파일 형식 처리와 동적 로더의 동작도 구분합니다. 커널이 ELF의 필요한 정보를 읽어 초기 실행 환경을 만들고, 동적 링크된 프로그램은 지정된 인터프리터를 거쳐 라이브러리 준비와 사용자 코드 진입을 수행할 수 있습니다.

새 이미지로 바뀌어도 모든 상태가 무조건 초기화되지는 않습니다. close-on-exec 표시가 없는 열린 파일 디스크립터처럼 유지되는 항목이 있습니다. 이 때문에 셸의 파이프와 입출력 리다이렉션을 새 프로그램이 그대로 사용할 수 있습니다.

03

COW의 이득과 쓰기 비용

부모와 자식이 공유 중인 COW 페이지를 읽기만 하면 별도 데이터 복사를 피할 수 있습니다. 한쪽이 쓰려고 하면 보호 예외를 통해 커널이 쓰기 경로를 처리하고 필요한 경우 새 페이지를 할당·복사한 뒤 그쪽 매핑을 갱신합니다.

COW의 비용은 fork 시점에서 첫 쓰기 시점으로 이동할 수 있습니다. 따라서 fork가 빨랐다는 사실이 이후 메모리 작업 비용까지 사라졌다는 뜻은 아닙니다. 자식이 곧 exec하는 경우와 부모·자식이 많은 메모리를 계속 수정하는 경우의 비용 구조가 다릅니다.

COW와 공유 메모리는 목적이 다릅니다. MAP_SHARED로 공유하는 매핑은 쓰기를 다른 참여자에게 보이게 하려는 것이고, 사적 COW 매핑은 논리적으로 독립된 내용을 유지하려는 것입니다. 물리 페이지를 잠시 공유한다는 공통점만으로 같은 동작이라 생각하지 않습니다.

04

종료와 수거는 다른 단계다

task가 실행을 끝내면 많은 자원이 해제되지만 부모가 종료 상태를 받을 때까지 일부 종료 정보가 남을 수 있습니다. 이것이 좀비 상태의 핵심입니다. 좀비가 CPU에서 계속 실행 중인 것은 아니며 종료 상태를 보관하는 관리 정보가 남은 것입니다.

부모는 wait 계열 호출로 자식의 종료 상태를 수거합니다. 정상 종료 코드와 시그널에 의한 종료를 구분해 처리할 수 있습니다. 부모가 먼저 끝난 경우의 재부모화와 subreaper 정책도 수명 관리에 영향을 줍니다.

관측에서는 생성, 이미지 교체, 실행 종료, 부모의 수거를 별도 이벤트로 나눕니다. PID가 보인다는 사실만으로 실행 중이라고 판단하지 않습니다. 반대로 짧게 실행된 자식은 ps 스냅샷 사이에 생성·종료될 수 있으므로 추적 도구가 필요할 수 있습니다.

05

셸의 명령 실행을 다섯 개의 사건으로 나누기

셸에서 /bin/sleep 0.1을 실행하는 대표적인 흐름을 떠올려 봅시다. 셸은 명령과 인자를 준비하고 자식을 만들며, 자식은 필요하면 입출력 연결을 바꾼 뒤 execve로 sleep의 실행 이미지를 설치합니다. 부모 셸은 기다리거나 다른 명령을 처리할 수 있습니다. 실제 셸과 libc는 clone, vfork 또는 posix_spawn 계열의 다른 경로를 사용할 수 있으므로 이 설명은 역할의 구분이지 특정 호출 목록의 보장이 아닙니다.

fork가 성공하면 부모와 자식은 같은 호출 지점에서 서로 다른 반환값을 받아 실행을 이어갑니다. 부모는 자식 PID를 받고 자식은 0을 받습니다. 이 두 반환을 보고 부모 쪽에서만 수행할 일과 자식 쪽에서만 수행할 일을 나눕니다. 소스의 fork 호출 문장이 하나라는 이유로 이후 코드도 한 번만 실행된다고 생각하면 안 됩니다. 반대로 실패했을 때는 자식이 만들어지지 않으므로 오류 경로가 필요합니다.

자식이 execve에 성공하면 기존 프로그램 이미지의 다음 줄로 돌아오는 것이 아니라 새 이미지의 시작 경로로 넘어갑니다. PID는 유지될 수 있으므로 프로세스 ID가 같아도 실행 파일과 주소 공간이 크게 바뀔 수 있습니다. 모니터링에서 PID와 명령 이름을 한 번 읽은 뒤 영원히 고정된 조합으로 취급하면 이런 전환을 놓칩니다. 생성 사건과 이미지 교체 사건을 별도로 기록해야 합니다.

sleep이 끝나면 실행 종료가 일어나고 부모는 wait 계열 인터페이스로 결과를 수거합니다. 부모는 자식이 정상 종료했는지, 어떤 종료 코드를 냈는지, 시그널 때문에 끝났는지를 구분할 수 있습니다. 단순히 PID가 사라졌는지만 관찰하면 이런 결과 정보를 놓칠 수 있습니다. 종료를 기다리는 API는 자식의 수명과 결과 전달을 연결하는 계약입니다.

이 다섯 사건을 추적 로그와 맞출 때는 행이 꼭 보기 좋은 순서로 나올 것이라고 기대하지 않습니다. 부모와 자식은 동시에 실행될 수 있고, 추적 출력도 각 실행 주체의 이벤트를 섞어 보여 줍니다. PID 표시를 따라 생성→이미지 교체→종료→수거를 연결해 보세요. 출력 순서만 따라 읽기보다 실행 주체별 시간선을 그리면 동시 실행의 구조가 드러납니다.

06

16페이지 COW 계산: 같은 주소와 같은 물리 메모리

부모가 이미 사용 중인 사적 익명 페이지 16개를 가지고 있다고 합시다. 기본 페이지 크기를 4 KiB로 가정하면 데이터 부분은 64 KiB입니다. fork 뒤 부모와 자식이 해당 페이지를 읽기만 한다면 데이터 페이지를 즉시 32개로 만들 필요는 없습니다. 독립된 논리 주소 공간이 같은 물리 페이지를 잠시 참조할 수 있습니다. 이때 주소 공간의 독립성은 이후 쓰기가 상대의 내용을 바꾸지 않는다는 의미로 지켜집니다.

자식이 서로 다른 페이지 4개에 처음 쓰고 부모는 쓰지 않는 경우를 생각해 보세요. 단순 모델에서는 그 4개가 분리되어 총 고유 데이터 페이지가 20개가 됩니다. 아직 공유하는 12개와 부모·자식의 별도 페이지 8개를 합한 수입니다. 자식이 이미 분리한 한 페이지에 다시 쓴다고 매번 새로운 복사본을 계속 만드는 것은 아닙니다. 첫 분리와 이후의 일반 쓰기를 구분해야 합니다.

이 장의 슬라이더를 0에서 4로 옮기면 고유 페이지와 추가 메모리 수가 늘어납니다. 16까지 옮기면 모든 데이터 페이지가 분리되어 단순 모델의 총량은 32페이지입니다. 페이지 테이블, 커널 관리 구조, 라이브러리와 스택, huge page 관련 동작은 계산에서 제외했습니다. 실제 프로세스의 RSS를 단순히 두 배 해 고유 물리 메모리 사용량을 구하면 공유 페이지를 중복 집계할 수 있다는 점도 기억하세요.

COW는 항상 처음부터 복사하는 방식과 비용을 다르게 배치합니다. 자식이 곧 exec한다면 부모의 많은 데이터 페이지를 읽거나 쓰지도 않고 버릴 수 있으므로 불필요한 복사를 피합니다. 반대로 부모와 자식이 거의 모든 페이지를 수정하면 이후 fault와 복사 비용이 발생합니다. 생성 시점의 빠른 응답과 작업 전체의 메모리·지연 비용을 따로 측정해야 하는 이유입니다.

가상 매핑을 만들었다는 사실만으로 이 계산의 출발 조건이 성립하지는 않습니다. 예약한 주소 공간과 실제로 준비된 물리 페이지는 다를 수 있습니다. 또한 읽기만 한 익명 페이지와 실제로 사적 쓰기를 한 페이지의 상태도 구분해야 합니다. 모델은 이미 존재하는 16개의 사적 데이터 페이지를 명시적으로 가정하며, malloc이나 mmap 직후의 모든 페이지가 자동으로 그 상태라고 설명하지 않습니다.

07

자식의 쓰기가 부모의 값을 바꾸지 않는 작은 프로그램

아래 예제는 Linux VM에서 한 개의 사적 익명 매핑을 만들고 첫 바이트에 A를 쓴 뒤 fork합니다. 자식은 같은 가상 주소의 첫 바이트를 B로 바꾸고 종료합니다. 부모는 자식의 종료를 기다린 다음 자신의 첫 바이트를 출력합니다. 기대되는 의미는 부모의 값이 A로 유지된다는 것입니다. 이것은 별도 주소 공간의 사적 쓰기 계약을 확인하는 예제이며 물리 페이지 복사 횟수를 직접 측정하는 프로그램은 아닙니다.

먼저 페이지 크기를 sysconf로 구하고 mmap의 실패를 확인합니다. 고정된 4096이라는 숫자를 모든 환경의 실제 페이지 크기라고 가정하지 않기 위해서입니다. fork 실패 때는 자식이 없으므로 부모가 자신의 매핑을 정리하고 끝냅니다. 자식은 값을 바꾼 뒤 _exit로 종료하고, 부모는 waitpid로 자식 결과를 수거합니다. 예제에서도 자원 생성과 정리, 오류 처리를 함께 보세요.

코드를 cow_demo.c로 저장한 뒤 C 컴파일러가 있는 Linux VM에서 cc -Wall -Wextra -O0 cow_demo.c -o cow_demo로 빌드할 수 있습니다. 이 교재 작성 과정에서는 해당 Linux 프로그램을 실행하지 않았으므로 출력은 예상 의미로 제공합니다. 다른 결과가 나오면 빌드한 파일, 매핑 플래그, 부모·자식 분기와 출력 위치를 먼저 확인합니다. 소스와 다른 바이너리를 실행하지 않았는지도 확인해야 합니다.

MAP_PRIVATE를 MAP_SHARED로 바꾸면 학습 질문이 달라집니다. 그 경우는 서로 독립된 사적 변경이 아니라 같은 매핑의 변경을 공유하려는 계약을 사용합니다. 하지만 플래그 하나를 바꿨다고 임의의 복잡한 데이터 구조가 자동으로 동기화되는 것은 아닙니다. 이 예제는 부모가 waitpid 이후 읽는 작은 순서만 사용하며, 실제 공유 구조의 동시 수정은 별도의 동기화 설계가 필요합니다.

실험의 숫자와 이 프로그램을 연결할 때는 증명 범위를 구분합니다. 브라우저는 고유 페이지 수의 계산을 보여 주고, C 예제는 사적 변경이 부모에게 보이지 않는 관찰을 제공할 수 있습니다. 실제 물리 메모리 분리량은 더 적절한 메모리 관측과 환경 통제가 필요합니다. 한 가지 결과를 보고 다른 계층의 비용까지 검증했다고 확장하지 않는 습관이 중요합니다.

#define _GNU_SOURCE
#include <sys/mman.h>
#include <sys/wait.h>
#include <unistd.h>
#include <errno.h>
#include <stdio.h>
int main(void) {
    long page = sysconf(_SC_PAGESIZE);
    if (page <= 0) return 1;
    unsigned char *p = mmap(NULL, (size_t)page, PROT_READ | PROT_WRITE,
                            MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }
    p[0] = 'A';
    pid_t child = fork();
    if (child == -1) { perror("fork"); munmap(p, (size_t)page); return 1; }
    if (child == 0) { p[0] = 'B'; _exit(0); }
    int status;
    while (waitpid(child, &status, 0) == -1) {
        if (errno != EINTR) { perror("waitpid"); munmap(p, (size_t)page); return 1; }
    }
    printf("parent sees: %c\n", p[0]);
    if (munmap(p, (size_t)page) == -1) { perror("munmap"); return 1; }
    return WIFEXITED(status) && WEXITSTATUS(status) == 0 ? 0 : 1;
}
08

fork 뒤에 남는 것: fd·버퍼·다른 스레드의 흔적

fork는 여러 종류의 상태를 같은 방법으로 복사하지 않습니다. 메모리는 사적 논리 주소 공간과 COW의 관계를 가지지만 열린 fd는 같은 open file description을 참조할 수 있습니다. 그래서 부모가 파일 위치를 움직인 결과가 자식의 다음 읽기에 영향을 줄 수 있습니다. 프로세스가 분리되었다는 말에서 모든 외부 자원의 상태도 독립되었다는 결론을 끌어내면 안 됩니다.

사용자 공간의 출력 버퍼는 또 다른 함정을 만듭니다. printf의 데이터가 아직 libc 버퍼에만 남은 상태에서 fork하면 그 버퍼 내용이 양쪽 주소 공간에 나타날 수 있습니다. 이후 부모와 자식이 각각 버퍼를 내보내면 원래 한 번 만든 문자열이 두 번 출력될 수 있습니다. 커널이 과거의 write를 다시 실행한 것이 아니라, 복사된 사용자 공간 상태가 나중에 두 경로에서 사용된 것입니다.

다중 스레드 프로세스에서 fork한 자식에는 호출한 스레드만 이어지는 점도 중요합니다. 다른 스레드가 잠금을 보유한 시점의 메모리 상태가 남아 있는데 그 락을 해제할 실행 주체는 자식에 없을 수 있습니다. 그래서 자식의 exec 이전 경로에서 임의의 라이브러리 함수를 호출하는 것은 위험할 수 있습니다. 해당 환경의 async-signal-safe 제한과 fork 관련 런타임 계약을 확인해야 합니다.

exec 때 닫아야 하는 fd는 close-on-exec 같은 수명 정책으로 관리할 수 있습니다. 새 프로그램이 알 필요 없는 관리용 소켓이나 파일이 남으면 자원 유출뿐 아니라 예상치 못한 접근 경로가 생길 수 있습니다. 반면 표준 입출력이나 의도한 파이프 fd는 새 이미지에서 계속 사용해야 합니다. 무조건 모두 보존하거나 모두 닫는 대신 어느 경계를 넘어갈 자원인지 정해야 합니다.

좀비는 이런 실행 중인 자원 공유와 다른 단계의 현상입니다. 자식이 이미 끝났지만 부모가 종료 정보를 아직 수거하지 않은 상태입니다. CPU에서 계속 계산하거나 원래의 전체 사용자 메모리를 그대로 보유하는 실행 중 프로세스로 해석하지 않습니다. 부모가 결과를 수거하는지, 어떤 프로세스가 자식을 거두는 역할을 맡는지 확인해야 하며 무작정 다른 신호를 보내는 방식으로 원인을 설명할 수 없습니다.
