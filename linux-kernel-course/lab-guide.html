BEFORE YOU START

실습 환경과 C 코드 읽기

브라우저에서 개념을 먼저 익히고, Linux VM에서 관측합니다. 명령이 실패하면 개념이 틀렸다고 결론내리기 전에 버전·설정·권한을 확인하세요.

1. 브라우저와 Linux를 분리합니다

도식, 입력 실험, 퀴즈는 브라우저에서 실행되며 추가 패키지가 필요하지 않습니다. 커널 실습은 Linux 환경이 필요합니다. macOS의 터미널은 Linux 커널이 아니므로 /proc, perf, strace 명령을 그대로 실행할 수 없습니다. Docker 컨테이너도 호스트 또는 Docker VM의 커널을 공유하므로 독립적인 실습 커널을 부팅한 것과 다릅니다.

권장 구성은 폐기 가능한 Linux VM 한 대, 2–4 vCPU, 4 GiB 이상의 RAM입니다. 커널 빌드는 더 많은 디스크와 시간이 필요하므로 24장에서 따로 다룹니다. RAM 크기는 교재 모델과 별개입니다. 자신의 호스트 여유 자원에 맞추고, 실습 전 VM 스냅샷을 남기세요. 이 과정이 호스트 설정이나 운영 서버를 바꾸도록 요구하지는 않습니다.

6.18.x LTS 커널로 부팅한 환경을 기준으로 합니다. 배포판 기본 커널이 다르면 대부분의 관측 실습은 가능하지만, 그 결과를 6.18의 실행 증거라고 기록하지 마세요. x86-64를 설명 기준으로 삼되 ARM64 VM에서도 일반적인 시스템 콜·프로세스·메모리 실습은 사용할 수 있습니다.

2. 실행 조건부터 기록합니다

아래 명령은 관측용입니다. 출력의 주소·PID·커널 버전은 매번 달라도 됩니다. 핵심은 같은 실험의 전후를 비교할 때 환경이 바뀌지 않았는지 확인하는 것입니다. 도구가 없으면 해당 단계가 미실행임을 기록하고, 사용하는 배포판의 패키지 관리 절차로 준비하세요.

uname -r
uname -m
getconf PAGESIZE
getconf GNU_LIBC_VERSION  # glibc 환경에서만 의미 있음
cat /etc/os-release
command -v cc strace perf vmstat iostat pidstat
cat /proc/meminfo
cat /proc/sys/kernel/perf_event_paranoid
cat /proc/sys/kernel/kptr_restrict
cat /sys/kernel/mm/lru_gen/enabled 2>/dev/null
cat /sys/kernel/mm/transparent_hugepage/enabled 2>/dev/null
cat /proc/self/cgroup

필수 기본 도구는 C 컴파일러와 make, procps 계열 도구, strace입니다. I/O 관측에는 sysstat 계열 도구가, 추적에는 실행 커널과 호환되는 perf·tracefs·필요한 권한이 필요합니다. eBPF 도구는 커널 설정·BTF·배포판 정책에 따라 사용할 수 없을 수 있습니다. 권한 오류를 해결하려고 전역 보안 설정을 먼저 낮추지 마세요. VM 안에서 해당 실습에 필요한 권한만 사용합니다.

정확한 설정 파일은 배포판마다 다릅니다. /boot/config-$(uname -r) 또는 설정된 경우 /proc/config.gz에서 확인합니다. 파일이 없다는 사실만으로 기능이 없다고 판정할 수는 없습니다. 기능의 실제 인터페이스와 문서를 함께 확인합니다.

4. C 포인터는 주소 값입니다

int *p는 정수가 들어 있는 주소를 가리키는 변수입니다. p라는 포인터를 복사해도 가리키는 메모리까지 복사되는 것은 아닙니다. *p를 바꾸면 같은 메모리를 가리키는 다른 포인터에서도 새 값을 봅니다. 이 구분은 커널의 공유 객체, 참조 수, 수명 문제를 읽는 기초입니다.

#include <stdio.h>
struct task_demo { int state; int priority; };
int main(void) {
    struct task_demo a = { .state = 1, .priority = 10 };
    struct task_demo *p = &a;
    struct task_demo *alias = p;
    alias->state = 2;
    printf("%d %d\n", a.state, p->state); /* 2 2 */
    return 0;
}

p->state는 (*p).state와 같은 접근입니다. 구조체는 관련 상태를 묶지만, 구조체가 있다고 자동으로 동시성 제어가 생기지는 않습니다. 다른 CPU가 같은 필드를 바꾸면 락이나 원자적 연산, 메모리 순서 규칙을 별도로 검토해야 합니다.

주소 산술의 단위도 주의합니다. int *p에 1을 더하면 보통 한 바이트가 아니라 sizeof(int)만큼 이동합니다. 주소와 크기는 uintptr_t, size_t 등 목적에 맞는 타입으로 다룹니다. 할당 범위를 벗어나거나 free 이후에 접근하면 정상적인 관측 실험이 아니라 정의되지 않은 동작이 됩니다.

5. 사용자 C 코드와 커널 C 코드는 다릅니다

사용자 프로그램은 libc의 malloc, printf를 사용합니다. 커널 모듈은 이를 그대로 호출하지 않습니다. 커널의 할당 API, 로깅 API, 실행 문맥 규칙을 사용해야 합니다. 사용자 코드에서 동작한 패턴을 커널 코드에 복사하면 잠들 수 없는 문맥에서 잠들거나 사용자 포인터를 잘못 접근할 수 있습니다.

예제 사용자 프로그램은 cc -O0 -g -Wall -Wextra demo.c -o demo로 시작합니다. 최적화가 관측을 바꿀 수 있으므로 학습용 실행과 벤치마크를 구분합니다. 성능 비교에서는 같은 옵션, 반복 횟수, 입력, 워밍업 조건을 기록하고 출력·추적 오버헤드를 측정 구간에서 분리합니다.

실패 반환도 학습 내용입니다. 사용자 API는 실패 시 -1과 errno를 쓰는 경우가 많지만 모든 API가 동일한 것은 아닙니다. mmap 실패는 MAP_FAILED, malloc 실패는 NULL입니다. 커널 내부의 음수 errno와 사용자 공간 래퍼의 반환 계약도 구분하세요.

6. 결과를 네 줄로 정리합니다

  1. 가설: 반복 읽기가 빨라지는 이유가 page cache 때문일 것이다.
  2. 조건: 커널·파일 크기·메모리·실행 횟수·도구를 기록한다.
  3. 관측: 시간, fault, I/O 발생량의 전후 차이를 적는다.
  4. 판정: 증거가 지지하는 범위와 아직 구분하지 못한 원인을 적는다.

프로파일러에서 한 함수가 오래 보인다는 사실만으로 그 함수의 계산이 비싸다고 결론내리지 않습니다. 실행 중인지, 락을 기다리는지, I/O를 기다리는지 구분합니다. 이 방식이 28장 종합 실습까지 이어집니다.
