01

CPU가 여러 개면 메모리도 여러 관점으로 보인다

여러 CPU가 같은 메모리를 사용해도 모든 load와 store가 소스 코드 순서 그대로 동시에 전역에 보인다고 가정할 수는 없습니다. 컴파일러는 의미를 보존하는 범위에서 코드를 바꾸고 CPU는 성능을 위해 접근을 겹쳐 실행합니다. 단일 스레드에서는 같은 결과여도 다른 CPU의 관찰과 결합하면 순서가 중요해집니다.

캐시 일관성은 공유 위치에 대한 캐시 상태를 일관되게 관리하는 기반이지만 여러 위치 사이의 게시 순서를 자동으로 모두 해결하지 않습니다. 데이터 구조를 먼저 채우고 준비 플래그를 세우는 코드에서 다른 CPU가 플래그를 보고 데이터를 안전하게 읽을 수 있는지는 별도의 메모리 순서 계약에 달립니다.

따라서 “CPU 캐시가 일관되니 락 없이도 된다”와 “한 CPU에서만 테스트했으니 안전하다”는 결론은 성립하지 않습니다. 필요한 것은 어떤 관찰이 허용되면 안 되는지를 먼저 정하고, 그 관찰을 배제하는 동기화 관계를 만드는 일입니다. 강한 순서의 아키텍처에서 우연히 보이지 않던 오류가 다른 환경에서 드러날 수 있습니다.

커널의 메모리 모델은 C/C++ 사용자 코드의 모델과 완전히 같은 표기만으로 설명되지 않습니다. READ_ONCE, release/acquire, barrier, RCU API의 각각의 계약을 문서로 확인합니다. 도식은 원리를 설명하지만 특정 원자 명령이나 모든 CPU의 세부 동작을 대신하지 않습니다.

02

worked example: 준비 플래그의 함정

생산자 P가 data=42를 쓰고 ready=1을 쓴다고 가정합니다. 소비자 C는 ready가 1이면 data를 읽습니다. 우리가 원하는 결과는 ready가 게시된 것을 본 소비자가 그 전에 준비한 data도 보는 것입니다. 서로 다른 두 메모리 위치에 대한 요구이므로 ready의 접근만 나눠지지 않는다고 충분하지 않습니다.

release 게시와 acquire 관찰을 올바르게 연결하면 생산자의 앞선 준비 작업과 소비자의 이후 읽기 사이에 필요한 순서 관계를 만들 수 있습니다. 중요한 것은 소비자가 그 게시를 실제로 관찰하는 경로입니다. 임의의 barrier를 코드 아무 곳에 하나 넣었다고 모든 CPU의 모든 동작이 순서대로 되는 것은 아닙니다.

락의 획득과 해제도 해당 API가 약속하는 순서 관계를 제공합니다. 이미 일관된 락 프로토콜을 쓰고 있다면 같은 보호 상태에 불필요한 추가 barrier를 흩뿌리는 것은 추론을 어렵게 만들 수 있습니다. 먼저 기존 도구가 보장하는 범위를 이해한 뒤 부족한 관계만 추가합니다.

이 예시에서는 data 객체의 수명이 계속 유지된다고 가정했습니다. 실제 코드에서 생산자가 곧바로 객체를 해제할 수 있다면 올바른 게시 순서만으로 안전하지 않습니다. 소비자가 읽는 동안 객체가 살아 있다는 수명 보장이 추가로 필요합니다. 순서 문제와 수명 문제를 분리하는 이유입니다.

03

false sharing: 다른 변수인데 왜 경쟁하는가

CPU A와 B가 서로 다른 카운터를 계속 갱신하더라도 두 카운터가 같은 캐시 라인에 있다면 라인의 쓰기 소유권이 CPU 사이를 오갈 수 있습니다. 논리적으로 공유하지 않는 데이터가 하드웨어 단위 때문에 경쟁하는 false sharing입니다. 변수에 락이 없다는 사실이 캐시 비용도 없다는 뜻은 아닙니다.

예를 들어 CPU별 카운터 두 개가 인접한 작은 정수로 배치되어 있고 각 CPU가 자기 항목만 증가시킨다고 합시다. 결과는 정확할 수 있지만 갱신 빈도가 높으면 캐시 라인 이동이 전체 비용을 지배할 수 있습니다. 카운터 연산의 명령 수만 줄여도 이런 비용은 남습니다.

정렬과 패딩으로 항목을 분리하면 라인 공유를 줄일 수 있지만 메모리 사용량과 캐시 풋프린트가 커집니다. 실제 캐시 라인 크기와 구조체 배치는 아키텍처·빌드에 의존합니다. 모든 객체에 무조건 큰 패딩을 넣으면 오히려 더 많은 메모리와 캐시 미스를 만들 수 있습니다.

비교 실험은 같은 작업량과 CPU 배치 조건에서 수행해야 합니다. 두 스레드가 실제로 같은 CPU에서 번갈아 실행했다면 CPU 간 캐시 이동 효과를 제대로 측정하지 못합니다. 컴파일러가 반복 증가를 최적화해 제거하지 않았는지도 확인해야 합니다. 간단한 루프 시간만으로 원인을 확정하지 않습니다.

04

per-CPU 데이터의 교환 비용

전역 카운터 하나를 모든 CPU가 갱신하는 대신 CPU별 카운터를 두면 쓰기 경합을 줄일 수 있습니다. CPU는 자신의 데이터에 자주 접근하고 전체 합계는 필요할 때 계산합니다. 높은 빈도의 업데이트 비용을 낮추는 대신 조회·통합 비용과 일관성 요구를 바꾸는 선택입니다.

task가 실행 도중 다른 CPU로 이동할 수 있다면 현재 CPU를 기준으로 포인터를 얻고 사용하는 구간의 규칙을 지켜야 합니다. per-CPU라는 이름만으로 이동이나 동시 접근이 자동 방지되는 것은 아닙니다. 해당 API가 선점·migration에 대해 무엇을 보장하는지 확인합니다.

합계를 계산하는 동안 각 CPU가 계속 갱신하면 얻은 값이 단 하나의 완벽한 시점의 스냅샷이 아닐 수 있습니다. 통계처럼 약간의 시차를 허용하는 데이터에는 괜찮을 수 있지만 잔액이나 정확한 재고처럼 강한 일관성을 요구하는 상태에는 같은 설계를 그대로 적용하기 어렵습니다.

CPU hotplug도 수명과 통합 정책에 영향을 줍니다. CPU가 오프라인으로 바뀔 때 남은 상태를 어떻게 처리할지 고려해야 합니다. 이 per-CPU 설명은 개념 사례이며 현재 UI는 CPU 개수 대신 RCU 독자의 종료 시각을 다룹니다. 실제 커널 코드는 초기화·오프라인·회수 경로까지 포함해 읽어야 합니다.

05

RCU는 읽기와 갱신·회수를 나눈다

읽기가 매우 많고 갱신이 상대적으로 적은 구조에서는 모든 읽기가 같은 락을 획득하는 비용을 줄이고 싶을 수 있습니다. RCU는 읽기 구간과 갱신·회수의 관계를 조직하는 메커니즘입니다. 핵심은 새 데이터를 게시하는 시점과 옛 데이터를 실제로 해제하는 시점을 분리하는 것입니다.

갱신자는 새 객체를 준비하고 읽는 쪽이 참조할 포인터를 새 객체로 바꿀 수 있습니다. 이미 옛 포인터를 얻은 독자는 잠시 옛 객체를 계속 읽을 수 있습니다. 이때 옛 객체를 즉시 free하면 use-after-free가 생기므로 기존 독자들이 안전하게 끝났음을 알 수 있는 구간을 기다립니다.

grace period는 해당 회수 판단에 필요한 기존 읽기 구간들이 완료되도록 하는 개념입니다. 미래의 모든 독자가 영원히 사라질 때까지 기다리는 것이 아닙니다. 새 독자는 새 게시물을 볼 수 있고 시스템은 계속 읽기를 수행하면서 옛 객체를 회수할 수 있습니다.

RCU를 읽기 쓰기 락의 완전한 대체물로 보지 않습니다. 독자가 여러 객체에서 정확히 같은 순간의 최신 상태를 요구한다면 추가 설계가 필요합니다. 갱신자끼리의 충돌 방지 역시 별도 락이나 프로토콜로 처리할 수 있습니다. RCU는 여러 요구 중 특정 수명·게시 관계를 해결합니다.

06

worked example: 목록 노드 제거

목록에 A→B→C가 있고 독자 R이 이미 B의 포인터를 얻었다고 가정합니다. 갱신자 U가 A의 다음 포인터를 C로 바꾸면 새 탐색에서는 B를 건너뜁니다. 하지만 R은 여전히 B를 읽고 있으므로 목록에서 연결을 제거한 것과 B 메모리를 해제할 수 있다는 것은 다른 사건입니다.

U는 필요한 RCU 갱신 규칙으로 B를 제거한 뒤, 기존 독자가 안전하게 끝날 때까지 기다리거나 회수 콜백을 예약합니다. R이 읽기 구간을 마친 뒤 적절한 grace period가 완료되면 B를 회수할 수 있습니다. 목록 사례는 종이에 상태를 그려 보는 사고실험입니다. UI에서는 목록 색 대신 기존 독자의 종료 전후에 옛 객체를 회수할 수 있는지를 표시합니다.

만약 U가 B를 제거하자마자 해제하고 같은 주소에 D를 할당하면 R은 전혀 다른 객체를 B라고 읽을 수 있습니다. 이 문제는 값이 오래되었다는 수준보다 심각한 수명 오류입니다. 포인터 값이 여전히 유효한 숫자로 보인다는 사실은 객체 정체성과 수명을 보장하지 않습니다.

RCU 읽기 구간 밖으로 포인터를 가져가 계속 사용하려면 별도의 수명 유지 방법이 필요할 수 있습니다. 예를 들어 안전한 참조 획득 규칙과 참조 카운트를 연결하는 설계를 사용합니다. 단지 rcu_dereference를 호출했다는 이유만으로 포인터를 영구 보관할 수 있다고 생각하지 않습니다.

07

어느 RCU API와 문맥인가

일반 RCU, SRCU 등 계열은 읽기 구간에서 허용하는 동작과 grace period 관리 방식이 다릅니다. “RCU 읽기는 절대 선점되지 않는다”거나 “RCU에서는 언제나 잠들어도 된다” 같은 단일 문장을 모든 구성에 적용하면 틀립니다. 사용하는 API와 커널의 선점 구성에 맞는 계약을 확인해야 합니다.

synchronize_rcu 같은 대기형 호출은 기존 읽기 구간의 종료를 기다릴 수 있으므로 호출 문맥과 락 관계를 고려해야 합니다. 콜백 기반 회수는 호출자가 즉시 기다리지 않도록 할 수 있지만 메모리가 실제 회수되기까지 지연되고 콜백이 누적될 수 있습니다. 대기 비용을 다른 위치로 옮긴 것입니다.

갱신이 매우 빠르고 독자가 오래 머무르면 옛 버전의 메모리가 쌓일 수 있습니다. 읽기 비용이 낮다는 장점만 보고 RCU를 선택하면 회수 지연과 메모리 압박을 놓칠 수 있습니다. 갱신 빈도, 객체 크기, 읽기 구간 길이를 함께 고려합니다.

RCU stall 경고를 봤다면 즉시 특정 락 오류 하나로 단정하지 않습니다. CPU가 너무 오랫동안 필요한 진행을 하지 못하거나 특정 경로에서 오래 머무르는 등 여러 원인이 있을 수 있습니다. 경고의 CPU·task 정보와 스택, 시스템 부하를 함께 읽어야 합니다.

08

도구 선택과 검증의 범위

READ_ONCE·WRITE_ONCE는 특정 접근을 컴파일러가 예상 밖으로 합치거나 다시 읽는 문제를 제어하는 데 사용되지만 완전한 CPU 순서 보장을 대신하지 않습니다. atomic, barrier, 락, RCU의 역할을 하나로 합쳐 외우지 않습니다. 각각 어떤 금지된 결과를 배제하는지 질문하면 도구의 범위를 명확히 할 수 있습니다.

메모리 순서 버그는 일반적인 단위 테스트에서 쉽게 드러나지 않을 수 있습니다. 특정 interleaving이 필요하고 CPU·컴파일러·부하에 따라 발생 빈도가 달라지기 때문입니다. 커널 메모리 모델의 litmus test와 코드의 실제 API 계약 검토는 단순 반복 실행과 다른 근거를 제공합니다.

성능에서는 cache miss나 cache-to-cache 관련 이벤트를 지원하는 환경에서 측정할 수 있지만 이벤트 지원과 권한은 CPU·커널·VM에 따라 다릅니다. 도구가 없거나 이벤트가 지원되지 않는 결과를 false sharing이 없다는 증거로 사용하지 않습니다. 관측하지 못한 상태를 명확히 남깁니다.

이 장의 브라우저 모델은 게시 순서와 회수 시점을 눈으로 분리하는 데 목적이 있습니다. 실제 CPU의 모든 재정렬을 재현하거나 RCU 구현의 정확성을 증명하지 않습니다. 모델에서 배운 질문을 소스의 락·게시·참조·해제 경로에 적용하는 것이 다음 단계입니다.

09

RCU의 메모리 비용을 계산해 보기

객체 한 개가 64KiB이고 갱신이 초당 100번 발생한다고 가정합니다. 옛 객체가 평균 0.2초 동안 회수 대기한다면 단순한 정상 상태 근사에서 약 20개, 즉 1.25MiB의 옛 버전이 추가로 남을 수 있습니다. 실제 콜백 묶음과 갱신 패턴은 더 복잡하지만 낮은 읽기 비용이 메모리 수명 비용과 교환된다는 점을 수치로 볼 수 있습니다.

독자가 예상보다 오래 머물러 회수가 지연되면 보유 객체 수가 더 늘 수 있습니다. 한 번의 포인터 교체가 빠르다는 측정만으로 갱신 경로 전체가 저렴하다고 결론 내리지 않습니다. 장기적인 할당·회수율과 콜백 지연, 메모리 압박을 함께 관찰해야 합니다.

이 모델에서 모든 독자를 전역 mutex로 묶으면 옛 버전을 오래 보관하는 필요를 줄일 수 있지만 읽기 경합과 대기가 늘 수 있습니다. RCU와 mutex 선택은 최신성·수명·갱신 빈도에 따라 달라집니다. 데이터를 언제 읽을 수 있고 얼마나 오래된 상태를 허용하는지를 먼저 정해야 비교가 의미 있습니다.

현재 실험은 한 기존 독자의 종료 시각과 포인터 교체 후 현재 시각을 비교합니다. 현재 시각이 독자 종료 이전이면 회수를 보류하고 이후면 모델상 가능한 단계로 표시합니다. 실제 grace period 구현과 CPU 관찰 조건을 시간 숫자 하나로 대체하는 것이 아니라, 제거와 회수 사이에 반드시 확인해야 할 조건을 드러내는 그림입니다.

10

캐시 라인 단위와 객체 크기

64바이트 캐시 라인을 가정하면 8바이트 카운터 여덟 개가 같은 라인에 들어갈 수 있습니다. 여덟 CPU가 각자 카운터 하나만 바꿔도 라인을 놓고 경쟁할 여지가 있습니다. 논리적 소유권이 분리되어 있다는 코드 수준의 사실과 하드웨어가 이동시키는 단위는 다르다는 점이 false sharing의 핵심입니다.

이를 피하려고 각 카운터를 별도 라인에 두면 데이터 64바이트가 최소 512바이트 배치가 되는 식으로 공간 비용이 늘 수 있습니다. 예시는 특정 머신의 필수 배치가 아니라 단위 간 교환을 보여 줍니다. 실제 정렬·캐시 라인 크기를 확인하고 읽기 패턴과 전체 객체 수까지 고려한 뒤 적용해야 합니다.

카운터를 읽기만 하는 단계와 서로 다른 CPU가 계속 쓰는 단계의 비용도 다릅니다. 패딩 전후를 비교할 때 갱신 횟수와 CPU 배치를 같게 유지하고 전체 처리량뿐 아니라 메모리 사용량도 기록합니다. 모델의 공간 계산은 선택의 대가를 이해하기 위한 것이며 특정 머신의 성능 배수를 예측하지 않습니다.
