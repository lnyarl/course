01

파일을 읽는 일과 장치를 읽는 일

응용 프로그램이 read로 파일을 읽는 것은 커널에 파일 내용을 요청하는 동작입니다. 그 내용이 이미 page cache에 있으면 장치에서 같은 데이터를 다시 읽지 않고 사용자 버퍼로 복사할 수 있습니다. 따라서 시스템 콜 한 번과 물리 디스크 I/O 한 번을 일대일로 대응시키면 실제 경로를 놓칩니다.

page cache는 여러 파일 시스템 접근에서 사용되는 메모리 기반 캐시입니다. 동일 파일의 같은 내용을 여러 프로세스가 읽을 때 활용될 수 있으며 일반적인 buffered read·write와 파일 mmap 경로를 연결합니다. 저장 장치 자체의 캐시나 애플리케이션의 별도 캐시와는 다른 계층입니다.

파일 읽기 지연은 캐시 조회, 필요 데이터 준비, 사용자 버퍼 복사, 스케줄링 대기 등 여러 구간으로 나뉩니다. 두 번째 읽기가 빨랐다는 사실은 캐시의 영향을 의심할 근거이지만 다른 캐시나 장치 상태, CPU 주파수와 측정 오버헤드도 달라질 수 있습니다. 정확한 원인은 추가 관측으로 좁힙니다.

가상 머신에서는 게스트 page cache와 호스트 파일 캐시, 가상 장치 계층이 함께 있을 수 있습니다. 게스트에서 캐시 miss처럼 보인 경로가 호스트 메모리에서 빠르게 처리될 수 있습니다. 실험 환경의 계층을 적지 않으면 “디스크 속도”라고 발표한 숫자가 실제로 어느 캐시의 속도인지 알 수 없습니다.

02

파일 데이터는 어떤 객체에 연결되는가

VFS의 inode는 파일에 대한 메타데이터와 연결되고 address_space는 파일의 캐시된 데이터와 관련된 관리 구조입니다. 이름이 프로세스 가상 주소 공간과 비슷하지만 여기의 address_space를 mm_struct와 동일한 개념으로 읽지 않습니다. 서로 다른 역할의 객체가 파일 mmap 경로에서 만나게 됩니다.

파일의 오프셋과 캐시 엔트리의 관계를 통해 필요한 데이터가 있는지 찾습니다. 경로 문자열이 같다는 것만으로 항상 같은 파일 객체라고 가정해서는 안 됩니다. 이름 변경, 삭제 후 재생성, mount namespace와 파일 시스템 차이가 식별에 영향을 줄 수 있습니다. 열린 파일 참조와 경로 탐색을 구분합니다.

캐시 엔트리가 존재하더라도 데이터가 즉시 읽을 준비를 마쳤다는 뜻은 아닐 수 있습니다. 다른 요청이 데이터를 읽어 오는 중이거나 상태 갱신을 위해 기다려야 할 수 있습니다. “캐시에 있음”과 “완성된 최신 데이터를 지금 사용할 수 있음”은 동시성 때문에 별도 조건이 됩니다.

따라서 소스에서 자료구조 조회 다음에 락·상태 확인·대기가 나오는 이유를 함께 읽습니다. 캐시는 단순한 key-value 메모리 맵이 아니라 데이터 수명, I/O 진행, 쓰기 상태와 회수를 조정하는 구조입니다. 조회 hit만으로 전체 요청 비용이 결정되지 않습니다.

03

folio와 page를 구분하기

현대 Linux의 page cache 설명에서는 folio가 중요합니다. folio는 하나 이상의 기본 페이지를 묶어 다루는 메모리 관리 단위이며, 객체 전체를 대상으로 처리한다는 의미를 명확히 합니다. 모든 folio가 큰 페이지라는 뜻은 아니고 order 0 folio도 있을 수 있습니다.

기본 페이지가 4KiB인 환경에서 16KiB folio를 예로 들면 네 기본 페이지 범위를 함께 관리하는 모델을 생각할 수 있습니다. 하지만 실제 크기 사용 여부는 파일 시스템과 커널 정책, 작업 경로에 달려 있습니다. 이 묶음은 folio 크기를 이해하기 위한 수치 예시입니다. 현재 브라우저 UI는 folio 크기 선택 대신 파일의 dirty·writeback 상태를 비교합니다.

큰 단위로 관리하면 일부 메타데이터·락·순회 비용을 줄일 수 있지만 필요한 부분보다 더 많은 메모리를 유지하거나 읽어 올 가능성도 고려해야 합니다. 읽기 패턴과 회수 동작의 교환이 생기므로 folio 전환을 단순히 항상 메모리가 절약되는 변화로 설명하지 않습니다.

page 타입과 기존 API가 모두 사라졌다고 생각하지 않습니다. v6.18 소스에는 page와 folio가 각 추상화 수준에서 함께 등장할 수 있습니다. 오래된 페이지 단위 그림을 읽을 때 현재 경로가 folio 전체를 처리하는지 기본 페이지를 처리하는지 다시 확인합니다.

04

read와 mmap의 데이터 이동

buffered read는 커널이 준비한 파일 데이터를 사용자 버퍼로 복사하는 경로입니다. 같은 데이터를 반복 읽을 때 파일 page cache가 남아 있어도 사용자 버퍼로의 복사와 시스템 콜 비용이 계속 있을 수 있습니다. 버퍼 크기를 바꾸면 호출 횟수와 복사 패턴이 달라집니다.

파일 mmap은 파일 내용을 프로세스 주소 공간에 연결하는 접근입니다. 처음 mmap을 만들었다고 모든 데이터가 즉시 메모리에 들어오는 것은 아니며 실제 접근에서 fault를 통해 매핑과 데이터를 준비할 수 있습니다. 이후 준비된 매핑은 일반 메모리 접근으로 사용할 수 있습니다.

mmap이 read의 복사를 줄일 수 있다는 점과 전체 비용이 항상 작다는 주장은 다릅니다. fault 처리, 페이지 테이블, TLB, 접근 패턴과 여러 스레드의 동시 접근 비용이 중요합니다. 짧은 순차 읽기와 크고 반복되는 random access는 다른 결과를 낼 수 있습니다.

파일이 다른 주체에 의해 잘리거나 변경되는 상황도 생각해야 합니다. 매핑을 만들었다고 파일 수명이 모든 접근에 대해 고정되는 것은 아닙니다. 특히 잘린 범위 접근은 오류 시그널로 이어질 수 있으므로 파일 크기·수명·동시 변경 정책이 프로그램 설계에 포함되어야 합니다.

05

worked example: PRIVATE와 SHARED

내용 첫 바이트가 A인 파일을 두 방식으로 매핑한다고 가정합니다. MAP_PRIVATE 매핑에 P를 쓰면 해당 프로세스의 사적 변경을 유지하기 위한 COW가 발생할 수 있습니다. 프로세스는 P를 보지만 파일을 다시 읽는 다른 경로가 그 변경을 파일 내용으로 보는 것은 아닙니다.

MAP_SHARED 매핑에 S를 쓰면 파일과 연결된 공유 변경의 가시성을 다룹니다. 다른 매핑이나 일반 파일 읽기 경로에서 그 변경을 볼 수 있습니다. 그러나 다른 프로세스가 S를 볼 수 있다는 사실은 저장 장치에 영속적으로 기록되었다는 증거가 아닙니다. 가시성과 내구성은 별도 요구입니다.

사적 파일 매핑의 수정 페이지는 파일 내용과 달라진 익명 메모리처럼 관리될 수 있습니다. 따라서 프로세스의 메모리를 “파일 매핑이니 언제든 버리고 다시 읽으면 된다”라고 일괄 분류하면 틀립니다. 수정된 사적 내용은 원본 파일에서 재구성할 수 없기 때문입니다.

이 사례는 mmap 플래그가 단순 성능 옵션이 아니라 변경의 의미를 정하는 정책임을 보여 줍니다. 실습에서 pread로 관찰되는 값과 프로세스의 매핑 값을 비교해 보세요. 값이 같아지는 시점과 저장 보장을 요청하는 시점을 별도로 표시하면 캐시·공유·디스크를 구분할 수 있습니다.

06

dirty와 writeback의 수명

buffered write나 공유 매핑 변경으로 메모리의 파일 내용이 수정되면 저장소에 반영해야 할 dirty 상태가 생깁니다. write가 반환했다는 것은 요청한 데이터가 해당 API의 계약 아래 처리되었다는 뜻이며 일반적으로 모든 바이트가 전원 장애에도 안전한 저장소에 도달했다는 뜻은 아닙니다.

writeback은 더 나중에 dirty 데이터를 하위 파일 시스템·블록 계층으로 보내는 과정입니다. 여러 쓰기를 묶고 순서를 조정할 수 있어 처리량에 도움이 될 수 있지만, dirty 데이터가 너무 쌓이면 쓰기 작업이 제한되거나 대기할 수 있습니다. 빠른 초기 쓰기 뒤 지연이 급증하는 현상도 이런 흐름과 연결될 수 있습니다.

dirty와 writeback은 같은 표시가 아닙니다. 데이터가 변경되었다는 상태와 현재 I/O 진행 상태를 구분해야 하며, writeback 도중 다시 수정되는 경쟁도 있을 수 있습니다. 단순 “더러운 페이지 하나를 저장하면 즉시 깨끗해진다”는 그림은 실제 동시 갱신을 생략한 모델입니다.

fsync·fdatasync·msync 등은 각각의 계약 아래 동기화와 저장 보장을 요청하는 인터페이스입니다. 정확한 내구성은 파일 시스템, 장치와 오류 처리까지 연결됩니다. 18장에서 crash consistency를 더 다루며 여기서는 사용자에게 보이는 변경과 영속 저장을 같은 사건으로 표시하지 않는 데 집중합니다.

07

readahead와 접근 패턴

순차 읽기에서는 다음에 필요한 데이터를 미리 읽어 두면 장치 지연을 겹쳐 처리할 수 있습니다. readahead는 이런 예상에 기반한 동작입니다. 애플리케이션이 실제로 요청한 바이트와 장치가 읽은 바이트가 달라질 수 있는 이유 중 하나입니다.

예측이 맞으면 이후 요청은 준비된 데이터를 사용하지만, 접근이 불규칙하면 미리 읽은 데이터를 사용하지 않고 버릴 수 있습니다. 불필요한 I/O와 캐시 공간 사용이 생기는 교환입니다. readahead를 늘리면 항상 빠르다는 처방보다 접근 패턴과 캐시 압박을 확인해야 합니다.

POSIX_FADV 계열이나 madvise 같은 힌트 인터페이스는 접근 패턴을 커널에 알리는 데 관련됩니다. 힌트의 의미와 적용 범위는 API마다 다르고 반드시 모든 시스템에서 원하는 물리 I/O를 보장하는 명령은 아닙니다. 성능 변화는 해당 파일 시스템과 실제 workload에서 확인합니다.

순차 처리 프로그램이 작은 read를 매우 많이 호출한다면 사용자 공간 버퍼링만으로도 호출 횟수를 줄일 수 있습니다. 반면 저장 장치가 병목이면 호출 수 변화만으로 큰 개선이 없을 수 있습니다. API 호출·복사·장치 I/O 중 어떤 구간이 지배적인지 측정한 뒤 실험을 선택합니다.

08

캐시를 우회한다는 말의 범위

O_DIRECT는 일반적인 page cache 경로를 우회하는 I/O를 요청할 때 관련되지만 정렬·지원·혼합 접근 제약을 확인해야 합니다. 이를 “모든 캐시를 끈다”라고 설명하지 않습니다. 장치 내부 캐시나 가상화 계층의 상태, 파일 시스템 메타데이터 처리까지 모두 사라지는 것은 아닙니다.

동일 파일에 buffered I/O와 direct I/O, mmap을 섞으면 일관성과 성능의 고려가 복잡해질 수 있습니다. 벤치마크 옵션 하나만 켜고 결과를 단순 비교하기보다 정렬과 접근 경로가 실제로 의도한 대로 적용되었는지 확인해야 합니다. 요청이 실패하거나 다른 경로를 사용하는 경우도 구분합니다.

캐시가 나쁘고 direct I/O가 고급이라는 식의 서열은 없습니다. 자체 캐시와 I/O 스케줄링을 갖는 데이터베이스와 일반 파일 처리 도구는 요구가 다릅니다. 중복 캐시를 피하려는 목적, 지연 예측성, CPU 복사 비용과 구현 복잡도를 함께 비교합니다.

실험에서 운영 시스템의 전역 캐시를 강제로 비우는 행동은 다른 작업의 성능까지 바꿉니다. 이 강좌의 기본 실습은 그런 변경을 하지 않습니다. cold/warm 비교가 필요하면 격리된 VM과 명확한 준비 절차를 사용하고 어느 계층의 캐시를 통제했는지 기록합니다.

09

메모리 회수와 관측 함정

깨끗한 파일 캐시는 필요할 때 원본 파일에서 다시 읽을 수 있어 회수 후보가 될 수 있습니다. 반면 dirty 데이터는 저장 절차가 필요하고, 사적 변경이나 익명 메모리는 다른 보존 경로가 필요합니다. “캐시가 많으니 메모리가 낭비된다”는 해석보다 재사용 가치와 회수 비용을 봅니다.

/proc/meminfo의 Cached·Dirty·Writeback 등은 시스템 전체의 회계이며 특정 프로세스의 한 요청만을 보여 주지 않습니다. 짧은 실습 전후 차이가 다른 작업 때문에 바뀔 수 있습니다. 해당 프로세스·파일의 관측과 전체 지표를 서로 보완하는 근거로 사용합니다.

방금 만든 파일을 읽는 실험에서는 쓰기 과정에서 이미 page cache가 준비되었을 수 있습니다. 첫 read를 자동으로 cold read라고 이름 붙이면 안 됩니다. 첫 번째 실행과 두 번째 실행이라는 순번은 실제 캐시 상태의 증거가 아닙니다.

페이지 캐시 hit를 최종 목표로 삼지 않습니다. 데이터가 캐시에 있어도 복사·파싱·락 경합·스케줄링이 병목일 수 있고, 캐시 보유량 증가가 다른 작업의 회수를 유발할 수 있습니다. 애플리케이션의 처리량과 지연을 기준으로 캐시 경로가 어떤 영향을 주는지 확인합니다.

10

현재 실험: 변경과 writeback 사이

실험의 파일은 16페이지이며 변경한 페이지 수와 writeback을 마친 페이지 수를 따로 조작합니다. 10페이지를 바꾸고 4페이지의 writeback이 끝났다면 모델에서는 6페이지가 dirty로 남습니다. read는 남은 dirty 페이지의 최신 내용도 캐시에서 볼 수 있으므로 변경이 읽힌다는 관측으로 저장 완료를 판단할 수 없습니다.

모델은 동시 재쓰기와 오류가 없다고 가정하며 writeback 완료량을 변경량보다 크게 세지 않습니다. 실제 구현에서는 저장 중 다시 수정되는 경쟁과 오류 처리, 파일·디렉터리 메타데이터 보장이 추가됩니다. 모든 막대가 clean으로 바뀌어도 새 파일 이름의 crash durability까지 자동 입증된 것은 아닙니다.

이 장의 C 실습과 연결하면 MAP_SHARED 변경이 pread에서 보이는 것은 캐시 가시성 단계입니다. 실습은 고의 장애나 전원 차단을 수행하지 않으므로 내구성 검증 결과로 쓰지 않습니다. 상태별로 어떤 근거를 얻었고 무엇은 아직 검증하지 않았는지 분리해 기록하세요.

OBSERVE ON LINUX

실제 환경에서 확인하기

C 컴파일러가 있는 Linux VM에서 한 페이지짜리 임시 파일로 사적·공유 매핑의 가시성을 비교합니다.

/tmp가 tmpfs여도 가시성 실험은 가능하지만 블록 저장 장치 경로를 실험한 것은 아닙니다. 이 코드는 강제 캐시 제거를 하지 않습니다. 동일한 소스 파일명이 이미 있으면 다른 이름을 사용합니다.

환경 준비와 명령 실행 전제 · 아래는 제공 실습이며 이 교재 제작 환경에서 Linux 실행 결과를 검증하지 않았습니다.

Linux VM / Shell · C
cat > /tmp/kernel-map-policy.c <<'C'
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/mman.h>
int main(void) {
    char name[] = "/tmp/kernel-map-policy-XXXXXX";
    int fd = mkstemp(name);
    if (fd < 0) return 1;
    unlink(name);
    long page = sysconf(_SC_PAGESIZE);
    if (page <= 0 || ftruncate(fd, page) < 0 || pwrite(fd, "A", 1, 0) != 1) return 1;
    char value;
    char *p = mmap(NULL, page, PROT_READ | PROT_WRITE, MAP_PRIVATE, fd, 0);
    if (p == MAP_FAILED) return 1;
    p[0] = 'P';
    if (pread(fd, &value, 1, 0) != 1) return 1;
    printf("private mapping=%c file=%c\n", p[0], value);
    if (munmap(p, page) < 0) return 1;
    p = mmap(NULL, page, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    if (p == MAP_FAILED) return 1;
    p[0] = 'S';
    if (pread(fd, &value, 1, 0) != 1) return 1;
    printf("shared mapping=%c file=%c\n", p[0], value);
    if (munmap(p, page) < 0) return 1;
    return close(fd) < 0;
}
C
cc -O2 -Wall -Wextra /tmp/kernel-map-policy.c -o /tmp/kernel-map-policy

예상 관측과 해석

private mapping=P file=A, shared mapping=S file=S가 예상됩니다. 일반 읽기로 변경이 보인다는 실험이며 전원 장애 내구성을 검증하지 않습니다.

혼동하기 쉬운 점

  • 새로 만든 파일의 첫 read를 자동으로 cold read라고 부르지 않습니다.
  • mmap이나 O_DIRECT가 모든 상황에서 더 빠르다고 주장하지 않습니다.
  • 공유 변경이 보이는 것을 저장 장치 내구성 증거로 쓰지 않습니다.
