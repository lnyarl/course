01

26.1 느리다는 말을 측정 가능한 질문으로 바꾼다

먼저 어떤 요청이 언제부터 얼마나 느려졌는지 정의합니다. 처리량, 평균 지연, p95 또는 p99, 오류율은 서로 다른 결과입니다. 평균이 그대로여도 일부 요청의 긴 대기가 늘 수 있고, 처리량을 낮춰 지연만 줄인 경우는 같은 성능 개선이라고 보기 어렵습니다.

요청 시간을 큐에서 기다린 시간과 실제 서비스 시간으로 나누면 조사의 방향이 생깁니다. 서비스 시간이 같아도 유입이 처리 능력에 가까워지면 큐가 커지고 꼬리 지연이 늘 수 있습니다. 프로그램의 함수 하나를 최적화하기 전에 대기의 위치를 찾아야 하는 이유입니다.

측정 경계는 클라이언트 시작부터 응답 완료까지인지, 서버가 받은 뒤부터인지 명시합니다. 네트워크와 프록시 대기를 제외한 서버 내부 지연을 전체 사용자 경험으로 보고하지 않습니다. 단위, 구간, 작업량이 같아야 개선 전후 숫자를 비교할 수 있습니다.

02

26.2 USE는 자원마다 다른 세 질문을 던진다

USE 방법은 자원의 사용률, 포화, 오류를 확인하는 조사 틀입니다. CPU 사용률이 높다는 사실과 runnable 작업이 오래 기다리는 포화는 다릅니다. 하나는 바쁘다는 신호이고 다른 하나는 수요를 제때 처리하지 못한다는 신호입니다.

메모리 사용량이 높아도 회수 가능한 page cache라면 정상일 수 있습니다. 반대로 page fault와 reclaim, swap으로 작업이 멈추는 시간이 늘면 실제 압력이 문제입니다. 메모리 PSI와 관련 카운터를 같은 시간 구간에서 확인하면 사용량만 보는 것보다 구체적인 가설을 세울 수 있습니다.

스토리지에서는 처리량, 지연, 큐, 오류를 함께 보고 네트워크에서는 큐와 드롭, 재전송, 애플리케이션 소비 속도를 연결합니다. 모든 자원에 같은 임계치 하나를 붙이지 않습니다. VM과 cgroup처럼 관측 경계가 중첩되면 각 경계의 제한도 조사합니다.

03

26.3 실행 중인 비용과 실행하지 못한 비용

on-CPU 프로파일은 실행하면서 소비한 CPU의 위치를 보여줍니다. off-CPU 분석은 잠들거나 실행을 기다린 시간을 조사합니다. CPU 프로파일에서 작은 비중인 함수도 락이나 I/O를 기다리는 시간이 길면 전체 응답 지연을 지배할 수 있습니다.

flame graph의 가로 폭은 보통 집계된 표본 또는 지정한 비용의 양을 나타냅니다. 왼쪽에서 오른쪽으로 시간이 흐르는 타임라인이 아닙니다. 그래프가 CPU 표본인지 대기 시간 집계인지 먼저 확인해야 폭을 올바르게 해석할 수 있습니다.

락 경합이 보이면 락 구현을 즉시 바꾸기보다 임계 구역 안의 작업량, 공유 범위, 병렬 작업 수를 봅니다. 캐시 경합이나 메모리 대역폭이 병목이면 스레드를 늘려도 악화될 수 있습니다. CPU 수와 처리량이 비례한다는 가정을 실험으로 확인해야 합니다.

04

26.4 효과의 상한과 부작용을 확인한다

요청 시간 중 10%를 차지하는 부분만 완전히 제거해도 나머지 90%는 남습니다. 최적화 대상의 기여도를 추정하면 큰 노력을 들여도 전체 효과가 작은 작업을 피할 수 있습니다. 이 계산은 병목 이동과 대기열의 비선형 효과를 설명하는 만능 공식은 아니지만 출발점으로 유용합니다.

변경은 한 번에 한 가설을 검증하도록 좁힙니다. 작업량과 데이터, 동시성, 캐시 상태, 배경 부하를 맞추고 여러 번 측정합니다. 성능만 빨라졌어도 오류 증가, 메모리 증가, 공정성 악화가 있으면 최종 개선으로 받아들일 수 없습니다.

브라우저 실험의 숫자는 원리를 보여주는 모형입니다. 실제 운영 값과 연결할 때는 각 지표를 어떤 도구로 어떤 경계에서 얻었는지 설명해야 합니다. 최종 보고는 관측, 가설, 변경, 재검증 결과를 분리해 다른 사람이 같은 결론을 검토할 수 있게 만듭니다.

05

26.5 요청 하나를 실행·대기 시간으로 분해한다

교육용 서버 요청이 총 100ms 걸렸다고 합시다. CPU 실행이 20ms, 데이터베이스 응답 대기가 50ms, runnable 상태로 CPU를 기다린 시간이 20ms, 나머지 내부 대기가 10ms라면 CPU 프로파일은 주로 실행한 20ms를 보여줍니다. 그 프로파일에서 함수 A가 절반을 차지해도 전체 요청의 절반을 썼다고 바로 말할 수 없습니다.

함수 A의 CPU 비용 10ms를 5ms로 줄여도 다른 구간이 그대로라면 총 시간은 95ms입니다. 반면 runnable 대기가 CPU 경쟁으로 생긴 것이라면 작업량 감소가 대기열에도 영향을 줘 더 큰 효과를 낼 수 있습니다. 단순 합산 모델은 기여도를 생각하는 출발점이고, 실제 포화 시스템의 결과는 실험으로 확인해야 합니다.

이 분해에는 중첩도 주의해야 합니다. 여러 비동기 작업이 동시에 진행되면 각 작업의 시간을 모두 더한 값이 요청의 벽시계 시간보다 커질 수 있습니다. 병렬 구간에서는 가장 늦은 의존 경로와 대기 관계가 중요합니다. 모든 span duration을 합쳐 한 요청 지연이라고 보고하는 오류를 피하려면 타임라인과 의존성을 함께 그립니다.

06

26.6 평균과 p99는 다른 질문에 답한다

요청 100개 중 99개가 10ms, 한 개가 1000ms라면 평균은 약 19.9ms입니다. 대부분의 사용자는 10ms를 보지만 드문 요청 하나는 1초를 기다립니다. 평균만 보면 긴 지연 사건이 희석될 수 있고, 표본 수가 적은 p99는 매우 불안정할 수 있습니다. 지표 이름만 보고 품질을 판단하지 말고 요청 수와 계산 방식을 함께 확인합니다.

긴 지연은 GC, 파일 동기화, CPU throttling, lock convoy, 저장 장치 재시도처럼 간헐적인 상태 전이와 관련될 수 있습니다. 전체 구간 평균 CPU가 낮아도 짧은 버스트에서 경쟁이 발생할 수 있습니다. p99가 튄 시점과 겹치는 더 짧은 간격의 지표, 이벤트, 요청 추적을 모아야 원인 가설을 좁힐 수 있습니다.

벤치마크 클라이언트가 이전 요청이 끝난 뒤에만 다음 요청을 보내면 서버가 멈춘 동안 새 요청을 만들지 않아 실제 유입 상황의 대기열을 덜 드러낼 수 있습니다. 부하 생성 방식과 응답 지연의 시작점을 기록해야 합니다. 서버가 느릴 때 실험이 자동으로 부하를 낮추는 구조라면 같은 요청률의 운영 상황과 다른 결과를 낼 수 있습니다.

07

26.7 CPU 사용률을 코어와 실행 범위로 나눈다

8 CPU 시스템의 전체 사용률 12.5%는 한 CPU가 완전히 바쁘고 나머지가 쉬는 상태일 수 있습니다. 단일 스레드가 직렬 작업을 수행한다면 전체 평균이 낮아도 그 작업은 CPU 한계에 도달했을 수 있습니다. CPU를 늘리는 처방이 맞으려면 작업을 더 많은 실행 주체로 나눌 수 있는지부터 확인해야 합니다.

cgroup 한도가 1 CPU 상당이면 호스트가 여유로워도 해당 그룹은 제한될 수 있습니다. affinity가 좁거나 특정 IRQ와 애플리케이션이 같은 CPU에 몰려도 비슷한 증상이 생깁니다. 사용률을 볼 때 시스템 전체, 프로세스, 스레드, CPU별, cgroup별 관측을 구분하면 낮은 평균이 원인을 가리는 상황을 이해할 수 있습니다.

CPU 시간이 높아도 유용한 계산이 많다는 뜻만은 아닙니다. spin, 반복 재시도, 과도한 복사, 캐시 miss로 인한 stall 등이 포함될 수 있습니다. 프로파일과 하드웨어 이벤트를 질문에 맞게 사용해 어떤 일을 하는지 확인합니다. IPC 같은 지표도 아키텍처와 workload에 의존하므로 낮은 값 하나를 보편적인 버그 판정 기준으로 사용하지 않습니다.

08

26.8 메모리 병목은 사용량보다 진행 방해로 본다

캐시가 많은 시스템은 free 메모리가 적어 보여도 정상일 수 있습니다. 사용하지 않는 캐시를 회수해 새 요청을 처리할 수 있다면 높은 점유 자체가 장애가 아닙니다. 반면 working set이 가용 메모리를 초과해 같은 페이지를 반복해서 내보내고 다시 읽으면 처리량이 떨어지고 지연이 커질 수 있습니다.

관측에서는 page fault를 모두 디스크 접근으로 세지 않습니다. minor fault는 디스크 I/O 없이 처리될 수 있고, major fault는 저장소 접근과 관련될 수 있지만 실제 비용은 상태와 경로에 따라 달라집니다. 회수와 swap 카운터, memory PSI, 애플리케이션 지연을 함께 보아야 단순한 fault 횟수를 성능 원인으로 확대하지 않습니다.

NUMA 시스템에서는 메모리가 충분해도 원격 접근과 배치가 비용을 만들 수 있습니다. CPU affinity를 고정한 뒤 메모리의 초기 할당 위치가 바뀌면 성능이 달라질 수 있습니다. 메모리 부족, 대역폭 한계, 지역성 문제는 서로 다른 가설이므로 같은 “메모리 문제”라는 이름 아래 하나의 설정 변경으로 처리하지 않습니다.

09

26.9 락 경합에서 먼저 줄일 것은 공유 작업이다

여러 스레드가 하나의 락을 통해 전역 큐를 갱신한다면 스레드 수가 늘수록 임계 구역 앞의 대기가 커질 수 있습니다. 락 구현을 더 빠른 것으로 바꾸기 전에 보호하는 데이터와 임계 구역 안에서 하는 일을 확인합니다. 로그 포맷이나 메모리 할당, 느린 I/O를 임계 구역 안에서 수행하면 아주 짧은 데이터 갱신보다 큰 비용이 생깁니다.

일부 계산을 락 밖으로 옮기거나 작업을 배치하고, 독립적인 키별로 상태를 분리하면 경쟁 자체를 줄일 수 있습니다. 하지만 순서와 일관성 요구를 보존해야 합니다. 잠금을 없애는 것이 목표가 아니라 필요한 불변식을 더 적은 공유 비용으로 유지하는 것이 목표입니다. 잘못된 lock-free 구현이 빠르더라도 정확성 조건을 만족하지 못하면 개선이 아닙니다.

관측에서는 락 대기 시간과 획득 횟수, 보유 시간, 경쟁 스레드 수를 구분합니다. 획득 횟수가 많지만 보유가 짧아 영향이 작을 수도 있고, 드문 긴 보유가 p99를 지배할 수도 있습니다. 평균 보유 시간만으로 간헐적 convoy를 놓칠 수 있으므로 분포와 긴 사례의 실행 경로를 확인합니다.

10

26.10 재현 가능한 비교표를 만든다

비교표의 행에는 변경 전과 변경 후를, 열에는 작업 데이터, 요청률, 동시성, 완료 수, 오류 수, 평균과 꼬리 지연, CPU 시간, 최대 메모리를 둡니다. 동일한 코드 경로와 정확성 조건을 수행했는지 확인하는 항목도 필요합니다. 캐시나 warmup이 다르면 그 차이를 별도 실험으로 분리합니다.

한 번의 가장 좋은 결과만 선택하면 우연한 배경 부하와 온도·주파수 변동을 숨길 수 있습니다. 여러 반복의 분포를 보고 차이가 일관적인지 확인합니다. 실행 순서를 번갈아 배치하면 환경의 시간 변화가 한쪽에만 유리하게 작용하는 것을 줄일 수 있습니다. 통계가 복잡하지 않아도 원시값과 조건을 보존하면 재검토가 가능합니다.

개선 뒤 다른 자원의 비용도 확인합니다. CPU는 줄었지만 메모리와 큐가 늘거나, 처리량은 올랐지만 특정 요청의 공정성이 나빠질 수 있습니다. 서비스 요구에 맞는 최종 판단은 여러 결과를 함께 보는 것입니다. 교재의 실험은 이 판단 절차를 연습하며 특정 도구의 출력 한 줄을 성능 합격 판정으로 사용하지 않습니다.

11

26.11 실패한 가설도 다음 조사의 증거가 된다

CPU 프로파일의 상위 함수를 최적화했는데 p99가 그대로라면 측정이 무의미했던 것은 아닙니다. 그 비용이 현재 사용자 지연의 지배적 경로가 아니었거나 다른 대기가 효과를 상쇄했을 수 있습니다. 변경이 실제로 실행됐는지, 함수의 절대 비용이 줄었는지, 요청 범위가 같은지 먼저 확인합니다.

효과가 없었던 가설은 조건과 결과를 기록하고 원래의 단순한 구현으로 돌아갈지 판단합니다. 복잡한 최적화를 남기면 유지보수 비용과 다른 성능 경로의 위험을 만들 수 있습니다. “빠를 것 같다”는 예상보다 실제 결과를 우선하고, 개선이 확인되지 않은 상태를 완료된 성능 수정으로 보고하지 않습니다.

다음 조사는 남은 큰 구간에서 시작합니다. runnable 대기가 크면 스케줄링과 제한을, off-CPU에서 I/O 대기가 크면 파일·네트워크 경로를, 메모리 압력이 크면 working set과 회수를 봅니다. 커널의 각 장을 따로 외우는 대신 같은 요청의 실행 지도에서 필요한 장을 다시 연결하는 것이 이 과정의 마지막 학습 방식입니다.

12

26.12 조작 실험: 빠른 함수보다 큰 대기 구간을 먼저 찾는다

브라우저에서 CPU 경합 프리셋을 고르면 CPU 실행 10 ms, CPU 배정 대기 80 ms, I/O 대기 5 ms가 됩니다. 세 구간이 겹치지 않는 모델이므로 전체는 95 ms입니다. 화면의 시간선은 배정 대기→실행→I/O 순서로 그리지만, 실제 요청은 이런 구간을 여러 번 오갈 수 있습니다. 그림에서 한 번씩만 나타나는 것은 합계를 읽기 쉽게 만든 표현이며 실제 서버의 유일한 실행 순서가 아닙니다.

CPU 실행 슬라이더만 10에서 5로 줄이면 총 지연은 90 ms가 됩니다. 계산 코드를 두 배 빠르게 만들었지만 요청 전체의 감소량은 5 ms입니다. 원래 95 ms 대비 약 5.3% 감소이며 전체가 두 배 빨라진 것은 아닙니다. 화면이 보여 주는 CPU 절반 계산과 직접 바꾼 결과를 비교해 보세요. 고정된 나머지 대기라는 모델 가정 안에서 설명할 수 있어야 합니다.

이번에는 기본 CPU 경합 값으로 되돌리고 CPU 배정 대기만 80에서 40으로 줄여 봅니다. 결과는 55 ms입니다. 이 변화가 더 크다는 계산은 원래 대기의 기여도가 컸음을 보여 주지만 실제로 어떤 설정을 바꾸면 40 ms가 되는지까지 알려 주지는 않습니다. affinity, cgroup 제한, 경쟁 작업, 불필요한 CPU 소비 중 무엇이 이 대기를 만들었는지 관측하는 단계가 먼저 필요합니다.

I/O 병목 프리셋에서는 큰 막대가 I/O 대기로 이동합니다. 같은 CPU 최적화를 반복해도 주요 대기 구간은 그대로 남습니다. 이때 I/O 대기를 무조건 디스크 시간으로 해석하지 말고 애플리케이션이 어떤 I/O 경로에서 기다리는지 확인하세요. 파일 읽기인지 소켓 응답인지, 장치 완료 이후 실행 지연도 포함되었는지에 따라 다음 조사 지점이 달라집니다.

실험을 마치면 바꾼 변수, 이전 합계, 이후 합계, 생략한 조건을 네 칸으로 적습니다. 그다음 실제 시스템에서 같은 변수를 어떻게 측정하고 어떤 변경으로 영향을 줄 수 있을지 적어 보세요. 모델의 수치를 움직여 결과를 얻는 것과 실제 병목을 제거하는 것은 다른 작업입니다. 앞의 계산을 현실의 수정 효과로 보고하지 않고 검증할 가설의 우선순위를 정하는 데 사용합니다.
