01

21.1 기다리는 위치를 바꾸는 I/O

blocking read는 현재 처리할 데이터가 없으면 호출 작업을 잠들게 할 수 있습니다. nonblocking read는 진행할 수 없는 경우 EAGAIN을 반환해 호출자가 다음 행동을 선택하게 합니다. nonblocking은 작업을 공짜로 완료시키는 기능이 아니라 기다림을 관리하는 책임을 바꾸는 계약입니다.

poll은 여러 fd의 준비 상태를 한 번에 확인합니다. epoll은 관심 대상을 커널에 등록하고 준비된 이벤트를 회수하는 방식으로 많은 연결을 다룹니다. 이벤트 루프가 여러 소켓을 관리해도 각 요청의 업무 처리가 자동으로 병렬화되거나 빨라지는 것은 아닙니다.

이벤트가 온 뒤 read가 반드시 예상한 바이트 수만큼 성공하는 것도 아닙니다. 다른 소비자와 경쟁하거나 연결 상태가 변할 수 있습니다. 부분 읽기, EAGAIN, EOF, 오류를 별도로 처리해야 이벤트 루프가 실제 부하와 종료 상황에서 동작합니다.

02

21.2 readiness를 정확히 소비한다

level-triggered는 준비 상태가 유지되면 계속 통지받을 수 있습니다. edge-triggered는 준비 상태 변화에 맞춘 알림이므로 일부만 읽고 더 읽을 수 있는데 멈추면 다음 이벤트를 기대하다 정지할 수 있습니다. 일반적인 패턴은 nonblocking fd를 사용하고 EAGAIN까지 읽는 것입니다.

한 연결에서 무한히 읽으면 다른 연결이 굶을 수 있습니다. 실전 이벤트 루프는 공정성을 위한 처리 예산과 다시 처리할 작업 목록을 함께 설계합니다. EAGAIN까지 소비하는 원칙과 모든 연결을 균형 있게 처리하는 정책을 동시에 만족시켜야 합니다.

epoll 이벤트는 사용자 버퍼에 데이터를 채워 주지 않습니다. 준비 상태를 받은 뒤 read나 recv를 호출해 실제 결과를 얻습니다. 오류와 hangup도 준비 이벤트와 함께 나타날 수 있으므로 정상 읽기만 생각한 분기 구조는 연결 종료에서 쉽게 깨집니다.

03

21.3 io_uring은 요청과 완료를 큐로 교환한다

io_uring은 SQ에 작업 요청을 제출하고 CQ에서 완료 결과를 얻는 모델을 제공합니다. 사용자 공간과 커널이 공유하는 링으로 여러 요청을 묶어 전달할 수 있습니다. 큐 항목의 공유와 실제 파일·네트워크 데이터의 이동은 구분해야 합니다.

완료에는 성공 바이트 수 또는 오류 결과가 담깁니다. 작업 종류와 상태에 따라 커널이 즉시 처리하거나 비동기 경로, 작업자 등으로 진행할 수 있습니다. 모든 요청이 순서대로 완료되거나 모든 I/O가 장치의 순수 비동기 처리로 바뀐다고 가정하면 안 됩니다.

버퍼와 요청 데이터의 수명은 완료까지 유지해야 합니다. 취소를 요청했다고 즉시 버퍼를 해제할 수 있는 것도 아닙니다. 작업 간 순서, 취소와 완료의 경합, multishot 같은 확장 기능은 기본 요청·완료 계약을 이해한 뒤 별도로 학습합니다.

04

21.4 빠른 API보다 전체 비용을 먼저 본다

작은 작업을 많이 제출하면 시스템 콜과 제출 비용을 묶는 것이 도움이 될 수 있습니다. 반대로 장치 대기가 대부분이거나 작업 수가 적으면 API 교체만으로 큰 개선을 기대하기 어렵습니다. 같은 작업량과 동시성, 오류 처리 조건으로 비교해야 합니다.

zero-copy라는 이름은 모든 곳에서 복사가 사라진다는 보장이 아닙니다. 지원되는 경로에서 특정 복사를 피하되 페이지 고정, 참조 관리, 완료 통지 비용을 치를 수 있습니다. 작은 데이터에서는 이 관리 비용이 기존 복사보다 클 수도 있습니다.

io_uring은 커널 설정과 보안 정책, 배포판 운영 정책에 의해 제한될 수 있습니다. 기능이 6.18에 존재하는 것과 현재 VM에서 허용되는 것은 별도 확인 사항입니다. 예제에서는 먼저 readiness를 직접 관측하고, io_uring은 공식 API 문서로 제출·완료 구조를 연결합니다.

05

21.5 두 개의 fd로 readiness를 추적한다

이벤트 루프가 소켓 A와 B를 epoll에 등록했다고 합시다. A에는 100바이트가 도착하고 B에는 데이터가 없습니다. epoll_wait는 A의 읽기 준비를 알릴 수 있지만 그 알림이 A의 100바이트를 사용자 버퍼로 옮기지는 않습니다. 프로그램은 recv를 호출해 반환된 실제 바이트 수를 처리해야 하며, 알림과 데이터 이동 사이에 상태가 바뀔 가능성도 고려합니다.

level-triggered에서 A를 40바이트만 읽으면 60바이트가 남아 다음 대기에서도 읽기 준비가 보고될 수 있습니다. edge-triggered에서는 일부를 남기고 새 edge만 기다리는 방식이 정지 원인이 됩니다. 그래서 일반적인 ET 구현은 nonblocking 상태에서 더 읽을 수 없을 때까지 처리하고 EAGAIN을 다음 대기로 돌아갈 기준으로 사용합니다.

B가 나중에 준비되었을 때 A의 처리만 계속 반복하면 B는 기다립니다. 준비 상태를 정확히 비우는 일과 연결 간 공정성을 유지하는 일은 별도 정책입니다. 처리 예산을 쓰는 구현은 아직 남은 A를 사용자 공간의 준비 목록에 보관해 다음 차례에 이어가야 할 수 있습니다. 이벤트 통지 방식만 선택했다고 이벤트 루프의 공정성이 완성되는 것은 아닙니다.

06

21.6 nonblocking의 의미를 세 가지 시간으로 나눈다

nonblocking은 준비되지 않은 대상 때문에 호출 작업이 기다리지 않도록 하는 특정 인터페이스의 계약입니다. CPU에서 시스템 콜을 실행하는 시간까지 0이 된다는 뜻은 아닙니다. 락과 내부 작업, 데이터 복사 비용이 있을 수 있으며 대상의 종류에 따라 O_NONBLOCK의 효과가 다릅니다. 일반 파일에 같은 옵션을 주었다고 모든 저장 장치 대기가 소켓처럼 EAGAIN으로 바뀐다고 가정하지 않습니다.

첫 번째 시간은 호출을 준비하고 커널에 진입하는 비용, 두 번째는 실제 데이터를 처리하는 비용, 세 번째는 자원이 준비되기를 기다리는 시간입니다. 비동기 API는 주로 이 세 비용을 배치하거나 기다림을 다른 실행 문맥으로 옮기는 방법을 제공합니다. 어떤 비용이 줄었는지 구분하지 않으면 API 이름만으로 성능을 설명하게 됩니다.

예를 들어 저장 장치에서 5ms를 기다리는 64KiB 읽기의 제출 비용을 2µs 줄여도 단일 요청의 종단 지연은 크게 달라지지 않을 수 있습니다. 반대로 캐시에 있는 작은 작업 수십만 개를 처리하면 제출과 완료 회수의 반복 비용이 중요할 수 있습니다. 최적화 대상의 크기는 요청 수와 병목 비중으로 판단합니다.

07

21.7 SQE와 CQE를 상태 기계로 이해한다

io_uring에서 SQE는 수행할 작업의 설명이고 CQE는 해당 작업의 결과를 전달하는 항목입니다. user_data 같은 식별자를 사용하면 완료를 원래 요청 상태와 연결할 수 있습니다. 요청 A 다음에 B를 제출했다고 항상 A 다음에 B가 완료된다고 가정하지 않습니다. 순서가 필요한 작업은 인터페이스가 제공하는 연결·의존 규약을 검토해야 합니다.

작업 상태를 준비, 제출됨, 진행 중, 완료 결과 회수, 자원 반환으로 나누어 보세요. 제출 함수의 성공은 마지막 상태가 아니라 중간 상태로 이동했다는 뜻입니다. 요청 버퍼와 상태 객체는 커널이 더 이상 참조하지 않는 완료 경계까지 유지해야 합니다. 이 수명 규약을 빼면 빠른 제출 코드가 use-after-free나 데이터 손상으로 이어질 수 있습니다.

단순 단발 요청은 완료 결과 한 개로 이해할 수 있지만 multishot과 zero-copy notification 같은 기능에는 더 세밀한 완료 규약이 있습니다. 처음부터 모든 CQE를 하나의 요청을 즉시 해제하라는 신호로 일반화하지 않습니다. 이 장의 모형은 기본 단발 작업에 한정하고 확장 기능은 해당 opcode의 문서와 flag 의미를 함께 읽는 습관을 강조합니다.

08

21.8 취소는 이미 일어난 I/O를 되돌리지 않는다

클라이언트가 타임아웃되어 요청을 취소했어도 디스크 쓰기가 이미 진행되었을 수 있습니다. 취소 요청을 보냈다는 사실은 해당 데이터가 절대 기록되지 않았다는 증거가 아닙니다. 완료가 취소보다 먼저 도착하는 경합, 취소가 지원되지 않거나 이미 늦은 경우를 상태 기계에 포함해야 합니다.

버퍼를 취소 요청 직후 반환하면 진행 중 커널 작업이 해제된 메모리를 사용할 위험이 있습니다. 사용자 코드에서는 취소 결과와 원래 요청의 완료 규약을 확인한 뒤 소유권을 반환해야 합니다. 이 문제는 io_uring만의 특징이 아니라 모든 비동기 I/O와 작업 큐에서 반복되는 수명 문제입니다.

애플리케이션 의미도 따로 정해야 합니다. 파일 쓰기나 외부 서비스 호출은 취소해도 이미 발생한 효과가 남을 수 있습니다. 재시도가 같은 작업을 두 번 실행할 수 있다면 식별자와 멱등성 또는 보상 절차가 필요합니다. 커널 API의 취소 성공과 업무 트랜잭션의 롤백을 같은 동작으로 설명하지 않습니다.

일반적인 성공 단발 read를 단순화했습니다. io_uring의 poll opcode·multishot·취소 경합·짧은 결과는 별도 계약입니다.

09

21.9 배치 제출은 고정 비용을 나누지만 대기를 만든다

교육용 모델에서 시스템 콜 고정 비용이 2µs이고 작업 하나의 준비·완료 관리 비용이 1µs라고 합시다. 한 작업씩 제출하면 각 작업이 고정 비용을 따로 부담합니다. 16개를 묶으면 고정 비용을 나눌 수 있지만 첫 작업은 묶음이 준비될 때까지 기다립니다. 이 숫자는 실제 커널 측정값이 아니라 비용 구성 요소를 설명하기 위한 값입니다.

요청이 항상 충분히 쌓인 처리량 실험에서는 큰 배치가 유리해 보일 수 있습니다. 하지만 낮은 요청률에서 같은 배치 크기를 기다리면 사용자 지연이 커집니다. 최대 배치 크기와 최대 대기 시간을 함께 두는 이유가 여기에 있습니다. throughput과 p99를 동시에 확인하고 유입률에 따라 정책이 달라지는지도 봅니다.

진행 중 요청 수 역시 제한해야 합니다. 완료를 회수하지 않은 채 제출만 계속하면 CQ와 사용자 요청 상태, 데이터 버퍼가 쌓입니다. 링의 크기를 늘리는 것은 순간적인 여유를 주지만 소비 능력을 높이지 않습니다. 완료 처리 비용과 애플리케이션 후속 작업까지 포함한 전체 파이프라인이 안정적으로 진행하는지 확인합니다.

10

21.10 zero-copy가 실제로 생략하는 복사를 표시한다

일반적인 경로에서 사용자 버퍼와 커널 버퍼 사이의 복사, 커널 내부의 데이터 재배치, 장치 DMA는 서로 다른 작업입니다. zero-copy 기능을 설명할 때 도식에서 어느 화살표의 복사가 생략되는지 표시해야 합니다. 모든 복사와 모든 메모리 접근이 사라진다고 소개하면 페이지 참조와 캐시 비용을 이해할 수 없습니다.

페이지를 참조로 넘기는 방식은 버퍼가 전송 완료까지 살아 있어야 한다는 조건을 만들 수 있습니다. 작은 데이터에서는 복사 자체보다 참조와 알림을 관리하는 비용이 커질 수도 있고, 큰 데이터에서는 복사를 피하는 이득이 커질 수 있습니다. 경계 크기는 하드웨어와 작업 형태에 따라 측정해야 하며 교재의 고정 숫자로 결정하지 않습니다.

같은 데이터를 보낸 비교라도 CPU 사용, 지연, 메모리 고정량, 완료 처리 복잡도를 함께 봅니다. 사용자 버퍼를 일찍 재사용하는 기존 코드와 zero-copy를 요구하는 수명 규약이 충돌할 수 있습니다. API 선택은 빠른 함수 이름을 고르는 일이 아니라 데이터 소유권과 처리 흐름을 바꾸는 설계 선택입니다.

11

21.11 소스 읽기와 실습의 확장 순서

fs/eventpoll.c에서는 fd의 관심 상태를 등록하는 경로와 실제 준비 이벤트를 사용자에게 전달하는 경로를 나누어 읽습니다. read를 대신 수행하는 코드가 아니라 readiness를 관리하는 코드라는 관점이 중요합니다. 사용자 프로그램의 nonblocking 반복과 커널 준비 목록이 어떻게 맞물리는지 그려 보세요.

io_uring/io_uring.c와 UAPI 헤더에서는 요청 항목, 완료 항목, 링 인덱스와 플래그를 먼저 찾습니다. 공유 메모리라고 해서 동기화가 필요 없는 것은 아닙니다. 생산자와 소비자가 어떤 순서로 데이터를 쓰고 인덱스를 공개하는지 이해해야 메모리 순서 단원과 연결됩니다. 직접 링을 구현하기 전에는 liburing 같은 공식 사용자 라이브러리의 규약을 사용하는 편이 학습 범위를 줄입니다.

기본 실습이 끝나면 읽기 크기를 바꾸고 예측한 readiness 결과를 확인합니다. 그다음 실제 io_uring 예제를 별도 준비된 VM에서 실행할 때 지원 opcode와 보안 제한을 먼저 확인합니다. 실패를 감추기 위해 다른 API로 조용히 바꾼 뒤 io_uring을 검증했다고 기록하지 않습니다. fallback이 있다면 어떤 경로가 실행됐는지 출력과 관측으로 구분합니다.

12

21.12 확인 과제: 준비 알림과 완료 결과를 같은 칸에 넣지 않는다

브라우저 모델에서 API 종류와 사용 가능한 데이터를 바꾸며 결과를 비교하세요. epoll의 준비 상태가 참이라는 결과는 읽기 작업이 이미 끝났다는 뜻이 아닙니다. 이후 실제 read 결과를 확인해야 합니다. io_uring의 완료 모델은 요청 결과를 회수한다는 점이 다르지만 버퍼 수명과 오류 처리를 생략할 수 있다는 뜻은 아닙니다.

코드 리뷰에서는 상태 변수 ready와 completed를 별도로 찾는 연습을 합니다. 준비 이벤트를 받자마자 요청 상태를 완료로 바꾸거나, 제출 직후 버퍼를 반환하는 코드는 각 API의 경계를 혼동했을 수 있습니다. 테스트는 정상 데이터뿐 아니라 준비 후 경쟁, 짧은 읽기, EOF, 오류와 취소를 포함해야 동작 계약을 확인할 수 있습니다.

마지막 질문은 어떤 API가 더 현대적인지가 아니라 현재 프로그램의 기다림과 제출 비용 중 무엇을 바꾸려는가입니다. 적은 수의 연결을 다루는 단순한 blocking 코드도 요구사항에 맞을 수 있고, 많은 연결의 readiness 관리나 대량 요청의 completion 처리가 필요하면 다른 구조가 유리할 수 있습니다. 복잡성의 증가가 실제 측정된 병목을 줄이는지 확인합니다.

OBSERVE ON LINUX

실제 환경에서 확인하기

Linux VM에 C 컴파일러가 있을 때 파이프를 epoll level-triggered로 관찰합니다. 커널 모듈이나 root 권한은 필요하지 않습니다.

이 예제는 ET 루프나 io_uring 성능 시험이 아닙니다. 파이프 쓰기 끝을 닫지 않은 상태라 마지막에 EOF 준비 이벤트가 생기지 않습니다.

환경 준비와 명령 실행 전제 · 아래는 제공 실습이며 이 교재 제작 환경에서 Linux 실행 결과를 검증하지 않았습니다.

Linux VM / Shell · C
cat > /tmp/epoll-ready.c <<'C'
#include <sys/epoll.h>
#include <unistd.h>
#include <stdio.h>
int main(void) {
  int p[2]; if(pipe(p)) return 1;
  int e=epoll_create1(0); if(e<0) return 1;
  struct epoll_event ev={.events=EPOLLIN,.data.fd=p[0]}, out;
  if(epoll_ctl(e,EPOLL_CTL_ADD,p[0],&ev)) return 1;
  if(write(p[1],"AB",2)!=2) return 1;
  int n=epoll_wait(e,&out,1,0); printf("before read: %d\n",n);
  char c; if(read(p[0],&c,1)!=1) return 1;
  n=epoll_wait(e,&out,1,0); printf("one byte remains: %d\n",n);
  if(read(p[0],&c,1)!=1) return 1;
  n=epoll_wait(e,&out,1,0); printf("drained: %d\n",n);
  close(e); close(p[0]); close(p[1]); return 0;
}
C
cc -Wall -Wextra /tmp/epoll-ready.c -o /tmp/epoll-ready
