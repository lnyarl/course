01

22.1 커널은 요청자의 자격을 확인한다

프로세스가 파일을 열거나 다른 프로세스에 신호를 보낼 때 커널은 요청자의 자격과 대상의 속성을 비교합니다. credentials에는 사용자·그룹 식별자와 capability 등 접근 판단에 필요한 정보가 들어갑니다. 화면에 표시되는 사용자 이름은 이 숫자와 정책을 사람이 읽도록 바꾼 표현입니다.

파일의 소유자와 그룹, mode bit는 기본적인 임의 접근 제어의 일부입니다. 경로에 있는 디렉터리의 탐색 권한도 필요하므로 마지막 파일의 읽기 비트만 확인해서는 부족합니다. ACL이 있으면 mode bit만으로 전체 접근 규칙을 설명할 수 없습니다.

실제·유효·저장된 사용자 ID와 파일 시스템 접근에 쓰이는 자격은 목적이 다릅니다. 프로그램이 실행 도중 자격을 바꾸거나 이미 열린 fd를 넘겨받은 경우, 단순히 현재 사용자 이름만 보고 과거에 열린 객체의 권한을 추측하지 않습니다.

02

22.2 root 권한을 기능별로 나눈 capability

capability는 전통적으로 root가 수행하던 특권 동작을 기능별로 나눈 모델입니다. 네트워크 관리, 특정 파일 접근 우회 등 권한의 범위를 구체적으로 표현합니다. CAP_SYS_ADMIN처럼 넓은 권한은 이름만 보고 작은 권한이라고 생각하면 안 됩니다.

capability에는 permitted, effective, inheritable, bounding, ambient 같은 집합이 있습니다. 현재 동작에 쓰이는 집합과 exec 이후 가질 수 있는 집합이 다릅니다. 실습에서는 집합 이름과 현재 값을 관찰하고, 권한 승격 실험은 하지 않습니다.

user namespace 안의 root와 호스트의 root는 동일한 권한 범위를 뜻하지 않습니다. namespace가 소유하는 자원에 대한 capability 판단과 초기 user namespace의 권한이 구분될 수 있습니다. 컨테이너에 root라고 표시되는 사실만으로 호스트 전체의 관리 권한을 가진다고 결론내리지 않습니다.

03

22.3 LSM과 seccomp는 다른 경계에 있다

LSM은 커널의 여러 보안 검사 지점에 정책을 연결하는 기반입니다. SELinux나 AppArmor 같은 정책은 파일 mode bit가 허용하더라도 추가로 접근을 거부할 수 있습니다. 활성 정책과 보안 로그를 확인해야 chmod만 반복하는 시행착오를 줄일 수 있습니다.

seccomp는 시스템 콜 번호와 인자 값을 기준으로 허용·거부 등의 동작을 정합니다. 시스템 콜 인자가 가리키는 임의의 문자열 내용을 일반 필터가 따라가 읽는 방식은 아닙니다. 따라서 파일 경로 전체를 검사하는 LSM 정책과 같은 도구로 생각하면 안 됩니다.

이 기능들은 함께 사용해 노출 범위를 줄일 수 있지만 하나만으로 완전한 샌드박스를 보장하지 않습니다. 자격, namespace, 파일 시스템 배치, 장치 접근, 시스템 콜 정책과 애플리케이션 설계를 함께 고려해야 합니다. 보안 정책의 존재와 실제 활성 상태도 별도로 확인합니다.

04

22.4 거부 지점을 근거로 찾는다

먼저 실패한 시스템 콜과 errno를 확보합니다. 같은 Permission denied 문구라도 경로 탐색 권한, 파일 ACL, LSM 정책 등 원인이 다를 수 있습니다. 증상만 보고 전체 정책을 비활성화하면 원인과 재현 조건을 잃을 수 있습니다.

/proc/PID/status의 Uid, Gid, CapEff, NoNewPrivs, Seccomp는 요청자의 상태를 좁히는 단서입니다. /sys/kernel/security/lsm은 사용 가능한 환경에서 활성 LSM 목록을 보여줍니다. 파일이 없으면 기능 비활성, 마운트 상태, 접근 범위를 구분해 확인합니다.

관측 결과는 권한 판단의 일부 증거입니다. CapEff가 있다는 사실만으로 원하는 동작이 허용된다고 보장할 수 없고, 특정 로그가 없다고 정책 거부가 없었다고 확정할 수도 없습니다. 최소 권한을 유지한 채 실패한 동작과 관련된 규칙을 조사하는 것이 목표입니다.

05

22.5 같은 Permission denied를 만드는 세 경로

사용자가 /srv/private/report를 열지 못한다고 합시다. report의 mode가 0644라서 읽을 수 있어 보이지만 private 디렉터리의 탐색 권한이 없으면 이름 해석 단계에서 막힐 수 있습니다. 최종 파일만 ls -l로 보는 조사는 이 경로를 놓칩니다. 각 부모 디렉터리의 소유·그룹·탐색 권한을 확인하는 이유입니다.

두 번째 경우에는 경로와 mode 검사를 통과했지만 ACL 또는 LSM 정책이 접근을 거부할 수 있습니다. 세 번째 경우에는 시스템 콜이 seccomp 정책에 의해 다른 방식으로 차단될 수 있습니다. 애플리케이션의 오류 문구는 이 차이를 자세히 보여주지 않을 수 있으므로 실제 실패한 호출, errno, 정책 로그를 함께 확보해야 합니다.

검증은 정상 사용자와 실패 사용자의 숫자 UID/GID, 그룹 목록, namespace, 실행 파일과 활성 정책을 같은 조건에서 비교하는 방식으로 진행합니다. 관리자 권한으로 실행해 성공했다고 원인을 규명한 것은 아닙니다. 관리자 실행은 여러 조건을 동시에 바꾸기 때문에 어느 검사가 원인이었는지 분리하지 못할 수 있습니다.

06

22.6 자격을 바꿀 때의 객체 수명

커널의 credentials는 여러 참조가 공유할 수 있으므로 다른 실행 경로가 읽는 객체를 제자리에서 임의로 바꾸는 방식은 위험합니다. 자격 변경 경로는 새 자격을 준비하고 검증한 뒤 교체하는 모델을 사용합니다. 이 구조는 RCU와 참조 수 단원에서 본 “읽는 동안 객체를 안정적으로 유지한다”는 문제와 연결됩니다.

현재 작업의 자격과 파일을 열 때 기록된 자격은 의미가 다를 수 있습니다. 일부 파일 시스템 동작은 열린 파일의 자격을 사용해 후속 처리를 수행합니다. 따라서 프로세스가 현재 낮은 권한으로 실행된다는 사실만으로 이미 열린 모든 자원이 같은 권한 검사를 다시 거친다고 가정하지 않습니다. fd 전달이 권한과 자원 소유에 영향을 주는 이유입니다.

보안 설계에서는 특권이 필요한 초기화와 일반 요청 처리를 분리하고, 불필요한 fd와 capability를 남기지 않는지 점검합니다. 그러나 단순히 setuid 호출이 존재한다고 안전해졌다고 결론내리지 않습니다. 반환값, 남은 그룹, capability 집합, 열린 자원, exec 규약까지 함께 확인해야 실제 경계가 설명됩니다.

07

22.7 capability 집합을 작은 사례로 읽는다

현재 effective 집합에 어떤 capability가 있으면 해당 특권 검사에 사용할 수 있는 후보가 됩니다. permitted는 가질 수 있는 범위를 나타내며 현재 모든 항목이 활성이라는 뜻은 아닙니다. bounding 집합은 exec와 capability 획득 경로에 한계를 두는 데 관련됩니다. 이름이 비슷한 다섯 집합을 하나의 “root 여부” 비트로 줄이면 중요한 차이를 잃습니다.

예를 들어 네트워크 주소 설정 권한이 필요한 도구에 광범위한 관리 권한 전체를 부여하면 불필요한 동작까지 허용할 수 있습니다. 필요한 동작이 어떤 capability와 namespace에서 검사되는지 확인해 범위를 줄이는 것이 목표입니다. 실제로 파일 capability를 설정하거나 집합을 변경하는 실습은 이 읽기 전용 장의 범위를 넘어 별도의 일회용 환경에서 수행합니다.

/proc/PID/status의 CapEff는 16진수 비트 집합입니다. 값이 0이 아니라는 사실만으로 모든 특권을 가진다고 말할 수 없고, 0이라고 모든 파일 접근이 거부되는 것도 아닙니다. 일반 소유권과 mode로 허용되는 작업은 capability가 없어도 수행할 수 있습니다. 비트 값을 문서의 capability 번호와 연결하고 동작별 검사를 확인해야 합니다.

08

22.8 seccomp는 경로 정책과 다른 문제를 푼다

openat 시스템 콜의 인자에는 dirfd, 경로 문자열을 가리키는 포인터, flags 등이 들어갑니다. seccomp 필터는 시스템 콜 번호와 직접 제공되는 인자 값을 검사할 수 있지만 경로 포인터를 따라가 문자열 전체를 일반적으로 읽어 비교하는 정책 엔진이 아닙니다. 따라서 “/tmp 아래 파일만 허용”이라는 요구를 단순한 시스템 콜 번호 필터로 해결했다고 주장하면 안 됩니다.

필터는 허용하지 않는 호출에 오류를 돌려주거나 작업을 종료하는 등 지정된 동작을 적용할 수 있습니다. 애플리케이션이 필터 활성화 이전에 필요한 초기화를 끝냈는지, 라이브러리나 런타임이 예상치 못한 시스템 콜을 사용하는지 고려해야 합니다. 프로그램의 소스에 직접 보이는 호출만 목록화하면 libc와 런타임의 내부 호출을 놓칠 수 있습니다.

정책을 시험할 때 정상 경로뿐 아니라 오류, 취소, DNS, 로그 회전 같은 드문 경로도 살펴야 합니다. 처음 실행이 성공했다고 전체 기능이 정책 아래에서 동작하는 것은 아닙니다. 동시에 로그에 없는 호출을 무조건 허용 목록에 추가하는 방식은 정책의 목적을 흐릴 수 있으므로 필요한 기능과 커널 노출 범위를 연결해 판단합니다.

09

22.9 파일 검사와 사용 사이의 경쟁을 피한다

프로그램이 access로 파일을 확인한 뒤 open하는 사이에 다른 작업이 심볼릭 링크나 이름 연결을 바꿀 수 있습니다. 검사한 대상과 사용한 대상이 달라지는 TOCTOU 문제입니다. 두 호출을 매우 가까이 배치해도 스케줄링과 다른 CPU 실행 때문에 안전한 원자적 동작이 되지 않습니다.

가능하면 실제로 사용할 객체를 연 뒤 그 fd를 기준으로 필요한 속성을 확인하고 작업을 수행합니다. 경로 탐색 자체에 제약이 필요한 경우 openat2 등의 지원 기능과 디렉터리 fd를 검토합니다. 어떤 해결이 맞는지는 symlink 허용 여부, mount 경계, 공격자가 바꿀 수 있는 디렉터리의 범위에 따라 다릅니다.

이 문제는 파일만의 특수 사례가 아닙니다. 권한을 확인한 객체가 실행 시점까지 같은 객체이며 같은 상태인지 보장해야 한다는 일반적인 동시성 문제입니다. 보안 검사를 코드 한 줄로 끝내지 않고 객체 수명과 이름 재사용, 동시 변경을 함께 보는 이유가 여기에 있습니다.

10

22.10 LSM 로그를 정책의 언어로 읽는다

LSM 거부 로그에는 요청 주체와 대상, 요청한 동작, 적용된 정책 문맥에 관한 정보가 담길 수 있습니다. 로그 형식과 도구는 SELinux와 AppArmor 등 정책에 따라 다릅니다. 프로세스 이름이 같다는 이유만으로 동일한 정책 문맥이라고 가정하지 않고 실제 label이나 profile, 실행 경로를 확인합니다.

같은 파일을 읽는 동작도 프로세스의 보안 문맥이 바뀌면 허용 결과가 달라질 수 있습니다. 반대로 mode를 바꿔도 LSM 규칙이 그대로 거부하면 결과가 변하지 않습니다. 이렇게 하나의 조건을 바꿨을 때 어떤 검사가 달라지는지 이해하면 무차별적인 권한 확대 대신 필요한 정책 수정 범위를 설명할 수 있습니다.

운영 환경에서는 로그 접근이 제한되거나 audit 설정 때문에 원하는 정보가 없을 수 있습니다. 로그 부재는 허용의 증거가 아니며, 권한 오류와 함께 정확한 시간과 PID, 요청 경로를 남겨 권한 있는 운영자가 같은 사건을 찾을 수 있게 합니다. 이 과정에서도 다른 사용자의 민감한 파일 내용까지 수집할 필요는 없습니다.

11

22.11 코드에서 검사 위치와 결과 전달을 찾는다

include/linux/cred.h에서는 자격 객체에 어떤 종류의 정보가 들어 있는지, security/security.c에서는 보안 훅이 실제 동작 경로와 어떻게 연결되는지 봅니다. 처음부터 모든 LSM 구현을 비교하기보다 파일 열기 같은 하나의 동작을 고르고 요청자·대상·검사·오류 반환을 표시하는 편이 이해하기 쉽습니다.

kernel/seccomp.c에서는 시스템 콜 진입 시점의 필터 판단과 일반 파일 권한 검사가 다른 경계에 있다는 점을 확인합니다. 모든 아키텍처와 호출 경로의 세부 순서가 같은 그림 한 장으로 완전히 표현되는 것은 아닙니다. 교재의 흐름도는 개념적 검사 관계를 나타내며 정확한 실행 분기는 v6.18 소스와 해당 아키텍처에서 확인합니다.

마지막으로 실패 실험을 설계할 때 원인이 하나인 상황을 먼저 만듭니다. 테스트 디렉터리의 소유권과 mode를 고정하고 현재 자격을 기록한 뒤 한 조건만 바꾸어 예상 결과를 비교합니다. 실제 호스트의 보안 정책을 끄는 대신 일회용 VM에서 최소 사례로 검사 경계를 배우는 것이 재현성과 안전성을 모두 높입니다.

12

22.12 확인 과제: 하나의 허용으로 전체 허용을 예측할 수 있을까

모델에서 기본 접근 권한, LSM, seccomp의 허용 조건을 하나씩 바꿔 보세요. 어느 한 검사가 허용했다고 다른 검사도 허용한 것은 아닙니다. 다만 실제 Linux의 모든 시스템 콜이 항상 동일한 순서와 같은 검사를 수행한다는 의미는 아닙니다. 도식은 각 정책의 역할이 다르다는 것을 보여주고 실제 동작의 검사 경로는 해당 소스에서 확인합니다.

교육용 문제에서는 파일 mode는 허용하지만 LSM은 거부하는 경우와, 시스템 콜 필터가 먼저 거부하는 경우를 비교합니다. 두 경우 모두 사용자에게 실패가 보일 수 있어도 필요한 조사 자료는 다릅니다. 첫 경우에는 대상의 보안 문맥과 정책, 두 번째에는 호출 번호와 필터 동작이 핵심입니다. 오류 문구 하나를 정책 이름으로 바꾸어 읽지 않습니다.

실제 수정안은 거부된 동작이 업무상 필요한지부터 확인하고 필요한 최소 범위만 다룹니다. 전체 정책을 끄면 당장 동작할 수 있지만 어떤 경계가 필요한지 배우지 못합니다. 학습의 완료 기준은 “권한을 크게 주니 됐다”가 아니라 요청자·대상·동작·정책의 관계를 근거로 설명할 수 있는가입니다.
