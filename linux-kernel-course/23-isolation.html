01

23.1 namespace는 보는 세계를 나눈다

PID namespace는 프로세스 번호의 보이는 범위를, mount namespace는 마운트 구성을, network namespace는 네트워크 장치와 라우팅 등의 범위를 나눕니다. 컨테이너 안에서 다른 프로세스가 안 보이는 것은 CPU를 별도로 가진다는 뜻이 아닙니다.

같은 호스트의 컨테이너는 일반적으로 호스트 커널을 공유합니다. 이미지에 다른 배포판의 사용자 공간이 들어 있어도 별도의 커널을 자동으로 실행하지 않습니다. 시스템 콜의 실제 구현과 지원 기능은 실행 중인 호스트 커널과 설정에 의해 제한됩니다.

namespace만으로 모든 격리가 완성되지 않습니다. 파일 마운트, 장치 노출, capability, 보안 정책과 런타임 설정이 함께 경계를 만듭니다. 실습에서는 /proc/PID/ns의 식별자를 비교해 어떤 namespace를 공유하는지 관찰합니다.

02

23.2 cgroup v2는 자원을 계층적으로 제어한다

cgroup은 작업을 그룹으로 묶고 자원 분배와 제한을 적용합니다. cpu.weight는 경쟁 상황의 상대적 배분이고 cpu.max는 기간당 CPU 시간의 상한을 나타냅니다. 둘을 같은 우선순위 숫자로 이해하면 호스트가 한가한데도 작업이 제한되는 현상을 설명할 수 없습니다.

cpu.max가 50000 100000이면 100ms 기간에 합계 50ms의 CPU 시간을 사용할 수 있는 상한을 나타냅니다. 여러 스레드가 여러 CPU에서 동시에 달리면 그 예산을 더 빨리 소비할 수 있습니다. 벽시계 기준 50ms 동안 반드시 한 CPU를 연속 사용한다는 뜻은 아닙니다.

memory.high는 메모리 압력과 회수를 통해 사용을 억제하는 경계이고 memory.max는 더 강한 한도입니다. 한도에 도달했을 때 OOM 여부는 회수 가능성 등 실행 상태에 달려 있습니다. 부모 그룹의 제한도 적용되므로 현재 디렉터리 한 곳의 설정만 읽어서는 충분하지 않을 수 있습니다.

03

23.3 PSI는 자원 때문에 멈춘 시간을 본다

사용률은 자원이 얼마나 일했는지 보여주고, PSI는 작업이 자원 부족 때문에 진행하지 못한 시간의 영향을 보여줍니다. 메모리 사용량이 높아도 유용한 캐시일 수 있고, 사용량이 낮아 보여도 특정 제한 아래의 작업은 회수로 지연될 수 있습니다.

PSI의 some은 관측 범위에서 일부 작업이 지연된 시간을, full은 비유휴 작업 전체가 함께 진행하지 못한 상태의 시간을 나타내는 데 사용됩니다. 자원과 관측 범위에 따라 제공되는 의미와 필드가 다르므로 CPU·메모리·I/O 값을 동일하게 읽지 않습니다.

cgroup의 cpu.stat에서 nr_throttled와 throttled_usec 증가를 보면 CPU 한도에 의한 정지 가설을 조사할 수 있습니다. 이 카운터와 요청 지연의 같은 시간 구간을 비교해야 합니다. 누적값 하나가 크다는 사실만으로 지금의 장애 원인이라고 확정하지 않습니다.

04

23.4 KVM은 별도의 게스트 커널을 실행한다

KVM은 Linux의 가상화 기능을 사용자 공간 VMM이 /dev/kvm 인터페이스로 사용할 수 있게 합니다. VM은 게스트 커널과 게스트 사용자 공간을 실행합니다. 게스트의 프로세스 스케줄링 외에도 호스트가 vCPU 스레드를 언제 실행시키는지가 성능에 영향을 줍니다.

virtio는 게스트와 호스트 사이에서 가상 장치 I/O를 효율적으로 교환하는 규약입니다. 게스트가 보는 가상 디스크 완료 시간에는 호스트의 파일·블록 계층과 물리 장치 대기가 포함될 수 있습니다. 게스트 수치만으로 모든 하위 계층 원인을 알 수는 없습니다.

컨테이너는 namespace·cgroup·보안 정책을 연결하고, VM은 별도 커널 실행 경계를 둡니다. 어느 쪽이 항상 더 안전하거나 빠르다고 일반화하지 않습니다. 운영에서는 필요한 격리와 자원 통제, 장치 가상화, 관측 가능성을 기준으로 선택합니다.

05

23.5 같은 프로세스의 두 PID를 이해한다

호스트에서 PID 12000인 프로세스가 컨테이너 안에서는 PID 1로 보일 수 있습니다. 두 개의 프로세스가 생긴 것이 아니라 PID namespace에 따라 식별자가 다르게 보이는 것입니다. 로그의 PID만 비교해 서로 다른 작업이라고 판단하지 말고 namespace와 host PID, 컨테이너 식별자를 함께 기록해야 사건을 연결할 수 있습니다.

PID namespace의 PID 1은 해당 범위에서 자식 회수와 신호 처리와 관련된 특별한 역할을 가집니다. 평범한 애플리케이션을 그대로 PID 1로 실행했을 때 좀비 회수와 종료 동작이 기대와 달라질 수 있습니다. 컨테이너 런타임이 init 역할을 제공하거나 애플리케이션이 그 책임을 처리하는 이유를 프로세스 수명 단원과 연결합니다.

/proc의 보이는 내용도 mount와 PID namespace의 관계에 영향을 받습니다. namespace만 생성했다고 이미 마운트된 /proc가 자동으로 모든 기대를 충족한다고 가정하지 않습니다. 실습에서 lsns나 /proc/PID/ns의 링크를 확인할 때에는 누가 어느 범위에서 읽는지 명시하고, 호스트 관측과 컨테이너 내부 관측을 별도의 표로 정리합니다.

06

23.6 CPU quota가 벽시계 대기를 만드는 과정

cpu.max가 100000 100000인 그룹에 계산 스레드 네 개가 있고 네 CPU를 동시에 사용할 수 있다고 가정합니다. 교육용 단순 모델에서는 네 스레드가 25ms 동안 합계 100ms의 CPU 시간을 소비하면 그 기간의 예산을 모두 사용합니다. 남은 75ms에 호스트 CPU가 남아 있어도 해당 그룹은 제한을 받을 수 있습니다. 실제 스케줄링과 예산 분배의 세부 동작은 더 복잡하지만 합계 예산이라는 핵심은 같습니다.

동시 실행을 한 스레드로 줄이면 같은 예산을 기간 전체에 더 고르게 사용할 수 있습니다. 일부 요청의 순간적인 긴 정지가 줄 수 있지만 병렬 처리량도 달라집니다. 따라서 concurrency를 낮춰 p99가 줄었다는 결과만으로 개선을 확정하지 않습니다. 완료 요청 수와 애플리케이션 큐 대기, CPU 사용량을 함께 비교해야 실제 사용자 효과를 알 수 있습니다.

cpu.weight는 quota와 다르게 경쟁 상대가 있을 때 상대적 배분에 영향을 줍니다. 다른 작업이 없을 때 여유 CPU를 쓸 수 있는 정책과 절대 예산 한도는 다른 목적입니다. 컨테이너 설정의 “CPU 1”이라는 UI 표현이 어떤 cgroup 파일로 변환됐는지 확인하면 운영 설정과 커널 동작 사이의 오해를 줄일 수 있습니다.

07

23.7 부모 제한은 자식의 max보다 강할 수 있다

부모 그룹 P의 CPU 한도가 2 CPU 상당이고 그 아래 서비스 A와 B가 각각 2 CPU 한도를 가진다고 합시다. 두 서비스가 동시에 바쁘면 각자 항상 2 CPU씩 사용할 수 없습니다. 부모가 허용한 합계 한도가 먼저 전체 수요를 제한할 수 있습니다. 자식 파일에 적힌 숫자를 독립적인 예약 용량으로 해석하면 실제 배분을 잘못 설명하게 됩니다.

메모리도 계층의 사용과 제한을 고려해야 합니다. 서비스 자신의 memory.max가 넉넉해 보여도 상위 그룹의 압력과 한도가 실행에 영향을 줄 수 있습니다. 운영 도구가 보여주는 값이 leaf cgroup만의 값인지 계층 전체인지 확인해야 합니다. 컨테이너 런타임과 서비스 관리자가 서로 다른 깊이에 정책을 배치할 수도 있습니다.

조사에서는 현재 cgroup 경로에서 부모 방향으로 제한을 읽고 같은 시간 구간의 카운터 변화를 기록합니다. 그러나 컨테이너의 cgroup namespace가 상위를 숨길 수 있으므로 읽을 수 없는 정보를 임의로 추정하지 않습니다. 이 경우 호스트 관측이 필요하다는 한계를 명시하는 것이 잘못된 leaf-only 결론보다 정확합니다.

08

23.8 memory.high와 memory.max를 회수 관점에서 본다

메모리 한도에 가까워졌다고 모든 바이트가 즉시 반환 가능한 것은 아닙니다. 깨끗한 파일 캐시는 버리고 다시 읽을 수 있지만 dirty 데이터는 저장이 필요할 수 있고 anonymous 메모리는 swap과 사용 상태에 영향을 받습니다. 같은 memory.current라도 구성과 working set이 다르면 압력의 결과가 달라집니다.

memory.high를 넘으면 회수와 제한을 통해 그룹의 사용을 억제하는 경로가 작동할 수 있습니다. 프로그램은 할당 호출 주변에서 더 많은 시간을 보내거나 메모리 압력에 의해 진행이 늦어질 수 있습니다. 사용량이 조금 줄었다고 문제가 해결된 것은 아니며 reclaim 비용과 요청 지연, memory PSI를 같이 봐야 합니다.

memory.max는 더 강한 경계이고 회수로 요구를 만족하지 못하면 cgroup 범위의 OOM이 관련될 수 있습니다. host 전체에 메모리가 남아도 제한된 그룹에서는 실패할 수 있다는 점이 CPU quota와 비슷합니다. 반대로 memory.high 초과 이벤트를 모두 OOM이라고 부르면 실제 종료 사건과 단순 압력 신호를 혼동하게 됩니다.

09

23.9 PSI의 비율과 누적값을 혼합하지 않는다

PSI avg10, avg60, avg300은 서로 다른 시간 척도의 평균이고 total은 누적된 stall 시간입니다. 서로 다른 필드를 빼서 최근 2초의 지연을 만들지 않습니다. 짧은 관측 구간의 변화를 보고 싶다면 같은 total 필드의 두 시점 차이와 측정 간격을 사용하고, 필드의 단위와 자원별 의미를 확인합니다.

압력이 10%라고 해서 모든 요청이 정확히 10% 느려졌다는 뜻은 아닙니다. PSI는 관측 범위의 작업들이 자원 때문에 진행하지 못한 상태를 집계합니다. 요청 종류와 병렬성, 일부 작업의 중요도에 따라 사용자 지연 분포에 미치는 영향은 다릅니다. 특정 서비스의 PSI와 host 전체 PSI도 같은 모집단이 아닙니다.

카운터가 낮으면 해당 관측 범위와 시간 척도에서 압력이 적었다는 근거가 됩니다. 그러나 짧은 버스트를 긴 평균이 희석하거나 관측하지 않은 그룹에서 문제가 생길 수 있습니다. p99가 튄 정확한 구간의 더 짧은 지표와 이벤트를 연결해야 압력 부재를 강한 배제 증거로 사용할 수 있습니다.

10

23.10 VM 안의 스케줄러 위에 호스트 스케줄러가 있다

게스트 Linux는 자신의 vCPU를 CPU처럼 보고 작업을 배정합니다. 하지만 vCPU는 호스트가 실행시켜야 실제 물리 CPU에서 진행합니다. 게스트가 runnable 작업을 갖고 있어도 호스트 경합이나 제한 때문에 vCPU가 실행되지 않으면 게스트 내부만으로 설명하기 어려운 지연이 생길 수 있습니다. 두 스케줄러의 시간축을 분리해야 합니다.

가상 장치 I/O도 비슷합니다. 게스트의 virtio 요청이 호스트 사용자 공간이나 커널 backend, 호스트 파일 시스템과 블록 장치로 이어질 수 있습니다. 게스트에서 보이는 완료 지연은 이 여러 구간의 합입니다. 게스트의 큐 깊이만 조정해도 호스트 병목은 그대로일 수 있으므로 어느 경계에서 시간이 늘었는지 확인합니다.

컨테이너와 VM 비교는 시작 시간이나 메모리 수치 하나만의 문제가 아닙니다. 별도 커널 경계, 호스트 공유 자원, 장치 모델, 관측과 운영 복잡도를 함께 비교합니다. 둘을 조합해 VM 안에서 컨테이너를 실행하는 배치도 흔하므로 한 계층의 격리 설명만으로 전체 실행 환경을 묘사하지 않습니다.

11

23.11 격리 실험에서 보존해야 할 증거

학습 기록에는 uname -r, 아키텍처, cgroup 파일 시스템 종류, namespace 링크, 현재 cgroup 경로, 읽은 정책 파일의 실제 경로를 남깁니다. 같은 명령이 컨테이너와 호스트에서 다른 결과를 보일 때 이 정보가 있어야 원인을 추적할 수 있습니다. 출력값만 복사하면 어느 범위를 읽었는지 나중에 알기 어렵습니다.

제한 변경 실험은 원래 값과 새 값을 함께 기록하고 원복 경로를 준비한 일회용 VM에서 수행합니다. 본문의 기본 실습은 읽기 전용이므로 정책 변경 효과를 실측했다고 주장하지 않습니다. 브라우저 모델에서는 예산과 동시 실행의 관계를 확인하고, Linux 실습에서는 실제 파일과 카운터가 그 계약을 어떻게 노출하는지 연결합니다.

관측 결과에 기반한 보고 문장을 연습하세요. “CPU가 부족하다” 대신 “서비스 cgroup의 100ms 기간당 CPU 상한 아래에서 nr_throttled가 같은 10초 구간에 증가했다”라고 씁니다. 이 문장은 확인한 범위를 정확히 전달하고, 개별 요청의 지연과 연결하는 다음 추적이 아직 필요하다는 점도 자연스럽게 드러냅니다.

12

23.12 확인 과제: namespace가 CPU를 예약하지 않는 이유

같은 호스트에서 두 컨테이너가 서로 다른 PID·mount namespace를 사용하지만 같은 상위 cgroup 제한 아래 있다고 합시다. 서로의 프로세스 이름이나 파일 경로가 보이지 않아도 CPU와 메모리의 상위 한도를 함께 소비할 수 있습니다. 보이지 않는다는 격리와 사용할 수 있는 양의 제한은 다른 메커니즘이기 때문입니다.

모델에서 CPU 예산과 메모리 사용량을 바꿔 두 종류의 제한을 구분하세요. 모델의 메모리 한도는 64MiB로 고정되어 있습니다. CPU 예산 소모는 일정 기간의 실행 기회와 관련되고, 메모리 한도는 보유한 페이지와 회수 가능성에 영향을 줍니다. 두 값이 모두 숫자라고 해서 같은 방식의 즉시 종료 조건으로 해석하지 않습니다. 실제 결과는 현재 사용과 부모 정책, 회수 상태, 컨트롤러 활성 여부에 따라 달라집니다.

확인 과제의 답에는 namespace 식별자, 실제 cgroup 경로, 읽은 한도 파일과 카운터의 시간 차이를 넣습니다. 명령 출력이 보이지 않으면 경로와 권한의 한계를 명시합니다. 이것이 컨테이너 환경에서 “호스트 자원은 남는데 서비스가 느리다”는 상황을 추측 대신 실행 범위와 정책으로 설명하는 방법입니다.

실제 환경에서 확인하기

cgroup v2가 마운트된 Linux VM에서 현재 셸의 경로를 읽습니다. 호스트·컨테이너에 따라 마운트 루트가 달라 아래 후보 경로가 없을 수 있습니다.

경로가 보이지 않으면 /proc/self/mountinfo와 컨테이너의 cgroup namespace를 확인합니다. 이 실습은 cgroup을 생성하거나 한도를 변경하지 않습니다.

환경 준비와 명령 실행 전제 · 아래는 제공 실습이며 이 교재 제작 환경에서 Linux 실행 결과를 검증하지 않았습니다.

Linux VM / Shell · C
cat /proc/$$/cgroup
ls -l /proc/$$/ns
cg_rel=$(awk -F: '$1=="0" {print $3}' /proc/$$/cgroup)
cg_dir="/sys/fs/cgroup$cg_rel"
printf 'candidate path: %s\n' "$cg_dir"
for f in cpu.max cpu.stat memory.current memory.high memory.max memory.events cpu.pressure memory.pressure io.pressure; do
  if [ -r "$cg_dir/$f" ]; then printf '\n%s\n' "$f"; cat "$cg_dir/$f"; fi
done
cat /proc/pressure/cpu 2>/dev/null

예상 관측과 해석

현재 namespace 식별자와 cgroup 경로를 기록합니다. cpu.max의 max와 숫자 한도를 구분하고, cpu.stat은 두 시점 차이로 비교해야 함을 설명합니다.

혼동하기 쉬운 점

  • 호스트 CPU idle만으로 cgroup throttling을 배제하지 않는다.
  • 모든 memory.high 초과를 즉시 OOM으로 설명하지 않는다.
