01

먼저 무엇이 항상 참이어야 하는가

공유 큐에 count와 연결 리스트가 있다고 가정합니다. count가 실제 항목 수와 같아야 한다면 두 값의 관계가 불변식입니다. 락은 단지 한 변수에 표시하는 장식이 아니라 이 관계가 잠시 깨지는 갱신 구간을 다른 실행 주체가 관찰하지 못하게 하는 수단입니다. 어떤 상태를 지킬지 정의하지 않고 락부터 고르면 보호 범위를 놓치기 쉽습니다.

CPU가 하나여도 경쟁은 가능합니다. 한 task가 공유 상태를 바꾸는 도중 선점되어 다른 task가 같은 상태를 만질 수 있고, hardirq가 현재 코드를 중단시켜 접근할 수도 있습니다. 멀티코어에서는 동시에 실행되는 접근까지 추가됩니다. 경쟁을 이해하려면 CPU 수뿐 아니라 task·IRQ·softirq 등 모든 접근 문맥을 나열해야 합니다.

조회 함수가 데이터를 바꾸지 않는다고 해서 동기화가 불필요한 것은 아닙니다. 쓰기 중간 상태나 수명이 끝난 객체를 읽을 수 있기 때문입니다. 읽기 전용 경로가 정확히 어떤 일관성을 요구하는지, 오래된 스냅샷을 허용하는지, 여러 필드가 같은 시점이어야 하는지를 먼저 정합니다.

데이터 경쟁과 논리적 경쟁도 구분합니다. 각 변수의 접근을 atomic으로 바꾸더라도 여러 단계의 검사와 갱신 사이에서 조건이 달라질 수 있습니다. 재고를 읽고 충분하다고 판단한 뒤 감소시키는 동작이 예입니다. 필요한 것은 개별 접근의 원자성인지 전체 상태 전이의 원자성인지 구분해야 합니다.

02

worked example: 사라진 증가

공유 카운터가 0이고 CPU A와 B가 각각 한 번 증가시킨다고 생각합니다. 증가를 읽기·더하기·쓰기로 나누면 A가 0을 읽고 B도 0을 읽은 뒤 두 CPU가 모두 1을 쓸 수 있습니다. 최종값은 2여야 하지만 1이 됩니다. 각 CPU가 자신의 코드를 정상 실행했어도 전체 결과는 틀릴 수 있습니다.

atomic 증가 연산은 이 한 번의 read-modify-write를 원자적으로 연결해 두 증가가 사라지지 않도록 할 수 있습니다. 그러나 count와 별도의 리스트 포인터를 동시에 일관되게 바꾸는 요구까지 자동 해결하지는 않습니다. atomic 카운터가 맞아도 리스트 갱신과 공개 순서가 틀리면 소비자는 없는 항목을 기대할 수 있습니다.

락을 사용하면 필요한 상태 변경을 하나의 임계 구역으로 묶을 수 있습니다. A가 count와 리스트를 변경하는 동안 B가 같은 락을 얻기 전에는 그 중간 상태를 보지 않게 설계합니다. 중요한 전제는 모든 관련 접근 경로가 같은 보호 규칙을 지키는 것입니다. 한 곳만 락 없이 읽으면 보장은 깨집니다.

대화형 실험에서 겹쳐 실행된 증가 쌍의 수와 mutex 보호 여부를 바꿔 보세요. 경쟁은 빠르게 실행해야만 생기는 현상이 아니라 가능한 interleaving 중 잘못된 결과를 만드는 순서가 존재한다는 문제입니다. 현실에서 재현 빈도가 낮다고 안전한 코드라는 뜻은 아닙니다. 반복 테스트와 함께 허용되는 상태 전이를 논리적으로 확인해야 합니다.

03

spinlock과 기다리는 방식

비 PREEMPT_RT 구성의 일반적인 spinlock은 획득할 수 없으면 짧은 대기를 반복하는 락입니다. sleep할 수 없는 문맥의 짧은 임계 구역에 사용할 수 있지만 기다리는 동안 CPU 자원을 사용합니다. 임계 구역 안에서 블로킹 호출이나 긴 작업을 수행하면 다른 CPU의 대기까지 늘릴 수 있습니다.

spinlock이 선점을 막는 효과와 CPU 간 상호 배제는 다른 문제입니다. 자신의 CPU에서 task 전환을 막는 것만으로 다른 CPU의 접근은 막을 수 없습니다. 반대로 CPU 간 락을 잡았다고 같은 CPU의 IRQ가 같은 락을 획득하려는 상황까지 항상 안전해지는 것은 아닙니다. 필요한 경우 IRQ 상태 관리와 결합해야 합니다.

spin_lock_irqsave 계열은 기존 IRQ 상태를 저장하고 로컬 IRQ 제약을 함께 적용하는 용도로 사용합니다. 단순히 IRQ를 껐다가 무조건 켜는 코드보다 호출 당시의 상태를 복원하는 계약이 중요합니다. 다만 로컬 IRQ를 막는 것은 다른 CPU의 IRQ를 막는 것이 아니므로 락 자체의 공유 보호와 구분합니다.

PREEMPT_RT에서는 spinlock_t의 의미가 달라질 수 있고 raw_spinlock_t는 다른 역할을 가집니다. 최신 코드에서 락 이름을 읽을 때는 CONFIG_PREEMPT_RT와 문서의 문맥 규칙을 확인해야 합니다. 오래된 책의 spinlock 설명을 RT 빌드에 그대로 대입하지 않는 것이 이 강좌의 버전 기준입니다.

04

mutex와 sleep 가능한 문맥

mutex를 획득할 수 없을 때 대기자는 잠들어 CPU를 다른 작업에 줄 수 있습니다. 이것은 경합이 길 때 CPU를 낭비하지 않는 장점이 있지만 sleep 가능한 task 문맥이라는 전제가 필요합니다. hardirq에서 일반 mutex를 사용하면 안 되는 이유는 단순 성능 취향이 아니라 실행 문맥의 계약 때문입니다.

잠드는 락이라고 해서 획득과 깨우기의 비용이 없는 것은 아닙니다. 경합이 발생하면 대기 등록, 스케줄링, 깨우기와 다시 실행되기까지의 시간이 추가될 수 있습니다. 짧은 임계 구역에 무조건 spinlock, 긴 구역에 무조건 mutex라는 한 문장 규칙만으로는 충분하지 않고 실행 문맥을 먼저 확인해야 합니다.

mutex는 일반적으로 소유자가 해제하는 소유권 규칙을 가집니다. 자원 개수를 세는 semaphore나 이벤트 완료를 알리는 completion과 목적이 다릅니다. 락 해제와 이벤트 통지를 하나의 도구로 억지로 표현하기보다 공유 상태의 상호 배제와 조건 대기를 분리하는 편이 추론하기 쉽습니다.

락을 보유한 채 외부 작업 완료를 기다린다면 상대 작업이 그 락을 필요로 하는지 확인합니다. 비동기 작업 취소, 장치 제거, 사용자 메모리 접근 같은 경로는 예상보다 복잡한 대기를 만들 수 있습니다. 락의 획득 지점만 읽지 말고 임계 구역에서 호출하는 함수들의 sleep 가능성도 따라갑니다.

05

ABBA 교착을 상태로 보기

CPU A가 락 L1을 얻고 L2를 기다리는데 CPU B가 L2를 얻고 L1을 기다린다고 가정합니다. 각 락은 정상 동작하지만 두 작업 모두 상대가 가진 자원을 기다리는 순환이 생깁니다. 이것이 ABBA 형태의 교착입니다. CPU를 더 추가하거나 스케줄링을 빠르게 해도 순환 자체는 사라지지 않습니다.

예방 방법 중 하나는 여러 락을 획득하는 전역 순서를 정하고 모든 경로에서 지키는 것입니다. 객체가 동적으로 정해지는 경우에는 정렬 기준이나 특수한 획득 프로토콜이 필요할 수 있습니다. 단순히 코드 한 곳의 순서만 바꾸면 다른 오류 경로에서 순환이 다시 생길 수 있습니다.

trylock 실패 시 잠깐 기다렸다 다시 시도하는 코드는 교착을 피할 수 있어 보이지만 모두 같은 패턴으로 서로 양보하면 진행이 없는 livelock이 될 수 있습니다. 또한 한 작업만 계속 기회를 잃는 starvation 가능성도 있습니다. 안전성뿐 아니라 누군가 결국 진행하는지라는 liveness를 별도로 따집니다.

lockdep는 실행 중 관측된 락 의존성과 문맥 사용을 검사하는 중요한 도구입니다. 그러나 모든 가능한 실행을 자동 증명하는 것은 아닙니다. 해당 경로를 실제로 실행하지 않은 테스트에서 경고가 없다는 사실은 전체 동시성 설계가 안전하다는 증거가 되지 않습니다.

06

우선순위 역전과 보유 시간

높은 우선순위 작업 H가 낮은 우선순위 작업 L이 가진 락을 기다리는 상황을 생각합니다. 중간 우선순위 작업 M이 L의 실행을 계속 밀어내면 H도 오래 기다립니다. H 자체의 우선순위를 높였는데도 해결되지 않는 이유는 진행에 필요한 작업이 L이기 때문입니다.

우선순위 상속을 지원하는 락은 대기 관계에 따라 소유자의 실행 우선순위를 올리는 방식으로 이 문제를 줄일 수 있습니다. 그러나 모든 락이 이런 정책을 제공하는 것은 아니며 인터럽트 비활성 구간이나 다른 비선점 구간의 지연까지 자동 제거하지는 않습니다. 지원되는 메커니즘과 제한을 함께 확인합니다.

임계 구역의 평균 시간만 짧다고 충분하지 않습니다. 드물게 발생하는 긴 경로가 모든 대기자의 tail latency를 크게 늘릴 수 있습니다. 예외 처리, 메모리 할당, 페이지 폴트 가능 접근, 장치 응답 대기처럼 긴 경로가 락 안에 들어 있는지 봅니다.

최적화의 첫 선택이 락 구현 교체일 필요는 없습니다. 락 밖에서 준비할 수 있는 계산을 옮기고 공유 범위를 줄이며 데이터 소유권을 명확히 하는 것으로 더 큰 개선을 얻을 수 있습니다. 다만 밖으로 옮긴 계산이 이후 락 안에서 사용하는 상태와 여전히 일치하는지 재검사해야 합니다.

07

원자성·순서·수명은 별개

atomic은 지정된 연산의 원자성 및 API가 약속한 순서를 제공합니다. 모든 atomic 연산이 모든 메모리 접근에 대해 동일한 강한 barrier를 제공한다고 생각하면 안 됩니다. 필요한 게시·관찰 순서가 무엇인지 정하고 해당 API의 메모리 모델 계약을 읽어야 합니다.

참조 카운트가 양수였다는 관측만으로 그 뒤의 접근이 안전하다고 단정할 수 없습니다. 마지막 참조가 동시에 사라지는 경로에서 어떻게 안전하게 참조를 획득하는지가 중요합니다. 객체 포인터를 찾는 보호와 참조 수명을 유지하는 보호는 서로 다른 단계가 될 수 있습니다.

volatile은 컴파일러의 일부 접근 처리에 영향을 주지만 일반적인 락이나 원자 연산의 대체물이 아닙니다. 공유 자료구조에 volatile을 붙였다는 이유로 CPU 간 순서나 복합 갱신의 원자성이 생기지 않습니다. 커널에서는 READ_ONCE·WRITE_ONCE와 barrier 등도 각각 역할을 구분해 사용합니다.

RCU와 per-CPU 설계는 특정 조건에서 공유 경합을 줄일 수 있지만 아무 코드에나 락 대신 넣을 수 없습니다. 읽기 일관성 요구, 갱신 빈도, 수거 시점과 합산 비용이 달라집니다. 다음 장에서는 이러한 대안을 한 가지 도구의 우월성보다 요구 조건의 차이로 비교합니다.

08

진단 순서와 관측 한계

락 문제를 조사할 때는 먼저 누가 무엇을 기다리는지와 소유자가 무엇을 하는지 연결합니다. 대기자 스택만 읽으면 “mutex에서 멈춤”까지만 알 수 있습니다. 소유자의 긴 I/O나 다른 락 대기, 우선순위와 CPU 제한이 실제 원인일 수 있습니다.

경합 횟수, 대기 시간, 보유 시간은 다른 지표입니다. 짧은 경합이 자주 발생하는 락과 거의 경합하지 않지만 한 번에 오래 멈추는 락은 개선 방향이 다를 수 있습니다. 합계 시간뿐 아니라 분포와 중요한 요청 경로에서의 위치를 함께 봅니다.

디버그 설정과 tracing은 실행 비용과 타이밍에 영향을 줄 수 있습니다. 버그를 드러내는 데 도움을 줄 수도 있고 재현 빈도를 바꿀 수도 있습니다. 관측 환경을 기록하고 계측된 결과를 그대로 운영 환경의 절대 지연으로 주장하지 않습니다.

실습은 락 설정 변경이나 실제 커널 교착 유발 없이 현재 구성 정보를 확인합니다. 사용자가 커널 모듈로 실패를 재현하는 단계는 스냅샷이 있는 일회용 VM에서 진행해야 합니다. 정상 브라우저 시뮬레이션의 결과는 불변식 학습 근거이며 실제 커널 락 검증 결과가 아닙니다.

09

read-mostly 상태의 다른 선택

읽기가 많다면 reader-writer 계열 락을 고려할 수 있지만 독자가 많다는 이유만으로 무조건 유리하지는 않습니다. 읽기 락 획득도 공유 상태를 변경해 캐시 경합을 만들 수 있고, writer의 대기와 공정성 문제가 생길 수 있습니다. 읽기 경로의 길이와 빈도, writer가 기다릴 수 있는 시간을 함께 평가합니다.

seqcount 계열은 독자가 일관되지 않은 중간 상태를 감지하면 다시 읽는 방식에 관련됩니다. 짧은 스냅샷 읽기에 적합할 수 있지만 갱신자가 오래 진행하지 못하면 독자가 반복 재시도할 수 있습니다. 객체 포인터 수명과 writer 직렬화도 별도 요구이므로 락보다 항상 빠르고 안전한 대체물이라고 설명하지 않습니다.

전역 락을 여러 작은 락으로 나누면 병렬성이 늘 수 있지만 두 객체를 함께 변경하는 연산의 락 순서와 불변식이 복잡해집니다. 전체 합계를 항상 맞춰야 한다면 부분 락만으로 충분한지 다시 질문해야 합니다. 성능 개선이 요구된 일관성 수준을 몰래 낮추지 않도록 합니다.

동일 데이터의 단일 소유자를 두고 메시지나 작업 큐로 변경 요청을 보내는 설계도 가능합니다. 공유 쓰기 경쟁을 줄이는 대신 큐 지연과 소유자 처리 능력이 병목이 될 수 있습니다. 알고리즘의 선택은 상호 배제 비용을 어디에 둘지의 문제이지 어떤 도구 하나가 모든 비용을 없애는 문제가 아닙니다.

10

모델의 수치와 실제 C 코드

증가 모델은 두 실행 주체가 읽기·더하기·쓰기를 명시적으로 교차 실행하는 추상화입니다. 실제 C에서 락 없는 일반 정수의 데이터 경쟁은 언어 규칙상 정의되지 않은 동작일 수 있습니다. 따라서 모델의 최종값 범위를 실제 최적화된 C 프로그램이 반드시 따르는 결과 목록으로 해석하지 않습니다.

UI에서 충돌 횟수를 늘려 관찰하는 것은 전체 증가 연산을 보호해야 한다는 인과관계입니다. 실제 검증은 올바른 atomic 또는 mutex 계약을 사용하는 코드로 수행하고, compiler flag·CPU 배치·작업량을 기록해야 합니다. “내 PC에서는 언제나 맞았다”는 관측은 정의되지 않은 경로의 안전성을 증명하지 않습니다.

검증의 정답은 단순히 최종 카운터가 한 번 맞는지가 아니라 모든 필요한 상태 전이가 보호되고 종료까지 진행하는지입니다. 모델에서 mutex를 켜는 조작을 실제 코드의 모든 관련 접근 경로에 같은 보호 규칙을 적용하는 것으로 대응시켜 보세요. 빠진 읽기 경로가 하나 있으면 모델보다 약한 계약이 됩니다.
