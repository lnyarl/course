01

20.1 소켓은 프로세스와 네트워크 스택의 접점

소켓 fd는 프로그램이 네트워크 기능을 사용하는 핸들입니다. 커널의 socket과 프로토콜별 상태에는 주소, 연결 상태, 송수신 큐, 타이머가 포함됩니다. 사용자 프로세스가 recv를 호출하는 경로와 장치가 패킷을 수신하는 경로는 서로 다른 시점과 문맥에서 진행합니다.

TCP는 바이트 스트림을 제공합니다. 애플리케이션의 send 두 번이 상대의 recv 두 번과 대응하지 않습니다. 패킷은 분할되거나 합쳐져 처리될 수 있으며, 상대 애플리케이션이 읽는 단위도 다릅니다. 메시지 경계는 길이 필드나 구분자 같은 응용 프로토콜이 정해야 합니다.

send 성공은 보통 데이터가 로컬 송신 경로에 받아들여졌다는 뜻입니다. 상대가 받아 처리하고 디스크에 저장했다는 확인은 아닙니다. 네트워크 전송의 완료와 업무 처리 완료를 구분해야 재시도와 타임아웃을 올바르게 설계할 수 있습니다.

02

20.2 NIC에서 NAPI까지

NIC는 수신 버퍼에 DMA로 데이터를 넣고 수신 이벤트를 알립니다. 패킷마다 긴 인터럽트 처리를 하면 높은 패킷률에서 CPU가 통지 처리에 몰릴 수 있습니다. NAPI는 일정한 예산으로 여러 이벤트를 처리하는 경로를 제공해 배치 처리를 가능하게 합니다.

일반적인 경로에서 인터럽트가 NAPI 처리를 예약하고, poll이 수신 작업을 처리합니다. 예산을 다 쓰면 다음 처리 기회를 이어가고, 처리할 일이 끝나면 완료와 인터럽트 재활성화가 연결됩니다. 실제 드라이버와 설정에는 busy polling, threaded NAPI 같은 다른 실행 방식도 있습니다.

RX queue가 여러 개이면 RSS 등으로 흐름을 분산할 수 있습니다. 그러나 특정 연결 하나가 한 큐 또는 CPU에 집중될 수도 있습니다. 전체 CPU 평균이 낮아도 수신 경로의 특정 CPU가 포화되어 패킷 손실과 지연이 발생할 수 있습니다.

03

20.3 sk_buff와 프로토콜 처리

sk_buff는 패킷 데이터와 관련 메타데이터를 다루는 핵심 구조입니다. 데이터가 항상 구조체 뒤에 하나의 연속 버퍼로 붙어 있는 것은 아닙니다. 헤더 위치, fragment, 참조 공유를 표현하므로 패킷 처리에서 무조건 전체 복사가 일어난다고 가정하면 안 됩니다.

수신 데이터는 링크 계층, IP, TCP 처리와 필요한 정책 경로를 거쳐 해당 소켓에 연결됩니다. GRO는 여러 패킷을 더 큰 단위로 처리해 CPU 비용을 줄일 수 있습니다. 이 때문에 서로 다른 위치에서 관측한 패킷 수와 크기가 다를 수 있습니다.

TCP 수신 큐에 읽을 데이터가 생기면 잠든 작업을 깨우거나 epoll에 준비 상태를 알립니다. 작업이 깨어나도 곧바로 실행되는 것은 아닙니다. 네트워크 처리 이후의 CPU 대기와 애플리케이션 자체의 처리 속도까지 포함해야 요청 지연을 설명할 수 있습니다.

04

20.4 큐가 쌓인 위치를 찾는다

NIC ring에서 드롭이 늘면 장치 수신과 CPU 처리의 균형을 봅니다. softirq 처리량과 특정 CPU 사용률이 높으면 커널 수신 경로를 조사합니다. 소켓 Recv-Q가 지속해서 커지면 애플리케이션의 읽기 속도와 스케줄링 지연을 확인할 근거가 됩니다.

TCP의 흐름 제어는 수신자가 버퍼와 처리 능력을 반영해 송신을 제한하도록 돕습니다. 버퍼를 크게 만드는 것은 일시적인 버스트를 흡수할 수 있지만 지속적인 처리 능력 부족을 해결하지는 못합니다. 큰 큐는 더 오래된 요청을 보관하며 지연을 늘릴 수도 있습니다.

실습은 ss와 /proc/net/dev, /proc/softirqs를 함께 읽습니다. 누적 카운터는 일정 간격의 차이로 해석해야 합니다. 패킷 캡처에 재전송이 보여도 원인이 무조건 회선인 것은 아니므로 CPU, 큐, 상대 처리 상태를 함께 조사합니다.

05

20.5 작은 HTTP 응답 한 개의 두 방향 경로

서버가 1KiB 응답을 send했다고 합시다. 먼저 사용자 버퍼의 내용이 소켓 송신 경로에 받아들여지고 TCP는 전송할 바이트의 순서와 상태를 관리합니다. 혼잡 제어와 상대 수신 윈도, 현재 송신 버퍼 상태에 따라 실제 전송 시점이 달라집니다. send 반환 시각이 NIC에서 마지막 비트를 보낸 시각과 같다는 가정은 여기서 이미 틀립니다.

송신 데이터는 IP와 장치 송신 경로를 거쳐 NIC 큐로 전달됩니다. 장치 오프로딩이 활성화되면 커널이 큰 덩어리를 넘긴 뒤 NIC가 세그먼트를 나누거나 체크섬을 계산할 수 있습니다. 애플리케이션 바이트 수, 커널에서 보이는 패킷 크기, 선로 위 패킷 개수는 관측 위치와 offload 설정에 따라 다르게 보일 수 있으므로 패킷 캡처의 위치를 반드시 기록합니다.

상대 TCP가 ACK를 보내도 상대 프로그램이 응답을 읽고 업무 처리를 완료했다는 뜻은 아닙니다. ACK는 전송 계층의 수신 상태에 관한 신호입니다. 결제 승인이나 파일 저장 완료 같은 의미는 응용 프로토콜의 응답으로 확인해야 합니다. 이 구분은 타임아웃 후 재시도에서 중복 업무가 발생하는 원인을 이해할 때도 중요합니다.

06

20.6 수신 예산이 만드는 공정성과 지연의 절충

한 번의 NAPI poll에서 처리할 수 있는 수신 작업에는 예산이 있습니다. 예산 없이 계속 패킷을 처리하면 높은 트래픽에서 다른 작업이 CPU를 얻기 어려워질 수 있습니다. 반대로 예산이 너무 작으면 다시 예약하고 상태를 확인하는 비용이 커질 수 있습니다. 배치 처리는 호출 비용을 나누지만 특정 작업이 CPU를 오래 점유할 수 있다는 양면성을 가집니다.

교육용으로 poll당 최대 64개를 처리하고 150개가 대기 중이라고 합시다. 다른 조건을 생략하면 적어도 세 번의 처리 기회가 필요합니다. 첫 64개와 마지막 22개가 같은 지연을 가지지는 않습니다. 예산을 128로 늘리면 필요한 기회 수는 줄지만 한 번의 CPU 점유 시간은 늘 수 있습니다. 실제 Linux는 전체 softirq 예산과 시간, 드라이버 동작 등 추가 조건이 있으므로 이 숫자는 구조를 이해하는 모형입니다.

실제 분석에서는 NET_RX softirq의 증가와 CPU별 사용, ksoftirqd의 실행, 소켓 큐 변화를 같은 구간에서 봅니다. ksoftirqd가 보인다는 이유만으로 항상 비정상이라고 판정하지 않습니다. 어느 큐에서 대기가 증가했고 그 대기가 요청 지연에 어떻게 이어지는지 연결해야 설정 변경의 목적이 생깁니다. 설정을 한 번에 여러 개 바꾸면 효과를 어떤 변화에 귀속할 수 없게 됩니다.

07

20.7 하나의 흐름이 한 CPU를 바쁘게 할 수 있다

네 개의 수신 큐가 있는 NIC에서 네 개의 CPU가 사용된다고 해서 한 TCP 연결의 패킷이 네 CPU에 매번 균등 분배되는 것은 아닙니다. RSS는 일반적으로 흐름을 기준으로 큐를 선택해 순서와 캐시 지역성을 유지하려 합니다. 많은 작은 연결과 아주 큰 연결 하나는 같은 총 바이트 수여도 CPU 분산 양상이 다를 수 있습니다.

따라서 총 CPU 사용률이 25%이고 네 CPU 중 하나가 수신 처리를 거의 전담한다면 그 경로는 이미 한계에 가까울 수 있습니다. CPU를 더 추가해도 해당 흐름의 실행 위치가 그대로라면 문제가 해결되지 않습니다. 큐와 IRQ affinity, RSS 설정, 애플리케이션의 연결 수와 작업 분배를 함께 살펴야 실제로 병렬화할 수 있는 단위를 찾을 수 있습니다.

RPS·RFS 같은 소프트웨어 분산이나 XPS 같은 송신 선택은 다른 단계에서 CPU 지역성을 조정합니다. 이름을 외우는 것보다 분배가 일어나는 위치, 순서 유지 요구, CPU 간 이동 비용을 비교하세요. 분산을 늘려 CPU 하나의 부하는 줄었지만 캐시 miss와 교차 CPU 통지가 늘어 전체 지연이 악화될 가능성도 있습니다.

08

20.8 소켓 버퍼를 두 배로 하면 무엇이 달라지는가

애플리케이션이 초당 10MiB를 소비하고 상대가 지속적으로 12MiB를 보낸다고 가정합니다. 수신 측이 무제한으로 받아들인다면 큐는 초당 2MiB씩 커집니다. 버퍼를 4MiB에서 8MiB로 늘리면 가득 차는 시점을 늦출 뿐 소비 능력 자체는 바뀌지 않습니다. 실제 TCP는 흐름 제어로 상대를 제한하므로 이 계산은 압력이 생기는 방향을 보여주는 단순 모델입니다.

일시적인 버스트라면 더 큰 버퍼가 유용할 수 있습니다. 예를 들어 짧은 GC 정지 동안 들어온 데이터를 보관해 드롭이나 전송 지연을 줄일 수 있습니다. 반면 지속적 병목에서는 큐에 오래 머무는 바이트가 늘어 응답 지연이 커질 수 있습니다. 버퍼 크기 변경의 목적이 버스트 흡수인지 처리 능력 보완인지 먼저 구분해야 합니다.

Recv-Q는 애플리케이션이 아직 소비하지 않은 수신 상태를 조사하는 단서이고, Send-Q는 송신 측 미완료 상태를 조사하는 단서입니다. 값의 정확한 의미는 소켓 상태와 프로토콜에 따라 확인합니다. 큰 큐 하나를 보고 곧바로 상대가 느리다고 확정하지 말고 로컬 CPU 대기, 애플리케이션 락, 상대 윈도와 재전송을 함께 확인합니다.

09

20.9 sk_buff의 메타데이터와 실제 데이터는 다르다

sk_buff는 packet 자체라는 말로 요약되지만 실제로는 데이터의 위치와 소유 관계를 설명하는 구조입니다. head 영역과 선형 데이터, fragment 목록, 각 계층의 헤더 위치 등이 관련됩니다. 헤더를 앞에 추가하거나 제거할 때 매번 전체 payload를 이동하지 않도록 표현을 나누는 이유가 있습니다. 메모리 구조를 이해하면 네트워크 처리 비용이 어디에서 발생하는지 질문할 수 있습니다.

여러 경로가 같은 데이터를 참조하면 참조 수와 복사 시점의 규약이 중요해집니다. 객체를 복제했다고 데이터 전체가 복사되는지, 메타데이터만 새로 생기는지는 사용한 API에 따라 다릅니다. 드라이버나 프로토콜 코드를 읽을 때 free 함수 이름만 보고 장치 버퍼가 그 순간 모두 반환된다고 가정하지 않고 어느 참조가 마지막인지 확인합니다.

GRO는 수신 데이터를 더 큰 처리 단위로 합쳐 상위 스택의 반복 비용을 줄이고, GSO·TSO는 송신 분할 비용의 위치를 바꿀 수 있습니다. 같은 사용자 payload라도 커널 함수 호출 수와 패킷 캡처 모양이 달라질 수 있습니다. 성능 비교에서 offload 설정을 기록하지 않으면 코드 변경의 효과와 처리 단위 변경의 효과가 섞일 수 있습니다.

10

20.10 재전송은 현상이지 단일 원인이 아니다

TCP 재전송은 데이터가 기대한 방식으로 확인되지 않았다는 신호입니다. 실제 네트워크 손실, 수신 경로의 과부하, 장치 큐 드롭, 지연과 재정렬 등이 관련될 수 있습니다. 재전송이 늘었다는 사실만으로 회선 품질이 나빠졌다고 단정하면 로컬 CPU나 애플리케이션 정지를 놓칩니다.

조사 순서는 시간 구간과 연결을 고정하고 재전송 변화, 인터페이스 오류·드롭, CPU별 수신 처리, 소켓 큐를 함께 보는 것입니다. 필요할 때 양 끝의 패킷 캡처를 비교해 어느 구간에서 보이지 않게 됐는지 좁힙니다. 캡처 자체의 드롭과 offload 때문에 한 위치에서 보이지 않는 패킷을 실제 선로 손실로 잘못 읽지 않도록 수집 품질도 확인합니다.

애플리케이션 타임아웃과 TCP 재전송 타이머는 다른 계약입니다. 업무 타임아웃이 먼저 끝난 뒤에도 커널의 연결 상태나 전송 작업이 남을 수 있습니다. 취소와 소켓 종료, 재시도의 관계를 설계해야 중복 작업과 자원 누적을 피할 수 있습니다. 커널 네트워크를 공부하는 목적은 이런 응용 계층의 증상을 하위 상태와 연결하는 데 있습니다.

11

20.11 소스와 관측 사이의 연결점을 고른다

net/core/dev.c에서는 장치에서 올라온 작업이 네트워크 처리로 연결되는 경계를, net/ipv4/tcp_input.c에서는 TCP 수신 상태가 바뀌는 부분을 봅니다. 첫 읽기에서는 모든 분기를 따라가기보다 입력 객체, 소켓을 찾는 기준, 큐에 넣는 시점, 깨우는 조건을 표시합니다. 이 네 가지 질문만으로도 단순한 함수 이름 목록보다 유용한 실행 지도가 만들어집니다.

ss는 소켓 관점, /proc/net/dev는 인터페이스 관점, /proc/softirqs는 CPU의 처리 사건 관점을 제공합니다. 세 값의 단위가 모두 같지 않으므로 직접 더하거나 빼서 하나의 패킷 수를 만들지 않습니다. 각각의 변화를 통해 어느 경계에 더 상세한 tracepoint나 프로파일이 필요한지 결정합니다.

실습 결과가 예상과 다르면 먼저 트래픽이 실제로 해당 namespace와 인터페이스를 지나갔는지 확인하세요. loopback 통신은 물리 NIC의 DMA 경로를 거치지 않으므로 동일한 실험이 아닙니다. VM의 가상 네트워크도 호스트와 별도의 관측 범위를 만들며, 게스트의 신호만으로 호스트 NIC 상태를 확정하지 않습니다.

12

20.12 확인 과제: 큐를 늘릴 것인가 소비를 빠르게 할 것인가

교육용 서비스에서 Recv-Q가 계속 커지고 NIC 드롭은 늘지 않으며 애플리케이션 스레드가 긴 락 대기로 잠든다고 합시다. 이 증거는 장치 수신보다 애플리케이션의 소비 경로를 우선 조사하게 합니다. NIC ring을 크게 바꾸는 조치는 현재 관측된 대기를 직접 해결하지 못할 수 있습니다. 큐가 어디에 쌓였는지가 처방의 출발점입니다.

반대로 애플리케이션은 빠르게 읽는데 특정 CPU의 NET_RX 처리와 장치 드롭이 증가한다면 수신 분산과 드라이버·커널 처리 비용을 조사합니다. 같은 “네트워크 느림” 증상이라도 두 상황의 실행 주체와 대기 위치가 다릅니다. 인터랙티브 모델의 패킷 수와 poll 예산을 바꾸면서 남은 작업 수가 어떻게 달라지는지 보고, 그 모형에 포함되지 않은 소켓 소비 단계도 별도로 설명해 보세요.

최종 답에는 관측, 우선 가설, 추가로 필요한 증거를 나눠 적습니다. 소켓 큐 하나로 전체 경로의 원인을 확정하지 않되, 모든 계층을 한꺼번에 바꾸지도 않습니다. 현재 증거가 지목하는 경계에서 한 가지 조건을 시험하고 종단 지연과 처리량을 다시 확인하면 네트워크 커널 지식이 실제 진단 절차로 연결됩니다.
