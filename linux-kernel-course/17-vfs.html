01

17.1 파일을 열었다는 말의 세 가지 의미

프로그램이 받은 fd 3은 파일 자체가 아니라 프로세스의 파일 디스크립터 테이블을 가리키는 번호입니다. 다른 프로세스의 fd 3은 전혀 다른 대상을 가리킬 수 있습니다. 커널은 이 번호로 struct file을 찾고, 그 객체에 저장된 접근 모드와 현재 파일 위치를 사용합니다.

열린 파일 설명(open file description)은 한 번의 open에 대응하는 커널 상태입니다. 같은 파일을 두 번 open하면 일반적으로 서로 다른 struct file이 생깁니다. 반면 dup으로 복제한 fd는 같은 열린 파일 설명을 참조하므로 파일 위치와 일부 상태 플래그를 공유합니다.

inode는 파일의 메타데이터와 파일 시스템 내부 정체성을 나타냅니다. 파일 이름 자체를 저장하는 역할과는 구분합니다. 같은 inode를 가리키는 하드 링크가 여러 개 있어도 open의 방식에 따라 현재 읽기 위치는 공유될 수도, 따로 유지될 수도 있습니다.

02

17.2 경로 이름은 한 번에 디스크 주소가 되지 않는다

open("/var/log/app.log")는 루트에서 각 경로 요소를 탐색합니다. dentry는 이름과 부모 디렉터리, inode의 연결을 표현하는 메모리 객체입니다. 경로 탐색 결과가 캐시에 있으면 매번 디스크에서 디렉터리를 읽지 않아도 됩니다. 존재하지 않는 이름을 기억하는 negative dentry도 있습니다.

mount는 경로 트리에 다른 파일 시스템을 연결합니다. 같은 문자열 경로라도 mount namespace가 다르면 다른 파일을 가리킬 수 있습니다. 그래서 장애 조사에서 호스트의 경로만 보고 컨테이너 안에서 열린 파일을 판단하면 틀릴 수 있습니다.

파일을 unlink해도 열린 fd가 즉시 무효가 되는 것은 아닙니다. 디렉터리에서 이름을 제거하는 작업과 열린 참조를 해제하는 작업은 다릅니다. 로그를 지웠는데 디스크 공간이 돌아오지 않는다면, 프로세스가 삭제된 파일을 계속 열고 있는지 확인할 이유가 생깁니다.

03

17.3 VFS는 공통 규약을 실제 구현으로 연결한다

VFS는 read, write, lookup 같은 공통 동작과 파일 시스템 구현 사이를 연결합니다. 일반 파일, 파이프, 소켓이 모두 fd로 보인다고 해서 읽기 경로가 동일한 것은 아닙니다. struct file의 연산 테이블과 파일 종류가 실제 동작을 결정합니다.

일반 파일의 buffered read는 page cache에 있는 데이터를 사용할 수 있습니다. 캐시에 없다면 파일 시스템이 블록 위치를 찾고 I/O를 요청합니다. 따라서 read 호출을 관측한 횟수와 실제 디스크 읽기 요청 수가 같다는 가정은 성립하지 않습니다.

pread는 명시한 오프셋에서 읽고 공유 파일 위치를 바꾸지 않습니다. 여러 스레드가 같은 열린 파일을 사용하면서 각자 지정 위치를 읽어야 할 때 유용합니다. 이것은 파일 내용 변경에 대한 동기화까지 대신하는 기능은 아닙니다.

04

17.4 공유 관계로 결과를 예측한다

내용이 ABCDE인 파일을 열고 fd를 dup했다고 합시다. 첫 fd에서 두 바이트를 읽으면 AB가 나오고, 복제 fd에서 다음 두 바이트를 읽으면 CD가 나옵니다. 정수가 두 개여도 파일 위치를 보관한 객체는 하나이기 때문입니다.

같은 경로를 새로 open한 fd에서는 다시 AB를 읽습니다. 파일 내용과 inode가 같아도 열린 파일 설명은 독립적입니다. fork 후 부모와 자식이 상속한 fd도 열린 파일 설명을 공유할 수 있으므로 이 규칙이 프로세스 경계를 넘어 적용됩니다.

실제 조사에서는 /proc/PID/fd의 심볼릭 링크로 대상을 보고, /proc/PID/fdinfo에서 pos와 flags를 확인합니다. 숫자를 볼 때에는 해당 프로세스와 시점을 함께 기록하세요. 프로세스가 fd를 닫고 재사용하면 같은 번호가 곧 다른 파일을 뜻할 수 있습니다.

CHANGE ONE THING

05

17.5 네 번의 시스템 콜로 객체 그래프를 그린다

내용이 ABCDEFGH인 파일을 처음 open한 결과를 a=3이라고 하고, dup(a)의 결과를 b=4라고 합시다. 다시 같은 경로를 open해 c=5를 얻습니다. 사용자 공간에는 번호 세 개가 있지만 커널의 열린 파일 설명은 두 개입니다. a와 b는 객체 F1을, c는 F2를 가리킵니다. F1과 F2의 파일 위치는 모두 처음에는 0이며, 둘은 같은 inode I를 참조합니다.

a에서 두 바이트를 읽으면 AB를 반환하고 F1.pos가 2가 됩니다. 다음에 b에서 한 바이트를 읽으면 C를 반환하며 F1.pos는 3이 됩니다. 이때 c에서 두 바이트를 읽으면 AB입니다. F2.pos가 독립적이기 때문입니다. 공유되는 자원을 표현할 때 번호를 세는 것보다 화살표의 도착점을 세는 것이 중요한 이유입니다. 이 도식은 소켓 fd 전달과 fork 상속을 이해할 때도 재사용합니다.

이제 close(a)를 호출해도 b가 F1을 참조하므로 F1은 즉시 없어지지 않습니다. 하지만 a라는 번호 3은 빈 슬롯이 되어 다음 open에서 재사용될 수 있습니다. 오래 보관한 숫자 3으로 뒤늦게 read를 실행하면 원래 파일이 아닌 새 파일에 접근할 수 있습니다. 비동기 작업에서는 fd 번호뿐 아니라 그 번호를 소유하는 객체의 수명과 닫는 시점도 관리해야 합니다.

a = open(path, O_RDONLY);
b = dup(a);
c = open(path, O_RDONLY);
/* a와 b는 열린 파일 설명 공유, c는 독립 */
시점F1 위치F2 위치결과
open·dup·open 후00a,b → F1 / c → F2
read(a,2)20AB
read(b,1)30C
read(c,2)32AB
06

17.6 fork와 exec 사이에서 무엇을 상속하는가

fork는 자식에게 fd 테이블을 복제하지만 테이블의 모든 대상 파일을 다시 open하는 것은 아닙니다. 부모와 자식의 해당 항목은 같은 열린 파일 설명을 가리킬 수 있습니다. 따라서 부모가 read해 움직인 파일 위치가 자식의 다음 read에 영향을 줄 수 있습니다. 메모리 주소 공간이 COW로 분리된다는 설명만 기억하면 파일 위치도 독립적이라고 오해하기 쉽습니다.

execve는 현재 프로세스의 프로그램 이미지를 바꾸지만 기본적으로 열린 fd 모두를 자동으로 닫지는 않습니다. FD_CLOEXEC가 설정된 항목은 성공한 exec에서 닫힙니다. 여기서 FD_CLOEXEC는 fd별 플래그이고 O_NONBLOCK 같은 파일 상태 플래그는 열린 파일 설명에 속합니다. 어떤 플래그가 어느 객체에 붙는지 알아야 dup 뒤의 변경이 다른 사용자에게 영향을 주는지 예측할 수 있습니다.

여러 스레드가 있는 프로그램에서 open 후 별도 fcntl로 CLOEXEC를 설정하면 그 사이에 다른 스레드가 fork와 exec를 수행하는 경합이 생길 수 있습니다. O_CLOEXEC를 open 시점에 지정하는 인터페이스는 이 틈을 줄입니다. 문제의 본질은 플래그가 존재한다는 사실이 아니라 자원을 노출하는 순간부터 필요한 속성이 함께 설정되는가입니다.

int fd = open(path, O_RDONLY | O_CLOEXEC);
/* fd를 생성하는 동작과 close-on-exec 설정을 결합 */

07

17.7 이름 탐색에서 캐시와 정확성은 함께 움직인다

경로 /a/b/c를 찾을 때 각 요소의 dentry가 이미 캐시에 있으면 디렉터리 저장소를 반복해서 읽지 않아도 됩니다. 하지만 캐시 hit가 접근 검사를 생략한다는 뜻은 아닙니다. 경로 탐색은 현재 루트와 작업 디렉터리, mount 연결, 심볼릭 링크, 접근 자격을 함께 다룹니다. 캐시를 성능 기능으로만 보고 namespace와 권한을 별개로 떼어내면 경로 결과가 바뀌는 이유를 놓칩니다.

파일이 없다는 결과를 저장한 negative dentry는 실패가 반복되는 경로 탐색의 비용을 줄일 수 있습니다. 그렇다고 다른 작업이 새 파일을 생성한 뒤에도 영원히 없다고 답하는 것은 아닙니다. 파일 시스템과 VFS의 일관성 규칙이 캐시 상태를 갱신합니다. 네트워크 파일 시스템은 원격 서버와의 일관성 조건이 추가되므로 로컬 ext4의 직관을 그대로 적용하지 않습니다.

사용자 프로그램이 먼저 stat으로 검사한 뒤 open하면 두 호출 사이에 이름 연결이 바뀔 수 있습니다. 이것이 경로 기반 TOCTOU의 한 형태입니다. 이미 연 디렉터리 fd를 기준으로 openat 계열을 쓰면 기준 경로를 명확히 할 수 있고, openat2의 resolve 제약은 허용할 경로 탐색 범위를 더 구체화합니다. 보안 보장을 주장할 때에는 사용한 플래그와 symlink·mount 경계를 함께 검토합니다.

/* 먼저 열린 디렉터리를 기준으로 상대 경로를 해석 */
fd = openat(dirfd, "config", O_RDONLY | O_CLOEXEC);
08

17.8 파일 삭제와 공간 반환을 수명으로 해석한다

1GiB 로그 파일을 서비스가 열어 둔 상태에서 운영자가 unlink했다고 합시다. 디렉터리에서 이름이 사라졌으므로 ls에는 보이지 않지만 열린 파일 설명의 참조는 살아 있습니다. 서비스가 계속 쓸 수도 있고, 파일 시스템은 살아 있는 참조가 있는 데이터를 즉시 재사용할 수 없습니다. 이름 기준으로 합산한 du와 파일 시스템의 할당 상태를 보여주는 df가 다르게 보일 수 있는 사례입니다.

이 상황에서 같은 이름으로 새 파일을 만들면 새 inode에 연결될 수 있습니다. 서비스의 기존 fd는 자동으로 새 파일로 이동하지 않습니다. 로그 회전에서는 rename 뒤 서비스에 재열기를 요청하거나, 애플리케이션이 정한 회전 프로토콜을 사용합니다. 이름이 같아 보인다는 이유만으로 실행 중인 서비스가 새 파일을 쓰고 있다고 판단하지 않습니다.

관측할 때 /proc/PID/fd/N이 deleted를 표시하는지 확인하고, 프로세스의 재열기 동작과 열린 참조를 연결합니다. 강제로 프로세스를 종료하는 처방을 먼저 선택할 필요는 없습니다. 서비스가 제공하는 로그 재열기 기능, 파일 크기와 실제 디스크 점유, 다른 프로세스의 참조를 확인해 최소한의 조치로 수명을 정리하는 것이 목적입니다.

09

17.9 read 결과는 요청 크기와 같을 필요가 없다

read(fd, buf, 4096)는 최대 4096바이트를 요청합니다. 반환값이 1024면 그만큼의 유효 데이터만 처리해야 하며 남은 버퍼를 새 데이터로 간주하면 안 됩니다. 반환값 0은 그 읽기 대상과 상황에서 EOF를 뜻하고, 음수이면 errno를 확인합니다. 일반 파일과 파이프, 소켓은 짧은 읽기가 발생하는 조건이 다르므로 파일 전용 가정을 모든 fd에 적용하지 않습니다.

공유 파일 위치가 필요 없다면 pread가 위치 지정과 읽기를 하나의 인터페이스로 제공합니다. lseek 후 read를 별도 호출하면 다른 스레드가 그 사이 파일 위치를 바꿀 수 있습니다. pread는 공유 위치를 바꾸지 않는다는 차이가 있지만 다른 작성자가 파일 내용을 변경하는 문제까지 해결하지는 않습니다. 위치 원자성과 데이터 일관성은 서로 다른 동기화 질문입니다.

오류 처리에서도 재시도를 무조건 반복하지 않습니다. EINTR은 진행된 바이트 여부와 인터페이스 규약을 고려해야 하고, EAGAIN은 nonblocking 대상의 준비를 기다릴 근거입니다. 잘못된 fd인 EBADF를 재시도하는 것은 문제를 해결하지 않습니다. 실습에서 시스템 콜 반환값을 출력하는 이유는 정상 데이터만 보는 것보다 실제 커널 계약을 더 정확히 배우기 위해서입니다.

17.10 소스에서 읽을 세 지점과 검증 질문

첫 번째로 include/linux/fs.h에서 struct file의 f_pos, f_flags, f_inode와 f_op을 찾아 각 정보가 왜 그 객체에 있는지 생각합니다. inode와 파일 위치를 같은 구조에 두었다면 같은 파일을 독립적으로 읽는 두 open을 어떻게 표현해야 할까요? 현재 분리는 영속 대상의 정체성과 열린 사용 세션의 상태가 다른 수명을 갖기 때문에 필요합니다.

두 번째로 fs/read_write.c에서 사용자 read 진입점과 VFS 읽기 경로가 연산 테이블로 연결되는 부분을 봅니다. 함수 이름을 모두 외우기보다 fd 유효성 확인, 접근 모드 검사, 오프셋 처리, 대상 연산 호출, 반환값 전달이라는 책임을 따라갑니다. 아키텍처별 시스템 콜 진입 코드까지 한 번에 펼치지 않아도 이 경계를 이해할 수 있습니다.

세 번째로 /proc의 fdinfo를 읽는 실험과 소스의 상태를 연결합니다. dup 전후에 pos가 함께 움직이는지, 별도 open에서는 독립적인지 예측한 뒤 관찰하세요. 관측이 예상과 다르면 stdio의 사용자 공간 버퍼링, 다른 스레드의 접근, 파일 종류를 확인합니다. 라이브러리 버퍼를 커널 파일 위치와 혼동하지 않는 것이 소스 읽기와 실제 실험을 연결하는 마지막 단계입니다.

11

17.11 확인 과제: 로그를 다시 열었는지 어떻게 증명할까

서비스가 파일 X를 열고 운영 절차가 X를 X.old로 바꾼 뒤 새 X를 생성했다고 합시다. 서비스 로그에 “회전 완료”라는 문구가 있다는 것만으로 기존 fd가 새 파일을 가리킨다고 증명할 수 없습니다. 서비스가 실제로 close와 open을 수행했는지, /proc/PID/fd의 대상과 해당 inode가 어떻게 바뀌었는지 확인할 필요가 있습니다.

관측 전에는 기존 fd와 inode, 새 경로의 inode를 기록합니다. 회전 후에는 같은 fd 번호가 유지됐는지만 보지 말고 대상 객체가 바뀌었는지 비교합니다. close 후 open이 같은 번호를 재사용하면 숫자는 같아도 열린 파일 설명은 새 객체일 수 있습니다. 반대로 번호가 달라졌어도 dup으로 기존 객체를 다시 참조했다면 위치와 대상은 공유될 수 있습니다.

이 사례의 답은 “fd 번호가 달라졌다”가 아니라 “프로세스가 참조하는 열린 파일이 새 경로의 대상과 연결됐고 새 쓰기가 그 파일에 나타난다”입니다. 이름, 숫자 핸들, 열린 객체, 실제 데이터라는 네 층을 나누면 운영 현상을 커널 구조로 설명할 수 있습니다. 실습에서는 서비스 프로세스를 임의로 중단하지 않고 준비한 작은 사용자 프로그램에서 이 관계를 먼저 재현합니다.

  char x[3] = {0}, y[3] = {0};
