01

27.1 oops와 panic은 같은 단어가 아니다

oops는 커널에서 예외나 잘못된 상태를 감지하고 진단 정보를 출력하는 상황을 나타냅니다. 설정과 오류 문맥에 따라 해당 작업을 종료하고 일부 실행이 계속될 수 있지만 시스템이 안전한 상태라는 보장은 없습니다. panic은 더 이상 정상 실행을 계속하지 않는 경로입니다.

동일한 오류라도 panic_on_oops 같은 정책과 발생 문맥에 따라 최종 동작이 달라질 수 있습니다. 따라서 로그의 한 줄만 보고 시스템이 반드시 즉시 재부팅했다고 말하지 않습니다. 실제 재부팅 시각, boot ID, 수집 시스템의 로그 범위를 함께 확인합니다.

taint는 외부 모듈, 경고 등 진단에 영향을 줄 수 있는 이력을 표시하는 플래그입니다. taint가 있다는 사실 자체가 특정 모듈이 이번 오류의 원인이라는 증거는 아닙니다. 반대로 원인을 제거해도 플래그가 남을 수 있으므로 시점과 이력을 함께 기록합니다.

02

27.2 stack trace는 당시 실행 경로다

스택에는 오류 당시 실행한 함수 경로와 주소가 나타납니다. 가장 위의 함수는 문제가 드러난 곳이지 반드시 최초로 메모리를 손상시킨 곳은 아닙니다. 앞서 잘못 해제한 객체가 훨씬 뒤에 사용되면서 다른 함수에서 오류를 낼 수 있습니다.

심볼 해석에는 실행한 커널과 정확히 맞는 vmlinux, 디버그 정보, 모듈 파일이 필요합니다. 비슷한 버전의 소스를 대입해 같은 줄이라고 단정하면 잘못된 결론이 나올 수 있습니다. 최적화와 인라이닝, 주소 무작위화도 해석 조건에 포함됩니다.

로그에는 CPU, PID, Comm, 오류 주소, 접근 종류, call trace와 이전 경고가 함께 있습니다. 중간 줄만 잘라 공유하기보다 첫 오류부터 필요한 문맥을 보존하세요. 반복 오류는 최초 손상의 연쇄 결과일 수 있으므로 가장 이른 신호를 찾는 것이 중요합니다.

03

27.3 kdump는 분석할 메모리를 보존한다

kdump는 crash kernel을 위한 메모리를 미리 예약하고, 장애 시 별도 수집 커널로 전환해 이전 커널의 메모리 이미지를 저장하는 체계입니다. 장애 후에 설정을 켠다고 과거의 메모리가 생기는 것은 아닙니다. 사전 준비와 저장 공간, 수집 경로의 검증이 필요합니다.

vmcore는 작업·스택·객체 상태를 더 깊이 조사할 재료입니다. 정확한 심볼과 분석 도구를 함께 사용해 당시 상태를 해석합니다. 파일이 생성되었다는 사실과 완전하고 분석 가능한 dump가 확보되었다는 사실도 별도로 확인합니다.

이 장에서는 실제 panic을 발생시키지 않습니다. 읽기 전용 상태 확인과 교육용 오류 기록을 사용합니다. 강제 crash 시험은 별도의 일회용 VM, 복구 경로, 명시된 실험 목적을 준비한 고급 운영 절차로 분리합니다.

04

27.4 오류 종류에 맞는 검출기를 선택한다

KASAN은 out-of-bounds와 use-after-free 같은 메모리 오류를 발견하는 동적 검사 도구입니다. 지원 아키텍처와 모드에 따라 메모리·성능 비용과 검출 방식이 다릅니다. 모든 커널에서 기본으로 실행되는 무비용 검사라고 생각하면 안 됩니다.

lockdep은 관측된 락 사용과 의존 관계를 바탕으로 잘못된 락 순서 등의 문제를 찾습니다. 두 경로가 A→B와 B→A 순서로 잠금을 얻으면 실제 교착이 매번 발생하지 않아도 잠재적 순환 의존을 보고할 수 있습니다. 보고를 단순한 느린 락 통계와 혼동하지 않습니다.

교육용 사례에서 worker가 해제한 객체를 timer 콜백이 참조했다면, 오류 위치의 NULL 검사만 추가하는 것은 수명 규약을 해결하지 못할 수 있습니다. 타이머 취소와 참조 관리, 동기화의 순서를 검토해야 합니다. 수정 후에는 해당 경합을 재현하는 조건과 검사 도구로 다시 검증합니다.

CHANGE ONE THING

05

27.5 use-after-free를 사건 순서로 재구성한다

교육용 request 객체 R을 작업자 W가 생성하고 타이머 T가 나중에 상태를 확인하도록 등록했다고 합시다. 정상 수명은 R 생성, 필요한 참조 유지, 타이머 완료 또는 취소 확인, 마지막 참조 해제의 순서입니다. W가 오류 경로에서 R을 먼저 free하고 타이머가 뒤늦게 R을 읽으면 T의 콜백에서 문제가 드러납니다.

로그의 오류 위치가 timer_callback이라고 해서 타이머 함수의 해당 줄만 바꾸면 해결된다고 보장할 수 없습니다. R이 유효할 것으로 기대한 계약이 어디에서 깨졌는지 찾아야 합니다. NULL 검사도 해제된 포인터가 자동으로 NULL이 되지 않으므로 근본 해결이 아닐 수 있습니다. 할당·등록·취소·해제 경로를 하나의 상태 기계로 다시 그립니다.

KASAN 보고에 할당과 해제의 스택이 포함되면 현재 접근 스택과 비교해 세 시점을 연결할 수 있습니다. 다만 검출기 설정과 모드에 따라 제공되는 정보가 다를 수 있습니다. 실제 로그에 없는 스택을 가정해서 원인을 확정하지 않고, 누락된 수명 정보를 어떤 추적이나 재현으로 얻을지 정합니다.

06

27.6 오류가 먼저 일어난 CPU와 발견한 CPU

멀티코어에서 CPU 0이 공유 객체를 잘못 수정하고 CPU 3이 나중에 읽다가 오류를 낼 수 있습니다. panic 로그의 CPU 번호는 당시 오류를 감지한 실행 문맥을 나타낼 수 있으며 최초 손상 주체를 자동으로 가리키지 않습니다. 공유 객체의 쓰기 경로와 메모리 순서, 참조 관리까지 보아야 합니다.

반복되는 오류가 서로 다른 함수에서 나타나면 각각 독립적인 버그일 수도 있지만 공통 메모리 손상의 후속 증상일 수도 있습니다. 처음 경고가 언제 발생했는지, 같은 객체와 모듈이 관련되는지, 앞선 경고 이후 시스템이 계속 실행됐는지 확인합니다. 가장 마지막의 화려한 panic 메시지에만 집중하면 최초 신호를 놓칠 수 있습니다.

재현에서는 CPU 수와 부하, 타이밍이 영향을 줄 수 있습니다. 단일 CPU에서 사라진다고 버그가 고쳐진 것은 아니며, 로그를 추가해 재현률이 줄어도 수명 계약은 여전히 잘못됐을 수 있습니다. 실제 조건을 기록하고 가능한 한 검출 도구와 반복 가능한 동시 실행 순서를 통해 원인을 좁힙니다.

07

27.7 심볼 일치가 분석의 출발 조건이다

주소를 함수와 소스 줄로 바꾸려면 실제 실행된 바이너리와 디버그 정보가 맞아야 합니다. 같은 6.18 계열이라도 패치와 config, 컴파일러 최적화에 따라 함수 배치와 코드가 달라집니다. “비슷한 버전”의 vmlinux로 얻은 줄 번호를 확정 근거로 사용하지 않습니다. 배포 때부터 심볼과 build 식별자를 보존하는 이유입니다.

인라인 함수와 최적화 때문에 하나의 주소가 소스 수준에서 여러 호출 의미와 연결될 수 있습니다. 스택 언와인딩이 깨졌거나 메모리 자체가 손상되면 call trace 일부가 신뢰하기 어려울 수 있습니다. 분석 도구가 출력한 함수명을 무조건 완전한 실행 기록으로 받아들이지 않고 오류 문맥과 다른 증거로 교차 확인합니다.

모듈 오류에는 해당 모듈의 정확한 바이너리와 적재 정보도 필요합니다. 커널 본체의 심볼만으로 외부 모듈 내부를 모두 해석할 수 없습니다. 수집 목록에 kernel release, config, vmlinux, 모듈, 전체 로그, 재현 조건을 포함하면 분석을 시작한 뒤 필수 자료가 없다는 사실을 뒤늦게 발견하는 일을 줄일 수 있습니다.

08

27.8 kdump 준비와 수집 성공은 다른 단계다

crashkernel 메모리가 예약되었다는 것은 수집 커널이 사용할 공간이 있다는 조건입니다. crash kernel 이미지가 적재되었다는 것은 장애 시 전환할 대상이 준비되었다는 조건입니다. 실제 장애에서 그 커널이 부팅하고 저장 장치나 네트워크에 접근해 vmcore를 끝까지 기록하는 것은 또 다른 검증 단계입니다.

수집 경로에는 저장 공간 부족, 네트워크 부재, 장치 드라이버 지원, 암호화 볼륨 접근 같은 실패가 있을 수 있습니다. 따라서 운영 준비 검증은 의도된 일회용 또는 시험 환경에서 전체 경로를 확인해야 합니다. 기본 학습 실습에서 kexec_crash_loaded를 읽는 것만으로 이 전체 경로가 검증되었다고 주장하지 않습니다.

vmcore는 메모리 내용을 포함할 수 있으므로 분석 파일의 보관과 접근 범위도 실제 운영 절차에 맞게 정합니다. 공개 보고서에는 필요한 스택과 진단 정보만 선별하고 민감한 내용을 무심코 포함하지 않습니다. 이 장에서는 dump 생성이나 외부 전송을 자동으로 수행하지 않으며 필요한 관측의 의미를 설명하는 데 집중합니다.

09

27.9 KASAN과 lockdep의 성공 기준을 구분한다

KASAN이 use-after-free를 보고하면 검출된 접근의 크기와 주소, 객체 수명 정보를 따라갑니다. 보고가 없다는 사실은 실행한 경로와 검출 모드 안에서 오류가 발견되지 않았다는 뜻입니다. 실행하지 않은 경로나 검출 범위 밖의 문제까지 없다고 증명하지 않습니다. 테스트의 입력과 반복 횟수, 커널 config를 함께 기록해야 합니다.

lockdep은 실제로 관측된 락 순서를 바탕으로 의존 관계를 축적합니다. A를 가진 채 B를 획득하는 경로와 B를 가진 채 A를 획득하는 경로가 관측되면 잠재적 순환이 문제가 됩니다. 항상 같은 실행에서 실제 deadlock이 일어나야만 의미 있는 경고가 되는 것은 아닙니다. 보고된 클래스와 획득 스택이 실제 데이터 보호 규약과 일치하는지 검토합니다.

두 검사 도구는 서로 대체되지 않습니다. 메모리 수명 오류와 락 순서 오류가 동시에 관련될 수도 있지만 한 검사가 깨끗하다고 다른 종류의 오류가 사라지는 것은 아닙니다. 수정의 목표 불변식을 먼저 적고, 그 불변식을 깨뜨릴 수 있는 경로를 해당 도구와 기능 테스트로 검증합니다.

10

27.10 oops 이후의 시스템을 정상 기준으로 쓰지 않는다

oops 뒤에도 일부 프로세스가 실행될 수 있지만 커널의 락이나 객체 상태가 이미 손상되었을 수 있습니다. 이후에 나타난 성능 저하와 추가 오류를 모두 독립적인 정상 환경의 결과처럼 해석하지 않습니다. 최초 오류 전후를 구분하고 분석 자료를 수집한 뒤 환경을 깨끗하게 재현하는 절차가 필요합니다.

외부 모듈을 제거했어도 taint 상태는 남을 수 있습니다. 이력 플래그를 지워 깨끗한 결과처럼 만드는 것이 목적이 아닙니다. 원인 후보를 제외한 새 부팅 환경에서 같은 증상이 재현되는지 확인하면 외부 코드와의 관계를 더 정확히 조사할 수 있습니다. 단, 재현되지 않았다고 한 번의 실험만으로 무관함을 확정하지 않습니다.

보고서에는 오류 당시 작업, 최초 경고, 정확한 버전과 taint, 재현률, 증거 파일의 유무를 적습니다. “커널이 죽었다”는 요약보다 어떤 오류로 어떤 문맥에서 더 이상 진행하지 못했는지 전달합니다. 확인하지 못한 원인은 가능성으로 남기고, 근거 없는 특정 모듈 지목을 피합니다.

11

27.11 수정 후에는 원래 실패 조건으로 돌아간다

타이머 취소 순서를 고친 예제라면 타이머와 cleanup이 경합하는 원래 조건을 다시 실행해야 합니다. 단순히 정상적인 read 한 번이 성공했다는 결과로 수명 버그가 해결됐다고 판단하지 않습니다. 정상 종료, 초기화 실패, 반복 로드·제거, 사용 중 종료 같은 관련 경로를 불변식 중심으로 선택합니다.

검사 도구가 켜진 실행에서 오류가 사라지고 기능 결과도 맞는지 확인합니다. 이후 검사 비용이 없는 환경에서도 정상 동작과 자원 반환을 확인합니다. 디버그 환경과 일반 환경은 실행 타이밍이 다를 수 있으므로 한 환경의 성공을 모든 환경에 대한 무제한 보장으로 확대하지 않습니다.

최종 설명은 “어떤 객체가 언제까지 살아 있어야 했고, 기존 코드가 어느 순서에서 이를 어겼으며, 새 순서가 어떤 참조와 완료를 기다리는가”로 작성합니다. 함수에 NULL 검사를 넣었다는 변경 목록보다 이 설명이 원인과 해결을 정확히 전달합니다. 커널 디버깅은 마지막 스택을 읽는 기술에서 시작해 공유 상태의 수명을 증명하는 작업으로 이어집니다.

12

27.12 세 종류의 오류 증거에서 주장할 수 있는 범위를 고른다

실험의 첫 선택지는 커널 oops의 fault 스택입니다. 이 경우 잘못된 접근이 드러난 명령과 주소, 당시 실행 경로 같은 정보를 출발점으로 삼습니다. 일반 사용자 프로그램의 정상적인 demand paging fault를 뜻하는 선택지가 아닙니다. fault라는 단어만 보고 모든 페이지 준비를 커널 오류로 묶거나, 반대로 oops를 정상 페이지 준비라고 넘기지 않도록 문맥을 함께 읽습니다.

두 번째 선택지인 KASAN use-after-free 보고서에서는 탐지된 접근과 확보된 할당·해제 이력 사이의 관계를 더 볼 수 있습니다. 예를 들어 worker_cleanup의 해제 뒤 timer_callback의 접근이 나타났다면 객체의 수명을 넘긴 참조를 조사할 근거가 됩니다. 하지만 아직 모든 타이머 경로와 소유권 규칙을 확인한 것은 아닙니다. 보고서가 지목한 접근을 막는 임시 조건과 객체 수명 계약을 바로잡는 수정은 구분해야 합니다.

세 번째 선택지는 lockdep의 순환 잠금 경고입니다. 이것은 앞의 두 메모리 접근 오류와 질문이 다릅니다. A를 잡은 채 B를 잡는 경로와 B를 잡은 채 A를 잡는 경로가 관측되었다면 어떤 호출 문맥과 잠금 순서가 그 관계를 만드는지 확인합니다. 이 보고서만으로 지금 모든 CPU가 이미 교착 상태라고 단정하지 않습니다. 잠재적인 위험을 알려 주는 의존 관계와 실제 멈춤의 관측을 나누세요.

각 선택에서 결과 카드의 직접 증거와 다음 확인을 읽고 한 문장씩 다시 써 보세요. oops에서는 오류가 드러난 지점과 객체 생성 경로를, KASAN에서는 해제와 이후 접근의 관계를, lockdep에서는 서로 반대인 잠금 획득 경로를 연결하는 것이 과제입니다. 세 경우를 모두 커널 크래시라는 한 단어로 요약하면 다음에 어떤 소스와 실행 증거를 모을지 결정하기 어렵습니다.

이 장의 로그 문구와 함수 이름은 교육용으로 만든 것이며 실제 Linux 6.18 장애 기록이 아닙니다. 따라서 특정 드라이버의 알려진 버그나 재현된 취약점으로 인용하지 않습니다. 실제 조사에서는 정확한 release와 config, 모듈과 심볼, 최초 로그를 확보한 뒤 같은 분류를 적용합니다. 증거 유형에 맞춰 주장 범위를 제한하는 연습이 도구 이름을 외우는 것보다 중요한 학습 결과입니다.
