01

18.1 성공한 write 이후에도 남은 일이 있다

일반적인 buffered write는 사용자 버퍼의 내용을 커널 page cache로 옮기고 해당 folio를 dirty 상태로 만듭니다. 호출자가 성공을 받았어도 장치까지 데이터가 전달되었다고 결론낼 수 없습니다. 메모리의 최신 내용과 저장 장치의 내용이 일시적으로 다를 수 있습니다.

writeback은 dirty 데이터를 파일 시스템과 블록 계층을 통해 내려보냅니다. 커널은 메모리 압박과 dirty 비율, 시간 조건 등을 고려해 이를 수행합니다. 쓰기가 많아지면 작성자가 제한을 받거나 저장 장치의 처리 속도를 직접 기다릴 수 있으므로 처음 빠르던 write가 나중에 느려지는 현상이 생깁니다.

장치에 요청을 보냈다는 사실도 최종 영속성의 전부는 아닙니다. 장치 캐시와 전원 장애 처리, flush/FUA 지원이 함께 관련됩니다. fsync는 파일 데이터와 필요한 메타데이터의 저장을 요청하고 결과를 반환하지만, 실제 보장은 파일 시스템과 저장 장치가 자신의 계약을 지키는 것을 전제로 합니다.

02

18.2 ext4 저널은 애플리케이션 트랜잭션이 아니다

파일 생성이나 확장에는 데이터 블록뿐 아니라 inode, 디렉터리, 할당 정보도 바뀝니다. 일부 메타데이터만 기록된 채 전원이 꺼지면 파일 시스템 구조가 모순될 수 있습니다. 저널은 관련 변경을 복구 가능한 단위로 관리해 이런 구조적 불일치를 줄입니다.

ext4의 일반적인 data=ordered 모드는 모든 사용자 데이터를 저널에 복제하는 방식이 아닙니다. 데이터와 메타데이터의 쓰기 순서를 조정하며 주로 메타데이터를 저널링합니다. data=journal, writeback 모드와 보장·비용이 다르므로 실제 mount 옵션을 먼저 확인해야 합니다.

저널이 있다고 해서 두 파일에 걸친 은행 이체가 자동으로 원자적이지는 않습니다. 애플리케이션의 의미 단위는 파일 시스템 메타데이터 트랜잭션과 다릅니다. 데이터베이스의 WAL과 복구 절차가 필요한 이유를 이 경계에서 이해할 수 있습니다.

03

18.3 이름 교체의 원자성과 영속성을 분리한다

설정 파일을 제자리에서 잘라 쓰면 독자가 부분 내용을 볼 수 있습니다. 같은 파일 시스템의 임시 파일에 새 내용을 모두 기록한 뒤 rename하면 이름을 통해 보는 교체는 원자적으로 처리할 수 있습니다. 하지만 원자적인 이름 교체와 충돌 후에도 유지되는 교체는 같은 성질이 아닙니다.

일반적인 로컬 Linux 파일 시스템에서 내구성을 의도한 패턴은 임시 파일 작성, 그 파일의 fsync, rename, 부모 디렉터리의 fsync 순서입니다. 파일 fsync는 내용에 관한 약속을, 디렉터리 fsync는 이름 연결의 변경에 관한 약속을 강화합니다. 다른 디렉터리로 이동하는 경우에는 관련 디렉터리와 파일 시스템의 계약까지 검토해야 합니다.

각 시스템 콜의 오류를 확인해야 합니다. 저장 장치가 가득 찼거나 writeback 오류가 생겼는데 마지막 rename만 성공했다고 전체 작업이 성공한 것으로 처리하면 데이터 손실을 숨기게 됩니다. 파일 교체 API는 정상 경로보다 중간 실패와 재시도 시 남는 상태를 먼저 정리하는 편이 좋습니다.

04

18.4 관측으로 어디까지 말할 수 있는가

strace는 write, fsync, rename이 어떤 순서로 호출되었는지 보여줍니다. 이 관측으로 애플리케이션의 프로토콜을 검토할 수 있지만 실제 전원 장애 복구가 검증되었다고 말할 수는 없습니다. 장애 시험은 일회용 VM과 별도의 스토리지 모델을 갖춘 실험입니다.

실습에서는 임시 디렉터리에 파일을 만들고 각 호출의 반환값을 확인합니다. fsync 지연은 파일 크기 외에도 이전 dirty 데이터, 파일 시스템 저널, 장치 캐시 상태에 영향을 받습니다. 한 번의 작은 파일 실험으로 저장 장치의 일반 성능을 판단하지 마세요.

write를 매번 동기화하면 지연이 늘 수 있습니다. 여러 변경을 묶어 fsync하는 group commit은 내구성 경계를 유지하면서 비용을 나누는 방법입니다. 묶음 크기를 늘리면 처리량과 개별 요청 대기 시간 사이의 절충이 생깁니다.

05

18.5 세 번의 장애 시점을 비교한다

설정 파일의 이전 내용이 A이고 새 내용이 B라고 합시다. 첫 번째 장애는 write가 B를 page cache에 복사한 직후 발생합니다. 프로세스는 성공을 받았지만 저장 장치에는 아직 A가 남을 수 있습니다. 애플리케이션의 메모리에는 완료 표시가 있어도 재부팅 후 읽을 수 있는 내용과는 다른 시간축에 있다는 뜻입니다.

두 번째 장애는 임시 파일 B의 fsync가 끝났지만 rename 전에 발생합니다. B의 내용이 저장되었더라도 독자가 사용하는 기존 이름은 여전히 A를 가리킬 수 있습니다. 재시작 시 남은 임시 파일을 어떻게 처리할지는 애플리케이션의 복구 정책입니다. 파일 시스템은 어느 파일이 업무상 최신 버전인지 스스로 결정하지 않습니다.

세 번째 장애는 rename이 끝나고 디렉터리 동기화 전에 발생합니다. 실행 중인 독자는 새 이름 연결을 볼 수 있지만 충돌 후 어느 변경이 유지되는지는 해당 파일 시스템의 저장 보장과 상태에 달려 있습니다. 따라서 실행 중 가시성 검증과 재부팅 후 영속성 검증을 나누어야 합니다. 교육용 도식은 이 세 경계를 보여주며 실제 crash 결과를 모든 장치에 보편적으로 예언하지 않습니다.

장애 시점확인한 사실아직 별도인 질문
write 직후커널이 데이터를 받음장치에 저장되었는가
임시 파일 fsync 후임시 내용의 동기화 성공이름 교체가 완료됐는가
rename 후실행 중 이름 교체디렉터리 변경이 영속화됐는가
06

18.6 파일 데이터와 메타데이터가 함께 움직이는 이유

빈 파일에 처음 4KiB를 쓰는 작업은 사용자 데이터 4KiB만 바꾸지 않습니다. 파일 길이, 데이터 블록의 할당 정보, inode의 시간 정보 같은 메타데이터가 관련될 수 있습니다. 저장 장치가 일부 쓰기만 완료한 상태에서 중단되면 데이터 위치와 이를 가리키는 구조가 맞지 않을 위험이 있습니다. 저널은 이 구조 변경의 복구 단위를 다루는 장치입니다.

저널에 먼저 안전한 기록을 남긴 뒤 본래 위치로 변경을 반영하는 과정은 추가 쓰기를 만들 수 있습니다. 하지만 매번 모든 구조를 즉시 최종 위치에 동기화하는 것보다 순서와 복구를 관리하기 유리합니다. group commit과 지연 할당 등 여러 기법이 성능과 저장 보장의 절충을 만듭니다. 옵션 이름 하나로 전체 디스크 경로를 설명하려 하기보다 어떤 순서가 필요해졌는지 먼저 이해합니다.

파일 데이터가 저널에 포함되는지, 메타데이터와 데이터의 순서를 어떻게 보장하는지는 모드에 따라 달라집니다. ext4의 설명을 XFS나 네트워크 파일 시스템의 내부 구현으로 그대로 바꾸어 읽으면 안 됩니다. 공통으로 사용할 수 있는 애플리케이션 인터페이스와 각 파일 시스템의 구현 전략을 분리하면 새로운 파일 시스템을 배울 때도 같은 질문을 적용할 수 있습니다.

07

18.7 fsync와 fdatasync를 의미로 고른다

fsync는 파일 데이터와 관련 메타데이터를 저장하도록 요청합니다. fdatasync는 이후 데이터 검색에 필요하지 않은 일부 메타데이터 갱신을 생략할 수 있습니다. 예를 들어 단순한 시간 정보와 파일 길이 변경은 같은 범주가 아닙니다. 길이가 바뀌면 어느 바이트까지 데이터인지 읽는 데 필요하므로 데이터와 무관한 메타데이터라고 쉽게 제외할 수 없습니다.

이름으로 접근할 새 파일을 만들었다면 파일 fd에 대한 동기화만 생각해서는 부족합니다. 디렉터리의 이름 연결도 변경되었기 때문입니다. 기존 파일의 내용만 덮는 작업과 새 파일 생성·이름 교체는 필요한 저장 대상이 다릅니다. 인터페이스를 선택할 때 “더 빠른 동기화 함수”라는 순위보다 어떤 상태를 복구 후 보존해야 하는지 적는 편이 정확합니다.

close의 성공을 fsync의 대체물로 사용하지 않습니다. close는 열린 참조를 반환하는 동작이고 저장의 내구성 계약은 별도입니다. 또한 지연된 I/O 오류가 뒤늦게 보고될 수 있으므로 write, fsync, close의 결과를 각각 처리합니다. 오류 후 재시도에서 이미 닫혔을 수 있는 fd 번호를 다시 close하면 재사용된 다른 fd에 영향을 줄 수 있다는 Linux close 규약도 확인해야 합니다.

08

18.8 동기화 묶음의 비용을 숫자로 생각한다

교육용 모델에서 요청 하나의 데이터 준비가 0.1ms이고 저장 동기화가 2ms라고 가정합니다. 한 요청마다 순차적으로 fsync하면 배치 없는 한 작업자의 처리 간격은 대략 2.1ms입니다. 실제 장치 성능을 예측하는 숫자가 아니라 고정 동기화 비용이 작고 잦은 쓰기에서 큰 비중을 차지할 수 있다는 설명입니다.

요청 10개를 모아 한 번 동기화하면 데이터 준비 1ms와 동기화 2ms를 합쳐 약 3ms의 작업이 됩니다. 요청당 나눠 가진 비용은 줄어들지만 가장 먼저 도착한 요청은 묶음이 채워지기를 기다립니다. 처리량은 좋아져도 개별 요청 지연이나 최대 대기 시간이 나빠질 수 있으므로 타이머와 최대 배치 크기를 함께 정하는 이유가 생깁니다.

여러 요청에 성공을 돌려줄 시점은 반드시 해당 묶음의 내구성 경계 이후여야 합니다. 메모리에 넣자마자 성공을 알리고 나중에 fsync하면 다른 계약입니다. 둘 다 가능한 설계지만 같은 내구성을 가진 성능 비교가 아닙니다. 벤치마크 보고에서는 응답 시점, 동기화 빈도, 동시성, 데이터 크기를 함께 기록합니다.

모델준비 비용동기화 비용중요한 절충
1개마다 동기화0.1ms2ms/요청짧은 배치 대기, 큰 고정 비용
10개 묶음1ms2ms/묶음고정 비용 분담, 배치 대기 발생
09

18.9 쓰기 오류를 재현하지 않고도 설계할 수 있다

파일 교체 절차를 상태 기계로 적어 보세요. 임시 파일 없음, 임시 파일 작성 중, 내용 동기화 완료, 이름 교체 완료, 디렉터리 동기화 완료라는 상태가 있습니다. 각 단계에서 오류가 나면 기존 파일이 남는지, 임시 파일만 남는지, 새 파일이 이미 보이는지를 구분해야 합니다. 성공과 실패라는 두 값만으로 모든 복구 판단을 표현하기 어렵습니다.

저장 공간 부족은 write 시점뿐 아니라 지연된 할당과 writeback 시점에서 드러날 수 있습니다. 부분 쓰기도 가능하므로 전체 버퍼가 저장되었다는 전제로 바로 rename하면 안 됩니다. 실습 코드가 작은 고정 크기 write의 길이를 검사하는 이유도 여기에 있습니다. 운영용 구현에서는 반복 쓰기와 오류 전달, cleanup 범위를 더 세밀히 구성합니다.

복구 시 남은 임시 파일을 모두 지우는 정책도 주의가 필요합니다. 다른 실행의 파일일 수 있고, 이미 성공한 작업의 흔적일 수도 있습니다. 고유한 작업 식별자와 원자적인 이름 규약, 재시도 시 동작을 정의하면 재시작 가능한 절차가 됩니다. 이 장의 목적은 파일 시스템 원리를 외우는 데서 끝나지 않고 애플리케이션의 실패 상태를 설명하는 데 있습니다.

10

18.10 관측 계층별로 다른 증거를 확보한다

strace가 fsync의 반환을 보여주면 사용자 프로그램이 어떤 내구성 요청을 했는지 확인할 수 있습니다. 블록 tracepoint는 장치 요청의 제출과 완료를 보여줄 수 있습니다. 둘을 연결할 때 하나의 fsync가 이전 dirty 데이터나 메타데이터와 연관되어 여러 요청을 만들 수 있음을 고려해야 합니다. 시간상 가까운 요청 하나를 임의로 그 파일의 쓰기라고 단정하지 않습니다.

장치 flush 완료가 기록되어도 하드웨어가 실제 전원 장애에서 계약을 지키는지는 별도 계층의 검증입니다. 클라우드 블록 장치와 RAID 컨트롤러, 물리 SSD의 캐시 정책까지 포함되는 실제 시스템에서는 각 계층의 보장을 확인해야 합니다. 소프트웨어 로그의 성공을 근거로 검증하지 않은 장치 특성을 추가해 주장하지 않습니다.

소스에서는 fs/ext4/fsync.c가 파일 동기화 요청을 저널·데이터 상태와 연결하는 부분을 보고, mm/page-writeback.c에서는 쓰기 제한과 dirty 회계의 역할을 봅니다. 함수 전체를 외우는 대신 동기화를 요청하는 주체, 기다리는 완료 조건, 오류를 돌려주는 지점을 표시하면 애플리케이션의 write 지연 변화와 연결할 수 있습니다.

11

18.11 확인 과제: 성공 응답을 어느 지점에서 보낼까

파일 업로드 API가 “저장 완료”를 반환한다고 합시다. 요구사항이 프로세스 종료에도 보존인지, 호스트 전원 장애에도 보존인지, 다른 서버에서 즉시 읽을 수 있어야 하는지에 따라 필요한 계약이 달라집니다. write 성공만 확인하는 구현과 fsync까지 확인하는 구현을 같은 성공으로 부르면 성능과 신뢰성을 모두 잘못 비교하게 됩니다.

먼저 응답 전에 보장해야 할 상태를 문장으로 적습니다. 로컬 파일 교체라면 내용의 동기화와 이름 연결의 동기화, 각 호출 오류를 포함합니다. 복제 저장소라면 원격 복제의 확인 기준이 추가됩니다. 파일 시스템의 로컬 fsync는 원격 애플리케이션이 그 내용을 읽고 처리했다는 신호가 아니므로 계층별 완료를 분리합니다.

그다음 교육용 장애 표에서 각 단계 직후 프로세스가 종료됐을 때 남을 수 있는 상태와 복구 행동을 적습니다. 실제 장애를 발생시키지 않아도 이 표로 누락된 오류 처리와 잘못된 성공 시점을 찾을 수 있습니다. 최종 검증에서는 제공한 코드의 호출 순서, 파일 내용 확인, 요구한 장애 조건의 복구 시험을 서로 다른 증거로 기록합니다. 마지막 시험을 하지 않았다면 내구성이 실측 검증됐다고 말하지 않습니다.

Linux VM / Shell · C
cat > /tmp/durable.c <<'C'
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
int main(void) {
  char d[]="/tmp/kernel-durable-XXXXXX";
  if (!mkdtemp(d)) return 1;
  int dir=open(d,O_RDONLY|O_DIRECTORY); if(dir<0) return 1;
  int f=openat(dir,"new",O_WRONLY|O_CREAT|O_EXCL,0600);
  if(f<0) return 1;
  if(write(f,"version=2\n",10)!=10 || fsync(f)<0) return 1;
  if(close(f)<0 || renameat(dir,"new",dir,"config")<0) return 1;
  if(fsync(dir)<0) return 1;
  close(dir); printf("saved in %s/config\n",d); return 0;
}
C
cc -Wall -Wextra /tmp/durable.c -o /tmp/durable
strace -e trace=write,fsync,renameat /tmp/durable

예상 관측과 해석

파일 fsync → renameat → 디렉터리 fsync의 순서를 확인합니다. 성공 시 생성된 config 내용은 version=2입니다. 이것은 호출 순서 확인이며 전원 장애 시험은 아닙니다.

혼동하기 쉬운 점

  • 모든 ext4 mount가 같은 data 모드를 사용한다고 가정하지 않는다.
  • 호출 순서 확인을 실제 crash 복구 검증으로 보고하지 않는다.
