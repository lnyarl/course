01

커널이라는 경계

프로그램은 자신만의 주소 공간과 파일 디스크립터를 사용합니다. 다른 프로그램의 메모리나 디스크 장치를 마음대로 조작하지 못하도록 CPU의 보호 기능과 커널의 검사가 함께 작동합니다. 커널은 이 경계를 지키면서 제한된 물리 자원을 여러 실행 주체에게 배분합니다.

파일 읽기 하나에도 권한 검사, 파일 위치 해석, 캐시 조회, 장치 요청, 대기와 깨우기가 들어갈 수 있습니다. 이 과정이 하나의 read 인터페이스 뒤에 숨겨져 있으므로 응용 프로그램은 저장 장치 종류마다 완전히 다른 코드를 작성할 필요가 없습니다.

커널을 이해한다는 것은 함수 이름을 모두 외우는 일이 아닙니다. 요청을 받은 주체가 어떤 상태를 소유하고, 무엇을 기다리며, 누구에게 제어를 넘기는지 추적하는 일입니다. 이 강좌에서는 CPU 시간, 주소 공간, 파일, 패킷을 연결해 그 경계를 배웁니다.

02

Linux와 주변 프로그램

Linux는 커널의 이름입니다. 배포판에는 커널 외에도 libc, 셸, 서비스 관리자, 패키지 도구와 여러 응용 프로그램이 함께 들어 있습니다. 터미널에서 명령을 입력하는 것은 셸과 대화하는 것이며 커널에 직접 문자열 명령을 전달하는 것이 아닙니다.

libc는 응용 프로그램에 익숙한 함수들을 제공합니다. 일부 함수는 사용자 공간 계산만 하고, 일부는 시스템 콜로 커널 서비스를 요청합니다. printf는 형식 변환과 버퍼링을 사용자 공간에서 수행할 수 있으므로 printf 호출 횟수와 write 시스템 콜 횟수는 일치하지 않습니다.

systemd 같은 서비스 관리자는 사용자 공간에서 서비스를 시작하고 감시합니다. 커널이 첫 사용자 프로세스를 시작한 뒤 구체적인 서비스 구성을 맡기는 것입니다. 따라서 서비스 재시작 정책과 CPU 스케줄링 정책은 책임 계층이 다릅니다.

malloc도 이 구분을 연습하기 좋은 사례입니다. 작은 할당은 사용자 공간 할당자가 이미 확보한 영역에서 처리할 수 있으므로 malloc 호출마다 커널에 새 페이지를 요청하는 것은 아닙니다. 필요하면 brk나 mmap 같은 인터페이스로 주소 공간을 마련하고, 실제 페이지 준비는 접근 방식에 따라 다른 시점에 일어날 수 있습니다. 함수 호출, 가상 주소 확보, 물리 페이지 사용을 세 단계로 나누어 생각해 보세요.

03

큰 지도에서 실행 경로 찾기

프로세스 관리는 실행 단위와 수명을, 스케줄러는 다음 CPU 사용자를 다룹니다. 메모리 관리는 주소 변환과 물리 페이지의 배분·회수를 담당합니다. VFS는 서로 다른 파일 시스템을 공통 파일 인터페이스에 연결하고 네트워크 스택은 소켓과 장치를 잇습니다.

Linux는 핵심 서비스와 많은 드라이버가 커널 주소 공간에서 실행되는 모놀리식 구조입니다. 모듈은 기능을 선택적으로 넣고 빼는 수단이지, 모듈마다 별도의 메모리 보호 경계를 만드는 수단은 아닙니다. 한 드라이버의 잘못된 메모리 접근이 시스템 전체에 영향을 줄 수 있습니다.

모든 요청이 지도 전체를 통과하지는 않습니다. 캐시에 있는 파일은 장치 읽기를 생략할 수 있고, 사용자 공간에서 완료되는 계산은 시스템 콜이 필요하지 않습니다. 도식에서 생략되는 경로를 이해하면 왜 같은 API의 지연 시간이 달라지는지도 설명할 수 있습니다.

04

이 강좌의 버전 약속

설명과 소스 탐색의 기준은 Linux 6.18 LTS 계열입니다. 소스 링크의 v6.18은 재현 가능한 출발점을 고정한 태그이며, 실제 실습에서는 해당 LTS 계열의 유지보수 업데이트가 적용된 커널을 사용하고 uname -r 출력을 기록합니다.

배포판은 같은 버전 계열에도 보안 패치나 기능을 추가할 수 있고 빌드 설정도 다릅니다. 기능 문서가 존재한다는 이유만으로 현재 VM에 그 기능이 활성화되어 있다고 판단하지 않습니다. 버전, 아키텍처, 설정, 권한을 구분해 확인합니다.

브라우저의 실험은 인과관계를 보여 주는 개념 모델입니다. 애니메이션의 한 단계는 실제 CPU의 한 사이클이 아니며 표시된 가상 시간은 벤치마크가 아닙니다. 실제 Linux 명령의 관측 결과와 모델의 예측을 비교하면서 모델이 생략한 조건을 찾습니다.

05

사례: 파일 한 개를 화면에 출력하면 누가 일할까

터미널에서 cat notes.txt를 실행한다고 합시다. 처음 입력한 글자는 셸이 읽습니다. 셸은 명령의 이름과 인자를 해석하고 실행할 프로그램을 찾습니다. 사용자 공간의 명령 해석 결과가 프로세스 생성과 실행 요청으로 이어지는 것입니다. 커널이 cat이라는 영어 단어의 뜻을 이해해서 직접 파일을 출력하는 구조가 아닙니다. 셸 기능인 파이프와 파일 이름 확장도 이 구분 위에 놓입니다.

cat이 실행된 뒤에는 notes.txt라는 경로를 열어 달라고 요청합니다. 커널은 현재 작업 디렉터리와 마운트 구성을 출발점으로 이름을 해석하고, 접근할 권한과 파일의 종류를 확인합니다. 성공하면 파일 디스크립터라는 작은 정수를 돌려줍니다. 이 숫자는 디스크의 물리 주소가 아니라 현재 프로세스의 열린 자원 목록을 찾기 위한 식별자입니다. 같은 숫자 3이 다른 프로세스에서는 전혀 다른 파일을 가리킬 수 있습니다.

이어서 read는 파일 내용을 사용자 버퍼로 가져오도록 요청합니다. 필요한 데이터가 page cache에 이미 있으면 저장 장치까지 내려갈 필요가 없을 수 있습니다. 캐시에 없다면 파일 시스템과 블록 계층을 거쳐 장치 요청이 만들어지고, 데이터가 준비될 때까지 cat이 잠들 수 있습니다. 잠든 동안 CPU는 다른 작업을 실행합니다. 파일 읽기의 벽시계 시간에는 실제 CPU 계산뿐 아니라 이런 대기 구간도 들어갑니다.

마지막으로 cat은 읽은 바이트를 표준 출력에 씁니다. 표준 출력이 터미널이면 터미널 경로로, 다른 파일로 리다이렉션되었다면 해당 파일 경로로, 파이프라면 파이프 버퍼로 전달됩니다. 애플리케이션은 같은 write 호출을 사용하지만 커널 내부의 최종 대상은 달라집니다. 공통 인터페이스는 호출 형태를 통일하는 것이지, 모든 대상의 동작 비용과 완료 의미까지 같게 만드는 것은 아닙니다.

이 사례에서 기억할 질문은 네 가지입니다. 지금 실행 중인 주체는 셸인가 cat인가 커널 코드인가, 데이터는 사용자 버퍼·캐시·장치 중 어디에 있는가, 어느 객체가 열린 파일의 위치를 보관하는가, 지금 CPU에서 계산하는가 아니면 무엇을 기다리는가입니다. 다음 장부터 등장하는 task_struct, 주소 공간, VFS, 대기 큐는 이 질문에 답하기 위한 구체적인 자료구조입니다.

06

CPU·메모리·장치가 서로 다른 자원인 이유

CPU는 실행 시간을 나누어 줄 수 있는 자원입니다. 한 CPU 코어가 한 순간에 실행할 수 있는 작업에는 한계가 있으므로 여러 runnable task가 경쟁하면 순서를 정해야 합니다. 메모리는 동시에 여러 작업이 점유하는 공간입니다. CPU를 잠깐 양보했다고 그 작업의 메모리가 자동으로 반환되지는 않습니다. 따라서 CPU 사용률이 낮은 서버도 메모리 부족을 겪을 수 있으며, 두 문제는 별도의 관측이 필요합니다.

저장 장치와 네트워크는 요청을 받는 속도와 완료하는 속도가 다를 수 있습니다. 애플리케이션이 데이터를 빠르게 제출하면 커널이나 장치의 큐에 요청이 쌓입니다. 큐는 짧은 부하 변동을 흡수하지만 무한하지 않고, 오래 쌓이면 지연과 메모리 사용이 커집니다. CPU를 더 많이 주는 변화가 저장 장치의 처리 폭을 늘리지 못한다면, 요청 제출만 빨라져 대기열이 더 길어질 수도 있습니다.

커널은 자원마다 다른 방식으로 가상화를 제공합니다. 프로세스는 자신만의 연속적인 가상 주소 공간을 보지만 실제 페이지는 여러 물리 위치에 배치될 수 있습니다. 파일은 바이트의 연속처럼 보이지만 실제 저장 공간은 여러 블록에 나뉠 수 있습니다. 이러한 추상화는 프로그램을 단순하게 만들면서 내부 배치와 공유 정책을 바꿀 여지를 줍니다. 그 대가로 주소 변환·메타데이터·일관성 관리가 필요합니다.

격리는 모든 자원을 완전히 독립시킨다는 뜻은 아닙니다. 두 프로세스는 서로의 주소를 직접 읽지 못해도 같은 CPU 캐시, 물리 메모리, 디스크 대역폭을 경쟁할 수 있습니다. 그래서 보안상 메모리 접근이 격리되어 있어도 성능 간섭은 남을 수 있습니다. 컨테이너의 namespace와 cgroup을 배울 때도 보이는 이름의 범위, 사용량의 제한, 실제 하드웨어 경쟁을 분리해서 생각해야 합니다.

서버가 느리다는 보고를 받으면 자원 하나의 숫자를 보고 결론 내리지 않습니다. CPU에서 실행하느라 시간이 긴지, 실행 가능하지만 차례를 못 받는지, 메모리 회수나 장치 완료를 기다리는지 먼저 나눕니다. 같은 1초 응답이라도 1초 동안 CPU를 계산한 요청과 5밀리초 계산한 뒤 대부분 기다린 요청은 개선 방향이 다릅니다. 이 구분이 커널 학습과 운영 진단을 연결합니다.

조작 실험: 64개의 쓰기를 묶으면 무엇이 줄까

이 장의 실험에서는 크기가 같은 레코드 64개를 모두 전달한다고 가정합니다. 한 번의 write에 레코드 하나를 넣으면 호출이 64번 필요합니다. 16개씩 모으면 4번이면 됩니다. 각 호출이 정상적으로 진입하고 복귀한다는 단순 모델에서 사용자·커널 경계 통과는 각각 128번과 8번입니다. 레코드의 내용과 총량을 바꾸지 않고 호출 단위만 바꿨다는 점을 먼저 확인하세요.

배치 크기 슬라이더를 1에서 16으로 옮기면 그래프의 진입과 복귀 횟수가 함께 줄어듭니다. 이것은 계산식으로부터 얻은 개념 결과이며 Linux 6.18에서 측정한 시간은 아닙니다. 실제 시간은 인자 검사, 사용자 데이터 접근, 파일 시스템 처리, 장치 대기 같은 여러 구간의 합입니다. 호출 횟수를 16분의 1로 만들었다고 전체 시간이 반드시 16분의 1이 되지는 않습니다.

배치에는 비용도 있습니다. 16개가 모일 때까지 첫 번째 레코드를 보관해야 한다면 그 레코드의 전송 시작이 늦어집니다. 임시 버퍼를 유지할 메모리도 필요하고, 종료 전에 버퍼를 내보내지 못하면 애플리케이션 수준의 유실이 생길 수 있습니다. 처리량을 높이는 설계와 개별 레코드의 지연을 낮추는 설계는 같은 목표가 아닐 수 있으므로 두 지표를 함께 봐야 합니다.

libc의 표준 입출력 버퍼는 이런 묶음 처리를 구현하는 한 사례입니다. printf는 문자열 형식을 만들고 사용자 공간 버퍼에 추가한 뒤 조건이 맞을 때 write를 호출할 수 있습니다. 따라서 소스 코드에서 printf를 세는 방식으로 커널 호출 수를 세면 틀릴 수 있습니다. 출력 대상이 터미널인지 파일인지, 버퍼링 설정과 개행·flush 시점이 무엇인지에 따라 실제 호출 패턴이 달라집니다.

현실의 write는 요청한 바이트 전부를 한 번에 처리하지 못하거나 시그널과 오류의 영향을 받을 수도 있습니다. 이 실험은 그러한 분기를 제외해 호출 단위의 효과만 드러냅니다. 모델을 읽을 때는 먼저 고정한 조건을 찾고, 실제 프로그램을 관측할 때는 그 조건이 성립하는지 확인하세요. 이 습관이 단순한 그래프를 실제 운영의 성능 보장으로 오해하는 일을 막습니다.

08

왜 사용자 API는 오래 유지하고 내부 구현은 바꿀까

응용 프로그램은 read 같은 사용자 인터페이스의 계약에 의존합니다. 커널 내부 함수 이름이나 자료구조 배치에 직접 의존하는 것보다 안정적인 경계입니다. 커널이 스케줄러 알고리즘이나 파일 캐시의 내부 표현을 개선해도 프로그램은 같은 인터페이스를 사용할 수 있어야 합니다. 내부를 바꿀 자유를 얻기 위해 외부에서 보이는 의미를 조심스럽게 유지하는 것입니다.

이 차이는 오래된 책을 읽을 때 특히 중요합니다. 프로세스를 보호하고 자원을 배분한다는 목적은 오래 유지되지만, 그 목적을 달성하는 자료구조와 알고리즘은 변합니다. 예전 스케줄러의 특정 트리를 현재 커널의 전체 스케줄러라고 설명하거나, 과거 메모리 할당자를 지금도 기본이라고 단정하면 잘못된 지도를 만들게 됩니다. 책의 원리 설명과 현재 소스의 구현 증거는 서로 다른 역할을 합니다.

Linux의 모듈도 안정된 사용자 API와 같은 계약이라고 생각하면 안 됩니다. 외부 모듈은 사용한 내부 API와 빌드 환경, 설정과 버전에 영향을 받습니다. 사용자 프로그램의 시스템 콜 호환성이 유지된다는 설명에서 임의의 옛 드라이버 바이너리도 새 커널에 그대로 로드된다는 결론은 나오지 않습니다. 모듈 실습에서는 실행 중인 커널에 맞는 빌드 트리와 설정을 확인합니다.

이 강좌에서는 원리, v6.18 소스에서 읽을 구현, 실제 VM에서 보이는 결과를 나누어 제시합니다. 원리는 왜 그런 장치가 필요한지 설명하고, 소스는 해당 버전에서 어떻게 구현했는지 보여 주며, 실습은 현재 구성에서 그 경로가 관측되는지 확인합니다. 세 층이 어긋나면 어느 하나를 무조건 버리기보다 버전 차이, 설정 차이, 측정 범위를 순서대로 조사합니다.

첫 학습에서는 모든 코드 경로를 끝까지 읽을 필요가 없습니다. read가 어떤 파일 객체를 받고 누가 버퍼를 소유하는지처럼 한 질문을 정하고 필요한 경계까지만 내려가세요. 이후 메모리와 동기화를 배운 뒤 같은 코드를 다시 보면 참조 카운트, fault 가능성, 락 범위가 새롭게 보입니다. 커널을 한 번에 암기하려는 방식보다 구체적인 동작을 반복해서 연결하는 방식이 전체 구조를 이해하는 데 도움이 됩니다.
